Tries and segment trees

Also called a prefix tree (trie) and an interval or range tree (segment tree). Two trees that answer "what lives under here?" in one walk from the root: a trie groups strings by prefix, a segment tree groups array cells by range. The source guide lists Word Search, Palindrome Pairs and kth Smallest in Lexicographical Order under Trees, all with empty bodies, so this card is supplemented.

Prime · 2 minutes before you read

The problem: Searching a board for 465 words one at a time repeats the same DFS over and over; ranking numbers in dictionary order by sorting all n is O(n log n); range min with updates can't use a Fenwick tree because min has no inverse.

Where it fits: Follows the Fenwick card. Both trees here answer what lives under this node? in one walk from the root: a trie groups strings by prefix, a segment tree groups array cells by range. The DFS on the board is the traversal card's walk plus backtracking.

Builds on: Fenwick tree (binary indexed tree) · Binary tree traversals

You'll meet: trie nodes as prefixes, end marks for words pruning a board DFS at the first dead prefix counting an implicit 10-ary trie without building it segment tree nodes as ranges, split at mid lazy tags for range updates

By the end: Use a trie to prune a many-word search, find the k-th number in dictionary order by counting subtrees, and answer range queries with point updates in O(log n) with a segment tree.

In one breath

A trie stores each word as a path of letters, so every word that starts with "oa" sits under one node and a dead prefix can be abandoned after one lookup. A segment tree stores the sum of each half, quarter and eighth of an array, so any range sum is a handful of stored pieces and any update rewrites one node per level.

2 · K-th lexicographical number: count the implicit trie

3 · Segment tree: range sum with point update

fully inside [1,4]: take its sumoverlaps: splitdisjoint: 0never visited
a = [5, 2, 9, 1, 5, 6] node [lo,hi] stores a[lo] + … + a[hi] query a[1..4] = [1,1] + [2,2] + [3,4] = 2 + 9 + 6 = 17 (9 calls, 3 sums kept) update a[3] = 4 : delta +3 up one path [3,3] 1→4 · [3,4] 6→9 · [3,5] 12→15 · [0,5] 28→31 (4 nodes) query a[1..4] = 2 + 9 + 9 = 20

The course array. The tree splits each range at mid = (lo + hi) // 2, so it is balanced to within one level. Every number above is printed by the code file.

Range updates, lazily. To add 3 to every cell of a[1..4], don't walk to all four leaves. Stop at the same nodes a query would keep, [1,1], [2,2] and [3,4], add 3 × (their length) to each sum (2→5, 9→12, 6→12) and leave a "+3 pending" tag on [3,4]. Parents are recomputed on the way back up (root 28→40 = 5 + 5 + 12 + 4 + 8 + 6). The tag is pushed to [3,3] and [4,4] only when a later call needs to go inside [3,4], so range update and range query both stay O(log n).

In Python

class Trie:
    def __init__(self):
        self.root = {}               # node = dict: char -> child node

    def insert(self, word):
        node = self.root
        for ch in word:
            node = node.setdefault(ch, {})
        node["$"] = word             # "$" marks the end of a word

# inside find_words(board, words): one DFS per start cell
def dfs(r, c, node):
    ch = board[r][c]
    if ch not in node:
        return                   # no word has this prefix: prune
    nxt = node[ch]
    if "$" in nxt:
        found.append(nxt.pop("$"))   # pop: report each word once
    board[r][c] = "#"            # mark: used on this path
    for i, j in neighbours(r, c):
        if board[i][j] != "#":
            dfs(i, j, nxt)
    board[r][c] = ch

def steps(prefix, n):          # size of prefix's subtree in 1..n
    total, lo, hi = 0, prefix, prefix + 1
    while lo <= n:
        total += min(n + 1, hi) - lo
        lo, hi = lo * 10, hi * 10
    return total

def kth_lex(n, k):
    cur, k = 1, k - 1
    while k > 0:
        s = steps(cur, n)
        if s <= k:
            cur, k = cur + 1, k - s    # skip the whole subtree
        else:
            cur, k = cur * 10, k - 1   # step down one level
    return cur

print(kth_lex(13, 2), kth_lex(13, 7))  # → 10 3
class SegTree:                   # node i has children 2i, 2i+1
    def query(self, l, r, i=1, lo=0, hi=None):
        hi = self.n - 1 if hi is None else hi
        if r < lo or hi < l:
            return 0                 # disjoint
        if l <= lo and hi <= r:
            return self.t[i]         # fully inside: stored sum
        mid = (lo + hi) // 2
        return (self.query(l, r, 2 * i, lo, mid)
                + self.query(l, r, 2 * i + 1, mid + 1, hi))

    def update(self, pos, val, i=1, lo=0, hi=None):
        hi = self.n - 1 if hi is None else hi
        if lo == hi:
            self.t[i] = val
            return
        mid = (lo + hi) // 2
        if pos <= mid:
            self.update(pos, val, 2 * i, lo, mid)
        else:
            self.update(pos, val, 2 * i + 1, mid + 1, hi)
        self.t[i] = self.t[2 * i] + self.t[2 * i + 1]

st = SegTree([5, 2, 9, 1, 5, 6])
print(st.query(1, 4)); st.update(3, 4); print(st.query(1, 4))
# → 17
# → 20

Trie: Time O(L) per insert or lookup · Space O(total letters). Each letter of a word is one dict step, whatever the number of words stored; nodes are shared only where prefixes are.

K-th lexicographical: Time O((log n)²) · Space O(1). Each steps call walks about log₁₀ n levels, and the walk makes at most 10 skips plus one step down per digit of the answer, so it never touches the n numbers themselves.

Segment tree: Time O(log n) per query or update, O(n) to build · Space O(n) (4n array here). The height is ⌈log₂ n⌉; an update rewrites one node per level, and a query keeps at most two nodes per level.

Why a segment tree beats the alternatives (range sums with updates, n = 10⁶)

✗ Plain array

Update is one write, but a range sum reads every cell in it: up to 10⁶ additions per query.

✗ Prefix sums

A query is two lookups, P[r+1] − P[l]. But one update shifts every later prefix: up to 10⁶ writes.

✗ √n blocks

1,000 blocks of 1,000 with a stored sum each. A query adds ≤ 998 block sums plus ≤ 2 × 999 loose cells: about 3,000 steps.

✓ Segment tree

Height ⌈log₂ 10⁶⌉ = 20. An update rewrites ≤ 21 nodes on one path; a query keeps ≤ 2 nodes per level. Works for min, max or gcd too.

Is it always the tool?

Segment tree: no. With no updates, a prefix-sum array answers in O(1). For sums with point updates, a Fenwick tree gives the same O(log n) in n + 1 cells and a few lines; reach for the segment tree when the operation can't be undone by subtraction (range min or max), or when you need lazy range updates.

Trie: if you only ask "is this exact word in the set?", a Python set is simpler and smaller, since every trie node here is its own dict (our inference, not measured). The trie pays off when the question is about prefixes: autocomplete, Word Search II, and Palindrome Pairs, whose standard solution inserts each word reversed and checks whether the leftover part of a word is a palindrome (not traced here; its source heading is empty too).

Understand and remember

  • A trie stores each word as a path of letters → all words with a prefix share one node → one DFS over the board serves every word at once and stops as soon as the path isn't a prefix of any word → 41 calls against 57 on the example, 5,587 against 51,079 on a random 8×8 board
  • Numbers in dictionary order = preorder of the digit trie → count the numbers under the current prefix level by level → if the count ≤ k, skip the whole subtree (cur + 1), else step down (cur × 10) → O((log n)²) without touching the n numbers
  • Each segment node stores the combined value of [lo, hi] → a query takes whole nodes fully inside the range and splits only partial ones → at most two kept nodes per level → O(log n); an update rewrites one node per level
  • A range update stops at the nodes a query would keep → adds value × length there and parks a tag → pushes the tag down only when a later call must go inside → range update and range query both O(log n)
  • detail that matters Popping the end mark when a word is found → each word is reported once even if the board spells it twice → and a dict per trie node costs far more memory than a set of words, so a trie only pays when the question is about prefixes
