Big-O and amortized O(1)

Also called asymptotic notation (O, Θ, Ω) and amortized analysis. The source guide's Big-O Notation heading holds one problem, Insert Delete GetRandom Θ(1) with duplicates, so this card teaches the notation first and then solves that problem.

In one breath

Big-O says how the work grows as the input grows, ignoring constant factors: O(n) means doubling n roughly doubles the work. Amortized O(1) means a sequence of n operations costs O(n) in total, even if a few single operations are expensive: the rare big cost is spread over the many cheap ones.

Doubling copies a geometric series, which sums to less than 2n, so the total is O(n) and each append is O(1) amortized. Growing by a fixed amount copies 1 + 2 + … + (n − 1), which is O(n²). CPython 3.10 grows by about 1.125× instead of 2×: sys.getsizeof shows new buffers at appends 1, 5 and 9 of the first 16, and 86 in 10⁶ appends. Any constant factor above 1 keeps the bound.

The source's problem: a multiset with O(1) insert, remove and random pick

insert(val) returns True if val was absent; remove(val) removes one copy; getRandom() picks each value with probability proportional to its count. The trick: keep the items in a list (random pick = one random index) and a dict from value to the set of its positions. To remove from the middle without shifting, move the last item into the hole, then pop the end.

In Python

import collections, random

class RandomizedCollection:
    def __init__(self):
        self.vals = []                           # multiset, any order
        self.idx = collections.defaultdict(set)  # value -> positions

    def insert(self, val):
        self.idx[val].add(len(self.vals))
        self.vals.append(val)                    # amortized O(1)
        return len(self.idx[val]) == 1

    def remove(self, val):
        if not self.idx[val]:
            return False
        i = self.idx[val].pop()                  # any copy of val
        last = self.vals[-1]
        self.vals[i] = last                      # fill the hole
        self.idx[last].add(i)
        self.idx[last].discard(len(self.vals) - 1)
        self.vals.pop()                          # O(1): drop end
        return True

    def get_random(self):
        return random.choice(self.vals)          # index a list

Add before discard: when the removed copy is already last, i equals the last index, and the discard must win. The source's version is also correct: it keeps index lists plus each item's slot in its list instead of sets. Both match a Counter over 20,000 random operations.

Time O(1) per call, amortized and expected · Space O(n). append and pop() at the end are amortized O(1), set and dict operations are expected O(1), and random.choice indexes the list once. So the source's "Θ(1)" holds in that averaged sense, not for every single call.

Why it beats the alternatives

✗ A plain list

Random pick is O(1), but remove must find the value and shift the rest: O(n). Finding alone cost 232 µs per call at n = 10⁵ (measured).

✗ A Counter of values

Insert and remove are O(1), but a weighted random pick has to walk the counts: O(number of distinct values) per call.

✗ List + dict of one index

The no-duplicates version of this problem. With two 1s the dict can only remember one position, so removing the other one leaves a stale index.

✓ List + dict of index sets

Every operation touches the end of the list and a few set entries: O(1). Swap-with-last is what makes removal from the middle cheap.

Is amortized O(1) always good enough?

Not when a single slow call matters. Amortized bounds the total, so one append can still copy the whole list; a latency-sensitive loop can preallocate ([None] * n) or use collections.deque, which CPython builds from fixed 64-slot blocks, so it never copies everything at once. And amortized is not "on average over random inputs": it holds for every sequence. Expected O(1) is weaker: a dict's O(1) assumes keys spread across slots.

Big-O also hides constants. For tiny n the "worse" class can win (scanning a 5-item list against hashing a key), and the measured 9,400× belongs to n = 10⁵: the list's cost shrinks with n, the set's doesn't.
