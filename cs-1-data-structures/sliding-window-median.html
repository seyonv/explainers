Sliding window median

Also called the running median or rolling median of a window. For every window of k consecutive numbers, report the middle value (the mean of the two middles when k is even). The source guide solves it in C++ with a multiset, under Lists › Arrays; this card uses the standard Python answer, two heaps with lazy deletion.

Prime · 2 minutes before you read

The problem: A window median needs the middle of k values, which neither a Counter nor a monotonic deque keeps. Sorting every window is O(n · k log k), about 10⁹ comparisons for n = 10⁵, k = 10³, and a sorted list with insort shifts O(k) per step.

Where it fits: Comes right after the heaps card, because it is two heaps working together plus heapq's lazy deletion. It reuses the fixed-window sweep from the monotonic deque card; the difference is that no value can be thrown away for good.

In one breath

Split the window into a low half and a high half. A max-heap holds the low half and a min-heap the high half, so the median is always sitting on top of one or both heaps. When a number leaves the window, don't dig it out of the heap: note that it's gone and throw it away only when it reaches a top.

In Python

import heapq
from collections import defaultdict

def median_sliding_window(nums, k):
    lo, hi = [], []            # lo: max-heap (negated), hi: min-heap
    gone = defaultdict(int)    # value -> copies waiting to be deleted
    for x in nums[:k]:
        heapq.heappush(lo, -x)
    for _ in range(k // 2):    # lo keeps the extra one when k is odd
        heapq.heappush(hi, -heapq.heappop(lo))
    def median():
        return float(-lo[0]) if k % 2 else (-lo[0] + hi[0]) / 2
    out = [median()]
    for i in range(k, len(nums)):
        x, old = nums[i], nums[i - k]
        gone[old] += 1         # lazy: just remember it left
        bal = -1 if old <= -lo[0] else 1
        if x <= -lo[0]:
            heapq.heappush(lo, -x); bal += 1
        else:
            heapq.heappush(hi, x); bal -= 1
        if bal < 0:            # lo is one short: borrow hi's min
            heapq.heappush(lo, -heapq.heappop(hi))
        elif bal > 0:          # lo is one over: give hi its max
            heapq.heappush(hi, -heapq.heappop(lo))
        while lo and gone[-lo[0]]:     # delete only at the tops
            gone[-heapq.heappop(lo)] -= 1
        while hi and gone[hi[0]]:
            gone[heapq.heappop(hi)] -= 1
        out.append(median())
    return out

print(median_sliding_window([1, 3, -1, -3, 5, 3, 6, 7], 3))
# → [1.0, -1.0, -1.0, 3.0, 5.0, 6.0]

The source's C++ is missing the closing brace and using namespace std;; corrected in the footer's compile check, and rewritten in Python here.

Deleting by value is safe because equal values are interchangeable: which copy of a 3 gets thrown away doesn't change either half. The saved file also runs 1,000 random cases against sorting every window; all match.

Time O(n log n) · Space O(n). Each step does at most three pushes or pops plus pruning, and every value is pruned at most once over the whole run. But buried leavers are never removed early, so a heap grows toward n entries, not k. That happens on random data too, because values far from the median never reach a top: n = 10⁵ uniform random values with k = 1,000 peaked at 91,491 heap entries (computed). So each step is O(log n), not O(log k), and memory is O(n).

Why it beats the alternatives

✗ Sort every window

O(n · k log k). For n = 10⁵, k = 10³ that's 99,001 sorts of about 1,000 × 10 comparisons: roughly 10⁹.

✗ One sorted list plus bisect

Finding the slot is O(log k), but del and insort shift elements: O(k) per step, O(n · k) total. Fine for small k (it's the baseline in the saved file).

✗ The source's multiset

C++ multiset with an iterator parked on the middle: insert, nudge the iterator one step, erase, all O(log k). Ideal in C++, but Python's standard library has no balanced tree to hold it.

✓ Two heaps, lazy deletion

Standard library only, O(log n) per step. The median is a heap top, so reading it costs O(1).

Is it always the tool?

No. If you may install packages, sortedcontainers.SortedList gives the multiset approach directly (add, remove, index k // 2) with less code and no buried entries. For small k, the bisect list is simpler and often quick enough, since shifting is a C-level memory move (our inference, not timed here). For a running median over a stream that never forgets, you need the two heaps without any deletion at all.

It's the wrong tool for window max or min: a monotonic deque does that in O(n). And for any other percentile, the two halves just get unequal target sizes; the same two-heap idea works with a different split (our generalisation, not in the source).

Understand and remember

  • Every value in lo ≤ every value in hi, with sizes (k + 1) // 2 and k // 2 → the median is top(lo) for odd k, or the mean of both tops for even k → reading it is O(1)
  • A heap can only remove its top cheaply → when a value leaves, record gone[v] += 1 and remove it only when it surfaces on a top → each value is pruned at most once → O(log n) per step
  • The leaver and the newcomer each shift the real size difference by ±1 → balance is −2, 0 or +2 → at most one top moves across → the halves stay the right sizes
  • Buried leavers are never removed early → values far from the median never reach a top (on rising input all 20 of range(20) stay, 17 stale; on n = 10⁵ random values with k = 1,000 the heaps peak at 91,491 entries) → heaps grow toward n, not k → O(n log n) time and O(n) space
  • detail that matters Equal values are interchangeable → deleting any copy of 3 leaves the same two halves → so lazy deletion by value is correct even with duplicates

  1. concept Explain why the two-heap split makes the median O(1) to read but O(log k) to maintain.
    Check
    • the median is always at the boundary between the halves, which is where the tops are
    • reading a top is O(1)
    • each step pushes, possibly moves one top and pops stale tops, each O(log size)
  2. mechanism Walk through step i = 5 of the trace (window [−3, 5, 3], −1 leaving, 3 arriving).
    Check
    • −1 leaves from lo: gone[−1] = 1, balance −1
    • 3 > top(lo) = −1, so it goes into hi: balance −2
    • lo is one short: move hi's min 3 into lo
    • −1 is buried under 3 in lo and stays; the median is 3
  3. tradeoff Your input is a sorted stream of sensor readings. What happens to memory with two heaps, and what would you use instead?
    Check
    • on monotone input the leavers sit at the bottom of their heap and never surface
    • so the heaps hold every value seen: O(n) memory, not O(k)
    • a SortedList (add, remove, index k // 2) holds exactly k values
    • an order-statistic Fenwick tree over value ranks also stays at the number of distinct values

vs Monotonic deque: Both slide a window of k. Why can the deque forget values forever while the median must keep every value until it leaves?

Check
  • a smaller, older value can never become the max, so the deque discards it
  • any value can become the median as others leave
  • so the median keeps all k values (plus buried ones) in two heaps
  • cost: O(1) amortized per step for the max, O(log n) for the median

vs Heaps and priority queues: The heaps card uses one heap for smallest next; this card uses two for the middle. What does the second heap buy, and what new bookkeeping does it bring?

Check
  • one heap exposes only one extreme
  • two heaps facing each other expose both sides of the boundary, where the median lives
  • they must be kept the right sizes (balance) and consistent (lo ≤ hi)
  • lazy deletion must track which side a leaver was on
