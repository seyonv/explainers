Heaps and priority queues

Also called a binary heap, a min-heap, or a priority queue (the job it does). A list kept in a loose order so the smallest item is always at index 0. The source guide's Heaps section uses Python's heapq for Course Schedule, The Skyline Problem and Rearrange String k Distance Apart.

Prime · 2 minutes before you read

The problem: Repeatedly taking the smallest item from a changing collection costs a full scan per pop with an unsorted list, or an O(n) shift per insert with a sorted list. At n = 10⁶ either is 10⁶ steps per operation.

Where it fits: Follows the tree cards: a heap is a complete binary tree with no node objects, stored in a list by index arithmetic. The toolkit card gave heapq's costs; this card shows why they hold. Sliding window median and the Fibonacci heap build directly on it.

In one breath

A heap is a complete binary tree stored in a plain list: the children of index i sit at 2i + 1 and 2i + 2, and every parent is ≤ its children. That rule makes the root the minimum, and fixing the rule after a push or pop only walks one root-to-leaf path, so both cost O(log n).

Worked example: push a = [5, 2, 9, 1, 5, 6]

parent(i) = (i − 1) // 2 children(i) = 2i + 1, 2i + 2 heap rule: h[parent(i)] ≤ h[i] for every i ≥ 1 → min = h[0] = 1

The tree is only a picture: there are no node objects or pointers, just index arithmetic on one list. Pushing all six values gives [1, 2, 6, 5, 5, 9], the same list heapq.heapify(a) builds.

In Python

def push(heap, x):
    heap.append(x)                   # new leaf at the end
    i = len(heap) - 1
    while i and heap[i] < heap[(i - 1) // 2]:
        p = (i - 1) // 2             # sift up: swap with parent
        heap[i], heap[p] = heap[p], heap[i]
        i = p

def pop(heap):
    top, last = heap[0], heap.pop()  # min is always heap[0]
    if heap:
        heap[0], i = last, 0         # last leaf goes to the root
        while 2 * i + 1 < len(heap):
            c = 2 * i + 1            # sift down: smaller child
            if c + 1 < len(heap) and heap[c + 1] < heap[c]:
                c += 1
            if heap[i] <= heap[c]:
                break
            heap[i], heap[c] = heap[c], heap[i]
            i = c
    return top

h = []
for x in [5, 2, 9, 1, 5, 6]:
    push(h, x)                       # same as heapq.heappush
print(h)                             # → [1, 2, 6, 5, 5, 9]
print(pop(h), h)                     # → 1 [2, 5, 6, 9, 5]

Push and pop O(log n) · peek O(1) · heapify O(n) · Space O(n). A complete tree of n nodes is ⌊log₂ n⌋ levels deep, and each sift moves one level per swap: at most 19 swaps for n = 10⁶. heapify is O(n) because most nodes sit near the bottom and sift only a level or two.

Course Schedule III: courses [[100, 200], [200, 1300], [1000, 1250], [2000, 3200]] → 3

Grey struck chip = dropped. In the source's example the course dropped is the one just added; the made-up last row shows the heap swapping out an earlier longer course so two short ones fit.

def schedule_course(courses):
    days, taken = 0, []              # taken: max-heap of -duration
    for duration, last_day in sorted(courses, key=lambda c: c[1]):
        days += duration
        heapq.heappush(taken, -duration)
        if days > last_day:          # over: drop the longest course
            days += heapq.heappop(taken)
    return len(taken)

print(schedule_course([[100, 200], [200, 1300],
                       [1000, 1250], [2000, 3200]]))  # → 3

Time O(n log n) · Space O(n). The sort is n log n, and each course is pushed once and popped at most once. One pop is always enough: the course dropped is at least as long as the one just added, so days fall back to at most the previous total, which was already within an earlier deadline. The source calls this problem Course Schedule; the code matches it.

Why it beats the alternatives

✗ Unsorted list

Push is an O(1) append, but every pop-min scans the whole list: 10⁶ comparisons per pop at n = 10⁶.

✗ Sorted list + bisect.insort

Pop from the end is O(1), but each insert shifts everything after the slot: up to 10⁶ moves per push at n = 10⁶.

✗ Balanced BST

O(log n) for everything, plus deleting any item and walking in order (C++ multiset, Java TreeMap). Python's standard library has none, and every node carries pointers.

✓ Binary heap (heapq)

O(1) peek, O(log n) push and pop, at most 19 swaps at n = 10⁶, and O(n) heapify, all on a plain list with no pointers.

Is it always the tool?

Use a heap when you only ever need the current smallest or largest: merging k sorted lists, top-k of a stream, Dijkstra, event simulation, scheduling. When items tie, heapq compares the next tuple field, so store (priority, counter, item) if items can't be compared. The heapq docs recommend exactly this.

It's the wrong tool when you need to find, delete or update any item other than the top. heapq has no decrease-key, so Dijkstra pushes a duplicate and skips stale entries. A sorted structure or an indexed heap does this directly. For top-k of a list you already have, heapq.nsmallest suits a small k; for k close to n, just sorted(). Across threads, use queue.PriorityQueue, which wraps heapq in a lock.

Understand and remember

  • Every parent ≤ its children → the root is the minimum → peek is O(1), and the rest stays only loosely ordered, so pushes and pops are cheap
  • A complete tree in a list has ⌊log₂ n⌋ levels → push appends a leaf and sifts it up; pop moves the last leaf to the root and sifts it down → one path, O(log n) (at most 19 swaps at n = 10⁶)
  • Heapify sifts down every parent from the bottom up → most nodes sit near the leaves and move a level or two → the total is O(n), cheaper than n pushes
  • Course Schedule III: take courses by deadline → if days pass the deadline, pop the longest taken so far from a max-heap (−duration) → count stays, days used shrink, later courses can only benefit → O(n log n)
  • detail that matters heapq can only remove the top → updating or deleting a middle item means pushing a new entry and skipping stale ones when they surface (lazy deletion) → the heap can grow beyond the live item count
  • detail that matters Ties compare the next tuple field → store (priority, counter, item) when items aren't comparable, as the heapq docs recommend

3 · Retrieve from memory, card closed
  1. concept Explain why a heap, unlike a sorted list, gets O(log n) inserts.
    Check
    • a sorted list keeps total order, so an insert shifts every later item: O(n)
    • a heap keeps only parent ≤ child, so a new leaf only needs to climb its own path
    • that path is ⌊log₂ n⌋ long in a complete tree
  2. mechanism Walk through pushing 1 into [2, 5, 9] (indices 0–2).
    Check
    • append at index 3
    • parent (3 − 1) // 2 = 1 holds 5 > 1: swap
    • parent (1 − 1) // 2 = 0 holds 2 > 1: swap
    • result [1, 2, 9, 5]: 2 swaps
  3. tradeoff Dijkstra in Python needs decrease-key, which heapq lacks. What does the standard workaround cost compared with an indexed heap or a Fibonacci heap?
    Check
    • push a duplicate with the smaller distance and skip stale pops
    • the heap may hold up to E entries: O(E log E) = O(E log V)
    • an indexed heap does decrease-key in O(log V) but needs a key → index map kept in sync on every swap
    • a Fibonacci heap makes it O(1) amortized, but with large constants

Check
  • heapsort heapifies in O(n), then repeatedly swaps the max to the end and sifts down
  • in place, O(n log n) worst case
  • not stable, and its jumps through memory are cache-unfriendly
