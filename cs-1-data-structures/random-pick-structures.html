Random pick with a blacklist

Also called uniform sampling with exclusions, or the remap trick (LeetCode 710). Pick a uniformly random integer in [0, n) that isn't blacklisted, with one call to the random function per pick. The source guide lists it under Object-oriented Design and Programming, in Java.

In one breath

If b values are banned, only m = n − b values are allowed, so draw from [0, m) and nothing else. Some banned values sit inside [0, m) and leave holes; the same number of allowed values sit outside it, at m or above. Build a small dict that sends each hole to one of those outside values, and every draw lands on a distinct allowed value, each with probability 1/m.

Worked example: n = 7, blacklist = [2, 3, 5]

remap = {2: 6, 3: 4} draw x: 0 1 2 3 returns: 0 1 6 4 ← each allowed value exactly once, P = 1/4

Red = banned. Holes are banned values below m; fillers (green) are allowed values at or above m. There are always equally many of each: b − (banned ≥ m) = (n − m) − (banned ≥ m).

In Python

import random

class Solution:
    def __init__(self, n, blacklist):
        banned = set(blacklist)
        self.m = n - len(banned)          # draw from [0, m)
        self.remap = {}
        top = n - 1
        for b in blacklist:
            if b < self.m:                # a hole in the draw range
                while top in banned:      # skip banned values up top
                    top -= 1
                self.remap[b] = top       # fill the hole with top
                top -= 1

    def pick(self):
        x = random.randrange(self.m)      # the only random call
        return self.remap.get(x, x)

s = Solution(7, [2, 3, 5])
print(s.m, s.remap)   # → 4 {2: 6, 3: 4}

Same algorithm as the source's Java, which stores every banned value in its map (the ones ≥ m map to a dummy 1); here a set holds the bans and the dict holds only the holes.

Time O(b) to build, O(1) per pick · Space O(b). top only moves down, so the while skips at most b banned values over the whole constructor, and each pick is one random call plus one dict lookup.

Why it beats the alternatives

✗ Draw again until allowed

Rejection sampling needs n / m random calls on average: 7 / 4 = 1.75 here (the same run measured 122,626 calls for 70,000 picks = 1.752). With n = 10⁶ and all but 10 banned, that's 10⁵ calls per pick, and no bound on the worst case.

✗ List every allowed value

Build allowed = [0, 1, 4, 6] and index it. One call per pick, but O(n) memory and build time even when the blacklist is tiny: 10⁹ entries for n = 10⁹ (illustrative).

✗ Binary search the k-th allowed value

Sort the blacklist, draw k in [0, m), then bisect for the value with k allowed numbers below it. Also one call and O(b) memory, but O(log b) per pick instead of O(1).

✓ Remap the holes

One random call, O(1) per pick, memory proportional to the blacklist only: a 2-entry dict here. Draws inside [0, m) are a bijection onto the allowed values, so uniformity is exact.

Is it always the tool?

It fits when the blacklist is fixed and you pick many times. If bans change between picks, each change can break the hole-to-filler pairing, so the dict must be rebuilt; a sorted structure with the binary-search pick handles inserts better (our inference, not from the source).

When the blacklist is a small fraction of n, plain rejection is simpler and nearly as cheap: with 1% banned it averages 1 / 0.99 ≈ 1.01 calls. And for weighted rather than uniform picks, use the alias method or prefix sums with binary search instead. The same "swap into a dense range" idea powers O(1) random removal in RandomizedSet: move the last element into the hole.
