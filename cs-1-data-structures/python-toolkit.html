The Python interview toolkit

Also called the standard-library containers: list, deque, dict, set, heapq, bisect, Counter, defaultdict, OrderedDict. The source guide's coding page opens with an empty "C++" heading; since this series writes every solution in Python, this card takes its place.

Prime · 2 minutes before you read

The problem: Python hides its containers' costs behind friendly syntax: x in lst and x in st look identical, and lst.pop(0) looks as cheap as lst.pop(). Pick the wrong one inside a loop and an O(n) solution becomes O(n²) without any visible change in the code.

Where it fits: The second Foundations card, next to Big-O and amortized O(1). It turns that card's growth classes into a cost table for the containers every later card in this course uses: deque for the windows, heapq for the heap cards, dict and set for the composites.

You'll meet: list as a dynamic array (cheap ends, costly front and middle) deque for both ends dict, set, Counter, defaultdict, OrderedDict as hash tables heapq and bisect as functions on a plain list immutable str and join

In one breath

Most interview solutions repeat one operation millions of times: pop from the front, test membership, grab the smallest, keep things sorted. Each has one container that makes it O(1) or O(log n). Pick the container for the operation you repeat, and a plain list for everything else.

In Python, on the course's running example

import bisect, heapq
from collections import Counter, defaultdict, deque

a, s = [5, 2, 9, 1, 5, 6], "ADOBECODEBANC"

q = deque(a); q.append(7)
print(q.popleft(), list(q))        # O(1); list.pop(0) is O(n)
h = [-x for x in a]                # min-heap of negatives
heapq.heapify(h)                   # O(n)
print(-heapq.heappop(h))          # the max, O(log n)
b = sorted(a)                     # [1, 2, 5, 5, 6, 9]
print(bisect.bisect_left(b, 5))   # first index with b[i] >= 5
bisect.insort(b, 4); print(b)     # O(n): shifts 5, 5, 6, 9
print(Counter(s).most_common(3))
groups = defaultdict(list)
for x in a:
    groups[x % 2].append(x)       # no KeyError on first use
print(dict(groups))
seen = set(a); print(9 in seen, 3 in seen)

# → 5 [2, 9, 1, 5, 6, 7]
# → 9
# → 2
# → [1, 2, 4, 5, 5, 6, 9]
# → [('A', 2), ('D', 2), ('O', 2)]
# → {1: [5, 9, 1, 5], 0: [2, 6]}
# → True False

Time O(n log n) · Space O(n) for the snippet as a whole: sorted(a) dominates; everything else is O(n) or less. Six letters of s appear twice, so most_common(3) breaks the tie by first appearance: A, D, O.

Why the right container beats a plain list

✗ A list as a queue

pop(0) in a BFS loop. Emptying 105 items moves 4,999,950,000 elements, so an O(n) search quietly becomes O(n²).

✗ A list for "seen before?"

if x not in seen_list inside a loop. 232 µs per test at n = 105, measured; 105 such tests is over 20 s.

✗ Sorting to get the smallest

Re-sorting, or insort plus pop(0), after every insert: O(n) or O(n log n) per step for what a heap does in O(log n).

✓ One tool per hot operation

deque for the ends, set or dict for "have I seen it?", heapq for "the smallest next", bisect for ranks in sorted data. Each turns the repeated step into O(1) or O(log n).

"Over 20 s" = 105 × 232 µs = 23.2 s, extrapolated from the measured per-lookup time, not run.

Is the fancier container always better?

No. For a few dozen items, a list scan is fast and simplest; a set also costs memory and needs hashable items (no lists inside). A deque gives up fast indexing in the middle. heapq has no decrease-key, so Dijkstra in Python pushes duplicates and skips stale entries. And a dict's O(1) is an average: adversarial keys that all collide make it O(n), which is why Python randomizes string hashes per process.

When the operation is "add 17 to every item", no container helps: the per-item interpreter cost dominates, and numpy's whole-array operations are the fix (see the Python loops card).

Keep it if it changes what you can explain, predict, compare, choose, build or debug. Otherwise it's reference.

Understand and remember

  • A list is a contiguous dynamic array → the end has spare room and nothing moves → append and pop() are O(1) → the front or middle forces every later element to shift → pop(0), insert(0, x) and insort are O(n)
  • dict and set hash the key to one slot → membership is one probe instead of a scan → 1,000 lookups at n = 10⁵ drop from 0.232 s (list) to 24.6 µs (set), ≈ 9,400× → but only on average, and only for hashable keys
  • A deque is linked fixed-size blocks → both ends are O(1) → it is the container for queues, BFS and sliding windows → but indexing the middle is O(n)
  • heapq keeps a min-heap in a plain list → the smallest is h[0] and push/pop are O(log n) → there is no max flag or decrease-key → store −x for a max-heap and push duplicates, skipping stale entries
  • detail that matters str is immutable → each s + t may copy everything built so far → O(n²) for a loop of concatenations → collect pieces in a list and join once (0.468 s → 0.0073 s measured)
  • detail that matters heapify sifts down from the bottom → most nodes sit near the leaves and move a level or two → O(n), cheaper than n pushes at O(n log n)

Reference only

  • the exact method names (popleft, appendleft, move_to_end, popitem(last=False))
  • Counter.most_common using heapq.nlargest and first-seen tie order
  • sortedcontainers.SortedList as the third-party sorted list
  • the measured M3 timings and the 4.6 ns per comparison division
  • the Python wiki TimeComplexity page

  1. concept Explain to a Python beginner why if x not in seen_list inside a loop over 10⁵ items is a performance bug, using the card's measured numbers.
    Check

  2. mechanism Walk through what happens in memory when a 5-element list runs pop(0), and count the moves for emptying a 10⁵-element list this way.
    Check
    • the first slot is removed and every later element shifts one slot left: 4 moves for 5 elements
    • emptying n items costs (n − 1) + (n − 2) + … = n(n − 1)/2
    • 4,999,950,000 moves for n = 10⁵; deque.popleft moves none
  3. tradeoff You need a max-heap of (priority, task) pairs where tasks aren't comparable. What do you push, and what breaks if you push (priority, task) as is?
    Check
    • push (−priority, counter, task): negation turns the min-heap into a max-heap
    • the counter breaks ties before the task is compared
    • without it, equal priorities make Python compare tasks, which raises TypeError for non-comparable items

5 · Predict commit to an answer before revealing

A BFS over a graph with 10⁴ nodes uses queue = [], queue.pop(0) and queue.append. Before counting: how many element moves do the pops cost in the worst case, and how would the total running-time class change?

Reveal

If all 10⁴ nodes sit in the queue, emptying it with pop(0) moves n(n − 1)/2 = 49,995,000 elements. The BFS is supposed to be O(V + E); the queue alone makes it O(V²). Swapping in a deque (popleft) restores O(V + E) with zero moves.
