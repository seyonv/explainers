Monotonic deque

Also called a monotonic queue, max-queue or decreasing deque. A double-ended queue whose values stay sorted, so the front is always the answer and stale items leave from the other end. The source guide uses it for Sliding Window Maximum, under Queues.

Prime · 2 minutes before you read

The problem: The max of each window of k numbers costs k − 1 comparisons if you rescan: 98,901,999 for n = 10⁵, k = 10³. A heap with lazy deletion is O(n log n) and can pile up stale entries.

Where it fits: Follows the counts window: same forward-only sweep, but with a fixed width. It uses the toolkit's deque for O(1) work at both ends, and the amortized argument from the Big-O card.

In one breath

Slide a window of k numbers along the array and keep a deque of indices whose values never rise from front to back. A new number evicts every smaller number at the back, since those can never be the max again while it's in the window. The index at the front leaves when the window slides past it. The front is then the window's max.

Worked example: nums = [1, 3, −1, −3, 5, 3, 6, 7], k = 3 → [3, 3, 5, 5, 6, 7]

window at step i: indices i − k + 1 … i full once i ≥ k − 1 = 2 front expires if: front ≤ i − k at i = 4: 1 ≤ 4 − 3 → pop 3 back is beaten if: nums[back] < x −3 < 5, then −1 < 5 → pop both

At i = 4 the window is −1, −3, 5. The old max 3 (index 1) just slid out, and 5 is bigger than everything still waiting behind it, so the deque shrinks to one index and the max is 5.

In Python

from collections import deque

def max_sliding_window(nums, k):
    dq = deque()                 # indices; their values never rise
    out = []
    for i, x in enumerate(nums):
        if dq and dq[0] <= i - k:        # front fell out of window
            dq.popleft()
        while dq and nums[dq[-1]] < x:   # x beats them: never max
            dq.pop()
        dq.append(i)
        if i >= k - 1:                   # window [i-k+1, i] is full
            out.append(nums[dq[0]])      # front is the max
    return out

print(max_sliding_window([1, 3, -1, -3, 5, 3, 6, 7], 3))
# → [3, 3, 5, 5, 6, 7]

The source's C++ is correct; this is a rewrite, not a fix. It decrements k first, so its expiry test reads front < i − k; here k stays as given and the test is front ≤ i − k.

Time O(n) · Space O(k). Each index is pushed once and popped at most once (from either end), so all the while loops together run at most n times: here 8 pushes and 7 pops. Every index in the deque is inside the window, so it never holds more than k.

Why it beats the alternatives

✗ Rescan every window

max(nums[i:i+k]) costs k − 1 comparisons per window: (n − k + 1)(k − 1) = 6 × 2 = 12 here, 98,901,999 for n = 10⁵, k = 10³.

✗ Max-heap, lazy delete

Push (−x, i); pop the top while its index is outside the window. Correct, but O(n log n), and stale entries can pile up to n when the array only rises.

✗ Sparse table

Precompute the max of every power-of-two block, then answer any range in O(1). O(n log n) time and memory to build, all to answer queries that only ever slide right.

✓ Monotonic deque

One pass, O(n) always, O(k) memory: at most 2n deque operations, so ≤ 200,000 for n = 10⁵ whatever k is.

Is it always the tool?

Use it when a window moves only forward at both ends and you need its max or min (flip < to > for the min). The same trick drives the O(n) solutions to "shortest subarray with sum ≥ K" (a deque of prefix sums) and to DP steps like "best of the last k states" (jump game VI, constrained subsequence sum). These uses are standard practice, not from the source.

It's the wrong tool when you need more than the extreme. A sliding median needs the middle of the window, which a deque throws away, so use two heaps (the sliding-window median card). If the ranges aren't a sliding window (arbitrary [l, r] queries asked later), use a sparse table or a segment tree. And if items only ever leave from the top, a monotonic stack is enough.

Understand and remember

  • A new x arrives → every older value smaller than x will leave the window before x does and is smaller → it can never be a max again → pop it from the back → values in the deque never rise from front to back → the front is the window's max
  • The window slides one step → at most the front index falls out (front ≤ i − k) → store indices so expiry is a comparison → the deque only holds in-window indices → O(k) memory
  • Each index is pushed once and popped at most once, from either end → all the while loops together run ≤ n times → at most 2n deque operations, O(n) total whatever k is
  • detail that matters Pop only strictly smaller values (<) → equal values stay → the older equal expires first while the newer one still covers the max → either < or <= gives correct maxima, but < keeps duplicates in the deque

Reference only

  • the source's decrement of k and its front < i − k form
  • collections.deque method names
  • sparse tables as the O(1)-query, O(n log n)-build alternative
  • jump game VI and shortest subarray with sum ≥ K as further uses

4 · Compare against what you already know

vs Monotonic stack: Monotonic deque vs monotonic stack: which ends does each drop from, what does the popped element learn, and when does a stack stop being enough?

Check
  • the stack drops only from the top; the deque also drops expired indices from the front
  • a stack pop means the new element is the popped one's nearest smaller or larger neighbour (its wall)
  • a deque back-pop means the popped one can never be a max again; the front is the answer
  • when elements also expire from the left (a sliding window), a stack can't remove them: use the deque

vs Sliding window median: Both handle a fixed window of k. Why can the max throw values away forever while the median can't?

Check
  • a smaller, older value can never become the max again, so discarding it is safe
  • any value can become the median as others leave, so the median needs the whole window
  • the median keeps all k values in two heaps with lazy deletion: O(log) per step
  • the max needs only the dominating subsequence: O(1) amortized
