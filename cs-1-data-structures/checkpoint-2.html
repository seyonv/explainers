Checkpoint 2: trees and heaps

Ties together binary tree traversals, the Fenwick tree, tries and segment trees, heaps, the sliding window median and the Fibonacci heap: what each tree or heap stores at a node, which question that makes cheap, and what it costs to keep up to date.

How to use this page. Close the six cards. Answer each question in writing, in full sentences, before opening its Check. A wrong or shaky answer isn't a failure; it tells you exactly which section to reopen. The questions are mixed on purpose, so you have to work out which idea applies before you can answer.

1 · Mixed retrieval

  1. which concept?A game has 10⁶ players by ID. Scores change one player at a time, and the dashboard asks for the total score of IDs l through r. Which structure, what does each operation cost, and what changes if the dashboard asks for the highest score in l through r instead?
    Check
    • point updates plus range sums: a Fenwick tree, O(log n) for both, at most 20 cells per update and 19 per prefix query at n = 10⁶
    • a range total is query(r) − query(l − 1), which works because + can be undone
    • max has no inverse, so two prefixes can't give a range max: switch to a segment tree

    Missed it? Reopen the Fenwick tree, "Is it always the tool?", and tries and segment trees, section 3.

  2. Push 4, 7, 1 and 3, in that order, into an empty heapq list. What list do you end with, and how many swaps did the sift-ups make?
    Check
    • [4] → [4, 7] → push 1: it swaps with 4 → [1, 7, 4]
    • push 3 lands at index 3; its parent (index 1) holds 7, so swap; its new parent 1 is smaller, stop
    • final [1, 3, 4, 7], 2 swaps in total

    Missed it? Reopen heaps, the hand trace and "The four moves".

  3. which concept?A shop's search box must list every product name that starts with what the user has typed so far, over 50,000 names, updating on every keystroke. Why is a set of names the wrong tool, and what do you use?
    Check
    • a set answers only is this exact name present?; a prefix query would scan every name
    • a trie puts all names with a prefix under one node: walk the typed letters, then list that subtree
    • each keystroke is one more step down from the previous node

    Missed it? Reopen tries and segment trees, "Is it always the tool?".

  4. Morris inorder uses O(1) extra space. What does it borrow from the tree, why is the tree the same afterwards, and what goes wrong if you stop at the k-th smallest and return early?
    Check
    • it borrows empty right pointers: the inorder predecessor's right pointer is threaded back to the node
    • every thread laid on a first visit is removed on the second visit, so a full walk restores the tree
    • stopping early leaves the threads you laid in the tree, and later code sees them as real edges

    Missed it? Reopen binary tree traversals, the Morris worked example and "Is Morris always the tool?".

  5. which concept?You run Dijkstra in Python on a graph with V = 1,000 and E = 10,000. A colleague insists on a Fibonacci heap because it makes the bound O(E + V log V). What do you recommend, and what numbers support it?
    Check
    • on paper: about 19,966 steps for the Fibonacci heap against 109,624 for a binary heap, from the two bounds
    • in practice heapq with lazy deletion (push duplicates, skip stale pops) pushed only 2,021 entries on the card's graph
    • each Fibonacci node is 7 fields and pointer chasing in Python, while heapq is a flat array in C: use heapq

    Missed it? Reopen the Fibonacci heap, "Costs next to a binary heap" and "So should you use one?".

  6. The two-heap sliding median deletes lazily. On a stream that only rises, what happens to the heaps' size, and why doesn't the monotonic deque have this problem for the window max?
    Check
    • each leaver is the smallest value in the max-heap lo, so it sits at the bottom and never surfaces; nothing is pruned
    • on range(20) with k = 3 all 20 entries stay, 17 of them stale: memory grows toward n
    • the deque can discard a dominated value for good, because it can never be the max again; any value can become the median, so the heaps can't

    Missed it? Reopen the sliding window median, the complexity line, and heaps, "Lazy deletion".

  7. What would go wrong in a Fibonacci heap if decrease-key cut nodes but never marked or cascaded?
    Check
    • a node could lose many children and still keep its place, so a degree-k root could hold only k + 1 nodes
    • then the degree is no longer bounded by log_φ n, and consolidate may need many more slots
    • extract-min would no longer be O(log n) amortized; marks keep subtree sizes Fibonacci-sized

    Missed it? Reopen the Fibonacci heap, "Why the trees can't get thin".

3 · Project: the sliding median two ways

What it reinforces: two heaps with lazy deletion (sliding window median, heaps), a Fenwick tree over value ranks walked down like a tree (Fenwick tree, binary tree traversals), and the segment tree as the heavier alternative (tries and segment trees).

A Fenwick tree can count values instead of summing an array: give each distinct value a rank 1…d, add 1 at its rank when it enters the window and −1 when it leaves, and the r-th smallest value in the window is the smallest rank whose prefix count reaches r.

find r-th smallest: pos = 0 for step in (highest power of 2 ≤ d, …, 2, 1): if pos + step ≤ d and t[pos + step] < r: pos += step; r -= t[pos] answer rank = pos + 1
  1. Two heaps. Take the card's median_sliding_window and add a counter for the heaps' total size after each step.
  2. Fenwick over ranks. Sort the distinct values, map each to a rank, and write fenwick_median(nums, k) with the descent above (two lookups when k is even). Count the tree cells read.
  3. Trace. Run both on [1, 3, −1, −3, 5, 3, 6, 7] with k = 3.
  4. Check. Compare both against sorting each window on 1,000 random inputs (n 1–15, k 1–n, values −5…5, seeded).
  5. Memory. For k = 10, record the heaps' peak size and the Fenwick size (distinct values) on three inputs: range(1000); 10⁴ values of i % 50; and 10⁴ random integers in 0…10⁶.
  6. Design. In three sentences: when would you pick each, and when would a segment tree over ranks or a SortedList be better?
Done when: both versions print [1.0, −1.0, −1.0, 3.0, 5.0, 6.0], match the brute force on all 1,000 inputs, you have the memory table, and your design paragraph names the condition under which each wins. Then compare with the check.
Check: the numbers (computed with a Python version of exactly these steps)
  • Example: 7 distinct values, so the Fenwick tree has 7 cells; each lookup descends 4 steps (8, 4, 2, 1), 24 cell reads for the 6 medians. The heaps peak at 6 entries.
  • Random check: 0 mismatches for either version out of 1,000.
  • Memory, heaps' peak vs Fenwick cells: range(1000): 1,000 vs 1,000. i % 50: 1,642 vs 50. Random 0…10⁶: 1,866 vs 9,951.
  • So neither always wins: the Fenwick tree is small when values repeat, but needs every value known in advance to assign ranks, and grows with the number of distinct values; the heaps work online but keep stale entries.
  • A segment tree over ranks answers the same order statistic with a descent from the root, at 2 to 4 times the cells; a SortedList holds exactly k values, if a third-party package is allowed.

LFU cache in O(1)Also called a least-frequently-used cache, or an LFU cache with LRU tie-breaking. The source guide asks for LeetCode's version under Object-oriented Design: get and put in Θ(1), a use counter per key,…In one breathWhen the cache is full, throw out the key used the fewest times, and among equals the one untouched for longest. The trick for O(1) is to never sort: keep one bucket of keys per use count, each bucket in recency order, and remember the smallest count in use. The victim is always the oldest key in that bucket.
