Queues as rolling state

Also called a sliding DP window, or a rolling array kept in a collections.deque. The source guide's Queues section uses a deque twice in Python: as a moving window of DP values (Number of People Aware of a Secret) and as a list you build from the right end back (Integer to English Words).

Prime · 2 minutes before you read

The problem: A DP table over all n days, or a list of every person, grows without bound: at n = 1,000, delay = 1 the secret count has 301 digits, so a person-by-person simulation can't even be built. Re-summing the window each day costs O(n · forget).

Where it fits: Follows the monotonic deque: the same container, used here not to find an extreme but to hold exactly the last k DP values. It relies on the toolkit's O(1) append and popleft, and previews the rolling arrays of cs-3's DP cards.

Builds on: Monotonic deque · The Python interview toolkit

You'll meet: a recurrence that reads only the last forget days append today, popleft the day that drops out a running sum updated by two terms per day appendleft for building output from the right (Integer to English Words)

By the end: Turn a recurrence that looks back a bounded number of steps into an O(n)-time, O(window)-memory loop, and trace People Aware of a Secret and Integer to English Words by hand.

In one breath

When today's answer depends only on the last k days, you don't need a table of all n days. Keep those k values in a deque: append today on the right, pop the day that just fell out of range on the left. Both ends are O(1), so the window slides for free and memory stays at k.

In Python

from collections import deque

def people_aware(n, delay, forget):
    new = deque([0] * (forget - 1) + [1])  # learned on days 2-f .. 1
    share = 0                              # people sharing today
    for day in range(2, n + 1):
        share += new[-delay]     # learned on day - delay: starts now
        share -= new.popleft()   # learned on day - forget: forgets
        new.append(share)        # each sharer tells one new person
    return sum(new)              # learned in the last `forget` days

print(people_aware(6, 2, 4))    # → 5
# all 455 cases with n < 15 match a person-by-person simulation

The source seeds the deque with [0] * forget, pops one and appends 1; same window, same answer. No bug. LeetCode's version of this problem asks for the count modulo 10⁹+7; the source's statement leaves that out, and Python's big integers keep it exact (a 301-digit count at n = 1,000, delay = 1, forget = 1,000).

Time O(n) · Space O(forget). Each day does one read near the right end, one popleft and one append, all O(1), and the deque never holds more than forget values.

Why it beats the alternatives

Scale for the counts below: n = 1,000, delay = 1, forget = 1,000 (computed).

✗ Simulate every person

Store each person's learning day and step them all. The count doubles fast: the answer has 301 digits, so the list could never be built.

✗ Re-sum the window daily

Keep all new[t] and add up the sharers each day. Right answer, but 499,500 additions, O(n · forget), where two per day will do.

✗ A list with pop(0)

Same idea, wrong container: pop(0) shifts every remaining item left. 999 × 999 = 998,001 element moves.

✓ Deque window

Add who starts, subtract who forgets, append, pop. 999 days × 3 O(1) steps = 2,997 operations, and 1,000 stored values.

The other use: building from the right, Integer to English Words

Here the deque is not a window. divmod(num, 1000) hands you the lowest three digits first, but they are read last, so each chunk goes on the left with appendleft, O(1).

# below_1000(567) -> ["Five", "Hundred", "Sixty", "Seven"]
# (11 lines, in code/)
def number_to_words(num):
    if num == 0:
        return "Zero"
    parts = deque()
    for scale in ["", "Thousand", "Million", "Billion"]:
        num, chunk = divmod(num, 1000)   # lowest chunk first ...
        if chunk:
            words = below_1000(chunk) + ([scale] if scale else [])
            parts.appendleft(" ".join(words))  # ... reads last
    return " ".join(parts)

print(number_to_words(1234567))
# → One Million Two Hundred Thirty Four Thousand Five Hundred
#   Sixty Seven

The source builds each chunk word by word with extendleft, which reverses what it adds (extendleft(["One", "Hundred"]) gives ['Hundred', 'One']), then extendlefts the chunk again so the two reversals cancel. It is correct; this version appends whole chunk strings instead, and matches the source on 102,000 inputs.

Is a deque always the right tool?

Use it when the state you need is a fixed-length run of recent values, or when you must add at the front. deque(maxlen=k) even drops the left end for you, though here you need the dropped value, so pop it yourself.

It is not a random-access array: the Python docs say indexing is O(1) at the ends but slows to O(n) in the middle, so window[-delay] with delay near forget / 2 on a huge window is not free. Then a plain list of size forget used as a ring buffer (new[t % forget]) is O(1) everywhere. And for Integer to English Words, with at most four chunks, a list plus reversed() is just as good; the deque there is for clarity, not speed.

Understand and remember

  • Today's sharers = yesterday's + those who learned delay days ago − those who learned forget days ago → only the last forget values of new[] are ever read → keep them in a deque of length forget → O(forget) memory instead of O(n)
  • Each day: add new[t − delay], subtract the popleft'd new[t − forget], append today → three O(1) steps per day → O(n) time versus 499,500 additions to re-sum at n = 1,000
  • divmod(num, 1000) yields the lowest chunk first but it is read last → appendleft each chunk (O(1) on a deque) → no reversal or front inserts into a list
  • detail that matters Deque indexing is O(1) near the ends but O(n) in the middle → new[-delay] with delay near forget/2 on a huge window isn't free → a ring buffer new[t % forget] is O(1) everywhere
  • detail that matters Python ints don't overflow → the exact count is kept (301 digits) → LeetCode's version needs the answer mod 10⁹ + 7 because fixed-width languages would overflow

3 · Retrieve from memory, card closed
  1. concept Explain why this problem needs only a window of forget values, not a full DP table.
    Check
    • the recurrence reads new[t − delay] and new[t − forget], both within the last forget days
    • people who learned earlier have forgotten: they neither share nor count
    • so older values are never read again and can be dropped
  2. mechanism Walk through day 6 of the trace (n = 6, delay = 2, forget = 4): what is added, what is popped, what is appended, and what is the answer?
    Check
    • share was 1; add new[4] = 1 (C starts sharing): 2
    • popleft new[2] = 0 (nobody learned on day 2): still 2
    • append 2 (E and F learn)
    • aware = new[3..6] = 1 + 1 + 1 + 2 = 5
  3. tradeoff Re-summing the window each day gives the same answer. What does it cost at n = 1,000, forget = 1,000, and what does the running sum risk that re-summing doesn't?
    Check
    • re-summing: 499,500 additions, O(n · forget)
    • running sum: two updates per day, 2,997 operations
    • the running sum depends on reading new[−delay] before popping; an order bug corrupts every later day, whereas a re-sum recomputes from scratch

5 · Predict commit to an answer before revealing

Set delay = 1 and forget = n (nobody forgets in time, everyone shares from the day after learning). For n = 10, how many people know the secret at the end, and what pattern does the count follow?

Reveal

512 = 2⁹. From day 2 on, everyone who knows shares with one new person each day, so the number who know doubles daily: 1, 2, 4, …, 2ⁿ⁻¹. That doubling is why the card's n = 1,000 answer has 301 digits and why person-by-person simulation is hopeless.
