Linked lists of buckets

Also called a frequency list, count buckets or the "All O(1)" structure. The source guide's only Linked Lists problem, All O(1) Data Structure, keeps a C++ std::list of count buckets plus a map from each key to its bucket.

Prime · 2 minutes before you read

The problem: You need inc, dec, getMaxKey and getMinKey all in O(1). A dict of counts makes the max a scan of every key; a heap makes every change O(log n) with stale entries; a sorted list shifts O(n) items per change.

Where it fits: The last card of Lists, stacks and queues. It combines the hashing card's dict (find a key's bucket) with a linked list (keep counts in order), and it is the direct ancestor of the LFU cache in the Coding and design part.

In one breath

Keep one bucket per count that's in use, holding every key with that count, and chain the buckets in increasing order of count. A count only ever changes by 1, so a key only ever moves to the neighbouring bucket, and the list stays sorted without any sorting. The smallest count is right after the head and the largest is right before the tail.

A linked list splices in O(1) only if you already hold the node. C++ gives you that as a list::iterator; Python has no linked list with stable node handles, so we build a tiny doubly linked one and store the node itself in a dict.

Worked example: after inc a, inc b, inc a

inc a (count 1 → 2): cur = where["a"] # bucket 1, O(1) cur.next is tail, count 0 ≠ 2 → add bucket 2 after cur move "a" from bucket 1 to bucket 2; bucket 1 still has b, keep it getMaxKey → tail.prev = bucket 2 → "a" getMinKey → head.next = bucket 1 → "b"

Counts increase left to right and every bucket in the list is non-empty. Both sentinels carry count 0, which never equals a real count, so "is there already a bucket for count ± 1?" is one comparison with no special case at either end.

In Python

class AllOne:                  # Bucket: count, keys, prev, next
    def __init__(self):
        self.head, self.tail = Bucket(0), Bucket(0)  # sentinels
        self.head.next, self.tail.prev = self.tail, self.head
        self.where = {}          # key -> its bucket: the handle

    def _add_after(self, node, count):
        b = Bucket(count)        # 4 pointer writes, O(1)
        b.prev, b.next = node, node.next
        node.next.prev = b
        node.next = b
        return b

    def _drop(self, key, b):
        del b.keys[key]
        if not b.keys:           # unlink: 2 pointer writes, O(1)
            b.prev.next, b.next.prev = b.next, b.prev

    def inc(self, key):
        cur = self.where.get(key, self.head)   # new key: count 0
        nxt = cur.next           # sentinel counts are 0: never equal
        if nxt.count != cur.count + 1:
            nxt = self._add_after(cur, cur.count + 1)
        nxt.keys[key] = None
        self.where[key] = nxt
        if cur is not self.head:
            self._drop(key, cur)

    def dec(self, key):
        cur = self.where.pop(key)
        if cur.count > 1:
            prv = cur.prev
            if prv.count != cur.count - 1:
                prv = self._add_after(prv, cur.count - 1)
            prv.keys[key] = None
            self.where[key] = prv
        self._drop(key, cur)

    def get_max_key(self):     # get_min_key: head.next, same shape
        b = self.tail.prev
        return "" if b is self.head else next(iter(b.keys))
# inc a: [(1, ['a'])]  max='a' min='a'
# inc b: [(1, ['a', 'b'])]  max='a' min='a'
# inc a: [(1, ['b']), (2, ['a'])]  max='a' min='b'
# dec b: [(2, ['a'])]  max='a' min='a'

The source's dec tests it_prev->count != count before it_current == nodes.begin(), so when the key sits in the lowest bucket (inc a, inc a, dec a) it dereferences nodes.end(), which is undefined behaviour; the sentinels here make that an ordinary comparison. Corrected here.

Time O(1) per operation · Space O(n) for n keys. Each op does a constant number of dict operations and at most one splice in and one splice out, because a count moves by exactly 1. There are never more buckets than keys, since every bucket in the list is non-empty. O(1) here means average-case dict hashing, as with any hash map.

Why it beats the alternatives

✗ A dict of counts

inc and dec are O(1), but getMaxKey scans every key: 100,000 comparisons per call with 10⁵ keys.

✗ Two heaps (max and min)

O(log n) per change, about 17 levels for 10⁵ keys, and a count change can't update the old entry in place, so stale entries pile up and must be skipped lazily.

✗ A sorted list via bisect

Finding the key's slot is O(log n), but moving it shifts up to n items. insort is O(n) per inc.

✓ Linked buckets + handle

O(1) for all four operations. The ±1 steps mean a key only moves to a neighbour, so order is kept for free and max and min sit at the two ends.

Is it always the tool?

It relies on counts changing by exactly 1. If a key can jump by an arbitrary amount (add(key, 7)), the target bucket isn't a neighbour any more and you need a sorted structure again: a heap or a balanced tree, O(log n). The same count-bucket idea powers the LFU cache, where each count maps to an OrderedDict so ties break by least recently used.

For small n it's usually overkill: a plain dict plus max(d, key=d.get) is a few lines, and a scan over a few hundred keys is cheap. Linked nodes are also scattered in memory, so each hop is a pointer chase the CPU cache can't prefetch well. That's standard practice rather than something the source says.

Understand and remember

  • A linked list splices in O(1) only if you hold the node → a dict key → bucket node gives the handle → find and splice are both O(1)
  • Counts change by exactly ±1 → a key moves only to the adjacent bucket (count + 1 or count − 1) → create it right after or before if missing → the list stays sorted by count with no sorting → min is head.next, max is tail.prev
  • Empty buckets are unlinked at once → every bucket in the list is non-empty → at most one bucket per key → O(n) space and O(1) max/min without skipping
  • Sentinels carry count 0, which no real count equals → does the neighbour have count c ± 1? is one comparison at both ends → no special case at the list's edges (the source's C++ lacks this and reads past begin())
  • detail that matters Linked nodes are scattered in memory → each hop is a pointer chase the CPU cache can't prefetch → for a few hundred keys a plain dict plus max(d, key=d.get) is simpler and often faster

Reference only

  • the Bucket class fields (count, keys, prev, next)
  • storing keys in a dict for ordered O(1) removal
  • C++ list::iterator as the source's handle
  • the 4 and 2 pointer writes per splice
  • returning the first-inserted key when several share a bucket

vs LFU cache in O(1): All O(1) and LFU both keep a bucket per count. What does LFU add, why, and why can LFU use dict-of-OrderedDict instead of a linked list of buckets?

Check
  • LFU needs the least recently used key within the minimum count: an OrderedDict per bucket
  • LFU only asks for the minimum, which it tracks with a min integer (resets to 1 on insert, +1 when its bucket empties)
  • All O(1) needs both min and max, and counts can go down, so it links buckets in order
  • both rely on counts changing by exactly 1

vs Heaps and priority queues: Linked buckets vs a heap for tracking the max count: what does each cost per change, and what assumption lets the buckets win?

Check
  • heap: O(log n) per change, and an entry can't be updated in place, so stale entries are skipped lazily
  • buckets: O(1) per change, max at tail.prev
  • the buckets win only because counts move by ±1
  • the heap handles arbitrary priority changes

5 · Predict commit to an answer before revealing

Run inc a, inc a, inc b, dec a. Before tracing: what do get_max_key and get_min_key return, and why is the answer not decided by the counts alone?

Reveal

Both return b. After dec a, a and b both have count 1 and sit in the same bucket, and a bucket keeps insertion order: b entered bucket 1 first, a joined it second. With a tie the problem accepts any key, so which one you get depends on the bucket's ordering, not on the counts.
