Binary tree traversals

Also called tree walks: preorder, inorder, postorder (depth-first) and level order (breadth-first). The source guide's Binary section has two problems: inorder traversal done the Morris way in O(1) extra space, and Maximum Path Sum done with an iterative postorder.

Prime · 2 minutes before you read

The problem: Almost every tree question is a walk: print sorted keys, compute something from children, read row by row. Without a clear model of when a node is visited, you mix up the orders, and recursion on a deep tree crashes Python at about 1,000 levels.

Where it fits: The first card of Trees and heaps. It uses the parsing card's stack (DFS is a stack, explicit or the call stack) and the toolkit's deque (level order is BFS). The heap, Fenwick and segment-tree cards that follow are trees stored in arrays, walked with the same ideas.

In one breath

A depth-first walk visits every node three times: on the way down, between its two children, and on the way back up. Pre-, in- and postorder are just which of those three moments you write the value down. Level order is different: it reads the tree row by row with a queue.

The four orders on one tree

Picture walking around the outside of the tree, starting left of the root. You pass each node on its left side (pre), under it (in) and on its right side (post).

def orders(root):
    pre, ino, post = [], [], []

    def walk(n):
        if n is None:
            return
        pre.append(n.val)    # before both children
        walk(n.left)
        ino.append(n.val)    # between them
        walk(n.right)
        post.append(n.val)   # after both

    walk(root)
    return pre, ino, post

def level_order(root):
    out, q = [], deque([root] if root else [])
    while q:
        n = q.popleft()
        out.append(n.val)
        q.extend(c for c in (n.left, n.right) if c)
    return out
# pre   [4, 2, 1, 3, 6, 5, 7]   in    [1, 2, 3, 4, 5, 6, 7]
# post  [1, 3, 2, 5, 7, 6, 4]   level [4, 2, 6, 1, 3, 5, 7]

Time O(n) · Space O(h) or O(w). Every node is touched a constant number of times. The recursion holds one frame per level (h = 3 here, but n on a chain); the queue holds one row (w = 4 here).

Worked example: Morris inorder on a 5-node tree

The recursion (or an explicit stack) exists only to remember where to go back up to. Morris stores that instead in the tree's empty right pointers: before going left, point the rightmost node of the left subtree back at yourself. A tree with n nodes has n + 1 empty child pointers, so there is always room.

Node 3 is the rightmost node of 4's left subtree, so it is 4's inorder predecessor: 4 comes right after 3. The thread 3 → 4 is how the walk gets back to 4 once 3 is done.

def morris_inorder(root):
    out, cur = [], root
    while cur:
        if cur.left is None:          # nothing on the left
            out.append(cur.val)
            cur = cur.right           # may follow a thread
            continue
        pred = cur.left               # rightmost of left subtree
        while pred.right and pred.right is not cur:
            pred = pred.right
        if pred.right is None:        # 1st visit: lay thread
            pred.right = cur
            cur = cur.left
        else:                         # 2nd visit: remove it
            pred.right = None
            out.append(cur.val)
            cur = cur.right
    return out

print(morris_inorder(build([4, 2, 5, 1, 3])))  # → [1, 2, 3, 4, 5]

Time O(n) · Space O(1). The predecessor searches walk each left subtree's right spine twice in total (once to thread, once to unthread), so the extra work is bounded by the edges. Counted: 7 moves + 6 predecessor steps for these 5 nodes; 1,999 + 1,998 = 3,997 for a 1,000-node chain.

Worked example: Maximum Path Sum on [−10, 9, 20, null, null, 15, 7] → 42

A path can bend at one node, taking an arm down each side. So every node answers two questions from its children's answers, which is why this needs postorder.

The stack pushes the left child, then the right, so the right subtree pops first (7, 15, 20), then 9, then the root. The best path skips the root: going through −10 only reaches 34.

def max_path_sum(root):
    best = -sys.maxsize
    gain = {None: 0}                         # best downward path
    stack = [(root, False)]
    while stack:
        node, seen = stack.pop()
        if not seen:                         # children first
            stack.append((node, True))
            stack += [(c, False) for c in (node.left, node.right) if c]
            continue
        left = max(gain[node.left], 0)       # drop negative arms
        right = max(gain[node.right], 0)
        best = max(best, node.val + left + right)  # bend here
        gain[node] = node.val + max(left, right)   # or pass one up
    return best

print(max_path_sum(build([-10, 9, 20, None, None, 15, 7])))  # → 42

Same algorithm as the source's; it is correct. Renamed node_sum to gain and seeded gain[None] = 0 in place of its .get(…, 0).

Time O(n) · Space O(n). Each node is pushed twice and popped twice, and gain holds one number per node. It is iterative so that a 1,000-deep tree can't hit Python's recursion limit.

Why Morris beats the alternatives (for O(1)-space inorder)

✗ Recursion

Shortest to write, but uses one call frame per level. On a 1,000-node chain the recursive walk raises RecursionError under Python's default limit of 1,000 (ran it).

✗ Explicit stack

Safe from the limit and the usual interview answer, but still O(h) memory: 1,000 nodes on the stack for that chain, 18 at peak for a random 1,000-node tree (computed).

✗ Parent pointers

Walk up via node.parent with O(1) extra space during the walk. The catch: every node carries one more pointer forever, and every insert and delete has to keep it right.

✓ Morris threading

O(1) extra space, no new fields: it borrows the n + 1 empty right pointers and gives them back. The 1,000-node chain finishes in 3,997 pointer steps with no stack at all.

Is Morris always the tool?

No. Morris writes to the tree while it reads it. Another thread reading the tree at the same time sees the temporary threads as real edges, and a read-only or shared tree can't be walked this way at all. If you break out early (say, at the k-th smallest), the threads you laid stay in the tree unless you finish the loop. It also chases more pointers: 3,483 steps on a random 1,000-node tree (computed), against one push and one pop per node for a stack walk.

In practice (not from the source): use recursion when the tree is balanced (depth ≈ log₂ n, so about 20 for a million nodes), an explicit stack when it might be deep, and Morris only when asked for O(1) space. Preorder Morris is the same loop, writing the value when the thread is laid (and when there is no left child). Postorder, which Maximum Path Sum needs, has no simple Morris form, so an explicit stack stays the default there.

Understand and remember

  • A depth-first walk passes each node three times (down, between children, up) → writing the value at the first, second or third pass gives pre-, in- or postorder → level order is different: a FIFO queue reads row by row
  • A stack (or recursion) exists only to remember where to go back up → Morris stores that in the predecessor's empty right pointer (n + 1 of them exist) → first visit lays the thread, second visit finds it and removes it → O(1) extra space, tree restored
  • A value that depends on both children (best path bending here) must wait until both are done → postorder → through(v) = x + max(0, gL) + max(0, gR), but only x + max(0, gL, gR) can be passed up, since a path can bend only once
  • Recursion depth = tree height → a 1,000-node chain exceeds Python's default limit and raises RecursionError → an explicit stack costs O(h) memory but no crash; Morris costs O(1)
  • detail that matters Morris writes into the tree while reading it → concurrent readers see threads as real edges, and stopping early leaves threads behind → use it only when asked for O(1) space on a tree you own
  • detail that matters max(0, …) drops negative arms → a negative subtree never helps a path → best must start at −∞, not 0, or an all-negative tree returns 0
