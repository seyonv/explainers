LFU cache in O(1)

Also called a least-frequently-used cache, or an LFU cache with LRU tie-breaking. The source guide asks for LeetCode's version under Object-oriented Design: get and put in Θ(1), a use counter per key, and ties broken by least recently used.

Prime · 2 minutes before you read

The problem: An LFU cache must evict the key used least often, breaking ties by least recently used, in O(1). Scanning all keys on eviction is O(n); a heap of (count, time) is O(log n) and fills with stale entries because every touch changes a key's priority.

Where it fits: The first Coding and design card. It is the linked-bucket-list idea (one bucket per count, counts move by 1) with an OrderedDict per bucket for the recency tie-break, and a single min integer instead of a linked list of buckets.

In one breath

When the cache is full, throw out the key used the fewest times, and among equals the one untouched for longest. The trick for O(1) is to never sort: keep one bucket of keys per use count, each bucket in recency order, and remember the smallest count in use. The victim is always the oldest key in that bucket.

Worked example: capacity 2, just before put(4, 4)

victim = keys[min].popitem(last=False) # smallest count, then oldest here: keys[2] = [1, 3] → victim 1 (count 2 = 2, but 1 was used at op 3, 3 at op 6)

Each get or put on a key moves it from bucket c to the end of bucket c + 1. A new key always enters bucket 1, so after an insert min is 1.

In Python

from collections import OrderedDict, defaultdict

class LFUCache:
    def __init__(self, capacity):
        self.cap = capacity
        self.val = {}                        # key -> value
        self.cnt = {}                        # key -> use count
        self.keys = defaultdict(OrderedDict)  # count -> keys, LRU first
        self.min = 0                         # smallest count in use

    def _touch(self, key):                   # count += 1, move bucket
        c = self.cnt[key]
        del self.keys[c][key]
        if not self.keys[c]:
            del self.keys[c]
            if self.min == c:
                self.min = c + 1             # key went to c + 1
        self.cnt[key] = c + 1
        self.keys[c + 1][key] = None         # newest in its bucket

    def get(self, key):
        if key not in self.val:
            return -1
        self._touch(key)
        return self.val[key]

    def put(self, key, value):
        if self.cap <= 0:
            return
        if key in self.val:
            self.val[key] = value
            self._touch(key)
            return
        if len(self.val) == self.cap:        # evict: min count, LRU
            old, _ = self.keys[self.min].popitem(last=False)
            if not self.keys[self.min]:
                del self.keys[self.min]
            del self.val[old], self.cnt[old]  # the evicted key
        self.val[key], self.cnt[key] = value, 1
        self.keys[1][key] = None
        self.min = 1
# get(3)     -> 3   buckets={2: [1, 3]} min=2
# put(4, 4)         buckets={1: [4], 2: [3]} min=1
# 1000 random op sequences match brute force

The source's Java evicts with key_count.remove(key), the new key, where it should remove lfu. Answers stay right (a line-for-line port matches the brute force on 1,000 random sequences), but evicted keys' counts are never freed: after 1,000 distinct puts into a capacity-2 cache its count map holds 1,000 entries, not 2. Corrected here. It also never deletes empty count buckets, and with capacity 0 it looks up the missing bucket 0 (a null in Java).

Time O(1) per get/put · Space O(capacity). Every step is a fixed number of dict and OrderedDict operations (O(1) average-case hashing), and a count only ever moves by 1, so min can only reset to 1 on insert or step up by 1 when its bucket empties. Nothing is ever searched.

Why it beats the alternatives

✗ Dict + scan on evict

Store (value, count, last use) and take min over all keys when full. Correct, and it is the brute force the code tests against, but every eviction is O(n): a pass over all 10,000 keys at capacity 10⁴.

✗ Heap of (count, time)

O(log n) per op, about 14 levels at 10⁴ (log₂ 10⁴ = 13.3). Every touch changes a key's priority, so old heap entries go stale and must be skipped lazily.

✗ Plain LRU

O(1) with one OrderedDict, but a different policy. On this trace it happens to evict the same keys (2, then 1), purely by age: a key read 100 times is evicted after one quiet stretch.

✓ Count buckets + min

O(1) for both ops. Counts step by exactly 1, so a key only hops to the neighbouring bucket, and the victim is always at the front of bucket min.

Is exact LFU what real caches use?

Rarely. Exact LFU never forgets: a key that was hot yesterday keeps its big count and squats in the cache, while every newcomer enters at count 1 and is the next victim (key 4 above is first in line the moment it arrives). If the access pattern shifts, the hit rate suffers until the old counts are outgrown.

Production caches approximate it and add decay. Redis's allkeys-lfu keeps a few-bit probabilistic (Morris) counter per key that decays over time and evicts from a random sample, not an exact minimum. TinyLFU keeps approximate frequencies in a Bloom-filter-like sketch and uses them to decide whether a newcomer is worth admitting. Plain LRU remains the default when recency predicts reuse, as with most web and page caches. The exact structure here is the interview answer and a fine choice for small, stable workloads.

Understand and remember

  • Each touch raises a key's count by exactly 1 → it moves from bucket c to bucket c + 1 → appending puts it at the newest end → each bucket is in recency order for free → the LRU tie-break is popitem(last=False)
  • min tracks the lowest non-empty bucket → a new key enters at count 1, so min = 1 after insert → otherwise min changes only when its bucket empties during a touch, and then the key went to min + 1 → no search for the minimum, ever
  • Evict = keys[min].popitem(last=False), then delete from val and cnt → all steps are dict or OrderedDict operations → O(1) average per get and put
  • Exact counts never decay → yesterday's hot keys squat with big counts while newcomers enter at 1 and are evicted first → production caches approximate LFU with decaying or sampled counters (Redis allkeys-lfu, TinyLFU)
  • detail that matters Update an existing key before checking capacity → otherwise updating at capacity evicts a different key first (the bug the testing card hunts down)
