Fenwick tree (binary indexed tree)

Also called a BIT or a Fenwick array. An array of partial sums, sized by the lowest set bit of each index, that gives prefix sums and point updates in O(log n). The source guide uses its 2-D form for Range Sum Query 2-D – Mutable, under Trees.

In one breath

Store, at each index i, the sum of a block of the array that ends at i and is as long as i's lowest set bit. Any prefix 1..i then splits into one block per 1-bit of i, and any single element sits inside one block per level, so both counts stay at most ⌊log₂ n⌋ + 1. So both a sum and an update touch only a handful of cells.

In Python

class Fenwick:
    def __init__(self, n):
        self.t = [0] * (n + 1)       # t[0] unused

    def add(self, i, delta):         # a[i] += delta
        while i < len(self.t):
            self.t[i] += delta
            i += i & -i              # next node that covers i

    def query(self, i):              # a[1] + ... + a[i]
        s = 0
        while i > 0:
            s += self.t[i]
            i -= i & -i              # drop the lowest set bit
        return s

    def range_sum(self, lo, hi):     # a[lo] + ... + a[hi]
        return self.query(hi) - self.query(lo - 1)

f = Fenwick(8)
for i, v in enumerate([3, 2, -1, 6, 5, 4, -3, 3], 1):
    f.add(i, v)
print(f.t[1:], f.query(6))
f.add(3, 2)
print(f.t[1:], f.query(6), f.range_sum(3, 6))
# → [3, 5, -1, 10, 5, 9, -3, 19] 19
# → [3, 5, 1, 12, 5, 9, -3, 21] 21 16

Time O(log n) per query or update · Space O(n). A query does one step per 1-bit of i, so at most ⌊log₂ n⌋ + 1 steps; an update's index at least doubles its lowest bit each step, so it also stops within ⌊log₂ n⌋ + 1. For n = 10⁶ the worst cases are 19 query steps and 20 update steps (counted over every i by code/fenwick-tree.py's helpers). Building by n calls to add is O(n log n).

The source's problem: the same thing in 2-D

def update(self, row, col, val):
    delta, self.a[row][col] = val - self.a[row][col], val
    i = row + 1
    while i <= self.m:
        j = col + 1
        while j <= self.n:
            self.t[i][j] += delta
            j += j & -j
        i += i & -i

def _sum(self, r, c):            # cells above-left of (r, c)
    s, i = 0, r
    while i > 0:
        j = c
        while j > 0:
            s += self.t[i][j]
            j -= j & -j
        i -= i & -i
    return s

def sumRegion(self, r1, c1, r2, c2):
    return (self._sum(r2 + 1, c2 + 1) - self._sum(r1, c2 + 1)
            - self._sum(r2 + 1, c1) + self._sum(r1, c1))
# sumRegion(1,1,2,2) = 3; after update(1,2,0): 6

This follows the source's C++ line for line, including building by one update per cell. Its sign pattern and 1-offset are correct. 2-D cost: O(log m · log n) per operation, (m + 1)(n + 1) cells.

Why it beats the alternatives

✗ Plain array

Update is O(1), but a prefix sum adds up to n numbers: 10⁶ additions for query(10⁶).

✗ Prefix-sum array

Query is O(1), but changing a1 shifts every prefix: 10⁶ rewrites per update. Fine only if the data never changes.

✗ Segment tree

Also O(log n) for both, and it handles min, max and range updates. The cost is 2n to 4n cells and noticeably more code for a plain sum.

✓ Fenwick tree

O(log n) for both in n + 1 ints and a 15-line class: at most 19 reads per query and 20 writes per update at n = 10⁶.

Is it always the tool?

It fits when the operation can be undone, like + or XOR, so that a range is a difference of two prefixes, and when updates hit single cells. Counting inversions, order statistics over values (index by value and binary-search the tree), and running rank queries are standard uses. These are general practice, not from the source.

Use something else for range min or max (no inverse, so use a segment tree or a sparse table), for range updates with range queries (two Fenwick trees can do it, but a lazy segment tree is clearer), and for data that never changes (a plain prefix-sum array answers in O(1)).
