How to test your code

Also called hand-tracing, edge-case testing, differential or randomized testing (checking against a brute force), and property-based testing. The source guide's "How to Test Your Code" heading is empty, so this card supplies the method and tests it on the LFU cache from the same page.

Prime · 2 minutes before you read

The problem: The given example passes, the hand-picked edge case passes, and the code is still wrong: the LFU bug on this card survives both and fails 26 of 1,000 random cases. Code that returns wrong answers quietly is never caught by checking for crashes.

Where it fits: The last card of the course. It tests the structures you've built (the LFU cache, the monotonic stack, atoi) and turns the edge-case card's list into a checklist, then adds a brute force, an invariant and shrinking.

Builds on: LFU cache in O(1) · Corner cases: parsing numbers and passwords · Monotonic deque

You'll meet: hand-trace the example first the edge checklist: empty, one, repeats, negatives, max size, overflow differential testing against a brute force on small random inputs invariants for internal state shrinking a failure and freezing it in a test

By the end: Build a harness that compares your fast version to an obviously-right slow one on 1,000 tiny random cases, checks an invariant, and shrinks any failure to a handful of ops you can trace by hand.

Read with these questions (answer them in your head as you go; don't take notes line by line):

  5. What does shrinking do, and why keep the shrunk case as a permanent test?

In one breath

Walk the given example by hand, then try the inputs that break code: empty, one element, repeats, negatives, the largest size, overflow. Then write a slow version that is obviously right and compare the two on a thousand small random inputs. When they disagree, cut the failing input down to its smallest form and keep it as a permanent test.

Step 2: random cases against a brute force

The brute force stores (value, count, last use) per key and scans for the minimum on eviction: O(capacity) per op and too simple to get wrong. Keep inputs tiny (capacity 1–3, keys 0–4) so collisions and evictions happen constantly.

def random_case(rng):
    cap = rng.randint(1, 3)
    ops = []
    for _ in range(rng.randint(1, 12)):
        k = rng.randint(0, 4)                 # few keys: many hits
        ops.append(("get", k) if rng.random() < 0.5
                   else ("put", k, rng.randint(0, 9)))
    return cap, ops

def check(cls, cases=1000, seed=0):
    rng = random.Random(seed)             # seeded: reproducible
    wrong_out = bad_state = 0
    first = None
    for _ in range(cases):
        cap, ops = random_case(rng)
        got, c = run(cls, cap, ops)
        out_bad = got != run(Brute, cap, ops)[0]
        state_bad = set(c.cnt) != set(c.val)  # invariant
        wrong_out += out_bad
        bad_state += state_bad
        if (out_bad or state_bad) and first is None:
            first = (cap, ops)
    return wrong_out, bad_state, first

# LFU       wrong output    0   broken invariant    0
# BuggyLFU  wrong output   26   broken invariant    0
# LeakyLFU  wrong output    0   broken invariant  467

Cost: at most 1,000 × 12 = 12,000 ops per version, each O(capacity) ≤ O(3) in the brute force. The pytest run below, which includes one full 1,000-case check, took 0.02 s (one run on the author's M3).

Step 3: shrink the failure, then trace it by hand

The first failing case had 12 ops. Deleting one op at a time, and keeping each deletion that still fails, leaves 4:

def shrink(cls, cap, ops):
    i = 0
    while i < len(ops):
        smaller = ops[:i] + ops[i + 1:]
        if fails(cls, cap, smaller):
            ops = smaller
        else:
            i += 1
    return ops

Step 4: freeze it in a test file

def test_leetcode_example():

def test_update_does_not_evict():             # the shrunk failure
    ops = [("put", 0, 2), ("put", 4, 7), ("put", 4, 7), ("get", 0)]
    assert run(LFU, 2, ops)[0] == [None, None, None, 2]

    assert check(LFU)[:2] == (0, 0)

# same file with BuggyLFU     → 1 failed, 2 passed

pytest runs every test_* function and reports each failing assert with both sides. unittest (standard library) does the same with a TestCase class and self.assertEqual. The hypothesis library automates steps 2 and 3: you describe the inputs (for example, lists of ops), it generates random cases and shrinks any failure to a minimal one. It isn't installed on this machine, so it isn't run here.

Why it beats the alternatives

✗ Run the given example

Necessary, not enough. All three versions passed the 10-op example; it never updates a key and never breaks the count table.

✗ Only hand-picked edge cases

You test the cases you thought of, which are the ones you already handled. The update-at-capacity test passed the buggy version by luck of which key was evicted.

✗ Random inputs, check only for crashes

Fuzzing without a reference finds exceptions. Neither buggy version raised once in 1,000 cases: they return wrong answers quietly.

✓ Brute force + invariant + shrink

Caught both bugs: 26 wrong outputs and 467 broken invariants out of 1,000, each shrunk to 3–4 ops you can trace by hand.

Is random testing always worth it?

Not in a 45-minute interview. There, trace the example aloud, name the edge cases from the table, and say how you'd test further. Build the harness when you're practising, or when the fast version is subtle (caches, heaps, window structures) and a slow version is easy to write.

It needs a trustworthy oracle. When there's no brute force, check properties instead: the output of a sort is ordered and is a permutation of the input; a cache never holds more than its capacity. And comparing outputs alone missed the source's leak entirely: internal state needs its own invariant checks. That tiny inputs catch most bugs is our reading of these runs (both shrunk failures use capacity 2 and at most 3 keys), not a guarantee.

Understand and remember

  • You only hand-pick the cases you already thought of → those are the ones you handled → a slow, obviously-correct brute force compared on many random inputs finds the combinations you didn't → 26 wrong outputs of 1,000 for the buggy put
  • Tiny inputs (capacity 1–3, keys 0–4) → collisions, evictions and ties happen constantly → bugs that need a rare combination show up within a few ops
  • Some bugs leave outputs right but corrupt internal state → an invariant check (the count table holds exactly the cached keys) catches them → 467 of 1,000 for the source's leak, 0 by output comparison
  • A 12-op failure is hard to trace → delete one op at a time, keeping each deletion that still fails → a 4-op case you can trace on paper → freeze it as a named test so the bug can't return
  • detail that matters A random tester needs a trustworthy oracle → when there's no brute force, check properties instead (a sort's output is ordered and a permutation; a cache never exceeds capacity)

Check

  • robust design assumes some bugs and bad inputs will get through anyway
  • tests shrink the number of bugs; robustness limits the damage of the rest
  • an invariant check can serve both: in tests, and as an assertion in production

5 · Predict commit to an answer before revealing

Plant a bug in the monotonic deque: change the expiry test from dq[0] <= i − k to dq[0] < i − k. Before testing: will the card's example still pass, and what is the smallest input you can think of that fails?

Reveal

The card's example still passes. [2, 1] with k = 1 fails: the buggy version returns [2, 2] instead of [2, 1], because index 0 isn't expired at i = 1 (0 < 0 is false) and its 2 stays at the front. The bug only shows when the old front is still the largest value just after it should have expired, which small random tests hit often.

Why this step?

6 · Apply use the model, don't restate it

Write a harness for the monotonic deque: a brute force (max(nums[i:i+k]) per window), a generator of tiny cases (n 1–8, k 1–n, values 0–9) and a seeded loop over 1,000 cases. Run it on the correct version and on the planted < bug, then shrink the first failure by deleting one value at a time while k stays fixed.

Done when: The correct version has 0 failures; with random.Random(0) and that generator, the buggy one failed 370 of 1,000 cases in our run (your count depends on how you draw cases). Your shrinker reaches a case of at most 7 values, and you can also find the 2-value failure [2, 1], k = 1, by hand.

Hint

Deleting values with k fixed can't go below k values; shrinking k too gets you to [2, 1].
