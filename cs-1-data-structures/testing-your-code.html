How to test your code

Also called hand-tracing, edge-case testing, differential or randomized testing (checking against a brute force), and property-based testing. The cheat-sheet's "How to Test Your Code" heading is empty, so this card supplies the method and tests it on the LFU cache from the same page.

In one breath

Walk the given example by hand, then try the inputs that break code: empty, one element, repeats, negatives, the largest size, overflow. Then write a slow version that is obviously right and compare the two on a thousand small random inputs. When they disagree, cut the failing input down to its smallest form and keep it as a permanent test.

Worked example: one bug in an LFU cache, three ways to test for it

The bug: put checks "is the cache full?" before "is this key already here?", so updating an existing key can evict a different one. It's a common slip, and the problem's own example never updates a key.

Step 2: random cases against a brute force

The brute force stores (value, count, last use) per key and scans for the minimum on eviction: O(capacity) per op and too simple to get wrong. Keep inputs tiny (capacity 1–3, keys 0–4) so collisions and evictions happen constantly.

def random_case(rng):
    cap = rng.randint(1, 3)
    ops = []
    for _ in range(rng.randint(1, 12)):
        k = rng.randint(0, 4)                 # few keys: many hits
        ops.append(("get", k) if rng.random() < 0.5
                   else ("put", k, rng.randint(0, 9)))
    return cap, ops

def check(cls, cases=1000, seed=0):
    rng = random.Random(seed)             # seeded: reproducible
    wrong_out = bad_state = 0
    first = None
    for _ in range(cases):
        cap, ops = random_case(rng)
        got, c = run(cls, cap, ops)
        out_bad = got != run(Brute, cap, ops)[0]
        state_bad = set(c.cnt) != set(c.val)  # invariant
        wrong_out += out_bad
        bad_state += state_bad
        if (out_bad or state_bad) and first is None:
            first = (cap, ops)
    return wrong_out, bad_state, first

Cost: at most 1,000 × 12 = 12,000 ops per version, each O(capacity) ≤ O(3) in the brute force. The pytest run below, which includes one full 1,000-case check, took 0.02 s (one run on the author's M3).

Step 3: shrink the failure, then trace it by hand

The first failing case had 12 ops. Deleting one op at a time, and keeping each deletion that still fails, leaves 4:

def shrink(cls, cap, ops):
    i = 0
    while i < len(ops):
        smaller = ops[:i] + ops[i + 1:]
        if fails(cls, cap, smaller):
            ops = smaller
        else:
            i += 1
    return ops

# same file with BuggyLFU     → 1 failed, 2 passed

pytest runs every test_* function and reports each failing assert with both sides. unittest (standard library) does the same with a TestCase class and self.assertEqual. The hypothesis library automates steps 2 and 3: you describe the inputs (for example, lists of ops), it generates random cases and shrinks any failure to a minimal one. It isn't installed on this machine, so it isn't run here.

Why it beats the alternatives

✗ Run the given example

Necessary, not enough. All three versions passed the 10-op example; it never updates a key and never breaks the count table.

✗ Only hand-picked edge cases

You test the cases you thought of, which are the ones you already handled. The update-at-capacity test passed the buggy version by luck of which key was evicted.

✗ Random inputs, check only for crashes

Fuzzing without a reference finds exceptions. Neither buggy version raised once in 1,000 cases: they return wrong answers quietly.

✓ Brute force + invariant + shrink

Caught both bugs: 26 wrong outputs and 467 broken invariants out of 1,000, each shrunk to 3–4 ops you can trace by hand.

Is random testing always worth it?

Not in a 45-minute interview. There, trace the example aloud, name the edge cases from the table, and say how you'd test further. Build the harness when you're practising, or when the fast version is subtle (caches, heaps, window structures) and a slow version is easy to write.

It needs a trustworthy oracle. When there's no brute force, check properties instead: the output of a sort is ordered and is a permutation of the input; a cache never holds more than its capacity. And comparing outputs alone missed the source's leak entirely: internal state needs its own invariant checks. That tiny inputs catch most bugs is our reading of these runs (both shrunk failures use capacity 2 and at most 3 keys), not a guarantee.
