Corner cases: parsing numbers and passwords

Also called edge cases, boundary inputs or "the tricky tests". The source guide's Corner Cases section holds three problems where the algorithm is easy and the bugs live at the edges: String to Integer (atoi), Valid Number and Strong Password Checker.

Prime · 2 minutes before you read

The problem: atoi, Valid Number and Strong Password are easy algorithms with hard edges: an empty string, a lone sign, the first value past 2³¹ − 1, a dot in the exponent, a password that is too long and has runs. Patching each failing test one at a time misses the combinations.

Where it fits: A Coding and design card that pairs with the parsing stack: flat input needs stages or flags, not a stack. It sets up the testing card, which turns this card's edge list into a checklist and a random tester.

1 · atoi: four stages, then one boundary

The spec reads as four stages in order: skip spaces, take at most one sign, read digits until the first non-digit, clamp to [−2³¹, 2³¹ − 1]. Every tricky input stops at a different stage.

"-91283472332": the sign sets sign = −1, then ten digits are read; the tenth would make x a 10-digit number above 2147483647, so it stops and returns INT_MIN = −2147483648.

INT_MAX, INT_MIN = 2**31 - 1, -(2**31)

def my_atoi(s):
    i, n = 0, len(s)
    while i < n and s[i] == " ":        # 1. skip spaces
        i += 1
    sign = 1
    if i < n and s[i] in "+-":          # 2. at most one sign
        sign = -1 if s[i] == "-" else 1
        i += 1
    x = 0
    while i < n and "0" <= s[i] <= "9":  # 3. digits
        d = ord(s[i]) - ord("0")
        # 4. would 10*x + d pass 2147483647? check BEFORE multiplying
        if x > INT_MAX // 10 or (x == INT_MAX // 10 and d > 7):
            return INT_MAX if sign == 1 else INT_MIN
        x = 10 * x + d
        i += 1
    return sign * x

print(my_atoi("-91283472332"))   # → -2147483648

Python ints never overflow, so max(INT_MIN, min(INT_MAX, sign * x)) at the end also works; the early check is kept because interviewers ask for it. The i < n guards are new: C++ reads a '\0' past the end, Python raises IndexError. The source's global int div clashes with the C library's div() and fails to compile with Apple clang 17; renamed here.

2 · Valid number: four flags, one pass

Track digits (any digit seen), dot, e, and exp_ok (a digit seen after the e). Each character either updates a flag or breaks a rule. At the end, the string is valid if digits and exp_ok.

def is_number(s):
    digits = dot = e = False
    exp_ok = True                       # digits seen after the e
    for i, c in enumerate(s):
        if "0" <= c <= "9":
            digits = exp_ok = True
        elif c == ".":
            if dot or e: return False      # one dot, not in exponent
            dot = True
        elif c in "eE":
            if not digits or e: return False
            e, exp_ok = True, False
        elif c not in "+-" or (i and s[i - 1] not in "eE"):
            return False                # sign only at 0 or after e
    return digits and exp_ok
# all 20 source examples agree; equals an ASCII regex on all
# 3,906 strings over "1.e+-" of length ≤ 5

The source tests digits with str.isdigit(), which is also True for '²' and '٣', so its version accepts "²" and "1e²". That's harmless on LeetCode's ASCII-only inputs; tightened here to "0" <= c <= "9".

Time O(n) · Space O(1) for both parsers: one left-to-right pass, a few ints or flags of state.

3 · Strong password: three constraints, one formula

A strong password has 6–20 characters, a lowercase letter, an uppercase letter and a digit, and no run of 3 equal characters. The trick is that one edit can fix two problems at once: a replace in the middle of aaa can also add the missing uppercase letter. So the answer takes a max, not a sum.

steps= { max(m,6−n)n < 6: inserts also break runs max(m,R)6 ≤ n ≤ 20 (n−20)+max(m,R′)n > 20: deletions are forced
npassword length"aaa111": 6 mmissing character types, 0 to 3no uppercase: 1 Rreplaces to break runs: ∑ ⌊L / 3⌋ over runs of length L ≥ 3⌊3/3⌋ + ⌊3/3⌋ = 2 R′R after spending the forced deletions where they save the mostsee the table

"aaa111": n = 6, m = 1, R = 2, so steps = max(1, 2) = 2, e.g. "aaa111" → "aBa111" → "aBa1b1". The first replace fixes a run and the missing uppercase at once.

The mod-3 greedy, for n > 20. A run of length L needs ⌊L/3⌋ replaces. Deleting from it lowers that count only when L steps down from a multiple of 3, so a run with L mod 3 = 0 saves a replace after 1 deletion, L mod 3 = 1 after 2, and anything after 3. Spend deletions in that order. Illustrative password "aaaabbbbbbccccc12345678A" (n = 24, all three types present, m = 0):

RunLL mod 3Replaces beforeDeletions spentReplaces after
bbbbbb6021st pass: 1 (6 → 5)1
aaaa4112nd pass: 2 (4 → 2)0
ccccc5211 left over, < 3: saves nothing1
forced deletions 24 − 20 = 4; R = 2 + 1 + 1 = 4 → R′ = 1 + 0 + 1 = 2 smart: 4 + max(0, 2) = 6 delete 4 digits instead: 4 + max(0, 4) = 8
def strong_password(p):
    n = len(p)
    missing = 3 - (any(c.islower() for c in p)
                   + any(c.isupper() for c in p)
                   + any(c.isdigit() for c in p))
    runs = runs_of_3(p)                 # lengths of runs >= 3
    if n < 6:
        return max(missing, 6 - n)
    replace = sum(L // 3 for L in runs)
    if n <= 20:
        return max(missing, replace)
    delete = left = n - 20
    one = min(left, sum(L % 3 == 0 for L in runs))
    replace, left = replace - one, left - one      # 1 del saves 1
    two = min(left, 2 * sum(L % 3 == 1 for L in runs)) // 2
    replace, left = replace - two, left - 2 * two  # 2 del save 1
    replace -= left // 3                           # 3 del save 1
    return delete + max(missing, replace)

print(strong_password("aaa111"))                    # → 2
print(strong_password("aaaabbbbbbccccc12345678A"))  # → 6
# matches an exact BFS on all 5,461 strings over "abA1", length ≤ 6

The source never initialises mod[3] and counter[3], so it adds to whatever is on the stack: compiled with Apple clang at -O0 it returned 1804642434 for "aaa111" (one run on the author's M3; undefined behaviour, so the value varies). Corrected here with explicit counts.

Time O(n) · Space O(r). One pass finds the runs and the character types; the rest is arithmetic on r ≤ n/3 run lengths (keep three counters instead to get O(1) space).

Why a staged scan beats the alternatives

✗ int() / float() in a try

Python's grammar isn't the spec's. float accepts "1_0", " 1", "inf", "nan" and "٣"; int rejects "4193 with words" instead of reading 4193.

✗ A regex

Correct for Valid Number with re.ASCII, but without it Python's \d matches "٣.5". It also can't clamp, count runs or say which rule failed.

✗ Patch each failing test

An if per bug report. It passes the tests you wrote and misses the combinations: ".e1", "-2147483648", a password that is too long and has runs.

✓ One stage or flag per rule

Each rule of the spec is one line you can point at, so the edge-case list becomes a checklist of stages. One pass, O(n), and it clamps exactly where the spec says.

Should you parse by hand in real code?

Usually not. Hand-rolled parsers belong in interviews and in formats whose grammar differs from your language's. In production use int(), float(), decimal.Decimal or a real parser (JSON, CSV), then validate the range. If you must accept only ASCII digits, say so explicitly, since str.isdigit() and \d don't.

The password rules are the LeetCode problem's, not good policy. NIST SP 800-63B-4 says verifiers shall not impose composition rules such as mixing character types, and requires at least 15 characters for a password used alone (8 with multi-factor). Check length and a breached-password list instead.

Understand and remember

  • The spec is a sequence of rules → one stage (atoi) or one flag (Valid Number) per rule → one left-to-right pass → every tricky input stops at a stage you can name, so the edge list becomes a checklist
  • A 32-bit int can't hold 10·x + d before it's compared → check x > 214748364, or x = 214748364 and d > 7, first → clamp to 2³¹ − 1 or −2³¹ → Python ints never overflow, so the clamp must be written on purpose
  • One replace inside a run can also add a missing character type → for 6 ≤ n ≤ 20 the answer is max(missing types, Σ⌊L/3⌋) → inserts play the same double role when n < 6
  • Over 20 characters, deletions are forced → a deletion saves a replace only when a run steps down from a multiple of 3 → spend them on L mod 3 = 0 runs (1 deletion each), then mod 1 (2 each), then 3 at a time → n − 20 + max(missing, remaining replaces)
  • detail that matters str.isdigit() and regex \d accept Unicode digits like ² and ٣ → a validator that means ASCII must say so ("0" <= c <= "9" or re.ASCII)
