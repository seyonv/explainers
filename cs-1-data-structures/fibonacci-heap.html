Fibonacci heap

A min-priority queue made of a loose list of heap-ordered trees, with O(1) amortized insert and decrease-key (Fredman and Tarjan, 1987). The source guide gives it as a bare Java file, code/FibonacciHeap.java, with no notes and no example; that file does not compile, so this card rewrites it in Python.

In one breath

Be lazy until someone asks for the minimum to be removed. Insert just drops a one-node tree into the root list. Decrease-key just snips the node off and makes it a root. Only extract-min tidies up, merging trees of equal degree until at most one of each degree is left, and a "mark" on each node stops the snipping from leaving trees too thin.

Worked example: insert 5, 2, 9, 1, 5, 6, 8, 3, 7

The course array a = [5, 2, 9, 1, 5, 6] plus 8, 3, 7, so that extract-min leaves 8 nodes and one full tree. Then three decrease-keys that end in a cascading cut.

Each link puts the larger key under the smaller and uses up one root, so 8 roots take exactly 7 links. The inserts paid O(1) each but raised Φ by 1; extract-min's 7 links are paid for by Φ falling from 9 to 1. The last row cuts twice yet Φ drops by 2: each of those cuts unmarks a node (−2) and adds a root (+1), so a cascade pays for itself.

Why Fibonacci: a node's i-th child had degree ≥ i − 1 when it was linked (links only join equal degrees), and a mark lets it lose at most one child before it is cut itself, so the i-th child keeps degree ≥ i − 2. Those minimum sizes add up like Fibonacci numbers (CLRS lemma 19.4). Without the marks, cuts could leave a degree-k root with only k + 1 nodes, and extract-min would no longer be O(log n).

Both count n = 9, before extract-min decrements it (as CLRS does). In this very trace root 2 reaches degree 3, but the source's array has slots 0–2 only, so even with its loops fixed it would throw ArrayIndexOutOfBoundsException. Linking alone already needs floor(log2 n) + 1 slots; cuts push it up to the φ bound.

In Python: consolidate and decrease-key

    def _consolidate(self):
        size = int(math.log(self.n, PHI)) + 1   # floor(log_phi n)+1
        by_deg = [None] * size
        for x in _siblings(self.min):      # snapshot the root list
            while by_deg[x.degree] is not None:
                y = by_deg[x.degree]
                by_deg[x.degree] = None
                if y.key < x.key:
                    x, y = y, x
                self._link(y, x)           # larger key goes under
            by_deg[x.degree] = x
        roots = [x for x in by_deg if x is not None]
        self.min = min(roots, key=lambda r: r.key)

    def decrease_key(self, x, key):
        assert key <= x.key
        x.key = key
        p = x.parent
        if p is not None and x.key < p.key:
            self._cut(x, p)
            while p.parent is not None:    # cascading cut
                if not p.mark:
                    p.mark = True          # first child lost: mark
                    break
                q = p.parent               # second child lost: cut
                self._cut(p, q)
                p = q
        if x.key < self.min.key:
            self.min = x

The source's Java does not compile (Node<T> for Node<E>; undefined z, d and cut; current declared twice; return currents). Its two list walks start at their own stop node, while (current != min), so they never run: children are never promoted and roots never merged. Its degree array is floor(log2 n) long. All corrected here.

Time: insert, find_min, decrease_key O(1) amortized; extract_min O(log n) amortized · Space O(n). Insert and cut add a root and raise Φ by 1 or 3; consolidate spends that stored credit, and what's left is bounded by the number of degree slots, O(log n). Each node carries 7 fields: key, parent, child, left, right, degree, mark.

Why it beats the alternatives (on paper)

✗ Unsorted array

O(1) insert and decrease-key, but O(n) extract-min. Dijkstra becomes O(V²): fine when E ≈ V², far too slow on sparse graphs.

✗ Binary heap with decrease-key

Every decrease-key sifts up O(log V), and needs a key→index map kept in sync on every swap. Dijkstra O(E log V).

✗ heapq with lazy deletion

Push a duplicate instead of decreasing; skip stale pops. Simplest, but the heap can hold up to E entries: O(E log E) = O(E log V).

✓ Fibonacci heap

Decrease-key is a cut, O(1) amortized, so the E term loses its log: Dijkstra and Prim become O(E + V log V), the reason it was invented.

So should you use one?

Almost never in real code. The win is asymptotic: it needs decrease-keys to dominate, as on very large dense graphs (our reading). Each node is 7 fields reached by pointer chasing, versus heapq's flat array of tuples maintained in C, and Fibonacci heaps have a reputation for being slow in practice because of those constants and memory per node (Wikipedia). For Dijkstra in Python, use heapq with lazy deletion; for small integer weights, a bucket queue (Dial's algorithm) is simpler still. These last recommendations are standard practice, not from the source.

Where it does matter: complexity arguments in interviews and papers ("Dijkstra is O(E + V log V) with a Fibonacci heap"), and as background for its simpler, self-adjusting cousin, the pairing heap. Know the four ideas (lazy root list, consolidate by degree, cut, marks), not the code.
