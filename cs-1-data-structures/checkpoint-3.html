Checkpoint 3: hash to find, order to choose

Ties together RandomizedCollection, linked lists of buckets, the LFU cache, random pick with a blacklist, the read4 reader and how to test your code: small designs where a dict finds the thing, a second structure decides what comes next, and a test harness proves the two stay in sync.

How to use this page. Close the six cards. Answer each question in writing, in full sentences, before opening its Check. A wrong or shaky answer isn't a failure; it tells you exactly which section to reopen. The questions are mixed on purpose, so you have to work out which idea applies before you can answer.

1 · Mixed retrieval

  1. which concept?A social feed shows, at all times, the most-liked and the least-liked post. Every event is a single like or unlike, so a post's count changes by exactly 1. You need every operation in O(1). Which design, and what breaks if a moderator can add 50 likes at once?
    Check
    • linked count buckets plus a dict from post to its bucket (the All O(1) structure)
    • a ±1 change only moves a post to the neighbouring bucket, so the list stays sorted for free; max and min sit at the two ends
    • a jump of 50 lands in a non-neighbouring bucket that must be found by walking: switch to a heap or balanced tree, O(log n)

    Missed it? Reopen linked lists of buckets, "Is it always the tool?".

  2. In RandomizedCollection, remove fills the hole with the last item. Why must the code add the hole's index to the last item's set before discarding the old last index?
    Check
    • if the removed copy is itself the last item, the hole index and the last index are the same
    • adding then discarding leaves that index out, which is right because the slot is about to be popped
    • discarding first and then adding would leave a stale index pointing past the end of the list

    Missed it? Reopen Big-O and amortized O(1), "In Python" and the note under it.

  3. which concept?A cache must evict the item used the fewest times, and among equals the one untouched longest, in O(1). The cache holds {1: count 2, 3: count 2}, key 1 was last used before key 3, and a new key arrives. Which design, which key goes, and what is the minimum count right after?
    Check
    • LFU: a dict of values and counts, an OrderedDict of keys per count, and a min integer
    • the victim is the front of the min bucket: key 1 (count 2, older use)
    • the newcomer enters bucket 1, so min resets to 1, and the newcomer is the next victim

    Missed it? Reopen the LFU cache, the worked example.

  4. Build the blacklist sampler for n = 8, blacklist = [0, 5]. What are m and the remap, and why is every allowed value picked with probability exactly 1/m?
    Check
    • m = 8 − 2 = 6; both 0 and 5 are below m, so both are holes
    • walking down from 7: 0 ↦ 7, then 5 ↦ 6; remap {0: 7, 5: 6}
    • the draws 0…5 map one-to-one onto the six allowed values 1, 2, 3, 4, 6, 7, so each has probability 1/6

    Missed it? Reopen random pick with a blacklist, the constructor trace.

  5. Two files are open through the source's global-buffer read4 reader. File A starts "abcd…" and file B starts "wxyz…". A.read(1), then B.read(2). What does B get, and what is the fix?
    Check
    • A.read(1) pulls a whole chunk "abcd" into the one shared buffer and returns "a"
    • B.read(2) finds leftovers in that buffer and returns "bc", A's characters, not "wx"
    • fix: the buffer and its cursors belong to each reader object

    Missed it? Reopen the read4 reader, "Why it beats the alternatives".

  6. which concept?Your All O(1) structure passes the problem's example, and your own three edge tests. You suspect a bug when a key in the lowest bucket is decremented. What do you build to find it, and what does each part catch?
    Check
    • a brute force (a plain dict of counts) and a generator of tiny random op sequences over a few keys
    • compare max and min after every op to catch wrong answers; check an invariant (every live key's bucket holds it, no empty buckets) to catch bad state
    • shrink the first failure op by op and freeze it as a named test

    Missed it? Reopen how to test your code, steps 2–4.

  7. An LFU put checks is the cache full? before is this key already here?. On what kind of input does that go wrong, and why did the given example never show it?
    Check
    • updating an existing key while the cache is full evicts some other key first
    • the shrunk case: capacity 2, put(0, 2), put(4, 7), put(4, 7), get(0) returns −1 instead of 2
    • the example never updates a key, so the order of the two checks never matters there

    Missed it? Reopen how to test your code, the worked example, and the LFU cache's put.

3 · Project: a counter with O(1) max, min and random key

What it reinforces: count buckets with a handle (linked lists of buckets), swap-with-last for a dense random pick (RandomizedCollection, blacklist), the ±1 argument shared with the LFU cache, and a brute force, an invariant and shrinking (how to test your code).

Extend the All O(1) class with random_key(): return a uniformly random key among those with count ≥ 1. Every operation must stay O(1).

  1. Dense list. Keep a list keys of live keys and a dict pos from key to its index. A key enters the list when its count goes 0 → 1 and leaves when it goes 1 → 0, by moving the last key into its slot.
  2. Trace. Run inc a, inc b, inc c, inc a, dec b and write, after each op, the buckets, keys, pos, max and min.
  3. Uniformity. After inc a, inc a, inc b, inc c, draw 30,000 random keys with a seeded generator and compare with 10,000 each. Is this pick uniform over keys or weighted by count? Which card's structure would you need for the other?
  4. Test it. Write a dict-of-counts brute force and 1,000 random sequences of up to 12 ops over keys a–d (never dec a key at 0). After every op, check max, min, the live key set and the invariant keys[pos[x]] == x.
  5. Break it. Delete the line that updates pos for the moved key, rerun, and shrink the first failure op by op.
Done when: your trace matches the check, the correct version passes all 1,000 sequences, the broken one fails and shrinks to a sequence you can trace on paper, and you can say whether your random pick is uniform or weighted. Then compare with the check.
Check: the numbers (computed with a Python version of exactly these steps, built on the card's AllOne class)
  • Trace buckets: [1:{a}] → [1:{a, b}] → [1:{a, b, c}] → [1:{b, c}, 2:{a}] → [1:{c}, 2:{a}]. After dec b, c moved into b's slot: keys = [a, c], pos = {a: 0, c: 1}; max a, min c.
  • 30,000 draws with random.Random(2026): a 10,133, b 10,055, c 9,812. The pick is uniform over keys even though a has count 2; a pick weighted by count needs one list entry per copy, as RandomizedCollection keeps.
  • Correct version: 0 failures in 1,000 sequences (seed 0).
  • Broken version: 410 of 1,000 sequences fail the invariant. The first failure shrinks to 3 ops: inc d, inc c, dec d. Removing d moves c into slot 0, but pos[c] still says 1, which is now past the end of the list.
