Hashing and buckets

Also called a hash table, hash map or hash set; Python's dict and set. The source guide's Sets, Tables and Dictionary headings are empty; its one bucket problem is Contains Duplicate (LeetCode's Contains Duplicate III), at the top of Sorting.

In one breath

A hash function turns a key into a number, and that number picks one bucket out of m. To find the key later you recompute the number and look in that single bucket instead of scanning everything. The same trick works with any "bucket id" you choose: bucket numbers by value range and two values in one bucket are guaranteed to be close.

Worked example 1: a = [5, 2, 9, 1, 5, 6] into 8 buckets

5 % 8 = 5 2 % 8 = 2 9 % 8 = 1 1 % 8 = 1 (collides) 5 → bucket 5, found 6 % 8 = 6 load factor α = keys / buckets = 5 / 8 = 0.625

Finding 1 later means computing 1 % 8 = 1 and searching one bucket of two keys, not six. Separate chaining, as drawn, is the textbook picture; CPython's dict and set store a colliding key in another free slot instead (open addressing). The table size 8 is illustrative.

Worked example 2: Contains Duplicate III

Is there a pair with indices at most indexDiff apart and values at most valueDiff apart? Hash by value range: bucket width w = valueDiff + 1.

So each step checks its own bucket and two neighbours, and each bucket holds at most one value (a second one would already be an answer). Floor division puts negatives in the right bucket too: −1 // 4 = −1.

In Python

def contains_near_dup(nums, index_diff, value_diff):
    w = value_diff + 1           # bucket width: same bucket => close
    seen = {}                    # bucket id -> the one value in it
    for i, x in enumerate(nums):
        b = x // w
        if b in seen:
            return True          # same bucket: |x - y| <= value_diff
        for nb in (b - 1, b + 1):   # neighbours may also be close
            if nb in seen and abs(x - seen[nb]) <= value_diff:
                return True
        seen[b] = x
        if i >= index_diff:      # drop the value leaving the window
            del seen[nums[i - index_diff] // w]
    return False

print(contains_near_dup([1, 5, 9, 1, 5, 9], 2, 3))   # → False
print(contains_near_dup([1, 5, 9, 1, 5, 9], 3, 3))   # → True

The source's version is correct (it matched a brute force on 1,000 random cases), but its defaultdict adds a placeholder key on every neighbour lookup, so its map ends this trace with 4 keys, 2 of them fake; b in seen avoids that.

Time O(n) · Space O(min(n, indexDiff)). Each step does at most three O(1) average dict lookups, one insert and one delete, and the map never holds more than indexDiff + 1 values because each bucket holds one.

Why it beats the alternatives

✗ Check every pair in the window

Compare x with the last indexDiff values. O(n · indexDiff): 949,995,000 comparisons for n = 10⁵, indexDiff = 10⁴.

✗ A set of exact values

Only finds equal values. For valueDiff = 3 you'd probe x − 3 … x + 3, 7 lookups per step, and O(valueDiff) per step in general.

✗ A sorted window

Binary-search the nearest value: O(n log k) with a balanced tree (C++ multiset). Python has none built in, and bisect.insort into a list shifts O(k) items.

✓ Value buckets

One dict, three lookups per step, O(n) average. For the trace above: 6 steps, 6 neighbour checks, no sorting.

Is a hash table always the answer?

No. Hashing throws order away. If you need the smallest key, the next key above x, sorted output or a range query, use a sorted structure (a heap, bisect on a list, a tree). If the keys are small dense integers, a plain array indexed by the value is faster and has no collisions at all: see the array-as-its-own-hash-table card. And O(1) is an average: keys chosen to collide on purpose can make every lookup O(n), which is why Python salts string hashes.

The bucket trick itself needs integer-like values and a fixed tolerance. If valueDiff changes per query, or you want the closest pair rather than any close pair, go back to the sorted window.
