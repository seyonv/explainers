Choosing a data structure

The overview for course 1 of the CS core reference series. It ties together the 20 cards on the source guide's Coding and Data Structures pages: which structure to reach for, what each one costs, and how much the choice changes your running time on real inputs.

In one breath

Name the operation you will repeat most (find by key, take the smallest, slide a window, sum a prefix), then pick the structure that makes that operation cheap. Every hard problem in this course is one or two cheap operations glued together, usually a hash map to find a thing plus an ordered structure to decide which one comes next.

The words people use

Worst case vs average

Worst case bounds every single call; average (expected) bounds a typical call over random inputs or random choices. Hash lookups are O(1) average, O(n) worst.

O vs Θ

O is an upper bound, Θ is tight. Interviewers say "O" and mean Θ: "merge sort is O(n log n)" means it is also never faster than that order.

In-place, stable

In-place: O(1) extra memory (heapsort, Morris traversal). Stable: equal keys keep their order (Timsort, merge sort). Two words that settle most "which one" follow-ups.

✓ Amortized

The cost averaged over a whole sequence of operations. It's why list.append, dict insert, the monotonic stack and the deque are all "O(1)" even though single calls can be slow.

When this advice doesn't apply

Big-O ranks structures for large n. For a handful of items the constant factors win: a short list scan can beat building a dict, and CPython's own Timsort switches to insertion sort for runs under 64 items. Measure before you replace simple code.

In production, reach for a library before a hand-built structure: sortedcontainers.SortedList instead of a hand-rolled balanced tree, functools.lru_cache instead of your own LRU, heapq instead of a Fibonacci heap. The interview versions on these cards teach the idea; the library versions are tested and usually faster.
