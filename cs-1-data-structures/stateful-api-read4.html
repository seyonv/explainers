Designing a stateful API: read4

Also called a buffered reader, or "Read N Characters Given read4 II: call multiple times". You may only read a file 4 characters at a time, and must serve reads of any size. The source guide's APIs section solves it in C++ with global variables.

Prime · 2 minutes before you read

The problem: read4 hands over 4 characters whether you wanted them or not and can't rewind. A read(n) that keeps no state loses the extras for good: read(1) then read(6) returns "efghij" and "bcd" is gone. Keeping the extras in globals breaks as soon as there are two files.

Where it fits: A Coding and design card about state rather than a structure. The leftover buffer is a tiny queue (the deque cards), and the question of who owns it leads to cs-4's cards on encapsulation and API layers.

In one breath

read4 hands you 4 characters whether you wanted them or not, and it can't rewind. So when a caller asks for fewer, the extras must be kept somewhere until the next call. That "somewhere" is state, and the design question is who owns it: the reader object, not the program's globals.

Worked example: file "abcdefghij", then read(1), read(6), read(5)

The two sets of brackets don't line up. Every time a read call ends inside a read4 chunk, the rest of that chunk (green) has to wait in a buffer.

In Python

class Reader:
    def __init__(self, read4):
        self.read4 = read4
        self.buf4 = [""] * 4   # chars read4 gave us, not yet returned
        self.i = 0             # next unread slot in buf4
        self.m = 0             # how many slots the last read4 filled

    def read(self, buf, n):
        j = 0
        while j < n:
            if self.i == self.m:            # leftover used up: refill
                self.m, self.i = self.read4(self.buf4), 0
                if self.m == 0:             # end of file
                    break
            take = min(n - j, self.m - self.i)
            buf[j:j + take] = self.buf4[self.i:self.i + take]
            j += take
            self.i += take
        return j

The source's C++ is correct for one file; the change here is where the state lives: its globals i, m, buf4 become fields of Reader.

Time O(n) per call · Space O(1). Each character is copied once, and a call makes at most ⌈n/4⌉ + 1 read4 calls (checked on 1,000 random files and call sizes against plain slicing). The state is 4 characters and two integers, whatever the file size.

Why it beats the alternatives

✗ Keep no state

The one-shot answer: call read4, copy what fits, drop the rest. read(1) → "a", then read(6) → "efghij" and read(5) → "". "bcd" is gone for good, since read4 can't rewind.

✗ Keep it in globals

The source's C++. Right for one file, but every reader shares one buffer. Two files: A.read(1) → "a", then B.read(2) → "bc", A's leftovers, not "wx". Tests must also reset the globals between cases.

✗ Read everything first

Pull the whole file into a string, then slice. Simple, but memory grows with the file, the first read waits for all of it, and an endless stream (a socket, a pipe) never finishes.

✓ State on the object

Each Reader owns its 4-slot buffer and two cursors. Any number of files at once, O(1) extra memory, and a fresh object is a clean test.

The two-file run is our Python copy of the source's globals fed two read4 functions; in the source read4 is itself global, so it can't open a second file at all. The outputs are from code/stateful-api-read4.py.

Is a stateful API always the right design?

Only when the layer below forces it, as read4 does by handing over more than you asked for. Stateless calls are easier to retry, cache and share between threads, which is why web APIs usually hand the state back to the caller as a cursor or page token instead of remembering it. That's the same leftover-and-position pair, just held by the client.

This Reader is also not thread-safe: two threads calling read on one object can both copy the same slot before either moves i. Use one Reader per thread or a lock. And in real Python you don't write it at all: open() already returns a BufferedReader that does exactly this.

Understand and remember

  • read4 fetches whole chunks and can't rewind → a read that stops mid-chunk leaves characters already fetched but not returned → they must survive until the next call → that leftover is state
  • Keep a 4-slot buffer with cursors i (next unread) and m (filled) → copy from the buffer first, refill only when i == m → each character copied once → O(n) per call, at most ⌈n/4⌉ + 1 read4 calls
  • read4 returning 0 means end of file → stop and return what you have → short reads are normal, not errors (os.read and pipes behave the same)
  • State in globals is shared by every reader → two files mix leftovers → put the buffer and cursors on the object → any number of readers, O(1) extra memory each, and a fresh object is a clean test
  • detail that matters Two threads calling read on one object can copy the same slot before either advances i → a race → one Reader per thread or a lock around read
