Quantization

Also known as Q4_K_M, Q8_0, FP8, FP4 and "4-bit". Your qwen3.5:4b is Q4_K_M, and OpenRouter lists each provider's quantization (bf16, fp8, fp4).

Prime · 2 minutes before you read

The problem: A model stored at 16 bits per weight is slow to generate with and may not even fit in memory. Dropping bits makes it smaller and faster, but past a point the answers get worse, and a suspiciously fast host may be doing exactly that without saying so.

Where it fits: Third mechanism card: the bytes side of the memory-bandwidth division. Hardware raised the bandwidth; quantization shrinks what has to be read per token. MoE, next, shrinks it a different way.

In one breath

Store each weight in fewer bits, like 4 instead of 16. The model gets smaller, and since generating each token means reading every weight, fewer bytes means faster tokens. The cost is a small loss of accuracy that grows as you drop bits.

Worked example: Llama-3.1-8B in llama.cpp

Bits/weight is derived as 16 × size ÷ 14.96 GiB. Speed goes up with smaller size, but less than proportionally: turning the packed numbers back into usable values (dequantizing) takes extra compute. The README summary didn't name the hardware used.

Why it beats the alternatives

✗ Full precision (F16/BF16)

Best quality, but 2 bytes per weight: half the speed of 8-bit and about 3.3× the memory of 4-bit. A 9B model won't comfortably fit alongside everything else in 24 GB.

✗ A much smaller model

Also fewer bytes, but you lose knowledge and reasoning, not just a bit of precision. A 4-bit 9B model usually beats a 16-bit 2B model of similar size.

✗ Very low bits (Q2)

Only about 11% faster than Q4_K_M here (79.85 vs 71.93 t/s), for noticeably worse output. Past about 4 bits the gains shrink and the damage grows.

✓ 4–8 bit (Q4_K_M, Q8_0, FP8)

Most of the speed (1.75–2.5× over F16) for a small quality cost (under 1% perplexity at 5–8 bits). That's why Ollama's default tags ship Q4_K_M.

Is lower always better?

No. Quantization only speeds up the memory-bound writing phase. It does little for a slow first token on a long prompt, where prompt caching is the lever.

Perplexity understates damage on precise tasks like code, math and long reasoning. When quality matters more than speed, prefer Q8/FP8 or a bigger model.

On hosted APIs you usually can't choose. A suspiciously cheap or fast OpenRouter provider may be serving fp4 while another serves bf16, so check the quantization field before comparing their speeds.

Understand and remember

  • Fewer bits per weight → fewer bytes read per token → decode is bandwidth-bound → tokens come faster (F16 → Q4_K_M: 29.17 → 71.93 t/s)
  • Packed weights must be unpacked before use → extra compute per byte → speed rises less than size falls → gains shrink below about 4 bits while quality loss grows
  • Quantization only speeds the memory-bound writing phase → prefill is compute-bound → a long-prompt TTFT barely changes → use caching there instead
  • detail that matters Hosts choose precision for you → OpenRouter lists bf16 / fp8 / fp4 per provider → a fast or cheap host may be fp4 → compare speeds only at the same precision

4 · Compare against what you already know

vs Mixture of experts (MoE): Quantization and MoE both cut the bytes read per token. Which one also cuts the memory needed to hold the model, and which cuts bytes by more?

Check
  • quantization shrinks both storage and bytes read (about 4× from 16 to 4 bits)
  • MoE cuts bytes read by 9–23× but you still hold every expert
  • they combine: MoE models are usually also quantized

vs Quantization for serving: On a laptop, quantization is about fitting and single-user speed. What changes when a server quantizes for many users, and why can weight-only quantization help less there?

Check
  • servers batch many users, so each weight read serves many tokens
  • at high batch the step is less bandwidth-bound, so fewer weight bytes help less
  • servers then also quantize activations or the KV cache, and care about throughput per GPU

Reveal

The Llama table gives 71.93 → 50.93 t/s, about 0.71×, so roughly 15.4 × 0.71 ≈ 10.9 t/s. An 82-token answer goes from about 5.3 s to about 7.5 s of writing: noticeable, but small next to the 653-token vs 82-token difference. Worth it if the code gets better.
