Grammar compilation time (GCT)

Also called schema compilation, or "first-request latency for a new schema". It's paid when you use structured outputs, strict tool calling or JSON-schema constrained decoding on Claude, OpenAI, vLLM, SGLang and Outlines. It shows up as extra time to first token.

Prime · 2 minutes before you read

The problem: Structured outputs and strict tool calling guarantee valid JSON, but the server first has to turn your schema into a grammar machine. That build can take milliseconds or minutes, and if your schema changes every request, you pay it every time.

Where it fits: Seventh mechanism card, another hidden part of TTFT. Like prompt caching, it's a one-time cost hidden by a cache; unlike prefill, it depends on the schema, not the prompt.

In one breath

To make sure a model can only write valid JSON for your schema, the server first converts the schema into a grammar: a machine that tells the model, at every step, which tokens are allowed next. Building that machine is grammar compilation. It happens before the first token, so it adds to TTFT. The result is cached, so it's normally paid once per new schema, not once per request.

Worked example: the same schema, first time and second time

first request, new schema TTFT = network + queue + compile grammar + prefill same schema, cache still warm TTFT = network + queue + prefill every token after that + mask check (under 40 µs with XGrammar)

How it differs from related ideas

✗ Cold start

Loading the model's weights into memory. It's paid once per model load, whatever the schema: 4.07 s on your M3.

✗ Prefill

Reading the prompt. It's paid on every request, grows with prompt length, and prompt caching can skip it.

✗ Per-token masking

Checking the grammar before each token. It's paid on every token, but good engines keep it under 40 µs. A slow engine shows up as lower output speed, not as a longer TTFT.

✓ Grammar compilation

Paid once per new schema, before the first token, then cached (24 h from last use on Claude). What costs you is how often the schema changes, not how often you call.

Is this something I need to worry about?

Usually no. With a fixed schema, or a fixed set of tools, you pay it once and the cache handles the rest. Locally with Ollama it's effectively zero. It starts to matter when the schema changes on every request, for example an enum filled with today's IDs, or a tool list assembled per user. Then every call is a first call. On Claude, renaming a field or changing the set of tools creates a new cache entry. Editing only name or description doesn't.

If that's you, fixes include: keep the schema's structure stable and put the variable parts in the prompt; send one warm-up request at deploy time; pick a lazy engine (llama.cpp, Guidance) or XGrammar over Outlines when you host it yourself. Or skip strict decoding entirely: prompt for JSON, validate it, and retry on failure. That has no compile cost, but each failure costs a whole extra call. One more catch on Claude: changing output_config.format also invalidates the prompt cache for that conversation.

Understand and remember

  • Constrained decoding needs a machine that says which tokens are allowed next → the schema is compiled into it before the first token → compile time adds to TTFT → cached, so paid once per new schema
  • Engines split the work differently → eager engines precompute (Outlines 8.05 s, up to minutes on hard schemas) → lazy ones check as tokens are generated (Guidance 0.01 s) → upfront cost vs per-token work
  • A schema that changes per request (today's IDs in an enum, per-user tool lists) → every call misses the cache → the compile is paid every time → keep structure stable and move variable parts into the prompt
  • detail that matters The per-token mask check runs every token → a good engine keeps it under 40 µs (0.26% of a 15.2 ms token) → a slow engine shows up as lower output speed, not longer TTFT

Reference only

  • JSONSchemaBench engine timings (0.01 / 0.06 / 0.20 / 8.05 s)
  • Claude's 24 h compiled-schema cache and output_config.format
  • XGrammar-2's 534 ms → 5.37 ms benchmark

5 · Predict commit to an answer before revealing

Outlines takes 8.05 s to compile a schema and XGrammar 0.20 s. If each answer is 200 tokens at 66 t/s, after how many reuses of the same schema does Outlines' compile add less than 10% to the total time? Commit to an order of magnitude first.

Reveal

One answer takes about 1.39 + 200 ÷ 66 ≈ 4.42 s. 10% of the total means 8.05 ÷ k < 0.1 × (4.42 + 8.05 ÷ k), which rearranges to k > 8.05 × 0.9 ÷ 0.442 ≈ 16.4, so about 17 reuses. A handful of calls with a new schema each time is terrible; hundreds of calls with one schema makes it negligible.
