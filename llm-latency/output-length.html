Output length

Also called tokens generated, completion tokens, or eval_count in Ollama. It's how much the model writes. It's usually the biggest speed lever you control, and it's free.

Prime · 2 minutes before you read

The problem: People chase faster hardware and hosts while their model writes 8× more text than they need. Every extra token costs the same fixed time, so a long answer is slow on any machine.

Where it fits: Third metric card, the numerator of the writing-time term. After TTFT and output speed, this is the one lever that is free and works everywhere. Thinking tokens later extend it to hidden output.

Builds on: Time to first token (TTFT) · Output speed (tokens per second)

Used in the field guides: Project 1: One tool, one planted bug: the loop from scratch (Agents Field Guide) · F08: stop_reason is max_tokens and the tool call is cut in half (Agents Field Guide) · F13: Output lengths are 5× what you planned (thinking mode on by default) (Serving Field Guide)

You'll meet: time grows in a straight line with tokens total ≈ TTFT + tokens ÷ speed max_tokens / num_predict and stop sequences when length is the wrong lever

In one breath

Every output token costs the same fixed time, so total time grows in a straight line with how much the model writes. Asking for half as much text roughly halves the wait, on any hardware.

Why it beats the alternatives

✗ Faster Mac

M3 → M3 Max is about 3.1× (Llama 7B Q4_0: 21.34 → 66.31 t/s). Real, but it costs thousands of dollars.

✗ Harder quantization

Q4_K_M → Q2_K is only 1.11× (71.93 → 79.85 t/s on Llama-3.1-8B), and quality drops noticeably.

✗ Switch host

Can be 10–100× faster, but it costs money, needs a network, and your code leaves your machine.

✓ Write fewer tokens

653 → 82 tokens (7.96× fewer) was about 7.9× faster, for free. Ask for "code only", set num_predict / max_tokens, turn thinking off, and add stop sequences.

Is shorter always better?

No. Tokens are also where the model does its work. Thinking tokens often fix hard problems, and a max_tokens limit that's too tight cuts code off mid-function. Output length is also the wrong lever when the prompt is long. Your M3 took 12.6–33.9 s just to read a 2,605-token prompt and 1.6–4.9 s to write the 29-token reply. There, use prompt caching or a shorter prompt instead.

Understand and remember

  • Each output token costs one decode step of fixed time → total grows linearly with output tokens → cutting tokens cuts time proportionally on any host → it is the free lever
  • Model and host set only the per-token cost → a short answer on slow hardware can beat a long one on fast hardware (5.7 s on M3 vs 11.3 s on Sonnet 5) → fix length before paying for speed
  • Tokens are also where the model works → too-tight limits cut code mid-function or remove useful thinking → trim fluff, not reasoning the task needs
  • detail that matters When the prompt is long, TTFT (prefill) dominates → the 29-token reply took 1.6–4.9 s against 12.6–33.9 s of reading → then caching or a shorter prompt is the lever, not answer length

Check
  • length changes the numerator (tokens); quantization changes the denominator (speed)
  • past 4 bits, dequantizing overhead eats most of the byte savings
  • cutting tokens has no such floor: fewer steps, full stop

5 · Predict commit to an answer before revealing

Streaming is on. You cut an answer from 653 to 82 tokens. Predict whether the user's perceived wait improves by the full ~7.9×, and explain what they actually notice.

Reveal

Not the full amount in perception. With streaming, the first words arrive after TTFT either way, so the moment "something happens" doesn't change. What shrinks is the time until the answer is complete and usable (42 s → 5 s on the M3). For code, which you can't use until it's finished, that completion time is what matters.

Memory-bandwidth-bound decodingAlso called "decode is memory-bound" or "the bandwidth ceiling". It's the main reason your M3 writes about 15 tokens/s with qwen3.5:4b, and why hosted GPUs are so much faster.In one breathWriting each new token means streaming every active weight of the model from memory through the chip. The chip does little math per byte, so speed is capped by how many bytes per second memory can deliver, not by how fast the chip computes.
