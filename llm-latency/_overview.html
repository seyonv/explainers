How to think about LLM speed

Overview card: latency, time to first token, tokens/sec, end-to-end time. It covers one model call and ranks what actually moves the number. For whole agent tasks, see agent speed and reliability.

Prime · 2 minutes before you read

The problem: "The model is slow" is not something you can fix. Without a breakdown you tune the wrong thing: you buy hardware when the answer was 20× too long, or switch hosts when the wait was all hidden thinking.

Where it fits: This is the map for the whole course. Every later card is one term of a single formula: a start (time to first token), plus tokens ÷ speed, repeated for every call. The agents overview then wraps that formula in a loop.

You'll meet: T ≈ Σ [TTFT + (nthink + nanswer) ÷ vout] + ttools knobs → metrics → end-to-end time fewer tokens vs faster tokens vs a shorter start multipliers vs seconds added

By the end: Place every card in the course on one causal map, and say which term of the formula a given change attacks and roughly how big the win can be.

Read with these questions (answer them in your head as you go; don't take notes line by line):

  1. Which term of the formula is a multiply and which only adds seconds, and why does that decide the ranking of levers?
  2. Why do thinking tokens show up in two places at once (the start and the writing time)?
  3. For the 653-token FizzBuzz run, what fraction of the 42 s is the start? What would have to change for the start to dominate instead?
  4. Why does the ranking put "change host" above "buy hardware" but below "cut tokens"?
  5. Why is caching's 83× speed-up not an 83× faster response?

In one breath

A response takes as long as it takes to get started, plus how many tokens it writes times how long each token takes, repeated for every call the harness makes. Most of the time goes into the multiply, not the start.

Filled in for your M3 FizzBuzz run: N = 1, thinking off, 653 answer tokens at 15.4 t/s → 653 ÷ 15.4 = 42.4 s of writing time. The start was a small slice of that.

The same thing in plain text:

total ≈ Σ over calls [ network + queue + cold start + prefill ← time to first token + (thinking tokens + answer tokens) ÷ output speed ] + tool run time between calls

The mental model: knobs → metrics → time

Thinking tokens count twice: they delay the first answer token and they are paid for at the same per-token speed as the answer.

Barely

Grey rows add or remove seconds rather than multiply. Caching's 83× applies only to reading the prompt, not to writing the answer. Each row is a different workload, so read them as orders of magnitude, not one benchmark. Hosted figures are Artificial Analysis medians as of 2026-09-21.

The takeaway

Cut tokens first, pick the host second, buy hardware last. The cheapest wins are the ones that shrink the multiply: turn thinking off or down when the task is easy, ask for exactly the output you need, cache long stable prefixes, and avoid agent loops for one-shot questions. Then compare hosts for the same model on Artificial Analysis or OpenRouter before changing models.

Speed is not always the right target. On a hard bug, a slow high-effort answer that is right the first time beats five fast wrong ones, and an agent that runs your tests is slower per task but saves you the checking. Optimize the time until you have a correct result.

1 · Core model what to internalise, what to just look up

Keep it if it changes what you can explain, predict, compare, choose, build or debug. Otherwise it's reference.

Understand and remember

  • Tokens are written one at a time at a fixed pace → writing time = tokens ÷ output speed → for any answer longer than a few sentences the multiply dwarfs the start → cut tokens first
  • Each lever touches exactly one term → fewer tokens (thinking, length, calls), faster tokens (host, hardware, quantization, speculative decoding), or a shorter start (caching, cold start, network) → name the term before picking the fix
  • Thinking is output that is hidden → it delays the first visible token and is paid at the same per-token speed → effort settings move both TTFT and total time (16–23× in the measurements)
  • An agent repeats the formula N times → per-call costs multiply by the call count → the number of calls is itself a token lever you choose when you pick the tool
  • detail that matters Grey rows (cold start, network + queue) add or remove seconds rather than scale with tokens → they matter only when the answer is short

Reference only

  • the exact speed-up per lever row (36×, 3.1×, 2.5×, 83×)
  • which company controls which knob
  • the log-scale bar widths

Why this step?

5 · Predict commit to an answer before revealing

Suppose a new host serves the same model 10× faster per token but has 3 s more TTFT. For which answer lengths (on a baseline of 66 t/s and 1.39 s TTFT) is it actually faster end to end? Commit to a rough cut-off before revealing.

Reveal

The new host saves n ÷ 66 − n ÷ 660 = n × 0.0136 s and costs 3 s extra. It wins once n × 0.0136 > 3, so beyond about 220 tokens. Short answers (a few sentences) are faster on the old host; anything code-sized is faster on the new one. That's the start-vs-multiply split in one line.
