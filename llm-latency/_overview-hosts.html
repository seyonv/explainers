Same model, different host

Overview card: providers, deployments, inference endpoints. This is why "the model" isn't enough to say how fast a response will be, and where to look up the numbers before you pick a deployment.

Prime · 2 minutes before you read

The problem: "Which model?" isn't enough to say how fast a response will be. The same gpt-oss-120b weights run 36× faster on one host than another, and the reasons (chip, precision, speculative decoding, how many users share a chip) are mostly unpublished.

Where it fits: The synthesis for the mechanism part. Memory bandwidth, hardware, quantization and speculative decoding each explained one factor; this card multiplies them into one host's speed and shows where to look the numbers up.

In one breath

A host is the company whose chips actually run the model when you call an API: Azure, Amazon Bedrock, Groq, Cerebras, DeepInfra and so on. Open models like gpt-oss can be rented from many hosts; Claude and GPT-5 are only served by their makers and a few clouds. The same weights can be served 36× faster or slower depending on who hosts them. The chip's memory bandwidth, quantization, speculative decoding, batching and load are all the host's choices. What "output speed" is, and where the number comes from

Is it the host's advertised number?

No. Artificial Analysis calls each host's public API itself, several times a day, with standard test prompts, and reports the median. It's an outside measurement of what one ordinary request saw, not a marketing peak.

What exactly is timed?

Tokens streamed per second after the first token arrives, for one request. The wait before that is TTFT, reported separately. So output speed is how fast text scrolls once it starts.

Is it the same as "throughput"?

No. Throughput is a whole server's total across every user. A host can raise throughput by packing more users onto each chip, which makes each user's own speed lower.

✓ What you should read it as

"If I send this model to this host today, text arrives at about this rate." Multiply your answer length by 1 ÷ speed to get the writing time.

What it really comes down to

Every token means reading the model's active weights from memory once. So one user's speed is roughly:

your speed ≈ chip memory bandwidth (1) ÷ bytes read per token (2) × tokens per pass (3) ÷ users sharing the chip (4, roughly)
1The chip. How many bytes per second memory delivers. An H100 GPU does 3.35 TB/s; Groq and Cerebras keep weights in on-chip SRAM at 80+ TB/s and 21 PB/s.hardware 2Bytes per token. Set by the model's active parameters and the host's precision. A host serving fp4 reads half the bytes of fp8. OpenRouter lists each host's precision.quantization 3Tokens per pass. With speculative decoding the host guesses several tokens and checks them in one read of the weights, typically 2–3× more tokens per pass.spec. decoding 4Sharing. Cheap hosts batch many users per chip to cut cost per token. Hosts don't publish batch sizes, so this is the part you only see in the measured number.output speed
gpt-oss-120b reads about 5.1B active params × ~4.25 bits ÷ 8 ≈ 2.7 GB per token (estimate) one H100, one user alone: 3,350 GB/s ÷ 2.7 GB ≈ 1,240 t/s ceiling measured on GPU hosts: 48–334 t/s → most of it lost to sharing, overhead measured on Cerebras (SRAM): 1,745 t/s → bandwidth is no longer the limit

The ceiling is an upper bound that ignores attention and the KV cache, and hosts may split one model across several GPUs. The point is the shape: the chip sets the ceiling, and how the host runs it decides how much of that ceiling you get.

The metrics to compare, every time

Output speed

Tokens/sec after the first token. Dominates any answer longer than a few sentences.

TTFT and time to first answer

How long until anything appears. For thinking models, the first answer token is the one you care about.

End-to-end at your input size

A 100k-token prompt behaves very differently from a 1k one. Match the workload to your real one.

✓ Quality, price, uptime

A fast host is only a win if it is quantized acceptably, affordable, and up. OpenRouter shows all three.

Is the fastest host always the right pick?

No. These are medians sampled a few times a day. They move with load, and the numbers here will drift. Some fast hosts serve lower-precision weights, have tighter rate limits, or cost more per token. Speed also only helps if tokens dominate. For a short answer, the 0.3–1.4 s TTFT spread matters more than a 2× output-speed gap. OpenRouter's page is rendered in the browser; its public /endpoints API returned price, quantization and uptime but empty latency and throughput fields when checked, so read those numbers on the page itself.

5 · Predict commit to an answer before revealing

A host moves gpt-oss-120b from bf16 to fp4 on the same GPUs and the same batch size. Predict the change in the bandwidth ceiling and in delivered speed, and one reason delivered speed won't rise by the full factor.

Reveal

Bytes per token roughly quarter (16 → 4 bits), so the ceiling rises up to ~4×. Delivered speed rises less: dequantization costs compute, attention and KV-cache reads don't shrink with weight precision, and sharing overhead stays. Quality may also drop, which the speed number won't show.
