Prompt caching (prefill reuse)

Also called prefix caching, KV cache reuse, or context caching. Built into Ollama (it keeps the last prompt in memory) and offered by the Anthropic and OpenAI APIs.

Prime · 2 minutes before you read

The problem: Chat apps and agents re-send the same long system prompt, documents and history on every request. Without caching the model re-reads all of it each time: seconds on a laptop, and full price on an API.

Where it fits: Sixth mechanism card, and the first that attacks the start rather than the writing. TTFT showed prefill as one part of the wait; this card removes it for a repeated prefix. Context growth later shows why agents depend on it.

In one breath

Before writing anything, the model has to read the whole prompt (this step is called prefill). Caching saves the result of that reading, so the next request that starts with exactly the same text skips straight to the new part.

Worked example: one 2,605-token prompt on an M3, three times

speed-up on repeat = 33.88 s / 0.41 s ≈ 83× (99% less prompt reading time) fresh read rate = 2,605 / 33.88 s ≈ 77 tokens/s (other run: 207)

Measured with Ollama, qwen3.5:4b on an Apple M3 (24 GB). The machine was busy, so the fresh read time varied from 12.6 s to 33.9 s between runs. The repeat and changed-start results held up. Only the prompt reading step is shown; writing the answer is a separate cost.

Price: Anthropic cache reads cost 0.1× the normal input price. Writing to the cache costs 1.25× (kept 5 minutes) or 2× (kept 1 hour). OpenAI caches automatically once the prompt is 1,024 tokens or longer.

Why it beats the alternatives

✗ Re-read every time

The default without caching. An agent that resends a 20K-token system prompt on every call pays the full reading time and full price each time.

✗ Shorten the prompt

Faster, but you drop instructions, files or history the model needed, and answer quality falls.

✗ Cache the final answer

Only helps when the whole request repeats exactly. A new question on the same document still misses.

✓ Prefix caching

Reuses the expensive shared part (system prompt, documents, history) while the question at the end changes freely.

Does it always help?

No. It only speeds up prompt reading, so it barely matters for short prompts or long answers. Your 26-token FizzBuzz prompt took 0.33 s to read, while writing the answer took 42 s. The match must be exact from the very first token: put stable content (system prompt, documents) first and changing content (timestamps, the question) last, or every request misses, as in row 3.

Caches also expire (Ollama unloads idle models, and Anthropic keeps caches 5 minutes or 1 hour). Hosted APIs charge extra to write a cache, so a prompt used only once costs more with caching than without.

1 · Core model what to internalise, what to just look up

Keep it if it changes what you can explain, predict, compare, choose, build or debug. Otherwise it's reference.

Understand and remember

  • Prefill turns every prompt token into stored state (the KV cache) → the state for a token depends on every token before it → a saved prefix can be reused only if it matches exactly from the first token → one changed early token misses everything after it
  • A cache hit skips reading the shared prefix → only the new tail is read → TTFT drops (33.88 s → 0.41 s on the M3) → but writing time is untouched
  • Hosted caches charge to write (1.25× or 2×) and discount reads (0.1×) → worth it only when the prefix is reused within the cache lifetime → a one-off prompt costs more
  • detail that matters Put stable content first (system prompt, tools, documents) and changing content last (timestamps, the question) → otherwise every request misses, as in the 25.99 s "new first words" row

Reference only

  • OpenAI's 1,024-token minimum for automatic caching
  • the 5-minute and 1-hour lifetimes
  • Anthropic's published 100K-book example (11.5 s → 2.4 s)

  1. concept Explain why the cache must match from the first token, rather than matching any repeated chunk anywhere in the prompt.
    Check
    • each token's stored state depends on all tokens before it
    • if an early token changes, every later token's state changes too
    • so only an identical prefix can be reused
  2. mechanism Trace what happens on three agent calls whose prompts are: system prompt + history A; system prompt + history A + turn B; timestamp + system prompt + history A + turn B.
    Check
    • call 1: full read, the prefix is written to the cache
    • call 2: system prompt + A hit, only turn B is read
    • call 3: the timestamp changes the first tokens, so nothing matches: full read
  3. tradeoff Your API app sends a 20k-token document once per user, and each user asks one question. Should you turn on caching? What if each user asks ten?
    Check
    • one question: you pay the 1.25× write and never read it: more expensive
    • ten questions within the lifetime: nine reads at 0.1× plus faster TTFT: clearly worth it
    • the decision is reuse count within the cache lifetime

Reveal

Only the 300 new tokens are read: about 300 ÷ 207 ≈ 1.4 s (a little more, since each new token attends to the long cached prefix). With the question at the start, the first tokens differ, so nothing matches: all ~2,900 tokens are re-read, about 14 s at 207 t/s.
