Model routing: the right size model per step

Also called model cascades, tiered models, or using small/fast models. It shows up in agents and harnesses that send easy steps (classifying, pulling out a field, summarizing a tool result, a one-line edit) to a small model and keep the big model for the hard steps.

Prime · 2 minutes before you read

The problem: Using the biggest model for every call in an agent means every "is this JSON valid?" step pays a big model's start, speed and price. Using the smallest means hard steps fail. Neither size fits every call.

Where it fits: Last agent card, the lever that touches both sides of the fraction. Compounding errors showed checks turn failures into cheap retries; routing uses those same checks to escalate from a small model to a big one.

In one breath. Not every call in an agent loop needs the smartest model. A router (a rule or a tiny classifier that picks the model for each call) sends easy calls to a small model that starts sooner, writes faster and costs less. If the small model fails a check, the call escalates: it is re-run on the bigger model.

Why it beats the alternatives

✗ Biggest model everywhere

Safe and simple, but every "is this JSON valid?" call pays the big model's 2.94 s start and $25 per 1M output: 60.1 s and at least $0.30 above.

✗ Smallest model everywhere

Fastest and cheapest (28.2 s, $0.061), but its Intelligence Index is 15 vs 39. It fumbles the hard steps, and each wrong answer triggers retries that eat the savings.

✗ Let the model pick freely

Asking a model "which model should handle this?" is itself an extra call, and a model is not a reliable judge of its own limits. You get an extra step and unpredictable cost.

✓ Route by step type, escalate on failure

Fixed rules send known-easy steps to Haiku, a cheap check (tests, schema, parse) catches misses, and only those re-run bigger. Here: 37.9 s and $0.104, even after paying for one failed route.

Should every agent route?

No. Routing adds moving parts: two models to test, a router to maintain, and a check you must trust. A wrong route costs a whole extra call (2.91 s here). Also, the stored prompt work (the KV cache, the saved result of reading the prompt) belongs to the model that made it. Switching models means the small model reads its prompt from scratch, so give it a short, self-contained prompt rather than the full history.

For hard reasoning, unclear bugs, or steps where a mistake sends the rest of the loop the wrong way, just use the big model. The research agrees routing pays off at scale: FrugalGPT reports it "can match the performance of the best individual LLM (e.g. GPT-4) with up to 98% cost reduction", and RouteLLM "significantly reduces costs-by over 2 times in certain cases-without compromising the quality of responses". Both measure cost on benchmarks, not agent latency.

Understand and remember

  • Smaller models start sooner and write faster (Haiku 0.68 s, 89 t/s vs Opus 2.94 s, 62 t/s) and cost less → easy calls don't need the big model's intelligence → route easy steps small

  • Hard calls dominate the routed time → routing helps most when the model gap is wide and most calls are easy → for hard, ambiguous steps just use the big model
  • detail that matters The stored prompt state (KV cache) belongs to the model that built it → a switched model re-reads its prompt from scratch → give the small model a short, self-contained prompt, not the full history
