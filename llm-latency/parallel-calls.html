Parallel calls and batching

Also called parallel tool use, fan-out, concurrency, and (for the cheap, slow version) the Batch API. Shows up whenever an agent has several independent things to do: read 5 files, run 5 searches, or hand 5 subtasks to subagents.

Prime · 2 minutes before you read

The problem: An agent that does five independent searches one after another waits for the sum of everything, including five separate model calls. Doing them together waits only for the slowest. And for work no one is waiting on, batching halves the price.

Where it fits: Fourth agent card, a way to shrink the top of the agents fraction. Harness calls showed the loop; tail latency showed that waiting for the slowest has a cost. This card trades those off.

In one breath. Work done one after another (sequentially) makes you wait for the sum of every step. Work done at the same time (in parallel) makes you wait only for the slowest step. Batching is a different deal: you hand the provider a pile of requests, accept a much longer wait, and pay half price.

Worked example: an agent needs 5 web searches

Claude can put several tool calls (tool_use blocks, each one a request to run a tool) in a single response. The harness then decides whether to run them one by one or all at once.

Subagent times, the 400-token merge and the nightly job's token counts are illustrative. Subagents cut your wait, not the bill: each one pays for its own prompt and calls. Batch prices are the Anthropic rates this set uses ($2 / $10 per 1M input/output) at the documented 50% discount.

Latency vs throughput. Latency is how long one request takes. Throughput is how many requests finish per hour. Parallel calls improve latency for one task. Batching improves throughput and price, and makes each request's latency worse. You trade your wait for money.

Why it beats the alternatives

✗ Do everything sequentially

Simple and safe, but you wait for the sum: 22.4 s instead of 12.4 s above, and each extra step adds a full model call.

✗ One giant prompt

Stuff all 5 tasks into one request. One call, but the model writes all 5 answers one token at a time, so writing time still adds up, and one mistake can derail the rest.

✗ Batch API for interactive work

Half price, but "most batches" finish within an hour and the limit is 24 h. An 11 s answer becomes a wait of minutes to hours. Useless while someone is waiting.

✓ Parallelize independent steps, batch offline jobs

Run steps that don't need each other at the same time, so you wait for the max, not the sum. Send evals, labelling and overnight reports to the Batch API for 50% off.

Can't I just run everything in parallel?

No. Dependent steps can't be parallelized: if step 2 needs step 1's output (read the error, then fix it), they must run in order. Tools with side effects are risky too, and parallel agents editing the same files overwrite each other's changes. Give each one its own files or its own copy of the code (a git worktree).

Fanning out has limits. Rate limits cap how many requests you can send: Anthropic notes that 60 requests per minute may be enforced as 1 per second, so a burst of 5 at once can trip a rate-limit error. Waiting for the slowest of N also makes bad luck more likely. If each call has a 5% chance of being slow (illustrative), at least one of 5 is slow 1 − 0.955 = 23% of the time, and at least one of 20 is slow 64% of the time (see tail latency).

Understand and remember

  • Independent steps don't need each other's output → run them at the same time → you wait for the max, not the sum (tool wait 6.5 s → 2.0 s)
  • Several tool calls in one response → one model call replaces five → each saved call removes a TTFT and its writing time → fewer calls is most of the win (6 → 2 calls)
  • Batching hands the provider a pile of requests with a long deadline → the provider fills idle capacity → 50% off but up to 24 h → better throughput and price, worse latency
  • detail that matters Waiting for the slowest of N raises exposure to the tail (at least one of 20 slow 64% of the time at 5% each) and bursts can trip per-second rate limits → fan out, but not without limits
