Context growth in agent loops

Also called history re-sending, context accumulation, or quadratic context cost. It shows up in every agent harness (Claude Code, Cursor, Codex CLI, your own loop), because the model API keeps no memory between calls.

Prime · 2 minutes before you read

The problem: The model API remembers nothing between calls, so an agent re-sends its whole history every time. Input grows each call, and the total read over a session grows with the square of the call count: slower, pricier, and eventually worse answers.

Where it fits: Third multiplier card. Harness calls showed that an agent makes many calls; this card shows that each one is bigger than the last. Prompt caching is the main defence, and compaction the second.

In one breath. The model forgets everything after each call, so the harness re-sends the system prompt, the tool definitions and the whole conversation so far every time. Each call's input grows by a fixed step, so the input per call grows in a straight line and the total input read over a session grows roughly with the square of the number of calls.

Treat these as lower bounds: reading each new token gets a little slower as the context grows. Hosted models read far faster, but the shape is the same: Anthropic's own example of a 100K-token prompt took 11.5 s to the first token uncached and 2.4 s cached, against Sonnet 5's 1.39 s median at about 10k tokens.

Why it beats the alternatives

✗ Re-send everything, uncached

Simplest, and the model sees everything. But cost and prompt reading grow with the square of the calls: $2.94 and 2 hours of M3 reading here, versus $0.47 and 6 minutes cached.

✗ Truncate old turns

Drop the oldest messages to stay under a budget. Cheap, but the model forgets what it already tried, repeats mistakes, and every cut changes the prefix so the cache misses.

✗ Start a fresh session

Resets input to the 20k start. Great between unrelated tasks, but mid-task you lose the plan and findings unless you write them down first.

✓ Cached stable prefix + compaction

Keep the system prompt and tools byte-identical at the front so they cache, append new turns at the end, and when history gets long, replace it with a short summary. In the example, compacting 28k of history into 4k at call 15 caps call 30 at 52k instead of 78k.

compaction at call 15 (illustrative): calls 16–30 start at 24,000 instead of 50,000 calls 1–15 = 510,000 calls 16–30 = 15 × 24,000 + 2,000 × 105 = 570,000 + one summarizing call that reads 48,000 → 1,128,000 total (23% less than 1,470,000)

Is a longer context just slower and pricier?

No, it can also make answers worse. Liu et al. (2023, "Lost in the middle") found models use facts at the start and end of a long prompt best; with the answer buried mid-context, GPT-3.5-Turbo did worse than with no documents at all (below its 56.1% closed-book score). Chroma's "Context rot" (2025) tested 18 models, including Claude 4, GPT-4.1 and Gemini 2.5, and found accuracy falls as input grows, even on simple tasks. A 1,000,000-token window (Sonnet 5 on OpenRouter) is a hard limit, not a quality promise: at +2k per turn it would fill around call 491, and 78k is only 7.8% of it.

When is it not the problem? Short tasks. A 4-call FizzBuzz loop never gets far past its starting prompt, so the fixed start and the call count matter more. Compaction also costs something: the summary drops details, is itself a model call, and resets the history part of the cache.

Keep it if it changes what you can explain, predict, compare, choose, build or debug. Otherwise it's reference.

Understand and remember

  • The API is stateless → the harness re-sends system prompt, tools and full history each call → input grows by a fixed step per call → the session total is a sum of a growing series ∝ N² (1,470,000 tokens for 30 calls)
  • Every call's prefix is the previous call's whole input → a byte-identical prefix hits the cache → only the new turn is read and written → cost and prefill time drop (6.2× cheaper, 2 h → 6 min on the M3)
  • Long contexts degrade answers (lost in the middle, context rot) → a big window is a hard limit, not a quality promise → compact history into a summary or start fresh between tasks
  • detail that matters Any edit near the start (truncating old turns, a timestamp, compaction) changes the prefix → the next call misses the cache → compaction saves tokens (23% here) but pays one full re-read

Reference only

  • Sonnet 5 input prices ($2 / 1M, cache read $0.20, write $2.50)
  • the 1,000,000-token window and call 491
  • the illustrative 20k start and +2k per turn
