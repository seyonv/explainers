Time to first token (TTFT)

Also called first-token latency, or the "time to first chunk" when streaming. It's the wait before anything appears. Artificial Analysis reports it for every model and provider.

Prime · 2 minutes before you read

The problem: When nothing appears on screen, you can't tell whether the request is crossing the network, waiting for a free chip, loading weights, reading your prompt or thinking. Each has a different fix, and the spread is huge: 0.13 s to over two minutes.

Where it fits: The first metric card. The overview split a response into a start and a writing time; this card opens up the start. Output speed and output length, next, cover the writing time.

In one breath

TTFT is the time from sending a request to getting the first token back. It includes everything that happens before the model starts writing: the network, waiting in a queue, loading the model, reading your prompt, and any hidden thinking.

The parts of the wait, in plain words

Think of ordering at a restaurant. Network is the walk there and back. Queue is waiting for a table. Cold start is the kitchen still warming up. Prefill is the chef reading your order, and a long order takes longer to read. Only then does the first dish (token) come out.

How it differs from related ideas

✗ Output speed

How fast tokens come once they start. A provider can have low TTFT and slow output, or the reverse: Baseten has the lowest TTFT above (0.28 s) but is only 5th in output speed.

✗ End-to-end time

The whole response, TTFT plus writing time. It's what you feel with stream:false, because nothing shows until the end.

✗ Time to first answer token

For reasoning models: when the visible answer starts, after thinking ends. gpt-oss-120b (high): first token after 0.81 s, first answer token after 10.18 s.

✓ TTFT

The moment something appears. When you stream, it's the number that decides whether the app feels responsive.

When should I care about it?

Care about it for chat and autocomplete, and any time a person watches the screen. For long answers, background jobs, or requests with stream:false, it's the wrong thing to optimize: a 42-second answer on your M3 is 99% writing time, so TTFT barely matters. Also check whether a quoted TTFT includes thinking. For proprietary reasoning models, Artificial Analysis's TTFT includes the hidden thinking, which is why Sonnet 5 jumps from 1.39 s to 141 s.

Understand and remember

  • Everything before the first token happens in sequence → TTFT = network + queue + cold start + prefill (+ hidden thinking) → the largest part dominates → fix that one, not the sum
  • Prefill reads the whole prompt in one parallel pass → time grows with prompt length and chip speed → long prompts on a laptop take seconds, on a datacenter GPU a fraction of one → a cached prefix skips it
  • Reasoning models write hidden thinking before the first visible token → TTFT as reported can include minutes of output → separate "first token" from "first answer token"
  • detail that matters Cold start copies the weights from disk → 4.07 s for the 3 GB model on the M3 → only when the model was unloaded, so keep_alive decides whether you ever see it

vs Output speed (tokens per second): TTFT and output speed are both "how fast". What does each one exclude on purpose, and which one decides the wait for a 20-token reply vs a 2,000-token reply?

Check
  • TTFT excludes writing time; output speed starts its clock at the first token
  • the split lets each metric show one cause
  • 20 tokens: TTFT dominates; 2,000 tokens: output speed dominates

vs Prefill vs decode, measured on your Mac: The prefill part of TTFT and the per-token writing time run the same model on the same Mac. Why is reading a prompt token so much cheaper than writing an output token?

Check
  • prefill processes all prompt tokens in one parallel pass
  • each weight read is reused across many tokens, so it is compute-bound
  • decode reads every weight for one token at a time, so it is memory-bound (≈ 207 vs 15.4 t/s here)

Why this step?

5 · Predict commit to an answer before revealing

You double the prompt from 2,605 to about 5,200 tokens on the warm M3. Predict whether prefill time roughly doubles, more than doubles, or less, and give one reason it might not be exactly 2×.

Reveal

Roughly doubles (about 25 s at 207 t/s), and a bit more in practice: attention work per token grows with the context already read, so later prompt tokens cost slightly more. The machine's load also swings it (12.6 vs 33.9 s for the same prompt). Caching the first 2,605 tokens would leave only the new half to read.
