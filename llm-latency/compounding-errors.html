Compounding errors in agent loops

Also called per-step reliability, error accumulation, consistency, or pass^k. It shows up whenever a harness chains many model calls into one task: coding agents, customer-service bots, anything with “autonomous” in the pitch.

Prime · 2 minutes before you read

The problem: A step that's right 95% of the time sounds reliable, but chain 20 of them and the task succeeds only about a third of the time. Faster steps don't help if the result is wrong and you have to redo the whole task.

Where it fits: Third agent card: the bottom of the agents overview's fraction. Tail latency and retries dealt with slow or failed calls; this card deals with calls that return a wrong answer, and why checking each step is the biggest lever.

  2. Why did τ-bench's pass^8 come out far above the 2% that independence predicts?
  3. Why does a check with 2 retries raise one step from 90% to 99.9% for only 11% more calls?
  4. Why does the careful slow model beat the fast one with an end check, but lose to the fast one with step checks?
  5. When do retries not help at all?

In one breath. If each step of a task goes right 95% of the time, the whole task goes right only when every step does. So the odds multiply: 20 unchecked steps at 95% each finish correctly only 36% of the time. Checking each step against reality (run the test, validate the output) turns silent failures into cheap retries.

Worked example 1: success of an unchecked N-step task, pN

Per-step success pN = 15102050

task success = p × p × … × p = p^N (every step must go right, no checking) 0.95^20 = 0.358 → a “95% reliable” step fails the 20-step task 64% of the time 0.99^50 = 0.605 → even 99% per step loses 4 in 10 fifty-step tasks

Pure arithmetic, assuming every step is equally hard and failures are independent. A “step” is one model call or tool action. The 4-call FizzBuzz loop in harness calls is N = 4; a real coding session is often dozens.

τ-bench if tries were independent: 0.612^8 = 0.020 = 2% τ-bench measured: <25% (the paper's intro: “as low as ~25%”) METR: asking for 80% instead of 50% success cuts task length 59 → ~15 min (≈ 4×)

pass^k is “the chance that all k i.i.d. task trials are successful, averaged across tasks” (τ-bench §3). Measured pass^8 is far above 2% because failures cluster: some tasks the agent nearly always gets right, others it nearly always gets wrong. METR finds 80% horizons “roughly 5x shorter” than 50% ones across models, and horizons doubling about every 7 months. These are 2024–25 models; newer ones score higher, but the shape holds.

Worked example 2: checking turns failures into retries

one step, p = 0.90, checked, up to 2 retries (3 tries total): fails only if all 3 tries fail: 1 − 0.1^3 = 1 − 0.001 = 99.9% average tries used: 1 + 0.1 + 0.01 = 1.11 20-step task: unchecked 0.90^20 = 12.2% vs checked 0.999^20 = 98.0%

Assumes each retry is an independent draw and the check (a test, a schema validator, a compiler) catches every bad output. 11% more calls buy an 8× higher task success rate here.

time to a correct result = time per attempt ÷ success rate (retry until it passes) fast, end check: (10 × 2.91) ÷ 0.90^10 = 29.1 ÷ 0.349 = 83.5 s careful, end check: (10 × 6.00) ÷ 0.99^10 = 60.0 ÷ 0.904 = 66.3 s ← slower model wins fast, step checks: 10 × (2.91 + 0.5) ÷ 0.90 = 10 × 3.79 = 37.9 s ← checking wins fast step = 1.39 s first token + 100 tokens ÷ 66 tokens/s = 2.91 s

The 2.91 s step uses Claude Sonnet 5's Artificial Analysis medians (1.39 s, 66 tokens/s, 2026-09-21). The careful model's 6 s, both success rates, 100 tokens per step and the 0.5 s test are illustrative. Retrying only the failed step is far cheaper than redoing the whole task.

Why it beats the alternatives

✗ Longer, stricter prompts

More rules in the system prompt add prefill time on every call, but can't stop a wrong step from passing silently. τ-bench agents already had the full policy and still broke it.

✗ A bigger model, nothing else

Raising p from 90% to 95% helps, but 50 unchecked steps still finish only 7.7% of the time. Every model's errors compound; they just compound slower.

✗ More autonomy, no checks

Letting the agent run longer raises N, and success falls with pN. METR's horizons shrink about 4× when you ask for 80% success instead of 50%.

✓ Verify each step against reality, keep tasks short

Tests, type checks and schema validation catch a bad step immediately, so it costs one retry, not the whole task: 12.2% → 98.0% for 20 steps. Short tasks keep N small.

Do retries always fix it?

No. The 99.9% figure assumes each try is a fresh coin flip. When the model is systematically wrong (it misreads the spec, doesn't know an API, or the test itself is wrong), it fails the same way every time. τ-bench shows this: 61% single-try success but ~25% all-8, not the 2% independence would predict, so the failures sit on the same tasks. Retries also can't help if nothing checks the output: a confident wrong answer looks like success.

For those cases, change something between tries (new context, a different model, a hint from the error message), or put a human at the steps that are expensive or impossible to undo: payments, deletes, deploys. Checking isn't always worth it either: for one-shot questions with no cheap check, a single careful call is simpler.

Understand and remember

  • Every unchecked step must go right → success = pN → falls fast with N (0.9520 = 35.8%) → longer autonomous runs fail more
  • A check after each step catches a bad output immediately → only that step is retried → per-step success rises to 1 − (1 − p)3 with 2 retries → 20 steps: 12.2% → 98.0%
  • Time to a correct result = attempt time ÷ success → a failed unchecked attempt repeats the whole task → checking each step (37.9 s) beats both a faster unchecked model (83.5 s) and a careful one (66.3 s)
  • detail that matters Failures cluster on the same tasks → retries of a systematically wrong model fail the same way (τ-bench: ~25% pass^8 vs 2% if independent) → change something between tries or put a person at irreversible steps

Reference only

  • τ-bench retail numbers (61.2% pass^1)
  • METR horizons (59 min at 50%, ~15 min at 80%, ~7-month doubling)
  • the 99%/95%/90% × N table values

    Check

    • pass^1 says how often it can succeed; pass^k says how consistently
    • an agent you rely on repeatedly needs consistency (61.2% pass^1 vs <25% pass^8)

4 · Compare against what you already know

vs Thinking tokens: Thinking raises p per call; checking catches failures after the fact. Which one changes the numerator and which the denominator of time to a correct result, and when would you use both?

Check
  • thinking makes each attempt slower (numerator up) but more likely right (denominator up)
  • checking adds a little time per step but turns failures into cheap retries
  • both: hard steps with cheap checks, e.g. a tricky bug fix with tests

vs The prompt-and-repair loop: The repair loop validates JSON and retries with the error; this card validates each agent step and retries. What does feeding the error back add over a blind retry?

Check
  • a blind retry is a fresh draw with the same odds
  • feeding the error back changes the input, so the next try isn't identical
  • it attacks correlated failures, which blind retries can't
