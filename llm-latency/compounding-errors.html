Compounding errors in agent loops

Also called per-step reliability, error accumulation, consistency, or pass^k. It shows up whenever a harness chains many model calls into one task: coding agents, customer-service bots, anything with “autonomous” in the pitch.

In one breath. If each step of a task goes right 95% of the time, the whole task goes right only when every step does. So the odds multiply: 20 unchecked steps at 95% each finish correctly only 36% of the time. Checking each step against reality (run the test, validate the output) turns silent failures into cheap retries.

task success = p × p × … × p = p^N (every step must go right, no checking) 0.95^20 = 0.358 → a “95% reliable” step fails the 20-step task 64% of the time 0.99^50 = 0.605 → even 99% per step loses 4 in 10 fifty-step tasks

Pure arithmetic, assuming every step is equally hard and failures are independent. A “step” is one model call or tool action. The 4-call FizzBuzz loop in harness calls is N = 4; a real coding session is often dozens.

pass^k is “the chance that all k i.i.d. task trials are successful, averaged across tasks” (τ-bench §3). Measured pass^8 is far above 2% because failures cluster: some tasks the agent nearly always gets right, others it nearly always gets wrong. METR finds 80% horizons “roughly 5x shorter” than 50% ones across models, and horizons doubling about every 7 months. These are 2024–25 models; newer ones score higher, but the shape holds.

Worked example 2: checking turns failures into retries

one step, p = 0.90, checked, up to 2 retries (3 tries total): fails only if all 3 tries fail: 1 − 0.1^3 = 1 − 0.001 = 99.9% average tries used: 1 + 0.1 + 0.01 = 1.11 20-step task: unchecked 0.90^20 = 12.2% vs checked 0.999^20 = 98.0%

Assumes each retry is an independent draw and the check (a test, a schema validator, a compiler) catches every bad output. 11% more calls buy an 8× higher task success rate here.

Why it beats the alternatives

✗ Longer, stricter prompts

More rules in the system prompt add prefill time on every call, but can't stop a wrong step from passing silently. τ-bench agents already had the full policy and still broke it.

✗ A bigger model, nothing else

Raising p from 90% to 95% helps, but 50 unchecked steps still finish only 7.7% of the time. Every model's errors compound; they just compound slower.

✗ More autonomy, no checks

Letting the agent run longer raises N, and success falls with pN. METR's horizons shrink about 4× when you ask for 80% success instead of 50%.

✓ Verify each step against reality, keep tasks short

Tests, type checks and schema validation catch a bad step immediately, so it costs one retry, not the whole task: 12.2% → 98.0% for 20 steps. Short tasks keep N small.

Do retries always fix it?

No. The 99.9% figure assumes each try is a fresh coin flip. When the model is systematically wrong (it misreads the spec, doesn't know an API, or the test itself is wrong), it fails the same way every time. τ-bench shows this: 61% single-try success but ~25% all-8, not the 2% independence would predict, so the failures sit on the same tasks. Retries also can't help if nothing checks the output: a confident wrong answer looks like success.

For those cases, change something between tries (new context, a different model, a hint from the error message), or put a human at the steps that are expensive or impossible to undo: payments, deletes, deploys. Checking isn't always worth it either: for one-shot questions with no cheap check, a single careful call is simpler.
