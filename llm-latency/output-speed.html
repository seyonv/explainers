Output speed (tokens per second)

Also called decode speed, generation speed, or tok/s. It's how fast the answer streams once it starts. It's the headline number on Artificial Analysis and OpenRouter provider pages.

Prime · 2 minutes before you read

The problem: Once text starts streaming, the pace it scrolls at decides how long any answer longer than a few sentences takes. Without a clean per-request number you can't compare hosts, and you'll confuse it with server throughput or end-to-end time.

Where it fits: Second metric card. TTFT covered the wait before the first token; this card is the divisor in the writing-time term, tokens ÷ speed. The mechanism cards later explain what sets it.

In one breath

Output speed is how many tokens the model writes per second after the first token arrives. A token is about ¾ of a word. The model has to produce tokens one after another, so this number sets the pace of every answer.

How it differs from related ideas

✗ TTFT

The wait before the first token. Measuring speed from the first token keeps queueing and prompt reading out of this number, so each metric shows one thing.

✗ Throughput

Total tokens per second a server produces across all users. Providers batch many users together to raise it, which can make each person's speed slower.

✗ End-to-end time

The whole response. It mixes speed with length and thinking, so a slow model that writes briefly can still finish first.

✓ Output speed

The per-request writing pace. It's set by hardware memory bandwidth, model size, and serving tricks, so it's the number to compare hosts on.

Is a higher number always what I want?

Not always. For short answers, TTFT matters more. At 82 tokens, Cerebras (0.50 s + 0.05 s) and Groq (0.72 s + 0.17 s) are both under a second, and the wait is mostly TTFT. For reasoning models, a fast speed can hide a long silent think: Gemini 3.8 Flash (high) writes at 344 t/s but has a 22.7 s TTFT. The fastest host may also cost more or run a more heavily quantized model, which OpenRouter's provider list shows (bf16 / fp8 / fp4). Compare quality before choosing the fastest.

Understand and remember

  • Tokens are generated strictly one after another → the pace per token sets the whole writing time → writing time = tokens ÷ output speed → a 36× faster host writes the same answer 36× faster
  • Output speed is timed from the first token → queueing and prompt reading are excluded → it isolates the decode pace, which is what hardware, quantization and serving tricks change
  • Hosts batch many users per chip to raise throughput → each user's share of the chip shrinks → per-request speed falls → compare hosts on per-request speed, not throughput
  • detail that matters Reasoning models are measured on the last 80% of answer chunks → a high speed can sit on top of a long silent think (Gemini 3.8 Flash high: 344 t/s but 22.7 s TTFT) → always read speed next to TTFT

Why this step?

5 · Predict commit to an answer before revealing

A host doubles its batch size to cut cost. Predict what happens to its output speed per request and to its throughput, and say whether either change is exactly 2×.

Reveal

Throughput rises and per-request speed falls, but neither by exactly 2×. While decode is memory-bound, one weight read serves the whole batch, so a bigger batch costs little extra time per step: throughput nearly doubles and each user slows only a little. Once the batch is big enough that compute or KV-cache reads dominate, each step gets noticeably slower and per-user speed drops more.
