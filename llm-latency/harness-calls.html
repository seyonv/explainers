Harness call count

Also called the agent loop, tool-use loop or turns. The harness is the program around the model: Claude Code, Cursor, Codex CLI, or your own llm.chat() script. It decides how many times the model gets called for one task.

Prime · 2 minutes before you read

The problem: "Claude Code is slower than Claude" is a confusion of model and harness. One request to an agent becomes a loop of model calls and tool runs, and each call pays its own start and writing time. Without seeing the loop you optimise tokens/s when the real cost is the call count.

Where it fits: Second multiplier card. The per-call formula from the overview now repeats N times with tool time between. Context growth, next, shows that each call in the loop also gets bigger.

In one breath. Claude Code is a harness, not a model. One request from you becomes a loop: call the model, run a tool, send back the result, call again. Each call pays its own time to first token and writing time, then waits for the tool.

Worked example: “write FizzBuzz”, 1 call vs a 4-call agent loop

Raw API: just answer1503.66 s—3.66 s

total = Σ over calls ( time to first token + output tokens ÷ speed ) + tool time per call: 1.39 s + out ÷ 66 tokens/s e.g. call 1: 1.39 + 200/66 = 4.42 s loop: 4 × 1.39 s waiting + 480/66 s writing + 0.6 s tools = 13.43 s → 3.7× the raw call

Time to first token (1.39 s) and speed (66 tokens/s) are Artificial Analysis medians for Claude Sonnet 5, non-reasoning (2026-09-21). The call count, token counts and tool times are illustrative. Real sessions vary a lot.

Why it beats the alternatives

✗ One raw API call

Fastest (3.66 s), but it can't see your files, run the code or fix its own mistakes. You do all of that yourself.

✗ Paste the whole repo in one prompt

Still one call, but a huge prompt pays a large first-token delay every time, and it goes stale as soon as the code changes.

✗ Chat, copy, paste, repeat

Same loop as an agent, but you are the tool runner. Your copy-paste minutes dwarf the model's seconds.

✓ Agent harness loop

More calls (3.7× here), but each step is checked against reality. Prompt caching keeps re-sending the history cheap, and the task ends up done, not just answered.

Is Claude Code slower than “Claude”?

Per call, no: it uses the same model at the same speed. Per task, often yes for tiny tasks. A one-shot question like FizzBuzz is fastest as a single API call or chat, where the loop's extra calls and big system prompt buy nothing. The harness wins on real multi-step work: reading files, editing, running tests and retrying.

To speed up an agent, cut the number of calls (clear instructions, fewer check-backs) before chasing tokens/s. Running a harness on a local model is where it hurts most: every call re-reads thousands of prompt tokens at laptop prefill speed.

Understand and remember

  • The harness wraps the model in a loop → call, run a tool, send back the result, call again → each call pays its own TTFT and writing time → total ≈ N × TTFT + total output ÷ speed + tool time
  • Per call the model is the same speed → per task the number of calls multiplies the cost → for a one-shot question a single call wins (3.66 s vs 13.43 s, 3.7×)
  • Each tool result is checked against reality → the task ends up done, not just answered → for multi-step work (read, edit, test, retry) the loop beats you as the tool runner
  • detail that matters Every call re-sends the growing history as its prompt → prefill on each call → cheap with prompt caching on a fast host, very expensive on a laptop's prefill speed

Check
  • token loop: one decode step per output token, inside the server
  • harness loop: one full call (prefill + decode) per step, outside the server
  • prompt wording can cut both: fewer calls and fewer output tokens

5 · Predict commit to an answer before revealing

Run the same 4-call loop on your M3 with qwen3.5:4b (15.4 t/s) and a 5,000-token system prompt that is not cached. Predict whether the total is dominated by writing, tools or prefill. Commit before revealing.

Reveal

Prefill. Each call reads at least 5,000 tokens at about 207 t/s ≈ 24 s, so 4 calls ≈ 97 s of reading, against 480 ÷ 15.4 ≈ 31 s of writing and 0.6 s of tools. That's why a harness on a local model hurts most, and why caching the prefix matters.
