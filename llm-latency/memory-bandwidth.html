Memory-bandwidth-bound decoding

Also called "decode is memory-bound" or "the bandwidth ceiling". It's the main reason your M3 writes about 15 tokens/s with qwen3.5:4b, and why hosted GPUs are so much faster.

Prime · 2 minutes before you read

The problem: If you think "faster chip = faster tokens", you'll buy compute that sits idle. Token generation is limited by how fast memory can feed the weights to the chip, and one division predicts it.

Where it fits: First mechanism card. The metric cards measured output speed; this card explains what sets it. Hardware, quantization, MoE and speculative decoding each attack one side of the division introduced here.

In one breath

Writing each new token means streaming every active weight of the model from memory through the chip. The chip does little math per byte, so speed is capped by how many bytes per second memory can deliver, not by how fast the chip computes.

Worked example: your Mac

ceiling (tokens/s) ≈ memory bandwidth ÷ bytes read per token qwen3.5:4b Q4_K_M: 4.7B params × ~4.85 bits ÷ 8 ≈ 2.85 GB per token (estimate) Apple M3 bandwidth: 100 GB/s ceiling ≈ 100 ÷ 2.85 ≈ 35 tokens/s measured (Ollama eval rate) 15.4 tokens/s → about 44% of ceiling your 653-token FizzBuzz answer: 653 ÷ 15.4 = 42.4 s

Across Apple chips, the same model's speed goes up with bandwidth (llama.cpp, Llama 7B Q4_0, about 3.5 GB):

ChipBandwidthCeiling (bw ÷ 3.5 GB)Measured% of ceiling
M3100 GB/s28.6 t/s21.34 t/s75%
M3 Pro150 GB/s42.9 t/s30.74 t/s72%
M3 Max400 GB/s*114.3 t/s66.31 t/s58%

4× the bandwidth gives about 3.1× the speed. *The M3 Max ships at 300 or 400 GB/s. The thread doesn't say which variant was benchmarked, so 400 is assumed. Your qwen3.5 run reaches a lower share of its ceiling than Llama does. My best guess, not verified: Ollama's code for the newer qwen35 architecture is less optimized.

How it differs from related ideas

✗ "Faster chip = faster tokens"

More compute (TFLOPS) barely helps generation. The cores spend most of their time waiting on memory, so a chip with more bandwidth wins even with less compute.

✗ Prefill (reading the prompt)

Prompt tokens are processed in parallel, so each weight you read is reused many times. That's compute-bound: your M3 read 2,605 prompt tokens at about 207 t/s, over 13× its writing speed.

✗ "Model size in GB on disk"

What counts is the bytes actually read per token. A mixture-of-experts model only reads its active experts, and a vision encoder sits idle during text generation.

✓ Bandwidth ÷ bytes per token

One division predicts speed well: shrink the bytes (quantization, MoE, smaller model) or raise the bandwidth (better hardware). Every speed lever maps onto one side of it.

Is it always the bottleneck?

No. It dominates when one user writes a long answer, which is your case. It stops being the limit when:

  • the prompt is huge (prefill takes over);
  • a server batches many users together (reading the weights once serves the whole batch, so compute becomes the limit);
  • the answer is only a few tokens (time to first token and network dominate).

If your wait is mostly before the first token, look at prompt caching or TTFT instead.

Understand and remember

  • Each decode step produces one token and needs every active weight → the whole model streams from memory once per token → little math per byte → speed ≈ bandwidth ÷ bytes read per token
  • Two ways to go faster → shrink the bytes (quantization, MoE, smaller model) or raise the bandwidth (better hardware) → every speed lever maps onto one side of the division
  • Prefill processes many prompt tokens per weight read → each byte is reused many times → compute-bound, not memory-bound → prompt reading is over 13× faster per token than writing on the M3
  • detail that matters Real runs reach only part of the ceiling (44% for qwen3.5 on the M3, 58–75% for Llama 7B) → software overhead and attention reads matter → use the ceiling as an upper bound, not a prediction
