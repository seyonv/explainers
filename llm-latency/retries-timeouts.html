Retries, timeouts and fallbacks

Also called rate limits, 429 / 529 errors, exponential backoff, failover or provider fallback. Built into the Anthropic and OpenAI SDKs (on by default) and into routers like OpenRouter. It matters most in agents, where one task is many calls.

In one breath. Some API calls fail (the server is busy, or you are over your limit) and some just hang. A retry sends the same call again after a short wait. A timeout is how long you wait before giving up. A fallback sends the call to a different provider or model when the first one keeps failing. Set them well and a failure costs you a second. Set them badly and it costs you minutes, or the whole task.

Anthropic and OpenAI Python SDKs, current main: max_retries = 2, timeout 10 minutes (5 s to connect). A 429 caused by hitting a monthly spend cap has no retry-after and keeps failing until the cap resets.

Worked example 1: exponential backoff with jitter

Exponential backoff doubles the wait after each failure so a busy server gets breathing room. Jitter shaves a random amount off each wait so a thousand clients that failed together don't all retry in the same instant. The SDK numbers:

wait(n) = min(0.5 s × 2^(n−1), 8 s) × (1 − 0.25 × random) n = retry number 2 retries: 0.5 + 1 = 1.5 s max (× 0.75 → 1.125 s min) 4 retries: 0.5 + 1 + 2 + 4 = 7.5 s max (× 0.75 → 5.625 s min) if the server sends retry-after: wait exactly that instead of wait(n)

Constants are from the SDKs' source (INITIAL_RETRY_DELAY = 0.5, MAX_RETRY_DELAY = 8.0). The sleeping is cheap. The real cost is each failed attempt's own time, plus a retry-after that can be tens of seconds. The OpenAI SDK only obeys retry-after up to 2 minutes; the Anthropic SDK obeys any value. In the 4-call agent loop from harness calls (13.43 s), one quick 529 on a call adds about 0.4–0.5 s of sleep, plus the failed attempt's own time.

Why it beats the alternatives

✗ No retry (max_retries=0)

Every brief 429 or 529 kills the call. In a 20-call agent task, one blip anywhere fails the whole task.

✗ Retry right away in a loop

Hammers a server that is already overloaded, burns your rate limit faster, and all clients retry in the same instant. It ignores retry-after, so those early retries fail anyway.

✗ Huge timeout, no streaming

Nothing breaks, but a call that is truly stuck hangs for the full 10 minutes before you find out. Some networks also drop idle connections well before that.

✓ Bounded backoff + streaming + fallback

A few jittered retries (about 1.5 s) cover blips. Streaming lets a short timeout catch dead calls without killing long ones. When one provider stays down, a fallback (OpenRouter models: [...], or a second SDK client) answers instead.

Are retries free safety?

No, for two reasons. First, duplicate side effects. If a step fails after its tool already ran (say, the tool worked but the reply timed out), a harness that retries the whole step runs the tool again: two emails sent, two rows inserted, two payments. Make tool actions idempotent, meaning safe to run twice: send a unique request ID, check "already done?" before writing, and prefer "set X to 5" over "add 1 to X".

Second, retries hide outages. The SDK quietly absorbs failures, so you only see "slow", not "failed twice". Log every retry (the SDKs send an x-stainless-retry-count header, and debug logging names each one) and alert when the rate climbs. Also, don't retry what can't succeed: a 400, a bad key or a spent monthly cap fails the same way every time, and a fallback model may give different quality answers and bills at its own price.
