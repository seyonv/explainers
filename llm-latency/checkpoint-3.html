Checkpoint 3: time to a correct result

Ties together tail latency, retries, timeouts and fallbacks, compounding errors, parallel calls and model routing: what stretches an agent's attempt, what spoils it, and which defence fits which failure.

How to use this page. Close the five cards. Answer each question in writing, in full sentences, before opening its Check. A wrong or shaky answer isn't a failure; it tells you exactly which section to reopen. The questions are mixed on purpose, so you have to work out which idea applies before you can answer.

1 · Mixed retrieval

  1. which concept?A step that sends an invoice email timed out, the harness retried it, and the customer got two emails. Which idea explains it, and what's the fix that still lets you retry?
    Check
    • the tool had already run when the reply timed out, so retrying the step ran it again: a duplicate side effect
    • make the action idempotent: a unique request ID, check "already sent?" before sending
    • a hedged backup request would have the same problem, so don't hedge calls with side effects

    Missed it? Reopen retries, timeouts and fallbacks, "Are retries free safety?".

  2. A 20-step task has 90% per-step success. Compute task success with no checks, and with a check and up to 2 retries per step. How many extra calls does checking cost on average?
    Check
    • unchecked: 0.9020 ≈ 12.2%
    • checked: each step fails only if all 3 tries fail: 1 − 0.13 = 99.9%; 0.99920 ≈ 98.0%
    • average tries per step 1 + 0.1 + 0.01 = 1.11: about 11% more calls for about 8× the success

    Missed it? Reopen compounding errors, worked example 2.

  3. which concept?An agent's median call is 0.61 s, yet 50-call tasks regularly take far longer than 50 × 0.61 s, and nothing is failing. Which idea explains it, and how likely is at least one slowest-1% call per task?
    Check
    • tail latency: identical calls vary, and many calls make hitting the tail likely
    • 1 − 0.9950 ≈ 39.5% of tasks have at least one call in the slowest 1%
    • one p99 call at Together AI's numbers is 12.45 s, about 20× the median; budget p95/p99 and hedge after the p95 wait

    Missed it? Reopen tail latency, worked examples 2 and 3.

  4. A max-effort call takes 147.4 s. The client uses a 60 s timeout, no streaming and the SDK's default 2 retries. Walk through what happens and how long it takes.
    Check
    • no bytes arrive until the end, so each attempt is cut off at 60 s and its thinking thrown away
    • 3 attempts × 60 s + backoff 0.5 + 1.0 s = 181.5 s, then a timeout error and no answer
    • fix: stream (pings keep bytes arriving) or raise the timeout for thinking calls

    Missed it? Reopen retries, timeouts and fallbacks, worked example 2.

  5. which concept?A test step fails, the agent retries it three times, and it fails in exactly the same way each time. Which idea predicts this, and what should the harness do instead?
    Check
    • retries assume independent tries; this is a systematic (correlated) failure
    • τ-bench shows it: 61% single-try success but ~25% on all 8 tries, not the 2% independence predicts
    • change something between tries (new context, the error message as a hint, a bigger model), or hand it to a person

    Missed it? Reopen compounding errors, "Do retries always fix it?".

  6. An agent needs 5 independent web searches. Compare one search per response with all 5 in one response run at once, using the card's numbers. Which change gives most of the saving?
    Check
    • sequential: 5 × 2.30 + 6.5 + 4.42 = 22.42 s
    • parallel: 5.94 + max 2.0 + 4.42 = 12.36 s
    • most of it is fewer model calls (6 → 2): putting all 5 in one response but running them one by one is already 16.86 s

    Missed it? Reopen parallel calls, the worked example.

  7. In the routed 10-call plan (7 easy on Haiku, 3 hard on Sonnet), what happens to time and cost if 3 easy calls fail their check and escalate, instead of 1?
    Check
    • time: 7 × 1.80 + 3 × 7.45 + 3 × 2.91 ≈ 43.7 s, now slower than all-Sonnet's 42.7 s
    • cost: $0.0245 + $0.072 + 3 × $0.007 ≈ $0.118, still just under $0.121
    • a high escalation rate erases the time win first; route only steps the small model reliably passes

    Missed it? Reopen model routing, the worked example.

  8. With the SDK's backoff (0.5 s doubling, jitter 75–100%), how long does a client sleep in total across 4 retries, and why is the sleep rarely the real cost of a failure?
    Check
    • 0.5 + 1 + 2 + 4 = 7.5 s at most, 5.625 s at least with jitter
    • the real cost is each failed attempt's own time, plus any retry-after the server sends (it can be tens of seconds)

    Missed it? Reopen retries, timeouts and fallbacks, worked example 1.

3 · Project: simulate an agent's time to a correct result

What it reinforces: slow calls in the tail (tail latency), failures that restart the task vs one step (compounding errors), hedging and its limits (retries, tail latency), and why a median alone misleads.

10 steps · each step is one model call, correct with p = 0.90 call time: 0.61 s with probability 0.99, 12.45 s with probability 0.01 (Together AI's measured p50 and p99) check: 0.5 s per step (designs B and C) A unchecked: if any step was wrong, redo the whole task B checked: retry only the failed step until it passes C checked + hedge: if a call hasn't returned after 1.0 s, send a backup and take whichever returns first

In about 40 lines of Python, simulate each design 100,000+ times and print the mean, p50, p95 and p99 of the task time. Then:

  1. Predict first. Before running, write down which design has the lowest mean and whether any two designs have nearly the same median.
  2. Check the means analytically. Expected call time = 0.99 × 0.61 + 0.01 × 12.45. Design A = 10 × that ÷ 0.9010. Design B = 10 × (call + 0.5) ÷ 0.90. Your simulated means should match within about 1%.
  3. Read the tails. Compare p95 and p99 across the three designs. Which design does the median flatter most?
  4. Break the hedge. Make the slowness shared: if the first call is slow, the backup is slow too. What happens to design C?
Done when: your analytic and simulated means agree, you have a four-number summary per design, and you can explain in one sentence why A and B have almost the same median but very different p95. Then compare with the check.
Check: the numbers (from a Python simulation with 200,000 runs per design, seed 1)
  • Expected call time: 0.99 × 0.61 + 0.01 × 12.45 ≈ 0.728 s. Analytic means: A ≈ 7.28 ÷ 0.349 ≈ 20.9 s; B ≈ 10 × 1.228 ÷ 0.90 ≈ 13.6 s; C ≈ 12.5 s (hedged call ≈ 0.621 s).
  • Simulated: A mean 20.9, p50 12.2, p95 about 55, p99 about 85 s. B mean 13.6, p50 12.2, p95 about 24, p99 about 26 s. C mean 12.5, p50 12.2, p95 about 14.4, p99 about 16.7 s.
  • The medians match because a typical run has no slow call and at most one failure. The difference is all in the tail: A's failed attempts restart the whole task, B confines a failure to one step, and C also cuts off the 12.45 s outliers.
  • Shared slowness: the backup is as slow as the first call, so C falls back to about B's numbers while still paying for the extra calls. Hedging only helps when slowness is independent.
