How to think about agent speed and reliability

Overview card: end-to-end latency, time to a correct result, reliability, pass^k. The other overview explains one model call. This one explains a whole agent task, where the question is how long until you have a result you can trust.

Prime · 2 minutes before you read

The problem: An agent that is fast per call can still take ages to finish, because it makes many calls, re-sends its growing history, hits slow outliers, and sometimes produces a wrong result you have to redo. Timing one call tells you almost nothing about when you'll have something you can trust.

Where it fits: The second map. The first overview explained one model call; this one puts that call in a loop and adds reliability. Its formula divides one attempt's time by the chance the attempt is right, and the agent cards each explain one term.

In one breath

An agent is many model calls in a loop. Its speed is the sum of those calls, stretched by a growing history, slow outliers and retries. Its reliability is every step going right, which multiplies down fast unless something checks each step. What you actually wait for is the time to a correct result: the time for one attempt divided by the chance that attempt is right.

Filled in with the compounding-errors card's example: 10 unchecked steps of 2.91 s at p = 0.90 → 29.1 s ÷ 0.9010 = 29.1 ÷ 0.349 = 83.5 s. Test each step instead and a failure costs one step, not the whole task: 37.9 s. Checking changes the denominator, and it's the biggest lever here.

The words people use

Inference latency

The time for one model call: time to first token plus writing time. What the first 13 cards cover.

End-to-end latency

The time for a whole request or task, including every call, tool and retry. What you feel with an agent.

Throughput, p50 / p99, availability

Server-side terms: tokens per second across all users, the typical vs the slowest-1% request, and the share of time the API is up.

✓ Time to a correct result

The number that matters for agents. It folds speed and reliability (success rate, pass^k) into one: attempt time ÷ chance of success.

The takeaway

Check first, then trim, then speed up. An unchecked agent that's twice as fast can still take longer to reach a correct result, because a failed attempt costs the whole task. So make every step verifiable (run the tests, validate the output) and keep tasks short. Then cache the stable prefix, parallelize independent steps, and route easy steps to a small model. Last, handle the tail: timeouts sized for thinking, backoff with jitter, a fallback provider.

This isn't always worth it. For a one-shot question with no cheap check, one careful call beats any loop (see harness calls). And retries don't fix a model that's wrong the same way every time. Change something between tries, or put a person at the steps you can't undo.

Understand and remember

  • Every step must go right and failures are silent → success = pN → falls fast with N → expected attempts = 1 ÷ pN → a failed attempt costs the whole task
  • Checking each step against reality → a bad step costs one retry, not the whole task → the denominator jumps (12.2% → 98.0% for 20 steps at p = 0.9) → checking beats any speed lever
  • Each call re-sends the history and some calls land in the tail → attempt time grows faster than the call count → cache the stable prefix, parallelise independent steps, budget for p95/p99
  • Model size moves both sides → a small model makes easy steps faster, but the wrong model for a hard step lowers p → route by step type and escalate on a failed check
  • detail that matters Retries only help when tries are independent → systematic errors fail the same way every time → change something between tries or put a person at irreversible steps

Why this step?

3 · Retrieve from memory, card closed
  1. concept Explain "time to a correct result" to someone who only measures agent speed in seconds per call. Why is it the number that matters?
    Check
    • an attempt that ends wrong has to be repeated or fixed by you
    • so expected time = attempt time ÷ chance the attempt is right
    • it folds speed and reliability into one number you can compare across setups
  2. mechanism Walk through the example: 10 unchecked steps of 2.91 s at p = 0.90. Compute the time to a correct result, then say what testing each step changes and why the result drops to 37.9 s.
    Check
    • attempt: 10 × 2.91 = 29.1 s; success 0.9010 = 0.349
    • 29.1 ÷ 0.349 = 83.5 s
    • with a test per step, a failure retries only that step: 10 × (2.91 + 0.5) ÷ 0.90 = 37.9 s
  3. tradeoff You have one afternoon to speed up an agent that often ends with a wrong result. Rank caching the prefix, adding step checks and switching to a faster host, and justify the order.
    Check
    • checks first: they raise the denominator, which dominates when failures are common
    • caching next: cheap, cuts the growing re-sent history
    • faster host last: only shrinks the top, and wrong results still repeat

Why this step?

5 · Predict commit to an answer before revealing

Keep 10 steps of 2.91 s but raise per-step success from 0.90 to 0.95, still with no checks. Is the new time to a correct result closer to 83.5 s or to 37.9 s? Commit, then reveal.

Reveal

0.9510 = 0.599, so 29.1 ÷ 0.599 ≈ 48.6 s. A better model helps a lot, but checking the fast model (37.9 s) still wins. With checks, the p = 0.95 model would be 10 × 3.41 ÷ 0.95 ≈ 35.9 s: checks and a better model stack.
