Checkpoint 2: what multiplies the tokens

Ties together output length, thinking tokens, harness call count, context growth and prompt caching: the ways one request turns into far more tokens than you see, and what keeps that affordable.

How to use this page. Close the five cards. Answer each question in writing, in full sentences, before opening its Check. A wrong or shaky answer isn't a failure; it tells you exactly which section to reopen. The questions are mixed on purpose, so you have to work out which idea applies before you can answer.

1 · Mixed retrieval

  1. which concept?A team doubles its agent sessions from 30 calls to 60 and the input-token bill goes up 3.2×, not 2×. Which idea explains the extra, and which two fixes attack it?
    Check
    • context growth: each call re-sends the whole history, so input on call k grows linearly and the session total grows with the square of the calls
    • 30 calls: 1,470,000 tokens; 60 calls: 4,740,000, about 3.2×
    • fixes: a byte-identical cached prefix (0.1× reads), and compaction or a fresh session when history gets long

    Missed it? Reopen context growth, the worked example.

  2. Split the 115.5 s thinking-on FizzBuzz run on the M3 into its three parts, with numbers. Which part would an effort setting change?
    Check
    • the answer: 80 tokens ÷ 15.7 t/s ≈ 5.1 s
    • thinking: about 1,684 tokens ÷ 15.7 t/s ≈ 107.3 s
    • slightly slower tokens from the longer history: about +3.1 s
    • effort changes the number of thinking tokens, not the speed per token

    Missed it? Reopen thinking tokens, "Where the extra 110 seconds come from".

  3. which concept?Someone times FizzBuzz in Claude Code at about 13 s and in a raw API call at under 4 s, and concludes Claude Code uses a slower model. Which card explains it, and what's the real cause?
    Check
    • harness call count: the same model, called several times in a loop
    • the 4-call loop pays 4 × 1.39 s of TTFT, 480 ÷ 66 s of writing and 0.6 s of tools ≈ 13.43 s vs 3.66 s for one call
    • per call the speed is identical; per task the call count multiplies

    Missed it? Reopen harness call count, the worked example.

  4. For the 30-call session (20k start, +2k per turn) at Sonnet 5 prices, walk through why caching cuts the input cost from $2.94 to $0.47 without sending fewer tokens.
    Check
    • each call's prefix is exactly the previous call's whole input, so it hits the cache
    • cache reads: 1,392,000 tokens at $0.20 / 1M ≈ $0.28
    • cache writes: 20,000 + 29 × 2,000 = 78,000 tokens at $2.50 / 1M ≈ $0.20

    Missed it? Reopen context growth, the cost table, and prompt caching, the pricing note.

  5. which concept?An agent on a local model writes short replies, yet every call sits for a minute or more before any output. Which ideas combine to explain it, and what's the first fix?
    Check
    • the harness re-sends the growing history each call, so every call starts with a big prefill
    • laptop prefill is slow: 20,000 tokens at about 207 t/s ≈ 97 s
    • first fix: keep the prefix stable so it caches; then keep the system prompt short or move the agent to a hosted model

    Missed it? Reopen harness call count, "Is Claude Code slower", and context growth, "What it does to the wait".

  6. On Sonnet 5 (TTFT 1.39 s, 66 t/s), an 82-token answer takes about 2.6 s and a 653-token answer about 11.3 s. Why is the short answer only about 4.3× faster when it has 8× fewer tokens?
    Check
    • total ≈ TTFT + tokens ÷ speed
    • the fixed 1.39 s start doesn't shrink with the answer
    • it is about half of the short answer's time but only an eighth of the long one's

    Missed it? Reopen output length, the formula block.

  7. An agent makes 10 calls with Sonnet 5 at high effort instead of none. Using the effort ladder (first token 11.7 s at high vs 1.4 s at none), roughly how much hidden waiting does that add to the task, and when is it worth it?
    Check
    • about 10 × (11.7 − 1.4) ≈ 103 s more before first tokens (a rough estimate: the ladder was measured on ~10k-token inputs)
    • the thinking repeats on every call that thinks
    • worth it on planning and debugging steps that would otherwise go wrong; not on routine reads and edits

    Missed it? Reopen thinking tokens, worked example 2 and "So should thinking be off?".

3 · Project: model one agent session end to end

What it reinforces: writing time from token counts (output length), hidden tokens that are paid like output (thinking tokens), per-call starts (harness calls), re-sent history (context growth) and what a cache hit saves (prompt caching).

session: 10 calls · 20,000-token start · +2,000 input per turn 150 answer tokens per call hosted: Sonnet 5 · TTFT 1.39 s · 66 t/s per 1M: $2 in · $10 out · cache read $0.20 · cache write $2.50 local: your M3 · prefill 207 t/s · writing 15.4 t/s · no network

Write session(calls, start, step, answer, thinking, cached, host) in about 40 lines of Python. It returns total time, input tokens and input + output cost. Then:

  1. Hosted, thinking off. Total time (N × TTFT + answer tokens ÷ speed), total input tokens, uncached and cached input cost, and output cost.
  2. Hosted, 1,000 thinking tokens per call. What happens to time and to output cost?
  3. Local, no cache vs cached prefix. Here TTFT is mostly prefill, so compute prefill time from the tokens actually read on each call.
  4. Which multiplier dominates? For each of the three setups, say which term is the largest, and which single change you'd make first.
Done when: your function reproduces the card's 30-call totals when you set calls = 30 (1,470,000 input tokens, $2.94 uncached, $0.47 cached), prints all three setups for 10 calls, and you've named the dominant term and first fix for each. Then compare with the check.
Check: the numbers (computed with a Python version of this model)
  • Input tokens for 10 calls: 20,000 + 22,000 + … + 38,000 = 290,000. Uncached: $0.58. Cached: reads 252,000 × $0.20 / 1M ≈ $0.050 plus writes 38,000 × $2.50 / 1M ≈ $0.095, ≈ $0.145.
  • Hosted, thinking off: 10 × 1.39 + 1,500 ÷ 66 ≈ 13.9 + 22.7 ≈ 36.6 s; output cost 1,500 × $10 / 1M = $0.015. The largest term is writing time, then the per-call starts.
  • Hosted, thinking on: 11,500 output tokens → 13.9 + 11,500 ÷ 66 ≈ 188.1 s, and output cost $0.115, now almost as much as the cached input. Thinking dominates: turn it down on routine calls first.
  • Local, uncached: prefill 290,000 ÷ 207 ≈ 1,401 s (23 min) plus writing 1,500 ÷ 15.4 ≈ 97.4 s. Cached: 20,000 ÷ 207 + 9 × 2,000 ÷ 207 ≈ 96.6 + 87.0 ≈ 183.6 s of prefill plus 97.4 s of writing. Re-sent history dominates, so caching is the first fix; a 1,000-token think per call would add 10,000 ÷ 15.4 ≈ 649 s more.
