Checkpoint 1: what sets the speed of one call

Ties together memory-bandwidth-bound decoding, quantization, mixture of experts, speculative decoding, prompt caching and same model, different host: which part of one call each lever speeds up, and by how much.

How to use this page. Close the six cards. Answer each question in writing, in full sentences, before opening its Check. A wrong or shaky answer isn't a failure; it tells you exactly which section to reopen. The questions are mixed on purpose, so you have to work out which idea applies before you can answer.

1 · Mixed retrieval

  1. which concept?A local chatbot on an M3 gets a 2,605-token prompt each time. It sits silent for about 13 s, then streams a short reply at a normal pace. Its owner plans to switch from a 4-bit version of the model (Q4_K_M) to a 2-bit one (Q2_K) to make it faster. Which idea predicts this won't help much, and what will?
    Check
    • the silence is prefill (reading the prompt), which is compute-bound, not bandwidth-bound
    • quantization speeds only the memory-bound writing phase, and Q4 → Q2 is only about 1.11× even there
    • cache the prompt's stable prefix: the card's repeat went from 33.88 s to 0.41 s; keep variable text at the end

    Missed it? Reopen prompt caching, the worked example, and quantization, "Is lower always better?".

  2. Compute the speed ceiling for qwen3.5:4b at 4-bit quantization (Q4_K_M: 4.7B params, about 4.85 bits per weight) on the M3's 100 GB/s, and explain why the measured 15.4 tokens/s is lower.
    Check
    • bytes per token ≈ 4.7B × 4.85 ÷ 8 ≈ 2.85 GB
    • ceiling ≈ 100 ÷ 2.85 ≈ 35 tokens/s; measured is about 44% of it
    • the ceiling ignores attention and KV-cache reads, dequantizing and software overhead (the card guesses a less optimised qwen35 path)

    Missed it? Reopen memory-bandwidth-bound decoding, "Worked example: your Mac".

  3. which concept?Two hosts run the same open model on the same GPU type, both at full 16-bit precision (bf16). You get 300 tokens/s from one and 60 from the other, and neither publishes anything else. Which factor of the host formula most likely explains the gap?
    Check
    • speed ≈ bandwidth ÷ bytes per token × tokens per pass ÷ users sharing the chip
    • bandwidth and bytes per token are the same here, so it's tokens per pass (speculative decoding) or sharing (batch size)
    • sharing is the usual suspect: cheap hosts pack many users per chip, and no host publishes its batch size

    Missed it? Reopen same model, different host, "What it really comes down to".

  4. Qwen3-30B-A3B and a dense 30.5B model both need about 17.2 GB to hold at 4.5 bits. Why is one's speed ceiling on the M3 about 9× the other's, and what happens if you try either on a 16 GB machine?
    Check
    • MoE reads only the active experts: 3.3B × 4.5 ÷ 8 ≈ 1.9 GB per token → ≈ 54 t/s; dense reads all 17.2 GB → ≈ 5.8 t/s
    • memory follows total params, because any token may need any expert
    • neither fits in 16 GB with room for the KV cache and the OS: the speed number is irrelevant until the memory number fits

    Missed it? Reopen mixture of experts, the memory table and "Is MoE always the better pick?".

  5. With acceptance α = 0.8, k = 4 guesses and a draft costing 0.1 of a big pass, what is the average speed-up from speculative decoding, what would 15.4 tokens/s become, and why is the output unchanged?
    Check
    • tokens per pass = (1 − 0.85) ÷ 0.2 = 3.36; time per pass = 4 × 0.1 + 1 = 1.4 units
    • speed-up ≈ 3.36 ÷ 1.4 ≈ 2.4× → about 37 tokens/s
    • the big model verifies every guess and replaces the first wrong one, so only its own tokens survive

    Missed it? Reopen speculative decoding, the worked example.

  6. which concept?Someone says Cerebras must be serving a heavily quantized gpt-oss-120b to reach 1,745 tokens/s, since the ceiling on an H100 is only about 1,240. Which fact from the cards answers them?
    Check
    • OpenRouter lists Cerebras at fp16, not fp4
    • Cerebras keeps weights in on-chip SRAM at 21 PB/s, so bandwidth is no longer the limit at all
    • the 1,240 t/s figure is an H100 ceiling; a different chip has a different ceiling

    Missed it? Reopen same model, different host, the host table and the ceiling estimate, and inference hardware, the bandwidth ladder.

  7. An app sends the same 2,605-token document with a timestamp as the very first line. Every request takes about as long to start as the first one. Walk through why, and what the fix changes.
    Check
    • each token's stored state depends on every token before it, so a cache hit needs an exact prefix from token 1
    • the timestamp changes the first tokens, so nothing after it matches (the card's "new first words" row: 25.99 s)
    • move the timestamp to the end: the document becomes a stable prefix and only the tail is read

    Missed it? Reopen prompt caching, row 3 and "Does it always help?".

3 · Project: a speed-budget calculator for one call

What it reinforces: the bandwidth ceiling (memory bandwidth), bytes per token (quantization, MoE), tokens per pass (speculative decoding), cached vs uncached prefill (prompt caching), and the host view that these factors multiply (hosts).

writing speed ≈ bandwidth ÷ (active params × bits ÷ 8) × efficiency × spec speed-up prefill time ≈ uncached prompt tokens ÷ prefill rate (≈ 0.41 s when the whole prefix is cached) total ≈ prefill time + answer tokens ÷ writing speed

In about 30 lines of Python, write estimate(...) with these inputs: bandwidth (GB/s), active params, bits per weight, efficiency (share of the ceiling reached), acceptance α and k for speculative decoding (or none), prompt tokens, cached prompt tokens, prefill rate, and answer tokens. Then:

  1. Calibrate. For qwen3.5:4b on the M3 (100 GB/s, 4.7B, 4.85 bits), set the efficiency so writing speed is 15.4 t/s.
  2. Reproduce. Estimate a 653-token answer with a short prompt, then the same answer after a 2,605-token prompt at 207 t/s prefill, uncached and cached.
  3. Swap the model. Keep the efficiency and switch to Qwen3-30B-A3B (3.3B active, 4.5 bits). What happens to the 653-token time?
  4. Add a draft. Back on qwen3.5:4b, add speculative decoding with α = 0.8, k = 4 and a draft costing 0.1 of a pass.
  5. Rank the levers for two workloads. (a) short prompt, 653-token answer; (b) 2,605-token prompt, 29-token reply. For each, which of quantize-to-Q2 (1.11×), MoE, speculative decoding and caching cuts the total most?
Done when: steps 1–2 match the cards within 5% (42.4 s, and about 55 s uncached vs 42.8 s cached), your program prints steps 3–4, and you have a ranked list of levers for each workload with one sentence of reasoning. Then compare with the check.
Check: the numbers (computed with a Python version of this calculator)
  • Calibrate: ceiling 100 ÷ 2.85 ≈ 35.1 t/s, so efficiency ≈ 0.44.
  • Reproduce: 653 ÷ 15.4 ≈ 42.4 s. With the long prompt: 2,605 ÷ 207 ≈ 12.6 s + 42.4 s ≈ 55.0 s uncached; 0.41 + 42.4 ≈ 42.8 s cached.
  • MoE: 3.3B × 4.5 ÷ 8 ≈ 1.86 GB per token → ceiling ≈ 53.9 t/s → at 0.44 ≈ 23.6 t/s → 653 tokens ≈ 27.6 s (and 17.2 GB to hold, which fits in 24 GB).
  • Speculative decoding: 2.4× → about 37 t/s → 653 tokens ≈ 17.7 s.
  • Workload (a), writing-dominated: speculative decoding (42.4 → 17.7 s) > MoE (27.6 s) > Q2 (about 38 s, with a quality cost) > caching (nothing to cache in a short prompt).
  • Workload (b), prefill-dominated: 12.6 + 29 ÷ 15.4 ≈ 14.5 s. Caching wins by far (0.41 + 1.9 ≈ 2.3 s); speculative decoding only gets to about 13.4 s and Q2 to about 14.3 s, because neither touches the 12.6 s of reading.
