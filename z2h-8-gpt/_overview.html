The problem: Seventeen cards add one piece each, and the val loss drops a little every time. Without the causal map that joins them, you can retype gpt.py but can't say why the mask, the √head_size, the x + or the LayerNorm has to be there, or which one to suspect when a loss looks wrong.

Where it fits: This is the front page of course 8, read first as the map or last as the recap. It reuses the makemore machinery (embeddings, cross-entropy, train/val splits, BatchNorm, the WaveNet habit of fusing context) and replaces the fixed way context is combined with weights computed from the data.

In one breath: turn Shakespeare into 65 character ids and train a model to predict the next id. Start from a lookup table that sees one character, then let every character gather information from the ones before it, with weights computed from the characters themselves (self-attention). Wrap that in Blocks that communicate, then compute, on a residual stream, normalise and regularise them, and scale up: validation loss falls from 4.87 to 1.48.

1 · Core model what to internalise, what to just look up

Keep it if it changes what you can explain, predict, compare, choose, build or debug. Otherwise it's reference.

Understand and remember

  • Every prefix of a chunk predicts its next character → one (B, T) batch holds B·T examples scored in one pass → but position t's target sits at t + 1 inside the same input → a causal mask (−∞ above the diagonal, then softmax) is required, or the loss falls by reading the answer
  • Equal weights 1/(t + 1) blur the past (row 7 is 0.125 everywhere) → let each token's query dot each earlier token's key → weights now differ per sequence and are learned → but q·k has variance ≈ head_size, so scale by 1/√head_size or softmax starts near one-hot (17.47 → 1.09)
  • Attention only gathers → a per-token feed-forward then processes what was gathered → stacking these Blocks as x = f(x) made 3 Blocks worse (2.33) → x = x + f(x) keeps a gradient path of 1 through every layer (2.16, then 2.08 with projections and 4× FFN)
  • A bigger stack amplifies drifting activations and memorisation → pre-norm LayerNorm keeps each sublayer's input at mean 0, std 1 (2.06) and dropout 0.2 blocks memorising → only then does 255× more parameters pay off: 10,788,929 params, val 1.48
  • detail that matters Attention treats its inputs as a set → without a position table "tab" and "atb" give the last token identical output → so order must be added as a learned position embedding, which also caps context at block_size and forces the crop in generate
  • detail that matters Multi-head attention splits one 32-wide softmax into four 8-wide ones at the same 7,553 parameters → several independent looks per token → 2.41 to 2.29; nanoGPT computes all heads as one batched tensor with identical results (590,208 params either way)

Reference only

  • the chapter timestamps and each card's numbers (4.8786, 0.1574 / 0.8426, 41,921 params)
  • gpt.py hyperparameters: batch 64, block 256, n_embd 384, 6 heads, 6 layers, dropout 0.2, lr 3e-4, 5000 iters
  • APIs: torch.tril, masked_fill, register_buffer, torch.multinomial, F.cross_entropy wants (B·T, C)
  • Adam's defaults: betas (0.9, 0.999), eps 1e-8, AdamW weight decay 0.01

3 · Retrieve from memory, card closed
  1. concept Explain to a programmer who has used the makemore MLP why self-attention is a better way to use 256 characters of context than concatenating their embeddings into one long input.
    Check
    • concatenation fixes which position feeds which weight, and the input grows with context (256 × 384 = 98,304 numbers)
    • attention keeps one C-wide vector per token and mixes past tokens with weights computed from their content
    • the same q, k, v matrices work at every position and every context length up to block_size
    • order comes back through the position table, which concatenation had built in
  2. mechanism Walk one training step of gpt.py from get_batch to optimizer.step(), giving the tensor shape after each stage and saying which card's idea runs there.
    Check
    • get_batch: xb, yb (64, 256) ids, yb shifted one to the left (batches-of-chunks)
    • tok_emb + pos_emb: (64, 256, 384) (embeddings-and-positions)
    • each of 6 Blocks: LayerNorm, 6 heads with q·kᵀ (64, 6, 256, 256) scaled, masked, softmaxed, @ v and concatenated back to 384, projection, add; then LayerNorm, FFN 384 → 1536 → 384, add
    • ln_f, lm_head: (64, 256, 65) logits; cross-entropy on the (16,384, 65) view against yb
    • backward fills every .grad; AdamW moves all 10,788,929 weights by about lr each
  3. tradeoff Your first gpt.py run prints a val loss of 0.9 after 500 steps and generates gibberish. Rank the levers you'd suspect, and say which check from the course confirms each.
    Check
    • the mask first: a loss far below 1.48 that doesn't show in samples means position t can read t + 1; check wei is 0 above the diagonal (masked-softmax, attention-notes note 4)
    • then the split: val must be the untouched last 10%; if val and train overlap, both look good (char-tokenizer-split)
    • then the targets: yb must be xb shifted by one; xb[:, 1:] == yb[:, :-1]
    • scaling or LayerNorm bugs make training worse, not suspiciously good, so they come later
  4. tradeoff The ladder's steps (bigram 2.49, one head 2.41, four heads 2.29, FFN 2.27, residual Blocks 2.08, LayerNorm 2.06, scaled 1.48) each cost something. Which steps add almost no parameters, and which buy their gain with size?
    Check
    • four heads instead of one: same 7,553 parameters, a pure design gain
    • residual connections: same 16,865 parameters, 2.33 → 2.16
    • LayerNorm: 448 extra (42,369 vs 41,921), 2.08 → 2.06
    • scaling: 42,369 → 10,788,929 parameters and a GPU for 2.06 → 1.48, and it needs dropout because the model is large next to 1M characters

4 · Compare against what you already know

vs WaveNet's idea: fuse context slowly, in a tree: WaveNet and GPT both refuse to crush a long context into one layer at once. WaveNet fuses neighbours two at a time in a fixed tree; GPT lets every token weight every earlier token. Which design choice makes GPT's mixing depend on the data, and what does each approach cost?

Check
  • WaveNet's tree has fixed wiring: which positions combine, and at which level, never changes with the input
  • GPT's weights are softmax(q·k) of the tokens themselves, so each sequence gets its own mixing pattern
  • WaveNet's work grows about linearly with context and needs no position table, since position is built into the wiring
  • attention's work grows with T² (65,536 scores per head per sequence at 256) and it needs position embeddings, but any token can reach any earlier one in one step

vs The six big ideas of Let's build GPT: The big-ideas card states six claims; this overview gives one formula and a pipeline. Which claims does softmax(mask(QKᵀ/√d_k))V already contain, and which only appear in the Block lines or the levers table?

Check
  • in the formula: data-dependent weights (query · key), the causal mask, the √head_size scaling, message passing via V
  • only in the Block lines: communicate then compute, the residual stream, pre-norm LayerNorm
  • only in the levers and ladder: dropout, heads vs head_size, and that scale pays off only after the stabilisers
  • not in either: the data side (the loss is next-character prediction on (B, T) chunks)

Why this step?

5 · Predict commit to an answer before revealing

The next course swaps characters for GPT-2's tokenizer: 50,257 tokens, and tiny Shakespeare becomes 338,025 tokens instead of 1,115,394 characters. With block_size still 256 and n_embd 384, predict how much text the model sees at once, and how big the token embedding table becomes next to all of gpt.py.

Reveal

Each GPT-2 token covers 1,115,394 / 338,025 = 3.30 characters on average, so 256 tokens cover about 845 characters of Shakespeare instead of 256: 3.3× more context for the same attention cost. But the token table grows from 65 × 384 = 24,960 to 50,257 × 384 = 19,298,688 weights, nearly twice the whole 10,788,929-parameter model, and lm_head grows the same way. That's the trade the tokenizer course explains, and why the GPT-2 course ties the two tables together.
