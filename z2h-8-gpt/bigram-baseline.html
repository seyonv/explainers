The simplest model that works: bigram

Also called: a bigram language model, a lookup-table language model, the baseline. Lecture 7 · simplest baseline: bigram language model, loss, generation · 0:22:11

Prime · 2 minutes before you read

The problem: Before building a Transformer you need a working pipeline (batches in, a loss out, text sampled back) and a number to beat. Without a trivial model first, a bug in the loss or the sampling loop looks exactly like a weak model.

Where it fits: It takes the (B, T) batches from the chunks-and-batches card and adds the smallest possible model on top. It's the same bigram you counted and then trained in z2h-3, rewritten as an nn.Module whose interface every later GPT keeps.

In one breath: the model is a single 65×65 table of learnable numbers. To guess the next character it looks only at the current one, reads that character's row of 65 scores, and turns the scores into probabilities. It knows nothing about earlier characters, but it gives us a full working pipeline (loss, training, sampling) and a loss number that every later model has to beat.

Predict first: guessing every character with equal probability 1/65 scores a loss of −ln(1/65) = 4.17. The untrained table is filled with random numbers. Will its loss on the first batch be above or below 4.17?

Above: 4.8786. Random scores make the model confidently prefer characters for no reason, and on average it's confidently wrong. Being wrongly confident costs more than admitting you don't know, so the random table loses to the uniform guess. Karpathy reads this as the initial predictions being "not super diffuse" (0:22:11 chapter).

One step of the model

A few words first. A logit is a raw score, any real number; higher means "more likely next". Softmax turns a row of logits into probabilities: exponentiate each one and divide by their sum. nn.Embedding(65, 65) is PyTorch's lookup table: passing in id 24 hands back row 24. Here the row is 65 wide because it is the 65 scores for the next character; there's no hidden layer in between.

The loss: cross-entropy over 32 guesses

The batch from the previous card has B = 4 sequences of T = 8 characters, so the table produces logits of shape (B, T, C) = (4, 8, 65), where C = 65 is the number of possible characters. F.cross_entropy wants one guess per row, so the forward pass flattens them to (32, 65) and the targets to (32,). The loss is the average surprise at the true next character:

Why random is worse than uniform: with logits drawn from a standard normal, the average of e^z is e^0.5 = 1.6487, so ln Σ e^z ≈ ln(65 × 1.6487) = 4.1744 + 0.5 = 4.67, while the true character's own logit averages 0. That estimate matches the whole-train figure (4.7262); one batch of 32 lands higher by chance. The counting row tallies every pair in the 90% train split, as in z2h-3, adds 1 to each count, and scores the val split.

▶ Build itruns on your M3 · about 2 s

When: pause the video at 0:22:11 and type this under your get_batch cell (you need xb, yb, vocab_size and decode from the previous cards). The model:

class BigramLanguageModel(nn.Module):
    def __init__(self, vocab_size):
        super().__init__()
        self.token_embedding_table = nn.Embedding(
            vocab_size, vocab_size)        # the 65 x 65 table

    def forward(self, idx, targets=None):
        logits = self.token_embedding_table(idx)   # (B,T,C)
        if targets is None:
            return logits, None
        B, T, C = logits.shape
        logits = logits.view(B*T, C)          # (32, 65)
        targets = targets.view(B*T)           # (32,)
        return logits, F.cross_entropy(logits, targets)

Sampling, as a method inside the same class. It feeds the whole history each time and keeps only the last column; a bigram doesn't need the history, but the attention models later in the course will:

    def generate(self, idx, max_new_tokens):
        for _ in range(max_new_tokens):
            logits, loss = self(idx)
            logits = logits[:, -1, :]                  # (B, C)
            probs = F.softmax(logits, dim=-1)
            idx_next = torch.multinomial(probs, num_samples=1)
            idx = torch.cat((idx, idx_next), dim=1)    # (B, T+1)
        return idx
torch.manual_seed(1337)
m = BigramLanguageModel(vocab_size)
logits, loss = m(xb, yb)
print("logits.shape:", logits.shape)
print("loss:", loss)
idx = torch.zeros((1, 1), dtype=torch.long)   # token 0 is '\n'
print(decode(m.generate(idx, max_new_tokens=100)[0].tolist()))

Why it beats the alternatives

✗ Guess uniformly

Scores 4.1744 forever. There's nothing to train, so it can't tell you whether your loss, optimizer or sampling code works.

✗ Count the pairs (z2h-3)

The same model, solved exactly: 2.4819 on val with no training. But counting has no gradients, so there's no way to bolt attention layers onto it later.

✗ Start with the full Transformer

Ten million parameters and many more places for bugs. Without a simple reference number you can't tell a broken GPT from a weak one.

✓ A learned 65×65 table

4,225 parameters, trained by gradient descent to 2.49 val in about 15 s on CPU. Every later model keeps its interface, (idx, targets) → (logits, loss) plus generate, and has to beat its number.

Isn't nn.Embedding for embeddings?

Usually yes: a row is a learned vector that later layers process. Here the vector happens to be 65 wide and is used directly as the logits, which is why the table is square. On the Token and position embeddings card it gets split into a 65×32 embedding plus a separate lm_head layer that maps 32 numbers back to 65 scores.

The bigram is a baseline, not a model you'd keep. It can't use context: its 'e' gets the same guesses after "Th" as after "wh", so training stalls near the counting answer: 2.4546 on train (the exact counts fit train as well as a bigram can, apart from the tiny +1 smoothing) and 2.4819 on val. Anything that needs two or more characters of history needs a model that reads them, which is what the rest of this course builds.

1 · Core model what to internalise, what to just look up

Keep it if it changes what you can explain, predict, compare, choose, build or debug. Otherwise it's reference.

Understand and remember

  • The current character's id picks one row of the 65×65 table → that row is the 65 logits for the next character → the prediction depends on the current character only → identical characters get identical guesses whatever came before
  • Random N(0, 1) logits → ln Σ ez averages about ln 65 + 0.5 ≈ 4.67 while the true logit averages 0 → confident wrong guesses cost more than uniform ones → untrained loss 4.73 over all train pairs (4.8786 on the first batch) sits above −ln(1/65) = 4.17
  • One character of context → the best possible table is just the pair frequencies → training stalls near the counting answer (2.45 train, 2.48 val; bigram.py reaches 2.49 val) → going lower needs a model that reads earlier characters
  • forward(idx, targets) → (logits, loss) and generate feed the full history → the bigram ignores it, but attention models later swap in without touching the training or sampling code
  • detail that matters logits.view(B*T, C) and targets.view(B*T) → cross-entropy treats all 32 positions as independent guesses → one batch gives 32 training signals, not 4

Reference only

  • nn.Embedding(vocab_size, vocab_size) with vocab_size 65 → 4,225 parameters
  • PyTorch's cross-entropy expects logits as (N, C) and targets as (N,)
  • kick-off token torch.zeros((1, 1), dtype=torch.long) = id 0 = '\n'
  • torch.multinomial(probs, num_samples=1) and torch.cat((idx, idx_next), dim=1)
  • seed 1337 set right before building the model to reproduce 4.8786

Why this step?

5 · Predict commit to an answer before revealing

You train the bigram with block_size 256 instead of 8, same batch size and steps. Does the final val loss go well below 2.49? What changes?

Reveal

No. Each position still sees only its own character, so the ceiling stays at the pair-count answer (about 2.48 val). What changes is that each batch holds 32 × 256 guesses instead of 32 × 8, so the gradient is less noisy and each step costs more. Context length only helps a model that reads its context.
