One head, then many heads

Also called: the self-attention layer, sa_head, multi-head attention (MHA), multi-headed self-attention. Lecture 7 · inserting a single self-attention block to our network · 1:19:11 · multi-headed self-attention · 1:21:59

Prime · 2 minutes before you read

The problem: A single head gives each token one softmax row, one way of weighting its past. If a character needs two different earlier characters for two different reasons, one head has to blend them into a single compromise.

Where it fits: The self-attention-head card built one head as a toy cell. This card plugs that head into the bigram model between the embeddings and lm_head, trains it, then splits it into several smaller heads that run side by side.

Predict first: model A has one head with head_size 32. Model B has four heads with head_size 8, concatenated back to 32. Which has more parameters, and which reaches the lower val loss?

Same parameters, 7,553 each. B wins: val 2.2884 vs 2.4103. Each head's q, k and v are 32 × head_size, so one head of 32 costs 3 × 32 × 32 = 3,072 weights and four heads of 8 cost 4 × 3 × 32 × 8 = 3,072. B doesn't get more capacity. It gets four separate softmax rows per token instead of one, so a token can look for different things at once.

The model after chapter 22

A head is one copy of the attention computation from the crux card: its own query, key and value layers, and its own (T, T) weight matrix wei. Multi-head attention runs several heads on the same x and concatenates their outputs along the channel axis (dim=-1): head 0 fills channels 0–7, head 1 channels 8–15, and so on. Karpathy compares it to a group convolution: several small independent channels instead of one big one.

class Head(nn.Module):
    def __init__(self, head_size):
        super().__init__()
        self.key = nn.Linear(n_embd, head_size, bias=False)
        self.query = nn.Linear(n_embd, head_size, bias=False)
        self.value = nn.Linear(n_embd, head_size, bias=False)
        tril = torch.tril(torch.ones(block_size, block_size))
        self.register_buffer('tril', tril)  # not a parameter
    def forward(self, x):
        B,T,C = x.shape
        k, q = self.key(x), self.query(x)             # (B,T,hs)
        wei = q @ k.transpose(-2,-1) * k.shape[-1]**-0.5
        wei = wei.masked_fill(self.tril[:T,:T] == 0, float('-inf'))
        return F.softmax(wei, dim=-1) @ self.value(x)  # (B,T,hs)
class MultiHeadAttention(nn.Module):
    def __init__(self, num_heads, head_size):
        super().__init__()
        self.heads = nn.ModuleList([Head(head_size)
                                    for _ in range(num_heads)])
    def forward(self, x):
        return torch.cat([h(x) for h in self.heads], dim=-1)

Why it beats the alternatives

✗ One 32-dim head

Each token gets a single softmax row, so it has to blend everything it needs into one weighting. In the ROMEO example it splits 0.52 / 0.26 / 0.17. Val 2.4103.

✗ Four full-size 32-dim heads

Four patterns, but 4 × 3,072 = 12,288 attention weights, and a 128-wide output that needs another layer to shrink back to 32. More cost for the same idea.

✗ Add the heads' outputs instead

Every head would write into the same channels, so lm_head couldn't tell which head found what. Concatenating gives each head its own 8 slots.

✓ Four 8-dim heads, concatenated

Same 7,553 parameters, four independent attention patterns per token, each in its own slice of the output. Val 2.2884.

Are more heads always better?

No. Splitting 32 channels more ways gives more attention patterns, but each head's scores come from a shorter dot product, so each head can match on less. There's a sweet spot, and gpt.py lands on 6 heads of 64 for n_embd 384 (the study section below has a sweep you can try on this model).

This model is also not yet a Transformer block. The heads gather information, but nothing processes it per token before lm_head, and there's no residual path. The next card adds a feed-forward layer and residual connections, and gpt.py's final MultiHeadAttention gains a projection layer after the concatenation. Running the heads as a Python list is also slow on a GPU; nanoGPT computes all heads in one batched matmul with the same result (From our decoder to nanoGPT).

1 · Core model what to internalise, what to just look up

Keep it if it changes what you can explain, predict, compare, choose, build or debug. Otherwise it's reference.

Understand and remember

  • Each head computes its own softmax row per token → four heads give four independent weightings of the same past → a token can pull from ':' in one head and from itself in another → val 2.2884 vs 2.4103 for one head at the same 7,553 params
  • Splitting 32 dims into 4 × 8 keeps q, k, v at 3 × 32 × 32 = 3,072 weights in total → the parameter budget doesn't change, only how it's partitioned → the gain comes from more attention patterns, not more capacity
  • Heads' outputs are concatenated on the last axis → each head writes its own 8 slots of the 32-dim vector → lm_head can still tell which head said what (a sum would mix them into the same slots)
  • The position table has only block_size rows → a context longer than 8 indexes past it → IndexError → generate must crop to idx[:, -block_size:]
  • detail that matters tril is a buffer, not a parameter → it's saved in state_dict and moves with .to(device), but the optimizer never updates it → the mask stays a fixed rule, not something training can erode

Reference only

  • self.register_buffer('tril', torch.tril(torch.ones(block_size, block_size)))
  • nn.ModuleList([Head(head_size) for _ in range(num_heads)]) and torch.cat(..., dim=-1)
  • hyperparameters here: batch 32, block 8, n_embd 32, lr 1e-3, 5000 iters
  • param split: token table 2,080 + position table 256 + attention 3,072 + lm_head 2,145 = 7,553
  • scaling uses k.shape[-1]**-0.5 (head_size), per the correction at 1:20:05
