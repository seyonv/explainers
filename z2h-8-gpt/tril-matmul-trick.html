A triangular matrix multiply does the averaging

Also called: matrix multiply as weighted aggregation, the tril trick, a causal averaging matrix. Lecture 7 · the trick in self-attention: matrix multiply as weighted aggregation · 0:47:11, then version 2: using matrix multiply · 0:51:54

Prime · 2 minutes before you read

The problem: The for-loop average from the previous card is correct but calls torch.mean once per sequence and position. At gpt.py's size that's thousands of small calls per step, and there's no obvious place to plug in weights other than 1/(t+1).

Where it fits: This card rewrites the previous card's xbow loop as a single matrix multiply. It reuses matmul by shapes and broadcasting from the toolkit, and the wei @ x it builds is the exact line every later attention card keeps.

In one breath: row i of a matrix product a @ b is a mix of the rows of b, and row i of a says how much of each row to take. Keep only the lower triangle of a (so row i can't reach rows after i) and make each row sum to 1, and a single multiply computes every token's average of its past. That replaces the double for loop from the previous card with one call, for the whole batch.

Predict first: b is 3 rows by 2 columns, [[2, 7], [6, 4], [6, 5]]. If a is a 3×3 matrix of all ones, what is row 0 of c = a @ b?

[14, 16], the sum of all three rows. Every row of c is the same, because each row of a takes "1 × every row of b". If the rows of b were tokens, token 0 would already contain tokens 1 and 2, which are in its future. Zeroing the upper triangle is what stops that.

Row by row, version 3 is:

c[0] = 1·[2, 7] = [2, 7] c[1] = 0.5·[2, 7] + 0.5·[6, 4] = [4, 5.5] c[2] = ([2, 7] + [6, 4] + [6, 5]) / 3 = [14, 16] / 3 = [4.6667, 5.3333]

torch.sum(a, 1, keepdim=True) sums along dimension 1 (across each row) and keeps the result as a column of shape (3, 1): [[1], [2], [3]]. Dividing the (3, 3) matrix by that column broadcasts it across each row, so every row is divided by its own count.

The sum only ever runs over the past. Any weights would do, as long as the upper triangle stays 0; equal weights are just the simplest choice.

Version 2: the whole toy batch in one multiply

The previous card built x with shape (B, T, C) = (4, 8, 2): 4 sequences (B, the batch), 8 positions each (T, time), 2 numbers per token (C, channels). Its double loop called torch.mean once per (sequence, position): 4 × 8 = 32 calls. Now the weights are an 8×8 matrix called wei, with rows 1, 1/2, 1/3 … 1/8 on and below the diagonal.

wei (8, 8) # row t: 1/(t+1) in columns 0..t, then zeros x (4, 8, 2) # 4 sequences wei @ x → (4, 8, 2) # wei is reused for each of the 4 sequences

wei has no batch dimension, so PyTorch broadcasts it: the same 8×8 matrix multiplies each sequence's own (8, 2) block. Sequences never mix, because wei only ever combines rows within one (8, 2) block. Checking one row by hand against the loop (sequence 0, position 2):

wei[2] = [1/3, 1/3, 1/3, 0, 0, 0, 0, 0] xbow2[0, 2] = (x[0,0] + x[0,1] + x[0,2]) / 3 dim 0: (0.1808 − 0.3596 + 0.6258) / 3 = 0.4470 / 3 = 0.1490 dim 1: (−0.0700 − 0.9152 + 0.0255) / 3 = −0.9597 / 3 = −0.3199

x[0] rows and the loop's xbow[0, 2] = [0.1490, −0.3199] are from labs/average-the-past.py (seed 1337). Across all 64 numbers the largest gap between the loop and the multiply is 1.19e-7: float rounding, because the two add the same numbers in a different order.

Why it beats the alternatives

✗ The double for loop

Correct, but one torch.mean call per sequence and position: 32 for the toy, and 64 × 256 = 16,384 at gpt.py's batch and block size, every step.

✗ A full matrix of ones

One multiply, but nothing blocks the future: every row of c is [14, 16], so token 0 already contains tokens 1 and 2.

✗ A running sum (torch.cumsum) divided by the count

Dividing by 1, 2 … 8 gives the same numbers (allclose is True, computed), but it only does equal weights. It can't say "take most of token 6".

✓ A lower-triangular weight matrix

One batched multiply, the zeros guarantee no peeking ahead, and any weights can sit in the triangle. That last part is what self-attention will use.

Is this attention yet?

Not yet. The weights are fixed at 1/(t+1): every past token gets the same say, in every sequence, which is the lossy "bag of words" average from the previous card. The next card rebuilds the same matrix with masked_fill and softmax, so the zeros can later become learned scores (masked softmax), and then one head computes those scores from the tokens.

The multiply also does wasted work. Of the 64 entries in the 8×8 wei, 28 are zeros, so it does 64 multiply-adds per output channel where 36 would do (1.78×). At block_size 256 that's 65,536 against 32,896, about 2×. It's worth it because one big parallel multiply is far faster than a loop. But if all you ever need is an equal-weight running mean, cumsum does it with work proportional to T instead of T².

A common slip: tril on its own gives sums, not averages (row 2 is [14, 16], three times the mean). The row normalisation is what makes it an average.

Understand and remember

  • Row i of a @ b = Σj aij · row j of b → a's row i is a recipe for mixing tokens → choosing a chooses who talks to whom
  • tril sets aij = 0 for j > i → row i can only mix rows 0…i → no information from the future, which a next-character predictor needs so it can't cheat
  • Divide each row by its sum → every row of weights sums to 1 → each output is a weighted average (1/(t+1) each) instead of a growing sum ([4.6667, 5.3333] instead of [14, 16])
  • wei (T, T) has no batch axis → PyTorch broadcasts it across B → one batched multiply does all B·T averages, and each sequence is mixed only with itself
  • detail that matters The multiply still computes the zeroed upper triangle → 64 multiply-adds per channel where 36 are needed at T = 8, about 2× at T = 256 → attention's cost grows with T², accepted because one parallel matmul beats a Python loop

Reference only

  • torch.tril(torch.ones(T, T))
  • torch.sum(a, 1, keepdim=True) gives shape (T, 1)
  • torch.allclose(xbow, xbow2) → True, max gap 1.19e-7 (float rounding)
  • seed 42 for the 3×3 demo (b = [[2,7],[6,4],[6,5]]), seed 1337 for x

Reveal

wei.sum(1) has shape (8,), which broadcasts along the last axis, so column j is divided by j+1 instead of row t by t+1. Row 7 becomes [1, 0.5, 0.3333, 0.25, 0.2, 0.1667, 0.1429, 0.125], summing to 2.7179, and allclose prints False (computed). No error is raised: a silent broadcasting bug.
