Training it, and moving from notebook to script

Also called: the training loop, the optimization loop, the eval loop (estimate_loss), bigram.py. Lecture 7 · training the bigram model · 0:34:53 · port our code to a script · 0:38:00

Prime · 2 minutes before you read

The problem: An untrained bigram guesses at loss 4.7, and one batch's loss is too noisy to tell you whether training is working or whether the model is only memorising the text it trains on.

In one breath: training repeats five moves thousands of times: grab a random batch, run the model forward to get the loss, wipe the old gradients, backpropagate new ones, and let the optimizer nudge the weights. Moving the code into a script adds a proper report card: every few hundred steps, average the loss over many batches of both the training and the held-out text, with gradient tracking switched off.

Predict first: the untrained bigram starts near 4.7. In the notebook, Karpathy runs 100 AdamW steps at learning rate 1e-3. Where is the loss after those 100 steps?

Barely moved: 4.6563 (the very first step read 4.6924, so 100 steps bought a drop of 0.0361). AdamW moves each weight by roughly the learning rate per step, so 100 steps of about 0.001 hardly dent weights that start around size 1. It takes about 10,000 steps to reach 2.38.

The loop, and the side trip the script adds

Here forward means running the model on xb to get logits and the loss. backward (loss.backward()) is backpropagation: it fills in .grad, the gradient of the loss, on every weight. zero_grad clears last step's .grad first, because PyTorch adds new gradients onto old ones. step is where the optimizer, AdamW, uses the gradients to change the weights (the Adam card explains how).

In the script: a loss you can trust

A single batch is a noisy thermometer. bigram.py raises the learning rate to 1e-2 and, every eval_interval = 300 steps, calls estimate_loss(). That function averages 200 batches from the training split and 200 from the validation split (the 10% of text the model never trains on).

@torch.no_grad()
def estimate_loss():
    out = {}
    model.eval()
    for split in ['train', 'val']:
        losses = torch.zeros(eval_iters)
        for k in range(eval_iters):
            X, Y = get_batch(split)
            logits, loss = model(X, Y)
            losses[k] = loss.item()
        out[split] = losses.mean()
    model.train()
    return out
optimizer = torch.optim.AdamW(model.parameters(), lr=learning_rate)
for iter in range(max_iters):
    if iter % eval_interval == 0:
        losses = estimate_loss()
        print(f"step {iter}: train loss {losses['train']:.4f}, "
              f"val loss {losses['val']:.4f}")
    xb, yb = get_batch('train')
    logits, loss = model(xb, yb)
    optimizer.zero_grad(set_to_none=True)
    loss.backward()
    optimizer.step()

Why it beats the alternatives

✗ Print one batch's loss

Only 256 predictions. On the trained bigram, single val batches range from 2.29 to 2.75, so a real 0.03 improvement is buried in the noise.

✗ Score the whole val split each time

Exact, but 111,540 characters is about 436 batches per check, and it grows with the dataset. 200 random batches already pin the mean to about ±0.005.

✗ Watch only the training loss

It keeps falling even when the model starts memorising. Later in this lecture train reaches 1.98 while val sits at 2.08; only the val column shows that gap.

✓ estimate_loss on both splits

Averaged over 51,200 predictions per split, with no graph recorded, every 300 steps. Cheap, steady and honest about overfitting.

Is 1e-2 the right learning rate, and will more steps help?

Not in general. Karpathy calls roughly 3e-4 a "typical good setting" (chapter at 0:34:53) and notes that tiny networks tolerate 1e-3 or more. The bigram has 4,225 weights and can take 1e-2; gpt.py, with 10.8M, uses 3e-4. With 1e-3 instead, the same 3000 steps only reach val 2.8059 (computed in a scratch run), so the lr sets how many steps you need.

More steps won't help this model. A bigram built from raw counts of the training text (add-one smoothing) scores 2.4819 on val (computed), and the trained one is at 2.49. A bigram sees one character of context, so the next cards give it more. Also, bigram.py only checks for CUDA. For this 4,225-weight model the CPU is the right place anyway; the gpt.py lab adds an mps check so the big model can use your M3's GPU.

Understand and remember

  • AdamW moves each weight by roughly lr per step → at lr 1e-3, 100 steps shift a weight by at most about 0.1 → loss only drops 4.6924 → 4.6563 → a 10× bigger lr (1e-2) reaches val 2.51 by step 900, while 1e-3 is still at 2.81 after 3000
  • PyTorch adds each backward into .grad → without zero_grad every step would follow the sum of all past gradients → so each step is get_batch → forward → zero_grad → backward → step
  • One batch is only 256 predictions → its loss swings 2.29 to 2.75 on the trained model → averaging 200 batches cuts the noise to about 0.005 → only then can a 0.03 change or a train/val gap be read
  • Val tracks train (gap under 0.03) and both flatten near 2.49 → not overfitting but the bigram's ceiling (a counted bigram scores 2.48) → more steps won't help, only more context will
  • detail that matters @torch.no_grad() on estimate_loss → no graph is stored for the 4,000 eval forward passes (more forwards than the 3,000 training steps) → evaluation costs memory and time only for the forward itself

Reference only

  • bigram.py hyperparameters: batch_size 32, block_size 8, max_iters 3000, eval_interval 300, learning_rate 1e-2, eval_iters 200, seed 1337
  • device = 'cuda' if torch.cuda.is_available() else 'cpu' (add an mps check for the M3's GPU)
  • optimizer.zero_grad(set_to_none=True) sets .grad to None instead of writing zeros
  • the notebook loop: AdamW lr 1e-3, batch 32, 10,000 steps, single-batch loss 2.3824 at the end

4 · Compare against what you already know

vs From neuron to MLP to a training loop: micrograd's hand-written loop vs this one: which of the five moves are the same, which are now done by a library object, and what failure mode do both share?

Check
  • same: forward, zero the grads, backward, update
  • micrograd zeroes each p.grad and does p.data += -lr * p.grad by hand; here AdamW's zero_grad and step do it
  • both break the same way if you forget to zero the grads: gradients pile up across steps

vs Train/dev/test and under- vs overfitting: makemore split names 80/10/10 and scored the whole dev set by hand between training runs. What does bigram.py do differently, and when would you want each approach?

Check
  • bigram.py splits 90/10 and checks both splits periodically during training
  • periodic checks show the curve, so you can stop or tune early
  • scoring the full split is exact and fine when it is small (a few thousand names); a random-batch estimate scales to large text and runs inside the loop

vs Adam and AdamW, explained: Why does this card's lr 1e-2 work for the bigram when gpt.py uses 3e-4, given how Adam sizes its steps?

Check
  • Adam's step is about lr regardless of gradient scale
  • the bigram's 4,225 independent table entries can take big steps safely
  • a deep 10.8M-parameter network with interacting layers becomes unstable with steps that large, so it uses a smaller lr and more steps
