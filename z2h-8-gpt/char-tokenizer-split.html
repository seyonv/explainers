Characters to integers, and a held-out 10%

Also called: character-level tokenization, a vocabulary with stoi/itos, encode/decode, the train/validation split, a held-out set. Lecture 7 · tokenization, train/val split · 0:09:28

Prime · 2 minutes before you read

The problem: A neural net does arithmetic on numbers, and Shakespeare is a string. And a model that only ever gets scored on the text it trains on can memorise that text and look like it's improving while learning nothing that carries over.

Where it fits: Second step of the GPT lecture. The previous card loaded 1,115,394 characters and found 65 distinct ones; this card turns them into integer ids (the same stoi/itos idea as the makemore names) and sets aside the text that every later val loss is measured on.

In one breath: a neural net eats numbers, not text, so we give each of the 65 distinct characters in Shakespeare an integer id and turn the whole 1,115,394-character file into one long list of ids. Then we cut that list: the model trains on the first 90%, and the last 10% stays hidden so we can check whether it learned Shakespeare in general or only memorised the pages it saw.

Predict first: after encoding, data holds one integer per character. What is the largest integer in it, and how many integers land in the held-out 10%?

64, and 111,540. The 65 characters get the ids 0 to 64, and the last one in sorted order is z, so 64 is the largest. The split point is int(0.9 × 1,115,394) = int(1,003,854.6) = 1,003,854; int drops the .6, so the held-out part gets the remaining 1,115,394 − 1,003,854 = 111,540 characters.

Step 1: a lookup table from the sorted characters

chars = sorted(list(set(text))) keeps each distinct character once, in Unicode order. A character's position in that list becomes its id. stoi ("string to integer") is a dict from character to id, and itos is the reverse dict.

idscharacterscount
0 – 12\n (newline) · space · ! $ & ' , - . 3 : ; ?13
13 – 38A B C … Z26
39 – 64a b c … z26
vocab_size65

So a lowercase letter's id is 39 + its place in the alphabet (a = 0): h = 39 + 7 = 46, t = 39 + 19 = 58. Newline is 0 and space is 1.

Step 2: encode and decode

encode looks up each character in stoi; decode looks each id up in itos and joins the characters back into a string. Karpathy's example:

h46i47i47␣1t58h46e43r56e43

encode("hii there") = [46, 47, 47, 1, 58, 46, 43, 56, 43], and decode of that list gives back 'hii there'. Nine characters in, nine integers out.

Encoding the whole file gives data, a 1-D tensor (PyTorch's array) of 1,115,394 integers of type torch.long (64-bit integers, the type that embedding lookups expect later). Its first 20 entries decode to the play's opening:

F18i47r56s57t58␣1C15i47t58i47z64e43n52:10\n0B14e43f44o53r56

data[:20] = "First Citizen:\nBefor". The 18 at the start is the F of "First Citizen", and the 64 is the z.

Step 3: cut off the last 10%, to scale

train_data = data[:n] · 1,003,854
val
index 0n = 1,003,8541,115,394
n = int(0.9 × 1,115,394) = int(1,003,854.6) = 1,003,854 val = 1,115,394 − 1,003,854 = 111,540 (10.0%) train ends … "But who comes here" | val starts "?\n\nGREMIO:\nGood morrow, …"

The cut is one slice, not a shuffle: the model trains on the first 90% of the file, and val_data is the unbroken last 10%. The slice doesn't care about sentences, so it lands between "here" and its question mark. The split is there to catch overfitting: a model can drive its training loss down by memorising the exact text it sees, and only a loss measured on text it has never trained on shows whether it learned something that carries over. That is the reason Karpathy gives for the split in this chapter. From the next cards on, every run reports a train loss and a val loss side by side.

When: pause the video at 0:09:28 and type this under your cell that loaded text, before watching on.

chars = sorted(list(set(text)))
vocab_size = len(chars)                     # 65
stoi = { ch:i for i,ch in enumerate(chars) }
itos = { i:ch for i,ch in enumerate(chars) }
encode = lambda s: [stoi[c] for c in s]
decode = lambda l: ''.join([itos[i] for i in l])
print(encode("hii there"), decode(encode("hii there")))

data = torch.tensor(encode(text), dtype=torch.long)
print(data.shape, data.dtype, data[:20].tolist())
n = int(0.9*len(data))   # first 90% will be train, rest val
train_data = data[:n]
val_data = data[n:]
print(len(train_data), len(val_data))

The trade-off: vocabulary size vs sequence length

Karpathy points out that real models don't use characters. OpenAI's GPT-2 tokenizer (via the tiktoken library) uses sub-word pieces. Same text, two tokenizers:

Tokenizervocab size"hii there" becomestokens for all of Shakespeare
Ours: one id per character65[46, 47, 47, 1, 58, 46, 43, 56, 43] · 9 ids1,115,394
GPT-2 (byte-pair encoding)50,257[71, 4178, 612] · 3 ids: "h", "ii", " there"338,025

Measured by the lab with tiktoken. 1,115,394 / 338,025 = 3.30 characters per GPT-2 token: sequences about 3.3× shorter, paid for with a vocabulary 773× bigger (50,257 / 65 = 773.2). The piece split "h" / "ii" / " there" is computed with enc.decode on each id.

Why these two choices, for this lecture

✗ One id per word

Split on spaces, the file has 25,670 distinct "words". Worse, 2,361 of the 20,153 words in the val text (11.7%) never appear in the train text, so a word vocabulary built from train has no id for them.

✗ GPT-2's sub-word pieces

Sequences 3.3× shorter, which is why real LLMs use them. But the 50,257-row vocabulary is a lot of extra machinery for a lecture about attention; the tokenizer lecture (z2h-9) builds it.

✗ Score on the training text

The loss keeps falling as the model memorises, so memorising looks exactly like learning. Nothing warns you when the model stops generalising.

✓ 65 characters + the last 10% held out

Tiny vocabulary, trivial code, and no unknown ids: all 65 characters appear in the train part. The held-out tail gives an honest val loss for every later card.

Word and vocabulary counts computed from input.txt with text.split() and the same n = 1,003,854 cut. Punctuation stays attached to words, so "words" here is rough.

Is a 90/10 tail split always right?

No. It suits one long, fairly uniform text. The tail is one unbroken stretch of plays, so val sees 61 of the 65 characters ($, &, 3 and X appear only in train), and its style may not match the rest perfectly. With many separate documents, you'd hold out whole documents instead. The makemore lectures shuffled the names and split them 80/10/10 into train, dev and test (see Splits and fit). This lecture keeps only train and val, and uses val both to watch overfitting and to compare model versions. A third, untouched test set is the safer habit once you start tuning choices against val.

A character vocabulary is also closed: it only knows the 65 characters it was built from. encode("café") raises KeyError: 'é'. Byte-level tokenizers like GPT-2's avoid that, which is one reason the tokenizer lecture exists.

Understand and remember

  • sorted(set(text)) gives a fixed order → a character's position is its id → stoi/itos are exact inverses → decode(encode(s)) == s for any string made of the 65 characters
  • Training lowers the loss on whatever text it sees → memorising that text also lowers it → train loss alone can't tell learning from memorising → hold out text the model never trains on and watch its loss (val) instead
  • Small vocabulary (65) → one id per character → long sequences (1,115,394 ids) but a tiny table and no unknown pieces; big sub-word vocabulary (50,257) → about 3.3× fewer ids → longer context per token, at the cost of a much bigger table and a separate tokenizer
  • The vocabulary is built only from characters seen in the file → it is closed → any new character (é) has no id → encode raises KeyError
  • detail that matters The split is a contiguous slice (data[:n], data[n:]) → val is an unbroken stretch the model never sees, not scattered characters whose neighbours are in train → a more honest measure of generalisation, but its content (61 of the 65 characters) can differ a bit from train

Reference only

  • the exact code: stoi = { ch:i for i,ch in enumerate(chars) }, the encode/decode lambdas
  • dtype=torch.long is the same type as torch.int64
  • the specific ids: newline 0, space 1, A 13, a 39, z 64
  • the split sizes 1,003,854 / 111,540
  • tiktoken.get_encoding('gpt2') and its n_vocab of 50,257

4 · Compare against what you already know

vs Train/dev/test and under- vs overfitting: The makemore split shuffled 32k names into 80/10/10 train/dev/test; this lecture slices one text 90/10 with no shuffle and no test set. What causes the difference, when would you choose each, and how does each fail?

Check
  • names are independent examples, so shuffling them is safe; Shakespeare is one continuous text, so a slice keeps val's contexts unseen
  • shuffle-and-split fits collections of separate items; hold out whole documents or a contiguous tail for one long text
  • a shuffled split of one text would leak neighbouring context into val; a tail split can differ in style or content from train
  • no test set means repeatedly picking models by val slowly overfits to val too

vs Tokenization: the root of much LLM weirdness: A character tokenizer vs a byte-pair (BPE) tokenizer: what is fundamentally different about how each gets its vocabulary, and how does each fail on unusual input?

Check
  • characters: the vocabulary is just the distinct characters seen, no training needed
  • BPE: starts from bytes and learns merges of frequent pairs, so common chunks get one id
  • characters: an unseen character raises KeyError; byte-level BPE can always fall back to single bytes
  • characters give long sequences; BPE gives shorter ones but adds its own quirks (the tokenizer lecture's topic)

5 · Predict commit to an answer before revealing

Suppose you build the vocabulary from val_data's text only (the last 10%) and then try to encode the training text. Does it work, and does 'a' keep the id 39?

Reveal

No on both counts. The val text contains only 61 distinct characters: $, &, 3 and X appear only in the train part. Encoding the train text raises KeyError: '&' at character 75,323 (from 'Senators, &C:'). And since those four characters all sort before a, every lowercase id shifts down by 4: 'a' becomes 35 and 'h' becomes 42. Ids depend on the whole vocabulary, which is why the lecture builds it from the full text before splitting.
