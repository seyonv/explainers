Chunks and batches: block_size 8 gives 8 examples

Also called: the data loader, get_batch, context windows, a minibatch of sequences. Lecture 7 · data loader: batches of chunks of data · 0:14:27

Prime · 2 minutes before you read

The problem: You have one tensor of 1,003,854 training integers and a model that predicts the next character. Fed the whole thing at once it's far too long to process, and there's no obvious answer to "what is one training example?"

Where it fits: The previous card turned the text into integers and split off 10% for validation. This card decides how those integers reach the model each step. It reuses the makemore idea of a context window and a random minibatch, and widens it so every position in a window is a target.

In one breath: the model never reads all 1,003,854 training characters at once. Each step it cuts a few random windows of block_size + 1 characters out of the text. One window of 9 characters holds 8 training examples, because every prefix of it, from 1 character up to 8, must predict the character that comes next. Stack 4 windows and you get a batch of 4 × 8 = 32 examples.

Predict first: the lab's first batch row xb[0] decodes to "Let's he". What does the matching target row yb[0] decode to, and how many of its 8 characters also appear in xb[0]?

"et's hea", and 7 of its 8 characters. yb is the same window shifted one step to the right in the text, so yb[0, t] is the character right after xb[0, t]. Only the last one, a, is new: the 9th character of the window.

One chunk, eight examples

Words used here: block_size (Karpathy's name for the context length) is the most characters the model may look at before predicting; it's 8 in this chapter. A chunk is train_data[:block_size+1], the first 9 integers of the text. The input x is its first 8, the target y its last 8. Position t uses the context x[:t+1] to predict y[t].

Why train on the short contexts too? When you generate, you start from one character and grow. A model trained only on full 8-character contexts would never have seen a 1-character one. The flip side: 8 is also the maximum. The model is never shown a context longer than block_size, so generation must feed it only the last 8 characters (the heads card adds that crop).

Many chunks: the batch dimension

A batch is several chunks from random places in the text, processed side by side so the GPU (or your M3) stays busy. torch.randint(len(data) - block_size, (batch_size,)) draws batch_size random starting offsets ix, and torch.stack piles the windows into a 2-D tensor with B rows (batch) and T columns (time, i.e. position in the chunk).

Computed. The bound len(data) − block_size is what keeps y's window inside the data. Offsets are drawn with replacement, so 81.6 × is "that much reading", not 81 clean passes over the text.

▶ Build itruns on your M3 · about 3 s

When: pause the video at 0:14:27 and type this below your train_data / val_data split from the previous card.

torch.manual_seed(1337)
batch_size = 4  # independent sequences per step
block_size = 8  # maximum context length
def get_batch(split):
    data = train_data if split == 'train' else val_data
    ix = torch.randint(len(data) - block_size, (batch_size,))
    x = torch.stack([data[i:i+block_size] for i in ix])
    y = torch.stack([data[i+1:i+block_size+1] for i in ix])
    return x, y
xb, yb = get_batch('train')
print(xb.shape); print(xb); print(yb[0])
for t in range(block_size):
    print(f"when input is {xb[0,:t+1].tolist()} the target: {yb[0,t]}")

Why it beats the alternatives

✗ Feed the whole text as one sequence

One sequence of 1,003,854 positions. Attention compares every position with every earlier one, so the work grows with the length squared, and you'd get one weight update per trip through the text.

✗ One target per window

The makemore MLP built one (context → next char) row per window. Here that would score only y[7] and throw away 7 of 8 targets the model computes anyway, and it would never practise short contexts.

✗ One chunk per step

A single 9-character window gives a gradient from 8 examples that all share one spot in the text. It's noisy, and it leaves most of a parallel processor idle.

✓ Random chunks, every position a target, B of them stacked

Each step sees B·T = 32 examples (16,384 in gpt.py) from B unrelated places, and one forward pass scores all of them. The rows never talk to each other.

Are the 32 examples really independent?

Across rows, yes: row 0 and row 1 come from unrelated parts of the play, and nothing in the model lets them exchange information (note 3 of the attention notes). Within a row, no: the 8 examples share their characters, since each is a longer prefix of the same window. That sharing is the point. A Transformer computes all 8 predictions in one pass over the 8 positions, with a mask stopping position t from seeing t+1 onwards (the self-attention cards).

Random offsets aren't the only choice. For GPT-2 on billions of tokens, Karpathy's DataLoaderLite.next_batch walks the token stream in order, taking B*T + 1 tokens and reshaping them into x and y. With that much data, one ordered pass uses every token exactly once and never needs random access. For a small text you reread about 80 times, random windows are the easy way to mix it up.

Understand and remember

  • A window of block_size + 1 characters → x = first 8, y = last 8 → y[t] is the character after x[:t+1] → one window gives 8 (context → target) examples, from 1 to 8 characters of context
  • Training on every context length → the model has practised 1-character contexts → generation can start from a single character; but 8 is also the ceiling → at generation time only the last block_size characters can be fed in (the crop)
  • Random offsets from randint(len(data) − block_size) → B windows from unrelated places, stacked into (B, T) → one forward pass scores B·T examples (32 here, 16,384 in gpt.py) → a less noisy gradient per step and a busy processor
  • Rows in a batch never exchange information → each row is an independent sequence; positions within a row share their characters → a Transformer can compute all T predictions of a row in one pass, as long as a mask hides later positions
  • detail that matters The bound len(data) − block_size → the largest offset is 1,003,845 → y = data[i+1 : i+9] ends exactly at the last element; use len(data) and any offset in the last 8 gives a short window, so torch.stack raises "stack expects each tensor to be equal size"

Reference only

  • torch.manual_seed(1337) must come right before the first get_batch to reproduce the Colab's xb
  • torch.stack joins a list of 1-D tensors into a new leading dimension
  • the lab's offsets ix = [76049, 234249, 934904, 560986] and rows "Let's he" → "et's hea"
  • bigram.py uses batch 32 × block 8; gpt.py uses 64 × 256

5 · Predict commit to an answer before revealing

You call get_batch('val') with block_size 8. How many different starting offsets are possible, and what would happen if block_size were 200,000?

Reveal

val_data has 111,540 integers, so randint(111,540 − 8) allows 111,532 offsets (0 … 111,531). With block_size 200,000 the bound goes negative: torch.randint refuses a high of −88,460 and raises a RuntimeError ("random_ expects 'from' to be less than 'to'"), because not even one full window fits in the validation split.
