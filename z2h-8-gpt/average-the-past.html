Letting tokens talk: average the past

Also called: bag of words (xbow), a causal running mean, cumulative average. Lecture 7 · version 1: averaging past context with for loops, the weakest form of aggregation · 0:42:13

Prime · 2 minutes before you read

The problem: The bigram model predicts each next character from the current character alone. Everything earlier in the chunk is sitting right there in the tensor, but no token can see it, so training stalls around val loss 2.49.

Where it fits: This opens the lecture's self-attention section. It builds on the batches-of-chunks card, where position t of a chunk is a training example whose target is the character at t + 1, and on the bigram baseline it tries to beat.

In one breath: the bigram model lets each character predict the next one from itself alone. The simplest way to let it hear from the characters before it is to replace its vector with the average of its own vector and every earlier one in the same sequence. It never looks ahead, which keeps next-character training honest, but it gives every past token the same say and forgets their order.

Predict first: in the toy below, the last token of sequence 0 is x[0,7] = [−0.9211, 1.5433]. After averaging, will xbow[0,7] still look like it?

Hardly at all: [−0.0341, 0.1332]. Token 7 is one of eight equal voices, so its own vector counts for only 1/8. The other seven push in different directions and mostly cancel, and the result shrinks towards zero. That blurring is the price of treating every past token the same.

Who each token hears from

Words used here: B is the batch (4 separate sequences), T the time axis (8 positions in a chunk), C the channels (each token is a vector of 2 numbers, a stand-in for the embeddings that come later). x[b,t] is the vector of token t in sequence b.

Why stop at t: in the batch, position t's target is the character at t + 1. Averaging it in would hand the model the answer.

When: pause the video at 0:42:13 and type this cell before watching on (after import torch).

torch.manual_seed(1337)
B,T,C = 4,8,2              # batch, time, channels
x = torch.randn(B,T,C)
# want: xbow[b,t] = mean of x[b,i] for i <= t
xbow = torch.zeros((B,T,C))
for b in range(B):
    for t in range(T):
        xprev = x[b,:t+1]            # (t+1, C)
        xbow[b,t] = torch.mean(xprev, 0)
print(xbow[0])

Why it beats the alternatives

✗ No talking at all (bigram)

Each token predicts from itself only. Trained with bigram.py, it stalls at val loss 2.49 (step 2700): no amount of training lets it use the characters before.

✗ Average the whole chunk

Every row would become [−0.0341, 0.1332], including the answer for every position. The model could just read off the answer, and at generation time there is no future to average.

✗ Glue every past vector together

Keeps everything, in order, but the size grows with t: 2 numbers at t = 0, 16 at t = 7, and 256 × 384 = 98,304 at gpt.py's block size and width. The next layer needs one fixed size.

✓ Average of the past

Fixed size (C numbers), strictly causal, no parameters, and one line of maths. It also leaves an obvious slot to improve: the equal weights 1/(t + 1).

Is this what GPT does?

No, it's the skeleton. Three upgrades turn it into attention. The Python double loop becomes one matrix multiply (next card), which matters: at gpt.py's batch 64 × block 256 the loop would make 64 × 256 = 16,384 tiny torch calls. The equal weights become learned, content-dependent ones (queries and keys). And because a sum ignores order, position has to be added back in with position embeddings.

Plain averaging is still the right tool when order genuinely doesn't matter and you only need a fixed-size summary, such as pooling word vectors for a simple bag-of-words classifier. For predicting the next character, where the nearest characters usually matter most, it's too blunt.

1 · Core model what to internalise, what to just look up

Keep it if it changes what you can explain, predict, compare, choose, build or debug. Otherwise it's reference.

Understand and remember

  • In next-character training, position t's target is the character at t + 1 of the same chunk → any mix that includes positions after t leaks the answer → the slice x[b,:t+1] stops at t → the same model still works at generation time, when no future exists
  • Every token in the past gets the same weight 1/(t + 1) → the current token's own share falls to 1/8 at t = 7 → xbow[0,7] = [−0.0341, 0.1332] barely resembles x[0,7] = [−0.9211, 1.5433] → the one earlier token that matters is blurred with all the rest
  • A mean is a sum divided by a count, and a sum ignores order → reordering tokens 0…t gives the same xbow[b,t] (a "bag of words") → order has to come back from position embeddings, and relevance from learned weights
  • detail that matters The double loop makes one small torch call per (b, t) pair → 32 calls in the toy, 64 × 256 = 16,384 at gpt.py's batch and block size → the next card replaces the whole loop with one triangular matrix multiply that gives the same numbers

Reference only

  • toy sizes B,T,C = 4,8,2, seed 1337, x = torch.randn(B,T,C)
  • torch.mean(xprev, 0): mean over dim 0 of the (t+1, C) slice, i.e. over time
  • xbow = "x bag of words"; Karpathy's comment says (t,C) but the slice has t + 1 rows
  • equivalent one-liner: x.cumsum(1) / torch.arange(1, T+1).view(1, T, 1)

    Check

4 · Compare against what you already know

vs The simplest model that works: bigram: Both give each position one fixed-size vector to predict from. What is fundamentally different about what that vector can contain, and how does each one fail?

Check
  • bigram: the vector is looked up from the current character only
  • average: the vector mixes the current character with all earlier ones
  • bigram fails by ignoring context entirely (stuck near val 2.49)
  • average fails by weighting every past token equally and forgetting order

vs Self-attention: one head (Q, K, V): Both output a weighted mix of earlier tokens. Which design choice separates them, and when would the plain average be good enough?

Check
  • average: weights fixed at 1/(t + 1), the same for every sequence
  • attention: weights from query·key scores, so they depend on the tokens' contents
  • the average is fine when every past item is about equally useful and order doesn't matter (e.g. a simple bag-of-words summary)
  • for next-character prediction the nearby, specific characters matter, so equal weights are too blunt

5 · Predict commit to an answer before revealing

In sequence 0, shuffle the first three tokens so the order becomes x[0,2], x[0,0], x[0,1], and leave the rest alone. Which rows of xbow[0] change: all of them, rows 0–2, or only rows 0–1?

Reveal

Only rows 0 and 1. Row 0 becomes the old x[0,2] = [0.6258, 0.0255] and row 1 becomes [0.4033, −0.0222]. Rows 2–7 are identical (torch.allclose is True), because from row 2 on each mean includes all three shuffled tokens, and a sum doesn't care about order. The model can't tell "ab" from "ba" once both are in the past, which is why position embeddings come in a few cards later.
