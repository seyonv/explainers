Token and position embeddings

Also called: embedding tables, learned positional embeddings (the paper's "positional encoding"), wte / wpe in nanoGPT, and the LM head. Lecture 7 · minor code cleanup · 0:58:26 · positional encoding · 1:00:18

Prime · 2 minutes before you read

The problem: The bigram reads its logits straight out of a 65×65 table, so there is no per-token vector for later layers to work on. And the attention coming next mixes tokens without knowing their order: "tab" and "atb" would look the same to it.

Where it fits: This is the cleanup just before the crux. It rebuilds the bigram baseline out of the embedding lookups you met in makemore, and adds a second table for positions so that the self-attention card has something to tell order by.

Needs first: The simplest model that works: bigram

In one breath: the bigram's 65×65 table becomes three pieces. A token table gives each character a vector of 32 learned numbers (what it is), a position table gives each slot 0–7 its own 32 numbers (where it is), the two are added, and a Linear layer called lm_head turns those 32 numbers back into 65 logits. Positions don't help yet, because each token still sees only itself. They matter once attention mixes tokens, since attention on its own can't tell what order the tokens came in.

Predict first: the model gains 256 numbers that say where each character sits in its chunk. Trained with bigram.py's settings, does its val loss beat the plain bigram's 2.49?

No: 2.5163, slightly worse (the plain 65×65 bigram reached 2.4903). Every prediction still comes from one character, and knowing "I'm in slot 5" says almost nothing about the next character. A scratch run that keeps everything but skips the + pos_emb got 2.5123, so the position rows aren't what costs the extra 0.02. The likelier cause is squeezing each character through 32 numbers instead of a full row of 65 (an inference, not a measured split).

The data flow

An embedding is a learned vector you fetch by an integer id. nn.Embedding(n, d) holds an n×d matrix, and calling it with an id returns that row (the embedding lookup card). n_embd (Karpathy's C, "channels") is the row length, 32 here. torch.arange(T) is the tensor 0, 1, …, T−1: the slot numbers.

xb,t= Etok[idxb,t]what the character is + Epos[t]where it sits logitsb,t= xb,tW+c
b, twhich sequence in the batch, and which slot in itb 0–31 · t 0–7 idx[b,t]the character id at that spotidx is (32, 8) E_toktoken_embedding_table.weight: one row per character65 × 32 E_posposition_embedding_table.weight: one row per slot8 × 32 W, clm_head's weight matrix and bias: 32 numbers in, 65 logits out32 × 65, 65

In code, tok_emb is (32, 8, 32) and pos_emb is (8, 32). Adding them broadcasts: PyTorch lines up the last two dimensions and reuses the same 8 position rows for all 32 sequences.

The first block is printed by the lab; the gpt.py lines are computed from its hyperparameters. The position table grows with block_size, which is why gpt.py's is four times bigger than its token table.

Why attention needs the position rows

Attention (next card) scores each earlier token by its content and mixes them. Feed one untrained head (seed 1337, head_size 16) the chunks "tab" and "atb", and look at what the last token, b, gets:

weights on t, a, blast-token output
no position rows, "tab"t 0.0948 · a 0.6881 · b 0.2172identical (max diff 6e-8, float noise)
no position rows, "atb"t 0.0948 · a 0.6881 · b 0.2172
with position rows, "tab"t 0.2339 · a 0.7210 · b 0.0450different (max diff 0.8732)
with position rows, "atb"t 0.2029 · a 0.7542 · b 0.0429

Computed in a scratch script with the next card's head code. Without positions, swapping t and a only moves the same weights to the other slot, so the mix is the same. The position rows are the only thing that tells the head the order.

class BigramLanguageModel(nn.Module):
    def __init__(self):
        super().__init__()
        self.token_embedding_table = nn.Embedding(vocab_size, n_embd)
        self.position_embedding_table = nn.Embedding(block_size, n_embd)
        self.lm_head = nn.Linear(n_embd, vocab_size)

    def forward(self, idx, targets=None):
        B, T = idx.shape
        tok_emb = self.token_embedding_table(idx)      # (B,T,C)
        pos = torch.arange(T)                          # (T,)
        pos_emb = self.position_embedding_table(pos)   # (T,C)
        x = tok_emb + pos_emb                          # (B,T,C)
        logits = self.lm_head(x)               # (B,T,vocab_size)

How it differs from related ideas

✗ Keep the 65×65 table

bigram.py reads the logits straight out of a row. It trains to 2.49, but there's no per-token vector in the middle for later layers to mix and transform.

✗ No position information

Attention treats its inputs as a set. "tab" and "atb" give the last token exactly the same output, so word order is invisible.

✗ Fixed sine waves (the 2017 paper)

Not wrong: Attention Is All You Need adds fixed sinusoids with no parameters, and reports that learned position embeddings gave nearly identical results. GPT-2 and gpt.py learn them.

✓ Two learned tables, added

One row per character plus one row per slot, summed into one C-wide vector. Adding keeps the width at 32, costs 256 numbers here, and training decides what each position row means.

Can a position table handle any length?

No. The table has exactly block_size rows, so slot 8 has no row: feeding the lab's model 9 characters raises IndexError: index out of range in self. The bigram's generate() keeps growing idx, so it has to crop to the last block_size characters first. gpt.py does this with idx[:, -block_size:] (L185), and the heads card adds it.

Also, "adding" does not mean the model can't separate the two parts. Both tables are trained together, so training can spread "what" and "where" over the 32 dimensions in whatever way helps the loss. And with no attention, this model is still a bigram: don't expect the position rows to lower the loss until the next card.

Understand and remember

  • Token table row + position row are added into one C-wide x → the same character in two slots gets two different vectors → anything downstream that compares vectors can now tell slots apart
  • Attention scores tokens by content and sums them → swapping two earlier tokens just moves the same weights with them → the output is unchanged ("tab" = "atb") → the only order signal it gets is the position row added into x
  • The bigram model predicts from one token at a time → a position row can only say "I'm in slot t", not what came before → val loss doesn't improve (2.5163 vs 2.4903) → positions pay off only after tokens can talk
  • The position table has exactly block_size rows → there is no row for slot 8 → a 9-character input raises IndexError → generate() must crop the context to the last block_size characters
  • detail that matters lm_head is a Linear layer with PyTorch's default init → the initial logits spread less (std 0.79 vs 1.01 for the 65×65 table) → the step-0 loss starts nearer the uniform 4.17 (4.48 vs bigram.py's 4.73)

Reference only

  • nn.Embedding(vocab_size, n_embd), nn.Embedding(block_size, n_embd), nn.Linear(n_embd, vocab_size)
  • torch.arange(T) (gpt.py passes device=device)
  • parameter counts: 2,080 + 256 + 2,145 = 4,481; at gpt.py's size 24,960 + 98,304 + 25,025
  • nanoGPT's names for the same tables: wte and wpe
  • the 2017 paper's fixed sinusoids, which it reports as nearly identical to learned rows

5 · Predict commit to an answer before revealing

Before attention, the average-the-past card mixed tokens with a plain average. If you add position rows to x and then take that plain average over "tab" and "atb", does the last token's average now differ between the two orders?

Reveal

No. With the lab's seeded tables the difference is 1.2e-7, which is float noise. The average of (token + position) rows is the average of the three token rows plus the average of position rows 0–2, and both averages are the same in either order. Position rows only help when the weights depend on what sits in each slot, which is what queries and keys add on the next card.
