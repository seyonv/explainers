Encoding: apply merges in training order

Also called: tokenizing, text → token ids, BPE encode. Lecture 8 · encoding strings to tokens · 0:48:21

Prime · 2 minutes before you read

The problem: Training gave you a merge table, but a model needs ids for text it has never seen: a prompt, a validation file. If new text were cut differently from the training text, the same id would mean different bytes, and the model's learned embeddings would stop lining up with its input.

Where it fits: The train-loop card learned 20 merges on the blog post and the decode card turned ids back into text. This card goes the other way: string → bytes → ids, reusing get_stats and merge from the stats-and-merge card.

In one breath: to turn new text into tokens, start from its UTF-8 bytes and replay the merges you learned in training, always the one learned earliest first, until no neighbouring pair is in the merge table. The loop is short. The one idea that matters is that the order comes from training (the merge index), not from the text you're encoding.

Predict first: with the 20 merges trained on the blog post, "the " is 4 bytes: t h e ␣. Two merges could fire right away: th (id 259) at the left, e␣ (id 256) at the right. Which fires first, and how many tokens come out at the end?

e␣ fires first, and the answer is one token, [275]. Encoding doesn't read left to right. It picks the pair with the lowest merge index, and 256 was learned before 259. Then th merges, and that leaves [259, 256], which is exactly merge 275 (the␣).

"the " step by step

The merges are the 20 from the train-loop card: a dictionary merges from a pair of ids to its new id, e.g. (101, 32): 256. The new id is the merge's position in training: 256 was learned first, 275 last. Each round, get_stats lists every neighbouring pair; each pair gets its merge index, or infinity (inf) if it was never learned; min picks the smallest.

The break needs care. When no pair was ever learned, every key is inf, and min still returns something: the first pair, arbitrarily ((104, 101) for "hello world"). So the loop checks pair not in merges to know it's done. The other edge is a string with 0 or 1 bytes: it has no pairs at all, and min of an empty dict raises ValueError. Hence while len(tokens) >= 2.

The loop

Why training order, and not some other order

Training ran the merges one at a time, in index order, over the whole training text. When co (261) was learned, or (266) didn't exist yet, so every "cor" in the post became co | r. Replaying the same order is what makes encode cut text the way training did. It also guarantees the pieces exist before a merge needs them: 275 is (259, 256), so it can only fire after th and e␣ have.

Round trips: one way only

decode(encode(text)) == text True on the training post True on an unseen sentence encode(decode([128])) → [239, 191, 189] not [128] encode(decode([101, 32])) → [256] not [101, 32]

The first three lines are from the lab. The last one is computed: it's valid UTF-8, but encode always merges e␣.

Encode never loses information, because merges only group bytes and decode ungroups them. The other direction fails for two reasons. Byte 128 on its own isn't valid UTF-8, so decode (with errors="replace", from the decode card) turns it into �, and � is three bytes, 239 191 189. And even a valid id list may not be the one encode would produce: [101, 32] spells "e ", but encode always turns that into 256.

▶ Build itruns on your M3 · under 1 s

When: pause the video at 0:48:21 and write encode before watching on. You need get_stats, merge, merges, vocab and decode from the earlier cards, trained with 20 merges on the blog post.

def encode(text):
    # given a string, return a list of integers (the tokens)
    tokens = list(text.encode("utf-8"))
    while len(tokens) >= 2:
        stats = get_stats(tokens)
        pair = min(stats, key=lambda p: merges.get(p, float("inf")))
        if pair not in merges:
            break  # nothing else can be merged
        idx = merges[pair]
        tokens = merge(tokens, pair, idx)
    return tokens
print('encode(""):', encode(''))
print('encode("h"):', encode('h'))
print('encode("hello world"):', encode('hello world'))
print('training text round-trips:', decode(encode(text)) == text)
print('encode(decode([128])):', encode(decode([128])), '!= [128]')

Why it beats the alternatives

✗ Count pairs in the new text

That's training again, on the wrong data. In "hello world" every pair appears once, so the first new id would mean he. But the model learned 256 as e␣, so the ids no longer mean what it learned.

✗ Newest merge first

Picking the most recently learned merge cuts text in ways training never did: "corner" becomes c | or instead of co | r.

✗ One pass per merge, in order

Apply merge 256 everywhere, then 257, and so on. It gives the same tokens (checked on the whole post). But it costs one pass per merge on every string, even "h": 50,000 passes with GPT-2's merge table.

✓ Lowest merge index each round

It replays training order exactly, and it only loops once per merge that actually fires. That's one round for "hello world" and 20 for the whole post. It stops as soon as nothing applies.

Is this how GPT's tokenizer encodes?

The rule is the same. OpenAI's GPT-2 encoder.py picks the next pair with the same min over merge rank (its merge table is called bpe_ranks). Two things differ. Real tokenizers first cut the text into chunks with a regex, so merges never cross from letters into spaces or punctuation (the next card), and they run this loop on each chunk. And this version is slow: every round recounts all pairs from scratch. That's fine for learning, but tiktoken does the same work in Rust.

Don't treat encode as the inverse of decode. If you generate ids with a model and want to compare them with an encoding, compare the decoded strings, not the id lists.

Understand and remember

  • Training applied merges one at a time in index order → the training text was cut by that exact history → encode replays the same order (lowest merge index first) → new text is cut the way the model saw during training
  • A merged token can be built from earlier merged tokens (275 = 259 + 256) → it can only appear after its parts exist → processing lowest index first always creates the parts before the merge that needs them
  • Merges only group bytes, and decode ungroups them → decode(encode(text)) == text always holds → but an arbitrary id list may be invalid UTF-8 (→ �) or not what encode would produce ([101, 32] → [256]) → the round trip only works in one direction
  • detail that matters The key is merges.get(p, inf) → when nothing applies, min still returns an arbitrary pair → without the pair not in merges check the loop would crash on merges[pair] (a KeyError)
  • detail that matters Each round recounts every pair from scratch → cost is about (merges that fire) × (length of the text) → fine for learning, which is why real tokenizers split text into chunks first and tiktoken runs this in Rust

Reference only

  • float("inf") as the default key
  • minbpe's BasicTokenizer.encode (basic.py L57–L74)
  • the ids from this card's 20 merges: 256 = e␣, 259 = th, 266 = or, 275 = the␣
  • GPT-2's encoder.py calls its merge table bpe_ranks

4 · Compare against what you already know

vs Training a tokenizer, and why it's a separate stage: Training and encoding both call get_stats and merge. What does each one choose the next pair by, what does each produce, and what breaks if you swap their rules?

Check
  • training picks the most frequent pair (max by count) and creates a new merge each round
  • encoding picks the earliest-learned pair (min by merge index) and creates nothing new
  • encoding by count re-trains on the input and yields ids the model never learned
  • training by index is impossible: there is no index before the merge exists

vs Decoding, and the invalid-byte trap: Decode is a table lookup plus one bytes-to-text step, and encode is a loop. Why is one so much simpler, and where does each one fail?

Check
  • decode just concatenates each id's bytes; there is only one way to do it
  • encode has to choose how to group bytes, so it needs the priority rule and a stopping check
  • decode fails on invalid UTF-8 (fixed with errors="replace")
  • encode never fails on a string, but it may not reproduce a given id list

vs Characters to integers, and a held-out 10%: The GPT lecture's character tokenizer encodes with one dictionary lookup per character. What does BPE's encode add, and what does it buy?

Check
  • char: one lookup, one id per character, and no choices to make
  • BPE: a merge loop that groups bytes, and whose result depends on merge order
  • BPE buys shorter sequences (24,597 bytes → 19,438 ids with only 20 merges) and covers any text through bytes
  • the char tokenizer fails on any character outside its 65-character vocabulary
