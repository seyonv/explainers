sentencepiece and the Llama 2 tokenizer

Also called: SentencePiece, spm, the Llama / Mistral tokenizer, BPE with byte fallback. Lecture 8 · sentencepiece library intro, used to train Llama 2 vocabulary · 1:28:42

Prime · 2 minutes before you read

The problem: A tokenizer trained on mostly English will meet characters it never kept, like Korean or a rare symbol. If it has no plan for them, it either throws the text away as "unknown" or needs a vocabulary row for every character in Unicode.

Where it fits: You built byte-level BPE (minbpe, tiktoken's way) and saw how UTF-8 turns a character into 1–4 bytes. Llama 2's tokenizer runs the same BPE on characters instead, and uses those UTF-8 bytes only as a fallback.

In one breath: sentencepiece is Google's library that can both train a tokenizer and use it, and Meta used it for Llama 2. It runs the same BPE (byte pair encoding) you wrote, but on code points (Unicode characters) instead of UTF-8 bytes. A character too rare to get its own entry is either replaced by a single <unk> ("unknown") token or, with byte_fallback=True, spelled out as its UTF-8 bytes, each of which has its own token.

Predict first: Karpathy trains a 400-token vocabulary on one English paragraph, so it has never seen Korean. How many tokens does "hello 안녕하세요" become, and what id does the first Korean token get?

21 tokens, and the first Korean id is 239. "hello" and the two spaces take 6 pieces. Each of the 5 Korean syllables is 3 UTF-8 bytes, so they fall back to 5 × 3 = 15 byte tokens. The first byte of 안 is 0xEC = 236, and byte tokens sit 3 ids up (after <unk>, <s>, </s>), so its id is 236 + 3 = 239.

Bytes first, or characters first?

Everything so far in this course (minbpe, and OpenAI's tiktoken library behind GPT-2 and GPT-4) turns text into UTF-8 bytes and then merges bytes. sentencepiece reverses the order: it merges characters, and bytes are only a safety net for characters it didn't keep.

Karpathy's verdict on the two orders: he finds tiktoken's bytes-first way "a lot cleaner" (Colab, the sentencepiece section).

What tok400 learned

The training text is the opening paragraph of sentencepiece's own README: 503 characters, 39 of them distinct (counting the space). Trained with Llama 2's options at vocab_size=400, the vocabulary comes out in four blocks, in this id order:

3specials: <unk> (unknown), <s> (start), </s> (end)ids 0–2 256byte tokens <0x00> … <0xFF>, one per byte value, only there for fallbackids 3–258 102merges, first en, ▁t, ce, in, raids 259–360 39single characters, most frequent first (e, ▁, n, t …, last K)ids 361–399
3 + 256 + 102 + 39 = 400 (vocab_size) 39 = every distinct character in the 503-character text ▁ = U+2581, the stand-in sentencepiece uses for a space

Unlike minbpe, the single characters come last, after the merges. The 102-merge and 39-character split is counted from the trained model in a script (your M3, sentencepiece 0.2.2).

6 pieces for "hello" and the spaces + 5 syllables × 3 bytes = 21 ids, and decode gives back 'hello 안녕하세요' exactly. Without fallback, the whole unknown word becomes one <unk>, which decodes to " ⁇ ": the Korean is gone. "hello" also splits differently there (el), because the 256 freed byte slots went to other pieces.

The dummy prefix. add_dummy_prefix=True puts a space in front of the text before encoding, so a word at the very start looks like the same word mid-sentence. "world" becomes ['▁w', 'or', 'l', 'd'], the same pieces as in "hello world". The catch: " world", which really starts with a space, now has two, and gets an extra '▁' in front.

When: pause the video at 1:28:42, pip install sentencepiece, and save the first paragraph of the sentencepiece README as toy.txt (it's the Colab's toy text).

import sentencepiece as spm
options = dict(input="toy.txt", model_prefix="tok400",
  model_type="bpe", vocab_size=400,
  normalization_rule_name="identity",  # no text rewriting
  remove_extra_whitespaces=False,
  character_coverage=0.99995, byte_fallback=True,
  split_digits=True, add_dummy_prefix=True,
  allow_whitespace_only_pieces=True,
  unk_id=0, bos_id=1, eos_id=2, pad_id=-1)  # <unk> must exist
spm.SentencePieceTrainer.train(**options)
sp = spm.SentencePieceProcessor(); sp.load("tok400.model")
ids = sp.encode("hello 안녕하세요")
print(ids); print([sp.id_to_piece(i) for i in ids])
print('decode:', repr(sp.decode(ids)))

The real thing: Meta's settings for Llama 2

tok400 copies the options Karpathy read out of the tokenizer.model file Meta released (he dumped its settings; they're in the Colab). The ones that change behaviour:

OptionLlama 2What it does
vocab_size32,000About a third of GPT-4's 100,277 (32,000 / 100,277 = 0.32).
byte_fallbacktrueRare characters become byte tokens, never <unk>.
character_coverage0.99995Keep the most common characters that cover 99.995% of the training text; the rest are "rare".
split_digitstrueEvery digit is its own piece, so 677 is always 6, 7, 7 (GPT-2 turns " 677" into " 6" + "77").
add_dummy_prefixtruePrepend a space, as above.

Where rare characters can go

✗ Map them to <unk>

byte_fallback=False: the Korean word collapses to id 0 and decodes as " ⁇ ". The model never sees what was written, and you can't get it back.

✗ Give every character a row

Coverage 1.0 keeps characters seen once (B, E and K each appear once in tok400's 503), wasting rows that barely get trained, and a character never seen at all still has no id.

✗ A fixed word list

Short sequences for listed words, but every typo, name or foreign word is <unk>. This is the problem subword tokenizers were built to fix.

✓ Characters, with byte fallback

Common characters and their merges get pieces; anything else costs a few byte tokens but always round-trips. 256 reserved ids buy "nothing is ever unknown".

Should you use sentencepiece?

Karpathy's advice (2:10:20): if you can, reuse GPT-4's vocabulary with tiktoken. If you must train your own vocabulary, sentencepiece is a reasonable choice because it trains and encodes efficiently, and it's what Llama and Mistral use. But copy Meta's settings, because it has a huge number of options and several defaults quietly change your text.

The traps: normalization is on unless you set identity; remove_extra_whitespaces (on by default) collapses repeated spaces (with default settings, 'a b' decodes back as 'a b' in a scratch run), which ruins code indentation; max_sentence_length (4,192 bytes here) crops long "sentences" without saying so; the byte-token ids are offset by the specials; and the dummy prefix adds a ▁ you didn't type. Hugging Face's tokenizers library is another option the Colab points to, which Karpathy didn't cover in detail.

Understand and remember

  • sentencepiece merges code points, not bytes → a character outside the kept set has no piece → it must go somewhere: <unk> (text lost, decodes as " ⁇ ") or, with byte_fallback, its UTF-8 bytes (1–4 byte tokens, always round-trips)
  • character_coverage keeps the most frequent characters covering that share of the training text → characters from languages rare in the training data are dropped → those languages cost one byte token per UTF-8 byte (3 per Korean syllable) instead of merged pieces
  • Reserving 256 byte tokens costs vocabulary slots (256 of tok400's 400) → but guarantees any string can be encoded and decoded → which is why Llama 2 turns fallback on, and why tiktoken's bytes-first design gets the same guarantee for free
  • detail that matters Specials come first (<unk>=0, <s>=1, </s>=2) → byte b lives at id b + 3 → code that assumes byte token = byte value is off by 3
  • detail that matters add_dummy_prefix prepends a space → a word at the start of the text gets the same pieces as mid-sentence → but text that already starts with a space gets an extra ▁

Reference only

  • the full option list (input_sentence_size, seed_sentencepiece_size, shuffle_input_sentence, split_by_*, num_threads)
  • ▁ is U+2581; <unk> decodes as " ⁇ " (U+2047)
  • Llama 2 values: vocab_size 32,000, character_coverage 0.99995, max_sentencepiece_length 16, max_sentence_length 4,192
  • the API: SentencePieceTrainer.train(**options), SentencePieceProcessor().load(), encode, decode, id_to_piece

vs Code points, bytes, and why neither works raw: That card argued raw code points and raw bytes both fail as a vocabulary. How does sentencepiece combine the two to get around each one's problem?

Check
  • raw code points: too many (about 150k) and they keep changing, so keep only the common ones
  • raw bytes: sequences too long, so use them only for rare characters
  • result: common text is short, and rare text is long but never lost
