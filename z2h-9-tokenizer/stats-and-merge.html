Count pairs, merge the winner

Also called: one BPE step, get_stats and merge, pair counting. Lecture 8 · counting consecutive pairs, finding most common pair · 0:28:35

Prime · 2 minutes before you read

The problem: Raw UTF-8 bytes make text long: the lecture's 533-character paragraph is 616 byte ids. BPE shortens it, but only if you can find the byte pairs worth fusing and then actually fuse them in the list.

Where it fits: The by-hand card ran BPE on letters with a pencil. This card turns one step of it into code on real UTF-8 bytes, the 0–255 integers from the unicode card; the next card wraps these two functions in a loop.

In one breath: one step of byte pair encoding (BPE) is two small functions. get_stats walks the list of byte ids and counts how often each adjacent pair occurs; merge rewrites the list, putting a brand-new id (256, then 257, …) wherever the winning pair appears. On the 616-byte paragraph from the lecture, the winner is (101, 32), which is "e " (the letter e followed by a space), seen 20 times, so one merge takes the list from 616 ids to 596.

Predict first: the runner-up pair, seen 15 times, is (240, 159). Neither number is a printable ASCII character (those stop at 126). What in the paragraph produces it?

Emoji. The paragraph opens with 🅤🅝🅘🅒🅞🅓🅔‽ 🇺🇳🇮🇨🇴🇩🇪! 😄: 7 circled letters, 7 flag letters and 1 smiley. Each is a 4-byte UTF-8 character, and all 15 start with the bytes 240, 159: 7 + 7 + 1 = 15. BPE never sees characters, only bytes, so it would happily mint a token for "half an emoji".

Step 1: count every adjacent pair

The input is the list ids of integers you got from list(text.encode("utf-8")), each 0–255. zip(ids, ids[1:]) lines the list up against itself shifted by one, so it yields every neighbour pair in order. A dict then tallies them. Here's the example from the docstring in base.py:

5 ids give 4 pairs. counts.get(pair, 0) + 1 reads the current count (0 if the pair is new) and adds one.

max(stats, key=stats.get) loops over the dict's keys (the pairs) and ranks each one by stats.get(pair), its count. On a tie it keeps the first pair it met, and a dict remembers insertion order, so ties go to whichever pair appeared earliest in the text.

Step 2: merge the winner

merge(ids, pair, idx) walks the list with an index i. If ids[i] and ids[i+1] are the pair, it writes the new id idx and jumps 2; otherwise it copies ids[i] and steps 1. The i < len(ids) - 1 test stops it from peeking past the end when the last id happens to equal pair[0].

Karpathy's toy call: the first 6 is followed by another 6, so it's copied; the second 6 is followed by 7, so the two become 99. Six ids in, five out.

def get_stats(ids):
    counts = {}
    for pair in zip(ids, ids[1:]):  # consecutive elements
        counts[pair] = counts.get(pair, 0) + 1
    return counts

def merge(ids, pair, idx):
    newids, i = [], 0
    while i < len(ids):
        if i < len(ids) - 1 and (ids[i], ids[i+1]) == pair:
            newids.append(idx); i += 2    # 2 ids become 1
        else:
            newids.append(ids[i]); i += 1
    return newids
text = "Ｕｎｉｃｏｄｅ! 🅤🅝🅘🅒🅞🅓🅔‽ ..."   # Colab cell 5, pasted whole
tokens = list(map(int, text.encode("utf-8")))
print('length:', len(text), 'characters,', len(tokens), 'bytes')
stats = get_stats(tokens)
print('distinct pairs:', len(stats))
top5 = sorted(((v, k) for k, v in stats.items()), reverse=True)[:5]
print('top 5 (count, pair):', top5)
top_pair = max(stats, key=stats.get)
print(merge([5, 6, 6, 7, 9, 1], (6, 7), 99))
tokens2 = merge(tokens, top_pair, 256)
print('length after merge:', len(tokens2),
      f'(= {len(tokens)} - {stats[top_pair]})')
print('256 appears', tokens2.count(256), 'times')

Why it beats the alternatives

✗ Leave the bytes alone

A vocabulary of 256 that needs no training, but the 533-character paragraph costs 616 positions, and every "e " costs two of them.

✗ A fixed list of whole words

Short sequences for words on the list, but a typo, a new name or a Korean word has no id at all, so it needs an "unknown" token that throws the text away.

✗ Take the top 20 pairs from one count

Saves recounting, but it can only ever pair raw bytes. The lecture's 20th merge on the full post is (259, 256) = "th" + "e " → "the ", a pair that doesn't exist until two earlier merges have rewritten the list.

✓ Count, merge the top one, recount

Each merge is chosen on the current list, so new ids can pair with each other and build longer chunks. Anything unseen still falls back to its bytes.

Does get_stats count what merge replaces?

Not always. get_stats counts overlapping pairs, but merge jumps 2 after each match. For [97, 97, 97, 97] ("aaaa"), get_stats reports (97, 97): 3, yet merge gives [256, 256]: only 2 replacements, so the length drops by 2, not 3. The count only picks the winner; the real saving can be smaller whenever the pair's two bytes are the same.

Recounting from scratch after every merge is also the slow part. Each merge rescans the whole list, which is fine for 616 bytes. On the 185,768-byte Taylor Swift page, 256 merges took about 11 s on your M3 (build-gpt4-tokenizer lab, under load). Doing 50,000 merges over gigabytes of text needs smarter bookkeeping, for example updating only the counts next to each merge. That last point is our inference; the lecture doesn't cover it.

Understand and remember

  • zip(ids, ids[1:]) pairs each id with its right neighbour → a list of n ids yields n − 1 overlapping pairs → a dict tallies them (615 pairs, 269 distinct on the paragraph) → max(..., key=stats.get) picks the most frequent, (101, 32) = "e " ×20
  • merge writes the new id and skips 2 on a match → each replacement turns 2 ids into 1 → length drops by the number of replacements → 616 − 20 = 596 for "e "
  • Counting sees overlapping pairs but merge can't reuse an id it already consumed → for pairs with two equal bytes the saving can be smaller than the count ("aaaa": counted 3, replaced 2) → the count ranks pairs, it doesn't promise the saving
  • BPE counts bytes, not characters → multi-byte characters share lead bytes (every emoji here starts 240, 159) → frequent byte fragments of characters compete with real words for new tokens
  • detail that matters Ties in max go to the pair inserted into the dict first → dicts keep insertion order → ties are won by the pair that appears earliest in the text, which makes training deterministic for a given text

Reference only

  • counts.get(pair, 0) + 1 as the tally idiom
  • list(map(int, text.encode("utf-8"))) vs list(text.encode("utf-8")) (same result)
  • the counts=None argument in minbpe's get_stats for updating an existing dict
  • the exact top-5 counts after the winner (15, 12, 12, 10)

4 · Compare against what you already know

vs Byte pair encoding by hand: The by-hand card merged letters on paper; this card merges byte ids in Python. What is identical, what changed by moving to bytes, and how does each version handle a tie?

Check
  • identical: count adjacent pairs, replace the most frequent with a new symbol, repeat
  • bytes mean new symbols are ids 256+ instead of letters Z, Y, X, and any text can be encoded from the start
  • by hand you choose among ties; max takes the first pair inserted, which is why the byte version of aaabdaaabac merges aa, aaa, aaab rather than aa, ab, ZY

vs Encoding: apply merges in training order: Training picks a pair with max over counts; encoding picks one with min over merge indices. Why can't encoding reuse the training rule?

Check
  • encoding must reproduce the merges in the order they were learned, not the order that happens to be frequent in the new text
  • picking by count on new text could apply a later merge before an earlier one its pieces depend on
  • both reuse get_stats and merge; only the choice rule differs
