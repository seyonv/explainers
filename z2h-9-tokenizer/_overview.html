Prime · 2 minutes before you read

The problem: The GPT lecture fed its model one id per character, 65 in all, which only works for one small English text. Real models read about 50,000 to 100,000 learned chunks, and without knowing how those chunks are made you can't explain why an LLM miscounts letters, stumbles on arithmetic, costs more in Korean or breaks on a stray space.

Where it fits: This is the map of course z2h-9, read first or as a recap. It replaces the character tokenizer from the GPT lecture (z2h-8) and reuses that lecture's embedding table and lm_head, which are the only places the vocabulary size reaches the model. The next course, z2h-10, trains GPT-2 on this lecture's 50,257-token vocabulary.

In one breath: a language model reads integers, not text, and the tokenizer is the separate program that makes them. It turns text into UTF-8 bytes (256 base tokens, so nothing is ever unknown), cuts the bytes into chunks with a regex, and then applies merges it learned beforehand by counting: over and over, the most frequent neighbouring pair becomes a new token. Decoding looks each id's bytes up and reads them as UTF-8. On the lecture's blog post, 20 merges shrink 24,597 bytes to 19,438 tokens. GPT-2 stops at 50,000 merges and GPT-4 at about 100,000, and many of the odd things LLMs do trace back to how those merges cut text.

1 · Core model what to internalise, what to just look up

Keep it if it changes what you can explain, predict, compare, choose, build or debug. Otherwise it's reference.

Understand and remember

  • Code points are ~150k and still growing, raw bytes make text several times longer → start from the 256 UTF-8 bytes so anything encodes → merge the most frequent pair into a new id, again and again → 24,597 bytes become 19,438 tokens after 20 merges, 1.27×
  • Merges are learned by counting on the tokenizer's own text, once, before the LLM → whatever that text is dense in gets short tokens → the blog tokenizer compresses the blog 1.27× but Korean barely at all (158 → 155) → non-English and code cost more context
  • Later merges are built from earlier ones (275 = 259 + 256) → encode must replay them lowest rank first, and stop when no learned pair is left → the ids match what training produced (19,438 on the post) → decode just joins each id's bytes, but some byte runs aren't UTF-8 → errors="replace"
  • The token id is all the model sees → letters inside a token, arbitrary digit groups and a lone trailing space (220) are invisible or rare → spelling, arithmetic and completion quirks; an id the LLM never trained on (43453) has an untrained embedding row → SolidGoldMagikarp
  • detail that matters V sets the embedding rows and the lm_head outputs → in gpt.py's shape each id costs 769 parameters, so V = 50,257 is 78.3% of a 49.39M model → bigger vocabularies shorten sequences but cost compute and leave rare rows undertrained
  • detail that matters The regex split forbids merges across letters, numbers, punctuation and spaces → compression drops (2.36× → 2.13× on the Taylor Swift page) but no token glues a word to its punctuation (110 of 256 basic merges did)

Reference only

  • GPT-2: 50,257 = 256 + 50,000 + 1, <|endoftext|> = 50256; cl100k n_vocab 100,277
  • the example string: 300 gpt2 tokens, 185 cl100k
  • encoder.json = vocab, vocab.bpe = merges, bpe_ranks = merge rank
  • enc._mergeable_ranks, recover_merges, byte_shuffle (a → 64, space → 220)
  • sentencepiece options: byte_fallback, character_coverage=0.99995, split_digits, add_dummy_prefix; Llama 2 vocab 32,000

4 · Compare against what you already know

vs Characters to integers, and a held-out 10%: The GPT lecture's tokenizer was sorted(set(text)): 65 characters, no training. What is fundamentally different about a byte-level BPE tokenizer, which design choice causes it, when would you still pick characters, and how does each fail?

Check
  • characters: the vocabulary is read off one text, one id per character, nothing learned
  • BPE: 256 bytes as the base plus learned merges, so any text encodes and common chunks are one id
  • characters fit a small single-language demo: 65 rows, every row trained, no training step
  • characters fail on any unseen character and spend one position per character; BPE fails through its merges: hidden letters, arbitrary digit groups, untrained rows

vs Token and position embeddings: The GPT lecture's model looks each token id up in an embedding table and scores every id with lm_head. How does this course's choice of V change that model, and what doesn't it change?

Check
  • V sets the number of embedding rows and lm_head outputs, nothing else
  • the Blocks between them only see vectors of width n_embd, so they are unchanged
  • each id costs 769 parameters at n_embd 384; 65 → 50,257 takes the model from 10.79M to 49.39M
  • more ids also means each row is updated less often, which is where glitch tokens come from

5 · Predict commit to an answer before revealing

The next course trains GPT-2 124M (n_embd 768) on exactly this lecture's 50,257-token vocabulary. Before watching: what loss should the freshly initialised model print at step 0, and how many parameters does the token embedding table alone cost?

Reveal

A uniform guess over 50,257 ids scores −ln(1/50257) = 10.82 (z2h-10's first-loss lab prints 10.96). The embedding table is 50,257 × 768 = 38,597,376 parameters. GPT-2 shares that one matrix with lm_head (weight tying), which saves 31.0% of the 124M model, and the course later pads V to 50,304 because it divides evenly by 128.
