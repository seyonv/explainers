What tokens look like

Also called: tokenization by example, the tiktokenizer tour. Lecture 8 · tokenization by example in a Web UI (tiktokenizer) · 0:05:50

Prime · 2 minutes before you read

The problem: You can't reason about why an LLM stumbles on arithmetic, spelling, Korean or Python until you've seen what it actually receives. It isn't letters: it's a list of integer ids for chunks that often cut words and numbers in surprising places.

Where it fits: The GPT lecture fed the model one character per token from a 65-character vocabulary. This card looks at real tokenizers (GPT-2's and GPT-4's) before the next cards build one from scratch.

In one breath: a language model never sees letters. A tokenizer cuts text into chunks called tokens and swaps each chunk for an integer, its token id. Pasting a paragraph into a tokenizer viewer shows how odd those chunks are: spaces glued to words, numbers cut at random places, the same word with four different ids, and Korean or Python costing far more tokens than English.

Predict first: GPT-2's tokenizer reads 127 + 677 = 804. How many tokens does it make, and is 677 one of them?

7 tokens, and 677 isn't one. The pieces are 127 · + · 6 · 77 · = · 8 · 04. 127 happens to be a single token, but 677 becomes 6 + 77, and 804 becomes 8 + 04. The model has to do arithmetic on pieces like these.

One sentence, cut into tokens

The first line of Karpathy's example string, as GPT-2 tokenizes it. Each chip is one token with its id underneath. ␣ marks a space. Green chips are the ones the lecture points at.

76 characters → 20 tokens, about 3.8 characters per token (76 ÷ 20). Computed with tiktoken's gpt2 encoding; the first 10 ids match the lab.

Three things to notice. Common words are one token each. The space before a word belongs to that word's token (␣is = 318), so "is" with and without a space are different tokens. Rarer words split into pieces (Token + ization, ␣weird + ness). Both ␣of tokens are id 286: the same chunk always gets the same id, which is the row the model looks up in its embedding table.

The whole example string: GPT-2 vs GPT-4

The example string has five paragraphs: English, arithmetic, Egg/egg, Korean, and FizzBuzz in Python. gpt2 is GPT-2's tokenizer, with a vocabulary (the list of all tokens it knows) of 50,257. cl100k_base is GPT-4's, with 100,277.

Counted inside the full string (a token that touches a blank line goes in "blank lines"). Bars are scaled to the longest, 132. The totals 300 and 185 match the lab and the video.

Fewer tokens matters because a model has a fixed context length: the most tokens it can look at at once (1024 for GPT-2). The Korean paragraph costs GPT-2 132 tokens for 72 characters, more than the English line's 20 for 76. It's almost as bad as feeding raw bytes (158). The tokenizer saw little Korean when it was trained, so it learned few Korean chunks.

▶ Build itruns on your M3 · under 1 s

When: pause the video at 0:05:50. First paste the example string into tiktokenizer and switch between gpt2 and cl100k_base. Then do the same in Python with tiktoken (pip install tiktoken), OpenAI's tokenizer library. Save the string (cell 1 of the Colab, ending with one newline) as example.txt.

import tiktoken
s = open('example.txt').read()   # the Colab's example string
gpt2 = tiktoken.get_encoding('gpt2')
cl100k = tiktoken.get_encoding('cl100k_base')
def show(enc, t):
    ids = enc.encode(t)          # text -> list of token ids
    return ' + '.join(f'{enc.decode([i])!r}={i}' for i in ids)
print('gpt2 tokens       :', len(gpt2.encode(s)))
print('cl100k_base tokens:', len(cl100k.encode(s)))
print('first 10 gpt2 ids :', gpt2.encode(s)[:10])
for t in [' 677', '1275', 'Egg', ' Egg', 'egg', 'EGG']:
    print(f'gpt2 {t!r:14}', show(gpt2, t))

Why chunks beat the alternatives

✗ One token per character

416 tokens for the example string, and the vocabulary must hold every character in every script. The z2h-8 GPT used 65 characters, which only works for one small English text.

✗ One token per raw byte

A tiny vocabulary of 256, but 502 tokens here, and 158 for the Korean line alone. Sequences get long, and they fill the context fast.

✗ One token per word

Splitting on spaces gives 80 words, 61 of them distinct, including Egg., egg. and range(1,. Any word not in the list, such as a typo or a new name, has no id at all.

✓ Learned chunks (BPE)

Common chunks get one token and rare ones fall back to smaller pieces, down to single bytes, so any text can be encoded. 300 tokens with GPT-2, and 185 with GPT-4's bigger vocabulary.

416 characters, 502 UTF-8 bytes, and 80 whitespace-separated words, all computed on the example string. BPE (byte pair encoding) is how the chunks are learned; it's built from scratch starting at BPE by hand.

So is a bigger vocabulary just better?

Not automatically. cl100k_base cut the string from 300 to 185 tokens, but it wasn't better on every paragraph: the arithmetic went from 16 to 18 tokens, because GPT-4's tokenizer splits off the space and caps number chunks at 3 digits. Each extra token in the vocabulary also adds a row to the model's embedding table and one more output the final layer must score, so the model gets bigger and slower. Karpathy covers this trade-off at 1:43:27.

Token ids also belong to one tokenizer. ␣Egg is 14562 in gpt2 and 42313 in cl100k_base, so a model only understands the tokenizer it was trained with. Before you count tokens for a price or a context limit, check which one your model uses.

1 · Core model what to internalise, what to just look up

Keep it if it changes what you can explain, predict, compare, choose, build or debug. Otherwise it's reference.

Understand and remember

  • The tokenizer learned its chunks from how often text appeared in its own training data → common English words and ␣word forms became single tokens → rare words, other scripts and odd digit runs fall back to small pieces → the same meaning costs very different numbers of tokens (English 20 vs Korean 132 in gpt2)
  • Case, a leading space and position each produce a different chunk → E|gg, ␣Egg, egg, EG|G are unrelated ids → the model must learn from data that they mean the same thing, and it can't see letters inside a token
  • Numbers are chunked by what was frequent, not by place value → ␣6|77, 12|75, ␣8|041 differ from number to number → the model gets no consistent digit columns → arithmetic is harder
  • More tokens per text → the fixed context holds less text and every step costs more compute → a bigger vocabulary (cl100k: 300 → 185) packs more text per token, but at the price of a bigger embedding table and output layer
  • detail that matters gpt2 makes each indent space its own token (220) while cl100k groups runs of spaces (7 spaces = 286) → FizzBuzz drops from 108 to 71 tokens → GPT-4 fits more code into its context

Reference only

  • the exact ids: ␣is = 318, ␣the = 262, ␣Egg = 14562, space = 220
