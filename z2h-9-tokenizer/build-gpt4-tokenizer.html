Exercise: rebuild the GPT-4 tokenizer

Also called: the minbpe exercise, GPT4Tokenizer, matching tiktoken's cl100k_base. Lecture 8 · minbpe exercise time! write your own GPT-4 tokenizer · 1:25:28

Prime · 2 minutes before you read

The problem: You've written get_stats, merge, a training loop, encode and decode, but only as separate pieces, and your ids mean nothing to GPT-4. A model trained on GPT-4's ids can only read ids produced by exactly GPT-4's tokenizer, and tiktoken gives you that tokenizer without showing how it's built.

Where it fits: This is the capstone of the byte pair encoding and real-tokenizer cards. It combines the training loop and encode with the regex pre-split and special tokens, and checks the result against tiktoken id for id. The sentencepiece card comes next.

  2. tiktoken stores only bytes → rank. What property of BPE lets you rebuild the pair behind every rank?
  3. Why does the replay for a token have to stop before reaching the token's own rank?
  4. What goes wrong if you load GPT-4's merges but feed them raw byte values, and why do most merges then never fire?

In one breath: Karpathy's exercise.md has you assemble everything from the earlier cards into one tokenizer that gives exactly the same token ids as GPT-4's. First you train a plain BPE tokenizer, then add the GPT-4 regex split, then throw your own merges away and load GPT-4's, and last you handle special tokens. Two hurdles sit in step 3: tiktoken doesn't store GPT-4's merges as pairs, and it stores the 256 single bytes in a shuffled order.

Predict first: you train two tokenizers with 256 merges each (vocab 512) on the same 185,768-byte Taylor Swift Wikipedia page. One is plain BPE. The other first splits the text with GPT-4's regex. Which one ends up with fewer tokens?

The plain one: 78,746 tokens (2.36×) against 87,339 (2.13×). The regex forbids merges across letters, digits, punctuation and spaces. The plain tokenizer uses that freedom: 110 of its 256 merges span such a boundary, like e␣ and .␣Archived␣from␣the␣original␣on␣. Fewer tokens isn't the goal, though; tokens that mean something are.

Steps 1–2: same text, same vocab size, different merges

Step 2 changes only the start of the training loop. The text becomes a list of chunks, pair counts are added up over all chunks, and each merge is applied inside every chunk, so a merge can never join the end of one chunk to the start of the next. Give get_stats an optional counts dict to add into, as base.py does.

chunks = [list(ch.encode("utf-8"))
          for ch in re.findall(GPT4_SPLIT_PATTERN, text)]
merges = {}
for i in range(512 - 256):
    stats = {}
    for chunk_ids in chunks:
        get_stats(chunk_ids, stats)   # add counts across chunks
    pair = max(stats, key=stats.get)
    chunks = [merge(c, pair, 256 + i) for c in chunks]
    merges[pair] = 256 + i

Step 3: two hurdles before your ids match GPT-4's

Hurdle 1: the merges aren't stored as pairs. tiktoken keeps a dict called _mergeable_ranks that maps each token's bytes to its rank (its id, which is also its place in the merge order), for example b'hello' → 15339. It doesn't record which two tokens were merged to make it. You recover that by replaying BPE on the token's own bytes, allowing only merges with a lower rank. Whatever two pieces are left when you get stuck are its parents:

b'hello' has rank 15339; replay using only merges ranked below 15339: h e l l o → h el l o → h el lo → h ello ← stuck: the next merge would be 'hello' itself so merge (71, 4896) → 15339, i.e. 'h' + 'ello'

Doing that for every token longer than one byte gives 100,256 − 256 = 100,000 merges, the same size of table your own train produces. Karpathy's version is recover_merges in gpt4.py, which exercise.md says you may copy.

Hurdle 2: the single bytes are shuffled. In your tokenizer, byte 104 (h) is token 104. In GPT-4 it's token 71. The lab prints a → 64, space → 220, byte 0 → 188, and none of the 256 bytes keeps its own number. So before merging, map every byte through byte_shuffle, and undo it when decoding.

'!' (33) → 0 ... '~' (126) → 93, then the other printable Latin-1 bytes → 94–187 'a' is byte 97, and 97 − 33 = 64 → token 64 byte 0 is the first non-printable byte → token 188 space is byte 32, and 188 + 32 = 220 → token 220

Computed: the shuffle is exactly the byte order of GPT-2's bytes_to_unicode helper, the "spurious" layer in encoder.py (printable bytes first, the other 68 after). minbpe's comment calls the permutation "probably historical". Skip it and the test string comes out as 41 ids instead of 14, and decoding them gives garbage.

▶ Build itruns on your M3 · about 30 s

When: pause the video at 1:25:28, open exercise.md, and do the steps before he shows minbpe. For steps 1–2, run the loop above at vocab 512 on taylorswift.txt (or Karpathy's train.py). Then step 3: recover the merges.

enc = tiktoken.get_encoding("cl100k_base")
ranks = enc._mergeable_ranks        # bytes -> rank; no pairs stored
def bpe(token, max_rank):  # replay only merges older than max_rank
    parts = [bytes([b]) for b in token]
    while True:
        r = [(ranks.get(a + b, max_rank), i)
             for i, (a, b) in enumerate(zip(parts, parts[1:]))]
        if not r or min(r)[0] >= max_rank:
            return parts
        i = min(r)[1]
        parts[i:i + 2] = [parts[i] + parts[i + 1]]
merges = {tuple(ranks[p] for p in bpe(t, rk)): rk
          for t, rk in ranks.items() if len(t) > 1}
print("recovered", len(merges), "GPT-4 merges")

Then encode each regex chunk through the byte shuffle, with the encode card's loop:

byte_shuffle = {i: ranks[bytes([i])] for i in range(256)}
rank = lambda p: merges.get(p, float("inf"))
def encode(text):
    ids = []
    for chunk in re.findall(GPT4_SPLIT_PATTERN, text):
        t = [byte_shuffle[b] for b in chunk.encode("utf-8")]
        while len(t) >= 2:
            pair = min(get_stats(t), key=rank)
            if pair not in merges:
                break
            t = merge(t, pair, merges[pair])
        ids.extend(t)
    return ids
s = "hello world!!!? (안녕하세요!) lol123 😉"; ids = encode(s)
print(repr(s), ids, "matches tiktoken:", ids == enc.encode(s))

Step 4 is the last line. Before the regex runs, split the text on the special strings with re.split and a capturing group, which keeps the matches. Send each special piece straight to its id and every other piece through encode. tiktoken only does this when you pass allowed_special="all"; by default it raises a ValueError, so typed-in text can't smuggle in a special token. Why it beats the alternatives

✗ Your basic tokenizer

Best compression here (2.36×), but 110 of its merges glue words to spaces and punctuation, and its ids mean nothing to GPT-4. A model trained with GPT-4's ids can't read them.

✗ Your regex tokenizer

The right structure, the wrong merges. Trained on one Wikipedia page, it starts with er and 20; GPT-4 starts with runs of spaces. Same algorithm, different training text, different ids.

✗ GPT-4's merges, raw bytes

Recovering the merges without byte_shuffle still runs, but h is looked up as 104 instead of 71. Most merges never fire: 41 ids instead of 14 on the test string, and the decode is garbage.

✓ Regex + recovered merges + shuffle + specials

Every id matches tiktoken on all three test strings, and now you know what each piece of a production tokenizer is for.

Should you ship your own GPT4Tokenizer?

No. For GPT-4's ids, use tiktoken itself: it gives the same ids, its core is written in Rust, and it's the reference your version was checked against. minbpe's GPT4Tokenizer even refuses to train, save or load. The point of the exercise is understanding, and a trainable tokenizer: tiktoken can only use a vocabulary, while minbpe can learn one. Karpathy's closing advice (2:10:20) is to reuse GPT-4's vocabulary with tiktoken when you can.

Matching on three strings is evidence, not proof. The regex that minbpe and the video use is textually different from the one tiktoken 0.14 stores (the regex card), and Python's loop is far slower than tiktoken on big inputs. To train a vocabulary of your own at scale, the lecture points to sentencepiece, with its settings copied carefully from a model like Llama 2 (next card).

Understand and remember

  • Regex pre-split → merges can't cross letters/digits/punctuation/space → the tokenizer spends its merges on words instead of e␣ or citation boilerplate → worse raw compression (2.13× vs 2.36× on taylorswift.txt) but more meaningful tokens
  • A token's rank is also its place in the merge order → replaying BPE on its bytes with only lower-ranked merges ends exactly at its two parents → the whole 100,000-merge table can be rebuilt from bytes → rank alone
  • Merges are keyed by token ids, and GPT-4's byte tokens are permuted (h is 71, not 104) → encoding raw bytes looks up the wrong pairs → most merges never fire (41 ids instead of 14) → you must shuffle bytes on encode and un-shuffle on decode
  • Same algorithm + same merges + same regex + same byte order + same special-token handling → identical ids → any one layer wrong silently gives different ids that GPT-4's embedding table would misread
  • detail that matters Special tokens are split off with re.split and a capturing group before the regex → their ids never pass through BPE → and because typed text could contain <|endoftext|>, tiktoken raises unless you pass allowed_special

Reference only

  • the exact GPT4_SPLIT_PATTERN string (copy it from regex.py)
  • enc._mergeable_ranks (a private tiktoken attribute) and its 100,256 entries
  • the special-token ids: <|endoftext|> 100257, FIM 100258–100260, <|endofprompt|> 100276
  • the byte_shuffle values (a → 64, space → 220, byte 0 → 188) and that they follow GPT-2's bytes_to_unicode order
  • minbpe's class and method names (encode_ordinary, _encode_chunk, register_special_tokens)

5 · Predict commit to an answer before revealing

Keep GPT-4's recovered merges and byte shuffle, but split with the GPT-2 regex instead. On "x = 1234567", will your ids still match tiktoken's? If not, where will they differ?

Reveal

They differ, even though both give 6 tokens. GPT-2's regex keeps ␣1234567 as one chunk, while GPT-4's regex splits it into ␣, 123, 456, 7. GPT-4's merges never learned a space+digit token or anything longer than three digits, so BPE on the GPT-2 chunk ends as ␣ 123 45 67 ([220, 4513, 10961, 22] from tiktoken vs [220, 4513, 1774, 3080] from yours). On the lab's test string the two regexes happen to give identical chunks, so it would still match. That's why one test string isn't proof.
