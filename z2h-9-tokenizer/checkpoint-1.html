Checkpoint 1: bytes in, merges learned, ids back out

Ties together code points and bytes, BPE by hand, count pairs, merge the winner, training a tokenizer, decoding and encoding, with the GPT lecture's character tokenizer, the bigram lecture's count matrix and the loss you should see at step 0. Lecture 8 · chapters 3–13, strings in Python to encoding · 0:14:56 to 0:57:36

Prime · why this checkpoint, why now

You now have a whole working tokenizer: UTF-8 bytes in, 20 learned merges, encode and decode. At 0:57:36 the lecture moves on to real tokenizers (a regex split, OpenAI's files, special tokens, sentencepiece), and each of them changes one piece of the thing you just built. If you can't yet say which piece is which, those changes will look like new algorithms instead of small edits.

  • Code points and bytes → a string is code points; UTF-8 writes each as 1 to 4 bytes. Bytes give a fixed vocabulary of 256 that can encode anything, at the cost of length.
  • BPE by hand and count pairs, merge the winner → count neighbouring pairs, mint a new id for the most frequent, replace it, repeat. Counts overlap; replacements don't.
  • Training a tokenizer → 20 merges take the blog post from 24,597 bytes to 19,438 ids (1.27×). It is "a completely separate stage" (the 0:39:20 chapter title), trained on its own text.
  • Decoding → join every id's bytes, then decode once with errors="replace", because not every id sequence is valid UTF-8.
  • Encoding → replay the merges lowest index first, so new text is cut the way training cut the training text.

1 · Mixed retrieval

  1. With the 20 merges from the blog post, encode the 4-byte string "the " by hand. Two learned pairs are present at the start: th (259) on the left and e␣ (256) on the right. Which merges first, what happens next, and how many ids come out?
    Check
    • round 1: the pairs score th 259, he inf, e␣ 256; min picks 256, so e␣ merges first even though it's on the right
    • round 2: th → 259; round 3: (259, 256) is merge 275, the␣
    • one id left, so while len(tokens) >= 2 stops: the answer is [275]
    • encode doesn't read left to right; it replays training order, the lowest merge index first

  2. In the bigram lecture you filled N[ix1, ix2] += 1 for 27 characters. Do the same with a 256 × 256 tensor over the blog post's 24,597 bytes. What is the largest entry, how many cells are non-zero, and how do both relate to get_stats? Then say what BPE does next that the bigram model never does.
    Check
    • the largest entry is 646, at (101, 32) = e␣: the same pair and count max(stats, key=stats.get) returns, and the first merge
    • 1,381 non-zero cells = len(get_stats(tokens)), and the entries sum to 24,596 = 24,597 − 1 pairs
    • get_stats is a sparse bigram count: a dict holds only the pairs that occur, instead of 65,536 cells
    • the bigram model normalises each row into probabilities and stops. BPE mints id 256, rewrites the list and counts again, so the table itself changes (the next winner is in, 446 times)

  3. which idea?You build a chat app for Korean speakers and reuse a tokenizer trained with 256 merges on the English blog post. The example string's first English line shrinks from 76 bytes to 42 tokens, but its Korean line only from 158 to 154. Nothing crashes. Which idea explains the gap, and what would you change?
    Check
    • BPE merges only the pairs that were frequent in the tokenizer's own training text, and the blog post has almost no Korean
    • 76 → 42 is 1.81×; 158 → 154 is 1.03×, so the Korean stays about one token per byte
    • the tokenizer is a separate stage with its own training set, so fix it there: put Korean into the tokenizer's training text, and Korean merges will follow
    • the same logic explains GPT-2's 132 tokens for the 72-character Korean paragraph in the tiktokenizer tour

    Missed it? Reopen training a tokenizer, "A completely separate stage" and "Is the tokenizer trained on the LLM's data?", and what tokens look like, "The whole example string: GPT-2 vs GPT-4".

  4. get_stats([97, 97, 97, 97]) ("aaaa") reports (97, 97): 3. How much shorter does one merge make the list, and why doesn't the count tell you? Where did the same thing happen in the Wikipedia example?
    Check
    • merge gives [256, 256]: 4 → 2, so 2 replacements, not 3
    • get_stats counts overlapping pairs; merge jumps 2 after each match, so a replacement uses up both of its symbols
    • in aaabdaaabac, aa counts 4 but is replaced only twice: 11 → 9 symbols
    • the count only picks the winner; for a pair of two different bytes, like e␣, count and replacements agree (616 → 596 on the paragraph)

    Missed it? Reopen count pairs, merge the winner, "Does get_stats count what merge replaces?", and BPE by hand, "Three merges on the Wikipedia example".

  5. debugYou plug your 276-id tokenizer into the GPT lecture's bigram model (vocab_size = 276). The loss at step 0 is 5.62. To see what the untrained model "says", you decode 50 random ids in 0–275 with a strict .decode("utf-8"), and it crashes: 'utf-8' codec can't decode byte 0xf6 in position 0: invalid start byte. What's wrong?
    Check
    • the loss isn't the problem: ln 276 = 5.6204, the cost of guessing uniformly over 276 ids, which is what a healthy untrained model should cost (ln 65 = 4.17 was the character model's)
    • the bug is the strict decode. 0xf6 = 246 is one of the 13 byte values that can never appear in UTF-8, and a model can emit any id in any order
    • fix: join all the bytes and decode once with errors="replace". Those 50 ids (seed 42) then give a string with 20 � in it, which is honest: the model is producing garbage
    • don't decode token by token either: a character split across two ids would turn into several �

    Missed it? Reopen decoding, "Where it breaks" and "Does a � mean the tokenizer is broken?", and the loss you should see at step 0, "What "knowing nothing" should cost".

  6. which idea?A colleague argues for code points instead of bytes as the base vocabulary: the blog post only has 224 distinct characters, fewer than 256 bytes, and it's 23,328 characters long against 24,597 bytes. Your tokenizer must accept anything users type, including emoji added to Unicode after you ship. Which idea settles it, and what does each choice cost?
    Check
    • 224 characters cover this text only. Any character outside the set has no id, the same way "café" crashes the GPT lecture's 65-character tokenizer
    • covering all of Unicode means about 150,000 base symbols, and the standard is "very much alive" (0:14:56): new releases keep adding characters
    • bytes are a fixed alphabet of 256 in which every string encodes; the cost here is 24,597 − 23,328 = 1,269 more positions
    • BPE on top wins the length back: 19,438 ids after only 20 merges

    Missed it? Reopen code points and bytes, "Why neither works raw", and the GPT lecture's character tokenizer, "The trade-off: vocabulary size vs sequence length".

  7. To save time, someone trains by counting pairs once on the raw bytes and taking the 20 most frequent. Which of the lecture's 20 merges can that never produce, and what else in your code depends on the order the merges were made in?
    Check
    • the 3 merges of merges: 270 = (257, 103) ing, 271 = (261, 100) cod and 275 = (259, 256) the␣
    • their pairs don't exist in the raw bytes; they appear only after earlier merges have rewritten the list, which is why training recounts after every merge
    • decode builds vocab by walking merges in insertion order, so both parents exist before a child is built
    • encode relies on the same order: 275 can fire only after 259 and 256 have

    Missed it? Reopen training a tokenizer, "Merges of merges: a forest", and count pairs, merge the winner, "Why it beats the alternatives".

  8. which idea?You save a model's generated text and later re-encode it to score it. For some samples the ids don't match what the model generated: one had [101, 32] and now has [256]; another had [128] and now has [239, 191, 189]. Is the tokenizer broken? Which idea explains both?
    Check
    • the round trip only works one way: decode(encode(text)) == text always, encode(decode(ids)) == ids not always
    • [101, 32] is valid but non-standard: encode always merges e␣ into 256
    • [128] isn't valid UTF-8, so decode turned it into �, and � is the three bytes 239, 191, 189
    • so keep the generated ids (or the raw bytes) if you need them, and compare decoded strings, not id lists

    Missed it? Reopen encoding, "Round trips: one way only", and decoding, "Does a � mean the tokenizer is broken?".

3 · Build: a whole tokenizer, checked against the bigram counts

runs on your M3 · about 1 s

What it reinforces: bytes as the base alphabet (code points and bytes), pair counting as a bigram count matrix (stats and merge, the bigram lecture's count matrix), the training loop (training), both directions of the round trip (decode, encode), and why an untrained model's output needs errors="replace".

  1. Bytes. Load the blog post with blog_text() from labs/common.py (run from the course folder). Print its characters, bytes and distinct characters.
  2. The count matrix. Fill a 256 × 256 N the way the bigram lecture did, and check it against get_stats.
  3. Train. Run 20 merges (vocab_size = 276) and build vocab.
  4. Round trips. Check that encode reproduces the training ids exactly, that encode("the ") is one id, and that decode(encode(text)) == text.
  5. Break it. Decode 50 random ids, as an untrained model might emit, and re-encode decode([128]). Predict both before running.
from common import blog_text, get_stats, train
from common import build_vocab, decode, encode
import torch
text = blog_text(); tokens = list(text.encode('utf-8'))
N = torch.zeros((256, 256), dtype=torch.int32)  # z2h-3's N, bytes
for a, b in zip(tokens, tokens[1:]):
    N[a, b] += 1
print(N.max().item(), divmod(N.argmax().item(), 256),
      (N > 0).sum().item(), len(get_stats(tokens)))
merges, ids = train(tokens, 276)                 # 20 merges
vocab = build_vocab(merges)
print(len(ids), encode('the ', merges), encode(text, merges) == ids)
print(decode(encode(text, merges), vocab) == text)
g = torch.Generator().manual_seed(42)            # random ids
samp = torch.randint(0, 276, (50,), generator=g).tolist()
print(decode(samp, vocab).count('�'),
      encode(decode([128], vocab), merges))
