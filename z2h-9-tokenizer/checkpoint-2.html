Checkpoint 2: real tokenizers, and what the model pays for them

Ties together the GPT-2/GPT-4 regex, encoder.py and special tokens, rebuilding the GPT-4 tokenizer, sentencepiece and Llama 2, how big the vocabulary should be and the quirks, explained, with the GPT lecture's token and position embeddings and character tokenizer, and the loss you should see at step 0. Prime · why this checkpoint, why now

You've reached the end of the lecture. Everything after 0:57:36 was a variation on the tokenizer you built in checkpoint 1: a different split, a different base unit, different merges, or extra ids that BPE never makes. Then the lecture crossed into the model, where every id is a row of the embedding table and a column of lm_head. Next comes GPT-2 itself, which uses one of these tokenizers unchanged, so this is the moment to be sure which design choice causes which quirk.

  • The regex → cut the text into letter, number, punctuation and space chunks first, and run BPE inside each chunk; GPT-4 changed case, digit and newline handling.
  • encoder.py and special tokens → OpenAI's files are your vocab and merges under other names; <|endoftext|> is an id no merge can make.
  • Rebuilding GPT-4 → basic, then regex, then GPT-4's recovered merges with its shuffled byte order, then specials: ids that match tiktoken.
  • sentencepiece → BPE on code points, with bytes only as a fallback for rare characters.
  • Vocabulary size → V touches only the embedding table and lm_head: V × 769 parameters in gpt.py's shape.
  • The quirks → spelling, numbers, Korean, Python, a trailing space and SolidGoldMagikarp each trace back to one of the choices above. Karpathy's closing line: "Eternal glory to anyone who can delete tokenization" (2:10:20).

1 · Mixed retrieval

  1. which idea?You're choosing a tokenizer for a coding assistant. In GPT-2, eight spaces of indentation followed by print(i) cost 11 tokens; in GPT-4's cl100k, 4. GPT-2's regex even hands BPE whole runs of spaces as one chunk. Which ideas explain the difference, and what does GPT-4's merge list suggest about its training text?
    Check
    • GPT-2 emits seven 220s (the eighth space rides on ␣print): its vocabulary has no token for two or three spaces, a result of unpublished training rules, not of the regex
    • cl100k has tokens for runs of spaces (7 spaces = 286), and its pattern changed newline and whitespace handling
    • which merges exist comes from the tokenizer's training text: GPT-4's first two merges are two spaces and four spaces
    • Karpathy's guess is that it saw "a lot of python code" (1:25:28); OpenAI hasn't published the data, so it stays a guess

    Missed it? Reopen the regex, "GPT-2 → GPT-4: what the new pattern changed", and rebuilding GPT-4, the note under "Step 3: two hurdles before your ids match GPT-4's".

  2. Three tokenizers, three rules for digits. Say how GPT-2, GPT-4 and Llama 2 cut four-digit numbers, which design choice causes each, and whether any of them lines digits up by place value.
    Check
    • GPT-2: the regex allows a digit run of any length and the merges follow frequency, so the 9,000 numbers 1000–9999 split five ways (2 + 2 64.5%, 1 + 3 28.2%, 3 + 1 6.0%, one token 1.0%, 1 + 2 + 1 0.3%); 1275 → 12|75
    • GPT-4: \p{N}{1,3} caps a chunk at 3 digits from the left, so all 9,000 split 3 + 1 (1275 → 127|5): consistent, but still not aligned to place value
    • Llama 2: split_digits in sentencepiece makes every digit its own piece, so 677 is always 6, 7, 7
    • only per-digit splitting gives a fixed shape, at the cost of more tokens per number

    Missed it? Reopen the quirks, "Arithmetic: how GPT-2 cuts four-digit numbers", and sentencepiece, "The real thing: Meta's settings for Llama 2".

  3. debugYou retrain the GPT lecture's model on Tiny Shakespeare with GPT-2's tokenizer instead of its 65 characters. The loss at step 0 prints 10.82, and a teammate says the init is broken because the character model started near 4.17. What's wrong?
    Check
    • nothing about that number: ln 50,257 = 10.8249 is what uniform guessing over 50,257 ids costs, just as ln 65 = 4.17 was for 65 characters
    • the real costs are elsewhere: gpt.py's shape grows from 10.79M to 49.39M parameters, 78.3% of them in the embedding table and lm_head
    • the train split's 301,966 GPT-2 tokens use only 11,234 distinct ids, so 39,023 rows (77.6%) never get a gradient
    • what you gain: 338,025 tokens instead of 1,115,394, so 256 positions now cover about 845 characters

    Missed it? Reopen vocabulary size, "What a bigger vocabulary buys, and what it costs", and the loss you should see at step 0, "What "knowing nothing" should cost".

  4. which idea?A user pastes a forum post containing the text <|endoftext|> into your GPT-2-based chatbot, and the bot stops answering in the middle. Which idea explains it, and how do you encode user text safely?
    Check
    • your code parsed special tokens in user text, so the string became the real id 50256, which the model learned means "document over"
    • as plain text it's 7 ordinary tokens (27, 91, 437, 1659, 5239, 91, 29); allowed_special='all' turns it into [50256] ([100257] in cl100k)
    • tiktoken's default raises a ValueError for exactly this reason
    • fix: encode untrusted text with disallowed_special=(), and let only your own code insert specials

    Missed it? Reopen encoder.py and special tokens, "Special tokens: ids that BPE never makes", and the quirks, "Every quirk, traced to the tokenizer".

  5. At vocab 512 on the 185,768-byte Taylor Swift page, the basic tokenizer gives 78,746 tokens (2.36×) and the regex one 87,339 (2.13×). Why would anyone accept 8,593 more tokens, and why can't the regex tokenizer ever go below 46,196 however many merges it gets?
    Check
    • 110 of basic's 256 merges span a category edge, such as the 32-byte citation token .␣Archived␣from␣the␣original␣on␣; the regex tokenizer has 0
    • with a split, the vocabulary goes on pieces of words and numbers, not on dog., dog! and dog? (the GPT-2 paper's reason)
    • the GPT-4 pattern cuts this text into 46,196 chunks, merges never cross a chunk edge, and each chunk needs at least one token
    • the price is about 10.9% more tokens here (8,593 ÷ 78,746)

    Missed it? Reopen the regex, "What the split costs and buys: minbpe on the Taylor Swift page", and rebuilding GPT-4, "Steps 1–2: same text, same vocab size, different merges".

  6. You recovered all 100,000 GPT-4 merges from _mergeable_ranks and your regex encode runs, but the test string "hello world!!!? (안녕하세요!) lol123 😉" comes out as 41 ids instead of tiktoken's 14. What did you skip, and where had you already met the same odd numbering?
    Check
    • the byte shuffle: GPT-4's single-byte tokens aren't numbered by byte value (h is 71, not 104), so most merges never find their pairs
    • fix: map every byte through byte_shuffle = {i: ranks[bytes([i])] ...} before merging, and undo it when decoding
    • the order is GPT-2's bytes_to_unicode: the 188 printable bytes first from ! = 0, so a = 97 − 33 = 64; then byte 0 = 188 and space = 220
    • it's the "spurious implementation detail" layer of encoder.py (the 1:14:59 chapter), and the reason the lone-space token is 220

    Missed it? Reopen rebuilding GPT-4, "Step 3: two hurdles before your ids match GPT-4's", and encoder.py and special tokens, "What encode() does to a string".

  7. Karpathy's tok400 was trained on one English paragraph. Encode "hello 안녕하세요" with it, then with a copy trained with byte_fallback=False. What comes out each time, and why does tiktoken never face this choice?
    Check
    • with fallback: 21 ids; the 5 unseen syllables become 5 × 3 = 15 byte tokens, and the first is 0xEC = 236, plus 3 for <unk>, <s>, </s> = 239. It decodes back exactly
    • without: [362, 378, 252, 102, 362, 0]; the whole Korean word is one <unk> and decodes to 'hello ⁇ ', so the text is gone
    • sentencepiece merges code points and keeps only the characters that cover 99.995% of its text; bytes are a safety net for the rest
    • tiktoken starts from UTF-8 bytes, so every string already has ids and nothing is ever unknown

    Missed it? Reopen sentencepiece, "Encoding Korean it has never seen" and "Where rare characters can go", and code points and bytes, "Why neither works raw".

  8. which idea?You add a chat token by model surgery and fine-tune. A formatting bug means the new token never appears in the fine-tuning data. At inference, prompts that contain it get strange, evasive answers. Which quirk have you recreated, and what's the mechanism in the model?
    Check
    • it's your own SolidGoldMagikarp: a token that exists in the vocabulary but never appeared in the model's training data
    • an embedding lookup selects one row, so a row gets a gradient only on steps where its id is in the batch; the surgery lab shows only row 50257 receiving one
    • here the new row never gets one, so it stays at its random init: the model reads a vector it never learned to interpret
    • GPT-2's ␣SolidGoldMagikarp (43453) came about the same way: frequent in the tokenizer's text (a Reddit username), absent from the LLM's

    Missed it? Reopen the quirks, "SolidGoldMagikarp: a token nobody trained", vocabulary size, "New tokens after training", and the GPT lecture's token and position embeddings, "Where the parameters go".

3 · Build: one string, four tokenizers, and the bill in gpt.py

runs on your M3 · under 1 s

What it reinforces: why the GPT lecture's character tokenizer can't be reused, the token counts of GPT-2 and GPT-4 and of tok400, what each vocabulary costs in parameters and in step-0 loss, how special tokens are parsed, and what byte fallback buys.

  1. The string. Load the Colab's example string with example_string() from labs/common.py (run from the course folder). Count the distinct characters Shakespeare's 65-character vocabulary can't encode.
  2. Four tokenizers. Encode it as raw bytes, with tiktoken's gpt2 and cl100k_base, and with the tok400.model the sentencepiece lab trained.
  3. The bill. For each vocabulary size V, print gpt.py's parameter count, 10,738,944 + 769·V, and the step-0 loss of uniform guessing, ln V.
  4. Specials. Encode <|endoftext|> as plain text and as a special in both encodings.
  5. No fallback. Encode the string with tok400_nofallback.model; count the <unk> ids and check the round trip. Predict before running.
import math, tiktoken, sentencepiece as spm
from common import example_string, read
s = example_string()
chars = set(read('input.txt'))                 # z2h-8's 65 characters
print(len(s), len(set(s) - chars), 'distinct chars have no id')
gpt2 = tiktoken.get_encoding('gpt2')
cl = tiktoken.get_encoding('cl100k_base')
sp = spm.SentencePieceProcessor(model_file='labs/data/tok400.model')
for name, V, ids in [('bytes', 256, list(s.encode())),
        ('gpt2', gpt2.n_vocab, gpt2.encode(s)),
        ('cl100k', cl.n_vocab, cl.encode(s)),
        ('tok400', sp.get_piece_size(), sp.encode(s))]:
    print(f'{name:6} {len(ids):4} tokens  params {10_738_944 + 769*V:,}'
          f'  ln V {math.log(V):.2f}')
e = '<|endoftext|>'
print(len(gpt2.encode(e, disallowed_special=())),
      gpt2.encode(e, allowed_special='all'),
      cl.encode(e, allowed_special='all'))
nf = spm.SentencePieceProcessor(
    model_file='labs/data/tok400_nofallback.model')
ids = nf.encode(s)
print(len(ids), ids.count(0), nf.decode(ids) == s)
