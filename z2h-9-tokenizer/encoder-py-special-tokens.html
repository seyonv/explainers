OpenAI's encoder.py and special tokens

Also called: GPT-2's BPE encoder, encoder.json + vocab.bpe; special tokens, control tokens, <|endoftext|>. Lecture 8 · GPT-2 encoder.py released by OpenAI walkthrough · 1:14:59, then special tokens · 1:18:26

Prime · 2 minutes before you read

The problem: You've built a tokenizer, but a real model ships with someone else's. If you can't read OpenAI's files, you can't reproduce GPT-2's ids, and a model fed the wrong ids is fed nonsense. And a tokenizer made only of merges has no way to say "this document ended", because any marker spelled in text can also appear in ordinary text.

Where it fits: This is where the from-scratch tokenizer meets the real one. It reuses your vocab, merges and encode loop from the encode card and the regex split from the previous card, then adds the one thing BPE can't give you: ids reserved for control.

In one breath: OpenAI released GPT-2's tokenizer as two data files plus a short script. encoder.json is the vocabulary (token string → id) and vocab.bpe is the merge list in training order, so it is the same algorithm you just wrote under different names. The last id, 50256, is special: no merge can produce it, and only your code can insert it, to mark where one document ends and the next begins.

Predict first: in your tokenizer the letter a is token 97, its byte value. What id does GPT-2's encoder.json give the single letter a?

64, not 97. The 256 single-byte tokens are numbered in the order of OpenAI's byte_encoder alphabet, which puts the 188 printable bytes first, starting at ! (byte 33) = id 0. So a = 97 − 33 = 64. The 68 unprintable bytes come after them: byte 0 = id 188, and space (byte 32) = 188 + 32 = 220, the "lone space" token you met in the tiktokenizer tour. GPT-4 kept the same order (computed from encoder.json; the GPT-4 exercise measures a → 64, space → 220, byte 0 → 188).

What encode() does to a string

The byte_encoder detour. OpenAI's BPE code works on Unicode strings, not integers. Its docstring says the code "barfs on" whitespace and control characters, and vocab.bpe itself uses a space to separate the two halves of each merge. So bytes_to_unicode() gives each of the 256 bytes a visible stand-in character: the 188 printable ones keep their own character, and the other 68 get a character from 256 upward. Space (byte 32) becomes Ġ (code point 288) and newline becomes Ċ. Karpathy calls this layer a "spurious implementation detail" (1:14:59 chapter) and skips it. The only lasting trace is the id order from the Predict box above.

Special tokens: ids that BPE never makes

A special token is an id added on top of BPE. No merge produces it; code inserts it. GPT-2 has exactly one, <|endoftext|> = 50256, which goes between documents in the training data. It has no built-in meaning: the model learns, from seeing it between documents during training, that what follows is unrelated to what came before. tiktoken handles specials in its own code, outside BPE. Measured with tiktoken's gpt2 encoding on '<|endoftext|>hello world'. OpenAI's own encoder.py has no special-token code, so it always gives the first row.

The default raises for a safety reason. If user-typed text could become 50256, anyone could forge a document boundary in the middle of a prompt. So you have to say explicitly which specials may be parsed.

GPT-4 has more. The cl100k_base encoding keeps <|endoftext|> and adds four:

idstokenwhat it's for
0 – 100255100,256 BPE tokens256 bytes + 100,000 merges
100256unusedno token has this id
100257<|endoftext|>document boundary, as in GPT-2
100258 – 100260<|fim_prefix|> <|fim_middle|> <|fim_suffix|>fill in the middle: train on (prefix, suffix) → middle, so a code model can fill a gap (FIM paper)
100261 – 100275unused15 empty ids
100276<|endofprompt|>not documented
n_vocab = 100,256 BPE + 5 special + 16 unused (1 + 15) = 100,277

Chat models go further: Karpathy shows tokens such as <|im_start|> and <|im_end|> that wrap each message in a conversation. You can fork cl100k_base in tiktoken and register your own specials the same way.

Adding a token means model surgery. A new id needs a new row in the token embedding table and a new output in lm_head (the final layer that scores every token). On gpt.py's shape, with GPT-2's vocab, the vocab-size lab measures:

embedding (50257, 384) -> (50258, 384) lm_head (50257, 384) -> (50258, 384) old rows unchanged: True old logits unchanged: True rows with nonzero grad: [50257] ← only the new token learns

From labs/vocab-size-new-tokens.py (384 is gpt.py's embedding width). The full story, including freezing the rest of the model, is on the vocabulary-size card.

Why a reserved id beats the alternatives

✗ A blank line as separator

Blank lines appear inside documents all the time, so the model can't tell "new paragraph" from "new, unrelated document".

✗ The marker as plain text

<|endoftext|> spelled out is 7 ordinary tokens (27, 91, 437, 1659, 5239, 91, 29) that could also turn up in real text, such as this card.

✗ Parse specials from any input

Then a user who types the marker injects a real 50256 into your prompt. That's why tiktoken and minbpe raise by default.

✓ A reserved id outside BPE

50256 sits past every merge id (256–50255), so text can never become it by accident. Only your code adds it, and it costs one embedding row and one lm_head output.

Is encoder.py how GPT-2's tokenizer was trained?

No. encoder.py only uses a finished tokenizer (encode and decode). OpenAI never released the training code, and Karpathy points to signs of extra, undocumented rules. For example, GPT-2 never merged runs of spaces (each one stays 220) even though the regex hands whole runs to BPE. So you can reproduce GPT-2's ids exactly, but not the training run that produced them.

Don't use encoder.py in real code either: tiktoken gives the same ids (both give the same 300 tokens for the Colab example string, checked) and does the work in Rust. Read encoder.py to connect names to what you built. To train your own vocabulary, use minbpe or sentencepiece.

Understand and remember

  • encoder.json is the vocab (inverted) and vocab.bpe is the merge list in rank order, with merge #r → id 256 + r → bpe()'s min-rank loop is our encode → load the two files and you reproduce GPT-2's ids exactly (300 tokens on the Colab string)

5 · Predict commit to an answer before revealing

You append <|im_start|> to GPT-2 as id 50257 with a small random embedding row and don't train yet. For the prompt 'hello world', do the logits of the old 50,257 tokens change? Do their probabilities change?

Reveal

The old logits are identical (the lab measures old logits unchanged: True): the old rows of lm_head didn't change and the input ids don't use the new row. The probabilities do change slightly, because softmax divides by a sum that now includes one more term, exp(new logit), so every old probability shrinks a little. Until you fine-tune, the new token gets a small, arbitrary share of probability.
