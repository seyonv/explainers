The quirks, explained

Also called: tokenization weirdness, tokenizer footguns, glitch tokens. Lecture 8 · revisiting and explaining the quirks of LLM tokenization · 1:51:41

Prime · 2 minutes before you read

The problem: LLMs miscount letters, fumble arithmetic, cost more in Korean, and derail on a stray space or a strange word. Without knowing what the model actually receives, these look like random flaws of "intelligence" that you can't predict or work around.

Where it fits: This is the payoff of the whole lecture. You've built BPE, the regex pre-split, special tokens and the vocab-size trade-off; now each of Karpathy's opening list of weird behaviours gets traced back to one of those pieces.

In one breath: most of the odd things LLMs do with spelling, arithmetic, Korean, Python or a stray space come from one fact: the model never sees characters, only a list of token ids that a separately trained tokenizer produced. Once you know how the tokenizer cut the text, each quirk stops being mysterious.

Predict first: GPT-4's tokenizer (cl100k_base) reads .DefaultCellStyle. How many tokens does the model receive, and how many letter ls can it see?

One token (id 98518), and zero visible ls. The whole 17-character string is a single vocabulary entry, so the model gets one integer. The four ls are hidden inside it; the model only "knows" them if training happened to teach it how that id is spelled. In the video, GPT-4 counted three.

Arithmetic: how GPT-2 cuts four-digit numbers

Every number from 1000 to 9999 (9,000 of them), encoded on its own. A human adds column by column; GPT-2 gets whatever chunks the merges made.

gpt2 splitshare of the 9,000 numberscount 2 + 264.5%5,807 1 + 328.2%2,538 3 + 16.0%538 4 (one)1.0%88 1 + 2 + 10.3%29
5,807 + 2,538 + 538 + 88 + 29 = 9,000 cl100k (GPT-4): 9,000 of 9,000 split 3 + 1 (1275 → 127|5, 8041 → 804|1)

Computed with tiktoken over range(1000, 10000). GPT-4's regex caps number chunks at 3 digits, so its splits are at least consistent, though still not aligned to place value. Llama 2's sentencepiece tokenizer splits every digit (split_digits).

cl100k ids, computed. In training text, a space after : usually arrives glued to the next word, as in ␣Oh. A prompt that ends with a bare 220 puts the model somewhere it has rarely been, and the next token must be a space-less word. The completion playground Karpathy tried (gpt-3.5-turbo-instruct) shows a warning for exactly this.

SolidGoldMagikarp: a token nobody trained

An embedding is the table of learned vectors the model looks up, one row per token id. The tokenizer's data had enough of a Reddit username to earn it a merge, but the LLM's data (per the lecture) never contained it, so row 43453 was never trained. Karpathy likens feeding it to reading "unallocated memory" (in the 1:51:41 chapter): the model sees a vector it never learned to read, and replies with evasions, hallucinations or insults.

import tiktoken
gpt2 = tiktoken.get_encoding('gpt2')
cl = tiktoken.get_encoding('cl100k_base')
def show(enc, s):  # plain text: special tokens are not parsed
    ids = enc.encode(s, disallowed_special=())
    return f'{len(ids)} tokens, last {ids[-4:]}'
for w in [' SolidGoldMagikarp', 'SolidGoldMagikarp']:
    print(f'gpt2 {w!r:21}', gpt2.encode(w))
p = "Here's a tagline for an ice cream shop:"
print('prompt      :', show(cl, p), '| " Oh" =', cl.encode(' Oh'))
print('prompt + " ":', show(cl, p + ' '))
print('eot as text :', show(gpt2, '<|endoftext|>'))
ids = cl.encode('DefaultCellSta')
print('partial     :', ids, [cl.decode([i]) for i in ids])

What to use, per the final recommendations

✗ Train a vocab with default settings

sentencepiece has a "million settings", and the defaults can crop long sentences or normalise text you wanted kept. If you must train one, copy Meta's Llama 2 configuration.

✗ Parse special tokens in user text

Anyone who types <|endoftext|> then controls your end-of-text marker. Keep specials out of untrusted input; tiktoken raises an error unless you pass allowed_special.

✗ Drop the tokenizer, feed bytes

The dream, but raw bytes make sequences several times longer, and tokenizer-free models (such as MEGABYTE) were still research when the lecture was made.

✓ Reuse GPT-4's tokens via tiktoken

Efficient, well tested, and spaces, numbers and code are already handled. To train your own, use BPE; minbpe is the readable "tiktoken with training code".

Recommendations from 2:10:20. Karpathy promises "eternal glory" to whoever can delete tokenization.

Is every LLM mistake a tokenization problem?

No. The table explains why these specific failures are likely, not that tokenization is the only cause. A model can still spell DefaultCellStyle if training taught it the letters of id 86662, and a model with digit-by-digit numbers can still get sums wrong. Treat the tokenizer as the first thing to check, by printing the token ids, not the last word.

Several counts here also differ from the video: tiktoken 0.14 gives 4 tokens for "Hello how are you" where the video showed 5, and the JSON/YAML record is a small illustrative one, not the video's data. The direction of each gap is the same.

1 · Core model what to internalise, what to just look up

Keep it if it changes what you can explain, predict, compare, choose, build or debug. Otherwise it's reference.

Understand and remember

  • The model's input is token ids, not characters → a long token like .DefaultCellStyle (98518) is one embedding row → its letters aren't in the input → spelling, counting and reversal fail unless the text is first spelled out one letter per token
  • BPE merges follow the tokenizer's training text → frequent text (English, common digit pairs) gets long tokens, rare text (Korean) gets short ones → more tokens for the same meaning and digit chunks that don't line up with place value → bloated context and shaky arithmetic
  • The tokenizer and the LLM are trained on different data → a token frequent in the first but absent from the second (␣SolidGoldMagikarp, 43453) never appears in a batch → its embedding row gets no gradient → feeding it gives the model a vector it never learned to read
  • The space usually belongs to the next token (␣Oh = 8840) → a prompt ending in a lone 220, or cut mid-token (DefaultCellSta), is a sequence the model rarely saw in training → strange continuations or an immediate stop
  • detail that matters Special tokens are matched as strings before BPE → if user text is parsed for them, typing <|endoftext|> inserts the real id 50256 → so tiktoken refuses by default and you opt in with allowed_special

Reference only

  • the exact ids: 98518, 86662, 43453, 8840, 220, 50256
  • the GPT-2 four-digit split shares (2+2 64.5%, 1+3 28.2%, …)
  • tiktoken's disallowed_special=() / allowed_special arguments
  • the JSON vs YAML token counts for any one record
  • sentencepiece's split_digits option name

3 · Retrieve from memory, card closed
  1. concept Explain why an LLM can fail to count the letters of a word it can use perfectly well in a sentence.
    Check
    • the word may be one token, so the model receives one id, not its letters
    • using the word only needs its meaning; counting needs its spelling, which must be memorised per id
    • spelling it out with spaces gives one token per letter (16 tokens for DefaultCellStyle)
  2. mechanism Walk through what happens when a user prompt ends with a space: what the tokenizer emits, what the model has usually seen at that position, and what it has to produce next.
    Check
    • the prompt ends in the lone space token 220
    • in training, a space after : almost always came glued to the next word (␣Oh = 8840)
    • the model must now continue with a space-less token (Oh = 12174) after a bare 220, a rare pattern
    • result: worse or odd completions, hence the warning
  3. mechanism Walk through how ␣SolidGoldMagikarp ended up as one GPT-2 token whose embedding is useless.
    Check
    • it was frequent in the tokenizer's training text (a Reddit username), so BPE merged it into id 43453
    • the LLM's training text didn't contain it, so id 43453 never appeared in a batch
    • embedding rows only get gradient from tokens in the batch, so the row stayed as initialised
    • at inference the model reads an untrained vector
  4. tradeoff You're choosing a tokenizer for a new model that must do arithmetic and serve Korean users. What would you take from GPT-4 and Llama 2, and what does each choice cost?
    Check
    • numbers: cap chunks at 3 digits (GPT-4) or split every digit (Llama 2's split_digits); digits give consistent place value but longer sequences
    • Korean: include enough Korean in the tokenizer's training text so it earns merges, at the cost of vocabulary slots for other text
    • a bigger vocabulary shortens sequences but grows the embedding and lm_head
    • keep the tokenizer's and the LLM's training data aligned to avoid untrained tokens

4 · Compare against what you already know

vs What tokens look like: The tour showed odd splits (numbers, Egg/egg, Korean, indents); this card explains the resulting behaviours. For the number splits, what is the observation, what design choice causes it, and how did GPT-4's tokenizer change the failure rather than remove it?

Check
  • observation: 677 is one token but ␣677 is ␣6|77
  • cause: BPE merges frequent digit pairs, with no notion of place value
  • GPT-4's regex caps chunks at 3 digits and splits off the space, so 4-digit numbers always go 3+1
  • consistent, but still not aligned with columns; per-digit splitting (Llama 2) is the stronger fix

vs How big should the vocabulary be?: Adding a new token by model surgery vs a SolidGoldMagikarp-style glitch token: both start with an untrained embedding row. What makes one useful and the other harmful?

Check
  • surgery: you add the row and train on data containing it, so it gets gradient (only row 50257 did in the lab)
  • glitch token: the row exists but the LLM's data never contains the token, so it never trains
  • failure mode of surgery: too little fine-tuning data leaves the new row near its initialisation, the same problem at a smaller scale

5 · Predict commit to an answer before revealing

GPT-2 spends a token on almost every indent space. If your Python used tabs instead of 4 spaces, predict how many GPT-2 tokens \t\tprint(i) takes compared with print(i) (8 spaces), and what else changes about the print token.

Reveal

6 tokens vs 11. Each tab is one token (197), while 8 spaces become seven 220s with the eighth space glued to ␣print (3601). The catch: after a tab there is no space to glue on, so print becomes a different id (4798). The same keyword now has two ids depending on the indent style, and the model must learn both.
