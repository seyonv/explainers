How big should the vocabulary be?

Also called: choosing vocab_size, extending the vocabulary, model surgery. Lecture 8 · how to set vocabulary set? revisiting gpt.py transformer · 1:43:27 · training new tokens, example of prompt compression · 1:48:11

Prime · 2 minutes before you read

The problem: Training a tokenizer only asks you for one number, vocab_size, and nothing in BPE says when to stop merging. Pick too few and sequences stay long; pick too many and the model grows, slows down and gets rows it never learns. And once a model is trained, you still need a way to add tokens without breaking it.

Where it fits: The train-loop card made vocab_size the number of merges plus 256. This card goes back to the GPT lecture's gpt.py and finds where that same number shows up inside the model: the token embedding table and lm_head.

In one breath: inside the GPT from the previous lecture, the vocabulary size touches exactly two layers: the token embedding table (one row per token id) and lm_head, the final layer that scores every id as the next token. A bigger vocabulary packs more text into each position, but it makes those two layers bigger and slower, and it spreads the training data across more rows. Adding a token later means growing both layers by one row and training only the new row.

Predict first: gpt.py has 10.79M parameters with its 65-character vocabulary. Keep every other setting and swap in GPT-2's 50,257 tokens. Roughly how many parameters now, and what share sits in the two vocabulary layers?

49.39M, and 78.3% of them are in the embedding table and lm_head. The rest of the model (positions, 6 Blocks, the final LayerNorm) stays at 10,738,944 whatever the vocabulary is. Each extra token id costs 769 parameters: 384 in its embedding row and 385 in lm_head.

Karpathy names three costs of turning the knob up (1:43:27):

  • Compute. lm_head computes one dot product per id at every position, and softmax then normalises over all V of them, so its cost grows in step with V.
  • Undertrained rows. An embedding row gets a gradient only on steps where its token is in the batch. More ids means each one appears less often; in the table, 39,023 GPT-2 rows would never be updated at all.
  • Too much per token. The same 6 Blocks run once per position, whether it holds 1 character or 3.7. Squeeze too much text into one token and the model gets too little computation to process it.

His read of the state of the art: vocabularies in the high tens of thousands, around 100,000.

▶ Build itruns on your M3 · under 10 s

When: first find vocab_size in your gpt.py (its definition at L27, then the two layers at L143 and L147). Then pause the video at 1:48:11 and add one new token to a GPT-2-sized model before watching on.

import torch, torch.nn as nn
n_embd, vocab_size = 384, 50257   # gpt.py width, GPT-2 vocab
token_embedding_table = nn.Embedding(vocab_size, n_embd)
lm_head = nn.Linear(n_embd, vocab_size)
new_emb = nn.Embedding(vocab_size + 1, n_embd)  # one more row
new_head = nn.Linear(n_embd, vocab_size + 1)    # one more logit
with torch.no_grad():                           # keep the old rows
    new_emb.weight[:vocab_size] = token_embedding_table.weight
    new_head.weight[:vocab_size] = lm_head.weight
    new_head.bias[:vocab_size] = lm_head.bias
x = torch.randn(1, n_embd)                      # any hidden state
print('old logits unchanged:',
      torch.allclose(new_head(x)[:, :vocab_size], lm_head(x)))
mask = torch.zeros(vocab_size + 1, 1); mask[vocab_size] = 1
new_emb.weight.register_hook(lambda g: g * mask)  # freeze old rows
new_emb(torch.tensor([5, vocab_size])).sum().backward()
print('rows with nonzero grad:',
      new_emb.weight.grad.abs().sum(1).nonzero().flatten().tolist())

You should see (measured on your M3):

old logits unchanged: True
rows with nonzero grad: [50257]

The hook multiplies the embedding's gradient by a mask that is 1 only on the new row, so a batch that uses old token 5 still leaves row 5 untouched. Freezing the rest of the model works the same way (or with requires_grad = False).

New tokens after training

Fine-tuning a base model into a chat assistant usually needs new special tokens, such as markers for where a turn starts and ends. That's the surgery above: the old rows keep everything they learned, the new row starts out random, and you can train only the new rows while the rest stays frozen. The same idea goes further:

IdeaWhat gets new rowsWhat is trained
Special tokensOne row per new marker (chat turns, tool calls)the new rowsoptionally the whole model too
Gist tokensA few new ids that stand in for a long promptonly their embeddingsthe model is frozen, the prompt is distilled into them
Images, video, audioA new input domain chopped into patchesa tokenizer for that domaininteger codes (vector quantization) or soft vectors; the Transformer stays the same

Karpathy's point at 1:49:58: keep the Transformer and tokenize the new input domain. Its architecture barely changes.

Why it beats the alternatives

✗ Tiny vocabulary (characters, bytes)

Cheap output layer, every row trained. But one character per position: a 256-position context holds 256 characters instead of about 845.

✗ As big as possible

lm_head grows with V, most rows see few or no examples (39,023 of GPT-2's rows never appear in Tiny Shakespeare), and each position has to digest too much text.

✗ Retrain the tokenizer to add a token

New merges change how the text splits and which id means what, so every row the model learned now points at the wrong string. You'd be retraining from scratch.

✓ Tens of thousands, grown by surgery

Around 50k–100k ids balances sequence length against the cost of the two vocab layers. New tokens are extra rows appended at the end, so nothing the model learned moves.

So is there a right number?

No formula gives one: it's an empirical hyperparameter. The trade-off moves with the model. At gpt.py's size, GPT-2's vocabulary would be 78% of the parameters. In a much wider and deeper model the body dominates, so the same vocabulary is a small share and more ids become affordable. Your data matters too: 77.6% of GPT-2's ids never appear in Shakespeare, which is why the GPT lecture's 65 characters were the sensible choice there.

A larger vocabulary is not the right tool when the data is small or narrow, or when a model must handle a language the tokenizer barely saw. There, more merges mostly add rows that stay untrained, which is the root of the SolidGoldMagikarp quirk.

Understand and remember

  • The body only ever sees vectors of width C = 384 → V appears only in the embedding table (V × C) and lm_head (C × V + V) → each extra id costs 2C + 1 = 769 parameters → at gpt.py's size, GPT-2's 50,257 ids make those two layers 78.3% of the model
  • lm_head scores every id at every position and softmax normalises over all of them → its compute grows in step with V (24,960 → 19,298,688 multiply-adds per position going from 65 to 50,257)
  • An embedding row only gets a gradient when its token is in the batch → more ids means each is seen less often → rare rows stay undertrained (39,023 of GPT-2's ids never appear in Tiny Shakespeare's train split) → untrained rows behave unpredictably when they do show up
  • More text per token → fewer positions (3.30 characters per GPT-2 token, so a 256 context holds about 845 characters) → but the same fixed compute runs once per position → too much text per token leaves the model too little computation per character
  • detail that matters New ids are appended at the end and old rows are copied → every old logit is computed from the same weights → the model's behaviour on old text is unchanged, and masking the gradient trains only the new row (the lab: rows with nonzero grad: [50257])
  • detail that matters Weight tying shares one V × C matrix between the embedding and lm_head → the vocab cost is paid once, not twice → real GPT-2 is smaller than gpt.py's shape with 50,257 ids

5 · Predict commit to an answer before revealing

You add a new chat token as row 50257 and fine-tune, but by mistake the token never appears in your fine-tuning data. Afterwards a user's message contains it. What does the model receive for it, and what happens to its lm_head row during fine-tuning?

Reveal

The model receives the new row's random embedding, because that row never got a gradient: embedding rows only update when their token is in the batch. Its lm_head row does get a gradient every step, but only one that pushes its score down, since it is never the right answer. So the model never predicts it, and reading it feeds in an untrained vector with unpredictable effects. That's the same mechanism as SolidGoldMagikarp on the quirks card.
