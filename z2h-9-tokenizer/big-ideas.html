The six big ideas of the GPT tokenizer

Big idea 1: The model never sees text, only a list of token ids

A separately trained tokenizer cuts text into chunks and swaps each chunk for an integer. The LLM looks that integer up in its embedding table, so whatever is inside a chunk, such as its letters, is invisible to it.

“a lot of weird behaviors and problems of LLMs actually trace back to tokenization” · Karpathy, 0:00:00

Why it matters: When an LLM fumbles letters, digits or a foreign language, print the token ids before blaming the network. The quirks card traces each failure on Karpathy's list to how the text was cut.

Big idea 2: Start from UTF-8 bytes, then compress them

Unicode code points make a vocabulary of about 150,000 that keeps growing; raw UTF-8 bytes make a tiny vocabulary of 256 but long sequences. GPT tokenizers keep the bytes as the base and merge frequent runs of them.

“the Unicode standard is very much alive” · Karpathy, 0:14:56

Why it matters: Starting from bytes means nothing is ever unknown: any string encodes, unlike the GPT lecture's 65-character vocabulary. And 3.30× fewer positions means a fixed context holds 3.30× more text.

Big idea 3: BPE is one greedy move, repeated: merge the most common pair

Count every neighbouring pair, mint a new id for the most frequent one, replace it everywhere, and repeat. Each round adds one vocabulary entry and shortens the sequence; the list of merges is the tokenizer.

“a binary forest” · Karpathy, 0:34:58

Why it matters: Every production tokenizer you meet later (GPT-2's 50,000 merges, GPT-4's 100,000, Llama 2's sentencepiece) runs this same loop, longer and on more text. The training-loop card has you write the loop yourself.

Big idea 4: The tokenizer is a separate stage, trained once on its own text

BPE is counting, not gradient descent, so it is trained first and frozen. After that it is only a translator: encode replays the merges in the order they were learned, and decode glues each id's bytes back together.

“it is a completely separate stage” · Karpathy, 0:39:20

Why it matters: The LLM's loss can't change a merge, and a token common in the tokenizer's text but absent from the LLM's keeps an untrained row. Encode and decode are the whole interface between the two stages.

Big idea 5: Real tokenizers are BPE plus hand-written rules

GPT-2 and GPT-4 first cut the text into chunks of letters, digits, punctuation or spaces with a regex and run BPE inside each chunk, and they reserve special ids, like <|endoftext|>, that no merge can make.

“none of this is documented” · Karpathy, 1:11:38

Why it matters: Matching GPT-4 exactly needs every rule: its regex, its 100,000 merges, its shuffled byte order and its specials. The GPT-4 exercise gets all 14 ids of the test string right; skip the byte shuffle alone and you get 41.

Big idea 6: Every vocabulary entry is a row the model must pay for and train

vocab_size only touches the embedding table and lm_head. A bigger vocabulary packs more text into each position, but those two layers grow, and rare tokens get too few updates; a token the LLM never saw keeps a random row.

“unallocated memory” · Karpathy, 1:51:41

Why it matters: GPT-2 in the next lecture pays the V × C cost once by sharing one matrix between the two layers (weight tying), and adding chat tokens later is just the model surgery on the vocabulary card.

1 · Core model what to internalise, what to just look up

Keep it if it changes what you can explain, predict, compare, choose, build or debug. Otherwise it's reference.

Understand and remember

  • The LLM's input is a list of ids → each id is one embedding row → the characters inside a token are not in the input → spelling, letter counting, reversal and digit-by-digit arithmetic depend on how the text was cut
  • Code points give ≈150,000 ids that grow with each Unicode release; raw bytes give 256 ids but 3.30× more positions than GPT-2 tokens → keep UTF-8 bytes as the base (nothing is ever unknown) → merge frequent byte runs to win the length back
  • Count adjacent pairs → mint an id for the most frequent → replace it everywhere → repeat → the vocabulary grows by 1 and the sequence shrinks each round, with ever-rarer pairs (616 → 596 for "e "; 24,597 → 19,438 after 20 merges) → the ordered merge list is the tokenizer
  • Merges come from counting the tokenizer's own training text, then freeze → encode replays them lowest index first and decode joins bytes → text rare in that training set stays about one token per byte, and a token absent from the LLM's text keeps an untrained row (SolidGoldMagikarp)
  • detail that matters The regex split forbids merges across letters, digits, punctuation and spaces → worse raw compression (Taylor Swift: 87,339 vs 78,746 tokens) → but a vocabulary spent on words and numbers instead of e␣ or citation boilerplate
  • detail that matters vocab_size appears only in the embedding table and lm_head → each extra id costs 2C + 1 = 769 parameters at C = 384 → at gpt.py's size, GPT-2's 50,257 ids would be 78.3% of the model

Reference only

  • GPT-2 vocab 50,257 = 256 + 50,000 + 1; cl100k n_vocab 100,277
  • <|endoftext|> = 50256 in GPT-2, 100257 in cl100k
  • the GPT-2 and GPT-4 regex strings, and tiktoken's allowed_special
  • sentencepiece options: byte_fallback, character_coverage, split_digits, add_dummy_prefix
  • GPT-4's byte shuffle and recover_merges

  1. concept Explain, without code, why the tokenizer can be the cause of a model failing to count the l's in .DefaultCellStyle, even though the model is otherwise very capable.
    Check
    • in cl100k the whole string is one id, 98518
    • the model receives one embedding row, not letters
    • it only knows the spelling if training happened to teach it what that id spells
  2. mechanism Walk through what encode("the ") does with the 20 merges trained on the blog post, round by round, and say why the result is a single id.
    Check
    • bytes t h e ␣ = 116, 104, 101, 32
    • pairs th (259) and e␣ (256) are both learned; the lowest index, 256, fires first
    • then th → 259, leaving [259, 256]
    • (259, 256) is merge 275, so the result is [275] and the loop stops at one token
  3. tradeoff A team wants a tokenizer that compresses its multilingual chat logs better. They can add merges (bigger vocab_size) or change the tokenizer's training text. What does each option buy, and what does each cost the LLM?
    Check
    • more merges: more text per position, but the embedding table and lm_head grow by V × C each, and rare ids get few updates
    • changing the training mix: languages that are dense in the tokenizer's text get merges and shorter sequences
    • either way the ids change, so a model trained on the old tokenizer can't read the new ids without retraining
  4. mechanism Why do minbpe, GPT-2's encoder.py and tiktoken decode by joining all the bytes first and then calling .decode("utf-8", errors="replace")?
    Check
    • tokens are byte runs, so one character can be split across two tokens (’ = 263 + 153)
    • joining first rebuilds split characters before decoding
    • the model can emit any id, e.g. a lone byte 128, which isn't valid UTF-8; replace turns it into � instead of crashing

4 · Compare against what you already know

vs Counting bigrams in a 27×27 tensor: The bigram model and BPE both start by counting adjacent pairs. What does each one do with the counts, and which design choice makes one a language model and the other a compressor?

Check
  • bigram: normalises each row of counts into next-character probabilities and samples from them
  • BPE: takes only the single most frequent pair, replaces it with a new id and recounts
  • bigram predicts the next symbol; BPE rewrites the sequence to be shorter
  • both are learned by counting, not by gradient descent, so both are fixed by their training text

vs Characters to integers, and a held-out 10%: The GPT lecture's tokenizer was stoi over 65 characters. What is fundamentally different about byte-level BPE, when would you still pick characters, and how does each one fail?

Check
  • characters: no training step, 1 token per character, and any unseen character (é) can't be encoded
  • byte-level BPE: 256 byte base, so anything encodes, plus learned merges: 3.30 characters per GPT-2 token on Shakespeare
  • pick characters for a tiny single-text demo (65 rows, nothing to go wrong)
  • BPE fails in the quirks: hidden letters, arbitrary digit chunks, untrained rows

vs Token and position embeddings: In the GPT lecture the embedding table had 65 rows. What changes in that layer and in lm_head when the tokenizer's vocabulary becomes 50,257, and what doesn't change?

Check
  • both layers get one row or output per id: 50,257 × 384 = 19,298,688 numbers each (plus V biases in lm_head)
  • the Blocks between them see only width-384 vectors and never learn V
  • rows for ids rare in the data get few gradient updates; lm_head's compute per position grows with V

5 · Predict commit to an answer before revealing

GPT-2 tokenizes " SolidGoldMagikarp" as the single id 43453, whose row was barely trained. Commit first: how many tokens does GPT-4's cl100k_base make of the same string, and does that make GPT-4 immune to glitch tokens in general?

Reveal

5 ordinary tokens: ' Solid', 'Gold', 'Mag', 'ik', 'arp' (ids 22925, 26509, 34015, 1609, 8035, computed with tiktoken). GPT-4's tokenizer was trained on different text, so this username never earned a merge. That fixes this one string, not the cause: any token that is frequent in the tokenizer's training text but rare in the LLM's still ends up with an undertrained row. The cure is matching the two data sets, not a bigger vocabulary.

Hint

Every token sits inside one chunk, so tokens ≥ chunks. A chunk becomes several tokens when no merge covers all of it, which happens most for text the tokenizer's training set had little of.
