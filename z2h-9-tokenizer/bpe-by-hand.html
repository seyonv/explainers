Byte pair encoding by hand

Also called: BPE, byte-level BPE, the Wikipedia toy example. Lecture 8 · Byte Pair Encoding (BPE) algorithm walkthrough · 0:23:50

Prime · 2 minutes before you read

The problem: Raw bytes give a tiny vocabulary of 256 but make every text long (the lecture's paragraph: 533 characters, 616 bytes). A vocabulary of every code point or every word is huge and still misses things. You need short sequences without losing the ability to encode any text at all.

Where it fits: The unicode-utf8 card turned text into a list of bytes, ids 0–255. BPE starts from exactly that list and adds new tokens one merge at a time. The next cards turn this pencil procedure into code (get_stats, merge, the training loop).

  3. At round 2, Za and ab are tied at 2. What decides the winner, and does the choice change the final ids for this string?

In one breath: byte pair encoding (BPE) shortens a sequence by repeating one move. Find the pair of neighbouring symbols that appears most often, invent a new symbol for it, and replace every occurrence. Each round adds one entry to the vocabulary (the set of symbols a token can be) and makes the sequence shorter. The list of merges you made is the tokenizer.

Predict first: in aaabdaaabac, counting neighbouring pairs finds aa 4 times. If you replace aa with a new symbol Z, how many symbols shorter does the 11-symbol string get?

Only 2 shorter: 11 → 9. Each aaa holds two overlapping aa pairs (positions 1–2 and 2–3), so the count is 2 + 2 = 4. But a replacement uses up both of its letters. Scanning left to right, aaa becomes Za: one replacement per run, two in total. So aaabdaaabac becomes ZabdZabac.

Three merges on the Wikipedia example

This is the example Karpathy walks through from Wikipedia's BPE article. Start with 11 symbols over a vocabulary of 4 letters, {a, b, c, d}. Each round: count every neighbouring pair, pick the most frequent, and mint a new symbol for it. Green chips are symbols that didn't exist a round earlier.

Counts from labs/bpe-by-hand.py, which uses the same get_stats and merge as the lecture. Round 3 merges a merged symbol again, so X stands for four letters.

To undo it, keep the merge list and expand it in reverse: X → ZY → aa ab. The short sequence plus the merge table gives back the original exactly. That's why the merge table, not the compressed text, is what a tokenizer saves.

The same thing with bytes, as minbpe does it

Real tokenizers run BPE on UTF-8 bytes, not letters (the unicode-utf8 card). All 256 byte values are tokens from the start: a=97, b=98, c=99, d=100. So new tokens get the ids 256, 257, 258 and so on. Here, vocab_size = 256 + 3 means 3 merges.

bytes : [97, 97, 97, 98, 100, 97, 97, 97, 98, 97, 99] merges : {(97, 97): 256, (256, 97): 257, (257, 98): 258} encoded : [258, 100, 258, 97, 99] = "aaab" d "aaab" a c

Round 2 ties (256, 97) ("Za") with (97, 98) ("ab"), both 2. Python's max(stats, key=stats.get) returns the tied pair it met first in the string, which is Za. Wikipedia picked ab. On this string both paths end at [258, 100, 258, 97, 99], the result in minbpe's README.

▶ Build itruns on your M3 · under 1 s

When: pause the video at 0:23:50. First do the three rounds on paper, writing the pair counts at each step. Then clone minbpe and run this from its folder to check the byte version.

from minbpe import BasicTokenizer
tokenizer = BasicTokenizer()
text = "aaabdaaabac"
tokenizer.train(text, 256 + 3)   # 256 byte tokens, then 3 merges
ids = tokenizer.encode(text)
print('bytes:', list(text.encode("utf-8")))
print('merges:', tokenizer.merges)
print('encoded:', ids)
print('tokens:', [tokenizer.vocab[i] for i in ids], '->',
      tokenizer.decode(ids))

You should see (measured on your M3; the lab prints the same four lines):

bytes: [97, 97, 97, 98, 100, 97, 97, 97, 98, 97, 99]
merges: {(97, 97): 256, (256, 97): 257, (257, 98): 258}
encoded: [258, 100, 258, 97, 99]
tokens: [b'aaab', b'd', b'aaab', b'a', b'c'] -> aaabdaaabac

Why it beats the alternatives

✗ One token per code point

Unicode has about 150,000 characters (the video's figure), and the standard keeps adding more. That makes a huge vocabulary that is never finished, and most of its entries are rare.

✗ Raw UTF-8 bytes

A tiny vocabulary of 256 covers everything, but sequences get long: the lecture's paragraph is 533 characters and 616 bytes. The model can only look at a fixed number of tokens at once, and long inputs use that up.

✗ One token per word

The vocabulary has no natural size limit, and any word missing from it (a typo, a name, a new language) has no token at all.

✓ Byte pair encoding

It starts from the 256 bytes, so it can encode any text. Merges then add shortcuts only for patterns that are actually common. How many merges you do is a setting you choose: GPT-2 did 50,000.

Is BPE the best possible compression?

No. It's greedy: each round takes the pair with the highest count right now and never goes back. Ties are broken by whatever rule the code happens to use, as the Wikipedia vs minbpe split shows. The two merge lists compress aaabdaaabac equally well, but they will cut new text differently, because each tokenizer only knows the merges it made.

The count is also only a guide. Overlapping pairs inflate it, so aa scored 4 but could be replaced only twice. And plain BPE will happily merge across a space or between a letter and a digit. GPT-2 and GPT-4 therefore split text into chunks with a regex first (the regex-presplit card), and Llama's sentencepiece runs BPE on code points with a byte fallback instead of on bytes.

Understand and remember

  • Count every neighbouring pair → replace the most frequent with one new symbol → the vocabulary grows by exactly 1 while the sequence loses one symbol per replacement → common patterns get short and rare ones stay as single bytes
  • Start from all 256 byte values → any UTF-8 text can be encoded before a single merge → merges only add shortcuts → BPE never meets an unknown symbol, unlike a word vocabulary
  • Merges may reuse earlier merged symbols (X = ZY, 258 = 257 + b) → the merge list forms trees → one token can stand for a long byte string (aaab), and decoding just expands the tree back to bytes
  • Each round is greedy and ties are broken by an arbitrary rule (Wikipedia takes ab; Python's max takes the first pair seen, Za) → two tokenizers can compress the training text equally well → but they cut new text differently, because each only knows its own merges
  • detail that matters get_stats counts overlapping pairs, but merge scans left to right and uses up both symbols → in a run like aaa the count overstates the replacements (aa: counted 4, replaced 2) → the length drops by the number of replacements, not by the count

Reference only

  • ASCII byte values a=97, b=98, c=99, d=100
  • minbpe's BasicTokenizer API: train(text, vocab_size), encode, decode, save
  • vocab_size = 256 + num_merges
  • the letters Z, Y, X are just Wikipedia's names for the new symbols

5 · Predict commit to an answer before revealing

Take minbpe's toy tokenizer trained on aaabdaaabac (merges aa, then aa+a, then aaa+b). How many tokens does it produce for abab? And Wikipedia's version (Z=aa, Y=ab, X=ZY)?

Reveal

minbpe gives 4 tokens, [97, 98, 97, 98]: it never learned a merge for ab, because the tie at round 2 went to Za. Wikipedia's version gives 2 tokens, YY. Two tokenizers that compress the training string identically can disagree on new text. How to apply merges to new text is the encode card's problem.
