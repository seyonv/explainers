Decoding, and the invalid-byte trap

Also called: detokenization, ids → text, decode(). Lecture 8 · decoding tokens to strings · 0:42:47

Prime · 2 minutes before you read

The problem: Training gave you a list of merges and a model will give you a list of ids, but people read text. Without a decoder you can't see what the model said, and a naive decoder crashes the first time the model emits bytes that aren't valid UTF-8.

Where it fits: The training loop minted ids 256–275 as pairs of older ids. This card turns that merge table into vocab (id → bytes) and uses the UTF-8 rules from the code points card to explain when bytes are, and aren't, text.

In one breath: every token id stands for a fixed run of bytes, so decoding means looking each id up, gluing the bytes together, and reading the result as UTF-8 text. The trap is that not every run of bytes is valid UTF-8, and a language model can emit any id in any order. So a strict decode can crash, and errors="replace" turns the bad bytes into � instead.

Predict first: all 256 byte values are in the vocabulary, so every id has bytes behind it. Can decode([128]) fail?

Yes. With a plain .decode("utf-8") it raises UnicodeDecodeError: … can't decode byte 0x80 in position 0: invalid start byte. Byte 128 is 10000000 in binary. In UTF-8, a byte starting with 10 can only continue a character that an earlier byte started, and here nothing came before it. With errors="replace" you get '�' instead.

Step 1: build the vocab from the merges

Training (the previous card) gave us merges, a dict from a pair of ids to the new id minted for it, such as (101, 32) → 256. Decoding needs the reverse view, vocab: a dict from each id to the bytes it stands for. Ids 0–255 are the single bytes. Every merged id is the concatenation of its two parents' bytes. The loop walks merges in insertion order (Python dicts keep it, since 3.7), which is also the order the ids were minted, so both parents already exist when a child is built.

▶ Build itruns on your M3 · about 0.2 s

When: pause the video at 0:42:47, when decoding starts, and write decode yourself before watching on. It uses the merges dict from your training loop.

vocab = {idx: bytes([idx]) for idx in range(256)}
for (p0, p1), idx in merges.items():  # insertion order = merge order
    vocab[idx] = vocab[p0] + vocab[p1]

def decode(ids):
    tokens = b''.join(vocab[idx] for idx in ids)
    return tokens.decode('utf-8', errors='replace')
print('vocab[256], vocab[275]:', vocab[256], vocab[275])
print('decode([104, 105, 256, 275]):',
      repr(decode([104, 105, 256, 275])))
print('128 in binary:', format(128, '08b'))
try:                       # the version without errors=
    b''.join(vocab[i] for i in [128]).decode('utf-8')
except UnicodeDecodeError as e:
    print('strict decode([128]) ->', type(e).__name__ + ':', e)
print("decode([128]) with errors='replace':", decode([128]))
print("'👋' as bytes:", list('👋'.encode('utf-8')),
      '-> only the first 2:', repr(decode([240, 159])))

Why it beats the alternatives

✗ Strict .decode("utf-8")

Crashes on the first bad byte. One unlucky sample, such as [128], takes down the whole generation loop.

✗ errors="ignore"

Never crashes, but silently deletes the bad bytes: [104, 105, 128] decodes to 'hi', and nothing tells you the model emitted garbage.

✗ Decode each token, then join strings

Breaks characters that span tokens. 👋 sent as [240, 159] then [145, 139] becomes '���' (3 replacement characters), though all 4 bytes together are a valid 👋.

✓ Join all bytes, decode once, with errors="replace"

Characters split across tokens come out whole, and truly invalid bytes become a visible � instead of a crash. minbpe and OpenAI's GPT-2 encoder.py both do this.

Does a � mean the tokenizer is broken?

Usually not. The vocab is fine; the model sampled an id sequence that isn't valid UTF-8, and the decoder is showing you that honestly. Seeing � in LLM output points to the model's choices, not to decode.

Replace is the right choice for showing text to a person, but it is lossy. decode maps the different byte runs [128] and [240, 159] to the same '�', so encode(decode(ids)) can't get your ids back: the encoding card measures encode(decode([128])) = [239, 191, 189], the UTF-8 bytes of �. When you need the exact bytes (storing outputs, or streaming tokens one at a time), keep the joined bytes and decode only at the end, or use an incremental decoder that holds back an unfinished character until its remaining bytes arrive.

Understand and remember

  • each merged id = its two parents' bytes concatenated → built in merge order, both parents already exist → one pass over merges gives every id's bytes (vocab[275] = b'th' + b'e ' = b'the ')
  • tokens are byte runs, not characters → a character can be split across tokens (’ = 263 + 153) → join all bytes first, then decode once, or split characters turn into �
  • the model picks any id at every step → nothing forces valid UTF-8 → a lone continuation byte like 128 (10xxxxxx) or a cut-off emoji can appear → strict decode raises UnicodeDecodeError, so use errors="replace" and show �
  • replace maps many different bad byte runs to the same � → decode is lossy on invalid input → encode(decode(ids)) can't recover the ids ([128] comes back as [239, 191, 189])
  • detail that matters Half the base ids are fragments: all 128 bytes ≥ 128 fail to decode alone, and a learned merge can be a fragment too (263 = e2 80) → 129 of the 276 ids can't be printed on their own → streaming output must hold back bytes until a character completes (an incremental decoder)

Reference only

  • vocab = {idx: bytes([idx]) for idx in range(256)}, then vocab[idx] = vocab[p0] + vocab[p1]
  • b"".join(...) and .decode("utf-8", errors="replace")
  • Python dicts keep insertion order since 3.7
  • � is U+FFFD, UTF-8 bytes [239, 191, 189]
  • byte ranges: 0–127 ASCII, 128–191 continuation, 194–244 lead, 192, 193 and 245–255 never valid
  • minbpe basic.py L51–L55 and base.py _build_vocab; GPT-2 encoder.py also uses errors='replace'
