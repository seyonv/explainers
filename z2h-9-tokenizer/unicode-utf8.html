Code points, bytes, and why neither works raw

Also called: Unicode, character encodings, UTF-8 / UTF-16 / UTF-32, byte-level input. Lecture 8 · strings in Python, Unicode code points · 0:14:56

Prime · 2 minutes before you read

The problem: A neural network eats integers, and text isn't integers. The GPT lecture got away with 65 characters from one Shakespeare file, but real text has emoji, Korean, accents and code, and every choice of 'which integers' has a price in vocabulary size or sequence length.

Where it fits: The character tokenizer in the GPT lecture mapped each character to a row of the embedding table. This card looks at the two integer views of text Python already gives you, code points and UTF-8 bytes, and shows why GPT builds on bytes and then needs BPE.

In one breath: a Python string is a list of Unicode code points: one integer per character, which ord() shows you. UTF-8 writes each code point as 1 to 4 bytes (integers 0–255). Neither is a good token vocabulary on its own. Code points give a huge vocabulary that keeps growing, and raw bytes make every text several times longer than it needs to be. So GPT tokenizers start from UTF-8 bytes and then compress them with byte pair encoding (BPE, the next cards).

Predict first: "안녕하세요 👋 (hello in Korean!)" has 26 characters. How many bytes is it in UTF-8?

39 bytes. The 20 ASCII characters (English letters, digits, spaces, basic punctuation) take 1 byte each, each of the 5 Korean syllables takes 3, and the emoji takes 4: 20 + 15 + 4 = 39. The more a text strays from English, the more bytes each character costs.

One character, three levels

A byte is 8 bits, so it holds an integer from 0 to 255. A code point is the number Unicode assigns to a character; ord(c) returns it and chr(n) goes back. UTF-8 is the rule that turns a code point into bytes. s.encode("utf-8") applies it and list(...) shows the bytes as integers.

The grey prefix bits are UTF-8's bookkeeping. The first byte says how many bytes follow (0 = one byte, 110 = two, 1110 = three, 11110 = four), and every continuation byte starts with 10. The black bits, read in order, are the code point.

Take 안 apart. Strip the prefixes from 236, 149, 136 and you have 4 + 6 + 6 payload bits: 1100 010101 001000. As place values:

50504= (236−224)×4096first byte: 12 × 2¹² + (149−128)×64second: 21 × 2⁶ + (136−128)third: 8

Filled in: 49,152 + 1,344 + 8 = 50,504 = ord('안'). ASCII (the first 128 code points) keeps its 1-byte form exactly, which is why UTF-8 is called ASCII-compatible: plain English text is the same bytes in both.

Why it beats the alternatives

✗ Code points as tokens

No encoding step at all, but a vocabulary of about 150,000 that grows with every Unicode release, many of them characters the training data hardly contains.

✗ UTF-16 or UTF-32

Fixed-ish widths, but ASCII text is padded with zero bytes: 56 and 108 bytes for a string UTF-8 fits in 39. More length for nothing.

✗ Raw UTF-8 bytes

A tidy vocabulary of 256 that never changes, but text gets 3.30× longer than GPT-2 tokens, so a fixed context sees far less of it.

✓ UTF-8 bytes, then BPE

Keeps UTF-8's small, stable, universal base (any text encodes, nothing is ever unknown) and merges frequent byte runs into tokens to win the length back.

Could we skip tokenization and feed raw bytes?

Karpathy would like to (0:22:47). The obstacle is the length: attention gets expensive on sequences several times longer, so the Transformer itself has to change. MEGABYTE (2023) proposes a hierarchical Transformer that reads bytes in patches, and aims to "establish the viability of tokenization-free autoregressive sequence modeling at scale". In the lecture he says this isn't yet proven at the scale of frontier models, so for now every GPT uses a tokenizer.

A related trap: len(s) counts code points, not bytes, and not always what a reader would call one character. A flag emoji such as 🇺🇸 is 2 code points and 8 UTF-8 bytes.

1 · Core model what to internalise, what to just look up

Keep it if it changes what you can explain, predict, compare, choose, build or debug. Otherwise it's reference.

Understand and remember

  • Code points as tokens → one embedding row per character, about 150,000 and growing with each Unicode release → a vocabulary that is huge and never stable → rejected
  • UTF-8 spends 1 byte on ASCII and 2–4 on everything else → English stays compact and byte-identical to ASCII → but non-English text costs more bytes per character (Korean 3, emoji 4)
  • Raw bytes as tokens → vocabulary only 256 → every text becomes 1–4 positions per character (Shakespeare 3.30× longer than GPT-2 tokens) → a fixed context sees far less text and attention work grows with the square of length → compress the bytes with BPE instead
  • UTF-16/32 use fixed 2- or 4-byte units → ASCII gets padded with zero bytes (56 and 108 bytes vs UTF-8's 39) → more length for no information → UTF-8 is the base layer
  • detail that matters UTF-8's lead byte announces the length (0, 110, 1110, 11110) and continuation bytes start with 10 → a byte sequence can be invalid, such as a lone continuation byte or a cut-off emoji → decoding arbitrary token ids can crash, which is why decode needs errors="replace" (the decode card)

Reference only

  • ord(c) / chr(n), s.encode("utf-8"), list(b) to see bytes as ints
  • the code space ends at U+10FFFF (1,114,112 values); Unicode 15.1 has about 150,000 characters (per the video)
  • the byte-order mark Python's utf-16/utf-32 codecs prepend (255, 254, …)
  • UTF-16 surrogate pairs for code points above 65,535
  • unicodedata.unidata_version (13.0.0 in Python 3.10)
