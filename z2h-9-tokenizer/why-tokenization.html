Tokenization: the root of much LLM weirdness

Also called: tokenizing, text → token ids, the input representation. Lecture 8 · intro: Tokenization, GPT-2 paper, tokenization-related issues · 0:00:00

Prime · 2 minutes before you read

The problem: A Transformer only reads integers. Something has to turn arbitrary text (any language, emoji, code) into a short list of ids, and the choice of how to chop the text decides what the model can and can't see.

Where it fits: The GPT lecture used the simplest tokenizer possible: one id per character, 65 in all. This card is the first of the tokenizer lecture; it shows why real models replace that with about 50,000 byte-level BPE chunks, and lists the failures the rest of the course will trace back to it.

In one breath: a language model can't read text; it reads a list of integers called tokens. The tokenizer is the separate piece that turns text into those integers and back. In the GPT lecture each character was one token (65 of them). Real models like GPT-2 use about 50,000 multi-character chunks built by byte pair encoding (BPE), and many strange LLM failures come from how text got chopped into those chunks.

Predict first: tiny Shakespeare is 1,115,394 characters, so the GPT lecture fed the model 1,115,394 tokens. With GPT-2's 50,257-token vocabulary, how many tokens is the same text?

338,025 tokens, about 3.3 characters per token. The vocabulary got about 773 times bigger (50,257 / 65), but the sequence only got about 3.3 times shorter. Most tokens are short common pieces like " the", not whole sentences. In the GPT lecture Karpathy guessed "~300k tokens" (1:48:53); tiktoken measures 338,025.

Notice the space rides at the front of the word: " Citizen" is one token, with its space included. The model gets id 22307 and nothing else, so it never sees the letters C, i, t, i, z, e, n. That one fact is behind most of the symptoms below.

The embedding table is the lookup table from the GPT lecture: token id i picks out row i, a vector of n_embd = 384 numbers. Same text, same window, but BPE lets the model see about 3.3 times more of it, and the price is a far bigger table.

Why byte-level BPE beats the alternatives

✗ Characters seen in training

The GPT lecture's 65 symbols only cover Shakespeare. "café" crashes encode, because é isn't one of them, and every character costs one of the 256 window positions.

✗ Unicode code points

Covering every character needs over 130,000 base symbols before any merges, per the GPT-2 paper, versus the 32,000–64,000 vocabularies BPE usually uses. The standard also keeps growing.

✗ Raw UTF-8 bytes

Only 256 symbols and any string fits, but sequences get even longer than characters. The paper reports that byte-level models weren't competitive with word-level ones on large datasets.

✓ Byte-level BPE (GPT-2)

Start from the 256 bytes, so any string encodes ("café" → c, af, é), then add 50,000 learned merges for frequent chunks. That gives 3.30 characters per token on Shakespeare.

Is every LLM failure the tokenizer's fault?

No. The list above is things that trace back to tokenization; plenty of mistakes are the network's own. And a bigger vocabulary isn't strictly better. Each extra token adds a row to the embedding table and a column to the output layer, and a rare token's row gets few training updates (SolidGoldMagikarp is the extreme case). The vocabulary-size card covers that trade-off.

For a small demo like the GPT lecture, characters are the right tool: 65 rows, no training step, and nothing to go wrong. Deleting tokenization altogether means feeding raw bytes and changing the architecture to cope with the length. The MEGABYTE paper tries this, but Karpathy says it isn't yet proven at large scale.

1 · Core model what to internalise, what to just look up

Keep it if it changes what you can explain, predict, compare, choose, build or debug. Otherwise it's reference.

Understand and remember

  • The model sees only token ids → the characters inside a token are invisible to it → tasks that need individual letters (spelling, counting l's, reversing) get hard
  • Chunks instead of characters → 3.30 characters per GPT-2 token on Shakespeare → the same 256-token window holds about 845 characters instead of 256 → more context for the same attention cost
  • Start from the 256 byte values, then merge frequent pairs → every string encodes (no unknown characters, unlike the 65-character vocab) → while common chunks stay short sequences
  • vocab_size sets the rows of the embedding table and the width of the output layer → 50,257 × 384 = 19,298,688 numbers vs 24,960 for 65 characters → a bigger vocab isn't free, and rare tokens' rows get little training
  • detail that matters The tokenizer is trained separately, on its own text, before the LLM → which languages and formats get short tokens depends on that text → non-English text and odd formats cost more tokens (132 GPT-2 tokens for a 72-character Korean line)

Reference only

  • GPT-2 vocab 50,257 = 256 bytes + 50,000 merges + 1 special (<|endoftext|> = 50256)
  • cl100k_base (GPT-4) n_vocab 100,277
  • tiktoken.get_encoding('gpt2'), enc.encode, enc.n_vocab
  • GPT-2 context length 1024 tokens (up from 512 in GPT-1)
  • the Colab's exact list of eleven symptom questions

5 · Predict commit to an answer before revealing

The GPT-2 tokenizer was trained on mostly English web text. You feed it a 72-character Korean line and a 76-character English line. Roughly how do their token counts compare, and why?

Reveal

About 132 tokens for the Korean vs 20 for the English (measured with tiktoken). Korean characters are 3 UTF-8 bytes each, and the tokenizer's training text had little Korean, so few Korean byte runs got merged. The line's 158 bytes become 132 tokens, only 1.2 bytes per token on average. The model sees over 6 times as many tokens for the same length of text, so it fills its context faster. The tour card shows the same line in cl100k (61 tokens).
