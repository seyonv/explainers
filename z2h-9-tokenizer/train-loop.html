Training a tokenizer, and why it's a separate stage

Also called: BPE training, learning the merges, building the vocabulary. Lecture 8 · training the tokenizer: adding the while loop, compression ratio · 0:34:58 · tokenizer/LLM diagram: it is a completely separate stage · 0:39:20

Prime · 2 minutes before you read

The problem: One merge makes a 616-byte paragraph only 20 tokens shorter. A useful tokenizer needs thousands of merges, chosen automatically, and a clear boundary between the text it learned from and the model that will use it.

Where it fits: The previous card wrote get_stats and merge and did one merge by hand. This card wraps them in a loop that trains a whole tokenizer, then steps back to show where that tokenizer sits relative to the LLM.

In one breath: training a tokenizer means running the previous card's two steps in a loop: count every adjacent pair of tokens, merge the most common pair into a brand-new token id, and repeat until the vocabulary is as big as you asked for. The only thing you keep is the list of merges. It's learned once, from its own training text, before the language model (LLM) ever sees anything, and afterwards the tokenizer just translates text to ids and back.

Predict first: the whole blog post is 24,597 bytes. The first merge on it replaces 646 pairs. After 20 merges, will the sequence be about 2× shorter, about 1.3× shorter, or about 1.05× shorter?

About 1.3×: 24,597 → 19,438 tokens, a compression ratio of 1.27×. Each merge helps less than the one before it, because it merges a rarer pair: the 1st removes 646 tokens and the 20th only 144. Twenty merges remove 5,159 tokens in total.

Merges of merges: a forest

Karpathy calls this structure a binary forest. It's why the order of merges matters: token 275 can't exist until 256 and 259 do. The decode and encode cards both lean on that order.

▶ Build itruns on your M3 · under 5 s

When: pause the video at 0:34:58 and type the loop before watching on. Put the whole blog post from the Colab's cell 9 into text, and reuse your get_stats and merge from the previous card.

tokens = list(map(int, text.encode("utf-8")))
vocab_size = 276    # the desired final vocabulary size
num_merges = vocab_size - 256
ids = list(tokens)  # copy, so the original stays intact
merges = {}         # (int, int) -> int
for i in range(num_merges):
    stats = get_stats(ids)
    pair = max(stats, key=stats.get)
    idx = 256 + i
    print(f"merging {pair} into a new token {idx}")
    ids = merge(ids, pair, idx)
    merges[pair] = idx
print("ids length:", len(ids))
print(f"compression ratio: {len(tokens) / len(ids):.2f}X")

A completely separate stage

Because the merges only come from counting, whatever text you train the tokenizer on decides which strings get short. To check, a second 20-merge tokenizer was trained for this card on the first 24,597 characters of tiny Shakespeare (its merges include :\n, \n\n and you, from the play's layout), and the two were compared:

Each tokenizer compresses its own kind of text best, and neither saw Korean, so the Korean stays almost one token per byte. With 256 merges on the blog, the example string's first English line shrinks 76 → 42 tokens (1.81×) but the Korean line only 158 → 154 (1.03×).

How it differs from related ideas

✗ Raw bytes, no training

Every text encodes, but the blog post costs 24,597 positions. The LLM's context and compute are spent one byte at a time.

✗ A character vocabulary

The GPT lecture's 65 characters came straight from its text. Any character outside them can't be encoded at all, and every character is still one position.

✗ Learning tokens inside the LLM

BPE picks merges by counting, and there's no gradient through "which pair to merge", so the LLM's loss can't tune them. That's one reason Karpathy's list says tokenization is not end-to-end.

✓ Byte-level BPE, trained once

It starts from 256 bytes, so any text still encodes. Merges add density exactly where the tokenizer's training text was dense, and vocab_size is a knob you set.

Is the tokenizer trained on the LLM's data?

Not necessarily. The Colab says the tokenizer's training set "could be different" from the LLM's. The data mixture is a choice: put more Japanese (or code) into the tokenizer's text and you get more merges for it, so the same Japanese text becomes fewer tokens and fits more of it into the LLM's context. The Korean row above shows the flip side.

The mismatch can bite. A string that's common in the tokenizer's text but absent from the LLM's text still gets its own token, and that token's embedding row never gets trained. That's the SolidGoldMagikarp story on the quirks card. More merges aren't free either: every new id adds a row to the embedding table and to the output layer (the vocab-size card).

Understand and remember

  • Each pass merges the currently most common pair → every later pair is rarer (646 → 144 removals) → compression grows ever more slowly with vocab_size (1.27× at 276, 2.15× at 512)
  • A minted id goes back into ids → later passes can pair it again ((259, 256) = 'the␣') → merges form a forest → a merge only makes sense after its parents exist, so the dict's order is part of the tokenizer
  • Merges are chosen by counting pairs in the tokenizer's own training text → strings that are frequent there get short → text the tokenizer rarely saw (Korean for a blog-trained tokenizer) stays about one token per byte and eats the LLM's context
  • BPE training is counting, not gradient descent → it's done once and frozen before the LLM trains → the LLM only ever sees ids, and a token that's rare in the LLM's data keeps an untrained embedding
  • detail that matters Each pass rescans the whole sequence (get_stats then merge) → training cost grows with text length × number of merges → this card's 20 merges on 24,597 bytes finish in about a second, while minbpe's 256 merges on 185,768 bytes took 10.9 s on your M3

    Check

4 · Compare against what you already know

vs Encoding: apply merges in training order: The training loop and the encode loop both call get_stats and merge repeatedly. What's fundamentally different about how each picks the next pair, and what would go wrong if encode used training's rule?

Check
  • training picks the most frequent pair in its text (max by count) and mints a new id
  • encode picks the pair with the lowest merge index (min over merges) and mints nothing
  • using counts at encode time would apply merges in a text-dependent order, so the same string could tokenize differently in different documents and could try merges whose parents don't exist yet

vs Training it, and moving from notebook to script: Training the bigram LLM vs training the tokenizer: both are called training. What does each optimise, how does each update, and how does each fail?

Check
  • LLM: minimises a loss by gradient descent, many small updates to real-valued weights
  • tokenizer: greedy counting, one irreversible discrete merge per step, no loss and no gradient
  • LLM failure: underfitting or overfitting the loss
  • tokenizer failure: merges fitted to the wrong text mixture, so other languages or formats stay long

Reveal

Training order (lowest merge index first), regardless of counts in the new text. Token 275 is defined as 259 + 256, and those only exist after merges 1 and 4 have been applied. Counts in the new text are irrelevant: the tokenizer is frozen. That's the encode card's min over merge index.
