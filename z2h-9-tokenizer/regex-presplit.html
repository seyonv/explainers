The GPT-2/GPT-4 regex: never merge across categories

Also called: pre-tokenization, the split pattern, chunking. Lecture 8 · regex patterns to force splits across categories · 0:57:36, and GPT-2 vs GPT-4 regex in tiktoken · 1:11:38

Prime · 2 minutes before you read

The problem: Plain BPE merges whatever pairs are most common, even across a word and the punctuation or space after it. The vocabulary fills up with pieces like dog., dog! and 'e ' that mix a word's meaning with whatever symbol follows it.

Where it fits: You've written get_stats, merge, the training loop and encode for a byte-level BPE. This card adds the one step real GPT tokenizers put before all of that: cutting the text into chunks that BPE is never allowed to cross.

In one breath: before BPE sees any bytes, a regular expression cuts the text into chunks, where each chunk is one run of letters, numbers, punctuation or whitespace (a category). BPE then trains and encodes inside each chunk on its own, so no token can ever glue a word to the punctuation or digits next to it.

Predict first: GPT-2's pattern splits "Hello world" (three spaces). What chunks come out, and where does each of the three spaces go?

['Hello', ' ', ' world']. Two spaces form their own chunk and the third joins the word. The part \s+(?!\S) grabs whitespace but stops one space short of the next word, so the text still contains ' world' with its usual leading space. That keeps it the same common token as in ordinary text (measured by the lab).

Chunk first, then BPE inside each chunk

This is the fix the GPT-2 paper (§2.2) describes. Plain BPE on raw bytes happily learns separate tokens for dog., dog! and dog?. That spends vocabulary slots on word-plus-punctuation combinations and mixes up what a word means with the symbol after it. Splitting by category first rules out all of those combinations, and the training loop stays the same apart from running once per chunk.

Reading the GPT-2 pattern

The pattern is a list of alternatives joined by |. re.findall walks the text left to right, and at each position it takes the first alternative that matches there. You need these pieces of regex syntax:

\p{L}any letter, in any script (h, é, 안). \p{N} is any numeric character. Both need import regex; Python's built-in re doesn't support them. \sany whitespace (space, tab, newline). \S is anything that is not whitespace. ? +x? = zero or one x; x+ = one or more x. [^…]one character that is not in the set. (?!\S)lookahead: "only if the next character is not a non-space". It checks the next character but doesn't consume it.
AlternativeWhat it grabsChunks it made from "Hello've world123 how's are you!!!?"
'(?:[sdmt]|ll|ve|re)English contractions: 's 't 'd 'm 'll 've 're've's
␣?\p{L}+an optional space, then a run of lettersHello␣world␣how␣are␣you
␣?\p{N}+an optional space, then a run of digits (any length)123
␣?[^\s\p{L}\p{N}]+an optional space, then anything else: punctuation, symbols, emoji!!!?
\s+(?!\S)whitespace, minus the last space before a wordnone here; "Hello world" gives ␣␣
\s+any whitespace left over, e.g. at the very endnone here

␣ marks the literal space in the pattern. Spaces go on the front of words, so ' you' is one chunk. Karpathy points out the contraction rule breaks on the curly apostrophe ’ and on uppercase 'S (table below).

What the split costs and buys: minbpe on the Taylor Swift page

minbpe's train.py trains both tokenizers to a vocabulary of 512 (256 merges) on the same 185,768 bytes (taylorswift.txt, a Wikipedia article). The regex one uses the GPT-4 pattern. Measured on your M3:

TokenizerFirst 5 mergesTokensCompression
Basic (no split)e␣,␣d␣.␣r␣78,7462.36×

185,768 / 78,746 = 2.36 185,768 / 87,339 = 2.13 87,339 − 78,746 = 8,593 more tokens with the split (+10.9%)

All five of the basic tokenizer's first merges join a letter or punctuation to the space after it. Under a split pattern that can't happen, because the space belongs to the next word's chunk. We checked all 256 of basic's merges against the GPT-4 pattern (computed in a scratch script): 110 of them span a chunk edge, including ', 201' and '. Retrieved ', which come from the article's citation lines. One more merge is a partial UTF-8 character and can't be checked. The regex tokenizer loses some compression, but its vocabulary is spent on pieces of words and numbers.

The split also sets a floor on the token count. The GPT-4 pattern cuts this text into 46,196 chunks, and each chunk needs at least one token, so no number of merges can take the regex tokenizer below 46,196 tokens (computed).

GPT-2 → GPT-4: what the new pattern changed

tiktoken's cl100k_base (GPT-4) pattern is below, in minbpe's copy. tiktoken now stores a faster form that looks different but splits text the same way.

'(?i:[sdmt]|ll|ve|re)|[^\r\n\p{L}\p{N}]?+\p{L}+|\p{N}{1,3} | ?[^\s\p{L}\p{N}]++[\r\n]*|\s*[\r\n]|\s+(?!\S)|\s+

(?i:…) = ignore case inside. ?+ and ++ are "possessive": they match like ? and + but never give characters back. {1,3} = one to three times. The pattern is one line; it's broken here to fit.

↵ = newline. All outputs are from labs/regex-presplit.py on your M3 (the FizzBuzz row shows a few chunks from the Colab's FizzBuzz snippet). The digit cap works: of cl100k's 1,122 tokens that contain a digit, none has 4 or more digits and none mixes digits with any other character, while GPT-2's vocabulary has 288 tokens with 4+ digits (computed by scanning both vocabularies).

The last row is the odd one. GPT-2's regex hands BPE a three-space chunk, yet GPT-2's vocabulary has no token for two or three spaces (checked across all 50,257), so each space stays token 220. OpenAI must have applied extra rules during training, and that training code was never released: encoder.py only encodes. The GPT-4 changes aren't explained either; Karpathy notes that none of it is documented (1:11:38).

import tiktoken
GPT2 = (r"""'(?:[sdmt]|ll|ve|re)| ?\p{L}+| ?\p{N}+"""
        r"""| ?[^\s\p{L}\p{N}]+|\s+(?!\S)|\s+""")
GPT4 = (r"""'(?i:[sdmt]|ll|ve|re)|[^\r\n\p{L}\p{N}]?+\p{L}+"""
        r"""|\p{N}{1,3}| ?[^\s\p{L}\p{N}]++[\r\n]*"""
        r"""|\s*[\r\n]|\s+(?!\S)|\s+""")
print(re.findall(GPT2, "Hello've world123 how's are you!!!?"))
for t in ["house’s", "HOUSE'S", "abc 1234567"]:
    print(repr(t), re.findall(GPT2, t), re.findall(GPT4, t))
for name in ["gpt2", "cl100k_base"]:
    enc = tiktoken.get_encoding(name)
    print(name, enc.encode("    hello world!!!"))

Why it beats the alternatives

✗ BPE on raw bytes, no split

Best compression (2.36× vs 2.13× above), but 110 of its 256 merges on the Taylor Swift page glue things like ', 201' together. dog., dog! and dog? can each become their own token.

✗ Split on whitespace only

"dog.".split() is still ['dog.']: punctuation and digits stay stuck to words, and runs of spaces or newlines vanish, so the text can't be rebuilt exactly.

✗ Make each space its own chunk

The most common English tokens are words with a leading space (' the', ' you'). With spaces split off, every word would need at least two tokens, one for the space and one for the word (our reasoning, not measured).

✓ Regex split by category, BPE per chunk

Merges stay inside words, numbers or punctuation runs, a word keeps its leading space, and ''.join(chunks) rebuilds the text exactly. It gives up about 10% compression for a cleaner vocabulary.

Is a regex split always right?

No. It's a hand-written, English-leaning heuristic. The contraction list only covers English apostrophes, GPT-2's version is case-sensitive and ignores ’, and on top of the pattern GPT-2 applied spacing rules that were never published. The "right" pattern is a design choice nobody has documented: OpenAI changed number, case and newline handling between GPT-2 and GPT-4 without saying why.

Not every tokenizer uses one. sentencepiece, which trained Llama 2's tokenizer, has no regex split. It works on code points and uses options such as split_digits instead (sentencepiece card). And if raw compression is all you care about, the basic tokenizer wins on bytes per token.

Understand and remember

  • Regex cuts text into category chunks → get_stats counts pairs inside each chunk only → no pair ever spans two chunks → no merge (and so no token) can join a word to the punctuation, digits or space beside it
  • Space attaches to the front of the next word ( ?\p{L}+) → ' you' is one chunk and one common token → so \s+(?!\S) stops one space early to leave that space for the word → merges like basic BPE's 'e ' or ', ' become impossible
  • Chunks can only be merged within, never joined → fewer merge options → worse compression (Taylor Swift: 87,339 vs 78,746 tokens, 2.13× vs 2.36×) and a floor of one token per chunk (46,196) → you trade bytes-per-token for a vocabulary spent on real words and numbers
  • GPT-4 caps numbers at \p{N}{1,3} → digit chunks are at most 3 long → no cl100k token has 4+ digits (GPT-2 has 288) → every long number splits into 3-digit groups from the left, e.g. 1234567 → 123|456|7
  • detail that matters tiktoken GPT-2 leaves ' ' as three 220 tokens even though the regex hands BPE a three-space chunk → the pattern is not the whole story; GPT-2's unreleased training applied extra rules, so you can't reproduce GPT-2's vocabulary from encoder.py alone

Reference only

  • the exact GPT-2 and GPT-4 pattern strings (minbpe regex.py L18–L19)
  • import regex as re is needed for \p{L}/\p{N}
  • possessive quantifiers ?+, ++ and tiktoken's newer, equivalent stored pattern
  • the tiktoken ids 220 (space), 262 (three spaces in cl100k)

    Check
    • pairs are only counted inside a chunk, so a cross-chunk pair never gets a count

  2. mechanism Walk GPT-2's pattern through "abc 1234567" position by position: which alternative fires at each step, and what chunk does it return? Then do the same with the GPT-4 pattern.
    Check
    • GPT-2: ?\p{L}+ takes abc; at the space, ?\p{N}+ takes ' 1234567' (space plus all digits)
    • GPT-4: abc, then the numbers alternative has no optional space, so ' ' becomes its own whitespace chunk
    • then \p{N}{1,3} fires three times: 123, 456, 7
  3. tradeoff You're designing a tokenizer for a corpus that's mostly source code. Would you use the basic tokenizer or a regex split, and what would you watch for in the pattern?
    Check
    • basic compresses better (fewer tokens per byte), which matters for context length
    • the split keeps identifiers, numbers and punctuation apart, so tokens are reusable across contexts
    • watch whitespace: indentation runs must merge (GPT-4 merges spaces, GPT-2 didn't), and newline handling decides where indents land

    Check
