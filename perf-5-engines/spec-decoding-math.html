Speculative decoding I: exact sampling with a draft

Also called speculative sampling or draft-and-verify; the two knobs are the acceptance rate α and the draft length γ. This card walks Leviathan, Kalman & Matias, "Fast Inference from Transformers via Speculative Decoding" (ICML 2023), §1–3 and Appendix A.1, in the paper's notation: Mp is the target model with next-token distribution p, Mq the draft with q. Chen et al. (arXiv 2302.01318), published independently, swap the letters (q = target, p = draft), so check which paper you are reading before you trust a formula. Part II, drafts, batch size and our Mac, covers §4, Chen's Chinchilla results and our own measurement.

In one breath

A decode step at small batch spends its time reading weights, so the target can score several tokens in one run for about the price of one. A cheap draft proposes γ tokens. The target keeps each one with probability min(1, p/q), and at the first rejection it samples a replacement from the leftover mass max(0, p − q). The tokens that come out are distributed exactly as if the target had sampled them alone, with any sampling method. What you gain is 1 to γ + 1 tokens per target run instead of 1.

Already seen elsewhere, so this card doesn't repeat it: the draft-and-verify idea with a code example (LLM latency: speculative decoding), a one-step picture with an α table (speculative decoding), and the Scaling Book's greedy recipe, a numpy exactness check and Llama-3.1-8B on an H100 at batch 1 and large batch (course 2: speculative sampling). Here we go through the paper itself: why every sampling method fits, the algorithm line by line, the proof, and each theorem in §3 with its numbers.

§1 and §2.1: the idea

§1 makes two observations. Some tokens are easy enough for a much smaller model to guess, and large-model inference "is often not bottlenecked on arithmetic operations, but rather on memory bandwidth and communication, so additional computation resources might be available." Speculative decoding spends that spare compute the way a CPU spends it on branch prediction: it does the work before knowing whether it's needed. The paper's contribution is doing this for random choices ("stochastic speculative execution"). §2.1 has three steps: (1) Mq generates γ guesses; (2) Mp scores all of them in parallel; (3) accept every guess that can lead to the identical distribution, then sample one more token from an adjusted distribution. Every target run yields at least 1 token and at most γ + 1, so in the worst case it needs no more target runs than plain decoding. The paper's Fig 1 example: 38 tokens generated in 9 serial runs of a 97M target using a 6M draft.

§2.2: standardized sampling, so one rule covers all of them

Argmax, top-k, nucleus and temperature are usually coded differently at the logits level. But each one is just "sample from an adjusted distribution". Argmax, for example, zeroes every non-max entry and renormalizes. So the paper only handles plain sampling from p and q, after both have been adjusted by the same method (in its experiments the draft always used the same standardization as the target). The proof uses nothing about what q is, so any draft is exact. The draft only affects speed (§3.6). Applied position by position in Algorithm 1 (each accepted token becomes the next position's prefix), every emitted token follows p. Checked in labs/spec-sim.py:

TV = total variation distance, ½ Σ |a − b|; 0 means identical. Sampling 200k tokens directly from p gives 0.0020 in the same run, so 0.001–0.006 is sampling noise. The bigram check compares each row of the transition matrix. Appendix A.2 adds why this isn't plain rejection sampling: a one-shot rejection sampler that falls back to p accepts with probability Σ p · minx′(q/p), which is at most α and often far lower.

§3.3: walltime (Theorem 3.8 and Corollary 3.9)

§3.3 assumes γ + 1 parallel target evaluations cost the same wall time as one. That is the memory-bound assumption, and §3.4 checks it. Then one iteration costs γ draft runs plus one target run, cγT + T, and yields Eq 1 tokens:

speedup= 1−αγ+1tokens per run × (1 − α) (1−α)(γc+1)cost per run, in target steps Cor 3.9: if α>c,some γ gives ≥1+α1+c
cdraft run time ÷ target run time. Unlike α, it depends on hardware and software. In the paper it was "always less than 0.05 and often negligibly close to 0"0.05 γc + 1γ draft runs plus 1 target run1.20
worked example, α = 0.8, γ = 4, c = 0.05 (illustrative, in the paper's range): tokens per run E = 3.36 (Eq 1, above) cost per run = 4 × 0.05 + 1 = 1.20 target steps speedup = 3.36 / 1.20 = 2.80× Cor 3.9 (γ = 1) = (1 + 0.8) / (1 + 0.05) = 1.71× a guaranteed floor for the best γ

Cor 3.9's proof uses a monotonicity fact: if some γ helps, every smaller γ helps too, so checking γ = 1 tells you whether speculation can help at all. The theorem assumes long generations. Since Mp runs at least once, the speedup is capped by the number of tokens generated.

§3.4: arithmetic goes up, memory reads go down (Theorem 3.11)

ops factor= (1−α)(γc^draft+γ+1target positions)1−αγ+1 target weight + KV reads per token÷1−αγ+11−αread once per iteration
α = 0.8, γ = 4, ĉ = 0.05 (assumed = c): ops = 0.2 × (0.2 + 5) / 0.67232 = 1.55× more math target weight reads per token: ÷ 3.36, i.e. 0.297 of plain decoding on the running example (our arithmetic): 16.06 GB of Llama-3.1-8B weights per token → 16.06 / 3.36 = 4.78 GB per token (plus the draft's own reads)

This is the trade. Every rejected position wastes the math the target did on it, so total arithmetic rises (1.55× here). The target's weights and KV cache are read once per iteration, not once per token, so memory traffic per token falls by Eq 1's factor. That only speeds things up when the step is memory-bound, meaning the extra math fits in time the GPU would otherwise spend waiting on reads. At batch 1, Llama-3.1-8B on an H100 spends ≈ 4.8 ms reading weights, and scoring 5 tokens instead of 1 adds about 81 µs of math (course 2's recomputation). At large batch the step is already compute-bound, so the extra 1.55× of math costs real time (see critical batch size and Part II). The paper says so directly: "our method is not helpful for configurations where additional computation resources are not available." It also notes that for a decoder, the target's total verification math is bounded by one run of a same-size encoder.

At α = 0.8, c = 0.05 the best γ is 8 (3.09×), but γ = 4 already gets 2.80×: the curve is flat near its peak.

The paper also bounds what an adaptive γ could add. An oracle that knew each β in advance would get E = 1/(1 − α) tokens per run, and "for typical values of c and α … up to ∼60% higher" speedup than a fixed γ. The paper leaves this for future work. The dynamic draft trees in EAGLE-2 go in this direction (our connection, not the paper's).

§3.6: what makes a good draft

Any Mq keeps the output exact. The choice is only a trade between α (bigger drafts guess better) and c (bigger drafts cost more). With same-architecture off-the-shelf drafts, "around two orders of magnitude smaller than Mp usually performed best". Negligible-cost drafts (c ≈ 0) cap the speedup at 1/(1 − α). Even a bigram lookup table gets α ≈ 0.2 on T5-XXL English→German, and at γ = 3 that gives (1 − 0.2⁴)/0.8 = 1.25×. The paper also suggests copying tokens from the context when a prefix matches (the idea behind today's prompt-lookup and n-gram drafts), non-autoregressive drafts that propose all γ tokens in one call, and, "mostly from a theoretical perspective", a random draft, which still gives a tiny gain.

Why it beats the alternatives

✗ Plain autoregressive decoding

Exact, but γ tokens cost γ serial target runs, each reading all the weights. At batch 1 almost all of the GPU's math sits idle.

✗ Greedy "accept if equal"

Keep a draft token only if it equals the target's argmax. That is exact for greedy decoding only. At T = 1 it always emits argmax p, which is off by TV = 0.55 on the rug/mat example. Matching a sampled target token instead is exact, but it accepts only Σ p·q = 0.26 vs 0.70 (lab part 2).

✗ Typical acceptance (Medusa)

Accept any draft token the target finds "plausible enough" (above an entropy-scaled threshold). Acceptance is higher, but the output is no longer the target's distribution, so quality has to be re-checked. See Medusa.

✓ Rejection-sampling speculative decoding

min(1, p/q) plus the residual is exact for every sampling method and every draft (App A.1), and it accepts the most any exact single-draft rule can: Σ min(p, q) = 1 − TV.

"Accepts the most" is our inference from the proof: min(p(x), q(x)) is the largest probability of emitting x through the draft without exceeding p(x). The paper only compares against one-shot rejection sampling (App A.2).

Why is the bonus token free?

Because the target's verify pass already computed it. To check draft xi, Mp needs pi, the distribution at position i given prefix + x1…xi−1. A transformer run over prefix + x1…xγ produces logits at every position, including the one after xγ: that is pγ+1. When all γ drafts pass, Algorithm 1 samples t from pγ+1, so the run yields γ + 1 tokens for no extra target work. When a draft is rejected, the same slot goes to the fix token t ~ norm(max(0, pn+1 − qn+1)) and the distributions after it are discarded. Either way, each target run produces exactly one token the draft didn't propose, which is where the "+1" in Eq 1 comes from.

That doesn't make speculation free. It only pays while the extra positions ride along with the weight read (§3.4). When a server already batches enough sequences to be compute-bound, scoring γ + 1 positions per sequence costs real time, and plain continuous batching wins. The same happens when c is large, as on our Mac, or when α is low (c = 0.05 and α = 0.5 top out at 1.63×). Those cases get cheaper drafts (EAGLE, n-gram lookup) or no speculation at all.
