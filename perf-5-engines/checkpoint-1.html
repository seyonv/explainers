Checkpoint 1: keeping the batch full without stalling

Ties together Orca I, Orca II, Sarathi-Serve I, Sarathi-Serve II, the scheduler and the anatomy of vLLM and SGLang: how an engine decides, every step, which tokens run, and what that decision costs in latency, memory and CPU time.

How to use this page. Close the six cards. Answer each question in writing, in full sentences, before opening its Check. A wrong or shaky answer isn't a failure; it tells you exactly which section to reopen. The questions are mixed on purpose, so you have to work out which idea applies before you can answer.

1 · Mixed retrieval

  1. which concept?An operator raises max_num_seqs from 128 to 256 on a workload with short prompts and very long outputs. Peak running requests go up, but throughput drops about 1% and the preemption counter climbs. Which idea explains it, and what should they change?
    Check
    • past the point where the KV block pool binds, a higher cap doesn't make a bigger batch
    • the extra admitted requests grow into the same blocks and evict each other (latest arrival first), and each victim recomputes its prompt plus output
    • in the lab: 250 → 299 preemptions, 6,100 → 6,038 tok/s; lower the cap or the budget, or raise gpu_memory_utilization

    Missed it? Reopen the scheduler, "Why does raising max_num_seqs sometimes lower throughput?".

  2. Orca reserves max_tokens KV slots for every new request. On the running example (487,823 slots, max_tokens = 2,048), how many requests can it admit, how much of an average ShareGPT request's reservation is ever written, and what did paging change?
    Check
    • ⌊487,823 ÷ 2,048⌋ = 238 requests
    • an average ShareGPT request writes 499 of its 2,048 slots: 24.4%
    • paged allocation takes 32 blocks (512 slots) for the same request, so about 952 fit; overflow is then handled by preemption instead of reservation

    Missed it? Reopen Orca II, "Our framing: the reservation is the waste PagedAttention removed".

  3. which concept?A chat service's median time between tokens is 8 ms, but its P99 is about 80 ms, and the spikes line up with long new prompts arriving. Which idea explains the spikes, and what is the standard fix?
    Check
    • a generation stall: a whole prompt in one step pushes it far past the ridge (≈ 295 tokens), so every decoding user waits for that step
    • on the running example, 32 users at 7.36 ms per step see 74–78 ms when a 4,096-token prompt is admitted
    • fix: chunked prefill with stall-free batching (decodes first, a token budget sized to the TBT SLO)

    Missed it? Reopen Sarathi-Serve I, the worked example, and Sarathi-Serve II, §4.2.

  4. Orca runs attention separately for each request but batches every other operation over one flat token list. Why does leaving attention unbatched cost almost nothing?
    Check
    • batching pays by reusing one weight read across many tokens
    • attention has no weights; each request reads only its own KV cache
    • so there's no shared read to reuse, and splitting just before attention loses nothing (modern engines do batch it, but for launch overhead and occupancy)

    Missed it? Reopen Orca I, "S2: selective batching".

  5. which concept?Llama-3.1-8B at batch 1 on an H100 makes 170 tok/s where the step model says 205. A profiler shows the GPU idle for about 1 ms between steps, and CUDA graphs are already on. Which idea explains it, and which fix targets that gap?
    Check
    • CPU work (scheduling, input preparation) runs serially between GPU steps: 4.87 + 1 ms = 5.87 ms per token
    • CUDA graphs only speed up the inside of a step, not the work between steps
    • overlap (or async) scheduling prepares step n + 1 while the GPU runs step n, so step = max(GPU, CPU) and throughput returns to 205 tok/s

    Missed it? Reopen anatomy, "What 1 ms of CPU costs the running example" and "Four ways to keep the GPU fed".

  6. Walk through what vLLM V1's scheduler decides in step 30 of the card's burst (115 requests decoding, budget 8,192): in what order does it fill the budget, and why does request 120 have to wait?
    Check
    • all 115 decodes first, one token each
    • then the rest of request 115's ongoing prompt (1,597 tokens), then new prompts 116–118 whole (2,048 each) and the first 336 tokens of 119
    • the budget is now used up, so 120 waits even though KV blocks are still free (12,018 left)

    Missed it? Reopen the scheduler, "One step, drawn from the lab".

  7. For the same 4,096-token prompt arriving during 32-user decoding, vLLM V0 gives users a 78.32 ms gap and Orca a 74.04 ms gap. Why are they different, and why is neither acceptable for interactive chat?
    Check
    • vLLM V0 runs a prefill-only iteration (70.96 ms) and then a decode iteration (7.36 ms), so users wait for both
    • Orca puts the prompt and the decodes in one hybrid iteration (74.04 ms)
    • both are about 10× the clean 7.36 ms step; hybrid batching alone doesn't bound how many prompt tokens a step holds

    Missed it? Reopen Sarathi-Serve I, §3.2.

  8. In the Orca I simulation, iteration-level scheduling gives 1.93× the peak throughput of request-level batching at the same B = 64. Why does it come out at about 2×, and what workload would make the gap bigger?
    Check
    • a static batch lives as long as its longest request (≈ 1,000 tokens) while the mean is 513, so about half the slot-iterations compute finished requests (49.1%)
    • iteration-level refills each slot as soon as it frees
    • longer-tailed output lengths make the longest request even longer relative to the mean, so the gap grows

    Missed it? Reopen Orca I, "Worked example: static vs iteration-level on one H100".

3 · Project: a step-level scheduler model for one H100

What it reinforces: the step formula and the ridge (Sarathi I), stall-free batching and the budget (Sarathi II), whole-prompt schedulers (Orca I), KV admission (the scheduler) and serial vs overlapped CPU work (anatomy).

Llama-3.1-8B in BF16 on one H100. Thirty-two users are decoding at 2,048 tokens of context (hold it fixed). One 4,096-token prompt arrives. Model one iteration with B decodes plus a chunk of c prompt tokens that follows p earlier tokens of the same prompt:

t = B·2048·131,072 / 3.35e12 (decodes' KV reads) + max(2·8.03e9·(B + c) / 989e12, 16.06e9 / 3.35e12) (math or weight read) + 32·2·c·(2p + c)·4096 / 989e12 (causal attention for the chunk)

(The chunk's re-reads of its own earlier KV are left out, to keep it short.) In about 40 lines of Python:

  1. Clean step. Compute t(32, 0, 0). Set a TBT SLO of 5× that clean step, as Sarathi does.
  2. Whole-prompt schedulers. vLLM V0: a prefill-only iteration t(0, 4096, 0), then a decode iteration; report the worst gap users see and the prompt's TTFT (queueing ignored). Orca: one hybrid iteration t(32, 4096, 0).
  3. Stall-free. For budgets τ = 512, 1,024 and 2,048: each iteration takes 32 decodes plus a chunk of up to τ − 32 prompt tokens. Report the number of iterations, the worst iteration, and TTFT (the sum of the prompt's iterations). Which budgets meet the SLO?
  4. Admission. With blocks of 16 tokens, how many blocks does the prompt need, and how many do the 32 decoding users hold? Does it fit the 27,437-block pool at gpu_memory_utilization 0.92?
  5. CPU. Add 1 ms of serial CPU work to every iteration (an illustrative cost), then make it overlapped (max instead of sum). What happens to τ = 512's worst gap and TTFT in each case?
Done when: your program prints one table (policy, iterations, worst gap, TTFT, meets SLO?), the block counts, and the CPU variants, and you can say in one sentence why the largest budget that meets the SLO is the one to pick. Then compare with the check.
Check: the numbers (computed with a Python version of this exact model)
  • Clean step 7.36 ms, so the SLO is 36.8 ms.
  • vLLM V0: prefill-only 70.96 ms, worst gap 78.32 ms, TTFT 70.96 ms. Orca: 74.04 ms for both. Both miss the SLO by about 2×.
  • Stall-free τ = 512: 9 iterations (8 × 480 + 256), worst 11.79 ms, TTFT 98.83 ms. τ = 1,024: 5 iterations, worst 21.02 ms, TTFT 88.58 ms. τ = 2,048: 3 iterations, worst 39.05 ms, TTFT 83.45 ms, which misses 36.8 ms. So τ = 1,024 is the largest of the three that meets the SLO, and it gives the best TTFT that does.
  • Admission: the prompt needs 4,096 ÷ 16 = 256 blocks; the 32 users hold 32 × 128 = 4,096 (plus what they generate). Plenty of room in 27,437, so the budget, not memory, limits this prompt.
  • With 1 ms serial CPU, τ = 512's worst gap becomes 12.79 ms and TTFT 107.83 ms (9 iterations × 1 ms more), and even the clean step becomes 8.36 ms. Overlapped, the CPU millisecond hides under every iteration and the numbers return to 11.79 and 98.83 ms.
