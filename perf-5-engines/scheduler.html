The scheduler: KV budget, admission and preemption

Also called the vLLM scheduler, or by its knobs: max_num_batched_tokens (the token budget), max_num_seqs, gpu_memory_utilization, and preemption (recompute or swap). This card is about vLLM V1's scheduler, as its blog, docs and source describe it, and connects it to PagedAttention §4.5. Every time and count for Llama-3.1-8B on an H100 is our recomputation with labs/kv-admission.py, a simulator; none of it is measured.

In one breath

Before every step, the scheduler picks which requests run and how many tokens each one gets. It has two budgets. The token budget limits how much compute (and so how much latency) one step can take. The KV block pool limits how many tokens of history can sit in memory. A waiting request starts only if its blocks fit. If a running request needs a block and none are free, the scheduler evicts the most recently arrived request, which later rebuilds its KV from scratch.

What vLLM V1 says it does

  • One dictionary per step. V1 "removes the traditional distinction between 'prefill' and 'decode' phases by treating user-given prompt tokens and model-generated output tokens uniformly. Scheduling decisions are represented as a simple dictionary, e.g., {request_id: num_tokens}." With "a fixed token budget, the scheduler dynamically decides how many tokens to allocate to each request" (V1 blog).
  • Decodes first, then chunks. "In V1, chunked prefill is enabled by default whenever possible … It batches all pending decode requests before scheduling any prefill operations. When there are available tokens in the max_num_batched_tokens budget, it schedules pending prefills. If a pending prefill request cannot fit into max_num_batched_tokens, it automatically chunks it" (tuning docs). Where this came from is on Sarathi-Serve II.
  • Prefix caching is on. V1's prefix caching causes "less than 1% decrease in throughput even when the cache hit rate is 0%", so "we now enable prefix caching by default" (V1 blog).
  • Preemption recomputes. "In vLLM V1, the default preemption mode is RECOMPUTE rather than SWAP, as recomputation has lower overhead in the V1 architecture" (tuning docs). We found no swap path in the current V1 scheduler source: a preempted request frees its blocks, resets its computed tokens to 0 and goes back to the front of the waiting queue.
  • FCFS or priority. "First-Come, First-Served (FCFS) and priority-based scheduling (where requests are processed based on assigned priority, with FCFS as a tie-breaker)", chosen with --scheduling-policy (V1 guide). A lower priority value means earlier handling.

One step, drawn from the lab

This is step 30 of the burst below: 200 requests with 2,048-token prompts, budget 8,192, pool 27,437 blocks. The scheduler's output is literally {0: 1, 1: 1, …, 114: 1, 115: 1597, 116: 2048, 117: 2048, 118: 2048, 119: 336}.

Green solid: decode tokens. Light green: prefill chunks. Both are useful compute. Our step-time model prices this step at 142.6 ms, almost all of it the 8,192 tokens of matmul (133 ms at 100% of 989 TFLOPS). A pure decode step for the same 115 requests would be about 14 ms (at 2,048 context), and that gap is the TBT cost of a big budget.

The knobs, each at 2k and 8k context

An analogy: a restaurant with a fixed number of seats (KV blocks) and a kitchen that can cook a fixed number of plates per round (the token budget). The host seats a group only if there are chairs for it now. Diners keep ordering, and if the chairs run out, the group that came in last has to get up and start its meal over later.

Worked example: a burst of 200 requests

200 requests arrive at once. Each has a 2,048-token prompt and wants between 512 and 1,024 output tokens (uniform, seed 0, mean 760.4, so 152,080 in total). Settings: vLLM's H100 vllm serve default budget of 8,192, max_num_seqs 256 (above 200, so like the 1,024 default here), utilisation 0.92, FCFS, recompute. The outputs are made up; the scheduling rules follow vLLM V1; the times come from the course-2 step model.

Output of labs/kv-admission.py, sampled every 12 steps. The whole burst takes 1,491 steps and 29.38 s.

Our recomputation. The first preemption lands almost exactly where the arithmetic says the pool runs dry: 140 generated tokens against 147 of headroom per request. PagedAttention §4.5 describes the same situation: "As the number of requests and their outputs grow, vLLM can run out of the GPU's physical blocks."

Our recomputation. Capping at 64 never preempts, but 136 requests start out waiting: half of all requests wait 12 s or more for their first token, the last one 27.9 s, and throughput drops 16%. The small budget cuts the worst step to a third (better TBT) but doubles preemptions, because it admits all 200 over more steps while early requests are already growing, and recomputing a request takes several chunked steps.

Why it beats the alternatives

✗ Reserve for max length (Orca)

Never preempts, but it holds blocks for tokens that may never exist. Reserving a max length of 8,192 fits 53 requests and gives 4,097 tok/s with a TTFT p50 of 12.85 s. A tight 3,072-token cap (142 requests) matches vLLM in this burst, but only because every output here is known to stop by 1,024.

✓ Admit greedily, preempt when out (vLLM)

Admit while the next chunk's blocks fit, grow on demand, and evict whole requests, latest first, only when the pool is truly empty. All 200 run by 7.16 s: 5,177 tok/s, a TTFT p50 of 3.57 s, at a cost of 33 preemptions.

✗ Swap to CPU on preemption

PagedAttention's other option copies the victim's blocks over PCIe and back. It keeps the work done, but small blocks make for inefficient transfers, and the paper admits no new requests while any sequence is swapped out. V1 dropped it: "recomputation has lower overhead in the V1 architecture."

✗ Recompute, taken alone

This is the default and the right recovery, but it is not free: 77,487 re-prefilled tokens here (4.3% of the run at 100% MFU), and each victim's tokens stop until it gets back in. Frequent preemption is a sign that the knobs are wrong, not that it's working.

Numbers from the lab. The bottom row compares the two ways to recover KV (see PagedAttention II for a swap-vs-recompute cost estimate and III for §7.3's measurements). Neither is a way to avoid preemption.

Why does raising max_num_seqs sometimes lower throughput?

Because past the point where the KV pool binds, more admitted sequences don't make a bigger batch. They just make more requests that grow into the same blocks and evict each other. Every eviction throws away KV and spends compute rebuilding it, and bigger batches also mean longer steps and a worse TBT for everyone. In the lab, long outputs (512-token prompts, 2,048–4,096 outputs) at utilisation 0.5 give:

Going from 128 to 256 adds 49 preemptions and lowers throughput by 1%. The dip in our model is small because recompute is cheap for an 8B model at these lengths. It grows with longer contexts, larger models and real overheads, like scheduler CPU time and re-prefill slower than 100% MFU, which the model leaves out. This framing is ours; the vLLM docs simply say that if preemptions are frequent, "Decrease max_num_seqs or max_num_batched_tokens" or "Increase gpu_memory_utilization".

The right cap depends on context length. At 2k the pool holds 214 full sequences and at 8k only 53, so one value can't suit both. Chat traffic with short outputs rarely preempts, and there a high cap is simply better (the first table: 256 beats 64 by 19%). When you need guaranteed latency, cap lower, or look at cache-aware scheduling and disaggregation instead.

Run it yourself

Run it: labs/kv-admission.py [L] runs on your Mac in about 3 seconds using only the Python standard library. It prints the KV pool at 1.0 / 0.92 / 0.9 / 0.5, the per-GPU table, step 30's {request_id: num_tokens}, the burst timeline and first preemption, the knob table with the two Orca-style reservations, and the long-output table above. Try prompt=8192 (only 53 fit, 30 preemptions, 1,555 tok/s, and a cap of 53 doesn't prevent them, because outputs keep growing), out_lo=1 (early finishers free blocks and nothing is preempted) or budget=16384 (TTFT p50 3.52 s, but a worst step of 282 ms).
