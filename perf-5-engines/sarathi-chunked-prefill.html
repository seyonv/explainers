Sarathi-Serve II: chunked prefill and stall-free batching

Also called chunked prefill, token budget (max_num_batched_tokens in vLLM) or hybrid batching. Card 2 of 2 on Sarathi-Serve (Agrawal et al., OSDI '24). It walks §4 (design), §5 (evaluation) and §6 (related work) in order. Card 1 covers §1–3: why a prefill stalls every running decode.

In one breath

A decode iteration leaves most of the GPU's math idle, so the scheduler can fill it with prompt work. To do that without making running requests wait, it cuts each long prompt into chunks. Every iteration gets a fixed token budget τ: all running decodes go in first (one token each), then as much of one prompt as still fits. No iteration is ever much slower than a decode step, so no running request stalls. Prompts still get processed, a few hundred tokens at a time.

Where this sits

The dilemma from §1–3 (card 1): Prefill-prioritising schedulers (vLLM, Orca) get throughput but cause generation stalls: every running request freezes while a new prompt is processed. Decode-prioritising ones (FasterTransformer) avoid stalls but keep batches small. Sarathi-Serve's answer has two parts, and §5.4 shows you need both: chunked prefills (§4.1) and stall-free batching (§4.2), plus a rule for choosing the budget (§4.3).

§4.1 Chunked prefills: small enough to hide, big enough to saturate

The paper gives two reasons chunking works. First, "a prefill request with modest sequence length can effectively saturate GPU compute": in its Fig 4, prefill throughput starts to saturate at about 512 tokens. Second, real prompts are much longer than that. The median prompt is 1,730 tokens in openchat_sharegpt4 and 7,059 in arxiv_summarization (Table 2). So a prompt can be split into pieces that are each still large enough to use the GPU well.

Here is the running example, with the course's step-time model (our recomputation, labs/chunked-prefill-sim.py). A decode batch of 64 requests at 2k context takes 9.92 ms. Add prefill tokens to that same iteration and see what it costs:

Llama-3.1-8B BF16 on one H100, 100% of peak, our model. The first 256 prompt tokens cost almost nothing (+0.5 ms): the iteration is still waiting on the 16.06 GB weight read, and 2·8.03e9·256 FLOPs fit under it. A whole P90 prompt makes this one iteration 10.8× longer, so every one of the 64 users gets a ~108 ms gap. The paper's Fig 9 measures the same effect on real GPUs: naive hybrid batching raises TBT "up to 28.3×" over a decode-only batch (Mistral-7B on one A100, budget 256; LLaMA2-70B on four A100s, budget 512).

§4.2 Stall-free batching (Algorithm 3)

Each iteration's batch is built in a fixed order under a token budget τ, which comes from the TBT SLO (§4.3). Shortened from the paper:

τ ← compute_token_budget(TBT SLO) # once, offline loop every iteration: n ← 0; B ← running requests for each running request R that is decoding: # lines 6–8 n ← n + 1 # 1 token each, always included for each running R whose prompt is unfinished: # lines 9–12 c ← next chunk of R that fits in τ − n; n ← n + c while a new request fits in memory and n < τ: # lines 13–20 c ← its first chunk that fits in τ − n if c = 0: break n ← n + c; add it to B run B as ONE hybrid iteration # line 22 drop finished requests from B

Decodes are never delayed for a prefill. New requests only get what is left after running work is packed. The paper: "By restricting the computational load in every iteration, stall-free batching ensures that decodes never experience a generation stall due to a co-running prefill chunk."

§4.3 Choosing the token budget

A smaller τ means shorter iterations, so TBT is lower. It also means more chunks and more overhead. The paper names two overheads: lower GPU use per iteration and attention re-reading earlier chunks' KV (the first chunk's KV is "loaded N − 1 times" for N chunks). It says attention prefill stays compute-bound even at small chunks, and that "fixed overheads of kernel launch, etc." add a little more. Its rule: profile once and set τ to "the maximum number of tokens that can be packed in a batch without violating TBT SLO". In our model, one iteration costs:

The lab's "one-time profiling" (our model). The catch: P99 TBT is set by the worst iterations, which have bigger batches and longer contexts than this one. In the full simulation below, τ = 2,048 misses a 50 ms P99 above 10.8 req/s, and τ = 512 is the better choice there. That is why the paper profiles whole deployments with its simulator, Vidur, instead of one batch.

§4.4 Implementation, and where it lives today

Sarathi-Serve is built on vLLM. It added paged chunked prefill using FlashAttention v2 and FlashInfer kernels, and used the FlashAttention backend for all its experiments. It also added pipeline parallelism and telemetry. The idea has since become the default: in vLLM V1, "chunked prefill is enabled by default whenever possible", and "the scheduling policy prioritizes decode requests. It batches all pending decode requests before scheduling any prefill operations". max_num_batched_tokens plays the role of τ. The docs say smaller values such as 2,048 give better inter-token latency and larger ones give better TTFT. Setting it equal to max_model_len is "almost the equivalent to the V0 default scheduling policy (except that it still prioritizes decodes)". The scheduler card covers the rest of V1's unified token-budget scheduler.

Two more findings. First, Orca and vLLM usually break the P99 TBT SLO before they reach their maximum throughput, so relaxing the SLO helps them a lot. Second, vLLM beats Orca under the relaxed SLO. Orca batches several whole prompts together, which can mean an even longer stall, and without PagedAttention it can't run batches as large as vLLM's.

§5.2 The throughput–latency trade-off Fig 12

The authors sweep five P99 TBT SLOs for Mistral-7B and Yi-34B on openchat. They run vLLM at max batch 32, 64 and 128, and Sarathi-Serve at budgets 512 and 2,048. The key result: vLLM's capacity is "largely identical" for all three batch sizes. PagedAttention makes room for big batches, but with a latency target the stalls, not memory, set the limit. Sarathi-Serve reaches 3.5× vLLM's capacity at the strict SLO with τ = 512, and 1.65× at a relaxed 1 s with τ = 2,048 (Yi-34B).

Source inconsistency: the text attributes the 3.5× to "(100ms, Mistral-7B)" and the Fig 12 caption to Yi-34B. 100 ms is Mistral-7B's strict SLO in Table 3, which fits the text.

§5.3 Pipeline parallelism becomes viable Fig 13

Falcon-180B runs on two 4×A100 nodes linked by 100 Gbps Ethernet. Tensor parallelism across both nodes (TP8) gives about 2× the median decode latency of TP4 within a node plus PP2 across nodes, because of cross-node all-reduces. But vLLM with PP collapses under the strict SLO because of pipeline bubbles. Sarathi-Serve's evenly sized hybrid batches keep the stages busy: 4.3× vLLM TP8's capacity and 3.6× vLLM TP4-PP2's under strict SLOs, and 1.48× vLLM TP4-PP2's under relaxed ones.

§6 Related work: disaggregation instead

The other way to stop prefills disturbing decodes is to run them on different GPUs. The paper names Splitwise, DistServe and TetriInfer. These "can entirely eliminate the interference", and prefills run at full efficiency, so TTFT is better. The costs are that every request's KV cache has to be migrated after its prefill, which is "challenging in the absence of high-bandwidth interconnects", and that the prefill replicas' memory is under-used because only decode replicas hold KV. The paper leaves a quantitative comparison for future work. It also notes that APIServe has adopted Sarathi's chunked prefills. Course 4's Mooncake II shows a disaggregated system that still chunks its prefills, pipelining them across nodes.

Why it beats the alternatives

✗ Prefill-only iterations (vLLM V0)

Whole prompts get an iteration to themselves, which is good for TTFT. Every running user freezes for it: in our sim P99 TBT is 72.7 ms at 6 req/s, and capacity drops to 4.56 req/s at a 50 ms SLO.

✗ Hybrid with whole prompts (Orca)

Decodes ride along, but the iteration is as long as the whole prompt. Up to 28.3× a decode step in Fig 9, and 0.68 s P99 TBT in Table 4.

✗ Chunked only

Stalls become short, but chunks still take turns with decodes instead of sharing iterations. TTFT gets worst: 1.04 s vs 0.53 s in Table 4, and 78 vs 39 ms in our sim.

✓ Chunked + stall-free hybrid

Every iteration carries every decode plus a budget-sized chunk. P99 TBT is 0.14 s in Table 4 and capacity is 2.6–3.7× vLLM's in the paper. In our sim it's 12.75 req/s at 50 ms, 2.8× vLLM V0.

Doesn't chunking a prompt make its TTFT worse?

Somewhat. Each chunk re-reads earlier KV and pays fixed costs, and a chunk only gets the budget left after decodes. In Table 4, chunking on its own nearly doubles median TTFT on openchat: 1.04 s against 0.53 s for hybrid batching only. The combined scheduler gets back most of that (0.76 s) and has about 5× better P99 TBT than hybrid-only (0.14 vs 0.68 s). A bigger budget shrinks the cost: in our sim at 6 req/s, τ = 2,048 gives 38 ms median TTFT against vLLM V0's 36 ms, while τ = 512 gives 51 ms.

When it's not the right choice: if you serve one request at a time, or batch offline jobs with no TBT target, chunking only adds overhead. Use a large budget (vLLM's docs suggest > 8,192 for throughput) or turn chunking off. If TTFT matters more than smooth streaming and you have a fast interconnect, disaggregating prefill and decode removes the interference altogether, at the cost of moving KV between GPUs. And for very long prompts, a small τ means many iterations per prompt. The budget is a dial, not a fixed setting.
