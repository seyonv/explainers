Orca I: iteration-level scheduling and selective batching

Also called continuous batching, in-flight batching (TensorRT-LLM's name) or token-level batching. This card walks the Orca paper (Yu et al., OSDI '22) §1–3 in order: the problem, the background, and its two ideas, each answering a challenge (C1 → S1, C2 → S2). Orca's own experiments (GPT-3 on A100s) are on Orca II; the Llama-3.1-8B on H100 numbers here are our simulation.

In one breath

A language model answers a request by running many times, one token per run, and different requests need different numbers of runs. So instead of handing the GPU a fixed batch and waiting for all of it to finish, Orca's scheduler hands it one run ("iteration") at a time: finished requests leave after any iteration and new ones join at the next. To make such a mixed batch runnable, it batches every operation except attention over one flat list of tokens, and runs attention separately for each request.

The problem (§1)

At the time, you served a model with two layers of software. A serving system such as Triton Inference Server takes requests and groups them into batches; an execution engine such as FasterTransformer runs the model on a batch. That split was built for models like ResNet or BERT, where a request is one run of the model. A generative model like GPT must run once per output token, and "the serving system schedules the execution of the engine at the granularity of request". So a request that finishes early can't return, and a request that arrives mid-batch waits for the whole batch.

The state grows. Attention needs the keys and values of every earlier token. Instead of recomputing them each iteration, systems since fairseq's "incremental decoding" keep them (the KV cache). Unlike an LSTM, whose state stays the same size, the Transformer's k and v at layer l grow from kl,1:t−1 to kl,1:t each iteration, so attention works on tensors whose shape depends on how many tokens that request has processed. For Llama-3.1-8B that's +128 KiB per token.

S1: iteration-level scheduling

The scheduler repeats three steps: (1) select requests to run next, (2) invoke the engine to execute one iteration for them, (3) receive the results. Because it hears back every iteration, it can return a finished request immediately, and a new request waits at most for the iteration in flight. The scheduler "has a full control on how many and which requests are processed in each iteration".

Fig 4, redrawn with the paper's tokens: xij is token j of request i. Grey tokens came from the client, green ones were generated. x1 has run 2 iterations; x3 and x4 haven't started, so the scheduler hands the engine their prompts. One iteration returns exactly one new token per request. Which requests to pick (FCFS, a max batch size, KV memory reservation) is Algorithm 1 on Orca II.

Why it matters on an H100: the batch must stay full

At B = 1, 16.06 GB of weights buy ONE token.

So every slot left empty, or spent on a request that's already finished, throws away most of a token's worth of the weight read. Request-level batching does both: slots go idle as requests finish, and new work can't fill them.

C2: batching an arbitrary set of requests

Iteration-level scheduling creates a new problem. To batch, every request must run "identical operations, each consuming identically-shaped input tensors". The scheduler now picks requests at different points in their life, and for a pair of requests there are three cases where the next iteration can't be batched:

Batching then needs requests in the same phase with the same length or index. The paper: "The likelihood further decreases exponentially as the batch size increases", so an engine without a fix would be stuck at tiny batches, exactly where the step-time formula says the H100 is wasted.

S2: selective batching

Most operations don't care which request a token belongs to. Instead of a [B, L, H] tensor (batch × tokens × hidden), selective batching flattens every token in the iteration into one 2-D tensor of shape [ΣL, H] and runs Linear, LayerNorm, Add and GeLU on it directly. Only attention needs the notion of a request, so the batch is split just before attention, each request runs its own attention, and the outputs are merged back to [ΣL, H]. Requests in the increment phase fetch their earlier keys and values from the Attention K/V manager, which keeps them per request until the scheduler says the request is finished.

Why is leaving attention unbatched acceptable? The paper's answer (§1):

"Since the Attention operation is not associated with any model parameters, applying batching to Attention has no benefit of reducing the amount of GPU memory reads by reusing the loaded parameters across multiple requests."
Llama-3.1-8B, B = 64, 2,048-token contexts (our arithmetic): weights 16.06 GB, read once, shared by all 64 → batching saves 63 × 16.06 GB KV 64 × 2,048 × 131,072 B = 17.18 GB, each request reads only its own → batching attention saves nothing

Our framing, not the paper's: modern engines do batch attention too, for other reasons (launch overhead and GPU occupancy with many small requests). They keep the flat [ΣL, H] layout and run one attention kernel over the whole ragged batch, reading each request's KV through a block table. FlashInfer stores queries and outputs "as ragged tensors … without padding, which facilitates the compact packing of queries and outputs from diverse requests into a single tensor" (see FlashAttention-3, -4 and FlashInfer). Split-then-merge became one varlen kernel; the flat token batch is Orca's.

Why it beats the alternatives

✗ Request-level batching

FasterTransformer behind Triton: the batch is fixed until its longest request ends. In our run 49% of decode slots compute finished requests, peak throughput is 3,120 tok/s, and mean TTFT is 4.7 s at a load iteration-level serves in 13 ms.

✗ Padding to the max length

Make shapes equal by padding every request to the longest prompt, or treating finished rows as padding. This batches, but pad tokens cost real FLOPs and KV slots, and it's still one batch at a time: nobody joins or leaves.

✗ Iteration-level without selective batching

S1 alone. The scheduler may only batch requests in the same phase with the same length or token index, which gets exponentially less likely as the batch grows, so a new prompt can't join 63 decodes. Batches stay tiny, where an H100 makes 205 tok/s.

✓ Iteration-level + selective batching

Re-pick the batch every iteration and flatten all tokens to [ΣL, H], splitting only for attention. Any mix of prefills and decodes runs together, so slots refill as soon as they free: 0% waste, 1.93× peak throughput, TTFT ≈ one iteration.

Is "continuous batching" the same as Orca's iteration-level scheduling?

Yes, in spirit. "Continuous batching" and "in-flight batching" are the industry's names; the paper never uses either. The FlashInfer paper (§5.4) says "Orca … introduces continuous batching". Kiely's Inference Engineering (pp. 186–187) defines it as "swapping in requests as slots become available", with requests "batched at the token level", and says vLLM, SGLang and TensorRT-LLM ("in-flight batching") implement it. The vLLM V1 blog calls vLLM "a full-fledged continuous batching engine". What those engines run differs from 2022 Orca in details: paged KV instead of Orca's per-request slot reservation, attention batched as above, and chunked prefill (next point).

It isn't free, and not always the best choice. Putting a whole prompt into the same iteration as 63 decodes makes that iteration long: every decoding user waits for it. That "generation stall" is what Sarathi-Serve fixes by chunking prefills. For offline jobs where every request has the same, known length (say, scoring a fixed set of equal-length prompts), static batching wastes nothing and is simpler. And iteration-level scheduling doesn't decide which requests fit: KV memory does, which is the job of the scheduler and paged memory.
