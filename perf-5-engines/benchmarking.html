Benchmarking a server

Also called load testing, the throughput–latency curve, a load generator, goodput, MLPerf scenarios, burstiness. This card is about measuring a whole server under load: what curve to draw, what traffic to send it (the MLPerf Inference scenarios, closed vs open loop, BurstGPT's real Azure traces) and what to report (the metrics vllm bench serve prints). The worked example is our own llama-server sweep on the Mac, and the H100 script repeats it with vLLM on the running example.

In one breath

A server has no single "speed". It has a curve. As you push more load in, total tokens per second rises while every user's latency gets worse, until the server saturates. Benchmarking means drawing that curve with traffic shaped like real users' (random arrivals, bursts, mixed lengths, no free cache hits), reading off latency percentiles, and reporting how much load it can take while still meeting a latency target. That last number is goodput.

1. The object you measure: the throughput–latency curve

We ran Llama-3.2-3B (Q4_K_M) under llama-server on the Mac. For each concurrency C, the server got C parallel slots and C requests fired at once: ~150-token prompts, 128 output tokens, temperature 0, prompt cache off, median of 3 runs. Caveat: the Mac was busy with other work during these runs (load average ≈ 33 on 8 cores). Treat every timing as rough and re-run the lab on an idle machine.

Reading it. The shape is the textbook trade-off: batching lets one pass over the weights serve more users, so the server's total rises while each user's stream slows and their first token waits behind everyone else's prefill. That is the same trade course 1 computed for the H100 (serving metrics: 207 tok/s at batch 1 → 12,050 total at batch 120, each user down to 100). A benchmark's job is to draw this curve for your server and find where it crosses your latency target.

The odd part. Throughput doesn't rise smoothly. It dips at C = 4–8 (36 tok/s, below C = 2's 48) and then jumps at C = 16 (100). This repeated in all three runs (C = 16: 100.2 / 92.7 / 102.0), so it isn't noise. Our guess, not verified: llama.cpp's Metal backend switches from matrix–vector to matrix–matrix kernels once the batch is large enough, and the middle batch sizes fall between the two. Don't read it as a general law. vLLM on an H100 has different kernels and needn't show it. The lesson that does generalise: measure every point you care about, because a curve interpolated from C = 2 and C = 16 would miss a whole region.

2. The load you send: shape matters as much as size

Two habits worth stealing: the metric is always a rate under a latency bound, never raw throughput alone, and the number of requests is set by the percentile you claim. A p99 from 100 requests is one request.

Closed loop vs open loop

A closed-loop client keeps C requests in flight: each finishes, the next one starts. Our Mac sweep is closed-loop, and so is vLLM's --max-concurrency. An open-loop client sends requests on its own clock, whatever the server is doing, as MLPerf's server scenario does with Poisson arrivals. Real users are open-loop: a thousand people don't wait for each other's answers before typing.

The difference shows when the server slows down. vLLM's docs warn that with --max-concurrency, "the actual request rate may be lower than specified with --request-rate, if the server is not processing requests fast enough to keep up." The load politely backs off, so the queue that real users would build never forms, and its wait never shows up in TTFT. Our note: load-testing folk call this kind of hidden queueing "coordinated omission". We didn't open a source for the term, so take it as our gloss. The docs still call the closed-loop pattern (--request-rate inf --max-concurrency N) "the most commonly used configuration for production benchmarking". It is the right tool for finding peak throughput at a concurrency cap. It is the wrong tool for measuring latency at a given traffic level.

Burstiness: same average, different day · vLLM's --burstiness

vllm bench serve draws the gaps between requests from a Gamma distribution with shape = burstiness and mean = 1 / rate. The coefficient of variation is CV = 1/√burstiness. So 1 gives a Poisson process (CV = 1), 5 gives near-even spacing (CV ≈ 0.45), and 0.1 gives heavy bursts (CV ≈ 3.16). What real traffic looks like: BurstGPT · Wang et al., KDD '25, §3

BurstGPT is 10.31 million request traces from regional Azure OpenAI GPT services (ChatGPT and GPT-4) over 213 days. Each row has a timestamp, the model, request and response token counts, and whether the call came from the conversation UI or the API. What it found:

  • Burstiness shifts over time. Fitted every 20 minutes with a Gamma distribution, the shape α changes sharply during working hours (conversation). For the API, both α and the rate β swing through the day. "A smaller α indicates a higher coefficient of variation … meaning the workload is more bursty". That is the same knob as vLLM's --burstiness.
  • Conversation traffic is periodic, API traffic isn't. Chat volume peaks on weekdays and in working hours. API traffic is "aperiodic … characterized by burstiness": irregular, dense clumps.
  • Lengths are skewed. Request lengths follow a Zipf distribution: many short, a long tail. ChatGPT's response lengths are bimodal. A fixed 1,024-in / 128-out benchmark is neither.
  • Conversations are short. Over 35% end after one request; the median is 2 and 75% have four or fewer. Multi-turn prefix reuse is real but modest.

The paper's point for benchmarkers: a scheduler tuned on smooth, uniform traffic can lose its edge on these patterns. Their example is an FCFS tweak that helps conversation traffic but less so API traffic, and they tie failure spikes to KV-cache pressure during bursts.

3. What to report

vllm bench serve measures at the client. Its docs define the latency metrics like this, and they warn that "metric terminology is not standardized across benchmarking tools", so compare formulas, not names:

TPOT= E2Esend → last token−TTFTsend → first token noutput tokens−1
E2Eend-to-end latency of one request, at the client4.42 s (Mac, C = 1) TTFTincludes queueing and the prefill0.42 s noutput tokens the request produced128

Filled in for our Mac C = 1 row: E2E = 0.421 + 127 × 0.0315 = 4.42 s, so TPOT = (4.42 − 0.42) / 127 = 31.5 ms. TPOT is one number per request. ITL is every gap between streamed chunks, pooled across requests.

Goodput on the Mac is judged on the slowest TTFT and the median TPOT, because the sweep kept no per-request TPOTs. The best goodput sits at C = 2, not at the throughput peak: C = 4 meets the SLO too, but at 36.1 tok/s. The docs' sample run doesn't name its GPU, so use it only for the metric definitions.

The checklist

  • State ISL and OSL (and whether you set --ignore-eos). A 1,024/256 run and a 150/128 run aren't the same benchmark. Real traffic has Zipf-shaped inputs and bimodal outputs, so run a trace-shaped dataset too (vLLM's list includes sharegpt and burstgpt).
  • Warm up. The first requests pay for compilation, CUDA-graph capture and cold caches. MLPerf lets the system do "cache warmup" untimed. vLLM has --num-warmups, and our lab sends one untimed request per server start.
  • Fix seeds, and change them between runs. --seed (default 0) makes the random dataset reproducible. That is exactly why reruns hit the prefix cache.
  • Avoid the prefix-cache trap. vLLM's docs: "Repeating vllm bench serve against the same server can reuse prompts left in the prefix cache and inflate throughput." Identical prompts, or a shared system prompt, get their prefill for free (RadixAttention). Vary the seed, restart the server, or measure the hit rate on purpose. Our lab turns the cache off and puts a different ticket number in every prompt.
  • Run long enough for the percentile you report (MLPerf: ≥ 60 s, and 270k queries for a p99). Repeat runs and show the spread, as our three runs do.
  • Report the curve plus goodput at a stated SLO, not one throughput number.

Why it beats the alternatives

✗ Time a single request

Measures single-stream latency only: 28.9 tok/s on our Mac hides that the server can do 100.2 at C = 16. It says nothing about queueing, batching or the tail. Misleading as a "server speed".

✗ Closed loop at fixed concurrency

Simple and good for peak throughput at a cap. But load backs off when the server slows, so the queue never builds and TTFT looks better than users would see.

✓ Open loop, Poisson at a request rate

What independent users actually do, and MLPerf's server scenario. Sweep the rate, read P50/P99 TTFT and TPOT, and report the highest rate that meets the SLO: the capacity, and the goodput at it.

✗ Replay a bursty trace (BurstGPT-like)

The most realistic: bursts, Zipf lengths, bimodal outputs. But it's harder to reproduce and compare, and a trace from someone else's service may not match yours. Use it as the final check, not the only one.

Why does my benchmark look great but production feels slow?

Usually because the benchmark quietly left out what production has:

  • Cache hits. Repeated or identical prompts reuse the prefix cache, so the prefill is nearly free. Production prompts are mostly new, apart from shared system prompts.
  • Uniform lengths. 1,024 in / 128 out every time. Real inputs are Zipf-skewed with long outliers, and one 30k-token prompt stalls everyone's decode (see chunked prefill).
  • No bursts. Closed loop or smooth Poisson at the average rate. Real traffic arrives in clumps: at CV 2, the busiest second in our draw held 15 requests against an average of 1.
  • No tail. Only the mean or median was reported, or too few requests to estimate a P99. Users, and agents that make many calls, live in the tail (tail latency).

When the simple benchmark is the right one: offline batch work, such as evals, bulk summarising or synthetic data. There nobody waits on one request, so the offline scenario (--request-rate inf, total tokens/s) is the honest metric. The single-request timing is also right when you really serve one user, like our Mac.
