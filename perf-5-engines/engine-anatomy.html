Anatomy of vLLM and SGLang

Also called: engine core, model runner, busy loop, detokenizer, overlap scheduling. This card follows one request through vLLM V1's processes (vLLM architecture docs and the January 2025 V1 blog) and then sets SGLang's layout and its "zero-overhead" overlap scheduler (v0.4 blog) beside it. The GPU step times are the running example from course 2. Every CPU cost on this card is an illustrative "what if", because neither source gives a per-step CPU number for our setup.

In one breath

An inference engine is a small distributed system on one machine. A front-end process speaks HTTP, tokenizes, and later detokenizes and streams. A separate engine process runs a tight loop that asks the scheduler for the next batch and hands it to one worker process per GPU, which builds tensors, replays a CUDA graph and samples. The GPU step for a small model is only a few milliseconds, so every millisecond of Python on the critical path shows up in throughput. The design question is how much CPU work you can move off that path (vLLM V1) or hide under the GPU step (SGLang's overlap scheduler).

Process layout from the vLLM architecture overview; component names from the V1 blog, the CUDA Graphs design doc and vllm/v1/engine/async_llm.py. Simplified: one GPU, no data parallelism.

  1. API server. The docs: it "handles HTTP requests (e.g., the OpenAI-compatible API), performs input processing (tokenization, multi-modal data loading), and streams results back to clients."
  2. ZMQ. The tokenized request crosses to the engine process over ZeroMQ sockets. With data parallelism, "each API server connects to all engine cores via ZMQ in a many-to-many topology".
  3. EngineCore busy loop. It "runs the scheduler, manages KV cache, and coordinates model execution across GPU workers. It runs a busy loop that continuously schedules requests and dispatches work to the GPU workers." Each step the scheduler emits a dictionary such as {req_A: 1, req_B: 1, req_C: 512} (illustrative): how many tokens each request advances under the token budget. The scheduler card covers the rules.
  4. Executor → worker. The step goes to one worker process per GPU. V1 caches request state on the worker side and sends "only incremental updates (diffs) at each step".
  5. Model runner. It prepares input tensors and captures CUDA graphs. V1's "Persistent Batch" "caches the input tensors and only applies the diffs to them at each step", using NumPy instead of Python loops. The forward pass then replays a captured graph. The default cudagraph_mode is FULL_AND_PIECEWISE: a "full CUDA Graph for uniform decode, piecewise CUDA Graphs for others" (course 3's fusion and CUDA graphs card explains capture, replay and padding). Attention runs in a backend kernel library such as FlashAttention or FlashInfer.
  6. Sampler. Logits processors (temperature, penalties, bad words), the structured-output token mask (structured outputs card), then top-k/top-p sampling to one token id per sequence.
  7. Back to EngineCore. The loop appends the new token ids, frees finished requests' KV blocks, and immediately schedules the next step. Token ids travel back over ZMQ.
  8. OutputProcessor, in the front-end process. It turns token ids back into text and streams it. vLLM has no separate detokenizer process: AsyncLLM owns an OutputProcessor (source comment: "Adding the Request to the Detokenizer"). SGLang, below, does run a separate one.

Worked example: what 1 ms of CPU costs the running example

The V1 blog names the problem: "the CPU overhead for tasks like running the API server, scheduling work, preparing inputs, de-tokenizing outputs, and streaming responses to users becomes increasingly pronounced. This issue is particularly noticeable with smaller models like Llama-8B running on NVIDIA H100 GPUs, where execution time on the GPU is as low as ~5ms." That is our running example. Course 2's step formula gives Llama-3.1-8B on one H100 at 2k context a decode step of 4.87 ms at batch 1 and 23.86 ms at batch 238. Small batches, small models and fast GPUs are where CPU overhead bites, which is also where CUDA graphs matter most: a batch-1 step is hundreds of small kernels, and launching them one by one is CPU time too. Why V1 moved to an isolated busy loop

vLLM V0 ran the scheduler in the same process as the first GPU worker and rebuilt input tensors every step. V1's goal list includes "near-zero CPU overhead", and it gets there in pieces:

  • Take the front end off the loop. V1 creates "an isolated EngineCore execution loop that focuses exclusively on the scheduler and model executor", so "tokenization, multimodal input processing, de-tokenization, and request streaming" overlap with it in another process.
  • Make each remaining piece cheap. Persistent batch (diffs instead of rebuilds), worker-side request state (diffs over IPC), prefix caching with O(1) eviction and minimal "Python object creation overhead" (< 1% throughput cost even at a 0% hit rate, so it's on by default), and piecewise CUDA graphs.
  • Result. "Up to 1.7x higher throughput compared to V0 (without multi-step scheduling)". The blog attributes it to CPU work: "the kernels used for V0 and V1 are almost identical, the performance difference is mainly due to the architectural improvements (reduced CPU overheads)". Measured by the vLLM team on Llama 3.1 8B and Llama 3.3 70B with ShareGPT.

What isolation does not remove, as we read it: scheduling and input preparation still sit inside the loop, between one GPU step and the next. That is the gap SGLang's overlap scheduler goes after. Current vLLM has a similar option, --async-scheduling ("helps to avoid gaps in GPU utilization, leading to better latency and throughput"). Whether it is on by default depends on the version and configuration, so check your release.

SGLang for contrast

SGLang's Engine docstring lists three components: a TokenizerManager that "Tokenizes the requests and sends them to the scheduler"; a Scheduler (subprocess) that "schedules batches, forwards them, and sends the output tokens to the Detokenizer Manager"; and a DetokenizerManager (subprocess) that "Detokenizes the output tokens and sends the result back to the Tokenizer Manager". "The HTTP server, Engine, and TokenizerManager all run in the main process", and the processes talk "via the ZMQ library". So detokenization gets its own process here, unlike vLLM.

The v0.4 blog (December 2024) starts from the same observation as vLLM: "An unoptimized inference engine can spend as much as half of its time on CPU overhead." Its fix: "The scheduler runs one batch ahead and prepares all the metadata required for the next batch. By doing this, we can keep the GPUs always busy and hide expensive overheads such as the radix cache operations." The prefix lookups against the radix tree (RadixAttention card) are part of what gets hidden. The catch is that batch n+1 is prepared before batch n has sampled its tokens, so the implementation creates "future tokens" and carefully schedules CUDA events. The reported gain: "a 1.1x speedup against its previous version and a 1.3x speedup against other state-of-the-art baselines", "most significant on small models and large tensor parallelism sizes". It is on by default; --disable-overlap-schedule turns it off.

Four ways to keep the GPU fed

✗ Synchronous loop

Receive, tokenize, schedule, build tensors, run the GPU, sample, detokenize, stream, then repeat, all in one Python process. Every CPU millisecond is a GPU idle millisecond: 1 ms costs the batch-1 example 17% of its tokens (205 → 170 tok/s).

✗ Isolated busy loop + API process (vLLM V1)

Moves tokenization, detokenization and streaming to another process and makes each step's bookkeeping cheap: up to 1.7× over V0. On its own, the scheduling and input preparation left inside the loop still run between GPU steps.

✗ CUDA graphs

Replaces hundreds of per-kernel launches inside the step with one replay, which matters most at batch 1. But it only speeds up the inside of a step. The scheduling between steps is untouched, and each graph is fixed to a captured batch size.

✓ Overlap scheduling, one batch ahead (SGLang)

The CPU prepares batch n+1 while the GPU runs batch n, so step time becomes max(GPU, CPU) instead of their sum. That's the only one of the four that hides scheduling time itself; SGLang's Nsight trace shows "no single idle time on the GPU" across five decode batches (Triton attention backend). Real engines stack all three fixes.

Why is detokenization a performance topic at all?

Turning an id back into text looks trivial. But it has to be done incrementally: a single token can be half a UTF-8 character or a word piece whose spacing depends on its neighbours, so the engine keeps per-request state and decides each step how much new text is safe to emit. Then it frames and sends a streaming chunk. At batch 1 that happens 205 times a second. At batch 238 it happens 9,973 times a second across 238 streams (our recomputation), all in Python, and it has to keep up with the GPU. If it ran inside the busy loop, the GPU would wait for it every step. That is why vLLM V1 lists "de-tokenizing outputs, and streaming responses" among the CPU costs it moved off the loop, and why SGLang gives detokenization its own process. vLLM also has stream_interval: a larger value "reduces host overhead and may increase throughput by batching multiple tokens before sending", at the price of choppier streaming.

When none of this matters much: big models and big batches. The same 1 ms is 20.5% of a batch-1 step but 4.2% of a batch-238 step, and a 70B model's steps are longer still. SGLang's own blog says the overlap gain is "most significant on small models and large tensor parallelism sizes". Overlap also has a cost: it's harder to build, because the next batch is planned before this batch's tokens exist (the "future tokens" trick), and --disable-overlap-schedule exists for when that gets in the way. We have no per-token detokenization cost in µs from a source, so the card gives rates, not CPU percentages.
