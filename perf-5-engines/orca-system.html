Before this: Orca I: iteration-level scheduling and selective batching

Orca II: the distributed engine and its results

Also called the engine master and workers, control plane vs data plane, KV slot reservation, or max_tokens. Card 2 of 2 on Orca (Yu et al., OSDI '22): §4–8 in order, meaning how the engine is spread over many GPUs, the scheduling algorithm (Algorithm 1), the implementation, the evaluation behind the famous 36.9×, and related work. The paper's numbers are GPT-3-shaped models on 40 GB A100s; Llama-3.1-8B on an H100 is our recomputation.

In one breath

Orca splits a big model over GPUs, sends the "what to run next" messages on a CPU channel (gRPC) and the tensors on a GPU channel (NCCL), and schedules one iteration at a time, first come first served. Each new request reserves KV memory for its longest possible length, so a request can never get stuck halfway. Kernel for kernel, the engine is about as fast as FasterTransformer. The 36.9× comes from scheduling: at the same latency, Orca keeps far more requests in each batch.

§4.1 Splitting the model over GPUs

Orca combines the two model-parallel schemes that were first built for training (and that FasterTransformer also uses). Intra-layer parallelism (today: tensor parallelism) splits each matrix multiplication and its weights across GPUs. Inter-layer parallelism (today: pipeline parallelism) gives each GPU group a run of whole layers, the same number of layers each. Fig 6 applies both to a toy 4-layer GPT on 6 GPUs:

Fig 6 redrawn: 2 inter-layer partitions × 3 intra-layer partitions = 6 GPUs. The paper omits how each matrix is cut; "thirds" is our shorthand.

The engine: one master, one worker per pipeline stage (Fig 7)

Fig 7 redrawn for the Fig 6 split. Solid grey = control messages on a CPU channel; dashed green = tensors between GPUs. Each worker runs one CPU thread per GPU it controls; workers can sit on different machines.

One iteration, step by step (§4.1):

  1. The engine master sends Worker1 the tokens for this iteration plus a control message: the request ids in the batch, the current token index of each decoding request, and the number of input tokens of each new one.
  2. Worker1's GPU threads turn that into kernel launches. The attention kernel, for example, uses the request id and token index to find that request's earlier keys and values in the Attention K/V manager.
  3. Meanwhile Worker1's controller forwards the control message to Worker2 without waiting for its own kernels to finish, so Worker2's CPU can prepare while Worker1's GPUs compute.
  4. Only the last worker waits for its GPUs, to read the output token of each request and send it back to the master.

Why a separate channel. FasterTransformer and Megatron-LM pass these control messages (batch size, sequence lengths, which requests finished) over NCCL, a GPU-to-GPU channel. The CPU needs them to decide which kernels to launch, so every process has to synchronise the CPU with the GPU each time a message arrives, which happens every iteration. Orca sends control messages over gRPC, which never touches the GPU, and keeps NCCL for tensors that GPUs produce and consume. The CPU can then stay ahead of the GPU instead of stalling once per iteration. The paper measures this later: up to 47% faster on the 175B model (§6.1).

§4.2 The scheduling algorithm

Iteration-level FCFS. Orca never reorders requests. Its definition: for any two requests in the pool, if xi arrived before xj, then xi has run the same number of iterations as xj or more. A later request can still finish first if it needs fewer iterations.

Two more things constrain each choice:

  • Max batch size (max_bs). A bigger batch raises throughput and latency together, and each extra request adds less throughput than the one before. So, like Triton and Clipper, Orca caps the batch; the operator tunes the cap against a latency budget.
  • KV memory. Buffers for intermediate results are reused at once, but a request's keys and values stay until it finishes. A naive scheduler can deadlock: every running request needs one more slot for its next token, no slot is free, and nobody can finish to free one. Orca's fix: when a request is scheduled for the first time, reserve max_tokens slots for it, the most tokens it can ever hold (input plus maximum output). If the reservation fits, the request is guaranteed to finish.
Algorithm 1, shortened (paper line numbers on the right) params: n_workers, max_bs, n_slots loop: batch = Select(pool) # 4 launch one iteration; don't wait # 5 n_scheduled += 1 # 8 if n_scheduled == n_workers: # 9 pipe full wait for the oldest batch # 10 finished: n_rsrv -= req.max_tokens # 14 free slots n_scheduled -= 1 # 15 Select(pool): for req not RUNNING, oldest first: # 19-21 FCFS if len(batch) == max_bs: stop # 22 if req is new: # 23 if n_rsrv + req.max_tokens > n_slots: stop # 25 can't reserve n_rsrv += req.max_tokens # 26 worst case add req to batch # 27

Arrivals and returns happen in other threads that add requests to the pool and remove finished ones. Note that a new request that doesn't fit stops the scan (break), so no younger request jumps it: that is what keeps FCFS.

Sizing n_slots. Choosing max_bs means measuring a latency–throughput trade-off, but n_slots needs no experiment: given the model shape and the parallel split, memory use depends mostly on n_slots, so the operator sets the largest value that fits. How many requests that admits:

Pipeline parallelism without microbatches (Fig 8)

With pipeline stages, the scheduler doesn't wait for a batch to come back before sending the next: it keeps n_workers batches in flight (lines 9–10), so every worker is always busy. When batch AB returns, A and B are the oldest requests again, so they go straight back in. FasterTransformer, driven by Triton at request level, can't add request C until batch AB has fully finished. To use a pipeline at all it cuts AB into microbatches A and B, which shrinks the batch each stage runs and leaves bubbles whenever there are fewer microbatches than stages.

Fig 8 redrawn with 3 stages and max batch size 2; Xi is iteration i of request X. The bubble positions in (b) are our reconstruction: A2 can't start until A1 leaves the last stage. FasterTransformer must trade batch efficiency (bigger microbatches) against bubbles (more microbatches); Orca doesn't face that trade-off.

§5 Implementation

13K lines of C++ on CUDA; gRPC for the control plane and NCCL for the data plane (both the intra- and inter-layer traffic). Fused kernels for LayerNorm, Attention and GeLU, as in other Transformer systems; the attention kernel fuses the dot products with keys, the softmax and the weighted sum of values into one. Then one step further: selective batching (card I) runs attention separately per request, and Orca fuses those per-request kernels into one launch by concatenating their thread blocks. Blocks in one kernel then work on tensors of different shapes and live for different times, which CUDA practice usually discourages, but the paper finds it raises GPU utilisation and cuts launch overhead (see kernel fusion and launch overhead).

§6.1 Engine alone (no scheduler)

The same batch is fed in again and again until it finishes, which mimics request-level scheduling; every request has 32 or 128 input tokens and generates 32. What it shows:

  • 13B (1 GPU) and 101B (8 GPUs): about equal, or Orca slightly slower. Orca doesn't batch attention (selective batching), FasterTransformer batches everything. The gap is small because attention has no weights to reuse across requests.
  • FasterTransformer runs out of memory at batch 8 or more on 13B and 16 or more on 101B, because it preallocates KV for every request at the model's max length, 2,048. Orca sizes each request's buffer from its own max_tokens.
  • 175B (2 stages, pipelining turned off in both): Orca up to 47% faster, which the authors attribute to the control/data-plane split. 341B is omitted as similar.
Our check of the OOM points (FP16, KV per token = 2 × hidden × layers × 2 B): 13B: 2 × 5,120 × 40 × 2 = 800 KiB/token → × 2,048 = 1.68 GB per request 40 GB − 25.2 GB weights = 14.8 GB → 8.8 requests before activations 101B: 2 × 10,240 × 80 × 2 = 3,200 KiB/token → × 2,048 = 6.71 GB per request 320 GB − 201 GB weights = 119 GB → 17.7 requests before activations

Our inference: once activations and workspace take their share, 8 and 16 no longer fit, which matches the batch sizes where FasterTransformer's entries go missing in Fig 9 (the paper marks out-of-memory runs as missing).

§6.2 End to end: where 36.9× comes from

Now the full stack, scheduler included. FasterTransformer gets a custom scheduler that takes up to max_bs requests from the queue, like Triton and TensorFlow Serving. Fig 10 plots median latency, normalised by each request's number of generated tokens, against throughput for 101B, 175B and 341B.

190 ms/token = 2 × Orca's normalised execution time at batch 128 in Fig 9c (so ≈ 95 ms/token) 6.81 req/s ÷ 0.185 req/s = 36.81 → the paper prints 36.9× (the inputs are rounded)
  • 101B at low load is the one case where Orca doesn't win: there aren't enough requests to batch, so latency is just engine speed, and the engines are about equal (6.1). As load grows, Orca's throughput rises with little extra latency because late arrivals "hitch a ride" on the running batch. FasterTransformer peaks at 0.49 req/s on 101B: it can't cope with requests that arrive at different times, need different numbers of iterations, or start with different input lengths.
  • 175B and 341B (more than one pipeline stage): Orca wins at every load on both latency and throughput, an order of magnitude more throughput at similar latency.
  • Raising Orca's max_bs (1 → 8 → 16 → 32) raised throughput without hurting latency here, because early finishers leave and new arrivals join each iteration. The paper warns this isn't guaranteed on other hardware, models or workloads.
  • Raising FasterTransformer's didn't help. Over all (max_bs, microbatch size) pairs the best were (1, 1) and (8, 8): a microbatch smaller than the batch shrinks what each stage batches, and a bigger batch mixes more lengths. FasterTransformer runs the first iteration as if every input were as short as the shortest one, and early finishers can't return.
  • Homogeneous traces (Fig 11, 175B): with every request at (32 in, 32 out) or (256, 256), nobody finishes early, so a bigger batch now does help FasterTransformer. Orca still beats FasterTransformer at max_bs 8, except Orca at max_bs 1, which is just a pipeline with no batching.

§7 Related work, §8 conclusion

BatchMaker (for RNNs) already scheduled and batched at the level of cells, so requests could join and leave a running batch. It can't do this for Transformers: the cell for token t needs its own keys and values, so a model with L tokens has L different cells (L runs from 33 to 640 in Orca's traces), identical cells rarely line up, and execution falls back to one at a time. It also lacks model and pipeline parallelism. Orca's principle instead: "perform as much computation as possible per each round of model parameter read", because reading weights from GPU memory is the main bottleneck for large models. Every ready token goes into one weight read, whether or not its attention can be batched. That is the same memory-bound argument as the critical batch size.

The authors also note that engines like FasterTransformer, LightSeq, TurboTransformers and EET sit behind serving layers (Triton, TensorFlow Serving) that schedule whole requests; iteration-level scheduling needs the scheduler and engine tightly joined, and a general interface for that is left to future work. §8 sums up: iteration-level scheduling plus selective batching give an order of magnitude more throughput than the state of the art at the same latency.

Our framing: the reservation is the waste PagedAttention removed

Reserving max_tokens prevents deadlock, but a request holds its whole reservation while it uses only part of it. Two years later, the PagedAttention paper profiled its reimplementations of Orca and found only 20.4%–38.2% of KV memory holding real tokens (vLLM Fig 2; PagedAttention I). vLLM kept Orca's iteration-level scheduling and replaced the reservation with blocks allocated as tokens arrive, plus preemption as the answer to deadlock. This link is our framing; Orca's paper doesn't discuss the waste.

Why it beats the alternatives (in 2022)

✗ FasterTransformer

Request-level batches from Triton, KV preallocated for the full 2,048 tokens. Fast kernels, but out of memory at batch 8 on 13B, and at 190 ms/token on 175B only 0.185 req/s.

✓ Orca

Iteration-level FCFS, selective batching, max_tokens reservation that can't deadlock, and a gRPC control plane. Same kernels, but 6.81 req/s at that latency: 36.9×.

✗ Orca + microbatch pipelining

Splitting each batch across pipeline stages, FasterTransformer-style, would shrink what each stage batches and add bubbles when microbatches < stages. Orca instead keeps n_workers whole batches in flight.

✗ Not yet: vLLM (Orca + paging)

Orca's scheduling with KV allocated in blocks as needed: 952 vs 238 requests in our H100 example, 1.7–2.7× Orca (Oracle) in the vLLM paper. It came in 2023 and now beats Orca; in 2022 Orca was the best on offer.

Where does 36.9× come from if the engine alone is about as fast as FasterTransformer?

From scheduling, not kernels. §6.1 gives both engines the same fixed batch, and they take about the same time (Orca is even a little slower on 13B/101B because it doesn't batch attention). §6.2 feeds them a stream of requests of different lengths arriving at random. FasterTransformer then waits for whole batches, keeps finished requests in them, pads to the shortest input and preallocates for 2,048 tokens, so its batches stay tiny; Orca adds and removes requests every iteration, so each weight read serves many more tokens. The only engine-level gain in the number is the up-to-47% from the control plane on multi-stage models.

Don't read 36.9× as "continuous batching is 37× faster". It is one point (175B, 190 ms/token) against a 2022 baseline with a naive scheduler, on synthetic traces where nothing emits <eos>; at low load on 101B Orca had no edge at all. Today every serious engine does iteration-level scheduling, so the next gains come from elsewhere: paged KV (PagedAttention III), and chunked prefill to stop long prompts stalling everyone else's decode, which is a problem Orca's plan of batching whole prompts creates (Sarathi-Serve I).
