Before this: Benchmarking a server

Reading the server's counters

Also called server-side metrics, engine metrics, the /metrics page, Prometheus metrics, observability or telemetry. This card is about what to watch while a load test runs against a vLLM server, and how to turn each reading into a diagnosis. Every counter name here was checked against vLLM's metrics page on 2026-09-30; the run in mind is a load test of Llama-3.1-8B on one rented GPU, with concurrency swept from 1 to 128.

Prime · 2 minutes before you read

The problem: A load test hands you latency and throughput as seen from outside. When time to first token turns upward you can't tell whether requests queued, memory filled, the prefix cache missed, or the load never reached the server. Without the engine's own counters you end up turning knobs by guesswork.

Where it fits: Directly after Benchmarking a server. That card chose the traffic and the client-side numbers to report; this one adds the server's side of the same run, so you can explain the curve you just drew. It reuses the KV budget and preemption from the scheduler card.

In one breath

A load test gives you two views of the same run. The client's numbers are what the load generator saw from outside: how long it waited, how fast tokens arrived. The server's counters are what the engine says it was doing inside: how many requests it was working on, how many were waiting, how full its memory was. The client's numbers tell you that something got slow. The counters tell you why. A result is only trustworthy when the two views agree.

1. Two views of one run

You already know the left column: it is in Serving metrics and Measuring a server, and Benchmarking a server covers the traffic you send. This card is the middle and right columns.

The first check is that the two views describe the same run. The engine keeps a running total of the output tokens it has produced (vllm:generation_tokens), of the prompt tokens it has processed (vllm:prompt_tokens) and of the requests it has finished successfully (vllm:request_success). These are running totals, and on the page each one appears with _total added to its name, so search the file for vllm:generation_tokens_total, not the bare name (section 3 says why). If a total appears on more than one line, add the lines up. Read each total before the run and after it, subtract, and compare with what the load generator says it did:

illustrative run: the client says it sent 500 requests, 1,024 tokens in, 256 out client claims server total should rise by requests 500 500 vllm:request_success output tokens 500 × 256 = 128,000 128,000 vllm:generation_tokens prompt tokens 500 × 1,024 = 512,000 512,000 vllm:prompt_tokens

Illustrative numbers, chosen to show the arithmetic; not a measurement. If the server's totals rise by less, some requests failed, were cut short, or never arrived, and the client's throughput figure describes a different run from the one you think you did.

2. Collecting the counters with no monitoring stack

You need no dashboard. The engine serves a plain-text page listing every counter and its current value, at the address /metrics on the same port as the API (vLLM's docs fetch it with curl http://0.0.0.0:8000/metrics). Fetch that page once a second into a file, and start the GPU's own command-line sampler (nvidia-smi) next to it:

# terminal 1: one copy of the engine's counter page per second, each stamped with the time while true; do echo "# t=$(date +%s)" >> r07.metrics curl -s http://localhost:8000/metrics | grep '^vllm:' >> r07.metrics sleep 1 done # terminal 2: one line of GPU readings per second nvidia-smi --query-gpu=timestamp,memory.used,utilization.gpu,power.draw \ --format=csv -l 1 > r07.gpu.csv # terminal 3: the load test itself. Stop the other two when it ends.

Written for this card and not run by the author (this Mac has no NVIDIA GPU). r07 is a made-up run id; section 7 says why every file carries one. -l 1 repeats the query every second; nvidia-smi --help-query-gpu lists every field your driver supports.

Both files have a time on every sample, and so does the load generator's output. That shared clock is the point: it lets you lay the counters over the latency curve and see which counter moved at the moment latency did.

Prometheus and Grafana are the same data: Prometheus is a program that fetches this page on a timer and stores it, and Grafana draws the stored values as dashboards. The production picture, where these readings feed a router and an autoscaler, is in The whole system, drawn.

3. How to read the labels

The prefix. Every name starts with vllm:. That only says which program reported it. The rest is words joined by underscores, so vllm:num_requests_running reads "vLLM, number of requests running". The underscores are part of the name. Nothing is being subtracted or subscripted.

Three kinds of reading.

  • A gauge is a value right now. It goes up and down, like a fuel gauge. Read it directly. Example: the number of requests waiting.
  • A counter is a running total since the server started. It only goes up, like a car's odometer. One reading means little; the useful number is how much it rose during your run, so subtract the first reading from the last. When you fetch the page, a counter appears with _total added to its name: the docs list vllm:num_preemptions, and the page shows vllm:num_preemptions_total.
  • A histogram records many measurements, one per request or per token, by sorting them into bins. On the page it becomes three kinds of line: _bucket lines, each counting how many measurements were at or below a limit (the limit is written as le="0.5", "less than or equal to 0.5"), one _sum line adding up all the measurements, and one _count line saying how many there were. The average over your run is the rise in _sum divided by the rise in _count.
# TYPE vllm:num_requests_running gauge vllm:num_requests_running{model_name="…"} 32.0 # TYPE vllm:num_preemptions_total counter vllm:num_preemptions_total{model_name="…"} 0.0 # TYPE vllm:request_queue_time_seconds histogram vllm:request_queue_time_seconds_bucket{le="0.5",model_name="…"} 470.0 vllm:request_queue_time_seconds_sum{model_name="…"} 60.0 vllm:request_queue_time_seconds_count{model_name="…"} 500.0

What the page looks like. The layout follows the sample in vLLM's docs; the values and the 0.5 limit are illustrative. The part in braces says which model the line is about.

Names change between versions. Metrics get added, renamed and retired. Before a run, open the /metrics page of the server you actually started and check that each name you plan to plot is there.

4. The counters that matter

The page lists dozens. These are the ones to plot. Each row gives the plain meaning first, then the literal name and its kind, then what a reading tells you.

Load and memory · gauges and one counter: is the load arriving, and what is it filling?

What it countsWhat a reading tells you
Requests runningthe requests in the batch the engine is working on right now
vllm:num_requests_running
a gauge		This is the engine's real batch size. In a test that keeps C requests in flight it should climb to C and stay there. If it never gets there, either the client is not sending what you think, or the engine is holding requests back, and the next row says which.
Requests waitingthe requests that have arrived but have not started
vllm:num_requests_waiting
a gauge		Zero means everything that arrives is served at once. A value that keeps rising means requests arrive faster than the engine takes them in, and each one's wait shows up in the client's time to first token.
Waiting, split by reasonthe same count, divided by why each request is waiting
vllm:num_requests_waiting_by_reason
a gauge		The page names two reasons: capacity, waiting for scheduling capacity, and deferred, held back by a temporary constraint. The two add up to requests waiting. In a plain load test expect nearly all of it under capacity. Our reading: it does not say whether that capacity is memory or a cap, so the next row is still what separates those.
KV cache usagethe fraction of the engine's KV cache memory in use
vllm:kv_cache_usage_perc
a gauge		It runs from 0 to 1, and 1 means 100% full (despite "perc" in the name, it is not 0 to 100). Near 1, memory is what stops the engine admitting more requests. Well below 1, memory is not the limit and something else is.
Preemptionshow many times the engine has preempted a running request. Our gloss, from the scheduler cards: pushed it back out to free KV cache memory
vllm:num_preemptions
a counter		It should stay flat. If it rises during a run, the engine admitted more than its memory could hold and is now redoing work. See Admission, preemption and thrashing.

The prefix cache · two counters, read as a pair

What it countsWhat a reading tells you
Prefix cache queriesprompt tokens the engine looked up in its prefix cache
vllm:prefix_cache_queries
a counter		Both count tokens, not requests. The hit rate over a run is the rise in hits divided by the rise in queries. Queries climbing while hits stay flat means nothing is being reused: the prompts do not start with exactly the same tokens. A hit rate near 1 in a benchmark is the opposite warning: you may be re-sending the same prompts and measuring a prefill that was free.
Prefix cache hitsof those tokens, the ones found in the cache. Our gloss: their prefill is skipped
vllm:prefix_cache_hits
a counter

Time, as the engine measured it · histograms, one measurement per request or per token

What it measuresWhat a reading tells you
Time to first tokenas the engine saw it
vllm:time_to_first_token_seconds
a histogram		Compare it with the client's time to first token. They should be close. A client figure that is much larger means the extra time is outside the engine: the network, or the load generator itself.
Gap between tokensinter-token latency, as the engine saw it
vllm:inter_token_latency_seconds
a histogram		The same cross-check for streaming speed. If this grows as concurrency grows, each step is doing more work, which is the expected cost of a bigger batch.
Waiting timehow long each request sat in the queue before starting
vllm:request_queue_time_seconds
a histogram		These two split time to first token into waiting and computing. If waiting grew and prefill did not, the engine is not slow; it is busy. If prefill grew, look at prompt length and at what else shared those steps.
Prefill timehow long each request spent having its prompt processed
vllm:request_prefill_time_seconds
a histogram
Decode timehow long each request spent generating its output tokens
vllm:request_decode_time_seconds
a histogram		The generating part of the request. Our reasoning, not the page's: divided by the output length it should roughly match the gap between tokens.
Whole-request timeend-to-end time for each request, as the engine saw it
vllm:e2e_request_latency_seconds
a histogram		The time a request spends inside the system. Its average is the "time inside" that Little's law needs: requests in flight = arrival rate × time inside (Queueing and the knee). Also a cross-check on the client's end-to-end latency.
Running timehow long each request spent running, waiting excluded
vllm:request_inference_time_seconds
a histogram		Our reasoning, not the page's: waiting time plus this is roughly the request's whole life inside the engine.
splitting time to first token, averages over one run (illustrative values) rise in _sum rise in _count average vllm:request_queue_time_seconds 60.0 s ÷ 500 = 0.120 s waiting vllm:request_prefill_time_seconds 35.0 s ÷ 500 = 0.070 s computing vllm:time_to_first_token_seconds 100.0 s ÷ 500 = 0.200 s 0.120 + 0.070 = 0.190 s of the 0.200 s. Waiting is 0.120 ÷ 0.200 = 60% of the wait.

Illustrative numbers, not a measurement. That time to first token is roughly waiting plus prefill is our reading of the phase names; vLLM's page describes each histogram but gives no formula. A histogram describes all requests together. It cannot tell you which request was slow.

The GPU sampler · three fields from nvidia-smi

What it readsWhat a reading tells you
Memory usedmemory handed out to programs on the GPU
memory.used		With vLLM this is nearly flat. The engine claims its whole memory pool when it starts, so the Serving field guide notes this reading sits near the card's total even with zero requests. It confirms the server is up and how much it reserved. It does not tell you how full the KV cache is; the KV cache usage gauge does.
GPU utilizationthe percentage of the last sample period in which at least one piece of GPU code was running
utilization.gpu		A weak signal. See below.
Power drawwatts the card is drawing
power.draw		A rough second opinion on how hard the card is working. Useful for spotting an idle card, and for cost per token later. Our gloss: it rises with real work more smoothly than utilization does, but it is not a throughput meter.

Why "GPU utilization" is a weak signal for an LLM server. The name suggests "how much of the GPU is in use". NVIDIA's definition is narrower: the share of time in which something was running on it. Between one step and the next the engine does work on the CPU, such as choosing what to run and turning token numbers into text, and for that moment the GPU is idle. So a single stream of requests can read anywhere from about 30%, as in the first worked symptom below, to near 100%, depending on how much CPU-side work sits between steps. A full batch reads near 100%. The number does not rise in step with load, and it cannot tell you how much room is left. (This is our reasoning from the definition and the guide's symptom, not a measurement.) A low reading is still informative: the GPU is idle between steps, so the server has room and the limit is somewhere else, often the client. For "how full is the server", read requests running and KV cache usage.

5. Where the knee comes from: the picture to draw

The knee is the point on the latency curve where time to first token turns sharply upward. To show its cause, plot requests running, requests waiting and KV cache usage against time for the whole sweep. The shape below is drawn for a deliberately small-memory server, so you can see what a memory limit looks like.

It is not a prediction for your run. Queueing and the knee shows how to estimate, for your own GPU, how many requests fit in KV memory (its section "Predict your own knee before you run the test"). If that estimate is well above 128, expect requests running to equal the target at every stage, requests waiting to stay at zero, and KV cache usage to end at roughly 128 divided by the number that fit. If your plot looks like the one below instead, something is smaller than you estimated: the memory pool, or the GPU.

reading the last stage (illustrative) requests: 128 in flight = 90 running + 38 waiting KV usage: 0.70 ÷ 64 ≈ 0.011 per running request, so 90 × 0.011 ≈ 0.98: full

Illustrative values for a server with far less KV memory than the lab's GPU, chosen so the arithmetic is easy to follow. The thing to learn from it is the order of events, not the numbers.

Read it left to right. For three stages the engine takes everything it is sent: running equals the target, nothing waits, and KV cache usage climbs in step. In the last stage the cache fills, the engine cannot start more requests, and the rest wait. On a server like this one, the knee on the latency curve is the moment waiting leaves zero. The KV cache usage track says why it happened here: memory ran out. Had usage still been at 0.35 when waiting began, the cause would be something else, and the table in the next section says what.

6. From a reading to a diagnosis

What you seeWhat it meansWhat to check or change
Requests running never reaches the concurrency you intended, and nothing is waitingThe client is not sending the load. The server never saw a batch.The load generator: a loop that sends one request at a time, or a concurrency setting left at 1. Guide failure F03.
Requests waiting rises while KV cache usage is near 1Memory is the limit. No room for another request's KV cache.Shorter contexts, fewer requests at once, or more KV memory. See The scheduler: KV budget, admission and preemption.
Requests waiting rises while KV cache usage is lowThe cap on concurrent sequences, the per-step token budget, or compute is the limit. Memory is free, but the engine will not or cannot run more at once.Is requests running pinned at the cap on concurrent sequences (--max-num-seqs; the queueing card calls it the seat cap)? If not, look at the per-step token budget (--max-num-batched-tokens), the limit on how many tokens one step may process: new prompts can be held back until there is room in a step. If neither is binding, each step is simply taking too long for the arrival rate.

7. What to write down for every run

Two runs can only be compared if you know exactly what differed between them. Before starting, give the run an id and put it in every file name. Afterwards, one short record:

Change one knob per run. If two things changed and latency moved, the counters can tell you what happened inside the engine but not which change caused it.

Why it beats the alternatives

✗ Trust the client's numbers alone

You see that time to first token rose, but not whether requests waited, memory filled, or the load never arrived. F03's three identical "runs" looked like a finished sweep from the client's side.

✗ Watch the GPU sampler alone

Memory used is flat because the engine reserves its pool at start. Utilization says only how often something was running, not how much. Neither shows the queue or the KV cache.

✗ Guess, and turn a knob

Raising the cap on concurrent sequences helps when the cap is the limit and hurts when memory is: the engine starts more requests than fit and preempts them. Without the counters you cannot tell which case you are in.

✓ Client numbers plus counters, on one clock

Sample the engine's page and the GPU every second, tag both with the run id, and lay them over the latency curve. The counter that moved when latency moved names the limit.

Do the counters always give the answer?

No. They narrow the search to one part of the engine; they do not always finish it.

  • Histograms describe the crowd, not a request. They can show that some requests waited a long time, but not which ones or why those. For that you need a record per request (tracing), which the guide's F05 write-up uses.
  • Once a second is coarse. A gauge sampled each second misses anything shorter: a brief burst of waiting can come and go between two samples. The histograms and counters do not have this gap, because they add up every event.
  • They stop at the engine's edge. Time in the network, a gateway or the load generator is invisible here. That is why the client's numbers stay in the record.
  • One server only. Each replica has its own page. With several replicas you need them collected in one place, which is what Prometheus is for (The whole system, drawn).

When the file-and-loop method is the wrong tool: anything that runs for days or serves real users. A loop in a terminal has no alerts, no history and no view across replicas. Use it for benchmark runs, and a real monitoring stack for production.

Understand and remember

  • Client numbers show that latency rose, not why → the engine reports what it was doing each second (running, waiting, KV usage) → lining both up on one clock shows which counter moved when latency did → that counter names the limit

4 · Compare against what you already know

vs Benchmarking a server: Benchmarking a server warned that a closed-loop client hides queueing. Which server counters would reveal the difference between a closed-loop and an open-loop run at the same nominal load, and what would each run's waiting count look like past the knee?

Check
  • closed loop caps requests in flight, so running + waiting can never exceed the concurrency setting and waiting stays bounded
  • open loop keeps sending, so waiting keeps growing for as long as arrivals outpace the engine
  • the queue-time histogram shows the wait the closed-loop client's numbers under-report
  • both still need the running count checked against what was intended

vs Measuring a server: TTFT, TPOT, throughput, goodput: That card defines time to first token, TPOT, throughput and goodput at the client. What can the server's histograms add that those cannot, and what can only the client's numbers tell you?

Check
  • the server splits time to first token into waiting and prefill, which the client cannot see
  • the server's histograms pool all requests and stop at the engine's edge
  • only the client sees network and gateway time and can judge each request against an SLO for goodput
  • so the counters explain a result; the client numbers are the result

vs The scheduler: KV budget, admission and preemption: The scheduler card described admission against a KV budget and preemption. Which counters are the visible trace of each of those decisions?

Check
  • admission held back by memory: waiting rises while KV usage sits near 1
  • admission held back by the cap on concurrent sequences: waiting rises while running is pinned at the cap and KV usage is low
  • preemption: the preemption counter rises
  • healthy: running equals the target, waiting is zero, preemptions flat

Why this step?

5 · Predict commit to an answer before revealing

Waiting is rising, KV cache usage reads 0.35 and running is pinned at the engine's cap. You double the cap. What do running, waiting and KV usage do next, and what new reading should you start watching? Commit before revealing.

Reveal

Running rises towards the new cap, waiting falls, and KV usage climbs roughly in proportion: about 0.70 if running doubles with similar requests. Each user's tokens slow down because every step now carries a bigger batch. The reading to watch is preemptions: if a later increase pushes KV usage to 1, the engine starts evicting running requests and total throughput can fall, which is the guide's 'more concurrency makes the server slower' failure.

6 · Apply use the model, don't restate it

Diagnose two runs from their readings, on paper. Run A: the client says it sent 500 requests of 256 output tokens each at concurrency 32. Over the run, the engine's output-token total rose by 32,000, and requests running peaked at 8. Run B (the guide's F05): at 6 requests/s, time to first token is 80 ms at p50 and 900 ms at p95, and step times look normal. For each run, say which row of the diagnosis table applies, what the numbers imply, and which one extra reading you would pull to confirm.

Done when: Run A: you state how many full-length requests the server actually completed and how far the running count fell short, and name the client as the suspect. Run B: you state how much of the p95 is waiting under the card's assumption, and name the histogram that would confirm it.

Hint

A: 32,000 ÷ 256 = 125 full-length requests, a quarter of the 500 claimed (500 × 256 = 128,000 expected), and running peaked at 8 of an intended 32, so the client is not sending the load; check its concurrency setting and its error count.
