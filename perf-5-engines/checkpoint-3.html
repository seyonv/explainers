Checkpoint 3: per-request work, and proving it

Ties together the anatomy of vLLM and SGLang, structured outputs inside the engine, serving many LoRA adapters, benchmarking a server and, again, the scheduler: the side work every request adds to a step (CPU time, masks, adapter reads), how engines hide it, and how to measure whether they did.

How to use this page. Close the five cards. Answer each question in writing, in full sentences, before opening its Check. A wrong or shaky answer isn't a failure; it tells you exactly which section to reopen. The questions are mixed on purpose, so you have to work out which idea applies before you can answer.

1 · Mixed retrieval

  1. which concept?After an engine upgrade, a benchmark shows 2× the throughput. The same seeded prompt set was replayed three times against the same running server. Which idea should make you distrust the result, and how would you rerun it?
    Check
    • the prefix-cache trap: repeated identical prompts reuse cached KV, so their prefill is nearly free and throughput inflates
    • vLLM's docs warn about exactly this for repeated vllm bench serve runs
    • vary the seed, restart the server, or measure the cache hit rate on purpose

    Missed it? Reopen benchmarking, "The checklist".

  2. Why can one batch serve requests for 64 different LoRA fine-tunes without losing the shared weight read, and what does each distinct adapter still cost per step on the running example?
    Check
    • adapters stay unmerged: every row multiplies the same base W in one GEMM, and each segment adds its own small (x·A)·B via one SGMV shrink and one expand launch
    • each distinct r = 16 adapter adds 27.26 MB of reads: 64 of them are 1.74 GB, 0.52 ms, +10.9% of the 4.79 ms weight read
    • requests sharing an adapter share its read, so grouping by adapter helps

    Missed it? Reopen multi-LoRA, sections 2–4.

  3. which concept?Turning on JSON mode makes TPOT jump from 5 ms to about 70 ms on one backend, while another backend on the same model and GPU adds almost nothing. Which idea explains the gap?
    Check
    • the mask is built on the CPU and must be ready before sampling, so a slow mask sits on the critical path
    • checking every one of 128k tokens against the grammar takes about 65.8 ms per token (XGrammar's naive baseline), 13.7× a 4.8 ms step
    • XGrammar precomputes context-independent tokens (all but about 120 of 128k need no runtime check) and builds the mask during the forward pass: under 40 µs and hidden

    Missed it? Reopen structured outputs, "Why it's a performance problem".

  4. Write the serial and the overlapped step formulas for CPU work in the busy loop, and fill them in for 1 ms of CPU per step at batch 1 (4.87 ms GPU step) and batch 238 (23.86 ms).
    Check
    • serial: t_GPU + t_CPU; overlapped: max(t_GPU, t_CPU)
    • batch 1: 5.87 ms, +20.5%, 205 → 170 tok/s; batch 238: 24.86 ms, +4.2%, 9,973 → 9,574 tok/s
    • overlapped: 4.87 and 23.86 ms, no loss while the CPU work is shorter than the step

    Missed it? Reopen anatomy, the worked example.

  5. which concept?A closed-loop load test at concurrency 64 shows a P99 TTFT of a few hundred ms. In production, at the same average request rate, users see multi-second first tokens during busy minutes. Which idea explains the difference, and what test would have caught it?
    Check
    • closed loop: the generator waits for answers, so when the server slows, the load backs off and the queue never forms
    • production is open-loop and bursty: at the same average, clumps of arrivals queue (at burstiness 0.25, CV 2.0, our draw's busiest second held 15 requests against an average of 1)
    • test open loop at swept rates with bursty arrivals, and report goodput at a TTFT SLO

    Missed it? Reopen benchmarking, "Closed loop vs open loop" and "Burstiness".

  6. The grammar mask for step n + 1 can be built while forward pass n + 1 runs, but SGLang needs "future tokens" to prepare the scheduling for batch n + 1 early. Why the difference?
    Check
    • the mask needs only token n, which exists the moment forward pass n + 1 starts, so both begin together
    • scheduling batch n + 1 while the GPU is still running batch n means planning before batch n's tokens are sampled
    • so the scheduler uses placeholders for tokens that don't exist yet and syncs with CUDA events

    Missed it? Reopen structured outputs, "Overlap, drawn to scale", and anatomy, "SGLang for contrast".

  7. At concurrency 16 our Mac made 100.2 tok/s. Under an SLO of TTFT ≤ 2 s and TPOT ≤ 100 ms, what is its goodput there, and at which concurrency is goodput highest?
    Check
    • at C = 16 the median TTFT is 5.16 s, so no request meets the SLO: goodput 0
    • C = 2 (0.77 s, 35.7 ms) gives the best goodput, 48.3 tok/s; C = 4 also passes but at only 36.1 tok/s
    • so the throughput peak and the goodput peak are different operating points

    Missed it? Reopen benchmarking, section 3, the goodput row.

  8. Resident LoRA adapters and the KV cache compete for the same GPU memory. How does S-LoRA let them share it, and what does the scheduler card's block arithmetic say one r = 16 adapter is worth in tokens of context?
    Check
    • both are rows of width H, so one paged pool holds KV pages and adapter pages side by side, without fragmentation
    • one r = 16 adapter (27.26 MB) weighs as much as about 208 tokens of KV at 131,072 B per token
    • so every resident adapter is a short conversation's worth of KV the scheduler can't admit

    Missed it? Reopen multi-LoRA, the adapter-size table and S-LoRA §5.1, and the scheduler, "The memory budget".

3 · Project: budget one step of a multi-tenant JSON API, then design the test

What it reinforces: serial vs overlapped CPU work (anatomy), mask cost per request (structured outputs), per-adapter reads and memory (multi-LoRA), the KV pool (the scheduler) and how to prove any of it (benchmarking).

Llama-3.1-8B in BF16 on one H100, 2k context. Every request brings its own r = 16 adapter (27.26 MB, on q/k/v/o) and its own JSON schema. Use XGrammar's 40 µs per mask on one CPU core, and an illustrative 1 ms of other CPU work (scheduling, input prep) per step.

GPU = B·2048·131,072 / 3.35e12 + max(2·8.03e9·B / 989e12, 16.06e9 / 3.35e12) + (distinct adapters)·27.26e6 / 3.35e12 CPU = B·40 µs + 1 ms serial step = GPU + CPU overlapped step = max(GPU, CPU)

  2. The naive mask. What would the CPU term be with 65.776 ms masks?
  3. Capacity at a TPOT target. Find the largest B with step ≤ 20 ms, serial and overlapped, and the total tok/s at each.
  4. Memory. With 64 adapters resident, how many 2k-context sequences still fit in the free 63.9 GB? (Compare with 238 without adapters.)

Write the benchmark that would confirm your overlapped number on a real server: dataset and ISL/OSL, open-loop rates, burstiness (with its CV), a goodput SLO of TPOT ≤ 20 ms plus a TTFT target, warm-ups, seeds, and how you'd make sure the requests really use 64 distinct adapters and schemas.

Check: the numbers (computed with a Python version of this exact model)
  • B = 64: GPU 9.92 + 0.52 = 10.44 ms; CPU 2.56 + 1 = 3.56 ms. Serial 14.00 ms → ≈ 4,570 tok/s; overlapped 10.44 ms → ≈ 6,130 tok/s. With one shared adapter, GPU is 9.93 ms.
  • Naive masks: 64 × 65.776 ms + 1 ms ≈ 4,211 ms of CPU per step, over 400× the GPU step.
  • TPOT ≤ 20 ms: serial B = 110 (19.90 ms, ≈ 5,530 tok/s); overlapped B = 172 (19.98 ms, ≈ 8,610 tok/s). Hiding the CPU work buys about 56% more users at the same TPOT.
  • Memory: 64 × 27.26 MB = 1.74 GB, so (63.9 − 1.74) GB ÷ 268.4 MB ≈ 231 sequences instead of 238.
  • One reasonable test: a ShareGPT- or BurstGPT-shaped dataset (state ISL/OSL), --request-rate swept open-loop, --burstiness 1 (CV 1.0) and 0.25 (CV 2.0), --goodput with TPOT ≤ 20 ms and a TTFT target, --num-warmups, a new --seed per run, and a request mix that assigns adapters and schemas round-robin so no two neighbours share one. A closed-loop run would back off when the server slows and hide the queue.
