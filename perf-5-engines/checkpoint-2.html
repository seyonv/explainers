Checkpoint 2: fewer bytes or more tokens per step

Ties together quantization for serving, speculative decoding I and II, Medusa and EAGLE, MTP and n-gram drafts: two ways to get more out of each weight read, and the batch size at which each one stops paying.

How to use this page. Close the five cards. Answer each question in writing, in full sentences, before opening its Check. A wrong or shaky answer isn't a failure; it tells you exactly which section to reopen. The questions are mixed on purpose, so you have to work out which idea applies before you can answer.

1 · Mixed retrieval

  1. which concept?A laptop user pairs a 3B model with a 1B draft from the same family. The logs show 87% of drafted tokens accepted, yet generation is no faster. Which idea explains it, and what would you try instead?
    Check
    • the cost ratio c: at batch 1 both models are memory-bound, so a step costs about its bytes, and the 1B Q8 draft reads 65% as many bytes as the 3B Q4 target (c = 0.665)
    • Theorem 3.8 with α = 0.867, γ = 4: E = 3.84 tokens over a cost of 3.66 steps, so 1.05×
    • try a much cheaper draft (smaller or lower-bit), prompt lookup for copy-heavy output, or no speculation

    Missed it? Reopen speculative decoding II, "The lesson: c is the killer".

  2. The target gives 'mat' probability 0.20 and the draft 0.50; the draft samples 'mat' and the uniform draw is r = 0.71. The other tokens are rug (p 0.45, q 0.25), sofa (0.25, 0.15) and floor (0.10, 0.10). What happens, and why is the result still an exact sample from p?
    Check
    • keep with probability min(1, 0.20 ÷ 0.50) = 0.40; 0.71 > 0.40, so reject
    • residual max(0, p − q): rug 0.20, sofa 0.10, the rest 0; normalised by 0.30 = 1 − β, so rug 0.667, sofa 0.333
    • exact because accepted mass min(p, q) plus residual mass p − min(p, q) equals p for every token

    Missed it? Reopen speculative decoding I, §2.3 and Appendix A.1.

  3. which concept?A team moves its 8B chat model to 4-bit weights (W4A16) on an H100. Single-user decode gets about 3× faster, but the busy production server, running near full batch, barely changes, and long-prompt TTFT doesn't move at all. Which idea explains both observations?
    Check
    • W4A16 shrinks only the weight read; the math still runs at the BF16 rate because weights are unpacked before the multiply
    • prefill is math-bound, so it gets 1.00×
    • at full batch the KV reads (untouched) are 80% of the step, and W4A16's matmuls turn math-bound after B = 76: 1.04× at B = 238

    Missed it? Reopen quantization for serving, "The regime map".

  4. Why does EAGLE feed its draft the token that was actually sampled, and what did that single change buy on Vicuna-7B?
    Check
    • after a token like "I", the target might sample "always" or "am", and each leads to a different next feature
    • without the sampled token, one input has two right answers; with it, each branch has one
    • speedup 1.9× → 2.8× (features alone had given 1.5× → 1.9×)

    Missed it? Reopen EAGLE, §1 "Two observations".

  5. With α = 0.8 and γ = 4, how many tokens does each target run produce on average, and what speedup do you get when a draft step costs 5% of a target step?
    Check
    • E = (1 − 0.8⁵) ÷ (1 − 0.8) = 0.67232 ÷ 0.2 = 3.36 tokens
    • cost per iteration = 4 × 0.05 + 1 = 1.20 target steps
    • speedup = 3.36 ÷ 1.20 = 2.80×

    Missed it? Reopen speculative decoding I, §3.2 and §3.3.

  6. which concept?At batch 64 on an H100, an SGLang deployment drops its draft tree and runs EAGLE-3 with a 3-token chain. Which idea explains the choice, and what gain does it still get?
    Check
    • speculation spends idle compute; the step stays memory-bound until about 295 tokens, shared by the whole batch
    • 295 ÷ 64 ≈ 4.6 verified tokens per sequence: a 3-token chain (4 verified) fits, a tree of dozens doesn't
    • measured: 1.38× at batch 64 vs 1.81× at batch 2 (EAGLE-1 falls to about 1×)

    Missed it? Reopen EAGLE, "Why the gain shrinks at batch 64", and Medusa, the batch table.

  7. Medusa-2 and EAGLE both report around 3× at batch 1. Why is EAGLE's output exactly the target's distribution while Medusa-2's isn't?
    Check
    • EAGLE verifies with multi-round speculative sampling (Leviathan's rule generalised to siblings), and leaves the target frozen
    • Medusa-2 fine-tunes the backbone itself, so even greedy output can change
    • and Medusa's typical acceptance keeps any "plausible" token above an entropy-scaled threshold, which isn't distribution-exact

    Missed it? Reopen Medusa, "Does Medusa change the model's outputs?", and EAGLE, §3.3.

  8. FP8 W8A8 makes a 1,000-token prefill 2.00× faster on the H100, but W4A16 doesn't speed it up at all. Walk through the prefill step for both.
    Check
    • prefill does 2 × 8.03e9 × 1,000 = 16.1 TFLOP of matmuls, so it's math-bound
    • W4A16: 16.24 ms of math at 989 TFLOPS; the 1.24 ms weight read hides under it, so 1.00×
    • FP8: the matmul runs on 8-bit tensor cores at 1,979 TFLOPS, 8.12 ms, so 2.00×

    Missed it? Reopen quantization for serving, "Why does weight-only 4-bit speed up chat but not long-prompt prefill?".

3 · Project: a batch-regime calculator

What it reinforces: the regime map and each format's Bcrit (quantization), Eq 1 and the speedup formula (speculative decoding I), speculation fading with batch (II), and the per-sequence token allowance behind tree and chain choices (Medusa, EAGLE).

Llama-3.1-8B (8.03B parameters) on one H100: 3.35 TB/s, 989 TFLOPS BF16, 1,979 TFLOPS FP8, KV 131,072 B per token. Three formats: BF16 (2 B per weight, BF16 math), W4A16 (0.5156 B per weight, BF16 math), FP8 (1 B per weight, FP8 math). In about 50 lines of Python:

  1. Decode steps. At 2k context, compute step = B·2048·131,072 / BW + max(2·N·B / C_fmt, N·b / BW) and total tok/s for B = 1, 16, 64 and 238, for each format.
  2. Ridge per format. Compute the tokens per step at which math equals the weight read, C_fmt · b / (2 · BW), for each format.
  3. Speculation per format. Use course 2's speculation model: α = 0.8, K = 4, a 1.0B draft stored in the same format as the target, and a step of max(weight read, math) with KV ignored. Normal step = max(N·b/BW, 2·N·B/C); verify = max(N·b/BW, 2·N·5B/C); draft = 4 × (1.0e9 · b / BW). Speedup = 3.36 × normal ÷ (verify + draft). Compute it for B = 1, 16, 32, 64 and 128.
  4. Decide. For B = 1, 32 and 238, say which lever you would turn on first and why, in one line each.
Done when: you have a 4 × 3 table of step times, three ridge values, a 3 × 5 table of speculation speedups, and one sentence explaining why 4-bit weights make speculation fade at a much smaller batch. Then compare with the check.
Check: the numbers (computed with a Python version of this exact model)
  • Steps (ms · total tok/s): B = 1: BF16 4.87 · 205, W4A16 1.32 · 760, FP8 2.48 · 404. B = 16: 6.08 · 2,633, 2.52 · 6,354, 3.68 · 4,349. B = 64: 9.92 · 6,450, 6.36 · 10,056, 7.53 · 8,505. B = 238: 23.86 · 9,973, 22.94 · 10,377, 21.47 · 11,086.
  • Ridge: BF16 295, W4A16 76, FP8 295 tokens per step. FP8 halves both the bytes and the math time, so the ridge doesn't move.
  • Speculation: BF16 2.24 · 2.24 · 2.24 · 2.12 · 1.26 for B = 1 · 16 · 32 · 64 · 128. FP8 2.24 · 2.24 · 2.24 · 2.13 · 1.26. W4A16 2.24 · 2.17 · 1.29 · 0.71 · 0.63. The draft is in the same format, so c = 0.125 in all three.
  • Why: W4A16's weight read is only 1.24 ms but its math still runs at the BF16 rate, so a verify pass of 5B tokens passes the 76-token ridge at B ≈ 15. By B = 64 speculation is a slowdown. Quantizing weights to 4 bits and speculating compete for the same idle compute.
  • One reasonable decision: B = 1, 4-bit weights plus a cheap trained draft (EAGLE-style); B = 32, FP8 with speculation still on (2.24× in this model); B = 238, FP8 and no speculation, then attack the KV reads.
