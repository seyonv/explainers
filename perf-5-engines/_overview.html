In one breath

An engine's job is to pick, every step, which tokens go through the model. Batching more users into a step raises total throughput almost for free until the step turns compute-bound, but each user then waits longer between tokens. Every technique in this course moves you along that trade-off or pushes the whole curve outward. Continuous batching keeps the batch full. Chunked prefill stops long prompts from stalling everyone else. Quantization shrinks the bytes each step reads. Speculative decoding gets several tokens out of one step while there is idle compute. A tight engine loop removes CPU overhead. Measure the whole curve, never a single point.

Tstep≈ max ( N·bWread weights , 2N(B+P)Cmath for all tokens ) + B·SKVWread KV +tCPU
Bdecode tokens this step, one per running user1 … memory limit Pprefill tokens packed into the same step (chunked prefill's budget)0 … 8,192 N·b, C, Wweight bytes, peak FLOP/s, HBM bandwidth16.06 GB · 989 TF · 3.35 TB/s tCPUscheduling, input prep, masks, detokenization not hidden behind the GPU0 if overlapped

Per-user speed = 1 ÷ Tstep; total throughput = B ÷ Tstep. Filled in for Llama-3.1-8B on one H100 at 2k context: B = 1 → 4.87 ms (205 tok/s for that one user); B = 64 → 9.92 ms (101 tok/s each, 6,450 total); B = 238 → 23.86 ms (42 each, 9,973 total). Adding a whole 4,096-token prompt to a 32-user step takes it from 7.36 to 74.04 ms, a 10× stall for every user.

The same thing in plain text:

step ≈ max( weight bytes ÷ bandwidth, 2 × params × (decode + prefill tokens) ÷ FLOP/s ) + users × KV bytes per user ÷ bandwidth + CPU time not hidden per-user tok/s = 1 ÷ step total tok/s = users ÷ step

The mental model: what each lever does to the curve

Batching moves you rightward along one curve: more total tokens, slower per user. Quantization and removing CPU overhead push the whole curve outward. Chunked prefill doesn't change the average; it removes the stalls that ruin P99 inter-token latency. Speculation lifts only the left end of the curve, where compute sits idle, and it can hurt at large batch.

These don't multiply. Speculation and big batches compete for the same idle compute. Quantization helps least exactly where batching helps most, once the KV reads dominate. The Orca and S-LoRA multipliers are measured against weak 2022–23 baselines. Today's engines already include continuous batching, paging, chunked prefill and prefix caching by default.

The words people use

Continuous batching

Orca's iteration-level scheduling: every step, finished sequences leave and waiting ones join. The paper calls it iteration-level scheduling plus selective batching; the industry calls it continuous or in-flight batching.

Chunked prefill, token budget

Split long prompts into chunks and fill each step up to a token budget (vLLM's max_num_batched_tokens; 8,192 by default on an H100), decodes first. Small budgets protect inter-token latency; big ones favour throughput.

TTFT, TPOT/ITL, goodput

Time to first token; time per output token after the first, (E2E − TTFT) ÷ (n − 1); goodput is the throughput that meets your SLOs. At 16 users our Mac made 100 tok/s but zero goodput under a 2 s / 100 ms SLO.

Acceptance rate α, cost ratio c

The share of draft tokens the target accepts, and the draft's cost per token relative to the target. Leviathan's speedup is (1 − αγ+1) ÷ ((1 − α)(γc + 1)): a draft that costs 66% of the target can't win much, whatever α is.

W4A16, W8A8, FP8

Weight bits and activation bits. Weight-only formats speed up memory-bound decode. Formats that quantize activations too also use faster tensor cores, which speeds up prefill and large batches.

Preemption: recompute vs swap

When KV runs out, the scheduler evicts the latest request whole. vLLM V1 recomputes it later by default rather than swapping to CPU.

The takeaway

Pick an operating point, not a benchmark number. Decide the per-user speed you promise (TPOT and P99 TBT) and the TTFT you can tolerate. Then push throughput as high as it goes without breaking those. For interactive serving that means: continuous batching with paged KV, chunked prefill with a token budget sized to your TBT SLO, FP8 on Hopper, and speculative decoding with a trained draft only while batches are small. Keep the CPU off the critical path. Then measure the curve with open-loop, bursty traffic and realistic lengths, as in the benchmarking card.

Where this doesn't apply as-is: offline batch jobs don't care about TBT, so they should run at the largest batch that fits and skip speculation. On a laptop or any memory-bound single-user setup, quantization is the big lever and a similar-sized draft model isn't. Our Mac measured about 1.0×. The paper multipliers come from specific models, GPUs and baselines. Current vLLM and SGLang already include most of these techniques by default. The Mac timings were taken on a busy machine, so re-run the labs before relying on them.

Understand and remember

  • One step reads all weights once, whoever is in it → adding a user costs only their KV read and a little math while the step is memory-bound → total tok/s = B ÷ step climbs while per-user tok/s = 1 ÷ step falls → batching moves you along one curve
  • Quantization and a lighter CPU loop shrink terms every step pays → the whole curve shifts outward; continuous batching and paging let you reach larger B → you slide further right on the same curve
  • A prompt packed whole into a decode step turns it compute-bound (4,096 tokens: 7.36 → 74.04 ms for 32 users) → one huge gap between tokens → chunked prefill caps prefill tokens per step → the P99 gap shrinks while the average barely moves
  • Speculation turns idle math into extra tokens → at large batch the math is no longer idle → it lifts only the left end of the curve and can lose at B = 256 (0.70× in course 2's model)
  • detail that matters KV reads grow with B × context and no weight quantization touches them → at B = 238 they're 80% of the step → this is why W4A16 gives 3.7× at B = 1 but 1.04× at full batch

Why this step?

5 · Predict commit to an answer before revealing

You move the same service from an H100 (3.35 TB/s) to a GPU with twice the HBM bandwidth and the same FLOP/s. Which levers in the table get more valuable and which get less? Commit before revealing.

Reveal

The ridge point (FLOP/s ÷ bandwidth) halves, so steps turn compute-bound at about half as many tokens. Speculation and piggybacked prefill both lose headroom, since there's less idle math to spend. Weight-only quantization matters less, because the weight read is already cheaper. CPU overhead matters more, because each GPU step is shorter while the CPU work per step stays the same. FP8's faster math becomes relatively more valuable.
