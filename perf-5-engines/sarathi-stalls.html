Sarathi-Serve I: why prefill stalls decode

Also called generation stalls, the throughput–latency trade-off, piggybacking and pipeline bubbles. This card walks Sarathi-Serve (Agrawal et al., OSDI '24) §1–3 in order: the problem, the background it assumes, and the three measurements that motivate the fix. The paper's numbers are for Mistral-7B, Yi-34B, LLaMA2-70B and Falcon-180B on A100s. The H100 and Llama-3.1-8B numbers are our recomputation. Card 1 of 2. The fix (chunked prefill and stall-free batching) is card 2.

In one breath

A decode step for 32 users is short because it only has to read the weights once. When the scheduler drops a whole prompt into that step, the step becomes as long as the prompt's math, and every one of those 32 users waits for it. That gap between tokens is a generation stall. Schedulers today either accept the stalls to get throughput (vLLM, Orca) or avoid them and lose throughput (FasterTransformer). Sarathi's way out comes from §3.1: a decode step leaves most of the GPU's math idle, so a limited number of prompt tokens can ride along almost free.

§1 · The problem: a trade-off nobody escapes (Figs 1–2)

Fig 1 runs Yi-34B on two A100s serving 128 requests from the arxiv-summarization trace. In vLLM one request's token stream freezes: "a generation stall in vLLM can last over several seconds". As load rises, vLLM's tail latency climbs. The paper sorts schedulers into two camps (a third, disaggregated, is left to §6):

  • Decode-prioritizing (FasterTransformer, request-level batching): once a batch starts, no new prefill runs until it finishes. TBT stays low, but throughput suffers, because the batch shrinks as requests finish.
  • Prefill-prioritizing (Orca, vLLM, iteration-level batching): new prompts are prefilled at the first chance, "whenever GPU memory becomes available". Later decode steps then run at a larger batch, so throughput is high. But every prefill interrupts the running decodes.

Fig 2 redrawn. Like the original ("the figure is illustrative and actual values will depend on the model and workload"), the positions are qualitative. Red: the schedulers that stall.

§2 · Background the paper assumes

Everyday version: a kitchen with one big oven. Decode is reheating one plate per diner per round. Prefill is cooking a new party's whole order. The metrics ask how long a new party waits for its first plate (TTFT), and how long a seated diner waits between plates (TBT).

Algorithm 1 · request-level (paraphrased)

loop: if batch is empty: admit while memory allows prefill(batch) else: decode(batch) # TBT safe; batch shrinks drop finished requests

Algorithm 2 · iteration-level, vLLM (paraphrased)

loop: new = admit while memory allows if new is not empty: prefill(new) # decodes wait batch += new else: decode(batch) drop finished requests

§3.1 · Prefill and decode cost very different amounts

Throughput vs batch size (Fig 3, Mistral-7B on one A100, 1,024-token prompts). Decode throughput rises "roughly linearly" with batch size, while prefill throughput "almost saturates even with a single request".

Takeaway-1. "batching boosts decode phase throughput immensely but has little effect on prefill throughput."

Where the time goes (Fig 4). Linear layers (the weight matmuls) dominate both phases: attention's cost grows with the square of the sequence, yet "linear operators still contribute more than 80% to the total time even at high sequence lengths". Fig 4's caption gives the ratio that motivates the whole design: "the cost of linear operation for 1 decode token is nearly same as 128 prefill tokens."

Roofline view (Figs 5–6). The paper uses T = max(Tmath, Tmem). Fig 5 (LLaMA2-70B on four A100s) splits the token count into three regions: decode batches are memory-bound (low MFU), big prefills are compute-bound (low MBU), and in between is the balanced point Sarathi aims for. Fig 6 shows LLaMA2-70B's linear-layer time is "largely stagnant in the 128-512 tokens range" and then grows linearly. In theory the switch comes at "∼200 tokens on A100 GPUs", but "in practice … ∼500-600 tokens for higher tensor parallel dimensions due to fixed overheads" (footnote 2).

The same shape for our running example, using the step-time formula from course 2 with P prefill tokens added to the step (our recomputation, theory only):

Linear-layer time per step = max(2N(B + P)/C, W/BW) for B = 32 decodes on one H100. It stays at the 4.79 ms weight read until B + P ≈ 295 tokens (the course's Bcrit). The width of the green band around the ridge is illustrative. On real GPUs the ridge comes later: the paper's A100 measurement is ~500–600 tokens against ~200 in theory.

Takeaway-2. "Decode batches operate in memory-bound regime leaving compute underutilized. This implies that more tokens can be processed along with a decode batch without significantly increasing its latency." This is piggybacking: prompt tokens ride in a decode step's idle math.

§3.2 · The throughput–latency trade-off (Fig 7)

Four requests: A and B are decoding when C and D arrive. The same four requests under each scheduler:

Fig 7 redrawn. Solid green: decode iterations (tokens users see). Grey: prefill-only iterations. Dashed green: hybrid iterations with decodes and prefill work together. Widths are schematic. Subscript d = decode, p = full prefill, p1/p2 = a prompt split into two chunks (card 2).

  • vLLM supports only all-prefill or all-decode batches, so A and B wait through both prefills. Our H100 example: a 78.32 ms gap.
  • Orca supports hybrid batches, but "the execution time of batches containing long prompts remains high". Our example: 74.04 ms. Hybrid batching alone isn't enough.
  • FasterTransformer has no stalls, but C and D wait until A and B both exit, and the batch shrinks to one request meanwhile. Kwon et al. (PagedAttention) report iteration-level batching reaching "an order of magnitude higher throughput".
  • Orca's own advice, smaller batches, reduces the spikes but "adversely impacts throughput". A prefill iteration "can take several seconds depending on the lengths of input prompts."
Takeaway-3. "The interleaving of prefills and decodes involves a trade-off between throughput and latency for current LLM inference schedulers. State-of-the-art systems today use prefill-prioritizing schedules that trade TBT latency for high throughput."

§3.3 · Pipeline bubbles waste GPU cycles

With pipeline parallelism, each micro-batch passes through every stage in turn. Micro-batching hides bubbles in training, and Orca argued that iteration-level scheduling removes them in inference. Sarathi shows they come back, because consecutive micro-batches can need very different amounts of compute. There are three kinds:

This can lead to significant bubbles when using pipeline-parallelism." The paper says the problem grows with longer prompts and larger batches, and the fix is micro-batches of uniform compute.

Why the fix beats the alternatives

✗ Decode-prioritizing

FasterTransformer, request-level. TBT stays at the clean 7.36 ms, but new prompts wait for the whole batch to drain and the batch shrinks as requests finish. Low TBT, poor throughput and poor TTFT.

✗ Prefill-prioritizing

vLLM (at the time) and Orca. Eager prefills keep decode batches big, so throughput is high. But one 4k prompt makes every running user's next token 10× late (74–78 ms on our H100), and on long prompts the stall runs to seconds.

✗ Disaggregation

Prefill and decode run on separate machines (Splitwise, DistServe, §6), so they never interfere, and TTFT is better. The cost is moving each request's KV cache between machines and sizing two pools. See Mooncake II and designing an inference engine.

✓ Chunked prefill + stall-free batching

Cut each prompt into chunks and fill every decode step up to a fixed token budget. The first ~263 tokens are nearly free (our H100), the step stays bounded, decodes never pause, and batches have uniform compute for PP. See card 2.

Why don't decode tokens slow each other down, but prefill tokens do?

Below the ridge the step is set by the weight read. Above it, the math sets it. Thirty-two decode tokens are 32 tokens of linear math, 0.52 ms, hidden under the 4.79 ms it takes to stream 16 GB of weights. A 4,096-token prompt is 4,128 tokens of math, 67 ms, far past the ridge (≈ 295 tokens on an H100 in theory), so the step becomes a math step and every token in it waits. It's not "decode vs prefill". It's how many tokens a step holds.

  • Decode tokens do cost something. Each one reads its own KV cache: 2.56 ms for 32 users at 2k, and 19 ms at the 238-user HBM limit (step-time card). That grows with batch but doesn't stall anyone.
  • The free region is smaller than theory says. Real GPUs leave the flat region later (500–600 tokens in the paper's A100 measurement), and a big decode batch (B near 295) leaves almost no room for prefill tokens.
  • Stalls aren't always the problem. In offline batch jobs, where nobody watches a stream, prefill-prioritizing is fine: TBT doesn't matter and throughput is all you want. When TTFT SLOs are strict at cluster scale, disaggregation may win (card 2 compares them).
