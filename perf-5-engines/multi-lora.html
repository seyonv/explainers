Serving many LoRA adapters

Also called multi-LoRA serving, multi-tenant LoRA, S-LoRA, Punica, or SGMV batching. This card skims two MLSys 2024 papers: Punica (§3–4 and §7, Llama-2 7B/13B/70B on A100s) and S-LoRA (§4–6 and Table 3, Llama-7B/13B on A100 and A10G). The Llama-3.1-8B / H100 sizes are our recomputation.

In one breath

A LoRA adapter is a fine-tune stored as two thin matrices per adapted layer, so thousands of customers' fine-tunes can share one copy of the base model. The trick in serving is to not merge them into the weights. Run the big base matmul once for the whole batch, then add each request's own small x·A·B with a kernel that handles many different adapters in one launch (Punica's SGMV). Keep the adapters in host memory and page the active ones into the same GPU pool as the KV cache (S-LoRA's unified paging).

1. What an adapter is, in serving terms

LoRA freezes the base weight W and learns an update of rank r. In the papers' row-vector notation (S-LoRA Eq. 1–2):

y=x(W+AB)= xWbase: shared, batch it + (xAi)Biadapter i: shrink, then expand
Wbase weight, din × dout, frozen and shared by every adapterq_proj 4096 × 4096 A_iadapter i's down-projection, din × r ("shrink")4096 × 16 B_iadapter i's up-projection, r × dout ("expand")16 × 4096 rrank, r ≪ d (S-LoRA's configs use 8, 16, 32, 64)8 · 16 · 64

The original LoRA paper writes the update as BA (column vectors); it is the same thing. Computing (xA)B costs 2·r·(din + dout) FLOPs per token, never the din·dout of forming AB.

2. The problem: merging and batching pull in opposite directions

The LoRA paper's serving advice was to merge: W′ = W + AB, then serve W′ at zero extra cost. That is perfect for one adapter. With many adapters, S-LoRA says, merging "significantly reduces overall serving throughput", for two reasons:

  • Memory: a model copy per adapter. A merged W′ is a full 16.06 GB model. Only 4 fit in 80 GB even with no KV cache, and 64 adapters would need 1,028 GB. Shared base + 64 r = 16 adapters is 17.80 GB.
  • Batching: one GEMM needs one weight. Continuous batching works because every request in the step multiplies the same W, so decode reads the weights once for the whole batch. Requests for different merged W′ can't share that read. Punica: "batching only works when requests are for the exact same model", so baselines in its mixed-adapter runs ran at batch sizes of 1–3.

Unmerged, the cost per decode step on our H100 (memory-bound, each weight read once per step):

base, read once per batch: 16.06 GB / 3.35 TB/s = 4.79 ms + each distinct r=16 adapter: 27.26 MB → 0.008 ms 3 adapters: 81.8 MB = 0.024 ms (+0.5%) 64 adapters: 1,744.8 MB = 0.521 ms (+10.9%)

Our recomputation, labs/lora-cost.py; an upper-bound model that ignores kernel launch and gather overhead. Requests that share an adapter share its read, which is why grouping by adapter helps.

4. Punica: batch across adapters with one kernel

SGMV · Chen et al., MLSys 2024 · §3–4, §7

Punica keeps one base model per GPU, reserves most memory for the KV cache, and loads only A and B for a new adapter from remote storage ("millisecond-level latency"). The base runs as a normal GEMM. The LoRA addon is two launches of one kernel, Segmented Gather Matrix-Vector multiplication: shrink (v += x·A) then expand (y += v·B). The adapter index maps to blockIdx.y, so every adapter in the batch runs in the same launch. It is designed for decode, which the paper calls "the predominant factor in the cost of model serving".

What batching different adapters costs. Punica's microbenchmark (one A100, hi = 16, ho = 4096, batch 1 → 64): the SGMV-based LoRA operator (two launches) takes → 40 µs when all requests share one adapter, 37 → 46 µs for uniform or skewed popularity, and 37 → 116 µs when every request has its own adapter. With all-distinct adapters, extra requests add no reuse, so intensity stays flat and time grows with bytes. Our +10.9% for 64 distinct adapters is the same effect in a simple bytes model, not a reproduction of their numbers.

5. S-LoRA: thousands of adapters, one memory pool

S-LoRA · Sheng et al., MLSys 2024 · §4–6, Table 3

  • Adapters live in host memory (§4). All adapters sit in main RAM, and only those the running batch needs are fetched to the GPU. The adapter count is then "bounded by the main memory size", not HBM. Scheduling is Orca's iteration-level batching.
  • Unified paging (§5.1). An adapter of rank R and a KV cache of S tokens both have shape (· , H), so both are stored as rows of H in one pre-allocated pool, "interleaved and non-contiguously". This extends PagedAttention from KV blocks to adapter weights, so loading and unloading adapters of different ranks doesn't fragment memory.
  • Prefetching (§5.2). While the current decode batch runs, S-LoRA looks at the waiting queue and loads the next batch's adapters, hiding the host-to-GPU copy.
  • Kernels (§5.3). MBGMM for prefill and MBGMV for decode: gather each request's adapter from the pages, with mixed ranks and no padding. A plain batched GEMM would "require significant padding".
  • Tensor parallelism (§6). The adapter matrices are split to match Megatron's split of the base, so no weight is stored twice. LoRA's extra messages carry vectors r wide, not h wide. The paper counts 5(N−1)Br/N extra against the base's all-reduce of 2(N−1)Bh/N (N GPUs, B tokens). The ratio is 5r / 2h, and on Llama-3.1-8B's h = 4096 at r = 16 that is 80 / 8,192 = 0.98% more traffic (our arithmetic).

Note: 2023 vLLM had no LoRA support; that baseline is not today's vLLM.

In engines today. vLLM serves adapters with --enable-lora and --lora-modules. Its knobs mirror the ideas above: max_loras, "max number of LoRAs in a single batch" (default 1); max_lora_rank (default 16); max_cpu_loras, how many stay in CPU memory (must be ≥ max_loras). SGLang lists "multi-LoRA batching" among its runtime features. Above one server, Kiely describes "LoRA-aware routing": send a request to a replica that already has its adapter in memory (Inference Engineering, p.191).

Why it beats the alternatives

✗ Merge the adapter into W

Zero overhead per token, the LoRA paper's advice. But a replica serves one adapter at a time; switching means subtracting one AB and adding another, so mixed traffic runs serially.

✗ One merged replica per adapter

Memory × N: 16.06 GB each, 4 fit in 80 GB with no KV, 64 need 1,028 GB. Batches split by adapter, so each GPU runs tiny batches (vLLM-packed: OOM at 100 adapters).

✗ Batch across adapters with SGMV (Punica)

One base, one GEMM, one SGMV launch for every adapter: 1,044 tok/s on 7B vs 1,140 for the bare base. But adapters must fit on the GPU next to the KV cache, and the paper focuses on decode.

✓ Unified paging + batched kernels (S-LoRA)

Host memory holds the catalog, one paged pool holds active adapters and KV, and MBGMM/MBGMV cover prefill and decode with mixed ranks. 7.61 req/s at 2,000 adapters vs 8.05 at 5: the winner at thousands of adapters.

Why are LoRA adapters cheap to serve but not free?

Cheap: an r = 16 adapter is 27.26 MB (0.17% of the base) and adds 0.17% FLOPs per token. 366 of them fit in 10 GB.

Not free, for three reasons. (1) Extra kernels every step. Each adapted matrix gains a shrink and an expand launch per layer (Punica's two-launch LoRA operator: 37 µs even at batch 1), and the LoRA path doesn't fuse into the base GEMM. End to end, Punica reports "only adding 2ms latency per token". (2) Distinct adapters don't share reads. 64 different r = 16 adapters add 1.74 GB, +10.9% of the base read per step in our model. At r = 64 that grows to +43%. This is why S-LoRA offers "adapter clustering", preferring requests with the same adapter, at some cost in fairness and latency. (3) The adapter must be resident. A cold adapter waits on a copy from host RAM or remote storage, and resident adapters take pages the KV cache could use. Prefetching and LoRA-aware routing exist for this.

When not to bother: a single fine-tune with steady traffic. Merge it and serve it as a plain model, at zero overhead. Multi-LoRA pays off when you have many adapters, each with too little traffic to fill a GPU alone.
