.view: reshaping for free

Also called: tensor views, storage and strides, reshape without a copy. Lecture 3 · implementing the hidden layer + internals of torch.Tensor: storage, views · 0:18:35

Prime · 2 minutes before you read

The problem: The embeddings come out as a (32, 3, 2) block, but the hidden layer's weights want one row of 6 numbers per example. Gluing the pieces together with a copy on every forward pass is clumsy, and it hard-codes the context length.

Where it fits: It follows the embedding lookup (emb = C[X]) and comes right before the hidden layer. It reuses tensor shapes and indexing from the toolkit, and shows what a tensor really is underneath.

Read with these questions (answer them in your head as you go; don't take notes line by line):

  1. Which three small numbers per tensor turn a flat block of memory into a (3, 3, 2) grid?
  2. Why are each example's six numbers already adjacent in emb's memory, and in which order?
  3. What does cat have to do that view doesn't, and how often does that happen in training?
  4. What goes wrong with .view after a transpose, and why does .reshape still work?

In one breath: a PyTorch tensor is one flat run of numbers in memory (its storage) plus a few small numbers (shape, strides, offset) that say how to read that run as a grid. .view writes new shape and strides over the same memory. So turning emb from (32, 3, 2) into (32, 6), which puts each example's three character embeddings side by side, copies nothing.

Predict first: emb.view(-1, 6) and torch.cat(torch.unbind(emb, 1), 1) give exactly the same (32, 6) numbers. How much new memory does each one allocate?

view: none. cat: 768 bytes. The view is new metadata pointing at emb's own storage (the lab checks data_ptr(): same address). cat writes a fresh copy: 32 × 6 floats × 4 bytes = 768 bytes. That's tiny here, but it happens on every forward pass, and the view never does.

One strip of memory, read as many shapes

a = torch.arange(18) stores the numbers 0 to 17 in one row: 18 int64s × 8 bytes = 144 bytes (the lab prints storage: 144 bytes = 18 int64s). A stride is how many storage slots you skip to move one step along a dimension. Each view below is the same 144 bytes with different strides.

Why the MLP needs it: (32, 3, 2) → (32, 6)

From the last card, emb = C[X] has shape (32, 3, 2): 32 examples, 3 context characters each, a 2-number embedding per character. The hidden layer's weights W1 are (6, 100), where 6 = 3 characters × 2 numbers, so each example must become one row of 6. Karpathy tries three ways (from 0:18:35): torch.cat of the three slices emb[:, 0, :], emb[:, 1, :], emb[:, 2, :]; torch.cat(torch.unbind(emb, 1), 1), where unbind splits dimension 1 into a list of three (32, 2) tensors; and emb.view(-1, 6). All three give equal numbers (the lab prints True).

The view works because emb's strides are (6, 2, 1) (computed): example n's six numbers already sit together at storage[6n : 6n + 6], character 0 first. view(-1, 6) just says "rows of 6, stride (6, 1)". The -1 means "work this dimension out": 32 × 3 × 2 = 192 numbers ÷ 6 = 32 rows.

Why it beats the alternatives

✗ cat of three slices

torch.cat([emb[:, 0, :], emb[:, 1, :], emb[:, 2, :]], 1) hard-codes 3. Change block_size and you must rewrite the line, and it copies all 192 numbers every pass.

✗ cat of unbind

torch.cat(torch.unbind(emb, 1), 1) works for any context length, but still builds a list of tensors and a fresh copy (768 bytes here) on every forward pass.

✗ view with a fixed batch size

emb.view(32, 6) works only for batches of exactly 32. Evaluating all 228,146 examples, or sampling one name at a time, needs a different shape; that's what -1 is for.

✓ emb.view(-1, 6)

New strides over the same memory: no copy and no list, and -1 fits any batch. It's the line the rest of the lecture uses, later as view(-1, 30) for 10-D embeddings.

When view won't work (and what a view shares)

A view needs memory that is already in the right order. emb.transpose(1, 2) is itself a view with strides (6, 1, 2), so its numbers are no longer laid out row by row. Calling .view(-1, 6) on it fails with RuntimeError: view size is not compatible with input tensor's size and stride ... Use .reshape(...) instead. (run in the course venv). .reshape returns a view when it can and quietly copies when it can't, so it always works, but you no longer know whether you got a copy.

A view shares writes too. Setting emb.view(-1, 6)[0, 0] = 99. changes emb[0, 0, 0] to 99.0 (checked). In the MLP that never bites, because nothing writes into emb. The copy cat saves is also tiny at this size: prefer view for clarity and because it scales, not because 768 bytes matter. For the full picture of storage, strides and offsets, see ezyang's PyTorch internals, linked from the video description.

Understand and remember

  • A tensor = storage + shape + strides + offset → element [i, j, k] is found at offset + i·s₀ + j·s₁ + k·s₂ → changing shape and strides re-reads the same memory → .view is free (no copy)
  • emb has strides (6, 2, 1) → example n's 6 numbers sit together at storage[6n : 6n + 6], character 0 first → view(-1, 6) just declares stride (6, 1) → the same row-of-6 layout cat builds by copying
  • A view only re-reads memory, never reorders it → after transpose the numbers aren't in row order → .view raises an error → .reshape (or .contiguous()) has to copy
  • -1 lets PyTorch infer a dimension from the total count (192 ÷ 6 = 32) → the same line handles a batch of 32, all 228,146 examples, or 1 during sampling
  • detail that matters Views share storage → writing through a view changes the original (setting view[0, 0] = 99. sets emb[0, 0, 0]) → harmless in this MLP, a silent bug if you edit a view expecting a copy

Reference only

  • t.stride(), t.data_ptr(), t.storage_offset(), t.untyped_storage().nbytes(), t.is_contiguous()
  • torch.unbind(t, dim) returns a tuple of slices along dim
  • the exact RuntimeError text for an incompatible view
  • the arange(18) storage is 144 bytes (18 int64s × 8 bytes)

  3. tradeoff You have a non-contiguous tensor and need it flattened to rows. Compare .view, .reshape and .contiguous().view: what does each cost, and how does each fail?
    Check

4 · Compare against what you already know

vs An embedding is just indexing: Both C[X] and emb.view(-1, 6) produce a new tensor from an old one. Which one copies memory and which doesn't, what design choice causes it, and when would the difference matter?

Check
  • C[X] is advanced indexing: it gathers rows (repeating C[0] many times), so it must allocate a new (32, 3, 2) tensor; checked: it does not share C's memory
  • view only changes the header, so it shares emb's memory
  • a gather can't be described by strides when rows repeat or jump around; a reshape of contiguous memory can
  • it matters for memory at scale and for writes: editing emb never changes C, but editing a view changes emb

vs Batched matmul and FlattenConsecutive: Here view flattens all 3 characters into one row; in WaveNet a view groups consecutive pairs, (4, 8, 10) → (4, 4, 20). What is the same mechanism in both, and what new question does WaveNet's version raise?

Check
  • same: contiguous memory, only the strides change, so both are free
  • here the whole context is merged at once; WaveNet merges two neighbours at a time to build a tree
  • WaveNet's view puts characters 2k and 2k+1 side by side because they are adjacent in memory, which is why it equals torch.cat([e[:, ::2, :], e[:, 1::2, :]], dim=2) without the copy

Reveal

The view raises RuntimeError: view size is not compatible with input tensor's size and stride ...: the transpose made strides (6, 1, 2), so rows of 6 aren't contiguous. With .contiguous() it copies and succeeds, but row 0 becomes 1.5674, 1.5674, 1.5674, -0.2373, -0.2373, -0.2373: first all three characters' dimension 0, then all their dimension 1. Same numbers, different order, and the model would be wired differently (measured in the course venv).
