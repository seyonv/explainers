An embedding is just indexing

Also called: an embedding lookup table, nn.Embedding, token embeddings. Lecture 3 · implementing the embedding lookup table · 0:12:19

Prime · 2 minutes before you read

The problem: A network does arithmetic on numbers, but a character is a symbol. Feeding its index (5 for e) invents a fake ordering, and a one-hot vector wastes almost all of its work multiplying by zero.

Where it fits: The previous card turned names into a (32, 3) tensor X of character indices. This card turns each index into a learned vector, the first layer of Bengio's MLP. It builds on the bigram card's one-hot input times a weight matrix.

Needs first: Names into (context → next char) pairs

Builds on: One-hot inputs and a linear layer · Tensors: shapes, dims and indexing · Matrix multiply by shapes

In one breath: C is a table with one row of numbers per character (27 rows, 2 numbers each to start). To embed a character you read its row: C[5] is the vector for e. That gives exactly the same answer as multiplying a one-hot vector by C, so an embedding is a linear layer done the cheap way. And C[X] does it for every index in the dataset at once.

Predict first: C has shape (27, 2) and X has shape (32, 3). What shape is C[X]? And since X[13, 2] is 1 (the letter a), what is emb[13, 2]?

(32, 3, 2), and emb[13, 2] is simply C[1] = [−0.0274, −1.1008]. Indexing swaps each integer in X for its 2-number row, so the result keeps X's shape and gains one axis of size 2. Nothing is multiplied; row 1 is just copied.

The table

C is a parameter (a number the network learns): 27 rows × 2 columns, one row per character in the order stoi gives (. is 0, a is 1, … z is 26). It starts as random numbers from torch.randn. Training will move the rows, and characters that behave alike should end up near each other, which is Bengio's idea from the previous card. Four of its 27 rows, seeded as in the lab:

Two ways to get row 5

A one-hot vector for 5 is 27 zeros with a single 1 at position 5 (the bigram card's input). Multiply it by C and every row is scaled by 0 except row 5, which is scaled by 1:

one_hot(5)1 × 27 @ C27 × 2 = ∑i=026 oi⁢C[i] = C[5]just row 5
one_hot(5)a row of 27 numbers: 1 at position 5, 0 everywhere else1 × 27 @matrix multiply (each output = a dot product of the row with a column of C)(1×27)@(27×2) → 1×2 oientry i of the one-hot vectoro5 = 1, the rest 0 C[i]row i of the table: the 2-number embedding of character iC[5] = e's row
one_hot(5) @ C = 0·C[0] + 0·C[1] + … + 1·C[5] + … + 0·C[26] = C[5] = [-0.4713, 0.7868] (the lab prints both: equal) cost: one-hot route 27 × 2 = 54 multiply-adds, 52 of them times 0 index route copy 2 numbers

So an embedding layer is a linear layer (no bias, no nonlinearity) fed one-hot inputs. PyTorch skips the zeros and reads the row.

Index with a whole tensor: C[X]

PyTorch lets the index be a list or a tensor of any shape, and the answer keeps that shape with one extra axis of size 2 on the end: C[[5, 6, 7]] is (3, 2), and C[X] embeds all 32 × 3 = 96 context characters in one line.

Why it beats the alternatives

✗ Feed the index itself

Using 5 as the input for e says e sits between d and f and is "5 times" a. That order is meaningless, and one number has no room for learned features.

✗ A count table per context

Gives every 3-character context its own row: 19,683 rows, most seen too rarely. Nothing learned about e in one context helps any other.

✗ Literally multiply one-hots

The same numbers, but 27× the work here and a (32, 3, 27) tensor of mostly zeros; with a 17,000-word vocabulary that is 510,000 multiply-adds per word instead of 30 copies.

✓ Look up a learned row

C[X] copies one shared row per character, and the same row is used wherever that character appears, so what is learned about it carries to every context.

If it's only indexing, how does C learn?

Because indexing is secretly that matmul, gradients flow into C exactly as they would into a weight matrix, just only into the rows that were used. On emma's first 5 rows, a backward pass gives non-zero gradients to 4 of the 27 rows (., a, e, m) and exactly zero to the other 23 (computed with the lab's seeded network). A row used several times, like . here, adds up the gradient from every use; the embedding-backward card in z2h-6 does this by hand.

When the lookup is not the right tool: it only works when the input is a whole-number id. If the input were a blend over characters (say 70% a, 30% e), you would need the real matmul, which is exactly what a linear layer does.

Understand and remember

  • one-hot vector has a single 1 → one_hot(i) @ C scales every row by 0 except row i → the product equals C[i] → an embedding is a bias-free linear layer, and indexing is the same math without the wasted multiplies
  • indexing with a tensor replaces each integer by its row → C[X] has shape X.shape + (row width,) → (32, 3) becomes (32, 3, 2) → the next layer must flatten 3 × 2 = 6 numbers per example
  • one shared table used at every position and in every context → what the network learns about a character's row carries to all contexts → similar characters can drift together and the model generalises (Bengio's idea)
  • lookup is mathematically a matmul → gradients reach C like any weight matrix, but only the rows that were looked up → a row used several times sums its gradients; unused rows get exactly zero
  • detail that matters the one-hot route costs vocabulary × width per lookup (27 × 2 = 54 here, 17,000 × 30 = 510,000 for Bengio's words) → a lookup costs only width → this is why real models never build the one-hot tensor

Reference only

  • F.one_hot(torch.tensor(5), num_classes=27) needs a tensor, not a Python int
  • one_hot returns int64; cast with .float() before @
  • C[[5, 6, 7]] accepts a list; nn.Embedding(27, 2) wraps the same table as a module
  • the seed 2147483647 used by the lab

4 · Compare against what you already know

vs One-hot inputs and a linear layer: The bigram net multiplied a one-hot by a (27, 27) weight matrix; here we index a (27, 2) table. What is fundamentally the same, what changed in the design, and what does each output mean?

Check
  • same: both are 'pick a row of a learned matrix' for one character
  • bigram: the row is 27 logits for the next character directly
  • here: the row is a small feature vector that later layers combine across 3 characters
  • the bigram can only use 1 character of context; the embedding lets context grow without a table per context

vs Why a bigger count table fails: Both a count table and an embedding table are 'one row per something'. Why does the count table explode with context length and the embedding table not?

Check
  • count table: one row per whole context, 27ⁿ rows (19,683 for n = 3)
  • embedding table: one row per character, 27 rows no matter the context length
  • context is handled by concatenating rows and a hidden layer, not by more table rows

vs Token and position embeddings: GPT uses the same lookup for tokens, plus a second table indexed by position. What problem does the position table solve that C[X] in this MLP never had to?

Check
  • the MLP keeps position by where each embedding sits when flattened (slot 0, 1, 2)
  • attention mixes tokens without a fixed slot order, so position must be added as its own learned vector
  • both tables are plain lookups trained by backprop

5 · Predict commit to an answer before revealing

The lecture later switches to C = torch.randn((27, 10)). Before running it: what shape is C[X] for the (32, 3) X, and what must the first dimension of W1 become?

Reveal

C[X] is (32, 3, 10): the appended axis is the row width. Flattening gives 3 × 10 = 30 numbers per example, so W1 must be (30, …); the lecture's final model uses (30, 200). Any code that hard-coded 6 now breaks, which is why Karpathy prefers view(-1, …) or emb.shape[0] on the next card.
