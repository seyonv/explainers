The six big ideas of the MLP

Big idea 1: Counting contexts explodes; learned points per character generalize

A count table needs one row per context, 27ⁿ of them, and the data can't fill them. Bengio's fix: give each character a few learned numbers, a point in space, shared by every context it appears in.

if two words end up with nearby embeddings, what the model learns about one carries over to the other · Karpathy, paraphrased, 0:04:25

Why it matters: Every language model since works this way: GPT starts by looking up a learned vector per token. Counting can't reach long contexts; shared points can.

Big idea 2: An embedding lookup is a one-hot matmul, done cheaply

Reading row 5 of C gives exactly what multiplying a one-hot vector for 5 by C gives. So the embedding is a first linear layer, and indexing just skips the zeros.

indexing into C is the same as multiplying a one-hot vector by C; the lookup is just faster · Karpathy, paraphrased, 0:12:19

Why it matters: Because it is secretly a matmul, gradients flow into C like into any weight. GPT's nn.Embedding is this lookup, and the backprop-ninja lecture writes its backward by hand.

Big idea 3: F.cross_entropy gives the same loss, and can't overflow

exp, normalize, pick the correct character, −log, mean: that is the loss. PyTorch's one call computes the same number, with fewer tensors, a simpler backward pass, and no nan when a logit is large.

F.cross_entropy is more efficient in the forward pass, much simpler in the backward pass, and numerically well behaved · Karpathy, paraphrased, 0:32:49

Why it matters: Every later model in the series ends in this call, from the BatchNorm MLP to GPT-2. Its one-line gradient, (probs − one_hot) / N, is derived by hand two lectures on.

Big idea 4: Overfit one small batch before training on everything

Train the new net on just 32 rows. A correct loop memorises them in under a second and lands right above the lowest loss you can work out by hand; a buggy one doesn't.

the loss can't reach zero, because the same starting context ... is followed by different letters · Karpathy, paraphrased, 0:40:37

Why it matters: It is the cheapest bug detector in deep learning, and the GPT-2 build uses it again: overfit one batch, then load real data.

Big idea 5: Many noisy steps beat a few exact ones

A step on 32 random rows costs about a thousandth of a step on all 228,146, so in the same second you take a thousand times more steps. Near the bottom the noise takes over, so you shrink the learning rate.

“much better to have an approximate gradient and just make more steps” · Karpathy, 0:44:23

Why it matters: Every model in the series trains on random minibatches, from GPT's random chunks to GPT-2's warmup-and-cosine schedule, which is this lr decay grown up.

Big idea 6: Judge on held-out data; train ≈ dev means find the bottleneck

Training loss can't tell fitting from memorising, so hold out dev and test names. When train and dev are equal the net is too small, and the fix is to grow the part that is squeezing it: here the 2-number embedding, not the hidden layer.

train and dev losses are about equal, so the network is too small: it is underfitting · Karpathy, paraphrased, 1:00:02

Why it matters: This train/dev reading drives every later decision in the series, and the next lecture opens by fixing what this one left: a first loss of 27 where a uniform guess gives 3.30.

1 · Core model what to internalise, what to just look up

Keep it if it changes what you can explain, predict, compare, choose, build or debug. Otherwise it's reference.

Understand and remember

  • A count table needs a row per context → 27ⁿ rows (19,683 at n = 3, only 28.9% ever seen) → most rows are empty or thin → give each character a learned point in C shared by all contexts → similar characters drift together → what is learned in one context transfers to similar ones
  • Indexing C[5] = one_hot(5) @ C → the embedding is a linear layer on one-hot inputs → gradients flow into the used rows of C like any weight → C[X] embeds a whole (32, 3) batch at once, then view(-1, 6) lays each row's three points side by side for free
  • Every training change is judged by a number on the right data → 32 fixed rows must overfit to just above 0.2515 (proves the loop) → random 32-row minibatches take ~1,000× cheaper steps (2.5214 vs 10.7096 in ~1.2 s) → near the bottom noise dominates → lr decay 0.1 → 0.01 (2.3401)
  • Training loss can't tell fitting from memorising → hold out dev and test names → train ≈ dev means underfitting → grow the part that squeezes the model → 3× hidden units gave dev −0.03, 2 → 10 embedding numbers gave −0.06 → final dev 2.1701 with 11,897 params
  • detail that matters F.cross_entropy subtracts each row's max logit before exp and stays in log space → no inf/nan for large logits (the hand-written version turns a logit of 100 into nan) → it also records 2 backward steps instead of 7, with a one-line gradient

Reference only

  • block_size 3, the 32 examples from the first five names, 228,146 examples in all
  • the seed 2147483647 and the split seed 42; split sizes 182,625 / 22,655 / 22,866 (Part 2's notebook prints 182,441 / 22,902 / 22,803)
  • parameter counts: 3,481 (2-D, 100 hidden), 10,281 (2-D, 300), 11,897 (10-D, 200)
  • torch.randint, lrs = 10**torch.linspace(-3, 0, 1000), torch.multinomial for sampling

3 · Retrieve from memory, card closed
  1. concept Explain, without numbers first, why a table of learned character points generalizes to contexts the model has never seen, while a count table can't. Then give the two numbers that show the count table's problem at 3 characters.
    Check
    • every context goes through the same C and weights, and the output changes smoothly as points move
    • characters used alike get nearby points, so evidence for one context helps similar ones
    • a count table's rows share nothing: .an teaches .on nothing
    • 19,683 possible contexts, only 5,686 (28.9%) ever seen
  2. mechanism Walk one minibatch through the final model: name the tensor and its shape after each step, from 32 row ids to the loss.
    Check
    • ix (32,) random ids → Xtr[ix] (32, 3)
    • C[Xtr[ix]] (32, 3, 10) → view(-1, 30) (32, 30)
    • tanh(@W1 + b1) (32, 200) → @W2 + b2 logits (32, 27)
    • F.cross_entropy(logits, Ytr[ix]) → one number; backward, then p.data += -lr * p.grad
  3. tradeoff You have a new training loop and a big dataset. In what order would you run the overfit test, the lr sweep and the split evaluation, and what does each one rule out?
    Check
    • overfit 32 rows first: rules out a broken loop (should land just above the hand-computed floor, 0.2515 here)
    • then sweep lr on minibatches: rules out a step size that crawls or diverges (valley near 0.1)
    • then train and compare train vs dev: rules out memorising, and says whether to grow or shrink the model
    • test stays unopened until the end
  4. tradeoff Growing the hidden layer 100 → 300 cost 6,800 parameters for a dev gain of 0.03; then switching to 10-number embeddings with 200 hidden units (11,897 parameters, only 16% more than 10,281) gained another 0.06 on the same 50k steps. What design fact explains the difference?
    Check
    • every hidden neuron only ever sees 3 × 2 = 6 numbers per example
    • more neurons reading the same 6 numbers add little
    • 10-number embeddings give the hidden layer 30 inputs, more information per character
    • the bottleneck was the input width, not the layer width

4 · Compare against what you already know

vs Counting bigrams in a 27×27 tensor: The bigram count table and the MLP both output 27 probabilities for the next character. What is fundamentally different about where those probabilities come from, which design choice causes it, and when would you still pick counts?

Check
  • counts: one independent row per context, filled by tallying
  • MLP: shared embeddings and weights, fitted by gradient descent, so contexts share evidence
  • the design choice is sharing: rows share nothing, parameters are reused by every context
  • counts win for short contexts with plenty of data (1 character: every row well filled); they fail as rows grow as 27ⁿ

vs Gradient descent finds the counting answer: The neural bigram already used one-hot inputs, a weight matrix and a softmax loss. What does the MLP add on top of it, and what does each addition buy?

Check
  • an embedding lookup instead of one-hot @ W: the same maths, cheaper, with a small learned point per character
  • 3 characters of context instead of 1, laid side by side with view
  • a tanh hidden layer, so characters interact instead of each adding a fixed vote
  • minibatches, lr decay and a dev split: dev 2.1701 vs the bigram's 2.45

vs From neuron to MLP to a training loop: micrograd's training loop and this lecture's loop run the same four moves. What changed between them, and which change is what makes training on 228,146 examples practical?

Check
  • same: forward, zero the grads, backward, p.data += -lr * p.grad
  • micrograd: scalar Value objects, 4 examples, the full batch every step
  • here: tensors, and a random 32-row minibatch per step
  • the minibatch is what makes it practical: ~1,000× cheaper steps

5 · Predict commit to an answer before revealing

The final 10-D model's first minibatch loss is 27.8817. A model that spread its probability evenly over all 27 characters would score −ln(1/27). Commit first: what is that number, and what does the gap say about the untrained network's logits?

Reveal

3.2958. 27.88 is far worse than knowing nothing, so the random init makes the logits large and confidently wrong: the plain randn weights give big preactivations and big logits. Karpathy's exercise E02 asks exactly this, and the next lecture opens by scaling the init down so the first loss starts near 3.30.
