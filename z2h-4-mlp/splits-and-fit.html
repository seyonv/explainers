Train/dev/test and under- vs overfitting

Also called: train/validation/test split, held-out data; underfitting = too little capacity, overfitting = memorising. Lecture 3 · splitting up the dataset into train/val/test splits and why · 0:53:20 · experiment: larger hidden layer · 1:00:49

Prime · 2 minutes before you read

The problem: The training loss only measures how well the net fits names it has already seen. A net that memorises its data gets a tiny training loss and is useless on new names, and without held-out data you can't tell the two apart, or know whether to make the model bigger or smaller.

Where it fits: The previous cards trained the MLP and read its loss on all 228,146 rows. This card splits the names first, so the same loss becomes a diagnostic. It turns the overfit-one-batch result from a sanity check into a warning, and it sets up the next card's experiment with bigger embeddings.

In one breath: the training loss only tells you how well the net fits examples it has already seen. So you hide some names from training (a dev set to compare settings, a test set to look at once at the very end) and compare losses. Train and dev nearly equal means the net is too small (underfitting); train far below dev means it has memorised (overfitting).

Predict first: the 100-unit net ends at train 2.3288 / dev 2.3279. You triple the hidden layer to 300 units (3,481 → 10,281 parameters) and train it the same 50,000 steps. Does the dev loss fall a lot, a little, or rise?

A little: 2.3279 → 2.2976, only 0.03 lower, for about 3× the parameters. Train and dev are still almost equal, so the net is still underfitting. The hidden layer wasn't the bottleneck; Karpathy suspects the 2-D embedding (1:00:49), which the next card grows.

Three piles, three jobs

n1 = int(0.8 × 32033) = 25626 words[:n1] → train 25,626 names n2 = int(0.9 × 32033) = 28829 words[n1:n2] → dev 3,203 names words[n2:] → test 3,204 names rows (one per character + the final '.'): Xtr 182,625 + Xdev 22,655 + Xte 22,866 = 228,146 (80.05% / 9.93% / 10.02%)

Measured with the lab. The Part 2 notebook printed 182,441 / 22,902 / 22,803 instead; one seed-42 shuffle gives the numbers above, the same as the Part 3–5 notebooks, and the cause of the difference isn't known.

A hyperparameter is a setting you pick rather than the net learning it: hidden size, learning rate, number of steps. Every time you keep a setting because its dev loss was lower, you've fitted a little to dev. That's why a third pile, test, stays unopened until the end: Karpathy's warning is that looking at it often means you "risk overfitting to it" (0:53:20).

Reading the two losses

The loss is the average negative log likelihood of the correct next character (lower is better; guessing uniformly over 27 characters gives −ln(1/27) = 3.2958). The number that diagnoses the net is the gap, dev − train.

A gap near zero, or even slightly negative, is noise between two samples of names: with train ≈ dev the net can't even fit the data it trains on, so it needs more capacity. After only the lr 0.1 phase the bigger net was behind (dev 2.4920 vs 2.3988): more parameters take more steps to train.

Why it beats the alternatives

✗ Trust the training loss

The 32-example net scores 0.2561 on its own examples and 13.6218 on dev names, far worse than a uniform guess (3.2958). Training loss can't tell fitting from memorising.

✗ Tune on the test set

Each setting you keep because test got lower leaks test into your choices, so the final test number comes out optimistic and nothing honest is left to report.

✗ Split rows, or skip the shuffle

Cutting the 228,146 rows puts parts of one name (.em → m in train, emm → a in dev) on both sides. Without a shuffle, dev is just the file's last block (it starts emma, olivia, ava), not a fair sample.

✓ Shuffle names, then 80/10/10

Train fits the parameters, dev compares settings, test is opened once. The dev − train gap tells you whether to grow the model or rein it in.

Is 80/10/10 a rule, and does train ≈ dev mean you're done?

Neither. 80/10/10 suits this 32k-name dataset. Karpathy's own makemore.py holds out only min(1,000, 10%) names as a single test set, and with very large datasets people often hold out a much smaller fraction. With very little data, one small dev set is noisy, and k-fold cross-validation (rotating which part is held out) is the usual fix.

Train ≈ dev only rules out overfitting; it doesn't say the net is good. Judge the level against a baseline: dev 2.3279 already beats the bigram's 2.45 (0:52:12). When the gap does open, the fixes run the other way: more data, a smaller model, or stopping earlier.

Understand and remember

  • The net only ever sees training rows → its training loss rewards memorising them → a low training loss can't tell fitting from memorising → score a held-out dev set (the 32-example net: train 0.2561, dev 13.6218)
  • Each setting kept because dev got lower → dev leaks into your choices → dev loss becomes slightly optimistic → keep a test set unopened and look at it once, for the honest final number
  • Train ≈ dev (gap −0.0009) → the net can't even fit the data it trains on → too little capacity (underfitting) → grow the model; train far below dev → memorising (overfitting) → more data, smaller model, or stop earlier
  • Hidden 100 → 300 (3,481 → 10,281 params) moves dev only 2.3279 → 2.2976 → the hidden layer wasn't the bottleneck → suspect another part: the 2-D embedding each character is squeezed into
  • detail that matters The split is over names, not rows → all of a name's rows land in one pile → dev can't contain the next character of a name the net trained on, so the dev loss isn't flattered by near-duplicates
  • detail that matters Bigger nets need more steps: after 30k steps at lr 0.1 the 300-unit net's dev was 2.4920 vs 2.3988 → compare sizes only after both have trained to a plateau, or you'll pick the smaller one for the wrong reason
