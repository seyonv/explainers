Logits to loss, and why F.cross_entropy

Also called: cross-entropy loss, negative log likelihood (NLL) of a softmax, log-softmax loss. Lecture 3 · implementing the negative log likelihood loss · 0:29:53 · introducing F.cross_entropy and why · 0:32:49

Prime · 2 minutes before you read

The problem: The network now outputs a (32, 27) block of raw scores, but training needs one number that says how wrong those scores are. Without it there is nothing to call .backward() on, and the obvious hand-written version silently returns nan once a score gets large.

Where it fits: It closes the forward pass. The hidden-and-output card produced logits; Lecture 2 already graded a bigram model with the average negative log likelihood. This card applies that same grade to logits and swaps the five hand-written steps for one library call before the first training loop.

Needs first: Hidden tanh layer and output logits

In one breath: the network ends in 27 logits per example: raw scores, any real number, one per possible next character. To grade them you turn each row into probabilities (exp, then divide by the row total), read off the probability of the character that actually came next, take −log of it, and average over the batch. F.cross_entropy(logits, Y) gives exactly the same number in one call, and it doesn't blow up when a logit gets large.

Predict first: one row of logits is [-2, 3, -3, 0, 100], so the model is very sure about the last character. What probability does the hand-written exp() then divide-by-sum give that character?

Not 1.0 but nan ("not a number"). A 32-bit float can't hold anything above about 3.4 × 10³⁸, which is e88.7. So exp(100) becomes inf, the row sum is inf too, and inf / inf is nan. F.cross_entropy on the same row gives a clean 0.0 if that character is the answer, and 97.0 if the answer is the second one (computed).

Same number, fewer pieces

Karpathy gives three reasons to switch (0:32:49):

  • Fewer tensors in memory. The manual version keeps counts and prob, two extra (32, 27) tensors, and autograd records 7 backward steps (exp, sum, divide, index, log, mean, negate). F.cross_entropy records 2: LogSoftmaxBackward0 and NllLossBackward0 (counted from loss.grad_fn).
  • A simpler backward pass. Like tanh's local derivative 1 − t² in micrograd, the whole chain collapses to one expression: dloss/dlogits = (prob − one_hot(Y)) / 32. It matches autograd through the manual steps to within 5.6 × 10⁻⁹ (computed).
  • It can't overflow, which the next table shows.

Why the hand-written version breaks at 100

[-2, 3, -3, 0, 100]inf0.0 · 0.0 · 0.0 · 0.0 · nan

The fix uses one fact: adding the same number to every logit in a row doesn't change the probabilities, because ec multiplies the top and the bottom of the fraction alike. So PyTorch subtracts each row's largest logit first. The biggest exponent is then e0 = 1, and nothing can overflow.

logits [-2, 3, -3, 0, 5 ] exp [0.1353, 20.0855, 0.0498, 1.0, 148.4132] sum 169.6838 minus the max (5) [-7, -2, -8, -5, 0 ] exp [0.000912, 0.135335, 0.000335, 0.006738, 1.0] sum 1.1433 last char: 148.4132 / 169.6838 = 0.8746 = 1.0 / 1.1433

Karpathy's demo at 0:35:31. With 100 in the row, the shifted logits are [−102, −97, −103, −100, 0] and the probabilities come out as 0, 0, 0, 0, 1.0 (the lab prints adding a constant changes nothing: True). F.cross_entropy goes one step further and stays in log space, so it never takes the log of a probability that rounded to 0.

counts = logits.exp()                         # (32, 27), all > 0
prob = counts / counts.sum(1, keepdims=True)  # rows sum to 1
loss = -prob[torch.arange(32), Y].log().mean()
print('manual loss    ', round(loss.item(), 4))
print('F.cross_entropy', round(F.cross_entropy(logits, Y).item(), 4))

lg = torch.tensor([-2., 3, -3, 0, 100])
print(lg.exp() / lg.exp().sum())    # the 100 breaks it
z = lg - lg.max()                   # what PyTorch does inside
print(z.exp() / z.exp().sum())

Why it beats the alternatives

✗ exp, normalize, log by hand

Gets the same 17.7697, but stores two extra (32, 27) tensors, records 7 backward steps, and turns any logit above 88.7 into inf and then nan.

✗ F.softmax, then .log()

The softmax is safe, but a tiny probability can round to 0.0 before the log. For [-2, 3, -3, 0, 200] with answer 1 this loss is inf; F.cross_entropy says 197.0 (computed).

✗ Clamp the logits

Capping logits hides the nan by changing the model's output, and a clamped value gets zero gradient, so the parameters behind it stop learning from that example.

✓ F.cross_entropy(logits, Y)

One call: subtract the row max, log-softmax, pick, mean. Same number, 2 backward steps, a one-line gradient, and no overflow.

Give it logits, not probabilities

F.cross_entropy applies the softmax itself, so it wants the raw logits. If you hand it prob instead, it softmaxes a second time and returns 3.3172 for our batch instead of 17.7697, with no error or warning (computed). The shape rule is (N, C) logits (C = 27 classes here) and (N,) integer labels; the GPT-style models later flatten (B, T, C) logits to (B·T, C) first, as makemore.py does with logits.view(-1, logits.size(-1)).

It is not the tool when you need the probabilities themselves, for example to sample the next character. Use F.softmax(logits, dim=1) there; it has the same max-subtraction built in.

1 · Core model what to internalise, what to just look up

Keep it if it changes what you can explain, predict, compare, choose, build or debug. Otherwise it's reference.

Understand and remember

  • logits can be any real number → exp makes every score positive and keeps their order → dividing by the row sum makes each row a probability distribution → −log of the label's probability is 0 when the net is sure and right, and huge when it is sure and wrong → the mean over 32 rows is the loss (17.7697 here)
  • adding a constant c to every logit multiplies top and bottom of the softmax by ec → probabilities don't change → subtract the row max so the largest exponent is e0 = 1 → nothing overflows, whereas by hand a logit above 88.7 gives inf → inf/inf = nan
  • F.cross_entropy fuses log-softmax and the pick into one op → no counts/prob tensors kept, 2 backward nodes instead of 7 → its gradient is one expression, (prob − one_hot(Y)) / N → cheaper and more robust training with the same loss value
  • detail that matters it works in log space (log-softmax = logit − max − log Σ elogit − max) → it never takes the log of a probability that rounded to 0 → F.softmax(...).log() can still return inf loss (row with 200: inf vs 197.0), F.cross_entropy can't

Reference only

  • F.cross_entropy(logits, Y) takes (N, C) float logits and (N,) integer labels; (B, T, C) is flattened with .view(-1, C)
  • float32's largest value is about 3.4 × 10³⁸ = e88.7
  • keepdims=True in counts.sum(1, keepdims=True) keeps shape (32, 1) so the division broadcasts per row
  • the backward nodes are named LogSoftmaxBackward0 and NllLossBackward0
  • uniform guessing over 27 characters scores −ln(1/27) = 3.2958

  3. mechanism Walk [-2, 3, -3, 0, 100] through the hand-written softmax and through the max-shifted one. Where exactly does the first fail?
    Check

    Check
    • both avoid the overflow, because softmax subtracts the max
    • softmax-then-log can round a tiny probability to 0.0 first, so log gives −inf and the loss is inf (the row with 200: inf vs 197.0)

4 · Compare against what you already know

vs Logits → counts → probabilities: the softmax: Lecture 2's neural bigram also did exp-then-normalize by hand and never hit nan. What about that model kept it safe, and why can't the MLP rely on the same thing?

Check
  • the bigram's logits were just one row of a 27×27 matrix of standard-normal weights, so they stayed within a few units of 0
  • the MLP's logits come from h @ W2 + b2 with 100 hidden units, so they are already in the ±20s at init (up to 27.9 here)
  • the manual version is only safe while every logit stays below about 88.7; training can push logits there
  • the loss formula is identical in both; only the numerical safety differs

vs Cross-entropy backward in three lines: softmax − one-hot: This card uses the fact that F.cross_entropy's gradient is (prob − one_hot(Y)) / N. How does that one-liner differ from backpropagating through the five manual steps, and when would you want the manual route anyway?

Check
  • the manual route multiplies local derivatives through exp, sum, divide, index, log, mean and negate
  • the fused route collapses them algebraically into one expression, so it is faster and has fewer places to lose precision
  • both give the same gradient (here they agree within 5.6 × 10⁻⁹)
  • you'd go manual to learn or to debug, which is exactly what the backprop-ninja course does

5 · Predict commit to an answer before revealing

Before any training, suppose every logit in the (32, 27) block were exactly 0. What would F.cross_entropy(logits, Y) return, and is that better or worse than our seeded net's 17.7697?

Reveal

3.2958, which is −ln(1/27): all-zero logits give every character probability 1/27, whatever the label. That is far better than 17.7697. A net that knows nothing but admits it beats one that is confidently wrong, and making the initial logits small is the first fix in the next lecture (the expected-initial-loss card).
