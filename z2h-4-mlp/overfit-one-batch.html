First training loop: overfit 32 examples

Also called: the gradient descent loop, overfitting a single batch (as a sanity check). Lecture 3 · implementing the training loop, overfitting one batch · 0:37:56

Prime · 2 minutes before you read

The problem: You now have a network that turns 32 contexts into a loss of 17.77, but its 3,481 numbers are random. Without a loop that changes them, the loss never moves, and without a quick test you can't tell whether a slow, stuck loss is a bug or a hard problem.

Where it fits: The micrograd lecture's training loop, now on tensors: the same zero-grad → backward → update moves, applied to the MLP from the hidden-and-output and cross-entropy cards. The next card swaps the fixed 32 rows for random minibatches of all 228,146.

In one breath: training is four lines run over and over: a forward pass to get the loss, wipe the old gradients, a backward pass to fill every .grad, then nudge every parameter a little against its gradient. With 3,481 parameters and only 32 examples, the network can almost memorise the batch. The loss falls from 17.77 to 0.2561, which proves the whole pipeline works. It can't reach 0, because the context ... appears five times with five different answers.

Predict first: no model can reach loss 0 on these 32 rows. What is the lowest loss any model could reach, and which rows stop it?

0.2515, set by the five ... rows. Every name starts with the context ..., and its labels are e, o, a, i and s. The best a model can do for that one input is to give each of the five letters probability 1/5. Those five rows then cost −ln(1/5) = 1.6094 each, and the other 27 rows can cost almost nothing: 5 × 1.6094 / 32 = 0.2515. After 1,000 steps the lab lands at 0.2561, just above it.

One step is four moves

The parameters are the numbers the network learns: the embedding table C and the weights and biases W1, b1, W2, b2 from the previous cards. The batch is the set of examples a step looks at, and here it is all 32 rows built from the first five names, every time.

Step ④ is gradient descent. Each gradient says how much the loss rises when that one number is nudged up, so you move each number a small step the other way. The learning rate (lr) sets the size of the step:

▶ Build itruns on your M3 · under 1 s

When: pause the video at 0:37:56 and type this before watching on. X, Y come from build_dataset(words[:5]), and C, W1, b1, W2, b2 are the seeded tensors from the hidden-and-output card.

parameters = [C, W1, b1, W2, b2]
for p in parameters:
    p.requires_grad = True
for i in range(1000):
    emb = C[X]                                  # (32, 3, 2)
    h = torch.tanh(emb.view(-1, 6) @ W1 + b1)   # (32, 100)
    logits = h @ W2 + b2                        # (32, 27)
    loss = F.cross_entropy(logits, Y)
    for p in parameters:
        p.grad = None
    loss.backward()
    for p in parameters:
        p.data += -0.1 * p.grad
print(loss.item(), logits.max(1).indices, Y)

Without requires_grad = True, loss.backward() raises an error, because no tensor asked for gradients. Setting p.grad = None is Karpathy's way to zero the grads; PyTorch's zero_grad(set_to_none=True) does the same.

Why overfit one batch first

✗ Start on all 228,146 rows

One full-batch step took 126.0 ms on the M3 (minibatches card), and nobody knows the best reachable loss there, so a loss that stalls could be a bug or just a hard problem.

✗ Check only that the loss falls

Delete p.grad = None and the loss still falls, to 0.2711 at step 100. Then the stale gradients pile up and it climbs to 41.4 by step 999 (computed).

✗ Stop when the number looks small

After 10 steps the loss is 3.9858, a big drop from 17.77, yet only 11 of 32 rows are predicted correctly (computed). A drop alone doesn't say the model has learned what it can.

✓ Overfit a tiny batch

It runs in under a second and has a target you can work out by hand (0.2515). A correct loop has to land just above it, and this one does: 0.2561 with only the ... rows wrong.

Isn't overfitting bad?

Here it is the goal, and only here. Overfitting means fitting the training rows so closely that the model memorises them. With 3,481 parameters for 32 rows (about 109 per row), that's easy, and it says nothing about names the model hasn't seen. It is a debugging test: if the loop can't memorise 32 rows, it can't learn 228,146.

The test is not complete. Leave C out of the update and the loss still reaches 0.2704 with 28/32 correct (computed), because the other layers can memorise alone. The real training starts on the next card: random minibatches of the full dataset, and after that held-out dev rows to catch real overfitting.

Understand and remember

  • .grad accumulates with += on every backward() → without p.grad = None each step uses the sum of all past gradients → steps grow and the loss blows up (0.2711 at step 100, 41.4 at step 999 here)
  • Each gradient says how the loss changes as one number moves up → step every number by -lr × grad → the loss drops, from 17.77 to 0.2561 in 1,000 steps with lr 0.1
  • 3,481 parameters for 32 rows → the net can memorise every row that has a single answer (p ≥ 0.982 on the other 27 rows) → this tests the pipeline, not how well the model generalises
  • The context ... appears 5 times with labels e, o, a, i, s → the best any model can do is 1/5 each → the loss floor is 5 × ln 5 / 32 = 0.2515 → a correct loop lands just above it, and argmax gets only 1 of those 5 rows right (28/32)
  • detail that matters p.data += … updates the numbers outside autograd → the update isn't recorded in the graph → the next forward pass starts a fresh graph from the new values

Reference only

  • p.grad = None vs zero_grad(set_to_none=True) in makemore.py L683
  • requires_grad = True must be set once before the loop, or backward() raises an error
  • logits.max(1) returns (values, indices); compare .indices with Y
  • the lab's printed steps: 0, 1, 10, 100, 500, 999

  2. mechanism Walk one step of the loop for the single number b2[5] at step 0: what does each of the four moves do to it?
    Check
    • forward: b2[5] = 0.4381 is added into the logit for e in every row

  3. tradeoff The final loss is 0.2561. Split it into the part you could never remove and the part more training could still shrink. Is running 10,000 more steps worth it?
    Check
    • the five ... rows give 0.2522, and the floor for them is 0.2515
    • the other 27 rows give 0.0039
    • at most about 0.005 is left to gain, and all of it is on training rows, so it tells you nothing new about the model
  4. tradeoff Lowering lr from 0.1 to 0.01 still gets 28/32 correct after 1,000 steps. What does the smaller rate cost you, and what would a much larger rate risk?
    Check
    • lr 0.01 is slower: loss 13.77 at step 10 and 0.3167 at step 999 instead of 3.9858 and 0.2561
    • a large rate takes steps that overshoot, so the loss can bounce or climb instead of settling

Reveal

The best distribution for ... is now i: 2/6 and the others 1/6 each. That costs 2 × ln 3 + 4 × ln 6 = 9.36 over the ... rows, spread over more rows than before (the new name adds its own rows too), and the net will now clearly predict i, because i is the most common label rather than a near tie.
