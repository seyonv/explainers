Checkpoint 2: from a loop that runs to a model you can trust

Ties together overfitting one batch, minibatches, the learning-rate finder, train/dev/test splits and scaling the embeddings, plus micrograd's zero_grad and the bigram lecture's counting baseline and smoothing: how the lecture gets from 17.77 to a dev loss of 2.17, and how it knows each step helped.

What this ties together, and why now. Five cards turned one forward pass into a trained model, and each one added a check. First, overfit 32 rows to prove the loop works. Then train on random minibatches, because exact gradients are too slow. Sweep the learning rate instead of guessing it, and decay it once progress stalls. Judge the model on names it never saw, and read train vs dev to decide what to grow. Growing the hidden layer barely helped; widening the embeddings did. The lecture ends here, and the next one opens by fixing the init. Before you move on, check that you can tell which of these tools a given symptom calls for.

Comes back from earlier courses: micrograd's training loop and why gradients accumulate, gradient descent finding the counting answer, smoothing with fake counts and sampling with multinomial. The build pits the MLP against the bigram's counts on the same held-out names.

How to use this page. Close the cards. Write a full answer to each question before you open its Check. A wrong or shaky answer tells you exactly which section to reopen. The questions are mixed on purpose, so part of the work is spotting which idea applies.

1 · Mixed retrieval

  1. The sweep uses 10**torch.linspace(-3, 0, 1000), not torch.linspace(0.001, 1, 1000). Why? And the lowest smoothed loss sat at lr 0.157, so why is 0.1 the better pick?
    Check
    • even spacing puts only 99 of the 1,000 steps below lr 0.1, so 90% of the run is spent where training is already unstable. Spacing the exponent evenly gives each factor of ten 333 steps, so 666 of them are below 0.1
    • the valley is flat. Smoothed loss by exponent: −1.1 → 3.54, −1.0 → 3.32, −0.9 → 3.23, −0.8 → 3.14, −0.7 → 3.22. Anything from about −1.1 to −0.7 is fine
    • the sweep is one training run, so its left side is also high because the net hasn't learned yet (first minibatch loss 21.81). That pushes the dip to the right, which is a reason to pick from the low side of the valley
    • rerun the sweep whenever the batch size, the model size or the init changes

    If you missed it, reopen the learning-rate finder, "Step 2: sweep lr in one run" and "Is the valley 'the' learning rate?".

  2. which idea?Your 300-unit net ends at train 2.2967 / dev 2.2976. A teammate suggests adding regularisation, like the bigram's fake counts, to "close the gap". Which idea applies here, and what actually lowers the dev loss?
    Check
    • dev − train = +0.0009, so there's no gap to close. Train ≈ dev means underfitting: the net can't even fit the data it trains on
    • regularisation, like fake counts, pulls the model toward uniform. It helps against memorising, which isn't the problem here. In the bigram lecture, +1 fake counts only raised the training loss (2.4540 → 2.4546), and the payoff came on unseen names
    • more hidden units barely helped: 100 → 300 cut dev by only 0.0303 (2.3279 → 2.2976) for 2.95× the parameters, because each neuron still reads the same 6 numbers
    • widening the embeddings did help: 10-D × 200 is 11,897 parameters (+16%), with dev 2.2376 after 50k steps and 2.1698 after 200k (notebook 2.1701). Now the gap opens to +0.043, the first sign of overfitting

    If you missed it, reopen train/dev/test, "Reading the two losses", scaling the embeddings, "Step 2: widen the bottleneck", and smoothing, "Is +1 the right amount?".

  3. What is the lowest loss any model could reach on the 32 rows from the first five names, and which rows set that floor?
    Check
    • the five ... rows. That one context is followed by e, o, a, i and s, so the best any model can do is give each of them probability 1/5
    • each of those rows then costs −ln(1/5) = 1.6094, and the other 27 rows can cost almost nothing: 5 × 1.6094 / 32 = 0.2515
    • the lab lands at 0.2561 after 1,000 steps with 28/32 correct. The four misses are ... rows, all predicted as i

    If you missed it, reopen overfit one batch, "Why it stops at 0.2561, not 0".

  4. debugYour overfit loop on the 32 rows gets the loss down to 0.2711 by step 100. Then it climbs, and by step 999 it's 41.4. The forward pass and the update are copied from the card. What's missing, and why does the loss fall at first?
    Check
    • the p.grad = None line before loss.backward(). Backward adds into .grad (it has to, because a reused value like C[0] collects the gradient from every use)
    • without the reset, each step's gradient is the sum of every earlier step's gradient. Early on they all point roughly the same way, so the loss falls fast. Later the pile of stale gradients keeps pushing past the minimum, and the loss climbs
    • the working loop ends at 0.2561. micrograd has the same bug under a different name: forgetting zero_grad

    If you missed it, reopen overfit one batch, "Why overfit one batch first" (the "Check only that the loss falls" cell), micrograd's training loop, "Forgetting zero_grad", and the += bug, "The smallest case: b = a + a".

  5. which idea?You have about 1.2 seconds of compute and all 228,146 rows. Do you spend it on 10 full-batch steps or on 10,000 steps of 32 random rows? Predict both losses.
    Check
    • one full-batch step took 126.0 ms and one minibatch step 0.119 ms, which is 1,063× faster (measured under load)
    • 10 full-batch steps reach a full-set loss of 10.7096. 10,000 minibatch steps reach 2.5214
    • per step, the exact gradient wins only slightly (after 100 steps: 3.5755 vs 3.7658). Per second it loses badly. Karpathy prefers an "approximate gradient" and more steps (0:44:23)
    • a 32-row gradient still points the right way early on: its cosine with the full gradient is 0.826 at init

    If you missed it, reopen minibatches, "What one step costs" and "What 10,000 cheap steps buy".

  6. The 32-row net from the overfit card scores 0.2561 on its own rows. Predict its loss on the dev names. Then explain why you shuffle and split by names, not rows, and why the test set stays closed.
    Check
    • 13.6218, far worse than guessing uniformly (3.2958). A low training loss can't tell fitting from memorising; only held-out names can
    • split by names so a name's rows can't land on both sides (.em → m in train, emm → a in dev). Shuffle once with seed 42 first, or dev is just the file's last block
    • every setting you keep because dev went down fits dev a little. Test is opened once at the end, or you "risk overfitting to it" (0:53:20)
    • it's the same reason the bigram's fake-count k can't be picked on the training loss, which always prefers k = 0

    If you missed it, reopen train/dev/test, "Three piles, three jobs" and "Why it beats the alternatives".

  7. which idea?At lr 0.1 the full-set loss moves only from 2.5227 at step 5,000 to 2.5214 at step 10,000. There are three options: raise lr, train longer at 0.1, or cut lr to 0.01. Which one, and why does it work only late in training?
    Check
    • cut lr 10×. From the 30k-step point, 10,000 more steps at 0.01 drop the loss by 0.0774 (to 2.3401), while 10,000 more at 0.1 drop it by only 0.0169 (to 2.4006)
    • the cause is minibatch noise. Near the bottom, 32-row gradients barely agree with the full one (cosine 0.328, against 0.826 at init), and lr scales the resulting jitter. Early on the real downhill direction dominates, so big steps win
    • raising lr makes it worse: the sweep's loss climbs past exponent −0.6 (3.957, then 5.925). A bigger batch also cuts the noise: the spread is ± 0.195 at 32 rows and ± 0.073 at 256

    If you missed it, reopen the learning-rate finder, "Step 3: train at 0.1, then decay to 0.01", and minibatches, "How noisy is noisy?".

  8. Between step 1,000 and step 10,000, the minibatch loss your loop prints rises from 2.4407 to 2.6622. Is training going backwards? How should you report progress?
    Check
    • no. Over the same steps the full-set loss fell from 2.6531 to 2.5214
    • a minibatch loss describes 32 rows, not the model: after 10,000 steps it ranges from 1.945 to 2.975 across 200 random batches
    • report the loss on all training rows and on dev, computed under torch.no_grad() so no graph is built

    If you missed it, reopen minibatches, "What minibatches do not do".

3 · Build: sanity-check, train, and beat counting on unseen names

runs on your M3 · about 10 sWhat it reinforces: the zero-grad / backward / update loop and the overfit test (overfit one batch, micrograd's loop), random minibatches (minibatches), step decay (lr finder), a seeded split by names and the train/dev reading (splits), the 10-D model and sampling (scale and sample), and the bigram counts with fake counts as the baseline (counting, smoothing). Write it in one file without looking at the cards.

  1. Sanity first. Build the 32 rows from words[:5] and the seeded 2-D, 100-unit net (C, W1, b1, W2, b2 from manual_seed(2147483647), in that order). Run 1,000 full-batch steps at lr 0.1, then count how many rows logits.argmax(1) gets right.
  2. Split. random.seed(42), shuffle a copy of the words once, cut at 80% and 90%, and call build_dataset on each piece.
  3. Baseline. The bigram only looks at the last character of each context. Count (Xtr[:, -1], Ytr) pairs into a 27 × 27 table N (N.index_put_(..., accumulate=True) does it in one line), add 1, normalise the rows, and score train and dev with the mean of −log P.
  4. The MLP. A fresh seeded net with C (27, 10), W1 (30, 200), b1 (200,), W2 (200, 27), b2 (27,). Train on 32 random rows of Xtr per step: 30,000 steps at lr 0.1, then 20,000 at 0.01.
  5. Read it. Under torch.no_grad(), compute the full train and dev losses and the gap between them.
  6. Sample. Using manual_seed(2147483647 + 10), draw 8 names: start from [0, 0, 0], take the softmax, call torch.multinomial, slide the window, and stop at ..
Done when: the overfit loss is 0.2561 with 28/32 right; Xtr is (182625, 3); the bigram baseline scores dev 2.4533; the MLP has 11897 parameters and reaches train 2.2171 / dev 2.2376, which is 2.4533 − 2.2376 = 0.2157 below counting on the same unseen names, with a small gap (+0.0205); and most samples look like names. Stretch: run 200,000 steps with the decay at 100,000 (about 50 s) and dev drops to about 2.17 (2.1698 on the scale-and-sample card).
