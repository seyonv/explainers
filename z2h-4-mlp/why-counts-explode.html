Why a bigger count table fails

Also called: the curse of dimensionality, data sparsity in n-gram models. Lecture 3 · intro · 0:00:00

Prime · 2 minutes before you read

The problem: The bigram model sees one character of context, so its names barely look like names. The obvious fix, counting longer contexts, needs a table whose rows multiply by 27 per character, and the data can't fill them.

Where it fits: This opens the MLP course. It takes the bigram count table from Lecture 2 and asks what happens when you widen its context, which is the reason the course switches to learned embeddings next.

In one breath: the bigram model from Lecture 2 kept one row of counts per previous character. To look further back you'd need one row per combination of previous characters, and that number multiplies by 27 with every extra character. The 228,146 training examples in names.txt can't come close to filling those rows, so most rows are empty or hold a handful of counts, and a handful of counts is a guess, not a probability.

Predict first: with 3 characters of context there are 27³ = 19,683 possible contexts. names.txt gives 228,146 (context → next char) examples. How many of those 19,683 contexts show up even once?

Only 5,686 (28.9%). And 3,374 of those 5,686 appear fewer than 10 times. The average of 11.6 examples per row hides the skew: the single context ... (start of a name) takes 32,033 of the examples by itself.

from collections import Counter

print(len(words), 'names')
for n in range(1, 5):
    X, Y = build_dataset(words, block_size=n)
    counts = Counter(tuple(r) for r in X.tolist())
    rows = 27 ** n                       # every possible context
    seen = len(counts)                   # contexts that occur at all
    few = sum(1 for c in counts.values() if c < 10)
    print(f'n={n} rows {rows:>7,} seen {seen:>6,} '
          f'({100*seen/rows:5.1f}%) <10: {few:>6,} '
          f'per row {len(Y)/rows:7.2f}')

More context helps, then hurts

To see the failure as a loss, fill a count table from the training words only (the 80% seed-42 split), add 0.1 fake counts to every cell so no probability is zero, and score it on the 22,655 dev examples it never saw. For comparison, the flat MLP with 8 characters of context reaches dev 2.0342 with 22,097 parameters (measured on the WaveNet course's baseline).

Why it beats the alternatives

✗ Just grow the count table

Each extra character multiplies the rows by 27. By n=4 the table has 14.3 million cells for 228,146 examples, and dev loss is already worse than at n=3.

✗ Smooth harder

Fake counts stop the infinite losses but pull thin rows toward uniform. With +1 instead of +0.1, dev loss at n=4 is 2.3574, worse than +0.1's 2.1522 (computed).

✗ Fall back to shorter contexts

Classic n-gram "backoff" uses a shorter row when the long one is thin. It softens the problem (not measured here), but rows still share nothing: .em (288 examples) teaches .am nothing about what follows a vowel.

✓ Learned embeddings + an MLP

Characters become points in a small space, so similar contexts share what they learned. Adding a character adds one slice of weights to W1 (10 embedding numbers × 200 hidden units = 2,000 in this lecture's final net), not 27× more rows.

Is a count table always worse?

No, not at 3 characters. Well smoothed, the n=3 table's dev loss of 2.1018 is actually a bit better than this lecture's final MLP (notebook dev 2.1701). The 0.1 fake counts were picked as the best of 0.01, 0.1 and 1 on the dev set, so that number is slightly optimistic, but the point stands. For short contexts and plenty of data, counting is simple, exact and hard to beat.

Counts lose when the context gets long (n=8: 2.5423 vs the MLP's 2.0342) or the vocabulary gets big. Bengio's paper works on words: 17,000 words with 3 words of context is 17,000³ ≈ 4.9 × 10¹² rows. That's the regime the rest of this series is built for.

Understand and remember

  • each context gets its own row → rows = 27ⁿ → examples per row = 228,146 / 27ⁿ falls 27× per extra character (11.59 at n=3, 0.43 at n=4) → most rows are empty or thin
  • thin row → counts / total from a few examples → overconfident probabilities (one example becomes P = 1) → unseen continuations get zero probability → infinite loss unless you add fake counts
  • fake counts pull thin rows toward uniform → longer contexts gain information but lose reliability → dev loss bottoms out at n=3 (2.1018) and climbs to 2.5423 by n=8
  • rows share nothing → what .em learned can't transfer to .am → the fix is to share parameters across similar contexts (embeddings), so parameters grow linearly with n instead of 27×
  • detail that matters the average hides the skew: ... alone takes 32,033 of 228,146 examples → the long tail of contexts is even thinner than 11.59 per row suggests

Reference only

  • the exact counts per n (27 / 602 / 5,686 / 22,135 seen)
  • collections.Counter over tuple(row) to count contexts
  • 27ⁿ includes impossible contexts like a.b; 18,279 are possible at n=3
  • the smoothing strength 0.1 used in the dev-loss table

4 · Compare against what you already know

vs Model smoothing with fake counts: In Lecture 2, +1 fake counts barely changed the bigram loss (2.4540 → 2.4546). Why does the same knob matter so much at n=4, and how does each model fail if you set it wrong?

Check
  • bigram rows hold thousands of counts, so +1 per cell is negligible
  • n=4 rows hold a few counts, so +1 per cell can outweigh the real data
  • too little smoothing: zero probabilities and infinite loss; too much: rows collapse toward uniform (log 27 ≈ 3.30)

vs Bengio 2003: characters as points in space: The count table and the embedding model both predict the next character from the last n. What design choice lets the embedding model use a long context without a 27ⁿ-row table?

Check
  • the table stores an independent row per context
  • the embedding model stores a vector per character and shares one set of weights across all contexts
  • similar characters get nearby vectors, so learning about one context transfers to similar ones
  • cost: it must be trained by gradient descent and can underfit, while the table is exact from counting
