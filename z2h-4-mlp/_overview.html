In one breath: a count table can't look back three characters, because 27³ = 19,683 contexts leave most rows empty. So give each character a few learned numbers (an embedding), lay the three characters' embeddings side by side, run them through one tanh hidden layer to get 27 scores, and train everything with minibatch gradient descent. Then learn the habits that tell you whether it worked: overfit a tiny batch first, sweep the learning rate, and judge on names the model never saw. The lecture goes from a first loss of 17.77 to dev 2.17, below the bigram's 2.45.

The cards, in lecture order

The idea

  1. 1Why a bigger count table fails · 27ⁿ rows: at n = 3 only 5,686 of 19,683 contexts ever occur.
  2. 2Bengio 2003: characters as points in space · a learned vector per token, shared by every context, so similar tokens share what they learn.

Building it

  1. 3Names into (context → next char) pairs · pad with dots, slide a 3-wide window: 5 names give X (32, 3).
  2. 4An embedding is just indexing · C[5] equals one_hot(5) @ C; C[X] gives (32, 3, 2).
  3. 5.view: reshaping for free · storage plus strides: view(-1, 6) lays the 3 embeddings side by side with no copy.
  4. 6Hidden tanh layer and output logits · (32, 6) → (32, 100) → (32, 27); 3,481 parameters, 78% in W2.
  5. 7Logits to loss, and why F.cross_entropy · same 17.7697 as by hand, but no nan at a logit of 100.
  6. ✓Checkpoint 1: from three characters to one loss number · mixed retrieval over cards 1–7 and the bigram lecture.

Training it

  1. 8First training loop: overfit 32 examples · 17.77 → 0.2561, just above the 0.2515 floor set by the five ... rows.
  2. 9Minibatches: noisy but fast · 32 random rows, ~1,000× cheaper steps: full-set 2.5214 after 10,000.
  3. 10Finding the learning rate, then decaying it · sweep 10⁻³ … 10⁰, train at 0.1, decay to 0.01: 2.3401.
  4. 11Train/dev/test and under- vs overfitting · 80/10/10 by name; train ≈ dev means too small; 300 hidden units barely help.
  5. 12Seeing the embeddings, scaling up, sampling · vowels cluster in 2-D; 10-D × 200 reaches dev 2.1698; sample names.
  6. ✓Checkpoint 2: from a loop that runs to a model you can trust · mixed retrieval over cards 8–12, micrograd and the bigram baseline.
  7. ★The six big ideas of the MLP · six claims and six sketches to redraw.

1 · Core model what to internalise, what to just look up

Keep it if it changes what you can explain, predict, compare, choose, build or debug. Otherwise it's reference.

Understand and remember

  • A context of n characters needs 27ⁿ count rows → the data leaves most rows thin (5,686 of 19,683 seen at n = 3) → give each character a learned row of C shared by every context → similar characters drift together → evidence in one context helps similar ones, and one extra character costs d·H weights, not 27× more rows
  • Embed (C[X], a one-hot matmul done by indexing) → view(-1, 3d), free because it only rewrites strides → tanh(x@W1 + b1) → h@W2 + b2 logits → F.cross_entropy, which subtracts the row max so it can't overflow → one differentiable number, so backward reaches every parameter including C
  • A loop that can't memorise 32 rows can't learn 228,146 → overfit first (0.2561 vs a 0.2515 floor) → then 32 random rows per step, ~1,000× cheaper than the full batch → near the bottom the gradient noise dominates → decay lr 0.1 → 0.01 (2.4175 → 2.3401)
  • Training loss can't tell fitting from memorising → hold out dev and test names → train ≈ dev means underfitting → grow the part that squeezes the model: 3× hidden units gave dev −0.03, 2 → 10 embedding numbers −0.06 → dev 2.1698 with 11,897 parameters
  • detail that matters Plain randn init → logits far from zero → first loss 17.7697 on 32 rows (27.8817 on the final model's first minibatch) instead of 3.2958, and 32.7% of tanh units saturated → wasted early steps and weak gradients → the next lecture's first fix

Reference only

  • block_size 3; seeds 2147483647 (parameters) and 42 (the name shuffle)
  • split sizes 182,625 / 22,655 / 22,866 (the Part 2 notebook prints 182,441 / 22,902 / 22,803)
  • parameter counts 3,481 (d 2, H 100), 10,281 (d 2, H 300), 11,897 (d 10, H 200)
  • torch.randint, 10**torch.linspace(-3, 0, 1000), torch.multinomial

Why this step?

3 · Retrieve from memory, card closed
  1. concept Explain to someone who knows only the bigram count table why a network with 3,481 numbers can say something useful about three-character contexts that a 531,441-cell table can't.
    Check
    • the table gives every context its own row, and at n = 3 most rows have few or no counts
    • the network shares C and the weights across all contexts
    • characters that behave alike get nearby embeddings, so a rare context borrows from similar common ones
    • it generalises smoothly because its output changes smoothly as the input points move
  2. mechanism Walk one minibatch through the whole course's training step: from ix to the parameter update, naming each tensor's shape for the final model.
    Check
    • ix = torch.randint(0, Xtr.shape[0], (32,)) picks 32 rows
    • C[Xtr[ix]] (32, 3, 10) → view(-1, 30) (32, 30)
    • tanh(@W1 + b1) (32, 200) → @W2 + b2 (32, 27)
    • F.cross_entropy(logits, Ytr[ix]) → a scalar
    • set every p.grad = None, loss.backward(), then p.data += -lr * p.grad with lr 0.1 or 0.01
  3. tradeoff Your net ends at train 2.30 / dev 2.31. A teammate wants to triple the hidden layer; you want to widen the embedding. Using this course's measurements, argue which to try first, and name what each change costs.
    Check
    • train ≈ dev says underfitting, so more capacity is the right direction
    • tripling H (3,481 → 10,281 params) moved dev only 0.03, because every neuron still reads the same 6 numbers
    • d 2 → 10 with H 200 (11,897 params) moved dev about 0.06 at the same step budgets
    • both need more steps to pay off (50k → 200k), and a bigger model can start to overfit: the final gap is 0.043
  4. concept Which of this course's measured numbers are sanity checks with a known target, and which can only be judged against another run?
    Check
    • known targets: 3.2958 for a uniform guess at step 0, 0.2515 as the overfit floor for the 32 rows, F.cross_entropy equal to the manual loss
    • relative only: dev loss vs the bigram's 2.45, vs the previous setting, vs train
    • the known-target checks catch bugs; the relative ones choose settings

Why this step?

4 · Compare against what you already know

vs Gradient descent finds the counting answer: The bigram course's overview idea was that counting and gradient descent land on the same model (≈ 2.45). Why can't gradient descent beat counting there, while here the MLP reaches 2.17? What design choice makes the difference, and how does each approach fail?

Check
  • bigram: one-hot @ W is just a row per previous character, the same free parameters the count table has, so the best either can do is the counts
  • MLP: longer context plus shared embeddings and a hidden layer, so it can use 3 characters without a row per context
  • the counting model fails on long contexts (empty rows); the neural bigram fails because it has no more information than the counts
  • the MLP fails differently: a fixed 3-character window and a careless init

vs The six big ideas of the MLP: This page gives one equation and a table of levers; the big-ideas card gives six claims. Which claims map onto which terms of the equation, and which claims are about the training process rather than the model?

Check
  • counts vs embeddings and lookup = matmul describe the xi term
  • F.cross_entropy is the outer loss term
  • overfit one batch, noisy minibatch steps and judging on held-out data describe the update rule and how it is checked, not the model
