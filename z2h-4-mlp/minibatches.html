Minibatches: noisy but fast

Also called: minibatch gradient descent, stochastic gradient descent (SGD), batch size. Lecture 3 · training on the full dataset, minibatches · 0:41:25

Prime · 2 minutes before you read

The problem: With all 228,146 rows in every step, one forward and backward pass takes about 126 ms, so training moves at under 8 updates a second. The net learns, just far too slowly to experiment with.

Where it fits: The previous card trained on 32 rows until it overfit them. This card keeps that exact loop and scales it to the whole dataset by changing what goes into each step, not the step itself.

  1. Why is a 32-row step about 1,000× cheaper and not 7,130× cheaper, when it uses 7,130× fewer rows?
  2. What does a 32-row gradient estimate, and why is it right on average but wrong on any single draw?
  3. Why do 32-row gradients agree with the full gradient at 0.826 early on but only 0.328 after 1,000 steps?
  4. Why can the printed minibatch loss go up while the model is getting better?
  5. What would change if you took the next 32 rows in order instead of 32 random ones?

In one breath: instead of running all 228,146 examples through the network before every update, pick 32 rows at random (a minibatch), compute the loss and gradient on just those, update, and pick a fresh 32. Each gradient is only an estimate of the true one, but a step costs about a thousandth as much, so you get to take a thousand times more steps.

Predict first: the network starts at a full-set loss of 19.5052. You take 1,000 steps, each on 32 random rows. That is 32,000 rows drawn, about 14% of the dataset. Where does the full-set loss end up?

2.6531. Most of the way down after seeing a seventh of the data once. Each 32-row gradient points roughly the right way, and early on "roughly" is plenty. Another 9,000 steps only take it to 2.5214 (measured on your M3, labs/minibatches.py).

The loop, with a fresh 32 rows each step

This is the overfitting loop from the previous card, with one new line at the top. torch.randint(0, X.shape[0], (32,)) returns 32 random whole numbers from 0 to 228,145: the row ids ix. X[ix] and Y[ix] pull out those rows. The batch size is how many rows go into one step (32 here), and one step is one forward pass, one backward pass and one update.

What you get from 32 rows is an estimate of the gradient: the average over a random sample instead of the average over everyone, like polling 32 voters instead of counting every ballot.

On average the left side equals the right side. Any single draw is off by some random amount: that is the "noisy" in the title.

How noisy is noisy?

To measure how well a minibatch gradient points, compare its direction with the full gradient's using cosine similarity: 1 means the same direction, 0 means unrelated. I drew 200 random minibatches of each size and averaged:

Computed (200 batches per size, seed 0, same seeded net as the lab). Spread = standard deviation of the minibatch loss around the full-set 2.5214. It shrinks like 1/√(batch size): 8× more rows (32 → 256) gives only √8 = 2.8× less spread (0.195 → 0.073).

Two things follow. Early on the loss slope is steep and every batch agrees (0.826), so 32 rows is plenty. Near the bottom the batches disagree (0.328): the steps start to jitter around the minimum instead of going down it, which is why the loss stalls near 2.52 at lr 0.1. The fixes are a smaller learning rate (the next card) or a bigger batch, which Karpathy mentions at 1:00:49.

When: pause the video at 0:41:25. Rebuild X, Y from all words, re-create the parameters with the seeded g (as on the hidden-and-output card), and change the training loop to this.

for i in range(10000):
    ix = torch.randint(0, X.shape[0], (32,), generator=g)  # 32 rows
    emb = C[X[ix]]                                # (32, 3, 2)
    h = torch.tanh(emb.view(-1, 6) @ W1 + b1)     # (32, 100)
    logits = h @ W2 + b2                          # (32, 27)
    loss = F.cross_entropy(logits, Y[ix])
    for p in parameters:
        p.grad = None
    loss.backward()
    for p in parameters:
        p.data += -0.1 * p.grad
emb = C[X]                                        # all rows
h = torch.tanh(emb.view(-1, 6) @ W1 + b1)
print(F.cross_entropy(h @ W2 + b2, Y).item())

Why it beats the alternatives

✗ Full batch every step

The exact gradient, at 126.0 ms a step. In the 1.2 s that minibatches need to reach 2.5214, it manages 10 steps and a loss of 10.7096.

✗ One row per step

Cheapest per step, but a single row's gradient barely agrees with the true one (0.216 at init, 0.032 later), and its loss swings by ± 1.168. Most of each step is noise.

✗ The next 32 rows in order

Rows are stored name by name, so 32 neighbours come from about five names. Each step would chase those names' letters, not the whole dataset's. Random ids make every batch a fair sample.

✓ 32 random rows per step

A gradient that points the right way (0.826 at init) for a thousandth of the cost, so 10,000 steps fit in about a second. Karpathy: better an "approximate gradient" and more steps (0:44:23).

Agreement and spread from the noise table above. "About five names" is computed: 228,146 rows / 32,033 names ≈ 7.1 rows per name, so 32 rows ≈ 4.5 names.

What minibatches do not do

The minibatch loss is not the model's loss. After 10,000 steps it ranges from 1.945 to 2.975 across 200 random batches while the true value is 2.5214. Report the loss on all rows (and, from the splits card on, on the dev set), computed with torch.no_grad() so no graph is built.

They are not free. The noise that makes steps cheap also stops the loss from settling: 5,000 → 10,000 steps moved it only from 2.5227 to 2.5214. And when the whole dataset is tiny, as with the 32 rows on the overfit card, just use it all: the full batch is already cheap and gives the exact gradient. 32 is a hyperparameter, not a law: bigger batches trade speed per step for a cleaner direction.

Understand and remember

  • Step cost grows with the rows per step → 32 rows cost about 1/1,000 of 228,146 → about 1,000 steps for the price of one → in the same ~1.2 s, 10,000 minibatch steps reach 2.5214 while 10 full-batch steps reach only 10.7096
  • Random rows → the minibatch gradient is an unbiased sample average of the per-row gradients → right on average, off by random noise on each draw → the noise shrinks only like 1/√(batch size)
  • Early the loss slope is steep and every row agrees → noise is small relative to the signal (cos 0.826) → near the bottom the true gradient is small and rows disagree (cos 0.328) → steps jitter around the minimum → the loss stalls near 2.52 at lr 0.1 until the learning rate drops or the batch grows
  • Each step's loss is measured on only 32 rows → it swings by about ± 0.2 around the true value → progress must be judged by a loss on all rows (later the dev set), never by the last minibatch loss
  • detail that matters Small steps are dominated by fixed per-step overhead, not arithmetic → the measured speedup is about 1,063×, not the 7,130× row ratio → a batch of 256 processes rows faster per row than a batch of 32, so bigger batches are cheaper than their row count suggests on this net

Reference only

  • torch.randint(low, high, size, generator=g) returns integers in [low, high)
  • sampling is with replacement: a row can appear twice in one batch or across batches
  • the lab's seed is 2147483647 and its lr is 0.1
  • PyTorch's DataLoader with a RandomSampler does the same job in makemore.py

Reveal
