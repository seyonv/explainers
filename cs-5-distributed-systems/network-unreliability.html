The network is unreliable

Also called fallacy #1 of distributed computing, the asynchronous packet network, or "partitions happen". The source guide's Networks page opens with it: in a shared-nothing system the network is the only channel between machines, and it guarantees nothing about delivery.

In one breath

When you send a request and hear nothing back, six different things could have gone wrong, and from where you sit they all look the same: silence. You can't tell whether the other side did the work, so every networked program needs a plan for silence, and that plan has to be tested.

Worked example: one resize call, six ways to go silent

The course's image-resize service: an API server sends a 256 KB image to a resize worker and waits. The source lists six things that can go wrong. The two grey dashed replies do arrive, but after the caller has stopped waiting.

timeout = 2d + r = 2 × 5 + 100 = 110 ms (d = max one-way delay, r = max processing) healthy = 2 + 100 + 2 = 104 ms ≤ 110 → reply queued = 400 + 100 = 500 ms work done, reply at 502 > 110 → timeout paused = 2 + 1,000 + 100 = 1,102 ms work done long after the caller gave up

r = 100 ms comes from the course's 10 conversions/s per core. The delays (d = 5 ms, 2 ms typical, 400 ms queue, 1 s pause, 300 ms late reply) are illustrative. The 2d + r rule is from the source's Delay section.

silent cases: 6 of 6 look identical ("timeout at 110 ms") the resize ran anyway: 4 of 6 (2, 4, 5, 6) → a blind retry resizes twice the resize never ran: 2 of 6 (1, 3) → giving up loses the request

This tally is our reading of the six cases, not a line from the source. It's why retries need to be idempotent.

The code

D, R = 5, 100          # max one-way delay, max processing (ms)
TIMEOUT = 2 * D + R    # the source's 2d + r -> 110 ms

# (case, request delay, worker pause, reply delay) in ms.
# None means it never arrives (lost packet, crashed worker).
CASES = [
    ("healthy",          2,    0,    2),
    ("request lost",     None, 0,    2),
    ("request queued",   400,  0,    2),
    ("node crashed",     2,    None, 2),
    ("node paused (GC)", 2,    1000, 2),
    ("response lost",    2,    0,    None),
    ("response delayed", 2,    0,    300),
]

def call(req, pause, reply):
    if req is None or pause is None:
        return "timeout", None             # the work never ran
    done = req + pause + R                 # the worker finishes here
    if reply is None or done + reply > TIMEOUT:
        return "timeout", done             # ran, but caller gave up
    return f"reply at {done + reply} ms", done

# healthy           reply at 104 ms  work ran: yes, at 102 ms
# request lost      timeout          work ran: no
# request queued    timeout          work ran: yes, at 500 ms
# node crashed      timeout          work ran: no
# node paused (GC)  timeout          work ran: yes, at 1102 ms
# response lost     timeout          work ran: yes, at 102 ms
# response delayed  timeout          work ran: yes, at 102 ms
# silent cases: 6; work ran anyway in 4

Why it beats the alternatives

✗ Assume the network works

Deutsch's fallacy #1. If network faults aren't handled and tested, the source warns the cluster can stop serving for good or delete data, as in the GitHub outage it quotes.

✗ Silence means "it failed", so retry

In 4 of the 6 cases the resize already ran or will run. A plain retry does it twice, and the usage records bill it twice.

✗ Silence means "it's dead", fast

A short timeout declares the paused worker (case 4) dead while it's alive. Its load moves elsewhere, and the source's Delay section warns this can cascade.

✓ Expect it, decide, test it

Choose a timeout, make retries safe to repeat, and decide what users see. Then break the network on purpose (Chaos Monkey) to check the system recovers.

Does every system have to survive partitions?

No. The source is explicit: handling a fault doesn't always mean tolerating it. If your network is normally reliable, showing users an error during a partition is a valid choice. What isn't optional is knowing how your software reacts and making sure it recovers afterwards.

Theory backs up the caution: FLP shows consensus can't be guaranteed in an asynchronous network if even one process can fail. With a network that guarantees timely delivery, FLP no longer holds, which is why real systems (ZooKeeper, Raft) lean on timeouts, betting that silence usually means a crash. A single machine with no network hop avoids all this, but gives up the redundancy that made shared-nothing worth it.
