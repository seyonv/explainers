Sizing a service: image resize

Also called capacity planning, fleet sizing or a back-of-the-envelope estimate. The source guide's running system: an image-resize service at 10K requests/s per region, p99 < 500 ms for images < 1 MB, 99.9% available. It sizes the fleet in four lines; this card redoes each line and adds the checks it skips.

Prime · 2 minutes before you read

The problem: "10K requests a second" doesn't tell you how many machines to buy. Size for the average and the queue in front of each machine grows until the p99 target is blown; size from the user count and you can be off by 1,000×. You need a chain of divisions plus a reason for the headroom.

Where it fits: The course's running example, sized. It uses cs-4's back-of-the-envelope estimation and Little's law, and every later card (architecture, backpressure, service discovery, sharding) reuses its 10K requests/s, 100 ms per image and 40 servers.

In one breath

Turn the requirement into a chain of divisions: requests per second ÷ work one core does per second = cores; cores ÷ cores per machine = machines; then leave room so the machines are never run flat out, because a queue in front of a fully busy machine grows without limit and blows the latency target.

The chain

servers= ⌈ λ×tcpubusy cores ccores/box × umaxtarget utilisation ⌉
λarrival rate, requests per second10,000 per region (given) tcpuCPU seconds per image = 1 ÷ (conversions/s per core)1/10 s = 100 ms (assumed at 256 KB) ccores in one machine32 (given) umaxbusiest you let a machine get0.8 = 20% headroom
servers = ceil(rps * cpu_seconds / (cores_per_box * max_util)) = ceil(10,000 * 0.1 / (32 * 0.8)) = ceil(39.06) = 40

λ × tcpu is Little's law: 10,000 arrivals/s each holding a core for 0.1 s means 1,000 cores busy at any instant.

Why the headroom is not optional

Same traffic, spread evenly over 32 or 40 machines of 32 cores each. Bars show the 99th-percentile time a request waits in the queue before a core picks it up; the dashed line is the whole 500 ms p99 budget.

per machine: λ = 10,000 / 32 = 312.5/s → ρ = 312.5 / (32 × 10) = 0.977 λ = 10,000 / 40 = 250/s → ρ = 250 / (32 × 10) = 0.781 p99 wait = ln(P(wait) / 0.01) / (c·μ − λ) (Erlang C, M/M/32 queue) 32 boxes: ln(0.849 / 0.01) / (320 − 312.5) = 4.44 / 7.5 = 0.592 s 40 boxes: ln(0.127 / 0.01) / (320 − 250) = 2.54 / 70 = 0.036 s

A model, not a measurement: it assumes random (Poisson) arrivals and exponential service times averaging 100 ms. The lesson is the shape: waits explode as utilisation nears 100%. At 32 machines the queue alone overshoots the budget before any image is resized.

In Python

import math

def size(rps, per_core, cores_per_box, headroom):
    cores = rps / per_core                    # 10,000 / 10
    boxes = math.ceil(cores / cores_per_box)  # 31.25 -> 32
    times = math.ceil(boxes * (1 + headroom)) # 38.4 -> 39
    idle = math.ceil(boxes / (1 - headroom))  # 40.0 -> 40
    return cores, boxes, times, idle

print(size(10_000, 10, 32, 0.20))
# → (1000.0, 32, 39, 40)

Why it beats the alternatives

✗ Size from the user count

100K users says nothing about load: they could send 10K requests/s or 10. Requests/s times work per request is what uses cores.

✗ Size for the average, no headroom

32 machines cover the mean exactly, at 97.7% busy. The model's p99 queue wait is 592 ms, over the whole 500 ms budget.

✗ One big machine

1,000 cores of work won't fit on one box, and one box down is 100% of traffic down, against a 43-minute monthly budget. The source: "a single-server monolith is impossible".

✓ The chain, then headroom

λ × tcpu ÷ cores ÷ umax: four checkable divisions. 40 machines at 78% busy leave room for surges, a lost machine and a rolling deploy.

Is 40 the answer?

Only as good as its weakest input, and the weakest is "10 conversions per second per core": the source assumes it. Measure it by resizing a sample of real images on the target machine and use the p99 CPU time, not the mean, since big images are what break the latency target. Traffic peaks also need a real number: 20% covers a surge of 1.25× the mean (1 ÷ 0.8), no more.

It's the wrong tool when load is bursty or unknown: there, autoscaling on queue depth or utilisation beats a fixed fleet, and a load test beats any queueing model. And the fleet is only the processing tier; the queue, auth and billing services in the source's Figure 1 are sized separately.

Understand and remember

  • Requests/s × CPU seconds per request → busy cores (Little's law: 10,000 × 0.1 s = 1,000) → ÷ cores per box → machines that cover the mean (32)
  • Utilisation near 100% → almost every arrival finds all cores busy (P(wait) 84.9% at 97.7%) → the spare capacity cμ − λ shrinks to 7.5/s → the p99 queue wait explodes (592 ms, over the whole 500 ms budget)
  • Cap utilisation at 80% → ÷ 0.8, not × 1.2 → 40 machines at 78.1% → spare capacity 70/s → p99 wait 36 ms, and room for a surge of 1.25×, a lost machine or a rolling deploy
  • Size from requests/s × work per request, never from users → the same 100K users could send 10K/s or 10/s → the user count is only a sanity check
  • detail that matters p99 wait = ln(P(wait)/0.01) / (cμ − λ) → the denominator is the spare capacity per machine → halving the spare capacity roughly doubles the tail wait, which is why the last few percent of utilisation cost the most

Reference only

  • the Erlang C formula itself and its O(c) evaluation
  • the ingress numbers (2.62 GB/s = 21.0 Gb/s; 0.52 Gb/s per machine)
  • downtime per target (43.2 min/month at 99.9%, 4.3 at 99.99%)

5 · Predict commit to an answer before revealing

Traffic grows 20% to 12,000 requests/s and nobody adds machines. With 40 machines, what is the utilisation, and roughly how does the p99 queue wait compare with today's 36 ms and the 500 ms budget? Commit, then check with p99_wait(40, rps=12000).

Reveal

Utilisation becomes 12,000 × 0.1 / 1,280 = 93.75%. The M/M/32 model gives P(wait) 63.0% and a p99 queue wait of about 207 ms: nearly 6× today's 36 ms, still under the 500 ms budget but using 41% of it before any resizing. The headroom was exactly what absorbed a 1.2× surge; one more machine failure would push it much further.
