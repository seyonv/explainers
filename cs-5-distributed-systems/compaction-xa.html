Compaction, deletion and XA

Also called log compaction and garbage collection; tombstones, purge and erasure; two-phase commit (2PC) and X/Open XA distributed transactions. The second half of the source guide's Limitations page: why append-only stores must clean up after themselves, why deleting for real is hard, and why XA transactions across different systems hurt in operation.

In one breath

An append-only store never overwrites, so an update or a delete is just one more record and the old bytes stay on disk until compaction rewrites the files. Two-phase commit makes several systems commit together by first asking each one "can you promise?", but a participant that has promised can't change its mind, so if the coordinator dies it waits, holding its locks.

The source's point: LSM trees, CouchDB's append-only B-tree and Datomic all get high write throughput and cheap snapshots from immutability, and all pay for it in extra disk and compaction work that is "a hard engineering problem" to tune. RethinkDB mitigates it with a "young blocks" subsystem that prioritizes recently updated blocks. And when a law such as the GDPR's right to erasure says the data must go, a tombstone is not enough: every compacted file, replica and backup has to be rewritten or destroyed.

The source's sentence "the data structures you query are used in Datomic" reads as a garbled "immutable data structures" (the wording of DDIA ch. 11, which it follows); our reading.

Part 2: two-phase commit, and the coordinator dies

An order service writes a row to a database and a message to a queue in one XA transaction (DDIA's standard example). The coordinator collects both YES votes, logs its COMMIT decision, then crashes before telling anyone.

Having voted YES, a participant may not abort (the coordinator might have decided COMMIT) and may not commit (it might have decided ABORT). Only the coordinator's log knows. A participant that hasn't voted yet can still time out and abort alone.

The client can be told "committed" once the decision is logged; the ACKs only let the coordinator forget the transaction.

The code

class Participant:
    def __init__(self, name):
        self.name, self.state = name, "working"

    def prepare(self):           # write YES to disk, keep locks
        self.state = "prepared"
        return "YES"

    def finish(self, decision):  # COMMIT or ABORT, release locks
        self.state = {"COMMIT": "committed",
                      "ABORT": "aborted"}[decision]
        return "ACK"

def two_phase_commit(parts, crash_after_votes=False):
    msgs = 0
    votes = []
    for p in parts:                      # phase 1
        msgs += 1                        # PREPARE ->
        votes.append(p.prepare())
        msgs += 1                        # <- YES / NO
    decision = "COMMIT" if all(v == "YES" for v in votes) \
        else "ABORT"                     # logged: commit point
    if crash_after_votes:
        return msgs, None                # coordinator is down
    for p in parts:                      # phase 2
        msgs += 1                        # COMMIT ->
        p.finish(decision)
        msgs += 1                        # <- ACK
    return msgs, decision
# n=2: 8 messages, COMMIT, ['committed', 'committed']
# crash after votes: 4 messages, decision None, ['prepared', 'prepared']

Verbatim from code/compaction-xa.py, output from demo_2pc() under python3 3.10. Messages grow O(n), but latency is 2 round trips whatever n is, because each phase is sent to all participants in parallel in a real system (this loop is sequential for clarity).

The source's four problems with XA

ProblemWhat goes wrong
Coordinator is a single point of failureIf it isn't replicated, the timeline above stalls every participant. Many implementations aren't highly available by default or have only rudimentary replication.
App servers become statefulThe coordinator usually runs inside the app server, and its log is now as important as the databases. You can't just kill and replace that server.
Lowest common denominatorXA has to work with every system, so it can't detect deadlocks that span two systems and doesn't work with serializable snapshot isolation.
Failure amplificationAny one participant down or slow aborts or blocks the whole transaction: 0.9993 above, and locks held on healthy systems.

Why a log plus idempotent consumers beats the alternatives

✗ XA across different systems

Atomic, but blocks while the coordinator is down (3,750× the normal lock hold above) and multiplies failures: 129.5 min/month down with n = 2 instead of 43.2.

✗ Dual writes, no coordination

Write the DB, then the queue. A crash between the two leaves them disagreeing forever, and two writers can apply in different orders on each system.

✗ Three-phase commit

Designed not to block, but it assumes bounded network delay and reliable failure detection, which real networks don't give (DDIA ch. 9).

✓ One log, derived views

Commit once, to one system's log; every other system consumes it and dedups by request id. A slow consumer lags instead of blocking the writer. The source's "alternative methods" (DDIA ch. 11–12).

So is 2PC always a mistake?

No. The source's complaints are about heterogeneous XA: different products, one lowest-common-denominator protocol. Transactions inside one distributed database, where every node runs the same software, can use 2PC far better; Spanner runs 2PC with each participant and the coordinator replicated by Paxos, so a crashed coordinator is replaced instead of waited for. Use XA only when you truly need atomic commit across systems you can't restructure, and keep n small.

Likewise, compaction isn't always the answer to immutability: a store that mostly adds data (little churn) can keep its whole history cheaply. Churn-heavy data and anything that may be subject to erasure needs a real purge path, including for backups (for example, per-user encryption keys you can destroy; a common practice, not from the source).
