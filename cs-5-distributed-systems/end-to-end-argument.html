The end-to-end argument

Also called end-to-end arguments in system design (Saltzer, Reed and Clark, 1984), "correctness belongs at the ends", or the end-to-end principle. The source guide uses it twice: careful file transfer needs an application checksum, and failure detection gets faster once you tell a crashed process apart from a partition.

In one breath

If only the two applications at the ends can tell whether a job was done right, they have to check it themselves, whatever the layers below promise. Checks lower down, like link CRCs, TCP retransmits and heartbeats, can't make the result correct. They only make the end check fail less often, so they're a performance choice.

Worked example: careful file transfer through 10 hops

This is the paper's "too-real example" from MIT: gateways checksummed every hop, yet one gateway swapped a byte pair while copying between buffers, about once per million bytes. Operating-system source files came through corrupted, and their owners fixed them by hand from old listings. Put an illustrative rate on it: each hop lets 1 byte in 109 through damaged in a way its own check can't see.

So the end check is needed for correctness, and making it pass is a performance problem. Two fixes: a better network, or a smaller unit to check and resend.

Low-level reliability buys performance, not correctness

Hash and resend per chunk instead of per file. Expected sends of a chunk = 1 / P(chunk clean) = eλ, so the extra bytes sent = eλ − 1.

Hand trace: the end-to-end acknowledgement over TCP

The source's C fix, rewritten in Python. sendall() and close() return once A's kernel has the bytes, so neither says whether B's app got them. A half-closes instead and waits for B's own answer.

StepProgram AProgram B
1s.sendall(data)returns when A's kernel has queued itdata →
2s.shutdown(SHUT_WR)sends FIN: "no more data from me"; A can still readFIN →
3recv() → bytes …, then b""b"" means A's FIN arrived after the last byte
4← digestsendall(sha256(all bytes))the app's own answer, after it has read everything
5← FINconn.close()
6recv() → 32 bytes, then b""read() returning 0 = B has closed
7reply == sha256(data) → Truenow A knows B's app has every byte, unchanged

SO_LINGER (the source's other option) only makes close() wait until B's kernel has ACKed the data or the linger time runs out. That's delivery to the host, not to the app.

In Python

def send_file(addr, data):
    s = socket.create_connection(addr)
    s.sendall(data)                   # in the kernel, not yet at B
    s.shutdown(socket.SHUT_WR)        # FIN: "no more data from me"
    reply = b""
    while chunk := s.recv(4000):      # 0 bytes = B closed too
        reply += chunk
    s.close()
    return reply == hashlib.sha256(data).digest()

def receiver(srv):
    conn, _ = srv.accept()
    h = hashlib.sha256()
    while chunk := conn.recv(4000):   # b"" = A sent FIN, all read
        h.update(chunk)
    conn.sendall(h.digest())          # the app's own answer
    conn.close()                      # our FIN back to A

# B's digest matches A's: True

Sent the 1 MB file over localhost TCP under python3 3.10. The full file adds the retry-per-chunk loop and the crash test below.

Why it beats the alternatives

✗ Trust TCP

TCP checksums and retransmits, but its promise stops at B's kernel. A bad disk, a buffering bug in the transfer program or a crash just after the ACK all get past it.

✗ Make every hop perfect

It costs bandwidth and delay on every flow, and the bytes still sit unprotected in memory between checks. That's exactly how the MIT gateway got through.

✗ close() or SO_LINGER and hope

close() can return with data still queued. SO_LINGER waits for B's host to ACK it, which says nothing about B's app.

✓ End-to-end check plus an app reply

Only the endpoints can see every fault on the path, whatever caused it. Lower layers are then tuned only to keep retries rare: 1 MB chunks cost 1% extra.

So should the lower layers stop trying?

No. The paper says low-level reliability is "justified only as performance enhancements", and the table shows how much performance it buys: at 10−9 per hop a 10 GB file never gets through whole, and at 10−11 it takes 2.72 tries. The advice is to buy the cheap reliability low down, then check the leftover error rate against an acceptable retry rate at the top.

The argument isn't always the right frame. VoIP doesn't want the ends to retry at all: a late packet is useless, and TCP's retransmits just add jitter (the source's own example). For failure detection it means using fast crash signals to cut MTTR and saving the timeout for the real partition. A signal is only a hint, though. It can be missing, and a TCP ACK doesn't mean the app acted, so success still needs a positive reply from the app itself.
