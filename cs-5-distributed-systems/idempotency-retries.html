Idempotency and retries

Also called safe retries, retry with exponential backoff and jitter, idempotency keys, or "at-least-once delivery plus dedup = effectively once". The source guide says timeouts and exponential backoff are essential and that the app should do its own retries, but never shows how; this card fills that in for the image-resize service.

Prime · 2 minutes before you read

The problem: A call times out, and you can't tell whether the request was lost or only the reply. Giving up loses work; retrying can do it twice (billed 80 for 40 conversions). And if every client retries at once, and every layer retries too, a brief blip becomes a flood of 64 attempts per user action on a server that was already struggling.

Where it fits: The course's closing card ties together the unreliable-network card's six silent cases, the end-to-end argument (the client owns the id) and the money-transfer card's dedup, and turns the backpressure card's "back off" into a schedule.

In one breath

When a call times out you can't tell whether the request was lost or only the reply was, so the only safe move is to try again, and that is only safe if doing it twice has the same effect as doing it once. Make the operation idempotent (often with a client-chosen key the server remembers), then retry with waits that grow exponentially and are randomised, and retry at one layer only.

Worked example: the reply to a billing write is lost

The image-resize service reports usage for billing. POST /usage adds 40 conversions to a customer's bill. The server applies it, but the reply is dropped on the way back (one of the source's six network failures). The client times out and retries.

Why the randomness matters

If a blip fails 100 clients at the same moment and they all back off by exactly the ceiling, they all come back at the same moment too, and the server gets the same spike again, one ceiling later. Full jitter spreads each wave across its window.

100 clients, first retry, window 100 ms, counted in 10 ms slots: no jitter: all 100 in one slot → peak 100 full jitter: mean 100 / 10 = 10 per slot → peak 16 (seed 1) fourth retry, window 800 ms (80 slots): mean 1.25 → peak 6

Retry at one layer: amplification

If every layer between the user and the database retries, attempts multiply. With r retries (r + 1 attempts) at each of L layers, one user action can reach the bottom layer (r + 1)L times, exactly when it is already failing.

Retries per layer1 layer2 layers3 layers4 layers
1 retry (2 attempts)24816
2 retries (3 attempts)392781
3 retries (4 attempts)41664256

Google's SRE book gives the 64: JavaScript, frontend and backend each issuing 3 retries means 43 = 64 attempts on an overloaded database. Its fixes: retry only at the layer just above the one rejecting, cap attempts per request at 3, and keep retries under 10% of a client's requests. "3 layers × 3" is 27 only if 3 counts attempts, not retries.

Which requests are safe to retry

TermWhat it meansExample AExample B
SafeOnly reads: asks for no change to server state. GET, HEAD, OPTIONS, TRACEGET /images/42 twice returns the image twice A read that logsstill "safe": the client didn't ask for the log line
IdempotentThe intended effect of N copies equals one. RFC 9110 lists PUT, DELETE and every safe method. PUT /quota/acme = 500twice: quota is still 500 DELETE /images/42second call may say 404, but the state is the same: gone
Not idempotentEach copy does it again. Needs a key before it can be retried. POST /usage +40twice without a key: billed 80 PATCH "count += 1"RFC 5789: PATCH isn't necessarily idempotent
Idempotency keyA random ID the client picks once per logical operation and sends on every retry. Idempotency-Key: <UUID4>Stripe: any POST, up to 255 characters Request ID in a messagea consumer skips IDs it already applied (see exactly-once transfer)

RFC 9110 says idempotent requests "can be automatically retried by a client following an underlying connection failure"; that is why HTTP clients retry GET and PUT on their own but not POST.

In Python

import random

def full_jitter(n, rng, base=0.100, cap=10.0):
    return rng.uniform(0, min(cap, base * 2 ** n))

class Server:
    def __init__(self):
        self.balance, self.keys = 0, {}   # key -> (request, reply)

    def charge(self, amount, key=None):
        req = ("charge", amount)
        if key in self.keys:
            seen, reply = self.keys[key]
            if seen != req:               # same key, other request
                return ("422 key reused", None)
            return reply                  # replay, no new charge
        self.balance += amount            # the side effect
        reply = ("201 charged", self.balance)
        if key is not None:
            self.keys[key] = (req, reply)
        return reply

# call(): first reply is lost, client sleeps full_jitter(0),
# then retries with the SAME key (full version in code/)
# → no key  : reply ('201 charged', 80), slept [24] ms, balance 80
#   with key: reply ('201 charged', 40), slept [24] ms, balance 40
#   same key, amount 50: 422 key reused

Time O(1) · Space O(keys kept). Each request costs one hash lookup; the table grows by one row per keyed request until rows expire. At the image service's 10K requests/s that's 10,000 × 86,400 = 864 million rows a day per region if every request carried a key.

In a real service the check and the insert must be atomic (a unique constraint or a conditional write), and the side effect and the key row should commit in one transaction. Otherwise two concurrent copies can both miss the table and both apply. Our note, not the source's.

Why it beats the alternatives

✗ Never retry

Every dropped packet and every GC pause becomes a user-facing error, even though most such failures are brief (the source: loss is usually congestion, not a cut cable).

✗ Retry at once, no key

Duplicates non-idempotent work (billed 80 for 40) and hits a struggling server again with no pause, turning a blip into overload.

✗ Fixed backoff at every layer

No jitter: all 100 clients return in the same 10 ms slot. Retries at 3 layers: up to 64 attempts on the database per user action.

✓ Key + jittered backoff, one layer

The key makes copies harmless (billed 40). Full jitter cut the peak from 100 to 16. Retrying at one layer with a budget keeps it at 4 attempts, not 64.

Should every failure be retried?

No. Retry only failures that might go away: timeouts, dropped connections, 503. Don't retry a 400 or a 422; the same request will fail the same way. If the server says it's overloaded (429 or 503, maybe with Retry-After), wait at least that long, or give up. Google's SRE book uses an "overloaded; don't retry" error so upper layers stop. And don't retry where a late answer is useless: the source's VoIP example drops lost packets instead of resending them.

Idempotency keys make retries safe for a while, not forever. Once a key is pruned (Stripe: after at least 24 hours), a late retry runs as a new request. And a key only dedupes one hop: the service behind it needs its own keys or natural idempotency (a PUT of a final value, a unique request ID in a ledger). That's the end-to-end argument again.

Understand and remember

  • A timeout can't tell a lost request from a lost reply → the only safe move is to try again → that is safe only if two copies have the effect of one → make the operation idempotent, naturally (PUT a final value) or with a key
  • The client picks a key once per logical operation and resends it on every retry → the server stores (key → request, reply) → a repeat replays the stored reply without a new side effect (billed 40, not 80) → a mismatched request with the same key is refused
  • Every client that failed together would retry together → multiply the wait each time (base × 2n, capped) and draw uniformly below it (full jitter) → retries spread across the window (peak 100 → 16 in one 10 ms slot)
  • Each layer retrying r times multiplies attempts → (r + 1)L: 43 = 64 on an overloaded database → retry only at the layer just above the one failing, with a budget
  • detail that matters The key check and the side effect must commit atomically (unique constraint or conditional write, same transaction) → otherwise two concurrent copies both miss the table and both apply → hence the "in progress" 409 row

5 · Predict commit to an answer before revealing

A team uses base 50 ms and cap 2 s with full jitter. What are the ceilings for retries 1 to 8, at which retry does the cap first bite, and what is the expected total wait over the first 6 retries? Commit first.

Reveal

Ceilings: 50, 100, 200, 400, 800, 1,600, 2,000, 2,000 ms. The cap bites at retry 7, where 50 × 26 = 3,200 ms is cut to 2,000. Expected total over 6 retries = (26 − 1) × 25 ms = 1,575 ms, exactly half the card's 3,150 ms, because every ceiling is halved. Over all 8 it's 3,575 ms.

Hint

(2 + 1)2 = 9 vs 2 + 1 = 3. The race needs the check and the insert to be separable; threading.Lock around "check + mark in progress" is enough in one process, a unique constraint across processes.
