Invariant confluence

Also written I-confluence; the test from Bailis et al.'s coordination-avoidance paper. It asks whether two replicas that each made a valid change on their own can always be merged into a valid state. The source guide uses it to decide which rules (unique usernames, non-negative balances, room bookings) can be enforced without replicas talking to each other.

Prime · 2 minutes before you read

The problem: Coordinating every write costs a round trip and refuses during partitions; coordinating none breaks rules like unique ids and non-negative balances. You need a test that says, rule by rule, whether replicas can commit on their own and still be valid after the merge.

Where it fits: Builds on the eventual-consistency card's broken merge and its four target properties. This card gives the exact test (invariant confluence) and Theorem 1, which says the test is also the limit. The money-transfer card then designs around the rules that fail it.

In one breath

Let every replica commit transactions locally, checking the rule only against what it can see, and later merge the replicas by taking the union of their data. If every such merge of two locally valid states is still valid, the rule never needs coordination. If even one merge can break it, some transactions must coordinate. Theorem 1 says there is no third option.

The rule

A set of transactions T is I-confluent if this holds for all pairs Di, Dj reachable from a common ancestor. One passing merge proves nothing; one failing merge settles it.

The code

def merge(a, b):
    return a | b                      # set union of versions

def check(inv, ds, t1, t2):
    di, dj = ds | {t1}, ds | {t2}     # each replica commits locally
    assert inv(ds) and inv(di) and inv(dj), "must be valid locally"
    return inv(merge(di, dj)), merge(di, dj)

def non_negative(d):                 # ("op", op_id, +/- amount)
    return sum(r[2] for r in d if r[0] == "op") >= 0

ds = frozenset({("op", "d0", 100)})
w1, w2 = ("op", "w1", -60), ("op", "w2", -70)
print(check(non_negative, ds, w1, w2)[0])

Theorem 1: why the test is exact

A globally I-valid system can run T with coordination-freedom, transactional availability and convergence if and only if T is I-confluent.

If: by construction. Each replica checks the invariant against its own state, commits, and merges later; confluence guarantees the merge is valid. Only if: a partitioning argument. Cut the network, let each side commit its locally valid transaction (availability forces it to answer); after the heal, convergence forces the merge, and a non-confluent pair makes that merge invalid. One of the four properties has to give.

The source writes the partitioning proof under "←" and calls it the forwards direction; in the paper it proves the "only if" half (coordination-free ⇒ confluent). The source's footnote on "these sequences" points to [^01] where it means [^08] (Din and Djm).

Why it beats the alternatives

✗ Coordinate everything

Serializable transactions are always correct but pay at least one round trip per coordinated write: 83 ms East US → West Europe, and nothing commits during a partition.

✗ Coordinate nothing

Plain eventual consistency converges, but to states like id 5 twice, a balance of −30 or an order for a deleted user.

✗ Just check locally

Every replica above did check the invariant, and each commit passed. The failure only appears at merge time, after both users were told "ok".

✓Check I-confluence per rule

Coordinate only the (invariant, operation) pairs that fail: withdrawals, chosen ids, deletes. Everything else runs locally. The paper's prototype got a 25× gain over prior TPC-C New-Order results on 200 servers.

Does passing the test make the system correct?

Only for the invariants you wrote down. The analysis guards exactly the declared rules; a missing or wrong invariant gives a "confluent" system that is still wrong for the app (the paper's section 4.3). The answer also depends on the merge: the table assumes set union, and a last-writer-wins merge changes it.

It's not the tool when the rule is inherently global, like "take the last seat" or "withdraw only what's there": those fail the test, so use consensus or a single owner for that item. A common workaround (general practice, not from the source) is to reshape the rule so it passes: have replicas pick ids from their own prefix, or split a budget so each replica can spend only its share.

Understand and remember

  • Replicas commit locally, checking the rule on their own state → later merge by union → if every merge of two locally valid states is valid, the rule needs no coordination → one failing pair (100 − 60 − 70 = −30) is enough to say No
  • Operations that only add (deposits, FK inserts, system-chosen ids) → union never removes a row or double-spends a quantity → merges stay valid → I-confluent
  • Operations that consume or claim something shared (withdrawals, user-chosen ids, deletes, overlapping bookings) → two replicas can each take the same thing → the merge over-commits → not I-confluent → these pairs must coordinate
  • Theorem 1: cut the network, availability forces each side to commit, convergence forces the merge → a non-confluent pair yields an invalid merged state → you can't have validity, availability, convergence and coordination-freedom together for it
  • detail that matters The verdict depends on the merge → with set union deletes need tombstones and cascades to stay safe → with last-writer-wins, two withdrawals can collapse into one (a lost update), so the whole table changes

5 · Predict commit to an answer before revealing

A prepaid plan caps an account at 1,000 credits: "balance ≤ 1,000", with deposits only. Is that I-confluent? Try it from 900 with two replicas depositing 80 and 70. Commit first.

Reveal

No. Each replica is valid locally: 980 and 970. The merge applies both deposits: 900 + 80 + 70 = 1,050 > 1,000. Deposits were safe for "≥ 0" because they move away from that bound; here they move toward it. Confluence belongs to the (invariant, operation) pair, never to the operation alone.
