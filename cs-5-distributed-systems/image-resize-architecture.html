Choosing consistency per subsystem

Also called per-component CAP choices, or splitting the management plane from the data plane. The source guide's image-resize service (10K RPS per region, 99.9% availability) breaks into five services, and each one picks consistency or availability on its own.

Prime · 2 minutes before you read

The problem: "Is the image service CP or AP?" has no single answer. A job queue that loses or reorders work is broken; an auth check that is a few seconds stale is fine; a usage counter can wait hours. Forcing one choice on all of them either makes every request depend on the slowest part, or lets the queue split-brain.

Where it fits: Applies the partial-failure and CAP card's per-partition choice to the running example's five subsystems, using the sizing card's 10K requests/s and 40 workers. The Paxos failover it relies on is taught later in the Raft card.

In one breath

A system doesn't pick one side of CAP; each part of it does. Ask what each subsystem's readers can live with. A job queue can't lose or reorder work, so it favours consistency and pays with a failover election. An auth check runs on every request and can be a few seconds stale, so it favours availability.

In Python

from collections import defaultdict
from math import comb

def k_of_n(a, k, n):   # P(at least k of n up), independent
    return sum(comb(n, i) * a**i * (1 - a)**(n - i)
               for i in range(k, n + 1))

def local_aggregate(requests):  # on ONE API server, per window
    agg = defaultdict(lambda: [0, 0.0, 0])
    for cust, cpu_ms, nbytes in requests:
        row = agg[cust]
        row[0] += 1
        row[1] += cpu_ms
        row[2] += nbytes
    return agg                   # shipped as ONE batch write

def edge_copy_time(t, ttl, down):  # last successful refresh
    return max(s for s in range(0, t + 1, ttl)
               if not down[0] <= s < down[1])

def edge_auth(created, t, ttl=5, down=(10, 30)):
    return 200 if edge_copy_time(t, ttl, down) >= created else 401

# each 99.5% up -> 2 of 3 up 99.99253% (indep.)
# usage, 10 s: 100,000 requests -> 3 batch writes

Why it beats the alternatives

✗ Consistent everywhere

Every auth check asks the source of truth: 864M round trips a day, and when the auth data plane is down, every resize fails with it.

✗ Available everywhere

A queue that accepts jobs on both sides of a partition ends up with two leaders: jobs duplicated or lost, FIFO order gone, customers maybe billed twice.

✗ One store for all of it

Usage writes at 10K/s and rare account changes share one database, so the noisiest, least urgent data sets its load and its failure modes.

✓ Choose per subsystem

Each part gets the guarantee its readers need: the queue refuses rather than diverge, auth tolerates a few stale seconds, usage waits for the batch job.

Is availability at the edge always safe?

No. The same staleness that makes a new user wait a few seconds lets a revoked key keep working until the next refresh. When access must end at once, push invalidations to the edge or check the data plane for sensitive calls (our inference; the source only discusses new users). And the 2-of-3 math holds only if servers fail independently.

Nor does every queue favour consistency: Amazon SQS standard queues give at-least-once delivery with best-effort ordering, and only its FIFO queues promise order. This service needs FIFO, which is what pushes it to C. At small scale none of this is needed: the source reaches for a distributed stack only because 1K cores won't fit on one machine.

Understand and remember

  • Ask what each subsystem's readers can live with → a queue can't lose or reorder jobs → favour C: refuse while a majority elects a new leader (j2 refused ~2 s) → no job lost, FIFO kept
  • Auth runs on every request (864M a day) but accounts change rarely → cache identity at the edge and favour A → requests keep working through an auth-plane outage → the price is staleness: a new user waits (18 s in the trace), and a revoked key works until the next refresh
  • Availabilities in series multiply → a 99.99% front door leaves 0.999 / 0.9999 = 99.91%, 38.9 min a month, for everything behind it → the front door needs more nines than the SLA
  • Usage is write-heavy and read hours later → aggregate locally, batch to an eventually consistent store → 100,000 requests become 3 writes per 10 s per window → billing tolerates the delay
  • detail that matters ⌈10K / 5K⌉ + 1 = 3 API servers → losing one still leaves 2 × 5K = 10K → 2-of-3 availability 99.9925% at 99.5% each, if they fail independently, which correlated failures break

5 · Predict commit to an answer before revealing

The team adds a sixth subsystem: an image metadata store that clients read after each resize to get the output URL and dimensions. Should it favour C or A, and what failure would each choice produce? Commit first.

Reveal

Read-your-write matters: the client just caused the resize and immediately asks for its output. Favouring A with plain eventual consistency means a client can get "not found" for an image it just made. So favour C for the write-then-read path (or route the read to the replica that took the write, a session guarantee), and allow A for other readers such as galleries, where a few seconds' lag is fine. The per-subsystem rule even splits one subsystem by reader.
