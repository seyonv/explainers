Choosing consistency per subsystem

Also called per-component CAP choices, or splitting the management plane from the data plane. The source guide's image-resize service (10K RPS per region, 99.9% availability) breaks into five services, and each one picks consistency or availability on its own.

In one breath

A system doesn't pick one side of CAP; each part of it does. Ask what each subsystem's readers can live with. A job queue can't lose or reorder work, so it favours consistency and pays with a failover election. An auth check runs on every request and can be a few seconds stale, so it favours availability.

In Python

from collections import defaultdict
from math import comb

def k_of_n(a, k, n):   # P(at least k of n up), independent
    return sum(comb(n, i) * a**i * (1 - a)**(n - i)
               for i in range(k, n + 1))

def local_aggregate(requests):  # on ONE API server, per window
    agg = defaultdict(lambda: [0, 0.0, 0])
    for cust, cpu_ms, nbytes in requests:
        row = agg[cust]
        row[0] += 1
        row[1] += cpu_ms
        row[2] += nbytes
    return agg                   # shipped as ONE batch write

def edge_copy_time(t, ttl, down):  # last successful refresh
    return max(s for s in range(0, t + 1, ttl)
               if not down[0] <= s < down[1])

def edge_auth(created, t, ttl=5, down=(10, 30)):
    return 200 if edge_copy_time(t, ttl, down) >= created else 401

Why it beats the alternatives

✗ Consistent everywhere

Every auth check asks the source of truth: 864M round trips a day, and when the auth data plane is down, every resize fails with it.

✗ Available everywhere

A queue that accepts jobs on both sides of a partition ends up with two leaders: jobs duplicated or lost, FIFO order gone, customers maybe billed twice.

✗ One store for all of it

Usage writes at 10K/s and rare account changes share one database, so the noisiest, least urgent data sets its load and its failure modes.

✓ Choose per subsystem

Each part gets the guarantee its readers need: the queue refuses rather than diverge, auth tolerates a few stale seconds, usage waits for the batch job.

Is availability at the edge always safe?

No. The same staleness that makes a new user wait a few seconds lets a revoked key keep working until the next refresh. When access must end at once, push invalidations to the edge or check the data plane for sensitive calls (our inference; the source only discusses new users). And the 2-of-3 math holds only if servers fail independently.

Nor does every queue favour consistency: Amazon SQS standard queues give at-least-once delivery with best-effort ordering, and only its FIFO queues promise order. This service needs FIFO, which is what pushes it to C. At small scale none of this is needed: the source reaches for a distributed stack only because 1K cores won't fit on one machine.
