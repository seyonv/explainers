The path of a request

Also called "what happens when you type a URL": name lookup, routing, filtering and load balancing, in that order. The source guide's Routers and Firewalls headings are empty, and its DNS and Load Balancers sections are really about service discovery and messaging, so this card is supplemented, with real timings from curl and dig.

Prime · 2 minutes before you read

The problem: Between a client typing a URL and your resize code running, four systems decide where the request goes: a resolver, routers, a firewall and a load balancer. Each can send it to the wrong place, cache a stale answer or add round trips. Debugging latency or a misrouted request means knowing what each one decides and on what information.

Where it fits: Builds on the delay card's round trips and TCP windows: a fresh connection pays several RTTs before any work. The next card, service discovery, replaces DNS for the inside of a data centre; the load-balancing choices here come back in consistent hashing.

Builds on: Delay, timeouts and congestion control · Sizing a service: image resize

You'll meet: DNS: walk the tree once, cache for the TTL longest-prefix match (and BGP between networks) stateless vs stateful firewall L4 vs L7 load balancing: round robin, least outstanding, hash fresh vs reused connection: 286.6 ms vs 83.6 ms

By the end: Trace one request through name lookup, routing, filtering and load balancing, say what each step decides and what it caches, and explain why reusing connections and picking by load matter.

In one breath

Before your request reaches a server, a resolver turns the name into an address (and caches it for the record's TTL), routers forward each packet toward the most specific matching prefix, a firewall decides whether the packet may pass, and a load balancer picks one of many identical servers. Opening a fresh connection costs round trips before any work happens, which is why real clients reuse connections.

Stateless rules: r1 allow to port 443 · r2 allow from port 443 · r3 deny. A stateless filter can't tell a reply from a forgery, so letting replies in (r2) opens a hole for anything sent from port 443. The stateful one keeps a table of connections and admits only packets that belong to one. Illustrative addresses.

Round robin blindly sends huge.jpg to s1, still busy with big.jpg, so it waits 700 ms. Least outstanding looks at the queues. Hashing (rendezvous here) always sends a.jpg to s3 and b.jpg to s1, which is what lets a server cache its images, but it ignores load, so a.jpg queues behind big.jpg.

The code

import hashlib
import ipaddress as ip

def next_hop(dst):                  # ROUTES: [(prefix, hop)]
    a = ip.ip_address(dst)
    hits = [(ip.ip_network(p), h) for p, h in ROUTES
            if a in ip.ip_network(p)]
    net, hop = max(hits, key=lambda t: t[0].prefixlen)
    return str(net), hop

def stateful(pkt, conns):          # pkt = (src, sport, dst, dport)
    src, sport, dst, dport = pkt
    if (dst, dport, src, sport) in conns:   # a reply we expect
        return "allow tracked"
    if dst == SERVER and dport == 443:
        conns.add(pkt)                # remember the new connection
        return "allow r1"
    return "deny"

def least_outstanding(i, key, busy):
    return min(SERVERS, key=lambda s: busy[s])

def rendezvous(i, key, busy):     # same key, same server
    h = lambda s: hashlib.sha256(f"{s}|{key}".encode()).digest()
    return max(SERVERS, key=h)

Why a load balancer behind one name beats the alternatives

✗ Hard-code server IPs

Every client must be updated when one of the 40 servers is replaced, and no one routes around a dead one.

✗ DNS round robin alone

Return all 40 IPs and let clients pick. Answers are cached for the TTL, and, as the source says, DNS tells you what could be at an address, not what is up.

✗ One bigger server

No failover, and the source's own sizing needs about 1K cores at 10K requests/s: no single box has that.

✓ DNS name → load balancer

DNS changes rarely; the LB health-checks servers, drops dead ones at once, and can pick by load (1000 ms worst vs 1700 ms above).

Does every request take this whole path?

No. Most requests skip most of the setup: the OS caches DNS (3.2 ms above instead of 118–238 ms), and a reused connection skips the TCP and TLS round trips, 83.6 ms instead of 286.6 ms. HTTP/3 (QUIC) merges the transport and TLS handshakes into one round trip. A CDN answers cacheable responses at the edge, so the request never reaches your servers.

Inside a data centre, services often skip the central load balancer: the client asks a registry (ZooKeeper, etcd, Consul, as in the source) for the live servers and balances itself. That saves a hop but puts the balancing logic in every client. And hashing isn't always better than least outstanding: use it when cache locality matters more than an even queue.

Understand and remember

  • A fresh HTTPS connection → TCP handshake + TLS handshake before the request (≈ 1 RTT each) → plus TCP slow start (10 segments, doubling) for the body → 286.6 ms vs 83.6 ms reused → clients reuse connections
  • DNS answers are cached for the TTL → one walk of the tree serves every client of a resolver until it expires → a changed address reaches clients only after the TTL → DNS says what could be at an address, not what is up
  • Routers forward to the most specific matching prefix → a more specific announcement wins everywhere → BGP hijacks work by being more specific, and so does the fix
  • A load balancer picks among identical servers → round robin ignores queues (huge.jpg waits 700 ms behind big.jpg) → least outstanding looks at load (worst 1,000 ms) → hashing keeps a key on one server for cache locality but ignores load
  • detail that matters Slow start: a new connection's window starts at 10 segments and doubles each RTT → 275 KB (189 segments) needs 4 extra RTTs → ≈ 157 ms, close to the 160.4 ms transfer measured → a warmed connection skips this

5 · Predict commit to an answer before revealing

Add a fourth route, 203.0.113.192/26 → canary pool. Where do packets to 203.0.113.200 and 203.0.113.130 now go? Commit first.

Reveal

A /26 fixes the first 26 bits: it covers .192–.255. So 203.0.113.200 matches /0, /24, /25 and /26; the longest, /26, wins → canary pool. 203.0.113.130 is in .128–.255 (/25) but not .192–.255, so /25 still wins → LB pool. One more specific route silently steals traffic from a broader one, which is exactly how the YouTube hijack worked.
