Why independent-failure math lies

Also called correlated failure, common-cause failure, or "PN is hogwash". The source guide opens its distributed-systems page with it: replication math assumes replicas fail independently, and shared power, the same bug, one poisonous client or one bad config break that assumption.

Hey I just met you / The network's laggy / But here's my data / So store it maybe
— Kyle Kingsbury, Carly Rae Jepsen and the Perils of Network Partitions (2013), quoted by the source

In one breath

If each replica fails on its own with chance p, all N fail together with chance pN, so it looks as if adding replicas buys any reliability you want. But anything the replicas share (a power feed, a code version, a config push) can take them all down at once, and that shared chance c doesn't shrink as N grows. It sets a floor, and in practice the floor is the whole story.

The rule, with and without a shared cause

P(all N down) = cshared event + (1−c)pNN independent failures ≥ c
pchance one replica fails on its own in some window0.01 (illustrative) Nnumber of replicas; survives N − 1 failures1 to 5 cchance of one event that kills every replica at once0.01 (illustrative) Rthe loss rate you're aiming for; the source's claim is "pick N with pN < R"10−9
p_all_down = c + (1 - c) * p**N # c = 0 gives the textbook p**N

Filled in, N = 3: independent 0.01³ = 10⁻⁶; with c = 0.01: 0.01 + 0.99 × 10⁻⁶ = 0.01000099, about 10,000× worse. The shared event is 0.01 / 0.01000099 = 99.99% of the risk.

The source's third case: "one client sends corrupt requests; it's able to sequentially bring down all the servers." Failover is what spreads it, because the client (or load balancer) retries the same request on the next healthy replica.

In Python

import numpy as np

def p_all_down(p, n, c=0.0):
    """Chance all n replicas are down: shared event, or n own ones."""
    return c + (1 - c) * p**n

def simulate(p, n, c, trials=10**6, seed=0):
    rng = np.random.default_rng(seed)
    shared = rng.random(trials) < c              # one event, all die
    own = (rng.random((trials, n)) < p).all(axis=1)
    return int((shared | own).sum())

for n in range(1, 6):
    a, b = p_all_down(0.01, n), p_all_down(0.01, n, c=0.01)
    print(n, f"{a:.0e}", f"{b:.8f}")
print(simulate(0.01, 3, 0.0), simulate(0.01, 3, 0.01))
# → 1 1e-02 0.01990000
#   2 1e-04 0.01009900
#   3 1e-06 0.01000099
#   4 1e-08 0.01000001
#   5 1e-10 0.01000000
#   0 9996

Real output of this snippet under python3 3.10.20, numpy 2.2.6; the full file adds the R = 10⁻⁹ check and the poison trace. Time O(trials × n) · Space O(trials × n) for the simulation: one random draw per replica per window; the closed form is O(1).

Why it beats the alternatives

✗ Add more replicas

Each one multiplies only the independent term by p. With c = 1%, going from 3 to 5 replicas moves P(all down) from 0.01000099 to 0.01000000: nothing.

✗ Trust the datasheet

"Replicated 3×, so 10⁻⁶" is a theoretical number. It says nothing about bugs, monitoring or operations, which is where the shared events come from.

✗ Buy better hardware

Lowers p, which the floor already ignores. Identical, better machines still share the bug, the input and the config.

✓ Attack c, measure empirically

Shrink what replicas share: stage rollouts (a canary to 1 of 40 servers risks 1/40 = 2.5% of the fleet, not 100%), separate power and zones. Then trust only "continuous hours of successful production operations".

So is replication pointless?

No. It is necessary, just not sufficient: it removes the independent term (0.0199 → 0.01000099 at N = 3 above) and nothing else. In this model, past two or three replicas the next dollar is better spent on what they share: staged deploys, input validation, diverse failure domains, and checking invariants ("are all messages sent actually received?", as the source puts it). The independence assumption is closer to true when replicas really differ (other zone, other power, changes rolled out one at a time), and the PN math is fine for choosing N once c is small. It never tells you c.

c is hard to estimate from first principles, which is why the source says to ask any storage vendor for the observed real-life distribution of MTTF (mean time to failure) and MTTR (mean time to repair), not a single average. A file system takes about a decade to mature, so a young system's c is likely its biggest number (our inference, not the source's).

The source's PN passage, "hogwash" and "I call this empirical reliability" paraphrase Jay Kreps (2012) without credit; the "I" is Kreps. The formula c + (1 − c)pN is this card's model of a shared event, not the source's.
