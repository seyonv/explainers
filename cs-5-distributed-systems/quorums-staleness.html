Quorums and quantifying 'eventual'

Also called partial or strict quorums, n/w/r tuning, or probabilistically bounded staleness (PBS). The source guide's Limitations page: monitor replication lag, overlap the write and read sets (its Figure 1: n = 5, w = 3, r = 3 with two replicas down), the ways quorums still go stale, and the limits of the WARS staleness model.

Prime · 2 minutes before you read

The problem: A Dynamo-style store calls a write done after w of n replicas ack and a read done after r answer. Pick w and r too small and reads can miss the latest write; too large and every request waits on slow replicas. "Eventually consistent" gives no number to choose with: how often is a read stale, and for how long?

Where it fits: Builds on the eventual-consistency card (replicas accept writes alone) and the service-discovery card's majority quorums. This card generalises the overlap to any w and r, and turns "eventual" into a probability. Raft, next, uses the w = r = majority case with a leader.

In one breath

A Dynamo-style store sends each write to all n replicas but calls it done after w acks, and a read asks all n but returns after r answers, picking the newest version. If w + r > n, every read set shares at least one replica with the last write set, so the read can see it. If not, the read can miss it, and "eventually consistent" becomes a number you can compute: how often, and for how long.

Worked example 1: why w + r > n works

n = 5, w = 3, r = 3: w + r = 6 > 5 any write set and read set share ≥ 6 − 5 = 1 replica tolerates n − w = 2 down for writes, n − r = 2 for reads

Pigeonhole: 3 + 3 = 6 picks among 5 replicas must land on some replica twice. The left panel is the source's Figure 1; the right is our added contrast case.

Worked example 2: n = 3, w = 1, r = 1, how stale?

Now drop to the fastest settings: a write returns after one ack, a read after one answer. At the moment of the ack the new value is on k replicas (at least 1, more as it spreads). If the read's r replicas are a random pick, it's stale only when every one of them is among the n − k that don't have it yet. That's a hypergeometric count:

Worked example 3: stale for how long? (WARS)

The table above freezes time at the ack. In reality the write keeps spreading while the read travels. Bailis et al.'s WARS model draws four latencies per replica: Write arrives, Ack returns, Read request arrives, reSponse returns. A replica answers stale if the read reaches it before the write does. At t = 0, w = 1, r = 1 is stale 1 − 0.514 = 0.486 of the time, below the 2/3 bound, because more replicas get the write while the ack and the read are in flight. The paper notes its closed forms are conservative for this reason.

In Python

from fractions import Fraction
from math import comb

def p_stale(n, k, r):
    """Read r of n replicas at random; k have the new value."""
    return Fraction(comb(n - k, r), comb(n, r))

def wars_trial(n, w, r, ts, rng):
    """One write then one read (WARS). True per t if read is fresh."""
    W = [rng.expovariate(1 / 20) for _ in range(n)]  # write lands
    A = [rng.expovariate(1 / 5) for _ in range(n)]   # ack returns
    R = [rng.expovariate(1 / 5) for _ in range(n)]   # read request
    S = [rng.expovariate(1 / 5) for _ in range(n)]   # read response
    commit = sorted(W[i] + A[i] for i in range(n))[w - 1]
    first = sorted(range(n), key=lambda i: R[i] + S[i])[:r]
    return [any(W[i] <= commit + t + R[i] for i in first)
            for t in ts]

print(p_stale(3, 1, 1), p_stale(5, 3, 3), p_stale(5, 2, 3))

Why measuring staleness beats the alternatives

✗ Trust "eventually"

No bound on how long or how often. The source calls it a vague guarantee: with w = r = 1 here, 2 reads in 3 right at the ack can miss the write.

✗ Watch replication lag only

Works when a leader defines an order. Leaderless replicas have no position to subtract, so the lag metric doesn't exist.

✗ Treat w + r > n as a guarantee

LWW clock skew, concurrent writes, a partly failed write read back through repair, or plain bad timing can still return an old value, as the source warns.

✓ Quantify it (PBS)

Pick n, w, r from numbers: 2/3 stale at the ack, 0.959 fresh 50 ms later under these latencies. Detect stale reads asynchronously from the late replies and compensate.

Does w + r > n make reads always fresh?

No. Overlap means the newest value is in the answers, not that the store knows which one is newest: with last-write-wins and skewed clocks it may pick the wrong one. The source adds that stronger promises (read-your-writes, monotonic reads, consistent prefix) generally need transactions or consensus, not tuned quorums. Use those for money or uniqueness; use a partial quorum (w + r ≤ n) when latency and "always writable" matter more, as Riak chooses, and put a number on the risk.

And the numbers come with WARS's stated limits: one write and one read (conservative when several writes overlap), latencies i.i.d. across replicas, no read repair or Merkle-tree anti-entropy (both make data fresher), no node failures or partitions, and clients go through a coordinator.

1 · Core model what to internalise, what to just look up

Keep it if it changes what you can explain, predict, compare, choose, build or debug. Otherwise it's reference.

Understand and remember

  • Write waits for w acks, read for r answers → if w + r > n the two sets share ≥ w + r − n replicas (pigeonhole) → at least one answer has the latest acked write → the read can pick it
  • w + r ≤ n (a partial quorum) → the read set can miss every replica holding the new value → P(stale) = C(n − k, r)/C(n, r) with k replicas holding it → 2/3 at the ack for n = 3, w = r = 1 → "eventual" becomes a number
  • The write keeps spreading after the ack → the longer the read waits (t), the more replicas have it → WARS: fresh 0.514 at t = 0 rising to 0.959 at 50 ms → staleness is both how often and for how long
  • Overlap delivers the newest value but the store must still know which is newest → with last-write-wins and skewed clocks it can pick the older one; a partly failed write can be spread by read repair → w + r > n is not linearizability
  • detail that matters Each tuning point trades staleness for latency and availability → w tolerates n − w failures for writes, r tolerates n − r for reads → Riak-style w = r = 1 stays writable when most replicas are down, at the price the table quantifies

4 · Compare against what you already know

vs Consensus with Raft: Raft commits on a majority and reads through the leader; a Dynamo-style store with w = r = 2 of 3 also overlaps. What does Raft's leader add that the quorum store lacks, and what does the quorum store keep that Raft gives up?

Check
  • Raft's leader puts all writes in one order, so there's no "which version is newest" question and no LWW clock skew
  • the quorum store has no leader to fail over: any replica can take writes, so it stays available with more combinations of failures
  • Raft refuses writes without a majority; a partial-quorum store keeps accepting them at a quantified staleness

vs Hypergeometric and capture–recapture: The staleness formula is a hypergeometric count. Map its parts onto the capture-recapture setting: what are the "marked" items, the population and the sample?

Check
  • population: the n replicas; marked: the k that already have the new value
  • the sample: the r replicas the read hears from, drawn without replacement
  • P(stale) is the chance the sample contains zero marked items: C(n − k, r)/C(n, r)

5 · Predict commit to an answer before revealing

A 5-replica store uses w = 2, r = 2. Right at the ack (k = 2), what is P(stale)? And what is the chance a read returns one of the last two versions? Commit first.

Reveal

w + r = 4 ≤ 5, so staleness is possible. P(stale) = C(3, 2)/C(5, 2) = 3/10. Within the last 2 versions: 1 − (3/10)2 = 0.91. For comparison, n = 5 with w = r = 1 is stale 4/5 at the ack, and w = 3, r = 2 is stale 1/10 even though it still doesn't overlap.
