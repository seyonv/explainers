What eventual consistency can't promise

Also called BASE, Dynamo-style or optimistic replication. The opening of the source guide's "Designing a system under certain constraints": four guarantees an eventually consistent store can't give, then the four properties we'd like instead (global validity, transactional availability, convergence, coordination-freedom), from Bailis et al.'s coordination-avoidance paper.

Prime · 2 minutes before you read

The problem: An eventually consistent store lets every replica accept writes alone, which keeps it fast and up through partitions. But any rule that depends on what another replica just did ("no two users share a name") can be broken before the copies meet, and both users were already told "ok".

Where it fits: First card of the consistency part. The CAP card showed the AP choice returning stale reads; this card shows the worse case, where each replica is valid but the merge isn't, and names the four properties the next card's I-confluence test decides between.

In one breath

An eventually consistent store lets every replica accept writes on its own and promises only that the copies will agree once writes stop. That keeps it fast and up during failures, but any rule that depends on what other replicas just did, like "no two users share a name", can be broken before the copies meet. The app has to live with that window.

Worked example: two users, one username

Ann and Bo sign up at nearly the same moment and both ask for sam. Ann's request lands on replica A, Bo's on replica B. Each replica checks its own copy, sees the name free, and says yes.

The four guarantees it can't give

GuaranteeWhat goes wrong (source)Simulated in the code
Key uniquenessReplicas each accept the same key, so one email or name ends up attached to two accounts. A: ok · B: okmerged: sam → [ann, bo]
Check-and-setDone as read-then-write, competing writers' updates reach storage nodes in different orders, so the nodes disagree for a while. node 1: ann then bo → bonode 2: bo then ann → annnodes agree? False
All-or-nothingIn a partition the coordinator's write lands on 1 of 3 storage nodes; the client is told "partial success", and the write is still sitting on that node. 1 of 3 acked, needed 2→ partialstored [pro, free, free]
Read-your-writeThe write succeeds in the zone that took it; readers in other zones may not see it, even the same user. write in us, read us → newread eu → old

The "needed 2" (a write quorum of 2 of 3) is our illustrative choice; the source says only "1 of 3" and "partial success". Rows 2–4 are the other three demos in the same file.

The code

class Replica:
    """Stores versions: name -> set of owners. Merge is union."""
    def __init__(self, name):
        self.name, self.users = name, {}

    def register(self, username, owner):
        if self.users.get(username):  # sees local data only
            return "taken"
        self.users[username] = {owner}
        return "ok"

    def merge(self, other):  # commutative, associative, idempotent
        for u, owners in other.users.items():
            self.users.setdefault(u, set()).update(owners)

def unique_ok(r):
    return all(len(o) <= 1 for o in r.users.values())

a, b = Replica("A"), Replica("B")
a.register("sam", "ann"); b.register("sam", "bo")   # both "ok"
a.merge(b); b.merge(a)
# 1. key uniqueness
#   t1 Ann -> A register sam: ok
#   t2 Bo  -> B register sam: ok
#      each replica valid? A True, B True
#   t3 merge: sam -> ['ann', 'bo'], replicas equal: True
#      invariant 'one owner per name' holds? False

What we'd like instead: four properties, two examples each

The source then names the system it wants: any server can run a transaction without talking to the others, yet the data stays valid and the servers end up agreeing.

PropertyWhat it means (source)HoldsBroken
Global validityInvariants hold over every committed state, including merged ones. A after t1{sam: {ann}}: one owner A after t3{sam: {ann, bo}}: both commits stood, the rule didn't
Transactional availabilityEvery transaction gets a response, commit or abort, even while replicas can't talk. Bo gets "ok" from Bduring the lag window B waits for A's "sam is free"partition: Bo waits or times out
ConvergenceWith no new writes, servers end up holding the same version of every item they both store. A = B after t3replicas equal: True Check-and-set nodesbo vs ann, until a deterministic merge rule picks one
Coordination-freedomA transaction's progress depends only on the versions it reads, not on other transactions in flight. register abovereads only its own replica Lock or leader firstmust hear from another server before answering

The trace above kept three of the four (available, convergent, coordination-free) and lost global validity. The next card's Theorem 1 says that for a user-chosen unique name you can't keep all four: some step has to coordinate.

Why coordinating only the unique part beats the alternatives

✗ Check the local replica

What the trace does. Fast and always available, but two people own sam after the merge, and both were told "ok".

✗ Last writer wins at merge

Converges to one owner, but an acknowledged signup silently disappears. With clock skew the "last" writer isn't even the later one. A lost update, not a fix.

✗ Make every write strongly consistent

Correct, but every profile edit and like now waits on a round trip, and during a partition the side without a majority must refuse writes it didn't need to.

✓ Coordinate only non-mergeable rules

Send just the "claim a name" step to one owner (a leader or consensus group for that name). Everything whose merge keeps the rules valid stays local and coordination-free.

So is eventual consistency the wrong choice?

Not for data whose merge can't break a rule. Dynamo was built for shopping carts: merging two carts is a union, so an "add to cart" is never lost, though the Dynamo paper notes that deleted items can resurface. Counters, likes and logs merge just as safely. It's the wrong choice for rules like uniqueness or "balance never below zero" when replicas withdraw independently.

Some limits are cheaper to patch than full coordination. Read-your-write can come from session guarantees, such as routing a user back to the zone that took their write. Uniqueness is mergeable if the system picks the value (replica id + counter), just not when the user picks it; Bailis et al. make this distinction. So many apps key accounts by a generated id and coordinate only the human-readable handle (our reading).

Understand and remember

  • Each replica accepts writes checking only its own copy → a concurrent write on another replica is invisible during the lag → both commit → the merge (union) holds both → a cross-replica rule like uniqueness breaks, after both users were told ok
  • Converging isn't being valid → A = B after the merge, yet sam has two owners → eventual consistency promises agreement, not that invariants hold
  • Fixing it at merge time (last writer wins) → converges but silently drops an acknowledged write, and clock skew can drop the later one → a lost update, not a fix
  • Coordinate only the non-mergeable step (claim a name at its one owner) → everything whose merge keeps the rules (carts, counters, likes, generated ids) stays local and coordination-free
  • detail that matters Uniqueness of a system-chosen value (replica id + counter) → each replica owns its own prefix → merges can't collide → so key accounts by a generated id and coordinate only the human-readable handle

5 · Predict commit to an answer before revealing

The same store holds a shopping cart as a set of items with union merge. Ann adds a book on replica A while, on replica B, she removes the pen that was already in the cart. After the merge, which items are in the cart? Commit first.

Reveal

With plain union, the book is added and the pen comes back: B's copy lost the pen, but A's still has it, and union keeps anything either side has. Adds are never lost, but deletes can resurface, which is exactly what the Dynamo paper reports for its carts. To make removes stick, the merge needs tombstones (a record of the delete) so union can tell "removed" from "never seen".
