Consistent hashing

Also called a hash ring (Karger et al., 1997); with many points per server, virtual nodes or tokens. It decides which server owns which key so that adding a server moves only that server's fair share of keys. Amazon's Dynamo and the Chord lookup protocol build on it; the source guide file named "distributed hash table" is really about Bigtable, so this card is supplemented.

Prime · 2 minutes before you read

The problem: Every client must compute which server owns a key, with no lookup table. hash(key) mod N does that perfectly evenly, until N changes: going from 4 to 5 servers reassigns 80% of keys, which for a cache is a near-total miss storm and for a database means copying 4 of every 5 records.

Where it fits: Builds on the request-path card's hash-based load balancing, which never had to handle a server joining. It's the placement half of scaling data; the next card, sharding and hot keys, covers what hashing can't fix.

In one breath

Hash servers and keys onto the same circle. A key belongs to the first server you meet walking clockwise from it. A new server lands somewhere on the circle and takes over only the arc just behind it, so only those keys move. With hash(key) mod N, changing N reshuffles almost everything.

In Python

import bisect, hashlib

def h(s):                     # 32-bit position on the ring
    d = hashlib.md5(s.encode()).digest()
    return int.from_bytes(d[:4], "big")

class Ring:
    def __init__(self, nodes, vnodes=1):
        pts = sorted((h(f"{n}#{i}"), n)
                     for n in nodes for i in range(vnodes))
        self.pos = [p for p, _ in pts]     # sorted positions
        self.own = [n for _, n in pts]     # server at each one

    def owner(self, key):
        # first position clockwise; % wraps past the top
        i = bisect.bisect(self.pos, h(key)) % len(self.pos)
        return self.own[i]

keys = [f"key-{i}" for i in range(100_000)]
a, b = Ring("ABCD", 100), Ring("ABCDE", 100)
moved = sum(a.owner(k) != b.owner(k) for k in keys)
print(f"{moved / len(keys):.2%}")
# → 19.35%   (hash mod N on the same keys: 80.01%)

Lookup O(log(N·v)) · Space O(N·v) for N servers with v virtual nodes each. The positions are one sorted list, so finding the owner is a binary search; this toy rebuilds the list when a server joins, O(N·v log(N·v)), which is fine because joins are rare.

Why it beats the alternatives

✗ hash(key) mod N

Perfectly even and needs no state, but going from 4 to 5 servers moved 80.01% of keys. For a cache that is a near-total miss storm; for a database, 4 of 5 records copied.

✗ Ring, one point per server

Moves the minimum, but random points cut uneven arcs: C got 39.99% of keys and B 1.42%. A newcomer also relieves only one neighbour (all 17,266 from D).

✗ A table of every key

Any placement you like, but the table is as big as the key set and sits on every request's path, so it must itself be replicated and kept consistent.

✓ Ring with virtual nodes

Moved 19.35% against the 20% minimum, busiest server 1.14× the mean, and every client computes the owner itself from the server list.

Is it always the right way to place data?

No. Hashing destroys key order, so range scans (all images uploaded today) hit every server; systems that need them split by key range instead, as Bigtable and HBase do. If the server count never changes, plain mod N is simpler and perfectly even. Many databases instead create a fixed number of partitions, far more than servers, and move whole partitions when a server joins (DDIA ch. 6). Jump consistent hash needs no ring memory at all, but servers can only be added or removed at the end of the list.

It also can't fix a hot key: one viral image still lands on one server however the ring is cut. That needs replication or key splitting (see sharding and hot keys). In one line each: Chord uses the ring for a peer-to-peer lookup where each node knows only O(log N) others; Dynamo uses it with tokens to place each key and its N − 1 clockwise replicas.

Understand and remember

  • Owner = h mod N → changing N changes almost every key's owner → only 1/(N + 1) stay → 80.01% of keys moved from 4 to 5 servers
  • Put servers and keys on one circle; owner = first server clockwise → a new server takes over only the arc just behind it → about 1/(N + 1) of keys move, the minimum possible (19.35% with virtual nodes)
  • One random point per server → arcs are very uneven (39.99% vs 1.42%) and a newcomer relieves only one neighbour → give each server many points (virtual nodes) → each server's share averages over many arcs → spread falls about √v (std dev 16.56% → 1.69% at v = 100)
  • Clients compute the owner from the server list with a binary search → no per-key table on the request path → the server list is the only shared state
  • detail that matters Hashing destroys key order → range scans (all images uploaded today) must hit every server → systems needing scans split by key range instead, or hash the first part of a compound key and sort by the second

Reference only

  • md5's first 4 bytes as the 32-bit position
  • jump consistent hash and fixed-partition schemes
  • Chord's O(log N) finger table; Dynamo's N − 1 clockwise replicas
  • the per-server shares in the 1-point and 100-vnode table

  1. concept Explain why mod N is "perfectly even and needs no state" yet unusable for a cache fleet that grows.
    Check
    • even: a good hash spreads keys uniformly over N buckets; no table needed
    • but the owner depends on N itself, so adding one server moves N/(N + 1) of keys

  2. mechanism Walk through img-4 (h = 490555030) under mod N and under the ring, before and after E joins.
    Check

    • E at 51.6° lands between them, so img-4 now goes to E: moved, and only because it's in E's arc
  3. tradeoff Your server count never changes. Ring with virtual nodes, or plain mod N? And what if you expect to double the fleet twice a year?
    Check
    • fixed count: mod N is simpler, stateless and perfectly even
    • frequent growth: the ring (or many fixed partitions moved whole) keeps each change to ≈ 1/(N + 1) of keys
    • the ring costs a sorted list of N·v positions and a binary search per lookup

vs Sharding and hot keys: Consistent hashing evens out keys across servers; the sharding card shows load still uneven. What is the difference between spreading keys and spreading load, and which tool handles each?

Check
  • virtual nodes make each server own about the same number of keys
  • but traffic per key is skewed (Zipf): one key can carry 13.47% of requests
  • a key can't be split by any placement scheme; salting (or replication for reads) handles the hot key

vs Hashing and buckets: A hash table resizing its bucket array also changes "mod N". Why is that fine in memory and a disaster for a fleet?

Check
  • in memory, rehashing every key is a fast local pass, amortised by doubling
  • in a fleet, a moved key means copying data over the network or a cache miss hitting the database
  • so distributed placement minimises movement; in-memory tables minimise probe cost
