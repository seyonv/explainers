Partial failure and CAP

Also called Brewer's theorem (proved by Gilbert and Lynch, 2002) and "you can't pick CA". The source guide's Engineering section: partial failure is what makes distributed systems different, CAP's consistency means linearizable, available means every non-failing node answers, and the speed of light caps how global consistency can be.

Prime · 2 minutes before you read

The problem: On one machine a call either works or everything dies. Across a network, a caller that sees a timeout can't tell whether the write never arrived, crashed mid-way or landed with its reply lost. And when the link between two replicas drops, each must decide alone whether to answer or refuse.

Where it fits: Builds on the correlated-failure card's point that parts fail in unexpected ways. This card names the two consequences the whole course deals with: partial failure (you don't know what happened) and CAP (during a partition, choose consistency or availability). The next card applies that choice subsystem by subsystem.

In one breath

On one machine a call either works or the whole machine dies. Across a network, part of the system can fail while the rest keeps running, and a caller often can't tell which part. When the network splits replicas apart, each replica must choose: refuse requests (stay consistent) or answer with what it has (stay available). It can't do both.

Worked example: a partition between two replicas

A customer of the image-resize service upgrades from free to pro. Replicas A and B both hold plan = free. Then the link between them drops, and a write arrives at A while a read arrives at B.

The code

class TwoReplicas:
    def __init__(self, mode):
        self.mode = mode              # "CP" or "AP"
        self.data = {"A": {}, "B": {}}
        self.partitioned = False

    def write(self, node, key, value):
        if not self.partitioned:
            for d in self.data.values():
                d[key] = value        # ack only once both have it
            return "ok"
        if self.mode == "CP":
            return "error: can't reach peer"
        self.data[node][key] = value  # AP: accept locally
        return "ok"

    def read(self, node, key):
        if self.partitioned and self.mode == "CP":
            return "error: can't reach peer"
        return self.data[node][key]

    def heal(self):
        self.partitioned = False
        if self.mode == "AP":         # toy merge: A's copy wins;
            self.data["B"].update(self.data["A"])  # real: LWW, CRDTs

# CP:
#   write A plan=pro   -> error: can't reach peer
#   read  B plan       -> error: can't reach peer
#   heal; read B plan  -> free
# AP:
#   write A plan=pro   -> ok
#   read  B plan       -> free
#   heal; read B plan  -> pro

Why choosing per subsystem beats the alternatives

✗ Claim to be CA

Needs a network that never drops messages and nodes that never die. "These types of systems don't exist" (source); partitions happen, so a "CA" system just behaves unpredictably when they do.

✗ Coordinate every write globally

Correct, but each write waits ≥ 1 round trip: 83 ms East US to West Europe, 265 ms West Europe to Australia East, over half the 500 ms p99 budget. And in a partition it still has to refuse.

✗ Treat a timeout as "it failed"

The reply-lost row shows the write may have landed. Retrying a non-idempotent write then applies it twice.

✓ Decide C or A per subsystem

The source's image service does this: the job queue favours consistency with Paxos failover; the identity cache favours availability. Coordinate only where a wrong answer costs more than no answer.

Does CAP mean you give up C or A all the time?

No. CAP only bites during a partition. With the network healthy you can have both; the everyday trade-off is consistency against latency, the round trips in the table above. Abadi calls this PACELC: under a Partition choose A or C, Else choose Latency or Consistency.

CAP's definitions are also narrow. Its C is linearizability, not ACID's C. Its A demands an answer from every non-failing node, so a Raft or ZooKeeper cluster that keeps serving on its majority side counts as CP, even though operators call it highly available. That's why this card's two-node CP example refuses on both sides: with 2 nodes neither side has a majority; with 3, the side with 2 would keep working (our reading, not in the source). Kleppmann argues CAP is too narrow to classify real systems at all.

Understand and remember

  • Request lost, server crashed mid-way, reply lost → all three look like the same timeout → the caller can't know whether the write happened → a retry must be safe to repeat
  • Partition between replicas → a write at A can't reach B → B must either refuse (C: never wrong, but a healthy node errors) or answer stale (A: always answers, not linearizable) → it can't do both, and "CA" just means undefined behaviour when a partition comes
  • A write another replica must see → can't be acked before one round trip to it → light in fibre (~200,000 km/s) sets the floor → 8 ms nearby, 83 ms across the Atlantic, 265 ms to Australia (53% of a 500 ms budget)
  • CAP bites only during a partition → otherwise the everyday trade-off is latency vs consistency (PACELC) → choose per subsystem: coordinate only where a wrong answer costs more than no answer
  • detail that matters CAP's A demands an answer from every non-failing node → a 2-node CP pair must refuse on both sides → with 3 nodes the majority side keeps working and still counts as CP → this is why real "highly available" consensus systems are CP in CAP terms

5 · Predict commit to an answer before revealing

You rebuild the CP example with three replicas A, B, C, and the partition cuts A off from B and C. The write plan=pro arrives at B, the read arrives at A. What does each return, and is the system CP or AP? Commit first.

Reveal

B and C are a majority (2 of 3), so the write at B commits with C's ack and returns ok. A is alone and can't reach a majority, so its read must return an error (or it would risk serving free after pro committed). That's still CP: A is a non-failing node that refused. But the majority side stayed available, which is the difference a third replica makes.
