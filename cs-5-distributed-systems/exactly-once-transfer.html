Money transfer without distributed transactions

Also called exactly-once (or effectively-once) processing, multi-partition request processing, or an idempotent consumer. The closing part of the source guide's "Designing a system under certain constraints": ordered logs in Bayou, then Example 1, a money transfer split across a request log, a debit stream and a credit stream.

Prime · 2 minutes before you read

The problem: Moving 20 from Bob to Carol touches two partitions. Two plain writes lose money if the process crashes between them; a distributed transaction blocks when its coordinator dies; and retries after a crash or a timeout can debit twice. You need every transfer applied exactly once to both accounts, with no step waiting on another partition.

Where it fits: Builds on the I-confluence card: withdrawals need coordination, deposits don't. This design confines the coordination to one partition per account and makes everything else replay-safe with request ids, the same end-to-end idea the retries card uses over HTTP.

In one breath

Don't lock both accounts at once. Commit the transfer with one append to a log, tagged with a request ID. Then a processor turns it into a debit on the payer's partition and a credit on the payee's, each carrying that ID. The processor may crash and replay, so a step can arrive twice. Each partition remembers the IDs it has applied, so the second arrival changes nothing. The rule "apply every request exactly once to both accounts" holds, with no step that waits on another partition.

The code

class Account:
    """One account partition: a balance plus the ids it has seen."""
    def __init__(self, balance, dedup=True):
        self.balance, self.dedup, self.seen = balance, dedup, {}

    def apply(self, rid, delta):
        if self.dedup and rid in self.seen:
            return self.seen[rid]           # replay: same answer
        if self.balance + delta < 0:
            result = "rejected"             # debit: funds too low
        else:
            self.balance += delta
            result = "ok"
        self.seen[rid] = result             # same partition, same
        return result                       # write as the balance

def process(log, accts, start=0, crash_at=None):
    status = {}
    for rid, src, dst, amt in log[start:]:
        status[rid] = accts[src].apply(rid, -amt)   # debit first
        if rid == crash_at:
            return status                   # crash: no credit yet
        if status[rid] == "ok":
            accts[dst].apply(rid, +amt)     # then credit
    return status
# status {'r1': 'ok', 'r2': 'ok', 'r3': 'rejected', 'r4': 'ok'}
# naive: restart from r2       {'alice': 60, 'bob': 40, 'carol': 30} total 130
# dedup: restart from r2       {'alice': 60, 'bob': 60, 'carol': 30} total 150
# dedup: replay whole log x2   {'alice': 60, 'bob': 60, 'carol': 30} total 150

DDIA's version of this design checks funds before the request enters the log, so debits never fail. The source's diagram instead sends back a debit result and allows a "partial" final status; the code follows the source, and sends the credit only after an ok debit, so "partial" can only be the moment in flight.

The source says truncating the logs "guarantees that they can catch up". In Bayou it works the other way: truncation bounds the log, and a server that fell behind the cut can't catch up from the log, so it receives the whole database instead (Petersen et al. 1997). Why the log beats the alternatives

✗ Two plain writes

Debit bob, then credit carol, no log. A crash between them loses the 20 for good: nothing records that a credit is owed, so the total stays 130.

✗ Distributed transaction (2PC/XA)

Atomic across both partitions, but both must be up at once, locks are held across a round trip, and if the coordinator dies after prepare, everyone waits.

✗ Retry without request IDs

At-least-once delivery with nothing to recognise a copy. The trace: bob debited twice (−20), r4 paid twice, and r3's rejection flips to ok.

✓ Log + request ID + dedup

One append commits the transfer. Each partition applies its half on its own, and any replay is a no-op. The total came back to 150 after every replay.

Is this really "exactly once"?

Delivery is at-least-once; the effect is exactly-once, because each apply is idempotent. That depends on three things: the client makes the ID (so a client retry is caught, the end-to-end argument), the processor is deterministic (a replay emits the same instructions), and seen is written in the same local write as the balance. Lose any one and duplicates come back. The debit can check "balance ≥ 0" alone because every debit to bob goes through bob's partition in log order; credits only add, which is always safe to merge, like inserting a row that points at an existing parent (the source's foreign-key note; deletes are harder unless they cascade).

It's the wrong tool when the caller needs the money moved before it answers (the client gets "committed", then waits for the final status), when the rule spans accounts ("these two together stay above 1,000"), which needs coordination, or when both accounts live in one database: a local ACID transaction is simpler.

Understand and remember

  • Commit = one append of (request_id, from, to, amount) to the log → a processor turns it into a debit on the payer's partition and a credit on the payee's → no step waits on two partitions at once, and no locks span them
  • The processor can crash and replay; clients can retry → the same instruction can arrive twice (at-least-once) → each partition records request_id → result → a repeat returns the stored result and changes nothing → the effect is exactly-once
  • All debits to one account go through that account's partition in log order → the balance check is local and serial there → the non-confluent rule (withdrawal, balance ≥ 0) is enforced by a single owner; credits only add, which merges safely
  • Store the result, not just "seen" → a replayed rejected debit stays rejected → without it, r3 is re-checked against newer balances and flips to ok
  • detail that matters Exactly-once holds only if the client picks the id (so client retries are caught), the processor is deterministic (replays emit the same instructions) and seen commits atomically with the balance → drop any one and duplicates come back

4 · Compare against what you already know

vs Compaction, deletion and XA: 2PC and this log design both make a two-partition change all-or-nothing in the end. What is fundamentally different about when each partition can act, what each blocks on, and how each fails?

Check
  • 2PC: both partitions prepare, hold locks and wait for one coordinator's decision
  • log: the append is the decision; each partition applies its half independently, later
  • 2PC fails by blocking (in-doubt locks while the coordinator is down); the log fails by lag (a slow partition applies late) and by duplicates if dedup is missing

vs Idempotency and retries: The retries card's server stores (key → request, reply); this card's partition stores (request_id → result). What is the same, and what extra check does the HTTP version make that this one doesn't need?

Check
  • same: remember the id with its outcome, and replay the outcome on a repeat
  • the HTTP version also compares the request body (same key, different amount → 422) and handles in-progress duplicates (409)
  • here the log is the single source of each request, so an id can't arrive with a different amount

5 · Predict commit to an answer before revealing

After the card's r1–r4 (alice 60, bob 60, carol 30), append r5 carol→bob 30. The processor crashes right after r5's debit and restarts at r5. What are the final balances with dedup, and without it? Commit first.

Reveal

With dedup: the debit left carol at 0; the replayed debit is seen and returns ok, so the credit runs: bob 90, carol 0, alice 60, total 150. Without dedup: the replayed debit is checked again against carol's 0, is rejected, and so no credit is sent. Bob stays 60 and carol 0: total 120. The first debit's 30 has vanished. The naive system didn't just double-charge; it lost money and never finished the transfer.
