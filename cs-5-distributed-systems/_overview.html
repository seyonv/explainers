Choosing where to coordinate

The overview for course 5 of the core CS canon series. It ties together the 20 cards on the source guide's distributed systems, networks, internet and consistency pages, all built around its image-resize service (10K requests/s per region, p99 < 500 ms, 99.9% available): what fails, what a replica may decide on its own, and what it costs when replicas have to agree.

Prime · 2 minutes before you read

The problem: The image-resize service needs about 1K cores, so it can't live on one machine. Once it spans machines, parts fail on their own, the network answers with silence, and replicas disagree. Twenty cards each handle one piece of that; without a map they read as twenty separate rules.

Where it fits: This is the course map. It builds on cs-4's requirements and SLO arithmetic (the 99.9% target and the 500 ms p99 budget) and ties the four parts (the reality, the network, consistency, scaling data) with one question: where must replicas coordinate, and what does each coordinated write cost?

In one breath

Machines fail in parts, the network answers some requests with silence, and replicas go down together far more often than the pN arithmetic says. So replicate for availability, and let each replica act alone wherever merging two replicas' work can't break a rule. Coordinate (one owner, a majority quorum, Raft) only where a merge can break one, because every coordinated write waits at least one round trip and has to refuse during a partition. Underneath all of it: a timeout is a guess, so a retry must be safe to repeat. Judge a service by its p99 and its yield, not its mean and its uptime.

The words people use

Linearizable vs eventually consistent

Linearizable (CAP's C): every operation looks as if it happened at one instant on one copy. Eventually consistent: replicas may disagree for a while and agree once writes stop. The first costs a round trip per write; the second costs broken rules if a merge can break them.

Partial failure, partition, timeout

Partial failure: some parts fail while the rest runs, and the survivors can't tell which. A partition is the network case. A timeout is the only detector, and it is a guess: a 25 s GC pause looks exactly like a crash.

At-least-once, exactly-once

Delivery over a lossy network is at-least-once: a retry may bring a second copy. The effect can still be exactly-once if every apply is idempotent, keyed by a request id the client chose once.

✓ Coordination-free

A write that commits using only its own replica's state. It's safe exactly when the rule is I-confluent, meaning any two valid replicas merge into a valid state. Deposits and foreign-key inserts pass. Withdrawals, chosen usernames and deletes fail, and only those need to pay the round trip.

When this advice doesn't apply

Both formulas are simple models. The p and c on these cards are illustrative, and c can't be derived; it comes from how the system is run, which is why the source says to ask vendors for real MTTF and MTTR distributions. The round-trip floor only bites across distance: inside one region zones are under 10 ms apart, so coordinating every write there often costs little, and the price shows up across regions and during partitions. Everything here assumes crash faults; a server that lies (a Byzantine fault) needs a different family of protocols.

If the work fits on one machine, most of this course doesn't apply. The image service needs it only because 1K cores won't fit in one box. Two accounts in one database want a local ACID transaction, not a log and dedup. A small, stable fleet is fine with DNS or a load balancer instead of ZooKeeper, and with plain hash mod N instead of a ring. And when you do need consensus, use etcd, Consul or ZooKeeper rather than your own Raft.

Understand and remember

  • Work too big for one box → spread over machines → parts fail independently of each other and the network drops or delays messages → a caller's timeout can't tell lost request, crash, pause or lost reply apart → every retry must be safe to repeat
  • Replicas share power, code and config → a shared event c takes them all out at once → replication shrinks only the pN term → past two or three replicas, the next dollar goes to shrinking c (canaries, separate zones)
  • A write that other replicas must see → waits at least one round trip to a majority → 8 ms nearby, 69–162 ms across continents, and refuses during a partition → coordinate only the (rule, operation) pairs whose merge can break the rule (the I-confluence test)
  • Latency has a long tail and fan-out multiplies it → the mean hides the slow 1% that fan-out makes everyone's problem → judge a service by p99 and yield, and shed load early with backpressure instead of letting queues grow
  • detail that matters Majority quorums of ⌊n/2⌋ + 1 → any two majorities share a server → that one overlap is what makes Raft elections, ZooKeeper and w + r > n reads safe, and why an even n buys nothing

5 · Predict commit to an answer before revealing

A startup runs the image service on one 64-core machine for its first 500 requests/s. Which of this course's mechanisms does it still need on day one, and which can it skip? Commit before revealing.

Reveal

It still needs timeouts and idempotent retries: its clients talk to it over a network, so the six silent cases and the lost-reply double charge still happen. It can skip almost everything else: no replicas to coordinate, no quorums, no Raft, no consistent hashing, and a local ACID transaction instead of a request log. The overview says so directly: if the work fits on one machine, most of this course doesn't apply. The price is that one box down is 100% down, which is fine only while the availability target allows it.

6 · Apply use the model, don't restate it

Design review: the image service adds user handles (chosen by users), a likes counter per image and a prepaid credit balance that resizes spend. For each of the three, decide coordinate or not using the I-confluence test, name the mechanism (local merge, single owner or consensus group, log + dedup) and give the per-write cost. Assume the coordinating group is 3 nodes with the leader in East US and followers at 8 ms and 69 ms.

Done when: You have three rows (rule, operation, I-confluent?, mechanism, cost per write) and can say why the 3-node group commits in 8 ms while the course's 5-node example needs 69 ms.

Hint

Handles: user-chosen unique values fail the test → one owner or consensus per handle. Likes: increments merge by addition → local, 0 ms of coordination. Credit spend: decrements with balance ≥ 0 fail → route each account's debits through one owner (log + request id). A 3-node majority is 2, so the leader needs one ack: the fastest follower, 8 ms. Five nodes need two acks, so the 2nd-fastest RTT, 69 ms.
