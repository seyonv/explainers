Delay, timeouts and congestion control

Also called latency bounds, failure-detection timeouts, and AIMD (additive increase, multiplicative decrease) or TCP congestion avoidance. The source guide's Networks page derives a worst-case delay bound from the QJUMP paper, gives the timeout rule 2d + r, and sketches TCP's window halving.

Prime · 2 minutes before you read

The problem: Packet delay is mostly time waiting in queues, and with no limit on senders there is no limit on the queue. So a timeout can only be a guess: too short and healthy nodes get declared dead, too long and failures sit unnoticed. Meanwhile, if every sender just sends as fast as it can, the queues overflow for everyone.

Where it fits: Builds on the unreliable-network card, which used 2d + r without saying where d comes from. This card derives a real worst-case d (QJUMP), shows its throughput price, and explains how TCP's AIMD keeps queues short when there is no bound.

In one breath

A packet's delay is mostly time spent waiting in queues, so it has no upper limit unless every sender is rate-limited. Without that limit, a timeout is a guess: too short and healthy nodes get declared dead, too long and real failures sit unnoticed. Congestion control keeps the queues short by having each sender grow its window slowly and cut it in half at the first sign of loss.

1 · The worst case, if every host is rate-limited

Treat the whole network as one big switch. At worst all n hosts send to the same destination at once, and your packet waits behind the other n − 2 (≈ n), each taking P/R to leave the slowest link:

τ≤ 2×n×PRqueueing, doubled for phase drift + εswitch processing
nhosts that could send to one destination1,000 Plargest packet a host may send per epoch256 B = 2,048 bits Rrate of the slowest link10 Gb/s εcumulative processing delay of switch hops4 µs 2×mesochronous network: host clocks tick at one rate but out of phase, so two packets can meet in one epoch×2
synchronized: 1,000 × 2,048 / 10¹⁰ s + 4 µs = 204.8 + 4 = 208.8 µs mesochronous: 2 × 1,000 × 2,048 / 10¹⁰ s + 4 µs = 409.6 + 4 = 413.6 µs ← one network epoch

n, P, R and ε are the QJUMP paper's own example values (it states ε = 1–4 µs and "< 500 µs" for 1,000 hosts at 256 B); the arithmetic is ours.

The source names the doubled bound "e" and calls it the phase misalignment; it is still τ, the delay bound. It also says that with one packet per epoch "most permanent queues can build up"; the paper says the opposite: no permanent queue can build up, so the bound holds forever. Corrected here.

2 · The price: throughput, and the knob f

One 256 B packet per 413.6 µs is about 5 Mb/s per host on a 10 Gb/s link. QJUMP relaxes this by assuming only n′ = n / f hosts ever send to one place at once. Each host may then send about R / (2n′):

fAssumed senders n′Epoch 2n′P/R + εRate per host ≈ R / 2n′Guarantee
11,000413.6 µs5 Mb/shard bound, always
1010045.0 µs50 Mb/sholds if ≤ 100 send at once
100108.1 µs500 Mb/sholds if ≤ 10 send at once
1,00014.4 µs5,000 Mb/s = R/2none: like plain Ethernet

Computed. QJUMP gives each of the eight IEEE 802.1Q priority levels (0–7) its own f: high priority gets a small f (low latency, little bandwidth), low priority a large f (no bound, all the rest). Coupling priority to a rate limit stops the "race to the top". Its Linux rate limiter costs about 35 cycles per packet, under 0.5% of the kernel path.

3 · The timeout: 2d + r

timeout = 2d + r d = max one-way network delay, r = max processing time bounded (QJUMP f = 1): 2 × 413.6 µs + 50 µs = 877.2 µs image resize service: 2 × 20 ms + 500 ms = 540 ms

The 50 µs, 20 ms and the use of the 500 ms p99 target as r are illustrative. The rule needs a real maximum d, which only a bounded network has; on the internet it's a percentile you pick. The QJUMP paper's 2PC detects a failure within two epochs (≈ 40 µs on its network) vs a typical 150 ms timeout in RAMCloud.

4 · Congestion control: AIMD for 40 RTTs

Each loss-free round trip adds one packet to the congestion window (cwnd); a drop halves it. Here the path holds 16 packets, so sending more than 16 in one RTT loses one (illustrative capacity; no slow start).

drops at RTT 16, 26, 36 (cwnd 17 > 16 → 17 // 2 = 8) steady cycle 8, 9, …, 17 = 10 RTTs, mean window (8 + 17) / 2 = 12.5 = 78% of 16 all 40 RTTs: 430 packets sent, mean 10.75 per RTT
def aimd(rtts=40, cap=16, cwnd=1):
    trace = []
    for _ in range(rtts):
        trace.append(cwnd)
        if cwnd > cap:            # queue overflowed: a drop
            cwnd = cwnd // 2      # multiplicative decrease
        else:
            cwnd += 1             # additive increase
    return trace

def per_ack_growth(cwnd):
    w = float(cwnd)
    for _ in range(cwnd):     # one RTT = cwnd ACKs
        w += 1 / w                # the source's cwnd += 1/cwnd
    return w

t = aimd()
print([i for i, w in enumerate(t) if w > 16], sum(t))
print(round(per_ack_growth(8), 3))
# → [16, 26, 36] 430
# → 8.951

Output under python3 3.10. cwnd += 1/cwnd per ACK adds just under 1 per RTT (8 → 8.951), which is why "+1 per RTT" is the usual shorthand.

The source writes cwnd += 1\cwnd; the operator is division, 1/cwnd.

Why AIMD beats the alternatives

✗ Fixed window

Pick cwnd once. Too big and it overflows the queue on every RTT; too small and it wastes the link. It can't react when another flow joins.

✗ Additive decrease (AIAD)

Subtract 1 on loss. Two flows sharing 16 packets, starting at 1 and 12, are still 3 vs 14 after 40 RTTs: the gap never shrinks (computed).

✗ Rely on switches alone

Switches see the queues and are where fair sharing can be judged (the source's point), but a switch can only drop or mark packets; senders still have to slow down.

✓ AIMD

Halving cuts the bigger flow by more, so the same two flows end at 5.98 vs 6.02 (computed). It converges to a fair share while keeping the link about 78% full here.

Is AIMD with loss-based timeouts always the answer?

No. Loss-based AIMD only reacts after a queue has overflowed, so it keeps queues full and adds delay; that's why latency-critical data-centre traffic uses something else. QJUMP gives hard bounds, but only when every host runs its rate limiter. DCTCP and ECN let switches mark packets early, so senders make small cuts instead of halving (the source's "catch congestion early"); BBR models the path's bandwidth and RTT instead of waiting for loss. These three are general practice, not from the source.

For timeouts, don't treat every silence as a network fault: a crashed process on a live host sends RST or FIN at once, which is much faster than waiting out any timeout.

Understand and remember

  • Delay is queueing → queues are unbounded unless every sender is rate-limited → with rate limits, the worst case is all n hosts sending to one place: τ ≤ 2nP/R + ε (413.6 µs for 1,000 hosts) → the bound holds only because everyone obeys it
  • A hard bound caps each host at ~R/2n (5 Mb/s at f = 1) → QJUMP assumes only n/f senders at once → bigger f = more throughput, weaker guarantee → per-priority f lets latency-critical traffic keep the bound
  • Timeout = 2d + r → needs a real maximum one-way delay d → only a bounded network gives one → otherwise d is a percentile you choose and the timeout stays a guess
  • No bound → senders must slow themselves → AIMD: +1 packet per loss-free RTT, halve on loss → a sawtooth that keeps queues from growing forever (8 → 17 → 8, mean 12.5 of 16) → halving cuts the bigger flow by more, so flows converge to fair shares
  • detail that matters Loss-based AIMD reacts only after a queue overflows → it keeps queues full and adds delay → data-centre traffic uses early signals instead (ECN/DCTCP marks, BBR's path model)

Reference only

  • QJUMP's example values (256 B packets, 10 Gb/s, ε = 1–4 µs)
  • 802.1Q priority levels 0–7 and the ~35-cycle rate limiter
  • Wang & Ng's EC2 loss numbers (< 0.5%, episodes in > 10% of intervals)
  • cwnd += 1/cwnd per ACK ≈ +1 per RTT (8 → 8.951)

    Check
    • 150 ms is below r for many real resizes and below GC pauses: healthy workers are declared dead, their load moves, more time out (cascade)
    • 5 s: real failures wait 5 s to be noticed, eating the p99 budget ten times over

4 · Compare against what you already know

vs Backpressure, percentiles, yield and harvest: AIMD slows a sender when the network's queue overflows; backpressure slows a caller when a server's queue is full. What is the same mechanism underneath, and what signal does each use?

Check
  • both keep a queue short by making the sender slow down
  • AIMD's signal is a lost packet (implicit); backpressure's is an explicit fast error or a blocked put
  • both need the sender to cooperate: rejected callers back off exponentially, TCP halves its window

vs Idempotency and retries: TCP halves its window on loss; the retries card doubles the wait between retries. Both are multiplicative responses to trouble. Why multiplicative in both cases, and what does jitter add that AIMD doesn't need?

Check
  • multiplicative response backs off fast enough to relieve an overloaded resource (the one thing additive can't do quickly)
  • for retries, many clients fail at the same instant, so they'd return together; jitter spreads them
  • TCP flows lose packets at different times already, so their sawtooths desynchronise without explicit jitter

5 · Predict commit to an answer before revealing

Double the path capacity: AIMD with a drop whenever cwnd > 32, starting at 1, for 40 RTTs. When is the first drop, how many drops happen in 40 RTTs, and what is the steady-cycle mean as a share of capacity? Commit, then run aimd(cap=32).

Reveal

The first drop is at RTT 32 (cwnd 33 → 16), and it's the only one in 40 RTTs; 694 packets are sent. The steady cycle is 16, 17, …, 33: 18 RTTs, mean (16 + 33) / 2 = 24.5 = 76.6% of 32. Over 80 RTTs the drops land at 32, 50 and 68. A bigger pipe makes the sawtooth slower (18 RTTs per cycle instead of 10), which is why +1 per RTT is too timid for fast long-distance links.
