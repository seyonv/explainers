Sharding and hot keys

Also called partitioning (DDIA's word), horizontal scaling of data, or key-based routing; a hot key is also called a hot spot or a celebrity key. The source guide uses shards everywhere (MapReduce's hash(key) mod R, H-Store's partitions, the three-shard harvest example) but never covers them, so this card fills the gap using the image-resize service's 100,000 users and 10,000 requests/s.

In one breath

Split the keys over N machines with a rule every client can compute: by range (users 1–6,250 on shard 0, …) or by hash (md5(key) mod 16). Hashing spreads keys evenly, but it can't split a single key: if one user sends 13% of the traffic, one shard carries that 13% whatever you do. Salting splits that one key into 8 sub-keys, and every read of it then has to ask all 8.

Worked example: Zipf traffic over 16 hash shards

Web traffic is skewed: a few users send most of it. Model it with Zipf: the user ranked k sends a share proportional to 1/ks. The skew s = 1.1 and "user k is the k-th busiest" are illustrative, not measured.

Salting: split the hot key, pay on reads

Write user1#0 … user1#7, picking a suffix at random per write, so each sub-key gets 13.47% / 8 = 1.68%. A read of user 1 must fetch all 8 and add them up.

In Python

import hashlib
from collections import Counter

def shard_of(key, n=16):
    # md5, not hash(): str hashes change every run
    d = hashlib.md5(key.encode()).digest()
    return int.from_bytes(d[:8], "big") % n

def zipf(n=100_000, s=1.1):
    w = [k ** -s for k in range(1, n + 1)]
    total = sum(w)
    return [x / total for x in w]    # p[k-1] = share of user k

def shard_loads(p, salted=(), n=16, salts=8):
    load = Counter()
    for k, pk in enumerate(p, start=1):
        if k in salted:              # writes pick 1 of 8 sub-keys
            for i in range(salts):
                load[shard_of(f"user{k}#{i}", n)] += pk / salts
        else:
            load[shard_of(f"user{k}", n)] += pk
    return load

p = zipf()
for top in (0, 1, 2):
    load = shard_loads(p, salted=set(range(1, top + 1)))
    s = max(load, key=load.get)
    print(f"salt top {top}: shard {s} has {load[s]:.2%}")
# → salt top 0: shard 12 has 18.62%
# → salt top 1: shard 11 has 12.57%
# → salt top 2: shard 4 has 9.07%

Time O(1) per request · O(8) per salted read. Routing is one hash and a mod; a salted read costs one lookup per suffix. Computing the table above is O(N × salts) for N keys, 100,000 here.

Why it beats the alternatives

✗ Range sharding

Keeps scans on one shard, but sequential keys (timestamps, auto-increment ids) send 100% of new writes to the last shard, and a hot key is still in one range.

✗ Just add shards

No help for one key. Hottest share: 18.62% on 16 shards, 15.51% on 32, 14.28% on 64, 13.60% on 256; that's 34.8× fair. It can't go under user 1's 13.47%.

✗ Salt every key

Evens out load, but every read becomes 8 reads, so read traffic goes up 8× for 100,000 users to fix a handful. Most keys are cold and never needed it.

✓ Hash, plus salt the few hot keys

Hashing spreads the long tail; salting users 1 and 2 cuts the hottest shard from 18.62% to 9.07%, and only reads of those 2 keys pay the 8× fan-out.

Is salting always the fix?

No. It suits write-heavy hot keys whose values add up: counters, append-only logs. The source calls the image service's usage tracking read-light, which is why salting fits there (our inference). For a read-heavy hot key (a popular profile), cache it or add read replicas instead; salting would make each read 8× dearer. Salting also breaks anything that needs the whole key in one place: a uniqueness check, a transaction over the key, per-key ordering.

You also have to know which keys are hot, and they change, so the salted set has to be tracked (DDIA notes this bookkeeping). When you need range scans and even writes, use a compound key: hash the first part (user id) to pick the shard, then sort by the second (timestamp) inside it, as Cassandra does. To add shards without moving most keys, see consistent hashing.
