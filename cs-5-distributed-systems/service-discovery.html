Service discovery

Also called a service registry, distributed dynamic discovery, or a coordination service (Chubby, ZooKeeper, etcd, Consul). The source guide files it under "Domain Name Servers", but the section is really about why DNS stopped being enough and what ZooKeeper does instead.

In one breath

Service discovery answers "which machines are running service X right now?". Each server registers itself in a small, replicated store and keeps a heartbeat going; if the heartbeat stops, its entry disappears on its own and everyone watching the list is told. DNS answers a weaker question: what could be at an address, cached for a while.

Worked example: three resize servers, one registry

Three servers of the image-resize fleet each create an ephemeral node under /resize, tied to their session. A client watches /resize. The session timeout is 20 s, the source's "typically 20 seconds". srv-2 crashes; srv-3 hits a 25 s stop-the-world GC pause.

The timeout is the price of detection. The source puts it bluntly: it's "the major cost for MTTR". Here is what one dead server costs at the running example's load, if clients keep sending to it until they learn it's gone:

per server: 10,000 req/s ÷ 40 servers = 250 req/s registry: 20 s session timeout × 250 = 5,000 requests to a dead server DNS cache: 300 s TTL × 250 (illustrative) = 75,000, and only if something removes the record at all; DNS itself never notices the crash

10,000 req/s and 40 servers are the source's image-resize numbers; the 300 s TTL is illustrative. Real clients also retry on a refused connection, so these are upper bounds.

The registry itself must survive: majority quorums

A registry on one machine would be a single point of failure, so ZooKeeper runs as an ensemble that commits a change only when a majority agrees.

Computed by quorum(n). An even n buys nothing: 4 survives 1 crash, the same as 3, with one more machine that can fail. The same GC pause as srv-3 on an ensemble member makes it look dead too; the source warns this can "precipitate quorum loss". With n = 3, one paused plus one crashed leaves 1 of 3 < q = 2, and writes stop.

In Python: ephemeral nodes, sessions and watches

TIMEOUT = 20            # source: session timeout "typically 20 s"

class Registry:
    def __init__(self):
        self.nodes = {}          # path -> owning session
        self.last_beat = {}      # session -> last heartbeat time
        self.watchers = []       # callbacks, fired on any change

    def register(self, path, session, now):
        self.nodes[path] = session           # ephemeral node
        self.last_beat[session] = now
        self._notify(now, f"+ {path}")

    def heartbeat(self, session, now):
        if session in self.last_beat:        # expired: too late
            self.last_beat[session] = now
            return True
        return False

    def tick(self, now):
        for s, t in list(self.last_beat.items()):
            if now - t >= TIMEOUT:           # silent too long
                del self.last_beat[s]
                gone = [p for p, o in self.nodes.items() if o == s]
                for p in gone:
                    del self.nodes[p]
                    self._notify(now, f"- {p}")
# t= 0  + /resize/srv-3  -> [srv-1, srv-2, srv-3]
# t=25  - /resize/srv-2  -> [srv-1, srv-3]
# t=49  - /resize/srv-3  -> [srv-1]
# t=55  + /resize/srv-3  -> [srv-1, srv-3]

Real output under python3 3.10.20 (the first two register lines trimmed); the full file adds _notify, quorum and the scenario. Time O(sessions + nodes) per tick · Space O(nodes): each tick scans every session, and a real registry would keep a timer heap instead.

Why it beats the alternatives

The three ✗ cells are the source's alternatives table. They win in simpler setups; they fail at "who is up right now, with churn".

✗ Standard DNS

Read-optimized and fine if results can be a little stale. But caches keep old answers until the TTL runs out, every new machine means updating the DNS server, and it can't tell a dead server from a live one.

✗ A load balancer

Good for a simple service-oriented setup with short-lived connections: it health-checks backends for you. Long-lived connections stay pinned to one backend, and the balancer is one more thing that has to know the list.

✗ A database table

Fine for static configuration. As a live registry it adds polling load to the database, has no ephemeral entries, and gives no ordering guarantees for change notifications.

✓ A coordination service

ZooKeeper, etcd or Consul: entries expire with their owner, watches push changes, and a majority quorum keeps the list consistent while 1 of 3 (or 2 of 5) servers is down.

Do you always need ZooKeeper?

No. The source cares about operational overhead: in a simple environment DNS or a load balancer is enough, and ZooKeeper is "overkill". It's also easy to misuse. It stores small metadata in memory (a node's data is capped at about 1 MB by default), so it's not a distributed cache, and while it can pass messages it isn't a pub-sub system; use RabbitMQ or Kafka for volume. It's not a monitoring system either, just a good liveness check.

Among the Raft-based newer tools, which the source calls easier to implement than ZooKeeper's ZAB protocol: etcd (a key-value store; it backs Kubernetes), Consul (discovery plus configuration, many features) and Serf (a gossip membership protocol to build on). The source still calls ZooKeeper "the most reliable, crufty option", since it has had the longest time to shake out bugs. It suggests 3.4 for stability and notes that 3.5 added dynamic reconfiguration (changing ensemble members without a restart). That advice is dated: the 3.4 line is no longer maintained.

The source says ZooKeeper keeps its state in memory "to avoid" GC pauses. In-memory state is for speed, and a large heap makes pauses worse; that's one reason ZooKeeper keeps its data small. The source's load-balancer limitation reads "you don't have long-lived connections", which is the condition for using one; the limit is long-lived connections. Corrected here (our reading).
