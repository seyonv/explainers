Reinforcement learning for a coding agent

The group is the baseline.

You cannot tell a model how to write code you do not have. But you can run the tests. That one asymmetry is the entire reason reinforcement learning works on code — and one line of arithmetic is the reason it fits on a single GPU.

This page explains the whole mechanism from zero, then hands you a repository that runs it. No prior RL needed. The thing to hold onto, from here to the end, is drawn to the right: reinforcement learning does not ask “was this answer good?” It asks “was this answer better than the others I just tried?”

The opportunity

Why code is the perfect thing to train this way

Ordinary fine-tuning is imitation. You need the right answer for every example: here is the input, here is the output, copy it. That works right up until you do not have the answers.

Code is different, and the difference is worth being precise about. For most hard programming problems you cannot write down the solution — but you can recognise one instantly, because you can execute it against tests. Verifying is cheap; producing is expensive.

Reinforcement learning is the technique that converts a cheap verifier into a better generator. You never tell the model what to write. You let it write, then tell it how that attempt compared to its other attempts.

So the loop is short enough to state completely:

  1. 1Sample a group. Ask the model the same question eight times. Because we sample rather than take the most likely token, it answers differently each time. Those differences are the raw material — without them there is nothing to learn from.
  2. 2Score each answer. Run the unit tests. Three assertions pass out of three, or two, or none. No human, no labels, no judgment model.
  3. 3Compare within the group. Subtract the group's mean from each score. Answers that beat their peers get a positive number; answers that trailed get a negative one. This number is called the advantage.
  4. 4Nudge the weights. Make the tokens in the positive answers slightly more likely, and the tokens in the negative ones slightly less. Then do it all again, a few hundred times.
The starting point

One task, one model, one number

Everything in this section was measured on a laptop — an M3 MacBook, no GPU, eleven minutes. None of it is cited or illustrative.

The task is MBPP problem #17, and this is all of it:

Write a function to find the perimeter of a square.

assert square_perimeter(10) == 40
assert square_perimeter(5)  == 20
assert square_perimeter(4)  == 16

An English sentence and three assertions. Two properties make it the right thing to learn on: correctness is decidable — no human, no judge model, you run the code — and it is graded, because a function can pass one assertion or two. That second property turns out to matter more than anything else on this page.

The model is Qwen3-0.6B. The harness is a two-turn agent: write a function, run the assertions, read which ones failed, write a corrected function.

The number, over 100 problems:

solve rate      22.0%   (22/100, 95% CI 13.9%-30.1%)
assert rate     26.0%   (78/300 individual assertions)
solved turn 1  16
turn-2 rescues  6   (failed first, fixed after seeing the error)

Twenty-two out of a hundred problems a developer would call easy. Two details in that output are worth more than the headline. The confidence interval is 13.9–30.1%, so any improvement claimed later has to clear that band or it has shown nothing. And six of the twenty-two solves were turn-2 rescues — over a quarter of everything the agent got right came from reading its own error message and trying again. The loop is not decoration.

# MBPP #20 — "check if the given number is woodball or not"

That code is wrong. But it is not nothing — it parses, it has the right name and signature, and it gets one case right. A model that writes this is closer to correct than one that writes gibberish, and a graded reward can tell the difference. Everything that follows depends on that.

The algorithm

What the “G” in GRPO is for

Step 3 says “better than average.” Average of what? This is the question the algorithm exists to answer, and it is worth seeing the older answer first to appreciate the newer one.

PPO, the classical approach, trains a second neural network — a “value model” whose only job is to predict the score you are about to get. Then “better than expected” means “better than that network predicted.” It works. It also means a second set of weights to hold in memory, train, and debug.

GRPO — Group Relative Policy Optimisation — makes the substitution that seems obvious once stated: if you already sampled eight answers to this question, you already know what average looks like for this question. Just use the mean of the group.

Written out, the substitution is a single line — and this line is genuinely the whole idea:

# minisuey/grpo.py
advantage_i = (reward_i - mean(group)) / std(group)

Dividing by the spread is a convenience rather than a principle: it makes the size of the update independent of your reward's scale, so switching from a 0–1 reward to a 0–100 one does not silently retune your learning rate.

The trap

The failure that quietly wastes most first runs

Look at that line once more, and ask what happens when every answer in the group scores the same.

The numerator becomes zero. For all eight. Every advantage is zero, so every gradient is zero, so the weights do not move. Not “learn slowly” — do not move at all.

Nothing warns you. Your loss prints. Your run completes. Your GPU bill arrives. Your model is bit-for-bit the one you started with. This is why the repository ships a headroom command that refuses to start training when the groups do not disagree.

Our own measurement predicts exactly where this will bite. Seventy of the hundred problems scored zero, so for those, eight attempts will often be eight zeros. But thirty carry a spread — comfortably above the one-in-five floor the repository's headroom check enforces. And note what the graded reward buys: those eight partial-credit problems would collapse into the seventy under a pass/fail reward, dropping the usable signal from 30% of problems to 22%.

This is not a beginner's mistake that serious labs have outgrown. Meta hit exactly this in SWE-RL, and were unusually candid about it. They tried scoring a patch by exact match against the human's patch, and report that the average reward stayed at approximately zero for the entire training run — real pull requests are too varied to ever match exactly. They were running on 512 H100s. More compute does not fix this. A continuous reward does.

You can run the failure in ten seconds

The repository includes both rewards on the same toy task, so this is something you watch rather than something you take on faith. These are real measured runs:

Eight times as many wasted steps, from changing one line of the reward. On a real run that is 40% of your budget producing no gradient at all.

The reward

The reward is the entire specification

Everything else — the trainer, the model, the GPU — is machinery for climbing whatever hill your reward defines. Which means a badly-shaped reward does not produce an error. It produces a model that is excellent at the wrong thing.

Here is a small, true story from building the demo in this repository. The toy task asks a policy to fill in def f(x): return x _ _ so three assertions pass. I wrote it believing exactly one of the sixteen options was correct: x * 2.

It is not. x + x is also correct, and on most random seeds the policy finds that one first. Nobody told it about the second solution. The reward said “make the assertions pass”, so it made the assertions pass.

That is the power and the danger in the same mechanism. A reward specifies the goal, never the method — so the same process that finds a solution you did not think of will just as happily find a loophole you did not think of. The published literature is full of the loophole version: in one MBPP study, adding a code-style component to the reward made the model measurably worse at writing working code, because style was easier to optimise than correctness.

Two ways to score a patch

SWE-RL's actual reward is worth understanding, because it makes a tradeoff most people never consider. It never runs the code at all.

 Execution rewardSimilarity reward — SWE-RL
How it scoresRun the unit tests, count passes Textual similarity between your patch and the human's patch
Cost per score~20–40 msmicroseconds

Building a working test environment for 11 million repositories at arbitrary historical commits is not an engineering problem you solve; it is one you avoid. That is why SWE-RL scaled. The cost is real though, and the repository has a test that demonstrates it precisely: a genuinely correct solution, written differently from the reference, scores 1.0 on execution and under 0.75 on similarity.

The agent

Making it an agent, without making it impossible

So far the model writes code once. An agent acts, observes a real consequence, and acts again on what it saw. Our agent does exactly that, and stops there:

# minisuey/agent.py
turn 1  read the problem  →  write a function
        run the assertions
turn 2  read which ones failed  →  write a corrected function

Two turns is a deliberate choice, not an unfinished one. A real coding agent runs until it decides it is done — mini-swe-agent averages about 33 model calls per SWE-bench instance. Training that costs roughly 5–10× the engineering and 10–100× the compute per gradient step, and needs a model that already solves the task around 30% of the time before there is any signal at all. Small open models sit at 5–10% on real SWE-bench — below the floor.

Two turns keeps what makes an agent an agent, while the trajectory stays a single flat sequence with exactly one observation in the middle. That means it trains with the same machinery as ordinary single-turn generation. Raise the limit when you have a bigger model and a bigger budget; nothing else has to change.

Measurement

Making the improvement believable

The entire claim is “this number went up”, which is worth nothing unless the number is measured honestly. Two decisions carry most of that weight.

Why 500 problems, and not SWE-bench

SWE-bench is the benchmark everyone quotes, and it is the wrong instrument here. At 50 instances, one problem is two percentage points — so a “+4 point improvement” is two problems, indistinguishable from luck. A random 50 is also about 46% django and about 91% tasks a developer would fix in under an hour. The full 500 costs roughly $24–480 per evaluation pass and needs per-instance Docker images.

MBPP's test split is 500 problems that verify in about 1–5 ms each, for free. Same statistical resolution, none of the cost.

Confidence intervals, printed by default

Every number the repository reports comes with a 95% interval, and the comparison refuses to call an overlapping difference a win:

# the honest version of a result
BEFORE RL   27.3%  (137/500, 95% CI 23.4%-31.2%)
AFTER  RL   41.7%  (208/500, 95% CI 37.4%-46.0%)
CHANGE     +14.4%  (+71 problems)

The 95% confidence intervals do not overlap. This is a real effect.

Those figures are the published result this repository is shaped after — Qwen3-0.6B on MBPP with GRPO and LoRA, on a single RTX 3090. Your run produces your own numbers.

Running it

Four commands

Start with the one that costs nothing and needs no GPU, no account, and no model download:

make demo

Ten seconds. A policy goes from writing correct code 5.6% of the time to 81.5%. There is no neural network in it — but the reward genuinely executes code in the real sandbox, and the advantage is computed by the same function the GPU run calls. It exists so the idea moves in front of you before you spend anything.

Then the real thing, on a rented GPU:

pip install modal && modal setup
modal run train/modal_app.py

That measures the model, trains it with GRPO, measures it again on the same problems, and prints the difference. Modal gives every account $30/month in free credits and an H100 is about $3.95/hour, so the first run is free.

On the SWE-RL repository itself

facebookresearch/swe-rl is what prompted this project, and it is worth being clear about what it contains. Released: the reward function, the prompts, and an “Agentless Mini” repair pipeline. Not released: the trainer, the training data, the hyperparameters, or the weights. It is CC BY-NC 4.0, so the similarity reward in this repository is a clean reimplementation from the paper's equation rather than a copy.

It also trained on 512 H100s for about 32 hours — roughly 16,000 GPU-hours. You are not going to reproduce that, and this repository does not pretend to. What it does is take the idea and shrink it about four orders of magnitude, until it fits inside free credits and a page you can read in one sitting.

Going deeper

The reading list, and a cross-check

Everything above is implemented in the repository, but none of it is original to it. Three places are worth reading next, all runnable and all permissively licensed.

The maths here was checked against a reference implementation

Nathan Lambert's RLHF book ships a full training codebase under MIT — one loss.py with real implementations of GRPO, PPO, DAPO, GSPO and CISPO, plus ten ready configs. It is oddly hard to find: no lecture in the course links to it.

Cross-checking this repository against it produced exact agreement — the same masked_mean, the same min(unclipped, clipped), and the same asymmetric clip bounds. Their dapo.yaml independently sets clip_eps_hi: 0.28, beta: 0.0 and num_rollouts: 8 — the same three defaults chosen here, arrived at separately.

It also surfaced something this page had left unsaid. There are three defensible ways to average per-token losses into one number, and they disagree about what counts as a sample:

StrategyDivides byConsequence
Token-leveltotal tokens Long answers contribute more gradient. Used here.
Sequence-leveltokens per answer, then average Original GRPO. Introduces a length bias: a token in a 50-token answer outweighs one in a 500-token answer.
Fixed-lengtha constant Lmax The Dr. GRPO / DAPO fix. Safest when lengths vary.

Capping the agent at two turns makes this nearly moot — every trajectory is about the same length, so all three coincide. Raise the turn limit and it starts to matter. That is the kind of thing you only notice by reading someone else's implementation next to your own.
