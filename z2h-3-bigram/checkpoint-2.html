Checkpoint 2: two routes to the same model

Ties together negative log likelihood, smoothing, one-hot and a linear layer, the softmax and training the neural bigram, with micrograd's training loop and neuron and the toolkit's softmax and cross-entropy. Lecture 2 · 0:50:14 to 1:56:16

Prime · why this checkpoint, why now

The lecture has just built the same bigram model twice. Counting read the probabilities straight off the data; the neural net learned them by gradient descent on the same loss, and landed in the same place. Every later lecture keeps the second route and changes only how the logits are computed, so this is the moment to make sure you can say why the two routes agree, where they differ, and what each knob in one route corresponds to in the other.

  • NLL → one number both routes are judged by: counting gets 2.4540, the floor for this model.
  • Smoothing → +k fake counts: finite loss on unseen pairs, at a small cost in training loss (2.4546 at +1).
  • One-hot @ W → picks row xs[i] of W: a table lookup, like reading a row of N. Karpathy calls it "the dumbest, smallest, simplest neural net" (1:13:53).
  • Softmax → logits as log-counts: exp, then normalise each row exactly as counting did.
  • Training → micrograd's forward / zero-grad / backward / update loop on a 27×27 tensor: 3.7590 → 2.4729 in 100 steps.

1 · Mixed retrieval

  1. At random init the net scores 3.7693 on "emma", worse than the 3.2958 you'd get by guessing 1/27 for every character. Walk through why, and give the W that scores exactly 3.2958.
    Check
    • random logits aren't neutral: after exp and normalising they put large probabilities on arbitrary characters (row '.' gives 'o' 0.2378)
    • so the true next characters mostly get less than 1/27 ('e' after '.' gets 0.0123), and −log of those is above 3.2958
    • W = 0 makes every logit 0, every count e⁰ = 1 and every row uniform, so the loss is log 27 = 3.2958

    Missed it? Reopen the softmax, "Row 0, stage by stage", and the toolkit's softmax and cross-entropy, "Scale stretches it, shift does nothing".

  2. which idea?You try two things separately: an enormous regularisation strength instead of 0.01, and +100,000 fake counts on N. Both losses head toward the same number. Which number, and which single idea makes these two knobs the same knob?
    Check
    • both approach uniform guessing, log 27 = 3.2958 (+100,000 fake counts already gives 3.2837)
    • fake counts swamp the real counts, so every row flattens toward 1/27
    • the L2 term pulls W toward 0, and W = 0 means all logits 0, so all rows uniform
    • so the penalty strength plays the part of k; only the penalty carries over to networks where there are no counts to add to

    Missed it? Reopen smoothing, "Turning the knob", and training, "Note 2: regularisation is smoothing".

  3. debugSame seed, lr 50, all 228,146 bigrams. Your loop prints 3.7590, 3.3711, 3.0128, 2.8858, 2.8373 for steps 0 to 4, then the loss turns round: 2.8987 at step 5 and 3.2032 at step 99. What did you leave out, and why does it first work and then fail?
    Check
    • the gradient reset, W.grad = None
    • backward() adds into .grad, so without the reset each update uses the sum of all past gradients
    • step 1 is correct because the first gradient was fresh; after that the steps keep growing and overshoot, so the loss climbs back toward uniform (computed: lowest 2.8373 at step 4)
    • it's the same bug as micrograd's forgotten zero_grad, and the same += that made reused nodes work there

    Missed it? Reopen micrograd's training loop, "Forgetting zero_grad", and training, "One training step".

  4. The layer is one_hot(xs) @ W, with no bias and no tanh, unlike micrograd's neuron. Explain why it can still represent exactly what the count table represents.
    Check
    • a one-hot row has a single 1, so the matmul copies row xs[i] of W: every character gets its own free row of 27 logits
    • a softmax over a free row can produce any distribution with no exact zeros, the same freedom a row of P has
    • so W can hold log-counts: W = log(N + 1) scores 2.4546, the smoothed counting loss exactly (computed)
    • a bias would only add the same number to every row's logits per column; tanh would squash the logits to [−1, 1] and limit how peaked a row can be

    Missed it? Reopen one-hot and a linear layer, "Isn't multiplying by 26 zeros wasteful?", and training, "Note 1: one-hot @ W just picks a row".

  5. which idea?A validation name contains jq, a pair that never occurs in names.txt. The unsmoothed counting model scores it inf. What does the trained net give, and which design choice guarantees that?
    Check
    • a finite (large) loss: exp is never exactly 0, so the softmax gives every character some probability
    • counting gives an exact 0 for an unseen pair, and log 0 = −∞
    • the counting fix is fake counts: with +1, P[j, q] = 1 / 2,927 = 0.000342 and "andrejq" scores 3.4834

    Missed it? Reopen the softmax, "Why exp, and not something simpler", and smoothing, "Where the infinity comes from".

  6. After 200 steps with no regularisation, the net's probabilities are within 0.01 of the smoothed counts in 676 of 729 cells. The biggest gap is q. (0.0485), and P[qu] is 0.6720 for the net against 0.6923 for counting. Why is it the q row that lags?
    Check
    • row q of W only gets gradient from examples whose current character is q
    • q starts only 272 of the 228,146 bigrams, so the loss (an average over all of them) barely depends on that row: at step 0 its gradient is about 74× smaller than row '.''s
    • smaller gradient, same learning rate: smaller steps, slower convergence. Counting has no such problem; it reads row q straight off the data
    • rare rows are also where fake counts change the most (9.0% of the q row at +1)

    Missed it? Reopen training, the table under "Note 1", and smoothing, "Who pays for the fake counts".

  7. In the full loop, someone writes probs = counts / counts.sum(1), dropping keepdims. On the count table the same slip ran silently and divided columns. What happens here, and why the difference?
    Check
    • it raises an error: The size of tensor a (27) must match the size of tensor b (228146) at non-singleton dimension 1 (computed)
    • shapes line up from the right: 27 against 228,146, and neither is 1
    • the counting version only ran because N is square, so (27,) fit as a row

    Missed it? Reopen the keepdim trap, "Why did the bug look so plausible?".

  8. which idea?A teammate says: "the net reached 2.4624 after 200 steps. Train it for 10,000 and it'll beat counting's 2.4540." Which idea says it can't, and what change would let a model score lower on these names?
    Check
    • both models see only the previous character, and the normalised counts are the probabilities that maximise the likelihood of the training bigrams
    • so 2.4540 is the floor for any bigram model on this data; gradient descent can only approach it from above
    • to go lower, give the model more context: a trigram (exercise E01) or the MLP of the next lecture. That's the whole point of the neural route: counting tables grow 27× per extra character

    Missed it? Reopen training, "So is the neural net better than counting?", and negative log likelihood, "Is 2.4540 good?".

3 · Build: train the bigram both ways and show they agree

runs on your M3 · about 4 s

What it reinforces: fake counts (smoothing), one-hot as a row lookup (one-hot), logits as log-counts (softmax), the loss both routes share (NLL) and the training loop (training, micrograd's loop). It also does exercises E04 (index W instead of one-hot) and E05 (F.cross_entropy) from the video description.

  1. Data. Build xs, ys for all 228,146 bigrams and count N.
  2. Route 1, counting. P = (N + 1) normalised by rows; score it with -P[xs, ys].log().mean().
  3. Counts inside the net. Set W = (N + 1).float().log() and score F.cross_entropy(W[xs], ys). You should get the same number: W holds log-counts.
  4. Route 2, gradient descent. Start from torch.randn W (seed 2147483647, requires_grad=True). Each step: logits = W[xs], F.cross_entropy, W.grad = None, backward(), W.data += -50 * W.grad. No regularisation. Run 200 steps and print steps 0, 99 and 199.
  5. Compare the tables. Q = W.softmax(1) against P: the number of cells within 0.01, the largest gap and where it is, and qu in both.
  6. Break it. Delete W.grad = None, rerun 100 steps and watch the loss turn round (question 3).
P = (N + 1).float(); P /= P.sum(1, keepdim=True)
print('counting: %.4f' % -P[xs, ys].log().mean())
print('log-counts: %.4f' % F.cross_entropy(
    (N + 1).float().log()[xs], ys))
g = torch.Generator().manual_seed(2147483647)
W = torch.randn((27, 27), generator=g, requires_grad=True)
for k in range(200):
    loss = F.cross_entropy(W[xs], ys)   # E04 + E05
    W.grad = None
    loss.backward()
    W.data += -50 * W.grad
d = (W.detach().softmax(1) - P).abs()
print('within 0.01:', (d < 0.01).sum().item())
Done when: counting and log-counts both print 2.4546; the net prints 3.7590 at step 0, 2.4729 at step 99 and 2.4624 at step 199 (the same as labs/train-neural-bigram.py without regularisation); 676 of 729 cells are within 0.01, the largest gap is q. at 0.0485, and qu is 0.6720 (net) vs 0.6923 (counting); without the reset the loss bottoms out at 2.8373 (step 4) and reaches 3.2032 at step 99. Measured in the checkpoint's scratch run on the M3 (3.9 s).
