Gradient descent finds the counting answer

Also called: training the neural bigram, gradient-based optimisation of the NLL, maximum likelihood by gradient descent. Lecture 2 · vectorized loss, backward and update, putting everything together · 1:35:49

Prime · 2 minutes before you read

The problem: Counting bigrams gives the best model for one character of context, but the table needs a row for every possible context and can't grow. Without a way to learn the probabilities from the loss, there is no route to models that look further back.

Where it fits: This closes lecture 2. The softmax card turned one_hot(xs) @ W into probabilities and a loss of 3.7693 on 'emma'; micrograd gave you the forward / zero-grad / backward / update loop. This card runs that loop on all 228,146 bigrams.

Repeat. After 100 steps the loss is 2.4729, closing in on the 2.4540 that counting gets in one pass, because the net and the count table are the same model reached by two routes.

Predict first: counting scores 2.4540 on the training names. The net starts at 3.7590. Train it for as long as you like: will it end up below 2.4540?

No. It gets to 2.4729 after 100 steps and 2.4624 after 200 (measured), and can only creep toward 2.4540 from above. Both models see exactly one previous character, and the normalised counts are already the probabilities that minimise NLL on this data. Gradient descent can find that answer, but it can't beat it.

One training step

A gradient is, for each weight, how much the loss would rise if that weight went up a little. W.grad has the same 27×27 shape as W. Stepping against it (-50 * W.grad, where 50 is the learning rate) lowers the loss. This is the micrograd loop from lecture 1: forward pass, zero the gradients (W.grad = None), backward(), update. The only new things are that the parameters are a tensor and the loss is vectorised.

Note 1: one-hot @ W just picks a row, so W is the log-counts

A one-hot vector has a single 1, so multiplying it by W copies out one row: one_hot(5) @ W is W[5], the logits for "what follows e". That's a table lookup, exactly like reading row e of N. The softmax then exponentiates and normalises, so W plays the role of log(counts). Set W = log(N+1) by hand and the net's loss is 2.4546, the smoothed counting loss to four decimals (computed). Gradient descent is walking toward that matrix.

Note 2: regularisation is smoothing

If every weight is 0, every logit is 0, every exp is 1, and each row becomes uniform: loss log 27 = 3.2958 (computed). So pulling W toward zero pulls the model toward uniform, which is what adding fake counts did. The extra term 0.01*(W**2).mean() is L2 regularisation: it grows as weights move away from zero, so it acts like a spring. Its strength (0.01) is the knob that fake counts (+1, +10, …) were on the smoothing card.

at step 0: mean(W²) = 0.9665 → 0.01 × 0.9665 = 0.0097 data 3.75895 + reg 0.00967 = 3.76862 → prints 3.7686 at step 99: data 2.4750 + reg 0.0152 = 2.4901

Computed with the lab's seed. The regularised net pays a little data loss (2.4750 vs 2.4729) to keep its weights small.

Sampling from the net

▶ Build itruns on your M3 · about 8 s

When: pause the video at 1:42:55 ("putting everything together") and type this before watching on. Reuse words, stoi and itos from your counting code; build xs, ys over every word, not just "emma".

xs, ys = [], []
for w in words:
    chs = ['.'] + list(w) + ['.']
    for ch1, ch2 in zip(chs, chs[1:]):
        xs.append(stoi[ch1]); ys.append(stoi[ch2])
xs, ys = torch.tensor(xs), torch.tensor(ys)
num = xs.nelement()                  # 228146
g = torch.Generator().manual_seed(2147483647)
W = torch.randn((27, 27), generator=g, requires_grad=True)
for k in range(100):
    xenc = F.one_hot(xs, num_classes=27).float()
    logits = xenc @ W                   # log-counts
    counts = logits.exp()               # like N
    probs = counts / counts.sum(1, keepdims=True)
    loss = -probs[torch.arange(num), ys].log().mean()
    loss = loss + 0.01*(W**2).mean()   # regularisation
    if k in (0, 1, 9, 49, 99):
        print(f'step {k}: loss {loss.item():.4f}')
    W.grad = None                       # zero the gradient
    loss.backward()
    W.data += -50 * W.grad
g = torch.Generator().manual_seed(2147483647)
names = []
for i in range(5):
    out, ix = [], 0
    while True:
        xenc = F.one_hot(torch.tensor([ix]), num_classes=27).float()
        counts = (xenc @ W).exp()
        p = counts / counts.sum(1, keepdims=True)
        ix = torch.multinomial(p, num_samples=1, replacement=True,
                               generator=g).item()
        out.append(itos[ix])
        if ix == 0: break
    names.append(''.join(out))
print('neural net samples:', names)

Why it beats the alternatives

✗ Keep counting

Exact and instant for one character of context. But the table needs a row per possible context: 27 rows for one character, 729 for two, 19,683 for three (27k, computed), and most rows would be almost empty.

✗ Guess and check weights

Try random seeds and keep the best. Karpathy calls it "amateur hour" (1:26:17): with 729 weights there's no way to know which direction helps.

✗ Mean squared error

MSE is for predicting a number (regression). Here the output is a probability distribution over 27 classes, and the loss that matches maximum likelihood is the NLL.

✓ Gradient descent on the NLL

The gradient says which way to move all 729 weights at once. It lands on the counting answer here, and the same loop keeps working when the logits come from a bigger network with more context.

So is the neural net better than counting?

Not for bigrams. Counting is exact, takes one pass instead of 100 and has no learning rate to tune. The net matches it at best (2.4729 vs 2.4540 on the training set), and rare rows like q still lag after 200 steps. If your model really is "one previous character", count.

The payoff is flexibility. From here on, the only thing that changes is how the logits are computed: an MLP over several characters (makemore part 2), then a transformer. The loss, backward() and the update stay exactly as they are on this card.

Understand and remember

  • the net sees only the previous character, like the count table → the normalised counts already maximise the likelihood on this data → gradient descent can only approach 2.4540 from above (2.4729 at 100 steps), never beat it
  • one-hot row × W = one row of W → logits are a table lookup → softmax exponentiates and normalises that row → W becomes log-counts (W = log(N+1) gives exactly 2.4546)
  • W = 0 → all logits 0 → all counts 1 → uniform probabilities → so an L2 penalty that pulls W toward 0 pulls the model toward uniform → its strength is the fake-count knob
  • each row's gradient comes only from examples that start with that character → rare rows (q: 272 of 228,146) get tiny gradients → they converge slowly (P[qu] 0.3548 at 100 steps vs 0.6923 from counting)
  • detail that matters F.one_hot builds a 228,146×27 float matrix every step just to select rows → indexing W[xs] gives identical losses without the matrix (exercise E04)
  • detail that matters the loss is averaged over all 228,146 examples → every step is one full pass over the data → a high learning rate (50) is affordable because the gradient is exact, not a noisy minibatch estimate

Reference only

  • seed 2147483647 for torch.Generator().manual_seed
  • W.grad = None vs zeroing (None is cheaper)
  • W.data += -lr * W.grad update syntax
  • probs[torch.arange(num), ys] fancy indexing
  • keepdims=True in the row sum
  • regularisation coefficient 0.01 and learning rate 50
