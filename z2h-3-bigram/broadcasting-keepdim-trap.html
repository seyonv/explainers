Broadcasting and the keepdim trap

Also called: broadcasting semantics, keepdim / keepdims, vectorised row normalisation. Lecture 2 · efficiency! vectorized normalization of the rows, tensor broadcasting · 0:36:17

Prime · 2 minutes before you read

The problem: Sampling needs every row of the count table as a probability distribution. Dividing row by row in Python is slow and repetitive, and the one-line tensor version has a trap: drop one argument and it quietly divides the wrong axis, with no error.

Where it fits: The counting cards built the 27×27 table N, and the sampling card normalised one row at a time. This card normalises all rows at once using the broadcasting rules from the toolkit. The loss and softmax cards reuse the same sum(1, keepdim=True) pattern.

  3. Which property of the square 27×27 table lets the buggy version run without an error, and what would happen to a (5, 27) tensor instead?

  5. When is in-place /= safe here, and when would PyTorch refuse it?

In one breath: to turn the 27×27 count table into probabilities, every row must be divided by its own total. P /= P.sum(1, keepdim=True) does all 27 rows in one line: the totals come out as a (27, 1) column, and broadcasting stretches that column across all 27 columns. Leave out keepdim and the totals have shape (27,), which PyTorch reads as a (1, 27) row. The code still runs with no error, but it divides the columns, and row 0 sums to 7.02 instead of 1.

Predict first: P / P.sum(1) (no keepdim) runs without complaint. What does row 0, the "which letter starts a name" row, add up to: 1, about 7, or an error?

About 7: it's 7.0225. No error, because a length-27 vector fits a 27×27 matrix once it is treated as a row. Each column j gets divided by row j's total, so row 0 becomes a sum of 27 unrelated ratios. What does sum to 1 now is every column (column 0 sums to 1.0000).

Where the 27 totals get stretched

keepdim=True no keepdim P 27 × 27 P 27 × 27 P.sum(1, keepdim) 27 × 1 P.sum(1) 27 → read as 1 × 27 result 27 × 27 ✓ rows result 27 × 27 ✗ columns

The rule: line shapes up from the right. Each pair must be equal, or one of them 1, or one missing (a missing axis counts as 1, added on the left). Both versions pass the rule, so neither raises an error.

P = N.float()
sh = lambda t: tuple(t.shape)
print('P.sum(0, keepdim=True).shape:', sh(P.sum(0, keepdim=True)))
print('P.sum(1, keepdim=True).shape:', sh(P.sum(1, keepdim=True)))
print('P.sum(1).shape:', sh(P.sum(1)))
print('P.sum().shape:', sh(P.sum()))
good = P / P.sum(1, keepdim=True)   # (27,27) / (27,1)
bad = P / P.sum(1)                  # (27,27) / (27,) -> (1,27)
print('correct: P[0].sum() = %.4f' % good[0].sum())
print('bug:     P[0].sum() = %.4f' % bad[0].sum())
print('bug:     P[:, 0].sum() = %.4f' % bad[:, 0].sum())
P /= P.sum(1, keepdim=True)         # in place: no new tensor
print('in-place /= matches:', torch.equal(P, good))

Why it beats the alternatives

✗ Normalise inside the sampling loop

The sampling card rebuilt p = N[ix].float(); p = p / p.sum() on every draw. Correct, but it redoes the same division every time a row is visited.

✗ P / P.sum(1)

Runs, and looks like probabilities, but divides columns. Row 0 sums to 7.0225 and no row sums to 1. Nothing warns you.

✗ P / P.sum()

One scalar, 228,146. The whole table now sums to 1, but row 0 sums to 32,033 / 228,146 = 0.1404, so a row is not a next-character distribution.

✓ P /= P.sum(1, keepdim=True)

One vectorised operation, done once. Each row is divided by its own total, every row sums to 1, and the in-place /= reuses P's memory.

Why did the bug look so plausible?

Two coincidences hid it. P is square, so a length-27 vector fits either axis; on a (5, 27) tensor the same missing keepdim fails loudly with The size of tensor a (27) must match the size of tensor b (5) at non-singleton dimension 1. And in this data every character is followed exactly as often as it is preceded, so each row total equals its column total (N.sum(0) equals N.sum(1)). Dividing column j by row j's total therefore makes every column sum to exactly 1: a real-looking probability table, just the wrong way round.

When not to use in-place /=: on a tensor that needs gradients. PyTorch refuses it on a leaf with requires_grad=True, which is why the neural-net cards write counts / counts.sum(1, keepdims=True) out of place. And the habit to keep: print .shape after every reduction, or write keepdim=True by default.

Understand and remember

  • sum(1) collapses the column axis → one total per row → keepdim=True keeps that axis as size 1, giving (27, 1) → broadcasting stretches it across the 27 columns → each row is divided by its own total → every row sums to 1
  • No keepdim → shape (27,) → shapes align from the right, so the missing axis is added on the left → (1, 27) is stretched down the rows → column j is divided by row j's total → row 0 sums to 7.0225
  • P is square → a length-27 vector fits either axis → the broadcasting rule passes both ways → no error, just wrong numbers; a non-square tensor like (5, 27) ÷ (5,) raises a size-mismatch error instead
  • Every letter in names.txt is followed as often as it is preceded → each row total equals its column total → the bug makes every column sum to exactly 1 → the wrong table looks like a valid probability table
  • detail that matters Broadcasting stretches with a zero stride (the expanded sums have stride (1, 0)) → no 27×27 copy of the totals is made → the vectorised divide costs one pass over P
  • detail that matters In-place P /= … writes into P's existing memory → fine for plain data, but a leaf tensor with requires_grad=True refuses in-place ops → the neural-net cards divide out of place

Reference only

  • keepdims=True (Karpathy's notebook spelling) is an accepted alias of keepdim=True
  • P.sum() with no dim gives a 0-d tensor, shape ()
  • the exact error text: The size of tensor a (27) must match the size of tensor b (5) at non-singleton dimension 1
  • row totals: s0 = 32,033, sa = 33,885, sj = 2,900

5 · Predict commit to an answer before revealing

In the neural-net cards, counts has shape (5, 27): 5 examples, 27 characters. Someone writes probs = counts / counts.sum(1), leaving out keepdim. What happens this time: silently wrong columns, correct rows, or an error?

Reveal

An error. Right-aligning (5, 27) with (5,) puts 27 against 5 on the last axis; they aren't equal and neither is 1, so PyTorch raises The size of tensor a (27) must match the size of tensor b (5) at non-singleton dimension 1. The silent version on this card only happened because P is square.
