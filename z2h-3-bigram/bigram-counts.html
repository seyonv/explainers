Counting bigrams in a 27×27 tensor

Also called: the bigram count matrix N, "training" the counting model. Lecture 2 · counting bigrams in a 2D torch tensor ("training the model") · 0:12:45

Prime · 2 minutes before you read

The problem: A language model has to say which character is likely to come next. Before any neural net, you need somewhere to keep that knowledge, and a list of 32,033 names doesn't answer "what usually follows m?" by itself.

Where it fits: The names-dataset card turned each name into its bigrams (.e em mm ma a.). This card counts all 228,146 of them into one table, which the next cards turn into probabilities, samples and a loss.

In one breath: a bigram is a pair of neighbouring characters, like em in "emma". Pad every name with a '.' at both ends, walk all 32,033 names, and add 1 to cell N[first, second] of a 27×27 grid of integers for each pair. The finished grid is the whole model: row i says how often each character followed character i.

Predict first: once every name is counted, what do the '.' row N[0].sum() and the whole grid N.sum() add up to?

32,033 and 228,146. Row 0 counts "which letter comes after the start", and every name starts exactly once, so the row sums to the number of names. The whole grid holds one tick per bigram: each name of length L gives L + 1 pairs, and those add up to 228,146 over the dataset (the names-dataset card).

Step 1: count pairs in a dictionary

Karpathy starts with a plain Python dict whose keys are character pairs. He wraps each name in two special tokens, <S> (start) and <E> (end), so the model also learns which letters begin and end names. The dict ends up with 627 distinct pairs. The five most common ones (measured, and they match the notebook):

paircountwhat it says
('n', '<E>')6,763names often end in n
('a', '<E>')6,640…or in a
('a', 'n')5,438"an" is the top inner pair
('<S>', 'a')4,410a is the top first letter
('e', '<E>')3,983…or in e

A dict works, but you can't do arithmetic on a whole row at once, and the next card needs exactly that.

Step 2: the same counts in a tensor

A tensor is PyTorch's n-dimensional array. To use characters as row and column numbers you need two lookup tables: stoi ("string to integer") maps '.' → 0, a → 1, …, z → 26, and itos is its reverse. Karpathy's first try used 28 rows (26 letters plus <S> and <E>), but <E> never starts a pair and <S> never ends one, so a whole row and a whole column stay zero: 28 + 28 − 1 = 55 of 784 cells wasted. One '.' token doing both jobs gives the 27×27 grid.

Here is a 4×4 corner of the finished N (rows = first character, columns = the one that follows). The five cells 'emma' touched are green; row 0 is the "starts with" row and column 0 the "ends with" column:

N[0, 0] is 0 because no name is empty. 2,538 names start with m, and 516 end with it. Counted from names.txt with the course's common.py.

N[0].sum() = 32,033 one start per name N.sum() = 228,146 one tick per bigram nonzero = 627 of 27 × 27 = 729 cells (the same 627 pairs as the dict; 102 never occur)
▶ Build itruns on your M3 · about 2 s

When: watch through 0:20:54 (the single '.' token) and pause before 0:24:02 (sampling). Type this with names.txt next to it.

import torch
words = open('names.txt', 'r').read().splitlines()
chars = sorted(list(set(''.join(words))))      # the 26 letters
stoi = {s:i+1 for i,s in enumerate(chars)}; stoi['.'] = 0
itos = {i:s for s,i in stoi.items()}
N = torch.zeros((27, 27), dtype=torch.int32)  # default is float32
for w in words:
    chs = ['.'] + list(w) + ['.']
    for ch1, ch2 in zip(chs, chs[1:]):
        N[stoi[ch1], stoi[ch2]] += 1
print('N.shape, dtype:', tuple(N.shape), N.dtype)
print("N[stoi['e'], stoi['m']] (em):", N[stoi['e'], stoi['m']].item())
print('N[0].sum() (names):', N[0].sum().item())
print('N.sum() (bigrams):', N.sum().item())

You should see (measured on your M3):

Why it beats the alternatives

✗ A Python dict of pairs

Same 627 counts, but no shape: you can't sum, divide or sample a whole row in one call, and every lookup is a Python hash.

✗ 28×28 with <S> and <E>

Works, but the <E> row and <S> column can never be filled: 55 of 784 cells are always zero.

✗ Count longer contexts

Each extra character of context multiplies the table by 27. Trigrams need 27³ = 19,683 cells, and only 6,063 of them are ever seen in names.txt (computed). Counting doesn't scale.

✓ 27×27 int32 tensor with '.'

Every cell can be used, rows are real vectors, and the next cards turn each row into probabilities with one line of tensor math.

Is counting really "training"?

Yes, for this model. The counts are the parameters, and dividing each row by its sum (two cards on) gives exactly the probabilities that fit the data best. No gradient descent is needed. But N is not a probability table yet: it holds raw integer counts, and 102 of its cells are 0, which becomes a problem on the loss card.

The approach stops working as soon as you want more than one character of context, because the table grows 27× per character. That's why the course switches to a neural net that learns the same table (the last card in this course) and then to embeddings in makemore part 2.

Understand and remember

  • Pad each name with '.' on both sides → every name yields len + 1 pairs, including a start pair and an end pair → the one table learns first letters (row 0) and last letters (column 0) along with the inner pairs
  • Separate <S>/<E> tokens → <E> never starts a pair and <S> never ends one → a full row and column of dead cells (55 of 784) → one shared '.' at index 0 gives a dense 27×27 table
  • Counts stored as a tensor, not a dict → each row is a vector you can sum or divide in one call → the next cards can turn rows into probabilities and sample from them
  • The table is indexed by the whole context → each extra character of context multiplies it by 27 (27² = 729, 27³ = 19,683) → most cells are never seen → counting can't scale, which motivates the neural net
  • detail that matters torch.zeros defaults to float32 → counts are stored as dtype=torch.int32 so they stay exact integers; indexing returns a 0-d tensor → use .item() to get a Python int

Why this step?

5 · Predict commit to an answer before revealing

Before checking: does the sum of the m row equal the sum of the m column? What would each of those sums count, and would the answer change in the 28×28 <S>/<E> version?

Reveal

They are equal: both are 6,642, the number of times m appears in the dataset. Every letter has exactly one character after it (row) and one before it (column), because the padding guarantees a neighbour on both sides. For letters this holds in the 28×28 version too; only the special tokens differ, since <S> has a row but no column and <E> the reverse. With one '.', row 0 and column 0 both sum to 32,033.
