You've now built the whole counting model: names become pairs, pairs become a 27×27 table N, rows of N become probabilities P, P makes names, and one number (2.4540) says how good P is. At 1:02:57 the lecture keeps every one of those pieces and changes only where P comes from. If a link below is loose now, it'll be loose in the neural half too.

1 · Mixed retrieval

  1. Explain why N[0].sum() is 32,033 but N.sum() is 228,146. Say what each number counts in terms of the names file, and split 228,146 into two parts.
    Check
    • row 0 is "what comes after the start": every name starts exactly once, so it sums to the number of names
    • the whole table holds one tick per bigram; a name of length L gives L + 1 of them once it's padded with '.' at both ends
    • 228,146 = 196,113 letters (each is the "next" of one example) + 32,033 endings (one '.' per name)

    Missed it? Reopen the dataset, "Counting every example in the file", and counting bigrams, "Step 2: the same counts in a tensor".

  2. which idea?You wrote P = N.float() / N.float().sum(1), without keepdim. Your average NLL on all words prints 2.4540, exactly the correct table's score. But 1,000 names sampled from this table average 23.29 letters instead of 6.31. Which idea explains why the loss missed the bug, and why did the samples catch it?
    Check
    • without keepdim the totals are read as a (1, 27) row, so N[i, j] is divided by row j's total instead of row i's
    • every character is followed exactly as often as it is preceded, so row totals equal column totals (N.sum(0) equals N.sum(1))
    • over all 228,146 bigrams, the logs of the wrong divisors (one per next character) add up to the same total as the logs of the right ones (one per current character), because each character fills both roles equally often. So the log likelihood is identical: 2.454014 both ways in float64 (computed)
    • sampling reads one row at a time, and the buggy rows aren't next-character distributions (row 0 sums to 7.0225), so the names come out wrong: 23.29 letters on average, only 19 one-letter names (computed)
    • lesson: a matching loss doesn't prove the table is right; check P.sum(1) directly

    Missed it? Reopen the keepdim trap, "Why did the bug look so plausible?", and reading the count matrix, "The '.' row and the '.' column" (rows balance columns).

  3. Someone reports your model's quality as its likelihood, the product of the probabilities it gives to all 228,146 real bigrams. What will they print, and which three steps turn the product into a number you can compare between models?
    Check
    • they print 0.0, even in float64: the product underflows (for "emma" alone it's already 3.48 × 10⁻⁶)
    • take logs, which turns the product into a sum that can be stored
    • negate, so lower is better and 0 means certainty
    • divide by n, so it's per bigram and comparable across data sizes: 2.4540, against log 27 = 3.2958 for uniform guessing

    Missed it? Reopen negative log likelihood, "Score one word, bigram by bigram", and the toolkit's exp and log, "Why the product breaks: underflow".

  4. which idea?A colleague looks at the Blues heatmap of N and says every white-looking cell is a pair the model can never produce. Which idea corrects them, and how do you get the real list?
    Check
    • the colour scale is linear up to 6,763, so a count of 14 (eq) looks as white as 0
    • only exact zeros are impossible: (N == 0).sum() gives 102 of 729, and 43 more cells hold exactly 1
    • those 102 cells get probability 0: they can never be sampled, and scoring one gives an infinite loss

    Missed it? Reopen reading the count matrix, "Is a pale cell a rare pair?".

  5. debugYour average NLL prints nan, not a number near 2.45. You counted with for ch1, ch2 in zip(w, w[1:]), then scored with chs = ['.'] + list(w) + ['.']. What's wrong, which part of P goes bad first, and why is it nan rather than inf?
    Check
    • counting without the '.' padding never records a start or an end, so row 0 and column 0 of N are all zero (154 zero cells instead of 102)
    • row 0's total is 0, so normalising gives 0 / 0 = nan for the whole row (P[0, 1] prints nan; computed)
    • every name's first bigram (.e, .o, …) reads row 0, so the average is nan
    • a single zero cell in a row with a nonzero total gives p = 0 and inf; a whole empty row gives nan
    • fix: pad the same way when counting and when scoring

    Missed it? Reopen the dataset, "One word, five examples", and negative log likelihood, "One zero ruins it: andrej vs andrejq".

  6. which idea?To get "the best" names, you change the sampler to always take the most likely next character. What comes out, and which idea from the toolkit is the fix?
    Check
    • only a., every time: row '.' peaks at a (0.1377) and row a peaks at '.' (0.196), so the loop stops after one letter
    • the fix is to draw each character in proportion to its probability (torch.multinomial, i.e. sampling by cumulative sum), so rare continuations still happen sometimes
    • with sampling, names vary and keep the data's statistics: mean length 6.31 against the real 6.12

    Missed it? Reopen sampling, "Why it beats the alternatives", and the toolkit's probability distributions, "Sampling by cumulative sum".

  7. P / P.sum(1) runs silently on the 27×27 table. In the neural half, the same mistake on a (228,146, 27) tensor of counts fails straight away. Walk through the broadcasting rule for both and say why one fails and the other doesn't.
    Check
    • line the shapes up from the right; each pair must be equal, or 1, or missing
    • (27, 27) with (27,): 27 against 27 matches, and the missing axis counts as 1, so (1, 27) is stretched down the rows: legal, but it divides columns
    • (228146, 27) with (228146,): 27 against 228,146 on the last axis, neither is 1, so PyTorch raises The size of tensor a (27) must match the size of tensor b (228146) at non-singleton dimension 1 (computed)
    • the square table is the only reason the counting bug was silent

    Missed it? Reopen the keepdim trap, "Where the 27 totals get stretched", and the toolkit's broadcasting rules, "The two rules".

  8. Sample 1,000 names from P and score them with P's own average NLL. Then do the same with 1,000 names from the uniform sampler. Predict both numbers roughly before opening the Check: near 2.45, far below, or far above?
    Check
    • bigram samples: 2.4460, close to the 2.4540 of the real names, because they follow the same transition statistics that P was counted from (the small gap is noise from 1,000 names; computed)
    • uniform samples: inf. 3,891 of their 26,998 bigrams land on one of the 102 zero cells, and 785 of the 1,000 names contain at least one (computed)
    • one impossible pair makes the whole average infinite, which is exactly the problem the next card, smoothing, fixes

    Missed it? Reopen negative log likelihood, "One zero ruins it: andrej vs andrejq", and sampling, "Is the table learning anything?".

3 · Build: the whole counting model in one script, checked end to end

runs on your M3 · about 0.5 s

What it reinforces: examples as (given, next) pairs (the dataset), the table and its row/column sums (counting, reading N), keepdim (the trap), the sampling loop (sampling) and the loss (NLL). New here: the pairs become tensors xs, ys first, and the loss becomes one line, the form the neural half uses.

  1. Pairs. Build xs (current character) and ys (next character) as int64 tensors for every bigram in the file.
  2. Count. Fill N from them. Check N.sum() and N[0].sum().
  3. Normalise twice. P with keepdim, bad without. Assert every row of P sums to 1, and print bad[0].sum().
  4. Score both in one line. -P[xs, ys].log().mean() picks each bigram's probability with fancy indexing. Do the same for bad, and explain the result (question 2).
  5. Sample. Draw 1,000 names from P and 1,000 from bad with seed 2147483647 (torch.multinomial accepts rows that don't sum to 1; it rescales them). Print the mean length of each and the number of one-letter names from P.
  6. Score the samples. Turn the 1,000 P names and 1,000 uniform names back into pairs and score each set with P.
xs, ys = torch.tensor(xs), torch.tensor(ys)   # 228,146 each
N = torch.zeros((27, 27), dtype=torch.int32)
N.index_put_((xs, ys), torch.ones_like(xs, dtype=torch.int32),
             accumulate=True)                  # or the += loop
P = N.float(); P /= P.sum(1, keepdim=True)
bad = N.float() / N.float().sum(1)             # the bug, on purpose
assert torch.allclose(P.sum(1), torch.ones(27))
nll = lambda T, a, b: -T[a, b].log().mean().item()
print('%.4f %.4f' % (nll(P, xs, ys), nll(bad, xs, ys)))
Done when: N.sum() is 228146 and N[0].sum() 32033; the assert passes and bad[0].sum() is 7.0225; both losses print 2.4540; the first five names from P are cexze. momasurailezitynn. konimittain. llayn. ka. (torch 2.14; the video's differ), with mean length 6.31 and 117 one-letter names, against 23.29 for bad; P's own samples score 2.4460 and the uniform ones inf. All measured in the checkpoint's scratch run on the M3; the sample numbers match labs/sampling-multinomial.py.
