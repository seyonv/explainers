Anatomy of a tool call

Also called function calling or tool use. The three pieces every agent step is made of (a tool definition, a tool_use request and a tool_result answer), shown in the Claude Messages API format. Other APIs use different field names for the same three pieces.

Prime · 2 minutes before you read

The problem: Every step of an agent is one tool call, and most agent bugs live in its three pieces: a vague tool description, a result sent back in the wrong shape (a 400 error), or a result so long or so unclear that the model loses the thread. Seeing the real JSON makes all three concrete.

Where it fits: Zooms into one turn of the agent loop. What the tool sends back becomes part of every later call, which is the bridge to the next card on what the model sees.

In one breath. A tool is a function the harness offers the model. It is described by a name, a plain-English description and an input schema: a small JSON document that lists the allowed arguments. The model can't run anything itself. It writes a tool_use block asking for a call, with an id. The harness runs the tool and answers with a tool_result that carries the same id. What that result says, and how long it is, decides what the model can do next.

Worked example: one step of fixing test_slugify

1 · The harness describes the tool (sent in tools on every call)

{ "name": "run_tests", "description": "Run pytest on a file or folder. Returns the pass and fail counts first, then the output. Long output is cut.", "input_schema": { "type": "object", "properties": { "path": { "type": "string", "description": "e.g. tests/" } }, "required": ["path"] } }

A second tool, view, shows a file. Its definition looks the same.

2 · The model asks for two tools at once (response, stop_reason: "tool_use")

"content": [ { "type": "text", "text": "I'll run the test and read the code." }, { "type": "tool_use", "id": "toolu_01", "name": "run_tests", "input": { "path": "tests/test_slugify.py" } }, { "type": "tool_use", "id": "toolu_02", "name": "view", "input": { "path": "src/slugfy.py" } } ← typo in the path ]

3 · The harness answers both, in one user message

{ "role": "user", "content": [ { "type": "tool_result", "tool_use_id": "toolu_01", "content": "1 failed, 11 passed\nFAILED tests/test_slugify.py::test_unicode ..." }, { "type": "tool_result", "tool_use_id": "toolu_02", "is_error": true, "content": "File not found: src/slugfy.py. Did you mean src/slugify.py?" } ] }

Real ids are longer (like toolu_01A09q90qw90lq917835lq9). The file names and messages are illustrative; the field names are the API's. The error is written so the model can fix its next call without guessing.

The rules the API enforces

  • Answer every call, in the very next message. Each tool_use id needs a tool_result with the same tool_use_id, all together in the next user message. Leave one out and the next request fails with a 400 error: "tool_use ids were found without tool_result blocks immediately after".
  • Results first. In that message the tool_result blocks come before any text; text before them is also a 400. Text after them is allowed but best left out: it can make the model end its turn early.
  • A failed tool still answers. Send "is_error": true and a message that says what went wrong and what to try next. The docs' example: "Rate limit exceeded. Retry after 60 seconds." rather than "failed".
  • Don't split parallel results into one message each. The docs call that wrong, and it teaches the model to stop making parallel calls.

What the tool sends back matters: the agent-computer interface

The SWE-agent paper (Yang et al., 2024) named this the agent-computer interface: tools designed for a model the way screens are designed for people. Changing only what one tool showed moved the score on SWE-bench Lite (300 real GitHub issues, GPT-4 Turbo):

Tool designBugs fixed
FILE VIEWER: HOW MUCH OF A FILE TO SHOW
100 lines at a time18.0%
30 lines at a time14.3%
The whole file12.7%
SEARCH: HOW TO SHOW THE MATCHES
A summary, capped at 50 matches18.0%
No search tool15.7%
One match at a time12.0%
EDIT: WHAT HAPPENS AFTER AN EDIT
Check the syntax and reject broken edits with the error18.0%
No check15.0%

More was worse: the whole file scored lowest, and one-match-at-a-time search did worse than no search, because the agent paged through matches until its budget ran out. These are single runs of one 2024 model, so treat small gaps with care (measuring an agent shows why).

Worked example: a 26,000-character test log, cut or not

The run_tests call prints three long assertion diffs: 26,000 characters. The tool can send all of it, or keep the first 4,000 and last 4,000 characters plus a one-line note of what was cut. The log is the result of call 9 in a 14-call run, so calls 10 to 14 all carry it: 5 calls.

Tokens in the logTokens sent, calls 10–14Cost, cachedCost, uncached
Send everything6,50032,500$0.021$0.065
First + last 4,000 chars + note2,02510,125$0.007$0.020
full log: 26,000 chars ÷ 4 chars/token = 6,500 tokens cut log: (4,000 + 4,000 + a 100-char note) ÷ 4 = 8,100 ÷ 4 = 2,025 tokens sent: 5 calls × 6,500 = 32,500 vs 5 × 2,025 = 10,125 (22,375 fewer tokens) cached: written once (call 10) at $2.50/M, read on calls 11–14 at $0.20/M full: 6,500 × $2.50/M + 4 × 6,500 × $0.20/M = $0.0163 + $0.0052 = $0.021 cut: 2,025 × $2.50/M + 4 × 2,025 × $0.20/M = $0.0051 + $0.0016 = $0.007 uncached: 32,500 × $2/M = $0.065 vs 10,125 × $2/M = $0.020

Assumes about 4 characters per token, a round number. Claude's newer tokenizer is closer to 3.1, which makes the logs 8,387 and 2,613 tokens: the same 3.2× gap. The cents are small; the bigger cost is attention. The model has to find three failing test names in the log on every later turn, and pytest prints its summary at the end, which the tail keeps. Real harnesses cut the same way: mini-swe-agent replaces output of 10,000 characters or more with the first and last 5,000 plus a warning, and Claude Code caps bash output at about 30,000 characters.

Why it beats the alternatives

✗ Return everything

The full log or file rides along in every later call, and the key line is harder to find. SWE-agent's whole-file viewer scored lowest (12.7%).

✗ Return a bare "failed"

The model has to guess what went wrong, so it spends turns re-reading files or repeating the same broken call.

✗ Let the error escape the loop

If a tool's exception crashes the harness, or its result is dropped, the run dies or the next request fails with a 400.

✓ Short, labelled results and useful errors

Counts and failing test names first, the rest cut with a note, and every error sent back with is_error and a next step the model can act on.

Is less output always better?

No. Cutting the middle of a log can hide the one line that matters, so the note must say what was cut and how to see it (a narrower command, or a file where the full output was saved; Claude Code saves the rest to a file). And the SWE-agent table shows too little hurts too: 30-line views scored below 100-line views.

Output design also isn't the only tool fix. If the model keeps sending bad arguments, write a clearer description, or turn on strict tool use (strict: true), which makes inputs always match the schema. Neither helps if the tool's answer is unclear, which is what this card is about.

Understand and remember

  • The model can't run code → it writes a tool_use block with an id, name and input → the harness runs it and answers with a tool_result carrying the same tool_use_id
  • Parallel calls arrive in one response → every id must be answered in the very next user message, results before any text → otherwise the next request fails with a 400
  • A tool that fails still answers → is_error: true plus what went wrong and what to try next → the model recovers instead of guessing or the loop crashing
  • Every tool result is re-sent on every later call → a 26,000-character log costs 6,500 tokens per call, 2,025 if cut to head and tail → cap output at the tool and say what was cut
  • detail that matters More output is not more help → SWE-agent's whole-file view (12.7%) and one-match-at-a-time search (12.0%) scored below the bounded versions (18.0%) → tool defaults are design choices to measure

6 · Apply use the model, don't restate it

Pick one tool in an agent you use or are building (a test runner, a file viewer, a search). Run it on a case that produces long output and on a case that fails. Write down what the model would receive in each case, its size in tokens (characters ÷ 4), and rewrite the error message so it names the next action.

Hint
