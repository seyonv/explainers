The agent loop

Also called the tool-use loop or the harness loop. It is the core of every coding agent (Claude Code, Codex CLI, mini-swe-agent): a short program around the model that turns one request into many model calls, and decides when to stop.

Prime · 2 minutes before you read

The problem: An agent looks like magic until you see the loop: call the model, run the tool it asked for, append the result, call again. Without the loop in your head you can't say why an agent run costs what it does, why it re-sends the same text every call, or why it sometimes stops half-way.

Where it fits: First card of the course and the base for the other three. The tool-call card zooms into one turn of this loop, the context card into what each call carries, and the evals card into how to tell if a change to the loop helped.

In one breath. An agent is a model, a loop and some tools. The program around the model (the harness) calls the model. If the model asks for a tool, the harness runs it, adds the result to the conversation, and calls the model again. The API remembers nothing between calls, so every call re-sends the whole conversation. The loop ends when the model says it's done, or when something else stops it first.

The words on this card

HarnessThe program around the model. It sends requests, runs tools and owns the conversation. Claude Code is a harness; Claude is the model.
ToolA function the harness offers the model, such as "run the tests" or "show me this file". The model can only ask for it; the harness runs it.
Stop reasonA field on every response (stop_reason) that says why the model stopped writing: finished, wants a tool, hit a length cap, and so on.
BudgetA limit the harness sets: most steps, most dollars, or most minutes per task.

On the API, caching is opt-in: you turn it on (automatic caching or cache_control markers), and Claude Code does it for you. Caching makes this run 2.1× cheaper, not 10×, because it is short: writing new tokens costs more than reading old ones, and here the new tokens are a quarter of the input. The longer the run, the bigger the saving (6.2× over 30 calls in context growth). Prices: Anthropic's list prices for Sonnet 5, 5-minute cache. How the cache works: prompt caching.

Every way a run ends

What happenedWho decidesWhat the loop should do
tool_usemodelNot an end. Run every tool it asked for, append the results, call again.
end_turnmodelThe model thinks it's finished. Check the result if you can (run the tests), then stop.
max_tokensyour capThe reply hit its length cap and may have cut a tool call in half. Don't run the half call; retry the turn with a higher cap.
refusalmodelThe model declined. Sending the same request again won't change it: stop and report it, or retry on another model or with a rephrased request.
Step, cost or time budgetharnessStop, and log it as a failed run, not a crash. mini-swe-agent has all three: step_limit, cost_limit ($3 by default) and wall_time_limit_seconds.

The API has seven stop reasons in all. The other three are rarer: stop_sequence (a text marker you chose appeared), pause_turn (a tool the API runs itself paused; send the reply back to continue) and model_context_window_exceeded (the reply grew until it filled the context window, so it is cut off; a request whose input doesn't fit is rejected with an error instead, see what the model sees). Budgets matter because agents succeed quickly and fail slowly: in the SWE-agent paper, successful runs took a median of 12 steps and $1.21, failed runs an average of 21 steps and $2.52.

Why it beats the alternatives

✗ One call, no tools

Cheapest and fastest, but the model can't read the repo or run the tests. It guesses a fix and can't tell if it worked.

✗ A fixed script for a task you can't plan

"View the file, edit it, run the tests" in code. It breaks as soon as the bug isn't where the script expected.

✗ A loop that only checks for tool_use

Treats a cut-off reply as done, runs half-written tool calls, and never stops a model that keeps calling tools. Failed runs burn the most budget.

✓ A bounded loop with every exit handled

The model picks each step from what the tools show it, and the harness owns the conversation, the budgets and each way a run can end.

Is an agent always the right choice?

No. Anthropic's "Building effective agents" splits LLM systems in two. Workflows run the model and tools through code paths you wrote in advance. Agents let the model choose its own steps. If you know the steps ahead of time (say, "summarize this diff, then write a commit message"), a workflow is cheaper, faster and easier to test.

Cost pushes the same way. Barry Zhang's rule of thumb: a task worth about $0.10 affords roughly 30,000–50,000 tokens, and even the tiny run above sent 54,000 input tokens. Use an agent when the path can't be written down beforehand, like finding a bug in code you haven't seen, and the task is worth the extra calls.

Understand and remember

  • The API keeps no memory between calls → the harness re-sends the whole conversation every call → input per call grows by a fixed step and the run's total grows faster than the call count (54,000 tokens for 6 calls, 172,800 for 12)
  • The model can only ask for a tool → the harness runs it and appends the call and result → the loop repeats while stop_reason is tool_use
  • A reply can stop for reasons other than finishing (max_tokens, refusal) → a loop that only checks for tool_use runs half-written calls or never stops → give every stop reason its own branch
  • Agents succeed quickly and fail slowly (12 steps vs 21 in SWE-agent) → an unbounded loop spends most of its money on failures → step, cost and time budgets are exits, logged as failed runs
  • detail that matters Caching reads old tokens at 0.1× but writes new ones at 1.25× (Sonnet 5 with the 5-minute cache; the multipliers vary by model) → on a short run the writes dominate → the saving grows with the run (2.1× at 6 calls, 6.2× at 30)
