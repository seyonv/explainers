What the model sees on each call

Also called the context, the context window or the prompt. Everything a harness packs into one request (tool definitions, system prompt, repo instructions such as CLAUDE.md or AGENTS.md, the history and tool outputs), and where skills, MCP, subagents and hooks plug in.

Prime · 2 minutes before you read

The problem: The model only knows what is in the request, so everything an agent can do depends on what the harness packs in. Packed badly, a run costs more, misses the cache every call, gets less accurate as the input grows, or dies late with "prompt is too long".

Where it fits: The previous two cards showed the loop and one tool call. This card looks at the whole request those calls build up, and places skills, MCP, subagents and hooks on that picture.

In one breath. The model knows only what is in the request. On every call the harness packs the same stable part first (tools, system prompt, repo instructions), then the conversation so far, which grows each turn. The window is a hard limit, say 200,000 tokens. Filling it isn't free even before the limit: each token is paid on every call, the cache only helps while the start stays the same, and answers tend to get worse as the input grows.

Order matters: stable first, changes last

toolssystemCLAUDE.mdskills→turn 1turn 2…turn 29→new turn

The prompt cache (see prompt caching) matches the request from the start, in the order tools, then system, then messages. A change anywhere throws away the cache for that point and everything after it. So harnesses keep the front byte-for-byte identical and only append at the end. A timestamp at the top of the system prompt, or a tool added mid-task, makes every call re-write the cache at the write price (1.25×) instead of reading it at 0.1×:

toolssystem + 10:42:07CLAUDE.mdskills→turn 1…turn 29← nothing after the change is reused

Where skills, MCP, subagents and hooks plug in

ExtensionWhat it isWhere it lands in the requestThe catch
SkillInstructions (and maybe scripts) the model loads when it needs them.About 100 tokens of name and description sit in the prefix on every call. The body (under 5,000 tokens recommended) joins the history only when the model decides to use it.The model decides from the description alone, so a vague one rarely fires on its own (you can still run it yourself with /skill-name).
MCP serverTools served by a separate program over a standard protocol (the Model Context Protocol).In a plain API harness, its tool definitions join the tools block, the very front of every call. Claude Code defers them by default: only the names (120 tokens in its example) sit up front until a tool is needed.Loaded up front, one user's 566 MCP tools came to about 208,000 tokens: more than a 200k window.
SubagentA child loop with its own fresh context: its own system prompt, the task it was given, usually CLAUDE.md, and no conversation history (a "fork" subagent is the exception: it inherits the history).Only its final report comes back, as a result in the parent's history (420 tokens in Claude Code's docs example).The parent stays small, but total tokens don't fall: the child pays for its own reads.
HookHarness code that runs at fixed moments, such as before every tool call. The model doesn't choose it.Nowhere, unless it sends a message back. Exit code 2 on a "before tool use" hook blocks the call, whatever the model decided.Use it for rules that must hold; an instruction in the prompt can be outweighed.

When the window fills up

Compaction replaces old history with a summary written by the model, keeping decisions, open bugs, file paths, failing test names and the next step. A lighter version clears old tool results, which the model rarely needs again once they are deep in the history. Both rewrite the history, so the cache is rebuilt from the change onward: do it rarely, in large chunks.

Context rot is why you shouldn't wait for the limit. Chroma tested 18 models and found accuracy falls as input grows, even on simple tasks. On the same questions, every model did better with a short, focused prompt than with a full history of about 113,000 tokens. So good harnesses load content just in time: they keep file paths and search queries, and fetch the contents with tools when a step needs them.

Why it beats the alternatives

✗ Load everything up front

The repo map and every test file in the first call. You pay for them on every call, and the extra text lowers accuracy (context rot).

✗ Change the front of the request

A timestamp in the system prompt, tools added or reordered, or old turns edited. Every call misses the cache and pays full price.

✗ Let it fill until it fails

Nothing checks the size, so a long run dies with "prompt is too long" late in its budget, after most of the money is spent.

✓ Stable prefix, append-only, just in time

Fixed tools and instructions first, new turns appended, content fetched when needed, and a size check that compacts well before the limit.

Isn't a bigger window the fix?

Only for the hard limit. Claude Sonnet 5 accepts 1,000,000 tokens, which moves the "prompt is too long" wall far away. It doesn't change the rest: every token in the request is still paid on every call, and context rot still lowers accuracy as the input grows. A big window is room to use carefully, not a reason to fill it.

When doesn't any of this matter? On short tasks. A 6-call fix like the one in the agent loop never gets past 14,000 tokens, so there the prefix size and the number of calls matter more than compaction.

Understand and remember

  • The model sees only the request → the harness sends a stable prefix (tools, system prompt, repo instructions) then the growing history on every call → the prefix is paid every call and the history grows each turn
  • The cache matches from the start in the order tools → system → messages → any change invalidates that point and everything after → keep the front byte-identical and only append
  • History only grows → the window fills (call 95 in the example) and the run fails late → compact or clear old tool results well before the limit, in large chunks, because each rewrite restarts the cache
  • Accuracy drops as input grows, even on simple tasks → a full window costs quality, not only money → load files just in time and keep paths and queries instead of contents
  • detail that matters Skills and MCP tools sit in the prefix, a subagent returns only a report, a hook runs outside the context → each extension costs tokens in a different place → count where it lands before adding it

5 · Predict commit to an answer before revealing

Before a run, you add an MCP server whose tool definitions are 20,000 tokens. With the example's other numbers, predict at which call the 200,000-token window fills, compared with call 95 before.

Reveal

The prefix becomes 33,050, so input on call k = 33,050 + 2,000 × (k − 1). Call 84 is 199,050 and fits; call 85 is 201,050 and doesn't. The window fills 10 calls sooner (20,000 ÷ 2,000 per turn), and every one of those calls pays for the 20,000 extra tokens.
