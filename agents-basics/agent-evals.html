Measuring an agent

Also called agent evals or benchmarking. How to tell whether a change to a harness (a new tool, a skill, a retry) actually helped: fixed tasks, hidden tests, repeated runs, a pass rate with an honest interval, and cost per solved task.

Prime · 2 minutes before you read

The problem: You change your agent, rerun it, and the score goes up. Was it the change or luck? Agent runs are random, small task sets are noisy, and an agent that can see the tests can game them, so a bare pass rate can't answer that question.

Where it fits: The last of the four cards. The first three show what you can change in a harness; this one shows how to tell whether a change helped, and what it cost per solved task.

Read with these questions (answer them in your head as you go; don't take notes line by line):

  1. Why do the three trials each say 7 of 10 but disagree on which tasks?
  2. How does the Wilson interval get from 21/30 to 52.1%–83.3%?
  3. Why is the by-task interval wider than the Wilson one?
  4. What is the chance of seeing "gained 2, lost 0" if the change did nothing?
  5. Why divide by what was solved rather than by trials?

In one breath. Run the agent on a fixed set of tasks, several times each, and grade every run with tests it couldn't see or edit. Runs are random, so report the pass rate with a range, not a bare number, and only trust a change that moves it by more than that range. Then read the failed runs to learn why they failed, and divide what you spent by what got solved.

"All k passed" is called pass^k; "at least one of k passed" is pass@k. Someone who uses the agent every day lives with pass^k.

An honest interval, two ways

A 95% interval is a range built so that, if you reran the whole 30-trial experiment many times, about 95 of every 100 ranges built this way would contain the agent's true pass rate. The three methods below are three ways to build that range; wider means less sure.

1 · Wilson interval, treating the 30 trials as 30 coin flips p = 0.70, n = 30, z = 1.96 (for 95%) centre = (p + z²/2n) ÷ (1 + z²/n) = (0.700 + 0.064) ÷ 1.128 = 0.677 half = z × √( p(1−p)/n + z²/4n² ) ÷ (1 + z²/n) = 1.96 × √(0.0070 + 0.0011) ÷ 1.128 = 0.156 95% interval = 0.677 ± 0.156 → 52.1% to 83.3% 2 · By task, because 3 trials of one task are not independent per-task rates: 1, 1, 1, 1, ⅔, ⅔, ⅔, ⅓, ⅓, ⅓ mean 0.70 spread across tasks: √(0.767 ÷ 9) = 0.292 standard error = 0.292 ÷ √10 = 0.092 95% interval = 0.70 ± 2.262 × 0.092 = 0.70 ± 0.209 → 49.1% to 90.9%

2.262 replaces 1.96 because there are only 10 tasks (the t value for 9 degrees of freedom). A bootstrap cross-check, resampling the 10 tasks 10,000 times, gives 53.3% to 86.7%. Either way the honest answer is "about 70%, somewhere between 50% and 90%". Only more tasks narrow it much: extra trials of the same tasks remove at most two-thirds of the trial-to-trial noise (Miller, 2024).

Why a "+2 tasks" improvement on 10 tasks is noise

You add a retry and rerun. Counting a task as solved when at least 2 of its 3 trials pass, the old agent solved 7 of 10 and the new one solves 9 of 10.

Wilson 95%: old 7/10 → 39.7% to 89.2% new 9/10 → 59.6% to 98.2% (they overlap widely) task by task: new gained 2 tasks, lost 0 if the change did nothing, each changed task is a coin flip: chance both flips go one way = 2 × 0.5² = 0.5 → a 50% chance of seeing this by luck noise floor: 6 of the old agent's 10 tasks already flipped between its own 3 trials

For scale: at a 50% pass rate on 40 tasks, the 95% interval is ±15.5 points, and you need about 384 tasks to get it down to ±5. Compare versions task by task, and run the old version twice first to see how many tasks flip on their own.

Open each failed transcript and give it one label: a wrong fix, a chain of failed edits, the same failing command repeated, or the budget ran out. Then build for the biggest group. The SWE-agent authors did this for 248 failed runs: 52.0% were wrong or overly narrow fixes, 23.4% cascading failed edits. A run that died on an API error or a broken container is neither: rerun it and leave it out of the pass rate.

Why it beats the alternatives

✗ One run, one number

Any single trial above says 70%, yet 6 of 10 tasks flip between trials. A change measured this way is mostly luck.

✗ Tests the agent can see and edit

Editing the test is the shortest path to green. On ImpossibleBench, where any pass is a cheat, GPT-5 "passed" 54% with test access; hiding the tests took that near zero.

✗ A famous public benchmark alone

Old public tasks are in training data. Models named the buggy SWE-bench file from the issue text alone up to 76% of the time, against at most 53% elsewhere.

✓ Your own tasks, hidden tests, repeats

A fixed task set, graders the agent can't touch, 3 trials each, a pass rate with its interval, task-by-task comparisons, and cost per solved task.

Do I need hundreds of tasks?

Not to start. Anthropic suggests 20–50 simple tasks drawn from real failures, each run in a clean environment. Just be honest about what that size can show: big effects (a tool that doubles the pass rate) are visible, small ones (+2 of 10) are a hypothesis to rerun, not a result.

Tests aren't always possible. For a task with no clear right answer (a summary, a code review), people use a model grader with a written rubric, which must itself be checked against human judgments. And for a one-off script you'll run once, reading the output yourself beats building an eval.

Understand and remember

  • Agent runs are random → the same task passes one trial and fails the next (6 of 10 tasks here) → run each task several times and report a range, not one number
  • Trials of one task are alike → treating 30 trials as 30 independent flips understates the error → compute the interval by task (49%–91%) and add tasks, not trials, to narrow it
  • A small change on few tasks sits inside the noise → +2 of 10 tasks has a 50% chance by luck alone → compare task by task against a rerun of the old version before calling it a result
  • An agent that can see or edit the tests can game them → grade with hidden tests on the final repo state → the score measures the fix, not the agent's claim
  • detail that matters Failed trials cost money too → cost per solved task = total spent ÷ trials that passed → a cheaper model that solves fewer can come out cheaper or dearer per solve ($0.625 vs $0.70 here)

Reference only

  • the Wilson formula itself
  • t = 2.262 for 9 degrees of freedom
  • the SWE-agent failure shares (52.0%, 23.4%)
  • the 384-task rule of thumb

3 · Retrieve from memory, card closed
  1. concept In the example grid, what are pass@3 and pass^3? Say what each one counts, compute both for the example's 10 tasks. Which one does a daily user of the agent feel?
    Check
    • pass@3: at least one of 3 trials passes: 10 of 10
    • pass^3: all 3 trials pass: 4 of 10
    • a daily user feels pass^k, because they need it to work each time
  2. mechanism Walk through the by-task interval: what is the data point, how is the spread computed, and why 2.262?
    Check
    • each task's pass rate over its 3 trials is one data point (1, 1, 1, 1, ⅔, ⅔, ⅔, ⅓, ⅓, ⅓)
    • spread √(0.767 ÷ 9) = 0.292; standard error 0.292 ÷ √10 = 0.092
    • 2.262 is the t value for 9 degrees of freedom, used because there are only 10 tasks
  3. tradeoff Your interval is too wide. Do you add trials per task or add tasks? Justify with how the noise is made up.
    Check
    • extra trials only reduce the trial-to-trial noise, and at most two-thirds of it (Miller)
    • differences between tasks dominate a by-task interval, and only more tasks shrink them
    • so add tasks first, and keep about 3 trials for pass^k and flip counts
  4. tradeoff Why should the grader be tests the agent can't see, rather than the tests in the repo or a comparison with a known-good diff?
    Check
    • visible, editable tests invite gaming: 54% "passes" on impossible ImpossibleBench tasks with test access
    • a correct fix rarely matches the known-good diff line for line, so diff-matching fails good fixes
    • hidden tests check the outcome: the final state of the repo

4 · Compare against what you already know

vs Compounding errors in agent loops: Compounding errors multiplied per-step success into task success. How is pass^k the same kind of calculation, and what differs?

Check
  • both multiply chances that must all go right: p per step, or p per trial
  • compounding errors chains steps within one task; pass^k repeats the whole task k times
  • both fall fast: at 80% per trial, pass^3 is 0.8³ = 51.2%

vs Model routing: the right size model per step: Model routing picks a cheaper model for easy steps. How does cost per solved task change the way you judge that choice?

Check
  • a cheaper call is only a saving if the task still gets solved
  • divide total spend (failures included) by tasks solved
  • on 10 tasks, a few-cent gap per solve is inside the noise, so test on more tasks before switching

Why this step?

5 · Predict commit to an answer before revealing

A new version scores 26/40 against the old version's 22/40 on the same 40 tasks. Before computing, is a 10-point gain on 40 tasks likely to be real?

Reveal

Probably not on its own. At about 55–65% on 40 tasks the 95% interval is roughly ±15 points, so 10 points is inside it. What decides it is the task-by-task view: how many tasks the new version gained and lost, compared with how many tasks flip when you simply rerun the old version.

6 · Apply use the model, don't restate it

Pick 10 small tasks you can check with a test (fixing planted bugs in a toy repo works). Run your agent 3 times on each, graded by a test file the agent never sees. Fill in the grid, compute the pass rate, pass^3 and a Wilson interval, and label each failed trial with one reason.

Done when: You have a 10 × 3 grid, a pass rate with its 95% interval, pass^3, a count of tasks that flipped between trials, and a label for every failure.

Hint

Copy the hidden test into the repo only after the agent has stopped, then run it.
