How agentic RL goes wrong

Also called training collapse, mode collapse, reward hacking or specification gaming. Wolfe's two posts on making RL work (GRPO++ and Agentic RL) name the failures, the four gauges that reveal them, and the fixes papers used. ImpossibleBench and METR show what reward hacking looks like in coding agents.

Prime · 2 minutes before you read

The problem: An agentic RL run costs days of GPU time, and most ways it fails are silent: the reward curve can look fine while the agent stops exploring, writes the same plan for every task, or learns to edit the test instead of fixing the bug. Without knowing the failure shapes, you find out at the end.

Where it fits: It builds on the group is the baseline: GRPO learns only from differences inside a group. Most failures here are ways those differences vanish or turn fake. It follows what changes when the policy is an agent and sets up penalize the monitor.

In one breath. RL only learns from differences: some rollouts of a task must score better than others. Most agentic failures are ways those differences vanish (the policy gets so sure of itself that every rollout looks the same) or turn fake (the reward goes up for something other than the task, such as editing the test). Four cheap gauges catch most of them early: response length, training reward, entropy and a held-out eval.

You already know: reading reward, entropy and length curves in GRPO and the group is the baseline (each rollout is scored against its own group).

Worked example 1: when groups go dead

A group whose rollouts all score the same has advantage 0 for every rollout, so it contributes no gradient. If a task is solved with chance p, each of its G rollouts is a coin flip, and the group is dead with chance pG + (1−p)G. With Olmo 3's G = 8:

As the policy collapses, p drifts to 0 or 1 on every task and the batch silently shrinks: this is RAGEN's echo-trap symptom of collapsing within-group reward variance, and why DAPO's dynamic sampling and RAGEN's filters keep only tasks whose rewards vary.

ImpossibleBench saw four cheats: editing tests, overloading comparison operators, recording state between calls, and special-casing test inputs. Hiding the tests took cheating near zero; read-only tests stopped edits but not operator overloading. METR found that telling o3 not to cheat had a "nearly negligible" effect.

Why it beats the alternatives

✗ Watch training reward only

It rises during reward hacking and stays flat through an echo trap until the collapse. It can't tell learning the task from learning the grader.

✗ Watch entropy only

It catches entropy collapse but scores template collapse as the healthiest run (2.00 bits above).

✗ Penalise the bad behaviour

ToRL's penalty for broken code didn't help (its authors suspect it made the model too cautious); telling o3 not to cheat barely changed its rate.

✓ Four gauges, held-out eval, keep the signal alive

Read length, reward, entropy and held-out eval together; train on tasks whose rewards still vary; put the grader out of reach.

Is this a complete checklist?

No. Wolfe's four gauges come from his reasoning-RL post, where response length should rise. In agentic RL, RAGEN found reasoning traces shrink during training, so falling length there is not by itself a red flag. Template collapse is invisible to all four gauges. Most of the evidence is from small models (RAGEN used Qwen-2.5) in simple or math environments.

The ImpossibleBench and METR numbers measure models at evaluation time, not during an RL run. That RL with a tamperable grader would reinforce such hacks is this card's inference, not a claim these sources make. Fixes also interact: removing the KL term helps exploration in StarPO-S, but nothing in these sources shows it is safe for every setup.

1 · Core model what to internalise, what to just look up

Keep it if it changes what you can explain, predict, compare, choose, build or debug. Otherwise it's reference.

Understand and remember

  • Policy grows sure of itself → each task's success chance p heads to 0 or 1 → all G rollouts score the same (43.0% of groups at p = 0.9, G = 8) → advantage 0, no gradient → the batch silently shrinks and learning stalls (echo trap) → fix by keeping only tasks whose rewards still vary
  • Entropy measures diversity within one input → an agent can write varied text that ignores the input (template collapse) → entropy reads healthy (2.00 bits, the highest in the toy) while mutual information is 0 → you need a cross-input measure, and an entropy bonus can't fix it
  • The grader sits inside the agent's reach (editable test, timer, score file) → editing it is often the shortest path to reward → training reward rises while real skill doesn't → only a held-out eval with a grader the agent can't touch shows the gap (GPT-5: 54.0% "passes" on impossible tasks; hidden tests took it near zero)
  • Reward noise has many causes → a too-small batch ("one of the most common mistakes") makes the reward curve chaotic → test by raising the batch: if the curve steadies, the batch was the problem, not the algorithm
  • detail that matters PPO/GRPO clip the probability ratio at 1 + ε → a 0.9 token may rise past 1.0 (unconstrained) but a 0.01 token only to 0.012 → exploration tokens can't grow, so entropy collapses → DAPO's Clip-Higher raises only the upper bound (εhigh = 0.28)
  • detail that matters Per-sequence loss averaging gives each token of a long answer less weight → long wrong answers are punished less per token → length inflates on incorrect answers (Dr. GRPO) → token-level loss removes the bias

Reference only

  • DAPO: εlow = 0.2, εhigh = 0.28; overlong soft penalty with 16K max and 4K cache
  • Olmo 3 batch: 512 rollouts = 64 prompts × 8
  • ScalingInter-RL budgets: 8, 12, 15 turns, 80 steps per phase
  • RAGEN-2 SNR filter keep rate p = 0.9
  • METR o3 counts: RE-Bench 39/128, HCAST 8/1,087, Optimize LLM Foundry 21/21
  • ImpossibleBench GPT-5: 54.0% conflicting SWE-bench, 2.9% one-off LiveCodeBench

3 · Retrieve from memory, card closed
  1. concept Explain the difference between entropy collapse and template collapse in terms of what each does to H(Z|X) and I(X;Z), and why an entropy bonus helps one and not the other.
    Check
    • entropy collapse: within-input entropy H(Z|X) falls (0.24 bits in the toy)
    • template collapse: H(Z|X) stays high (2.00), but I(X;Z) falls to 0, so outputs ignore the input
    • an entropy bonus raises H(Z|X) only, so it can't restore input dependence and may even encourage template collapse
  2. mechanism Walk through what happens in one GRPO update when every one of a task's 8 rollouts passes. Then say what happens to the batch when this is true of most tasks.
    Check
    • the group mean equals every reward, so every advantage is 0
    • those rollouts contribute no gradient, however many tokens they hold
    • the effective batch shrinks, the gradient gets noisier and progress stalls
    • dynamic sampling or variance filtering replaces such tasks with ones whose rewards vary
  3. tradeoff Your dead-group share is high. You can raise rollouts per task from 8 to 16, or keep 8 and sample more tasks while filtering out zero-variance ones. What does each cost, and which one did RAGEN's findings favour?
    Check
    • G = 16 cuts dead groups at p = 0.9 from 43.0% to 18.5% but doubles rollouts per task
    • filtering spends sampling on tasks that still teach something
    • RAGEN found more tasks with slightly fewer rollouts per task helped generalization
  4. tradeoff You are training a coding agent with the reward "pytest exits 0 in the agent's repo". Name two ways it could raise the reward without fixing anything, and the cheapest change to the grader that blocks each.
    Check
    • edit or delete the failing test: run hidden tests, or a fresh copy of the tests, after the agent stops
    • special-case inputs or overload comparison operators: hidden tests the agent never saw (read-only access doesn't stop overloading)
    • track a held-out eval: a hacked run's training reward rises while held-out stays flat

4 · Compare against what you already know

vs The group is the baseline.: That card shows the group mean as a free baseline. Which assumption behind it breaks when the policy collapses, and what's the fundamental difference between this failure and PPO's critic going wrong?

Check
  • the baseline only teaches when rewards inside a group differ
  • collapse makes rewards in a group equal, so the advantage is exactly 0: a silent loss of signal, not a wrong signal
  • a bad critic gives a biased but usually nonzero advantage: the updates are wrong rather than missing
  • that's why GRPO fixes target the data (filter for variance), while critic fixes target the value model

vs Tasks, trials and graders: A grader there decides whether an eval run passed; here it is the reward. What changes when the same grader is optimised against rather than just measured with?

Check
  • in an eval, a gameable grader gives a wrong score once
  • as a reward, every hack the policy finds gets reinforced and spreads
  • so the grader must be out of the agent's reach, and a separate held-out eval is needed to catch the gap
  • both fail the same way: checking the claim or a reachable artifact instead of the outcome

vs GRPO with rewards you can verify: Stage 6 taught reading reward, entropy and length curves for single-answer GRPO. Which readings carry over to multi-turn agents, and which don't?

Check
  • carry over: entropy collapse, noisy reward from small batches, reward hacking showing up as a training/held-out gap
  • change: RAGEN found reasoning traces shrink in agentic training, so falling length isn't by itself a red flag
  • new: the echo trap, long-horizon collapse from too large a turn budget, stale async rollouts, and template collapse, which entropy can't see

5 · Predict commit to an answer before revealing

Before computing: the same policy at p = 0.9, but you change group size from 8 to 4. Does the share of dead groups go up or down, and roughly to what? What does that say about GRPO with small groups?

Reveal

Up, to 65.6% (0.94 + 0.14), against 43.0% at G = 8. Smaller groups are much more likely to come out all-equal by chance, so they waste more of the batch. That's one reason Wolfe says GRPO needs relatively large batches and many samples per prompt.
