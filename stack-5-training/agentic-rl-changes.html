Agentic RL: the design choices

Also called agentic RL, multi-turn RL or tool-integrated RL. Wolfe's "Agentic RL: Frameworks and Best Practices" (June 2026) reads seven recent papers (ToRL, AgentGym-RL, Agent-R1, AgentRL, AutoForge, RAGEN and RAGEN-2), plus GLM-5.2's report, and pulls out the design principles they share. Here they are applied to the Tuesday run, read as one training trajectory.

Prime · 2 minutes before you read

The problem: Take an RL recipe built for one-shot answers and point it at an agent, and it quietly trains on the wrong things: the model learns to imitate pytest logs it never wrote, the trainer scores tokens the policy never sampled, one domain's reward scale swamps the rest, and compaction leaves GRPO comparing rollouts that no longer line up.

Where it fits: Stage 3 of the training roadmap showed why agent RL is harder (long rollouts, a sandbox each, async generation) and the GRPO card showed the group as the baseline. This card is what the frameworks do about it, and it opens the course: the next cards ask what the reward should be and how training goes wrong.

You already know: stage 3, RL for agents (multi-turn rollouts, one sandbox per rollout, async RL) · the group is the baseline (GRPO advantages). This card covers what the frameworks add on top.

In one breath. In single-turn RL the model writes one answer and every token in it is the model's own. An agent's trajectory interleaves the model's tokens with tokens the world wrote: tool output, test logs, summaries. The world also changes underneath it, and not always the same way twice. So the frameworks record each step with the exact tokens sampled, mask everything the agent didn't write out of the loss, normalize rewards across a whole task or environment, and pick tasks the agent can learn from right now.

Predict first. The Tuesday run fails the checker. In a GRPO update, does the step-6 pytest call (the one good move in the run) get pushed up, pushed down, or left alone? And does the model get trained on pytest's output?

Drift: the policy sampled pass + ed; store the run as text and re-encode it, and the trainer scores a token (passed) the model never chose (toy tokenizer).

Compaction breaks the group comparison

GRPO compares rollouts of the same prompt. The Tuesday run compacts once, at step 7, so it trains as two pieces. Give its group of four rollouts (illustrative) lengths of 24k, 70k, 45k and 110k tokens and a 32k window, and they split into 1, 3, 2 and 4 trainable sub-traces of different lengths. Which piece should be compared with which? GLM-5.2 hit this and, as Wolfe quotes it, moved from group-wise optimization to critic-based PPO, where a learned critic scores each token without needing a group.

"Compact whenever the window fills" is a simplification used for the arithmetic; real harnesses compact on their own rules.

Why it beats the alternatives

✗ Train on every token

The model is also trained to predict pytest logs and API replies it didn't write, so tool output it didn't choose is treated as its own move.

✗ Store chats, re-template later

Tokenization isn't reversible, so the trainer can score tokens the policy never sampled (Agent-R1's retokenization drift).

✗ Plain GRPO on everything

Per-prompt groups don't hold up under compaction, and mixed domains with different reward scales let one domain dominate.

✓ Step records, mask, wider normalization

Exact tokens per step, loss only on what the agent wrote, advantages scaled per task or environment, and PPO's critic once compaction splits runs.

Is the action mask settled?

No. Wolfe points to newer work (Echo, PaW) that keeps RL on the agent's tokens but adds a supervised loss on the environment's tokens, which amounts to learning a world model; see the world models card. Nor is the optimizer settled: Agent-R1 found GRPO best on most tasks and PPO best only on WebShop, and GRPO remains the most common choice. Switching to PPO is a long-horizon, compaction-driven choice, not a default.

Be careful with the evidence. These are Wolfe's synthesis of other papers' results, mostly on 3B–32B models and benchmark environments, and AgentGym-RL found RL helps most where the rules are clear (TextCraft, SciWorld) and less on noisy WebArena. Nothing here was run on a coding agent like the Tuesday run. And none of it rewards honesty: an outcome reward never looks at the claim in step 9, which is the problem the next cards take up.

Understand and remember

  • Tool calls change an environment the model can't see in full → the state is context plus environment, and the transition can be random → each rollout needs its own copy of the environment, and the same action can earn different rewards
  • A trajectory mixes agent tokens with tool, prompt and summary tokens → the action mask gives loss only to agent-written tokens → the model learns its own moves instead of learning to predict pytest logs (17.2% of the Tuesday trace gets loss)
  • The loss pushes the probability of the exact sampled token → storing chat text and re-encoding it can produce different tokens (pass+ed → passed) → store step-level records with the exact action tokens (Agent-R1)
  • Compaction splits a long rollout into a varying number of sub-traces → rollouts of one prompt no longer line up as a group → GRPO's group comparison breaks → GLM-5.2 moved to PPO, whose critic scores tokens without a group
  • detail that matters An outcome reward is broadcast to every agent token in the run → the Tuesday run's good step-6 call and its false step-9 claim both get −1 → process rewards look like the fix, but ToRL's −0.5 code-error penalty didn't help
  • detail that matters Different domains have different reward scales → normalizing advantages within each task or environment (AgentRL, ERPO) → no single domain dominates the update

Reference only

  • framework names and their interfaces: AgentGym-RL's HTTP API, Agent-R1's Tool/ToolEnv.step(), AgentRL's function-call API
  • ScalingInter-RL's schedule: 3 phases of 80 iterations at 8, 12 and 15 turns
  • ToRL's reward values (+1, −1, −0.5) and its tool-call cap C
  • DeepSWE's 512 containers per iteration and the move to Kubernetes
  • RAGEN-2's keep rate p = 0.9

    Check
    • tool calls change files, databases or browsers the model can't fully see in its context
    • so the state is the joint (context, environment), not just the tokens
    • text still appends deterministically, but a tool call's effect and observation can be random
    • so the same actions can lead to different rewards, and each rollout needs an isolated environment
  2. mechanism Walk through what happens to the Tuesday run's tokens in one GRPO update: which get loss, what advantage they get, and what never gets trained.
    Check
    • the checker's exit 1 makes the reward 0; in a group with rewards 0, 1, 1, 0 its advantage is −1
    • that −1 is broadcast to the 940 agent-written tokens (the mask), the step-6 call and the false claim alike
    • the prompt, tool outputs, the pytest log and the compaction summary have mask 0 and get no loss
    • the update multiplies each agent token's log-probability, of the exact sampled token, by −1
  3. tradeoff You train a coding agent with long rollouts that compact several times. When would you keep GRPO, and when switch to PPO? Name the cost of each.
    Check
    • GRPO: no critic to train, and the most common choice; Agent-R1 found it best on most of its tasks
    • but it needs rollouts of a prompt that can be compared; varying sub-trace counts after compaction break that
    • PPO: a critic estimates per-token advantages from single rollouts, which is why GLM-5.2 switched
    • cost: a second model to train and keep accurate
  4. tradeoff ToRL's −0.5 penalty for code that won't run sounds like free extra signal. Why might it hurt, and what does that say about process rewards in general?
    Check
    • outcome-only rewards matched or beat it
    • the authors' guess: the penalty made the model overly cautious about writing code
    • process rewards shape behaviour you didn't intend; Wolfe: they don't always give a clear benefit

vs The group is the baseline.: That card scores a group of single answers and nudges every token by its advantage. What breaks when the answers are agent rollouts, and which choice fixes each break?

Check
  • not every token is the model's own: tool output must be masked out
  • the stored record must hold the exact sampled tokens, or the update pushes the wrong token
  • compaction makes rollouts split into different numbers of pieces, so the group no longer lines up; GLM-5.2 used PPO's critic
  • several domains in one batch need advantages scaled per task or environment

vs Compaction is a lossy state change: Both cards treat compaction as a problem. What does it break at run time, what does it break at training time, and why can the second be fixed while the first can't be fixed the same way?

Check
  • run time: the summary loses facts or inflates status, and the model acts on what it sees
  • training time: it splits the trajectory into sub-traces of different counts and lengths, breaking group comparison
  • training can keep the full step-level record and choose an optimizer that doesn't need groups
  • the model at run time only has the summary; the lost fact is gone from its working set

vs Tasks, trials and graders: A grader in an eval and a reward in agentic RL can be the same pytest run. What's different about how each is used, and how does each fail?

Check
  • eval: the verdict is reported and read by people; a bad grader misleads a decision
  • RL: the verdict is multiplied into every agent token's update; a bad reward is optimized against
  • both check the outcome, not the agent's claim, so neither alone punishes the false 'all tests pass' specifically

5 · Predict commit to an answer before revealing

Suppose the invoice-tools environment is flaky: a network-dependent test makes pytest pass or fail at random about one time in five, whatever the agent did. Before reading on, what happens to the GRPO advantages for a group of rollouts, and what does the agent learn?

Reveal

The rewards now carry noise that has nothing to do with the agent's actions, so some advantages are positive or negative by luck. On average the noise cancels, but each update pushes random runs' tokens up or down, so learning slows and the agent can pick up habits that merely coincided with lucky passes. This is the random transition from the card's MDP showing up as reward noise. The usual fixes are to make the environment deterministic (pin or remove the flaky test), re-run the checker, or use larger groups; process rewards don't help because the noise is in the outcome itself.
