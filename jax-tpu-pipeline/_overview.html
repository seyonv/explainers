The post, decoded

The overview card for this set. It covers Sholto Douglas's JAX GitHub post "Pipelining, xmap, and the global device array" (discussion #9696, February 2022), translated line by line, and what the answer turned out to be.

In one breath

Sholto wanted to split a model into an assembly line across a 32-core TPU slice that spans 4 host computers, and asked how to pass data from one stage to the next directly over the chips' own cables (ICI) instead of through the CPUs. The answer: you don't need to think about hosts at all. Lay out every core as one JAX mesh, and a single ppermute shifts data between stages over ICI, whichever host they sit on.

The mental model

The running example: 24 illustrative layers on a v3-32. Putting one pipeline stage on each host is an illustrative layout; JAX's mesh decides the real placement.

Words people use

Host vs chip vs core

A host is the CPU machine. A v3 host has 4 chips, and each v3 chip has 2 cores. "Node" is the GPU-world word for a host.

Collective vs point-to-point

A collective (psum, all-reduce) involves everyone. Point-to-point (send/recv) goes from one sender to one receiver. In JAX the latter is a collective permutation.

pmap → xmap → shard_map

JAX's multi-device APIs over time. xmap was experimental and was deleted in 0.4.31 (July 2024), and the global device array became jax.Array.

ppermute

The word Sholto was missing: "collective-permute is the operation I was looking for to shift the buffer."

So should you pipeline on TPUs?

Often not. The scaling book calls pipelining "a dominant strategy for GPU parallelism that is somewhat less essential on TPUs", because TPU chips are densely connected by ICI. Inside one slice, data, FSDP and tensor sharding usually do the job without a bubble. Where pipelining earns its keep is across slow links such as DCN between slices; that last point is our inference, not a quote. The post's real lesson was conceptual: on TPUs the host boundary is a software detail, not a network one.
