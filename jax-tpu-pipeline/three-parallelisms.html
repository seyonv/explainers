Data, tensor and pipeline parallelism

Also called DP; tensor or model parallelism (TP or MP, Sholto's "layer_shard"); pipeline parallelism (PP, Sholto's "time_shard"). They are the three axes of the mesh he proposes in the post: [time_shard, layer_shard, data_shard].

In one breath

When a model is too big or too slow for one chip, you split the work across many. There are three basic ways to cut it: give every chip a full copy and a different slice of the data (data), split each layer's weight matrices across chips (tensor), or give each chip a different run of consecutive layers (pipeline). Big training runs combine all three, one per axis of a grid of chips called a mesh.

Worked example: the three cuts on a v3-32

The running example: a 24-layer transformer (illustrative size) on a TPU v3-32 slice, which has 32 TPU cores. The mesh multiplies out to exactly the core count:

Ncores= ppipeline × ttensor × ddata =4×2×4=32
ppipeline stages: each holds a run of consecutive layers (Sholto's time_shard)4 stages · 24 / 4 = 6 layers each ttensor-parallel width: how many cores share each weight matrix (Sholto's layer_shard)2 · each core holds half ddata-parallel copies: whole-model replicas, each fed a different slice of the batch4 replicas · 8 cores each

Put the three together and each core ends up holding one stage's 6 layers, but only half of each matrix in them: 24 ÷ (4 × 2) = 3 layers' worth of weights, or 1/8 of the model. One full copy of the model is spread over 4 × 2 = 8 cores, and there are 4 such copies.

stage s holds layers 6s+1 … 6s+6 → 1–6 · 7–12 · 13–18 · 19–24 weights per core = 24 layers / (4 stages × 2 halves) = 3 layers' worth = 1/8 batch (illustr.) = 64 sequences / 4 copies = 16 per copy = 8 micro-batches of 2

The batch of 64 sequences is illustrative. 8 micro-batches is one of the cases on the pipeline bubble card (27.3% idle with 4 stages).

What each one splits and sends

Think of a kitchen. Data parallel is four identical kitchens each cooking a quarter of the orders, comparing notes at closing time. Tensor parallel is two chefs chopping halves of every dish, who must hand bits to each other at every step. Pipeline parallel is an assembly line: each station does its course and passes the plate on.

"12 per micro-batch" uses the How to Scale Your Model book's simplified layer: one all-gather before the block and one reduce-scatter after it. Real transformer layers have an attention block too, so real counts are higher. GPT-NeoX-20B ran on 12 servers of 8 A100 GPUs.

The GPT-NeoX-20B paper puts it this way: "the most efficient way to distribute the model given our hardware setup was to set a tensor parallel size of 2, and a pipeline parallel size of 4. This allows for the most communication intensive processes, tensor and pipeline parallelism, to occur within a node, and data parallel communication to occur across node boundaries." Sholto's "PP=4, MP=2 within a node" is this setup. The question was how to do the same across TPU hosts.

Why combine them

✗ Pure data parallel

Every chip must hold the whole model plus optimizer state. The scaling book's rule of thumb is about 10 bytes per parameter with Adam, so a 96 GB TPU v5p chip tops out near 9B parameters.

✗ Pure tensor parallel

It communicates inside every layer, so it only pays off over very fast links. The scaling book says it becomes communication-bound past roughly 8–16 ways for most models.

✗ Pure pipeline

Stages sit idle while the pipeline fills and drains (the bubble: 27.3% with 4 stages and 8 micro-batches). The slowest stage also sets the pace, so stages must be balanced.

✓ A 3D mix

Tensor parallel goes on the fastest, shortest links. Pipelining divides memory with little traffic, and data parallel scales throughput with one all-reduce per step. Each axis is kept small enough to stay cheap.

9B: 96 GB ÷ 10 bytes per parameter = 9.6B, which the book rounds to "about 9B" (bf16 weights plus fp32 Adam state, before activations).

Is pipelining always worth adding?

No. How to Scale Your Model, a Google DeepMind book whose co-authors include Sholto Douglas himself, says pipelining "is a dominant strategy for GPU parallelism that is somewhat less essential on TPUs". Its main strength is "a low communication cost between pipeline stages", which matters most on GPUs, "since they are not densely connected by ICI in the way TPUs are". The book itself mainly covers data parallel, fully sharded data parallel (FSDP: weights sharded across the data axis and gathered just in time) and tensor parallel.

My inference, not a sourced rule: if a model fits using FSDP plus tensor parallel over fast links, adding a pipeline axis mostly adds a bubble and scheduling complexity. Pipelining earns its place when the links between groups of chips are slow, as between GPU servers or between TPU pods over the data-center network. It also helps when a model is too large for the other axes alone. In the post, Sholto wanted pipelining across hosts because that split looked natural within one 8-core host and the goal was to extend it.
