TPU hosts, pod slices and ICI

Also called node, host or worker VM; "a v32" means a v3-32 slice; ICI is the inter-chip interconnect; DCN is the data-center network. The post asks to use "the ICI links that exist between TPU nodes when one has access to a v32 or greater".

In one breath

A TPU slice is many chips wired directly to each other (ICI), but split across several ordinary computers (hosts) that each feed only their own few chips. Data can hop from a chip on one host to a chip on another host over ICI, without going through either computer's CPU.

Worked example: a v3-32, and two ways to hand over activations

32 cores ÷ 2 cores per v3 chip = 16 chips 16 chips ÷ 4 chips per host = 4 hosts each host: 4 chips × 2 cores = 8 cores = 8 JAX devices mesh: pipeline 4 × model 2 × data 4 = 32 cores → one pipeline stage per host (8 = 2 × 4)

Stage 1 (host A) must hand its activations to stage 2 (host B). Green: one ICI hop between neighbouring chips that happen to sit on different hosts. Red: what a Ray setup like mesh-transformer-jax does, with a Ray worker on each TPU VM taking calls from a driver, so the data goes up to host memory and across the network. Which chip sits where, and the stage-per-host layout, are illustrative. Google lists v3 as a 2D torus pod-wide; whether a 32-core slice has the wrap-around links isn't stated, so none are drawn.

The words, with two examples each

Think of an office building. Each host is a floor with its own receptionist (the CPU) who handles the mail. ICI is a set of pneumatic tubes running straight from desk to desk, even between floors. DCN is the postal service between buildings, and between floors when nobody uses the tubes.

Why it beats the alternatives

✗ CPU-mediated (Ray)

Works across any hosts, but every handover leaves HBM over PCIe (about 16 GB/s per TPU, per the scaling book), sits in host RAM, crosses the network and goes back down. Python RPCs add to every step.

✗ DCN between pods (multislice)

The only way past one slice, and Google supports it. But per chip it's 64–192× slower than ICI on v5e/v5p, so it suits rare, tolerant traffic like data-parallel gradient sums, not every micro-batch handover.

✗ Staying inside one host

All on ICI and easy, but only 8 cores. Pipeline 4 × model 2 = 8 fills the host, leaving no room for data parallelism or a bigger model.

✓ ICI across hosts, within a slice

Chips on host A are wired straight to chips on host B. JAX docs: XLA "automatically exploits high-speed networking links like TPU ICI … between hosts". One hop on v3 is a 200 GB/s link.

If the chips are wired together, why does it feel like 4 machines?

Each host runs its own Python process, and Google's docs say you must start your code on every host. Each process can only feed its own 8 local devices from its own CPU memory, but JAX's processes "are aware of each other", and one compiled program can still move data chip to chip over ICI. The separation is in the software you launch, not the wires. In 2021 the question was which JAX call would do that (see the SPMD and ppermute card).

ICI isn't unlimited, though. It stops at the edge of the slice: two slices, or two pods, only talk over DCN (Google's "multislice"). ICI also only links nearest neighbours, so stage 1 → stage 4 may take several hops, while neighbouring stages need one. If the whole model fits in one host, or you only need data parallelism across slices, the simpler options are fine.
