Collectives vs send/recv

Collectives are also called all-reduce, psum or pmean. Send/recv is also called point-to-point communication. Sholto's post asks for "send/recv style operations in addition to global collective mean, sum", because pipeline parallelism needs the second kind.

In one breath

A collective is a message that every chip in a group takes part in at once. In an all-reduce, everyone hands in a number and everyone gets back the same total. Send/recv is a message between exactly two chips: one hands its data to one neighbour, and nobody else is involved.

The two words, in plain terms

An all-reduce is like a group of friends splitting a bill: everyone says what they spent, and everyone leaves knowing the same total. Send/recv is like passing a parcel along a line: each person hands it only to the next one.

Data and tensor parallelism only need sum and mean, which every tool already offered. Pipeline parallelism is the one that needs to pass data to a single neighbour, which is why the post asks for send/recv.

How they differ

✗ All-reduce for pipeline hand-offs

Every chip takes part and gets the sum. Stage 2 needs a₁ unchanged, not a₀ + a₁ + a₂ + a₃, so a sum is the wrong answer and also wasted traffic.

✗ One-sided "send whenever"

"Stage 3 sends whenever it likes" is not how JAX or NCCL work. NCCL needs a matching receive on the peer, and JAX compiles one program that every chip runs.

✗ Copy through the host CPU

Ray, as used by mesh-transformer-jax, moves the bytes off the chip, across the regular network and back. That works, but the post found the copies made it slower.

✓ ppermute over ICI

All chips run the same shift at once with a fixed list of (source, destination) pairs, and XLA sends it over the chip-to-chip links, even across hosts.

Isn't send/recv a separate command in JAX?

No. JAX programs are SPMD, which means every chip runs the same program. So there is no call where stage 1 alone says "send", and stage 2 alone later says "receive". Instead, every chip runs ppermute together, and the list of pairs tells each one where its data goes. The docs call it a "collective permutation", so it is technically a collective that happens to move data point to point. NCCL is less different than it looks, because its send needs a matching receive on the other GPU too.

When it's not the right tool: for data-parallel gradient averaging, use pmean, not a chain of permutes. When the pattern changes based on runtime data (for example, routing depends on the input), a fixed list of pairs doesn't fit. That last point is our inference from the API, since perm is a plain list of integer pairs. Within one 8-core host, the post expected this to work. The open question was only how to cross hosts over ICI.
