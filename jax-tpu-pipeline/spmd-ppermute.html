SPMD, meshes and ppermute: the JAX answer

Also: single program, multiple data; jax.sharding.Mesh; shard_map; jax.lax.ppermute (XLA's "collective permute"); jax.Array, the "global device array". This is the answer to the post's question: JAX's version of send/recv over ICI between TPU hosts.

In one breath

Every TPU core runs the same compiled program on its own slice of the data. Any communication is written as a collective step inside that program, which every core runs at the same time. ppermute is the step that moves each core's slice to a chosen other core along one axis of the mesh. XLA compiles it into a collective-permute, which runs over the TPU's chip-to-chip links (ICI), even when the two cores are on different hosts.

Worked example: one ring shift on the v3-32

The mesh is [pipe 4, model 2, data 4] = 32 cores. Each pipeline stage is 2 × 4 = 8 cores, and stage s holds layers 6s+1 … 6s+6 of the 24. One call, ppermute(h, 'pipe', perm) with perm = [(0,1), (1,2), (2,3), (3,0)], hands every stage's activations to the next stage.

Which host each stage lands on depends on the device order jax.make_mesh picks from the topology, so stages 2 and 3 may well be on other hosts. The arrow is still ICI: JAX's docs say XLA "automatically exploits high-speed networking links like TPU ICI … between hosts". The 24-layer model is illustrative.

The program behind that picture, written once and run on every host:

# SKETCH, not tested: the same script runs on all 4 hosts import jax from jax.sharding import PartitionSpec as P jax.distributed.initialize() # no args needed on Cloud TPU mesh = jax.make_mesh((4, 2, 4), ('pipe', 'model', 'data')) perm = [(0, 1), (1, 2), (2, 3), (3, 0)] # ring on 'pipe' @jax.jit @jax.shard_map(mesh=mesh, in_specs=(P('pipe'), P('pipe', 'data')), out_specs=P('pipe', 'data')) def step(params, h): # params: this core's stage = 6 layers # h: this stage's activations, 1/4 of the micro-batch h = stage_fn(params, h) # local compute h = jax.lax.ppermute(h, 'pipe', perm) # to next stage return h

The API names match current JAX docs: jax.shard_map (the jax.experimental.shard_map path is deprecated as of 0.8.0) and jax.lax.ppermute(x, axis_name, perm). stage_fn and the shapes are placeholders. A real pipeline also loops over micro-batches, as the JAX docs' "SPMD pipeline parallelism" example does.

How JAX got here

pmapOne copy of the function per device, with collectives named by axis. It was in the earliest JAX releases (the changelog mentions it by 0.1.59, Feb 2020). Since 0.8.0 (Oct 2025) it is "in maintenance mode" and built on jit + shard_map.
→
xmap (experimental)Named axes over a device mesh, the tool in the post. It was deprecated in 0.4.26 (Apr 2024) and deleted in 0.4.31 (Jul 2024): "Please use shard_map() as the replacement."
→
jax.Array + jit sharding + shard_mapjax.Array (introduced in 0.3.18, Sep 2022, and always on since 0.4.7, Mar 2023) is one array spread across many devices. jit splits the work up automatically, and shard_map is the manual per-device mode where ppermute lives.

The words, with two examples each

Think of an orchestra. Every player has the same score (SPMD). The seating chart is the mesh. Each player reading only their own part is shard_map, and passing a sheet to the next chair along the row is ppermute.

Why it beats the alternatives

✗ mpi4jax

Gives JAX MPI-style send/recv, but per the post it has no TPU support. It can't drive the ICI links at all.

✗ Ray

It works (mesh-transformer-jax used it), but per the post the activations get copied through each host's CPU instead of going chip to chip.

✗ Per-device send/recv by hand

NCCL-style "core 5 sends, core 13 receives" code doesn't match how JAX works. JAX compiles one program for every core, so a one-off point-to-point call has no natural home in it.

✓ ppermute inside shard_map / jit

The send/recv becomes one collective that every core runs. XLA lowers it to collective-permute over ICI, across hosts, with no CPU hop.

Does ppermute make pipelining free?

No. First, perm is a plain Python list of (source, destination) pairs, so it is fixed when the program compiles; you can't choose a destination from data at run time. Second, ppermute is a collective: every core on the axis runs it at the same step. A device that isn't a destination gets zeros back, which is why the ring above includes 3 → 0 (the JAX docs' example reuses that edge to carry outputs).

It moves data quickly, but it doesn't fill the pipeline bubble. With 4 stages and 8 micro-batches, 27.3% of the time is still idle. The JAX docs' pipelining example is "essentially the GPipe strategy".

Pipelining also isn't the default on TPU pods. The scaling book calls it "a dominant strategy for GPU parallelism that is somewhat less essential on TPUs", because pods are densely connected by ICI. The book also says pipelining's low traffic between stages suits low-bandwidth links. Our inference from that: on a single well-connected slice, reach for data, FSDP and tensor sharding first, and save pipelining for slow links such as DCN between pods.
