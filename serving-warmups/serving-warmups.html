Serving warm-ups: five rungs to the load-curve lab

Five small projects, in order, that lead up to serving an open model on a rented GPU and measuring its load curve, and one step past it. The first two run on a Mac for free. Each one teaches a single thing the next one assumes.

By the end: you can time a streamed reply by hand, tell a client that isn't sending load from a server that isn't batching, rent a GPU and check a prediction on it, and start the load-curve lab knowing what every number you plot means.

Rung A · Time one streamed reply by hand

After Day 1Your Mac45 minFree

Task. Send one chat request to a model running on your own machine, record the clock each time a piece of the reply arrives, and work out the four numbers every benchmark reports.

Steps

  1. 10 min. Install Ollama and download a small model, the 1-billion-parameter Llama 3.2 (its tag is llama3.2:1b, about 1.3 GB): 
    ollama pull llama3.2:1b
  2. 5 min. Before running anything, write down a guess: how long until the first word appears, and how many tokens per second after that?
  3. 10 min. Run the script. It needs uv, which fetches its one dependency for you. 
    uv run --python 3.12 stream_timing.py
    labs/stream_timing.py
  4. 20 min. Read the script; it is short. Find the line that records a timestamp, and the line that turns the timestamps into gaps. Then run it twice more and see which numbers move: once with the prompt changed to ask for a five-word reply, and once allowing a longer reply, by adding the option that raises the limit on output tokens, --max-tokens 400.

What we saw

warm-up request (includes loading the model): 2.05 s

chunks with text:        120
server's token counts:   36 prompt, 120 output
time to first token:     27 ms
inter-token latency:     mean 23.5 ms, median 23.6 ms, max 38.0 ms
output speed:            42.6 tokens/s   (1 / mean inter-token latency)
end to end:              2.82 s

check: TTFT + (chunks - 1) x mean ITL = 0.027 + 119 x 0.0235 = 2.82 s
share of the wait that was TTFT: 1%

What it teaches

  • The four numbers are just subtraction on a list of timestamps. Time to first token (TTFT in the output) is the first timestamp minus the send time. Inter-token latency (ITL) is the gap between neighbours. Output speed is one divided by that gap.
  • The total is the Day 1 formula: time to first token, plus the gap times the number of tokens after the first. Here 0.027 s + 119 × 0.0235 s = 2.82 s.
  • The first request took 2.05 s because the model had to be loaded into memory. That is a cold start, and it is why the script sends a throwaway request before timing anything.
  • For a short prompt, almost all of the wait is output: time to first token was 1% of it.

Pass. You can say, without looking, how each of the four numbers is computed from the timestamps, and you predicted which one would change when you asked for a longer reply.

Rung B · One at a time, then several at once

After Day 2Your Mac1 hFree

Task. Send the same 24 requests three ways and explain why the totals differ. This is the load-curve lab in miniature.

Steps

  1. 5 min. Guess first: if you keep 8 requests in flight at once, does the server produce 8 times the tokens per second, the same, or something in between?
  2. 10 min. Run it against Ollama. 
    uv run --python 3.12 concurrency.py
    labs/concurrency.py
  3. 15 min. Start a second server that batches: llama.cpp's server with 8 slots, on its own port so it doesn't disturb Ollama. Install it with brew install llama.cpp. The model file path is on the FROM line printed by ollama show --modelfile llama3.2:1b. 
    llama-server -m MODEL.gguf -ngl 99 -np 8 -c 8192 --cont-batching --port 18777
uv run --python 3.12 concurrency.py --base-url http://127.0.0.1:18777/v1
    The option -np 8 gives the server 8 slots to run requests side by side, and --cont-batching turns on continuous batching. The rest is housekeeping: -m names the model file, -ngl 99 puts every layer on the GPU, -c 8192 is the total context shared by the 8 slots, and --port is where it listens.
  4. 30 min. Explain both tables to yourself in writing, then read the notes below.

Each request asked for up to 32 output tokens from llama3.2:1b. One run each; no repeats.

What it teaches

  • A blocking loop is one user, however many requests it sends. Each request waits for the one before it, so the server never sees two at once. Both servers gave about 46 tokens/s. This is the Serving guide's failure F03.
  • Flat throughput has two causes, and latency tells them apart. In the first table, tokens per second stayed between 45 and 50 at every level, about the same as the blocking loop. But mean latency rose from 0.64 s to 4.69 s, which the blocking loop's did not. The requests did arrive together; this server ran them one after another, so they waited in its queue. A client that doesn't send load leaves latency flat. A server that doesn't batch makes latency grow.
  • Batching trades each user's speed for total output. In the second table, going from 1 to 8 in flight raised output from 44.9 to 115.9 tokens/s (2.6 times) and raised each request's latency from 0.71 s to 2.20 s (3.1 times). The gain is already flattening between 4 and 8: each added request now mostly slows the others.
  • Little's law holds on your own numbers. Requests in flight = request rate × time per request. At 8 in flight, 3.62 requests/s × 2.20 s = 7.96. On the first server it came to 6.79, below 8, because a run of only 24 requests ends with fewer than 8 left, and that server works through the last ones one at a time.

Pass. Given only a table like these, you can say whether the load reached the server and whether the server batched it, and you can turn a number of requests in flight into a request rate.

Rung C · Your first rented GPU: predict, then check

Day 3RunPod L4, then an H100 for 1 h6 hAbout $5

Task. The Serving guide's first project, Napkin to meter. On paper, predict a model's weight memory, the memory each token of context takes in the KV cache, how many tokens fit, and the fastest possible decode step. Then start a real server and check each prediction.

Why it comes before the lab. Day 3 has you do the paper half. Do the server half too. It is where you learn the routine work for a few dollars: start a pod, attach a disk that survives restarts, download the weights, start the engine, fetch its counters page. Learning those during the 12-hour lab costs more and teaches less.

Time. The guide sizes it at 6 hours: about 3 on the L4 and 1 on the H100, with the paper half before them.

Pass. The project's own line: after calibrating on the small GPU only, your predictions for the large one are within 10% for KV capacity, and within 25% for the gap between tokens with one request running and for time to first token on a 2,000-token prompt.

Rung D · The load-curve lab

Day 4RunPod L40S 48 GB12 hThe guide budgets $15

Task. The Serving guide's second project, Serving lab v1: serve Llama-3.1-8B with vLLM behind an API, and measure it from 1 to 128 users at once.

Two gates before the full sweep.

  1. Write the prediction first, about 20 minutes. At which level does the curve bend? Which limit breaks first, time to first token or the per-token time? How full is the KV cache at that point? Commit it to your repo before the first run.
  2. Do the project's "first 90 minutes" as its own small run, 90 minutes. Start the server, stream one reply, then measure at 1 and at 32 in flight while watching the engine's count of running requests. If that count doesn't reach 32, stop and fix the client (rung B taught you why).

Day 4 of the study path is the reading for this rung.

Rung E · Past the lab

After rung DSame L40S
  • A fixed-rate sweep, about 3 h. The lab's sweep holds the number of requests in flight fixed, so it waits for replies and can never overload the server. Add three or four runs that send at a fixed request rate instead, between the lab's slowest and fastest measured rates, then one with bursty arrivals. This is the test that shows a queue growing without limit. See the guide's failure F21 and Queueing and the knee.
  • Then the guide's third project, about 14 h: Prediction Ledger v0. Change one setting per run and commit a numeric prediction before each. It reuses this GPU, so the lab's curve is the baseline. Day 7 of the study path is the reading for it.

Where to serve it

For the curve: a RunPod pod with one L40S (48 GB), about $0.79 an hour. The Serving guide uses it for three reasons.

  • The 8B model's weights take about 16 GB, so most of the card is left for the KV cache. The curve then bends because of batching and queueing, which is what you want to study, and not because memory ran out.
  • A pod is one GPU that is yours for the hour, so repeated runs give the same numbers.
  • The third project stores the weights in a smaller number format (8 bits per weight instead of 16), and this GPU has hardware support for it.

Not a serverless platform for the curve. Platforms such as Modal start containers on demand, which adds start-up time and an extra network hop to your measurements. The guide's capstone keeps Modal for a later experiment that measures cold starts on purpose.

Before you start. Attach a network volume so the weights survive a pod restart. Llama 3.1 needs approval on Hugging Face, so request access the day before. Our own suggestion, not the guide's: run the load generator on the pod itself, so network time stays out of time to first token, then do one run from your laptop to see what the network adds.
