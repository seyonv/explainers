Retry, replay, resume

Also called durable execution, durable workflows or workflow engines (Temporal, Restate, DBOS, LangGraph persistence). Govindarajan's Agent Stack Part 4 puts it in the runtime layer, which "owns progress, not ultimate authority"; his OpenClaw Part 6 shows the same discipline in one real gateway.

Prime · 2 minutes before you read

The problem: An agent run that pushes a branch, waits for CI and asks for approval can be interrupted at any point. If the worker restarts and nothing recorded what already happened, the system either starts over (and pushes, emails or charges twice) or guesses where it was.

Where it fits: Second card of the Runs course. Owning the session gave the control plane the source of truth for the run; this card gives the runtime its job: moving that run forward across time without repeating side effects. It builds on the agent loop you already know, which is only the hot path inside one run.

In one breath. An agent run that pushes branches, waits for CI and asks for approval is not one request but a run that crosses time. Durable execution means the runtime writes down each step's progress before the world becomes ambiguous, so after a crash it can continue from where it was instead of starting over and doing a side effect twice.

You already know: the agent loop. The loop is the hot path inside one run; this card is about what survives when the process running that loop dies.

Four words that get collapsed

The post's warning: these are related but not interchangeable, and each one fails in a specific way without the others. Think of a restaurant ticket rail: the rail (journal) says which dishes are already out, so a new cook can pick up the order without sending a second steak.

Waiting is state, and a queue is not a workflow

Waiting is not sleeping. A long run spends most of its time waiting on CI, a human, a webhook or a timer. A weak runtime holds a blocked process; a strong one writes the wait down. An approval is a decision about one pending action in one run, so the record has to say which action, from which state, who may approve it, and what happens if nobody answers (record illustrative):

{"run": "run-1", "step": 5, "wait": "approval", "action": "open_pr", "diff": "sha of the pushed commit", "approver": "maintainer", "on_timeout": "fail run"}

If the diff changes while it waits, the approval no longer matches, which is exactly the post's question "is the approval still valid after the diff changed?". A CI webhook is the same shape: evidence that wakes one run, branch, commit and step, re-entering through the control plane.

Delivery is not progress. SQS standard queues are at-least-once: a message can arrive more than once and out of order, and AWS tells you to make processing idempotent. That is a queue guarantee, not a workflow guarantee: the queue doesn't know that step 4 of 7 already finished. Not from the posts, general practice: "exactly-once" in practice means at-least-once delivery plus an idempotent consumer, so each effect lands once. When an effect can't be made idempotent or must be undone after a later failure, a saga runs a compensating step (delete the branch, close the PR).

Why it beats the alternatives

✗ Plain retry loop

State lives in process memory. A crash after a partial side effect means starting over and repeating it; the post's fix is "not a better prompt" but step boundaries, recorded progress and idempotency.

✗ Queue + worker

Buffers work and smooths spikes, but delivers at least once and doesn't know which step of the run finished. Use it under a workflow, not instead of one.

✗ Background task

Avoids client timeouts (OpenAI's background mode), but the post says it does not automatically give replay, step-level recovery, approval persistence or side-effect dedupe. It can still lose its place.

✓ Durable workflow

Temporal's Event History, Restate and DBOS journals of step results, LangGraph checkpoints in threads with interrupts. Different shapes, same rule: deterministic workflow logic, side effects behind recorded step boundaries.

Is durable execution always worth it, and does it make the run correct?

Not always. The post says a plain loop is often enough for one turn: a question, a retrieved document, an answer. No webhook, no later approval, no restart to recover from, no side effect to protect. Add a workflow engine when the run waits, crosses restarts or changes the outside world.

And it doesn't make the run right. The runtime owns progress, not truth. In the Tuesday run (illustrative), a journal would faithfully record that step 6's pytest exited 1, and that step 9 said "all tests pass". Resuming or replaying reproduces that false claim exactly. Recording that a step ran is not checking that it worked; that's the next card.

"Replay" is used two ways. In Temporal it means rebuilding state from the event log. OpenClaw's Gateway says plainly that it does not replay events on sequence gaps; clients refresh state and recover from durable artifacts. Govindarajan's line: recovery is not replay. Ask which one a system means before trusting it.

1 · Core model what to internalise, what to just look up

Keep it if it changes what you can explain, predict, compare, choose, build or debug. Otherwise it's reference.

Understand and remember

  • A side effect happens in the outside world → the runtime can only record it a moment later → a crash in that gap leaves the run unsure whether the effect landed → re-running the step duplicates it unless the effect carries an idempotency key the outside system dedupes
  • Progress kept only in process memory → a restart forgets which steps finished → the run starts over → every earlier side effect repeats and every model step is re-rolled (14.10 steps per run vs 7.50 with a journal at a 0.2 crash rate)
  • Journal and key solve different problems → the key removes duplicate effects, the journal removes rework → you need both (journal alone 0.50 duplicates per run, key alone 14.10 steps per run)
  • Replay re-executes workflow code against recorded history → any non-deterministic call inside it (model, API, random choice) gives a new answer → workflow logic must be deterministic and side effects must sit behind recorded step boundaries
  • detail that matters Waits and approvals are written down as state tied to one pending action in one run (run, step, action, the diff it was asked about) → a restart doesn't lose them, and an approval for an old diff can be detected as stale instead of silently applied

Reference only

  • product names: Temporal Event History, Restate and DBOS journals, LangGraph checkpoints, threads and interrupts, OpenAI Agents SDK interruptions
  • SQS standard queue semantics (at-least-once, possibly out of order)
  • OpenClaw's inbound dedupe cache and its retry policy setting names
  • the illustrative crash probability 0.2 and the six step names

    Check

  2. mechanism Walk through the 'journal + key' trace after the crash: what is skipped, what re-runs, what does the git host do, and why?
    Check

    • push was not recorded (the crash came first), so it re-runs

  3. mechanism Why does the journal-only strategy give 0.50 duplicate effects per run at a 0.2 crash rate? Derive it.
    Check
    • each step runs until it survives: 1/(1−0.2) = 1.25 times on average
    • so each side-effect step runs 0.25 extra times
    • two side-effect steps × 0.25 = 0.50
  4. tradeoff Your team proposes 'just put every step on an SQS queue with retries' instead of adopting a workflow engine. What do you gain, what do you still lack, and what would you add?
    Check
    • gain: buffering, decoupling, redelivery after failure
    • lack: knowledge of which step of the run finished, persisted waits and approvals
    • at-least-once delivery means duplicates, so consumers must be idempotent
    • add a recorded run state or workflow on top; delivery is not progress

5 · Predict commit to an answer before revealing

Change the run so there are four side-effect steps instead of two (push, open PR, post a CI status, email the maintainer), still with a journal and no keys and a 0.2 crash rate. Commit to a number: duplicate effects per run, and the share of runs with at least one duplicate.

Reveal

Each side-effect step runs 0.25 extra times on average, so 4 × 0.25 = 1.00 duplicate per run. The chance no side-effect step crashes is 0.8^4 = 0.41, so about 59% of runs have at least one duplicate. More side effects make keys more important, not less; the journal alone doesn't help with the gap.
