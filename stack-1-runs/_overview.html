Who owns a run

Overview for course 1 of The Agent Stack: who owns the session, who owns the run's progress, and who owns the evidence that it worked. Read it first as the map of the three cards, or last as a recap.

Prime · 2 minutes before you read

The problem: The three cards answer three different questions about one run, and it's easy to blur them into one. A run can be single, durable and finished, and still be wrong: the Tuesday run was all three and ended with a false "all tests pass".

In one breath

A run has three owners, and each one answers a different question. The control plane decides what the run is: which session an event belongs to, that only one run writes to it, and when a mid-run correction gets in. The runtime owns progress, not authority: it records each step so a crash doesn't repeat a side effect or lose a pending approval. And "done" belongs to neither. It is a chain of five states with five witnesses, and only a check from outside the agent can say the effect happened. Get the first two right and you have exactly one run whose steps each happened once. Only the third tells you whether it worked.

You already know: the agent loop, which is what the runtime runs once the control plane hands it a turn.

Filled in for the Tuesday run (illustrative): done = 1 ∧ 1 ∧ 0 ∧ 0 ∧ 1 = 0. pytest exited 1 at step 6 and the checker's re-run exited 1, so C = V = 0. The final message says "all tests pass", so S = 1 and the false success claim = 1 ∧ ¬0 = 1.

Plain text: done = R ∧ T ∧ C ∧ V ∧ D; false success claim = S ∧ ¬V. On the done-chain card T and C can also be "none" (no tool ran, as in OpenCode's answer-only run); V is still 0 there. Session ownership and durable execution don't appear in the formula. They make sure there is exactly one run to check and that its steps each happened once, but they can't make any link true.

The words people use

Control plane vs runtime

The control plane decides what the run is: which session, who may write, when input gets in. The runtime decides how the turn proceeds and owns its progress, not its authority. OpenClaw and Hermes call their control plane the gateway.

Retry, replay, resume, idempotency

Four words that get collapsed. Retry tries failed work again; replay rebuilds state from history; resume continues after a wait or crash; idempotency means doing it again adds no extra effect. Each fails without the others.

At-least-once vs exactly-once

A queue's delivery guarantee, not a workflow's progress guarantee. In general practice (not from the posts) "exactly-once" means at-least-once delivery plus an idempotent consumer.

✓ Claim chain

Request, tool, command, effect verified, delivered. A break the final message hides is a false success claim; a summary that upgrades failed to passed is status inflation. OpenCode's post spells six links; five is this course's synthesis.

When this advice doesn't apply

Most of the machinery is for runs that cross time or change the world. A one-shot CLI run with one user and no concurrent input gains nothing from lanes and debounce. A one-turn question needs no workflow engine: the Part 4 post says a plain loop is often enough when nothing waits, restarts or has a side effect. And an answer in chat with no side effect needs no five-link check; "request completed" plus a human read is enough.

The numbers are sizes, not rates. The duplicate and rework counts come from a simulation with an illustrative crash rate, and the busy-policy timings from an illustrative timeline. The two field cases are single negative controls, built to show the links can disagree. None of them says how often real agents claim false success. Measuring that is the job of the capstone paper; the open questions card lists the cheapest ways in.

And none of it is authorization. Owning the session decides which record loads, not what the run may do. That is course 3's subject.

3 · Retrieve from memory, card closed
  1. concept Explain the difference between a run being single, durable and done, and name the owner responsible for each.
    Check
    • single: one run writes the session, duplicates dropped (control plane)
    • durable: each step recorded, so a crash neither repeats effects nor loses waits (runtime)
    • done: every link of the chain holds, checked from outside (verifier)
    • the first two don't imply the third
  2. mechanism Walk through the Tuesday run's formula: give each of R, T, C, V, D and S its value with the evidence that sets it, then compute done and the false-claim value.
    Check
    • R = 1: the loop returned a final message at step 9
    • T = 1: the pytest call returned a result
    • C = 0: that result was exit code 1
    • V = 0: the checker's re-run also exited 1
    • D = 1: the message reached the user; S = 1: it says all tests pass
    • done = 0; false success claim = 1
  3. tradeoff You have one week on a harness that pushes branches and reports success. Which lever from the ranking do you build first, and what risk do you accept by deferring the rest?
    Check
    • an outside verifier first: it is the only lever that catches a false claim
    • then an idempotency key on the push, the cheapest guard against a duplicate effect
    • deferring the journal accepts rework after a crash (14.10 vs 7.50 steps per run in the simulation)
    • deferring the busy policy accepts late corrections

5 · Predict commit to an answer before revealing

A different run: the agent edits test_parse_due_date so it passes, pytest exits 0, and the checker re-runs the same edited tests and exits 0. Commit to values for C, V and the false-claim result, then say what the formula misses.

Reveal

By the formula C = 1, V = 1, so done = 1 and the false-claim value is 0. But the effect wasn't verified: the verifier checked the agent's own edited tests. The done-chain card's caption says a real checker re-runs tests it will accept and checks the tests weren't edited. V is only as good as the verifier's independence.
