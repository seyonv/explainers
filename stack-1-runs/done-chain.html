'Done' is a chain of states

Also called the claim chain; when it breaks you get a false success claim, and when a summary hides the break, status inflation. Govindarajan's Hermes Part 4 cron run and his OpenCode Part 1 scripted-provider runs are two field cases where the layers disagreed.

Prime · 2 minutes before you read

The problem: An agent says "Done, all tests pass" and its process exits cleanly. If you treat that as one fact, you ship failed work: the sentence, the exit status and the state of the repo come from different parts of the system and can disagree.

Where it fits: The third card of the runs course. Owning the session asked who owns a run and Retry, replay, resume asked who owns its progress; this card asks who owns the evidence that the run actually worked.

  1. In the Hermes cron run, which owner said "completed", and why was it not lying about what it owns?
  2. Why can OpenCode's shell tool "complete" while the command it ran failed?
  3. Both OpenCode runs printed the same sentence: which single piece of evidence tells them apart?
  4. Where in the Tuesday run did "failed" first become "passing", and which link did that hide?
  5. Why must the verifier sit outside the agent rather than read the agent's own test output?

In one breath. "Done" is not one fact. It is five separate states: the request finished, the tool call finished, the command succeeded, the change in the world was checked, and the result reached someone. Each one needs its own evidence and is owned by a different part of the system, so any later link can be false while every earlier one is true, and the agent's final sentence proves only the first.

You already know: every way a run ends (a run "ending" is the first link only) · grade the outcome, not the claim (the fourth link, done at scale).

Where the claim came from: the step-7 compaction summary already said "tests passing" over an exit-1 result. That upgrade from failed to passed is status inflation; the final message just repeated it. See compaction is a lossy state change.

A tiny claim checker

Three inputs, each from a different owner: the agent's last words, the test command's exit code (None if nothing ran), and whether the files you will accept actually changed.

def check(final_message, exit_code, diff_nonempty): v = {} v["request completed"] = "yes" if final_message else "no" v["tool completed"] = "yes" if exit_code is not None else "none" if exit_code is None: v["command succeeded"] = "none" else: v["command succeeded"] = "yes" if exit_code == 0 else "NO" ok = diff_nonempty and exit_code == 0 v["effect verified"] = "yes" if ok else "NO" claims = bool(CLAIM.search(final_message or "")) v["delivered"] = "yes" if final_message else "no" v["false success claim"] = "YES" if claims and not ok else "no" return v

Toy simplification: one exit code stands in for both the agent's test run and your re-run, and "verified" is just "files changed and exit 0". A real checker re-runs the tests itself, on the files it will accept, and checks the tests weren't edited.

Why it beats the alternatives

✗ Trust the final message

Two OpenCode runs ended with the identical sentence; only one changed the file. The sentence is evidence of link 1, nothing more.

✗ Trust the process or scheduler status

Both OpenCode CLIs exited successfully, and the Hermes ledger said "completed" over two exit-2 commands. A lifecycle state describes the attempt, not the task.

✗ Trust the tool record

OpenCode's shell tool can finish normally and carry a nonzero exit code as metadata. "Tool completed" says the call returned, not that the command worked.

✓ Evidence per link, checked from outside

Keep a separate record for each link, and decide "done" with a verifier that re-checks the artifact you will accept: the diff, the unchanged tests, the receipt.

Does every task need all five links checked?

No. A question answered in chat has no side effect, so "request completed" plus a human read is enough. The chain matters once an agent changes something outside the transcript: files, records, deployments, scheduled work that runs with nobody watching.

A green link 4 is also bounded. OpenCode's verifier ran three unchanged tests: useful evidence but, as he puts it, not exhaustive correctness, and the verifier itself has an owner and a scope. And both field cases are single negative controls built to show the layers can disagree; they say nothing about how often real agents claim false success. Measuring that rate, by harness and by link, is the job of the capstone paper.

Understand and remember

  • Each link is recorded by a different owner (runtime, tool layer, process, verifier, channel) → each owner only reports its own lifecycle → a later link can be false while every earlier one is true → "done" must be decided per link, not from the last message
  • The final message is written by the model at the end of the loop → it is evidence only that the request completed → identical sentences can sit on top of a changed file and an unchanged one (OpenCode) → define done against the artifact you will accept
  • A tool returns a nonzero exit code as data, not as an error → "tool completed" stays true while "command succeeded" is false → a harness that checks only tool status, or a summary that drops the exit code, upgrades failure to success (status inflation)
  • The agent can misread, mis-summarize or edit its own evidence → effect verification has to be done by an owner outside the loop, on the final files, with unchanged tests → otherwise link 4 is just another claim
  • detail that matters A scheduler ledger records the attempt, not the operation → Hermes cron said "completed" while both commands exited 2 and no receipt existed → scheduled work needs its own operation-level verifier and receipt, because nobody is watching when it runs

Why this step?

4 · Compare against what you already know

vs Measuring an agent: Agent evals grade the outcome with hidden tests; this card verifies one run's links. What is fundamentally the same, what differs in scale and purpose, and how does each fail?

Check
  • same: both trust the final state of the artifact, checked from outside, over the agent's claim
  • evals score many tasks × trials to estimate a pass rate; the claim chain decides whether one run's "done" is true
  • evals fail with visible or weak tests and too few tasks; the chain fails when the verifier is in-band or its scope is too narrow (three tests)
  • the false claim rate is what you get by running the chain check across an eval set

vs Retry, replay, resume: Retry and resume make a run survive a crash. Why doesn't a successful resume prove the work was done, and which link does a durable runtime own?

Check
  • a durable runtime owns progress: which step ran, what to replay
  • a completed workflow is link 1 (and maybe 2), the same as the Hermes ledger's "completed"
  • after a crash mid-side-effect, the runtime may not know whether the effect happened; only an effect check settles it
  • so durable execution and the claim chain answer different questions: did it finish vs did it work

Why this step?

5 · Predict commit to an answer before revealing

You add a rule to the harness: the agent may only say "done" if its last pytest call exited 0. Which false claims does that stop, and name one it still lets through.

Reveal

It stops the Tuesday-run kind, where the last test exit was nonzero. It does not stop a run that edits or deletes the failing test and then gets exit 0, a run that tested in the wrong working directory (like Hermes's goal run watching the wrong state), or a run whose tests don't cover the bug. All three keep link 3 green with link 4 false, because the rule is still checked by the agent's own evidence, not by an outside verifier on the files you'll accept.
