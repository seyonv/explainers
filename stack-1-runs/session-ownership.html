Owning the session

Also called the control plane, the session layer or (in OpenClaw and Hermes) the gateway. In Govindarajan's posts it is the part that turns every incoming message, webhook or timer into an ordered write on exactly one session, and decides what happens when a new message lands while a run is still going.

Prime · 2 minutes before you read

The problem: Messages, webhooks and timers arrive whenever they like, but a session can only take one change at a time. Without a part of the system that owns the session, two runs write the same transcript, a redelivered message triggers a second run, and a mid-run correction is either ignored or cuts into a running tool.

Where it fits: First card of the Runs course. The agent loop showed what happens inside one turn; this card is the layer that decides which turn runs, on which session, and when. The next card (retry, replay, resume) is the runtime underneath it.

In one breath. Messages arrive whenever they like; a session can only take one change at a time. The control plane sits between the two. It drops duplicates, merges bursts, works out which session an event belongs to, lets only one run write to that session at a time, caps how many runs go at once, and follows a named rule for a correction that arrives mid-run. The runtime then runs the turn. In his words, the control plane decides what the run is; the runtime decides how the turn proceeds.

You already know: the agent loop, which is what the runtime runs once the control plane hands it a turn.

The order OpenClaw uses (post 02): per-session lane first, then the global lane, then the run. A run starts only once it holds both lanes. Green = the two lanes that decide who may write. The diagram is mine; the parts are his.

Then the busy policy decides when the correction lands

One writer per session means the correction can't start its own run. What happens instead is a setting, not model behaviour. OpenClaw calls these queue modes; the right-hand column comes from running the simulation on the timeline above.

The trade the post names: ignore the correction (collect, followup) or preempt inside a tool call, which it calls unsafe (interrupt). Steer takes a third option and preempts only at tool boundaries. He notes that on some surfaces steer behaves more like a follow-up. In the simulation, followup and collect differ only in the merging, which debounce already did.

Why it beats the alternatives

✗ Key sessions by user ID

Two unrelated tasks from the same person share one transcript and one scratch state. Post 09 says it looks coherent until it does something obviously wrong.

✗ Trust the database lock

Hermes's SQLite store allows one writer at a time, but post 22 calls that a database rule, separate from the gateway's rule about two turns changing one conversation. My reading: a lock per write still lets two turns interleave their writes.

✗ No named busy policy

A mid-run correction either waits until after "Done" or cuts into a running tool, and nobody chose which. Post 02's word for a system whose invariants aren't enforced: "haunted".

✓ A control plane that owns the session

Dedupe and debounce at the door, one run per session lane, a global cap, a named busy policy and idempotency keys on side effects. Every arrival has one defined outcome.

Does one writer per session make the run safe?

No. Govindarajan calls serialization "necessary, not sufficient". It keeps one session's history in order, but two different sessions can still change the same outside resource, a tool that isn't idempotent can still do damage twice, and a long tool call can finish on stale assumptions. It also does nothing about Tuesday's false "Done": that is the claim chain's problem. Session ownership isn't authorization either: post 09 keeps "which record do I load?" apart from "what may this run do?".

Check how far the guarantee reaches. OpenClaw's queue is a small in-process queue, so my reading is that its one-writer rule holds inside one gateway process. The Hermes post's checklist asks you to say whether yours is process-local or distributed. Across processes it is harder: Hermes Part 4 points to a public two-writer incident on Hermes's task board (issue #83736), where a claim was taken over while the first writer was still running. He did not reproduce it himself.

When it's not what you want: a one-shot CLI run with one user and no concurrent input gains nothing from lanes and debounce. And sometimes sharing is the point. Hermes (v0.19.1) shares a threaded chat as one session by default, so a team thread is meant to be one conversation.

Understand and remember

  • One run per session lane → a correction can't start a parallel run on the same transcript → no interleaved tool calls or duplicate sends → but now something must decide when the waiting message gets in (the busy policy)
  • Busy policy is a setting, not model behaviour → collect/followup wait for the run to end (correction lands after the damage) → interrupt aborts at once (preempts inside a tool call) → steer checks after each tool call and skips the rest of that message's calls (safe boundary, small delay)
  • Real channels redeliver and humans type in bursts → dedupe on (channel, peer, session, message id) drops repeats and debounce merges a burst into one turn → each human intent becomes exactly one queued turn → fewer surprise runs
  • Serialization covers one session's history only → two sessions, non-idempotent tools and stale assumptions are untouched → idempotency keys on side effects and a global cap are separate guarantees, and none of them makes a 'Done' true
  • detail that matters OpenClaw's queue is small and in-process → its one-writer guarantee is (my reading) process-local → run two gateway processes and the lane no longer stops two writers; that is the distributed lease problem behind Hermes issue #83736

Reference only

  • the five queue mode names and which one is default (collect)
  • messages.inbound.debounceMs, agents.defaults.maxConcurrent, lane names session:<key> and main
  • Hermes key shapes like agent:main:telegram:dm:… and the state.db location
  • the illustrative timings (10.0 s, 10.8 s, 11.8 s, 13.0 s, 14.0 s, 30.0 s) and 1.0 s debounce window

    Check
    • the database rule is per write; a turn is many writes
    • two turns could alternate writes and both be 'valid' to SQLite
    • the semantic rule is about who owns the conversation, not storage locking

vs The agent loop: The agent loop card owned the loop from one request to 'Done'. What does that card silently assume that this card makes explicit, and how does each fail when the assumption breaks?

Check
  • the loop assumes one caller and a conversation nobody else writes to
  • the control plane enforces that: one run per session, ordered inbound events
  • the loop fails inside a turn (bad stop reason, budget); the control plane fails between turns (two writers, duplicate run, lost correction)

vs Retry, replay, resume: Dedupe on message id and idempotency keys on side effects both make 'the same thing twice' happen once. What is fundamentally different about where each sits and what it protects?

Check
  • dedupe sits at the door and protects against a second run being started
  • idempotency keys sit at the side effect and protect against a retried action in the world
  • a run can be correctly single and still retry a send, so you need both
  • durable execution adds the runtime's view: replaying a step must not redo its effect
