The questions

1Does compaction turn a failed check into a claimed pass, and how often?

capstone: compaction → false success claimsstatus: opencost: ~$150–250 (the capstone plan)
Why it matters
If it does, a long run's final message is least trustworthy exactly when the run was longest, and the fix belongs in the summarizer, not the model.
Status
Open as a measured, causal question. The only direct evidence is a single-author Claude Code case study with no run counts: Tamba, "Compaction as Epistemic Failure" (arXiv 2607.13071), where partial output from killed processes was written into summaries as confirmed. Adjacent: Hu, "Silence Is Endorsement: Verification-Status Laundering" (arXiv 2609.20211), on summarizers dropping "unverified". The writer flagged 2609.20211 to check for capstone novelty.
Smallest experiment
Run the Tuesday task with compaction forced right after the failing pytest, and again with a context large enough that it never compacts. Score every final message with the done-chain checker and compare the false-claim rates.
Source card

2When a model step re-runs after a crash, how often is the new diff different from the one already pushed or approved?

status: opencost: under $20
Why it matters
Restart plus a key shows zero duplicate effects, but the key dedupes on the step, not the content. A different re-rolled diff would sit behind an approval given for the old one, and nothing would flag it.
Status
Open: the writer found no study of replay safety for agent steps.
Smallest experiment
From one recorded state, re-run only the edit step many times, hash each diff, and count distinct hashes. Then check whether the approval record's diff sha would have caught each change.
Source card
Retry, replay, resume

3In production coding CLIs, which link of the claim chain breaks, and how often?

capstone: the claim checkerstatus: partly studiedcost: $100–500
Why it matters
A per-link rate tells a harness builder where to put the check: if most false claims follow a nonzero exit, reading the exit code is enough; if they follow a passing run on edited tests, it isn't.
Status
Partly studied, at run level only. OverclaimBench (arXiv 2609.20812) measures overclaiming in native CLIs but covers file-review tasks, not fix or test claims. Advani, "From Confident Closing to Silent Failure" (arXiv 2606.09863) defines false success on tau2-bench and AppWorld, with no coding CLIs.
Smallest experiment
On a small fixed set of failing-test tasks, record each harness's final message, last exit code and diff, run them through code/done-chain.py, and tabulate the first link that goes false.

4Does an evidence contract cut false claims in a coding agent, or just move the failure to link 4 (edited tests)?

capstone: the claim checkerstatus: partly studiedcost: low, one extra arm (~$50)
Why it matters
If a prompt-level contract works in a real harness, it's the cheapest fix there is. If the agent satisfies it by editing the tests, a contract without an outside verifier is worse than none, because it looks safe.
Status
Partly studied. Failure-Transparent Agents (arXiv 2609.35732): false success fell from 22.8% to 0.8% with a structured evidence contract, on fixed deterministic failure traces, single-turn. Goal-Autopilot (arXiv 2606.11688) gates completion on SWE-bench Lite, but in a research scaffold. A production coding harness is untested.
Smallest experiment
Add one rule to the system prompt: the final message must quote the last test command and its exit code. On the same tasks, with and without it, count false claims and diffs that touch test files.
Source card

5For corrections that arrive mid-run, which busy policy gives the best outcomes: collect, steer or interrupt?

status: opencost: moderate
Why it matters
The policy is a setting nobody measures. The card's simulation shows when a correction reaches the model, not whether the run ends better.
Status
Open: the writer found no comparison.
Smallest experiment
In a harness with named queue modes (OpenClaw's), script one correction arriving during a long tool call, run the same task under each mode, and count runs where the action the correction forbade still happened.
Source card
Owning the session

6What share of agent incidents are two-writer or duplicate-run bugs?

status: open for agentscost: low–moderate
Why it matters
It says whether session ownership deserves engineering time compared with the model-side failures that get the attention.
Status
Open for agent harnesses. The method exists for distributed systems: TaxDC-style issue mining (Leesatapornwongsa et al., "TaxDC", ASPLOS 2016).
Smallest experiment
Label closed issues in one open-source agent gateway's tracker for "two writers", "duplicate run" and "duplicate send", starting from Hermes issue #83736.
Source card
Owning the session

7Under crash injection, how many duplicate side effects do real harnesses and gateways produce?

status: open for agentscost: low–medium; ~1 week for a Jepsen-style rig
Why it matters
The card's 1.70 duplicates per run is a simulation. A real number per harness would tell users which ones are safe to point at a live repo or inbox.
Status
Open: no fault-injection study of agent runtimes or gateways was found by either writer who raised it.
Smallest experiment
Kill the worker right after a push to a local git remote, as in the card's trace, let the harness recover, and count pushes and PRs per run.

8Does journalled progress reduce false claims, or only duplicates?

status: unknowncost: medium
Why it matters
A journal keeps the step-6 exit code on record. If resumed runs claim less falsely than restarted ones, durability helps honesty for free; if not, the card's "owns progress, not truth" holds in practice too.
Status
Unknown: the writer didn't know of any work.
Smallest experiment
Inject a crash after the failing test step; resume half the runs from a journal and restart the other half; score the final messages with the done-chain checker.
Source card

How to generate your own

  1. Split an overloaded word. His move on every card: "done" became five links, "replay" became retry, replay, resume and idempotency, "session" became key and ID. Each split makes a new thing you can count. Pick a word your harness uses for two things ("completed", "approved", "resumed") and ask which one the log records.
  2. Ask what's unmeasured. Every field case in this course is a single negative control and every number a simulation. "How often, in which harness, at which link?" is open almost everywhere.
  3. Check for a cheap controlled experiment. Hold the model and the task fixed and change one harness setting: compaction on or off, one busy policy, a journal or a restart. If it fits in a day and under a few hundred dollars, it's worth asking.

4 · Compare against what you already know

vs 'Done' is a chain of states: The done-chain card's two field cases are negative controls; question 3 asks for rates. What does a negative control prove that a rate can't, and the other way round?

Check
  • a negative control proves the links can disagree, with a mechanism you can see
  • it says nothing about how often
  • a rate says how often and where, per harness and link
  • but a rate needs a validated checker, and the control is what shows the checker works

vs Retry, replay, resume: That card's simulation gives 1.70 duplicate effects per run under restart; question 7 asks for the real number. Which assumption of the simulation would a crash-injection study test first?

Check
  • the simulation always crashes in the gap after the effect and before the record
  • its crash rate of 0.2 is illustrative
  • a real harness may record before acting, retry inside a call, or dedupe downstream
  • so the real count could be far lower or higher; only injection tells

5 · Predict commit to an answer before revealing

Question 4's rule: the final message must quote the last test command and its exit code. In a coding harness, predict whether false claims fall, and what else you would see in the diffs if the agent games the rule.

Reveal

Nobody has measured it; that is why it's open. On fixed traces the evidence contract cut false success from 22.8% to 0.8%, so a fall is plausible. But a harness agent can make the exit code 0 by editing the tests, so watch for a rising share of diffs that touch test files. That is the failure moving to link 4, which is why the experiment counts both.
