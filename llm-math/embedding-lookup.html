A token becomes a row of a table

Embedding lookup, token embeddings, nn.Embedding, one-hot times a matrix · Raschka §2.7

Prime · 2 minutes before you read

The problem: The tokenizer gives the model integers, but every layer after it multiplies and adds vectors. Feed it the raw ID and the model treats sat = 2 as "twice cat", an order and a size that the word list never meant.

Where it fits: First step of the forward pass. It reuses the matmul from the tools cards: a lookup is a one-hot row times a matrix. The next card adds position information to the same rows.

The tokenizer hands the model a list of integers, and a network can only do arithmetic on vectors. So the first step is a lookup: each ID picks one row of a learned table, and that row is the token's vector. The lookup is exactly a one-hot vector times the table, which is why training can change the table like any other weight.

The ID is a label, not a quantity

Why not skip the table and feed the ID itself? Because cat = 1 and sat = 2 is just the order the words were listed in. "1 is less than 2" means nothing about cats and sitting. But any number you feed into a layer gets treated as a size.

With the ID as a number, all five words lie on one line, and the order of the word list decides their geometry. With a table, each word gets its own row, and nothing ties one row to another. Cosine similarity is 1 when two vectors point the same way; 0.1912 means cat and mat point in different directions.

The second half of the reason: the 20 numbers in EEE are weights. They start random, and training moves them so that words used alike end up with similar rows.

Look it up, don't multiply it out

The one-hot form is how you reason about the lookup. The lookup is how you compute it. For one token, the product does 5×4=205 \times 4 = 205×4=20 multiply-adds, and 16 of them are multiplications by zero. The lookup copies 4 numbers.

At Qwen2.5-0.5B's size the gap is enormous: the one-hot product would be 151,936×896=136,134,656151{,}936 \times 896 = 136{,}134{,}656151,936×896=136,134,656 multiply-adds per token, to produce 896 numbers that a lookup simply copies. nn.Embedding is that lookup.

The backward pass only reaches the rows you read

A gradient dEdEdE has the same shape as EEE. Each entry says how much the loss would change if you nudged that entry of EEE. (The Part 2 cards compute these. Here we just read them from tiny.py.)

← scroll the sketch →

Rows 0–2 of dEdEdE are the gradients that arrived at x0x_0x0​ for each token, sent back into the row that token read. Rows 3 and 4 (on, mat) are exactly 0, because those rows never touched the loss. One plain gradient step leaves them where they were.

This is the one-hot picture again, run backwards: the 0s in the one-hot vector that wiped out rows going forward also block any gradient from reaching them.

Principle

Give every token its own learned row, and let training place it

An ID only says which token it is. A table row can say what the token is like, because training moves it. A lookup is the cheap way to compute one-hot times the table, and the one-hot view explains the gradient: only the rows you read get one.

Buys you: a free vector per token with no order built in, at the cost of copying dmodeld_{\text{model}}dmodel​ numbers.

Raschka §2.7; measured in labs/embedding-lookup.py and labs/tiny.py

Where this simplification breaks
  • Tokens are pieces of words. Real tokenizers split text into subword pieces, so one word can be several rows.
  • Tied embeddings. Qwen reuses EEE as its output head (weight tying, Raschka §4.6), so every row also gets a gradient from the output scores on every step, read or not. The "unread rows get 0" rule holds for a separate output head, as in this tiny model and Raschka's own GPT.
  • Optimizers can still move unread rows. With Adam, a row's leftover momentum from earlier steps keeps moving it, and weight decay shrinks every row. Plain SGD, as in the sketch, doesn't.
  • Rare tokens train slowly. A row only learns on the steps where its token appears, so rarely used tokens keep rows close to their random start for longer.
  • Learned PPP has a fixed length. It has one row per slot (3 here, 1,024 in GPT-2), so there's no row for a longer input. That's one reason newer models rotate instead.
