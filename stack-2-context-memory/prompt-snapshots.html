Prompt snapshots and freshness

Also called a frozen or session-start system prompt; the freshness side is sometimes called write-to-visibility lag. Govindarajan tested it in Hermes Agent v0.20.1: editing the user-profile file USER.md mid-session did not change the next model request; the new profile showed up only after compression rebuilt the prompt, under the same session ID.

Prime · 2 minutes before you read

The problem: You tell an agent something durable (edit USER.md, save a memory, add a rule) and it keeps acting as if you hadn't. The write succeeded; the model just never saw it. Without a model of when a write reaches a request, you debug prompt compliance when the real fault is a stale copy.

Where it fits: The previous card showed that the working set is assembled for each call. This card asks how often the assembler rereads its sources, and what caching and reproducibility cost you if it rereads too often. The next card, compaction, turns out to be one of the moments the snapshot refreshes.

In one breath. The runtime builds the system prompt from durable files once and reuses that copy, the snapshot, on every call. Writing to a file changes the disk, not the next request: the model sees the new value only when the runtime rebuilds the snapshot or puts the value into the request some other way. Holding the snapshot still is what keeps prompts reproducible and cacheable; that is the price of freshness.

Two things fall out. Compaction already changes the prompt, so it is a cheap moment to refresh: that is when Hermes does it (the cost reading is ours, not the post's). And a per-turn rebuild is only as cheap as its least stable byte: Hermes's volatile tier includes a timestamp, and a timestamp rebuilt every call would make every call a miss.

"A cached prompt object is not a provider cache hit": an unchanged digest says Hermes didn't rebuild, not that the provider served from cache. He recommends keeping prompt digest, history digest, and cache-read and cache-write tokens as separate metrics.

Refreshing and reconciling are two jobs

1 · Refresh the factPut the new value in the next request: rebuild the snapshot, inject a note, or let the model read the file. This is what Hermes's compaction did for USER.md, and what the experiment checked.
2 · Reconcile the stale copiesHistory may still hold the old value and choices made under it. In the Tuesday run, call 7 gets the exit-code rule and also a summary saying "tests passing". A refresh doesn't rewrite that summary. Nothing in the posts shows Hermes doing this job; that's our inference, not his finding.

Why a snapshot beats the alternatives

✗ Rebuild every turn

Fresh by the next call, but any changed byte (a clock, a memory write) invalidates the cached prefix, and the system message can change under a request already in flight.

✗ Read through a tool

Always current, but only if the model decides to read. One study counted 0 memory operations in 114 turns when memory use was voluntary.

✗ Inject on change

Current and cache-friendly (a note at the tail), but the old value is still in the snapshot, so the model gets two conflicting copies and has to guess which wins.

✓ Snapshot with named refresh points

Stable, cacheable, reproducible prompts. The lag is the cost, and it's fine if every write receipt answers two questions: did the source change, and when will the model see it?

Is a snapshot always the right call?

No. If a fact must act now (a revoked permission, a user saying "stop"), waiting for the next session or compaction is too slow: inject it at the tail of the next request or end the session. The snapshot wins for slow-moving context like identity, profile and project rules.

Caching is a big part of why snapshots exist. "Don't Break the Cache" (Lumer et al.) measured prompt caching on over 500 agent sessions with 10,000-token system prompts: 41–80% lower API cost and 13–31% faster time to first token across OpenAI, Anthropic and Google. It recommends keeping dynamic content at the end of the system prompt. Govindarajan cites the paper but didn't measure cost himself; his evidence is about what reached the model, from one profile on one release.

Understand and remember

  • The runtime builds the system prompt once and reuses it → a write to USER.md changes the disk but not the next request → the model keeps the old value until a refresh boundary (a new session, or compaction in Hermes) rebuilds the snapshot
  • Provider caches reuse the longest unchanged prefix → any changed byte in the system prompt invalidates everything after it → rebuilding every turn is only as cheap as the prompt's least stable byte (a clock makes every call a full miss)
  • Compaction rewrites history anyway → everything after the system prompt is a cache miss at that call regardless → rebuilding the snapshot there costs only the system prompt's own tokens, not the whole history behind it, which is why it is a natural refresh point
  • Refreshing puts the new value in the request → but summaries, tool results and earlier replies still hold the old value or decisions made under it → refreshing a fact and reconciling its stale copies in history are separate jobs
  • detail that matters Inject-on-change appends a note at the tail → the cached prefix survives (33,650 vs 33,600 tokens in the Tuesday run) → but the old value stays in the snapshot, so the model sees two conflicting copies
  • detail that matters A cached prompt object and a provider cache hit are different caches → an unchanged digest says the runtime didn't rebuild, not that the provider served from cache → you need both metrics to debug either

Check
  • Hermes places it in the volatile tier, near the end of the system prompt
  • stability is decided by lifecycle (how often it changes per session), not by importance
  • snapshotting turns a volatile source into stable bytes for the session, trading freshness for cache and reproducibility

5 · Predict commit to an answer before revealing

A harness snapshots per session, and a subagent is spawned at call 6 of the Tuesday run, after the USER.md edit. Does the subagent see the new rule? Commit before revealing.

Reveal

Not knowable from the parent's snapshot alone. In Hermes v0.20.1 a delegated child gets a separately constructed prompt, not the parent's copy, so if that construction rereads USER.md the child sees the new rule while the parent still doesn't. Two contexts in one run can then disagree. The post defers the details to Part 4; treat it as something to test, not assume.
