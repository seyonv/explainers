Context is assembled, not given

Also called the working set, the request payload or, for data agents, the evidence bundle. Govindarajan's thesis in The Agent Stack Part 5: context is not what the model knows but the bounded set of material the runtime builds for one turn; his Data Agent Stack Part 3 applies the same idea to analytics questions.

Prime · 2 minutes before you read

The problem: An agent can hold the right fact somewhere in the system and still act on the wrong one, because the model only reads what was put in this call's request. If you debug only the final text, you never find out what it was actually shown.

Where it fits: You already know what a request contains and in what order (what the model sees). This card asks who decides what goes into it, and opens the course: snapshots, compaction and memory are each one way that decision is made.

You already know: what the model sees on each call (the order of the request, the cache, compaction basics). This card is about who decides what goes in.

In one breath. The runtime holds far more than it sends: the full transcript, files, documents, memories, old tool results. For each call it selects a small subset, then filters, ranks, summarizes, budgets and orders it into one request. That request, the working set, is all the model can reason over. It is derived state, rebuilt every turn. The transcript is the record. When an answer is wrong, the working set is the first thing to inspect, because a capable model given the wrong material still writes a polished wrong answer.

Predict first: in the Tuesday run, step 6's pytest printed exit code 1, and the run's transcript still contains that line at step 8. Why might the model still believe the tests pass?

Because the model never reads the transcript. At step 8 it reads the working set, and the runtime built that from a compaction summary that says "tests passing" instead of from the step-6 record. The fact exists in the system, but it was not selected. Govindarajan lists this as one of six different causes behind "we already talked about this": a summary dropped the important detail.

Records persist and have owners. The working set is rebuilt for every call and owned by whoever assembles it. Diagram after Part 5's "responsibility boundary" picture, redrawn.

Long context and caching change the budget, not the responsibility

LeverWhat it changesWhat it leaves to the runtime
Bigger windowGemini's docs (cited in Part 5) describe windows of 1 million tokens or more. With one, the Tuesday run's 67,150 tokens fit, step 7 never compacts and exit 1 stays in view.Which session is this user's, which document superseded which, whether a memory is trusted. More room also means more cost, latency and noise. Lost in the Middle found models can use a relevant fact less well when it sits in the middle of a long input, even long-context models.
Prompt cachingRepeated prefix tokens get cheaper and faster.What to remember, when to delete, scope, conflicts. Govindarajan: caching optimizes reuse; memory governs persistence.

Why it beats the alternatives

✗ Transcript stuffing

Append everything, every turn. Fine in a demo; in long runs it gets slow, costly and noisy, then hits the limit and compacts anyway.

✗ Buy a bigger window

Pushes the limit away but still decides nothing about scope, freshness or trust, and buries the one fact that matters among many.

✗ Retrieval as truth

Whatever ranked highest goes in. A widely copied, outdated query outranks the current metric contract because it looks related.

✓ An owned, inspectable assembly step

The record is kept apart, every included item carries scope and provenance, and what was sent can be reproduced: Part 3 calls the log a context manifest.

Does every agent need a real assembly step?

No. A short run that never nears its budget sends the whole transcript every call, and that is fine: selection only starts to matter once something must be left out. And the runtime is not the only selector. Coding agents fetch files with tools mid-run, so the model also chooses part of its own working set. Govindarajan's ownership framing still applies, because the runtime decides which tools exist and how their output is kept, but that split is my reading, not his.

Know what the source is. Both posts are architecture arguments built on vendor docs and one paper; they report no experiments. The six context layers in Part 3 come from OpenAI's write-up of its in-house data agent, which Govindarajan calls a useful case study, "not a universal taxonomy". He also declines to call context assembly a "control plane for correctness", and calls it the evidence boundary for the turn.

Understand and remember

  • The API keeps no state → the runtime must rebuild the request every call → the model reasons only over what was selected → a fact can exist in the record yet be absent from the turn
  • Budget forces exclusion → the runtime swaps history for a summary or a subset → the working set becomes derived state that can disagree with the record → keep the transcript as the source of truth and never let the summary overwrite it
  • Bigger windows and caches only change cost and capacity → they decide nothing about scope, freshness or authority → more material can bury the governing fact (Lost in the Middle) → selection stays the runtime's job
  • Retrieval ranks by "looks related" → related is not authorized, current or canonical → evidence needs scope, version and provenance before it may steer the answer → otherwise popular or stale text becomes authority
  • detail that matters In the illustrative Tuesday run, 12,000 of the 12,210 working-set tokens are the fixed prefix → only 210 tokens carry the run's progress → whatever those few tokens say (the summary) dominates what the model believes about its own state

Reference only

  • Part 5's nine ingredients: instructions, latest message, selected history, workflow state, retrieved evidence, memories, tool definitions, tool outputs, artifacts
  • Part 3's evidence-record fields (source_id, claim_type, authority_class, scope, observed_at, supersedes, …)
  • The conflict outcomes: retain, supersede, verify, clarify, abstain
  • OpenAI's six data-agent context layers (a case study, not a taxonomy)

    Check
    • history is the chronological record and still holds exit 1
    • the working set is what call 8 received: prefix, task, and a summary saying tests pass

  2. mechanism Walk through what the runtime does between the end of step 7 and the moment call 8 reaches the model.
    Check
    • checks the budget: the uncompacted request would exceed it
    • chooses what to keep: fixed prefix and task
    • replaces steps 1–6 with the model-written summary

  3. tradeoff Your team proposes moving to a 1M-token model so the agent never compacts. What does that fix, what does it cost, and what does it leave unsolved?
    Check
    • fixes the Tuesday run's lost exit code, since nothing needs dropping
    • costs every token on every call, plus latency and noise
    • a fact in the middle of a long input can be used less reliably (Lost in the Middle)
    • still decides nothing about session, scope, stale documents or memory trust
  4. mechanism A user's saved correction ("exclude internal accounts") shows up in a teammate's answer about a global metric. Which assembly decision failed, and which fields should have stopped it?
    Check
    • the memory was selected without checking its scope
    • personal scope must not redefine a global metric contract
    • scope and authority must be eligibility checks before inclusion, not just ranking hints

4 · Compare against what you already know

vs What the model sees on each call: That card and this one both describe the request. What does each optimize for, and how does each fail?

Check
  • that card: order and size, so the cache hits and the window doesn't overflow
  • this card: which material is selected, and who owns it
  • a request can be perfectly cache-friendly and still contain the wrong facts
  • that card fails on cost and limits; this one fails on correctness (a false or missing fact)

vs Compaction is a lossy state change: Assembly picks a subset each turn; compaction replaces history with a summary. Which is reversible, which design choice makes it so, and when does compaction turn into deletion?

Check
  • selection is reversible while the record is kept: the next turn can select differently
  • compaction writes a new artifact the model treats as truth
  • it becomes deletion when the summary replaces the stored record, not only the working set
  • both are runtime decisions, so both belong in the audit log

vs Owning the session: The control plane owns the session; the runtime owns the working set built from it. If a user says "we already talked about this" and the agent disagrees, how do you tell which owner failed?

Check
  • control-plane failure: the event went to the wrong session key, so the right record was never loaded
  • assembly failure: the right session was loaded but the fact wasn't selected, or a summary dropped it
  • check the record first (is the fact stored in this session?), then the working set (was it sent?)
  • they need different fixes: routing rules vs selection and summary rules

Why this step?

5 · Predict commit to an answer before revealing

Change one rule in the Tuesday run: the runtime keeps the latest tool result verbatim after every compaction. Does the false "tests pass" claim go away for good? Think about a run where the agent runs git status after pytest.

Reveal

Not for good. At step 8 it would be fixed: pytest is the latest result, so exit 1 is visible (15,210 tokens, illustrative). But "latest" is a position rule, not a relevance rule: if git status ran after the tests, it would be the kept result and the exit code would again live only in the summary. The fix has to be about which facts survive (test outcomes, exit codes), which is the compaction card's question.
