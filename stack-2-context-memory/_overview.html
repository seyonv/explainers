Owning what the model sees

Overview for course 2 of The Agent Stack: context and memory as owned state. The working set is assembled, snapshots trade freshness for stability, compaction loses state, and memory writes are privileged. Read it first as the map, or last as a recap.

Prime · 2 minutes before you read

The problem: The four cards each explain one way an agent ends up reasoning over the wrong facts: selection, snapshots, compaction and memory. Read separately, it is easy to miss that they are gates in one chain, with different owners, and that a false success claim needs only one of them to fail.

Where it fits: The map for course 2. It builds on what the model sees (the request's layout) and on course 1's claim chain, and sets up course 3, where the question moves from what the model sees to what it may do.

In one breath

The model reads one request per call, and that request is built. The runtime keeps the record (the transcript, the files, the memory store) and assembles a small working set from it for each call. Three things sit between the record and that working set, and each one can hide the truth: a snapshot built at session start that doesn't see later writes, a compaction that swaps history for a summary, and a memory store that decides what persists into future sessions. In the Tuesday run the exit code was in the record all along. It never reached call 8, so the agent said "all tests pass".

The one relationship

There is no equation here; there is a chain of gates. A fact reaches the model only if it passes every one, and each gate has a different owner. When the model acts on a wrong fact, walk the gates in order and find the first one that stopped the right fact.

The words people use

Compaction, compression, /compact

The same move under three names: replace older history with a summary so the run can continue. The course treats it as a state change that loses information, not as housekeeping.

Snapshot vs cache hit

A snapshot is the harness reusing its own built prompt. A cache hit is the provider reusing stored work for identical leading bytes. An unchanged snapshot doesn't prove a hit.

Retrieval vs memory

Retrieval finds text that looks related. Memory is state the system chose to keep, with an owner, scope and lifecycle. In Govindarajan's words, retrieval solves access and memory solves ownership.

✓ Working set, not transcript

The working set is the bounded request built for one call; the transcript is the record. Debug the first, keep the second, and never let a summary overwrite the record.

When this advice doesn't apply

Short runs. A run that never nears its budget sends the whole transcript every call and never compacts. Selection, pinning and refresh points start to matter only once something has to be left out.

Facts that must act now. A snapshot suits slow-moving context such as identity, profile and project rules. A revoked permission or a user saying "stop" can't wait for the next session or compaction: inject it into the next request, or end the session.

Agents without memory. If nothing persists across sessions, the write gate has nothing to guard. Append-only logs can also skip the gate; anything that will steer later runs (instructions, procedures, "this test is flaky") is where it pays.

The evidence is thin in places. The OpenCode trace used a scripted provider and no model, so it shows where information can stop, not how often real summarizers lose it. The Hermes results are single runs on one release, with no no-skill control. The Tuesday run is constructed. And whether compaction actually causes false success claims has not been measured: that is the capstone's question.

Understand and remember

  • The model reads only the request built for this call → a fact must be stored, survive compaction, be fresh and be selected → the first gate that drops it is where to fix, and each gate has a different owner
  • Compaction replaces history with a model-written summary → the summary is selected as truth on every later call → a lossy cut or status inflation becomes the agent's belief → pin status, exit codes and obligations verbatim before discarding anything
  • A snapshot is built once per session for stable, cacheable prompts → later writes are invisible until a refresh point → freshness is a separate decision from caching → name the refresh points, and inject facts that must act now
  • A memory write persists into every later session → a wrong inference committed becomes a standing instruction → writes need a source, a decision and a validated commit before activation
  • detail that matters In the illustrative Tuesday run, 12,000 of call 8's 12,210 tokens are the fixed prefix → the run's whole state rides on 210 tokens → whatever the summary says dominates what the model believes

5 · Predict commit to an answer before revealing

Swap compaction for a 1M-token window in the Tuesday run, but put the failing pytest output in the middle of a much longer run. Do the gates now guarantee an honest final message?

Reveal

No. Gates 1–4 all pass (nothing is cut, summarized or left out), so the fact reaches the model. But reaching the model is not the same as being used: Lost in the Middle found facts in the middle of long inputs are used less well. Whether that turns into a false success claim is unmeasured, which is open question 4.

6 · Apply use the model, don't restate it

Take one wrong answer from an agent you've built (or the Tuesday run) and fill in the four-gate table: for the fact that should have stopped it, mark each gate passed, stopped or not involved, name each gate's owner, and pick one lever from the ranking that fixes the first gate that stopped it.

Done when: Every gate has a mark and an owner, the first ✗ is named, and the chosen lever targets that gate (for Tuesday: survived ✗, compactor, pin status before clipping).

Hint

Start from the record: if the fact isn't stored anywhere, no later lever helps.
