Research questions for course 2 of The Agent Stack: context and memory as owned state. Eight questions the four cards leave open, merged from the card writers' notes, deduplicated and ranked by novelty × cheapness × how much the answer would change practice.

1Does the compaction policy change how often an agent claims a success it didn't get?

capstonepartly studiedtens of dollars
Why it matters
If a summary can turn "exit 1" into "tests passing", every harness that compacts may be shipping false "done" messages, and the fix is a harness change, not a model change.
Status
Partly studied. Compaction as Epistemic Failure (Tamba, arXiv 2607.13071) is one case study with no run counts. Governance Decay (arXiv 2606.22528) and The Compaction Cliff (arXiv 2608.22752) measure rules lost, not claims. ContextEcho (arXiv 2605.24279) covers drift across compaction, also not claims. Nobody has a dose-response for false claims.
Cost
Tens of dollars for the policy comparison; about $50 more for the pinning arm.
Smallest experiment
Tuesday-style tasks whose tests fail mid-run. Force one compaction before the final report, with four arms: free summary, keep the last tool result, pin {cmd, exit, counts}, no compaction. Re-run the tests after each run and score the final message; report the false-claim rate and pass^k of honest reports, and check the pin arm's pass rate didn't drop.
Source card

2Do harnesses cut tool results before the summarizer sees them, and does a verdict-last layout predict what is lost?

capstoneopenunder $10
Why it matters
pytest prints its verdict last, so a head-only cut drops exactly the line a later step needs. If that holds across harnesses, it is a mechanism for false claims that no summary prompt can fix.
Status
Open. Govindarajan traced one harness (OpenCode v1.18.30, a 2,000-character cut) with a scripted provider and no model. No cross-harness measurement exists.
Cost
Under $10.
Smallest experiment
Feed the same failing pytest output through three or four harnesses' compaction paths, log the summarizer's input, and check whether the counts and exit code are in it. Repeat with the verdict moved to the top of the output.
Source card
Compaction is a lossy state change

3After a refresh brings in a new value, does the agent still act on the stale copy in its history?

open$20–60
Why it matters
Refreshing a fact and reconciling the old copies are two jobs. If only the first is done, the model gets two conflicting versions and has to guess which wins.
Status
Open. Hermes Part 2 shows when a USER.md edit reaches the prompt, not what the model does with a contradicting summary already in history. Delivery, Not Storage (arXiv 2607.20972) studies whether facts are delivered, not conflicts between copies.
Cost
Under $20 for the reconciliation test; $20–60 including the "acted before the refresh" variant.
Smallest experiment
One session with a refreshed snapshot carrying the new rule and a summary in history that contradicts it. Three arms: no note, a "supersedes" note, a clean rebuild. Count which value the next action follows.
Source card
Prompt snapshots and freshness

4Does where the contradicting fact sits in the working set change how often the model overclaims?

capstonepartly studiedcheap, synthetic
Why it matters
A bigger window keeps the exit code, but if a fact in the middle is used less, "never compact" may still produce false claims. That decides whether a long window is a fix at all.
Status
Partly studied. Lost in the Middle (Liu et al., arXiv 2307.03172) found facts in the middle of long inputs are used less well for question answering. Whether the same holds when the model reports on its own work is unknown.
Cost
Cheap: synthetic single-call prompts. The writer gave no dollar figure.
Smallest experiment
One long synthetic transcript with the failing pytest result placed at the start, middle or end, then a "summarize your status" request. Count "tests pass" claims per position.
Source card
Context is assembled, not given

5Can a check on the context manifest predict which runs will end in a false claim?

capstoneopenmedium
Why it matters
If "the last check's exit code was missing from the final call" predicts false claims, a claim checker can flag a run cheaply, without re-running the world.
Status
Open. Data Agent Stack Part 3 proposes the manifest as an audit log; nobody has tested it as a predictor.
Cost
Medium: it needs logged working sets for many runs, plus a ground-truth re-run of each.
Smallest experiment
Log what each call was sent in the question-1 runs. Label each run by whether the final call contained the last exit code, and compare false-claim rates between the two groups.
Source card
Context is assembled, not given

6Do self-written wrong memories carry a false claim into later sessions, and which approval boundary stops them?

partly studiedlow to medium, 50–100 runs
Why it matters
A committed "pytest is flaky in this repo" turns one false message into a standing instruction. Where the gate sits (no gate, a policy check, a human) decides how often that happens.
Status
Partly studied: work on memory poisoning covers memories planted by an attacker, not ones the agent writes itself; the writer named no specific paper. Where to put the boundary is open. Govindarajan ends Hermes Part 3 by asking that question.
Cost
Low to medium: 50–100 runs; the boundary comparison is medium.
Smallest experiment
Seed one session with a real failure, let the agent propose memories, commit them under three policies, then run a second session on the same task. Count "it's just a flake" claims.
Source card
Memory is owned state

7In each harness, which event makes a write visible to the model?

mostly openunder $30
Why it matters
Users assume "I edited the rules file" means "the agent now follows it". A write-to-visibility table per harness would tell them when to start a new session.
Status
Mostly open. Govindarajan measured it for Hermes v0.20.1 and USER.md (compaction or a new session). Delivery, Not Storage (arXiv 2607.20972) does not measure it across production harnesses.
Cost
Under $30.
Smallest experiment
His marker-word method (AMBER → COBALT): edit the profile, memory and rules files mid-session in each harness, and log which of next turn, compaction or new session first carries the new word.
Source card
Prompt snapshots and freshness

8Did the learned skill cause the success, or only appear alongside it?

openlow
Why it matters
"Self-improving" agents are judged by runs where a written skill was loaded and the task went well. Without a control, that is correlation.
Status
Open. The Hermes Part 3 lab ran no no-skill control; the card says so.
Cost
Low: his lab is public.
Smallest experiment
Re-run his public lab task with and without the committed skill, several times each, and compare whether the workflow's steps (dry run, verify) happen.
Source card
Memory is owned state

How to generate your own

  1. Split an overloaded word. Govindarajan's move throughout: "memory" splits into stored, committed and active; "context" into the record and the working set; "cached" into snapshot and cache hit. Each split creates a gap you can measure: written but not yet visible, kept but not selected.
  2. Ask what is unmeasured. Rules lost in compaction are measured. False claims caused by compaction are not. Look for the claim that everyone repeats and nobody has counted.
  3. Check for a cheap controlled experiment. A marker word, a forced compaction, a fact moved to another position, a no-skill arm. If one change and one count can answer it for under $50, it is worth running before you argue about it.

Understand and remember

  • Rules lost in compaction are measured but false claims caused by compaction are not → the gap between the two is where a cheap experiment is novel → question 1 is the capstone's core

5 · Predict commit to an answer before revealing

In question 1's experiment, predict the order of false-claim rates across the four arms before running it, and say which arm you expect to cost pass rate.

Reveal

One plausible order is free summary highest, keep-last-result next, pin lowest, with no compaction close to pin. But it is unmeasured: that is the point of the question. Keep-last-result fails whenever another tool runs after the tests, so its rate may depend on the task mix. Pinning could cost pass rate if the extra tokens crowd out useful context; the experiment should check that.
