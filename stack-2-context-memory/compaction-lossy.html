Compaction is a lossy state change

Also called context compression, summarization or /compact. The harness swaps older history for a summary so the run can keep going. Govindarajan traced it step by step in OpenCode v1.18.30 and Hermes v0.20.1; here it is applied to the Tuesday run's step-7 summary.

Prime · 2 minutes before you read

The problem: A long run hits the context limit, the harness summarizes the past, and the agent carries on. If you treat that as housekeeping, a failing test can come out the other side as "tests passing", and nothing in the transcript tells you where the fact went.

Where it fits: The previous cards showed the working set is assembled per call and that snapshots trade freshness for stability. Compaction is the moment the harness rewrites that working set for good. It sets up the memory card (what must be written somewhere durable) and the capstone's question about false success claims.

You already know: what the model sees on each call (what compaction is, when to trigger it, what a summary should keep). This card is about what it costs.

In one breath. When the history gets too big, the harness splits it into an older head and a recent tail, has a model summarize the head, and continues with summary plus tail. That buys forward progress and pays in fidelity: whatever the summary leaves out, and whatever was cut before the summarizer even saw it, is gone from every later request, even if the full record is still on disk.

Predict first. At step 6, pytest prints a long failure and exits 1. A compactor keeps only the first 2,000 characters of each old tool result. Which survive to the summarizer: the F in the progress line, the failing test's name, the "1 failed, 41 passed" line, the exit code?

Where state stopped flowing in OpenCode

Govindarajan ran the real OpenCode CLI against a scripted provider and forced a compaction. Compaction makes two calls that see different things: a summary request (the head, serialized as text) and a continuation (summary plus retained tail).

What a summary must carry verbatim

Copy exactly, never paraphraseMay paraphrase or drop
The last check's command, exit code and counts: pytest → exit 1, 1 failed, 41 passedHow the agent got there: files explored, dead ends, one line each
Open obligations: the failing test's name, unfinished to-dos, what the user asked forTool output that has served its purpose
Unknowns as unknown: a killed command is "killed, exit 143", not "confirmed"The model's reasoning along the way
Where each fact came from, and "reread before trusting" for files that can changeDecisions already acted on, as long as the reason is kept

This split is the card's recommendation, not any one source's. It builds on Anthropic's compaction prompt as quoted by Wolfe (keep architectural decisions, unresolved bugs and implementation details; drop redundant tool output; continue with the summary plus the five most recently accessed files) and on Govindarajan's ask that a summary stay traceable to the observations it came from.

The invariant: flush before discard. Before context is discarded, persist whatever must survive (OpenClaw Part 3). OpenClaw runs a silent turn (NO_REPLY) as compaction nears that nudges the model to write durable notes. The post's caveat: in a read-only sandbox there is nowhere to write, so the invariant can't be enforced.

For the Tuesday run: the harness records {cmd: pytest, exit: 1, counts: "1 failed, 41 passed"} from the full step-6 result before step 7, and carries it verbatim. A one-line check (in the script) then flags the summary.

Published evidence

PaperWhat it found
Compaction as Epistemic FailureTamba, 2026 · arXiv 2607.13071A Claude Code case study: partial output from timed-out commands (exit 143) was written into compaction summaries as confirmed results. One case, no run counts.
Governance DecayChen, 2026 · arXiv 2606.22528Constraints, not claims: across 1,323 episodes and 7 model families, rule violations rise from 0% to 30% after compaction (59% for some models). Proposes "Constraint Pinning".
The Compaction CliffZerhoudi, Mitrovic, Granitzer, 2026 · arXiv 2608.22752Runs Claude Code's /compact prompt offline on Sonnet 4.6 over 20 production agent configurations: 53% of safety rules survive one round, 10% survive five.

As summarized in the series' novelty check. Rules lost in compaction are measured; whether compaction causes false success claims is not: only one case study exists, with no run counts. That gap is the capstone's question.

Why it beats the alternatives

✗ Never compact

The window eventually fills, and long contexts recall worse. Without compaction OpenCode's control run kept both the old and the new file read, with the conflict unresolved.

✗ Free-form summary only

Smooth to continue from, but whatever the summarizer drops is gone, and it can upgrade "failed" to "passing", as at step 7.

✗ Clear old tool results only

Wolfe: less likely to lose essential information, but it can't on its own stop the window from filling.

✓ Flush, pin, then summarize

Write durable notes first, carry status and open obligations verbatim, let the summary paraphrase the rest, and reread mutable files before acting on them.

Is a better summary prompt the fix?

Only partly. Some losses happen before any prompt runs (the 2,000-character cut), and some aren't losses at all: OpenCode reloads instruction files after compaction through ordinary assembly, so rules in AGENTS.md come back while facts that lived only in the conversation do not. Hermes's compression reloads only the user profile and memory; it is not a universal refresh.

Be careful with the evidence. The OpenCode run used no model, so it shows where information can stop, not how often real summarizers lose it. The Tuesday run is constructed. And compaction isn't always worth having: a short run that never nears the limit needs none, and when you can, a fresh session rebuilt from durable notes is a cleaner restart than a summary. Hermes calls a fresh prompt build the reliable point at which durable state reaches the model again.

Understand and remember

  • History outgrows the window → the harness summarizes the older head and keeps the tail → later calls see only summary + tail → anything not carried into the summary is gone from every later request, even though storage still has it
  • The serializer cuts each old tool result to a fixed length before summarizing → anything appended late in a result (a nested rule, pytest's verdict line, an exit code) never reaches the summarizer → no summary prompt can recover it; only extracting it before the cut can
  • The summarizer sees a failure only as scattered evidence and writes a fluent one-line status → "failed" or "unknown" becomes "passing" (status inflation) → the final message repeats it → a false success claim the checker catches
  • Instruction files are reloaded by ordinary prompt assembly after compaction → rules in AGENTS.md come back → facts that lived only in the conversation (test results, user asks, decisions) do not → those are what must be flushed or pinned before the discard
  • detail that matters Where the harness places an appended item inside a tool result (before or after the body) decides whether a head-only cut keeps it → OpenCode appended the nested rule after the file, so the cut dropped it

    Check
    • it replaces what later calls are built from, not just what is displayed
    • later calls see summary + tail; the old records stay in storage but are no longer selected
    • so like any state mutation it needs a trigger, a commit point, recovery and observability
  2. mechanism Walk through OpenCode's compaction in the experiment: what goes into the summary request, what is cut, and what the continuation request contains.
    Check
    • the older head is serialized as text; the most recent user turn is kept as the tail
    • completed tool results are cut to 2,000 characters, so the end of the old read and the appended nested rule are lost
    • continuation: a "What did we do so far?" user message, the summary, the retained tail, then a "Continue…" user message

  3. tradeoff A colleague proposes fixing status inflation with a stronger summary prompt ("never claim tests pass unless you saw it"). What does that fix, and what can it not fix?
    Check
    • it can reduce the summarizer rewriting a failure it did see
    • it cannot recover facts cut before the summarizer saw them (the verdict line, the exit code)
    • it is still a model judgment; pinning status from the full result before the cut is deterministic
  4. mechanism Hermes's database showed 12 active rows after compression, yet the recent tail still reached the next request. Which surface would you inspect to debug a "forgotten" fact, and why not just the database?
    Check
    • the actual provider request (and the summary's input), because that is what the model saw
    • the active-row view differs from live selected history after compression
    • compare persisted history, live history and the outbound request to find where it stopped

4 · Compare against what you already know

vs Anatomy of a tool call: A read limit cuts a tool result when it is acquired; the compaction serializer cuts it later, before summarizing. What is fundamentally different about the two cuts, and how does each one fail?

Check
  • the read-time cut happens in the open: the model sees the truncated result at that step and can ask for more
  • the compaction cut is invisible to the model: it happens inside the summary request and later calls only see the summary
  • read-time cuts fail as missing detail the agent can notice; compaction cuts fail silently, which is how status can inflate

vs Prompt snapshots and freshness: Hermes's prompt snapshot keeps an old USER.md; compaction drops an old test result. Both make the model see something other than the current truth. What choice causes each, and which is easier to repair?

Check
  • snapshot: stale by design, for stability and caching; the durable file still has the truth and a rebuild brings it back
  • compaction: lossy by design, for space; if the fact lived only in the conversation there is no durable source to rebuild from
  • so compaction needs the flush-before-discard step and the snapshot does not

vs 'Done' is a chain of states: Which link of the claim chain does the step-7 summary break, and why can't a checker that only reads the transcript after step 7 catch it?

Check
  • it asserts "command succeeded" when the command exited 1
  • after compaction the transcript the model sees contains the summary, not the exit code
  • the checker must rerun pytest or read the stored full step-6 result, i.e. check the world, not the summary

5 · Predict commit to an answer before revealing

The Compaction Cliff reports 53% of safety rules surviving one round of /compact and 10% surviving five. If each round dropped rules independently at the same rate, what would five rounds give? Is the reported 10% higher or lower, and what might that say?

Reveal

Independent rounds: 0.535 ≈ 0.042, about 4%. The reported 10% is higher, which would fit rules that survive one round being likelier to survive the next (some rules are stickier). This is our arithmetic on the summarized figures, not the paper's analysis; check its methods before leaning on it.
