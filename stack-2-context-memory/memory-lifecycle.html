Memory is owned state

Also called long-term memory, durable memory or, in Hermes, the self-improvement loop. Govindarajan defines it narrowly: state kept outside the model and put back into a later turn. His Hermes Part 3 lab walks one fact, one preference and one procedure through a write path with approval turned on.

Prime · 2 minutes before you read

The problem: An agent that can write to its own memory can turn one wrong conclusion into an instruction for every later run. If nobody owns the write, a bad memory outlives the transcript that produced it, and nothing tells you where it came from.

Where it fits: The earlier cards in this course showed that the working set is assembled for each turn and that snapshots trade freshness for stability. This card asks what is allowed to persist into those future working sets, and who decides.

In one breath. A transcript records what happened; a memory is what the system chose to keep, so every memory needs an owner, a source, a scope and a lifecycle. No weights change. Retrieval decides what the model can reach; memory decides what is allowed to persist and steer later runs. In the post's words, retrieval solves access and memory solves ownership.

Facts, preferences and procedures need different contracts

Squash a procedure into one memory sentence and the ordering, checks and recovery are gone. The lesson worth keeping from Tuesday is a procedure, not the "flaky" fact.

Why it beats the alternatives

✗ Keep it in the transcript

The session is a working set, not a home. Compaction can summarise the only copy away (Tuesday's step 7), and whatever survives gets treated as truth.

✗ Call the vector index memory

It finds related text. You still need extraction, conflict handling, provenance, expiry, deletion and audit, which the index doesn't do.

✗ Write whatever the model says

Implicit writes. One wrong inference ("flaky") or one injected string becomes an instruction to every later run: prompt injection made persistent.

✓ Owned memory with a lifecycle

Each write carries scope, source and a decision; commit is checked by replay; activation is seen in a real prompt. Rejected proposals never touch the durable tree.

Is this learning, and does every write need a human?

Not learning. Hermes "grows" by promoting selected experience into files that are rebuilt into later prompts. That makes memory inspectable and deletable, and it also means the agent knows only what was written down.

A human gate on every write is the lab's setting, not the author's prescription. He turned background review off to keep the causal chain simple, and he ends by asking where you would put the approval boundary. Agent Stack Part 5 says most memory extraction can run in the background after the response. OpenClaw's pre-compaction flush has the model write notes in a silent turn, and the post describes no review step there. My read: append-only logs can skip the gate; anything that will steer future runs (instructions, procedures, "this test is flaky") is where it pays.

What the Hermes run does not show. The skill was loaded and the matching workflow ran, but with no no-skill control that is correlation, not proof the skill was needed. Rejecting a proposal also doesn't erase the transcript or other copies of the text.

1 · Core model what to internalise, what to just look up

Keep it if it changes what you can explain, predict, compare, choose, build or debug. Otherwise it's reference.

Understand and remember

  • Memory is what the system chose to keep → it steers runs long after the source transcript is compacted → a wrong write is a standing instruction → writes are the privileged operation ("writes can corrupt the future")
  • Approval is a decision, commit is a successful replay through validation → an approved write can still fail (152-char description vs a 60-char budget) → only a changed durable tree proves commit
  • Sessions load durable state when they start → a commit doesn't reach a running session → activation is proven only by a fresh prompt or an explicit load such as skill_view
  • Procedures carry ordering, checks and recovery → one memory sentence drops them → store them as skills: a short routing line in the prompt, the body loaded on demand
  • detail that matters Skill routing descriptions sit in every prompt → Hermes caps them at 60 characters → detail must move into the body, and an over-long description fails at replay, not at approval

Reference only

  • MEMORY.md (shared facts) and USER.md (user preferences, via memory(target=user)) in Hermes v0.20.1
  • OpenClaw's memory/YYYY-MM-DD.md daily log and memory_search → memory_get tools
  • the exact pending-write fields: source, target, proposal, decision, replay result

3 · Retrieve from memory, card closed
  1. concept Explain the difference between retrieval and memory in terms of what each one owns, and why a vector index alone isn't a memory system.
    Check
    • retrieval brings candidate evidence into a turn (access)
    • memory decides what persists, for whom, from what source, and when it expires (ownership)
    • the index finds related text but has no extraction, conflict handling, provenance, TTL, deletion or audit
  2. mechanism Walk the Hermes skill that passed human approval but failed: what happened at each stage, and what finally made it durable?
    Check
    • proposed and staged; the operator approved the diff
    • replay enforced the 60-character routing-description budget; the 152-character description failed
    • the durable tree stayed unchanged
    • a 54-character description replayed successfully and committed; a fresh session then loaded it
  3. tradeoff You run a coding agent for a team. Which memory writes would you let through without a human, and which would you gate? What does each choice cost?
    Check
    • append-only logs and low-stakes notes: background, no gate, cheap, but noisy
    • anything that will steer future runs (instructions, procedures, claims about tests) gets a gate
    • a gate adds latency and reviewer load; no gate risks durable poisoning
    • the source says most extraction can run off the hot path; the author leaves the boundary as an open question

4 · Compare against what you already know

vs Prompt snapshots and freshness: A snapshot freezes what a session sees; a memory commit changes what future sessions see. How does the snapshot explain the "commit ≠ activation" gap, and when would you want a mid-session refresh instead?

Check
  • the session loaded durable state at start, so later commits are invisible until a new session or a verified refresh
  • snapshots buy stable, cacheable prompts at the cost of freshness
  • refresh mid-session only when the user flow needs the write now ("remember this before we continue")
  • failure modes: snapshot serves stale memory; refresh churns the prompt and breaks caching

vs What the model sees on each call: That card shows skill descriptions as a small line in the prompt prefix. Why does this card treat the same skill as owned state with a lifecycle, and what changes when the agent can write its own skills?

Check
  • there, skills are installed by a human and only read
  • here, the agent proposes them, so each one needs source, decision, replay and load evidence
  • a self-written skill that is wrong is a durable, auto-routed instruction, worse than one bad turn

5 · Predict commit to an answer before revealing

Two Tuesday-style runs, from two different users, both propose "pytest is flaky" for the same repo memory on the same day. One is rejected, one is approved and committed. What does the next fresh session see, and what does the rejection actually protect?

Reveal

It sees the committed one. Rejection only stops that proposal; it doesn't block equivalent text arriving by another path, and it doesn't erase the transcript or other copies. Shared, project-scoped memory needs dedupe and conflict rules across writers, and the decision has to be about the claim and its evidence, not one proposal object.
