Lab: the compaction rig

Claim under test: OpenCode's compaction loses the test verdict before its summarizer runs, and that makes its summary report test status worse than Codex's does. You inspect the two transplanted prompts, prove the 2,000-character cut offline, then spend under one cent on one real compaction per prompt, and leave with the paper's compaction manipulation and its mechanism measurement.

Prime · 2 minutes before you read

The problem: The capstone asks whether compaction makes agents claim false success. If the two compaction prompts differ in what their summarizer is even given, a difference in claims could come from the serialization, not the prompt wording, and you would misattribute it.

Where it fits: The hands-on end of course 2. Compaction is a lossy state change located five places a fact stops flowing, on an illustrative 2,260-character output; this lab measures one of them, the 2,000-character serialization cut, on a real pytest output and with a real model.

Read with these questions (answer them in your head as you go; don't take notes line by line):

  1. Why is "Codex prompt on a GPT model" a transplant rather than how Codex behaves with OpenAI models?
  2. Where in a 2,181-character pytest result does the verdict line sit, and what else is cut with it?
  3. If the verdict line never reached OpenCode's summarizer, how did its summary still know the tests were failing?
  4. Which status fact did neither summary keep, and why does that matter for a later claim?
  5. What would make the cut lose the status entirely, not just the counts?

You already know: Compaction is a lossy state change (the five places a fact stops flowing, and the illustrative 2,260-character Tuesday output) · the forensics method.

What this lab builds for the paper: the manipulation (harness/compaction.py: two verbatim prompts, swapped in at a fixed trigger point) and the mechanism measurement (every compaction logs whether each test run's verdict line and exit code reached the summarizer).

The claim to test

HypothesisGiven the same failing transcript, the Codex prompt's summary states the test result, and the OpenCode prompt's summary doesn't, because OpenCode's summarizer never received the verdict line.
ControlOne fixed transcript, built by a scripted agent (no model): run tests (4 of 6 fail), make a wrong edit, run tests again (still 4 fail). Same model (gpt-5.4-mini-2026-03-17), temperature 0, seed 0, for both prompts. Only the prompt and its serialization change.
What would change your mindThe OpenCode summary still reports the tests as failing, or the Codex summary drops the status. Either means "verdict line in the summarizer's input" is not the same thing as "status survives the summary".

3 · Build the fixed failing transcript (no padding needed)2 min

The test needed artificial noise. Does a plain pytest failure need any? A scripted run stops at the trigger point (stop_at_trigger=True, the same mechanism the paper's prefixes use) and saves the history; then measure where the verdict sits.

4 · One real compaction per prompt (paid, capped)2 min · $0.0067

Needs OPENAI_API_KEY. The repo's Budget refuses any call whose worst case (4,096 output tokens) could take the total over $0.50. Measured spend in this session: $0.00668 for both calls together.

uv run python - <<'EOF'
import json, os
from harness.loop import TOOLS, Budget
from harness.models import make_model
from harness.compaction import compact

OUT = os.environ["OUT"]
hist = json.load(open(f"{OUT}/prefix/prefix.json"))["history"]
model = make_model("openai:gpt-5.4-mini-2026-03-17")  # temperature 0, seed 0
budget = Budget(cap_usd=0.50)
for variant in ("codex", "opencode"):
    budget.check(model.worst_case_cost(hist))  # refuse if cap could break
    res = compact(model, hist, 2, variant, tools=TOOLS)
    budget.add(res.response.cost)
    u = res.response.usage
    print(f"== {variant}: {u.input_tokens} in, {u.output_tokens} out,",
          f"${res.response.cost:.5f}, model {res.response.model_id}")
    print(res.summary)
    open(f"{OUT}/summary-{variant}.md", "w").write(res.summary)
print(f"total spend ${budget.spent_usd:.5f} (cap $0.50)")
EOF

The hypothesis half-holds. The cut did remove the counts, and the OpenCode summary never states them. But it did not lose the status: the failure tracebacks sit before the cut, so the summarizer rebuilt "these four tests fail" from them, and in more detail than Codex. Neither summary kept the exit code. So the mechanism measurement (verdict_in_text) is a measure of what was available, not of what the summary says; the paper needs both, which is why the repo plans a separate summary-coding step (judge/, not built yet).

The status survived here because pytest's traceback layout put the evidence early. The cut would take everything on a run whose first 2,000 characters are setup noise, as in step 2's test. A killed run is a different risk: the repo's retry-backoff output is only 49 characters (dots, the kill note, [exit code: 143]), so it all reaches the summarizer, and the danger moves to the summary itself, which has no verdict and no traceback to anchor it.

Honest caveat. One transcript, one model, one call per prompt at temperature 0: this is a mechanism demo, not a rate. And the "Codex" arm is a transplant: real Codex sends this prompt only to non-OpenAI providers, so "Codex prompt on gpt-5.4-mini" is a condition the paper defines, not a configuration any Codex user runs. Also note the rig drops OpenCode's recent tail, which in real OpenCode would keep the last tool result (and its verdict) verbatim; with the tail, the cut might not matter for the most recent run at all.

Understand and remember

  • OpenCode serializes each old tool result to its first 2,000 characters → pytest prints its verdict and the harness appends the exit code last → on a 2,181-character failure both are cut before any prompt runs → no wording of the summary prompt can recover them
  • The summarizer still sees whatever comes first (tracebacks, test names) → a capable model can rebuild "these tests fail" from them → losing the verdict line drops the counts but need not drop the status
  • Verdict-in-input is logged per compaction (verdict_in_text) → it measures what was available, not what the summary says → the paper needs a second measure that codes the summary itself
  • Codex with an OpenAI provider compacts server-side, and the rig drops OpenCode's recent tail → each arm is a defined condition, not a reproduction of the product → results generalize to the prompts, not to the shipped harnesses
  • detail that matters stop_at_trigger=True saves the history at the first failing post-edit test run → the same fixed transcript can be compacted any number of ways → this is how the paper's arms share one on-policy prefix
