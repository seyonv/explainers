Before this: The CUDA execution model

Your first kernel: vector add

Also called: a __global__ function, a <<<blocks, threads>>> launch, a grid-stride loop. Mark Harris's "Even Easier Introduction to CUDA" adds two arrays of 220 floats on an NVIDIA T4 (the GPU you get on free Colab) and goes from 1 thread to 1,932× faster in three steps. The CUDA guide's section 2.1 adds bounds checks, the two ways to manage memory, and error checking.

Open in Colab: labs/first-kernel.ipynb (view on GitHub)
Rebuilds the post's three kernels plus an explicit-memory version, all with prefetch and timed with cudaEvent. It prints ns, GB/s and % of 320 GB/s, checks max error = 0, and runs a broken 2,048-thread launch to show CUDA_CHECK catching it. Not yet run by the author. The numbers on this card are Harris's, measured on a T4; running it on your own T4 is the exercise. Colab's T4 clocks and availability vary, so expect some spread.

In one breath

A kernel is a C++ function marked __global__ that the CPU launches on the GPU as thousands of copies at once. Each copy is a thread. It reads its own block and thread number to work out which array elements are its job. Vector add does almost no math per byte, so the only question is how close you get to the memory's bandwidth. One thread gets 0.04% of it. A grid of 4,096 blocks gets 83%.

The kernel: four lines that matter

// runs on the GPU, launched from the CPU __global__1 void add(int n, float *x, float *y) { int index = blockIdx.x * blockDim.x2 + threadIdx.x; int stride = blockDim.x * gridDim.x;3 for (int i = index; i < n; i += stride)4 y[i] = x[i] + y[i]; } // host code: enough blocks to cover n (ceil-div) int blockSize = 256; int numBlocks = (N + blockSize - 1) / blockSize;5 add<<<numBlocks, blockSize>>>(N, x, y); cudaDeviceSynchronize();
1__global__ tells nvcc to compile the function for the GPU and let the CPU launch it. A kernel always returns void, so results come back through memory (here, y). 2The thread's global number: the start of its block (blockIdx.x * blockDim.x) plus its place inside the block. The post calls this "idiomatic CUDA". 3stride is the total number of threads in the grid. After finishing element index, a thread jumps a whole grid ahead. 4This is the grid-stride loop. It covers any n with any grid size, and i < n doubles as the bounds check. The guide's one-element-per-thread version writes if (i < n) instead, so spare threads in the last block do nothing. 5This is the ceiling division: adding blockSize − 1 before dividing rounds up. For N = 1,048,576 you get exactly 4,096 blocks. Launches are asynchronous, so the CPU has to call cudaDeviceSynchronize() before it reads y. The guide calls 256 threads per block "quite often a good value to start with". A block can hold at most 1,024 threads.

1 thread → 1 block: 91,811,206 ÷ 2,049,034 = 44.8× (256 threads, but all on 1 SM) 1 block → grid: 2,049,034 ÷ 47,520 = 43.1× ≈ 40 SMs (post: "proportional to the number of SMs") grid vs peak: 264.8 ÷ 320 GB/s = 82.7% T4 floor at peak: 12,582,912 B ÷ 320 GB/s = 39.3 µs (the kernel took 47.5 µs)

Why 256 threads give only 45×, not 256×, and why going to many blocks gives ≈ 40× more. A block runs on one SM from start to finish. With one block, 39 of the 40 SMs sit idle, and one SM can only keep so many memory requests in flight. Each of the 256 threads took about 500 ns per element (2,049,034 ns ÷ 4,096 elements each). The lone thread took 87.6 ns per element, so each thread got slower, which fits one SM's memory pipe filling up (our inference; see occupancy). Spreading 4,096 blocks over all 40 SMs gives 40 times the pipes: 43.1× measured. At that point the whole GPU is limited by DRAM bandwidth.

The pitfall: unified memory page faults

cudaMallocManaged gives one pointer that both CPU and GPU can use. The post calls it virtual memory whose pages "are migrated on demand". The arrays were filled in by a CPU loop, so every page started in CPU memory. When the kernel touched them, each page faulted and moved individually, and the GPU threads stalled while they waited. nsys showed 64 host-to-device and 24 device-to-host unified memcpy operations. The same grid-stride kernel took 4,514,384 ns, 95× slower than with prefetch, and no faster than the single block. The post's reasoning: 40× more compute that doesn't bring the time down means compute wasn't the bottleneck.

// move the pages to GPU 0 before the launch cudaMemPrefetchAsync(x, N*sizeof(float), 0, 0); cudaMemPrefetchAsync(y, N*sizeof(float), 0, 0); kernel: 4,514,384 ns → 47,520 ns but the 4 prefetch copies: 690,043 ns

Prefetching doesn't make the copy free. It moves the copy out of the kernel and into 4 large transfers instead of many faults. In the post's profile those transfers took 690,043 ns, 14.5× the kernel itself. The other option, from the guide (2.1.3.2), is explicit memory: cudaMalloc on the GPU, cudaMallocHost (pinned) on the CPU, and cudaMemcpy in each direction. It's more code, but you control exactly when the bytes cross PCIe. The notebook times both.

Check every call, and remember launches are asynchronous

// the CUDA guide's macro (2.1.7), abridged #define CUDA_CHECK(e) do { \ cudaError_t r = (e); \ if (r != cudaSuccess) \ fprintf(stderr, "%s:%d: %s\n", __FILE__, \ __LINE__, cudaGetErrorString(r)); \ } while (0) add<<<numBlocks, blockSize>>>(N, x, y); CUDA_CHECK(cudaGetLastError()); // bad launch config? CUDA_CHECK(cudaDeviceSynchronize()); // errors while it ran

A <<< >>> launch returns nothing, so you have to ask for the error state. cudaGetLastError returns it and resets it to success. cudaPeekAtLastError returns it without resetting. A clean check right after the launch only means the launch was accepted, not that the kernel ran. Errors that happen while the kernel runs, such as an illegal memory access, show up "when the error state is examined next": at the sync, or at whatever CUDA call comes next. The guide says they keep coming back from every runtime call until something clears the state. That's why a crash often gets reported at an unrelated cudaMemcpy three lines later.

The notebook's broken launch is add<<<512, 2048>>>. It asks for 2,048 threads per block, over the 1,024 limit, so the check after the launch fails. Toolkits name this invalid configuration argument or invalid argument. The guide's own <<<8192, 4096>>> example printed the latter. Your run shows which one your Colab toolkit prints.

On an H100 this whole kernel takes about as long as the overhead of launching it. A decode step in an LLM engine is hundreds of small kernels like this one, so engines cut the number of launches: they fuse kernels and replay whole steps as CUDA graphs. Why it beats the alternatives

✗ One thread <<<1,1>>>

Correct, but it uses 1 of the T4's 2,560 cores and waits on every load: 91.8 ms, 137 MB/s. That's 0.04% of peak and about 600× slower than numpy on your Mac.

✗ One block <<<1,256>>>

This is 45× better, but a block never leaves its SM, so 39 of 40 SMs idle. 2.05 ms and 6 GB/s: still 1.9% of peak.

✗ numpy on the M3 CPU

The honest baseline: about 0.12–0.15 ms, 82–104 GB/s measured, near the M3's ~100 GB/s. It's fine for 1M floats, but it can't go past the Mac's bandwidth, and it's still 2.6–3.2× slower than the T4 kernel.

✓ Grid-stride loop, many blocks

It keeps all 40 SMs busy and works for any N and any grid size: 47,520 ns and 265 GB/s, 83% of peak. The same kernel, unchanged, fills a 132-SM H100.

Why was the first GPU version slower than a CPU?

A GPU isn't fast per thread. It's fast because it runs many threads at once. The first version threw that away twice:

  • One thread on one of 2,560 cores. It handles one element at a time and waits for memory on each: 87.6 ns per element, compared with about 0.12–0.15 ns per element for numpy on the M3. The loads are what make it slow, not the adds.
  • Unified memory page faults. Before prefetching, the pages lived on the CPU and moved over on demand, one fault at a time. Even the 4,096-block version stayed at 4.5 ms until the data was prefetched.

When is writing this kernel not the right call? For real work, torch.add, x + y in CuPy, or a Triton kernel give you the same memory-bound result without the C++. And if the data lives on the CPU and you only add it once, the copy costs more than the kernel. Moving 8 MiB of inputs across took 690 µs, against 47.5 µs of kernel, so keep it on the CPU. A GPU only pays off when data stays on it across many operations, which is exactly what an inference engine does with the weights.
