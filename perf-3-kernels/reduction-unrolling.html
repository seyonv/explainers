Parallel reduction II: unrolling and cascading

Also called warp unrolling, template unrolling, algorithm cascading, Brent's theorem, grid-stride reduction. This card covers slides 16–38 of Mark Harris's "Optimizing Parallel Reduction in CUDA": kernels 4 to 7 on a G80 summing 222 ints with 128-thread blocks, taking the sum from 17 to 63 GB/s (73 GB/s on 32M elements).

In one breath

A tree reduction leaves most threads idle and spends its instructions on loop bookkeeping, not on adding. The fix that matters most is algorithmic: give each thread many elements to add on its own first (algorithm cascading, justified by Brent's theorem), then run a short tree. Unrolling the loop, especially the last warp, trims the remaining overhead. On GPUs since Volta you write that last warp with __shfl_down_sync, not the slides' volatile trick.

Kernel 4: first add during load · slides 17–19 · 1.722 → 0.965 ms, 1.78×

Kernel 3's loop starts at s = blockDim.x/2, so "half of the threads are idle on first loop iteration." Kernel 4 halves the number of blocks and has every thread load two elements and add them on the way into shared memory:

// kernel 3: one load per thread unsigned int i = blockIdx.x*blockDim.x + threadIdx.x; sdata[tid] = g_idata[i]; // kernel 4: two loads, first add of the reduction unsigned int i = blockIdx.x*(blockDim.x*2) + threadIdx.x; sdata[tid] = g_idata[i] + g_idata[i+blockDim.x];

The diagnosis: an instruction bottleneck · slide 20

"At 17 GB/s, we're far from bandwidth bound", and a reduction has low arithmetic intensity, so the likely bottleneck is instruction overhead: "address arithmetic and loop overhead". The strategy is to unroll loops. This is the course's loop in miniature: measure, compare with the peak, name the bound, fix that bound.

Kernel 5: unroll the last warp · slides 21–23 · 0.965 → 0.536 ms, 1.8×

Once s ≤ 32, only one warp has work. The slides reason that instructions are "SIMD synchronous within a warp", so the last six steps need neither __syncthreads() nor if (tid < s):

__device__ void warpReduce(volatile int* sdata, int tid) { sdata[tid] += sdata[tid + 32]; sdata[tid] += sdata[tid + 16]; sdata[tid] += sdata[tid + 8]; sdata[tid] += sdata[tid + 4]; sdata[tid] += sdata[tid + 2]; sdata[tid] += sdata[tid + 1]; } for (unsigned int s=blockDim.x/2; s>32; s>>=1) { // loop now stops at 64 if (tid < s) sdata[tid] += sdata[tid + s]; __syncthreads(); } if (tid < 32) warpReduce(sdata, tid);

The slides stress this "saves useless work in all warps, not just the last one": without unrolling, all warps run every loop iteration. In our model of a 128-thread block (lab section 3), kernel 4 runs 7 iterations × 4 warps = 28 warp-iterations (compare, branch, __syncthreads), and kernel 5 runs 1 × 4 = 4, then six straight-line adds in warp 0. That's a count of loop iterations, not of machine instructions.

Kernel 6: complete unrolling with templates · slides 24–28 · 0.536 → 0.381 ms, 1.41×

The block size is a power of two with a hardware maximum (512 threads on the G80; 1,024 today), so the whole tree can be unrolled if the compiler knows the block size. Harris makes it a template parameter, template <unsigned int blockSize>. Every if (blockSize >= 512) is then decided at compile time, and a switch (threads) over the 10 possible sizes (512 down to 1) picks the right instantiation at launch.

Complexity, cost and Brent's theorem · slides 29–30

A tree over N = 2D elements takes log N steps and does N − 1 adds in total, the same as a serial loop, so it is work-efficient. With P processors the time is O(N/P + log N). The slides then define the cost of a parallel algorithm as processors × time. With one thread per element (P = N) the time is O(log N), so the cost is O(N log N): "not cost efficient!" Brent's theorem suggests O(N / log N) threads, each doing O(log N) serial work first.

Algorithm cascading · slide 31

Cascading combines a serial sum per thread with the tree in shared memory. Brent says each thread should sum O(log n) elements, "i.e. 1024 or 2048 elements per block vs. 256". Harris found it "beneficial to push it even further": more work per thread may hide latency better (see occupancy, Volkov), and fewer blocks shrink the tree of recursive kernel launches, whose last levels have few blocks and high launch overhead. On the G80 the best was 64–256 blocks of 128 threads, 1,024–4,096 elements per thread. Our recomputation: 64 × 128 = 8,192 threads give 512 elements per thread at 222 and 4,096 at 32M (225).

Kernel 7: multiple elements per thread · slides 32–35 · 0.381 → 0.268 ms, 1.42×, 30.04× total

unsigned int i = blockIdx.x*(blockSize*2) + tid; unsigned int gridSize = blockSize*2*gridDim.x; // "to maintain coalescing!" sdata[tid] = 0; while (i < n) { sdata[tid] += g_idata[i] + g_idata[i+blockSize]; i += gridSize; } __syncthreads(); // then kernel 6's unrolled tree, ending in warpReduce

Each pass of the loop moves the whole grid forward by gridSize, so neighbouring threads still read neighbouring addresses (see coalescing and the grid-stride loop in your first kernel). The slides' final kernel (slide 35) is kernel 6's tree plus this loop. At 222 with 64 blocks, a thread does 512 serial adds before a 7-step tree, so the tree is a small tail. Our lab replays this with numpy and gets the exact sum.

Types of optimization · slides 37–38

algorithmic (addressing, cascading): 2.33 x 2.01 x 1.78 x 1.42 = 11.84x (kernels 2, 3, 4, 7) code (loop unrolling): 1.8 x 1.41 = 2.54x (kernels 5, 6) all six step speedups multiplied = 30.04x (slides: 30.04x; 8.054 / 0.268 = 30.05x)

The conclusion slide: understand coalescing, divergence, bank conflicts and latency hiding; use peak performance to guide you; know the complexity theory; identify the bottleneck (memory, core computation or instruction overhead); "Optimize your algorithm, then unroll loops"; use templates to generate optimal code.

The modern note: volatile warp code is unsafe on Volta and later

Kernel 5 relies on the 32 threads of a warp running in lock-step, so each lane sees its neighbours' writes without any synchronization. NVIDIA's blog "Using CUDA Warp-Level Primitives" (Yuan Lin and Vinod Grover, 2018) says code like this is not guaranteed to work:

"Such implicit warp-synchronous programming is unsafe and may not work correctly." … "Implicit lock-step execution is not guaranteed. Remember, thread convergence is guaranteed only within explicitly synchronous warp-level primitives." … "Volta independent thread scheduling enables interleaved execution of statements from divergent branches."

The blog's advice for "any form of implicit warp-synchronous programming (such as communicating between threads of a warp without synchronization)" is to "update the code to use the sync version of the primitives", or to use Cooperative Groups, whose collectives "are implemented on top of the warp primitives". The slides' warpReduce is exactly that pattern: warp lanes communicating through shared memory with no sync (our application of the blog's rule; the blog itself doesn't discuss Harris's slides). The replacement adds in registers with the blog's Listing 1 loop, here wrapped as a function:

__inline__ __device__ int warpReduceSum(int val) { for (int offset = 16; offset > 0; offset /= 2) val += __shfl_down_sync(0xffffffff, val, offset); // lane X reads lane X+offset return val; // lane 0 holds the warp's sum }

The blog: the exchange "is performed between registers, and more efficient than going through shared memory, which requires a load, a store and an extra register to hold the address." If you do keep a shared-memory warp tree, __syncwarp() must separate every read from the next write (the blog's Listings 7 and 8). The legacy mask-less __shfl primitives are "deprecated starting in CUDA 9.0."

Why cascading beats the other fixes

✗ Kernel 4: first add during load

algorithmic · fewer idle threads

No thread is idle on the first step and half the blocks are gone, but each thread still adds only two elements before a 7-step tree that is 14% busy. It reaches 17.4 GB/s, 20% of peak, and is instruction-bound.

✗ Kernels 5–6: unrolling

code · less loop overhead

Removes loop counters, branches and barriers: 1.8 × 1.41 = 2.54× combined. It makes a mostly idle tree cheaper instead of shorter, and its volatile warp step is unsafe on Volta and later.

✗ Warp shuffles alone

modern · correct last warp

The right way to write the last 5 steps: registers, no shared memory, safe under independent scheduling. But they only touch the tail of each block. Without cascading each thread still starts from two elements.

✓ Kernel 7: cascading

algorithmic · the winner

A grid-stride loop makes each thread sum hundreds of elements, cutting Brent's cost from 22 N toward N. 62.7 GB/s = 72.5% of peak, 73 GB/s (84.5%) on 32M elements, 30× over kernel 1.

Why optimize the algorithm before unrolling?

Because the algorithm decides how much work there is and unrolling only makes each piece cheaper. In the slides the algorithmic changes (addressing and cascading) gave 11.84× combined and loop unrolling 2.54×. Unrolling kernel 4's tree speeds up steps where up to 99% of lanes are idle. After cascading, a thread does 512 serial adds and 7 tree steps, so the tree barely matters and unrolling it is a final polish. Harris's order: "Optimize your algorithm, then unroll loops."

When this isn't the right move:

  • Small inputs. With a few thousand elements there is little to cascade, and launch cost can outweigh the work (our inference; slide 31 names "high kernel launch overhead in last levels with few blocks"). A common answer is to fuse the reduction into a bigger kernel, as fused RMSNorm and softmax kernels do (our note).
  • Writing it yourself at all. In practice you would usually call a library reduction (CUB's DeviceReduce, or torch.sum) and write your own only when fusing it into something else. This is our note, not the slides'.
  • Copying the slides' code verbatim. Replace warpReduce with shuffles. Source quirks: the templated kernels are named reduce5 (kernel 6) and reduce6 (kernel 7), slide 35 calls warpReduce without <blockSize>, and the 512-thread block limit is the G80's.
