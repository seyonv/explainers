Occupancy and latency hiding

Also called achieved vs theoretical occupancy, Little's law, or TLP vs ILP. This card walks Volkov's GTC 2010 talk "Better Performance at Lower Occupancy" in order (GTX480 and G80 numbers), then siboehm's occupancy calculation for matmul kernel 3 (A6000), and redoes both for the lab T4 and the H100.

In one breath

A GPU hides the long wait for memory or arithmetic results by keeping many independent operations in flight at once. How many it needs is latency × throughput (Little's law). Occupancy (resident warps ÷ the SM's maximum) is only one way to supply them. Giving each thread several independent operations (ILP) or bigger loads works too, often better, because fewer threads leave each thread more registers.

1. The claim: faster code ran at lower occupancy

Volkov opens with NVIDIA's own libraries on the G80. In both cases the newer, faster version used smaller blocks and half the occupancy:

He names the two fallacies the talk takes apart: "multithreading is the only way to hide latency on GPU" and "shared memory is as fast as registers".

2. Latency is a time, throughput is a rate

Volkov's numbers: an arithmetic result takes ≈20 cycles, a memory load 400+ cycles. You can't start a dependent operation until it lands, but an independent one can start right away. Throughput is how many operations complete per cycle. On the GTX480 that's 1.3 Tflop/s = 480 multiply-adds per cycle, and 177 GB/s ≈ 32 four-byte loads per cycle. Hiding latency makes you faster, but never faster than peak. To reach peak you need enough operations in flight, and Little's law says how many:

needed parallelismoperations in flight = latencycycles (or ns) × throughputops per cycle (or bytes/s)

3. The experiment: ILP buys the same peak with fewer threads

Volkov runs one block on one GTX480 SM (peak 89.6 Gflop/s = 1.3 Tflop/s ÷ 15 SMs) doing a = a * b + c in a loop, and grows the block until it reaches 100%. Then he gives each thread 2, 3 and 4 independent chains (a, d, e, …):

Thread counts are Volkov's (slides 16–21, GTX480). Occupancy percentages are our arithmetic (GF100 holds 1,536 threads per SM). ILP=1 needs exactly 18 × 32 = 576. Past ILP=4 it stops scaling.

His conclusions: raising ILP is another way to hide latency, so it isn't only occupancy; occupancy is one contributor to utilization, not a measure of it. And the CUDA guide's "at least 384 threads on compute capability 2.0" is wrong: 192 threads per SM is enough on GF100 (64 on G80–GT200). On the GF104 you must use ILP to get above 66% of peak, because 48 cores need 3 instructions issued per cycle from 2 warp schedulers.

4. Memory: keep ~100 KB in flight, however you get there

The same law for DRAM on the GTX480. Volkov's latency is "< 800 cycles (?)", with his own question mark:

177.4 GB/s ÷ 1.4 GHz = 126.7 B per cycle 126.7 B/cycle × 800 cycles = 101 KB in flight (Volkov: "< 100 KB") = 6.76 KB per SM across 15 SMs (our arithmetic) at 4 B per thread: 101 KB ÷ 4 = 25,343 threads (Volkov: "25 000") but a GTX480 holds only 15 × 1,536 = 23,040 at 100 B per thread: 101 KB ÷ 100 = 1,014 threads (Volkov: "1 000")

His test copies memory with 1, 2, 4, 8 floats per thread, then 8 float2, 8 float4 and 14 float4, controlling occupancy by allocating dummy shared memory. More bytes per thread needs less occupancy. "Threads don't stall on memory access, only on data dependency": a load that hasn't been used yet costs nothing.

The same law on the H100 (our recomputation). Luo et al. measured global-memory latency on a Hopper H800 PCIe (HBM2e) at 478.8 cycles. At that card's 1,755 MHz max clock that's about 273 ns. We use it as a stand-in for the H100 SXM (HBM3), since it's the same Hopper SM but not the same memory, and it's measured on an idle GPU. Under load latency climbs, so treat this as a floor.

latency = 478.8 cycles ÷ 1.755 GHz = 273 ns in flight = 273 ns × 3.35 TB/s = 914 KB for the whole H100 per SM = 914 KB ÷ 132 SMs = 6.92 KB per SM 4 B per thread (one float): 1,731 threads = 54 warps = 84.5% occupancy 16 B per thread (one float4): 433 threads = 13.5 warps = 21.1% 128 B per thread (8 × float4): 54 threads ≈ 2 warps = 2.6%

Per SM, the H100 needs about as many bytes in flight as the GTX480 did (6.9 vs 6.8 KB). Bandwidth per SM roughly doubled (177.4 GB/s ÷ 15 = 11.8 → 3.35 TB/s ÷ 132 = 25.4 GB/s), while latency roughly halved (Volkov's upper bound of 800 cycles at 1.4 GHz is 571 ns, vs 273 ns). Our arithmetic.

5. Why fewer threads can be faster: registers vs shared memory

An SM has a fixed register file (32,768 registers on GF100). Fewer threads means more registers each: 20 per thread at 100% occupancy, 63 at 33%. That matters because only registers are fast enough to feed the ALUs:

a*b+c = 2 flops, reads 3 × 4 B = 12 B operands needed: 1.344 Tflop/s ÷ 2 × 12 B = 8.1 TB/s (registers) shared memory: 4 B × 32 banks × 15 SMs × 0.7 GHz = 1.3 TB/s (6× short) global memory: 177 GB/s (7.6× below shared)

So the CUDA guide's "shared memory is as fast as a register (no bank conflicts)" is wrong too. On Fermi shared memory is 6× slower than registers, 3× on older GPUs. The fix is more outputs per thread: each value loaded from shared memory is reused from a register several times.

FFT, in one line: the same trick on a 1024-point FFT (2 → 16 outputs per thread, small FFTs done in registers, shuffles through shared memory) again raises Gflop/s while occupancy falls. Volkov's summary: do more parallel work per thread so fewer threads hide latency, and use more registers per thread so you touch slower shared memory less. Computing multiple outputs per thread does both. That is exactly siboehm's kernels 4–5.

Four ways to supply the parallelism

✗ Max out occupancy (TLP only)

More warps, one op each. It works, but it caps registers per thread (20 at 100% on GF100), forces operands through shared memory, and one float per thread can't even cover 100 KB on a full GTX480.

✗ Just bigger loads (float4)

Bit-level parallelism: 16 B per load puts 4× the bytes in flight per thread, and it's cheap. It covers memory latency, but alone it doesn't cut shared-memory traffic or arithmetic dependencies.

✗ Async copies / TMA (Hopper)

The Hopper tuning guide: one thread hands a 1D–5D tensor copy to the TMA unit, and the block works on while data is in flight. It's the modern memory answer, but it needs a new programming model (see overview), not a quick fix.

✓ ILP: more outputs per thread

Volkov's winner. Independent work per thread hides latency with fewer threads, and the freed registers reuse each loaded value, so matmul went from 242 to 485 Gflop/s as occupancy fell from 67% to 33%.

So should I ignore occupancy?

No. Occupancy is a means to hide latency, not a goal. Low occupancy works only if each thread really has independent work in flight: several loads issued before their first use, several accumulators. A kernel with one dependent chain per thread (one float loaded, then used) still needs many warps. Look at the execution model: warps are what the scheduler switches between.

  • Occupancy matters when it's very low and the profiler shows warps stalled on memory with few eligible warps. It also matters for memory-bound kernels with little work per thread, and in the H100 recomputation above, one float per thread needs ≈ 85% occupancy.
  • It doesn't when stalls are "not selected" (siboehm's kernel 3), or when the kernel is limited by shared-memory bandwidth. There, trading occupancy for registers wins.

Nsight Compute reports theoretical occupancy (this calculator) next to achieved occupancy (measured). A big gap means imbalance, not a resource limit; see profiling. The CUDA Best Practices Guide still says "low occupancy always interferes with the ability to hide memory latency", the sentence Volkov called a fallacy in 2010. The same section also says ILP can cover latency at low occupancy "in some cases".
