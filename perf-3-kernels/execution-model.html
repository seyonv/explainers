Before this: The GPU as a machine (perf-1)

The CUDA execution model

Also: grid → block → warp → thread, SIMT, CTA (cooperative thread array, the hardware name for a thread block). This card walks CUDA Programming Guide §1.2 "Programming Model" section by section, with one concrete launch worked out on the course's two GPUs: the Colab T4 (labs) and the H100 (running example).

In one breath

You write one function (a kernel) as if for a single thread, and launch it as a grid of up to millions of threads, cut into blocks. Each block lands whole on one SM and its threads can share memory and synchronise; blocks run in any order, so they must not depend on each other. Inside a block, hardware runs threads in warps of 32 that issue one instruction at a time, masking off the lanes that took the other branch.

Heterogeneous system: host launches, device runs §1.2.1

A CUDA program always starts on the CPU (the host, with host memory). The host copies data to the GPU (the device, with device memory), launches kernels, and waits. A launch is asynchronous: the call returns before the kernel finishes, or even starts, so the CPU keeps working until it calls something like cudaDeviceSynchronize(). The guide notes that best performance usually comes from keeping both busy.

host: copy x, y to the device add<<<4096, 256>>>(N, x, y) ← returns at once … other CPU work … cudaDeviceSynchronize() ← host waits here device: [ kernel runs: 1,048,576 threads ]

GPU hardware model: SMs in GPCs §1.2.2

For CUDA, a GPU is a set of SMs grouped into GPCs (graphics processing clusters), all connected to global memory. You met the SM on the GPU as a machine: registers, a unified data cache that is split between L1 and shared memory, and the functional units (CUDA cores, tensor cores). The GPC matters here for one reason: it is the unit a cluster is scheduled onto. The guide stresses that the real hardware layout may differ from this model without affecting correctness.

Worked example: one launch, two GPUs §1.2.2.1

Add two vectors of N = 1,048,576 floats (the size in Harris's "Even Easier Intro"), one element per thread, 256 threads per block. Every thread computes its own global index from built-in variables:

Filled in for one thread: block 3, thread 37 → i = 3 × 256 + 37 = 805. Each variable also has .y and .z; grids and blocks can be 1D, 2D or 3D, and unspecified dimensions default to 1.

Threads join warps in order of thread index, 32 at a time, with warp 0 holding threads 0–31 (guide §3.2.2.1). So thread 37 of block 3 is warp 1, lane 5, and warp 25 counting across the whole grid.

blocks = ⌈1,048,576 ÷ 256⌉ = 4,096 warps = 4,096 × (256 ÷ 32 = 8) = 32,768 threads = 4,096 × 256 = 1,048,576

"Waves" is our idealised picture: blocks handed out in index order, a new one starting as soon as a slot frees. CUDA promises no order and no SM, so which SM runs block 3 is unknown. The same grid runs unchanged on both chips; only the number of rounds changes.

Grid size is a separate question from speed: this kernel moves 3 × 4 B × 1,048,576 = 12,582,912 B (read x, read y, write y), a floor of 39.3 µs at the T4's 320 GB/s. Harris measured 47,520 ns for exactly this launch on a T4, which is 264.8 GB/s. The first kernel card walks that ladder.

Blocks run in any order, so they can't wait on each other §1.2.2.1

All threads of a block run on one SM at the same time and, in most cases, finish there. That is what lets them share on-chip memory and call __syncthreads(). Blocks get no such promise: a grid may have millions of blocks and a GPU only tens or hundreds of SMs, and the guide requires that blocks can run "in any order, in parallel or in series". A block that spins waiting for another block's result can hang forever, because that block may not be scheduled until the first one finishes. The same rule is what lets one 4,096-block grid run in 26 rounds on a T4 and 4 on an H100 without changes. The practical rule: no inter-block sync inside a kernel. If step 2 needs every block's step 1, end the kernel and launch another. The kernel boundary is the global barrier, which the reduction cards use.

Thread block clusters: CC 9.0 and newer §1.2.2.1.1

Hopper added an optional level between block and grid. A cluster groups adjacent blocks (1D, 2D or 3D). All of its blocks are scheduled at the same time on SMs of one GPC, so unlike ordinary blocks they can synchronise with each other (via Cooperative Groups) and read and write each other's shared memory, called distributed shared memory. The portable maximum is 8 blocks per cluster; H100 allows 16 if you opt in. Clusters don't change the grid or any block's index. The H100 has them; the T4 (CC 7.5) doesn't, so the Colab labs never use them.

Warps and SIMT §1.2.2.2

A warp is 32 threads (lanes 0–31) that execute in the SIMT style: single instruction, multiple threads. Every thread runs the same kernel code but may take its own branches. When lanes disagree at an if, the warp runs each taken path in turn, with the lanes that didn't take it masked off (warp divergence). A simple cost model: each side of an if/else that at least one lane takes costs one pass.

All trueall 32 lanes take the if
1 pass100% of lane slots used
Alternating laneseven lanes if, odd lanes else
2 passes50% of lane slots used
First 16 laneslanes 0–15 if, 16–31 else
2 passes50% of lane slots used

Green = lane doing useful work in that pass; grey = masked off, idle. Illustrative cost model from the lab: both branches equally long. Note that "first 16" costs the same as "alternating": what matters is whether both paths occur within one warp, not how the lanes are arranged.

block of 256 (8 warps), same 50/50 split two ways: if (threadIdx.x % 2 == 0) → every warp diverges → 16 warp passes if ((threadIdx.x / 32) % 2 == 0) → each warp agrees → 8 warp passes (no divergence)

Two more consequences from the guide. Pick block sizes that are multiples of 32: a 100-thread block still takes 4 warps, and the last one has 28 lanes idle throughout. And warps are why the later cards talk about coalescing and bank conflicts: both are about what 32 lanes do together on one memory instruction. SIMT vs SIMD: SIMD exposes a fixed vector width to software, and there's one control flow; SIMT lets you write scalar per-thread code with its own branches, and the hardware packs it into warps.

Tile programming (§1.2.2.3): CUDA now also has a tile model, where you write per-block code on tiles and the compiler picks the threads, so there's no warp divergence to reason about. It is the same idea as Triton, covered in Triton: programming blocks.

A block's threads talk through shared memory; different blocks can only talk through global memory, and only across kernel launches (or within a cluster on Hopper). The guide also warns that registers per thread × threads per block must fit in the SM's register file, or the launch fails.

How it differs from related ideas

✗ CPU threads

A few heavy threads (your M3 has 8 cores), each scheduled by the OS with its own instruction stream. Great for branchy, independent work; far too few to hide memory latency by switching, and creating a million of them would be absurd.

✗ SIMD vector units (AVX-512)

One instruction on a fixed-width register of lanes (512 bits = 16 floats). You, or the compiler, write the lanes explicitly, and branches become explicit masks. SIMT hides that width behind scalar per-thread code.

✗ Triton's blocked programs

You write one program per block operating on whole arrays (tl.arange(0, BLOCK_SIZE)), and the compiler handles threads, coalescing and shared memory. Often faster to write, but you give up per-thread control. That's the later Triton card.

✓ SIMT: grid → block → warp → thread

Scalar code that scales from one SM to hundreds unchanged (4,096 blocks = 25.6 waves on a T4, 3.9 on an H100), with full control of each thread and cheap block-level sharing. The cost is that you must think about warps and memory yourself.

Is a CUDA thread like a CPU thread?

Only partly. The guide says GPU threads "operate similarly to threads on CPUs" but with differences that matter for correctness and performance. The important ones:

  • Classic model: no independent instruction stream. Before Volta, a warp shared one program counter and an active mask. Since Volta (CC 7.0, so both the T4 and the H100), each thread has its own program counter and call stack for scheduling: "independent thread scheduling" lets threads diverge and reconverge below warp granularity. But the guide still says a warp "executes one common instruction at a time", so divergent lanes still take turns.
  • Cheap and plentiful. A block of 256 threads is created by one launch, and hardware (not the OS) schedules them in warps, switching between resident warps to hide memory waits. An H100 keeps up to 270,336 threads resident.
  • Limited cooperation. Threads can sync only within a block (or a cluster on CC 9.0+), never across the grid inside one kernel.

When isn't per-thread SIMT the right tool? Code that's mostly branches and pointer chasing, with little data parallelism, belongs on the CPU. And for many ML kernels (softmax, matmul, attention), block-level tools like Triton or CUTLASS, or the new CUDA tile model, get you most of the speed with less thread-level bookkeeping. The old "warp-synchronous" tricks that assumed lockstep execution (the reduction slides' volatile last warp) are unsafe since Volta; use __syncwarp() or __shfl_down_sync().
