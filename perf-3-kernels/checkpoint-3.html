Checkpoint 3: beyond hand-written CUDA, measured honestly

Ties together tensor cores and low precision, kernel fusion and CUDA graphs, Triton's programming model, Triton matmul and profiling: which lever moves which bound in a real LLM step, and how to prove the win is real.

How to use this page. Close the five cards. Answer each question in writing, in full sentences, before opening its Check. A wrong or shaky answer isn't a failure; it tells you exactly which section to reopen. The questions are mixed on purpose, so you have to work out which idea applies before you can answer.

1 · Mixed retrieval

  1. which concept?A team moves Llama-3.1-8B's GEMMs from BF16 to FP8 math but keeps BF16 weights in memory, and batch-1 decode on an H100 doesn't get faster. Which idea explains it, and what would have helped?
    Check
    • batch-1 decode is memory-bound (intensity ≈ 1 FLOP/B): its floor is weight bytes ÷ bandwidth, 16.06 GB → 4.79 ms
    • faster math doesn't move a byte floor
    • FP8 weights halve the bytes: the ceiling goes 209 → 417 tok/s; FP8 math helps prefill (16.2 → 8.1 ms)

    Missed it? Reopen tensor cores and low precision, "Precision is a double lever".

  2. Derive the fused softmax's ~4× from element counts. What must be true of a row for the tutorial's kernel to work?
    Check
    • naive: 5 kernels reading 5MN + 2M and writing 3MN + 2M elements; fused: read MN, write MN
    • (8MN + 4M) ÷ 2MN = 4 + 2/N → 4
    • the whole row must fit in one program's on-chip memory; a 128,256-wide vocab row doesn't, and needs online softmax

    Missed it? Reopen Triton: programming blocks, tutorial 02.

  3. which concept?Your fused add + RMSNorm benchmark on an H100 reports 4.1 TB/s. Which idea says this number is wrong, and how do you get the right one?
    Check
    • more than 3.35 TB/s means the inputs were read from L2 (a hot, tight loop), not HBM
    • production reads them cold after other kernels evict them; for a bandwidth-bound kernel that's up to ~1.64× slower
    • flush L2 before each run (do_bench) or rotate input copies to ≥ 2× L2; report median and p90

    Missed it? Reopen profiling, "The benchmark that lies by 1.6×".

  4. You capture a batch-1 decode step of 323 kernels as one CUDA graph on an H100. What does the graph remove, what does it leave unchanged, and roughly how much does it save per step?
    Check
    • removes per-launch CPU cost and shrinks the GPU-side gap per kernel (~2.1 → ~1.3 µs, Hazy Research)
    • leaves every kernel's bytes and speed unchanged; an RMSNorm moves the same bytes graphed or not
    • 0.8 µs × 323 ≈ 0.26 ms of a 4.79 ms floor, about 5%

    Missed it? Reopen fusion and CUDA graphs, "Decode" and "Does a CUDA graph make my kernels faster?".

  5. Explain the tutorial's 90 vs 54 block loads, and name one case where grouped launch order can't help at all.
    Check
    • 9 programs in a row of C touch 1 A strip and 9 B strips: 10 × 9 blocks = 90; grouped in 3 rows, 3 + 3 strips: 54
    • fewer distinct blocks per wave means more L2 hits; the total work is the same
    • no help: decode with ≤ 128 tokens and BM = 128 has one row of tiles, so every order is identical (also: tiny matrices that fit in L2, or an already high hit rate)

    Missed it? Reopen Triton matmul, "L2 cache optimizations".

  6. which concept?Doubling the batch of a small model's step raises its runtime by about 5%. A teammate proposes FP8 tensor cores and another proposes fusing more elementwise ops to save bytes. Which regime are you in, and which lever would you pull?
    Check
    • Horace He's test: time barely moves with a 2× batch → overhead-bound
    • faster math (compute) and fewer bytes (bandwidth) attack the wrong costs
    • cut launches: CUDA graphs, or fusion for its fewer kernels, and at the extreme a megakernel

    Missed it? Reopen fusion and CUDA graphs, "First, find your regime".

  7. In the card's 32-weight example with one 0.15 outlier, MXFP4 sends 11 weights to zero and NVFP4 sends 5. Which two design choices in NVFP4 make the difference?
    Check
    • a fractional E4M3 scale instead of MX's power-of-two E8M0, so the block max can land exactly on 6 × scale
    • blocks of 16 instead of 32, so the outlier's coarse scale covers only its own block
    • the lab shows the scale type matters more: MXFP4 with 16-value blocks reaches only 0.130, NVFP4 with 32-value blocks 0.108

    Missed it? Reopen tensor cores and low precision, "Block scaling" and the 1M-weight sweep.

  8. Why shouldn't you quote Nsight Compute's kernel duration as your production number, and which tool do you use for that instead?
    Check
    • ncu replays the kernel over several passes, flushes caches, serialises launches and locks clocks
    • that makes metrics deterministic but the duration unlike production
    • use CUDA events or do_bench (cold L2, warm-up, many runs) or nsys for durations; ncu for why

    Missed it? Reopen profiling, "Why ncu's duration is not your production duration".

3 · Project: a fused add + RMSNorm in Triton, measured honestly

What it reinforces: counting fused vs unfused bytes and finding the regime (fusion), writing a block program with a masked row and an on-chip reduction (Triton basics), autotuning a block config (Triton matmul), timing with cold caches and reporting the spread (profiling), and why this op gets nothing from tensor cores (tensor cores).

On a Colab T4, in FP16 (the T4 has no BF16 tensor cores; this op doesn't use them anyway), hidden size D = 4,096:

  1. Predict bytes. Unfused is an add kernel (read 2, write 1) and a norm kernel (read 1, write 1): 5 transfers of an M × D activation. Fused reads the attention output and residual and writes the new residual and the normed output: 4. Compute both and the T4 floors at 320 GB/s for M = 1, 2, 4,096 and 8,192 rows.
  2. Write the kernel. One program per row, BLOCK_SIZE = 4,096, a mask, the sum of squares with tl.sum in fp32, then scale and store both outputs. Autotune num_warps over 4 and 8.
  3. Check it. Compare with an eager PyTorch reference (x + r, then RMSNorm) using torch.allclose at an fp16 tolerance.
  4. Time it. triton.testing.do_bench with quantiles=[0.5, 0.9] (L2 flushed) for your kernel, eager PyTorch and torch.compile, at all four M. Print GB/s against 320.
  5. Find the regime. Apply the doubling test between M = 1 and 2, and between 4,096 and 8,192. For the small case, capture the eager version in a CUDA graph and time it again.
Done when: you have a predicted-vs-measured table (median and p90) for three implementations at four sizes, the % of 320 GB/s at M = 4,096 and 8,192, a regime verdict for each size backed by the doubling test, and one sentence on what the graph did for M = 1.
Check: the predictions (computed with a short Python script)
  • One activation row is 4,096 × 2 B = 8,192 B. M = 4,096: unfused 5 × 33.55 MB = 167.8 MB → 0.524 ms; fused 134.2 MB → 0.419 ms (1.25× fewer bytes). M = 8,192: 335.5 MB → 1.049 ms vs 268.4 MB → 0.839 ms.
  • M = 1: fused 32.8 KB → about 0.10 µs of DRAM time, far below launch cost; M = 2 is 0.20 µs. Expect both to measure at a few µs and barely change when doubled: overhead-bound.
  • M = 4,096 → 8,192 should roughly double: bandwidth-bound. A fused kernel that reports more than 320 GB/s wasn't cold.
  • Eager Hugging Face-style RMSNorm is several ops (upcast, square, mean, rsqrt, two multiplies), so eager's real traffic exceeds the 5-transfer count; the 1.25× is a lower bound on fusion's byte saving.
  • The graph should cut the eager small-M time (fewer launches, smaller gaps) without changing the large-M time. All measured numbers are yours: nothing here has been run by the author.
