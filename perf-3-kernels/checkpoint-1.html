Checkpoint 1: memory patterns and cooperating threads

Ties together your first kernel, memory coalescing, shared memory and bank conflicts, occupancy and latency hiding, and the two parallel reduction cards: what 32 lanes do together on one memory instruction, and how many of those instructions a kernel must keep in flight.

How to use this page. Close the six cards. Answer each question in writing, in full sentences, before opening its Check. A wrong or shaky answer isn't a failure; it tells you exactly which section to reopen. The questions are mixed on purpose, so you have to work out which idea applies before you can answer.

1 · Mixed retrieval

  1. which concept?A kernel sums each row of a 4,096 × 4,096 float matrix by giving each thread one row and letting it walk along that row. It is correct, the profiler shows DRAM busy, but useful bandwidth is about an eighth of what you expected. Which idea explains it, and what would you change?
    Check
    • coalescing: at each step the 32 lanes of a warp read 32 different rows, 4,096 floats = 16 KB apart
    • every lane lands in its own 32-byte sector: 32 sectors for 128 useful bytes, η = 12.5%
    • fix: let a warp (or block) own a row so neighbouring lanes read neighbouring elements, then reduce across lanes; or stage tiles through shared memory

    Missed it? Reopen memory coalescing, the worked example and the stride rows.

  2. Harris's kernels 2 and 3 issue exactly the same warp instructions in their loops, yet kernel 3 is 2.01× faster on the G80. Where does the difference come from?
    Check
    • kernel 2's index = 2·s·tid puts several lanes of a warp on the same shared-memory bank
    • on 32 banks that is 2-, then 4-way conflicts (up to 8-way on the G80's 16 banks per half-warp): each access splits into passes
    • kernel 3 reads sdata[tid] and sdata[tid + s]: consecutive words, one pass

    Missed it? Reopen reduction I, "Kernel 2's new problem: bank conflicts".

  3. The unprefetched grid-stride vector add took 4.5 ms on a T4, 95× slower than with prefetch, and no faster than the single-block version. What was it waiting on, and does prefetching make that cost disappear?
    Check
    • unified-memory pages started on the CPU; each first touch faulted and migrated a page while the threads stalled
    • 40× more SMs didn't help, so compute wasn't the bottleneck
    • prefetch moves the copy out of the kernel into 4 large transfers (690 µs, 14.5× the 47.5 µs kernel); it isn't free

    Missed it? Reopen your first kernel, "The pitfall: unified memory page faults".

  4. which concept?You widen a transpose tile to float tile[32][64] so each block handles more data. Both global accesses are still coalesced, but the kernel drops to about half of copy speed. Which idea applies, and what's the one-character fix?
    Check
    • shared-memory bank conflicts: bank = word mod 32, and word = 64i + j puts every row of a column on bank j
    • a warp's column read is a 32-way conflict (the conflict degree is gcd(64, 32) = 32)
    • declare tile[32][65]: any odd width spreads a column across all 32 banks

    Missed it? Reopen shared memory and bank conflicts, "Worked example, part 2".

  5. A memory-bound kernel on an H100 runs 256-thread blocks at 64 registers per thread, so theoretical occupancy is 50%. Each thread issues eight independent float4 loads before using any of them. Should you cut registers to raise occupancy?
    Check
    • Little's law on the card's H100 numbers: about 6.9 KB must be in flight per SM
    • 32 resident warps × 32 threads × 128 B = 131 KB per SM in flight, far more than needed
    • so no: loads don't stall a thread until their result is used, and ILP already covers the latency; low occupancy only hurts when threads have one dependent chain each

    Missed it? Reopen occupancy, section 4 and "So should I ignore occupancy?".

  6. which concept?Your sum over 222 ints uses 32,768 blocks of 128 threads, one element per thread, sequential addressing, no divergence and no bank conflicts. It reaches about 11% of peak bandwidth. A teammate wants to unroll the loop. What would you do first, and why?
    Check
    • cascade first (Brent's theorem): far fewer blocks, a grid-stride loop, hundreds of elements per thread before a short tree
    • with P = N the tree's cost is 22 N; with ~N/22 threads it's about 2 N
    • on the G80 the algorithmic changes gave 11.84× and unrolling only 2.54×: unrolling makes a mostly idle tree cheaper, cascading makes it short

    Missed it? Reopen reduction II, "Complexity, cost and Brent's theorem" and "Why optimize the algorithm before unrolling?".

  7. Why does a multi-block sum need more than one kernel launch, and what happens if you try to make the last block wait for the others inside the kernel?
    Check
    • blocks have no co-scheduling guarantee; a grid can have far more blocks than fit on the GPU
    • a block spinning for another block's result can hang forever, because that block may never be scheduled while it waits
    • so each launch produces per-block partial sums and the next launch reduces them: 32,768 → 256 → 2 → 1 for 222 ints at 128 per block

    Missed it? Reopen reduction I, "Why reduction, and why it's hard".

3 · Project: a reduction cost simulator, checked against Harris

What it reinforces: sector counting (coalescing), warp issues and divergence (reduction I), bank arithmetic (shared memory), Brent's cost and cascading (reduction II), bytes in flight (occupancy) and the grid-stride loop (your first kernel).

In about 80 lines of Python with no GPU:

  1. Sectors. Write sectors(offset, stride, elem_bytes) for one warp request. Show that kernel 7's grid-stride loads are 4 sectors per request and that the row-per-thread layout from question 1 is 32.
  2. Warp issues. For kernels 1 and 3, count warp issues in the loop body and the share of useful lane slots for block sizes 128, 256 and 512.
  3. Bank conflicts. For kernel 2 on 32 banks and a 128-thread block, compute the worst bank per step for ints, then for doubles (two 4-byte words each).
  4. Brent. For one 4,096-element RMSNorm row, compute steps and cost ÷ N for P = 4,096, 128 and 32 threads.
  5. Bytes in flight. Using the occupancy card's H100 figure of ≈ 6.92 KB per SM, how many threads per SM does a cascaded kernel need if each thread keeps two 4-byte loads in flight? What occupancy is that?
  6. Measure. Run labs/reduction.ipynb on a T4 and fill in kernels 1–7, the shuffle kernel and CUB as % of 320 GB/s, next to the G80's column.

Check: the numbers (computed with a Python version of these counts)
  • Sectors: stride 1 floats → 4; one row per thread (stride 4,096 floats) → 32.
  • Warp issues, kernel 1 vs kernel 3: 128 threads 23 vs 8 (≈ 17% vs ≈ 50% useful); 256 threads 47 vs 12 (≈ 17% vs ≈ 66%); 512 threads 95 vs 20 (≈ 17% vs ≈ 80%). Kernel 1 stays at about 17% however big the block.
  • Kernel 2 conflicts, 128 threads: ints 2, 4, 4, 4, 4, 2, 1; doubles 4, 8, 8, 8, 4, 2, 1 (minimum 2 passes while a full warp of doubles is active). Kernel 3 with doubles: 2, 2, then 1.
  • Brent, N = 4,096: P = 4,096 → 12 steps, cost 12 N; P = 128 → 31 + 7 = 38 steps, ≈ 1.19 N; P = 32 → 127 + 5 = 132 steps, ≈ 1.03 N.
  • Bytes in flight: 6.92 KB ÷ 8 B ≈ 865 threads ≈ 27 warps ≈ 42% of the H100's 64 warps per SM.
