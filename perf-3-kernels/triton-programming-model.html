Triton: programming blocks, not threads

Also called OpenAI Triton, @triton.jit kernels, or the Triton language. (Not NVIDIA's Triton Inference Server, which is an unrelated model-serving product.) This card walks the Triton programming guide's introduction, then tutorial 01 (vector add) and tutorial 02 (fused softmax) section by section, with the tutorials' own printed tables.

Open in Colab: labs/triton-basics.ipynb (view on GitHub)
Rebuilds both tutorial kernels (adapted from the Triton repo, MIT license), checks them against torch, times them with triton.testing.do_bench on the T4 and prints GB/s next to 320 GB/s. It adds torch.compile as a fourth softmax line, runs this card's vocab-softmax example, and shows TRITON_INTERPRET=1. Not yet run by the author. Numbers on this card are from the Triton tutorials' printed tables (GPU not named) and our byte arithmetic; your T4 run is the exercise. Triton has no macOS wheels, so this runs on Colab or Linux only.

In one breath

In CUDA you write the code for one thread and launch a grid of blocks of threads. In Triton you write the code for one block of data (a "program"), work on whole vectors and tiles at once, and let the compiler decide how the threads split that block up. You still choose the tiling. The compiler handles the thread-level details that took the last several cards to learn by hand, such as coalescing, shared memory and synchronization.

The programming model: who is blocked?

The guide's introduction frames it as a change to SPMD ("Single Program, Multiple Data"): "programs – rather than threads – are blocked." Its own matmul pseudo-code, side by side (lightly abridged):

CUDA: "Scalar Program, Blocked Threads"

#pragma parallel for (m = 0; m < M; m++) #pragma parallel for (n = 0; n < N; n++) { float acc = 0; for (k = 0; k < K; k++) acc += A[m, k] * B[k, n]; C[m, n] = acc; // one scalar }

Triton: "Blocked Program, Scalar Threads"

#pragma parallel for (m = 0; m < M; m += MB) #pragma parallel for (n = 0; n < N; n += NB) { float acc[MB, NB] = 0; for (k = 0; k < K; k += KB) acc += A[m:m+MB, k:k+KB] @ B[k:k+KB, n:n+NB]; C[m:m+MB, n:n+NB] = acc; // a tile }

The guide's point: once the unit of work is a block, the compiler can see the whole tile's data flow and schedule it. The guide says its "block-level data-flow analysis" lets it apply these optimizations automatically.

Tutorial 01: vector add, line by line against CUDA

CUDA (first kernel, one element per thread)

__global__ void add(int n, float *x, float *y, float *out) { int i = blockIdx.x * blockDim.x1 + threadIdx.x; if (i < n)3 out[i] = x[i] + y[i];4 } // launch: ceil-div blocks of 256 threads add<<<(n+255)/256, 256>>>(n, x, y, out);5

Triton (tutorial 01, comments trimmed)

@triton.jit def add_kernel(x_ptr, y_ptr, output_ptr, n_elements, BLOCK_SIZE: tl.constexpr): pid = tl.program_id(axis=0)1 offsets = pid * BLOCK_SIZE \ + tl.arange(0, BLOCK_SIZE)2 mask = offsets < n_elements3 x = tl.load(x_ptr + offsets, mask=mask) y = tl.load(y_ptr + offsets, mask=mask) tl.store(output_ptr + offsets, x + y, mask=mask)4 # launch: one program per 1,024 elements grid = lambda meta: (triton.cdiv( n_elements, meta['BLOCK_SIZE']),) add_kernel[grid](x, y, output, n_elements, BLOCK_SIZE=1024)5
1Who am I? CUDA builds a global thread number from two indices. Triton only has the program number; there is no threadIdx in the language. 2Which elements? tl.arange(0, BLOCK_SIZE) is a whole vector of 1,024 offsets, so offsets is a block of pointers, not one index. BLOCK_SIZE is tl.constexpr "so it can be used as a shape value": it's fixed at compile time, and each new value compiles a new kernel. 3Bounds. The if becomes a boolean vector. Masked lanes are neither loaded nor stored. That's how the ragged last block is handled. 4Load, add, store. Same three memory operations, written once for the whole block. The compiler picks the thread layout and vector width that make these loads coalesced. 5Launch. triton.cdiv is the same ceiling division. The grid can be a function of the meta-parameters, so an autotuner can change BLOCK_SIZE and the grid follows. Launches are asynchronous: the tutorial notes the kernel "is still running" when add() returns.

Tutorial 01's numbers: overhead, then bandwidth

The benchmark counts three arrays (read x, read y, write output) of 4-byte floats and times with do_bench:

GB/s = 3 · numel · 4 B ÷ time (the tutorial's gbps lambda) 4,096 elements: 49,152 B ÷ 8.0 GB/s = 6.1 µs (Triton = Torch) 134,217,728 elements: 1.61 GB ÷ 1,684.0 GB/s = 0.956 ms (Triton = Torch) same 1.61 GB at T4 320 GB/s: ≥ 5.03 ms same 1.61 GB at H100 3.35 TB/s: ≥ 0.481 ms (T4 and H100 lines: our recomputation)

From 4,096 up to 65,536 elements, GB/s exactly doubles with each doubling of size (8, 16, 32, 64, 128). The time is constant at about 6 µs, which is launch and timing overhead, not memory. At the top the two lines are identical: an element-wise add has nothing to optimize past "stream at full bandwidth", and PyTorch already does that. The tutorial's point is the programming model, not speed. The printed tables don't name the GPU. 1,684 GB/s rules out the T4 and means a datacenter part with more than 1.7 TB/s (our inference).

Tutorial 02: fused softmax, and why fusion gives ~4×

Softmax of each row of an M × N matrix: subtract the row max (for numerical safety), exponentiate, divide by the row sum. Written in plain PyTorch it is five kernels, and each one goes back to DRAM. The tutorial's naive_softmax counts the elements each line touches:

Line of naive_softmaxReadsWrites
x_max = x.max(dim=1)[0]MNM
z = x - x_max[:, None]MN + MMN
numerator = torch.exp(z)MNMN
denominator = numerator.sum(dim=1)MNM
ret = numerator / denominator[:, None]MN + MMN
Total (tutorial: "read 5MN + 2M … wrote 3MN + 2M")5MN + 2M3MN + 2M
Fused kernel: read X once, write Y onceMNMN
speedup≈ (5MN+2M)naive reads+(3MN+2M)naive writes 2MNfused: read + write once = 8MN+4M2MN =4+2N →4
Mrows (independent softmaxes)4,096 in the benchmark Nrow length256 … 12,672 in the benchmark × 4 Bbytes per FP32 element; multiply both sides to get bytesratio unchanged

The tutorial: "a theoretical speed-up of ~4x (i.e., (8MN + 4M) / 2MN)". The 4 + 2/N form is our simplification: 4.0078 at N = 256, 4.0005 at N = 4,096. (The tutorial says "MN bytes" where it means MN elements; the ratio is the same.)

# tutorial 02 kernel, abridged row_start = tl.program_id(0) row_step = tl.num_programs(0) for row_idx in tl.range(row_start, n_rows, row_step,1 num_stages=num_stages): col_offsets = tl.arange(0, BLOCK_SIZE) # next_power_of_2(n_cols) mask = col_offsets < n_cols row = tl.load(row_ptr + col_offsets, mask=mask, other=-float('inf'))2 row_minus_max = row - tl.max(row, axis=0)3 numerator = tl.exp(row_minus_max) denominator = tl.sum(numerator, axis=0) tl.store(out_ptr + col_offsets, numerator / denominator, mask=mask)4
1One row per program at a time, persistent grid. The launch has only NUM_SM × occupancy programs, and each walks rows row_step apart. Occupancy comes from pre-compiling the kernel and reading its register use: NUM_REGS // (n_regs × 32 × num_warps), capped by shared memory. Illustrative: at 32 registers per thread, 65,536 ÷ (32 × 32 × 8) = 8 programs per SM, so 320 programs on a T4 (40 SMs) or 1,056 on an H100 (132 SMs). 2Padding. "Each block must have a power-of-two number of elements," so a 781-wide row runs as 1,024 lanes. The masked lanes load −∞, which can never be the max and becomes exp(−∞) = 0 in the sum. 3Two reductions (max, then sum) happen on-chip, across the program's 256 threads. In CUDA this is the tree reduction from parallel reduction, written twice. Here it's tl.max and tl.sum. The tutorial notes tl.exp is "fast but approximate (i.e., think __expf in CUDA)". 4One write. X is read once and Y written once: the 2MN of the formula. That only works while a whole row fits on the chip, which is the tutorial's own caveat: matrices "whose rows can fit in the GPU's SRAM".

Worked example: softmax at Llama-3.1-8B sizes (our recomputation)

Two softmaxes an engine actually runs, in FP32 as in the tutorial. Sampling: 4,096 sequences each get a softmax over the 128,256-token vocabulary. Attention scores: one layer of a 4,096-token prefill, where each of 32 heads × 4,096 queries is a row over 4,096 keys (causal masking ignored). Time = bytes ÷ peak bandwidth, a floor.

sampling: MN = 4,096 × 128,256 = 525,336,576 elements (2.10 GB FP32) naive: (8·MN + 4·4,096) · 4 B = 16.81 GB ÷ 3.35e12 B/s = 5.02 ms fused: 2·MN · 4 B = 4.20 GB ÷ 3.35e12 B/s = 1.25 ms (4.00002×) attention: 32 heads × 4,096 queries = 131,072 rows × 4,096 keys → 17.18 vs 4.29 GB (4.0005×)

The two rows are the same size by coincidence, but they differ in one way that matters. An attention row is 4,096 floats = 16 KiB and fits in one program. A vocab row is 128,256 floats, which pads to 131,072 = 512 KiB. That's more than the H100's 256 KB of L1/shared memory per SM, so the tutorial's one-row-in-one-block kernel can't hold it. A vocab-sized softmax needs a kernel that loops over chunks of the row and keeps a running max and sum (online softmax). That's also the trick that lets FlashAttention fuse attention without materializing the scores at all (perf-4). The notebook times torch.softmax and torch.compile on the vocab case for this reason.

7 of the 98 printed rows. The benchmark charges every line for 2 · M · N · 4 bytes (the fused minimum), so its "GB/s" is really a speed score, and Triton ÷ naive is the speedup. "Naive real traffic" is our recomputation: naive GB/s × (8N + 4) ÷ 2N, the bytes it actually moves per second.

What the table shows:

  • The ~4× prediction holds for N ≥ 2,048 (3.84–4.11×). Below that, fixed per-row and per-launch costs blunt it (2.44× at N = 256).
  • All three lines hit the same memory ceiling. Recomputed as real traffic, for N ≥ 1,024 naive moves 1.3–1.5 TB/s, about what Triton does. Naive isn't slow per byte; it moves 4× the bytes. That's the whole argument for fusion.
  • Triton vs torch.softmax is mixed. Triton is faster in 60 of the 98 rows. torch.softmax wins at N ≤ 1,024 (Triton is 0.71× of it at N = 256) and in the bands 5,888–6,144, 6,656–7,168 and 9,344–12,160. Its dips at N = 2,176 and 7,296–9,216 look like kernel-selection switch points inside PyTorch (our inference).
  • A claim to flag. The tutorial's closing text says "Triton is 4x faster than the Torch JIT". But the benchmark's third line is naive_softmax, which is plain eager PyTorch; no torch.jit.script appears in the code. Read it as "4× faster than unfused PyTorch".

Why it beats the alternatives

✗ CUDA C++ (program the threads)

Full control, but you write every item on the compiler list yourself: coalescing, shared-memory tiles, syncs, vector loads, pipelining. siboehm's SGEMM took two weekends for 80% of cuBLAS and four more for 94% (matmul IV).

✗ PyTorch eager (unfused)

One kernel per op, each going back to DRAM. naive_softmax is 5 kernels and moves 8MN + 4M elements. In the tutorial's table it is 3.84–4.11× slower than the fused kernel for N ≥ 2,048, even though it streams bytes just as fast.

✗ torch.compile (let it write Triton)

Zero effort. PyTorch's docs: "TorchInductor specifically works by generating Triton kernels." But you get the fusions the compiler finds. When you need a new algorithm, such as online softmax over a 128k-wide row or a custom attention, you write the Triton yourself (our framing).

✓ Triton (program the blocks)

About 20 lines of Python at block level. The compiler does the thread-level work. The fused softmax matches the ~4× bound over eager and beats torch.softmax in 60 of 98 printed rows. It's the best productivity-per-GB/s trade here, and the language the compiler above emits.

Does Triton beat CUDA?

Not reliably, and the tutorials don't claim it does. Their own tables (GPU not named):

  • Softmax vs torch.softmax (a hand-written CUDA kernel inside PyTorch): Triton is faster for most large N (1.25× at N = 8,192), slower at small N (0.71× at N = 256) and slower in several bands up to 12,160.
  • FP16 matmul vs cuBLAS (tutorial 03): 219.7 vs 221.1 TFLOPS at 4,096 (99%). At 2,048 it's 184.4 vs 217.9 (85%), and at 1,024 it's 95.3 vs 104.9 (91%). It roughly matches at large sizes but not everywhere.
  • Vector add: identical. When PyTorch already streams at full bandwidth, a custom kernel buys nothing.

Where hand CUDA and CUTLASS still lead (general practice, our summary, not from the tutorials): the newest hardware features arrive there first. On Hopper and Blackwell that means TMA, warp specialization and block-scaled FP8/FP4 tensor-core formats. The best inference kernels for those features are typically CUDA or CUTLASS. Triton follows; its tutorial list now includes persistent matmul (09) and block-scaled matmul (10).

When not to reach for Triton: element-wise ops that PyTorch already fuses or streams at full bandwidth; code that must run on a Mac (no macOS wheels; TRITON_INTERPRET=1, the CPU interpreter for debugging, still needs Linux); and rows too long for one block, which need a chunked, online-softmax design rather than the tutorial's one-row-per-program kernel. The tutorial code also has an AMD (HIP) path, so Triton isn't NVIDIA-only.
