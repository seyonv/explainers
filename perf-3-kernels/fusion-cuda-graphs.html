Kernel fusion, launch overhead and CUDA graphs

Also called: operator fusion, being overhead-bound, graph capture and replay, torch.compile. Horace He's "Making Deep Learning Go Brrrr" splits GPU time into compute, memory bandwidth and overhead. Fusion attacks bandwidth, CUDA graphs attack overhead, and inference engines such as vLLM use both to cut the time of every decode step.

In one breath

Each PyTorch op is a separate kernel. It reads its inputs from DRAM, writes its output back to DRAM, and costs a few microseconds of CPU and driver work to launch. Fusion merges a chain of ops into one kernel, so the intermediates stay in registers and never go through DRAM. A CUDA graph records a whole sequence of launches once and replays it with a single call, which removes the per-launch CPU cost and the gaps between kernels. Fusion cuts bytes. Graphs cut launches. Neither makes a matmul any faster.

First, find your regime

Horace He's claim is that you should know which of the three costs dominates before you optimize anything, because a fix for one does nothing for the others.

The picture: where the gaps come from

Case A is what happens when the CPU can't run ahead of the GPU. Horace notes that PyTorch runs asynchronously: while one kernel runs, the CPU queues the next. If the kernels are big, launch cost is hidden. If they are small, "the GPU is going to spend most of its time as an expensive paperweight". Small kernels are exactly what batch-1 decode produces.

Fusion: count the trips to DRAM

Horace's example: x1 = x.cos() reads x and writes x1, then x2 = x1.cos() reads x1 and writes x2. That's 4 global reads and writes. Fused, x.cos().cos() reads x once and writes x2 once: 2, so the fused version is "2x" faster. The same reasoning holds for any chain of elementwise ops:

tunfusedone kernel per op ≈ ∑i=1k ini+outiBW tfusedone kernel ≈ bytesin+bytesoutBW
knumber of ops (kernels) in the chaincos().cos(): 2 ini, outibytes kernel i reads and writes, intermediates included4 transfers of x's size bytes in/outonly the chain's real inputs and final outputs2 transfers BWDRAM bandwidthH100 3.35 TB/s · T4 320 GB/s

Both are memory-only times. They hold while the math per element is cheap compared with the bytes, as the next paragraph shows.

How much math is "cheap"? Horace's A100 numbers: 1.5 TB/s and 19.5 TFLOPS for non-matmul work. A unary FP32 op moves 8 bytes per element (4 in, 4 out).

A100: 1.5e12 B/s ÷ 8 B = 187.5e9 elements/s 19.5e12 FLOP/s ÷ 187.5e9 = 104 ops per element ("about a hundred") T4: 320e9 ÷ 8 = 40e9 elements/s 8.1e12 ÷ 40e9 = 202 FLOP per element (FMA counted as 2) = ~101 plain multiplies per element (our recomputation)

Below that line, adding more ops to a fused kernel is free. Horace measured it with x = x * 2 repeated inside one fused kernel on an A100: the runtime "doesn't increase noticeably at all until we're performing 64 multiplications", and throughput climbs from 0.2 TFLOPS to near 9.75 TFLOPS (the A100's non-FMA rate). That's why a fused GELU costs about the same as a fused ReLU. The notebook's part 2 repeats the sweep on the T4.

Decode: when launches rival the memory floor

At batch 1 a decode step has to read all 16.06 GB of weights: 4.79 ms at 3.35 TB/s (≈ 209 tokens/s). Each kernel now does little work, so a per-kernel gap matters. The per-kernel costs below are Hazy Research's H100 measurements. We assume 10 kernels per layer, which is illustrative: an input norm, the QKV matmul, RoPE, attention, the O projection, add + norm, gate/up, silu·mul, down, and a residual add. That's 32 × 10 + 3 (embedding, final norm, LM head) = 323 kernels per step. Hazy's own Llama-1B model uses 7 kernels × 16 layers.

The smaller the model, the more a fixed per-kernel cost dominates. That's why Hazy Research took the idea to its extreme: a megakernel that runs the whole Llama-1B forward pass as one kernel, so there are no launches between layers at all. Eager PyTorch is worse again: Horace measured PyTorch at about 280 thousand ops/s on tiny tensors, roughly 3.6 µs of CPU time per op, before the launch itself.

Graph launches have also become cheaper. NVIDIA's "constant time launch" post reports that on Ampere a repeat launch of a straight-line graph went from 2 µs + 200 ns per node to about 2.5 µs + ~1 ns per node. For a 323-node decode step that's 66.6 µs → 2.8 µs of CPU launch time (our arithmetic on their formula). This is CPU-side launch cost. Hazy's 1.3 µs above is the GPU-side gap per kernel that remains even inside a graph.

Why engines capture: vLLM

vLLM's CUDA Graphs design doc: cudagraph_mode's default is FULL_AND_PIECEWISE, meaning "full CUDA Graph for uniform decode, piecewise CUDA Graphs for others". Piecewise graphs cover everything between the attention ops and run attention eagerly. The doc calls it "generally the most performant setting, especially for low latency with small models or MoEs, but also requires the most memory and takes the longest to capture". A graph is fixed to the shapes it was captured with, so vLLM captures one per size in cudagraph_capture_sizes (the example sets [1, 2, 4, 8]). At run time the dispatcher looks up a key built from the padded token count. If no captured graph matches, it falls back to eager (NONE). What that means in practice, as we read the doc: a batch of 5 is run as a captured size, with padding, and batches past the captured sizes lose the graph.

How the four fixes differ

✗ Eager, unfused

One kernel and one DRAM round trip per op, plus Python and dispatcher time per op. Flexible and easy to debug, but at decode it pays every launch, and every intermediate goes through DRAM.

✗ Hand-fused kernel

The best bytes (e.g. fused_add_rms_norm: 5 → 4 transfers), but someone writes and maintains CUDA for each pattern and each GPU. Worth it only for hot spots; see reduction II for the effort involved.

✗ CUDA graphs alone

Removes per-launch CPU cost and gaps (3.8 → 3.4 µs per kernel on the V100), but every kernel still reads and writes DRAM. Shapes are frozen at capture, so batch sizes must match or be padded.

✓ Compiler fusion, then graph replay

torch.compile generates fused Triton kernels (fewer bytes and fewer kernels), and its reduce-overhead mode, like vLLM, replays them as CUDA graphs. Engines combine this with hand-fused kernels for the hottest ops.

Does a CUDA graph make my kernels faster?

No. The kernels in a graph are the same kernels and run at the same speed: a bandwidth-bound RMSNorm moves the same bytes whether it's graphed or not. A graph removes CPU launch overhead and shrinks the gaps between kernels (from ~2.1 to ~1.3 µs per kernel on an H100, per Hazy Research). That only matters when the gaps are a real share of the step.

  • When graphs don't help: big kernels, where the CPU already runs ahead. Prefill of 1,000 tokens has 441 µs matmul layers, so launch cost is already hidden. Also dynamic control flow or shapes that change every call: a graph replays exactly what was captured.
  • What they cost: capture time (~400 µs for 20 kernels on a V100; vLLM's full-and-piecewise mode "takes the longest to capture"), GPU memory for each captured size, and padding batches up to a captured size.
  • When fusion doesn't help: compute-bound matmuls. There the fix is tensor cores (tensor cores and low precision), not fewer bytes.

To tell which case you're in, use Horace's test: double the batch. If the time barely moves, you're overhead-bound, and graphs (or a megakernel) are the lever.
