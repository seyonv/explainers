Before this: Shared memory, tiling and bank conflicts

Parallel reduction I: divergence and bank conflicts

Also called sum reduction, tree reduction, or Harris's reduction. This card walks slides 1–15 of Mark Harris's "Optimizing Parallel Reduction in CUDA": why reduction is hard to make fast, the right metric, and kernels 1 to 3 on an NVIDIA G80, which go from 2.083 to 9.741 GB/s by changing only which thread adds which pair.

In one breath

Summing an array on a GPU means adding pairs in a tree: half as many partial sums each step, in log2(n) steps. The additions are trivial. What's slow is how the threads are assigned to the pairs: pick them so that whole warps sit out, rather than some lanes of every warp, and so that a warp's shared-memory reads land in different banks.

Why reduction, and why it's hard

Harris picks reduction because it is common, easy to write in CUDA, and hard to get right. Inside a block, threads add neighbours in a tree:

Slide 3's example: 8 values, 3 steps, 7 additions (n − 1, the same as a sequential loop).

A big array needs many blocks, so the blocks' partial sums must be combined. That needs a global synchronization: every block must finish before anyone reads the partial sums. CUDA has none, because it would be expensive to build for GPUs with many processors and would force programmers to run no more blocks than fit on the GPU at once, or deadlock. The fix on slides 4–5: a kernel launch is the global sync. Launch once to get one partial sum per block, then launch the same kernel again on those sums, until one value is left.

2^22 ints, 128 threads per block, 1 element per thread (kernels 1–3): launch 1: 4,194,304 ÷ 128 = 32,768 partial sums launch 2: 32,768 ÷ 128 = 256 launch 3: 256 ÷ 128 = 2 launch 4: 2 → 1 (our recomputation)

The three kernels

All three load one element per thread into shared memory sdata, run the loop below, then thread 0 writes sdata[0]. Only the loop changes (bd = blockDim.x).

Kernel 1: interleaved, divergent

for (s = 1; s < bd; s *= 2) {
  if (tid % (2*s) == 0)
    sdata[tid] +=
      sdata[tid + s];
  __syncthreads();
}

Kernel 2: strided index

for (s = 1; s < bd; s *= 2) {
  int index = 2*s*tid;
  if (index < bd)
    sdata[index] +=
      sdata[index + s];
  __syncthreads();
}

Kernel 3: sequential

for (s = bd/2; s > 0; s >>= 1) {
  if (tid < s)
    sdata[tid] +=
      sdata[tid + s];
  __syncthreads();
}

Slides 7, 11 and 15. Kernel 1's problem (slide 9): "highly divergent warps are very inefficient, and % operator is very slow". Kernel 2 fixes divergence but creates shared-memory bank conflicts (slide 12). Kernel 3 reverses the loop so active threads read consecutive words (slide 14: "conflict free").

Kernel 2's new problem: bank conflicts

Shared memory is split into banks; successive 4-byte words go to successive banks. A warp's access is served in one pass only if no two lanes want different words in the same bank; otherwise the hardware splits it into as many passes as the worst bank needs. Kernel 2's index = 2·s·tid spreads warp 0 across every 2nd, then every 4th bank:

Where this shows up in Llama-3.1-8B inference

Our framing, not in the slides. Inference is full of reductions, but they're many small rows, not one huge array:

A 4,096-element row fits one block, so the multi-launch problem disappears and the in-block tree from this card is the whole job. Real engines usually fuse these reductions into neighbouring kernels (see fusion).

Why it beats the alternatives

✗ Kernel 1: tid % (2*s)

Active threads are spread across every warp, so all 4 warps issue for 5 of 7 steps while most lanes sit masked. Plus a slow modulo. 2.4% of peak.

✗ Kernel 2: index = 2*s*tid

Packs the work into the fewest warps, but each warp's reads land 2 to 4 words per bank (up to 8 on G80), so shared memory serializes. 5.6% of peak.

✗ Kernel 3: sequential addressing

No divergence across warps and no bank conflicts. But half the threads never add anything, even in step 1, and address arithmetic and loop overhead remain. 11.3% of peak.

✓ A library call

cub::DeviceReduce::Sum or torch.sum: one line, correct for any size, and tuned per GPU (CUB's docs note it picks different tile sizes per architecture). Write your own only to learn, or to fuse the sum into another kernel.

Why is divergence costly if the idle threads do nothing?

Because a warp has one instruction stream for its 32 lanes. When some lanes take the if and others don't, the warp issues the if body anyway and masks the idle lanes: they are disabled, not freed to do other work. Kernel 1 at step 5 still spends 4 full warp issues on 4 additions. Idle lanes cost nothing only when a whole warp is idle, because then the warp skips the instruction (kernels 2 and 3).

Divergence isn't always the problem. Kernel 3 still diverges inside warp 0 for its last 5 steps (16, 8, 4, 2, 1 lanes active), and that's fine at the tail. Its real waste, the first loop step that leaves half the threads idle and the loop overhead, is where part II starts. And since Volta, lanes of a warp are scheduled independently, so code must not assume they run in lock step; that's exactly why the slides' kernel 5 needs rewriting today.

Next: part II

Kernel 3 leaves half its threads idle in the first step (slide 17). Once that's fixed, Harris finds the kernel limited by instruction overhead, not memory (slide 20). Parallel reduction II: unrolling and cascading adds during the load, unrolls the last warp, fully unrolls with templates, and has each thread sum many elements (Brent's theorem), reaching 62.671 GB/s, 72.5% of the G80's peak.
