Matmul II: coalescing and shared-memory caching

Also called siboehm's kernels 2 and 3, GMEM coalescing and SMEM cache-blocking. This card walks the worklog's sections "Kernel 2: Global Memory Coalescing" and "Kernel 3: Shared Memory Cache-Blocking" (including "Occupancy Calculation for Kernel 3") in order. The article's numbers are from an RTX A6000, multiplying 4092 × 4092 fp32 matrices.

In one breath

Kernel 2 changes only which thread computes which entry of C, so that the 32 threads of a warp read 32 neighbouring floats of B, which the hardware merges into one wide load. That gives 6.4× more speed from two edited lines. Kernel 3 then has each block copy 32 × 32 tiles of A and B into on-chip shared memory once and reuse them 32 times. Global loads drop 32-fold, but each multiply-add now waits on two shared-memory loads, so the gain is only 1.5×.

Kernel 2: make a warp read consecutive addresses

Warps come from consecutive thread IDs. A block's threads are grouped into warps of 32 in order of threadId = threadIdx.x + blockDim.x·(threadIdx.y + blockDim.y·threadIdx.z), so x is the fast-moving dimension. Each warp goes to a warp scheduler (the A6000 has four per SM). When the 32 threads of a warp load 32 consecutive, aligned 4-byte floats, the hardware can serve all of them with one 32 × 4 B = 128 B transaction. The GPU supports 32 B, 64 B and 128 B accesses. If the addresses are scattered, it issues as many 32 B loads as it needs, and most of each one is wasted.

What was wrong with kernel 1. Kernel 1 mapped threadIdx.x to the row x of C. A warp therefore computed 32 entries going down one column of C. On each step i of the dot product, its 32 threads read A[x*K + i] from 32 different rows, K floats (16 KB) apart. The profiler showed only 15 GB/s of global memory (GMEM) throughput.

// kernel 1: warp = 32 consecutive threadIdx.x = 32 different rows of C const uint x = blockIdx.x * blockDim.x + threadIdx.x; const uint y = blockIdx.y * blockDim.y + threadIdx.y; // kernel 2: 1-D block of 32*32 threads; warp = 32 consecutive columns of one row const int x = blockIdx.x * BLOCKSIZE + (threadIdx.x / BLOCKSIZE); const int y = blockIdx.y * BLOCKSIZE + (threadIdx.x % BLOCKSIZE); // launch: gridDim unchanged, blockDim(32 * 32); the loop body is identical

One warp, one step i of the k-loop, with no caching. Green: coalesced reads, or one float broadcast to the whole warp. In both kernels the warp touches 132 distinct useful bytes per step. Kernel 1 fetches 1,056 B to get them, kernel 2 fetches 160 B (6.6× less).

The assembly doesn't change. The article's sidenote: coalescing "changes nothing in the assembly" (the SASS is identical). The hardware merges the accesses at runtime, because the compiler can't know that pointers passed in as arguments are aligned. Two more details from the article. First, the threads in a warp only need to cover consecutive addresses together. They don't have to access them in order. Second, the per-thread work is unchanged: each result still needs 2K loads (K = 4092), which is 8,184 loads. Kernel 2 fixes how many bytes move per load, not how many loads there are.

Kernel 3: cache tiles in shared memory

Shared memory (SMEM) is a small memory physically on the chip, one per SM, divided logically among the blocks running there. On the A6000 a block may use up to 48 KB, and each SM has 100 KB. The article couldn't find Ampere benchmarks and quotes a Volta paper instead: 750 GiB/s global vs 12,080 GiB/s shared, which is 16.1× more bandwidth (and lower latency).

Each block owns a 32 × 32 tile of C (1,024 threads, one result each). Per step it loads the current 32 × 32 chunk of A and of B (green) into As and Bs, then slides right along A and down along B. Grey chunks are finished; the C tile accumulates in registers.

  1. Load. Each thread copies one float of A and one of B into SMEM. threadCol = threadIdx.x % 32 is the fast index, so these loads are coalesced, as in kernel 2.
  2. __syncthreads() waits until the whole tile is in SMEM.
  3. Compute. Each thread does 32 multiply-adds, reading its row of As and its column of Bs.
  4. __syncthreads() again, so that fast threads don't overwrite the tile while slow threads are still reading it. Then move on to the next chunk along K.
for (int bkIdx = 0; bkIdx < K; bkIdx += BLOCKSIZE) { // abridged from the article As[threadRow * BLOCKSIZE + threadCol] = A[threadRow * K + threadCol]; Bs[threadRow * BLOCKSIZE + threadCol] = B[threadRow * N + threadCol]; __syncthreads(); A += BLOCKSIZE; B += BLOCKSIZE * N; // next chunk for (int dotIdx = 0; dotIdx < BLOCKSIZE; ++dotIdx) tmp += As[threadRow * BLOCKSIZE + dotIdx] * Bs[dotIdx * BLOCKSIZE + threadCol]; __syncthreads(); } nvcc --ptxas-options=-v: Used 37 registers, 8192 bytes smem, 400 bytes cmem[0] SMEM per block = 2 × 32 × 32 × 4 B = 8,192 B = 8 KB

Loads per result: the thread through all four matmul cards

Count the loads one result of C costs. Kernel 1 (and kernel 2) load a whole row of A and a whole column of B per result, which is 2K loads from GMEM. In kernel 3, each float of A is loaded into SMEM once per block and then read by the 32 threads that compute the 32 results in its row of the C tile. The same holds for B, per column.

The article counts per thread: K/32 iterations of the outer loop × 2 GMEM loads = K/16, and K/32 × 32 × 2 = 2K SMEM loads. In general, a block tile of BM × BN results costs K·(BM+BN)/(BM·BN) GMEM loads per result. That is 2K when BM = BN = 1 (kernel 1) and K/16 when BM = BN = 32. An analogy: coalescing is a bus picking up 32 people waiting at one stop instead of 32 people scattered across town. Shared memory is the block's own shelf: fetch a tile once from the warehouse, and everyone in the block takes what they need from the shelf.

Occupancy: not the problem (briefly)

Occupancy is active warps per SM ÷ the maximum possible. The article works it out from the A6000's cudaGetDeviceProperties numbers and kernel 3's 37 registers, 8 KB of SMEM and 1,024 threads per block:

shared memory: 102,400 B/SM ÷ (8,192 + 1,024 runtime) B/block = 11.1 → 11 blocks threads: 1,536 threads/SM ÷ 1,024 per block → 1 block registers: 37 × 32 = 1,184 → rounded to 1,280 per warp × 32 warps = 40,960 of 65,536 per SM → 1 block occupancy = 32 active warps ÷ 48 max = 66% (limited by threads and registers)

The article says "66% occupancy is not too bad". The profiler agrees: warps often sit in "Stall Not Selected", meaning they were ready but another warp was picked. The full calculator, and why low occupancy can still be fast, is on occupancy and latency hiding.

What the profiler found: shared-memory loads dominate

Most executed instructions are LDS (shared-memory loads), ahead of FMA and the IADD3 pointer arithmetic. The inner loop in PTX has two ld.shared for every fma:

ld.shared.f32 %f91, [%r8+3456]; ld.shared.f32 %f92, [%r7+108]; fma.rn.f32 %f93, %f92, %f91, %f90;

The biggest stall is Stall MIO Throttle. The article quotes Nsight Compute's Kernel Profiling Guide:

"Warp was stalled waiting for the MIO (memory input/output) instruction queue to be not full. This stall reason is high in cases of extreme utilization of the MIO pipelines, which include special math instructions, dynamic branches, as well as shared memory instructions"

The kernel uses no special math and no dynamic branches, so the stalls come from SMEM accesses. The article's remedy: "have each thread compute more than one output element". That is the next card, which gets 8474.7 GFLOP/s (2.84×).

Why it beats the alternatives

✗ Kernel 1: naive

A warp walks down a column of C, so each step reads 32 rows of A that are 16 KB apart: 33 sectors to get 132 useful bytes. 15 GB/s, 309 GFLOP/s, 1.3% of cuBLAS.

✗ Kernel 2 alone: coalesced

Same loads, far fewer bytes moved: 5 sectors per step, 110 GB/s, 1986.5 GFLOP/s. But every result still issues 2K = 8,184 GMEM loads (0.25 FLOP/B), so it is stuck at 8.5% of cuBLAS.

✗ Let the L1 cache do the reuse

This already works well, which is the article's sidenote on why kernel 3 gains only 50%. But the hardware decides what stays in cache. Nothing guarantees a tile is still there when the next warp needs it, and you can't plan larger tiles around it.

✓ Kernel 3: coalesced + SMEM tiles

Each float of A and B crosses from GMEM once per block and serves 32 results: K/16 GMEM loads, 8 FLOP/B, 2980.3 GFLOP/s. Kernels 4–10 all build on this structure, which the programmer controls.

Kernel 3 caches data on-chip, so why is it only 1.5× faster?

Because the bottleneck moved from GMEM to SMEM instead of going away.

  • Two SMEM loads per multiply-add. Each thread still does one result with 2K SMEM loads, one As and one Bs per FMA. Shared memory is fast, but it isn't free. The LDS instructions fill the MIO queue, so warps stall in "MIO Throttle" while the FMA units sit idle. The kernel is SMEM-instruction-bound, not DRAM-bound.
  • Kernel 2 was already getting cache help. In the article's words, "our previous kernel already had pretty good L1 cache hit rates". Our inference from its numbers: at 1986.5 GFLOP/s and 0.25 FLOP/B, kernel 2 issues about 7.95 TB/s of thread-level loads, but the profiler measured 110 GB/s. Broadcasts and L1 must have served about 98.6% of them. Kernel 3 mostly turns implicit cache hits into explicit SMEM hits.
  • Occupancy isn't the cause. It is 66%, and warps are often "not selected".

The fix is to compute more results per thread, so that each value loaded from SMEM into a register feeds several FMAs. With 8 results per thread (kernel 4), SMEM loads drop from 2K to 9K/8 per result and speed rises 2.84×. See Matmul III.

When SMEM tiling is not worth it: when data isn't reused. Vector add, elementwise ops and a plain copy read each element once, so a tile only adds barriers (use coalescing alone, as on the coalescing card). And in production you rarely write this yourself. cuBLAS, CUTLASS and Triton (Triton matmul) already tile, and on tensor-core GPUs the real matmuls use MMA instructions, not the fp32 FMAs these kernels use.
