Matmul IV: vectorize, autotune, warptile

Also called siboehm kernels 6–11, float4 loads, warp tiling, or "the last 20%". Card 4 of 4 on Simon Boehm's CUDA matmul worklog: FP32 SGEMM on an RTX A6000 at 4092–4096², going from 78.4% to 93.7% of cuBLAS, then what cuBLAS does that a single kernel can't.

Prime · 2 minutes before you read

The problem: At 68.7% of cuBLAS, the big structural wins are spent. What's left is how loads are issued, which tile sizes suit this GPU, and whether the tiling matches how the hardware schedules warps. Each step is worth about 1.1×, and it took siboehm twice the effort of everything before it.

Where it fits: Last of the four siboehm cards. It builds on blocktiling's thread tile and adds a warp level between block and thread. It ends by showing what cuBLAS does that one kernel can't (many kernels, split-K) and points to tensor cores and Triton's autotuner.

In one breath

Once each thread computes 64 results from registers (kernel 5), what's left is getting data in wider chunks (128-bit loads), picking the tile sizes by search rather than by hand, and adding a warp-sized tile between the block and the thread so the code matches how the hardware schedules work. Each step gives about 1.1×. Together they take about twice as many weekends as everything before them.

Kernel 6: vectorize SMEM and GMEM accesses

Two separate changes, both aimed at the congested memory pipeline:

ChangeInstruction before → afterEffect in the article
Transpose As while copying it into shared memory, so a thread's 8 values of A sit next to each otherLDS → LDS.128"a 500GFLOPs speedup, or ~3%"
Read and write global memory through float4 (4 floats = 128 bits) with reinterpret_castLDG.E → LDG.E.128
STG.E → STG.E.128		Rest of the step; total 5 → 6 is 1.14× (table). Block tile BM = BN = 128.

Why a cast rather than an unrolled loop of 4 loads: the compiler can't prove the float* B argument is 16-byte aligned, which 128-bit loads require. The cast is a promise that it is. For shared memory, which the compiler lays out itself, it vectorizes on its own. This is the author's explanation ("I think the reason is…"), not a documented rule. Remaining problems in the profiler: shared-memory bank conflicts (which cuBLAS avoids), occupancy higher than necessary, and no double buffering.

Kernel 9: autotuning the five tile sizes

BM, BN, BK set how much of A and B each block caches in shared memory; TM, TN set how much each thread caches in registers. Kernel 6 used BM = BN = 128, BK = TM = TN = 8. A bash script benchmarked the ~400 combinations that were valid (for example, the A tile BM·BK must be divisible by 4 × threads so every thread issues one 128-bit load).

Kernel 10: warptiling

A new tiling level between the block and the thread. Warps never appear in CUDA source (you only see blocks and threads), but they matter for performance for three reasons the article gives: warps are what the SM's 4 warp schedulers issue; shared-memory bank conflicts happen only between threads of the same warp; and a tighter per-thread tile gives better locality in the register cache.

A6000 settings (src/runner.cu): 128 threads, BM = BN = 128, BK = 16, WM = WN = 64, WNITER = 4, TM = 8, TN = 4 WMITER = (WM·WN) / (32·TM·TN·WNITER) = 4096 / 4096 = 1 → subtile = 64 × (64 / 4) = 64 × 16 threads per subtile = (64/8) × (16/4) = 8 × 4 = 32 = one warp results per thread = WMITER·TM × WNITER·TN = 8 × 16 = 128 = 128·128 outputs / 128 threads

Result: "19.7 TFLOPs to 21.7 TFLOPs on an A100" says the text, but these are the A6000 table's numbers for kernels 9 and 10 (19,721 → 21,779), and the article reports 12.6 TFLOPs as the A100's best kernel 9. The word "A100" there is almost certainly a slip. (The text also writes warpId = threadIdx.x % warpSize; the code uses threadIdx.x / WARPSIZE. The % version gives the lane within the warp.)

Across matrix sizes, and what cuBLAS actually runs

Kernel 10 is within a few percent of cuBLAS at 2048 and 4096, and much worse on small matrices (the article shows this as a plot on an A100, without a table). The reason: cuBLAS is not one kernel. The author found 16 different SGEMM kernels across square sizes up to 4096 and traced which one ran with Nsight Systems:

The article doesn't say which GPU this trace ran on. The 4096 row works out to 14.8 TFLOP/s, which matches the A100 cuBLAS number (14.7), not the A6000's 23.2, so it's probably the A100 (our inference). At 256 the reduce kernel is 36% of the time.

At 256, cuBLAS uses split-K: it splits the shared K dimension across several blocks, so each block computes a partial sum for its chunk of C, then a second kernel adds the partials. The author draws this "but I'm uncertain here". Our explanation of why: a 256² output cut into 64×32 tiles is only 32 tiles, too few to keep every SM busy. The library holds hundreds of kernels, "500MB of compiled code", and picks one at run time from the shape.

A negative result, and the unfinished kernel 11

  • Thread swizzling didn't help. Remapping blockIdx to C tiles so that blocks running at the same time share inputs in L2 made no difference, "presumably because L2 hit rate is already fairly high at 80%". The code was removed.
  • Kernel 11 (work in progress): double buffering. Load the next tile while computing on the current one, at two levels (GMEM → SMEM and SMEM → registers, as in CUTLASS). The article gives no number. The README lists kernel 11 at 17,278.3 GFLOP/s (74.3%), slower than kernels 6, 9 and 10, so double buffering as written in this repo didn't pay off on the A6000. That says nothing against the technique: CUTLASS relies on it. The repo also has a kernel 12 (a second attempt using cuda::memcpy_async) with no published number.
  • Also on the author's to-do list: Hopper warp specialization plus loading straight from GMEM into SMEM without passing through registers, to reduce register pressure; bank-conflict-free SMEM layouts; reading Triton's generated PTX.

From a teaching SGEMM to real inference kernels

This part is our framing, not the article's. FP32 SIMT SGEMM is a teaching vehicle: every idea here (coalescing, tiling at three levels, vectorized loads, autotuning) carries over, but production LLM GEMMs run on tensor cores in BF16 or FP8. The article itself notes that letting cuBLAS use TF32 or BF16 tensor cores "increases FLOPS by 2.5x or 3.5x" on the author's setup, and the A6000 is advertised at 309 TFLOPs on tensor cores against 30 on CUDA cores. The whole 75× ladder happens inside the smaller box.

On Hopper, the next steps are the ones siboehm's kernel-11 notes point to. Shankhdhar's worklog starts from a Simon-style kernel (32 TFLOPs on an H100), switches to tensor-core WGMMA instructions with TMA loads (317), then adds warp specialization (producer warps load while consumer warps compute), larger tiles, clusters and Hilbert-curve tile ordering, and ends at 764 TFLOPs against cuBLAS's 716: 7% faster than cuBLAS at 4096² BF16.

running example: prefill of 1,000 tokens on Llama-3.1-8B FLOPs = 2 × 8.03e9 × 1,000 = 1.61e13 at H100 peak 989 TF → 16.2 ms (floor, from _facts) at 764 TF (best BF16 GEMM) → 21.0 ms at 32 TF (SIMT-style kernel) → 502 ms ≈ 31× slower than the floor

Illustrative: this treats the whole model as one 4096² GEMM running at that speed. Real prefill GEMMs have other shapes (for example 1,000 × 4,096 by 4,096 × 14,336), plus attention and other kernels.

Why it beats the alternatives

✗ Vectorized loads alone

Cheap and worth doing (1.14×), but they only widen each trip to memory. They don't change how work is split across warps, so bank conflicts and scheduling stay as they were, stopping at 78.4%.

✗ Autotuning alone

+8% with no new ideas, but the winner is specific to one GPU (0.95× of best when moved to an A100) and nobody can explain it. It only searches the design you already have.

✗ "Just call cuBLAS"

The right call in production: it picks among 16+ SGEMM kernels by shape, including split-K. But it's a ~500 MB black box: you can fuse only the epilogues it offers, and you learn nothing about why it's fast.

✓ Warptiling (with the other two)

Gives the warp, the unit the hardware schedules, its own tile, so the code matches all three levels of parallelism. It reached 93.7% of cuBLAS at 4096², and it's the structure tensor-core kernels build on.

Why did the bank-conflict fixes make it slower?

The article doesn't say. All it says is that kernels 7 and 8 "eliminate the conflicts but were overall still slower". The README gives the numbers: 16,213.4 and 16,459.2 GFLOP/s, against 18,237.3 for kernel 6 (0.89× and 0.90×). No profile or explanation is published.

A guess from reading the code (ours, unverified): kernel 6 reads its Bs values with 128-bit LDS.128 loads. Kernel 7 re-lays Bs so each thread's values are 16 floats apart, and kernel 8 pads each row to 133 floats (532 bytes, not a multiple of 16), so neither layout allows 128-bit reads of Bs. They may have traded bank conflicts for 4× as many shared-memory load instructions for Bs (8 scalar loads instead of 2 wide ones per step). Section 6 of the notebook counts LDS.128 per kernel in the compiled code so you can check this. Even if the counts match, that alone wouldn't prove it's the whole reason.

When warptiling is not the answer: for small or skinny matrices (kernel 10 falls well behind cuBLAS on sizes below 2048, where cuBLAS switches to other kernels and split-K); for anything in BF16/FP8 (use tensor cores through cuBLAS, CUTLASS or Triton); and in production, where you'd call a library unless you need a fused epilogue it can't give you.

Understand and remember

  • Kernel 5 stalls on a congested memory pipeline → 128-bit loads move 4 floats per instruction (transpose As so its reads are contiguous; float4 casts for global) → fewer load instructions for the same bytes → 1.14×
  • Tile sizes interact with registers, shared memory and SM count in ways nobody can predict → benchmark every valid (BM, BN, BK, TM, TN) → +8% on the A6000 → but the winner is GPU-specific and unexplained
  • Warps are what the SM's schedulers issue and where bank conflicts happen → give each warp its own tile inside the block tile → the code's three levels (block → warp → thread) match the hardware's three levels of parallelism → 1.10×, 93.7% of cuBLAS
  • Small or skinny shapes give too few output tiles to fill every SM → cuBLAS ships many kernels and splits K across blocks, then reduces the partials → one hand-written kernel falls behind below 2048²
  • detail that matters Re-laying out shared memory to kill bank conflicts can break 16-byte alignment → 128-bit LDS.128 reads become 4× as many scalar loads → a fix for one bottleneck can re-create another (the likely story behind kernels 7 and 8, not verified)

Why this step?

5 · Predict commit to an answer before revealing

You move siboehm's kernel 10 to 256 threads with BM = BN = 128, WM = 64, WN = 32, WNITER = 2, TM = 8, TN = 4. Commit before computing: how many warps per block, what is WMITER, and how many results per thread?

Reveal

The block tile holds (128/64) × (128/32) = 8 warp tiles for 8 warps (256 threads). WMITER = (64·32) ÷ (32·8·4·2) = 2,048 ÷ 2,048 = 1, so each warp tile splits into 2 subtiles of 64 × 16, each covered by (64/8) × (16/4) = 32 threads. Results per thread = (1·8) × (2·4) = 64 = 128·128 ÷ 256. Half the results per thread of the original config, so its effective register tile (8 + 8 loads for 64 FMAs, 0.25 per FMA) is back to kernel 5's.
