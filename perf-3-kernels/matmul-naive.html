Before this: Memory coalescing · Compute-bound or memory-bound? (perf-1)

Matmul I: the naive kernel and the lower bound

Also called SGEMM (single-precision general matrix multiply), siboehm's worklog, or "kernel 1". This is Simon Boehm's How to Optimize a CUDA Matmul Kernel for cuBLAS-like Performance (Dec 2022): the intro and results table, "Kernel 1: Naive Implementation", "Lower Bounding the Fastest Possible Runtime" and "Memory Access Pattern of the Naive Kernel". His numbers are on an RTX A6000. The T4, H100 and Llama figures are our recomputation.

In one breath

Before you tune a kernel, work out the fastest it could possibly run: the FLOPs divided by peak compute, and the minimum bytes divided by peak bandwidth. A 4092² fp32 matmul needs 137 GFLOP but only 268 MB of traffic, so a good kernel is compute-bound. The naive kernel, one thread per output, re-reads the inputs until it moves about 2,000× that minimum and reaches 1.3% of cuBLAS.

The setup

SGEMM computes C = αAB + βC in fp32. siboehm's benchmark uses three 4092 × 4092 fp32 matrices on an RTX A6000 (Ampere, 84 SMs), which is advertised at 30 TFLOP/s fp32 and 768 GB/s. The yardstick is cuBLAS at fp32. He notes that TF32 or BF16 would let cuBLAS use tensor cores, which would give 2.5× or 3.5× more FLOPs, but that's a different problem.

Kernel 1: one thread per entry of C

Each thread computes one dot product: row x of A with column y of B. No two threads write the same entry, so no synchronization is needed. The launch covers C with 32 × 32 blocks (1,024 threads, the per-block maximum):

// launch: as many 32×32 blocks as it takes to cover C dim3 gridDim(CEIL_DIV(M, 32), CEIL_DIV(N, 32), 1); dim3 blockDim(32, 32, 1); sgemm_naive<<<gridDim, blockDim>>>(M, N, K, alpha, A, B, beta, C); __global__ void sgemm_naive(int M, int N, int K, float alpha, const float *A, const float *B, float beta, float *C) { const uint x = blockIdx.x * blockDim.x + threadIdx.x; // row of C const uint y = blockIdx.y * blockDim.y + threadIdx.y; // column of C if (x < M && y < N) { // tile quantization guard float tmp = 0.0; for (int i = 0; i < K; ++i) tmp += A[x * K + i] * B[i * N + y]; // K loads of A, K loads of B C[x * N + y] = alpha * tmp + beta * C[x * N + y]; // 1 load + 1 store of C } }

From siboehm's article and repo (SGEMM_CUDA, MIT License). Matrices are row-major. The code is written from one thread's point of view.

The article's diagram uses two threads, one red and one green. Here green is one thread and dashed is its warp neighbour. A warp is 32 threads with consecutive threadIdx.x, so at each step i the warp reads 32 floats of A spaced 16 KB apart. That scattered pattern is what kernel 2 fixes (see memory coalescing).

Sidenote: tile quantization. When the matrix size isn't a multiple of the block size, extra blocks are launched to cover the edge, and the if idles the threads that fall outside. The article's picture shows 9 blocks with only 4 fully used. At 4092: CEIL_DIV(4092, 32) = 128, so 128² blocks × 1,024 = 16,777,216 threads for 16,744,464 entries, which leaves 32,752 idle (0.20%). At 4096 none are idle. The effect is small here and large for small or awkward shapes.

Lower-bounding the fastest possible runtime

This part doesn't depend on any implementation. Count the work, count the unavoidable bytes, and divide each by the hardware's peak.

Three quirks in the source, reproduced as written. (1) The minimum is 268 MB, but a later sentence says 278 MB, which looks like a typo. (2) "~10×" is a rounded 13.1×. (3) The article says cuBLAS reaches "~245 FLOPs/Byte", but 137.1 GFLOP ÷ 500 MB gives 274. The article doesn't show how it got 245, so we can't reconcile the two. With tensor cores the article concludes an optimized kernel "would almost surely still be memory bound": 0.44 ms of math is barely above the 0.35 ms floor, and any real kernel moves more than the minimum.

Memory access pattern of the naive kernel

Assume the worst case, zero caching: each thread loads its own row of A, its own column of B and one entry of C straight from global memory.

floats per thread = 2·4092 + 1 = 8,185 threads = 4092² = 16,744,464 traffic = 8,185 × 16,744,464 × 4 B = 548.2 GB (article: 548 GB) vs the minimum = 548.2 GB / 267.9 MB = 2,046× (the bound allows ~13×) at 768 GB/s that alone takes 548.2e9 / 768e9 = 0.71 s

What siboehm measured: ~300 GFLOP/s (the table says 309.0), so 137.1 GFLOP ÷ 309 GFLOP/s ≈ 0.44 s per matmul (the article says "about 0.5s"). That's 1.0% of the advertised 30 TFLOP/s. The profiler showed only 15 GB/s of global-memory throughput, 2% of the 768 GB/s peak. He blames this on non-coalesced access: a warp's 32 loads of A land on 32 different rows, so the hardware issues many 32-byte transactions to deliver 128 useful bytes. The article explains this in the next section, and Matmul II fixes it (15 → 110 GB/s).

Our inference, not in the article: 548 GB in 0.44 s would need 1,236 GB/s, more than the card's 768 GB/s. And 15 GB/s over 0.44 s is only about 6.7 GB of DRAM traffic. So L1/L2 caches absorb almost all of the 548 GB, and the kernel is limited by issuing and servicing billions of scattered loads, not by DRAM bandwidth itself.

The running example: which side of the roofline is a Llama matmul?

One Llama-3.1-8B MLP up-projection, bf16[B, 4096] × bf16[4096, 14336], on an H100 (ridge 295). The same count as above: FLOPs = 2·B·4096·14336, bytes = 2·(B·4096 + 4096·14336 + B·14336).

Prefill at B = 4,096 is almost exactly siboehm's problem: a 4096 × 4096 input against a 4096 × 14336 weight, compute-bound by a wide margin. Batch-1 decode is a matrix-vector product with intensity 1, far below 295, and no kernel trick changes that. Only batching more tokens does (see the critical batch size). Our recomputation.

Where the naive kernel sits

✗ Naive kernel

309 GFLOP/s, 1.3% of cuBLAS. It is correct and simple, but with no data reuse between threads the traffic is ~2,000× the minimum and the loads are scattered.

✗ Optimized CPU BLAS

siboehm notes that ~300 GFLOP/s is also about what an optimized BLAS got on his 2015 Haswell CPU. A 30 TF GPU running a naive kernel only ties a laptop-class CPU library.

✗ Tensor cores

A 0.44 ms floor at 309 TF, 10× faster than the fp32 floor, but only if you accept TF32 or BF16 precision. It's a different contract from SGEMM, and it would almost surely be memory-bound.

✓ cuBLAS fp32

23,249.6 GFLOP/s, 77.5% of peak. It moves 500 MB, under 2× the minimum, so it sits on the compute side of the bound. That's the target the next three cards climb toward.

If the matmul is compute-bound, why does the naive kernel crawl?

"Compute-bound" describes the problem, not the kernel. The bound says a kernel can be compute-bound if it moves less than ~10× the 268 MB minimum. The naive kernel moves 548 GB (zero-cache count), 2,046× the minimum, so in practice it is limited by memory accesses, not math. Its intensity is 0.25 FLOP/B against the A6000's ridge of 39.

The fix is reuse. Kernel 2 makes each warp's loads coalesced. Kernel 3 stages 32 × 32 tiles in shared memory so each value fetched from DRAM feeds 32 FMAs. Kernels 4–5 give each thread 8 or 64 outputs to raise reuse from registers. Every step lowers bytes per FLOP. That is tiling.

When the lower bound misleads:

  • Small or skinny matrices (the Llama decode row): the minimum traffic already dominates, so the problem itself is memory-bound, and tiling can't help. Batch more tokens instead.
  • Peak FLOP/s is optimistic. siboehm: it's "a reductionist metric" that assumes FMA-heavy code, and peak bandwidth needs a friendly access pattern. Even cuBLAS reaches 77.5%.
  • The 548 GB is a worst case. Caches catch most of it, as the measured 15 GB/s shows. Use the count to see how much reuse is available, not to predict time.
