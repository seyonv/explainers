Matmul III: 1D and 2D blocktiling

Also called siboehm's kernels 4 and 5, register tiling, thread coarsening, or the outer-product formulation. This card walks the worklog's sections "Kernel 4: 1D Blocktiling for Calculating Multiple Results per Thread", "Sidenote on Compiler Optimizations", "Areas of Improvement: Arithmetic Intensity" and "Kernel 5: Increasing Arithmetic Intensity via 2D Blocktiling", in order. The article's numbers are from an RTX A6000, multiplying 4092 × 4092 fp32 matrices.

In one breath

Kernel 3 stalled because every multiply-add needed two shared-memory loads. The fix is to give each thread several results, so that one value it loads into a register feeds several multiply-adds. Kernel 4 gives each thread a column of 8 results: 1.125 shared-memory loads per multiply-add and 2.84× faster. Kernel 5 gives each thread an 8 × 8 square: 0.25 loads per multiply-add, another 1.88×, and 68.7% of cuBLAS. A square beats a column because a TM × TN tile needs only TM + TN inputs for TM·TN results.

Kernel 4: a column of 8 results per thread

Kernel 4 keeps kernel 3's structure: a block copies a slice of A and a slice of B into shared memory (SMEM), syncs, computes, syncs, and moves along K. What changes is the shape. Each block now owns a 64 × 64 tile of C (BM = BN = 64) and walks K in chunks of BK = 8. The SMEM cache is BM·BK + BN·BK = 64·8 + 64·8 = 1,024 floats, 4 KB per block. Each thread computes TM = 8 results stacked in one column, so the block needs 64 × 64 ÷ 8 = 512 threads. Loading stays as before: 1,024 floats ÷ 512 threads = 2 GMEM loads per thread per chunk.

Dimensions reduced for drawing (the article does the same): the real tile is 64 × 64 with 8 rows of threads, here 32 × 16. Grey: the thread's 8 results, held in registers. Green: what it reads from SMEM at one dotIdx. The Bs value is read once and reused 8 times.

The trick is in the loop order. dotIdx is the outer loop, so the thread reads one value of Bs into a register variable Btmp and reuses it for all 8 of its rows:

float threadResults[TM] = {0.0}; // 8 accumulators in registers for (uint bkIdx = 0; bkIdx < K; bkIdx += BK) { // abridged from the article As[innerRowA * BK + innerColA] = A[innerRowA * K + innerColA]; Bs[innerRowB * BN + innerColB] = B[innerRowB * N + innerColB]; __syncthreads(); A += BK; B += BK * N; for (uint dotIdx = 0; dotIdx < BK; ++dotIdx) { float Btmp = Bs[dotIdx * BN + threadCol]; // 1 SMEM load, reused 8 times for (uint resIdx = 0; resIdx < TM; ++resIdx) threadResults[resIdx] += As[(threadRow * TM + resIdx) * BK + dotIdx] * Btmp; } __syncthreads(); }

The article's count, per thread. Kernel 3 (one result): K/32 outer iterations × 2 GMEM loads, and K/32 × 32 × 2 SMEM loads, so K/16 GMEM and 2K SMEM per result. Kernel 4 (eight results): K/8 iterations × 2 GMEM loads, and K/8 × BK(8) × (1 + TM(8)) SMEM loads, divided by 8 results, so K/32 GMEM and 9K/8 SMEM per result. The profiler agrees: "we now spend much fewer cycles per instruction stalling due to memory pressure" (the article warns that the chart's axis changed from kernel 3's).

Sidenote: the compiler already did the reordering

siboehm tried the obvious loop order too, with resIdx outside and no Btmp. On paper that is BK × TM × 2 = 8 × 8 × 2 = 128 SMEM accesses per chunk instead of 8 × (1 + 8) = 72. It made no difference to speed. The PTX shows why: the loop counts are compile-time constants, so the compiler unrolls both loops and removes the repeated loads, ending up with the same number of SMEM accesses as the hand-optimized version.

LDS R26, [R35.X4+0x800] // article's label: a 32b load from As LDS.128 R8, [R2] // article's label: a 128b load from Bs LDS.128 R12, [R2+0x20] LDS R24, [R35.X4+0x900]

In the SASS (the machine code under PTX) some SMEM loads become LDS.128, one instruction for four floats. The article labels the 128-bit loads as Bs and the 32-bit ones as As, and hints at kernel 6: transpose As so its loads vectorize too. Our reading of the offsets, not the article's: the 32-bit loads step by 0x100 = 64 floats (the row length of Bs) starting at 0x800 = 512 floats (the size of As), and the 128-bit loads step by 0x20 = 8 floats (the row length of As). That suggests the two labels are swapped in this kernel. It doesn't change the lesson: whichever operand a thread reads contiguously gets vectorized.

Why more results per thread: arithmetic intensity

Kernel 4 still stalls for memory, only less. The article's next step is to "just apply the same optimization again": more results per thread, to raise arithmetic intensity, which it defines as FLOPs per byte moved (loads and stores) between GMEM and SMEM. Every kernel does the same FLOPs. Only the loads shrink. And it's "more efficient to calculate a square of results per thread than a column of results because we can share more of the inputs". Redrawn with 16 results each:

One step along K. A column of 16 needs 16 values of A plus 1 of B. A 4 × 4 square needs 4 of A plus 4 of B. Red: inputs used by only one result each. Green: inputs shared by a whole row or column of results. The same argument applies at both levels: to a block's tile (GMEM → SMEM) and to a thread's tile (SMEM → registers).

Kernel 5: an 8 × 8 square of results per thread

Kernel 5 sets BM = BN = 128 and BK = TM = TN = 8. Each thread computes TM·TN = 64 results, so a 128 × 128 block tile takes 128·128 ÷ 64 = 256 threads. SMEM holds 128·8 + 8·128 = 2,048 floats = 8 KB (our arithmetic).

Step 1: everyone loads. 256 threads now fill 1,024 floats of As and 1,024 of Bs, so each thread loads 1,024 ÷ 256 = 4 of each per chunk. The loop strides by strideA rows so that the threads together cover the tile. Our arithmetic: 256 threads over BK = 8 columns cover 32 rows of As per pass, so 4 passes cover 128 rows.

for (uint loadOffset = 0; loadOffset < BM; loadOffset += strideA) As[(innerRowA + loadOffset) * BK + innerColA] = A[(innerRowA + loadOffset) * K + innerColA]; for (uint loadOffset = 0; loadOffset < BK; loadOffset += strideB) Bs[(innerRowB + loadOffset) * BN + innerColB] = B[(innerRowB + loadOffset) * N + innerColB]; __syncthreads();

Step 2: an outer product in registers. For each dotIdx, the thread copies 8 values of a column of As into regM and 8 values of a row of Bs into regN. It then multiplies every regM[m] by every regN[n]: 64 multiply-adds from 16 loads.

for (uint dotIdx = 0; dotIdx < BK; ++dotIdx) { // abridged from the article for (uint i = 0; i < TM; ++i) regM[i] = As[(threadRow * TM + i) * BK + dotIdx]; for (uint i = 0; i < TN; ++i) regN[i] = Bs[dotIdx * BN + threadCol * TN + i]; for (uint resIdxM = 0; resIdxM < TM; ++resIdxM) for (uint resIdxN = 0; resIdxN < TN; ++resIdxN) threadResults[resIdxM * TN + resIdxN] += regM[resIdxM] * regN[resIdxN]; }

The article's count. GMEM: K/8 iterations × 2 (A and B) × 1,024/256 loads. SMEM: K/8 × 8 (dotIdx) × 2 × 8 loads. Per result (÷ 64): K/64 GMEM and K/4 SMEM. The result is 15,971.7 GFLOP/s. But the profiler still shows it isn't done: "warp stalls due to memory pipeline congestion are still too frequent". Kernel 6 attacks that with vectorized loads (Matmul IV).

Volkov saw the same thing in 2010

This is Volkov's "Better Performance at Lower Occupancy" in practice (occupancy and latency hiding). His SDK matmul on a GTX480 went from 1 output per thread at 242 Gflop/s (21 registers, 67% occupancy) to 8 outputs at 485 Gflop/s (63 registers, 33% occupancy): 2.0× faster with 3× the registers and half the occupancy. His explanation fits kernels 4 and 5: independent multiply-adds within one thread (instruction-level parallelism) hide latency just as extra warps do, and "only registers are fast enough to get the peak". Kernel 5's 64 accumulators are 64 independent chains per thread.

Kernel 5's register count: the article doesn't give it (it printed ptxas output only for kernel 3: 37 registers). The source code alone needs at least 64 + 8 + 8 = 80 floats in registers per thread before indices and pointers. That's our lower bound, not a measurement.

Where this leads: tensor cores do the same outer product, bigger

Our framing, not siboehm's. A tensor-core MMA instruction is this kernel-5 inner loop moved into hardware at a larger grain. One WMMA mma_sync on a 16 × 16 × 16 tile has a whole warp compute D = A·B + C: 16 × 16 × 16 = 4,096 multiply-adds from 2 × 16 × 16 = 512 input values, 8 per input. Kernel 5's thread gets 64 from 16, 4 per input. The whole ladder, from block tiles to thread tiles to MMA tiles, is the same trick: pick tile shapes that make each loaded value feed as many multiply-adds as possible. On an H100 running the Llama-3.1-8B example, the BF16 matmuls run as MMAs, not the fp32 FMAs used here. See tensor cores and low precision.

Why it beats the alternatives

✗ Kernel 3: 1 result per thread

Every FMA needs one As and one Bs load: 2K SMEM loads per result. Warps pile up in "MIO Throttle" and the FMA units idle. 2,980.3 GFLOP/s, 12.8% of cuBLAS.

✗ Kernel 4: a column of 8

Btmp is reused 8 times, but each As value still feeds a single FMA: 9 loads for 8 FMAs (9K/8 per result). 2.84× better, yet still stalls for memory. 8,474.7 GFLOP/s, 36.5%.

✗ "More is better": 16 × 16 per thread

K/8 SMEM loads per result on paper, but 256 accumulators per thread. Our note: CUDA caps a thread at 255 registers, so they'd spill to slow local memory, and fewer threads fit per SM. Volkov: Fermi allowed only ≈64 registers per thread. siboehm's autotuner later picked TM = TN = 4 on an A100, so bigger isn't always better.

✓ Kernel 5: an 8 × 8 square

16 loads feed 64 independent FMAs (0.25 per FMA), and GMEM loads fall to K/64. 15,971.7 GFLOP/s, 68.7% of cuBLAS. Kernels 6–10 keep this thread tile and tune around it.

Why does a square tile beat a column of the same size?

Because a TM × TN tile needs TM + TN inputs per step of K for TM·TN results. For a fixed number of results, the sum TM + TN is smallest when the tile is square. For 64 results: a 64 × 1 column needs 65 inputs per step, an 8 × 8 square needs 16. That's 4× fewer loads for identical work. In the square, each A value feeds a whole row of results and each B value a whole column. In the column, each A value feeds one.

  • The same rule, twice. It sets GMEM traffic through the block tile (BM, BN) and SMEM traffic through the thread tile (TM, TN). Kernel 5 squares both.
  • When bigger or squarer is not better. Registers are finite. A bigger thread tile means more registers per thread and fewer resident warps, and past the limit it spills. A big block tile also wastes work at the matrix edges when the size isn't a multiple of the tile (the tile-quantization sidenote on Matmul I). And for small matrices a 128 × 128 block tile leaves most SMs idle: 4092² has 32 × 32 = 1,024 tiles of that size (our arithmetic), but a 256² matmul would have only 4. That's why cuBLAS ships many kernels and why siboehm autotunes (Matmul IV).
  • Intensity isn't the last bottleneck. Kernel 5 is still at 65% of its no-cache GMEM ceiling on the A6000, and the profiler says it stalls on the memory pipeline. The next wins come from how the loads are issued (128-bit loads, bank conflicts), not from how many there are.
