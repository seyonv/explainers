Before this: Memory coalescing

Shared memory, tiling and bank conflicts

Also called SMEM, __shared__, the tiled transpose, or "padding the tile". This card walks Mark Harris's "An Efficient Matrix Transpose in CUDA C/C++" section by section: a 1024 × 1024 float matrix, 32 × 8 threads per block, 32 × 32 tiles, measured on a Tesla M2050 and a Tesla K20c. The bank rules come from his "Using Shared Memory in CUDA C/C++".

In one breath

Shared memory is a small scratchpad on each SM that all threads of a block can read and write, with roughly 100× lower latency than uncached global memory. A block can load a tile from global memory in the order that is cheap, which is coalesced, rearrange it in shared memory, and write it out in the order that is cheap. Shared memory is split into 32 banks. When the threads of one warp need different words from the same bank, those reads take turns.

The words, each with two examples

A picture to keep in mind: shared memory is a counter with 32 cashiers (banks). Customers (threads) queue by cashier, so if all 32 line up at one cashier, everyone waits 32 turns.

Worked example, part 1: the transpose, kernel by kernel

Simple copy. This is the target speed. Each 32 × 8 block copies one 32 × 32 tile, so each thread moves 4 elements in a loop (j += 8). The loop runs over rows, so the 32 threads of a warp touch 32 neighbouring floats: coalesced reads and coalesced writes. The metric throughout is effective bandwidth = 2 × matrix bytes ÷ time (one read and one write).

Naive transpose. This is the copy kernel with the output index swapped: odata[x*width + (y+j)]. The reads stay coalesced, but neighbouring threads now write 1024 elements = 4,096 bytes apart, so each warp's store touches 32 separate memory segments (see memory coalescing).

Coalesced transpose via shared memory. Stage the tile in shared memory, then write it back out along rows:

transposeCoalesced. The green strips are one warp's row in global memory: coalesced both times. The grey strip is the column a warp reads from shared memory. The block writes its tile to the mirrored tile position (by, bx).

for (j = 0; j < 32; j += 8) // row in, stored as a row tile[ty+j][tx] = idata[(y+j)*width + x]; __syncthreads(); x = by*32 + tx; y = bx*32 + ty; // mirrored tile position for (j = 0; j < 32; j += 8) // column read, row out odata[(y+j)*width + x] = tile[tx][ty+j];

copySharedMem. Is the gap to copy caused by shared memory or by the barrier? Harris checks this with a copy that also stages through a shared tile and calls __syncthreads(). It runs as fast as copy, so neither is the cost. Bank conflicts are: in the second loop a warp reads down a column of tile[32][32], and all 32 of those floats sit in the same bank. Declaring tile[32][33] fixes it.

Why 33 works: 33 = 32 + 1, so each extra row moves the start one bank to the right (33i mod 32 = i). Any odd width works for floats. An even width such as 34 gives bank (2i + j) mod 32, which hits only 16 banks: a 2-way conflict.

Physical layout: each column of little cells is a bank, and each line is 32 consecutive words (128 B). Coloured cells are the 32 floats a warp reads in the column loop (tile column 0). Left: they stack in bank 0 and take 32 turns. Right: the pad shifts each row by one bank, so they fall on a diagonal and one request serves all 32.

This transpose needs very little shared memory. On an H100 the large shared memory goes to matmul and attention tiles (matmul II), where many more bytes are reused. Blocks over 48 KB must use dynamic shared memory and opt in explicitly (CUDA guide).

Why it beats the alternatives

✗ Naive transpose

Reads coalesced, writes 4,096 B apart. The writes decide the speed: 18.8 GB/s on the M2050 (17.9% of copy) and 55.3 on the K20c (40.7%).

✗ Shared-memory tile, [32][32]

Both global accesses become coalesced, which is the biggest single step (2.73× / 1.76×). But every column read from the tile is a 32-way bank conflict, so it stalls at 51.3 / 97.6 GB/s.

✗ Swizzled layouts (XOR)

Permute columns instead of padding. The CUTLASS docs XOR each thread's column, (lane_id % 8) ^ (lane_id / 8), so tensor-core ldmatrix loads don't conflict, and Hopper's TMA takes "smem swizzling patterns". Failure mode here: harder index math for no gain. In our bank model it also gives 1 request, so it only pays off where padding would break the alignment of wide loads.

✓ Padded tile, [32][33]

One extra float per row (128 B per block) puts row i of each column on bank i. A one-line change: 1.94× / 1.48×, reaching 99.5 / 144.3 GB/s, about 95% of the fastest copy.

The swizzle cell reports what the CUTLASS docs say. "No gain here" and "pays off where padding breaks alignment" are our summary: the first comes from the lab's bank model (both layouts need 1 wavefront), not from a measurement.

Why do we need __syncthreads() here but not in the copy kernel?

In copy nothing is shared: each thread reads its 4 elements from global memory and writes them itself. In transposeCoalesced the thread that reads tile[tx][ty+j] is not the thread that wrote it. That element was stored by a different thread, usually in a different warp (a block of 32 × 8 = 256 threads is 8 warps). Warps run in no fixed order, so without the barrier a warp could read a column before the other 7 warps have filled their rows, and you'd write stale values. Harris's copySharedMem keeps the barrier even though it's "technically not needed" there, because each thread reads back its own element. It's there only so the comparison with the transpose is fair.

Two rules: every thread in the block must reach the same __syncthreads() (inside a divergent if it's undefined behaviour and can deadlock), and a barrier only covers one block. Blocks can never wait for each other inside a kernel.

When shared memory is the wrong tool: if a copy is already coalesced (the copy kernel), staging it through SMEM adds nothing (104.6 vs 105.2 GB/s on the M2050). If each value is used once and read in the order it's stored, skip SMEM. Newer GPUs have larger L1/L2 caches, so a naive kernel may be hurt less than on the M2050 (it already was on the K20c: 40.7% vs 17.9% of copy). Measure it on your GPU; that's the Colab exercise. In production code you'd call a library transpose or let a compiler such as Triton choose the layout (Triton).
