Memory coalescing

Also called coalesced access, 32-byte sectors, or its failure modes: uncoalesced, misaligned or strided access. This card covers Harris's "How to Access Global Memory Efficiently" (offset and stride kernels) and the copy vs naive-transpose rows of his transpose blog, then checks them against the CUDA Best Practices Guide's modern rule.

In one breath

The 32 threads of a warp issue each load or store together, and the GPU fetches memory for them in aligned 32-byte chunks called sectors. If neighbouring threads touch neighbouring addresses, 32 four-byte floats fill exactly 4 sectors and every byte moved is used. If they're scattered, each thread drags in its own 32-byte sector to use 4 bytes of it, and 7/8 of the bandwidth is thrown away.

Everyday version: a delivery van that only carries full crates of 8 bottles. Order 32 bottles from one shelf and 4 crates arrive. Order one bottle from each of 32 shelves and 32 crates arrive, 224 bottles you didn't want included.

The rule, as NVIDIA states it today

CUDA C++ Best Practices Guide §10.2.1: "For devices of compute capability 6.0 or higher, the requirements can be summarized quite easily: the concurrent accesses of the threads of a warp will coalesce into a number of transactions equal to the number of 32-byte transactions necessary to service all of the threads of the warp." The guide says "32-byte transactions" or "segments". Nsight Compute's metric names and NVIDIA's 2025 update of Harris's blog call them sectors. Four sectors make one 128-byte cache line.

Arrays from cudaMalloc() are "aligned to at least 256 bytes" (Best Practices Guide §10.2.1.2), so element 0 always starts a sector.

What the sources measured

Offsets and strides (Harris, 2012). The blog runs a[i] = a[i] + 1 with i shifted by an offset or multiplied by a stride, on three Tesla generations. Its results are only plots, so here is what the text says about them:

  • Tesla C870 (compute capability 1.0) coalesced per half-warp of 16 threads. Any misaligned access became "16 separate 32-byte transactions", each carrying 4 useful bytes, so bandwidth fell by "a factor of eight". Any stride other than 1 gave "the familiar 1/8 bandwidth". That 1/8 is the same arithmetic as the stride-32 row above: 4 of 32 bytes.
  • Tesla C1060 (1.3): misaligned access was "less problematic", served in "a few transactions that 'cover' the requested data".
  • Tesla C2050 (2.0, Fermi) added an L1 cache with 128-byte lines, giving a "negligible effect of alignment on throughput". But "for large strides, the effective bandwidth is poor regardless of architecture version."

The naive transpose (Harris's transpose blog). transposeNaive is the copy kernel with the output indices swapped. Its reads stay coalesced, but "the writes to odata have a stride of 1024 elements or 4096 bytes between contiguous threads." 1024 × 1024 floats, 32 × 8 threads per tile, effective bandwidth = 2 × matrix size ÷ time, ECC on:

KernelTesla M2050Tesla K20cSectors per warp step (lab)
copy105.2 GB/s136.0 GB/s4 read + 4 write = 8
transposeNaive18.8 GB/s55.3 GB/s4 read + 32 write = 36
copy ÷ naive5.60×2.46×36 ÷ 8 = 4.50× the bytes

The sector count predicts 4.5× more DRAM traffic if nothing is merged in a cache. The M2050 lost even more (5.6×) and the K20c less (2.46×). Our inference, not stated in the blog: the other warps of the same block write the neighbouring floats of those same sectors, so a cache that holds partial sectors until they fill up can merge the writes, and how well that works depends on the GPU.

Why every serving kernel reads weights contiguously

An H100 decode step for Llama-3.1-8B in BF16 streams all 16.06 GB of weights. Suppose a kernel read them so that only 1 byte in 8 of each sector was used (illustrative: no real engine does this):

coalesced: 16.06 GB ÷ 3.35 TB/s = 4.79 ms per step → 209 tokens/s ceiling η = 12.5%: 16.06 GB ÷ 0.125 = 128.5 GB moved 128.5 GB ÷ 3.35 TB/s = 38.4 ms per step → 26 tokens/s

Our recomputation from the course's shared facts, illustrative. Same model, same GPU, 8× slower, and the profiler would still show the memory bus 100% busy. That's why weight layouts, and the kernels that read them, are arranged so that neighbouring threads read neighbouring bytes, usually 16 bytes per thread at a time (the float4 row above).

How the access patterns compare

✗ Misaligned offset

One extra sector per warp: 5 instead of 4, 80% efficient in the sector model. Since Fermi's L1 the measured cost is small (C2050 "negligible", V100 about 9/10), because the next warp uses the extra sector.

✗ Strided access

Stride 2 halves the useful bandwidth. From stride 8 on, every lane gets its own sector and you keep 1/8. Harris: poor "regardless of architecture version". The naive transpose's writes are this case, at 18.8 vs 105.2 GB/s on an M2050.

→ When the algorithm needs a stride

A transpose must read rows and write columns. Stage a 32 × 32 tile in shared memory: read it coalesced, write it out coalesced, and do the strided part on-chip, where a stride costs no DRAM sectors. See shared memory and tiling.

✓ Stride 1, coalesced

Thread k reads element k: 4 sectors per warp, 100% of moved bytes used. Map the fastest-varying thread index (threadIdx.x) to contiguous memory, and it's free: same instruction, same code size.

Doesn't the L1/L2 cache fix bad access patterns?

Partly, and only for offsets. On Fermi and later a misaligned warp's extra sector is usually the next warp's first sector, so it's already cached: Harris's C2050 shows almost no offset penalty, and the Best Practices Guide measures about 9/10 instead of the expected 4/5 on a V100.

It doesn't fix large strides. Bytes still move from DRAM in 32-byte sectors, so a lane that needs 4 bytes still costs a 32-byte sector. A cache only saves you if another warp uses the other 28 bytes before the sector is evicted, which is luck, not design. It may be why the K20c's naive transpose lost less than the M2050's, but even there it ran at 41% of copy.

When coalescing is not the thing to fix:

  • Compute-bound kernels. A well-tiled matmul reads each byte of DRAM once and spends its time in shared memory and registers. There, occupancy, bank conflicts and tensor cores matter more.
  • Small, reused data. A lookup table that fits in L1/L2 and is hit again and again can be read in any order.
  • When the stride is part of the algorithm (transpose, column access, gathers), don't fight the index math: re-stage through shared memory, or change the data layout (for example, an array of structs to a struct of arrays).
