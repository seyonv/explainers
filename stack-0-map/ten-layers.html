The ten layers, by what they own

Also called the agent stack (v1) or the systems map. Vinoth Govindarajan's Part 1 (30 Mar 2026) splits "the agent" into ten layers and says the list is not the main idea: ownership is. Which layer owns the run, the working set, the callable capability, the side effect and the evidence afterward?

Prime · 2 minutes before you read

The problem: When a run goes wrong, "the agent hallucinated" is true in the least useful way. Without naming which part of the system owned the moment that failed, you can't tell a lost exit code from a bad model, so you fix the wrong thing.

Where it fits: First card of the Agent Stack series. You already know the agent loop (call, tool, append, repeat); this card puts that loop inside the ten layers around it and gives every later course its address on the map.

In one breath. "Agent" names a whole chain of systems that don't own the same job. Split it into layers by what each one owns, and a failure stops being "the agent was weird" and becomes a question with an answer: which layer resolved the wrong session, assembled the wrong context, exposed the wrong tool, approved the wrong action or kept too little evidence?

Worked example: the Tuesday run, moment by moment

An illustrative run used across this series: a coding agent is asked to fix the failing test test_parse_due_date in a small repo, invoice-tools. Every moment of it belongs to one layer.

Which layer to blame: not "the model hallucinated". The summary at step 7 dropped the exit code (context layer), and nothing between step 9 and delivery checked the claim against the world. Assigning compaction to layer 5 and the transcript to layer 2 is my reading of his definitions; Part 1 doesn't place compaction.

Why it beats the alternatives

✗ One word: "agent"

Covers session state, orchestration, tools, execution and evidence at once, so every incident reads as "the agent forgot" and points at no fix.

✗ A market map of products

Products now span several layers (a provider API can bundle state, tools, hosted execution and tracing). Sorting by vendor hides which part owns the side effect.

✗ Your framework's boxes

Adopting a framework's abstractions as the architecture confuses product boundaries with system boundaries, and you inherit its blind spots.

✓ Layers by what they own

Every moment of a run has one owner, so "what failed?" becomes "which layer failed?", and you can see the gaps no layer owns, like checking the final claim.

Is this map final?

No, and he says so. He calls it a v1, "not final", and says products slice the layers differently. It isn't ten equal boxes either: the layers differ in size and shape, which is why the picture above is a path with wrappers, not a tower.

The eight parts that follow don't keep all ten apart. Part 7 covers execution surfaces and identity together; he writes that they are strictly separate layers but matter most at the same point, where execution becomes a side effect. From the series titles, Part 2 also pairs infrastructure with models, and interfaces get no part of their own.

When it's overkill: a single model call with no tools has no execution surface, nothing to approve and almost no runtime, so most layers are empty and the map adds little (my inference). It earns its keep once a run has side effects, survives across turns, or has to be debugged after the fact. And knowing which layer owns a moment says where to look, not who is at fault.

1 · Core model what to internalise, what to just look up

Keep it if it changes what you can explain, predict, compare, choose, build or debug. Otherwise it's reference.

Understand and remember

  • One word ("agent") covers state, orchestration, capability, execution and evidence → every failure gets the same vague label → split by what each part owns → a failure becomes "which layer resolved, assembled, exposed, approved or recorded the wrong thing?"
  • The model only turns a prepared request into output → what it sees is chosen by the context layer and what it can do is set by tools and execution → a wrong final claim can come from a working set that lost a fact (step 7), not from the model
  • A tool tells the model what it may ask for, while the execution surface decides what actually happens → exposing a tool is not granting authority → approvals belong where a side effect becomes real, owned by the identity and policy layer
  • The request path ends at delivery, and nothing on it re-checks the final claim against the world → that check has to come from the operator loop (trace, then an evaluation such as re-running the tests) → evidence is a separate layer, not a by-product
  • detail that matters Transcript (durable record, kept with the run) vs working set (assembled per turn) → compaction can drop a fact from the working set while the transcript still holds it → forensics can recover what the model no longer sees

Why this step?

3 · Retrieve from memory, card closed
  1. concept Explain to a teammate why "which layer owns this?" is a better first question in an incident review than "what did the agent do wrong?".
    Check
    • "agent" bundles session, context, capability, execution and evidence, which fail differently
    • naming the owning layer points at a specific fix (summary rules, tool exposure, approval placement, missing trace)
    • it also shows moments no layer owns, which is itself a finding
  2. mechanism Walk the Tuesday run from step 6 to the final message: for each step, say which layer acts, what it holds, and where the fact "exit code 1" exists afterward.
    Check
    • step 6: execution surface runs pytest, exit 1 enters the transcript
    • step 7: context layer compacts; the working set now says "tests passing"; the transcript (control plane) still has exit 1
    • step 9: model writes "all tests pass" from its working set; the interface delivers it
    • checker: operator loop re-runs pytest, exit 1 again, and the trace shows where it was lost
  3. tradeoff Your harness exposes a run_shell tool. A reviewer asks for an approval prompt on every tool call. Where would you put approvals instead, and what still has to stop a dangerous command once approved?
    Check
    • approve where a side effect becomes real (push, write outside the repo), not on every call, or users learn to click yes
    • approval decides whether to proceed; it doesn't limit what the action can do
    • a sandbox or scoped execution surface still bounds the blast radius (see approval is not containment)
  4. tradeoff A provider API bundles stateful continuation, tools, hosted execution and tracing. Does buying it remove layers from your map? What changes for you?
    Check
    • no: packaging collapses faster than architecture, the layers still exist
    • you no longer own some of them, so you must find out where state, side effects and evidence live
    • failures still need a layer name, even if the answer is "inside the vendor"

4 · Compare against what you already know

vs The agent loop: The agent-loop card has two parts, a harness and a model. Which of the ten layers did "the harness" quietly contain, and what goes wrong if you keep thinking of them as one thing?

Check
  • the harness held control plane (session, transcript), runtime (steps, budgets), context assembly, tool exposure and often execution
  • lumping them hides where state lives and who authorizes side effects
  • orchestration failures (retries, stale context, duplicate effects) get misread as model quality

vs Measuring an agent: Measuring an agent graded outcomes with hidden tests. In the ten-layer map, which layer does that belong to, and what is the difference between the trace and the grade?

Check
  • both sit in layer 9, the operator loop
  • the trace (observability) says what happened; the grade (evaluation) says whether it was good enough
  • you can replay a trace forever and still have no release decision without explicit criteria

Why this step?

5 · Predict commit to an answer before revealing

Suppose the harness had kept the raw pytest exit code outside the working set and checked it before letting step 9's message out. Which layer would now own the check, and does the false claim still reach the user?

Reveal

The check moves onto the request path: the runtime (or a policy gate before delivery) compares the claim with the recorded exit code, which was never lost from the transcript. The false claim is blocked or rewritten before the interface delivers it. The operator loop still matters, but now it confirms rather than discovers. Expect the done-chain card to formalize this as checking each link: request, tool, command, effect, delivered.

Why this step?

6 · Apply use the model, don't restate it

Take one transcript of your own (a mini-swe-agent run viewed in trajviz, or a Claude Code session). List every event in order and tag each with the one layer that owns it, using the ten-layer table. Then mark any event no layer checked: a claim, a summary, or a tool result that was taken on trust.

Done when: Every event has exactly one layer tag, at least eight of the ten layers appear or you can say why they are absent, and you name at least one unowned check with the layer you would give it.

Hint

Compaction or summarization events, and the final message, are where unowned claims usually hide. Look for the last real exit code before the final message.
