Same label, different authority

Also called "X is not Y", boundary pairs, or layer collapse. It is Vinoth Govindarajan's recurring move in The Agent Stack: take one overloaded word and split it into the different owners and risks it hides. Part 1 names six pairs, Part 8 adds two, and Hermes Part 5 adds a ninth.

Prime · 2 minutes before you read

The problem: When an agent run goes wrong, one word usually hides the answer. "Done", "tool", "session" and "memory" each cover two jobs owned by two parts of the system, so a check on one job gets read as a check on the other, and every failure gets filed as "the agent was weird".

Where it fits: Second card of the map. The ten-layers card sorted the stack by what each layer owns; this card shows the seams between those owners, using the claim chain from the Tuesday run that the rest of the series keeps returning to.

  3. Why does an approval gate not stop a shell command that never calls the approval?
  4. In the Hermes canary test, why is the comparison between the two Docker runs cleaner than local vs Docker?

In one breath. Words like session, tool, memory or done each get used for two jobs that belong to two different parts of the system. While one word covers both, nobody can say which part failed, and a check on one job gets mistaken for a check on the other. The fix is to name both owners, keep both records, and when something breaks, ask which owner failed instead of "the agent was weird".

Worked example: "done" in the Tuesday run means four things

An illustrative run (the series' running example): a coding agent is asked to fix the failing test test_parse_due_date in a repo called invoice-tools. At step 6, pytest reports 1 failed, 41 passed with exit code 1. At step 7 the context fills, and the harness compacts the history into a summary: "Fixed due-date parsing; tests passing." At step 9 the agent says "Done — fixed the parser and all tests pass."

Run donecontrol planeThe request was accepted, the run closed, and the final message was delivered.✓ yes

Task doneverifierThe world is in the intended state: an independent re-run of pytest passes.✗ exit 1

Two of the four meanings are true and two are false, yet the reply uses one word for all four. A dashboard counting "runs completed" shows green. The false claim also comes from a second collapse: the step-7 summary turned "1 failed" into "tests passing", and the model then wrote its reply from that summary, not from the raw pytest output. That is transcript ≠ context. Hermes Part 5 gives the same split as three receipts: approval (a proposal was allowed), execution (a backend returned) and verification (the target state exists), and recommends reporting "executed, effect unverified" until the verifier succeeds.

You already know: the agent loop (end_turn only means the model thinks it is finished) and measuring an agent (grade the outcome, not the transcript).

How it differs from the usual diagnosis

✗ "The agent was weird"

Blames the model for everything. Retries, stale context, wrong waits and duplicate side effects all look like model quality, so the fix lands in the wrong layer.

✗ Divide by product

"Which agent platform is this?" Products now bundle several layers each, so the product name says nothing about which layer owns the failure.

✗ Adopt a framework's words

You inherit its abstractions as if they were the architecture, and confuse product boundaries with system boundaries.

✓ Name both owners of the word

Ask which layer owns the run, the side effect and the evidence. Each owner keeps its own record, so a failure points at one place.

Is splitting every word always worth it?

No. Each split costs something: another record to keep, another owner, another check. Govindarajan presents the map as a useful v1, not a final standard, and the pairs are his framing, not an industry vocabulary. For a throwaway local script with no side effects, merging "tools done" and "task done" may be fine; the split pays when the agent acts on the outside world or someone has to explain a run later. (That last judgment is ours, not his.)

The pairs also leak into each other. He notes that switching profile can still change authority indirectly, because a profile may select different tools or credentials. And the Hermes results are narrow on purpose: one release, synthetic files, no adversarial test of credential theft. They show the boundary exists; they don't measure how often teams get it wrong. Finally, "approval ≠ isolation" is not a choice between them: he says sensitive systems usually need both.

Understand and remember

  • One word covers two jobs → each job has a different owner and a different failure → a check on one is read as a check on the other → the failure is blamed on the wrong layer ("the agent was weird")
  • "Done" spans run, tools, command and task → the runtime can truthfully report the first two while the command exited 1 → a reply that says "done" claims all four → only a separate verifier receipt can confirm the task
  • Transcript ≠ context → compaction rewrites history into a summary the model reads instead of the raw tool output → "1 failed" can become "tests passing" → the false claim starts from the summary, not from the model inventing it
  • Approval decides whether, isolation decides how far → an approval only guards the paths that call it → a blocked command proves nothing about the shell or the mounts → containment has to come from the OS, container mounts or service credentials
  • detail that matters Hermes Part 5's posture is the effective mount table, not the label "runs in Docker" → the container still had /workspace read-write plus eleven read-only mounts → adding one read-only mount restored read access to the sibling file → audit the real mounts, user and network, not the configuration story

Why this step?

5 · Predict commit to an answer before revealing

Suppose the harness never compacts: the model sees the raw 1 failed, 41 passed output at step 9. Does the false success claim disappear, and which of the four "done" rows would still be able to disagree with the reply?

Reveal

Not necessarily. Removing compaction removes one cause (the summary that upgraded the status), but the model's reply is still unverified text, and models can misread or overstate long tool output. The command and task rows can still be ✗ while the reply says done; only the verifier's independent re-run settles it. The split matters even when every record is accurate, because the reply is a claim, not a receipt.

6 · Apply use the model, don't restate it

Take one real run of your own agent (a mini-swe-agent or Claude Code transcript). Find every place a word like "done", "fixed", "passing" or "saved" appears in the model's text. For each one, write which of the four rows (run, tools, command, task) it claims, and point to the record in the transcript that would confirm it, or write "no receipt".

Done when: A table with one row per claim word, its row type, and either a pointer to a tool output or exit code, or "no receipt"; plus a count of claims that had no receipt.

Hint

Exit codes and test counts usually sit in the tool result just before the claim. A claim made after a compaction or summary step is the first place to look for a missing receipt.
