The forensics method

Also: claim-versus-evidence experiments, negative controls, receipts. This is how Vinoth Govindarajan produces findings in his Hermes posts (each pinned to one release, v0.19.1 to v0.21.0) and OpenCode posts (pinned to 1.18.30, with a scripted model). Every lab in this series reuses the six steps below.

Prime · 2 minutes before you read

The problem: An agent, a scheduler and a CLI can all report success while the file is unchanged or the command failed. If you judge runs by their prose or their own status field, you will ship false successes and draw conclusions that a single counter-example would sink.

Where it fits: The map cards named the layers and showed that the same label can carry different authority. This card is the method you'll use in every lab after it to find which layer's claim stopped matching the world. It builds on measuring an agent, which asks how often; this asks where.

In one breath. Hold one boring task constant, change one owner or condition, and judge every run by what the world shows (exit codes, file bytes, a receipt written only after an independent check), never by what the agent or scheduler says happened. Then write down the narrowest claim the evidence supports and publish everything someone needs to disagree with you.

Run it: the same check in about 80 lines

A Python re-creation of both experiments (not his lab code). Two scripted "agents" return the identical sentence; a cron-style runner logs completed regardless. The verifier only reads bytes and exit codes.

def verify(d, before): code, out = run([sys.executable, "test_slug.py"], d) return {"src_changed": sha(d / "slug.py") != before["src"], "tests_same": sha(d / "test_slug.py") == before["test"], "test_exit": code, "test_out": out} # output before any run: (1, '1 of 3 pass') answer_only said: 'The whitespace bug is fixed and the tests pass.' world: src_changed False, tests_same True, test_exit 1, '1 of 3 pass' tool_loop said: 'The whitespace bug is fixed and the tests pass.' world: src_changed True , tests_same True, test_exit 0, '3 of 3 pass' cron-style run: {'ledger': 'completed', 'exit_codes': [2, 2], 'receipt': False}

The exit code 2 here comes from Python's argparse rejecting apply. as a choice. It mirrors the shape of his cron result; it is not the command he ran. The three slug inputs are ours.

Why it beats the alternatives

✗ Benchmark leaderboard

Gives a pass rate across many tasks. Useful for "how often", but it can't tell you which layer (scheduler, tool, file, delivery) produced a false "done", and it isn't pinned to your harness version.

✗ Vibes and demos

Reads the final message. In the OpenCode experiment both final sentences were identical, word for word, and both processes exited 0. A demo literally cannot tell those runs apart.

✗ Reading the code alone

Tells you what the code intends. In Hermes Part 5 he expected a harmless command to pass; the live run classified and blocked it, which corrected his harness. Source is a hypothesis until a run tests it.

✓ Forensics

Pinned version, boring task, positive and negative controls, a verifier outside the system, a narrow claim, a public lab. It locates the exact boundary where "completed" stopped meaning "done".

Is a forensics lab always the right tool?

No. It finds where a claim can detach from the world, usually from a single run per condition. It does not say how often that happens with a real model. The scripted provider deliberately removes the model, so the OpenCode result is about runtime design, not about how often a model claims false success. For rates you need repeated trials and intervals (stack-4).

It is also narrow on purpose. His Hermes skill result is correlation, not causation, because there was no no-skill control, and every finding is tied to one release. Use forensics to find a boundary worth measuring; use evals to measure it. And for a one-off script you will run once, simply checking the output beats building a lab.

Understand and remember

  • Every layer reports its own lifecycle (CLI exit, scheduler ledger, final sentence) → none of them is entitled to report the operation's effect → check bytes, exit codes and receipts with a verifier outside the system
  • Hold the task constant and change one owner or condition → any difference in outcome belongs to that change → the answer-only vs tool-loop pair isolates "did a tool touch the file" from "what did the run say"
  • A positive run alone shows the path can work → a negative control shows what the status does when the work fails → only the negative cron run exposed that "completed" did not mean the operation succeeded
  • No control for the alternative explanation → you can only claim correlation → the skill-load result stays "correlated with success", not "necessary for success", until a no-skill run is added
  • detail that matters Scripted provider instead of a real model → no inference noise, so one run per condition is enough to show a runtime boundary → but it says nothing about how often a real model makes the false claim; that needs repeated trials

4 · Compare against what you already know

vs Measuring an agent: Forensics labs vs an eval with hidden tests and repeats: what question does each answer, which design choice causes the difference, and how does each one fail?

Check
  • evals answer how often a task succeeds; forensics answers which layer's claim diverged from the world
  • evals repeat many tasks and average; forensics holds one task fixed and varies one condition with a negative control
  • evals fail by hiding the cause inside a rate; forensics fails by over-generalising one run on one release
  • use forensics to find a boundary, then an eval to measure how often it bites

vs 'Done' is a chain of states: The done-chain card splits 'done' into request, tool, command, effect and delivery. Which link did each of his two experiments break, and which piece of evidence showed it?

Check
  • OpenCode answer-only: request completed but no tool ran and the effect was never made; shown by the unchanged file and failing tests
  • Hermes cron: the attempt completed but the command failed (exit 2) and no effect was verified; shown by exit codes and the missing receipt
  • both show that a later link can't be inferred from an earlier one

Why this step?

5 · Predict commit to an answer before revealing

You rerun the OpenCode tool-loop case, but the scripted edit also rewrites slug.test.mjs so all its assertions are trivially true. The final sentence and CLI exit code are unchanged. Which of his verifier checks catches it, and which would not?

Reveal

Re-running the tests would not catch it: they now pass. Checking that the source changed would not either. The check that catches it is "the test assertions did not change" (comparing the test file's bytes before and after). That is why his verifier also checks that the test file's bytes were unchanged, and why a verifier must pin its own oracle, not trust the workspace's.
