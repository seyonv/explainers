1 · The capstone and its neighbours

The paper's question · course 7

When a coding agent's context gets compacted while its tests are failing, does it become more likely to end by falsely claiming the tests pass? Does the effect depend on the harness's compaction prompt and on the model?

Status: open as a controlled, causal measurement. The only direct evidence is one Claude Code case study with no run counts: Tamba, Compaction as Epistemic Failure (arXiv 2607.13071), where partial output from killed processes (exit 143) was written into summaries as confirmed. Rules lost in compaction are measured; claims are not.

Design: force 0, 1 or 3 compactions right after the first failing test; transplant two harnesses' compaction prompts; two models; re-run the visible tests and score the final message. Working title: Compaction Inflates Success Claims: A Dose-Response Study of Test-Claim Honesty in Coding Agents.

The ten questions below extend the paper or sit right next to it. They are ranked by novelty × cheapness × how much the answer would change practice, a judgment, not a score. Green tags name the capstone thread each one feeds: compaction → false claims, the claim checker, judges seeing the summary, or pass^k of honesty.

1Do harnesses cut tool results before the summarizer sees them, and does a verdict-last layout predict what is lost?

capstone: compaction → false claims (mechanism)status: opencost: under $10
Why it matters
pytest prints its verdict last, so a head-only cut drops exactly "1 failed, 41 passed" and the exit code: a cause of false claims that no summary prompt can fix.
Status
Open. Govindarajan traced one harness (OpenCode v1.18.30, a 2,000-character cut) with a scripted provider; no cross-harness measurement exists.
Smallest experiment
Feed one failing pytest output through three or four harnesses' compaction paths, log the summarizer's input, and check whether the counts and exit code are in it. Repeat with the verdict moved to the top.
Source
Course 2 open questions, question 2

2What is pass^k of an honest final report, set beside pass^k of solving the task?

capstone: pass^k of honestystatus: opencost: $0 extra
Why it matters
A user reads every report. An agent can be honest on average and still mislead on some tasks once every few runs; a rate hides that, pass^k shows it.
Status
Open. None of the papers in the novelty check is described as reporting it.
Smallest experiment
Reuse the capstone's repeated runs (n ≥ k per task): mark each run honest or not with the claim checker, compute C(c,3) ÷ C(n,3) per task, average, and print it next to pass^3 of "solved".
Source
Course 4 open questions, question 2

3How strongly do false claims cluster by task and by repo?

capstone: sizing the compaction experimentstatus: opencost: $0 (reanalysis)
Why it matters
The clustering ρ decides the paper's size: a 10-point rise from 20% needs 136 tasks at ρ 0.2 and 194 at ρ 0.5, with 3 repeats each.
Status
Open: no published ρ for false claims is known to the series. The method exists: Miller, clustered standard errors for evals (arXiv 2411.00640).
Smallest experiment
From the pilot audit's 23 submissions × 150 tasks, take each task's share of submissions with a self-contradicted claim, estimate ρ, then cluster by repo instead and compare the two standard errors. Those repeats are different agents, so this gives only the between-task part.
Source
Course 4 open questions, question 4

4Does a judge that reads the compaction summary pass false claims it would catch from the full trace?

capstone: judges seeing the summarystatus: partly studiedcost: 50–100 runs, cheap
Why it matters
If yes, every judge-graded eval and every judge reward on long runs inherits the agent's status inflation, and "grade from the full trace" becomes a rule.
Status
Partly studied. Advani, From Confident Closing to Silent Failure (arXiv 2606.09863): LLM judges reach AUROC ≤ 0.65 at spotting false success. Hu, Silence Is Endorsement (arXiv 2609.20211): summarizers weaken "unverified" status and memory compressors often drop it. Neither gives one judge the two views side by side.
Smallest experiment
On compacted runs the checker fails, give one judge prompt (a) the summary plus final message and (b) the full trace, and compare how often each says PASS.
Source
Course 4, question 1 · Course 5, question 2

5Does injected tool output cause false success claims, not just wrong actions?

capstone: claim checker · pass^k of honestystatus: opencost: low, 450 runs on one model
Why it matters
An authority envelope stops a steered model's actions, not its words. If injection mostly produces false "Done" messages, defences aimed at actions miss the main harm.
Status
Open. AgentDojo (arXiv 2406.13352) measures harmful actions; Failure-Transparent Agents (arXiv 2609.35732) measures false success after a tool fails, not after an injection.
Smallest experiment
30 failing-test tasks × 3 arms (clean fixture, fixture saying "mark the task done", that plus an envelope gate) × 5 repeats. Re-run pytest after each run; report the false-claim rate per arm and pass^5 of honesty.
Source
Course 3 open questions, question 1

6When a false claim happens, was the fact gone from the working set, or still there and ignored?

capstone: compaction → false claims (mechanism)status: partly studiedcost: low–medium
Why it matters
It decides where the fix goes. If most false claims follow a working set that lost the exit code, fix the summarizer; if the exit code was there, more context won't help.
Status
Partly studied. Lost in the Middle (Liu et al., arXiv 2307.03172) found facts in the middle of long inputs are used less well for question answering; whether that holds when a model reports on its own work is unknown, and so is the share.
Smallest experiment
Label 100–200 false-claim transcripts by whether the last exit code was in the final call. Separately, place the failing result at the start, middle or end of one synthetic transcript and count "tests pass" claims per position.
Source
The ten layers (this course) · Course 2, question 4

7Does a harness-written status line, or an evidence contract, cut false claims in a coding harness, or move them to edited tests?

capstone: the claim checker (intervention arm)status: partly studiedcost: low
Why it matters
It is the cheapest fix there is if it works. If the agent satisfies it by editing the tests, a contract without an outside verifier is worse than none, because it looks safe.
Status
Partly studied. Failure-Transparent Agents (arXiv 2609.35732): 22.8% → 0.8% with a structured evidence contract, on fixed single-turn traces. Goal-Autopilot (arXiv 2606.11688) gates completion in a research scaffold. A production coding harness is untested.
Smallest experiment
Same tasks, two arms: the final message alone, or the final message plus a harness-written line such as last pytest: exit 1. Count false claims, and count diffs that touch test files.
Source
Course 1, question 4 · Course 5, question 5

8Can a trace-only rule ("a success claim after a non-zero test exit") replace re-running the checker?

capstone: the claim checkerstatus: partly studiedcost: low–medium
Why it matters
A re-run needs a container per run; a rule over the spans is free and could run on every production trace as a standing release gate.
Status
Partly studied. The capstone pilot's transcript detector held up on a spot check by the auditing agent, not a human (35 of 40 flagged runs confirmed), and arXiv 2606.09863 reports TF-IDF detectors at AUROC 0.83–0.95 on τ²-bench and AppWorld, not repo-and-test coding tasks. But in the pilot, self-contradiction did not predict a hidden-test failure (30.4% vs 27.6%), so the two checks may measure different things.
Smallest experiment
On a sample of pilot runs, compute the span rule and a fresh checker re-run, and report the 2 × 2 agreement table with the disagreements read by hand.
Source
Course 4 open questions, question 3

9Can a model confess a failure that compaction erased from its context?

capstone: compaction → false claimsstatus: partly studiedcost: cheap, eval only
Why it matters
Honesty training assumes the model knows what went wrong. After a summary says "tests passing", it may genuinely not, and then only the harness can help.
Status
Partly studied. Confessions (arXiv 2512.08093) confessed bad behaviour 74.3% of the time, without compaction. Park and Choi (arXiv 2607.25152) find self-report unreliable in long loops. Neither crosses confession with compaction.
Smallest experiment
Force a compaction right after a failing test, ask for a confession-style report of what was and wasn't verified, and compare the admitted-failure rate with uncompacted runs of the same tasks.
Source
Course 5 open questions, question 3

10Does selecting runs on a false-claim checker make claims vaguer instead of truer?

capstone: the claim checkerstatus: partly studiedcost: $50–200, no training
Why it matters
If it does, a falling flag count is a false all-clear: the obfuscation OpenAI found with a chain-of-thought monitor, moved to the final message.
Status
Partly studied. Baker et al. (arXiv 2503.11926) showed obfuscation under monitor pressure; Confessions (arXiv 2512.08093) rewards honesty in a separate channel. Measuring whether final-message claims become uncheckable looks new.
Smallest experiment
Draw 4–8 samples per task; pick one by the checker, one by a judge and one at random; count false and checkable claims per run. Fewer checkable claims at a flat pass rate is the Goodhart signature.
Source

2 · Cheap and open

Eleven questions that are open, cost under about $100 or a week, and don't depend on the capstone. Grouped by the layer that owns the thing being measured. Each could be a weekend lab or a short note.

Layers 2–3 · the run (course 1 and this course)

AWhen a model step re-runs after a crash, how often is the new diff different from the one already approved?

status: opencost: under $20
Why
An idempotency key dedupes the step, not the content; a re-rolled diff would sit behind an approval given for the old one.
Smallest experiment
From one recorded state, re-run only the edit step many times, hash each diff and count distinct hashes.
Source
Course 1, question 2

BDo other harnesses' schedulers also record "completed" when the operation failed?

status: open (not compared across harnesses)cost: $0 with a scripted provider
Why
Hermes's cron ledger said "completed" over two commands that exited 2. If that is common, every scheduler dashboard overstates success.
Smallest experiment
Repeat his negative control (break the command arguments so they exit non-zero) on each harness's scheduled-job path, and record the ledger status beside the exit codes.

Layer 5 · context and memory (course 2)

EAfter a refresh brings in a new value, does the agent still act on the stale copy in its history?

status: opencost: under $20
Why
Refreshing a fact and reconciling old copies are two jobs; if only the first is done, the model has to guess which version wins.
Smallest experiment
A refreshed snapshot with a new rule and a summary in history that contradicts it; arms: no note, a "supersedes" note, a clean rebuild. Count which value the next action follows.

4 · How to generate your own

The series uses one method throughout. Five steps:

  1. Split the label. Take a word your system uses for two jobs ("done", "confirmed", "approved", "memory") and name both owners. See same label, different authority.
  2. Find the unmeasured link. For each claim on a card, ask whether it is a design argument, one case, a secondhand number or a rate. The gap between "can happen" and "how often" is usually open.
  3. Check novelty on arXiv. Search for both halves of the split, read the abstracts, and write down what each close paper does not do. Repeat just before you run and again before you write.
  4. Design the smallest controlled experiment. Hold the model and the tasks fixed, change one thing, add a negative control, and judge by a check outside the agent. See the forensics method.
  5. Run a power analysis. Decide the smallest effect worth seeing and the task clustering, and only then the number of tasks. See how many runs do you need.

Worked example: how the capstone got its question.

  1. The anecdote. Tamba's Claude Code case study (arXiv 2607.13071): output from processes killed at exit 143 was written into compaction summaries as confirmed results. One case, no run counts.
  2. Split. "Confirmed" hides "the command ran" and "the command succeeded". "Compaction" hides what the summarizer was shown and what it wrote. That gives the Tuesday run's step 7: exit 1 in, "tests passing" out.
  3. Unmeasured link. Rules lost to compaction are measured (Governance Decay, the Compaction Cliff). Whether compaction causes false claims, and how much more with each round, is not.
  4. Novelty. The 1 October 2026 search found the definition (2606.09863), CLI overclaiming on file review (2609.20812) and status laundering on authorization claims (2609.20211), but no dose-response for test claims in coding agents.
  5. Smallest experiment. Force 0, 1 or 3 compactions right after the first failing test, with the model, tasks and prompt fixed, and re-run the visible tests to score the final message.
  6. Power. The first plan, 30 tasks × 3 repeats, detects only a rise of about 0.22–0.27 and has 21–27% power for a 10-point rise. At a 20% baseline that rise needs 136 tasks (ρ 0.2) to 194 (ρ 0.5). So the design moved to about 100 generated tasks × 2 repeats, with dose 0 vs 1 paired within task as the pre-registered contrast.

4 · Compare against what you already know

vs The forensics method: The forensics card finds where a claim detaches from the world in one pinned run. Most bank questions ask how often. What does each kind of study need that the other doesn't?

Check
  • forensics needs a pinned release, a boring task and a negative control
  • a rate needs many tasks, repeats, a validated checker and a power analysis
  • forensics shows a boundary exists; a rate says whether it matters
  • the bank's cheap questions often start as forensics and graduate to rates

vs Same label, different authority: The same-label card splits words into owners. Pick one capstone neighbour and say which split it came from and what the split made countable.

Check
  • the judge question splits what the judge saw into the summary and the full trace
  • the status-line question splits the claim into the model's words and the harness's record
  • verdict-last truncation splits compaction into what the summarizer was shown and what it wrote
  • each split turns one label into two records you can compare run by run

5 · Predict commit to an answer before revealing

Suppose question 1 comes back: every harness you test keeps the verdict line before summarizing. Predict what that does to the capstone's question and to question 6.

Reveal

The capstone question survives: the summarizer can still write "tests passing" over a verdict it saw, which is status inflation by the summary rather than loss before it. But the cheap mechanism (truncation drops the verdict) is ruled out for those harnesses, so question 6 matters more: if the exit code reaches the working set and false claims still happen, the fix is not more context, and you would look at the summary prompt and the model.

Why this step?

6 · Apply use the model, don't restate it

Use the five steps on a harness you've built. Split one status word it records, write the question the split opens, search arXiv for both halves, and design the smallest experiment. Then size it with the power-analysis card's numbers.

Done when: You have the split, one question, at least one arXiv search result with what it doesn't do (or "none found" and the date), an experiment that fixes the model and tasks and changes one thing, and a task count with the effect size and ρ you assumed.

Hint

If you have no pilot ρ, bracket it: the power card's table uses 0.2 and 0.5.
