Mutation testing (mutation analysis, mutant killing)

One of the three testing requirements EvalPlus uses for test-suite reduction (section 2.2): mutants are seeded into the ground-truth solutions, and the set of mutants each test kills becomes that test's requirement set in the set-cover problem. It is the "Killed mutants" column of table 4.

Prime · 2 minutes before you read

The problem: Counting tests says nothing about whether they would notice a bug. To shrink 764 tests safely you need a measure of what each test actually detects, or you'll throw away the one test that catches something.

Where it fits: HumanEval's 9.6 tests were counted, not weighed. This card gives each test a weight: the seeded bugs it kills. The next card, test-suite reduction, uses those kill sets as requirements.

Builds on: HumanEval (and HumanEval+, HumanEval+-mini)

A mutant is the program under test with exactly one small, deliberate bug injected by a fixed rule — the paper's own example is changing < into ≤. A test kills a mutant if it notices: it passes on the original and fails on the mutant. The share of mutants killed measures how alert a test-suite is.

mutation score = killed mutants / total mutants   a test's requirement set = the mutants it kills

Worked example: an is-prime ground truth, four mutants, four tests

Original (the ground truth)

def is_prime(n):
    if n < 2:
        return False
    for i in range(2, n):
        if n % i == 0:
            return False
    return True

Traced by hand. M1 only misbehaves at n = 2 (it calls 2 non-prime). M2 skips the divisor 2, so it only shows at n = 4, where it wrongly answers True. M3 flips the test and returns False at n = 7; at n = 4 it still answers False, so T3 misses it. M4 answers False for every prime.

These four mutants and tests are illustrative; the paper does not publish per-task mutant counts or mutation scores. Note how mutation analysis marks T1 as carrying no information — that is exactly the signal test-suite reduction consumes.

How it differs from the other two requirements in this paper

×Branch coverage

Requirement = the branches a test executes.

The paper's objection: a high-coverage test is not necessarily effective at finding defects in the code it covers — running a line is not checking it.

×Killed LLM samples

Requirement = the set of real wrong model outputs a test catches.

Needs wrong samples from other models to exist first, so it demands leave-one-out cross validation, and it consumes more tests than the theoretical metrics.

×Counting tests

Requirement = more tests is better.

HumanEval's 9.6 tests per task were counted, not weighed; quantity alone let the ChatGPT #58 bug through.

✓Mutant killing

Requirement = the seeded bugs a test would actually notice.

It asks about detection rather than execution, and the paper cites studies showing it can largely outperform code coverage at judging test effectiveness.

Is mutation testing the best of the three here?

Not in this paper's numbers. In table 4, reducing by each requirement alone and then scoring GPT-4 with greedy decoding gives pass@1★ of 86.0 (coverage, 11.3 tests), 82.9 (killed mutants, 11.4 tests) and 78.7 (killed samples, 13.8 tests), against 88.4 on base HumanEval and 76.2 on full HumanEval+. Mutation sits between the other two: better than coverage at preserving the HumanEval+ verdict, worse than the empirical sample-killing signal. The authors keep it anyway because coverage and mutation "serve as the base guarantees for the theoretical test adequacy" where sample killing has none.

Two standing caveats mutation testing always carries: some mutants are equivalent — semantically identical to the original, so nothing can ever kill them and the score is capped below 100% — and the score depends entirely on which mutation rules you chose. The paper does not state its rule set or its mutation tool.

Understand and remember

  • Inject one small bug per mutant (< → <=) → run each test on original and mutant → a different result means the test detects that kind of fault → its kill set measures detection, not execution
  • Each test's kill set becomes a requirement set → reduction must keep some test for every killed mutant → tests with empty kill sets (like n = 1) are dropped as carrying no information
  • Mutants are synthetic, not real model errors → they give a theoretical adequacy floor → but in table 4 they preserve less of the HumanEval+ verdict than real sample kills (GPT-4: 82.9 vs 78.7, full 76.2)
  • Some mutants behave identically to the original on every input → no test can kill them → the score is capped below 100% and a low score may reflect equivalents, not weak tests
  • detail that matters The score depends on the mutation rules chosen → different operators give different numbers → the paper doesn't state its rule set or tool, so its mutation column isn't reproducible from the text alone

Reference only

  • the name "mutation analysis"
  • the four example mutants M1–M4
  • table 4's test counts (11.4 tests for killed mutants)

4 · Compare against what you already know

vs Branch coverage (code coverage): Coverage and mutant killing are the paper's two theoretical requirements. What does each count, which design choice makes mutation stricter, and how does each still fail?

Check
  • coverage counts branches executed; mutation counts seeded faults detected
  • mutation requires the output to differ, not just the code to run
  • coverage fails when a test runs a branch without checking it
  • mutation fails on equivalent mutants and depends on its operators

vs Type-aware input mutation (type-aware mutation, mutation-based fuzzing): One mutates inputs to find bugs in samples; the other mutates the program to grade tests. Why does EvalPlus need both, and what would break if you dropped either?

Check
  • input mutation creates the tests
  • program mutation measures which of those tests matter
  • no input mutation: too few tests to catch wrong samples
  • no program mutation: reduction loses a model-independent guarantee

5 · Predict commit to an answer before revealing

Add mutant M5: range(2, n) → range(2, n - 1). Commit before checking: which of the four tests kill it, and could any test at all?

Reveal

None of T1–T4 kills it, and no input can. For any composite n ≥ 4, its smallest divisor is at most √n, which is below n − 1, so the shortened loop still finds it. For primes the loop finds nothing either way. M5 is an equivalent mutant: it caps the mutation score below 100% however good the tests are.
