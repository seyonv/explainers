Test-suite reduction (greedy set cover, HumanEval+-mini)

EvalPlus's optional speed-up (section 2.2): greedy set covering over branch coverage, killed mutants and killed LLM samples shrinks HumanEval+'s 764.1 tests per task to 16.1 — 47× smaller — while keeping nearly the same pass@1★ drop.

Prime · 2 minutes before you read

The problem: HumanEval+ runs about 764 tests per task for every sample of every model, which is slow. Cutting tests at random could drop the one test that catches a particular bug, and then scores rise again for no reason.

Where it fits: Mutation testing gave each test a kill set. This card treats those sets, plus branch coverage and other models' sample kills, as requirements, and keeps the fewest tests that still meet all of them.

Reduction assumes each test fulfils a set of testing requirements, and asks for the smallest subset of tests that still fulfils every requirement the full suite did. Written out, that is exactly the set covering problem, which the paper solves greedily: repeatedly take the test covering the most still-uncovered requirements.

reduce T to Tred such that  ∀r ∈ R ( ∃t ∈ T, t satisfies r  ⇒  ∃t′ ∈ Tred, t′ satisfies r )

Why it beats the alternatives

×Run the whole HumanEval+ suite

All ~764 tests per task, every time.

Correct but, in the paper's words, costly to execute — which is the reason reduction exists at all.

×Randomly sample N tests

Keep a fixed random fraction of the generated tests.

No guarantee any particular requirement survives; the one test that caught a given bug may simply not be drawn.

×Exact minimum set cover

Solve for the provably smallest covering subset.

NP-hard, and the paper cites Feige's ln n inapproximability threshold — the greedy algorithm is essentially the best practical option anyway.

✓Greedy set cover over merged requirements

One pass, always taking the test that adds the most uncovered branches, mutants and sample kills.

47× fewer tests with almost the same verdict, and by construction every requirement the full suite met is still met.

Is HumanEval+-mini just as good as HumanEval+?

Close, not identical — the paper says "similar", and the numbers show mini is slightly lenient: GPT-4 scores 78.0 on mini versus 76.2 on the full suite, ChatGPT 65.2 versus 63.4. StarCoder happens to match exactly at 29.3. If you want the strict number, run the full suite; mini is for when execution cost matters.

The preservation guarantee is also only as good as the requirements you chose. Nothing promises mini catches a bug that no branch, no seeded mutant and no other model's wrong sample ever exposed. And the sample-killing requirement is validated by leave-one-out cross validation over a subset of models, so a genuinely novel failure mode from a new model is outside what was tested.

Understand and remember

  • Each test satisfies a set of requirements (branches, killed mutants, killed samples) → keep a subset that still satisfies every requirement the full suite met → reduction becomes set cover → 764.1 tests shrink to 16.1 (47×)
  • Exact set cover is NP-hard → greedy repeatedly takes the test adding the most uncovered requirements → fast and within about a ln n factor of optimal, the best practical guarantee
  • Only requirements are preserved → a bug no branch, mutant or recorded sample ever exposed can lose its catching test → mini is slightly lenient (GPT-4 78.0 vs 76.2)
  • Coverage and mutants alone keep few tests but leave GPT-4 at 86.0 and 82.9 → real sample kills bring it to 78.7 → merging all three gives 78.0 with 16.1 tests
  • detail that matters Sample kills come from models' wrong outputs → using a model's own kills would fit the suite to it → the paper builds each model's reduced suite without that model (leave-one-out)

Reference only

  • the formal ∀r ∃t statement
  • Feige's inapproximability result
  • per-model test counts in table 4
  • tie-breaking order in the worked example

Check
  • merging adds mutant and sample-kill requirements that coverage can't see
  • those keep tests that detect wrong outputs, not just execute branches
  • dropping coverage loses the guarantee that every branch is still exercised, even if few tests are saved

Why this step?

5 · Predict commit to an answer before revealing

Greedy isn't always optimal. Take requirements {1, …, 6} and three tests: Y1 = {1, 2, 3}, Y2 = {4, 5, 6}, G = {1, 2, 4, 5}. Commit: how many tests does greedy keep, and what is the true minimum?

Reveal

Greedy takes G first (4 new), then needs Y1 for 3 and Y2 for 6: 3 tests. The minimum is 2 (Y1 + Y2). The test that covers the most at first can be a trap. Greedy's ln n bound says how bad this can get; in practice it is close enough that the paper uses it.

Done when: Round 1: T4 (6 new). Round 2: T3 (2 new: b5, M2). Round 3: T1 or T2 (1 each). Round 4: the other. All four tests are kept. T1 survives only for b1 (mutation alone dropped it), and T2 only for M1 (coverage alone dropped it).
