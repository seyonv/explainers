Type-aware input mutation (type-aware mutation, mutation-based fuzzing)

EvalPlus's scaling step: starting from about 30 ChatGPT-written seed inputs per task (produced with 3 separate prompts), per-type mutation rules generate 1,000 more inputs per task inside a one-hour budget.

Prime · 2 minutes before you read

The problem: You want about 1,000 test inputs per task. Random bytes are rejected before they reach real logic, and asking ChatGPT for all of them is too slow and costly. Something has to turn a few good inputs into many cheaply.

Where it fits: HumanEval's ground truth can answer any input, so the bottleneck moves to generating inputs. This is EvalPlus's scaling step, sitting between ChatGPT seeding and contract filtering.

Instead of inventing test inputs from nothing, the generator repeatedly picks an existing valid input and perturbs it using a rule chosen by the input's type — bump an int, drop a list element, splice a substring. Because the rule respects the type, the mutant is still a structurally legal input for the same function.

The loop (section 2.1)

1. Seed the pool
~30 ChatGPT inputs per task bootstrap the seed pool.
→
2. Pick and mutate
A random seed is selected and one type-appropriate rule is applied.
→
3. Check the contract
Mutants that satisfy the task's precondition go back into the pool; the rest are dropped.
↶

Step 3 feeds step 2, so later mutants are mutations of mutations. An "ingredient mechanism" also collects data fragments seen in valid inputs and reuses them during mutation, to avoid breaking subtle semantic constraints.

Why it beats the alternatives

×Classic black-box fuzzing (random bytes)

Feed random data to the function with no knowledge of its source or its types.

The paper calls this inapplicable for semantically meaningful inputs in a dynamically typed language — almost every input is rejected before it reaches real logic.

×Ask ChatGPT for every input

Keep querying the LLM until you have a thousand inputs per task.

The paper rules it out on "undesired speed and cost of querying such a large model" — 164 tasks × 1,000 inputs is far too many calls.

×Symbolic execution

Solve path constraints on the source to reach deep branches.

Strong on coverage, but the paper groups it with the traditional methods that cannot produce semantically meaningful inputs for arbitrary dynamically typed problems.

✓Type-aware mutation on LLM seeds

ChatGPT supplies semantically valid, structurally correct seeds; cheap local mutation multiplies them.

Gets the LLM's semantic understanding once per task, then scales to 1,000 inputs per task in an hour with no further model calls.

Does type-aware mean the mutants are always valid?

No. Type-awareness only guarantees the shape is legal — a list of ints stays a list of ints. Semantic requirements such as "the string must be a palindrome" or "n must be positive" can still be broken, which is exactly why every mutant is checked against the task's program contract before it is kept, and why the ingredient mechanism reuses fragments from inputs already known to be valid.

It is also not magic at finding bugs: mutation is random, with no coverage feedback loop described here, so it is bulk rather than targeted. Its job is quantity on top of ChatGPT's quality, not cleverness of its own.

Understand and remember

  • LLM seeds are semantically plausible but costly per call → take about 30 per task once → mutate locally with no further model calls → 1,000 inputs per task within an hour
  • Rule chosen by the value's type (int ± 1, drop/repeat list item, splice substring) → the mutant keeps the input's shape → the function can still be called on it → far fewer inputs wasted than random fuzzing
  • Valid mutants re-enter the pool → later mutants are mutations of mutations → the loop walks toward corners (duplicates, empty lists, boundaries) that hand-written tests skip
  • Type ≠ meaning → a mutant can break a semantic precondition (positive n, palindrome) → every mutant is checked against the task's contract before it is kept
  • detail that matters Ingredient mechanism reuses fragments seen in valid inputs → mutants stay closer to the valid domain → fewer are thrown away by the contract check

Why this step?

5 · Predict commit to an answer before revealing

Imagine a task whose argument must be a sorted list. Commit first: roughly what share of list mutants (remove, repeat, insert-a-mutated-item, replace-with-mutated-item) stay sorted, and which rules are the problem?

Reveal

Remove always keeps a sorted list sorted. Repeat usually breaks it, because the copy is inserted somewhere else, unless it lands next to the original. Insert and replace with an int ± 1 usually break it unless the new value happens to fit. So a large share fail a sortedness contract. Type-awareness gives the shape (a list of ints), not the invariant: the contract filter and the ingredient mechanism are what keep such tasks fed.

Then add a second seed ([6,8,1], [6,8,1]) and run again.

Done when: You have both runs' counts and one sentence explaining the difference. In our runs (Python's random, seeds 0, 1, 2) the single-seed pool gave 776–838 distinct inputs, 26–50 with an empty list, and 0 mismatches every time; adding the second seed gave 4–118 mismatches. Mutation by ± 1 rarely drifts far enough to make the intersection hold a value like 8 in both lists, so the bug stays hidden: seed diversity, which is ChatGPT's job, decides what bulk mutation can reach.

Hint

Store inputs as tuples of tuples so you can put them in a set. The mismatch needs an intersection whose set iteration order isn't ascending, such as {1, 8}.
