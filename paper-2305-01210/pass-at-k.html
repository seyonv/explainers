pass@k (unbiased pass@k, pass@1★)

The paper's only correctness metric: 200 samples per task at each temperature in {0.2, 0.4, 0.6, 0.8} give pass@k for k in {1, 10, 100}; pass@1★ is the single greedy-decoding sample. HumanEval+ lowers it by up to 19.3–28.9% relative.

Prime · 2 minutes before you read

The problem: Sampling k programs once and checking whether any passes gives a noisy 0 or 1 per task. Scoring code by text similarity rewards look-alikes over working code. You need an execution-based number that is stable enough to compare models.

Where it fits: First concept card. It is the metric the whole paper holds fixed. The Codex paper introduced it; here the question is what happens to it when the tests behind "correct" get stricter.

pass@k estimates the chance that at least one of k generated programs is functionally correct, where correct means passing every test. Because sampling k programs once is noisy, the unbiased version samples many more (here n = 200) and computes the answer in closed form.

pass@k = 1 − C(n − c, k) / C(n, k)   n = samples drawn, c = correct samples

Worked example: one task, n = 10 samples, c = 3 correct (illustrative)

kC(n−c, k) = C(7, k)C(n, k) = C(10, k)pass@k 
17101 − 7/10 = 0.300
221451 − 21/45 = 0.533
3351201 − 35/120 = 0.708
5212521 − 21/252 = 0.917

C(n−c, k)/C(n, k) is the probability that a random draw of k samples misses all 3 correct ones. The paper reports a per-task pass@k averaged over all 164 tasks, then keeps the best value across the four temperatures and records that temperature as T*k. The 10 and 3 here are illustrative; the paper uses n = 200 and never publishes per-task c.

Why it beats the alternatives

×BLEU and other text-similarity scores

Compare the generated code to a reference string, n-gram by n-gram.

Fails because two dramatically different snippets can be semantically equivalent — the paper's own reason for rejecting them.

×Naive pass@k: generate exactly k, check any

Draw k samples once and score 1 if any passes.

High variance at small k. For the example above one draw of k = 2 returns either 0 or 1, never the 0.533 expectation.

×Formal verification

Prove the program correct for every possible input.

The paper calls building a general verifier for arbitrary benchmark problems infeasible, and lists it only as future work.

✓Unbiased pass@k over n = 200 samples

Executes the code, so semantics not text decide, and averages over many samples in closed form.

Wins on stability and on measuring what users care about — does the program actually run correctly.

Is a higher pass@k the same as a better model?

pass@k is only as honest as the tests behind it, which is this paper's entire point: the same models, same samples, scored against HumanEval+ instead of HumanEval, lose up to 19.3–28.9% relative, and the ranking changes — WizardCoder-CodeLlama and Phind-CodeLlama pass ChatGPT only once the tests are strict.

Also be careful comparing k values: pass@100 assumes you can generate and then select among 100 attempts, which usually means you have your own tests to pick with. And the best temperature differs by k, so a model's pass@1 and pass@100 are typically measured at different settings (table 3).

The paper does not claim pass@k is the right metric in general; it holds the metric fixed and changes the tests underneath it.

Understand and remember

  • Draw n samples, count c that pass every test → the chance a random k-subset has no correct sample is C(n−c, k)/C(n, k) → pass@k is one minus that → an exact expectation instead of a noisy single draw
  • Correct is defined as "passes every test" → stricter tests turn some of the c passing samples into failures → c drops → pass@k drops, with the same model and the same samples
  • Larger k only needs one success among k → it rewards diversity → best temperature rises with k → pass@1 and pass@100 are measured at different settings, and pass@100 assumes you can pick the right program
  • detail that matters pass@1★ uses one greedy sample, not the estimator → it is 0 or 1 per task, averaged over 164 tasks → deterministic, but it can't give pass@10 or pass@100

Reference only

  • the temperatures swept ({0.2, 0.4, 0.6, 0.8})
  • k ∈ {1, 10, 100}
  • the 19.3–28.9% relative-drop range
  • the ★ notation for greedy results

    Check

5 · Predict commit to an answer before revealing

One task has n = 10 samples and c = 3 pass HumanEval's tests. HumanEval+ adds an input that one of those 3 fails, so c = 2. Commit first: does pass@5 fall by more or by less than pass@1, in absolute points and relative to where each started?

Reveal

Absolute: pass@5 falls more (0.917 → 0.778, 0.139) than pass@1 (0.300 → 0.200, 0.100). Relative: pass@5 falls less (about 15% vs 33%). High-k scores are cushioned because one surviving correct sample still rescues most k-subsets, but the curve is steep in the middle, so the absolute loss can still be larger. That's why the paper quotes relative drops for different k.
