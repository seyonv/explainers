Differential testing (cross-checking the ground truth)

EvalPlus's oracle: for every generated input x, the LLM sample f is judged only by whether f(x) equals gt(x) from the ground-truth solution. It is what lets the paper add ~764 tests per task without anyone writing an expected answer.

Prime · 2 minutes before you read

The problem: Generating 764 inputs per task is useless unless each one comes with the right answer, and nobody can hand-write 125,000 expected outputs. Without an automatic oracle, generated inputs can't judge anything.

Where it fits: Type-aware mutation produced the inputs. This card supplies their answers by running HumanEval's ground truth, which the HumanEval card showed every task already ships.

Needs first: HumanEval (and HumanEval+, HumanEval+-mini)

Builds on: HumanEval (and HumanEval+, HumanEval+-mini) · Type-aware input mutation (type-aware mutation, mutation-based fuzzing)

Differential testing runs two implementations of the same specification on the same input and treats any disagreement as a bug. Here one side is trusted: HumanEval's reference solution, re-implemented and re-tested by the authors, plays the role of the oracle.

for each generated input x:  f(x) == gt(x)?   any mismatch → the sample is wrong

Worked example: HumanEval #58, "sorted unique common elements of two lists"

ChatGPT's synthesized solution (figure 1)

def common(l1: list, l2: list):
    common_elements = list(
        set(l1).intersection(set(l2)))
    common_elements.sort()
    return list(set(common_elements))

It sorts correctly, then throws the order away by converting back to a set on the final line.

Input (l1, l2)f(x)gt(x)verdict
[5,3,2,8], [3,2][2,3][2,3]match
[4,3,2,8], [3,2,4][2,3,4][2,3,4]match
[4,3,2,8], [][][]match
[6,8,1], [6,8,1][8,1,6][1,6,8]mismatch

The first three are HumanEval's base inputs; the fourth is a HumanEval+ input.

Why the bug hides on the first three rows and not the fourth: CPython lays small ints out in a hash table by value, so iterating {2,3} or {2,3,4} happens to come out ascending, while {1,6,8} in an 8-slot table puts 8 at slot 0, 1 at slot 1 and 6 at slot 6, yielding [8,1,6]. The base tests agree with the ground truth by luck; one differently-shaped input exposes the flaw. (The slot arithmetic is worked out here, not in the paper.)

Why it beats the alternatives

×Hand-written expected outputs

A human writes both the input and the answer it should produce.

The paper calls crafting high-quality tests laborious; it is what caps HumanEval at 9.6 tests per task and it does not scale to 764.

×Text similarity to a reference solution

Score the generated source against the reference with BLEU or similar.

Two dramatically different snippets can be semantically equivalent, so the score says nothing about correctness.

×Formal verification of each sample

Prove f equivalent to the specification for all inputs.

The paper argues a general verifier for arbitrary benchmark problems is out of reach; even translation validation on narrow domains is already hard.

✓Differential testing against the ground truth

Reuse the reference implementation the benchmark already ships as the answer key.

Every new input is free to add: no expected output has to be authored, so test count scales with input generation.

If the two disagree, is the model always the one at fault?

No — and the paper found this the hard way. Differential testing is only as trustworthy as the reference: comparing their re-implementation against HumanEval's original reference surfaced 18 defects (11% of problems) in the reference, including the valid_date operator-precedence bug. A disagreement means one of the two is wrong, not which.

It also fails on invalid inputs: an input outside the function's intended domain can make the reference do something arbitrary, producing a false positive. That is why program input contracts filter inputs first, and why the oracle adds a floating-point tolerance (1e−6 by default) and a per-test timeout rather than demanding bit-identical, instant answers.

Understand and remember

  • Ground truth runs on any input → it produces the expected output for free → an input generator alone can grow the suite → test count scales with generation, not with human effort
  • A disagreement means one of the two implementations is wrong → the paper treats the reference as trusted → so the reference must be re-implemented and checked first → 18 defects were found that way
  • Out-of-domain inputs make both sides behave arbitrarily → mismatches that are not bugs (false positives) → contracts filter inputs before they reach the comparison
  • Base tests used small ints whose set order happens to be ascending → a bug that throws away sorting stays hidden → one input with a different hash layout ({1,6,8} → [8,1,6]) exposes it
  • detail that matters Comparison is exact except floats (tolerance, 1e−6 by default) and time (per-test timeout) → correct code that reassociates arithmetic still passes, but slow code fails

Reference only

  • the CPython hash-table slot arithmetic for small ints
  • the exact figure-1 code
  • the phrase "differential testing" and its history in compiler testing

    Check

  2. mechanism Walk through why list(set([1, 6, 8])) comes out as [8, 1, 6] in CPython, and why that makes the #58 sample fail on row 4 only.
    Check
    • small ints hash to themselves; an 8-slot table places them at hash mod 8
    • 8 → slot 0, 1 → slot 1, 6 → slot 6, so iteration gives 8, 1, 6
    • the sample sorts, then converts back to a set, losing the order
    • on {2,3} and {2,3,4} slot order equals ascending order, so the base tests pass by luck
  3. tradeoff Your reference solution is itself generated by a strong LLM, not written by a human. What does that do to differential testing, and how would you reduce the risk?
    Check
    • the oracle may share the model's bugs, so correct samples fail and shared bugs pass
    • agreement between two models is not evidence of correctness
    • reduce risk by hand-checking the reference, using contracts and properties, or comparing several independent references

Why this step?

5 · Predict commit to an answer before revealing

Run the #58 sample on ([1, 8], [8, 1]) and on ([9, 1], [1, 9]). Commit: does each match the ground truth?

Reveal

The first fails: in an 8-slot table 8 sits at slot 0 and 1 at slot 1, so the sample returns [8, 1] while the ground truth returns [1, 8]. The second matches: 9 and 1 both want slot 1, 1 was inserted first, and 9 is probed into a later slot, so iteration happens to give [1, 9]. Whether the bug shows depends on hash layout, which is exactly why many varied inputs beat a few hand-picked ones.
