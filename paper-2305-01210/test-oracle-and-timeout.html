Test oracle and timeout

Appendix A's definition of "passes": outputs must match the ground truth exactly, floats within HumanEval's annotated tolerance or 1e−6, and each individual test must finish within max(200ms, 4 × tgt) — replacing HumanEval's flat three seconds for a whole test-suite.

Prime · 2 minutes before you read

The problem: "Passes" needs a precise rule. Bit-exact float comparison fails correct code, a flat time limit either fails every correct solution on 764 tests or waves slow ones through, and HumanEval's 3 seconds per whole suite was built for 9.6 tests.

Where it fits: Differential testing compares f(x) with gt(x). This card is the rule for what counts as equal, and how long f may take, once there are about 764 inputs per task.

An oracle is the rule that turns a run into a verdict. With ~764 tests per task instead of 9.6, the rule has to say three things: what counts as equal, how much slack floating point gets, and how long a test may take before it is called a failure.

per-test timeout = max(200 ms, 4 × tgt)   tgt = run time of the ground-truth solution on that test

Arithmetic done here; the tgt values are illustrative, since the paper publishes no per-task run times. The floor binds below tgt = 50 ms (solve 4t = 200), which is where most of these small Python functions sit — so in practice the floor, not the 4× rule, is what most tests get.

Why HumanEval's rule could not be reused: 3 s for the whole suite ≈ 312 ms per test at 9.6 tests,
but 764 tests × 200 ms = 152.8 s of budget for one task — a flat 3 s would fail every correct solution.

The three parts of the verdict

RuleSettingWhy
EqualityExact matching by defaultOutputs are compared against the ground truth's return value under differential testing.
Float toleranceThe degree HumanEval annotates, else 1e−6 absoluteBit-identical floats would fail correct solutions that reassociate arithmetic.
Timemax(200ms, 4 × tgt) per testExpects the solution to be no slower than 4× the ground truth, with a floor that absorbs performance randomness on fast tests.

Why it beats the alternatives

×HumanEval's flat 3 s per suite

One budget covering every test-case of a problem.

The paper calls it neither suitable with more test-cases nor reasonable, since each problem has its own run-time characteristics.

×A generous fixed per-test timeout

Give every test the same large budget, say 10 s.

Blind to performance bugs — 3 of the 18 defects found in HumanEval's own ground truths were inefficient implementations that a loose limit would wave through.

×Bitwise float equality

Require the returned float to match the reference exactly.

A correct solution that sums in a different order differs in the last bits and is scored wrong — a false positive, not a bug.

✓Per-test, ground-truth-relative timeout

Scale the budget to what the reference needs on that same input, with a 200 ms floor.

Adapts to each task's real cost, so slow solutions are caught on heavy inputs without punishing fast ones for millisecond noise.

Does this mean a correct-but-slow program counts as wrong?

Yes, deliberately. The paper states the expectation directly: the LLM-provided solution should be no slower than the ground truth by four times. So pass@k on HumanEval+ mixes functional correctness with a performance requirement, and the paper's own pass-rate analysis names efficiency — "n-th prime Fibonacci number" — as one of the hardest task categories for LLMs.

That also makes the results hardware-dependent: tgt is measured on whatever machine runs the evaluation, so a borderline solution can pass on one box and time out on another. The paper does not report machine specifications for the timing or discuss flaky results.

And exact matching is stricter than it may sound for tasks whose answers are unordered — the #58 common example fails precisely on element order, which is intended there because the docstring asks for a sorted result.

Understand and remember

  • Suite-level budget (3 s) was sized for about 10 tests → 764 tests at even 200 ms each need 152.8 s → a per-suite limit would fail every correct solution → the limit moves to each test
  • Limit scales with the reference's own time on that input (4 × tgt) → slow solutions fail on heavy inputs → pass@k on HumanEval+ also measures efficiency → matching the 3 performance defects found in the ground truths
  • Fast tests have noisy timings → 4 × a few ms would flag noise as failure → a 200 ms floor absorbs it → below tgt = 50 ms the floor binds, which is where most tasks sit
  • Floats differ in the last bits when arithmetic is reordered → exact comparison would fail correct code → a tolerance (annotated, else 1e−6) accepts them → only the degree of slack is a design choice
  • detail that matters tgt is measured on the evaluating machine → a solution near 4× can pass on one box and time out on another → results can be flaky, and the paper doesn't report its hardware

Check

5 · Predict commit to an answer before revealing

A task's ground truth runs in 30 ms on the evaluation machine. A sample is correct but 5× slower on every input. Commit: does it pass? What if the ground truth took 120 ms?

Reveal

At 30 ms the sample takes 150 ms against a 200 ms limit: it passes, because the floor gives 6.7× slack. At 120 ms it takes 600 ms against 480 ms: it fails. The same relative slowness passes on fast tasks and fails on heavy ones, so the 4× rule only really bites where the reference is above 50 ms.
