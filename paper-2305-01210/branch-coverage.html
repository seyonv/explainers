Branch coverage (code coverage)

The first and weakest of the three testing requirements EvalPlus uses for test-suite reduction (section 2.2): keep a minimal subset of tests covering the same branches. It is the "Coverage" column of table 4, where reducing by it alone leaves GPT-4 at pass@1★ 86.0 with 11.3 tests — close to base HumanEval's 88.4, far from HumanEval+'s 76.2.

Prime · 2 minutes before you read

The problem: Reduction needs a cheap, model-independent reason to keep a test. "It runs code nothing else runs" is the classic one, but running code isn't checking it, so a suite reduced by coverage alone can lose the tests that actually catch bugs.

Where it fits: Test-suite reduction merges three requirements. Mutation testing was the stricter theoretical one; this is the weakest, and the worked example reuses the same is_prime tests and mutants.

Branch coverage measures which decision outcomes a test actually executes: for every if and loop, both the taken and the not-taken direction count separately. Under reduction, a test's requirement set is simply the branches it hits, and the goal is the smallest subset of tests hitting every branch the full suite hit.

branch coverage = branches executed / branches in the program   a test's requirement set = the branches it hits

Worked example: six branches, four tests

The ground truth, branches labelled

def is_prime(n):
    if n < 2:          b1 true / b2 false
        return False
    for i in range(2, n):  b3 body
        if n % i == 0: b5 true / b6 false
            return False
    return True        b4 loop exits

Traced by hand, reusing the tests and mutants from the mutation-testing card; illustrative, not from the paper. For n = 2 the loop range(2, 2) is empty, so T2 reaches b4 without b3 — and it is the only input on the boundary the mutant moves. Branch coverage cannot see that, because the mutated condition's branches are already covered by other tests.

Why it beats the alternatives

×No coverage metric at all

Judge a test-suite by how many tests it has.

HumanEval's 9.6 tests per task were counted, never measured; nothing flags the code paths nobody ever runs.

×Statement or line coverage

Require every line to be executed at least once.

An if with no else reaches 100% line coverage without ever taking the false direction — half the decisions go untested.

×Path coverage

Require every distinct route through the program.

Paths multiply exponentially and loops make them unbounded — the is_prime loop alone has a different path per value of n.

✓Branch coverage

Both outcomes of every decision, and nothing more.

Cheap to measure, finite, and standard — the paper picks it as the testing requirement precisely because prior test-suite reduction work uses it widely.

Does 100% branch coverage mean the tests are good?

No, and the paper says so plainly: coverage measures the extent to which code has been executed, but a high-coverage test is not necessarily effective at finding critical defects in the code it covers. The worked example shows it: 6 of 6 branches, yet a real seeded bug survives.

Table 4 confirms it empirically. Reducing by coverage alone keeps GPT-4 at 86.0 — only 2.4 points below base HumanEval, when the full HumanEval+ verdict is 76.2. That is the most lenient of the three requirements: it throws away most of the tests that were catching wrong code.

So why keep it? The paper's answer is that coverage and mutation "serve as the base guarantees for the theoretical test adequacy", underneath the purely empirical sample-killing signal which has no such guarantee.

Understand and remember

  • Requirement = branches a test executes → a test that repeats already-covered branches adds nothing → reduction drops it → even if it is the only input on a boundary a bug moves (n = 2 for M1)
  • Coverage measures execution, not checking → a subset can hit 6/6 branches and still miss a seeded bug → coverage-only reduction keeps few catching tests → GPT-4 stays at 86.0 vs 76.2 on full HumanEval+
  • Both outcomes of every decision, nothing more → finite and cheap to measure (unlike paths, which multiply with loop counts) → stricter than lines (an if without else) → a standard, model-independent floor for reduction
  • detail that matters In is_prime, n = 2 makes range(2, 2) empty → reaches return True without entering the loop → the only test on the M1 boundary shares all its branches with others → coverage can't tell it matters

Reveal

n = 9 hits b2, b3, b6 (i = 2 doesn't divide) and b5 (i = 3 divides): 4 branches, tied with T4 in round 1, so greedy may pick it first. It kills none of M1–M4: M1 and M4 differ only at n = 2 or on primes, M2 still finds the divisor 3, and M3 returns False at i = 2, which happens to be the right answer for 9. Coverage greed can prefer a test that detects nothing.
