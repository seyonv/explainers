Is your code generated by ChatGPT really correct? Rigorous evaluation of large language models for code generation

Jiawei Liu, Chunqiu Steven Xia, Yuyao Wang, Lingming Zhang · NeurIPS 2023 · arXiv:2305.01210 · 2023

Prime · 2 minutes before you read

The problem: A code benchmark only knows a program is "correct" because it passed that benchmark's tests. With about 9.6 hand-written tests per HumanEval task, wrong programs pass, so every leaderboard number built on them is too high and some model rankings are simply wrong.

Where it fits: This is the map of the whole paper. It picks up where the Codex paper left off: that paper defined pass@k and HumanEval, and this one keeps both fixed and asks how trustworthy the tests underneath them are.

The problem in one breath

Code benchmarks decide whether a model's program is "correct" by running a handful of hand-written tests — HumanEval averages 9.6 tests per problem. Wrong programs slip through those tests, so reported scores are too high; this paper generates far more tests automatically and re-measures.

What they did — the EvalPlus pipeline

1
Original dataset
In: HumanEval's 164 tasks, ground-truth solutions, base inputs. Out: material for the prompt.
→
2
Seed initialization via ChatGPT
In: ground truth + sampled base inputs + an instruction. Out: ~30 high-quality seed inputs per task, from 3 prompts.
→
3
Type-aware mutation
In: the seed pool. Out: 1,000 extra inputs per task within a one-hour budget.
4
Program input contracts
In: generated inputs. Out: only inputs that satisfy hand-written preconditions (83 of 164 tasks annotated).
→
5
Differential testing
In: valid inputs, LLM sample f, ground truth gt. Out: pass only if f(x) = gt(x) everywhere.
→
6
Test-suite reduction
In: the full HumanEval+ suite. Out: HumanEval+-mini, 47× smaller, via greedy set cover.

Stage names are the paper's own (figure 2). Steps 4–6 are described as an option / an add-on: reduction is optional, used to speed up evaluation.

Why it matters / what to be careful about

Why it matters

  • 80× more tests turns HumanEval's 9.6 tests per task into 764.1, and catches wrong code that every prior paper scored as correct.
  • Insufficient testing also mis-ranks models: WizardCoder-CodeLlama and Phind-CodeLlama look no better than ChatGPT on HumanEval but beat it on HumanEval+.
  • It found 18 defects (11% of problems) in HumanEval's own "ground truth": 10 bad logic, 5 unhandled edge cases, 3 performance issues.
  • HumanEval+-mini keeps almost the same effectiveness with 47× fewer tests, so the stricter evaluation stays cheap to run.

What to be careful about (the paper's own limits)

  • More tests is still testing, not proof. The authors list integrating formal verification (Dafny) or translation validation as future work.
  • Only HumanEval is augmented here; applying EvalPlus to other benchmarks such as MBPP is stated as future work.
  • Contracts are hand-crafted and partial — 83 of the 164 tasks are annotated.
  • The commercial models get a thinner evaluation for time and cost: GPT-4 is greedy-decoding only, ChatGPT adds only temperature 0.8.
  • Reduction effectiveness is shown by leave-one-out cross validation on a subset of models, not on every model in table 3.

Understand and remember

  • Hand-written tests are few (9.6 per task) → many wrong programs pass all of them → pass@k overstates correctness → the paper's HumanEval+ lowers pass@1★ by 4.8 to 12.2 points on the models it headlines
  • LLM seeds give semantically valid inputs but are slow and costly per call → cheap type-aware mutation multiplies them to about 1,000 per task → contracts drop the out-of-domain ones → 764.1 tests per task survive
  • Every new input needs an expected output → the ground truth already computes one → differential testing (f(x) = gt(x)) makes test count scale with input generation, not with human effort → but the ground truth must itself be right (18 were not)
  • 764 tests per task are slow to run → greedy set cover over coverage, mutant kills and other models' sample kills keeps 16.1 → almost the same verdict at 47× fewer tests, checked with leave-one-model-out
  • detail that matters Stricter tests reshuffle models unevenly → WizardCoder-CodeLlama and Phind-CodeLlama pass ChatGPT only on HumanEval+ → so a weak test-suite doesn't just inflate scores, it mis-ranks models

vs Evaluating large language models trained on code: The Codex paper and this paper both evaluate code models on HumanEval with pass@k. What is fundamentally different about what each one treats as the thing to improve, and how does each one's conclusion fail if its assumption is wrong?

vs Test-suite reduction (greedy set cover, HumanEval+-mini): Across the course there are two halves: making the suite bigger (seed, mutate, filter) and making it smaller again (reduce). Which design choice lets the second half undo the first without losing its benefit?

Check
  • tests are kept by the requirements they satisfy, not by count
  • set cover keeps at least one test for every branch, mutant and sample kill the full suite had
  • so the bugs the big suite found are mostly still found, at 16.1 tests per task

Why this step?

5 · Predict commit to an answer before revealing

Suppose the ground truth for a task has an unhandled empty-list case, and nobody re-implements it. After EvalPlus adds hundreds of inputs including empty lists, what happens to a model's sample that handles the empty list correctly?

Reveal

It fails. Differential testing treats the ground truth's output as the answer, so on empty-list inputs the correct sample disagrees with the buggy reference and is scored wrong. More tests amplify a wrong oracle: that's why the authors re-implemented every ground truth and found 18 defects, 5 of them unhandled edge cases.
