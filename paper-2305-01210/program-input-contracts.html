Program input contracts (preconditions, design by contract)

Hand-written assertions such as assert n > 0 annotated onto 83 of HumanEval+'s 164 tasks (section 2.3). They throw away generated inputs a function was never meant to receive, and double as a precise restatement of a vague docstring.

Prime · 2 minutes before you read

The problem: Mutation happily produces n = 0, n = −1 or "5" for a function that only makes sense for positive ints. Feed those to differential testing and the reference and the sample each do something arbitrary, so correct code gets marked wrong.

Where it fits: Type-aware mutation keeps the shape of an input but not its meaning, and differential testing trusts every input it gets. Contracts sit between the two: step 3 of the mutation loop.

Needs first: Differential testing (cross-checking the ground truth)

Builds on: Type-aware input mutation (type-aware mutation, mutation-based fuzzing) · Differential testing (cross-checking the ground truth)

You'll meet: executable preconditions (assert n > 0) keep / drop per generated input false positives from undefined behaviour 83 of 164 tasks annotated

By the end: Write a precondition for a task, classify generated inputs as keep or drop, and explain what contracts can't make unambiguous.

A contract states what a caller must guarantee before the function runs. EvalPlus writes those guarantees as executable Python assertions on the ground-truth solution, so every candidate test input can be checked automatically: assertion holds, keep the input; assertion fails, discard it.

Worked example: a task whose docstring never says n must be positive

Ground truth with its contract

def nth_prime_fib(n):
    """Return the n-th number that is
    both a Fibonacci number and prime."""
    assert isinstance(n, int)
    assert n > 0
    ...

The docstring alone leaves n = 0 and n = −1 undefined. The two asserts make the intended domain explicit and machine-checkable.

The task name and asserts are illustrative — the paper's own stated example is assert n > 0 and it does not publish the per-task contracts. The mutants are the kind type-aware mutation produces from an int seed.

Coverage of the annotation effort

83 of 164 tasks carry a hand-crafted contract — 50.6%, computed here. The remaining 81 tasks rely on the generated inputs simply being in-domain by construction. The paper does not say how it chose which tasks to annotate.

Why it beats the alternatives

×Trust the docstring

Let the natural-language description define the input domain.

The paper's stated problem: descriptions are often too vague to say whether inputs are only positive integers or how exceptions should be handled, so capable LLMs get misjudged as incapable.

×Type annotations in the signature

Let n: int and l: list stand in for the precondition.

Types cannot express semantic constraints — positivity, non-emptiness, or the paper's example of an input that must be a palindrome.

×Compare on invalid inputs anyway

Feed everything the generator produces into differential testing.

Ill-formed inputs incur undefined behaviour, creating false positives that mark correct code wrong.

✓Executable preconditions

One assertion per guarantee, checked on every generated and mutated input.

Two benefits at once: it filters invalid inputs during generation, and serves as a precise descriptor alongside the docstring.

Do contracts make the benchmark fully unambiguous?

No. They constrain what goes in, not what must come out — there are no postconditions here, so a docstring that is vague about the return format stays vague. And they cover only half the tasks and are written by hand, so they carry the same human-effort limit the paper criticises in hand-written tests.

The paper lists "serve as orthogonal descriptors together with the natural language description in the prompt" as benefit (ii), but does not spell out whether the contracts were shown to the 26 evaluated models when generating code; read that benefit as proposed rather than measured.

Assertions are also only as tight as they are written. assert n > 0 admits True in Python, since True == 1 — the sort of gap a precondition check does not close on its own. Not something the paper discusses.

Understand and remember

  • Docstrings leave the input domain vague → mutation generates inputs outside it → both implementations behave arbitrarily → mismatches that aren't bugs → an executable precondition drops those inputs before comparison
  • Types say shape, assertions say meaning → n: int admits 0 and −1 → assert n > 0 excludes them → only semantic constraints stop semantic false positives
  • Contracts are preconditions only → nothing constrains the output → an ambiguous return format stays ambiguous → exact matching can still penalise a defensible answer
  • Written by hand for 83 of 164 tasks → the same human-effort limit as hand-written tests → the other 81 rely on generated inputs happening to be in-domain
  • detail that matters An assertion is only as tight as written → isinstance(n, int) and n > 0 both accept True (a bool is an int in Python) → a sloppy contract lets odd inputs through

Reference only

  • the name "design by contract"
  • the illustrative nth_prime_fib asserts
  • the 50.6% annotation rate

Check

5 · Predict commit to an answer before revealing

The contract is assert isinstance(n, int) and assert n > 0. Commit for each: 6, 1, 0, −1, "5", True, 2.0, False. Which are kept?

Reveal

Kept: 6, 1 and True. Dropped: 0, −1, "5", 2.0 and False. True surprises most people: bool is a subclass of int and True > 0, so it sails through both asserts. False passes the type check but fails > 0; 2.0 fails the type check.
