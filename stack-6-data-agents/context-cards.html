Meaning lives in code

Also called code-enriched context, table context cards or a table-understanding layer. Govindarajan's Data Agent Stack Part 4: a schema says what columns exist, the pipeline code that builds a table says what a row means, so extract that meaning into a maintained card per table. Part 3 says how the card then competes with other evidence for one question.

Prime · 2 minutes before you read

The problem: A data agent can pick a table whose columns fit the question, write valid SQL, and still return the wrong number, because what a row means (its grain, what was dropped, when it is final) is not in the schema. Nobody notices: the chart looks fine.

Where it fits: You know the working set is assembled per turn and that relevance is not authority (context is assembled, not given). This card zooms in on one input to that assembly for data agents: the meaning of a table, and where that meaning is actually written down.

You already know: context is assembled, not given (the working set, relevance vs authority). This card is about one input to that assembly: what a table means.

In one breath. Two tables can have identical columns and mean different things: one row per order or per line, refunds subtracted or not, test accounts kept or dropped, final at 10 AM or after a finance close. Those facts live in the dbt model, Spark job or Airflow DAG that builds the table, not in its schema. A data agent should not read the repo at question time. Instead, an offline job extracts those facts into a table context card with a source for every fact, refreshes it when the code changes, and the agent retrieves the card before it writes SQL.

Predict first: an agent is asked "What was Q3 net revenue for EMEA?" and finds three tables with the same four columns. It writes the same SUM(amount) WHERE region = 'EMEA' against each. How many different answers come back?

Three, and only one is right: 600, 500 and 1,140 (illustrative data, below). Every query is valid SQL. The differences come from what each pipeline did before the rows landed: whether refunds were subtracted, whether test accounts were dropped, and what one row stands for.

Six raw orders go through three pipelines: five are in EMEA (one of them from an internal test account) and one in North America. Each output table exposes order_id, account_id, region, amount. The agent runs the same query against each.

Four signals, four different things they know

Why it beats the alternatives

✗ Schema only

Picks a table by its columns. All three tables above match, so the agent can return 600 or 1,140 with valid SQL and a clean chart.

✗ Learn from query history

History is behavior, including debug queries and copies of deprecated dashboards. Popular old logic outranks the current contract.

✗ Give the agent the whole repo

Old jobs, tests, dead paths and stale comments, read at question time. Noisy, slow, and a comment can contradict the code it sits in.

✓ A maintained card per table

Facts extracted from code once, each with a source; refreshed on change; access-controlled; retrieved before SQL; checked live for state.

Is the code always right about meaning?

No. Code is the authority on what the build does, which can differ from what finance means: if the dbt model forgot to subtract credits, the card faithfully records a bug. That is why Part 4 keeps metric contracts and owner annotations as separate signals and asks you to surface conflicts rather than merge them. Extraction also fails in known ways: the card goes stale when a transform changes and nobody re-extracts, static reading misses SQL generated by macros or runtime config, and a card can leak restricted consumer or experiment names to someone who can't see those tables.

Where you don't need it: a small warehouse with one well-modelled table per metric and a semantic layer that covers every question. Know the evidence, too. Part 4 is an architecture argument built on public write-ups (OpenAI's in-house data agent, Spotify, Pinterest, Grab, GitHub); Govindarajan reports no experiment of his own, and calls OpenAI's six context layers a useful case study, not a universal taxonomy.

Understand and remember

  • Schemas record only shape → look-alike tables match the same query → grain, filters and refund handling live in the pipeline code → an agent choosing by columns can return a valid but wrong number
  • Query history records behavior, not authority → it includes debug queries and copies of deprecated dashboards (Spotify's experts kept 12.5% of mined pairs) → treat it as precedent ranked below contracts and code → otherwise popular old logic wins
  • Code changes after the card was built → the card silently describes the old table → refresh on code, DAG or ownership change and store commit + timestamp per fact → plus a live check at question time, because the card states intent and only runtime state says whether it holds now
  • Different sources own different claims → metric contract defines meaning, code defines behavior, live checks define current state → assembly picks authority per claim and surfaces conflicts → no single source, however relevant, decides the whole answer
  • detail that matters Grain is the field that most changes numbers silently: an order-line table with the order amount copied onto each line inflated the illustrative total 2.28× (1,140 vs 500) with no error raised
  • detail that matters Static extraction reads the wrapper, not the executed SQL, when logic comes from macros, templates or runtime config → those tables need extraction from compiled or generated artifacts, or their cards are confidently wrong

Then compare with this checklist
  • schemas give shape; meaning (grain, filters, dedup, finality) lives in the code that builds the table
  • look-alike tables give different valid answers to the same SQL
  • facts are extracted offline into a per-table card, not read from the repo at question time
  • every fact carries a source and version; the card refreshes when code or DAGs change
  • a live check at question time verifies the card's contract still holds (e.g. the quarter is reconciled)
  • code owns behavior, not business meaning: conflicts with the metric contract are surfaced, not merged

3 · Retrieve from memory, card closed
  1. concept Explain the difference between what a table's schema tells a data agent and what its pipeline code tells it, using the revenue example.
    Check
    • schema: column names and types, e.g. amount is a decimal
    • code: whether refunds were subtracted, test accounts dropped, what one row is, when a quarter is final
    • the second set decides whether the table matches the metric contract
  2. mechanism Walk through what happens when an agent assumes order grain but sums amount from a line-grain table where the order amount is copied onto each line.
    Check
    • each order is counted once per line
    • an order with 3 lines contributes 3× its amount
    • the query runs without error and returns an inflated total (1,140 vs 500 in the illustrative data)
    • only the grain field on a card, or the pipeline code, reveals it
  3. tradeoff You can either let the agent search the whole pipeline repo at question time or maintain extracted context cards. What does each cost, and how does each fail?
    Check
    • repo search: always current code, but noisy (dead jobs, tests, stale comments), slow and costly per question, comments can contradict code
    • cards: fast, ranked, access-controlled, but need an extraction pipeline, refresh triggers and tests
    • cards fail by going stale or by missing macro-generated logic; repo search fails by drowning or misreading the governing line
  4. mechanism The card says a quarter is final after finance reconciliation. Why is that not enough to answer "Q3 net revenue" today, and what does the agent do?
    Check
    • the card states the intended contract, not today's state
    • a live check asks whether the Q3 reconciliation run finished
    • finished → answer; not finished → caveat as provisional, use complete periods, or abstain

Why this step?

4 · Compare against what you already know

vs Context is assembled, not given: That card says the runtime selects the working set each turn. This card adds a durable, per-table artifact built offline. What is fundamentally different about when each decision is made, and how does each fail?

Check
  • assembly decides per question, at query time; the card is prepared evidence built before any question
  • the card makes assembly fast and gives it ranked, sourced facts to select from
  • assembly fails by selecting the wrong or too much evidence; the card fails by being stale, unsourced or wrong about code it never really read

vs Memory is owned state: A context card and an agent memory both persist knowledge outside the model. What decides who may write each, and what goes wrong when either crosses its scope?

Check
  • card facts are extracted from owned code and owner annotations, with provenance and refresh triggers
  • memory holds scoped corrections or preferences from users
  • a personal memory must not redefine a global metric; a card must not expose restricted consumers or experiment names to users who can't see them

vs Tool output is untrusted input: A live warehouse check and a code-derived card fact both enter the bundle. Why does Part 3 send runtime observations back through the same permission and ranking path, and does the card get a free pass?

Check
  • a tool output is evidence for what it measured, at its timestamp and scope, not universal authority
  • a live check can say Q3 is unreconciled; it cannot redefine net revenue
  • the card gets no free pass either: it is ranked per claim and its facts carry provenance so they can be outranked

5 · Predict commit to an answer before revealing

Last week someone changed the fct_net_revenue transform so it no longer subtracts refunds. Nobody re-ran extraction. Using the illustrative orders, what does the agent now report for Q3 EMEA, and what does the card still claim?

Reveal

550 (120 + 80 + 200 + 150, the test order still dropped), while the card still says "gross minus refunds" from commit a1b2c3d. The SQL is unchanged and valid; the meaning moved underneath it. Part 4 lists this as "pipeline-derived context is stale": refresh-on-change (comparing the card's commit to the head commit) would flag it and trigger re-extraction, and the golden questions Part 4 runs on context changes would then show 550 where 500 was expected.
