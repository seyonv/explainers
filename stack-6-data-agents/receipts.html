Every answer ships with a receipt

Also called a run receipt, provenance or the evidence trail; its operator-side twin is the context manifest. Govindarajan's Data Agent Stack Part 5 asks every answer to carry its SQL, assumptions and result links; Part 6 lists what a governed run must record, including who it ran as and what it was denied.

Prime · 2 minutes before you read

The problem: A data agent says "Q3 net revenue for EMEA was $48.3M." Without the path behind that number, nobody can tell which revenue definition, table, date range or filters it used, whose access it ran under, or what it quietly assumed. A wrong number and a right one look identical.

Where it fits: The trust card of the data-agents course. It is the data-agent version of the claim chain from 'Done' is a chain of states, and it applies Authority only narrows to answers built from a warehouse.

In one breath. A data agent's answer is a number plus the path that produced it. The receipt records what ran (the SQL, tables, filters, checks and a link to the result), who it ran as, which defaults it assumed, and what it was denied or swapped. Behind it, the context manifest records why that query was chosen. A receipt makes a run explainable. It doesn't make it right.

You already know: the agent loop (the analyst loop is that loop with a validation step) · earlier in this series: 'Done' is a chain of states and Authority only narrows.

The analyst loop leaves a trail

Part 5's point is that real analysis is not question → SQL → answer. It is a loop: plan, inspect, execute, observe, validate, revise, explain. Each step changes the answer, so each step has to leave a line in the receipt. Here it is for this course's question, "What was Q3 net revenue for EMEA?" (an illustrative run).

A tiny receipt checker

It reads a receipt and lists what the receipt can't vouch for. Each rule is one failure mode from Parts 5 and 6.

def check(r): flags = [] if not (r.get("sql") and r.get("tables") and r.get("result_ref")): flags.append("no evidence: a sentence with a number") extra = set(r.get("actor_reads", [])) - set(r.get("may_read", [])) if extra and not r.get("policy_as_requester"): flags.append("privilege bridge: " + ", ".join(sorted(extra))) if r.get("fallback") and not r.get("fallback_disclosed"): flags.append("silent fallback: " + r["fallback"]) hidden = set(r.get("defaults", [])) - set(r.get("assumptions", [])) if hidden: flags.append("hidden default: " + ", ".join(sorted(hidden))) if r.get("destination") not in r.get("may_publish_to", []): flags.append("unapproved destination: " + str(r.get("destination"))) return flags or ["explainable (not proof it is right)"]

Why it beats the alternatives

✗ Just the answer

"EMEA Q3 net revenue was $48.3M." No SQL, tables, date range or definition. Part 5 calls this a plausible sentence with a number attached.

✗ Answer plus its SQL

Shows what ran, but not who it ran as, what was denied or swapped, or why that table won. Part 6's opening run would have had perfect SQL.

✗ Log the whole run, raw

Copying documents and result rows into the trace turns the audit store into a second, less governed warehouse. Part 6 prefers IDs, hashes, policy decisions and bounded samples.

✓ Scoped receipt, plus a manifest

The user sees what ran, what was assumed and what was off-limits; the operator sees why. Both point at governed data rather than copying it.

Does a receipt make the answer trustworthy?

No. Part 6 is explicit: a complete receipt can show the agent picking the wrong canonical table under the right permissions. It makes a wrong answer debuggable, not less wrong. Only an eval says whether it was right.

It also has costs. The receipt is sensitive itself (questions, identities, SQL, destinations), so it needs scoped access, tamper-resistant storage and a retention rule. For a scratch query an analyst writes and reads themselves, the SQL already is the receipt; the full form earns its keep once someone else acts on the number (that line is this card's inference, not the post's).

Open issue. Shared analytical memory has no public answer yet. Part 6 asks four questions of Meta's colleague-history feature: who may reuse another analyst's history, does the requester already have access to those queries, who owns and can revoke what was derived, and what happens when the source permission changes. "Shared" is a policy decision, not a vector-database setting.

Understand and remember

  • Real analysis loops (plan → inspect → execute → observe → validate → revise → explain) → each step can change the number (a zero-row result forces a new filter, a default picks the quarter) → each step must leave a line in the receipt → otherwise the answer is a plausible sentence with a number attached
  • The tool runs as a service identity, not the requester → the service account can usually read more → a correct query can return data the requester may not know → the receipt records requester and actor separately, plus the policy decision and denied sources → a successful query is not proof of an authorized answer
  • A receipt shows what ran, who as and what was assumed → it never compares the number to the truth → a complete receipt can document the wrong canonical table chosen under the right permissions → a receipt makes a run explainable; only an eval says it was right
  • Saving a correction or reusing a colleague's history is a data write and a read across people → if scope widens automatically, one analyst's filter or confidential context reaches others → shared memory needs an owner, provenance, a review step and revocation; whether Meta's colleague-history feature has these is not public
  • detail that matters The receipt references governed data (result IDs, hashes, bounded samples) instead of copying it → it stays small and doesn't become a second, less governed warehouse → but it is still sensitive (questions, identities, SQL, destinations), so it needs scoped access, tamper resistance and retention
  • detail that matters The context manifest keeps rejected and superseded candidates with reason codes → when two runs give different answers you can see whether ranking, permissions or a stale source changed → without it the divergence is visible but the cause isn't reproducible

  2. mechanism Walk through Part 6's opening run (42,871 rows, a chart that matched last quarter) and say which receipt fields would have exposed the problem.
    Check
    • the SQL compiled and the result looked right, so the what-ran section is clean
    • the requester couldn't access the customer-level table; the service identity could
    • recording requester and actor separately, plus the policy decision, shows the actor read beyond the requester's policy
    • a policy layer re-applying the requester's access on every call would have denied the table and logged the denial
  3. tradeoff Your security team wants every run's full result set and retrieved documents stored in the trace "for completeness". What do you argue, and what do you store instead?
    Check
    • a full copy turns the audit store into a second, less governed warehouse
    • the receipt is sensitive anyway (questions, identities, SQL, destinations)
    • store stable IDs, hashes, policy decisions and bounded samples that point back to governed systems
    • give the receipt its own scoped access, tamper-resistant storage and retention rule
  4. tradeoff The canonical table is denied, and an authorized weekly summary exists. When should the agent use it silently, use it and disclose, or stop and ask?
    Check
    • never silently: a fallback can keep authorization but change grain, population, filters, freshness or definition
    • compare the two on those dimensions first
    • disclose and name the limit when the substitute answers nearly the same question
    • ask when it answers a materially different question: a transparent limited answer beats a confident answer to another question

4 · Compare against what you already know

vs 'Done' is a chain of states: The claim chain checks a coding agent's "done"; the receipt backs a data agent's number. Which link does each leave to an outside verifier, and what does the data run add that a coding run never needs?

Check
  • same: both split one claim into separately witnessed states, and both leave "effect verified" to something outside the agent
  • coding: the checker reruns the tests on the files you accept; data: an eval compares the number with a golden result
  • the data run adds an authorization axis: a correct, verified number can still be one the requester may not know
  • failure: a coding run fails by a false success claim; a data run can also fail by being right and unauthorized, or explainable and wrong

vs Authority only narrows: Authority only narrows sets the rule; the receipt records whether the rule held. What does each one do, and how does each fail on its own?

Check
  • the envelope carries the requester's authority into every tool call and enforces it at run time
  • the receipt is after-the-fact evidence: requester, actor, policy decision, denied sources
  • envelope without receipt: enforcement you can't audit or debug, and denials that show up only as "I could not answer"
  • receipt without envelope: a precise record of a privilege bridge that already happened

5 · Predict commit to an answer before revealing

Next quarter the finance team changes the net_revenue definition to also subtract chargebacks. Maya re-asks the same question, and the stored receipt from this quarter is still on file. Which fields of the old receipt tell you why the two answers differ, and what does the receipt still not tell you?

Reveal

The interpreted-as line (metric definition and its registry version), the context manifest's source versions, and the model and workflow versions would show the definition changed between runs, so the difference is explainable. What neither receipt says is which number is right for Maya's purpose, or whether the new definition was applied consistently across tables: that needs a golden question re-run against the new contract, which is the next card's job.
