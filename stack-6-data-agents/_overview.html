How data agents earn trust

Overview for course 6 of The Agent Stack: a data agent that answers "What was Q3 net revenue for EMEA?" from a warehouse, where the query almost never fails and the meaning almost always can. One page for the five cards: the five gates an answer has to pass, a map of the loop, what matters most, and which card answers which question. Read it first as the map, or last as a recap.

Prime · 2 minutes before you read

The problem: The five cards each fix one way a data agent can return a clean, wrong number: the wrong reading, the wrong table, the wrong grain, the wrong permissions, the wrong grader. Read separately, it's easy to miss that they are one chain, and that only the last link says whether the answer was right.

In one breath

A data agent is the agent loop pointed at a warehouse, and its defining problem is that a wrong answer rarely looks like a failure. Every reading of "net", "EMEA" and "Q3" runs; a deprecated table and a fan-out join both return clean numbers. So trust has to be built outside the SQL: resolve what the question means, mark which source has authority, extract what a table's rows mean from the code that builds them, ship a receipt that says what ran, as whom and what was denied, and grade against a recorded data boundary and the path, not only the number. The receipt makes an answer explainable. Only the eval says it was right.

You already know: the agent loop and measuring an agent. Earlier in this series: the ten layers, 'Done' is a chain of states and tasks, trials and graders.

The words people use

Text-to-SQL vs data agent

Text-to-SQL turns a question into one query. A data agent is the whole governed analysis loop around it; Part 1 calls text-to-SQL one capability inside it, not the system.

Semantic layer vs context card

A semantic layer (e.g. MetricFlow) holds what a metric means. A context card holds what a table's build does: grain, filters, finality, each fact with a source.

Golden SQL vs golden case

Golden SQL is a reference implementation. A golden case also records its data boundary and the path to check, so a changed number can be classified.

✓ Answer with a receipt

The number plus what ran, as whom, what was assumed and what was denied, with the context manifest saying why. It makes the answer disputable; the eval decides if it's right.

When this advice doesn't apply

Simple, governed questions. If "Q3 net revenue" is already one metric in a semantic layer, a single query against it is the right tool, and the full loop adds latency for nothing. A small warehouse with one table per concept and one owner who knows it has little to disambiguate. The loop earns its cost when definitions are contested, tables overlap, or the question is a diagnosis ("why did it dip?").

Scratch work and frozen fixtures. For an analyst's own scratch query the SQL already is the receipt. On a frozen fixture with exact arithmetic, a fixed expected number is fine; boundaries and path checks matter once the data moves.

What the evidence is. The Data Agent Stack posts are architecture arguments built on public write-ups (OpenAI, Spotify, Meta, Pinterest, Grab); Govindarajan reports no experiment and no baseline of his own. Every effect size on this page from a toy warehouse is illustrative: it shows the shape of the failure, not how often it happens in production.

1 · Core model what to internalise, what to just look up

Keep it if it changes what you can explain, predict, compare, choose, build or debug. Otherwise it's reference.

Understand and remember

  • A warehouse query rarely fails loudly → many readings, tables and grains all return plausible numbers → correctness has to be decided before the SQL (meaning, source, rows), not by whether it ran
  • A receipt records what ran, as whom and what was assumed or denied → it witnesses gates 1 to 4 → it makes a wrong answer disputable, but only an eval with a data boundary and a path check says it was right
  • The data moves under a fixed expected value → a healthy agent fails and a wrong path can match → record the boundary, check the path, and gate per slice so an average can't hide a broken slice

Why this step?

4 · Compare against what you already know

vs 'Done' is a chain of states: The claim chain splits a coding agent's "done" into five states; this card splits a data agent's "verified" into five gates. What is the same, and what does the data version add?

Check
  • both split one overloaded claim into separately witnessed links
  • both leave "effect verified" to something outside the agent: re-run tests there, an eval with a data boundary here
  • the data version adds an authorization gate the coding chain never asks
  • and gates 1 to 3 exist because a query can't fail loudly the way pytest can

vs Tasks, trials and graders: Course 4 ordered graders from code to model to human. Which of those does gate 5 rely on for a data agent, and why is a fixed expected value weaker here than a test?

Check
  • code graders: path checks and a current reference query
  • model judges risk sharing the agent's wrong definition
  • a test's verdict is stable on fixed code; a warehouse number legitimately changes
  • so a code grader needs a recorded data boundary to stay meaningful

Why this step?

5 · Predict commit to an answer before revealing

Keep the evals card's rates (Product 80% → 90%, Finance 75% → 0%) but make Finance 40 of the 200 cases instead of 20. Does the overall score still rise after the upgrade?

Reveal

No. Before: (160 × 0.80 + 40 × 0.75) ÷ 200 = (128 + 30) ÷ 200 = 79.0%. After: (160 × 0.90 + 40 × 0) ÷ 200 = 144 ÷ 200 = 72.0%. With 20 Finance cases the average rose 79.5% → 81.0% and hid the collapse; doubling the slice makes the drop visible. A per-slice gate catches it at either size.

Why this step?

6 · Apply use the model, don't restate it

Pick one question your team (or a demo) would ask a data agent. Write the five gates as rows, and for each name the artifact that would witness it in your setup (a metric definition, a table status, a context card, a receipt field, an eval case), or write "missing".

Done when: A five-row table where every row names a concrete artifact or says "missing", and you can say which missing row would produce a silent wrong answer first.

Hint

Gate 5 is usually the one that's missing: no recorded data boundary, so a changed number can't be classified.
