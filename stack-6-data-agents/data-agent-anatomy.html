What a data agent is

Also called an analytics agent, a text-to-SQL agent or "chat with your warehouse". Vinoth Govindarajan's Data Agent Stack, Part 1 (8 Jun 2026) defines it as a governed analysis loop that turns an ambiguous data question into a verified answer with evidence, and says text-to-SQL is one capability inside it, not the system.

Prime · 2 minutes before you read

The problem: A warehouse question like "Q3 net revenue for EMEA" can be answered by several perfectly valid queries that return different numbers. Nothing errors, so an agent that only writes SQL hands back one of them with full confidence, and nobody can tell which reading it picked.

Where it fits: First card of the data-agents case study. You already have the agent loop and the ten-layer ownership map; this card points both at a warehouse and shows which layer has to carry the weight when the tool never fails loudly.

In one breath. A data agent is the agent loop pointed at a warehouse, with one twist that changes everything: a wrong answer rarely shows up as a failed query. The hard part is deciding what the question means (which metric, which entities, which time window, which table), whether the user may see the rows, and then proving the answer, so the agent has to return a receipt along with the number.

One question, three hidden choices

This course's running example (illustrative): an analyst asks "What was Q3 net revenue for EMEA?" He says ambiguity in a data question usually hides in three places: the metric, the entity and the time window. Each word below has at least two legal readings.

Hides inWhat has to be decidedIn "Q3 net revenue for EMEA"In his example: "revenue last week"
MetricWhich business definition the word maps to "net"minus refunds, or a column called net_amount that is only net of tax? "revenue"booked, recognized, net, ARR, Finance's or Growth's?
EntityWhat counts as one thing, and which ones are in "EMEA"accounts billed in EMEA, or accounts owned by the EMEA sales team? "user"account user, workspace user, seat, device or billing contact?
TimeWhich calendar, which boundaries, which timezone "Q3"calendar Jul–Sep, or a fiscal Q3 that starts in August? "last week"calendar week, fiscal week or trailing 7 days?

The loop he draws, and where text-to-SQL sits

Question→Intent + metric resolution→Context assembly→SQL or analysis plan→Safe execution→Validation→Answer with evidence→Feedback, memory, eval

How autonomous? Luo et al.'s levels

LevelWhat the agent does (paraphrased from the survey)
L0 · noneHumans do all data management, preparation and analysis.
L1 · assistanceStateless prompt and response: suggests queries or code, never touches the environment. A plain text-to-SQL chatbot sits here (my mapping).
L2 · partialPerceives and acts on the environment: databases, data lakes, code interpreters, APIs. Running a query and reacting to zero rows needs at least this.
L3 · conditionalOrchestrates and runs tailored data pipelines on its own, under human supervision. The survey calls today's cloud "data agent" products proto-L3.
L4 · highReliable enough to need no supervision or explicit instructions.
L5 · fullInvents new methods, a fully autonomous "generative data scientist".

Grey: a research roadmap with no existing systems, as the survey and his Part 7 both say. He draws one narrow lesson from it: as authority grows, evals must grow past accuracy into safe recovery, policy preservation, cost and rollback.

Why it beats the alternatives

✗ One-shot text-to-SQL

Writes one query and reports it. Fails as "correct SQL, wrong table" and misses dips and funnels that need several exploratory queries.

✗ Chat over the schema

A schema gives shape, not meaning: revenue_amount doesn't say gross or net. Fails as "right metric name, wrong definition", picked silently.

✗ A fluent answer, no receipt

Clean paragraph, no tables, filters, query link or permission note. Fine for a demo; when it's wrong, nobody can tell which step was.

✓ A governed analysis loop

Resolves meaning or asks, checks permissions before retrieval and execution, validates the result, and ships the receipt: SQL correctness is local, answer correctness is end-to-end.

Does every data question need this?

No. He notes some questions are simple lookups. If "Q3 net revenue" is already a governed metric in a semantic layer with one definition, a single query against it is the right tool and the loop adds latency for nothing. The loop earns its cost when definitions are contested, tables overlap, or the question is a diagnosis ("why did it dip?").

What the sources don't show. Everything about OpenAI's agent here is his summary of a public post, plus ByteByteGo's secondary reading; neither gives error rates or a comparison against plain text-to-SQL. The five-layer and eight-step pictures are his framing, not measurements. And a receipt makes a wrong reading visible; it doesn't make it right. Someone still has to own the definition.

1 · Core model what to internalise, what to just look up

Keep it if it changes what you can explain, predict, compare, choose, build or debug. Otherwise it's reference.

Understand and remember

  • The warehouse accepts any well-formed query → several readings of one question all execute and return plausible numbers → no exit code separates right from wrong → correctness has to come from definitions (metric contracts, catalog, pipeline code), not from running the SQL again
  • Meaning is spread across metric definitions, lineage, catalog notes, code and people → a schema gives only shape → the agent must assemble the smallest evidence set that pins the reading, or ask → otherwise it silently picks a definition ("right metric name, wrong definition")
  • A wrong reading can't be caught by re-execution → the answer must ship with a receipt (question as understood, definition, tables, filters, SQL, assumptions, denied data) → a human or an eval can see which choice was made → evals compare executed results against golden results, not SQL text
  • Conversational access must not create new authority → pass-through permissions mean the agent acts with the asker's rights → checks must run before retrieval and execution, because retrieved context and the summary can leak too
  • detail that matters Tool surface size: OpenAI's post (as he reports it) found the full overlapping tool set confused the agent, so tools were restricted and consolidated → ByteByteGo's account adds that reliability improved after the cut (from around 40 tools) → fewer, non-overlapping tools is a reliability lever, not just tidiness

Reference only

  • his five broad layers: meaning, context, governance, execution, verification
  • the six OpenAI context layers by name: table usage, human annotations, code enrichment, institutional knowledge, memory, runtime context
  • OpenAI platform scale as reported in Part 2: over 3.5k internal users, over 600 PB, 70k datasets
  • the exact wording of Luo et al.'s level names (none, assistance, partial, conditional, high, full)

3 · Retrieve from memory, card closed
  1. concept Explain why a data agent's answer can be wrong even when the generated SQL is syntactically and logically valid.
    Check
    • the query can hit the wrong table (grain, staleness, excluded population, deprecated)
    • the metric word can map to the wrong definition
    • a legal join can be semantically wrong
    • none of these raise an error, so execution success says nothing about meaning
  2. mechanism Walk the Q3 EMEA question through the eight-step loop. At which step should the fiscal-versus-calendar choice be settled, and what should appear in the receipt about it?
    Check
    • intent and metric resolution decides or asks about the time window
    • context assembly supplies the evidence (a fiscal calendar definition, the metric contract)
    • the plan and execution use the chosen window
    • validation checks the result makes sense
    • the receipt states the window used as an assumption, alongside definition, tables, filters and SQL
  3. tradeoff Your team must pick: ask the user a clarifying question every time a metric is ambiguous, or apply a documented default and state it in the receipt. What does each cost, and when would you pick each?
    Check
    • asking: slower, interrupts the user, but avoids a silently wrong reading
    • default plus receipt: fast, but only safe if the user actually reads the stated assumption
    • pick asking when readings diverge a lot or stakes are high (finance close)
    • pick defaults when a governed definition exists and the receipt is shown; his posts report OpenAI's agent asks when unclear and applies sensible defaults if the user doesn't answer
  4. mechanism Why does golden-SQL string matching make a poor eval for a data agent, and what does the eval shape he describes do instead?
    Check
    • different SQL can be equally correct, and similar SQL can return a wrong result
    • his described shape executes the generated SQL and compares its results with the expected results
    • a grader then returns a score and an explanation

5 · Predict commit to an answer before revealing

Finance publishes a single governed net_revenue metric in a semantic layer, with region and fiscal calendar built in. Of the eight readings in the worked example, how many can the agent still produce through that metric, and which loop step loses most of its work?

Reveal

If the agent must go through the governed metric, essentially one reading per definition remains: the eight collapse to the metric's own choices. Intent and metric resolution (and much of context assembly) shrinks to "map the words to this metric". The remaining risks move elsewhere: the agent bypassing the metric and querying raw tables, the metric definition itself being wrong or stale, and permissions. That's why he treats the foundation as part of the agent (next card).
