The foundation is part of the agent

Also called the data foundation, the metadata layer, or asset contracts. Govindarajan's Data Agent Stack Part 2 argues that the catalog, semantic layer, lineage, quality checks and ranked query history are part of what a data agent is, because they decide which tables the model can tell apart.

Prime · 2 minutes before you read

The problem: A warehouse usually holds several tables that could answer the same question, and nothing on them says which one the company trusts. A data agent will pick one anyway, the SQL will run, and a wrong number will look exactly like a right one.

Where it fits: You know the runtime assembles the working set from records it holds (context is assembled, not given). This card goes one layer lower: what the data platform must have marked before assembly has anything trustworthy to select. The next card asks where that meaning comes from (pipeline code).

In one breath. A schema tells the agent a column exists, not whether to use it. When several tables could answer a question and none is marked as the trusted one, the model guesses from names, examples and what's nearby, and every guess runs, returns a number and sounds fine. So mark authority in machine-readable metadata, attached to the table: canonical or deprecated, owner, grain, freshness, lineage, metric definition. Don't leave it for the model to infer.

foundation quality→metadata quality→context quality→query quality→answer trust

Part 2's one diagram, as text. If the chain breaks early, he says, every later stage "compensates with guesses".

Predict first: three tables could answer "What was Q3 net revenue for EMEA?". The agent picks the one whose name matches the question best. Which kind of table is it most likely to land on, and will the query fail?

In the example below it lands on the deprecated table: an old, question-specific table can carry the most literal name, and old queries still reference it (that it's typical is my inference; Part 2 lists it as a failure mode, not a frequency). The query won't fail. It returns a clean number that's wrong, which is the failure Part 2 worries about: "The query does not crash. The answer sounds reasonable."

def pick_by_contract(last_month=9): return [n for n, (_, c) in TABLES.items() if c["status"] == "canonical" and c["fresh_through"] >= last_month and c["grain"] != "unknown"] # fct_net_revenue canonical name=2 6100k +0.0% # emea_net_revenue_v1 deprecated name=3 5100k -16.4% # orders_enriched scratch name=0 9400k +54.1% # pick by name: emea_net_revenue_v1 # pick by contract: ['fct_net_revenue']

The rule is three lines because the hard work was done earlier: a person marked the status, freshness and grain. Without those fields, nothing here can tell the tables apart.

Query history shows behaviour, not authority

Past queries look like a free answer key: they show which joins and filters people really use. But most queries are exploration, debugging or one-offs. Spotify mined question-and-SQL pairs from its own query history and asked domain experts to review them. Only 12.5% were accepted.

acceptedad hoc explorationdebuggingone-off answerwrong tablecorrect SQL, wrong patternexplorationone-off
12.5% = 1 in 8 e.g. 40 mined pairs → 5 kept, 35 rejected

The 12.5% and the rejection reasons are from Spotify's write-up, as reported in Data Agent Stack Parts 4–6. The mix of chips and the 40-pair count are illustrative. Part 2 cites ByteByteGo's account of OpenAI: embedding all past queries worked poorly, and ranking dashboard-backed, repeated or data-scientist-written queries higher worked better.

dbt model contracts guarantee shape (columns and types) before a build; data tests check content after it. Neither says which table to trust. DataHub's freshness assertions and Soda's observability checks are Part 2's examples of quality signals; the point is that they reach the agent, not just a dashboard.

Why it beats the alternatives

✗ Let the model infer authority

It reads names, examples and nearby text. In the example that picks the deprecated table, and the answer is 16.4% low with no error raised.

✗ Embed all query history

History records what people did, including mistakes. With 1 in 8 mined pairs passing expert review at Spotify, unranked history mostly teaches residue.

✗ Trust the schema or a shape contract

It shows a column exists and has a type. The worst case per Part 2 is a column that exists, has the right type and means the wrong thing.

✓ Mark authority on the asset

Canonical and deprecated status, owner, grain, freshness, lineage and metric definitions, readable by the agent at retrieval and answer time.

Does every warehouse need this before an agent?

Not all of it, and not everywhere. A small warehouse with one table per concept and one owner who knows it has little to disambiguate. Govindarajan himself says "asset contract" is not a standard everyone must adopt, only enough machine-readable context to decide whether a table should be used. Start with the tables behind your most common questions. For ad hoc exploration, where no canonical answer exists yet, marking things up front buys little; a human reviewing the result does more.

Know what the evidence is. Part 2 is an architecture argument with no experiment of its own. The scale figures (over 3.5k internal users, over 600 PB, 70k datasets) and the silent failure modes (many-to-many joins, filter pushdown errors, unhandled nulls) are OpenAI's, as cited in the post. The 12.5% comes from one curation phase at Spotify, and the posts don't say how many pairs were reviewed. The post doesn't discuss table formats (Iceberg, Delta, Hudi) at all: its subject is the metadata on top of the tables, not how they're stored.

1 · Core model what to internalise, what to just look up

Keep it if it changes what you can explain, predict, compare, choose, build or debug. Otherwise it's reference.

Understand and remember

  • A schema gives names and types, not meaning → several tables fit the same question → the model infers authority from names, examples and proximity → a deprecated or wrong-population table can win and return a plausible wrong number with no error
  • Undocumented grain → a join to a table with more than one row per key → rows multiply silently → the SQL is valid and the total is too high (+54.1% in the example)
  • Query history records what people did, not what is right → most mined pairs are exploration, debugging or wrong-table use (Spotify kept 12.5%) → unranked history teaches the agent bad templates → rank by trust: dashboard-backed, repeated, owner-reviewed
  • Quality and freshness checks live in tools the agent can't see → the agent treats a failing or stale table as healthy → the signal must reach retrieval, planning or answer time to block, warn or reroute
  • detail that matters Selecting by contract is a three-line filter (status, freshness, grain) → the reliability comes from people having marked those fields, not from the rule → an unmarked table can't be filtered, only guessed

Reference only

  • OpenAI's scale figures: over 3.5k internal users, over 600 PB, 70k datasets
  • OpenAI's silent failure modes: many-to-many joins, filter pushdown errors, unhandled nulls
  • Part 2's eight failure modes and eight-item builder checklist
  • dbt model contracts (shape, before build) vs data tests (content, after build); MetricFlow semantic models
  • OpenLineage's object model (jobs, runs, datasets); DataHub freshness assertions; Soda observability signals

4 · Compare against what you already know

vs Context is assembled, not given: Assembly selects what goes into the turn; the foundation decides what can be told apart at all. If the EMEA agent answers 5,100, how do you tell an assembly failure from a foundation failure, and which fix does each need?

Check
  • foundation failure: emea_net_revenue_v1 carries no deprecated status, so no selection rule could reject it
  • assembly failure: the status existed but was ranked below name similarity, or dropped by the budget
  • check the catalog record first, then what the working set contained
  • fixes: mark the asset vs make status an eligibility gate in selection

vs Tool output is untrusted input: That card treats tool output as untrusted input. In what sense is mined query history the same thing, and what is different about how it fails?

Check
  • both are text that enters the model's context without having earned authority
  • tool output can carry injected instructions; query history carries habits and mistakes
  • history fails quietly, by teaching a bad template that still produces valid SQL
  • both need a gate on provenance before they can steer: trust rank for history, quoting and no authority for tool output

5 · Predict commit to an answer before revealing

Now suppose all three EMEA tables are perfectly marked, but finance changes the net-revenue definition on Oct 1 to also exclude chargebacks, and fct_net_revenue is rebuilt only from October on. The user asks for Q3 again. Will the contract filter still give a trustworthy answer?

Reveal

It still picks fct_net_revenue, and the number is right for the definition in force during Q3. But if the user wants Q3 under the new definition, the answer is wrong for their purpose, and nothing in status, freshness or grain says so. The contract also needs an effective period for the metric definition, and the answer should say which definition it used. That's a receipt question, not a table-choice question.
