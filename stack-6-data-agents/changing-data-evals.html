Evaluating against data that moves

Also called golden-case drift, stale expected values or mutable-data evals. Govindarajan's Data Agent Stack Part 7 makes the data boundary part of every test case and treats graders, context and metric definitions as deployables that each need a release gate. The post gives patterns and failure modes, no measured numbers.

Prime · 2 minutes before you read

The problem: A data agent's golden case stores an expected answer, but the warehouse keeps changing under it. Without more than a stored number, a healthy agent fails the test after a backfill, a wrong query passes because it happens to match, and you can't tell whether the agent or the data moved.

Where it fits: You know how to run tasks with repeats and intervals, and how to order graders (deterministic first, judge last). This card applies both to an agent whose ground truth is a live warehouse, the last piece of the data-agent course after receipts.

In one breath. A data agent's golden case stores an expected answer, but the warehouse keeps changing underneath it: late refunds, backfills, metric revisions. So a fixed expected number goes stale and fails a healthy agent, while a wrong query can match it by coincidence. Pin which data the case was checked against, grade the path (tables, filters, metric version) as well as the number, gate releases per slice, and version the graders like everything else.

Worked example: right in July, "wrong" in October

The course question, "What was Q3 net revenue for EMEA?", as a golden case written in July, right after fiscal Q3 (April to June for this card's company; the anatomy card's fiscal year differs) closed. The metric contract: net = sales − refunds, excluding intercompany transfers. Three agents answer it in July and again in October. All figures are illustrative, in $M.

P/F is the grader's verdict; green when it is the right verdict, red when it is wrong. "Path check" asks: canonical table, intercompany filter present. ±1% of 46.30 is ±0.46, so 46.05 (−0.54%) passes and 47.45 (+2.48%) fails. Every verdict is computed by code/changing-data-evals.py.

Read it by column. In July every result-only grader passes all three agents: a deprecated table and a missing filter both match today's number. In October the fixed golden value fails the healthy agent and passes the legacy one, because the stale expected value and the stale table agree. The tolerance rescues the healthy agent but still passes the legacy one. The snapshot rerun passes everyone; it is not a correctness check here, but it is what tells you who moved: the healthy agent still returns 46.30 on July data, so the −0.25 change (0.60 − 0.85) is the data, not the agent. Govindarajan's point is that without some data boundary (a fixture, a versioned snapshot, a time-travel id, an as-of timestamp, a current reference query or invariants) a changed result can't be classified at all.

One average is not a release gate

The overall score is a weighted mean of slice scores, so a slice's weight is its share of cases. A small slice can go to zero and barely dent it.

Soverall= nPpPbig slice+nFpFsmall slice nP+nF
ncases in the sliceProduct 180 · Finance 20 ppass rate in the sliceillustrative
before: (180 × 0.80 + 20 × 0.75) ÷ 200 = (144 + 15) ÷ 200 = 79.5% after: (180 × 0.90 + 20 × 0.00) ÷ 200 = (162 + 0) ÷ 200 = 81.0%

Slice sizes and rates are illustrative; the arithmetic is computed. The post's rule: thresholds per critical slice (domain, metric family, ambiguity, join type, schema evolution, permission path, failure class), with policy failures, prohibited tables, missing required evidence and critical metric regressions as hard blockers.

Graders are deployables too

For a data agent the answer depends on more than code. The post lists the answer-changing artifacts: model, prompt, tool description, context document, retrieval index, semantic contract, pipeline, policy and grader. Each needs a version, an owner and a test, and each goes down the same path:

change manifest→component evals→critical end-to-end suite→repeated trials→baseline + slice comparison→review→shadow or canary→rollout + monitoring→promote or roll back

Two artifacts get special treatment. A semantic-definition change should bump the metric version and update the affected cases explicitly, since the new number may be intended. A grader change is tested against a frozen human-labelled set, so you can tell an agent improvement from "a change in the ruler".

def strategies(month): ref_now = net(canon(month)) # canonical SQL, run today snap = answers("jul") # every agent on July data return { "fixed golden": lambda n, a: a["value"] == GOLDEN, "golden +-1%": lambda n, a: abs(a["value"] - GOLDEN) <= TOL * GOLDEN, "July snapshot": lambda n, a: snap[n]["value"] == GOLDEN, "reference now": lambda n, a: a["value"] == ref_now, "path check": lambda n, a: a["table"] == "fct_revenue" and a["excl_ic"], } # output (October) fixed golden F P F right 1/3 golden +-1% P P F right 2/3 July snapshot P P P right 1/3 reference now P F F right 3/3 path check P F F right 3/3 overall 79.5% -> 81.0%

Why it beats the alternatives

✗ A fixed expected number

Fine on a frozen fixture, but on live data it fails the healthy agent (46.05) and passes the deprecated table (46.30) in October.

✗ Exact match on golden SQL

Different CTEs, aliases or join order can implement the same metric. A string matcher rejects a valid query; the post calls golden SQL "a reference implementation".

✗ One judge, one average

A judge can share the agent's wrong definition, and one overall score can rise while Finance drops to zero.

✓ Pinned boundary, path checks, slice gates

Record the data boundary, compare to a current reference query or invariants, check tables and filters, gate per slice, and version the grader.

Is a frozen snapshot not enough?

A snapshot makes the test repeatable and lets you separate "the agent changed" from "the data changed". It can't catch bugs that only show on new data: in the example the missing filter is invisible on July data. That is why the post pairs fixed boundaries with canary questions against live dependencies, sampled production replay and monitoring. "Offline evals protect known behavior"; production tells you when the world moved.

When a fixed number is right: stable fixtures with exact arithmetic, where the post recommends plain exact scalar comparison. And a current reference query is only as good as its own definition: when the metric's meaning is contested, the post sends the case to human review. The strategies-by-agent table above is this card's construction; the post names the strategies and failure modes but runs no such comparison.

Understand and remember

  • The warehouse changes legitimately (late refunds, backfills, metric revisions) → a fixed expected value goes stale → it fails the healthy agent and can pass a stale path that froze at the same moment → every case needs a recorded data boundary or a current reference query
  • A wrong path can return today's right number (deprecated table, missing filter, bad join) → result-only grading passes it → also check the path: required and prohibited tables, filters, metric version, invariants
  • A model judge reasons from the same definitions as the agent → it rewards a fluent answer built on a shared wrong definition → put metric contracts, reference execution and invariants ahead of the judge, and calibrate it against human labels
  • The overall score is a case-weighted mean of slices → a small slice can collapse while the average rises → set thresholds per critical slice and make policy and critical-metric failures hard blockers
  • detail that matters A snapshot rerun is a classifier, not a correctness check → it separates "agent changed" from "data changed" but passes bugs that only show on new data (the missing intercompany filter) → pair it with canaries and replay on live data
  • detail that matters The grader is an answer-changing artifact → changing tolerance from exact to ±1% moves October from 1/3 to 2/3 right verdicts with no agent change → version graders and test them on a frozen human-labelled set

Reference only

  • the release path in order: change manifest → component evals → critical end-to-end suite → repeated trials → baseline and slice comparison → review → shadow or canary → rollout → monitoring → promote or roll back
  • the list of comparison strategies (exact scalar, normalized tables, subset/superset, tolerance, invariants, current reference query, SQL semantic analysis, human review)

  1. concept Explain why "the agent's answer changed" can't be called a regression unless the case records a data boundary, and name three kinds of boundary.
    Check
    • the change could come from the agent or from legitimate data change (late arrivals, backfill, metric revision, schema migration, freshness incident)
    • a boundary lets you rerun on the old data or compute today's right answer
    • kinds: fixture, versioned snapshot, time-travel id, as-of timestamp, current reference query, invariants
  2. mechanism Walk through the October run of the legacy-table agent under the fixed golden value, the current reference query and the path check. What does each grader read and decide?
    Check
    • fixed golden: reads 46.30, compares to 46.30 stored in July → PASS (wrong verdict)
    • current reference query: runs canonical SQL today → 46.05 ≠ 46.30 → FAIL (right)
    • path check: reads the table from the receipt/SQL → deprecated table → FAIL (right)
  3. tradeoff A teammate proposes widening the tolerance so late refunds stop breaking the suite. What does that buy and what does it cost?
    Check
    • buys: the healthy agent passes small legitimate drift (±1% passes 46.05)
    • costs: it still passes the stale table, and a wider band (±3%) passes the missing-filter agent too
    • it is also a grader change, so it should be versioned and checked against human labels
  4. tradeoff When is a model judge the right grader for a data-agent case, and when must it be overruled?
    Check
    • right for: whether claims are supported, assumptions visible, ambiguity handled
    • never overrides a policy failure, a broken invariant or a clear result mismatch
    • it can share the agent's wrong definition, so calibrate it against human labels and track disagreement

vs Tasks, trials and graders: The Tuesday run's grader reads a test exit code; the EMEA case's grader reads a number from a warehouse. What makes the second harder to ground, and how does the grader-ordering rule carry over?

Check
  • a test's pass/fail is stable on fixed code; a warehouse number legitimately changes over time
  • so the data agent's ground truth needs a boundary or a current reference query, not a stored value
  • same rule: deterministic checks (policy, structure, results, invariants) before any judge, and the judge never overrides them

Check
  • the error here is in the expected value and the slice weighting, not in sampling
  • more trials don't help: a stale golden value fails the healthy agent every time
  • more tasks help only if they cover the broken slice; otherwise the average still hides it
  • you need both: intervals for noise, boundaries and slice gates for drift

5 · Predict commit to an answer before revealing

The metric owners revise "net revenue" to subtract a new chargeback provision, and update the canonical reference query, but the agent's context still describes the old definition. Which strategies from the table now flag the agent, which of those verdicts are right, and what should happen to the golden case?

Reveal

The current reference query flags it, correctly: the agent is answering the old definition. The fixed golden value and the snapshot rerun don't notice, because they encode the old meaning. The path check flags it only if it checks the metric version. Per the post, a semantic-definition change should bump the metric version and update the affected cases explicitly, because the new number is the intended result; the agent's context then needs the same versioned change.
