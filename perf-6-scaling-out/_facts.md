## Running examples (use on every card that can)
**1. Llama-3.1-8B, BF16, one H100 SXM (the single-GPU baseline from courses 1–5).** L=32, D=4096, F=14336, N=32, K=8, H=128, V=128256. 8.03B params, **16.06 GB** BF16, KV **128 KiB/token**, decode ceiling at batch 1 **≈ 209 tok/s (4.8 ms/step)**, 63.9 GB free → 59 sequences of 8k.

**2. Llama-3.1-70B, BF16 — the dense model that needs several GPUs (this course's main example).** Shapes (Meta config): L=80, D=8192, F=28672, N=64, K=8, H=128, V=128256, untied embeddings. Computed (script scratchpad/p6/n70.py, 2026-09-24):
- Params: attention 151.0M/layer, MLP 704.6M/layer, layer 855.7M; total **70.55B** = MLP 79.9% · attention 17.1% · embeddings+LM head 3.0%
- Weights: **141.1 GB BF16**, 70.6 GB FP8 → does not fit one 80 GB H100 in BF16
- KV per token: 2·80·8·128·2 B = **327,680 B = 320 KiB**; 8,192-token sequence = **2.68 GB**
- Weights per GPU and memory-only decode step (weights/BW, batch 1, comms ignored):
  | TP | weights/GPU | free HBM/GPU | step | tok/s ceiling | KV room (8k seqs, whole group) |
  |---|---|---|---|---|---|
  | 1 | 141.1 GB | doesn't fit | 42.12 ms | 24 | – |
  | 2 | 70.6 GB | 9.4 GB | 21.06 ms | 47 | 7 |
  | 4 | 35.3 GB | 44.7 GB | 10.53 ms | 95 | 67 |
  | 8 | 17.6 GB | 62.4 GB | 5.27 ms | 190 | 186 |
- TP all-reduce per decode step (our inference from Megatron: 2 all-reduces per layer forward → 160 per token-step for 70B), message = B·D·2 bytes: B=1 16 kB · B=64 1.05 MB · B=256 4.19 MB. Bandwidth term with ring all-reduce 2·(n−1)/n·msg / 450 GB/s at TP8: 0.06 µs · 4.08 µs · 16.3 µs each → ×160 = 0.01 · 0.65 · 2.61 ms per step. At small batch the **latency** term dominates. **Shared illustrative value: α = 1 µs per ring hop (Scaling Book's TPU ICI figure; NVIDIA publishes no NVLink hop latency) → 2(n−1)·α per all-reduce inside a node (TP2 2 µs, TP4 6 µs, TP8 14 µs); 28 µs for an all-reduce spanning two nodes (illustrative 2×); a PP send is one hop (1 µs NVLink, 2 µs IB).** 160 × 14 µs = 2.24 ms = 43% of the 5.27 ms step (collectives card). Every card uses these values and labels them illustrative.
- Course 2 (serving-llama-70b, ours): FP8 8×H100 B=424 QPS/GPU 4.14; BF16 8× 1.90. Scaling Book (Part 7): 8×H100 all-reduce reaches ~370 GB/s busbw only at ~10 GB messages, ~150 GB/s at 58 MB.

**3. DeepSeek-V3 (the MoE example).** 671B total, 37B active per token, 61 layers (first 3 dense, 58 MoE), hidden 7168, MLA (d_c 512, d_h^R 64, 128 heads), per MoE layer 1 shared + 256 routed experts of width 2048, 8 routed active, node-limited routing M = 4, sigmoid gating, auxiliary-loss-free balancing (bias, γ = 0.001), MTP depth 1, FP8 (E4M3) training. ## Hardware numbers (reuse exactly)
- H100 SXM: 989 TFLOPS dense BF16, 1,979 dense FP8, 3.35 TB/s HBM3, 80 GB, ops:byte ≈ 295. NVLink 4: 18 links × 25 GB/s each way = **450 GB/s per direction** ("900 GB/s" bidirectional); a DGX/HGX H100 node = 8 GPUs on NVSwitch. Scale-out: one 400 Gb/s ConnectX-7 per GPU = **50 GB/s** per GPU, 400 GB/s per node. So NVLink ≈ **9×** InfiniBand per GPU (450/50).
- H800 (DeepSeek's GPU): same compute as H100, NVLink cut down; DeepSeek measured 160 GB/s NVLink, 50 GB/s IB.
- V100 DGX-2H (Megatron): NVSwitch 300 GB/s between GPUs; 100 GB/s between servers (8 IB adapters).
- A100 (DistServe, MegaScale roofline): 312 TFLOPS BF16, 2 TB/s (80 GB) → ops:byte 156.

## Collectives (reuse these definitions and cost formulas)
- AllReduce, Broadcast, Reduce, AllGather, ReduceScatter, AllToAll (NCCL names). Identities: ReduceScatter + AllGather = AllReduce.
- Ring cost, bandwidth-bound, message size S per GPU, n GPUs, link bandwidth W (per direction): AllGather = ReduceScatter = (n−1)/n · S/W; AllReduce = 2(n−1)/n · S/W. nccl-tests: algbw = S/t; busbw = algbw × 2(n−1)/n for AllReduce (1.75 at n = 8), × (n−1)/n for AllGather/ReduceScatter/AllToAll.
- Latency-bound regime: small messages cost a fixed per-hop latency (Scaling Book: ~1 µs per hop on TPU ICI; NVIDIA doesn't publish an NVLink collective latency — label specific µs values illustrative).

## Colour meanings (same on every card)
- green `--accent`: useful compute / the winner / kept tokens
- grey `--faint` / `--surface2`: communication, waiting, idle, pipeline bubbles, overhead (communication is overhead unless it's the bottleneck)
- neutral `--text`/`--muted`: weights and data at rest (and GPU boxes)
- red `--red`: ✗, SLO violations, the bottleneck, the worst value, dropped tokens, the overloaded expert/GPU
- `--amber` only for a third roofline region
