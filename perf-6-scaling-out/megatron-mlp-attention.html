Megatron I: splitting the MLP and attention

Also called tensor parallelism (TP), Megatron-style or intra-layer model parallelism, and column-parallel / row-parallel linear layers. Card 1 of 2 on Megatron-LM (Shoeybi et al., NVIDIA, 2019). It walks §2.3 (where this idea sits) and all of §3 up to the embeddings: Eq 1–3, the f and g operators, head-parallel attention, and Fig 3–4. The paper never uses the words "tensor parallelism"; it says "intra-layer model parallel". Card 2 covers the embeddings, the fused loss, the experiments and what TP costs when serving.

In one breath

Split every weight matrix of a transformer layer across GPUs so that each GPU does 1/8 of every matmul at the same time. Megatron's trick is the order of the splits: cut the first matrix of each block by columns and the second by rows. Each GPU then runs its whole slice of the block alone, and the GPUs talk only once at the end of the block to add up their partial results. That is one all-reduce after attention and one after the MLP.

§2.3 Where this sits: three ways to use many GPUs

The paper names two ways to scale out. Data parallelism splits the batch. It scales throughput almost linearly, but "the model must fit entirely on one worker". Model parallelism splits the model, and it comes in two kinds. Layer-wise pipeline parallelism (GPipe) gives each device a group of layers and "suffers from pipeline bubbles". Distributed tensor computation (Mesh-TensorFlow, FlexFlow) splits the individual tensor operations. Megatron borrows Mesh-TensorFlow's insight of splitting the attention heads, but uses no compiler, only "a few simple primitives" added to ordinary PyTorch. Everyday picture: data parallelism is 8 kitchens each cooking whole meals; pipeline is one assembly line where each cook does a few steps; tensor parallelism is 8 cooks chopping the same onion at once.

§3a The MLP: why column first, then row

A transformer layer is a self-attention block followed by a two-layer MLP (Fig 2), and the paper splits each block separately. The MLP starts with a matmul and a GeLU (Eq 1). There are two ways to cut the first weight matrix A across GPUs:

Y=GeLU(XA) (Eq 1) X=[X1,X2], A=[A1A2] ⇒ Y=GeLU(X1A1+X2A2) split A by rows (Eq 2): the sum must happen before GeLU, so the GPUs must sync first A=[A1,A2] ⇒ [Y1,Y2]= [GeLU(XA1),GeLU(XA2)] split A by columns (Eq 3): each GPU applies GeLU to its own columns, no sync Z=YB= Y1B1GPU 1+ Y2B2GPU 2 →all-reduceg: the one sync
Xinput activations, one row per token, replicated on every GPUtokens × 8,192 Afirst MLP weight (the paper's GPT-2 has one; Llama has two, see below)8,192 × 28,672 Bsecond MLP weight, split by rows to match Y's column split28,672 × 8,192 Y, ZGeLU output (split by columns), block output (after the all-reduce)F-wide · D-wide

Shapes are Llama-3.1-70B's (D = 8,192, F = 28,672). The paper's example uses 2 GPUs; TP8 cuts into 8 pieces the same way.

GeLU can't be pushed through a sum because it is non-linear. A one-number check from the lab: GeLU(1.0 − 0.5) = 0.3457, but GeLU(1.0) + GeLU(−0.5) = 0.8412 − 0.1543 = 0.6869. With the column split, each GPU already has complete pre-activations for its own columns, so GeLU (or any elementwise function) is exact locally. The second matmul then needs the columns of Y that each GPU owns, and those are exactly the rows of B it owns, so it "takes the output of the GeLU layer directly without requiring any communication". Each GPU ends with a full-size but partial Z. One all-reduce sums them "before passing the output to the dropout layer".

The f and g operators (Fig 3, Code 1)

The paper wraps this in two tiny autograd functions that are "conjugates" of each other. f sits at the start of the block and g at the end. Code 1 is about six lines: a torch.autograd.Function whose forward hands the input back unchanged and whose backward all-reduces the incoming gradient. g is the same with the two directions swapped. In outline (our paraphrase):

forward pass backward pass f (input) y = x # identity dx = all_reduce(dy) # sum the partial dX g (output) y = all_reduce(x) dx = dy # identity

Why f needs an all-reduce going backward: X was copied to every GPU, and each GPU only computes its own share of the gradient, dXi = dHi·AiT. The true dX is their sum. In the lab, one GPU's dX alone is off by up to 2.37; after f's all-reduce the error is 6.2e-15. So the MLP needs "a single all-reduce operation in the forward pass (g operator) and a single all-reduce in the backward pass (f operator)".

§3b Self-attention: split by heads

Attention already comes in independent pieces: the heads. The paper splits the Q, K and V matmuls "in a column parallel fashion such that the matrix multiply corresponding to each attention head is done locally on one GPU". Each GPU computes its heads' scores, softmax and weighted sum with no communication. The output projection is split by rows and consumes those head outputs directly, like B in the MLP. Its partial sums take one all-reduce. Llama adds two things the 2019 paper doesn't have, and neither breaks the split. RoPE rotates within one head, so it stays local. Grouped-query attention shares one KV head across 8 query heads, so the 8 query heads that share a KV head must sit on the same GPU as that KV head.

The paper's Fig 3, redrawn for Llama-3.1-70B at TP8 (it draws 2 GPUs and a GeLU MLP). LayerNorm (RMSNorm in Llama), dropout and the residual add sit outside these boxes and are simply repeated on every GPU; card 2 covers that.

The same thing in the Scaling Book's notation

Scaling Book Part 3 sorts every sharded matmul into four cases by whether the contracting dimension (the one summed over) is split. Write the 8 TP GPUs as mesh axis Y; A[D, FY] means "F is split 8 ways". Megatron's two matmuls are exactly Case 1 then Case 3 (the mapping is ours, not stated in either source):

StepSharded matmulCaseCommunication
Column-parallel (gate, up, q, k, v)X[T, D] ·D A[D, FY] → H[T, FY]1: contracting D not splitnone

{UY} is the book's mark for "unreduced along Y": each GPU holds a partial sum of the right shape. T = tokens in the batch.

Llama-3.1-70B has only K = 8 KV heads. TP8 gives each GPU exactly one. TP16 would give 4 query heads per GPU but half a KV head, so each KV head (and its KV cache) has to be replicated on 2 GPUs; TP32 on 4. The lab prints both. That is one reason 70B deployments usually stop at TP8 inside one node (our inference).

What the all-reduces carry per forward pass: after each block, every GPU holds a full tokens × 8,192 partial result in BF16. That is the message S:

message S = tokens × D × 2 B; per-GPU ring traffic = 2(n−1)/n × S = 1.75 × S S 1.75 × S × 160 per step decode, batch 1 16.4 kB (16 KiB) 28.7 kB 4.59 MB decode, batch 64 1.05 MB (1 MiB) 1.84 MB 293.6 MB decode, batch 256 4.19 MB (4 MiB) 7.34 MB 1,174 MB prefill 2,048 tok 33.6 MB (32 MiB) 58.7 MB 9,395 MB each GPU reads 213.9 MB of weights per layer: 13,056× the batch-1 message

Ring cost from the course's shared facts (see collectives). At batch 1 the bytes are tiny and the 160 fixed per-call latencies are what hurt. Card 2 turns these into milliseconds per decode step at TP 1–8. The row-first split (Eq 2) would all-reduce F-wide data instead: 57,344 B per token, 3.5× the D-wide message.

Why it beats the alternatives

✗ Split A by rows first

Eq 2. Each GPU holds a partial pre-activation, and GeLU of a partial sum is wrong (1.19 error in the lab). Syncing first costs an F-wide all-reduce, 3.5× the bytes for Llama, and you still have to split B.

✗ Split both matmuls by columns

The second matmul contracts over F, which is now split. That's Scaling Book Case 2, so every GPU must AllGather the F-wide activations first, and the output comes out split too. That's more traffic than one D-wide all-reduce (our reasoning).

✗ Only pipeline (split by layers)

Fits the model, but one token still walks through all 80 layers one stage at a time, so at batch 1 only one GPU's bandwidth is working (our inference for serving). In training it "suffers from pipeline bubbles".

✓ Column, then row (Megatron)

No sync inside a block, one D-wide all-reduce after it, and all 8 GPUs read their 1/8 of the weights at the same time. That's the 42.12 → 5.27 ms memory-only decode step from the shared facts (comms ignored), with no compiler and a few lines of PyTorch.

Is tensor parallelism always the right split?

No. It's the default inside one NVLink node, and a poor choice in several cases:

  • Across nodes. 160 all-reduces per token over InfiniBand (50 GB/s per GPU vs 450 GB/s NVLink) is too slow. Megatron itself kept its 8-way groups inside one DGX-2H. Across nodes people use pipeline or data parallelism (next cards).
  • When the model fits one GPU. Llama-3.1-8B on 8 GPUs gets more tokens per GPU as 8 independent copies. TP only buys lower latency per request, and pays for it in all-reduces.
  • Past the number of KV heads. Beyond TP8, Llama-3.1-70B has to replicate KV heads and their KV cache.
  • At small batch. The messages are tiny, so fixed latency dominates. Card 2 puts numbers on it.

Also note: f exists only because training has a backward pass. A serving engine needs only the g all-reduces. Some setups keep the activations between blocks split too and replace each all-reduce with a ReduceScatter at the end of a block and an AllGather at the start of the next (the Scaling Book's Q7 form). The total bytes are the same, since AllReduce = ReduceScatter + AllGather.

Run it: labs/tp-split.py [L] numpy only, under 1 s on the M3.
