MegaScale-Infer I: splitting attention from the experts

Also called attention–FFN disaggregation (AFD) or, in the paper's words, disaggregated expert parallelism. Card 1 of 2 on MegaScale-Infer (Zhu et al., ByteDance Seed and Peking University, arXiv 2504.02263 v4). It walks §1–3 in order: why MoE experts starve during decode, the roofline arithmetic, and the attention-node / expert-node layout. Then §4.3, which puts each side on different, cheaper GPUs, plus the two §4.2 formulas that size the split. Card 2 covers the ping-pong pipeline (§4.1), the plan search (§4.2), M2N communication (§5) and the results (§7).

In one breath

In a MoE model each expert sees only a small slice of the decode batch (top-k of E), so its matrix multiplies stay memory-bound and the GPU's compute sits idle. MegaScale-Infer moves attention and the experts onto different GPUs. Many attention replicas (data parallel, each holding its own requests' KV cache) all send their tokens to one shared set of expert nodes (expert parallel, one expert per node). Pooling the tokens gives each expert a batch big enough to be compute-bound. Each side can then scale on its own and run on the GPU that is cheapest for its bottleneck: memory for attention, FLOPs for experts.

§1–2.2 The problem: batching only helps the part that shares weights

Decode attention is memory-bound "because they must access the intermediate states (i.e., key-value cache) of all previous tokens". Batching doesn't fix that, because every request reads its own KV cache. FFN weights, on the other hand, are shared by every token in the batch, so "batching is only efficient for FFNs to reuse model parameters". In a dense model a big enough decode batch makes the FFN compute-bound. In a MoE model the router splits the batch, so "fewer tokens—less than a quarter, or even an order of magnitude less—are assigned to each expert within the same batch size". The paper's Fig 1 draws this as a sketch with no numbers: attention utilization stays low at every batch size, the dense FFN saturates, the MoE FFN doesn't.

§2.2 recaps the standard tools. Tensor parallelism splits each matmul and "introduces substantial communication overhead", so it stays inside an NVLink node (Megatron I). Pipeline parallelism "slightly increases inference time" but "scales serving throughput linearly". Expert parallelism puts whole experts on different devices, so each MoE layer needs "two all-to-all communications" (dispatch and combine, expert parallelism). EP runs complete matmuls, which GPUs like, but risks load imbalance and more traffic as top-k grows: "whether TP or EP benefits FFN more depends highly on the structure of MoE models and the real-time workload." Prior work: Infinite-LLM already split attention off, for dense long-context models, where memory capacity is the limit and the traffic is simpler than top-k routing.

Why not just raise the batch? §2.3 names three limits. A bigger batch makes each step slower, which can break the time-between-tokens SLO. Every sequence in the batch needs its KV cache in GPU memory, and "for large-scale MoE, the GPU memory becomes more scarce, resulting in a smaller maximum batch size". Spreading the model over more GPUs to make room "introduces more communication overhead". For DeepSeek-V3 on H100s, 9,440 sequences decoding in one replica's step is far beyond any of these limits (our inference).

§2.4 Two opportunities, two challenges

Splitting attention from the FFN "naturally provides two key advantages". Independent scaling: add attention replicas, and each one's requests are aggregated at the FFN, so it "becomes compute-intensive". Heterogeneous deployment: each module runs on "the most cost-effective GPUs" for it (§4.3 below). It also creates two problems, both solved in card 2. First, every token goes attention → FFN → attention in sequence, so one side idles while the other computes or while data is on the wire. A ping-pong pipeline of micro-batches keeps both busy. Second, M attention GPUs talking to N expert GPUs need M2N and N2M communication instead of all-to-all, and "directly leveraging peer-to-peer communication primitives from existing libraries results in significant performance degradation".

§3 The layout: attention nodes and expert nodes

MegaScale-Infer first splits prefill from decode onto separate clusters, "following prior work" (DistServe, Splitwise). The paper is about decode only. One runtime instance serves one model replica during decode and is made of two kinds of node:

"Each expert node typically consists of 1-8 GPUs within a single physical server and stores the parameters of one expert. All expert nodes together form an expert parallelism group. The parameters of the attention module (e.g., weight matrices for QKV and output projection) are replicated on each attention node, where the key-value caches are also stored. Tensor parallelism is employed within each attention/expert node to leverage high-bandwidth connectivity between GPUs (e.g., NVLink)."MegaScale-Infer §3

So attention is data parallel (DP: identical copies, each with its own requests and KV cache), the experts are expert parallel (EP: expert i of every layer on node i), and tensor parallelism (TP) appears only inside a node, over NVLink. The two sides are sized separately: the number of attention nodes na doesn't have to match the number of experts E.

Each part, with two examples. Everyday analogy: many order counters (attention) each keep their own customers' tickets, and a single row of specialist kitchens (experts) cooks for all counters at once.

Our inference from Example B: "one expert per node" suits coarse experts like Mixtral's. A fine-grained model such as DeepSeek-V3 would leave most of each node's memory empty, so it would need several experts per node. The paper's §3 doesn't describe that case. Three ways to split, side by side

P/D disaggregation (DistServe) splits a request by phase. AFD splits each decode step by layer type. MegaScale-Infer does both: P/D first, then AFD inside decode. DeepSeek's decode unit (expert parallelism) already pools tokens from many attention replicas, but on the same GPUs that run the experts.

Symbol clashes in the paper. B is memory bandwidth in §2.3 and the global batch in Table 1 and §4.2. K is top-k here, but §6 reuses it for the minimum cost of a cold expert. E counts both experts and expert nodes, which only works because each node holds exactly one expert. And F in §2.3 is FLOPS, not the FFN.

The second formula is the paper's balance rule: it fits a linear time model to each side and picks na so both finish a micro-batch at the same time (constraint 1 in card 2). Dropping the constants, k1ba = k3be gives be/ba = k1/k3, and substituting into the first formula gives k1E/(k3K). The paper doesn't print that step or any k values. With illustrative ratios for Mixtral (E/K = 4): k1/k3 = 0.5 → 2 attention nodes, 1 → 4, 2 → 8.

A different question is how many attention nodes you need before each expert is compute-bound, be ≥ F/B. The first formula answers it directly (lab section 4). The paper sizes na by balance, not by this target. This is our framing of what the pooling buys.

ba = 128 is the micro-batch in the paper's §7.3 message-size example, and m = 3 is where Alg 1 starts its search. Neither is a tuned plan. The 74 attention nodes land close to DeepSeek's own DP80 decode deployment, which also exists to pool tokens for 256 experts. We read that as a coincidence of the same arithmetic, not a design the papers share.

§4.3 Heterogeneous hardware: the cheapest GPU for each bottleneck

Once the two sides live on different nodes, they don't have to be the same GPU. Attention nodes are memory-bound and hold the KV cache, so they want "higher per-cost memory bandwidth and larger per-cost memory capacity". Our reading of the last lines: cheap FLOPs come with a very high ops:byte ratio, so an L40S expert only pays off with a large pooled batch. That is exactly what disaggregation supplies. "Per cost" is a normalized purchase price, not dollars. The TFLOPS and bandwidth columns look like vendor peak figures. We didn't re-derive them.

The paper enumerates every GPU type for each side and concludes: "H20 is more suitable for attention due to its large memory capacity and high memory bandwidth per unit cost. Meanwhile, the L40S GPU is more cost-effective for experts." Power points the same way: 500 W maximum for the H20 and 350 W for the L40S. At equal power the L40S gives more compute and the H20 more bandwidth. In §7.2 the H20 + L40S deployment reaches up to 1.86× the decode throughput per cost of TensorRT-LLM on H20 (the intro says 1.7×, and production cost fell 1.5–2.0×). Card 2 covers these results and their baselines.

Why it beats the alternatives

✗ Colocated replicas (TP inside a node)

Each replica's batch is split E/K ways before it reaches an expert. Mixtral at b = 156 on an A100 gets 39 tokens per expert and 25% FFN MFU. DeepSeek-V3 at b = 295 on an H100 gets 3.1%.

✗ Just grow the batch

The TBT SLO, KV cache memory, and the extra communication from more model parallelism all cap it (§2.3). DeepSeek-V3 would need 9,440 tokens in every step of one replica.

✗ Large EP with attention on the same GPUs

DeepSeek's decode unit does pool 80 attention replicas into EP320. But every GPU runs both halves, so attention and expert capacity grow together on one GPU type, in 320-GPU units (our inference on the trade-off).

✓ Attention–FFN disaggregation

na DP attention nodes feed E expert nodes. na is chosen so Ta ≈ Te, and pooling pushes be toward F/B. Each side runs on its cheapest GPU: H20 for memory, L40S for FLOPs.

Is splitting attention from the experts always better?

No. It pays off when experts starve, which means sparse MoE models with a large E/K. Cases where it doesn't:

  • Dense models. The FFN already reaches F/B with an ordinary batch. The earlier Infinite-LLM split attention off dense models for a different reason: long-context memory capacity.
  • Per-token latency. AFD raises throughput per GPU, not speed per token. §7.2 reports TBT "comparable" to the baselines, and the ping-pong pipeline "may even incur additional latency". The paper's 150 ms TBT SLO is loose, and StepFun's Step-3 paper points this out.
  • Prefill. Prefill is already compute-bound. End-to-end gains including prefill are only up to 1.18× on homogeneous GPUs.
  • Small deployments and slow networks. You need at least E expert nodes plus the attention nodes, and M2N traffic every layer. In the paper's ablation, the M2N traffic only fit under the compute time (Tc < Tf) once NCCL was replaced by its own library. That is card 2's §5.
  • Fine-grained experts. One expert per node wastes GPUs at DeepSeek-V3's 2.55 GB per expert (our inference). Large colocated EP, as in the expert parallelism card, is the usual choice there.
