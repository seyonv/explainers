Checkpoint 1: splitting a dense model

Ties together collectives and interconnects, Megatron I, Megatron II and pipeline and data parallelism: how one dense model is spread over many GPUs, what each split sends over which wire, and how to choose a layout for Llama-3.1-70B on H100s.

How to use this page. Close the four cards. Answer each question in writing, in full sentences, before opening its Check. A wrong or shaky answer isn't a failure: it tells you exactly which section to reopen. The questions are mixed on purpose, so you have to work out which idea applies before you can answer. All-reduce latencies are the course's illustrative values (1 µs per ring hop, 28 µs across two nodes).

1 · Mixed retrieval

  1. which concept?A team moves Llama-3.1-70B from TP8 on one node to TP16 across two nodes "to halve latency". At batch 1 it gets about 5% faster; at a big batch it holds half as many 8k sequences and serves about half the tokens. Which two ideas explain the two halves?
    Check
    • batch 1: TP8 → TP16 saves only 2.63 ms of weight read, but all 160 all-reduces per step now pay cross-node latency (7.13 vs 7.52 ms in the model; the verdict flips if a cross-node all-reduce costs more than ≈ 30 µs)
    • big batch: 70B has only 8 KV heads, so past TP8 each KV head and its cache is replicated; TP16 fits 212 sequences vs TP8 × PP2's 424, and serves 6,811 vs 13,717 tok/s

    Missed it? Reopen Megatron II, "Why TP beyond one NVLink node rarely pays", and pipeline and data parallelism, "16 GPUs across two nodes".

  2. An nccl-tests all-reduce of 1 GB on 8 H100s reports algbw ≈ 257 GB/s. Your colleague says the NVLink links are only 57% used. Are they? Show the conversion.
    Check
    • busbw = algbw × 2(n − 1)/n = 257 × 1.75 ≈ 450 GB/s
    • that equals the 450 GB/s per-direction spec: the link is full
    • algbw is lower only because the ring sends each byte 1.75 times

    Missed it? Reopen collectives, "algbw vs busbw".

  3. At TP4 × PP2 on one node, Llama-3.1-70B takes 11.70 ms per token at batch 1, the same as TP4 alone, and serves fewer tokens per second than TP8 at a big batch. Explain both facts.
    Check
    • a token still passes stage 1 then stage 2; each stage is half as long, so the sum is TP4's step plus a 1 µs hop
    • in memory-bound decode each micro-batch re-reads its stage's weights: 17.6 GB twice per cycle (29.06 ms of HBM vs TP8's 23.80 ms) to save 1.77 vs 4.13 ms of all-reduces
    • on NVLink, all-reduces are cheap, so that trade loses

    Missed it? Reopen pipeline and data parallelism, "Why PP loses throughput here".

  4. which concept?An engineer splits the first MLP matrix of a GeLU transformer by rows across 2 GPUs, applies GeLU on each GPU, then sums. The outputs are slightly wrong. Which idea predicts this, and what's the right split?
    Check
    • a row split leaves each GPU with a partial pre-activation; GeLU is non-linear, so GeLU of the parts ≠ GeLU of the sum (the lab's error is 1.19)
    • split the first matrix by columns so each GPU has complete pre-activations for its columns, then the second by rows
    • one all-reduce after the block, and it carries the D-wide output, not the F-wide one (3.5× fewer bytes for Llama)

    Missed it? Reopen Megatron I, §3a.

  5. For Llama-3.1-70B at TP8, batch 1, each of the 160 all-reduces per step carries 16 kB. Which cost term dominates, and roughly what share of the 7.52 ms step do the all-reduces take?
    Check
    • the data term is ≈ 0.06 µs per all-reduce; the 14 ring hops × 1 µs (illustrative) dominate
    • 160 × 14 µs = 2.24 ms, about 30% of the step
    • so the message is deep in the latency-bound region (the NVLink crossover is 3.6 MB at n = 8)

    Missed it? Reopen collectives, "Bandwidth-bound or latency-bound", and Megatron II, worked example 3.

  6. which concept?A startup serves Llama-3.1-8B (16.06 GB in BF16) on an 8×H100 node as one TP8 group to handle many users cheaply. What would you change, and why?
    Check
    • the model fits one GPU, so run 8 independent replicas (data parallelism)
    • replicas need no communication and scale capacity linearly; TP only buys lower latency per request and pays 2 all-reduces per layer for it
    • one GPU failure then takes out 1/8 of capacity, not the whole node

    Missed it? Reopen pipeline and data parallelism, the decision table, and Megatron I, "Is tensor parallelism always the right split?".

  7. Megatron exchanges b × s values for its loss instead of b × s × v logits. What extra information does each GPU need so the split softmax stays exact, and why is it still tiny?
    Check
    • each GPU holds only a vocabulary slice of the logits
    • it needs the global per-token max, the global sum of exponentials, and the target token's logit from whichever GPU holds it
    • each is one value per token, so three all-reduces of b × s: 8,192 values instead of 419M in Megatron's runs

    Missed it? Reopen Megatron II, worked example 1.

  8. Why is FSDP-style sharding (gather each layer's weights before using it) a regression for decode, when it is standard in training?
    Check
    • decode is bound by reading every weight for a handful of tokens
    • FSDP moves those weights over links far slower than HBM: gathering 7/8 of 141.1 GB per token ≈ 274 ms vs 5.27 ms to read a TP8 shard
    • serving should move activations, not weights

    Missed it? Reopen pipeline and data parallelism, "What the sources say".

3 · Project: build your own layout model for 70B

What it reinforces: the all-reduce cost with its latency and bandwidth terms (collectives), 2 all-reduces per layer and KV heads per GPU (Megatron I), the step-time model (Megatron II), stages, replicas and KV room (pipeline and data parallelism).

Write a short Python function, without looking at labs/layouts.py, that takes a layout (TP degree, PP stages, DP replicas, bytes per weight) and returns batch-1 time per token and the number of 8k sequences that fit. Use the course's numbers: 141.1 GB of BF16 weights, 80 layers, D = 8,192, KV 327,680 B per token (2.684 GB per 8k sequence), 80 GB and 3.35 TB/s per H100, 450 GB/s NVLink, an all-reduce of 2(n − 1) hops × 1 µs plus 2(n − 1)/n × message ÷ 450 GB/s, and 1 µs per in-node pipeline hop.

  1. Reproduce. TP8 at batch 1, including one 8k sequence's KV. Then TP4 × PP2.
  2. KV room. Sequences of 8k that fit for TP8 (one replica) and for TP4 × DP2 (per replica).
  3. Extend. TP2 × PP4 on the same 8 GPUs at batch 1. Before computing, predict whether it's faster or slower than TP4 × PP2 and why.
  4. Break it. Raise the hop latency until TP8 stops beating TP4 at batch 1 (weights only, no KV). Find the break-even.
Done when: your function reproduces the card values in step 1 and step 2 within 1%, you have a TP2 × PP4 number with a one-sentence explanation, and a break-even hop latency with its derivation. Then compare with the check.
Check: the numbers (computed with the course's formulas)
  • TP8: 17.64 GB ÷ 3.35 TB/s = 5.27 ms + KV 0.10 ms + 160 × 14.06 µs = 2.25 ms → 7.62 ms (131 tok/s). TP4 × PP2: each stage 5.37 ms of HBM + 80 × 6.05 µs = 5.85 ms; two stages + 1 µs → 11.70 ms.
  • KV room: (640 − 141.1) GB ÷ 2.684 GB = 185.9 → 185 sequences for TP8; (320 − 141.1) ÷ 2.684 = 66.6 → 66 per TP4 replica, 132 for both.
  • TP2 × PP4: each stage reads 17.64 + 0.34 GB (5.36 ms) and does 40 two-GPU all-reduces (≈ 0.08 ms) → 5.45 ms; 4 stages + 3 hops ≈ 21.8 ms (≈ 46 tok/s). Slower: the same bytes per GPU, but only 2 GPUs' bandwidth works on the token at any moment.
  • Break-even: TP8 − TP4 = (5.27 − 10.53) ms + 160 × (14 − 6) × α = 0 → α ≈ 4.1 µs per hop. Above that, TP4 wins batch 1.
