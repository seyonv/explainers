Disaggregation in production: Splitwise, Mooncake and Dynamo

Also called P/D disaggregation, disaggregated serving, split-phase serving, or xPyD serving. This card skims three systems that came after the idea: Splitwise (Patel et al., Microsoft + UW, ISCA '24, arXiv 2311.18677 v2) §III–VI, a three-line recap of Mooncake (course 4 has two cards on it), and NVIDIA Dynamo (README, docs and the March 2025 launch blog, fetched 2026-09-24). It ends with Kiely's Inference Engineering §4.4 and §5.5 on when splitting is worth it. The idea itself, and DistServe's version of it, are in DistServe I and DistServe II. This card doesn't repeat them.

In one breath

Once prefill and decode run on separate GPUs, three practical questions follow. Which hardware should each phase get? Splitwise's answer is that the token phase doesn't need the newest or most power-hungry GPU. Where does the KV cache live? Mooncake's answer is a shared pool in every node's spare DRAM and SSD. How does a real cluster decide, request by request, where work goes and how many GPUs each pool gets? Dynamo's answer is a router that scores cache hits against load, and a planner that resizes the pools. The honest answer to the fourth question, whether to do this at all, is often no.

Splitwise: characterize the two phases first §III, Llama2-70B and BLOOM-176B on DGX-A100 and DGX-H100

Splitwise calls the phases the prompt phase and the token phase, not prefill and decode. It profiles both on production traces from two Azure services (coding and conversation, 20 minutes each, November 2023) and draws seven "insights" before it designs anything. The four that drive the design:

Four cluster designs, plus two baselines

A Splitwise cluster has a prompt pool, a token pool and a mixed pool that absorbs overflow and runs both phases when load is high. A two-level scheduler runs it. The cluster-level scheduler routes each request to the prompt and token machines with the fewest pending tokens (join-the-shortest-queue) and picks both at arrival, so the KV transfer can start early. The machine-level scheduler batches: prompts first-come-first-served up to 2,048 tokens, token requests until memory is full.

Layer-wise KV transfer over InfiniBand §IV-C, §VI-A

The prompt machine has to send the KV cache it just built to the token machine. Sending it after the whole prompt phase (serialized) puts the full transfer on the critical path. Splitwise instead sends each layer's KV as soon as that layer finishes (layer-wise), overlapping the transfer with the next layer's compute. Only the tail is exposed. The implementation is on vLLM, using MSCCL++'s zero-copy one-sided put over InfiniBand (200 Gbps on the A100 setup, 400 Gbps on the H100 one), with a semaphore per request. Prompts under 512 tokens on H100 still go serialized, because their KV is small.

Mooncake, in three lines course 4 has the full treatment

KV-centric. Kimi's serving system (Moonshot AI; FAST '25) splits prefill and decode pools and pools every node's spare CPU DRAM and SSD into one RDMA-connected KV store, so a reused prefix is loaded instead of recomputed. Mooncake I shows that the needed bandwidth is only a few GB/s.

Scheduling around the cache. The Conductor sends each request to the prefill node with the earliest estimated first token (transfer + queue + uncached prefill), then streams KV layer by layer into the decode node's DRAM, and rejects requests up front if the SLOs can't be met. That's Mooncake II.

Ratio. In FAST '25 §5.5 (16 nodes, synthetic trace, TTFT ≤ 10 s, TBT ≤ 100 ms) effective capacity peaks when "the P/D ratio is approximately 1:1". Mooncake keeps the ratio fixed and switches node roles only "when significant load fluctuations occur". Compare DistServe's 2 prefill : 1 decode in its Fig 1 and the Scaling Book's P ≈ 3G. The ratio comes from the workload, not from the method.

Dynamo's own docs on when disaggregation doesn't pay

"Disaggregation changes where compute and memory are consumed; it does not make either phase free."disaggregated-serving doc, "Performance Characteristics"
  • "At low concurrency, an aggregated worker often avoids transfer and pool-fragmentation overhead."
  • "When decode KV capacity is the bottleneck, adding prefill replicas can reduce total serving capacity unless the latency benefit compensates for the GPUs removed from decode."
  • The prefill/decode boundary depends on model, quantization, GPU, backend and request lengths, and "should not be encoded as a universal token threshold".

Kiely's rule of thumb: when to split Inference Engineering §5.5.2, pp.149–150

"You should reach for disaggregation only when" all three hold. If 1 or 2 fails, "you're likely wasting money on extra hardware for minimal performance gains". If 3 fails, "you may be better off using the extra GPUs to scale replicas horizontally".

100e6 / 86,400 s = 1,157 tok/s; 1e9 / 86,400 = 11,574 tok/s; 608 / 168 = 3.6 (our arithmetic). By this rule our 70B running example wouldn't be disaggregated, though Dynamo's launch blog still reported more than 2× for Llama 70B on Hopper at ISL/OSL 3K/50, a prefill-heavy shape. Kiely's "textbook workload": "Tons of tokens, mostly prefill, on a trillion-parameter LLM", such as a frontier model behind a code editor. Mooncake reports "over 100 billion tokens daily" for Kimi.

Conditional disaggregation (§5.5.1): the request goes to the decode engine first. If its input "is already cached or is short enough to handle locally", the decode engine prefills it itself; otherwise it hands off to a prefill engine. Kiely: "Conditional disaggregation is better for real-world traffic." Dynamo implements it with thresholds on "ISL after prefix cache and prefill queue size" (§5.5.3). The two new bottlenecks, per Kiely, are prefill-queue growth (lower the local-prefill threshold or shift xPyD toward P) and running out of KV on decode engines (quantize the KV or offload it).

The words people use

TPOT DistServe

Time per output token: a request's average time per token after the first. One number per request.

TBT Splitwise, Mooncake

Time between tokens: each gap in the stream, so P99 TBT catches one stalled token that an average hides. Splitwise's SLO: P50/P90/P99 at 1.25/1.5/5× an unloaded A100.

ITL / TPS Dynamo, vLLM / Kiely

Inter-token latency is the same gap as TBT. Kiely uses TPS, "tokens per second per user" for latency or "total TPS" for throughput. "An ITL of 10 milliseconds equates to 100 tokens per second per user."

Goodput means three things

DistServe: the highest request rate per GPU that meets an SLO-attainment target, found by search. vLLM bench --goodput: requests per second that met the SLOs at the load you offered. Networking: useful bits per second. Splitwise never says goodput, but its "throughput" (the highest rate at which every SLO holds) is close to DistServe's.

How the production versions differ from the paper idea

✗ Disaggregate every request

Short or already-cached prompts pay a KV transfer and a second queue for nothing. Kiely and Dynamo both prefill those locally on the decode engine (conditional disaggregation).

✗ Size xPyD once

The best ratio moves with the traffic: 1:1 for Mooncake's trace, 2:1 in DistServe's Fig 1, 3:1 in the Scaling Book. A fixed split lets the prefill queue grow or decode run out of KV. Dynamo's planner resizes both pools.

✗ Route on load alone, or on cache alone

Load-only recomputes prefixes that another worker already holds. Cache-only piles work on the hot worker. Mooncake's Conductor and Dynamo's router both add cache hits and load into one cost.

✓ Split, route by cache and load, resize

Split only the requests that benefit, pick workers by cost, move KV layer by layer or non-blocking so it hides under compute (Splitwise: 0.8% of E2E), and put each phase on the cheapest hardware that meets its SLO.

So should you disaggregate?

Usually not at first. Every source here says so in its own words. Below roughly 100M–1B tokens a day, under about 100B parameters, or with short prompts, a pool of ordinary replicas with chunked prefill and prefix caching wins: no transfer, no idle prefill memory, no second queue (Kiely §5.5.2; Dynamo's "at low concurrency" note; DistServe §7). Kiely's §4.4 is blunter about Dynamo itself: "Unless you're operating with enough volume for disaggregation and KV-aware routing to matter, Dynamo will be unnecessary work and excess overhead."

Treat the big multipliers carefully. Splitwise's abstract pairs don't match its §VI text, and Dynamo's 30× was a projection that bundles FP4, wide EP and a rack-scale NVLink domain. The effects the sources do measure are smaller and more useful: layer-wise transfer costs 0.8% of E2E, and a token phase on A100s costs the same or less per request than on H100s, at 1.4–1.7× the TBT (Table IV: 40/28, 52/31).
