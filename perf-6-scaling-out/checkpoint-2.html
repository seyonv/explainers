Checkpoint 2: when to split prefill from decode

Ties together DistServe I, DistServe II, disaggregation in production and pipeline and data parallelism: why prefill and decode fight on one GPU, how a split fleet is sized, placed and routed, and when splitting isn't worth it.

How to use this page. Close the four cards. Answer each question in writing, in full sentences, before opening its Check. A wrong or shaky answer isn't a failure: it tells you exactly which section to reopen. The questions are mixed on purpose, so you have to work out which idea applies before you can answer.

1 · Mixed retrieval

  1. which concept?A colocated, prefill-first server's P90 TTFT stays around 35 ms as load rises, but past 20 req/s more and more requests miss a 10 ms TPOT target. Which concept explains the pattern, and what are your two options?
    Check
    • prefill–decode interference: each waiting prompt runs first and every decoding stream sits through it, so TPOT, not TTFT, breaks (the card's sim: 93.3% attainment at 20 req/s, 54.3% at 25)
    • option 1: chunked prefill, which smooths the stalls but doesn't remove them
    • option 2: separate prefill and decode instances, each sized for its own SLO

    Missed it? Reopen DistServe I, "Fig 1 again, for the running example".

  2. A prefill-only GPU sustains 6 req/s within the TTFT SLO, a decode-only GPU 12 req/s within the TPOT SLO, and a colocated GPU 3 req/s within both. What is the best per-GPU goodput with a small split, and the gain?
    Check
    • 2 prefill + 1 decode: min(2 × 6, 12) = 12 req/s on 3 GPUs = 4.0 req/s per GPU
    • 4P2D gives the same 4.0; 3P2D only 3.6, 1P1D 3.0
    • 4.0 ÷ 3 = 1.33× over colocation, before KV transfer and rounding

    Missed it? Reopen DistServe I, "§1 Fig 1: the 2.1× in four numbers".

  3. which concept?A cluster has NVLink inside nodes but only 25 Gb/s between them. OPT-175B's prefill and decode copies together need 700 GB, more than one node's 640 GB. How can the KV cache still move only over NVLink?
    Check
    • KV of layer ℓ only goes to layer ℓ of the decode instance
    • cut both instances into the same pipeline stages and put matching prefill and decode stages on the same node (instance segments, Alg 2)
    • DistServe measured transfer at under 0.1% of latency, with 95% of requests under 30 ms

    Missed it? Reopen DistServe II, "Algorithm 2".

  4. At load RD = 0.4 with an intra-op speedup K = 1.8, which gives lower average TTFT for prefill on 2 GPUs: two pipeline stages or tensor-style splitting? Where is the crossover for this K?
    Check
    • intra-op: 1/1.8 + 0.4 / (2 × 1.8 × 1.4) ≈ 0.63 D
    • inter-op: 1 + 0.4 / (4 × 1.6) ≈ 1.06 D, so intra-op wins at this load
    • the crossover moves right as K rises: about RD ≈ 1.43 at K = 1.8 (0.94 at K = 1.5)

    Missed it? Reopen DistServe I, "§3.1 The prefill instance".

  5. which concept?A router sends a request whose system prompt is cached on worker A to worker B, which holds nothing. The on-call engineer calls it a bug. Which mechanism explains it, and when is it right?
    Check
    • KV-aware routing scores prefill cost (reduced by cache hits) plus decode load; the lowest total wins
    • if A is busy (e.g. 50 active prefill and 300 decode blocks against B's 150), A can cost more even with a 30-block cache hit: 360 vs 190 at scale 1
    • neither pure load routing nor pure cache routing; Mooncake's Conductor makes the same trade

    Missed it? Reopen disaggregation in production, the Dynamo router row and its cost formula.

  6. Why can Splitwise put the token phase on A100s instead of H100s with little loss, and what does it measure to back that up?
    Check
    • the token phase is memory-bound, so the H100's extra compute barely helps it
    • Table IV: the H100 halves TTFT (185 → 95 ms coding) but TBT only improves 40 → 28 ms (conversation)
    • cost per request is lower on A100 ($2.4 vs $3.6 conversation), with equal or lower energy

    Missed it? Reopen disaggregation in production, the Splitwise section and Table IV.

  7. In the card's Llama-3.1-8B lab, disaggregation is 0.83× on code prompts but 2.85× on summarization. What about each workload decides it?
    Check
    • code: 171-token prompts, so a prefill costs about one decode step; splitting adds rounding and queueing for nothing
    • summarization: 1,738-token prompts against a 10 ms TPOT; each ~28 ms prefill would freeze decoders for about three TPOT budgets
    • so the gain grows with prompt length and SLO tightness

    Missed it? Reopen DistServe II, "Alg 1 in miniature" and "When not to disaggregate".

  8. How does Splitwise hide most of the KV transfer, and how much of end-to-end latency is left?
    Check
    • it sends each layer's KV as soon as that layer finishes, overlapping the rest of the prompt's compute
    • only the tail is exposed (~5 ms on H100, ~8 ms on A100)
    • 0.8% of end-to-end, vs up to 3% if sent after the whole prompt

    Missed it? Reopen disaggregation in production, "Layer-wise KV transfer".

3 · Project: plan a prefill/decode fleet on paper and in code

What it reinforces: the M/D/1 prefill model and goodput (DistServe I), replication and KV transfer (DistServe II), production thresholds (disaggregation in production), and TP vs PP as intra-op vs inter-op (pipeline and data parallelism).

  1. Simulate the queue. In about 40 lines of Python, simulate a single-server FCFS queue with Poisson arrivals and deterministic service D = 1. Add two variants: a two-stage pipeline (a request enters every D/2, latency D) and a K-times-faster server with capacity K. Run 200,000 requests at RD = 0.5 with K = 1.5 and compare with Eq 1–3.
  2. Find the crossover. Sweep RD and find where the two 2-GPU layouts tie for K = 1.5 and K = 1.8.
  3. Size a fleet. With the DistServe II lab's goodputs for a Llama-3.1-8B chatbot (prefill 68.4 req/s per GPU, decode 108.4, colocated 38.1), size both designs for 400 req/s and for 10 req/s.
  4. Price the move. For Llama-3.1-70B (320 KiB per token), compute the KV transfer for an 8,192-token prompt over one NVLink link and one IB link, and compare with a 5.27 ms TP8 decode step.
  5. Decide. Apply Kiely's three conditions to this 70B service at 500M tokens a day with 8k prompts and 200-token answers.
Done when: your simulation matches Eq 1–3 within 1%, you have two crossovers, four fleet sizes, two transfer times, and a verdict with the condition that decided it. Then compare with the check.
Check: the numbers (Eq 1–3, the cards' lab values and our arithmetic)
  • RD = 0.5: one GPU 1.500 D, inter-op 1.083 D, intra-op 0.833 D (the card's Monte Carlo: 1.508 / 1.084 / 0.835).
  • Crossovers: RD ≈ 0.94 at K = 1.5 and ≈ 1.43 at K = 1.8.
  • 400 req/s: ⌈400/68.4⌉ = 6 prefill + ⌈400/108.4⌉ = 4 decode = 10 GPUs vs ⌈400/38.1⌉ = 11 colocated. 10 req/s: 1 + 1 = 2 GPUs vs 1 colocated: rounding eats the gain at small scale.
  • 8k prompt of 70B: 2.68 GB → 5.97 ms over 450 GB/s NVLink (about one TP8 step), 53.7 ms over 50 GB/s IB.
  • 500M tokens a day ≈ 5,787 tok/s (volume passes), prefill-heavy (8k in, 200 out, passes), but 70.55B parameters is under Kiely's 100B: a borderline case. Start with replicas and chunked prefill, and use conditional disaggregation if TPOT tails appear; the Dynamo blog's 70B result (3K/50) shows prompt-heavy shapes can still pay.
