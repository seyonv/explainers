Pipeline and data parallelism when serving

Also called PP (pipeline model parallelism, inter-layer or inter-op parallelism) and DP (replicas, horizontal scaling), usually combined with TP as layouts written like "TP8PP2". This card follows Kiely's Inference Engineering §5.4 (pp. 142–147), the Scaling Book Part 7 on sharding for generation, DistServe §3.2, Megatron-LM §2.3 and Sarathi-Serve §3.3. The Llama-3.1-70B on H100 numbers are our ceiling model (labs/layouts.py), not measurements.

Prime · 2 minutes before you read

The problem: Tensor parallelism makes a token faster but can't leave the node, and a model that already fits wastes GPUs on all-reduces. You need the other two ways to use more GPUs, and a rule for which layout serves the most tokens at the latency you promised.

Where it fits: Fourth card, closing the dense-model block. Megatron II gave the TP step-time model; this card adds pipeline stages and replicas to it and compares every layout of 70B on 8 and 16 H100s. DistServe and the sizing card reuse these layouts.

In one breath

A pipeline stage owns a contiguous block of layers. Each token still passes through every stage one after another, so pipelining adds throughput, not speed: it lets more GPUs hold one model while sending only a single activation between stages. Data parallelism runs independent replicas that never talk to each other. Tensor parallelism is the one split that makes each token faster, and it pays for that with two all-reduces per layer. When serving, you pick TP for per-token latency, PP only to cross the slow link between nodes, and DP for everything else.

Four ways to place one 70B model on an 8×H100 node

Each box is one GPU. "¼ of L1–40" means a quarter of every weight matrix in layers 1–40 (tensor-split across the dashed group). Dashed groups are one TP group. TP4 × PP2 is still one replica; the DP layouts are independent copies. Llama-3.1-70B is 141.1 GB in BF16, and 70.6 GB in FP8.

Everyday version: a kitchen of 8 cooks making soup. TP: all 8 chop every ingredient together and have to shout after each step (all-reduce). PP: 4 cooks do the first half of the recipe and pass the pot to the other 4 cooks. DP: two separate kitchens, each with its own recipe book.

How a pipeline behaves at inference time

No backward, so a smaller bubble. Megatron-LM §2.3 sets up the choice: layer-wise pipelining (GPipe) "suffers from pipeline bubbles that reduce efficiency", which is why Megatron splits inside each layer instead. In training the bubble comes from the forward and backward passes; DeepSeek-V3's Table 2 puts 1F1B's bubble at (PP−1)(F+B). Inference has no B. A serving pipeline also never really drains: as soon as micro-batch A leaves the last stage with its new token, its next decode step re-enters stage 1. So the bubble left is fill/drain, which happens once, plus imbalance between micro-batches (our inference from these sources; Sarathi-Serve measures the imbalance part).

Balanced stages: splitting a step across p stages makes each stage p times shorter, and the token still visits all of them. So latency ≈ the TP-only step plus hops. Throughput grows because p micro-batches keep all stages busy at once.

Imbalance is the real bubble (Sarathi-Serve §3.3). Micro-batches aren't equal: one may carry a new prompt's prefill, and decode cost grows with each request's context. The paper's example: for Falcon-180B, "a single prompt of 4k tokens takes ≈ 1150 ms to execute compared to a decode only iteration with batch size 32 which would take about ≈ 200 ms", and interleaving them "could result in a bubble of ≈ 950 ms". Our 2-stage replay of those two numbers (we treat them as per-stage times, which is how the paper's 950 = 1,150 − 200 works out):

Green: a micro-batch running on a stage (A0 = micro-batch A, iteration 0). Grey dashed: idle. A micro-batch can't start its next iteration until it leaves stage 2, because it needs that token. Uniform: 1,400 ms for 3 iterations, each stage idle 200 ms (fill or drain). Mixed: 3,300 ms, and stage 1 sits idle for an extra 950 ms. Sarathi fixes this with chunked prefill, which makes micro-batches uniform (course 5, Sarathi-Serve I).

Worked example: Llama-3.1-70B on 8 H100s (our model)

A decode step costs max(HBM bytes ÷ 3.35 TB/s, FLOPs ÷ peak) + 160 all-reduces + hops, with no overlap. An all-reduce inside a node costs 2(n−1) ring hops × an illustrative 1 µs (14 µs at TP8, 6 at TP4, 2 at TP2; the shared value from the collectives card) plus 2(n−1)/n · message ÷ 450 GB/s. For "big batch", every sequence is at 8,192 tokens (2.68 GB of KV each), and we pack in as many as the HBM left after weights allows. We use full HBM and link speeds, so treat these numbers as ceilings.

  • Does FP8 TP2 fit? Yes: 70.6 GB ÷ 2 = 35.3 GB per GPU, leaving 44.7 GB each, so 89.4 GB of KV per replica = 33 sequences of 8k (BF16 KV). Activation memory and engine overhead would take a little of that. It reads the same 35.3 GB per GPU per step as BF16 TP4, and its 2-GPU all-reduce pays only 2 hops, so it is slightly faster at batch 1 (11.26 vs 11.70 ms) with half the GPUs per replica.
  • Why PP loses throughput here. In memory-bound decode, each micro-batch re-reads its stage's weights. TP4 × PP2 reads the 17.6 GB twice per cycle (29.06 ms of HBM time vs TP8's 23.80 ms) to save some all-reduce time (1.77 vs 4.13 ms). That's a bad trade inside a node, where NVLink makes all-reduces cheap.
  • Why DP loses throughput here too. Every replica holds its own copy of the weights. Two copies of 141.1 GB leave room for 132 sequences; one copy leaves room for 185. At 8k context, KV room decides the batch, so TP8 serves the most tokens per second. The replicas win on per-user speed at full load (24.3–25.3 vs 27.9 ms TPOT): each replica runs a smaller batch and does fewer, cheaper all-reduces. At 2k context the gap shrinks: FP8 TP2 × DP4 reaches 21.3k tok/s against TP8's 22.1k (lab "try this").

Cross-node all-reduce = illustrative 28 µs (2× the in-node TP8 value, collectives card) + 2 × message ÷ 400 GB/s per node; a cross-node PP send pays 2 µs. The Scaling Book: past one node, an AllReduce costs about 2 × bytes ÷ node egress, 400 GB/s on H100 (8 NICs × 50 GB/s). So in our model the cross-node bandwidth isn't what hurts TP16.

  • At batch 1, the winner depends on a number nobody publishes. TP16 halves the bytes per GPU (2.73 ms), but pays 160 cross-node all-reduce latencies (4.49 ms). It beats TP8 × PP2 only if one cross-node all-reduce costs under 30.4 µs; at our illustrative 28 µs it just wins (7.23 vs 7.62 ms). At 40 µs it takes 9.15 ms. The one measurement in our sources is on a slower network: Sarathi-Serve ran Falcon-180B on 2 nodes × 4 A100s over 100 Gbps Ethernet and saw TP8's median decode latency "∼ 2× higher" than TP4-PP2, "due to cross-node all-reduces" (§5.3).
  • At a big batch, TP16 loses on memory, not network. Llama-3.1-70B has only K = 8 KV heads, so beyond TP8 the KV cache can't be split further; pairs of GPUs hold the same heads. TP16 fits 212 sequences to TP8 × PP2's 424, and serves half the tokens per second. (The Scaling Book's fix is to shard KV along the batch dimension instead, at the cost of two extra AllToAlls per attention layer.)
  • If the model already fits one node, use replicas. TP8 × DP2 gets within about 3% of PP's throughput (13,252 vs 13,717 tok/s) with better TPOT (27.9 vs 30.9 ms), no cross-node traffic, and a failure only takes down half the capacity. Kiely: unless the model and KV cache need multiple nodes, "you're often better off using the extra nodes for horizontal scaling across replicas, or for disaggregated serving."

What the sources say

  • Kiely §5.4 (pp. 143–147). His table rates PP "Not recommended due to poor latency and utilization from step-by-step pipeline" (the row mentions a backward pass, which inference doesn't have). "Tensor Parallelism should be your default strategy for multi-GPU model inference." "Pipeline Parallelism is only used for multi-node inference." Across nodes, for dense models: "use Tensor Parallelism within each node and Pipeline Parallelism between nodes (e.g., TP8PP2)".
  • Scaling Book Part 7, generation. "FSDP is impossible": decode is limited by reading weights from HBM, and moving them over links "orders of magnitudes slower than HBM" is a regression. "We want to move activations rather than weights." For 70B on 8 GPUs (our recomputation): all-gathering 7/8 of 141.1 GB per token takes 274 ms, vs 5.27 ms to read a TP8 shard from HBM. On DP: "pure data parallelism is unhelpful because it replicates our parameters and doesn't help us load parameters faster. You're better off spinning up multiple copies of the model instead." In other words, use replicas, not a synchronized DP group (course 2, sharding prefill vs generation).
  • DistServe §3.2, the decode rule. At large batch (13B, Fig 5), "intra-op parallelism reduces latency with diminishing returns" while "inter-op parallelism can almost linearly scale the throughput. Hence, when the TPOT SLO is stringent, intra-op parallelism is essential to reduce TPOT… Beyond this, inter-op parallelism is preferable to enhance throughput linearly." And when the model fits one GPU, "replication is a competitive option". Intra-op is DistServe's name for TP-style splits; inter-op is its name for pipeline stages.

How it differs from related ideas

✗ PP inside a node for speed

A token still visits every stage in turn, so TP4 × PP2 takes 11.70 ms per token, the same as TP4 alone. It also re-reads weights once per micro-batch.

✗ TP across InfiniBand

160 cross-node all-reduce latencies per token, and past 8 KV heads the cache stops splitting. Half the batch of TP8 × PP2 at 8k context.

✗ FSDP / synchronized DP for decode

Moves weights instead of activations: 274 ms per token to gather 70B vs 5.27 ms to read a shard. A classic regression when training settings leak into serving.

✓ TP in the node, PP or replicas across

TP buys latency where links are fast. PP crosses the slow link with a single activation per stage. Replicas add capacity with no communication at all.

Is PP ever the right call inside a node, and is TP8 always best?

PP inside a node makes sense only when TP can't run there: Kiely notes that L4/L40-class GPUs without NVLink "must be used individually or via inefficient parallelism methods like Pipeline Parallelism" (p. 80). Otherwise use it just to cross nodes.

TP8 winning both columns in our table depends on the model's assumptions: 8k contexts, no compute/communication overlap, and an illustrative 1 µs per ring hop. At 5 µs per hop, FP8 TP2 becomes the fastest layout on the node (lab "try this"). Real engines lose efficiency as TP grows (smaller matmuls, synchronization across more GPUs), and the lab's "try this" shows DP gaining ground at shorter contexts. Replicas also bring things this model ignores: independent failures, rolling upgrades, and simpler routing. Pick the layout per workload, and when prefill and decode want different layouts, split them onto different GPUs (DistServe I).

Understand and remember

  • A pipeline stage owns a contiguous block of layers → a token still visits every stage in turn → latency ≈ sum of the stages + hops ≈ the TP-only step → PP adds memory and throughput (p micro-batches keep stages busy), never speed: TP4 × PP2 takes 11.70 ms, the same as TP4 alone
  • A serving pipeline has no backward and never drains → the bubble left is fill/drain plus imbalance between micro-batches → one long prefill next to short decodes idles the other stage (≈ 950 ms in Sarathi's Falcon-180B example) → chunked prefill makes micro-batches uniform and removes it
  • PP sends one activation per stage boundary instead of 160 all-reduces per step → it is the cheap way to cross the slow inter-node link → TP8 in each node × PP2 across nodes; TP16 over IB pays 160 cross-node latencies and, past 8 KV heads, can't split the cache (212 vs 424 sequences, 6,811 vs 13,717 tok/s)
  • Replicas share nothing → each holds its own weights and KV → no communication and a small blast radius, but each copy eats memory that could hold KV → at 8k context one TP8 copy holds 185 sequences vs 132 for two TP4 copies → KV room decides the batch, so layout choice depends on context length
  • detail that matters In memory-bound decode each micro-batch re-reads its stage's weights → TP4 × PP2 reads 17.6 GB twice per cycle (29.06 ms of HBM vs TP8's 23.80 ms) to save some all-reduce time (1.77 vs 4.13 ms) → a bad trade inside a node where NVLink is cheap
  • detail that matters FSDP moves weights instead of activations → gathering 7/8 of 141.1 GB per token takes 274 ms vs 5.27 ms to read a TP8 shard → synchronized DP is a training setting that regresses decode

5 · Predict commit to an answer before revealing

Put 70B on 8 H100s as TP2 × PP4 (four stages of two GPUs). Each GPU still holds 17.6 GB. What is the batch-1 time per token, roughly, and why? Commit first.

Reveal

About 21.8 ms (≈ 46 tok/s). Each stage reads 17.64 GB of weights plus 0.34 GB of KV (5.36 ms) and does 40 two-GPU all-reduces (≈ 0.08 ms), so ≈ 5.45 ms; the token passes all four stages plus 3 hops: 4 × 5.45 ≈ 21.8 ms. The same bytes per GPU as TP8, but a token only uses 2 GPUs' bandwidth at a time, so it's almost 3× slower than TP8's 7.62 ms.
