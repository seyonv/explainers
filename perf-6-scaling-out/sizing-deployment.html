Sizing a deployment: how many GPUs, and which layout

Also called capacity planning, GPU sizing or "VRAM math", and in vLLM the knobs gpu_memory_utilization, tensor_parallel_size and pipeline_parallel_size. This card closes course 6. It follows Kiely's Inference Engineering §5.4 (pp. 142–148) and §7.3.3 (pp. 196–197) and the vLLM docs. It reuses the step-time model and layout numbers from the pipeline card. Every GPU count, step time and dollar figure below is our calculation (labs/sizing.py), not a measurement.

In one breath

Size a deployment in four passes. Memory: the weights plus every user's KV cache must fit in the GPUs' usable memory, which sets the smallest replica. Traffic: the number of users you must hold at once, and the tok/s each must get, set how many replicas you need. Layout: use TP inside a node for speed, replicas for everything else, and PP or EP only when one model has to span nodes. Failure: one dead GPU takes its whole TP or EP group offline, so many small replicas degrade gracefully where one big group falls over.

Minimum "fits" is never the answer. Pass 2 is.

Pass 2: how many GPUs for my traffic? (our worked example)

The workload: Llama-3.1-70B in FP8, 500 concurrent chat users, 20 tok/s each, 4k context. Two requirements fall out. Memory: all 500 KV caches must be resident. Speed: each replica's decode step must take ≤ 1/20 s, because a user gets one token per step. Each replica's batch is the smaller of "what fits" and "what still meets 50 ms". The decode step is the pipeline card's model: max(HBM read, FLOPs) + 160 all-reduces, each costing an illustrative 2(n−1) × 1 µs of latency plus ring bytes ÷ 450 GB/s.

From labs/sizing.py. Every option passes the 50 ms target with room to spare, so memory decides the count here. H200 TP8 (1 replica of 720 users, 8 GPUs) isn't shown: one failure there takes all 500 users down.

  • The answer: 16 H100s (TP4 × 4 or TP8 × 2), or 8 H200s (TP2 × 4). Each H200 holds 1.76× the memory of an H100, and here memory is the constraint.
  • This is a floor. It sizes decode only. Prefill for new turns, bursts above 500, and uneven context lengths all come on top. On the other side, real chats average less than their full 4k, which frees KV. Planning for all 500 at full length is conservative on memory and optimistic on everything else.
  • The speed target rarely binds for chat. 20 tok/s is a 50 ms TPOT. Even TP8's 386-user batch runs at 28 ms. Ask for 40 tok/s (25 ms) and TP8's batch has to drop from 386 to 333 (lab "try this"). Speed targets start deciding the layout at roughly that point.

Pass 3: which layout?

Our summary of Kiely §5.4 and the course's earlier cards. Green: the answer at each rung.

  • Kiely, p. 144: "Tensor Parallelism should be your default strategy for multi-GPU model inference." p. 143: "Pipeline Parallelism is only used for multi-node inference." p. 147: over InfiniBand, "For dense models, use Tensor Parallelism within each node and Pipeline Parallelism between nodes (e.g., TP8PP2)", and "For MoE models, TP8PP2 will generally offer lower latency per user and EP16 will yield higher overall system throughput." pp. 147–148: if the model doesn't need several nodes, "you're often better off using the extra nodes for horizontal scaling across replicas, or for disaggregated serving."
  • vLLM's docs (Parallelism and Scaling) give the mechanical rule: single node, "Set tensor_parallel_size to the number of GPUs per node"; multi-node, TP = GPUs per node and pipeline_parallel_size = the number of nodes; and "Increase the number of GPUs and nodes until there is enough GPU memory for the model." That's advice on making the model fit, not on cost. Pass 2 shows TP4 × 4 needs no more GPUs than TP8 × 2, and it survives failures better.
  • TP16 across two nodes is a close call, not a clear loss. With the illustrative 28 µs cross-node all-reduce it narrowly wins batch-1 latency (7.23 vs 7.62 ms; break-even ≈ 30 µs). But only 8 KV heads limit its KV room, so it serves 426 tok/s per GPU against TP8 × PP2's 857 (pipeline card).

Pass 4: the blast radius of one failure

A TP or EP group runs in lockstep: every layer waits on an all-reduce or all-to-all from every member, so one dead GPU stops the whole group. Kiely (§7.3.3, from Llama 3's 419 unexpected interruptions on ~16k H100s over 54 days): "approximately one failure per 50,000 GPU-hours", and "running a single node of eight GPUs for inference for an entire year is over 70,000 GPU-hours". That's 8 × 8,760 = 70,080, or 1.40 failures per node-year. The mean time between failures of a group shrinks with its size:

Why it beats the alternatives

✗ Size by weights only

"70B FP8 fits on one H100" is true, with 3.0 GB of KV: 2 users at 4k. Serving 500 users that way takes 250 GPUs.

✗ One giant TP or EP group

Every extra GPU in the group shortens its mean time between failures (16 GPUs: 130 days; 320: 6.5 days), and one failure takes everything down. TP16 over InfiniBand also halves tok/s per GPU.

✗ Size by total tok/s alone

10,000 tok/s ÷ 6,626 per node says "2 nodes" whether it's 500 users × 20 tok/s or 250 × 40. Check memory and TPOT and the second case needs only 8 H100s (TP4 × 2). Users held at once decide the count, not tok/s.

✓ KV first, smallest TP, then replicas + 1

Hold every user's KV, meet the TPOT target, and use the smallest TP that does both. Add one replica as a spare. Here that's TP4 × 5 = 20 H100 at $2.22/M, degrading to 99.6% when a GPU dies.

Is "smallest TP × many replicas" always right?

No. Use bigger groups when:

  • Per-user speed is the product. TP8 cuts batch-1 latency by a third against TP4 (7.62 vs 11.70 ms). If you sell 100+ tok/s per user, that's the layout, and you pay for the blast radius with spare nodes.
  • Long contexts or a huge MoE. At 8k context, TP8's single weight copy leaves more room for KV and serves the most tokens per dollar. For DeepSeek-V3-class models at high volume, big EP units (DeepSeek's 144 GPUs) keep every expert's batch large. Their failure exposure is the price of that throughput.
  • Traffic is bursty. Then the question becomes autoscaling (how fast a new replica loads its weights), and a static count isn't enough. Course 7 covers it.

Two caveats on the blast-radius argument. Kiely: "GPU health is a node-level concern. When a single GPU fails, other GPUs on the node often fail next or need to be taken offline". So a TP2 replica's neighbours keep serving only until you drain and cordon the node, and spares should be counted in nodes too (our inference). And every number here is a ceiling from a model with illustrative all-reduce latency. The rented-node script below measures the real ones.
