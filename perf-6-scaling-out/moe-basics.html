Mixture of experts: routers, top-k and imbalance

Also called MoE, sparse MoE (SMoE), "total vs active parameters"; the router is also called the gate or gating network, and Switch Transformer calls its top-1 version a "Switch layer". This card opens the router: Shazeer et al. 2017 §2.1 (noisy top-k gating), Switch Transformer §2 (top-1, expert capacity, dropped tokens, the auxiliary loss, Table 1), Mixtral §2 (8 experts, top-2) and DeepSeek-V3's sigmoid gate, then asks what it all means for a serving batch. The consumer view (why a 30B-A3B model is fast on a laptop) is on the hub's Mixture of experts card; this card doesn't repeat it.

In one breath

An MoE layer replaces a transformer's single MLP with E smaller MLPs ("experts") and a tiny linear layer, the router, that scores all E for each token and sends the token to only the top k. So the model stores E experts' worth of weights but computes only k per token. The price: tokens don't spread evenly, so some experts overflow while others idle, and at serving time a batch of tokens scatters over almost every expert, so each expert does little work per weight it reads.

Gating, as the 2017 paper wrote it

Switch Transformer §2: top-1, capacity and dropped tokens

Shazeer had conjectured that k > 1 was needed for the router to learn anything. Switch routes each token to one expert and reports three wins: less router compute, expert batch "at least halved", simpler code with less communication. Because TPUs need static shapes, every expert gets a fixed number of slots:

expert capacity= tokens per batchnumber of experts ×capacity factorbuffer for imbalance

Switch Eq. 3. Filled in for the lab: 4,096 tokens / 8 experts × 1.25 = 640 slots per expert.

A token that arrives at a full expert is a dropped token: "computation is skipped and the token representation is passed directly to the next layer through the residual connection." A larger factor drops less but pads more empty slots, which is wasted compute and memory. With the aux loss below, Switch reports drops "typically < 1%". The auxiliary loss that keeps the router honest

Left alone, a router can collapse onto a few favourite experts, which then overflow. Switch adds one loss term per Switch layer:

loss=α·N· ∑i=1N fishare of tokens sent · Pishare of router probability
f_ifraction of the batch's T tokens whose argmax is expert i (Eq. 5; not differentiable)counts P_imean router probability p_i(x) over the batch (Eq. 6; differentiable, so gradients flow through it)soft Nnumber of experts; multiplying by N keeps the minimum at α for any N8 in the lab αcoefficient10⁻² (swept 10⁻¹…10⁻⁵)
Uniform: f_i = P_i = 1/8 loss = 0.01 × 8 × 8·(1/8 · 1/8) = 0.01 × 8 × 0.1250 = 0.0100 Skewed (Zipf s = 1): f_i = P_i = 0.368, 0.184, 0.123, 0.092, 0.074, 0.061, 0.053, 0.046 loss = 0.01 × 8 × Σ w_i² = 0.01 × 8 × 0.2068 = 0.0165 (1.65×) Lab, simulated: balanced 0.01 × 8 × 0.1251 = 0.0100 skewed 0.01 × 8 × 0.1851 = 0.0148

The simulated skewed value is below the analytic one because a token's soft probabilities P spread wider than its hard argmax f. Either way the loss is smallest when load is even, and α = 10⁻² was, per Switch, "sufficiently large to ensure load balancing while small enough to not to overwhelm the primary cross-entropy objective". DeepSeek-V3 replaces most of this with a per-expert bias nudged by γ = 0.001 each step and keeps only a tiny sequence-wise loss (α = 0.0001); the V3 architecture card covers it.

The serving catch: a batch splits across experts

This is where MoE meets the roofline from course 2, The math of serving an LLM. A dense layer is compute-bound once the batch passes Bcrit ≈ 295 tokens on an H100. In an MoE layer each expert only sees its share of the batch. Shazeer's "shrinking batch problem" (§3.1): with k of E experts, each gets about B·k/E tokens. So every expert only reaches Bcrit when

B·kEtokens per expert ≥Bcrit ⇔ B≥ Bcrit·EkMoE critical batch

DeepSeek-V3 on H100, BF16: 295 × 256/8 = 295 × 32 = 9,440 tokens per decode step. At B = 256 each expert sees 8 tokens on average; at B = 1,024, 32.

And almost every expert gets read anyway

Kiely (Inference Engineering, pp.53–54): "in batched inference on production servers, different requests activate different experts, and you should expect almost all of the model parameters to be active at any given time unless sparsity is achieved in large-scale Expert Parallelism." Per MoE layer, uniform routing: (1 − 8/256)64 = 0.131, so 86.9% of experts are touched at B = 64. Bytes read = the ~17B always-on parameters (attention, shared experts, dense layers, embeddings) + touched share × 654B routed, 1 byte each; our inference, lab section 6. Mixtral saturates sooner: 1 − (0.75)8 = 90.0% touched at B = 8.

Put the two tables together (our inference). By B ≈ 128 the step already reads nearly all 671 GB, like a dense model, but each expert still has only 4 tokens of work on average, about 74× short of Bcrit (295 / 4). That gap is why DeepSeek's decode deployment runs expert parallelism over 320 GPUs fed by 80 attention replicas (DP80): gathering tokens from many replicas is the only way to give each expert enough of them. The expert parallelism card does the plumbing.

Why it beats the alternatives

✗ Dense, same total size

Every one of 671B parameters computes for every token: 18× the FLOPs of 37B active (671/37). Same memory bill, far more compute per token.

✗ Dense, same active size

Same FLOPs per token, but far fewer parameters. Mixtral with 13B active beats Llama 2 70B "across most categories" per its paper; a 13B dense model has no such claim.

✗ MoE with no balancing

The router piles tokens on favourites. In the lab a skewed router drops 25.1% of tokens at capacity factor 1.25, and a big buffer mostly buys empty slots.

✓ Top-k MoE, balanced

Knowledge scales with total parameters, compute with active ones. Balancing (an aux loss or V3's bias) keeps load near the mean, so capacity 1.0–1.25 is enough and drops stay small.

Is MoE cheaper to serve?

Per token of compute, yes. Per GPU at small batch, often no. You pay memory for all 671B (DeepSeek-V3 doesn't fit one 8×H100 node in FP8), and at batch 64 a decode step already reads 585 GB, yet no expert is anywhere near compute-bound until about 9,440 tokens per step on an H100. Mixtral's paper says the same in one line: MoE is "more suitable for batched workloads where one can reach a good degree of arithmetic intensity". So MoE pays off at large scale with expert parallelism. For one user on one box (the laptop case on the hub card) it pays off because only the active weights are read. In between, a dense model is simpler: Kiely notes models under 32B, and especially under 8B, "tend to use traditional dense architectures efficiently".

Token dropping is mostly a training-on-TPUs artefact of static shapes. DeepSeek-V3 drops none in training or inference, and the Mixtral paper points to Megablocks kernels, which handle "a variable number of tokens" per expert. Whether a given engine can ever drop tokens at inference, check its docs; none of our sources says vLLM or SGLang do.
