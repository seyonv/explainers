How GPUs talk: collectives and interconnects

Also called collective communication, NCCL collectives, or "comms"; the wires are scale-up (NVLink, NVSwitch) and scale-out (InfiniBand, RoCE, the NIC). This card covers the six collectives in NVIDIA's NCCL docs, the ring all-reduce behind nccl-tests' "busbw" column, the cost formulas from the Scaling Book (Part 3 and the GPU chapter), and what one all-reduce costs Llama-3.1-70B split over 8 H100s. It is the vocabulary every later card in this course uses.

In one breath

When one model runs on several GPUs, each GPU computes part of the answer, and the pieces must be combined before the next layer can start. A collective is a combining pattern that every GPU joins at once: sum everything and give everyone the total (AllReduce), give everyone a copy of everyone's piece (AllGather), and so on. Its cost is a fixed latency per hop plus bytes divided by link bandwidth. The link inside a server (NVLink, 450 GB/s per direction on an H100) is 9× faster than the link between servers (InfiniBand, 50 GB/s per GPU), and that gap decides where each kind of parallelism can live.

The six collectives, on 4 GPUs

NCCL's names. Each letter is one GPU's data (a is on GPU0, b on GPU1 and so on) and each digit a chunk position. Green chunks are sums over all four GPUs (Σ0 = a0 + b0 + c0 + d0). Dashed boxes are buffers the operation doesn't write.

AllReduce

Sum across GPUs; every GPU gets the full sum. Tensor parallelism's workhorse.

ReduceScatter

Sum across GPUs, but GPU k keeps only chunk k of the result.

AllGather

Everyone's piece, concatenated in rank order, on every GPU. No arithmetic.

Broadcast

Copy the root's buffer (here GPU0) to every GPU. The root is a rank, not a device number.

Reduce

Like AllReduce, but only the root gets the sum.

AllToAll

GPU i sends its chunk j to GPU j: a transpose. Mixture-of-experts dispatch and combine.

ReduceScatter, then AllGather = AllReduce (NCCL docs, on the AllGather entry) Reduce, then Broadcast = AllReduce (NCCL docs, on the Reduce entry) labs/collectives.py checks all six definitions and both identities in numpy: OK

The first identity is the one to remember. It is how the ring below works, it is why the Scaling Book says "an AllReduce is twice as expensive as an AllGather", and it lets a tensor-parallel layer end in a cheaper ReduceScatter when the next step only needs a slice. NCCL also has Gather, Scatter and point-to-point Send/Recv; every collective call must use the same count and datatype on every rank, or the docs promise "undefined behavior, including hangs, crashes, or data corruption."

The ring all-reduce, step by step

Put the 4 GPUs in a ring (0 → 1 → 2 → 3 → 0) and cut each GPU's array into 4 chunks. In phase 1 (a ReduceScatter), at step s GPU i sends chunk (i − s) mod 4 to its neighbour, which adds it to its own copy. After 3 steps each GPU holds one fully summed chunk. That last line is the ring's big property: the time per byte doesn't grow with the number of GPUs.

What it costs: bandwidth plus latency

Two terms: the bytes each GPU must push through its link, and a fixed delay every time a message hops to the next GPU. The ring pays that delay 2(n − 1) times.

This is the textbook latency-plus-bandwidth model for a ring (our framing). The Scaling Book writes the same idea as a max, T = max[Tmin·X/2, V/W], for a bidirectional TPU ring. The two forms never differ by more than 2×. Filled in for 70B decode at batch 64 over NVLink: 14 × 1 µs + 1.75 × 1,048,576 B / 450 GB/s = 14 + 4.08 = 18.1 µs.

The Scaling Book's takeaway: in the bandwidth-bound regime the time "depends only on the size of the array and the available bandwidth, not the number of devices".

algbw vs busbw: reading an nccl-tests line

nccl-tests, the standard NCCL benchmark, prints two bandwidths. algbw = S / t is what your array experienced. busbw multiplies it by the factor above, so it can be compared with the link's spec "independently of the number of ranks".

1 GB AllReduce, 8 GPUs, links at 450 GB/s, bandwidth-bound: t = 1.75 × 1 GB / 450 GB/s = 3.89 ms algbw = 1 GB / 3.89 ms = 257 GB/s ← looks like 57% of the link busbw = 257 × 2(8 − 1)/8 = 450 GB/s ← the link is actually full busbw factor at n = 8: AllReduce 2(n−1)/n = 1.75 ReduceScatter, AllGather, AlltoAll (n−1)/n = 0.875 Broadcast, Reduce 1

So an algbw far below the spec isn't a problem by itself; a busbw far below it is. For AlltoAll the (n − 1)/n factor is a normalising convention, not a claim that it costs the same as an AllGather.

Bandwidth-bound or latency-bound: it depends on the message size

Setting the two terms equal gives the crossover size, below which the hop latency dominates and the link sits mostly idle:

2(n − 1) · α = 2(n − 1)/n · S*/W → S* = n · α · W NVLink: 8 × 1 µs × 450 GB/s = 3.6 MB (α illustrative) InfiniBand: 8 × 1 µs × 50 GB/s = 0.4 MB

Lines: the model above with α = 1 µs per hop (illustrative; the Scaling Book's figure for a TPU link hop, as NVIDIA publishes no NVLink hop latency). Dots: measured on 8×H100 with SHARP off, from the Scaling Book's GPU chapter. Dashed ticks: the all-reduce sizes of one 70B decode step at batch 1, 64 and 256.

The measured reality is worse than the model. The Scaling Book reports that 8×H100 all-reduce busbw reaches "close to 370GB/s … although only around 10GB/device" (82% of the 450 GB/s spec), and that a Llama-3-70B MLP-sized all-reduce under 8-way sharding (bf16[8192, 3584] = 58.7 MB) "can achieve only around 150GB/s" (33%). Working backwards (our arithmetic), 58.7 MB at 150 GB/s busbw is about 685 µs, 2.8× the model's 242 µs. Their takeaway: "it is difficult in practice to exceed 370 GB/s, so adjust the above estimates accordingly." Decode messages are 14 to 3,600 times smaller than that 58.7 MB, which puts them deep in the latency-bound region (our inference; the sizing card's rented-node script measures that part of the curve).

Scale-up vs scale-out: the two kinds of wire

Think of one building with wide internal corridors (scale-up), joined to other buildings by a road (scale-out). Everything inside an 8-GPU server moves over NVLink through NVSwitch chips; anything leaving it goes through a network card (NIC) onto InfiniBand.

Worked example: one 70B decode step at TP8

Llama-3.1-70B in BF16 split 8 ways by tensor parallelism does two all-reduces per layer (our inference from Megatron, see the next card), so 2 × 80 = 160 per decode step. Each message is batch × D × 2 bytes = B × 8,192 × 2. The memory-only step at TP8 (weights ÷ bandwidth, course facts) is 5.27 ms. Three things to take away. Over NVLink the data term stays below the 5.27 ms step at every batch. Over InfiniBand it passes the whole step by batch 64 and is 4.5× the step at batch 256, which is why tensor parallelism stays inside one NVLink node (Kiely: TP "generally requires too much communication across GPUs to be a good fit for multi-node inference"). And at batch 1 the data is nothing; any real cost is hop latency, which our illustrative α puts at 43% of the step. The Megatron II card turns this into a full step-time model.

Why the ring beats the obvious alternatives

✗ Send everything to one GPU

7 GPUs send their full array to GPU0, which sums and sends it back. GPU0's link carries 7S each way: ≥ 7 S/W, 4× the ring, while the other links sit idle.

✗ Everyone sends to everyone

Each GPU ships its whole array to all 7 peers and sums locally. 7 S/W per GPU, 4× the ring, and every GPU does the full sum redundantly.

✗ Sum inside the switch (SHARP / NVLS)

Hopper's NVSwitch can reduce in the network: in theory S/W, half the ring's cost. Measured: about 30% more bandwidth, not 75%, and it needs SHARP-capable switches (Scaling Book).

✓ Ring all-reduce

Every link busy on every step, each byte sent 2(n − 1)/n times, never more than 2 S per GPU however many GPUs join. Needs only neighbour links, so it works on any topology.

Is the ring always what runs?

No. The ring is bandwidth-optimal but pays 2(n − 1) hop latencies, which is the wrong trade for small messages. NCCL "uses a variety of implementations depending on latency requirements/topology" (Scaling Book): a tree does the same total work in log n hops instead of n − 1 (3 instead of 7 per phase at n = 8), and NVSwitch nodes can use in-switch reduction. nccl-tests' busbw formula holds for "ring, tree, or other" as long as they use point-to-point sends, which is why busbw is still the number to compare.

Collectives aren't always the right tool either. When a model fits on one GPU, the fastest collective is none: run independent copies (data parallelism). Across servers, pick a layout whose traffic suits the slow link: pipeline parallelism sends one small activation per stage, and expert parallelism uses AllToAll, which Kiely says "scales well to multi-node deployments". Two cautions: the Scaling Book warns that expert-parallel AllToAlls spread over several nodes "may struggle to achieve even 50% of the total bandwidth", and every spec here is a peak you won't reach at decode message sizes.
