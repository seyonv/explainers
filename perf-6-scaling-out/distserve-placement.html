DistServe II: placement, KV transfer and results

Also called placement search, xPyD sizing, instance segments or pull-based KV transfer. DistServe §4–7 (OSDI '24): how it picks each phase's parallelism and GPU count with a simulator, how it keeps the KV cache on NVLink when the network between nodes is slow, and what that gained on 32 A100s serving OPT-13B, 66B and 175B. DistServe I covers §1–3.

In one breath

Once prefill and decode run on separate GPUs, you still have to decide how many GPUs each phase gets, how each copy of the model is split, and which machines they sit on. DistServe calls that answer a placement. It finds one by simulating every candidate layout against your workload and SLOs, keeping the layout with the most goodput per GPU, and copying it until the fleet covers your request rate. When the links between nodes are slow, it lines up the prefill and decode copies layer by layer, so the KV cache only ever moves over NVLink inside a node.

What a placement is

DistServe's search returns three things (§4): (a) the parallelism of the prefill instance and of the decode instance, (b) how many of each to run, and (c) which GPUs they go on. An instance is one complete copy of the weights. The goal is the course's goodput, taken per GPU:

Algorithm 1: high node-affinity (fast network between nodes)

With InfiniBand-class links, DistServe treats KV transfer between any two nodes as negligible, so prefill and decode can be optimized separately. Then it replicates each one.

# G model · N nodes per instance · M GPUs/node · C GPU memory · W workload · R rate for intra_op in 1..M: # tensor-style split (TP) for inter_op in 1..(N·M / intra_op): # pipeline stages (PP) if G.size / (inter_op · intra_op) < C: # weights fit per GPU g = binary_search_rate(simu_prefill(G split this way, W)) # TTFT SLO keep as config_p if g / num_gpus is the best so far g = binary_search_rate(simu_decode(G split this way, W)) # TPOT SLO keep as config_d if g / num_gpus is the best so far n, m = ceil(R / config_p.goodput), ceil(R / config_d.goodput) return (n × config_p, m × config_d) # O(N·M²) configs; "under 1.3 minutes" in the paper's largest setting

Paraphrase of the paper's Algorithm 1. For DistServe, intra-op means tensor parallelism and inter-op means pipeline parallelism. Appendix B's Table 3 calls them TP and PP.

The shape matches the paper. Disaggregation pays most when a tight TPOT meets long prompts: in the colocated case, each 28 ms prefill of a 1,738-token prompt freezes every decoding user for almost three 10 ms TPOT budgets. It loses on short code prompts, where a prefill costs about one decode step and the GPU split only adds rounding and queueing. With a loose TTFT, the extra TP isn't worth its all-reduces for prefill here. Tighten the chatbot TTFT to 30 ms and prefill switches to TP4, which is the paper's "prefill gets more intra-op" pattern.

Back-of-envelope version (Scaling Book Part 8, course 2). Keep both pools busy: P / Tprefill = B · G / (Tstep · nout). The book's LLaMA 3-70B on TPU v5e gives P = 3G. With our 8B floors and the largest decode batch that meets TPOT, it gives P/G = 12.26 · 402 / (19.98 · 200) = 1.23 for chatbot, 1.96 for code and 2.31 for summarization. The simulator asks for more prefill (1.59, 2.31, 3.41) because the formula assumes 100% busy servers and no queueing or SLO tail. The formula gives you the ratio in a minute. The search tells you the parallelism, the SLO margin and the rounding.

Algorithm 2: low node-affinity (NVLink inside a node, slow links between)

DistServe's own testbed had only 25 Gbps between nodes, so every real experiment used this algorithm. OPT-175B is 350 GB in FP16. One prefill copy plus one decode copy needs 700 GB, but one 8×80 GB node holds only 640 GB. So the pair can't share a node. The key insight: "KV cache transfer occurs exclusively between corresponding layers". Cut both instances into the same pipeline stages, called instance segments, and put the prefill and decode segments of the same stage on the same node.

OPT-175B on ShareGPT, the placement DistServe chose. Each stage's weights are 350 / 3 = 116.7 GB, so 38.9 GB per prefill GPU and 29.2 GB per decode GPU. 3 + 4 = 7 GPUs per node. The paper doesn't say what the 8th GPU does. Alg 2 enumerates the number of stages, then every pair of in-node configs with Pp + Pd ≤ M GPUs, simulates prefill and decode jointly, and replicates the best one: n = ⌈R / goodput⌉.

§6.5 swaps the names. It labels "Alg. 1 (DistServe-Low) and Alg. 2 (DistServe-High)", but §4 and §6.4 use Alg 1 = High and Alg 2 = Low, and the text shows §4 is right. §6.5 also found that Low searches more slowly than High at large GPU counts: its prefill and decode configs must be enumerated together, while High's two searches are independent and parallel. Both still finish "in minutes" on a 96-core CPU, and the time doesn't depend on model size, because the simulator only replays events.

Online scheduling (§4.3)

  • Dispatch. A central controller sends each request, in arrival order (FCFS), to the prefill instance with the shortest queue, then to the least-loaded decode instance.
  • Pipeline bubbles. Prompts of different lengths leave pipeline stages idle. So prefill batches are sized to a total of about Lm tokens, the shortest prompt that saturates the GPU: several short prompts are batched together, and a long prompt runs alone. For decode, Lm is the largest batch size. In our H100 model, Lm = (16.06 GB / 3.35 TB/s) ÷ (2 · 8.03e9 / 989e12) = 295 tokens, the same crossover as the roofline's ~295.
  • Pull, not push. After a burst, pushing every finished KV cache at once could overflow decode memory. Instead, decode instances fetch KV "as needed", "using the GPU memory of prefill instances as a queuing buffer". Each side runs at its own pace.
  • Replanning. A profiler watches mean input and output length and arrival rate. On a significant shift, DistServe reruns the placement search (seconds to minutes) and reloads weights "within minutes". Workloads shift over hours.
  • Not built: preemption, since FCFS lets a long prompt block short ones (the "convoy effect"), and fault tolerance. "A fault in a single decoding instance mapped to multiple prefill instances could potentially cripple the entire service."

The paper gives A100 NVLink as "600 GB/s". That is both directions added together; one direction is 300 GB/s. Measured (§6.3, OPT-175B ShareGPT, the heaviest transfer): KV transmission is "less than 0.1% of the total latency", and "over 95% of requests experience a delay of less than 30ms". Our inference: an average 755.5-token OPT-175B prompt is 3.56 GB of KV (4.5 MiB/token), and moving it in 30 ms takes about 119 GB/s. Only NVLink gets there. Over 25 Gbps it would take 1.14 s. Why it beats the alternatives

✗ Colocate and tune parallelism

vLLM++ searched every parallelism and landed back on vLLM's default. Interference caps what any split of a colocated server can do.

✗ Chunked prefill (DeepSpeed-MII)

This reduces interference but doesn't remove it, and slower prefill misses TTFT. DistServe serves 1.6–7.4× its chatbot rate.

✗ Disaggregate with a hand-picked split

Pick a fixed P:D ratio and ship the KV over whatever network is there. On 25 Gbps, one 512-token OPT-66B request takes 387 ms to move. And the right ratio moves with the workload: 1.59 to 3.41 in our lab.

✓ Searched, bandwidth-aware placement

A simulator picks each phase's parallelism and count for your SLOs. Alg 2 keeps the KV on NVLink (under 0.1% of latency), and replanning follows the workload.

When not to disaggregate (§7)

Throughput-oriented or offline jobs. With loose latency targets, chunked prefill with piggybacking "may be preferred since it can fill each batch to the compute-bound threshold". Loosen all our SLOs 10× and the gains shrink to 1.01×, 0.98× and 1.55×.

Few GPUs. With a handful of GPUs, or one, the design space collapses. In our lab at 10 req/s, each phase rounds up to a whole instance, so disaggregation needs 2–5 GPUs where colocation needs 1–2. A non-disaggregated system is simpler.

Short prompts (our lab, not §7). With 171-token code prompts, a prefill costs about one decode step, and colocated replicas win: 0.83×. This matches the production advice in the next card (Kiely, Dynamo): disaggregation pays for big models, heavy traffic and long, prefill-heavy inputs.

Long context is the opposite case. §7 argues KV grows linearly with the prompt but prefill compute grows quadratically, so transfer becomes relatively cheaper while interference grows: "remains promising".

The price is a shared fate. In a colocated fleet, one failed replica takes down only itself. Here one decode instance serves several prefill instances, and DistServe left fault tolerance and preemption as future work.
