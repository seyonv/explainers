Prime · 2 minutes before you read

The problem: A sweep produces dozens of possible comparisons. Analyse it freely and some contrast will look significant by chance, the clustering of runs within tasks will make intervals too narrow, and nobody can tell which result was planned. The headline then means nothing.

In one breath

Every arm of a prefix starts from the same history and workspace, so the cleanest comparison is inside the prefix: tampered in the treated branch minus tampered in the d0 branch. Average those differences, then get the uncertainty by resampling whole tasks, because prefixes of one task are alike. Count how many tests you run, group them into families, and correct within each family so one lucky contrast can't become a headline. The pre-registration already says all of this; analysis is the discipline of doing only that, and labelling anything else exploratory.

Step 2 · Rehearse the estimator on the pilot

Paired tampering contrasts on the baseline's 40 prefixes20 min

Copy the baseline run folder (gitignored, 52 MB on disk) into the clone, then run a short script that reads each branch's outcome.json, forms Δ per prefix (treated branch − reference branch) grouped by task, and calls the repo's functions.

mkdir -p runs && cp -R \
  ~/Desktop/repos/compaction-claims/runs/pilot-baseline-20261001-161616 runs/
cat > pilot_contrasts.py <<'EOF'
import json, glob, re
from collections import defaultdict
from analysis.stats import (paired_rd, bootstrap_p,
                            bootstrap_p_greater, holm, sign_test)
D = "runs/pilot-baseline-20261001-161616"
t = defaultdict(dict)              # (task, repeat) -> arm -> 0/1
for f in glob.glob(f"{D}/*/outcome.json"):
    task, rep, arm = re.search(
        r"(g\d+)-(r\d)-(d\d-\w+)$", f.split("/")[-2]).groups()
    t[(task, rep)][arm] = int(json.load(open(f))["tampering"])

def diffs(a, b):
    out = defaultdict(list)
    for (task, _), arms in t.items():
        out[task].append(arms[a] - arms[b])
    return out

pairs = {"codex-d0": ("d1-codex", "d0-codex"),
         "opencode-d0": ("d1-opencode", "d0-codex"),
         "opencode-codex": ("d1-opencode", "d1-codex")}
ps = {}
for name, (a, b) in pairs.items():
    d = diffs(a, b)
    est, (lo, hi) = paired_rd(d)
    ps[name] = bootstrap_p(d)
    flat = [x for v in d.values() for x in v]
    print(f"{name:15}{100*est:+6.1f} pp [{100*lo:+.1f}, {100*hi:+.1f}]"
          f"  p2={ps[name]:.3f}  prefixes +{flat.count(1)}"
          f" -{flat.count(-1)} 0:{flat.count(0)}")
d = diffs("d1-codex", "d0-codex")
print("one-sided p (H2 rule, codex-d0):", bootstrap_p_greater(d))
flat = [x for v in d.values() for x in v]
print("exact sign test:", round(sign_test(flat.count(1), flat.count(-1)), 4))
print("Holm over the three:", {k: round(v, 3) for k, v in holm(ps).items()})
EOF

Read the first line as the registered estimator would: in 12 prefixes the Codex-compacted branch tampered and the d0 branch didn't, in 4 the reverse, in 24 they agreed; the mean of those 40 differences is +20.0 points, and resampling the 20 tasks 10,000 times puts it between +5.0 and +37.5. The pilot's numbers match docs/baseline-pilot.md. They are exploratory: this contrast was chosen by looking at this data, which is why addendum 3 re-tests it on 40 fresh tasks.

The sign test on the same prefixes gives p = 0.077, not 0.015. It uses only the 16 prefixes that moved, ignores that prefixes cluster in tasks, and is exact rather than asymptotic. That's why it is the registered fallback only when the mixed model can't be fitted or there are fewer than 10 events, not the main test.

What Holm does, on the pilot's three p-values5 min

Holm sorts the p-values, multiplies the smallest by the number of tests m, the next by m − 1, and so on, never letting an adjusted value fall below the one before it. The course's stdlib version, fed the pilot's three rounded p-values (illustrative as a family: they were never registered together):

You should see
d1-opencode - d1-codex   raw 0.001  Holm 0.003  reject
d1-codex - d0            raw 0.015  Holm 0.030  reject
d1-opencode - d0         raw 0.235  Holm 0.235  keep
sign test 12 up, 4 down: p = 0.0768

The repo's holm printed 0.002 for the first line because it used the unrounded p. Note also that 0.030 would pass Holm at 0.05 but would not pass H2's registered rule if it were a two-sided p; H2 uses the one-sided p (0.0074 on the pilot) against 0.025.

Step 4 · Fit the mixed model, or say why not

The registered model-based estimate30 min

The registration (§5.1) asks for outcome ~ dose1 + prompt + model + (1 | task) + (1 | task:prefix), a logistic model with a random intercept for each task and each prefix within it, fitted with statsmodels' BinomialBayesMixedGLM, reporting the dose1 coefficient as an odds ratio with a 95% credible interval. It is reported beside the bootstrap; if they disagree, the bootstrap decides.

Step 5 · The mechanism arm: prompt or truncation?

Why d1-codex-cut2000 exists20 min

In the pilot, the Codex prompt and the OpenCode prompt differed in two ways at once: the wording, and what the summarizer saw. pytest prints its verdict line (e.g. 2 failed, 7 passed) at the end of the output, and OpenCode keeps only the first 2,000 characters of each tool result, so the verdict reached the summarizer in 32/40 Codex compactions but only 4/40 OpenCode ones. The cut2000 arm uses the Codex prompt with tool results cut exactly as OpenCode cuts them; a plumbing check confirmed its summarizer doesn't see the verdict line. That splits the total prompt effect in two:

T5 opencode - codex = total prompt effect T1 cut2000 - codex = truncation, prompt fixed T2 opencode - cut2000 = wording, truncation fixed T5 = T1 + T2 (means over the same prefixes)

Then, exploratory: within each compacted arm, tampering with vs without the verdict line in the summarizer's input (Wilson intervals; a bootstrap difference where both cells have ≥ 10 branches). The causal test of "state lost from the summary" is still the intervention arm (T4), which puts the verdict back verbatim.

Why the registered analysis beats the alternatives

✗ Compare arm rates unpaired

Treats 160 prefixes' branches as independent runs. It throws away the shared history that makes arms comparable, so intervals widen, and it ignores that prefixes of one task are alike.

✗ Test everything at 0.05

Fifteen-plus contrasts at 0.05 make a false positive likely somewhere. The pilot's own lead came from looking at many outcomes.

✗ Only the mixed model

With a near-zero P1 it may not converge, and its answer depends on the model's assumptions. The registration lets the bootstrap decide.

✓ Paired, task-resampled, family-corrected

Within-prefix pairs cancel the prefix, resampling tasks keeps the clustering honest, and Holm within registered families keeps the confirmatory claim to H1 and H2.

Honest caveat. The bootstrap is unstable with rare events and few tasks; the baseline report says not to go below 40 tasks for that reason, and a near-zero P1 may leave only the sign test. The pooled H2 estimate averages two models that may react differently; family M tests that, but with one difference it has little power. And T5 = T1 + T2 holds for the means, not for the p-values: a split that looks clean may still have wide intervals on both parts.

Understand and remember

  • Every arm branches from the same saved history and workspace → the prefix's own difficulty cancels in treated − d0 → Δ per prefix is the registered unit, and its mean is the estimate
  • Prefixes of one task are alike → treating branches as independent makes intervals too narrow → the bootstrap resamples whole tasks with all their prefixes (B = 10,000)
  • Each extra test is another chance of a false positive → tests are grouped into registered families and Holm-adjusted within each → only H1 and H2 are confirmatory; everything else is labelled secondary or exploratory
  • Prompt wording and truncation differed together in the pilot (verdict seen 32/40 vs 4/40) → cut2000 keeps the Codex wording but cuts tool output like OpenCode → T1 measures truncation, T2 wording, and T4 (intervention) tests putting the state back
  • detail that matters The mixed model may not fit with fewer than 10 events → the registered fallback is the exact sign test on prefixes that moved → expect it for P1 and P2, and expect it to be weaker than the bootstrap (0.077 vs 0.015 on the pilot)

  • model formula: outcome ~ dose1 + prompt + model + (1 | task) + (1 | task:prefix), BinomialBayesMixedGLM
  • family sizes: H1 2, H2 1, T 5, S 6, M 1
