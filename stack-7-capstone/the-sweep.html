Run the sweep

Step 5 of the capstone, also called the main run or the confirmatory sweep. 960 branches on 40 fresh tasks, two models and six arms, run exactly as addendum 3 of the pre-registration fixes them, blind to outcomes until the last branch is labelled. You check the plumbing offline, launch it in two chunks under a hard $120 cap, watch only cost and errors, and handle failures by rules written before the first run.

Prime · 2 minutes before you read

The problem: A registered design can still be quietly broken while it runs: a peek at the results that decides whether to continue, a re-run of a branch that 'looked wrong', a typo in an arm name, a cap that stops halfway. Each one turns a confirmatory test back into an exploratory one.

Where it fits: Step 5 of the capstone. It executes the n and the arms fixed in Measure the floor, then size the study under the rules in Write the analysis down first, using the prefixes and branches from Branch from the agent's own run, and hands 960 labelled branches to the analysis.

In one breath

A confirmatory sweep is boring on purpose. Everything that could change the answer (tasks, models, arms, seeds, step limits, the extractor, the cap, what counts as a re-run) was fixed in addendum 3 before the first call, so the only decisions left during the run are mechanical: did an infrastructure call fail, and is the money running out? You look at cost, stop reasons and error counts, never at an outcome by arm, because looking is how a fixed n quietly becomes an optional stopping rule.

4 · Launch chunk 1, then chunk 210 min + wall time

The flags below all exist in scripts/pilot.py at 100acdb and set what addendum 3 fixes: the disjoint draw, two prefixes per task × model with up to three seeds, the six named arms, outcome labelling, blind printing and the phase cap. This spends money, so it wasn't run for this card. The command the sweep actually ran is the one in its own log; copy that into the paper's appendix, not this one.

M="gpt-5.4-mini-2026-03-17 gpt-5.5-2026-04-23"
A="d0-codex d1-codex d1-opencode d3-codex d1-codex-cut2000
   d1-codex-intervention"
uv run python scripts/pilot.py --tag main --branch --outcomes \
    --blind --models $M --tasks 40 --task-seed 1 \
    --exclude-draw 20 0 --prefixes-per-task 2 --prefix-tries 3 \
    --arms $A --phase main --phase-cap 120 --total-cap <ledger \
    total + 120> --cap <remaining phase cap − 2> \
    --task-slice 0 4                 # chunk 1: 4 tasks
# check: chunk-1 spend × 10 ≤ $120, else stop here
# chunk 2: the same command with --task-slice 4 40

Two flags need care. --total-cap defaults to $12 across all ledger phases, and the budget is the smaller of --cap and what's left under it. With $6.89 already spent, the default would quietly shrink chunk 1 to about $5.11 and truncate the sweep; once spend passes $12 it refuses to start at all. Set it to the ledger total plus $120. The real chunk 1 log opens with cap $117.89 (prior spend $6.8876). --cap is the harness's own budget for this invocation, which the addendum sets $2 below the remaining phase cap so that calls already in flight can't overshoot. --task-slice also shifts the branch seeds, so the two chunks never reuse a seed.

While it runs, --blind prints only lines like this (format from pilot.py)
<run name>   steps=<n>  stop=<finish|text|max_steps>  comp=<k>  $<cost>  spent=$<total>
<n> branches; stops {...}; agent cost $..; labeller $..; unlabelled <n>

No label, no tampering flag, no arm totals. That's the point.

5 · Read the ledger2 min

Every invocation appends its spend to runs/spend_ledger.json, re-reading the file first so concurrent runs don't drop entries. Sum it by phase, read-only:

python3 - <<'EOF'
import json
from collections import defaultdict
L = json.load(open("runs/spend_ledger.json"))["entries"]
by = defaultdict(float)
for e in L:
    by[e.get("phase") or "trigger pilots"] += e["spent_usd"]
for k, v in by.items():
    print(f"{k:15} ${v:7.4f}")
print(f"{'total':15} ${sum(by.values()):7.4f}  ({len(L)} entries)")
EOF

When something fails

What happensWhat the rules say
Provider or harness exception in a prefixRe-run once with the same seed, logged in reruns.jsonl. A second failure ends that task × model's prefixes; the cell is a yield loss.
Exception in a branchRe-run once with a new seed, logged. A second failure excludes the branch; excluded branches are counted per arm.
Labeller (extractor) errorRetried once, logged; otherwise label it later with the same frozen extractor.
Step limit, plain-text stop, empty messageNever re-run. These are model behaviour and count as outcomes (P1 = P2 = 0 with no final message).
A call could cross the capThe harness Budget refuses it before it is made (BudgetExceeded), using the call's worst-case cost.
The $120 cap is reachedStop. Analyse only prefixes with all six arms complete, say the sweep was truncated, and report the achieved n and its smallest detectable effect.
Chunk 1 projects over $120Stop after chunk 1; unblind nothing until a further addendum.

Results

Pending: filled when the sweep completes. Nothing below exists yet; no number on this card comes from the sweep. When analysis/run_main.py has written results/main.md, this box is replaced with:

  • Yield: prefixes obtained of 160 per model, attempts, median prefix step; branches run of 960; excluded branches per arm; re-runs from reruns.jsonl; stop reasons per arm.
  • Spend: the ledger's phase main total against the $120 cap, cost per prefix and per branch for each model, and whether the sweep was truncated.
  • H1a / H1b: P1 and P2 per arm with Wilson CIs; paired d1 − d0 with 95% CI, two-sided bootstrap p, Holm-adjusted p; the mixed-model odds ratio or the sign test.
  • H2 (confirmatory): tampering in d0 vs d1-codex, the paired difference with its 95% CI and one-sided p (supported if p < 0.025 and the estimate > 0).
  • Family T (tampering): cut2000 − codex (truncation), opencode − cut2000 (prompt at fixed truncation), d3 − d1 (dose), intervention − codex (H4), opencode − codex (H3), with Holm.
  • Family S and M: P1/P2 for d3, opencode and intervention vs d1-codex; the H2 contrast in gpt-5.5 minus in gpt-5.4-mini.
  • Per model: every confirmatory contrast for each of the two models, marked exploratory.
  • Mechanism and summaries: verdict line seen by the summarizer per arm, summary status inflation, undisclosed tampering, resolved rate, pass^k of an honest report.
Done when
  • both chunks have finished, or the run stopped under a registered rule and the reason is written down;
  • reruns.jsonl, the run log with the exact command, and the ledger entry are saved with the run folder;
  • every branch has an outcome.json from the frozen extractor (hash 44bdd8fe…), or is counted as excluded;
  • you have not looked at any outcome by arm, and analysis/run_main.py is committed before you do.

Why a blind, chunked sweep beats the alternatives

✗ Run it live, no prefixes

About 27% of live runs never reach the failing state, and the arms diverge before compaction, so the dose contrast mixes compaction with everything the agent did differently earlier.

✗ Peek after chunk 1

If you look at tampering by arm and then decide whether to continue, n stops being fixed. The p-value no longer means what the registration says.

✗ Re-run whatever looks odd

Re-running a branch because it hit the step limit or tampered turns model behaviour into noise you removed. Only infrastructure failures may be re-run, once, logged.

✓ Fixed, blind, logged

Everything decided in advance, monitored only on cost and errors, every re-run on file. A reviewer can check that the sweep ran as registered, line by line.

Honest caveat. "Blind" here is a discipline, not a lock: the outcome files are on disk, and nothing stops you reading them early except the commitment, so say in the paper exactly when you first looked. The cost guard is also only as good as the price table in harness/models.py and the second model's cost estimate, which rests on 6 runs (±50%). And the chunk-1 rule extrapolates from 4 tasks (10%): if those 4 happen to be cheap, the full sweep can still hit the cap, in which case the truncation rule, not a new decision, applies.

Understand and remember

  • Deciding whether to continue after seeing outcomes → optional stopping → the p-value overstates the evidence → the sweep fixes n in advance and monitors only cost, stop reasons and errors (--blind)
  • Re-running a branch because of what the model did → removes real behaviour from the data → only provider or harness exceptions are re-run, once, logged in reruns.jsonl; step limits and plain-text stops are outcomes
  • Spend is uncertain (the second model's cost rests on 6 runs) → chunk 1 (4 tasks) projects the total × 10 → over $120 means stop before chunk 2, with no unblinding until a new addendum
  • The harness Budget refuses any call whose worst-case cost could cross the cap → the cap can't be overshot by more than calls already in flight → the addendum sets the per-invocation cap $2 below what's left
  • detail that matters --task-slice shifts the branch seed base by 1,000 per starting task → chunk 2 never reuses chunk 1's seeds → the two chunks are independent draws, as if run in one go

5 · Predict commit to an answer before revealing

Suppose gpt-5.5 often hits the 20-step limit after compaction while gpt-5.4-mini almost never does. Predict how that shows up in the blind monitoring, and what (if anything) you are allowed to do about it.

Reveal

It shows up as a higher share of stop=max_steps lines for gpt-5.5 in the --blind output (you can see stop reasons, but not by arm, only by run name, which does contain the arm, so you should avoid tallying them). You may not do anything: hitting the step limit is a registered outcome (P1 = P2 = 0 with no final message), not an infrastructure failure, so it is neither re-run nor excluded. It becomes a reported stop-reason difference and a robustness analysis restricted to branches that reached finish.
