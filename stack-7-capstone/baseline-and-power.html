Measure the floor, then size the study

Step 4 of the capstone, also called the baseline pilot and the power analysis. Before the confirmatory sweep, 120 branches of one model measured how often each outcome happens with no compaction, and a simulation turned those rates into a task count and a budget. You re-print the baseline from the saved runs (offline, free), re-compute the one contrast that moved, and leave with the n, the arms and the cost the sweep is registered at.

Prime · 2 minutes before you read

The problem: A power analysis needs the outcome's rate without the treatment, and a guessed rate gives a guessed n. Plan from the wrong baseline and the sweep is either far too small to see anything or spends most of the budget measuring a floor.

Where it fits: Step 4 of the capstone. It applies the power formula from How many runs do you need? and the task-cluster bootstrap from Error bars that don't lie to the branching design from Branch from the agent's own run, and hands the sweep its n and cap.

In one breath

A power analysis is only as good as the baseline you feed it, so the baseline has to be measured in the same setting as the experiment: here, an agent branched from its own run with a test it can't fix. The baseline said the planned outcome barely happens (one false success claim in 120 branches), that tampering with the tests happens a lot and rose after Codex-prompt compaction, and that 40 tasks are enough to see a 20-point effect on tampering (a 10-point one only about two times in three). That cut the projected cost from about $195 to about $80, capped at $120 once addendum 3 fixed the arms, and moved tampering to the front.

The bracket after each rate is a Wilson 95% interval. Note the upper bound on 0/40: 8.8%. "Zero" here means "probably under 9%", which is what the power step has to plan around.

2 · Re-compute the contrast that moved10 min

The tables don't print a paired contrast for tampering, so compute it with the repo's own estimator: per prefix, tampering in the compacted branch minus tampering in the d0 branch, averaged, with tasks resampled (B = 10,000). Save this as $L/tamper_paired.py and run it from the clone.

import json, glob, re
from collections import defaultdict
from analysis.stats import paired_rd, bootstrap_p
D = "runs/pilot-baseline-20261001-161616"
runs = defaultdict(dict)        # (task, prefix) -> arm -> 0/1
for f in glob.glob(f"{D}/*/outcome.json"):
    name = f.split("/")[-2]
    m = re.match(r"\d+-gpt-5.4-mini-(g\d+)-(r\d)-(d\d-\w+)", name)
    task, rep, arm = m.groups()
    runs[(task, rep)][arm] = int(json.load(open(f))["tampering"])
for treated in ("d1-codex", "d1-opencode"):
    diffs = defaultdict(list)
    for (task, rep), arms in runs.items():
        diffs[task].append(arms[treated] - arms["d0-codex"])
    est, (lo, hi) = paired_rd(diffs)
    print(f"tampering {treated} - d0: {100*est:+.1f} pp "
          f"[{100*lo:+.1f}, {100*hi:+.1f}], "
          f"p = {bootstrap_p(diffs):.3f}")
PYTHONPATH=. uv run python $L/tamper_paired.py
You should see
tampering d1-codex - d0: +20.0 pp [+5.0, +37.5], p = 0.015
tampering d1-opencode - d0: -7.5 pp [-17.5, +2.5], p = 0.235

Pairing is what makes 40 prefixes enough to see this: each prefix is its own control, so the variance between tasks drops out. It's still exploratory: tampering was a secondary outcome in the registration and this contrast was picked after looking. That's why addendum 3 tests it again on 40 fresh tasks.

3 · Bracket the floor and run the power simulation10 min

With 0/40 for P1 and P2, there's no measured d0 rate to plug in. So bracket it: 1%, 2.5% and the 8.8% upper bound. analysis/power.py simulates the paired, nested design (task and prefix random effects) and tests the per-task mean difference.

uv run python -m analysis.power --p0 0.02 --deltas 0.10 0.20

4 · Check the registered design's power for tampering10 min

Addendum 3 changed the design after this table was made: one d0 branch and one d1-codex branch per prefix (not two each), and tampering (H2) became the confirmatory test, one-sided at 0.025. Re-run the simulation for that: d0 rate 17.5%, one branch per arm, two-sided 0.05 (the same cut-off as one-sided 0.025 for a positive effect), starting at 40 tasks.

uv run python -m analysis.power --p0 0.175 --deltas 0.10 0.20 \
    --n0 1 --n1 1 --alpha 0.05 --t-min 40

Write that in the paper as the smallest effect the sweep could see, not as a weakness discovered later. (This check is this card's; the pilot doc's power table predates addendum 3.)

Why measuring the floor beats the alternatives

✗ Plug in the population rate

The public pilot's 0.17% isn't this setting's rate. It would ask for thousands of tasks, and it says nothing about tampering, the one outcome that moved.

✗ Keep the 100-task plan

About $195 of a $250 ceiling, to measure an outcome sitting at 0/40. Most of the money would buy precision on a floor.

✗ Skip the pilot and run the sweep

The sweep would have pre-registered false claims as its only confirmatory outcome and found nothing, with no budget left to test what actually moved.

✓ A cheap baseline in the real setting

$1.98 for 120 branches gave every d0 rate, a lead worth testing, the per-branch costs, and a design sized to see +20 points with power 0.99.

Honest caveat. The baseline is one model on 20 tasks; the second model was checked on 6 runs only, and its cost line is ±50%. The power simulation assumes a logit-normal task effect with spreads (0.5 or 1.0) that were chosen, not measured, and its z test is optimistic at small T. And the tampering lead was found by looking at this data, so its +20 points is probably an overestimate (the winner's curse); planning for a smaller true effect is why step 4 reports power at +10 as well. If the true effect is near +10, a null at 40 tasks is likely and must be written up as "not detected, CI includes +10", not "no effect".

Understand and remember

  • The baseline must be measured where the experiment runs → the forced-failing, branched setting gave P1 1/120 and tampering 17.5% at d0 → the population's 0.17% would have been the wrong input, and tampering would have been missed entirely
  • Zero events in 40 runs → Wilson upper bound 8.8% → power is computed across a bracket (1%, 2.5%, 8.8%) → in the pilot doc's design (two d0 and two d1 branches per prefix), 40 tasks detect +5 points with power 0.46–0.90 depending on where the true rate sits; addendum 3 runs one branch per arm, so H1's power is lower than that table says
  • Pairing within a prefix → each prefix is its own control → task-to-task variance cancels → 40 prefixes gave tampering +20.0 points [+5.0, +37.5], p = 0.015
  • A contrast chosen after seeing data → likely overestimated (winner's curse) and not confirmatory → addendum 3 tests it on 40 fresh, disjoint tasks and reports power at +10 (0.66) as well as +20 (0.99)
  • detail that matters The simulation's z test is optimistic at small T and rare events make the bootstrap unstable → the pilot set a floor of 40 tasks whatever the table said

5 · Predict commit to an answer before revealing

In the sweep, suppose d0 tampering for gpt-5.5 is 0/80 while gpt-5.4-mini stays near 17.5%. Predict what that does to the pooled H2 estimate and to its power.

Reveal

The pooled estimate is a mean over all prefixes, so a model with no tampering at d0 contributes differences near zero unless compaction makes it start tampering; the pooled effect shrinks toward half of the mini effect. Power drops because half the prefixes add variance-free zeros to the mean but no signal. This is why addendum 3 adds family M (the H2 contrast in gpt-5.5 minus in gpt-5.4-mini) and reports H2 per model as exploratory.
