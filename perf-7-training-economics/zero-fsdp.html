Data parallelism, ZeRO and FSDP

Also called DP or DDP (PyTorch's DistributedDataParallel); ZeRO-1, ZeRO-2 and ZeRO-3 (the paper's Pos, Pos+g, Pos+g+p; "ZeRO-1/2/3" is DeepSpeed's and the community's naming); FSDP, "fully sharded data parallel", PyTorch's ZeRO-3; together, "sharding". This card follows the ZeRO paper's own example (7.5B parameters on 64 GPUs), then puts Llama-3.1-8B training on one 8×H100 node.

In one breath

Data parallelism gives every GPU a full copy of the model and a different slice of the batch, then averages the gradients so every copy takes the same step. ZeRO notices that every GPU is storing the same 16 bytes per parameter, so it gives each GPU only 1/Nd of the optimizer state, then of the gradients, then of the weights, and fetches a missing slice just before it is needed. Stages 1 and 2 cost no extra communication; stage 3 (FSDP) costs 1.5×, and that extra traffic can usually be hidden behind the math.

Plain data parallelism: a replica per GPU, one all-reduce per step

Each GPU runs forward and backward on its own micro-batch, so each one ends up with different gradients. An all-reduce (see How GPUs talk: collectives and interconnects) sums them so every replica applies the same optimizer step. The forward pass needs no communication at all. In the Scaling Book's words, the backward all-reduces "aren't in the 'critical path'": nothing waits on them until the optimizer step. The Playbook lists three optimizations on top of the naive version, which waits for backward to finish and then communicates ("A BIG NO-NO"):

  • Overlap with backward. A hook on each parameter starts reducing its gradient as soon as it's ready, while backward works through earlier layers.
  • Bucketing. Pack many small gradients into one buffer and all-reduce the whole bucket: "a few big boxes than many small ones". The Playbook's overlap appendix uses buckets of "default size 25 MB".
  • No sync during gradient accumulation. model.no_sync() skips the all-reduce on every micro-batch except the last, because one reduce at the end gives the same result.
global batch = micro-batch × gradient-accumulation steps × DP degree (Playbook) Playbook example: 4M tokens ÷ 4,096-token sequences = 1,024 sequences mbs 2, 128 GPUs → grad_acc = 1,024 ÷ (2 × 128) = 4 mbs 2, 512 GPUs → grad_acc = 1 (same batch, 4× fewer serial passes) mbs 2, 8 GPUs → grad_acc = 64 (our 8-H100 node, same target; our division)

DP never splits the model, so every GPU must hold all of its training state. At the 16 bytes per parameter from A training step and where its memory goes, Llama-3.1-8B needs 128.5 GB on every GPU before any activations. An 80 GB H100 can't hold that. The ZeRO paper puts it bluntly: "Without ZeRO, the largest model DP alone can run has less than 1.5 Billion parameters" (on its 32 GB V100s).

What it costs in communication: 2Ψ, or 3Ψ for stage 3

VDP, ZeRO-1, ZeRO-2= Ψreduce-scatter grads+ Ψall-gather=2Ψ VZeRO-3= Ψgather, forward+ Ψgather, backward+ Ψreduce-scatter=3Ψ
Velements each GPU moves per step (ZeRO §7); ×2 for bytes in BF16, ×(n−1)/n for the ringDP: 2 × 7/8 × 16.06 GB = 28.1 GB for the 8B

Plain DP's all-reduce is a reduce-scatter plus an all-gather, Ψ elements each (the identity from the collectives card). ZeRO-1 and ZeRO-2 do the same two collectives, just split up differently: reduce-scatter the gradients so each GPU gets the summed slice it owns, update that slice, then all-gather the updated weights. ZeRO says that's "exactly the same as the baseline DP". ZeRO-3 no longer keeps the weights, so it gathers each layer's weights in forward, throws them away, and gathers them again in backward. That second gather is the extra Ψ: "3Ψ which is 1.5x compared to the baseline". The PyTorch FSDP paper measures the same "1.5x communication overhead and volume over DDP". The Playbook also counts it in launches: "2·num_layers − 1 additional all-gathers" per step, each with its own latency.

FSDP: PyTorch's ZeRO-3

PyTorch FSDP (Zhao et al., VLDB 2023) implements stage 3 with a few engineering choices that are worth knowing by name:

  • Units. You wrap the model into FSDP units, for example one per transformer block. FSDP "only materializes unsharded parameters and gradients of one unit at a time", so peak memory is "the size of the sharded model plus the size of the largest fully-materialized FSDP unit".
  • FlatParameter. A unit's parameters are concatenated into one 1-D tensor, padded, and cut into equal chunks, one per rank. NCCL's all-gather and reduce-scatter need even sizes, and one big collective beats many small ones (the same idea as bucketing).
  • Prefetch. Backward prefetch issues the next unit's all-gather before the current reduce-scatter, so the two don't queue on one NCCL stream. On GPT-175B it gave "approximately 18% speedup". Forward prefetch does the same in forward when the CPU can't issue collectives early enough. The Playbook describes the same trick for ZeRO-3: gather layer n+1 while computing layer n.
  • Sharding factor F. F = 1 is plain DDP, F = world size is full sharding, and anything in between is hybrid sharding: shard within a group (say, a node on NVLink) and replicate across groups.

Headline result: GPT-175B on up to 512 A100s at "173 and 186 TFLOPS per GPU" (batch 1 and 2), "approximately 55% and 60%" of the A100's 312 TFLOPS BF16 peak, scaling linearly from 128 to 512 GPUs.

We read that as assuming the gradients are first reduced inside the node over NVLink, so each NIC carries only 1/8 of them. If every GPU pushed the full gradient through its own NIC, you'd need 8× the batch (our inference). The Scaling Book's own takeaway: "about 2500 tokens" per GPU on an H100 or B200. For MoE models it's E/k times more.

Why it beats the alternatives

✗ Plain DP (DDP)

The cheapest communication pattern, but every GPU holds all 16Ψ. That's 128.5 GB for an 8B model, so it doesn't fit an 80 GB H100 at any Nd. Adding GPUs adds throughput, never memory.

✗ Tensor parallelism alone

Shards weights and activations, but its collectives sit on the critical path of every layer. On TPU v5p the Scaling Book finds it comm-bound past about F/2550, 8–16 ways. On GPUs it stays inside a node (4D parallelism).

✗ Pipeline parallelism alone

Moves little data, but idles in the bubble and needs complex schedules. It also "plays badly with FSDP": each micro-batch would re-gather the weights, so pipelines pair with ZeRO-1 instead (DeepSeek-V3 did PP + ZeRO-1).

✓ ZeRO / FSDP sharding

Keeps DP's simple, overlappable, off-critical-path communication (the same 2Ψ, or 1.5× for stage 3). Model-state memory drops to 16Ψ/Nd: 16.1 GB per GPU for the 8B on one node.

Is FSDP always the answer?

No. It's the default for training dense models that don't fit one GPU. It's the wrong tool when:

  • You're serving, especially decode. Each decode step handles a handful of tokens, so there's no math to hide the weight gathers behind. Gathering 7/8 of Llama-3.1-8B's 16.06 GB over NVLink takes 31.2 ms per token, while one GPU reads the whole model from HBM in 4.79 ms (ours). For 70B on 8 GPUs it's 274 ms, against 5.27 ms to read a TP8 shard (Pipeline and data parallelism when serving). The Scaling Book: "We want to move activations rather than weights." Serving uses TP inside a node, plus independent replicas.
  • Tokens per GPU fall below C/W (~2,200–2,500 on H100s). Then the collectives outlast the math. Mixing in tensor parallelism cuts the floor to 2550²/2F ≈ 100 per chip on TPU v5p (Scaling Book). The Playbook's rule of thumb is that DP "shouldn't exceed 512", since past that the rings become latency-bound.
  • Activations are the problem. ZeRO shards only model states. For long sequences or big micro-batches you need recomputation or context parallelism (Mixed precision, FP8 and activation checkpointing).
  • You're pipelining. Use ZeRO-1 or ZeRO-2 with pipelines, not ZeRO-3.
