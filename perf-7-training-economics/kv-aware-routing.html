KV-aware routing: sending requests where their cache lives

Also called prefix-aware routing, prefix-cache-aware routing, cache-aware load balancing, or (for the component that decides) the endpoint picker. This is the step in front of the engines: when you run N copies of a model, which copy gets each request? Covered here: NVIDIA Dynamo's KV router cost function, llm-d's Endpoint Picker with its approximate and precise prefix modes, and the Kubernetes Gateway API Inference Extension, all read from their docs on 2026-09-24. Our 8-replica simulation runs Llama-3.1-8B on H100s. Prefix caching inside one engine is course 4's RadixAttention, and this card doesn't repeat it.

In one breath

Each replica keeps the KV cache of prompts it has already seen, so a request whose prefix it already holds skips most of prefill. A router that ignores this (round-robin) sends each conversation's next turn to a random replica, so the cache is almost never there. A KV-aware router scores every replica on "how much of this prompt is already cached here" and "how busy is it", then picks the cheapest.

The problem: round-robin scatters the cache

A chat conversation's prompt at turn k is the system prompt plus every earlier turn, and then the new message. The replica that served turn k − 1 holds all of that except the new message. Round-robin sends turn k to that replica with probability 1/N. For N = 8 that is 12.5%, so 7 turns in 8 recompute the whole history from scratch. The system prompt is different: every replica soon caches its own copy, and that costs memory N times over.

P(next turn lands where its history is) = 1 / N = 1 / 8 = 12.5% ← round-robin lab, 54,284 follow-up turns: 12.6% landed "home" → history hit rate 9.8% (below 12.6% because LRU evicts some of it first)

Our simulation (labs/kv-router.py), described in full below. Earlier turns make up 40% of all prompt tokens in this workload, so losing them costs real prefill work.

The naive fix: hash the prefix, always go to the same replica

Hash the system prompt and send it to replica hash mod N. Every request with that prefix now hits a warm cache, because it always lands in the same place. The failure is that prefix popularity is skewed. In our workload the most popular of four system prompts carries 53% of conversations (a Zipf split: 53 / 23 / 14 / 10%), so one replica gets 53% of all requests while its fair share is 12.5%. Its prefill queue grows faster than it drains. Four prompts can also use at most four of the eight replicas.

Its queue never drains, so its TTFT keeps growing until traffic dies down. Hashing on the user or session instead spreads load well (the lab's "session hash" row), and its weaknesses show up further down.

The real fix: a cost function over cache and load

Dynamo's KV router tracks, for every worker, how many KV blocks of the incoming prompt are already cached there (from a global prefix tree built from the workers' KV events) and how much work is already assigned, counted in KV blocks (fixed runs of tokens; 16 in llm-d's approximate mode and in our lab). It computes a cost for each worker and picks the lowest. Its documented formula, copied from router-design.md:

cost= spprefill scale · max(0,P−c·Odev−h·Ohost−d·Odisk−…)prefill blocks still to compute + Ddecode blocks + w·Aactive requests
Pprefill blocks: the prompt-side tokens already queued on that worker plus this request's input, ÷ block size10 in the example Odevblocks of this prompt already in that worker's GPU cache (overlap)2 · 5 · 8 coverlap_score_credit (× a decay factor when the worker has excess prefill load)1.0 in the example Ohost, Odiskblocks cached in CPU memory or on disk, credited with their own weights h, d0 in the example Dpotential decode blocks: KV blocks active on that worker, including this request's10 · 5 · 9 w · Aoptional charge per active requestw = 0 by default
effective_device_credit = overlap_score_credit * overlap_score_credit_decay_factor adjusted_prefill_blocks = max(0, ( prefill_blocks - effective_device_credit * device_overlap_blocks - host_cache_hit_weight * host_overlap_blocks - disk_cache_hit_weight * disk_overlap_blocks - shared_cache_multiplier * shared_beyond_blocks )) active_request_blocks = decode_active_request_weight * active_requests cost = ( prefill_load_scale * adjusted_prefill_blocks + potential_decode_blocks + active_request_blocks )

Verbatim from Dynamo's router-design.md. With router_temperature > 0 the router instead samples with "softmax sampling on the normalized cost logits", which spreads load.

llm-d: the same idea as a Kubernetes router

llm-d (a CNCF sandbox project founded by Red Hat, Google Cloud, IBM Research, CoreWeave and NVIDIA) splits its router in two. Any L7 proxy carries the traffic. For each request the proxy "parks" the request and calls an Endpoint Picker (EPP) over Envoy's ext-proc protocol, and the EPP returns the pod to send it to. Inside the EPP, a plugin pipeline narrows the candidates:

From llm-d's router and prefix-cache-aware-routing docs. The prefix scorer's score is the share of the prompt's blocks already matched on that pod. It is combined with load scorers, so, as in Dynamo, a warm but busy pod can lose.

The prefix index can be kept in one of two ways. It depends on the setup, so here they are side by side:

Our lab behaves like the precise mode: the router reads each replica's actual cache. Dynamo also has both options: workers publish KV events when the engine supports them, and --no-router-kv-events makes it predict cache state from its own routing decisions instead.

Gateway API Inference Extension (GIE) is the Kubernetes standard underneath. It is a kubernetes-sigs project that turns any gateway supporting ext-proc (Envoy Gateway, kgateway, GKE Gateway) into an "inference gateway" whose scheduling is "kv-cache and request cost aware, avoiding evictions or queueing as load increases". It adds model-aware APIs: routing a model name to a LoRA adapter, A/B splits, and "safe blue-green base model and model server upgrades". One quirk as of 2026-09-24: its README says the full EPP and its APIs "have moved" to llm-d/llm-d-router. GIE keeps the InferencePool API, a lightweight reference EPP and the conformance tests. So cite GIE for the standard and llm-d for the implementation. Dynamo can also plug in behind GIE as an EPP.

Worked example: 8 replicas, four routers

The lab sends one seeded workload to 8 replicas of Llama-3.1-8B on H100s. Each replica has an LRU prefix cache of 40 GB = 327,680 tokens, about the 64 GB left after the 16 GB of weights with some held back for running batches (illustrative). The workload: 18,000 conversations, starting evenly over 10 minutes, drawing from four system prompts (2,048 / 1,536 / 3,072 / 1,024 tokens) with Zipf popularity 53 / 23 / 14 / 10%, a mean of 4 turns each, users typing 48–256 tokens and replies of 128–512 tokens. That makes 72,284 requests, 116.8 per second in steady state, with a mean prompt of 3,564 tokens. With no cache at all the fleet would spend 81% of its time on prefill. Each replica runs one FIFO prefill queue at the 8B's prefill floor:

prefill floor = 2 × 8.03e9 × 1,000 / 989e12 = 16.2 ms per 1,000 tokens (compute-bound, 100% of dense BF16) TTFT = prefill queue wait + uncached tokens × 16.2 µs cost function = (prompt blocks − credit × cached blocks) + queued prefill blocks + active decode blocks (Dynamo's form, prefill_load_scale 1; decode at 100 tok/s per user, cost-per-token's B = 64 row)

System prompts are 100% cached under every router here because 40 GB holds all four on every replica, so every difference comes from the conversation history.

Four things to read off it:

  • Round-robin balances perfectly and wastes the history. 12.6% of turns land home, which is the 1/N from above.
  • Prefix hash caches well and melts one replica.
  • Session hash wins this workload on hits (80.5%) and mean TTFT (15 ms). That is honest: for plain multi-turn chat with plenty of memory, sticky sessions are a strong baseline. It is blind to load, though. The busiest replica runs on average 1.28× the mean decode load, against 1.06× under the cost function, and its p99 is 115 vs 103 ms. With a 2 GB cache (lab try-this 3) it falls to 45.4% cached and 53 ms mean / 259 ms p99, because every replica must hold every system prompt. The cost function at credit 4 keeps 53.7%, 34 / 149 ms.
  • The cost function gives up some hits to stay balanced, and the credit is the dial: raising it from 1 to 4 sends 41% of turns home instead of 22%. At credit 4 it has the best p99 in the table.

What routing saves, in dollars

Every cached prompt token is prefill you don't run. Price it with the prefill floor and the course's $3.99 H100-hour (the input-token row of $ per million tokens):

$ saved = tokens avoided × 16.2 µs × $3.99 / 3,600 s per million requests, vs round-robin: session hash: 0.76B tokens × 16.2 µs = 3.4 GPU-h = $14 cost fn, credit 4: 0.56B tokens × 16.2 µs = 2.5 GPU-h = $10 at 50% of peak FLOPs, double both: about $27 and $20 prefill GPU-s in the run: 1,703 → 814 (−52%) · 1,703 → 1,048 (−38%)
OUR REASONING, NOT FROM A SOURCE

For an 8B model the dollar saving per request is small, because 8B prefill is cheap: $0.018 per million input tokens at peak. The bigger prizes are elsewhere. First, freed prefill capacity: 38–52% fewer prefill GPU-seconds means the same fleet takes more traffic before TTFT degrades. Second, TTFT itself. Third, bigger models: prefill cost scales with 2N, so the same tokens avoided on a 70B are worth about 70.6 / 8.03 ≈ 8.8× more. Long agent or coding sessions with 50k-token histories also have a much larger share of history tokens than our 40%. That is where the published 2–3× results come from.

Why it beats the alternatives

✗ Round-robin / least-requests

Even load, but a conversation's next turn finds its cache only 1/N of the time (12.6% in the lab). Kiely also warns that counting requests fails when "a request with 10,000 [input tokens] will unbalance a simple system".

✗ Hash the prefix (sticky)

Always warm, but popular prefixes pile onto one replica: 53% of traffic on 1 of 8 replicas, and TTFT grows to minutes. Adding or removing a replica also reshuffles the hashes.

✗ Sticky per session

Strong for plain chat (80.5% cached, best mean TTFT in the lab), but blind to load and memory. Decode load is lopsided (1.28×), and it collapses when caches are small (259 ms p99 at 2 GB). Our inference: it also reshuffles when replicas scale.

✓ Cost function over cache + load

Scores cached blocks against queued and running work on every replica. It gets most of the hits without hot spots, and one knob (the overlap credit) trades TTFT against even load. It has the best p99 in the lab and holds up when memory is scarce.

Is KV-aware routing always worth it?

No. It pays when prompts share long prefixes and a fleet has several replicas: multi-turn chat, agents and coding tools resending long histories, RAG over a fixed corpus, few-shot templates. It does little in these cases:

  • One replica, or one big TP/PP instance. There is nothing to route, and in-engine prefix caching (RadixAttention, cache-aware scheduling) does the whole job.
  • Prompts with no shared prefix (one-off summarisation of unique documents). The best possible hit rate is near zero, so routing on load alone is simpler.
  • Small volume. Kiely on Dynamo: "Unless you're operating with enough volume for disaggregation and KV-aware routing to matter, Dynamo will be unnecessary work". Session affinity at the load balancer gets much of the gain for chat.
  • When the index is wrong. Approximate mode can route to a pod that already evicted the prefix, so you pay the balancing cost without the hit. Precise mode fixes that with KV events, at the price of ZMQ plumbing and a tokenizer in the router's path.

Caches that live off the GPU change the calculation. Mooncake's pooled KV store and LMCache-style offloading let any replica fetch a prefix, so where the request lands matters less (Mooncake scheduling, and Dynamo's host and disk hit weights in the formula above).

Run it yourself

Run it: labs/kv-router.py [L] runs on your Mac in about 3 seconds (numpy + stdlib). It prints the workload, the router table above with the hit rate split into system prompt and history, the dollars saved, and Dynamo's 18 / 10 / 11 example. Try N_REP = 32: round-robin sends 3.1% of turns home, while the cost function at credit 4 keeps 49% home and needs 584 prefill GPU-seconds instead of 1,760.
