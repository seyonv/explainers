How MapReduce runs

Also called the MapReduce execution model: one master, many workers, a shuffle through local disks, and re-execution for fault tolerance. The source guide summarises Google's 2004 paper: execution overview, master state, failures, locality, task granularity, backup tasks and the combiner, then a short Hadoop coda.

Prime · 2 minutes before you read

The problem: On thousands of cheap machines something fails during every long job, and one slow disk can hold up the whole run. A job that restarts from scratch on each failure might never finish.

Where it fits: Second batch card. It runs the model from the previous card on a cluster, and it reuses cs-5's ideas about partial failure and retries: here the retry unit is a deterministic task.

In one breath

The master cuts the input into M splits and hands out M map tasks and R reduce tasks to idle workers. Each map worker writes its output to its own disk, cut into R regions by hash(key) mod R. Reduce worker r pulls region r from every map worker, sorts it by key and writes one output file. Because every task is a deterministic function of its input, a failed task is simply run again somewhere else.

1 TB input in 64 MB splits: M = 2^40 / 2^26 = 2^14 = 16,384 map tasks R = 4,000 (illustrative) decisions M + R = 16,384 + 4,000 = 20,384 state M · R = 16,384 × 4,000 = 65,536,000 entries ≈ 65.5 MB at ~1 byte paper's typical job: 200,000 × 5,000 = 10^9 entries ≈ 1 GB, on 2,000 machines

Both M and R should be much larger than the number of workers: small tasks balance load, and a dead worker's tasks spread across many machines. The M·R table is what caps them.

What happens when something fails

EventWhat the master doesWhy
Worker dies, map task completedReset to idle, run it again elsewhereIts output was on that machine's local disk, now unreachable
Worker dies, any task in progressReset to idle, run it againPartial output lives only in private temp files, so nothing half-done is visible
Worker dies, reduce task completedNothingIts output file is already in the replicated global file system
Master diesJob aborts; the client retriesThere is only one master, so the paper judged this rare enough
A task runs slowly (straggler)Near the end, start a backup copy; take whichever finishes firstOne slow disk or busy machine would otherwise set the finish time

Detection is by periodic pings. A reduce task commits by atomically renaming its temp file to the final name, so even if two copies finish, exactly one output file exists.

The code: one-machine simulation

def part(key):                       # stable hash(key) mod R
    return crc32(key.encode()) % R

def run_map(text, combine):
    regions = [defaultdict(list) for _ in range(R)]
    for w in text.split():
        regions[part(w)][w].append(1)            # emit (w, 1)
    if combine:                                  # combiner = reduce
        for reg in regions:
            for w in reg:
                reg[w] = [sum(reg[w])]
    return regions

# inside run_job: worker w0 dies after the map phase
for i, w in list(where.items()):
    if w == kill_after_map:
        del disk[w, i]                  # its local disk is gone
        state["map", i] = "idle"         # completed -> idle
        disk["w9", i] = run_map(SPLITS[i], combine)
        where[i] = "w9"
        state["map", i] = "completed"

Cost of a failure: O(work on the dead machine), not O(job). Only that worker's tasks rerun, and because map and reduce are deterministic the output is byte-for-byte the same as a failure-free run.

Why re-execution beats the alternatives

✗ Restart the whole job

On hundreds or thousands of cheap machines, failures are routine. A long job would keep losing all its work and might never finish.

✗ Replicate map output to GFS

Completed maps would survive a crash, but every intermediate byte would be written to several machines over the network, which the paper treats as the scarce resource.

✗ Just wait for slow machines

The job ends when its last task ends. Without backup copies, one straggler sets the finish time: the paper's sort took 44% longer.

✓ Deterministic tasks, rerun on failure

Any task can be rebuilt from its input split. Failures cost only the lost tasks, intermediate data stays one copy on local disk, and atomic commit hides duplicates.

Is this still how batch jobs run?

Hadoop MapReduce copied the design: input is an HDFS directory, map output is partitioned by a hash of the key, sorted, copied to reducers and written back to HDFS. Jobs are chained into workflows only by pointing one job's output directory at the next job's input, so every stage pays a full write to the replicated file system. Unix pipes, by contrast, stream through small in-memory buffers.

It's the wrong fit for iterative work (machine learning, graph algorithms) that re-reads the same data every round, for interactive queries, and for data that fits on one machine. Dataflow engines such as Spark keep intermediate data in memory and recompute lost pieces from their lineage, the same "rerun the deterministic task" idea. And with non-deterministic map or reduce functions, the paper promises only weaker semantics.

1 · Core model what to internalise, what to just look up

Keep it if it changes what you can explain, predict, compare, choose, build or debug. Otherwise it's reference.

Understand and remember

  • Map output goes to the worker's local disk, split into R regions by hash(key) mod R → reducer r pulls region r from every map → all values of a key meet at one reducer with no coordination
  • Map output lives on one local disk; reduce output lives in the replicated file system → a dead worker's completed maps must rerun, its completed reduces don't → a failure costs the dead machine's work, not the job
  • Tasks are deterministic functions of their input → rerunning gives byte-identical output → atomic rename commits exactly one copy → failures and backup copies are invisible in the result
  • The master keeps one entry per (map, reduce) pair → O(M·R) state caps task counts (16,384 × 4,000 ≈ 65.5 M entries) → many small tasks balance load and spread a dead worker's work, up to that cap
  • detail that matters A combiner runs reduce locally on each map's output → fewer pairs cross the network (65 → 47 bytes here) → legal only for commutative, associative reduces (sum yes, median no)
  • detail that matters The job ends when its last task ends → near the end, start backup copies of stragglers and take the first to finish → without them the paper's sort took 44% longer

Reference only

  • crc32 as the toy's stable hash
  • 16–64 MB split sizes and ~1 byte of master state per pair
  • the paper's 200,000 × 5,000 job on 2,000 machines
  • Hadoop's HDFS naming

4 · Compare against what you already know

vs Idempotency and retries: MapReduce reruns deterministic tasks; cs-5 retries requests with idempotency keys. What makes a retry safe in each, and what goes wrong when that property is missing?

Check
  • MapReduce: determinism plus atomic rename, so any copy's output is identical and only one commits
  • cs-5: an idempotency key lets the server recognise and dedupe a repeated request
  • without determinism, reruns disagree; without idempotency keys, a retried payment runs twice

vs Backfilling and gang scheduling: MapReduce wants thousands of small, independent tasks; distributed training needs all its GPUs at once. How does that difference change what a scheduler must do on failure and when placing work?

Check
  • small independent tasks can start one at a time and be rerun individually
  • a gang job is all-or-nothing: partial placement hoards resources, and losing one worker stalls the whole job
  • hence reservations and gang placement for training, simple re-execution for MapReduce

5 · Predict commit to an answer before revealing

A map function samples 1% of its records with an unseeded random generator. Its worker dies after some reducers have already pulled its regions, and the map reruns elsewhere. Commit first: is the job's output still equal to some failure-free run?

Reveal

No. The rerun samples a different 1%, so reducers that pulled from the first run and reducers that pull from the rerun see different data, and the combined output matches no single failure-free run. That's why the paper promises only weaker semantics for non-deterministic functions. Seeding the generator from the split (making the map deterministic again) restores the guarantee.
