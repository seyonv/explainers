Caching patterns

Also called cache-aside (lazy loading), write-through, write-back (write-behind) and write-around, plus the eviction policies LRU, LFU and TTL. The cheat-sheet's Memory Cache page mentions an "app-managed caching layer" in front of a database but never names the patterns, so this card supplies them.

In one breath

A cache is a small, fast copy of some of the database. A pattern answers two questions: who fills it on a read, and what happens to it on a write. An eviction policy decides what to throw out when it's full. The common default is cache-aside: the app checks the cache, reads the database on a miss, fills the cache, and deletes the cached key when it writes.

The four patterns, read path and write path

Cache-aside reads and write-through as the AWS caching whitepaper defines them; the delete on write is from Facebook's memcache paper; write-back and write-around as CPU and disk caches use the terms (Wikipedia, "Cache (computing)"). The catch is AWS's stated drawback for the first two rows and our inference for the last two.

Reads: 1 → 2 → 3. Writes: a, then b. Facebook's memcache paper calls this a "demand-filled look-aside cache" and deletes rather than updates on writes "because deletes are idempotent".

In Python: cache-aside over an LRU

from collections import OrderedDict

class LRU:
    def __init__(self, cap):
        self.cap, self.d = cap, OrderedDict()
    def get(self, k):
        if k not in self.d:
            return None
        self.d.move_to_end(k)            # now the most recent
        return self.d[k]
    def put(self, k, v):
        self.d[k] = v
        self.d.move_to_end(k)
        if len(self.d) > self.cap:
            self.d.popitem(last=False)   # drop least recent
    def delete(self, k):
        self.d.pop(k, None)

def cache_aside_get(cache, db, k):
    v = cache.get(k)                     # 1. try the cache
    if v is None:                        # 2. miss: read the db
        v = db[k]
        cache.put(k, v)                  # 3. fill the cache
    return v

def cache_aside_write(cache, db, k, v):
    db[k] = v                            # 1. the db is the truth
    cache.delete(k)                      # 2. invalidate, don't set

# cap   100: LRU 0.389  LFU 0.496  top-100 share 0.530
# cap  1000: LRU 0.672  LFU 0.729  top-1000 share 0.765
# read A: 1 (miss, filled)
# after write, cached: None | next read: 10

Time O(1) per get, put or delete · Space O(cap). OrderedDict is a hash table threaded with a doubly linked list, so moving a key to the end or popping the oldest never scans. The O(1) LFU in code/ keeps one such list per hit count.

Thundering herd: one hot key expires

When a hot key disappears (a TTL runs out or a write deletes it), every request that arrives before it's refilled misses at once and hits the database. Request coalescing lets the first miss load the row while the rest wait for its answer.

our run: 100 threads miss "hot" together → 100 DB queries; with coalescing → 1 Facebook, leases (1 token per key per 10 s): peak DB 17K/s → 1.3K/s = 13.1× lower

Why cache-aside + delete beats the alternatives

✗ No cache

Every read goes to the database: 200,000 DB reads in the simulation instead of 65,572 with a 1,000-entry LRU.

✗ Update the cache on write

Two concurrent writers can set the cache in the opposite order to their DB commits, leaving an old value cached with no end date.

✗ Write-back for app data

Fast writes, but the cache becomes the only copy of a write until it's flushed. A crashed cache node loses writes the user was told succeeded.

✓ Cache-aside, delete on write

The DB stays the only truth, the cache can evict or crash freely, and a delete sent twice does no harm. Add a TTL as a safety net.

Is it always the right choice?

No. Delete-on-write still has a race: a reader misses, reads the old row, the writer commits and deletes, then the reader sets the old row. Facebook's fix is a lease token that the delete invalidates, so the late set is refused. Coalescing and leases also add waiting and moving parts, which a low-traffic app doesn't need.

Pick write-through when data must be read right after it's written (fewer cold misses), write-around for write-heavy data that's rarely read back (logs, uploads), and write-back only where the cache itself is durable or losing a few writes is fine, as in a CPU cache or a disk controller with battery-backed memory. If the whole working set fits in RAM, an in-memory database removes the sync problem: see anti-caching.
