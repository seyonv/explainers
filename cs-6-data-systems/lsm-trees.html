LSM trees

Also called a log-structured merge tree; the parts are a memtable, SSTables (sorted runs) and compaction. It is the storage engine of LevelDB, RocksDB, Cassandra and HBase. The source guide names LSM trees only in passing ("high write throughput", "compaction-related performance issues") and describes the same design for flash as the FD-tree.

Prime · 2 minutes before you read

The problem: A B-tree updates pages in place, so a write-heavy workload becomes a stream of random page writes, up to ~41 bytes written per byte changed, which is exactly what flash handles worst.

Where it fits: Second storage card. It builds on the B-tree card's read/write trade-off and is the storage engine behind the Bigtable card that follows; log-structured memory later applies the same append-then-clean idea in RAM.

In one breath

Never update data in place on disk. Buffer writes in a sorted in-memory table, dump it to disk as one sorted, immutable file when it fills, and merge those files in the background. Writes become sequential and cheap. A read checks the newest place first and works back to older files, using a Bloom filter to skip files that can't hold the key.

In Python

class LSM:
    def __init__(self):
        self.mem, self.l0, self.l1 = {}, [], None

    def put(self, key, value):     # value None = tombstone
        self.mem[key] = value          # newest wins in memory
        if len(self.mem) >= MEM_LIMIT:
            self.l0.insert(0, Run(self.mem.items()))  # flush
            self.mem = {}
            if len(self.l0) >= L0_LIMIT:
                self.compact()

    def compact(self):                # merge L0 + L1 into L1
        merged = {}
        older = [self.l1] if self.l1 else []
        for run in older + self.l0[::-1]:   # oldest first
            merged.update(run.items)         # newer overwrites
        live = [(k, v) for k, v in merged.items() if v is not None]
        self.l1, self.l0 = Run(live), []     # last level: drop †

    def get(self, key):
        if key in self.mem:
            return self.mem[key]
        for run in self.l0 + [r for r in [self.l1] if r]:
            if run.bloom.might_have(key) and key in run.index:
                return run.index[key]     # newest file first
        return None

# get(3) -> None ['memtable', 'L0[0] read']   (tombstone)
# get(6) -> None ['memtable', 'L1 skip']      (Bloom filter)
# user writes 9, entries written to disk 15, write amp 1.67

Condensed from code/lsm-trees.py, which adds the Run and Bloom classes, the write counter and the read path printed above (python3 3.10).

Time: put is a memtable insert (O(log m) in a real skip list, O(1) in this dict) plus amortized background rewrites; get checks at most every L0 file plus one run per level, each a binary search. Space O(n), plus shadowed versions and tombstones until compaction reaches them.

levels, 1 GB: ceil(log10(1024 MB / 64 MB)) = ceil(log10 16) = ceil(1.20) = 2 write amp: 10 × 2 = 20 (1 TB instead: ceil(log10 16,384) = 5 → 10 × 5 = 50) B-tree: a 100 B row rewrites its whole 4 KB page: 4096 / 100 ≈ 41 (worst case) Bloom: k = round(10 × 0.693) = 7; (1 − e^−0.7)^7 = 0.5034^7 = 0.0082 = 0.82 % missing key, 4 L0 files + 2 levels = 6 runs: 6 reads unfiltered → 6 × 0.0082 = 0.049 filter RAM for the 10⁷-row table: 10 bits × 10⁷ = 10⁸ bits = 12.5 MB

Computed by code/lsm-trees.py. T·L is the usual upper estimate for leveled compaction (each entry is rewritten up to about T times per level); the RocksDB wiki says leveled write amplification is "often larger than 10". The 0.82% is the textbook filter; RocksDB's cache-friendly filter gets about 1% at 10 bits/key. The B-tree figure assumes each row update writes its page alone; batching lowers it.

Why it beats the alternatives for write-heavy data

✗ B-tree, updated in place

Every write lands on a random page: up to 41× write amplification for a 100 B row, and random writes are exactly what flash SSDs handle worst (the source's FD-tree motivation).

✗ Append-only log, no index

Writes are as cheap as they get, but a read must scan the whole log backwards. For 10⁷ orders that is up to 1 GB read per lookup.

✗ Log plus in-memory hash index

Bitcask-style: one seek per read, but every key must fit in RAM, and a range query like id BETWEEN 100 AND 200 needs a full scan because the hash has no order.

✓ LSM tree

Only sequential writes, sorted files so range scans work, keys don't need to fit in RAM, and Bloom filters cut a missing-key lookup from 6 reads to 0.05 expected.

So should everything be an LSM tree?

No. Pick it for write-heavy workloads: event logs, time series, metrics, message stores, anything ingesting faster than it's read. B-trees (PostgreSQL, InnoDB, SQLite) are still the better default for read-heavy OLTP: a read is one path down one tree, with no chance of checking several files, and there are no background merges competing with foreground work.

The cost the source warns about is real: "getting purge/compaction right is a hard engineering problem". Compaction steals disk bandwidth, can stall writes when L0 fills up, and old versions take extra space until it runs. If write amplification matters more than reads, size-tiered compaction (as in Cassandra) merges less often: lower write amplification, but more files per read and more space. That trade-off is from general practice (DDIA ch. 3), not from the source.

1 · Core model what to internalise, what to just look up

Keep it if it changes what you can explain, predict, compare, choose, build or debug. Otherwise it's reference.

Understand and remember

  • Writes go to a sorted memtable (plus a WAL) → a full memtable is flushed as one immutable sorted file → every disk write is sequential → ingest is cheap even on flash
  • Files are immutable, so updates and deletes are new entries → a read checks newest to oldest (memtable, L0 files, then each level) → the first match wins, which is why a tombstone hides older values
  • Compaction merges runs into the next level, keeping only the newest version → each entry is rewritten about T times per level → write amplification ≈ T · ⌈logT(N/M)⌉ = 10 × 2 = 20 for 1 GB
  • A per-file Bloom filter says ‘definitely not here’ or ‘maybe’ → with 10 bits/key and k = 7, false positives ≈ 0.82% → a missing-key lookup over 6 runs drops from 6 reads to 0.049 expected
  • detail that matters A tombstone can only be dropped when compaction reaches the last level → until then it must shadow older copies → deletes cost space and read work for a while
  • detail that matters L0 files overlap and are checked one by one → if flushes outpace compaction, L0 piles up → engines slow or stop writes (write stalls)

Reference only

  • RocksDB's defaults (×10 level multiplier, 64 MB write buffer) and its cache-friendly filter at ~1%
  • the toy MEM_LIMIT = 3 and L0_LIMIT = 3
  • skip list as the memtable structure
  • the FD-tree's name for the same design

5 · Predict commit to an answer before revealing

You cut the filter to 5 bits per key to save RAM. Commit first: roughly how many wasted reads does a missing-key lookup over 6 runs now cost, and is halving the RAM worth it?

Reveal

k = round(5 × 0.693) = 3, false-positive rate (1 − e−0.6)3 ≈ 9.2%, so 6 × 0.092 ≈ 0.55 expected wasted reads, more than 11× the 0.049 at 10 bits, to save 6.25 MB on 10⁷ keys. The false-positive rate falls roughly exponentially in bits per key, so the last few bits are cheap insurance for a workload with many misses.
