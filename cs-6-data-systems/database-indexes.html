B-trees and database indexes

Also called an index, a B+-tree (the variant databases actually use), a clustered or secondary index. The source guide's Index page covers the read-versus-write trade-off, why B-trees beat hash indexes, and a list of specialised indexes and index chores.

In one breath

An index is an extra, sorted copy of some columns that points back at the rows, so the database can jump to a value instead of reading the whole table. A B-tree keeps that copy in pages of hundreds of keys each, so even 10 million rows are only 3 pages deep. The price: every write must also update every index.

Worked example: find one order among 10 million

The orders table from this course: 107 rows of about 100 bytes, 4 KB pages (illustrative sizing). We index created_at; each index entry is an 8-byte timestamp plus an 8-byte row pointer.

The primary (clustered) index on id stores the rows themselves in its leaves: 250,000 → 977 → 4 → 1, so 4 levels. If every page were only half full (the B-tree minimum, fan-out 128), this index would be 78,125 → 611 → 5 → 1, also 4 levels.

In Python: bulk load, then look up

import bisect

def bulk_load(keys, fanout):
    """Build a B-tree bottom-up from sorted keys (no inserts)."""
    nodes = [keys[i:i + fanout] for i in range(0, len(keys), fanout)]
    levels = [nodes]                       # levels[0] = leaves
    while len(nodes) > 1:
        firsts = [n[0] for n in nodes]     # separator = child's 1st key
        nodes = [firsts[i:i + fanout]
                 for i in range(0, len(firsts), fanout)]
        levels.append(nodes)
    return levels[::-1]                    # root level first

def search(tree, key, fanout):
    i = 0
    for level in tree[:-1]:                # branch levels: cached
        j = bisect.bisect_right(level[i], key) - 1
        i = i * fanout + max(j, 0)         # full nodes: child index
    leaf = tree[-1][i]                     # the one disk read
    j = bisect.bisect_left(leaf, key)
    return j < len(leaf) and leaf[j] == key, len(tree)

tree = bulk_load(range(10**7), 4096 // 16)
print([len(level) for level in tree])
print(search(tree, 7_654_321, 256), search(tree, 10**7, 256))
# → [1, 153, 39063]
# → (True, 3) (False, 3)

Real output under python3 3.10. The saved file also runs the one-hour range scan (3,600 found, 17 pages), the half-full tree and the bitmap AND.

Time O(logB n) page reads per lookup, O(logB n + k/B) for a range of k keys · Space O(n). Each page read divides the search space by the fan-out B = 256 instead of by 2, and the tree stays balanced, so every leaf is the same depth.

Why it beats the alternatives

✗ No index: full scan

Read all 250,000 pages to find one order. Writes are cheapest, which is the source's trade-off: fine only if you rarely read.

✗ Sorted file, binary search

⌈log₂ 250,000⌉ = 18 page reads, each a random disk read. And inserting in the middle shifts half the file, 125,000 pages on average.

✗ Hash index

One I/O for an exact match, but no ranges, no prefix of a composite key, and long overflow chains when many rows share a key value.

✓ B-tree

3 page reads, 2 of them cached, so 1 disk read. One hour of orders in 17 reads. An insert touches one leaf, plus a split now and then.

The rest of the source, one line each

Prefix compressionKeys "Smith, James", "Smith, Jane", "Smith, John" store "Smith, J" once: 12 + 11 + 11 = 34 bytes becomes 8 + 4 + 3 + 3 = 18. Branch pages keep only the shortest separator, e.g. "Smith, Jo" between Jane and John. More keys per page means a bigger fan-out.
FD-treeFor flash, where random writes are expensive: a small in-memory head tree takes all writes and is merged in batches into sorted runs on disk, a little at a time (de-amortized). The same idea as an LSM tree.
Bulk loadSort the keys and build the tree bottom-up, exactly like bulk_load above: no splits, full pages. The source calls it orders of magnitude faster than row-at-a-time inserts.
Other choresDelete in bulk by dropping a partition; defragment so leaves are contiguous again; verify invariants, made robust by fence keys (copies of separator keys kept in the child); drop an index by editing metadata only.
Merged indexStore Orders and Order_Details in one B-tree sorted by order id, so each order sits next to its lines: a join without the extra I/O, and no schema change.
B-tree on hashesIndex hash(key): keys spread evenly, and you keep ordered traversal, but only in hash order.

The source says a B-tree on hash values keeps "range-scan benefits"; a range of hashes is not a range of the original keys, so BETWEEN on the key no longer works. Corrected here. The source's footnote [^14] (on the merged index's common key) is referenced but missing.

Should you index every column?

No. Every index is another B-tree to update on each insert, update and delete, which is the source's whole trade-off: index the columns your real queries filter, join or sort on. A secondary-index hit also costs a second read to fetch the row, so a query that matches a large share of the table is often faster as a full scan; databases pick using statistics. Covering indexes (the index holds every column the query needs) skip that second read (DDIA ch. 3).

For write-heavy workloads, a log-structured merge tree (LSM) usually beats a B-tree: it turns random writes into sequential ones, like the FD-tree above. For exact-match lookups on data that fits in memory, a hash table is simpler. For analytics over a few low-cardinality columns, bitmap or column-store indexes win.
