Checkpoint 2: batch jobs, traversals and recursive queries

Ties together the MapReduce model, how MapReduce runs, querying graphs, how hard a query is and semi-naïve evaluation: how to process more data than one pass can handle, and how to avoid redoing work you've already done.

How to use this page. Close the five cards. Answer each question in writing, in full sentences, before opening its Check. A wrong or shaky answer isn't a failure: it tells you exactly which section to reopen. The questions are mixed on purpose, so you have to work out which idea applies before you can answer.

1 · Mixed retrieval

  1. which concept?A nightly job computes each product's median rating over 10 TB of reviews. Someone adds a combiner that runs the reducer on each map task's output "to cut the shuffle". The job gets faster and the answers change. Which idea explains it?
    Check
    • a combiner is a local partial reduce, legal only when reduce is commutative and associative
    • a median of per-split medians is not the median of all values, so the output is wrong
    • sum and count combine safely; a median needs all values, or an approximate sketch

    Missed it? Reopen how MapReduce runs, the Combiner row of "The words".

  2. A worker dies after finishing 3 map tasks and 1 reduce task, while running a fourth map. Which of those tasks does the master rerun, and why exactly those?
    Check
    • the 3 completed maps: their output sat on that worker's local disk, now unreachable
    • the in-progress map: its partial output was only in private temp files
    • not the completed reduce: its output is already in the replicated global file system

    Missed it? Reopen how MapReduce runs, "What happens when something fails".

  3. which concept?A team times a triangle-finding query written as three nested loops: doubling the table makes it 8× slower. Then they add a fourth variable to the query on the original table of 1,000 values, and it gets 1,000× slower. Which idea explains both numbers?
    Check
    • k nested loops over n values try nk assignments
    • data complexity (query fixed, k = 3): doubling n multiplies the work by 2³ = 8
    • expression complexity (data fixed): each extra variable multiplies the work by n = 1,000

    Missed it? Reopen how hard is a query?, "Why data and expression complexity split".

  4. On the property-graph schema, which index does each hop of "who knows someone who created lop?" use, and why would the query scan without it?
    Check
    • both hops walk edges backwards, from head to tail, so both use edges_heads
    • hop 1: lop's in-edges labelled created (from marko and josh); hop 2: in-edges labelled knows into those creators (marko → josh)
    • with only the tail indexed, a backward hop has to scan the whole edge table

    Missed it? Reopen querying graphs, the worked example's backward query.

  5. On a 6-node chain, naïve evaluation of transitive closure makes 70 derivations and semi-naïve 15, in the same 6 rounds. What does semi-naïve skip, and why is skipping it safe?
    Check
    • it joins only δ, the facts that were new last round, instead of all of tc
    • any combination made only of old facts was already joined in an earlier round
    • so every genuinely new fact still gets derived; naïve re-derives the known ones every round

    Missed it? Reopen semi-naïve evaluation, the worked example.

  6. which concept?A fraud team needs two things from a graph of 106 accounts: every pair of accounts connected by any chain of transfers, recomputed nightly; and, when an account is flagged, everything reachable from it right now. Which method fits each, and why not the same one for both?
    Check
    • all pairs: a fixpoint, evaluated semi-naïvely (or WITH RECURSIVE), since you need every derived fact
    • one flagged account: BFS or a traversal from that one vertex, Ω(V + E) at worst, following only its paths
    • the full closure can hold up to V² facts; computing it for one question wastes almost all of it

    Missed it? Reopen semi-naïve evaluation, "How hard can a recursive query be?", and querying graphs, "In one breath".

  7. 1 TB of input in 64 MB splits, with R = 4,000 reducers. How many map tasks, and what does the M·R table cost the master?
    Check
    • M = 240 ÷ 226 = 16,384
    • M·R = 65,536,000 entries, ≈ 65.5 MB at about a byte each
    • scheduling decisions are only O(M + R) = 20,384; the table is what caps how fine-grained tasks can be

    Missed it? Reopen how MapReduce runs, "Sizing".

3 · Project: transitive closure as a chain of MapReduce jobs

What it reinforces: map, shuffle and reduce as a join (the model), the per-job cost of chaining jobs (execution), naïve vs semi-naïve rounds (semi-naïve evaluation), polynomial growth in the data (query complexity) and a single-source traversal as the alternative (querying graphs).

Use run_mapreduce from code/mapreduce-model.py and chain from code/semi-naive-datalog.py. In about 40 lines of Python:

  1. One round as one job. Write a map that keys each left fact tc(x, z) by z and each edge(z, y) by z, tagging which relation it came from, and a reduce that pairs every left x with every edge y under the same key. Count the pairs the map emits (the shuffle).
  2. Naïve chain. Start with tc = edge. Each round, run the job with all of tc on the left; stop when a job finds no new fact. Count jobs and total shuffled pairs.
  3. Semi-naïve chain. Same, but put only δ (last round's new facts) on the left.
  4. Scale. Run both on the 6-node and the 12-node chain. How does the gap grow?
  5. One source. For the 6-node chain, run a BFS from node 1 and count the nodes reached and edges looked at. Cross-check the closure's size with the card's SQLite WITH RECURSIVE query.
Done when: both chains produce the same closure, you have job and pair counts for n = 6 and n = 12, and you can explain in one sentence each why semi-naïve shuffles fewer pairs but runs the same number of jobs, and why BFS is the right tool for one source.
Check: the numbers (computed with a Python version of this exact project)
  • 6-node chain: 15 facts. Naïve: 5 jobs shuffling 10 + 14 + 17 + 19 + 20 = 80 pairs (tc sizes 5, 9, 12, 14, 15, plus 5 edges each). Semi-naïve: 5 jobs shuffling 10 + 9 + 8 + 7 + 6 = 40 pairs (δ sizes 5, 4, 3, 2, 1, plus 5 edges). The last job of each finds nothing new.
  • 12-node chain: 66 facts, 11 jobs each; naïve 627 pairs, semi-naïve 187. The gap grows from 2.0× to about 3.4× as n doubles, because naïve's left side grows with tc while δ stays small.
  • Same number of jobs: the number of rounds is set by the longest path, not by how much each round joins. Every job still pays start-up and a DFS write, which is the MapReduce card's point about iterative work.
  • BFS from node 1: 5 nodes reached, 5 edges looked at. The SQLite cross-check gives 15 facts.
