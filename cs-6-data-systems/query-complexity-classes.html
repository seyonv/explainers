How hard is a query?

Also called query complexity, or data versus expression complexity (with "combined complexity" when both grow). The source guide's Run-time Complexity of Graphs page opens with it: the Turing-machine model, the chain LOGSPACE ⊆ PTIME ⊆ NP ⊆ PSPACE, completeness, and why relational calculus (CALC) sits in LOGSPACE and AC0.

Prime · 2 minutes before you read

The problem: Saying ‘this query is slow’ from one run on one database can't tell you how it will grow. You need to know which input is growing (the data or the query) and how cost scales with it.

Where it fits: Fourth card of the batch and queries part. It builds on cs-1's big-O and on the previous card's multi-hop queries, and it sets up the next card: recursive (fixpoint) queries are PTIME-complete.

In one breath

Measure a query language by the resources a Turing machine needs to answer its queries, as the input grows. The catch is which input: grow the database with the query held fixed (data complexity), or grow the query over a fixed database (expression complexity). Databases dwarf queries, so data complexity is the one that usually matters, and there plain relational queries are about as easy as computation gets.

Worked example: the classes, one query in each

AC⁰ ⊊ LOGSPACE ⊆ PTIME ⊆ NP ⊆ PSPACE ⊊ TIME(Hyp) (the source's chain, plus AC⁰) known to be strict: AC⁰ ≠ LOGSPACE (parity, Furst–Saxe–Sipser) LOGSPACE ≠ PSPACE (space hierarchy) so at least one of LOGSPACE ⊆ PTIME ⊆ NP ⊆ PSPACE is strict; nobody knows which

Every example is data complexity (the query is fixed) except the second PSPACE one. The 3-colouring example is Fagin's theorem: NP is exactly what existential second-order logic can say. Transitive closure itself is easier than PTIME-complete (it is in NL); the hard fixpoint queries are other ones.

Why data and expression complexity split: nk

The source's LOGSPACE argument: evaluate a CALC query with one pointer per variable, each scanning the input. With k variables over n values that is k nested loops.

work=nkassignments tried memory=k·⌈log2n⌉bits of pointers
nvalues in the database (the input grows here in data complexity)10 → 80 below kvariables in the query (the input grows here in expression complexity)2 → 6 below

Fix k and the work is a polynomial of degree k: doubling n multiplies it by 2k. Fix n and the work is exponential in the query: each extra variable multiplies it by n. Memory stays logarithmic in n either way.

The database is a ring of n people where each knows the 2 on either side; the query is "k people who all know each other" (a k-clique, a plain conjunctive query). The ring has no 4 mutual friends, so k ≥ 4 finds nothing but still tries every assignment.

In Python

from itertools import product
from math import ceil, log2

def ring(n, d=2):
    """i knows j if they sit within d seats on a ring of n."""
    return {(i, j) for i in range(n) for j in range(n)
            if i != j and min((i - j) % n, (j - i) % n) <= d}

def clique_query(E, n, k):
    """Evaluate q(x1..xk) = AND of E(xi, xj) for all i < j.
    Builds the whole answer; returns (answers, assignments tried).
    E stands in for the read-only input tape."""
    tried = found = 0
    for xs in product(range(n), repeat=k):     # k nested loops
        tried += 1
        if all((xs[i], xs[j]) in E
               for i in range(k) for j in range(i + 1, k)):
            found += 1
    return found, tried

def pointer_bits(n, k):
    return k * ceil(log2(n))    # k pointers, log n bits each

# the __main__ demo loops n over 10..80 (k = 3), then k over 1..6
# → Data complexity: fixed query k = 3, grow n
#     n=10  tried   1,000      answers  60  memory 12 bits
#     n=20  tried   8,000  x8  answers 120  memory 15 bits
#     n=40  tried  64,000  x8  answers 240  memory 18 bits
#     n=80  tried 512,000  x8  answers 480  memory 21 bits
#   Expression complexity: fixed n = 10, grow k
#     k=1   tried        10      answers  10  memory 4 bits
#     k=2   tried       100 x10  answers  40  memory 8 bits
#     k=3   tried     1,000 x10  answers  60  memory 12 bits
#     k=4   tried    10,000 x10  answers   0  memory 16 bits
#     k=5   tried   100,000 x10  answers   0  memory 20 bits
#     k=6   tried 1,000,000 x10  answers   0  memory 24 bits

Time O(nk · k²) · Space O(k log n) beyond the input. Every assignment of the k pointers is tried once and checks at most k(k−1)/2 edges; the loop state is just the k pointers. Here E is a Python set standing in for the read-only input tape; a real LOGSPACE machine would rescan the input instead of building it.

The source writes the recognition problem as "is u ∈ I?" and credits "Savich"; corrected here to u ∈ q(I) and Savitch's theorem.

Why the reduction must be weaker than the class: with PTIME reductions every nontrivial problem in PTIME would be PTIME-complete (the reduction could just solve it), so P-completeness uses LOGSPACE reductions. The source's AC0 line credits projection; more precisely, each quantifier becomes one unbounded-fan-in gate (∃ is OR, ∀ is AND), so circuit depth depends on the query, not the data (our reading, following the standard proof).

Why data complexity beats the alternatives

✗ Time it on one database

Tells you about that machine, that optimizer and that n. It can't tell a query that grows ×8 per doubling from one that grows ×10 per variable.

✗ Expression complexity alone

CALC is PSPACE-complete in the query. Every language then looks hopeless, though real queries are a few lines long.

✗ Combined: both grow

Plain conjunctive queries become NP-complete, the same as 3-colouring. True, but it hides that a fixed join is cheap on huge data.

✓ Data complexity

Fixes the part that stays small (the query) and grows the part that gets big, which the source calls the usual situation. It separates CALC (AC0) from Datalog (PTIME) from while (PSPACE).

Is data complexity always the right lens?

No. When queries are big or machine-generated (100-way joins from an ORM, graph pattern queries, query containment inside an optimizer), k is not small and nk bites: 6 variables on 10 people is already 106 tries above. Then people study combined complexity, query width (acyclic and bounded-treewidth queries are polynomial even in k) and worst-case-optimal joins.

And a class is a worst-case, asymptotic label. "In PTIME" allows n³, which at the course's 107 rows is 1021 steps; engines want near-linear work, which is what indexes and hash joins buy. The nested loops above are the textbook evaluator, not how a database runs the query.

Understand and remember

  • Evaluate a k-variable query with one pointer per variable → k nested loops over n values → nk assignments tried but only k·⌈log₂ n⌉ bits of state → CALC is in LOGSPACE
  • Hold the query fixed and grow the data → k is a constant → the work is a polynomial of degree k (×2³ = 8 per doubling for k = 3) → data complexity is polynomial or better for fixed joins
  • Hold the data fixed and grow the query → the work multiplies by n per extra variable → expression complexity is exponential in the query (CALC PSPACE-complete, conjunctive queries NP-complete)
  • Databases dwarf queries → data complexity is the usual lens → it separates CALC (AC⁰) from fixpoint queries (PTIME-complete) from while (PSPACE-complete)
  • detail that matters Each quantifier becomes one unbounded fan-in gate (∃ = OR, ∀ = AND) → circuit depth depends on the query, not the data → constant depth, so CALC ⊆ AC⁰, and parity (not in AC⁰) is beyond it

5 · Predict commit to an answer before revealing

Evaluate the same triangle query on the ring with an index: for each ordered edge (x, y), look only at y's neighbours z and check (x, z). Commit first: does the query's complexity class change, and roughly how many checks does it do at n = 80?

Reveal

The class doesn't change: it's a property of the language's hardest queries, not of one evaluator. The work does: the ring has 4 neighbours per person, so 4n ordered edges × 4 neighbours = 16n checks, 1,280 at n = 80 against the nested loops' 512,000 tries. That's the gap between the textbook evaluator and what indexes and hash joins buy.
