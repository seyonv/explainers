Querying graphs

Also called graph traversal, navigational queries, or property-graph queries. The source guide frames it as Bachman's programmer-as-navigator, then shows a vertices/edges schema in SQL and a three-line Gremlin session from TinkerPop.

In one breath

Start at a known record and follow relationships from it, one hop at a time, instead of scanning everything and filtering. Any store can do this if each hop is an index lookup: two tables, vertices and edges, with an index on each end of the edge, let a query walk forward along edges and backward against them at the same cost.

Worked example: what did the people marko knows create?

TinkerPop's classic toy graph without its sixth vertex (peter), so the ids and weights match the source's Gremlin output. Green = the 2-hop answer; grey = a branch that dies.

The source's schema, run as is in sqlite3, and the 2-hop query in both directions:

-- forward: marko -knows-> ? -created-> ?
SELECT json_extract(v.properties, '$.name')
FROM edges e1
JOIN edges e2 ON e2.tail_vertex = e1.head_vertex
JOIN vertices v ON v.vertex_id = e2.head_vertex
WHERE e1.tail_vertex = 1 AND e1.label = 'knows'
  AND e2.label = 'created'
→ lop, ripple
  SEARCH e1 USING INDEX edges_tails (tail_vertex=?)
  SEARCH e2 USING INDEX edges_tails (tail_vertex=?)
  SEARCH v  USING INTEGER PRIMARY KEY (rowid=?)

-- backward: who knows someone who created lop (v3)?
... WHERE e2.head_vertex = 3 AND e2.label = 'created' ...
→ marko
  SEARCH e2 USING INDEX edges_heads (head_vertex=?)
  SEARCH e1 USING INDEX edges_heads (head_vertex=?)

Output and EXPLAIN QUERY PLAN from SQLite 3.53.4 under Python 3.10. Forward hops use edges_tails, backward hops use edges_heads: that pair of indexes is what makes the relational schema walkable both ways.

The same walk, one traverser at a time

A TinkerPop traverser is a small record: the object it's on now, the path that led there, and a loop count. Each step turns every traverser into zero or more new ones.

Edges looked at: 3 at hop 1 (marko's out-edges) + 0 + 2 at hop 2 = 5 of 5 here, but only because the graph is tiny; the count is the degrees on the path, not the size of the graph.

The Gremlin snippet in plain Python

out_e = {v: [] for v in VERTICES}   # adjacency dict
for eid, (t, h, lab, w) in EDGES.items():
    out_e[t].append({"id": eid, "label": lab, "head": h,
                     "weight": w})

def V(): return list(VERTICES)          # g.V
def names(vs): return [VERTICES[v]["name"] for v in vs]
def outE(vs): return [e for v in vs for e in out_e[v]]
def weights(es): return [e["weight"] for e in es]

def out(travs, label):         # traverser = (vertex, path)
    return [(e["head"], path + [e["head"]])
            for v, path in travs for e in out_e[v]
            if e["label"] == label]

print(V())                  # → [1, 2, 3, 4, 5]
print(names(V()))
# → ['marko', 'vadas', 'lop', 'josh', 'ripple']
print(weights(outE(V())))   # → [0.4, 0.5, 1.0, 1.0, 0.4]
travs = out(out([(1, [1])], "knows"), "created")
print([names(p) for _, p in travs])
# → [['marko', 'josh', 'ripple'], ['marko', 'josh', 'lop']]

The source prints only the first two results of each line. Its parenthesis-free g.V.outE.weight is Groovy shorthand (TinkerPop 2 style); standard TinkerPop3 Gremlin writes g.V().outE().values('weight').

Time O(log E + d) per hop · Space O(V + E), plus two edge indexes. Each hop is one index descent to the vertex's edges, then a read of its d edges, so cost follows the degrees along the path, not the table size. Keeping the path copies it into every traverser, which is why TinkerPop turns path tracking off when a query doesn't need it.

Why it beats the alternatives

✗ Edges without indexes

Every hop scans the whole edge table. At an illustrative 107 edges that's 107 rows per hop, against about 3 index pages (fan-out 256, 2563 = 16.8M) plus the matching edges.

✗ Only the tail indexed

Forward hops are fast, but "who points at lop?" falls back to a scan. The source indexes both ends so the walk runs backward as cheaply as forward.

✗ One table per relationship

A knows table, a created table… Every new kind of edge is a schema change, and a query that follows "any edge" must union them all.

✓ Vertices + edges, both ends indexed

Any vertex can link to any other with any label and JSON properties. Each hop is an index lookup in either direction, and new relationship types need no schema change.

Do you need a graph database for this?

Often not. For a fixed number of hops, the two-index schema above is plain SQL, and WITH RECURSIVE handles "any number of hops" (the saved code finds all 4 vertices reachable from marko that way). Graph databases like Neo4j earn their place when queries are deep and variable-length, or need built-ins such as shortest path, Dijkstra and all simple paths, which the source lists for Neo4j, and when a declarative language (Cypher, Gremlin) is easier to read than a stack of self-joins.

They're the wrong tool when most queries aggregate or scan (totals per customer, reports): that is a relational or column-store job. And whichever you pick, don't depend on result order unless you sort: the source warns that TinkerPop's iteration order can change between releases, and our [0.4, 0.5] matching the source is an insertion-order accident.
