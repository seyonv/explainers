Designing an autodiff tape

Also called reverse-mode automatic differentiation, the adjoint method, backpropagation (machine learning) or AAD, adjoint algorithmic differentiation (finance). The source guide poses it as a hedge-fund interview prompt with no answers: price thousands of contracts, get sensitivities to hundreds of parameters, and design the tape that makes that cheap. This card answers it.

Prime · 2 minutes before you read

The problem: A pricer that needs sensitivities to 500 market parameters by bumping each one pays 501 full valuations, with a step size that trades truncation error against rounding error. Doing that for thousands of contracts is too slow and too noisy.

Where it fits: Last case-study card. It builds on cs-3's topological sort (the backward pass visits nodes in reverse topological order) and answers the source's interview prompt with a design; cs-10's Monte Carlo and Greeks cards are where the pricer lives.

Read with these questions (answer them in your head as you go; don't take notes line by line):

  1. Why does one backward pass give ∂f/∂x for every input at once, while bumping needs one extra valuation per input?
  2. Why must adjoints accumulate with +=, and where does that show up in f(x, y) = x·y + sin x?
  3. Why does the backward pass have to visit nodes in reverse topological order, and why is that just reverse recording order on a tape?
  4. What does keeping only √n checkpoints cost, and why is √n the best segment length?
  5. Why does a digital payoff give Delta = 0 through the tape, and what are the two fixes?

In one breath

Run the pricer once and write every operation onto a list, the tape, with each result's local derivatives. Then walk the tape backwards, pushing "how much does the output move if this value moves" (the adjoint) from each node to its inputs. One backward walk gives the derivative with respect to every input, however many there are.

The rule: the adjoint of a node

v¯iadjoint of node i = ∑j∈children(i) v¯jalready known · ∂vj∂vilocal, saved on the tape seed f¯=1
v̄i∂f / ∂vi: how much the final output moves per unit move in vithe Greek, at an input children(i)nodes that used vi as an input; later on the tapex feeds a and b ∂vj/∂viderivative of one operation, recorded during the forward pass∂(x·y)/∂x = y
adjoint[i] = sum(adjoint[j] * local[j][i] for j that used i) strict unary chain (the source's case): adjoint[k] = adjoint[k+1] * f_k'(v_k)

Every child must be finished before its parent is read, so the backward pass visits nodes in reverse topological order. On a tape that's simply reverse recording order.

In Python: a tape in 30 lines

import math

class Var:
    def __init__(self, val, parents=()):
        self.val = val
        self.parents = parents      # tuple of (Var, local gradient)
        self.grad = 0.0             # the adjoint, filled by backward
    def __add__(self, o):
        return Var(self.val + o.val, ((self, 1.0), (o, 1.0)))
    def __mul__(self, o):
        return Var(self.val * o.val, ((self, o.val), (o, self.val)))

def sin(a):
    return Var(math.sin(a.val), ((a, math.cos(a.val)),))

def backward(out):
    order, seen = [], set()
    def visit(v):                   # DFS post-order = topological
        if id(v) not in seen:
            seen.add(id(v))
            for p, _ in v.parents:
                visit(p)
            order.append(v)
    visit(out)
    out.grad = 1.0                  # seed: d out / d out
    for v in reversed(order):       # successors before predecessors
        for p, local in v.parents:
            p.grad += v.grad * local  # chain rule, accumulated

x, y = Var(2.0), Var(3.0)
f = x * y + sin(x)
backward(f)
print(f.val, x.grad, y.grad)
# → 6.909297426825682 2.5838531634528574 2.0

Time O(ops) · Space O(ops). The backward pass touches each recorded edge once, so it costs about as much as the forward pass. The catch is memory: every intermediate value has to stay alive until the backward pass reads it.

The source's tape: why a plain array isn't enough

The prompt wants a strict unary chain that grows at the end, drops old nodes (a sliding window), gets cut in the middle when a barrier is knocked out (everything downstream goes), and is split into segments for checkpointing. A design that fits: a doubly linked list of fixed-size segments, each segment an array of nodes plus the value at its start.

Trading memory for recompute: √n checkpoints

Keep only the value at the start of each segment. On the way back, re-run one segment forward from its checkpoint, back-propagate through it, throw it away, move to the previous one. Checkpoints plus one live segment is n/s + s values, smallest at s = √n.

Gradients match bit for bit (the chain is illustrative, a stand-in for time steps of a path). Chen et al. report the same shape for deep nets: O(√n) memory for about one extra forward pass. PyTorch ships it as torch.utils.checkpoint.

Plugging into PyTorch without breaking the gradient

For the Bermudan swaption's linked list of exercise dates (date, discount factor, exercise-value tensor): inside a custom torch.autograd.Function.forward, inputs are handed over with history tracking switched off, so a list built there is invisible to autograd. Two ways that keep gradients flowing: build the list outside any custom Function from ordinary tensor ops, so every tensor field has its own grad_fn; or, if you need a custom Function, save the tensors with ctx.save_for_backward and write backward to walk the list in reverse and return one gradient per input. The list is plain Python holding tensors; the tape lives in the tensors. (Our design, following the PyTorch docs.)

Non-differentiable payoffs

A call, max(S − K, 0), is fine: its slope is 0 or 1 except at one point. A digital, 1{S > K}, has slope 0 almost everywhere, so a tape returns Delta = 0. Fix it by smoothing the step (a sigmoid of width ε) or by the likelihood-ratio trick, which differentiates the probability density instead of the payoff.

Why it beats the alternatives

✗ Bump and reprice

Finite differences: 1 + N full valuations, 501 for N = 500, and the step size trades truncation error against rounding error. Useless on digitals, where a small bump rarely crosses the strike.

✗ Symbolic differentiation

Differentiate the formula by hand or with a CAS. Exact, but expressions blow up with repeated subterms, and a pricer with loops, branches and a Monte Carlo isn't one formula.

✗ Forward-mode AD

Carry a derivative alongside each value (dual numbers). No tape, no extra memory, but one pass per input: N passes for N sensitivities, the same scaling as bumping.

✓ Reverse-mode tape

One forward and one backward pass for all N sensitivities, exact to rounding (2.4e-11 off here). Pays in memory, which checkpointing buys back.

Is reverse mode always the answer?

No. It wins when there are many inputs and few outputs: one portfolio value, hundreds of market parameters. With few inputs and many outputs (a Jacobian that's tall rather than wide, or one parameter feeding thousands of prices), forward mode is cheaper and needs no tape. For one or two Greeks, bump-and-reprice is often the pragmatic choice: no new code paths and nothing to go stale.

The tape is also the bottleneck in memory, not flops: it grows with every operation, which is why the prompt asks about checkpointing on a GPU. And the source's "strict unary chain" is a simplification: real pricers fan in (a portfolio sums many contracts), which is why the general rule sums over children.

The source says the adjoint method "steps through time going forward to the payoff"; that's only its first half. The sensitivities come from the second sweep, which runs backwards from the payoff.

Understand and remember

  • Record each operation and its local derivatives on the forward pass → seed the output's adjoint at 1 → walk the tape backwards, adding adjoint × local derivative into each input → every ∂f/∂input from one backward pass, about the cost of one forward pass
  • A value used by several operations receives an adjoint from each → adjoints must be summed (+=), not assigned → x in x·y + sin x gets 3 + cos 2 = 2.583853
  • Every intermediate value must stay alive until the backward pass reads it → memory O(ops) → keep one checkpoint per segment and recompute segments on the way back → n/s + s values, minimal at s = √n (10,001 → 200 values for one extra forward pass)
  • A pathwise tape differentiates the payoff along each path → a step payoff has slope 0 almost everywhere → Delta = 0 → smooth the step or differentiate the density instead (likelihood ratio)
  • detail that matters A doubly linked list of fixed-size segments → O(1) append, drop-oldest and cut-after → fits the prompt's sliding window, barrier cut and checkpoint boundaries better than one flat array
  • detail that matters Inside a custom torch.autograd.Function.forward history tracking is off → a list built there is invisible to autograd → build it from ordinary tensor ops, or save tensors and write backward yourself

Check

  • reversed, each node is processed after every node that used it

Check

  • tape: one simulation forward and one backward for all N

5 · Predict commit to an answer before revealing

A risk system needs each of 1,000 contracts' own sensitivities to the same 2 parameters (not the portfolio total). Commit first: reverse mode, forward mode or bumping, and how many passes does each take?

Reveal

Forward mode: 2 passes, one per parameter, each carrying derivatives for all 1,000 outputs at once. Reverse mode needs a backward pass per output: 1,000. One-sided bumping needs 1 + 2 = 3 valuations, cheap here but approximate. Reverse mode's advantage flips when outputs outnumber inputs.
