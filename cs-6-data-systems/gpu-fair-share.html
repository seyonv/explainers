Fair-share GPU scheduling

Also called fair-share scheduling, weighted max-min fairness, or hierarchical fair queueing; with several resource types, dominant resource fairness (DRF). The source guide designs a shared GPU cluster: equal shares per user, split among each user's jobs by priority, plus priority bands, preemption and DRF.

Prime · 2 minutes before you read

The problem: Expensive GPUs shared by several teams: first come, first served lets one team's queue take everything for a week; static quotas leave GPUs idle; and when jobs also need CPU cores, being ‘fair on GPUs’ can still strand resources.

Where it fits: First case-study card. It builds on cs-7's CPU scheduling and cs-5's load balancing, and on the course's amplification lens (idle GPU-hours are waste). The next two cards add backfilling, gang placement and the user's view.

In one breath

Every user is promised a slice of the cluster. The slice is then divided among that user's jobs, and anything a user leaves idle goes to others until they want it back. When jobs need two scarce things at once (GPUs and CPU cores), DRF compares users by the resource each one uses the most of, and keeps those "dominant shares" equal.

These pull against each other: a week-long job holding GPUs hurts fairness, and reserving GPUs for fairness hurts utilization. The source gives these targets without a citation.

Worked example 1: the source's split, re-derived

Two users share the cluster equally. Within a user, each job gets a weight equal to its priority, divided by the sum of that user's priorities.

Matches the source's figure: 37.5 + 12.5 + 25 + 12.5 + 12.5 = 100%. The shares are guarantees, not caps: if B goes idle, A's jobs may use B's half until B returns, and then the scheduler preempts just enough of A to give B its 50% back.

The source's figure splits a user's share in proportion to priority, but its text says a user's jobs run "in priority order", which would give A1 all of A's 50% first. They're two different policies; the table follows the figure.

In Python

from fractions import Fraction as F

def split(users, total=F(1)):
    """{user: {job: priority}} -> {job: fraction of cluster}"""
    out = {}
    for jobs in users.values():
        share = total / len(users)          # equal share per user
        for job, prio in jobs.items():
            out[job] = share * prio / sum(jobs.values())
    return out

def dominant(tasks, need, cap):
    return max(F(tasks * n, c) for n, c in zip(need, cap))

def drf(cap, need):
    tasks = {u: 0 for u in need}
    used, active = [0] * len(cap), set(need)
    while active:
        u = min(sorted(active),              # smallest dominant share
                key=lambda u: dominant(tasks[u], need[u], cap))
        after = [x + n for x, n in zip(used, need[u])]
        if any(a > c for a, c in zip(after, cap)):
            active.discard(u)               # next task doesn't fit
            continue
        tasks[u] += 1
        used = after
    return tasks, used

shares = split({"A": {"A1": 3, "A2": 1},
                "B": {"B1": 2, "B2": 1, "B3": 1}})
print(*(f"{j} {float(s):.1%}" for j, s in shares.items()))
# → A1 37.5% A2 12.5% B1 25.0% B2 12.5% B3 12.5%
print(drf((16, 128), {"A": (2, 8), "B": (1, 16)}))
# → ({'A': 5, 'B': 5}, [15, 120])

Time O(T · n · R) · Space O(n · R) for T tasks placed, n users and R resource types: each placement scans every user's dominant share. A heap keyed on si makes each pick O(log n), which is what the DRF paper suggests.

Why DRF beats the alternatives

✗ First come, first served

Whoever queues first takes everything: A's 8 tasks fill all 16 GPUs and B gets 0 until A finishes, which can be a week. Fair queueing exists to stop one heavy source from blocking the rest.

✗ Static quotas

Half of each resource per team is simple and can't be gamed, but it never lends idle capacity: 4 of 16 GPUs sit idle while A still has tasks queued. That misses the source's 95% target.

✗ Count only GPUs

Fair on paper (A 8 GPUs, B 6), but B's CPU-heavy tasks take all 128 cores, stranding 2 GPUs and giving B a 3/4 real share against A's 1/2.

✓ DRF

Each team gets 5 tasks, more than its static half. Equal dominant shares of 5/8, 15 of 16 GPUs busy, and the DRF paper shows no user gains by lying about its needs.

Is fair share always the right goal?

No. DRF assumes a job is many small, independent tasks that can start one at a time. A distributed training job that needs 8 GPUs together is all-or-nothing, and handing it GPUs a few at a time makes it hoard them while it waits (see backfilling and gang scheduling). Production and monitoring work usually gets strict priority bands on top of fair share, because a latency target can't wait for the ratio to even out.

Fairness in shares at any instant also isn't fairness in outcome: a job whose GPUs are scattered across racks may run slower on the same share. Newer GPU schedulers such as Themis target finish-time fairness instead, which is the Platform row above. With only one resource, DRF reduces to plain max-min fairness.

Understand and remember

  • Each user gets an equal slice → split among that user's jobs by priority weight → share(job) = share(user) × priority / Σ priorities → A1 = 50% × 3/4 = 37.5%
  • Shares are guarantees, not caps → idle capacity is lent to others → when the owner returns, the scheduler preempts just enough → SIGTERM first so jobs can checkpoint before SIGKILL
  • Jobs need several resources → a user's dominant share is the largest fraction it holds of any one → DRF gives the next task to the smallest dominant share → A and B each reach 5/8, 5 tasks each, more than a static half (4)
  • Counting only GPUs ignores cores → B's CPU-heavy tasks look cheap → B takes all 128 cores, 2 GPUs are stranded, and B's real share is 3/4 against A's 1/2
  • detail that matters DRF is strategy-proof → no user gains by overstating its needs → one less thing to police; with one resource it reduces to max-min fairness
