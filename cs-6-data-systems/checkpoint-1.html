Checkpoint 1: what each storage engine amplifies

Ties together B-trees and indexes, LSM trees, where in-memory speed comes from, caching patterns, anti-caching and log-structured memory: each one lowers reads, writes or copies by paying somewhere else, and choosing between them means naming which.

How to use this page. Close the six cards. Answer each question in writing, in full sentences, before opening its Check. A wrong or shaky answer isn't a failure: it tells you exactly which section to reopen. The questions are mixed on purpose, so you have to work out which idea applies before you can answer.

1 · Mixed retrieval

  1. which concept?A metrics service ingests tens of thousands of points a second and is read only by a few dashboards. It stores them in a B-tree, and its SSD is saturated with small random writes. Which idea from this part explains the problem, what would you switch to, and what do you pay for it?
    Check
    • a B-tree updates pages in place: each small row rewrites a whole 4 KB page at a random spot (up to ~41× for 100 B rows)
    • an LSM tree buffers writes in a memtable and writes sorted runs sequentially; write amplification ≈ T·L = 20 for 1 GB, all sequential
    • the price: a read may check several runs (Bloom filters keep a miss near 0.05 reads), and compaction competes for disk bandwidth

    Missed it? Reopen LSM trees, "The two numbers that set the trade-off" and "So should everything be an LSM tree?".

  2. A team moves its disk-based database to a server with enough RAM that the whole working set sits in the OS page cache. Throughput rises, but nowhere near an in-memory engine's. Where did the rest of the time go, and roughly how much of the B-tree time could a stripped-down engine remove?
    Check
    • the disk reads are gone, but every access still goes through pages, the buffer pool, latches, locks and the log
    • in Shore, optimizations removed 80–88% of B-tree time and a minimal kernel 3/4 of the rest: only 3–5 of 100 units left
    • what remains is cache misses, which the index layout decides

    Missed it? Reopen in-memory speed, "Step 1: strip the overhead".

  3. which concept?Two services write the same user profile at almost the same time. Each writes the database and then sets the cache to its new value. An hour later, the cache still serves a value the database no longer has. Which idea explains it, and what is the standard fix?
    Check
    • set-on-write race: the two cache sets landed in the opposite order to the two database commits, and nothing expires the stale one
    • fix: cache-aside with delete on write (idempotent, can't install an old value) plus a TTL as a safety net
    • delete still has a narrower race (a slow reader re-fills the old row); leases close it

    Missed it? Reopen caching patterns, the invalidation row and "Is it always the right choice?".

  4. An LSM tree has 4 L0 files and 2 levels, each with a Bloom filter at 10 bits per key. How many disk reads does a lookup for a key that isn't there cost on average, and where does the number come from?
    Check
    • k = round(10 × ln 2) = 7 hash probes; false-positive rate (1 − e−0.7)7 ≈ 0.82%
    • 6 runs × 0.0082 ≈ 0.049 expected wasted reads, against 6 without filters
    • a filter never says "not here" wrongly, so a present key is never missed

    Missed it? Reopen LSM trees, the Bloom line of the formula block.

  5. which concept?An OLTP dataset is 3× the size of RAM, but 5% of the rows get almost all the traffic. One engineer proposes Memcached in front of MySQL; another proposes H-Store with anti-caching. Which design does the evidence favour, and what workload change would hurt it?
    Check
    • anti-caching: memory is home, cold tuples are evicted to disk in blocks, one copy of every tuple
    • in the paper it beat MySQL + Memcached 2×/4×/9× (read-only/read-heavy/write-heavy), because there are no two copies to sync and no double round trip
    • it depends on skew: with uniform access most transactions touch evicted tuples, abort and fetch

    Missed it? Reopen anti-caching, "Why it beats the alternatives" and "Is anti-caching always the answer?".

  6. A RAMCloud-style store runs memory at 90% full. Someone proposes 95% to save RAM. What happens to cleaning, and why does RAMCloud clean memory and disk at different fullness?
    Check
    • cleaning copies u to free 1 − u: u/(1−u) = 9 bytes per byte freed at 90%, 19 at 95%, so the cost doubles
    • the cleaner, not the clients, then sets write throughput
    • two levels: compact in memory at high u (DRAM bandwidth is plentiful), clean the disk log when it's emptier (at 50%, 1 byte per byte freed)

    Missed it? Reopen log-structured memory, "What cleaning costs" and "Two levels of cleaning".

  7. Why does binary search over 107 sorted 8-byte keys touch about 20 cache lines per lookup, a tree of 64-byte nodes 8, and a hash table about 1?
    Check
    • binary search jumps far each probe: nearly every one of its ~23 probes lands in a new line (20.19 lines)
    • 64-byte nodes hold 8 keys each, so the tree is 8 levels of exactly one line
    • a hash table at load 0.5 usually finds the key in one line (1.06), but gives up order

    Missed it? Reopen in-memory speed, "Worked example: find one of 107 keys".

3 · Project: size three stores for the orders table

What it reinforces: fan-out and caching the upper levels (B-trees), write amplification and Bloom filters (LSM trees), a cache's hit ratio (caching patterns), cache lines in memory (in-memory speed), one copy of each row (anti-caching) and cleaning cost (log-structured memory).

The course's table: 107 orders of ~100 B (≈ 1 GB), 4 KB pages, 16-byte index entries. Write one Python script, reusing functions from the cards' code/ files where you can, that prints a single comparison table:

  1. B-tree on disk. Fan-out, levels, the size of the cached upper levels, disk reads per point lookup, and worst-case write amplification for a 100 B row update.
  2. LSM tree (T = 10, 64 MB memtable). Levels and write amplification at 1 GB and at 1 TB. Bloom false-positive rate and expected wasted reads for a missing key over 6 runs, at 10 and at 8 bits per key, and the filter's RAM for 107 keys.
  3. A cache in front of the B-tree. Using the card's Zipf(1.0) simulation (10,000 keys, 200,000 requests, LRU of 1,000), how many requests still reach the B-tree, and so how many disk reads?
  4. All in memory, log-structured. RAM needed for 1 GB live at u = 0.75 and at u = 0.9, and bytes copied per byte freed at each. Cache lines per point lookup for a 64-byte-node tree vs a hash table.
  5. Choose. One paragraph each: (a) a 1 GB read-heavy order system; (b) a 1 TB event log that is written far more than read; (c) a 1 GB key-value store with constant overwrites and a tight latency target. Name the number that decided it and what you pay.
Done when: your script prints every number in steps 1–4, each matches the check, and each choice in step 5 names the amplification it lowers and the one it raises.
Check: the numbers (computed from the cards' formulas and code)
  • B-tree: fan-out 4,096 ÷ 16 = 256; 39,063 → 153 → 1: 3 levels; cached 154 pages ≈ 616 KB; 1 disk read per lookup; up to 4,096 ÷ 100 ≈ 41× write amplification (random writes).
  • LSM at 1 GB: ⌈log10(1,024/64)⌉ = 2 levels, write amplification 10 × 2 = 20; at 1 TB: ⌈log10 16,384⌉ = 5 levels, 50. All sequential.
  • Bloom at 10 bits/key: k = 7, 0.82%, 6 × 0.0082 ≈ 0.049 wasted reads, 12.5 MB of filters. At 8 bits/key: k = 6, (1 − e−0.75)6 ≈ 2.16%, ≈ 0.13 wasted reads, 10 MB.
  • Cache: LRU of 1,000 hits 67.2%, so 65,572 of 200,000 requests reach the B-tree: 65,572 disk reads instead of 200,000 (3.05× fewer).
  • Log-structured: u = 0.75 needs 1 ÷ 0.75 ≈ 1.33 GB and copies 3 bytes per byte freed; u = 0.9 needs ≈ 1.11 GB and copies 9. Lookups: 8 lines (64-byte nodes) vs ≈ 1.06 (hash table).
  • Reasonable choices: (a) B-tree plus a cache, or all in memory, since it fits 24× in a 24 GB machine; (b) LSM: write amplification 50 but sequential, vs random in-place writes; (c) log-structured memory at ≤ 90% full with a hash table, paying 11–33% extra RAM for cheap cleaning.
