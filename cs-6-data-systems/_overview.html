Touching less data

The overview for course 6 of the core CS canon series. It ties together the 17 cards on the source guide's storage, caching, MapReduce, graph-query and case-study pages: how B-trees, LSM trees, caches, in-memory stores, batch jobs, recursive queries and GPU schedulers all win the same way, by cutting the work done per unit of useful work.

In one breath

Every system in this course is judged by one ratio: how much it reads, writes, copies or holds idle for each byte, fact or GPU-hour the user actually wanted. An index reads 1 page instead of 250,000. An LSM tree rewrites each byte about 20 times, but in sequential runs. A cleaner at 90% full copies 9 bytes to free 1. A backfilling scheduler fills GPU-hours that would sit idle. Find the ratio, find what sets it, and remember that lowering one kind (reads) usually raises another (writes, memory, staleness).

The words people use

OLTP, OLAP, batch

OLTP: many small transactions that each touch a few rows (an order, a lookup). OLAP: few queries that each scan a lot. Batch: a whole dataset in, a whole dataset out, like MapReduce. The same A means different things in each, so name the workload first.

Utilization vs goodput

Utilization counts hardware handed out or busy; goodput counts work that survives. A cluster can be 95% allocated while 28% of allocated GPU time sits at 0%, and an hour lost to FAILED_PREEMPTED is busy but not good.

Data vs expression complexity

Grow the database with the query fixed, or grow the query over fixed data. Databases dwarf queries, so data complexity is the usual lens: a fixed join is polynomial, and plain relational queries sit in AC⁰.

✓ Read, write, space amplification

Units touched, rewritten or held per useful unit. They trade against each other: an LSM tree cuts write amplification to 20 but checks several files per read, and a cleaner copies less only if memory runs emptier. Name all three before you pick an engine.

When this advice doesn't apply

Amplification counts units, not time, and the units aren't equal. An LSM tree's 20 rewrites are sequential and a B-tree's 41 are random, which matters far more on a disk than the ratio suggests; a cached page read costs nanoseconds and a disk read milliseconds. Before comparing two A's, check that they count the same kind of step on the same device.

And small data changes the answer. The course's 1 GB orders table fits 24 times in a 24 GB laptop, where a dict or a SQL GROUP BY beats a MapReduce job, and page-level tricks matter less than cache lines. The scheduling cards assume people competing for a shared cluster; a single team with an overnight queue needs only FIFO and a utilization graph. Measure before you add an index, a cache or a cluster.

Understand and remember

  • The question fixes the useful work U → the design sets the amplification A → cost ≈ U × A → a better design lowers A, never U
  • Lowering one amplification usually raises another → B-tree cuts reads (250,000 → 1 page) but rewrites a 4 KB page per 100 B row → LSM cuts random writes (T·L = 20, sequential) but checks several runs per read → name all three before choosing
  • A copying design runs memory with a live fraction u → each byte freed costs u/(1−u) bytes copied → 9 at 90%, 19 at 95% → headroom (space) buys cheaper cleaning (copies)
  • Shared hardware held but not doing work is amplification too → FCFS, static quotas and half-placed gangs leave GPUs idle → fair share, DRF and backfill lower idle GPU-hours without breaking the head job's promise
  • detail that matters Amplification counts units, not time → a sequential rewrite on disk is far cheaper than a random one, and a cached page read costs nanoseconds vs milliseconds → compare two A's only when they count the same kind of step on the same device

  1. concept Explain, using this course's orders table, why a full scan and a B-tree lookup differ by a factor of 250,000 even though they return the same row.
    Check
    • U is one ~100 B row either way

  2. mechanism Walk through where the course's two write-amplification numbers come from: the LSM's 20 and the B-tree's 41.
    Check
    • LSM: T = 10 per level × L = ⌈log₁₀(1 GB / 64 MB)⌉ = 2 levels = 20, written sequentially

    • 41 is a worst case: batching several row updates per page write lowers it
  3. tradeoff A team wants to run RAMCloud-style memory at 95% full to save RAM. Using the cleaning cost, argue what they give up and what a sensible target is.
    Check
    • u/(1−u) at 0.95 = 19 bytes copied per byte freed, vs 9 at 90%
    • the cleaner then sets write throughput, not the clients
    • the paper's working range is 80–90%; the saved 5% of RAM doubles cleaning cost
  4. mechanism Which card would you reach for when a single 8-GPU job blocks a queue while GPUs sit idle, and which number on that card settles whether the fix helped?

Why this step?

5 · Predict commit to an answer before revealing

The course's table is 1 GB. Scale it to 1 TB with the same 64 MB memtable and T = 10. Commit first: what happens to the LSM's write amplification, and to the B-tree's height (fan-out 256)?

Reveal

The LSM needs ⌈log₁₀ 16,384⌉ = 5 levels, so write amplification rises from 20 to about 50 (the LSM card computes this). The B-tree barely moves: 10¹⁰ rows at fan-out 256 is ⌈log₂₅₆ 10¹⁰⌉ = 5 levels instead of 3, and if the upper levels stay cached it is still about one disk read per lookup. Read amplification grows logarithmically in both; the LSM's write cost grows with every added level.

The source guide's Index page covers the read-versus-write trade-off, why B-trees beat hash…In one breathAn index is an extra, sorted copy of some columns that points back at the rows, so the database can jump to a value instead of reading the whole table.
