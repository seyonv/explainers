The MapReduce programming model

Also called map / shuffle / reduce, or split-apply-combine. You write two small functions and the library runs them over a cluster. The source guide follows Google's 2004 paper: word count as the first example, the types of map and reduce, and six more jobs in one table.

In one breath

map turns each input record into some (key, value) pairs. The library then gathers every value that shares a key (the shuffle). reduce is called once per key with all of that key's values and boils them down to the answer. Neither function shares state with any other call, so the library can run thousands of them on different machines and simply rerun any that die.

The two types

map: (k1,v1)one input record → list(k2,v2)intermediate pairs reduce: (k2,list(v2))one key, all its values → list(v2)usually zero or one value
k1, v1input key and value, from their own domaindoc name, doc text k2, v2intermediate key and value: the same domain as the outputa word, 1 list(v2)every v2 emitted for one k2, by any map call, handed over as an iterator[1, 1, 1] for "the"

Filled in for word count: map("d2", "the cat ate the fish") → 5 pairs; reduce("the", [1, 1, 1]) → [3].

The source says reduce produces "zero one output values"; the paper says zero or one per call, as above.

3 + 4 + 3 = 10 pairs, not 11: map deduplicates words within a document so "the" doesn't list d2 twice. That dedup is our choice; the source's table only says map emits (word, documentID).

In Python

from collections import defaultdict

def run_mapreduce(mapper, reducer, inputs):
    groups = defaultdict(list)            # the shuffle
    for k1, v1 in inputs.items():
        for k2, v2 in mapper(k1, v1):
            groups[k2].append(v2)
    return {k2: reducer(k2, iter(groups[k2]))
            for k2 in sorted(groups)}  # keys in order

def wc_map(doc_name, text):
    for w in text.split():
        yield w, 1                        # EmitIntermediate(w, "1")

def wc_reduce(word, counts):
    return sum(counts)

def ii_map(doc_name, text):
    for w in set(text.split()):         # once per doc
        yield w, doc_name

def ii_reduce(word, doc_ids):
    return sorted(doc_ids)

DOCS = {"d1": "the cat sat", "d2": "the cat ate the fish",
        "d3": "a dog sat"}
print(run_mapreduce(wc_map, wc_reduce, DOCS))
# {'a': 1, 'ate': 1, 'cat': 2, 'dog': 1, 'fish': 1, 'sat': 2,
#  'the': 3}
print(run_mapreduce(ii_map, ii_reduce, DOCS)["sat"])
# ['d1', 'd3']

The source's word-count block is tagged cpp but is the paper's pseudocode, with counts as strings ("1", ParseInt). Python keeps them as ints.

Time O(P + K log K) · Space O(P) for this one-machine version, with P intermediate pairs and K distinct keys (here P = 11, K = 7). Every pair is appended once, and only the keys get sorted. A real cluster splits both P and K across machines; the execution card shows how.

Two of the six have a pass-through reduce: the job is really "move data to where its key lives", and the shuffle does that.

Why it beats the alternatives

✗ One machine, Counter

Perfect for these 11 words. The source's premise is data that won't fit one machine's memory, and one process can't read a cluster's disks in parallel either.

✗ Hand-written distributed code

Threads and RPCs across machines work, but you now own splitting the data, load balancing, retries and dead machines: the things the source says the library handles for you.

✗ Workers update a shared table

Every worker doing count[w] += 1 on one store needs locking or suffers lost updates. And after a crash you can't tell which increments already landed, so a rerun double-counts.

✓ MapReduce

Map and reduce share no state, so each call can run anywhere and a failed one is simply run again. With deterministic functions, the output equals a failure-free sequential run.

Is it always the right shape?

No, and the source says its importance is declining. If the data fits on one machine, a dict or a SQL GROUP BY does the same map-group-reduce with no cluster. Each MapReduce job also writes its full output to the distributed file system, and jobs are chained through directories, so iterative work (many passes of a graph or ML algorithm) pays a full disk round trip per pass. Systems such as Spark and Flink keep data between steps instead; that last point is from DDIA ch. 10, not the source.

The model also assumes reduce can see all values of a key in one call. A key that's far more common than the rest (think "the" in real English text) lands on one reducer and makes it the slow one. The combiner, which pre-sums on the map side, softens that for word count; that's on the execution card.
