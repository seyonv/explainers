From a math spec to a system: the limit order book

Also called an LOB, a matching engine, or price-time priority matching. The source guide defines the book as maths (a tick grid, orders (p, q, t), best bid and ask, the spread, three events) and stops there. This card does the translation into data structures and code.

Prime · 2 minutes before you read

The problem: The limit order book is usually given as maths: a tick grid, orders (p, q, t), best bid and ask, three events. That spec says nothing about which data structures make ‘best price’, ‘add’, ‘cancel’ and ‘market order’ fast, and a naïve choice makes one of them O(n).

Where it fits: Fourth case-study card, and the course's clearest spec-to-system translation. It builds on cs-1's heaps and on the dict-of-queues idea from the LFU cache card; cs-10's market-making card uses the same book from the trader's side.

In one breath

A limit order book is two queues of waiting orders: buyers sorted by highest price, sellers by lowest, and first come, first served within a price. The system version keeps, for each side, a map from price to a FIFO queue plus a heap of the prices, so the best price is always on top and a market order just eats queues from the top down.

L = live price levels, k = fills, d = levels emptied. The whole column is our translation; the source gives only the left column.

In Python

class Book:
    def __init__(self):
        self.levels = {"B": {}, "S": {}}  # tick -> deque of orders
        self.heaps = {"B": [], "S": []}   # -tick for bids, tick asks
        self.orders = {}                  # id -> [id, side, tick, qty]
        self.seq = count(1)               # t becomes a counter

    def best(self, side):                 # b(t) or a(t)
        h, lv = self.heaps[side], self.levels[side]
        while h:
            tick = -h[0] if side == "B" else h[0]
            q = lv.get(tick)
            while q and q[0][3] == 0:     # skip cancelled orders
                q.popleft()
            if q:
                return tick
            lv.pop(tick, None)            # empty level: drop lazily
            heapq.heappop(h)
        return None

    def submit(self, side, qty, tick=None):   # tick=None: market
        oid, opp, fills = next(self.seq), "SB"[side == "S"], []
        while qty:
            b = self.best(opp)
            if b is None or (tick is not None and
                             (b > tick if side == "B" else b < tick)):
                break                     # nothing left that crosses
            o = self.levels[opp][b][0]    # oldest order at best price
            n = min(qty, o[3])
            o[3] -= n
            qty -= n
            fills.append((o[0], b, n))
        # ...then rest any remainder of a limit order at its tick
        return oid, fills

    def cancel(self, oid):                # O(1): mark, skip later
        self.orders[oid][3] = 0

# market buy 250 on the book above:
#   fill #1:  60 @ 10.01
#   fill #5:  40 @ 10.01
#   fill #2: 100 @ 10.02
#   fill #3:  50 @ 10.03
#   250 shares, cost 2504.50, avg 10.0180, slippage 0.0080/share = 2.00
# fuzz: best() matches brute force in 2000 random books

Time: best O(1) peek · add O(1), or O(log L) for a new level · cancel O(1) · market O(k + d log L). Space O(orders + L). Each level's tick is pushed once and popped once, when best finds it empty, so a lazy pop costs O(log L) once per level, not per query. The fuzz test in code/ checks best against a brute-force max/min after every event and that the book never stays crossed (b < a).

Why it beats the alternatives

✗ One list, scan for the best

Adding and cancelling are cheap, but every best-price query scans all n orders, and a market order that fills k times scans k times: O(kn).

✗ One sorted list of orders

bisect.insort by (price, seq) makes the best O(1), but each insert and each cancel shifts up to n entries: O(n) per event.

✗ One heap of all orders

Keyed by (price, seq), it's O(log n) per order, not per level, and a level's total size or a mid-heap cancel needs a scan.

✓ Levels: dict + heap + FIFO

Group by price first. Adding to an existing level, cancelling and filling are O(1), and the heap only orders the L distinct prices, not every order.

Is a heap what real engines use?

Not usually, and it's a fair interview follow-up. A heap can't list levels in order, so publishing the top 10 levels costs a sort, and stale entries pile up under heavy cancelling. Common alternatives (general practice, not from the source): a balanced tree of levels (a sorted map) when prices are sparse, or an array indexed by tick offset from the best price, since most activity sits within a few ticks of it, giving O(1) everything. Cancels there use a doubly linked list per level instead of lazy zeroing.

The data structure is also the smaller half of the system. A matching engine processes one instrument's events in a single sequence, so t is simply the arrival order and replaying the event log rebuilds the book exactly. And price-then-time isn't universal: some venues split a level among orders in proportion to size (pro rata), where the FIFO deque is the wrong structure. Both points are our notes, not the source's.

Understand and remember

  • Price priority then time priority → per side, a dict tick → FIFO deque of orders, plus a heap of the distinct ticks → the best level is the heap top, and the oldest order at it is the deque head
  • The heap orders only L price levels, not every order → adding to an existing level, cancelling and filling are O(1) → a new level costs O(log L)
  • Cancel marks the order's quantity 0 instead of searching the deque → O(1) cancel → best() skips zeroed orders and pops empty levels when they reach the top, once per level
  • A market order eats the head of the best level, then the next level → average fill = Σ pᵢnᵢ / Σ nᵢ → slippage = average − best ask on arrival (10.018 − 10.01, $2.00 on 250) → and the spread widens as levels empty
  • detail that matters Integer ticks make comparisons exact and prices usable as dict keys → no float-equality bugs
  • detail that matters A sequence counter replaces the timestamp t → two clock readings can tie, a counter can't → replaying the event log rebuilds the book exactly

5 · Predict commit to an answer before revealing

The ask side holds exactly 400 shares (the card's book) and a market buy of 1,000 arrives. Commit first: what does this card's submit do with the other 600, and what state is the book in afterwards?

Reveal

It fills all 400 across 10.01, 10.02 and 10.03, then finds no best ask and stops; a market order has no tick, so the remaining 600 aren't rested: they're dropped, like an immediate-or-cancel order. The ask side is now empty, so there is no best ask and no spread until a seller arrives. Real venues add price protection so a market order can't sweep to absurd prices.
