Log-structured memory

Also called a log-structured allocator, or log cleaning / segment cleaning when people mean its garbage collector. The source guide uses it for RAMCloud, a key-value store that keeps every object in DRAM: 8 MB segments, tombstones, a cleaner, and two levels of cleaning.

In one breath

Treat memory like a log file: every write, including an overwrite or a delete, is appended at the end, and one hash table points each key at its newest record. Old copies just go dead in place. A cleaner later picks a mostly-dead segment, copies its few live records to the head, repoints the hash table and frees the whole segment.

Two levels of cleaning

Every segment also lives on backup disks, and a plain cleaner rewrites both, so disk bandwidth caps how full memory can be. RAMCloud splits the job:

LevelWhat it doesExample AExample B
1. Segment compactionRewrites one segment into a smaller piece of memory. Memory only: no disk or network I/O. The disk copy stays full size. s0 above4 slots → 1 slot (D) in memory At u = 90%: 9 bytes copiedper byte freed; DRAM bandwidth can afford it
2. Combined cleaningThe full cleaner: frees segments in memory and on the backups. Runs later, when more objects have died. Disk at u = 50%: 1 byteper byte freed (the paper's example) Forced earlywhen disk space runs low or tombstones pile up (compaction can't drop live tombstones)
same byte freed: memory at u = 0.9 → 0.9 / 0.1 = 9 disk at u = 0.5 → 0.5 / 0.5 = 1 the disk log is allowed to be bigger than memory, so it runs emptier and cleans 9× cheaper

In parallel. Several cleaner threads run next to normal reads and writes. Because written segments never change, a cleaner can copy from one without locking it. Every lookup goes through the hash table, so relocating an object means one atomic pointer update (bucket locks settle races with writers). A cleaned segment is freed only after every RPC already in flight has finished, since one of them might still be reading it.

In Python

class Log:  # segs: id -> records; table: key -> (seg, slot)
    def put(self, key, val):
        old = self.table.get(key)
        self.table[key] = self._append(("obj", key, val))
        if old is not None:          # overwrite: old copy is dead
            self._append(("tomb", key, old[0]))

    def live(self, sid, i):
        kind, key, x = self.segs[sid][i]
        if kind == "obj":            # live iff the table points here
            return self.table.get(key) == (sid, i)
        return x in self.segs        # tombstone: target seg exists

    def clean(self, sid):
        keep = [r for i, r in enumerate(self.segs[sid])
                if self.live(sid, i)]
        for rec in keep:                 # copy live records to the head
            where = self._append(rec)
            if rec[0] == "obj":
                self.table[rec[1]] = where   # the one pointer to swap
        del self.segs[sid]               # free the whole segment
        return len(keep), SEG - len(keep)    # copied, freed

Time O(1) per write · O(s) to clean a segment of s records · Space: live data ÷ u. A write is one append plus one hash-table update. Cleaning touches only the chosen segment, never the whole heap, because nothing but the hash table points at an object.

Why it beats the alternatives

✗ malloc and free in place

Can't move an object once placed, so memory fragments. In the paper's tests every allocator, glibc malloc included, could waste half of memory when the mix of object sizes changed (for example, small objects deleted and replaced by larger ones).

✗ A copying garbage collector

Moving objects fixes fragmentation, but a general GC must eventually walk all live data to fix every reference. So it waits for lots of garbage (1.5–5× the used space) and pauses threads; the paper saw 3–4 s pauses from stock Java collectors.

✗ One level of cleaning

RAMCloud's first design cleaned memory and disk together. At 80–90% memory utilization the cleaner's disk traffic throttled writes; making disk emptier would have made memory emptier too.

✓ Log + two-level cleaning

Allocation is an append, one pointer per object makes moves cheap, and the cleaner picks the emptiest segments. The paper reports 80–90% memory utilization, and up to 6× better performance at high utilization than one-level cleaning.

Is a log always the right way to manage memory?

No. It works because RAMCloud's objects are only ever reached through one hash table, so moving one means changing one pointer. A general program heap, where objects point at each other, has no such single reference, and needs malloc or a real GC. If objects rarely die or change size, plain malloc wastes little and never copies.

Keep headroom, too: past about 90% full the cost chart above explodes (19 bytes copied per byte freed at 95%), and the cleaner, not the clients, sets the write throughput. The same append-then-clean idea shows up on disk as log-structured file systems and LSM trees, where compaction plays the cleaner's role.
