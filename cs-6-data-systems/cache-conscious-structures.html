Where in-memory speed comes from

Also called main-memory databases, cache-conscious (cache-aware) data structures, or locality of reference. The source guide's Cache page retells the Shore experiments from "OLTP through the looking glass" (Harizopoulos et al., SIGMOD 2008): overhead first, cache misses second.

In one breath

A disk database with enough RAM already serves reads from memory, because the OS caches disk blocks. So an in-memory database is fast mostly because it skips the machinery built for disk: pages, a buffer pool, locking, logging. Once that's gone, what's left is the CPU waiting on cache misses, and the layout of the index decides how many there are.

Step 2: count the cache misses that remain

Each memory access pulls one 64-byte cache line. The ladder below is why a miss matters: DRAM is 200× slower than L1, but still 1,500× faster than a random SSD read.

The 4 KB B+tree needs only 3 disk reads, which is what it was built for; inside each page it still does a binary search across ~6 lines.

In Python: count the lines

LINE, KEY, N = 64, 8, 10**7

def probes(n, p):
    """Indices bisect_right visits to find slot p in n keys."""
    lo, hi, seen = 0, n, []
    while lo < hi:
        mid = (lo + hi) // 2
        seen.append(mid)
        if p < mid: hi = mid          # key p sits at index p
        else: lo = mid + 1
    return seen

def lines(idxs, width):            # distinct 64-byte lines
    return len({i * width // LINE for i in idxs})

def line_tree_levels(keys=LINE // KEY):
    n, levels = -(-N // keys), 1       # leaves: 8 keys per line
    while n > 1:                      # inner nodes: 9 children
        n, levels = -(-n // (keys + 1)), levels + 1
    return levels                      # one line per level

#   B+tree, 4 KB nodes     17.26 lines  ~ 1726 ns
#   tree of 64-byte nodes   8.00 lines  ~  800 ns
#   hash table, load 0.5    1.06 lines  ~  106 ns
# binary search: 23.33 probes (log2 N = 23.25)
# Shore B-tree time, 100 units:
#   remove 80%: 100 -> 20 -> x 1/4 = 5   (20x)
#   remove 88%: 100 -> 12 -> x 1/4 = 3   (33x)

Time O(logB N) lines · Space O(N). Every tree does O(log N) comparisons; what changes is how many keys B share a line, so a 64-byte node pays one miss per 8 keys' worth of fan-out instead of one per probe.

Why it beats the alternatives

✗ Just add RAM to a disk engine

The OS page cache already stops the disk reads, yet every lookup still goes through pages, latches, locks and the log. That machinery, not the disk, is where Shore's time went.

✗ Cache-tune the B-tree first

The paper expects only a modest gain while the overhead remains: saving a dozen misses matters little in a transaction where the real work is about 1/60 of the instructions.

✗ A sorted array and binary search

Compact and simple, but each probe halves the range and jumps far away: 20.19 lines for 107 keys, almost one miss per probe.

✓ Strip overhead, then fit lines

First remove disk-era work (100 → 3–5 units of B-tree time). Then lay nodes out one line each (8 lines) or use a hash table (~1 line) for point lookups.

So is a hash table always the answer in memory?

No. The source, following the paper, only conjectures that hash tables may win once a system is stripped down, and says it should be tested. A hash table has no order, so range scans, prefix queries and "next key" still need a tree. A node-per-line tree built as a packed array (the CSS-tree idea from Rao and Ross's 1999 paper on decision-support indexing) is best for read-mostly data; its successor, the CSB+-tree, exists to make updates cheaper.

And when the data no longer fits in RAM, the ladder flips the priorities back: a disk seek costs 100,000 DRAM misses, so 4 KB nodes with 3 reads beat 64-byte nodes with 8. Our reading, not the source's: pick the node size to match the slowest level the data actually lives in.
