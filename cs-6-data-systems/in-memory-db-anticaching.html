In-memory databases and anti-caching

Also called a main-memory DBMS (H-Store, VoltDB); anti-caching is the buffer pool turned inside out. The cheat-sheet's Memory Cache page argues OLTP belongs in RAM, lists four ways to stay durable, and walks through H-Store's evict and retrieve paths.

In one breath

An in-memory database keeps every row in RAM and uses disk only to recover after a crash, so no query ever waits on a disk read. When the data outgrows RAM, H-Store's anti-caching moves the coldest rows out to disk in blocks. A row lives in exactly one place, and a transaction that touches an evicted row never sits waiting on the disk: it's aborted, the rows are fetched in the background, and it runs again.

Why the whole database fits

Stonebraker (2007): most OLTP databases are < 1 TB TPC-C needs about 100 MB per warehouse → 1 TB ÷ 100 MB = 10,000 warehouses this course's orders table: 10⁷ rows × 100 B = 1 GB → fits 24× in a 24 GB laptop

RAM is volatile, so "in-memory" still needs a plan for power loss. Memcached has none: it's only a cache. Databases pick from these four (the source's list), usually more than one:

H-Store in three decisions

Shared-nothing: data is partitioned across nodes, and each node owns its part. One thread per core: each core runs its partition's transactions one at a time, so there are no locks or latches to take. Stored procedures only: the app calls named, pre-declared transactions, so one round trip runs the whole thing. With all three, the 2007 H-Store prototype ran TPC-C 82× faster than a tuned commercial RDBMS.

Worked example: T2 touches two evicted orders

Toy sizes (illustrative): room for 4 orders in memory, eviction blocks of 2, price = 10 × id. T2 reads orders 3, 1 and 4; 1 and 4 are on disk.

Steps 1 to 6 follow the source and the anti-caching paper (§3.3–3.4). Merging only the needed tuples, not the whole block, is the paper's "tuple-merge", which beat "block-merge" in its tests.

In Python

from collections import OrderedDict

class AntiCache:
    def __init__(self, cap, block):
        self.mem = OrderedDict()   # LRU chain: head = coldest
        self.evicted = {}          # Evicted Table: key -> block id
        self.disk = []             # blocks, each written once
        self.cap, self.block = cap, block
        self.log = []

    def insert(self, k, v):
        self.mem[k] = v            # new tuples join the hot tail
        self.shrink()

    def shrink(self):              # the eviction "transaction"
        while len(self.mem) > self.cap:
            blk = {}
            while len(blk) < self.block:
                k, v = self.mem.popitem(last=False)  # pop head
                blk[k] = v
                self.evicted[k] = len(self.disk)
            self.disk.append(blk)  # one sequential write
            self.log.append(f"evict {list(blk)} -> block "
                            f"{len(self.disk) - 1}")

    def run(self, name, keys):
        # pre-pass: run the reads, record evicted keys, change nothing
        miss = [k for k in keys if k in self.evicted]
        for k in keys:
            if k in self.mem:
                self.mem.move_to_end(k)   # O(1): doubly linked
        if miss:
            blocks = sorted({self.evicted[k] for k in miss})
            self.log.append(f"{name} pre-pass: {miss} evicted, "
                            f"abort, fetch blocks {blocks}")
            for k in miss:                # tuple-merge: only these
                b = self.evicted.pop(k)
                self.mem[k] = self.disk[b][k]
            self.log.append(f"{name} restart")
        out = [self.mem[k] for k in keys]  # all in memory now
        self.log.append(f"{name} commit {out}")
        self.shrink()
        return out

Two details the source compresses

Why the LRU chain is doubly linked. Touching a tuple means unlinking it and appending it at the tail. Unlinking needs the tuple before it. With only next pointers you find that by walking from the head, which is the cold end, but under skew the tuples being touched are hot and sit near the tail:

chain of 100,000 tuples (illustrative), hot tuple 10 from the tail singly linked: walk 99,990 hops to find the predecessor doubly linked: 1 hop (prev pointer) paper, high skew: 20× faster than singly, within 5% of no LRU chain at all

H-Store embeds both pointers in each tuple header as 4-byte offsets, not 8-byte addresses, to keep that cost small. It also updates the chain from only a sample of transactions (α = 0.01, "aLRU"), which costs 2–7% of throughput versus no anti-caching.

Why bigger eviction blocks hurt. Writing is a wash: evictions go out as one sequential write either way. Reading is not: to bring back one tuple you fetch its whole block.

writes: 5 × 1 MB = 5,120 KB = 20 × 256 KB = 5,120 KB (same sequential write) reads: one 1,000 B YCSB tuple (10 columns × 100 B) 256 KB block → fetch 262,144 B, 262 tuples per block 1 MB block → fetch 1,048,576 B, 1,048 tuples per block → 4× the bytes

The source says "Larger blocks reduce overall throughput, but they add the cost of being fetched", which contradicts itself. The paper says larger blocks reduce throughput because of the added cost of fetching them, most of all under high skew, where a block's other tuples are rarely wanted together. Corrected here.

Why it beats the alternatives

✗ Disk DBMS with a buffer pool

Hot pages are copied into RAM, but tuples still convert between disk and memory formats and every access pays for heavyweight locking. Anti-caching beat MySQL 9×/18×/10× (read-only/read-heavy/write-heavy YCSB, data 8× RAM, high skew).

✗ DBMS + Memcached in front

The app keeps two copies in sync, and a miss costs both a cache and a database round trip. Anti-caching beat it 2×/4×/9× on the same runs; writes hurt it most.

✗ Let the OS swap pages

A page fault stalls the thread for every missing page, one at a time, and a 4 KB page can mix hot and cold rows. With one thread per partition, the whole partition would stop.

✓ Anti-caching

Memory is the home and disk is overflow. Blocks are built from only cold tuples, a transaction learns all it needs in one pre-pass, and the fetch happens while other work runs.

Is anti-caching always the answer when data outgrows RAM?

No. It pays off when the workload is skewed, so a small hot set lives in RAM. As skew drops, more transactions hit evicted data and abort, and all three systems in the paper slow down. A full-table scan needs the whole table in memory, which is the case anti-caching can't serve (paper §6.1), so analytics belong elsewhere (a column store, in our view). And a pre-pass can miss rows it can only find by reading an evicted row's non-key columns; then the transaction restarts more than once.

If the data fits in RAM, the best anti-cache is none: plain H-Store or VoltDB with a command log and snapshots. If you can't route every transaction through stored procedures, a disk DBMS with a big buffer pool is simpler (our reading, not the source's).
