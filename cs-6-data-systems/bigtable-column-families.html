Bigtable's data model

Also called the wide-column model, column families, or family:qualifier columns; carried on by HBase and Cassandra. The source guide files it under "A Distributed Hash Table System", but the page actually describes Bigtable's model: a sorted map, not a hashed one, and mostly row-oriented.

In one breath

A Bigtable table is one huge sorted map from (row key, column, timestamp) to an uninterpreted string of bytes. Columns are named family:qualifier. The few families are fixed up front and carry the settings (who may read them, how many versions to keep), while qualifiers are made up on the fly, so a row can have millions of columns and most rows leave most of them empty.

Why reverse the domain in the row key

✗ Key = hostname

  1. mail.example.com/
  2. news.acme.org/
  3. news.example.com/today
  4. www.acme.org/
  5. www.example.com/
  6. www.zeta.io/

example.com lands in 3 separate blocks: sorting groups by subdomain first.

✓ Key = reversed hostname

  1. com.example.mail/
  2. com.example.news/today
  3. com.example.www/
  4. io.zeta.www/
  5. org.acme.news/
  6. org.acme.www/

example.com is 1 block: the prefix com.example. is one range scan.

Same 6 illustrative URLs, block counts from runs() in the code file. Rows are stored sorted and split into contiguous ranges (tablets), so one block usually means one or a few tablets, and a job that analyses one site reads them together. The trick is from the Bigtable paper.

In Python: the map, per-family GC and per-family access

def row_key(url):         # www.example.com/x -> com.example.www/x
    host, _, path = url.partition("/")
    return ".".join(reversed(host.split("."))) + "/" + path

class Table:
    def __init__(self, families):   # family -> versions to keep
        self.families = families
        self.cells = {}             # (row, column) -> [(ts, value)]

    def put(self, row, column, ts, value):
        family = column.split(":")[0]
        if family not in self.families:  # families are declared
            raise KeyError(f"no column family {family!r}")
        versions = self.cells.setdefault((row, column), [])
        versions.append((ts, value))
        versions.sort(reverse=True)            # newest first
        del versions[self.families[family]:]   # per-family GC

    def read(self, row, allowed=None):     # newest of each column
        return {col: v[0][1]
                for (r, col), v in sorted(self.cells.items())
                if r == row and (allowed is None
                                 or col.split(":")[0] in allowed)}

Time O(log n) per lookup in a real sorted store · Space O(cells actually written). The toy uses a dict and sorts on demand; Bigtable keeps the keys sorted on disk (SSTables) so a point read is a search and a prefix is one sequential scan. Empty cells take no space.

TermWhat it meansExample AExample B
Row keyAny string; rows are stored sorted by it, and every read or write inside one row is atomic. com.example.www/reversed host: a site stays together order#000042a plain id also works, but gives no clustering

The source's Webtable figure fills the language family with per-language columns (language:en, :es, :fr) and gives it referring-site qualifiers holding link text. In the paper, link text lives in the anchor family, and language is a single column holding the page's language id; corrected here.

Why it beats the alternatives for Webtable

✗ A relational table

One column per linking site is impossible: the set is unbounded and different per page. You'd move anchors to a second table and join, and a fixed schema needs a migration for every new attribute.

✗ A hashed key-value store

One blob per URL: updating one anchor rewrites the whole blob, there's no per-part access or version policy, and hashing the key scatters example.com, so "all pages of a site" becomes a full scan.

✗ A true column store

Parquet or a warehouse stores each column apart: great for one column over all rows, but reading a whole page touches every column file, and millions of anchor qualifiers would mean millions of columns.

✓ Sorted rows + column families

A row's cells sit together, so a page reads in one go; qualifiers are free-form; families carry versions and permissions; and reversed keys make a site one range scan.

So is it "column-oriented", and should you use it?

Not really, which is the source's point. Cells are sorted by row first, then column, as the stored order above shows, so it's a row store with flexible columns. The one column-ish feature is that families can be put in separate locality groups (separate files per group), so a scan of anchor alone can skip the heavy contents bytes.

It's the wrong choice when you need joins, secondary indexes or transactions across rows: the paper only promises atomicity within one row. Use a relational database for that, and a real columnar warehouse for analytics that aggregate one field over everything. Row-key design is also a trade-off: clustering a site also sends a big crawl of that site to one tablet, a hot spot. And Cassandra by default hashes the partition key and sorts only within a partition, so the reversed-domain trick helps there only inside one partition (general practice, DDIA ch. 6, not from the source).
