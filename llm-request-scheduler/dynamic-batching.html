Dynamic batching: wait a little, batch a lot

Also called time-window batching, adaptive batching, or the Triton dynamic batcher. It is the classic way to batch models that answer in one forward pass. In this course it is the middle row of the batching experiment (E2): batch size 32 with a 50 ms window, run on generation, where it helps a little and then fails.

In one breath

Don't send each request to the GPU alone, and don't wait for a full batch either. Hold requests in a queue and fire the batch as soon as either it reaches the maximum size or the oldest request has waited max_delay. You pay at most max_delay of extra latency, and you get batches that grow with traffic. That is a great deal when every request costs one forward pass. It is a bad one for generation, because once a batch starts nobody can join or leave until its longest answer is done.

The rule: full or timed out, whichever comes first

Illustrative arrival times. The timer starts at the oldest request, not at the last batch. Under slow traffic you pay the full window for a small batch; under busy traffic the batch fills before the timer, so you pay less than the window.

That is the whole algorithm. Here it is in the course's simulator, where static batching is the same function with max_delay = inf (simulate_request_level in labs/scheduler.py, comments shortened):

if len(queue) < max_batch and pending: deadline = queue[0].arrival + max_delay # inf for static if pending[0].arrival <= deadline: # someone can still join t = max(t, pending[0].arrival) continue t = max(t, deadline) # window closed: run it batch = [queue.popleft() for _ in range(min(max_batch, len(queue)))]

The Triton knobs

NVIDIA's Triton Inference Server is the reference implementation. You turn it on per model with a dynamic_batching block in the model config. The values below are illustrative:

max_batch_size: 32 dynamic_batching { preferred_batch_size: [ 8, 16 ] max_queue_delay_microseconds: 50000 # default 0 }

From the proto and the batcher docs: requests join the batch "in the order the requests were received". If a preferred_batch_size can be formed, it "will be executed immediately", and the batcher sends "the largest possible preferred size". Otherwise it sends "the largest size possible that is less than the maximum batch size". max_queue_delay_microseconds is how long a request may wait "to wait for additional requests for batching. Default is 0." With a delay set, the batch still goes out early if it hits a maximum or preferred size. Other fields: preserve_ordering, priority_levels, and a queue policy with max_queue_size and timeouts that REJECT or DELAY.

The trade-off as a formula back-of-envelope

Take Poisson arrivals at rate λ and a model that is idle when the first request arrives. The first request opens the window; in the next d seconds about λ·d more arrive, unless the batch fills first:

taddedextra wait, oldest request ≤ min( d, Bmax−1λ ) E[b]expected batch ≈ min( Bmax, 1+λ⋅d ) λfull=Bmax−1drate where the batch fills before the timer
dthe window, max_delay (Triton: max_queue_delay_microseconds)5–100 ms below B_maxmax batch size32 below λarrival rate, requests per second0–1,000 below bthe batch size that actually fires1 … B_max
d = 50 ms, B_max = 32: λ = 10 req/s → E[b] = 1 + 10 × 0.05 = 1.5 # pay up to 50 ms for 1.5× λ = 200 req/s → E[b] = 1 + 200 × 0.05 = 11 λ_full = 31 / 0.05 = 620 req/s # above this, it fills first

E[b] = min(32, 1 + λ·d), plotted, not simulated. A bigger window buys bigger batches at every rate, and costs up to d of latency each time the timer fires. Once λ passes λ_full the window no longer matters, since the batch fills before the timer. The dotted line is where our 32-token example below stops getting cheaper per request.

One caveat the formula hides: it assumes the model is idle. If the model is still busy with the last batch, requests pile up behind it, and the next batch is roughly λ × (time the model was busy), whatever d is. (Our inference from the docs' "largest size possible" rule: with the default d = 0, Triton still batches whatever queued while the model was busy.) This is exactly what happens with generation, below.

Why it is great for one-pass models

Vision models, embedding models and classifiers answer in one forward pass. Every request in a batch costs the same and finishes at the same moment, so there's no padding tax on output length. Batching only makes each pass wider. In our cost model, an 8B-parameter model on one H100 doing a single pass over 32-token inputs (an illustrative embedding-style workload):

b = 1: max(2·8.03e9·32 / 989e12 = 0.52 ms, 16.06 GB / 3.35 TB/s = 4.79 ms) = 4.80 ms per pass → 209 req/s b = 9: 4.81 ms per pass → 1,873 req/s # 9 × 32 = 288 ≈ 295 tokens b = 32: 16.67 ms per pass → 1,920 req/s # compute-bound, no gain

Our cost model (CostModel.raw(b·32, b·32)), a floor at 100% of peak. Up to about 295 tokens per pass the GPU is waiting on the 16.06 GB weight read, so extra requests ride along for free: 9 requests cost what 1 costs. With traffic at 200 req/s, a 50 ms window gives E[b] ≈ 11, past that knee, for at most 50 ms of extra wait. Without batching, the server tops out at 209 req/s. This is why Baseten's rule is "dynamic batching for most other models" (their example is SDXL image generation).

Why it is still wrong for generation E2, our simulation

A generated answer isn't one pass; it is one pass per token. A request-level batcher keeps the batch together from the first prefill until the longest output in it is done. The window fixes static batching's worst problem (waiting for 32 arrivals), but not the rest. TTFT p50 at 2 req/s, 1,000 requests, log scale (1 ms to 10 s):

Static, B=328,698 ms Dynamic, B=32, 50 ms1,957 ms Continuous + chunked11.1 ms

Our simulation (Llama-3.1-8B BF16, one H100, 100% of peak). Static waits for 32 arrivals, about 16 s at 2 req/s. Dynamic fires after 50 ms, so it is 4.4× better, but it is still 176× worse than continuous.

Where do dynamic's 1,957 ms come from if the window is only 50 ms? Almost all of it is waiting for the previous batch to finish. We instrumented the same run (same trace, seed 1): the dynamic batcher fired 169 batches with a mean size of 5.92 (none full), and each one ran for 3.06 s on average, until its longest output was done. The idle-server formula predicts 1 + 2 × 0.05 = 1.1 per batch. The busy-server estimate predicts 2 req/s × 3.06 s ≈ 6.1, which is what we see. The window barely matters: the output length sets the batch.

dynamic, 2 req/s: 58% padding waste 27% of requests in SLO TPOT p50 5.4 ms TTFT p99 8,065 ms saturated: 930 tok/s at 20 req/s 892 tok/s at 60 req/s static, saturated: 913 at 20, 916 at 60 # the same ceiling continuous + chunked, 60 req/s: 9,102 tok/s 9,102 / 892 = 10.2× # Databricks: "10x-20x"

"Padding waste" is the share of decode slot-steps where a row had already finished but still sat in the batch. The 169 / 5.92 / 3.06 s and the 892 tok/s at 60 req/s are our extra runs of the same simulator (simulate_request_level(clone(poisson_trace(1000, rate, seed=1)), CostModel(), 32, 0.05)). Databricks reports that continuous batching gets "10x-20x better throughput than dynamic batching". It also says dynamic batching "typically performs worse than static batching". In our model the two are within 2% of each other (930 vs 913 tok/s at 20 req/s), so we can't confirm that part.

The hybrid: dynamic batching inside continuous batching

Hugging Face TGI runs continuous batching, but for models without chunked prefill, a new request joining the running batch costs a prefill pass that stalls every running decode. So TGI batches the joiners, exactly the way a dynamic batcher does. New requests join only when one of these holds:

waiting ≥ ⌊running × waiting_served_ratio⌋ # like preferred_batch_size or decode steps since last join ≥ max_waiting_tokens # like max_delay
running = 10, waiting_served_ratio = 0.3 → join once 3 are waiting running = 10, waiting_served_ratio = 1.2 → join once 12 are waiting max_waiting_tokens = 20 → at most 20 decode steps ≈ 20 × 5.4 ms = 108 ms # batch 8 at 2k context, E1, our model

It is the same trade-off, but here the fixed cost being spread over the batch is a stall, not a forward pass. The window is counted in decode steps instead of microseconds. The default is disputed: the code (launcher/src/main.rs) and the launcher docs page say 0.3, while the doc comment's example and the router CLI listing say 1.2. max_waiting_tokens defaults to 20. The docs warn that setting it too high means "requests that could run in ~2s on an empty server could end up running in ~20s". When the model supports chunking, the launcher warns that both knobs "will be ignored".

Why it beats the alternatives for one-pass models

✗ No batching

Every request pays the full weight read alone. In the 32-token example that caps the server at 209 req/s, while the same GPU can do 1,873 req/s at batch 9.

✗ Static: wait for a full batch

Great throughput under heavy load, but at 10 req/s filling 32 seats takes 3.1 s, and the first request waits all of it. There's no upper bound on the wait.

✗ The same batcher, used for generation

The batch has to live for hundreds of steps. In E2 that's 1,957 ms median TTFT, 58% padding, and a ceiling around 900 tok/s, about a tenth of continuous batching.

✓ Dynamic batching, one pass

Latency added is capped at d, and the batch grows with traffic, as 1 + λ·d. Past the ~9-request knee in our example it serves 9× the requests of batch 1 for at most 50 ms of extra wait.

So is dynamic batching useless for LLMs?

As a request-level batcher for generation, yes. Triton's own docs send LLMs elsewhere: to "iterative sequences" in the sequence batcher (marked provisional), and in practice the TensorRT-LLM backend does its own in-flight batching. Baseten's advice is the same: "Use continuous batching for most LLM deployments and dynamic batching for most other models."

But its core idea, an admission window that trades a little waiting for a better-filled step, survives inside continuous batching. TGI's waiting_served_ratio and max_waiting_tokens are a dynamic batcher for joiners, above. Sarathi-Serve and vLLM V1 moved the window from time to tokens: each step, running decodes go in first, and waiting requests are admitted only into what's left of the token budget (max_num_batched_tokens). That is a per-step batch limit, re-decided every few milliseconds instead of once per request.

It is also not always right for one-pass models. When traffic is light, a window just adds latency: at 10 req/s a 50 ms window gives a batch of about 1.5, so keep d small or leave Triton's default of 0. When one item already fills the GPU (a large image, or a 512-token input to an 8B model, which is past the 295-token knee alone), batching adds almost no throughput. And a strict per-request latency target caps d directly, since the timer's wait adds straight onto every timed-out request.
