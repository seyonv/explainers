Handling concurrent requests

Also called async serving, the engine loop (busy loop, EngineCore), the request queue, streaming (SSE), backpressure (HTTP 429) and cancellation (abort). This card is what sits around step() inside one replica: how thousands of open connections feed one scheduler. The code is a stdlib asyncio lab, labs/async_server.py, driving the course's Scheduler with our simulator's step times (Llama-3.1-8B, BF16, one H100, 100% of peak).

In one breath

Many clients talk to an async API server, which tokenizes each request, drops it on a queue and hands the client a private stream. One engine loop, and only that loop, owns the scheduler: each turn it drains the queue, calls step(), runs the batch on the GPU and pushes each new token to the right stream. Concurrency happens at the edges (sockets, tokenizing, detokenizing); at the GPU it turns into batching.

The code: 30 lines of asyncio around the course's scheduler

Everything except engine_loop may run concurrently. generate is the HTTP handler; engine_loop is the only function that ever calls sched.add, step, finish_step or frees blocks. The names match labs/scheduler.py.

async def generate(req):              # one coroutine per HTTP client
    if len(streams) >= MAX_NUM_SEQS + MAX_WAITING:
        raise TooBusy("Retry-After: 1")          # -> HTTP 429
    q = streams[req.rid] = asyncio.Queue()       # this request's stream
    await inbox.put(("add", req))
    try:
        while (tok := await q.get()) is not DONE:
            yield f"data: tok{tok}\n\n"          # detokenize, SSE chunk
    finally:                                     # client hung up early?
        if streams.pop(req.rid, None) is not None:
            inbox.put_nowait(("abort", req.rid))

async def engine_loop():              # the ONLY code that touches sched
    while True:
        while not inbox.empty():                 # 1. drain new work
            kind, x = inbox.get_nowait()
            if kind == "add": live[x.rid] = x; sched.add(x)
            else: abort(x)       # live.pop(rid): O(1); free its blocks
        if not sched.has_work():
            await asyncio.sleep(0.001); continue
        plan = sched.step()                      # 2. schedule, no locks
        await asyncio.sleep(cost.step_time(plan))  # 3. fake GPU step
        done = sched.finish_step(plan, now())
        for r, _ in plan.scheduled:              # 4. stream new tokens
            if r.remaining == 1 and r.rid in streams:  # caught up
                streams[r.rid].put_nowait(r.num_generated)
        for r in done:                           # 5. close finished
            live.pop(r.rid, None)
            q = streams.pop(r.rid, None)         # None: client left
            if q is not None: q.put_nowait(DONE)
  • Cancellation. A closed socket runs the finally, which sends an abort message rather than touching the scheduler. Between steps the loop finds the request with live.pop(rid) (O(1) dict), removes it from running (O(R) list remove) or waiting (O(W) deque remove; vLLM's FCFS remove_request is also O(n)), and returns its blocks with free_request. Because this only happens between steps, the blocks are never freed while the GPU is still writing KV into them, and never freed twice.
  • Backpressure. len(streams) counts accepted, unfinished requests, so the cap is 8 seats plus a waiting queue of 10. The 19th client of the burst (client 18) gets 429 Too Many Requests with Retry-After: 1 at a cost of zero GPU time. A token cap (the sum of queued prompt tokens) is the better variant, because it prices a 4,096-token prompt as more work than a 50-token one. Mooncake goes one step further with prediction-based early rejection: when overloaded, it rejects a request at arrival if it predicts the request would miss its SLO anyway.

Why one owner beats a lock

step() keeps several facts true together: every block is in exactly one place (the free list, the evictable cache, or some request's block table); ref counts match the number of holders; len(running) ≤ max_num_seqs; the step's tokens fit the budget; a request is in waiting or running, never both. With many threads, every one of those needs the same lock, held for the whole of step() and finish_step(), so the threads just queue on it. The GPU is a single serial resource anyway: nothing is gained by planning two steps at once from two threads. A single owner that takes messages (the actor pattern) keeps the invariants trivially and makes the order of events deterministic. TGI's Rust router does the same thing: one background task owns the queue and serves Append and NextBatch commands over a channel, an actor with no locks (TGI source b4adbf2f, per our research notes).

The price: CPU time inside the loop

The loop is serial, so any CPU work it does between GPU steps adds to every step. Overlap scheduling (SGLang's default, vLLM's async scheduling) plans step n+1 while the GPU runs step n, which turns the sum into a max:

A real loop also builds input tensors, launches kernels and samples, and at small batches (a 5 ms step) 1.2 ms would be about 20%. That is why vLLM V1 moved tokenizing, detokenizing and streaming out of the loop ("up to 1.7x higher throughput compared to V0"), why SGLang's overlap scheduler exists ("1.1x" over its previous version), and why CUDA graphs matter: launching hundreds of small kernels one by one is CPU time too.

Why it beats the alternatives

✗ A thread per request, own forward pass

Each request runs alone, so the weights are read once per token per request. Our model: 205 tok/s at batch 1 against 9,973 tok/s for 238 requests batched (E1).

✗ Many threads, one locked scheduler

Correct if every path takes the lock, but the lock is held for the whole step, so it buys no parallelism, and one missed lock corrupts the free list or frees a block twice.

✗ Everything in one process

Tokenizing, detokenizing and streaming run between GPU steps and stretch every step. This is what vLLM V1 moved out of the loop, for up to 1.7× over V0.

✓ Async front end, one engine loop

Sockets and tokenizers run concurrently; one owner applies adds and aborts between steps and batches everything. Correct by construction, and the GPU sees one full batch per step.

Where does concurrency actually happen, if one loop runs everything?

At the edges, and then as batching. Waiting on thousands of sockets is I/O, and one event loop handles it without a thread each. Tokenizing and detokenizing are CPU work in other processes, running at the same time as the GPU. The GPU part is not threaded at all: 20 concurrent clients become rows of one step. You can see this on the M3 with llama-server (Llama-3.2-3B Q4, reused from Course 5): 1 client gets 28.9 tok/s; 16 clients get 100.2 tok/s in total but 8.5 each, with a 5.16 s TTFT. More concurrency bought throughput and cost each user speed, exactly as E1 predicts.

When one loop is not enough. One loop per replica is the rule, not one loop per cluster: data parallelism runs one engine core per replica, and a router spreads load across them. Tensor parallelism keeps one loop but fans each step out to N workers. With overlap scheduling the loop has two steps in flight, so an abort must wait until neither in-flight step can still write the request's blocks (our inference; SGLang tracks this with "future" tensors). And if the model is tiny and runs on CPU, a plain thread pool with no batching can be fine: batching only pays when one weight read can serve many tokens.
