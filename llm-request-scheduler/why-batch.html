Why batching works: one weight read, many tokens

Also called batch size, arithmetic intensity or the critical batch size. In this course it is the mechanism under everything else: every batching strategy and every scheduler decision later on exists to put more tokens into each read of the weights. Numbers are for the running example, Llama-3.1-8B in BF16 on one H100, from our simulator's step-time model.

In one breath

Producing one token means reading all 16.06 GB of weights from memory, and that read takes about 4.8 ms whether the step computes 1 token or 200. So if you run many requests in the same step, they share that one read: total throughput goes up almost in proportion to the batch, and each user's speed drops only a little. Two things stop this from going on forever. Every request also has to read its own KV cache, and there is only so much memory to keep that cache in.

Everyday version: a bus trip costs about the same fuel and driver time with 1 passenger or 50. The fuel and the driver are the weight read. Each passenger adds a few seconds to load their luggage (their KV cache), and people on long trips bring more luggage. The bus fills up with luggage long before it runs out of seats.

The step-time formula

This is the cost model our simulator uses for one forward step (CostModel.step_time in labs/scheduler.py). It is a floor at 100% of peak; real engines are slower by their kernel efficiency and CPU overhead.

tstep=max( 2PTCmath , WBWweight read, shared ) + KVBWKV read, per request

B = 64 decodes at 2k context:
math    2 × 8.03e9 × 64 ÷ 989e12                 =  1.04 ms
weights 16.06 GB ÷ 3.35 TB/s                     =  4.79 ms
max(1.04, 4.79)                                  =  4.79 ms  # weights win
KV      64 × 2,048 × 131,072 B = 17.2 GB ÷ BW     =  5.13 ms
t_step                                           =  9.92 ms
64 tokens ÷ 9.92 ms                              = 6,450 tok/s

The first two terms sit inside a max, so extra tokens are free until the math takes longer than the weight read. The third term is added on top and grows with every request and every token of its context.

Where the knee is

If the weights were the only thing read, extra tokens would be free up to the point where the math takes as long as the weight read: 2PB/C = W/BW, so B = C/BW × W/2P ≈ 989e12 / 3.35e12 ≈ 295. That is the critical batch size Bcrit. At B = 295 the step would still be 4.79 ms and throughput would be about 61,500 tok/s. In practice you never get there, for two reasons:

  • The KV read grows first. Each 2k-context request adds 2,048 × 128 KiB = 0.27 GB of reads per step. The KV read matches the 16.06 GB weight read at B ≈ 60 at 2k context, and at B ≈ 15 at 8k (16.06 GB ÷ 128 KiB = 122,528 tokens of context). Past that point, most of each step is KV reading, not weight reading.
  • Memory runs out. 63.9 GB of free HBM holds 487,504 tokens of KV: 238 sequences at 2k, 59 at 8k. Both caps are well below 295, so decode on this setup is memory-capacity-bound before it is ever compute-bound.

Four ways to get more tokens per weight read

✓ Bigger batch

More requests share each 4.79 ms read: 205 → 9,973 tok/s from B = 1 to 238 (our model). It is the one lever the scheduler owns, and the subject of this course. Cost: each user gets slower, and it only works if enough requests are in memory at once.

Speculative decoding

A cheap draft guesses k tokens, and one forward step of the big model checks them all, so one weight read can yield several tokens for the same user. Reported: 1.21× to 1.96× depending on batch size; DeepSeek about 1.8× at 80–90% acceptance. Cost: rejected guesses waste math, which is scarcer once the batch is already big (our inference).

Fewer bytes per weight

Quantize the weights, for example to 8 bits: W drops to 8.03 GB, so B = 1 goes from 205 to 404 tok/s in our model. At B = 238 it only goes from 9,973 to 10,377 (+4%), because the 19 ms KV read now dominates; for that, quantize the KV cache too. Reported: "30 to 50 percent better performance".

Shorter contexts

Less KV per request means less to read each step and more requests in memory: 238 fit at 2k against 59 at 8k, for 9,973 against 2,489 tok/s. Levers: trimming prompts, fewer KV heads (GQA, which Llama-3.1-8B already uses) and KV quantization. Cost: the model sees less, or loses some quality.

The 8-bit rows use our model with W halved and C unchanged; real FP8 also doubles peak math on an H100 and frees memory for about 268 sequences at 2k, so treat them as a floor. Quoted speedups are from the sources in the footer, not our simulation.

Then why not always run at the maximum batch?

Latency. Each step takes longer as B grows, and every user waits one step per token. At B = 238, decode alone takes 23.9 ms per token, inside our 50 ms TPOT SLO, but a 4,096-token prompt joining 64 decodes stretches their step from 9.9 to 72.8 ms. Capping max_num_seqs trades one for the other: under overload, 16 seqs give 2,694 tok/s at 5.8 ms TPOT, 512 seqs give 8,980 tok/s at 37.2 ms (our simulation, E4).

Memory. The cap is 238 at 2k and 59 at 8k, and every running request's KV keeps growing as it writes. Admit too many and the scheduler has to preempt and recompute: with 4,000 blocks at 30 req/s, 63 preemptions push TTFT p99 to 4.1 s.

Requests don't arrive together. At 2 req/s there are never 238 requests to batch, and every strategy delivers the same ~520 tok/s, because that is all the demand there is. The real question is how long you make an early request wait for company: static batching of 32 gives a median TTFT of 8.7 s, a 50 ms dynamic window 1.96 s, continuous batching 11 ms (E2). The next three cards are about exactly this.

When not to batch: a single user on a laptop (like the M3 above, where one stream is all there is), or a latency-critical request that should never share a step with long prompts. For offline jobs with no latency target, run at the memory cap.
