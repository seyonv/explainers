Static batching and its padding tax

Also called request-level batching or naive batching. It was the default before iteration-level scheduling (FasterTransformer-era servers, a plain padded generate() call), and it survives as TensorRT-LLM's kSTATIC_BATCH policy. On this card: our simulator, Llama-3.1-8B BF16 on one H100, B = 32.

In one breath

Wait until B requests have arrived, pad every prompt to the longest one, prefill them together, then decode the whole group until its longest answer is done. Nobody new can join mid-flight, and a row that finishes early keeps its seat, idle, until the last row is done. It's the simplest scheduler there is. You pay for that three times: padding, idle seats, and the wait for the batch to fill.

How it works four toy requests (0–3 of the course's toy trace)

  1. Collect B. The batch starts only when B = 4 requests are there. Request 3 arrives at 1 ms, so the batch starts at 1 ms.
  2. Pad and prefill. Every prompt is padded to the longest one (20 tokens), and one prefill step produces each row's first token.
  3. Decode to the longest. The group decodes one token per row per step until the row with the longest output (request 1, 9 tokens) finishes.
  4. Nobody joins. Rows that finish early sit idle. Requests 4–7 wait in the queue for the next batch.

Rows are seats in the batch and columns are forward steps. Column 1 is the prefill step, which makes each row's first token. Columns 2–9 are decode steps. Request 2 is done after column 2, but its seat stays reserved (and computed on) for 7 more steps.

# prompt padding: every row is padded to the longest prompt 4 rows × 20 = 80 prefill slots; real = 12 + 5 + 20 + 7 = 44 padding = 80 − 44 = 36 tokens (45%) # idle seats: 8 decode steps (columns 2–9) × 4 rows slot-steps = 4 × 8 = 32; useful = 3 + 8 + 1 + 5 = 17 idle = 32 − 17 = 15 slot-steps (47%) # the simulator's "padding waste" # time, our model: every step is weight-bound, about 4.8 ms 9 steps, 1.0 → 44.2 ms; request 4 arrived at 2 ms, first token at 49.0 ms

Our simulator (simulate_request_level(toy_trace(), cost, 4)). Request 4's TTFT is 47.0 ms. It waits behind request 1's ninth token, even though request 2's seat has been empty since 10.6 ms. At this tiny size the padding costs no time, because every step is paying for the 16.06 GB weight read anyway. It costs seats. At B = 32 with 500-token prompts it costs time too (below).

The waste, as an equation

The fraction of decode seats that sit idle depends only on the spread of output lengths inside a batch:

Brows in the batch4 toy · 32 at scale o_ioutput tokens of row i (the first comes from the prefill)4, 9, 2, 6 · median 201 o_maxthe longest output in the batch: every row runs this long9 · median 977.5
toy: 1 − 17 / (4 × 8) = 46.9% at scale (1,000 requests, 32 batches of 32, our trace): 1 − 269,469 / 917,528 = 70.6% → the 71% in E2

Our simulation. Output lengths are lognormal (median 200, σ 0.8, capped at 1,024). The median request writes 201 tokens, but the median batch runs 977.5 steps, and 15 of the 32 batches hit the 1,024 cap. The maximum of 32 draws from a long-tailed distribution is always near the tail. The rate doesn't change this: the same 32-request groups form at 2, 20 and 60 req/s, so waste is 71% at all three.

Our simulation (a floor at 100% of peak), from labs/experiments.py. Static batching is under the SLO even at 1 req/s: capacity 0 req/s, against 40 req/s for continuous + chunked. TPOT looks fine (8.0 ms), because once a batch is running it streams fast. The damage is all in the wait before the first token.

The memory side reserve for the worst row, for every row

A padded batch is one rectangular tensor. Its KV cache has to hold, for every row, the longest prompt plus room for the longest output the server allows. The server can't know in advance which row will run long, so it can't size rows individually.

one row: (4,096 max prompt + 1,024 max output) × 128 KiB = 671 MB 32 rows: 32 × 671 MB = 21.5 GB reserved average request uses 696 + 270.5 = 967 tokens = 18.9% of its row rows that fit in 63.9 GB: 487,504 / 5,120 = 95 # paged KV: 238 at 2k

Arithmetic on the course's shared numbers and our trace's means. The vLLM team reported that systems which reserve contiguous KV "waste 60% – 80% of memory due to fragmentation", against under 4% with paging. Engines that still reserve to completion (TGI, TensorRT-LLM's default GUARANTEED_NO_EVICT) do it per request, not per padded rectangle, and they let new requests join every step.

The code the core of simulate_request_level in scheduler.py

if len(queue) < max_batch and pending:
    deadline = queue[0].arrival + max_delay  # inf for static
    if pending[0].arrival <= deadline:       # someone can join
        t = max(t, pending[0].arrival)       # wait for them
        continue
batch = [queue.popleft() for _ in range(min(max_batch, len(queue)))]
b = len(batch)
p = max(r.prompt_len for r in batch)
o = max(r.output_len for r in batch)
t += cost.raw(b * p, b * p)                  # padded prefill
for k in range(1, o):
    t += cost.raw(b, b * (p + k))            # padded decode step
    for r in batch:
        if r.num_generated < r.output_len: ... # busy_slots += 1
        else: idle_slots += 1               # finished, seat idle

Lightly condensed from labs/scheduler.py: names are unchanged, and the first-token bookkeeping is left out. max_delay = inf is static batching; a finite window makes it dynamic batching (next card). Cost per batch is O(B · o_max) seat updates, and the batch is fixed from the first step to the last. The whole weakness is that the loop over k never looks at queue.

When static batching is the right tool

Two questions decide it: does all the work exist up front, and do the outputs have a (short, similar) length?

All work known up front · no decode, or equal lengths

✓ Static batching

Embeddings, classification, reranking or scoring (one forward pass, no decode). Offline jobs with a fixed short output. Sort by length into buckets and pad: no idle seats, no one waiting for a first token, and the simplest code there is.

Requests stream in · single pass (no decode)

✗ Static: waits to fill

Nobody should wait for 31 strangers. Use dynamic batching instead: a size cap plus a time window (Triton's max_queue_delay_microseconds, e.g. 16 requests or 100 ms in Baseten's example).

All work known up front · outputs vary

✗ Static: idle seats

A batch-API-style overnight job. Nobody is waiting, but 71% of seats idle is still 71% of the GPU bill. Sorting helps only if you know the output lengths (see below). Continuous batching still wins: 4,426 vs 2,164 tok/s with the same 32 seats in our sim.

Requests stream in · outputs vary (chat)

✗ Static: all three costs

This is the E2 table: 8.7 s TTFT p50 at 2 req/s, 0% in SLO at 20 req/s. Use continuous batching with chunked prefill, the default in vLLM, SGLang, TGI and TensorRT-LLM.

Inference: we don't have a source on how any provider's batch endpoint schedules work. "Batch-API-style" means only "large offline job, results in hours", and our sim says continuous batching is still the better engine for it.

Doesn't sorting by length fix it?

Partly. Bucketing similar lengths together attacks the padding, but not the wait for the batch to fill, and it can only fix the idle seats if you know the output lengths, which you don't until they're written. Our simulation: the same 1,000 requests, B = 32.

Sorting by prompt cuts the prefill padding and the padded KV reads (1.55× faster) but leaves the idle seats at 70%. Only oracle output sorting removes them, and even then continuous batching with the same 32 seats is 2× faster, because static still pads every prompt. Online, sorting doesn't help at all: with requests at 2 req/s arriving in perfect output-length order, static still has TTFT p50 8,642 ms and 1% in SLO. The bus still has to fill.

When static batching is the choice: single-pass models (embeddings, classifiers), offline jobs with fixed short outputs, and compiled engines that only run a few fixed shapes (one padded shape per length bucket). For anything that decodes a variable-length answer while people wait, use continuous batching.
