What real companies built

Also called case studies, production LLM serving, or reference architectures. This card collects what the teams that actually built these systems published: five open-source engines compared on the same seven scheduler choices, thirteen production write-ups as "what they faced → what they built → the number", what ByteByteGo covers and doesn't, and the patterns that show up again and again. Every row cites its source. Nothing here is our simulation except where a row says so.

In one breath

Every serious engine converged on the same core, the one this course builds: continuous batching over a paged KV cache, with prefix reuse. Where they differ is how bravely they admit work (gamble, estimate, or reserve the worst case) and what they do when memory runs out. Above the engine, the big fleets add the same three layers again and again: a router that sends each request to the replica already holding its prefix, separate pools for prefill and decode, and a gateway that says "no" early instead of letting queues explode.

Everyday version: restaurants. Every kitchen seats new diners as soon as a table frees up (continuous batching) and splits tables to fit parties (paging). Where they differ is the booking policy: some book tables speculatively and occasionally bump someone, some hold the table for the longest possible meal. The chains add a host who sends regulars back to the waiter who knows their order (cache-aware routing), a separate prep kitchen (prefill pool), and a "we're full" sign at the door (early rejection).

Patterns that recur

  • Continuous batching everywhere.vLLM, SGLang, TGI, TensorRT-LLM "in-flight batching", Anyscale's 23×, Databricks' 10–20× over dynamic, Baseten's rule. Dynamic batching survives only for one-pass models.
  • Paging everywhere.vLLM PagedAttention (under 4% waste vs 60–80%), TGI's block allocator, SGLang's paged radix cache, TensorRT-LLM's block accounting. Contiguous per-request slabs are gone from every engine above.
  • Reuse KV across requests, then route to it.Character.AI sticky sessions (95% hits), llm-d precise prefix routing (57× TTFT P90), SGLang's approximate radix tree in the router, GKE's prefix weight, Dynamo's Smart Router, ByteByteGo's agent-loop post. Round-robin quietly wastes a prefix cache.
  • Split prefill from decode, at scale.DeepSeek (4 prefill + 18 decode nodes), Mooncake, Dynamo's Planner, Together's three tiers, Meta's direction, TensorRT-LLM's disaggregated serving. None of these is a single-GPU deployment.
  • Push KV down a storage hierarchy.DeepSeek's on-disk cache (56.3% hits), Mooncake's CPU/DRAM/SSD pool, Dynamo's offload to SSD and object storage, Together's RDMA cache, Character.AI's host-memory cache.
  • Say no early.Mooncake's prediction-based early rejection, GKE's admission at the ingress, TGI's 128-request cap returning "overloaded". Rejecting at the door beats timing out in a queue.
  • Route and scale on load signals.Queue depth is a routing input in GKE (3:3:2, raised to 3:5:2) and in vLLM's data-parallel router (score = 4 × waiting + running). Dynamo's Planner shifts GPUs on TTFT/ITL SLOs; llm-d and the vLLM production-stack ship autoscalers, but our notes don't say which signal they scale on.

What to copy at your scale

✗ DeepSeek's P/D split on one box

Their split uses 4 prefill + 18 decode nodes and moves KV between them. On one GPU there is no second pool to hand off to; chunked prefill gets the no-stall benefit for free.

✗ Reserve to completion with varied outputs

TGI and TensorRT-LLM's default never preempt, but they hold max_new_tokens for every request. When most answers stop early, that memory sits empty and the batch stays small.

✗ Prefix caching behind round-robin

With several replicas, spreading requests evenly sends each conversation to a replica that doesn't hold its prefix. llm-d measured 2× throughput just from routing to the right pod.

✓ The shared core, one replica

Continuous batching, paged KV, hashed prefix cache, chunked prefill, FCFS, recompute on preemption: vLLM V1's defaults, and this course's reference scheduler. Add routing and pools only when you have more than one replica.

Caveats from the research

  • TGI's defaults conflict. The launcher page says waiting_served_ratio = 0.3 and the router CLI listing says 1.2; the source code sets 0.3 (1.2 is a doc example). The CLI text for max_batch_prefill_tokens ("max_input_tokens + 50") is also out of date against the code. TGI is now in maintenance mode.
  • Commissioned and vendor benchmarks. The GKE 92.8% result was commissioned by Google. The vLLM production-stack "10x" is the LMCache team's own benchmark. Dynamo's 30× is NVIDIA on NVIDIA hardware. Also, the GKE report's "+15.7%" throughput is 1 − 6,042.05 ÷ 7,169.21; measured the usual way, 7,169.21 ÷ 6,042.05 is 1.19× (our arithmetic).
  • Moved URLs. Character.AI's post moved from research.character.ai to blog.character.ai; vLLM's blog moved from blog.vllm.ai to vllm.ai/blog. Perplexity's own disaggregation post returned 403, so only NVIDIA's account of Perplexity is used here. That post's title says 400M queries a month and its body says 435M.
  • DeepSeek's 545% is theoretical. It is computed from theoretical revenue ($562,027 a day); DeepSeek says actual revenue is lower.

Why do the published speedups disagree so much (4× to 36.9×)?

Because each number divides by a different baseline, on a different model, hardware and workload. The same system can look 7× better or worse depending only on what it's compared with:

vLLM is 24× faster than HF and 3.5× faster than TGI in the same post: the baseline alone moves the headline 7×. Bigger models and longer, more varied outputs make static batching look worse, so the gap grows. Workload matters too: at 2 req/s every strategy in our simulation delivers about 520 tok/s, because there is nothing to batch.

How to read them: compare only within one row's setup, prefer "at the same latency" or "within SLO" claims over peak tok/s, and flag vendor or commissioned numbers. When a case study is the wrong model: a single-user local setup (one stream on a laptop) gains nothing from any of this, and fleet-scale designs (P/D pools, KV tiers) cost more than they save until the traffic is large enough to keep both pools busy.
