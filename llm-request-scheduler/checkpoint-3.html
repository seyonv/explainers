Checkpoint 3: past one GPU: reuse, split, route and size

Ties together prefix caching, every way to raise throughput, splitting prefill and decode, routing, admission and autoscaling and the whole system: which lever attacks which term, how reuse survives across many replicas, when to give prefill its own GPUs, and how many GPUs a target load needs.

How to use this page. Close the five cards. Answer each question in writing, in full sentences, before opening its Check. A wrong or shaky answer isn't a failure; it tells you exactly which section to reopen. The questions are mixed on purpose, so you have to work out which idea applies before you can answer.

1 · Mixed retrieval

  1. which concept?A service with 64 long system prompts grows from one replica to four behind a round-robin load balancer. Each replica is less loaded than before, yet the prefix hit rate falls to 46% and the median time to first token jumps to 2.7 s. Which concept explains it, and what fixes it?
    Check
    • each replica has its own prefix cache; round robin sends every prompt to every replica
    • the 64 prompts (8,192 blocks) overflow one replica's 4,000-block cache, so LRU evicts what the next request needs: 45.6% hits, TTFT p50 2,690 ms (workload B)
    • fix: prefix-aware routing, best a scored router (hit − load): 84.5% hits, 14.3 ms p50, 73.2 ms p99

    Missed it? Reopen routing, "Our simulation: four replicas, four routers".

  2. In E7 (four shared 2,048-token system prompts, a unique suffix each) the hit rate is 91.6%, but the median time to first token falls 209×. Why is 91.6% the ceiling for this workload, and where does the rest of the TTFT gain come from?
    Check
    • the unique suffixes (141,502 tokens) can never hit, and each shared prompt must be prefilled once: 149,694 computed of 1,779,902, so 91.6% is the best possible
    • without the cache, prefill takes about 72% of the GPU and a queue builds (3,344 ms p50)
    • with it, prefill falls to about 6%, the queue never forms, and TTFT is one short step (16.0 ms): the gain is mostly the vanished queue

    Missed it? Reopen prefix caching, the worked example.

  3. which concept?A team runs long prompts (median over 2k tokens) on 64 GPUs with strict targets on both TTFT and TPOT. Chunked prefill at budget 2,048 still leaves ITL p99 at 36 ms against a 9.9 ms decode-only step. Which idea do they need, and which single number tells them whether their network is fast enough for it?
    Check
    • disaggregation: prefill on one pool, decode on another, KV shipped between them; decode steps then never carry a prefill
    • the handoff-vs-recompute break-even: b_KV·C ÷ 2P ≈ 8.1 GB/s for this model; any faster link ships KV cheaper than rebuilding it
    • for scale: a 4,096-token prompt's 537 MB takes 10.7 ms at 50 GB/s and 1.2 ms on NVLink, against 66.7 ms of prefill

    Missed it? Reopen splitting prefill and decode, "The handoff".

  4. Size a fleet for 200 req/s of the course workload with one replica holding 40 req/s inside the SLO. Show the formula, the answer, and what each of its two safety terms protects against.
    Check
    • N = ⌈λ ÷ (ρ·μ)⌉ + 1 = ⌈200 ÷ (0.8 × 40)⌉ + 1 = 7 + 1 = 8 H100
    • ρ = 0.8: capacity is a cliff (41 req/s drops to 66% in SLO), so leave room for bursts and autoscaler lag
    • +1: survive one replica failing (7 × 40 = 280 ≥ 200)

    Missed it? Reopen the whole system, "Sizing the fleet".

  5. which concept?An autoscaler set to add replicas above 80% GPU utilisation never fires, even while TTFT p99 sits at 5 s. Which idea explains it, and which signals should it use?
    Check
    • GPU utilisation measures time busy, not work done: one decode stepping every 4.9 ms and 238 decodes stepping every 23.9 ms both look fully busy
    • scale on leading signals: queue depth (waiting requests or queued prefill tokens) and KV use
    • and keep headroom: a new replica needs its 16.06 GB of weights loaded (≈ 8 s at an illustrative 2 GB/s) before it serves anyone

    Missed it? Reopen routing and autoscaling, "Autoscaling: what to watch".

  6. At a full batch (B = 238, 2k context), compute the throughput with an FP8 KV cache and explain why 8-bit weights add only about 4% at the same batch.
    Check
    • KV read 19.07 → 9.5 ms; step 4.79 + 9.5 ≈ 14.33 ms; 238 ÷ 14.33 ms ≈ 16,609 tok/s (1.67×)
    • 8-bit weights halve the 4.79 ms weight read, which is only 20% of a full step, so 9,973 → 10,377 tok/s
    • levers multiply only when they attack different terms; at B = 1 the ranking flips (8-bit weights 2×)

    Missed it? Reopen throughput levers, the formula and "Which levers stack".

  7. A product team adds today's date and the user's name at the very top of every prompt, above a 2,048-token system prompt. Predict the prefix hit rate and explain why.
    Check
    • prefix matching starts at token 0: one changed token changes every block hash after it
    • every request's prefix is now unique, so the hit rate falls to about 0% (the E7 rerun with the unique part first: 0.0%, the same 3,344 ms TTFT p50 as no cache)
    • fix: stable parts first (system prompt, tools, documents), variable parts last

    Missed it? Reopen prefix caching, "Pitfalls".

3 · Project: route, split and size a fleet

What it reinforces: block-granular prefix reuse (prefix caching), affinity vs balance (routing), the KV handoff (disaggregation), which term a lever attacks (throughput levers) and fleet sizing (the whole system).

  1. Reuse arithmetic. 8 system prompts of 1,000 tokens; each of 500 requests picks one and adds a unique 100-token suffix. With 16-token blocks and plenty of memory, compute the tokens actually prefilled and the hit rate. Redo it for 256-token blocks.
  2. A new router. In labs/routing_sim.py, add a bounded-load prefix hash: hash as before, but if that replica's load (4 × waiting + running) is above 1.25 × the mean load + 1, try the next replica round the ring. Run it on both workloads with the file's seeds and put it in the table beside prefix-hash and scored.
  3. The handoff. For an 8,192-token prompt, compute its KV size, the handoff time over a 100 Gbps NIC (12.5 GB/s), an illustrative 50 GB/s link and NVLink (450 GB/s), its re-prefill time, and the break-even link speed with an FP8 KV cache.
  4. Size it. Size a fleet for 500 req/s of the course workload (μ = 40 req/s, ρ = 0.8, +1 spare, an illustrative $2.50 per H100-hour, mean output 265.8 tokens): replicas, hourly cost and cost per million output tokens. Then redo the count if a real engine reaches only 60% of our model's speed (μ = 24).
  5. Decide. In two sentences each: which router you would ship for workload B, and whether you would disaggregate 8,192-token prompts on the 50 GB/s link.
Done when: your router's rows are in the table, every number matches the check, and your two decisions each cite one number from your own results.
Check: the numbers (computed for this checkpoint with the course's labs)
  • Reuse: 550,000 prompt tokens; ⌊1,000 ÷ 16⌋ × 16 = 992 reused per hit; 550,000 − 492 × 992 = 61,936 prefilled; hit rate ≈ 88.7% (a token-level cache would reach ≈ 89.5%). With 256-token blocks only 768 tokens are reused per hit: ≈ 68.7%.
  • Bounded-load hash, workload A: 90.7% hits, TTFT p50 13.1 ms, p99 40.4 ms, 12,266 tok/s, requests 166 / 184 / 109 / 141: it fixes plain hashing's imbalance (10,459 tok/s). Workload B: 80.6% hits, p99 298.0 ms, 13,383 tok/s: spilling to the next replica breaks affinity, worse than plain hashing (84.5%, 117.6 ms) and the scored router (84.5%, 73.2 ms, 13,749 tok/s).
  • Handoff: 8,192 × 131,072 B ≈ 1.07 GB; ≈ 85.9 ms, 21.5 ms and 2.4 ms; re-prefill ≈ 133.4 ms; FP8 break-even ≈ 4.0 GB/s.
  • Sizing: ⌈500 ÷ 32⌉ + 1 = 17 H100, $42.50 per hour; 132,900 output tok/s ≈ 478.4 M tokens per hour → ≈ $0.089 per million. At μ = 24: ⌈500 ÷ 19.2⌉ + 1 = 28 H100.
  • Decisions (one reasonable pair): ship the scored router for B, because it is the only one best or tied on hits, p99 and throughput in both workloads; disaggregate the 8,192-token prompts only if decode streams need decode-only steps, since the 50 GB/s handoff adds 16% to a 133.4 ms prefill but spares every running stream a long stall.
