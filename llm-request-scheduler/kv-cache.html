The KV cache: what it stores and why generation needs it

Also called the key-value cache or the attention cache. It answers one of the course's three concept questions: the role of the KV cache during generation. Every size below is for the running example, Llama-3.1-8B in BF16 on one H100 SXM. Every time is from our simulator's cost model (CostModel in labs/scheduler.py), which runs at 100% of peak, so treat each time as a floor rather than a measurement.

In one breath

To predict the next token, every attention layer compares the new token with every earlier token. Those comparisons need two vectors per earlier token, per layer and per KV head: a key (K) and a value (V). The KV cache keeps them in GPU memory after they are first computed, so each decode step processes one new token instead of re-running the whole prefix. The price is memory: 128 KiB per token here. That memory, not compute, decides how many requests can share a batch.

Why decode needs every earlier token

At decode step t, the new token's query qt is scored against the keys of all t tokens so far, and those scores weight all t values. Nothing about token 5's key changes when token 500 arrives, because causal attention never lets earlier tokens see later ones. So K and V can be computed once and kept. What does change is the set: each step appends one K and one V per head per layer, and reads all of them back.

What happens without a cache

Without the cache, step t must push all t tokens through the model again just to rebuild the keys and values it needs. Generating n tokens then costs 1 + 2 + … + n token-passes instead of n.

∑t=1nt=n(n+1)2no cache: O(n²) vs nwith cache: O(n)

For n = 2,048 output tokens: 2,048 × 2,049 / 2 = 2,098,176 token-passes vs 2,048, which is 1,024.5× more tokens through the model.

The penalty looks mild for one request because batch-1 decode is paying mostly to read the 16.06 GB of weights (4.8 ms a step). Recomputing up to about 295 tokens hides under that read. Past that it turns compute-bound and grows with t. At a full batch there is no read to hide under, and the gap becomes 276×. That is why no serving engine runs without the cache.

So KV memory, not compute, caps the batch size. The GPU only becomes compute-bound at about 295 tokens per step (the critical batch size). Memory stops you at 238 sequences with 2k contexts and 59 with 8k, before you get there. When the pool is too small for the load, the scheduler has to preempt. In our simulation at 30 req/s, shrinking the pool from 30,469 blocks to 2,000 cut throughput from 6,736 to 4,063 tok/s, with 270 preemptions and 625,438 recomputed tokens.

So at full batch, the cache is 80% of the step time as well as 80% of the memory. Every byte you cut per token buys both more sequences and a faster step.

Cache, recompute or offload

A sequence's KV can stay on the GPU, be thrown away and rebuilt, or be parked somewhere cheaper. Each wins in a different situation.

OptionCost to use a 2k context againWins whenReal systems
Keep in HBM0.27 GB of HBM held; read 0.08 ms per step (our model)The sequence is decoding right nowEvery engine; vLLM's paged blocks
RecomputeA 2,048-token prefill: 33.3 ms (our model's floor)Memory is short and the prefix is short; nothing to store or movevLLM V1 preemption recomputes by default
Offload to CPU / SSDMove 0.27 GB back: 5.4 ms at an assumed 50 GB/s host link (illustrative)The sequence is idle between turns, or a long prefix is reused oftenMooncake pools CPU DRAM and SSD; Character.AI keeps inter-turn KV in host memory (95% hit rate); DeepSeek: 56.3% of input tokens hit its on-disk KV cache

Offload only pays when moving the bytes back is faster than rebuilding them. Mooncake's store-vs-recompute inequality works this out: see Mooncake I. The 50 GB/s link is an assumption, not a measured number.

Why it beats the alternatives

✗ Recompute the prefix every step

No memory needed, but 2,048 outputs push 2,098,176 tokens through the model. That is 276× slower at a full batch in our model.

✗ Reserve max length per request

A contiguous slot per request, sized for the longest possible output. vLLM measured 60–80% of KV memory wasted this way, so far fewer sequences fit.

✗ Keep the live cache off the GPU

Every step would pull 63.9 GB of context over a host link. At an assumed 50 GB/s that is 1.28 s per step instead of 19 ms (illustrative).

✓ Paged, compact cache in HBM

O(n) work, 238 sequences at 2k in 16-token blocks, shrunk further by GQA or FP8. It spills to host memory only between turns.

Is the KV cache the same as prompt caching?

No. The KV cache lives inside one request. It is built during prefill, grows by one token each decode step, and is freed when the request finishes. Prompt caching (prefix caching, automatic prefix caching, RadixAttention) keeps some of those KV blocks after a request ends, keyed by the tokens they came from, so the next request with the same opening skips that part of prefill. Every engine needs the first. The second is an optional layer on top of it, and it only helps when prompts share a prefix. It is covered on prefix caching and, from the caller's side, on prompt caching.

When you don't need it: a model that makes one forward pass per input, such as an embedding or classification model, never decodes, so it keeps no cache. And under memory pressure, a short preempted request is often cheaper to recompute than to keep or swap. vLLM V1 recomputes by default because, its docs say, recomputation has lower overhead there.
