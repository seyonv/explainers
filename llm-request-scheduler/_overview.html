The scheduler on one page

Overview of Build an LLM request scheduler, also called the serving-loop map or the batching cheat sheet. It pulls together the 24 cards: why decode is slow, what the KV cache is for, the four batching strategies, the scheduler's data structures and step(), KV paging, preemption, policies, concurrency, prefix caching, the throughput levers and the full system. H100 numbers come from our simulator (labs/scheduler.py: Llama-3.1-8B BF16 on one H100 SXM, a cost model at 100% of peak, so they are floors). Anything else names its source.

In one breath

A decode step reads all 16.06 GB of weights to make one token per sequence, so a lone request gets about 205 tok/s from a GPU that could do far more. The fix is to put many requests' tokens into each step. The whole job of the scheduler is deciding, every step, which tokens those are, under three limits: a token budget per step, a seat count, and KV-cache blocks. The KV cache holds every past token's keys and values (128 KiB per token), and it runs out first: 63.9 GB holds 238 sequences at 2k context. Continuous batching keeps the seats full (≈ 10× over static batching in our model). Chunked prefill stops long prompts stalling everyone. Paging and preemption keep memory full without running out. The wait-queue policy decides who waits, not how much gets done.

The three questions, answered in one line each

Bottlenecks?

Decode is bound by memory bandwidth (weights plus the KV read), prefill by compute, and the batch by KV capacity. Then come CPU overhead and prefill–decode interference. More →

The KV cache?

Each past token's keys and values, so each step computes only the new token: O(n) instead of O(n²). It costs 128 KiB per token, and it is what limits the batch size. More →

More throughput?

Fill every step: continuous batching, plus paging for room, plus chunking for smoothness. Then shrink bytes (GQA, FP8), skip work (prefix caching), and scale out (routing, P/D). More →

The words people use

Static vs dynamic batching

Static (request-level) waits for B requests and runs them to the longest output, with 71% padding in our runs. Dynamic adds a time window (Triton's max_queue_delay_microseconds). Both suit one-pass models, not generation.

TTFT · TPOT · ITL · goodput

TTFT is the wait for the first token. TPOT is the average gap after it. ITL is each individual gap. Goodput is requests/s that met the SLO. Capacity, the highest rate where 99% still do, is 40 req/s in our setup (TTFT ≤ 1 s, TPOT ≤ 50 ms).

Preemption · swap · recompute · retraction

These are the ways to evict a running request when KV blocks run out. vLLM recomputes the newest request. SGLang "retracts". TGI and TensorRT-LLM's default reserve to completion, so they never need to.

Continuous batching

Also called iteration-level scheduling (Orca) and in-flight batching (TensorRT-LLM): the batch is rebuilt every forward step. Chunked prefill (stall-free batching) and paged KV (PagedAttention) are what make it work in practice.

The takeaway

Keep every step full, and let KV memory be the only limit. Continuous batching, paging and a token budget get almost all of the win on one GPU. Everything after that is either about who waits (policies) or about many GPUs (routing, disaggregation).

When this doesn't apply: with a single user (a laptop, a private endpoint), there is no batch to fill, so per-user speed comes only from fewer bytes per step (quantization, speculative decoding). For one-pass models (embeddings, classifiers), dynamic batching is the right tool. Under sustained overload, no ordering helps: you need admission control (429s) or more replicas. Our H100 numbers are 100%-of-peak floors from a model that leaves out attention FLOPs and per-chunk overhead. Real engines are slower, but the shape is the same.
