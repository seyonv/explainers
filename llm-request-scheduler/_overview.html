Prime · 2 minutes before you read

The problem: An LLM server that runs one request at a time reads all 16.06 GB of weights to make a single token, so a GPU worth thousands of tokens a second delivers about 205. Without a map of why that happens, you tune the wrong thing: more FLOPs for a bandwidth problem, a smarter queue order for a memory problem, more replicas for a batching problem.

In one breath

A decode step reads all 16.06 GB of weights to make one token per sequence, so a lone request gets about 205 tok/s from a GPU that could do far more. The fix is to put many requests' tokens into each step. The whole job of the scheduler is deciding, every step, which tokens those are, under three limits: a token budget per step, a seat count, and KV-cache blocks. The KV cache holds every past token's keys and values (128 KiB per token), and it runs out first: 63.9 GB holds 238 sequences at 2k context. Continuous batching keeps the seats full (≈ 10× over static batching in our model). Chunked prefill stops long prompts stalling everyone. Paging and preemption keep memory full without running out. The wait-queue policy decides who waits, not how much gets done.

The three questions, answered in one line each

Bottlenecks?

Decode is bound by memory bandwidth (weights plus the KV read), prefill by compute, and the batch by KV capacity. Then come CPU overhead and prefill–decode interference. More →

The KV cache?

Each past token's keys and values, so each step computes only the new token: O(n) instead of O(n²). It costs 128 KiB per token, and it is what limits the batch size. More →

More throughput?

Fill every step: continuous batching, plus paging for room, plus chunking for smoothness. Then shrink bytes (GQA, FP8), skip work (prefix caching), and scale out (routing, P/D). More →

The words people use

Static vs dynamic batching

Static (request-level) waits for B requests and runs them to the longest output, with 71% padding in our runs. Dynamic adds a time window (Triton's max_queue_delay_microseconds). Both suit one-pass models, not generation.

TTFT · TPOT · ITL · goodput

TTFT is the wait for the first token. TPOT is the average gap after it. ITL is each individual gap. Goodput is requests/s that met the SLO. Capacity, the highest rate where 99% still do, is 40 req/s in our setup (TTFT ≤ 1 s, TPOT ≤ 50 ms).

Preemption · swap · recompute · retraction

These are the ways to evict a running request when KV blocks run out. vLLM recomputes the newest request. SGLang "retracts". TGI and TensorRT-LLM's default reserve to completion, so they never need to.

Continuous batching

Also called iteration-level scheduling (Orca) and in-flight batching (TensorRT-LLM): the batch is rebuilt every forward step. Chunked prefill (stall-free batching) and paged KV (PagedAttention) are what make it work in practice.

The takeaway

Keep every step full, and let KV memory be the only limit. Continuous batching, paging and a token budget get almost all of the win on one GPU. Everything after that is either about who waits (policies) or about many GPUs (routing, disaggregation).

When this doesn't apply: with a single user (a laptop, a private endpoint), there is no batch to fill, so per-user speed comes only from fewer bytes per step (quantization, speculative decoding). For one-pass models (embeddings, classifiers), dynamic batching is the right tool. Under sustained overload, no ordering helps: you need admission control (429s) or more replicas. Our H100 numbers are 100%-of-peak floors from a model that leaves out attention FLOPs and per-chunk overhead. Real engines are slower, but the shape is the same.

Understand and remember

  • Decode reads every weight once per step → one token per sequence per read → batch 1 wastes the read (205 tok/s) → put many requests' tokens in the step → throughput rises almost with B until the KV read and KV memory take over
  • Each request carries its own KV (128 KiB per token) → it must fit in the 63.9 GB left after weights and be read every step → KV capacity caps the batch (238 at 2k) and KV reads dominate a full step (80%) → the scheduler's real job is managing KV memory
  • The scheduler decides, every step, which tokens run under three limits → continuous batching keeps seats full, chunking caps the step length, paging and preemption keep memory full without running out → policies only reorder who waits
  • Past one GPU: many replicas behind a router that trades cache affinity against load, plus separate prefill and decode pools at scale → the outer layers keep the inner loop full and shed load before queues break the SLO
  • detail that matters Throughput levers multiply only when they attack different terms → FP8 KV stacks with batching (KV read is 80% of the step), 8-bit weights mostly don't (+4% at B = 238)

    Check

  2. mechanism Walk through what the scheduler does between two forward steps, naming the three limits it checks and the order it serves requests in.
    Check
    • finished requests leave and free their blocks
    • running requests go first: one decode token each, or their next prompt chunk
    • if a running request can't get a block, the newest is preempted
    • waiting requests are admitted in policy order while the token budget, the seat cap and the free blocks allow
  3. tradeoff At 60 req/s continuous batching gives 9,102 tok/s but only 41% of requests meet the SLO. Which row of the lever table do you reach for, and which rows would not help?
    Check
    • the replica is past capacity (40 req/s): the queue, not the step, is the problem
    • reordering levers (SJF, priority) only move who waits; under sustained overload they can't restore the SLO for everyone
    • admission control with 429s, or more replicas behind a KV-aware router, are what help

5 · Predict commit to an answer before revealing

Swap the running example for a model with MQA (16 KiB of KV per token) on the same H100 at 2k context. Before computing anything: which limit now binds first, and does the weight read or the KV read dominate a full step?

Reveal

KV per token shrinks 8×, so about 8× as many sequences fit (roughly 1,900 at 2k), which pushes the batch past the ≈ 295-token critical batch size: the math term now overtakes the weight read before memory runs out. At that batch the KV read per step is about the same 63.9 GB if memory is full, so KV read still matters, but compute starts to bind. The broader point is the one the card's caveat makes: with a tiny KV cache, weight bandwidth and then compute dominate for much longer.

Hint
