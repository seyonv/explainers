Who goes next: FCFS, SJF, priority, fairness

Also called scheduling policy, admission order or queue discipline. It covers FCFS (FIFO), SJF/SRPT (shortest job first / shortest remaining processing time), priority classes, VTC (Virtual Token Counter, a fair-share scheme), aging, EDF (earliest deadline first), MLFQ (multi-level feedback queue) and cache-aware LPM (longest prefix match). In our labs/scheduler.py it is one class, WaitQueue, and one argument: Scheduler(policy="fcfs" | "sjf" | "priority" | "fair").

In one breath

Each step, once every running request has its token, the scheduler admits waiting requests until the token budget, the seat limit or the KV blocks run out. The policy is just the order it reads the waiting queue in, which comes down to a data structure and a sort key. It changes who waits, not how much work gets done: throughput stays at 6,451–6,584 tok/s in every run below. Every policy that puts someone first puts someone else last.

It only matters when there is a queue

Below capacity, a request is admitted in the step after it arrives, whatever the order, because there is room for everyone. The policy only decides anything once requests pile up faster than they finish. Same trace, same simulator, two arrival rates:

# our simulation, 1,000 requests, max_num_seqs 64, seed 5 # rate 20 req/s: below capacity, a queue almost never forms FCFS TTFT p50 15.2 ms p99 81.8 ms worst E2E 8.22 s SJF TTFT p50 15.4 ms p99 81.2 ms worst E2E 8.18 s # same # rate 55 req/s: just past capacity, the queue keeps growing (E5) FCFS TTFT p50 7,489.8 ms p99 16,611 ms worst E2E 22.40 s SJF TTFT p50 97.2 ms p99 27,650 ms worst E2E 37.34 s

Rate 20 was computed for this card with poisson_trace(1000, rate=20, seed=5) and the E5 settings. At 55 req/s the policy is suddenly worth ~75× on the median (7,490 ÷ 97.2 = 77) and costs 1.7× on the worst request (37.34 ÷ 22.40).

Our derivation: because every waiting request ages at the same rate, linear aging is a fixed key (size + α·arrival), so it stays an O(log W) heap. A ratio like HRRN's (wait ÷ size) does reorder over time, which is why SGLang re-sorts its list every pass. Filled in with an illustrative request of 512 in / 200 out: SJF key 712; tenant counter +512 + 2×200 = +912.

If the high class alone exceeded capacity, batch would never be admitted: that is priority starvation, and it is why aging or a reserved share for the low class exists.

The code: WaitQueue

From labs/scheduler.py. Long lines are wrapped; the logic is unchanged. step() calls peek() to test whether the head fits and pop() to admit it, and it calls charge() for every request it runs, with that step's prompt and output tokens.

class WaitQueue:
    """Admission order. fcfs: deque, O(1). sjf / priority: heap,
    O(log n). fair: one deque per tenant + a served-token counter
    per tenant (VTC-style), pick = the tenant with the least
    service, O(tenants)."""

    def __init__(self, policy: str = "fcfs"):
        assert policy in ("fcfs", "sjf", "priority", "fair")
        self.policy = policy
        self.dq: deque[Request] = deque()
        self.heap: list[tuple] = []
        self.tenants: dict[str, deque[Request]] = {}
        self.served: dict[str, float] = {}
        self._n = 0
        self._seq = 0

    def _key(self, r: Request) -> tuple:
        if self.policy == "sjf":
            est = (r.predicted_len if r.predicted_len is not None
                   else r.output_len)
            return (r.prompt_len + est, r.arrival)
        return (r.priority, r.arrival)

    def push(self, r: Request, front: bool = False) -> None:
        self._n += 1
        if self.policy == "fcfs":
            self.dq.appendleft(r) if front else self.dq.append(r)
        elif self.policy == "fair":
            q = self.tenants.setdefault(r.tenant, deque())
            if r.tenant not in self.served:
                # VTC: a newly active tenant starts at the lowest
                # active counter, so it can't bank credit while idle
                active = [self.served[t]
                          for t, d in self.tenants.items()
                          if d and t in self.served]
                self.served[r.tenant] = min(active, default=0.0)
            q.appendleft(r) if front else q.append(r)
        else:
            self._seq += 1
            # a preempted request goes back with its original key,
            # so it is not penalised
            heapq.heappush(self.heap, (self._key(r), self._seq, r))

    def _fair_tenant(self) -> str:
        return min((t for t, d in self.tenants.items() if d),
                   key=lambda t: self.served[t])

    def peek(self) -> Request:
        if self.policy == "fcfs":
            return self.dq[0]
        if self.policy == "fair":
            return self.tenants[self._fair_tenant()][0]
        return self.heap[0][2]

    def pop(self) -> Request:
        self._n -= 1
        if self.policy == "fcfs":
            return self.dq.popleft()
        if self.policy == "fair":
            return self.tenants[self._fair_tenant()].popleft()
        return heapq.heappop(self.heap)[2]

    def charge(self, r: Request, prefill_tokens: int,
               decode_tokens: int) -> None:
        if self.policy == "fair":  # VTC: output costs 2x input
            self.served[r.tenant] = (self.served.get(r.tenant, 0.0)
                                     + prefill_tokens
                                     + 2 * decode_tokens)

Three details worth copying. _seq breaks heap ties, so two requests with equal keys never compare Request objects. front=True sends a preempted request to the head of an FCFS queue, while in a heap it keeps its original key. A tenant that returns after idling starts at the lowest active counter, so it can't save up credit and then flood the GPU.

How it differs from related ideas

✗ FCFS alone at overload

Nobody starves, but everyone's median is 7.5 s: every short chat waits behind every long job ahead of it.

✗ Pure SJF

A ~75× better median, but the longest jobs lose every tie: worst E2E 22.4 → 37.3 s, and p99 TTFT gets worse too.

✗ Strict priority, no floor

Interactive gets 36.1 ms, but if the high class ever fills the GPU on its own, batch is never admitted.

✓ A composite key, chosen per workload

Class first, then aged size, then arrival, in one heap, with per-tenant counters on top when tenants share the GPU. Each part fixes the failure of the one before it.

Which one should I pick?

SituationPickWhy
One tenant, one SLO, chatFCFS + chunked prefillThe engines' default. Nobody starves, and chunking keeps TPOT flat. Below capacity no ordering beats it (15.2 vs 15.4 ms)

They combine because a heap accepts any tuple. Fairness is the exception: it picks a tenant, then that tenant's own heap picks the request (O(T + log W)). An illustrative combined key (not in scheduler.py):

key = (r.priority,                        # class first
       r.prompt_len + est + ALPHA * r.arrival,  # aged SJF
       r.arrival)                         # tie-break

When the policy is not the answer: under sustained overload every order is just a choice of who suffers (see the aging table). Then the fix is fewer requests or more GPUs: reject or delay at the door (admission and backpressure) or add replicas (routing and autoscaling). And if every request has the same SLO and similar lengths, the extra machinery buys nothing over FCFS.
