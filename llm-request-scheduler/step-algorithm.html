step(), line by line

Also called the scheduling loop, schedule() (vLLM V1's name for it) or one scheduler iteration. This is the heart of the build-it exercise: the whole of Scheduler.step() and finish_step() from labs/scheduler.py, annotated block by block, then run on the course's 8-request toy trace. Every time on this card comes from our simulator (Llama-3.1-8B, BF16, one H100, 100% of peak), so treat it as a floor.

Prime · 2 minutes before you read

The problem: Everything the course has built so far (continuous batching, the token budget, KV blocks, preemption, policy order) has to happen in one function, before every forward pass, in well under a millisecond. Get the order of its phases wrong and you stall decodes, readmit the request you just evicted, or let big requests starve.

Where it fits: Third card of group 3, the heart of the build. It uses the counters and containers from the data-structures card and calls a BlockManager whose internals come on the next card; here you only need can_allocate and allocate.

In one breath

Before every forward pass, step() hands out a fixed token budget. Requests already running get served first, one token for a decode or the next slice of an unfinished prompt. If KV memory runs out, it evicts the newest running request. Whatever budget is left then goes to waiting requests, in policy order, until the budget, the sequence cap or free memory runs out. After the GPU runs the step, finish_step() moves the counters forward, emits a token for every request that has caught up, and frees the ones that are done.

The knobs step() reads

Think of a kitchen that cooks 16 plates a round (the budget), has 4 tables (the sequence cap) and 12 chairs (KV blocks). A group that keeps ordering needs more chairs the longer it stays.

step(), annotated

This is the reference code with the same names and logic. Only the comments are shorter, so that each line fits in 76 characters. The black numbers mark the four blocks explained under the code.

def step(self) -> StepPlan:
    budget = self.token_budget
    scheduled: list[tuple[Request, int]] = []
    preempted: list[Request] = []

1  # 1. running requests
    i = 0
    while i < len(self.running) and budget > 0:
        req = self.running[i]
        n = min(req.remaining, budget)
2      while not self.bm.can_allocate(req, n):
            victim = self.running.pop()  # newest = least work lost
            self._preempt(victim)
            preempted.append(victim)
            if victim is req:
                break
        else:
            self.bm.allocate(req, n)
            scheduled.append((req, n))
            budget -= n
            i += 1
            continue
        break                            # req itself was preempted

3  # 2. waiting requests (skip admission in a step that had to preempt)
    while (not preempted and len(self.waiting) and budget > 0
           and len(self.running) < self.max_num_seqs):
4      req = self.waiting.peek()
        self.bm.match_prefix(req)
        n = req.remaining
        if n > budget:
            if not self.chunked_prefill:
                break                    # whole prompt must fit this step
            n = budget
        if not self.bm.can_allocate(req, n, self.reserve):
            break                        # head of line waits for memory
        self.waiting.pop()
        self.bm.allocate(req, n)
        req.state = RUNNING
        self.running.append(req)
        scheduled.append((req, n))
        budget -= n

    return StepPlan(scheduled, preempted)
  1. 1Running requests first, in admission order. Each one takes n = min(req.remaining, budget). A request that is decoding has remaining = 1, and one halfway through its prompt has the rest of the prompt left, cut to whatever budget remains. That cut is what chunked prefill is. Nothing in the code checks for "prefill" or "decode": a request just has num_computed catch up with num_tokens, as in vLLM V1.
  2. 2Out of blocks? Preempt from the back. running.pop() removes the newest admitted request, which has done the least work, so the least is thrown away. It is also O(1). The loop keeps evicting until req fits. If req is itself the last one left to evict, it preempts itself and the running pass stops. Victims always come from behind the cursor i, so nothing already scheduled in this step is undone. (vLLM's priority mode picks the victim by priority instead, and has to refund one that was already scheduled.) Python's while … else: the else runs only if the loop ended without break, which means the allocation fits.
  3. 3No admission in a step that preempted. The victim was just pushed to the front of the waiting queue, so without not preempted the admission loop would pick it up again at once, into the memory it has just freed. vLLM V1 has the same rule (it only enters its waiting phase if not preempted_reqs). The reason given here is our reading of it, not a comment in their source. On the toy trace, removing the rule gives 5 preemptions instead of 3, and request 4 throws away 64 prompt tokens instead of 36. The finish time stays the same (100.7 ms), so the rule saves waste rather than time here.
  4. 4Admit in policy order while all three limits allow. peek() returns the head for FCFS, SJF, priority or fair. A prompt longer than the leftover budget is cut to fit. Admission has to leave self.reserve blocks free. If the head doesn't fit in memory, the loop breaks: nobody behind it gets to go first. That is head-of-line blocking, chosen on purpose. The alternative is shown below.
def _preempt(self, victim: Request) -> None:
    self.bm.free_request(victim)
    victim.num_computed = victim.num_cached = 0  # recompute
    victim.state = WAITING
    victim.preemptions += 1
    self.waiting.push(victim, front=True)

Preemption here means recompute: the victim gives back every block, and when it's readmitted it prefills its prompt and the tokens it has already generated. No KV is copied to CPU memory (swapping). vLLM V1 also defaults to recompute.

Head-of-line blocking or skipping ahead?

What if block 4 used continue to try the next waiting request instead of break? We changed that in a copy of the reference and ran the toy trace again (our variant, not in scheduler.py):

Admission when the head doesn't fitStepsPreemptionsReq 5 TTFTReq 4 TTFTLast finish
Stop at the head (reference)21353.5 ms50.7 ms100.7 ms
Skip ahead to anyone who fits22410.4 ms55.5 ms105.5 ms

Our simulation. Skipping lets small request 5 slip in at step 2 and get its first token 5× sooner. But it takes memory that request 4 (the big one) was waiting for, and request 5 is preempted itself one step later. Under steady load, skipping can keep a large request from ever finding enough free blocks: that is starvation. Engines that reorder the queue, such as SGLang with its cache-aware policies, add safeguards: it falls back to FCFS when the queue is long, and it offers an aging policy (HRRN).

finish_step(): apply what the GPU did

def finish_step(self, plan: StepPlan, now: float) -> list[Request]:
    done = []
    for req, n in plan.scheduled:
        prefill_part = min(n, max(0, req.prompt_len - req.num_computed))
        req.num_computed += n
        self.bm.cache_full_blocks(req)
        self.waiting.charge(req, prefill_part, n - prefill_part)
        if req.num_computed == req.num_tokens:  # caught up: a new token
            req.num_generated += 1
            req.token_times.append(now)
            if req.first_token_time is None:
                req.first_token_time = now
            if req.num_generated >= req.output_len:
                req.state = FINISHED
                req.finish_time = now
                done.append(req)
    for req in done:
        self.running.remove(req)       # O(R); a linked list: O(1)
        self.bm.free_request(req)
    return done
  • Advance num_computed by n. A chunk in the middle of a prompt emits nothing. The chunk that finishes the prompt catches up with num_tokens and emits the first token, which is where TTFT comes from. At step 0, request 1 gets 4 of its 5 prompt tokens and no token comes out. At step 1 its last prompt token runs and the first output token arrives, at 9.6 ms.
  • Emit a token whenever the request has caught up. num_generated += 1 makes num_tokens one larger, so next step remaining is 1 again: a decode.
  • Free finished requests once the loop is over. Their blocks go back to the free list and can be used from the next step on. cache_full_blocks publishes filled prompt blocks for prefix caching, and charge feeds the fair policy's per-tenant counters. Without those two features, both do nothing.

  1. Step 0: the budget splits 12 + 4. Request 0's whole 12-token prompt fits. Request 1 has a 5-token prompt but only 4 tokens of budget left, so it gets a 4-token chunk. Request 2 (20 tokens) arrived at the same moment and waits, because the budget is gone.
  2. Step 3: 0 free blocks, so request 3 waits despite a free seat. Only 3 of 4 sequences are running and 13 tokens of budget are left over, but request 2's decode took the last block. Request 3 needs 2 blocks for its 7-token prompt, so admission breaks at the head. Memory, not compute, is the binding limit here. At step 4, requests 0 and 2 have finished, 10 blocks come back, and requests 3 and 4 get in together.
  3. Steps 5–9: request 4 thrashes. Its 30-token prompt needs 8 of the 12 blocks. Admission only checks this chunk's blocks, so request 4 gets in with 8 tokens and then 14 more (6 blocks). At step 6, request 3's decode takes the last free block, request 4 needs 2 more, and it is the newest, so it preempts itself and loses 22 computed tokens. Block 3 keeps it out for that step. At step 7 it is readmitted with a 14-token chunk, and at step 8 it is preempted again (14 lost). Steps 6 and 8 each run only 2 decode tokens, so 14 of 16 budget tokens sit idle.
  4. Step 10: request 4 has the whole budget to itself. Requests 1 and 3 finish at the end of step 9 and give back 7 blocks. Request 4 re-prefills 16 tokens (30 − 14) in one step and gets its first token at 52.75 ms, a TTFT of 50.7 ms. In total it computed 66 prompt tokens to keep 30.
  5. Step 11 admits 5 and 6 behind it. Request 6 is preempted once more at step 12. The whole trace takes 21 steps with 3 preemptions, and the last request finishes at 100.7 ms.

The cure for thrashing is an admission rule, not a change to step()'s shape. Reserving each request's whole lifetime up front (TGI's approach) gives this trace 0 preemptions but 22 steps and 105.5 ms, and request 2's TTFT goes from 14.4 to 28.8 ms (our run, as on the build-it problem card). A watermark sits in between. See Admission, preemption and thrashing.

Why it beats the alternatives

✗ Waiting first

Admitting new prompts before serving running requests makes decodes wait behind prefill chunks, so TPOT and ITL jump. It also hands memory to newcomers that the running requests need in order to grow.

✗ Reserve every block up front

Never preempts, but it holds memory for tokens that may never be written, because the real output length is unknown. On the toy trace: 22 steps instead of 21, and request 2's TTFT doubles to 28.8 ms.

✗ Skip past a blocked head

Fills memory better and helps small requests (request 5's TTFT falls from 53.5 to 10.4 ms), but big requests can starve without aging, and on the toy trace there were more preemptions (4 instead of 3).

✓ Running first, lazy blocks, preempt the newest, stop at the head

O(R + A·log W) per step, FCFS order kept, and at most the newest request's work lost per eviction. The cost is thrashing when memory is tight, which admission rules and the watermark control.

Clarification

Why running before waiting? A running request has already been paid for. Its prompt is prefilled and its KV is in memory. Serving it first gets it to completion, which frees its blocks, and keeps its gaps between tokens short, which protects TPOT. It also means that when memory runs short, the newcomer is the one refused, not the request that is 90% done.

When it isn't the best choice. Prefill-first (SGLang's default loop) favours TTFT: a new request's prompt runs as soon as a prefill batch can form. That's the right call when time to first token is the SLO that matters, for example short chat turns. If preemption is unacceptable (long, expensive requests, or strict tail-latency promises), reserve to completion, as TGI and TensorRT-LLM's default do, and accept fewer requests in flight. If small requests must not wait behind big ones, skip ahead but add aging (see Admission, preemption and thrashing).

Understand and remember

  • Serve running requests first → they already hold KV and have paid for their prompt → finishing them frees blocks and keeps TPOT short → a newcomer is refused before a request that is 90% done
  • A running request can't get a block → pop the newest from running → it has done the least work, and pop() is O(1) → free its blocks, reset num_computed to 0, push it to the front of waiting
  • No admission in a step that preempted → otherwise the victim is readmitted at once into the memory it just freed → on the toy trace the rule saves waste (3 vs 5 preemptions), not time
  • Admit in policy order and break at a head that doesn't fit → strict order, no starvation of big requests → costs small requests some TTFT (request 5: 53.5 vs 10.4 ms with skipping)
  • detail that matters Python's while … else → the else runs only when allocation succeeded without a break → one loop both evicts until the request fits and detects that the request evicted itself
