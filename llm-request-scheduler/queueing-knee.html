Queueing and the knee: why p95 explodes before the GPU is full

Also called utilisation (the Greek letter ρ, "rho"), saturation, the hockey-stick curve, Little's law, and open-loop versus closed-loop load. You are about to sweep a server's load and mark "the knee" on a plot of p95 time to first token (p95 is the value 95% of requests beat). This card says why the curve has a knee at all, where it sits on an engine with continuous batching, and why a concurrency sweep and a request-rate sweep are two different tests. The measured-looking numbers are our simulation (the course's scheduler with Llama-3.1-8B on one H100 at 100% of peak, so they are floors, not a benchmark).

Prime · 2 minutes before you read

The problem: You sweep a server's load and p95 time to first token is flat, flat, flat, then ten times worse, while the token gap still looks healthy. Without a model of queueing you cannot say where that bend will be, why it is so sudden, or why two load tests of the same server disagree about it.

Where it fits: Group 1, straight after the metrics card. That card defined TTFT, TPOT and capacity and said a closed loop hides queueing; this one explains why the curve bends at all, using the running set that continuous batching and the KV cache cards fill in later.

In one breath

A server has a top speed: the most requests it can finish per second, second after second, without falling behind. This card calls it the maximum sustainable rate. Utilisation is how much of that rate the arriving traffic uses. Requests arrive in random clumps, not evenly, so the wait for a free place grows slowly at first and then very fast as utilisation nears 100%. The bend in that curve is the knee. On an LLM server the wait lands in time to first token (TTFT), so p95 TTFT blows up while tokens still stream smoothly and the GPU still seems to have room.

1. Utilisation: how much of the maximum sustainable rate is in use

Two rates matter. The arrival rate is how many requests show up per second. The maximum sustainable rate is the most requests the server can finish per second when it is never idle (queueing textbooks call it the service rate). Utilisation is the first divided by the second. It is not the same as "capacity" on the Measuring a server card: capacity is the highest rate that still meets the latency targets you promised (the SLO), so it can never be higher than the maximum sustainable rate.

ρutilisation = λrequests arriving per second μmost it can finish per second
λ"lambda", the arrival rate: you choose it in a rate sweep20 req/s μ"mu", the maximum sustainable rate: you measure itabout 39 req/s ρ"rho", utilisation: a share between 0 and 120 ÷ 39 = 51%
our simulated server finishes at most about 39 req/s 20 req/s arriving: 20 ÷ 39 = 51% # half its maximum rate 30 req/s arriving: 30 ÷ 39 = 77% 36 req/s arriving: 36 ÷ 39 = 92% 40 req/s arriving: 40 ÷ 39 = 103% # more than it can ever finish

Our simulation. The 39 req/s comes from flooding the simulator with 512 always-busy users and counting what it finishes: 39.4 req/s with 30,720 requests. With 15,360 requests it is 39.0, and 38.8 to 40.0 across seeds 0 to 3.

Below 100% the server keeps up on average. Above 100% it never catches up. The surprise is how bad things get just below 100%.

2. Why the wait grows much faster than the load

If requests arrived on a perfect beat, and every job took the same time, a server at 95% would never make anyone wait. Real requests arrive in clumps: nothing for a moment, then three at once. A server with spare time clears each clump in the quiet gap that follows. A nearly full server has almost no quiet gaps, so the leftovers from one clump are still there when the next clump lands.

The simplest textbook model makes this exact. It has one server that handles one job at a time, with random arrivals and random job lengths (its textbook name is M/M/1). In that model:

mean wait in queuebefore service starts = service timeone job, alone × ρ1−ρthe multiplier
UtilisationThe arithmetic, ρ ÷ (1 − ρ)Wait, in service timesIf one job takes 100 ms (illustrative)
50%0.50 ÷ 0.501×100 ms
80%0.80 ÷ 0.204×400 ms
90%0.90 ÷ 0.109×900 ms
95%0.95 ÷ 0.0519×1,900 ms

Pure arithmetic from the formula. From 50% to 95% the load grew 1.9× (0.95 ÷ 0.50) and the wait grew 19×. The bottom of the fraction, 1 − ρ, is the spare capacity, and dividing by a number that is heading to zero is what makes the curve turn upward.

An LLM server is not this simple model. With continuous batching it serves many requests in the same step, not one at a time, and each step gets slower as more requests share it (the step-time formula). So take the shape from the formula, flat and then a wall near 100%, and do not use it to predict your numbers. The next section shows what the shape looks like on an engine.

3. Where the knee sits on a real engine

An engine keeps a running set: the requests it is generating tokens for right now. Two things limit its size. One is the engine's cap on concurrent sequences (the setting --max-num-seqs in vLLM, max_num_seqs in our simulator, 256 in these runs). The other is KV cache memory: every running request holds memory for each of its tokens, and when no free blocks are left the next request cannot start.

  • While the running set has room, a new request joins at the next step. Extra load makes each step bigger and slower, so everyone's tokens come a little slower: TPOT, the time per output token (the gap between two tokens), goes up. TTFT hardly moves.
  • Once the running set is full, a new request has to wait outside until someone finishes. That wait happens before its first token, so it lands in TTFT. The requests already running keep the same batch size, so their token gaps stay where they were.

This is why TTFT breaks while the gap between tokens still looks fine. Past the knee, TPOT sits at 24.5 ms, well inside a 50 ms target, because the batch cannot grow past 256. All the damage is in the queue. It is also why an engine's knee comes later and sharper than the simple model says. Compare growth with growth, from 26% to 92% utilisation:

simple model: 0.256 ÷ 0.744 = 0.35× → 0.923 ÷ 0.077 = 12× the wait grows 12 ÷ 0.35 = about 34 times our engine: TTFT p95 43.8 → 114.3 ms = 2.6 times

Two things explain the gap. The growing batch soaked up the load. And any system that serves many requests at once has a later, sharper knee than the one-server model, because a newcomer only waits when every place is taken at the same moment.

Predictions from arithmetic, not measurements. Redo this with your own numbers. Read your GPU's real KV capacity from the server's startup log, and use your own request sizes: a shared 800-token system prompt and a spread of lengths will not give 1,280 tokens each. Check the cap on concurrent sequences (--max-num-seqs) in the same startup log rather than assuming a default. On an L40S, a sweep from 1 to 128 users may sit close to the memory limit, so the top of your sweep may already show queue time. The engine's own count of waiting requests (vLLM exports it as vllm:num_requests_waiting) stays at zero until the running set fills.

4. Little's law: turn a concurrency into a request rate

A concurrency sweep fixes how many requests are in flight, and your benchmark tool prints the request rate it achieved. One line of arithmetic connects the two. It lets you check the printed rate, and it explains why that rate stops rising. In words: the number of requests in flight equals the request rate times the time each request spends in the system (waiting plus being served). A café that serves 2 customers a minute, each staying 5 minutes, has 2 × 5 = 10 customers inside (illustrative).

Lrequests in flight = λrequests per second × Wseconds each one spends inside so λ=LW

A fixed-concurrency test pins L: it is the number you pass as the concurrency (--max-concurrency in vLLM's benchmark tool). If your tool reports the mean end-to-end time (you may have to ask for it), that is W. Divide, and you have the rate that test actually delivered. Our simulation, closed loop, seat cap 256. Each user sends its next request the moment the last one finishes. Doubling the number of requests moved the rates and mean times by about 6% or less, and p95 TTFT at 16 users or fewer by up to 7 ms.

Read the table twice. Up to 256 users, every added user made tokens slower (TPOT 4.8 → 24.5 ms) and TTFT stayed under 100 ms: the running set still had room. At 512 the running set was full, the rate stopped rising, and Little's law leaves only one place for the extra users to go: time. Once the rate is flat, doubling the users doubles how long each one waits.

5. Closed loop versus open loop: two different tests

The 64, 44 and 39 are from the tables above. 44 − 39 = 5 extra requests join the queue every second.

open loop at 44 req/s against a server that finishes 39: backlog grows by 44 − 39 = 5 requests every second after 60 s: 5 × 60 = 300 requests waiting a new arrival then waits 300 ÷ 39 = 7.7 s, and it keeps climbing

So a concurrency sweep can never show you an unbounded queue, however hard you push. Use it first, to find the maximum sustainable rate and watch tokens slow down. Then use Little's law to turn its best rows into request rates, and run a short rate sweep around them (for example 70%, 80%, 90% and 100% of that rate) to see where p95 TTFT bends. The flags and load shapes are covered on benchmarking a server in Inside an inference engine.

6. Where to set the operating point

Run below the knee: a common starting point is 70 to 80 percent of the maximum sustainable rate. For our simulated server that is 0.7 × 39 = 27 to 0.8 × 39 = 31 req/s. At 30 req/s, TTFT p95 is 79.8 ms and TPOT p50 is 10.9 ms. You give up about a quarter of the maximum rate and in return small surprises stay small: near the knee, going from 36 to 40 req/s (11% more traffic) takes TTFT p95 from 114 ms to 2.8 s.

Bursty arrivals need more headroom. The same average rate can arrive in tighter clumps, and a clump briefly pushes the server past 100% even when the average is well below it. Same simulator, same requests, only the spacing changed (the benchmark tool's --burstiness setting; 1 is Poisson, 0.25 is heavy bursts):

Average rateUtilisationTTFT p95, PoissonTTFT p95, bursty (0.25)
26 req/s67%71 to 72 ms119 to 144 ms

34 req/s87%98 to 103 ms184 to 1,217 ms

Our simulation. Each cell is the range over 3,000-, 6,000- and 12,000-request traces. The Poisson cells barely move with test length. The bursty cells at 26 and 30 req/s drift up by about a fifth, because a longer test catches rarer, bigger clumps. At 34 req/s the bursty result swings more than 6×: that server is already on the knee, at a rate where Poisson arrivals are still steady (they hold to 36 req/s in section 3). With bursty traffic, 70% is the safer end of the range.

What to do when traffic goes above the operating point (add replicas, or turn requests away early) is on many replicas: routing, admission and autoscaling.

Why running below the knee beats the alternatives

✗ Run at the maximum rate

The most tokens per GPU, and no slack at all. At 40 req/s against a maximum sustainable rate of about 39, TTFT p95 is 2.8 s after 6,000 requests and still growing.

✗ Trust a concurrency sweep alone

It throttles itself, so it cannot show a growing queue. 512 users settle at a TTFT p95 of about 7 s at either test length. An open loop at 44 req/s gives a p95 of 4.7 s after 3,000 requests, 12.4 s after 6,000, and still rising.

✗ Watch the token gap only

Past the knee TPOT sits at 24.5 ms, inside a 50 ms target, while TTFT p95 is over 100× worse. The queue is invisible in any per-token number.

✓ Find the maximum rate, run at 70 to 80%

A rate sweep finds the maximum sustainable rate (about 39 req/s here). At 30 req/s, TTFT p95 is 80 ms and a burst has a quarter of the server to land in.

Is the knee one fixed number for my GPU?

No. It is a property of the GPU, the engine settings and the traffic together. Longer prompts or longer answers make each request cost more, so the maximum sustainable rate drops and the knee moves left. A lower seat cap or less KV memory fills the running set sooner. Burstier arrivals reach the knee at a lower average rate. Measure it with traffic shaped like yours, and measure it again when the traffic changes.

It is not the GPU utilisation percentage that monitoring tools print. That number is the share of time the GPU was doing something. A single stream can read anywhere from about 30% to near 100%, depending on how much CPU-side work sits between steps, and a full batch reads near 100%. It does not rise in step with load, so it cannot tell you how much room is left. Utilisation on this card is the arrival rate divided by the maximum sustainable rate, which you have to measure with a sweep.

Near the edge, the answer depends on how long you test. The course quotes a capacity of 40 req/s for this server, from 3,000-request traces. That rate sits right on the maximum sustainable rate: with 3,000 requests TTFT p95 is 523 ms, with 6,000 it is 2,810 ms. A short test flatters a server that is slowly falling behind.

When staying below the knee is the wrong goal: offline batch work, such as evaluations or bulk summarising. Nobody is waiting on a first token, so run the server flat out and judge it on tokens per GPU-hour. There a closed-loop test is also the honest one. And p95 is only one point of the tail; how to read p50, p95 and p99 together is on tail latency.

Understand and remember

  • Arrivals come in random clumps → a server with spare time clears each clump in the next quiet gap → as utilisation nears 100% the gaps vanish and leftovers pile up → the wait grows like ρ ÷ (1 − ρ), far faster than the load
  • An engine adds new requests to the running set while it has seats and KV memory → extra load first becomes a bigger, slower step (TPOT rises) → once the running set is full, new requests wait outside before their first token → TTFT explodes while TPOT stays flat
  • Requests in flight = rate × time inside (Little's law) → a closed-loop test fixes the in-flight count → rate delivered = concurrency ÷ mean end-to-end time → once the rate is flat, more users only buy more time
  • A closed loop waits for each reply before sending again → it throttles itself and its queue is bounded → it cannot show the unbounded queue an open loop builds past the maximum sustainable rate → find that rate, then run at 70 to 80% of it
  • detail that matters Which limit fills the running set first decides where the knee is: min(seat cap, KV tokens ÷ tokens per request) → in our runs the 256 seats filled and memory never did → a sweep that stops below that number sees slower tokens but no queue knee
