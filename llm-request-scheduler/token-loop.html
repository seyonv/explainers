The token loop: prefill, then decode

Also called prompt processing and generation, autoregressive decoding, or one forward step (an iteration) at a time. This is the first concept card of "Build an LLM request scheduler": every later card schedules these two kinds of work. Numbers are for the running example, Llama-3.1-8B BF16 on one H100, plus real measurements on your M3.

In one breath

A request runs in two phases. Prefill is one forward pass over all the prompt tokens at once. They are all known up front, so the work is parallel and limited by compute. It ends by producing the first output token. Decode then runs one forward pass per remaining output token. Each pass needs the token the previous one produced, so the steps are strictly sequential, and each one reads all 16 GB of weights to make a single token.

One request, step by step toy request 0: prompt 12, output 4

Each row is one forward step, and each square is one token position. Amber squares are computed in a prefill pass and green squares in a decode pass. Grey means the token's keys and values are already stored (the KV cache), so the step reads them but does not recompute them. A dashed square is the new token that comes out of the step, and the arrow feeds it into the next step.

Our simulator (CostModel in labs/scheduler.py), request 0 running alone. The prefill pass emits output token 1, so 4 output tokens need only 3 decode steps. Token 4 is never fed back, because the request ends. Here all four steps cost the same 4.79 ms: 12 tokens of math take only 0.19 ms, so every step is waiting on the 16.06 GB weight read. Short prompts are that cheap. The next example shows a long prompt, where prefill finally costs more than a decode step.

A realistic request: 1,000 tokens in, 200 out

On the H100, run alone. The prefill pass does 2 × 8.03B × 1,000 FLOPs, which takes longer than reading the weights, so it is compute-bound. Each decode step does 1,000× less math but still reads every weight once, so it is bandwidth-bound:

The key idea for this course: a decode step barely cares how many tokens it carries

Decode's cost is the weight read, and one read can serve many requests at once: each row of the batch adds only its own KV read and a sliver of math. In our simulator (E1, decode at 2k context each), the step time grows far more slowly than the batch:

1 request4.9 ms · 205 tok/s 8 requests5.4 ms · 1,472 tok/s 32 requests7.4 ms · 4,349 tok/s 64 requests9.9 ms · 6,450 tok/s

Our simulation, labs/experiments.py E1. Bars are step time (full width = 10 ms). 64× the tokens for 2× the time: total throughput goes from 205 to 6,450 tok/s, while each user's speed falls from 205 to 101 tok/s.

So a scheduler's job is to put as many requests' tokens into each step as it can, and to stay within what memory holds and what latency targets allow. Everything else in this course (batching strategies, the token budget, KV blocks, admission, preemption, policies) is about how to do that well. Why batching works takes this apart.

There is more than one way to get more tokens out of each weight read. Batching is the one this course builds:

The shape is the same everywhere: prefill is many times faster per token than decode. The size of the gap depends on how much compute the chip has per byte of bandwidth (295 FLOPs per byte for the H100), on the kernels, and on prompt length. The H100 number is a floor at peak; the M3 numbers are real, with a busy machine. Why the M3 gap is so much smaller is our inference, not measured.

Why generation is shaped like this

PREFILL · SHAPE OF THE WORK

Parallel

Every prompt token is known before the first step, so all 1,000 go through the model in one pass. Causal attention lets each token look only at earlier ones, and that is still computed in parallel.

DECODE · SHAPE OF THE WORK

Sequential

Token 2 is the input for the step that makes token 3. Nothing can skip ahead, so 200 output tokens mean 200 passes (199 after prefill). That is what "autoregressive" means.

PREFILL · WHAT LIMITS IT

Compute

1,000 tokens share each weight read. The math takes 16.2 ms and the read 4.8 ms, so the GPU's arithmetic is the limit. Above about 295 tokens (the H100's FLOPs per byte), more tokens mean more time.

DECODE · WHAT LIMITS IT

Bandwidth: the opening

One token per 16.06 GB read: 0.016 ms of math waiting on a 4.79 ms read. Almost all of the arithmetic sits idle, which is exactly what batching fills: 64 tokens take 9.9 ms instead of 4.9.

Isn't prefill just the first decode step?

In code, nearly. It's the same model, the same forward function and the same causal attention, and it ends the same way, with one new token sampled from the last position. That's why vLLM V1's scheduler doesn't label steps as prefill or decode at all: each step is a dictionary {request_id: num_tokens}, and a prompt is simply a request with many tokens left to compute. Our scheduler.py works the same way (num_computed vs num_tokens).

In cost, no. Running the 1,000-token prompt one token per step, decode-style, would take 1,000 steps and about 4.81 s (our model), against 16.3 ms in one pass: about 300× slower. The difference is how many tokens share each weight read, and that is the reason prefill exists as its own phase.

When the split matters less: short prompts. Below about 295 tokens, a prefill pass costs about the same as a decode step, because both wait on the weight read (toy request 0: 4.79 ms either way). A prefix cache hit also shrinks prefill to the uncached tail. And a long prompt doesn't have to go in one pass: chunked prefill splits it across steps so decodes don't stall. When prefill and decode need different hardware, some systems run them on separate GPUs.
