The whole system, drawn

Also called the LLM serving architecture, the inference platform, or a reference architecture. This is the course's capstone: every part from the earlier cards put into one working system, from a client's HTTP request to the GPU and back. The timings come from our simulator (Llama-3.1-8B, BF16, one H100 per replica, 100% of peak, so they are floors). Network and gateway hops are marked illustrative.

In one breath

A gateway decides whether a request gets in (auth, per-tenant token limits, 429s). A router decides where it goes (the replica that already holds its prefix and isn't overloaded). Inside each replica, one engine loop decides when it runs: every step, the scheduler packs decodes and prompt chunks into a token budget that the paged KV block manager can hold. Metrics feed an autoscaler that adds or removes replicas. All the throughput comes from that inner loop; the outer layers exist to keep it full, keep its caches warm, and shed load before queues blow the SLO.

2 · Zoom: one engine step, and what it touches

The step our request is admitted in. 64 requests are decoding (one token each); request r65 arrives with a 1,000-token prompt. Names are the ones in labs/scheduler.py. The circled numbers in the right column say which phase of step() reads or writes each structure.

Our simulation: CostModel.raw(1064, 64·2048 + 1000) = 22.4 ms for the mixed step, against 9.9 ms for the 64 decodes alone (E1) and 16.3 ms for r65's prefill alone. Because r65 fits the budget in one chunk, its first token comes out of this step. With a 4,096-token prompt the step would be 72.8 ms and every other user would feel that stall; the budget exists to cap it (Chunked prefill). The 304-block reserve is 1% of 30,469 (Admission, preemption and thrashing).

The request pays about 2.1× in E2E for sharing the GPU, and in return the replica streams to 64 users at once: 6,450 tok/s instead of 205 (E1). Both numbers sit far inside the course SLO (TTFT ≤ 1 s, TPOT ≤ 50 ms). Everything in front of the engine together is about 3% of E2E; the decode loop is 96%, which is why the rest of this course is about the loop. At its peak, r65 holds ⌈1,199 / 16⌉ = 75 blocks (the 200th token is never fed back), 157 MB of KV.

5 · Sizing the fleet

Target: 200 req/s of the course workload (prompts median 512, outputs median 200) under the course SLO. One H100 replica with continuous batching and chunked prefill holds 40 req/s with every request inside the SLO (our simulation, steady state: 3,000-request traces, TTFT p99 675 ms). At 41 req/s only 66% make it: past capacity the queue grows without bound, so you never plan to run at the edge. Leave room for bursts and autoscaler lag, and for one replica dying:

no headroom:   200 / 40            = 5.00  → 5 replicas (all at the cliff)
with ρ = 0.8:  200 / (0.8 × 40)    = 6.25  → 7
plus N+1:                                  → 8 H100
check: lose one, 7 × 40 = 280 req/s ≥ 200

cost at $2.50 per H100-hour (illustrative):
  8 × $2.50       = $20.00 / hour = $480 / day
  200 req/s × 3,600 = 720,000 requests / hour
  → $0.028 per 1,000 requests
  mean output 265.8 tokens → 53,153 tok/s → 191.4 M tokens / hour
  → $20.00 / 191.4 = $0.105 per million output tokens

The mean output of 265.8 tokens is the mean of our poisson_trace lognormal (median 200, σ 0.8, capped at 1,024), computed over 100,000 draws. 40 req/s comes from a cost model at 100% of peak, so it is an upper bound on capacity. If a real engine reached 60% of our model's speed (illustrative), μ = 24 and the same sum gives ⌈200 / (0.8 × 24)⌉ + 1 = ⌈10.42⌉ + 1 = 12 H100 at $30/hour. Benchmark your own engine before you buy. Compare the throughput-levers card: at 9,973 tok/s a single H100 costs $0.070 per million output tokens (illustrative price).

Why it beats the alternatives

✗ Batch requests, one model server per GPU

Static or time-window batching behind a load balancer: each batch runs to its longest output. It misses the SLO even at 1 req/s (E2): capacity 0.

✗ Good engines behind a round-robin load balancer

Each replica is fast, but the prefix cache is split N ways and hot replicas queue. llm-d measured 57× worse P90 TTFT than precise prefix-aware routing.

✗ Disaggregate everything on day one

Two pools to size, a KV transfer on every request, and more ways to fail, when chunked prefill already holds TPOT at 7.1 ms for our short-prompt workload.

✓ Layers, each with one job

A gateway that sheds load, a KV-aware router, and one continuous-batching engine loop per replica. Each layer can scale and fail on its own, and the GPU sees full batches.

What would you build first?

One replica, done well. Continuous batching with a token budget, a paged KV block manager and prefix caching are most of the win: 916 → 9,100 tok/s at saturation (≈ 10×, E2), 2.5× more sequences in the same memory from paging, and 11.9× fewer prefill tokens when prompts share a system prompt (E7). Add a bounded queue with a 429 and streaming, and one H100 serves 40 req/s of our workload inside the SLO (steady state).

Then add layers only when the numbers ask for them. A second replica means you need a router. Make it prefix-aware once hit rates drop or queues build unevenly. Add an autoscaler when traffic varies over the day. Split prefill and decode only when long prompts push TTFT and TPOT against each other and chunked prefill can't fix both. Build the KV offload tier when the reusable prefixes outgrow HBM.

When this design is not the right one. An offline batch job (evaluations, synthetic data) needs no gateway, router or streaming: one engine fed a queue as fast as it drains, with the largest batch memory allows, is simpler and cheaper. A model small enough for a CPU, or one user on a laptop (llama-server on the M3: 28.9 tok/s at one client), doesn't need a fleet at all.
