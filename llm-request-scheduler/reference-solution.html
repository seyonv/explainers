The reference solution, end to end

Also called: a minimal continuous-batching scheduler, a toy vLLM. This card is where the build section pays off. It walks through labs/mini_scheduler.py, a complete solution in 176 lines of standard-library Python. The scheduler itself is the first 120 lines; the rest is a fake model loop, the invariant checks and the toy-trace run. It's built in the v1 → v2 → v3 order from the build-it problem, and it reproduces the reference's 21-step toy trace step for step. All times come from our simulator (Llama-3.1-8B on one H100 at 100% of peak, so they're a floor).

In one breath

Three containers and one rule. There's a waiting deque, a running list and a free list of KV blocks. Every step, the running requests go first: each gets one decode token, or the next chunk of its prompt. Then new requests are admitted from the head of the queue while the token budget, the seat cap and the free blocks allow. If a running request can't get a block, the newest one gives all of its blocks back and starts over later. That's about 45 minutes of code, and it has the same shape as the loop vLLM V1 runs.

Each version runs on the toy trace, and each fixes a failure you can see in the one before. v1 needs 17 blocks when the pool has 12. v2 is safe but takes 22 steps. v3 takes 21 steps and preempts 3 times.

The data structures, with two examples each

Think of a restaurant. There's a queue at the door (waiting), the tables in use (running), a stack of clean chairs (the free list), and a note of which chairs each party is sitting on (block tables).

Build it in three passes

Each block is collapsible. Green lines are new in that pass. v1 and v2 are earlier versions of the same methods. The v3 block is the file exactly as it is.

v1 · FCFS continuous batching with a budget 0–15 min · no memory model 
@dataclass
class Request:
    rid: int
    arrival: float           # seconds
    prompt_len: int
    output_len: int          # max new tokens; stop here
    num_computed: int = 0    # tokens whose KV is in the cache
    num_generated: int = 0   # output tokens so far
    state: str = "waiting"   # waiting|running|finished|cancelled
    first_token: float | None = None
    finish: float | None = None

    @property
    def remaining(self):     # tokens that still need a forward pass
        return self.prompt_len + self.num_generated - self.num_computed


class Scheduler:
    def __init__(self, budget=16, max_seqs=4):
        self.budget, self.max_seqs = budget, max_seqs
        self.waiting, self.running = deque(), []

    def add(self, r):                           # O(1)
        self.waiting.append(r)

    def step(self):                             # -> [(rid, n_tokens)]
        budget, self.plan = self.budget, []
        for r in self.running:                  # running first
            if budget == 0:
                break
            n = min(r.remaining, budget)
            self.plan.append((r, n))
            budget -= n
        while (self.waiting and budget > 0
               and len(self.running) < self.max_seqs):   # admit FCFS
            r = self.waiting.popleft()
            n = min(r.remaining, budget)        # the clip = chunking
            r.state = "running"
            self.running.append(r)
            self.plan.append((r, n))
            budget -= n
        return [(r.rid, n) for r, n in self.plan]

    def on_step_done(self, now):                # O(R)
        for r, n in self.plan:
            r.num_computed += n
            if r.remaining == 0:                # caught up: 1 new token
                r.num_generated += 1
                if r.first_token is None:
                    r.first_token = now
                if r.num_generated == r.output_len:
                    r.state, r.finish = "finished", now
        self.running = [r for r in self.running if r.state == "running"]
COSTadd O(1). step O(R + A) for R running and A admitted: the waiting queue is only touched at its head. on_step_done O(R). TOY TRACE16 steps, 76.7 ms, request 2's first token at 14.4 ms. But it holds 17 blocks at its peak, and the pool has 12. SKIP IT AND…Skip the budget, and a 4,096-token prompt joins 64 decodes: that step takes 72.8 ms instead of 9.9 ms (E3). Skip "running first", and new prompts use up the budget while decodes stall. Skip the min() clip (chunked prefill), and request 2's 20-token prompt never fits the 16-token budget, so it blocks the head of the queue forever.
v2 · KV blocks and admission 15–30 min · safe, never preempts 
class BlockAllocator:
    def __init__(self, num_blocks, block_size):
        self.total, self.size = num_blocks, block_size
        self.free = deque(range(num_blocks))    # the free list
        self.tables = {}                        # rid -> [block ids]

    def needed(self, r, n):                     # new blocks for n tokens
        have = len(self.tables.get(r.rid, ()))
        return max(0, -(-(r.num_computed + n) // self.size) - have)

    def can_fit(self, r, n):                    # O(1)
        return self.needed(r, n) <= len(self.free)

    def allocate(self, r, n):                   # O(blocks added)
        table = self.tables.setdefault(r.rid, [])
        for _ in range(self.needed(r, n)):
            table.append(self.free.popleft())

    def release(self, r):                       # O(blocks held)
        self.free.extend(reversed(self.tables.pop(r.rid, [])))


class Scheduler:
    def __init__(self, kv, budget=16, max_seqs=4):
        self.kv, self.budget, self.max_seqs = kv, budget, max_seqs
        self.waiting, self.running = deque(), []

    def add(self, r):                           # O(1)
        worst = r.prompt_len + r.output_len - 1   # peak KV tokens
        if -(-worst // self.kv.size) > self.kv.total:
            raise ValueError(f"request {r.rid} can never fit")
        self.waiting.append(r)

    # step(), the admission loop: reserve the worst case up front
            r = self.waiting[0]
            worst = r.prompt_len + r.output_len - 1
            if not self.kv.can_fit(r, worst):
                break                           # head of line waits
            self.waiting.popleft()
            self.kv.allocate(r, worst)          # never grows again

    # on_step_done(), after counting tokens: give the blocks back
        for r in self.running:
            if r.state == "finished":
                self.kv.release(r)
        self.running = [r for r in self.running if r.state == "running"]
COSTcan_fit O(1). allocate O(blocks added). release O(blocks held). step is still O(R + A) plus the blocks it touches. TOY TRACE22 steps, 105.5 ms, peak 12 blocks, 0 preemptions. Request 2 waits 28.8 ms for its first token instead of 14.4 ms, because its 6-block reservation has to fit first. SKIP IT AND…Skip admission, and v1 asks for 17 blocks from a pool of 12. On a GPU that means running out of memory, or writing KV over another request's. Skip the check in add(), and a request bigger than the whole pool waits at the head forever, with everyone behind it stuck too.
v3 · lazy blocks, preemption, chunked admission, cancel 30–45 min · the final file 
class Scheduler:
    def __init__(self, kv, budget=16, max_seqs=4):
        self.kv, self.budget, self.max_seqs = kv, budget, max_seqs
        self.waiting, self.running = deque(), []
        self.live = {}                          # rid -> Request
        self.plan, self.preempted = [], []

    def add(self, r):                           # O(1)
        worst = r.prompt_len + r.output_len - 1   # peak KV tokens
        if -(-worst // self.kv.size) > self.kv.total:
            raise ValueError(f"request {r.rid} can never fit")
        self.live[r.rid] = r
        self.waiting.append(r)

    def cancel(self, rid):                      # O(W) if waiting, else O(1)
        r = self.live.pop(rid, None)
        if r is not None:
            if r.state == "waiting":
                self.waiting.remove(r)
            r.state = "cancelled"               # running: _reap frees it

    def _reap(self):                            # O(R); never mid-step
        for r in self.running:
            if r.state != "running":
                self.kv.release(r)
                self.live.pop(r.rid, None)
        self.running = [r for r in self.running if r.state == "running"]

    def _preempt(self, r):                      # recompute, not swap
        self.kv.release(r)
        r.num_computed, r.state = 0, "waiting"
        self.waiting.appendleft(r)
        self.preempted.append(r)

    def step(self):                             # -> [(rid, n_tokens)]
        self._reap()
        budget, self.plan, self.preempted = self.budget, [], []
        for r in list(self.running):            # running first
            if budget == 0 or r.state != "running":
                break
            n = min(r.remaining, budget)
            while r.state == "running" and not self.kv.can_fit(r, n):
                self._preempt(self.running.pop())   # OOM: evict newest
            if r.state == "running":
                self.kv.allocate(r, n)
                self.plan.append((r, n))
                budget -= n
        while (not self.preempted and self.waiting and budget > 0
               and len(self.running) < self.max_seqs):   # admit FCFS
            r = self.waiting[0]
            n = min(r.remaining, budget)        # chunked prefill
            if not self.kv.can_fit(r, n):
                break                           # head of line waits
            self.waiting.popleft()
            self.kv.allocate(r, n)
            r.state = "running"
            self.running.append(r)
            self.plan.append((r, n))
            budget -= n
        return [(r.rid, n) for r, n in self.plan]

    def on_step_done(self, now):                # O(R)
        for r, n in self.plan:
            if r.state != "running":
                continue                        # cancelled mid-step
            r.num_computed += n
            if r.remaining == 0:                # caught up: 1 new token
                r.num_generated += 1
                if r.first_token is None:
                    r.first_token = now
                if r.num_generated == r.output_len:
                    r.state, r.finish = "finished", now
        self._reap()
COSTstep O(R + A + k), where k is the number of blocks allocated or freed. Each preemption is an O(1) pop plus O(its blocks). cancel is O(W) for a waiting request (deque.remove) and O(1) for a running one: it only sets a flag, and _reap frees the blocks later. _reap is O(R). TOY TRACE21 steps, 100.7 ms, 3 preemptions. Request 4 is preempted at steps 6 and 8 and request 6 at step 12. That is thrashing on a pool that small. v3 admits a prompt when this chunk's blocks fit, not the whole request's, which is why request 4 gets in with half its prompt. SKIP IT AND…Skip preemption, and a request that can't grow has to be skipped. Two requests (prompt 4, output 3) in a 2-block pool then each hold 1 block and each need a second one. Neither can ever move: a deadlock (our run; with preemption it's done in 5 steps). Skip the "no admits after a preemption" guard, and the toy trace preempts 5 times instead of 3. Free a cancelled request's blocks while its step is still running on the GPU, and a new request can reuse those block ids while the old writes land (the ABA bug in the public exercise).
The harness · fake model, invariants, event loop the last 5 minutes · verbatim 
def step_time(plan):     # fake model: Llama-3.1-8B, H100, 100% of peak
    toks = sum(n for _, n in plan)
    ctx = sum(r.num_computed + n for r, n in plan)
    return (max(2 * 8.03e9 * toks / 989e12, 16.06e9 / 3.35e12)
            + ctx * 131072 / 3.35e12)


def check(s):            # invariants, after every step()
    assert sum(n for _, n in s.plan) <= s.budget
    assert len(s.running) <= s.max_seqs
    held = sum(len(t) for t in s.kv.tables.values())
    assert held + len(s.kv.free) == s.kv.total
    assert not {r.rid for r in s.running} & {r.rid for r in s.waiting}
    for r, n in s.plan:
        assert len(s.kv.tables[r.rid]) * s.kv.size >= r.num_computed + n


def run(trace, s, log=lambda *a: None):     # the fake model loop
    pending, t, steps = deque(sorted(trace, key=lambda r: r.arrival)), 0, 0
    while pending or s.waiting or s.running:
        while pending and pending[0].arrival <= t:
            s.add(pending.popleft())
        if not (s.waiting or s.running):
            t = pending[0].arrival
            continue
        s.step()
        check(s)
        log(steps, t, s)
        t += step_time(s.plan)
        s.on_step_done(t)
        steps += 1
    return steps
COSTcheck is O(R + W + blocks), so run it in tests, not in production. step_time is the course's cost model: step = max(2·P·T / C, W / BW) + KV read / BW. SKIP IT AND…Without check() after every step, a bookkeeping bug such as a double free or a request in two queues shows up 50 steps later as a wrong TTFT, far from its cause.

Why it beats the alternatives

✗ Prefill-only or decode-only steps

nano-vllm runs a prefill batch whenever a prompt fits, and a decode batch otherwise. While a long prompt prefills, every running decode waits. Mixing both in one step under a budget avoids that stall: 72.8 ms vs 9.9 ms for a 4,096-token prompt (E3).

✗ Reserve to completion (v2, TGI)

This never preempts, but it holds blocks for tokens that may never be written. On the toy trace it takes 22 steps and 105.5 ms, vs 21 steps and 100.7 ms, and request 2's first token comes 2× later.

✗ Static batching

It's simpler still, but finished rows sit idle until the whole batch ends: 71% of decode slots are padding, and it meets the SLO at no request rate at all (E2).

✓ Mixed steps, lazy blocks, preempt the newest

The budget keeps each step short. Lazy blocks fit the most requests into memory. Preemption keeps it from deadlocking. It's the vLLM V1 loop in about 120 lines, and 40 req/s within SLO in our simulator (E2).

The extension follow-ups

1. Priority and fairness → Who goes next

Change the waiting deque to a heap keyed on (priority, arrival). Push and pop become O(log W). A preempted request goes back with its original key, since a heap has no "front". The victim becomes the worst (priority, arrival) instead of running[-1], which is an O(R) scan in vLLM. For tenants, keep one deque per tenant and a served-token counter (VTC), and admit from the least-served tenant. In our simulator at 55 req/s, priority brings interactive TTFT p50 from 7,395 ms down to 36.1 ms (E5). Under fairness, the light tenant's TTFT p50 drops from 8,353 ms to 46.0 ms (E6). Add aging so low-priority requests don't starve.

2. Prefix sharing → Prefix caching

Give the allocator a ref count per block and a map from a chained hash of each full prompt block to its block id. At admission, match the longest cached prefix. Bump the ref counts and start num_computed after the hit, but never cover the last prompt token, because a forward pass is still needed to produce logits. release decrements the counts. A block that drops to 0 stays cached as evictable, in LRU order, until the free list runs dry. With 4 shared 2,048-token system prompts we measured a 91.6% hit rate, and TTFT p50 went from 3,344 ms to 16.0 ms (E7).

3. Streaming and concurrency → Handling concurrent requests

Keep step() single-threaded. Callers on many threads put add and cancel into a thread-safe inbox, and the loop drains it before each step, which is where our run() admits arrivals. Stream by pushing each new token to a per-request queue inside on_step_done. Cancel is already safe against a step in flight, because blocks are only freed in _reap, which runs when no step is on the GPU. The next problem is CPU time: step() costs 0.3–0.6 ms against a 5–25 ms GPU step (E9), so real engines plan step N+1 while step N runs.

4. Many GPUs → Routing and autoscaling and Splitting prefill and decode

This scheduler stays per replica. In front of the replicas goes a router that picks one: random, least-loaded, or prefix-aware so repeated prompts land where their KV already lives. llm-d measured P90 TTFT of 0.542 s with precise prefix-aware routing vs 31.083 s for the baseline (8 vLLM pods, 16 H100s, Qwen-32B). Beyond that, split prefill and decode onto different replicas and send the KV between them. DistServe reports 7.4× more requests within its latency targets. Admission turns global: reject with HTTP 429 when every queue is too long, and autoscale on queue depth, since the H100 burst above shows memory isn't what runs out first.

5. "How would you measure it?" → Measuring a server

Record each request's arrival time, the time of every token and its finish time. run() already stamps first-token and finish times. From those you get TTFT, TPOT/ITL and end-to-end latency at p50 and p99, plus output tokens per second. Then report goodput: requests per second that meet TTFT ≤ 1 s and TPOT ≤ 50 ms. Sweep the arrival rate to find capacity (40 req/s for continuous plus chunked in our simulator), and also track preemptions, recomputed tokens (E4) and CPU time per step (E9). Test on a seeded trace so every change can be diffed step by step, the way this card was.

What is deliberately missing from this solution?

  • Swap. Preemption here recomputes: free the blocks, set num_computed = 0, and go to the front of the queue. That's what vLLM V1 does. Swapping the KV to CPU memory saves the recompute but costs a transfer; FastServe swaps idle KV ahead of time. → Admission, preemption and thrashing
  • A real model, EOS and sampling. step_time is a roofline floor, and a request stops only at output_len. A real engine runs the forward pass and samples, and it stops early at an end-of-sequence token, which the scheduler can't predict. → Inside an inference engine: anatomy of vLLM and SGLang
  • CUDA graphs. Our "GPU" launches no kernels. Real engines commonly capture decode steps as CUDA graphs to cut kernel-launch overhead (general practice; our research notes don't cover it). → Writing fast GPU kernels: fusion, launch overhead and CUDA graphs
  • Async overlap. Here the GPU sits idle while step() runs. SGLang's overlap scheduler (on by default) and vLLM's async scheduling plan the next batch while the current one runs, at the cost of forming it before the last step's outputs are known. → Handling concurrent requests
  • Speculative decoding. A decode asks for exactly 1 token. With k draft tokens it asks for 1 + k, and the verify step may accept fewer. vLLM folds this into the same catch-up rule: each request is given tokens until num_computed_tokens reaches num_tokens_with_spec. → Inside an inference engine: speculative decoding in practice

Also left out: the watermark, pluggable policies and prefix caching. All three are in the fuller labs/scheduler.py. When this design is the wrong choice: if output lengths are known or short, or memory is plentiful, v2's reserve-to-completion is simpler and can never thrash (TGI and TensorRT-LLM's default work this way). On hardware that needs static shapes, the problem becomes packing requests into a few fixed batch shapes instead.
