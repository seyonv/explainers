Prefix caching: never prefill the same tokens twice

Also called automatic prefix caching (APC, vLLM's name), RadixAttention (SGLang's name), prompt caching, or KV reuse. This card sets vLLM's block hashing next to SGLang's radix tree, as both engines' source code describes them, and walks the prefix-caching code in the course's reference scheduler. Every time on the card is from our simulator (labs/scheduler.py, a 100%-of-peak cost model for Llama-3.1-8B on one H100 SXM), so treat it as a floor, not a measurement.

In one breath

If two requests start with the same tokens, the keys and values those tokens produce in every layer are identical too. So when a request finishes, keep its KV blocks. Index them by the exact token prefix they came from, and when a new request arrives, look up the longest prefix that is already cached. Only the tokens after that point need prefill. The scheduler's side of the job is to order requests and route them to replicas so that the prefix they need is still in memory.

So 91.6% is the ceiling for this workload: every shared prompt is prefilled exactly once and never evicted, because 30,469 blocks is plenty of room for 4 × 128 of them. Without the cache, prefill alone eats 72% of the GPU (by the 16.2 ms per 1,000 tokens floor), the queue builds, and the median wait for a first token is 3.3 s. With it, prefill drops to 6% of the GPU and the queue never builds. Output throughput rises only 1.29× because the run can't finish before the last request arrives (39.9 s): the no-cache run takes 58.1 s to drain its backlog, the cached run 44.9 s, and both emit the same output tokens.

Two ways to find the longest cached prefix

(a) Block hashing

vLLM (and our BlockManager)

  • Hash = H(parent hash, this block's tokens, extra keys). Only full blocks.
  • Lookup: walk the hashes until the first miss. O(L/B) dict lookups for L tokens and block size B; hashing reads each token once.
  • Eviction: freed hashed blocks go to the back of the free queue, which is the LRU; a request's blocks are freed tail first.

(b) Radix tree

SGLang (RadixAttention)

  • Keys are token sequences on compressed edges, at token or page granularity (page_size).
  • Lookup: walk from the root comparing tokens. O(prefix length); partial edge matches split the node.
  • Eviction: a heap of evictable leaves (LRU by default; LFU, FIFO, priority and others exist). O(E log E) per call. A prefix never goes before its extensions.

The code · labs/scheduler.py, methods of BlockManager

step() calls match_prefix on a waiting request before sizing its prefill, so req.remaining already excludes the cached tokens. finish_step() calls cache_full_blocks after every chunk, so a prompt becomes reusable as soon as its blocks fill, even mid-prefill.

def _chain_hashes(self, req: Request) -> list[str]:
    if req.block_hashes is not None:    # computed once per request
        return req.block_hashes
    hashes, parent = [], ""
    bs = self.block_size
    for i in range(req.prompt_len // bs):
        chunk = req.prompt_tokens[i * bs:(i + 1) * bs]
        parent = hashlib.sha1(
            (parent + ",".join(map(str, chunk))).encode()
        ).hexdigest()
        hashes.append(parent)
    req.block_hashes = hashes
    return hashes

def match_prefix(self, req: Request) -> None:
    """Reuse cached full blocks for the longest matching
    prompt prefix."""
    if not (self.prefix_caching and req.prompt_tokens) or req.blocks:
        return
    hits = []
    for h in self._chain_hashes(req):
        b = self.hash_to_block.get(h)
        if b is None:
            break
        hits.append(b)
    # never reuse the very last prompt token: we need a forward pass
    # to get logits
    while hits and len(hits) * self.block_size >= req.prompt_len:
        hits.pop()
    for b in hits:
        if self.ref[b] == 0:
            self.evictable.pop(b)
        self.ref[b] += 1
    req.blocks = hits
    req.num_computed = req.num_cached = len(hits) * self.block_size

def cache_full_blocks(self, req: Request) -> None:
    """After a prefill chunk, publish newly filled full prompt blocks."""
    if not (self.prefix_caching and req.prompt_tokens):
        return
    full = min(req.num_computed, req.prompt_len) // self.block_size
    for i, h in enumerate(self._chain_hashes(req)[:full]):
        b = req.blocks[i]
        if b not in self.block_hash and h not in self.hash_to_block:
            self.block_hash[b] = h
            self.hash_to_block[h] = b

The eviction half lives in _take() (use a never-used block first, else evictable.popitem(last=False), the least recently freed cached block, and delete its hash) and free_request() (walk reversed(req.blocks), so a shared head outlives its tail). Our evictable is an OrderedDict, so hit, free and evict are all O(1) per block; vLLM gets the same with a doubly linked free queue.

The scheduler's half: order and route for hits

Ordering on one replica. A cache only helps if the prefix is still there when the next request that needs it runs. SGLang's LPM policy sorts the waiting queue by longest cached prefix, and DFS-weight walks the tree so requests that share a prefix run next to each other. Both are opt-in (the default at the commit studied is fcfs), and SGLang drops back to FCFS when more than 128 requests wait, because re-sorting costs O(W log W) plus a match per request. In Attention and the KV cache, a 64-request batch over 8 templates with room for 3 reaches a 84.7% hit rate with longest-shared-prefix-first against 30.2% for FCFS on shuffled arrivals (that course's recomputation). The cost is fairness: a request whose prefix is cold can wait behind a stream of warm ones.

Routing across replicas. With N replicas and round robin, the next turn of a conversation lands on the replica holding its history only 1 time in N (simple arithmetic), and every replica ends up caching every prefix. Cache-aware routers fix that:

Pitfalls

  • A prefix only matches from token 0. One changed token invalidates every block after it. Put the stable parts first (system prompt, tools, documents) and the variable parts (date, user name, the question) last. Rerunning E7 with the unique suffix moved in front of the shared prompt gives a 0.0% hit rate and results identical to having no cache (3,344 ms TTFT p50) our simulation, computed for this card
  • Sharing across tenants. A shared cache means one tenant's request can hit on another tenant's prompt, and a hit is faster than a miss. Timing that difference could in principle reveal what another tenant sent. vLLM's hash accepts a cache salt among its extra keys, which can keep tenants' blocks apart at the price of their hit rate the timing risk is our inference; the kit has no source for it
  • Eviction competes with running requests. Cached blocks with ref 0 count as free memory, so under pressure new allocations evict them first and the hit rate falls exactly when load is highest. Blocks with ref > 0 (or lock_ref > 0) can't be evicted, so a big shared prefix held by running requests shrinks room for everything else. The upside: a preempted vLLM request frees its blocks with hashes intact, so its recompute often hits the cache.
  • Hit rate is not speedup. A 91.6% token hit rate here saved 91.6% of prefill compute, but TTFT fell 209× because the unloaded queue vanished. At low load the same hit rate saves only the prefill time itself, 2,048 × 16.2 µs ≈ 33 ms per request on this model.

Why it beats the alternatives

✗ No cache

Every request prefills its whole prompt: 1,779,902 tokens in E7, 72% of the GPU, 3.3 s median TTFT.

✗ Cache whole prompts by exact match

Only identical prompts hit. Any unique suffix, which is almost every real request, misses everything (our reasoning).

✗ Hash each block on its own

Two blocks with the same tokens after different prefixes would collide, yet their K and V differ, because every layer mixes in earlier tokens. Wrong KV means wrong output.

✓ Prefix-keyed cache (chain hash or tree)

Reuses the longest shared opening, whatever follows it: 91.6% hit, 11.9× fewer prefill tokens, TTFT 3,344 → 16.0 ms here.

Is this the same as the provider "prompt caching" discount?

Same mechanism, sold as a product. When an API provider bills cached input tokens at a lower price, it is reusing prefill KV for a prefix it has seen, as on this card. From the caller's side it adds rules this card doesn't cover: some APIs need an explicit cache marker, a minimum prefix length, or a time-to-live, and all of them depend on routing you to a replica that still holds the prefix. See prompt caching in the latency course.

When it doesn't help: one-off prompts with nothing shared, short prompts where prefill was already a few milliseconds, and memory-starved servers where cached blocks are evicted before reuse. It also does nothing for decode, so an output-heavy workload gains little throughput (1.29× here even with a 91.6% hit rate). The cost when it misses is small in vLLM (under 1% throughput), so engines leave it on anyway.
