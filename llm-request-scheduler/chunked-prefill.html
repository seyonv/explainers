Chunked prefill and the token budget

Also called stall-free batching (Sarathi-Serve), piggybacking (prompt work rides along with decodes), Dynamic SplitFuse (DeepSpeed-FastGen's name for a similar idea), and, as a setting, max_num_batched_tokens. This is the default loop in vLLM V1 and the one our Scheduler in labs/scheduler.py runs.

Prime · 2 minutes before you read

The problem: With continuous batching, a new request's whole prompt joins the running decodes in one step. A 4,096-token prompt turns a 9.9 ms step into 72.8 ms, and every one of 64 streaming users freezes for it. Without a cap on tokens per step, streams stutter whenever long prompts arrive.

Where it fits: Last card of group 2, fixing the first problem continuous batching created. It adds one number, the token budget, to the continuous loop, and it is the default loop the scheduler cards build in group 3.

In one breath

Put a cap on how many tokens one forward step may process: the token budget. Every running decode goes in first at one token each. Whatever budget is left goes to a slice of a waiting prompt, and the rest of that prompt comes back next step. No step can grow much past the budget, so a long prompt can't freeze everyone else's stream. The price is that the long prompt reaches its first token a little later.

The problem: one long prompt stalls every stream

With continuous batching, a new request's prompt joins the running decodes in the same step. A decode step is cheap because it is waiting on the weight read, and the math units sit mostly idle. A 4,096-token prompt needs 16.2 ms of math per 1,000 tokens, so that one step becomes long. Every one of the 64 users who are mid-answer waits for it. This is a generation stall:

64 decodes at 2k context 9.9 ms # E1, our model 64 decodes + one 4,096-token prompt 72.8 ms # 7.4x: every stream freezes the 4,096-token prompt on its own 66.7 ms # 4.1 x 16.2 ms, plus KV

Picking the budget from a TPOT SLO

Every running stream waits one full step between tokens, so the step time at your budget has to stay under the per-token target. Past about 295 tokens the step is limited by math (the H100's ops:byte), so the step time grows linearly with the budget and you can solve for it:

Our model, one moment. That is a starting point, not the answer. A busier step (more decodes, longer contexts) is slower at the same budget, and real kernels run below peak. In E3, budget 1,024 held ITL p99 at 19.7 ms and 2,048 at 36.2 ms. Sarathi-Serve's rule is the same idea: profile, then take "the maximum number of tokens that can be packed in a batch without violating TBT SLO". Course 5 does that profiling in full.

Our CostModel has no per-chunk overhead (no kernel launches, no CPU cost), so real small budgets cost more than the E3 table shows.

Why it's simple in code: no prefill/decode flag

A request doesn't need a phase. It needs two counters: how many tokens it has (num_tokens) and how many already have KV in the cache (num_computed). A fresh prompt is far behind, and a decoding request is exactly one token behind. Each step, the scheduler hands out budget so that the counters can catch up. Chunking is just min(). From labs/scheduler.py:

@property
def remaining(self) -> int:   # tokens that still need a forward pass
    return self.num_tokens - self.num_computed

# step(), 1. running requests: a decode has remaining == 1,
#          a half-done prompt has the rest of its prompt left
n = min(req.remaining, budget)

# step(), 2. waiting requests
n = req.remaining
if n > budget:
    if not self.chunked_prefill:
        break                            # whole prompt must fit this step
    n = budget

# finish_step()
if req.num_computed == req.num_tokens:   # caught up: a new token comes out

The 4,096-token prompt at budget 1,024: num_computed goes 0 → 960 → 1,920 → 2,880 → 3,840 → 4,096 = num_tokens, and the first token comes out. After that, remaining is 1 every step. vLLM V1 works the same way. Its scheduler comment reads: "There's no 'decoding phase' nor 'prefill phase' in the scheduler", and one rule covers "chunked prefills, prefix caching, speculative decoding". Prefix caching just starts num_computed above zero.

Why it beats the alternatives

✗ Whole prompts in the step

Good TTFT, but one 4,096-token prompt makes a 72.8 ms step for all 64 streams. In E3, ITL p99 is 68.7 ms, above a 50 ms target.

✗ Prefill-only steps

Prompts go first, and every stream simply pauses while they run. It's fine offline, but streams stutter under any load.

✗ A budget far below what the SLO needs

At 256, ITL p99 is 7.2 ms, far under the SLO, but TTFT p99 nearly doubles (375.5 vs 179.4 ms at 2,048), and real per-chunk overhead grows.

✓ Decodes first, budget sized to the SLO

Streams can never stall for longer than one budget-sized step, and prompts use the leftover compute. Throughput stays the same (2,009–2,033 tok/s), and the budget is one number to tune.

Doesn't chunking redo attention work?

No. Chunk 2 doesn't recompute chunk 1. Chunk 1's keys and values are already in the KV cache, and chunk 2's tokens attend to them there. What chunking adds is extra KV reads: every chunk reads the KV of all the chunks before it. For the 4,096-token prompt at budget 512, that's 20,160 tokens re-read, 2.64 GB, about 0.79 ms in total in our model, against 66.7 ms of prefill. The attention math per token is the same as unchunked. Real costs we don't model: each small step pays kernel-launch and scheduling overhead, and matmuls tile less efficiently. Sarathi-Serve measured up to ~25% at 512 and almost nothing at 2,048.

When it's not the right choice: with offline batch jobs and nobody watching a stream, use a big budget or turn chunking off, since throughput is the same and TTFT is better. With one user at a time there is nothing to stall. And if you need both a tight TTFT and a tight TPOT at scale, disaggregation removes the interference entirely, at the cost of moving KV between machines.

Understand and remember

  • Cap the tokens per step → decodes go in first at 1 token each → the leftover budget gets a slice of a waiting prompt → no step grows much past the budget → the worst gap for streams is bounded (72.8 → 21.9 ms at budget 1,024)
  • The same work gets done either way → throughput stays flat (2,009–2,033 tok/s) → the budget only changes who waits: smaller budget → smoother ITL, slower first token for long prompts
  • Past ≈ 295 tokens a step is compute-bound → step time grows linearly with the budget → solve max(math, weights) + KV read ≤ SLO for T → ≈ 2,756 tokens for 50 ms with 64 decodes at 2k
  • A request tracks num_computed vs num_tokens, not a phase → chunking is just n = min(remaining, budget) → prefix caching (start above 0) and preemption (reset to 0) fit the same rule
  • detail that matters Each chunk reads the KV of earlier chunks instead of recomputing → 20,160 tokens re-read at budget 512 (0.79 ms of a 66.7 ms prefill) → chunking's cost is extra reads and per-step overhead, not repeated math

5 · Predict commit to an answer before revealing

Your budget is sized for 64 decodes at 2k context. Traffic grows to 150 running decodes at the same budget. Before computing: does the worst stream gap go up, down or stay the same, and why?

Reveal

Up. The KV read of the running decodes grows with their number (150 × 2,048 × 128 KiB is about 12 ms, versus 5.13 ms for 64), and decodes also eat more of the budget, so each step is longer even though the token count is capped. The budget bounds tokens, not time: a busier step needs a smaller budget to hold the same SLO.
