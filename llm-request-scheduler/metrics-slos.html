Measuring a server: TTFT, TPOT, throughput, goodput

Also called TBT or ITL (the gap between two tokens), E2E latency, P50/P99, SLO, capacity. Before you build a scheduler you need its scoreboard. This card defines each number on one request's timeline, shows where averages hide stalls, and settles what the scheduler should maximise. The numbers come from our simulator (Llama-3.1-8B on one H100 at 100% of peak, so they are floors) and one real sweep on an M3 Mac.

In one breath

A user feels two things: how long until the first word appears (TTFT) and how smoothly the rest streams (the gap between tokens, ITL, whose per-request average is TPOT). The operator cares about throughput, the tokens per second across everyone. Goodput joins the two views: it counts only the requests that met a latency target (an SLO). A scheduler should be judged on goodput, because raw throughput goes up when you let the queue grow.

Why averages lie

TPOT is an average, so one long stall disappears into hundreds of short gaps. In E3 (long prompts, median 2,048, 8 req/s, whole-prompt prefill), a new prompt joins the running batch as one big step and every decoding user waits for it. Here is one real request from that run, request 442: 1,834-token prompt, 521 output tokens.

Our simulation. Median gap 6.5 ms. Six gaps pass 50 ms and the worst is 185.1 ms, the run's ITL max, yet the request's TPOT is 7.9 ms and it counts as "in SLO".

request 442: TPOT = (4,164.1 − 32.2) ms ÷ 520 gaps = 7.9 ms passes 50 ms worst single gap = 185.1 ms whole run: TPOT P99 = 15.5 ms, ITL P99 = 68.7 ms, ITL max = 185.1 ms 540 of 600 requests had a gap > 50 ms; all 600 passed TPOT ≤ 50 ms

Two lessons. Report percentiles, not means (P50 and P99 at least), and if smooth streaming matters, put the SLO on ITL percentiles, not on TPOT. The fix for this stall is a scheduler change: with chunked prefill at a 512-token budget, the same run's ITL max drops to 11.7 ms (see chunked prefill).

The throughput–latency trade-off

Where does that curve come from? One decode step reads the weights once however many requests ride along, so adding requests raises total throughput almost for free, until the step gets longer and each user slows down. Per user = 1 ÷ step time; total = B ÷ step time.

Left: our simulation, decode at 2k context (E1): B = 64 gives 64 ÷ 9.9 ms ≈ 6,450 tok/s total and 101 per user. From B = 1 to 238 (the memory limit at 2k), total rises 49× while each user drops from 205 to 42 tok/s; all of these points still pass a 50 ms TPOT. Right: measured on the M3 Mac, Llama-3.2-3B Q4_K_M under llama-server, closed loop, busy machine (from Course 5's benchmarking card). C = 1 → 16: total 28.9 → 100.2 tok/s, per user 31.7 → 8.5 (TPOT 31.5 → 118.2 ms), so C = 16 misses the 50 ms target. That card also shows a dip at C = 4–8 not drawn here.

A real-world SLO

Why goodput beats the alternatives as the scheduler's score

✗ Raw throughput

Rewards letting the queue grow. 60 req/s gives the most tokens (9,102 tok/s) while 59% of users wait past 1 s for a first token, and goodput falls from 17.6 to 13.8 req/s.

✗ Mean latency or TPOT alone

Averages hide stalls: request 442's TPOT is 7.9 ms with a 185.1 ms freeze inside it, and 540 of 600 requests had a gap over 50 ms while all passed.

✗ Single-request latency

Timing one request on an idle server (28.9 tok/s on the Mac) says nothing about batching or queueing: the same server does 100.2 tok/s at C = 16, with users 3.7× slower.

✓ Goodput under an SLO

Counts only requests that met both targets, and the highest rate where 99% still do (capacity, 40 req/s here) is the number you size a fleet by.

Which metric does the scheduler optimise?

Goodput under an SLO, not raw throughput. Every knob the scheduler has trades one metric for another. A bigger batch (max_num_seqs) raises throughput and TPOT. A smaller token budget lowers ITL and raises TTFT: in E3, a 256-token budget gives ITL max 7.4 ms but TTFT P99 375.5 ms, against 37.1 and 179.4 ms at 2,048. Admission control can refuse work to keep the admitted requests inside their targets. The scheduler's job is to serve as many requests per second as possible while P99 TTFT and P99 ITL/TPOT stay inside the SLO. DistServe's paper frames serving the same way, as goodput with TTFT and TPOT met together.

When it's not the right score: offline batch jobs with no user watching (evaluations, bulk summarisation) have no latency target, so maximise raw throughput, meaning tokens per GPU-hour. When users stream text, per-token gaps matter more than the TPOT average, so put the SLO on ITL percentiles. With many tenants, a high overall goodput can still hide one tenant starving, so add a fairness goal (see policies).
