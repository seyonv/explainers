Checkpoint 2: inside step(): memory, order and one owner

Ties together the request lifecycle and data structures, step(), line by line, the paged KV block manager, admission, preemption and thrashing, scheduling policies and handling concurrent requests: what the scheduler keeps, in which containers, what it does when memory runs out, whom it lets in next, and who is allowed to touch it.

How to use this page. Close the six cards. Answer each question in writing, in full sentences, before opening its Check. A wrong or shaky answer isn't a failure; it tells you exactly which section to reopen. The questions are mixed on purpose, so you have to work out which idea applies before you can answer.

1 · Mixed retrieval

  1. which concept?A server has free seats and 20 requests waiting, yet many steps carry only two decode tokens, and the logs show the same large request admitted, evicted and admitted again. Which concept is this, what causes it, and what is the cheapest fix?
    Check
    • thrashing: the request is admitted when only its first prompt chunk fits, the running requests keep growing, and as the newest it is the victim when blocks run out
    • step()'s "no admission in a step that preempted" guard doesn't stop it, because readmission happens a step later (toy request 4: 36 tokens thrown away for a 30-token prompt)
    • fix: admit only if the whole remaining prompt fits, plus a small watermark (E4 at 2.1 GB: 469 → 11 preemptions)

    Missed it? Reopen admission, preemption and thrashing, "Thrashing, in the toy trace" and "Four fixes".

  2. At 2k context, how many sequences fit in 487,504 tokens of KV with a contiguous slot of 4,096 + 1,024 tokens per request, and with 16-token blocks? Where does paging's leftover waste come from?
    Check
    • contiguous: 487,504 ÷ (2,048 + 3,072) = 95 sequences, 60% of the pool held but empty
    • paged: 487,504 ÷ (2,048 + 8) = 237 sequences, 2.5× as many
    • a request takes a new block only when its last one fills, so on average half a block (8 tokens) per request is empty

    Missed it? Reopen the block manager, "Why page at all".

  3. which concept?At 55 req/s, interactive users see a 7.4 s median wait for the first token while batch jobs share the same GPUs. Throughput looks fine. Which idea helps, what does it cost, and what must you add so it doesn't backfire?
    Check
    • priority classes: a heap keyed (priority, arrival), interactive first: TTFT p50 7,395 → 36.1 ms in E5
    • cost: batch's median goes 7,500 → 9,760 ms; throughput doesn't change, because policy only reorders who waits
    • add aging or a reserved share, or the batch class starves whenever interactive alone fills the GPU

    Missed it? Reopen policies, "Priority classes".

  4. State the cost of each: admitting from an FCFS queue, from an SJF queue, and from the fair queue with T tenants; removing a finished request from the running list; and pulling a cached block out of the middle of the free list with a deque vs vLLM's structure.
    Check
    • FCFS deque O(1); SJF heap O(log W); fair O(T) (a min over tenants' counters)
    • running list removal O(R), acceptable because step() walks R anyway
    • deque.remove O(N): 1.4–1.8 ms at 30,469 blocks; vLLM's intrusive doubly linked list unlinks in O(1) and doubles as the LRU

    Missed it? Reopen the data structures, "The core table".

  5. which concept?After a team turns on overlap scheduling, cancelled requests now and then corrupt another user's output. Which idea from this part explains it, and what rule fixes it?
    Check
    • blocks are being freed while a step that still references them is in flight, so a new request reuses the block IDs while the old writes land (the ABA bug)
    • cancellation should be a message to the single engine loop, applied between steps
    • with overlap, two steps are in flight: free only after every step that includes the request has finished

    Missed it? Reopen handling concurrent requests, the cancellation paragraph and "When one loop is not enough", and the data structures, "Adding cancel(id)".

  6. Recompute or swap: derive the link speed above which swapping a preempted request's KV to host memory beats recomputing it on the running example, and say why vLLM V1 still recomputes by default.
    Check
    • recompute n·2P ÷ C vs swap 2·n·b_kv ÷ B_link: n cancels, so swap wins when B_link > b_kv·C ÷ P ≈ 16.1 GB/s
    • on paper swap wins over a 25 GB/s link (10.7 vs 16.6 ms for 1,024 tokens)
    • recompute rides in normal steps' token budget, needs no pinned host memory or copy bookkeeping, and freed prompt blocks may still hit the prefix cache

    Missed it? Reopen admission and preemption, "Preemption, part 2".

  7. Walk through the four rules of step() in order and give the reason for each.
    Check
    • running requests first, n = min(remaining, budget): they hold KV already, and finishing them protects TPOT and frees memory
    • out of blocks → preempt running.pop(), the newest: least work lost, O(1), and never a request already scheduled this step
    • no admission in a step that preempted: otherwise the victim is readmitted into the memory it just freed
    • admit in policy order and break at a head that doesn't fit: no big request starves behind small ones

    Missed it? Reopen step(), line by line, the four numbered blocks.

3 · Project: grow the mini scheduler, one guarded change at a time

What it reinforces: the two counters and the containers (data structures), the four rules of step() (step()), lazy block allocation (block manager), the admission guard (admission and preemption), a heap-keyed policy (policies) and freeing blocks only between steps (concurrency).

Start from labs/mini_scheduler.py (stdlib only). Keep its check() running after every step throughout.

  1. Baseline. Run the toy trace (budget 16, 4 seats, 12 blocks of 4) and record steps, preemptions and the last finish time.
  2. Predict, then trace. On paper, trace a small config: budget 8, 3 seats, 6 blocks of 4, all arriving at t = 0: request 0 (prompt 6, output 4), request 1 (prompt 5, output 3), request 2 (prompt 9, output 2). Write each step's plan and any preemption. Then run it and compare.
  3. Guarded admission. Change the admission check to can_fit(r, r.remaining) (the whole remaining prompt) while still computing only min(remaining, budget) this step. Rerun the toy trace.
  4. A policy. Replace the waiting deque with a heap keyed on (prompt_len + output_len, arrival) (SJF with an oracle). A preempted request can't go "to the front" of a heap: push it back with its original key. Rerun the original (unguarded) toy trace and record steps, preemptions, request 4's finish and request 2's time to first token.
  5. Safe cancel. Cancel a running request between step() and on_step_done(). Assert that its blocks are still held until on_step_done() runs, that the step's tokens for it are dropped, and that cancelling it twice changes nothing.
Done when: check() never fires, every run matches the check below, and you can say in one sentence each why guarded admission and SJF both cut preemptions on this trace, and what each costs.
Check: the numbers (from runs of mini_scheduler.py and labs/scheduler.py)
  • Baseline: 21 steps, 3 preemptions (request 4 at steps 6 and 8, request 6 at step 12), last finish 100.7 ms.
  • Small trace: step 0 0:6P 1:2P (3 blocks free); step 1 0:1D 1:3P 2:4P (1 free); step 2 0:1D 1:1D and request 2 preempts itself (it needs 2 more blocks, 1 is free); step 3 0:1D 1:1D, request 2 still can't fit; step 4 2:8P; step 5 2:1P; step 6 2:1D. 7 steps; request 2's first token at 28.77 ms, finish at 33.56 ms.
  • Guarded admission: 22 steps, 1 preemption, last finish 105.5 ms, mean E2E 59.5 ms (the admission card's "+ whole prompt must fit" row).
  • SJF heap: 19 steps, 1 preemption; request 4 finishes at 91.1 ms instead of 62.3 ms, and request 2 (prompt 20) waits 67.1 ms for its first token instead of 14.4 ms. The same numbers come out of labs/scheduler.py with policy="sjf". Fewer preemptions because the big request is admitted only once memory has cleared; the cost lands on the largest requests.
  • Cancel: the blocks stay allocated until on_step_done() calls _reap(), and only then return to the free list (the reference solution's test: a 40-token prompt still holds 8 blocks after cancel(), and all 12 are free after on_step_done()). A second cancel finds nothing in live and does nothing.
