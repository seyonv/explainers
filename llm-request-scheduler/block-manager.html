A paged KV block manager

Also called PagedAttention's memory manager, the KV cache manager, the block pool or the block table. This is the BlockManager class in the course's reference scheduler (labs/scheduler.py). Sizes are for the running example (Llama-3.1-8B in BF16 on one H100 SXM); timings come from our simulator, which runs at 100% of peak, so treat them as floors.

Prime · 2 minutes before you read

The problem: If each request gets one contiguous KV slot sized for the longest it could become, 60% of the pool is held but empty and only 95 requests fit at 2k. Nobody knows a request's final length, so the memory has to be handed out a little at a time, without scanning the pool and without ever freeing a block twice.

Where it fits: Fourth card of group 3. step() called can_allocate and allocate as black boxes; this card opens them. It builds on the KV cache's 128 KiB per token and sets up the next card's question: what to do when can_allocate says no.

In one breath

Cut the KV memory into fixed-size blocks of 16 tokens, keep the unused ones on a free list, and give each request a block table: a short list that maps its logical block 0, 1, 2… to whichever physical blocks it was handed. A request takes a new block only when its last one fills, so no request holds more than one partly empty block. Blocks can also be shared: a reference count on each block lets two requests point at the same prefix.

Why page at all

The alternative is to reserve a contiguous slot per request, sized for the longest request it could become. vLLM measured that existing systems "waste 60% – 80% of memory due to fragmentation", against "under 4%" with PagedAttention. Here is the same effect on our example: 63.9 GB of free HBM holds 487,504 tokens, and every request is at 2k context. The contiguous design must reserve the maximum length, a 4,096-token prompt plus 1,024 output tokens. The paged design holds each request's real length plus an average of half a block.

The picture: pool, block tables, one shared block

This is the toy config (12 blocks of 4 tokens) after three illustrative requests arrive. The block ids are the real output of BlockManager(12, 4, prefix_caching=True) in the lab: a fresh pool hands out blocks in order, so these happen to be neighbours. After a few frees they would be scattered, and the tables would work the same way.

Request B's prompt starts with the same 4 tokens as A's, so its logical block 0 points at A's physical block 0 (ref count 2) and only its last 3 tokens needed a new block. Six blocks hold 18 distinct tokens in 24 slots. The 6 empty slots are exactly the expected half a block per request (3 × 4 / 2). Without sharing it would take 7 blocks.

If request A now finishes, free_request walks its table backwards. Block 2 has no hash and goes straight onto the free list. Block 1 holds a full, hashed prompt block, so it becomes evictable but stays cached. Block 0 only drops to ref 1, because B still reads it. The pool then has 8 free blocks: 6 → 11 and 2 on the free list, and 1 as evictable (the lab's output).

The code, and what each call costs

From labs/scheduler.py, with type hints dropped and long lines wrapped. The prefix-cache parts (hash_to_block, block_hash) are explained on prefix caching.

class BlockManager:
    def __init__(self, num_blocks, block_size=16, prefix_caching=False):
        self.block_size = block_size
        self.free = deque(range(num_blocks))  # never-used or evicted
        self.ref = [0] * num_blocks
        self.evictable = OrderedDict()  # cached, ref 0, LRU order

    def num_free(self):
        return len(self.free) + len(self.evictable)

    def blocks_needed(self, req, new_tokens):
        total = req.num_computed + new_tokens
        return max(0, math.ceil(total / self.block_size)
                      - len(req.blocks))

    def can_allocate(self, req, new_tokens, reserve=0):
        return (self.blocks_needed(req, new_tokens)
                <= self.num_free() - reserve)

    def _take(self):
        if self.free:
            return self.free.popleft()
        b, _ = self.evictable.popitem(last=False)  # evict LRU
        del self.hash_to_block[self.block_hash.pop(b)]
        return b

    def allocate(self, req, new_tokens):
        for _ in range(self.blocks_needed(req, new_tokens)):
            b = self._take()
            self.ref[b] = 1
            req.blocks.append(b)

    def free_request(self, req):
        for b in reversed(req.blocks):  # tail first
            self.ref[b] -= 1
            if self.ref[b] == 0:
                if b in self.block_hash:
                    self.evictable[b] = None  # stays cached
                else:
                    self.free.append(b)
        req.blocks = []
CallCostWhy
blocks_neededO(1)One ceiling division minus the table length. It depends only on counts, not on which blocks.
can_allocateO(1)blocks_needed plus two len() calls. The scheduler calls it for every running and waiting request each step, so it must be cheap.
_takeO(1)deque.popleft; or OrderedDict.popitem plus two dict deletes to evict a cached block.
allocateO(new blocks)One _take per new block. A decode step needs a new block once every 16 tokens, so usually zero.
free_requestO(blocks held)Touches every entry of the table once: 128 for a 2k request.

Every per-block operation is O(1), which is also vLLM V1's design goal (see the free-list comparison below). Nothing scans the pool.

Our arithmetic at 63.9 GB free, with half a block empty per sequence on average. The PagedAttention paper's ablation (§7.2, OPT on A100) found that blocks that are too small can't use the GPU's parallelism when reading KV, while blocks that are too large waste more and share less; 16–128 was best on ShareGPT and 16–32 on Alpaca. One more cost of big blocks, by our inference: only full blocks are cached and shared, so up to block_size − 1 tokens of a shared prefix can't be reused.

The free list · what happens on a prefix-cache hit

A freed block that holds a cached prefix stays on the free list, still findable by its hash. If a new request hits it, the block has to come off the list from the middle. That operation decides the data structure.

"Out of blocks"

On-demand allocation means can_allocate can say no, in two places. At admission, the head of the waiting queue just waits (our step() breaks out of its admission loop). For a running request that needs its next block, the scheduler must free someone else's blocks: it preempts the newest running request, frees its blocks and recomputes it later. The toy trace shows both. At step 3 there are 0 free blocks, so request 3 waits even though a seat is free. Request 4 (a 30-token prompt, 8 of the 12 blocks) is admitted, then preempted at steps 6 and 8, then readmitted: thrashing. How to choose victims and avoid thrashing is the next card, admission, preemption and thrashing.

Why it beats the alternatives

✗ Contiguous max-length slot

One slot of 5,120 tokens per request. Only 95 requests fit at 2k, and 60% of the pool is held but empty. vLLM measured 60–80% waste in such systems.

✗ Paged, but reserved to completion

No waste from fragmentation and never a preemption, but blocks for max_new_tokens sit idle until the output grows into them. With our outputs (median 200, cap 1,024), most of that reserve would stay unused.

✗ One-token blocks

Almost no waste (238 at 2k), but 2,048 table entries per request and 487,504 blocks to track, and the paper found the kernel reads too-small blocks inefficiently.

✓ On-demand 16-token blocks with ref counts

237 requests at 2k, 0.4% empty, O(1) per block, and shared prefixes are stored once. The price is handling "out of blocks" with preemption.

Does paging make attention slower?

A little, per kernel. The attention kernel no longer reads one contiguous array. It looks up each block's address in the block table and gathers from scattered blocks. The PagedAttention paper measured 20–26% higher attention-kernel latency than FasterTransformer's kernel (Fig 18a, OPT on A100). Only attention pays; the linear layers don't change. End to end, vLLM still sustained up to 22× FasterTransformer's request rate, because far more sequences fit in a batch and batch size is what buys throughput (see PagedAttention results in Attention and the KV cache).

When it isn't worth it: when memory isn't the limit, such as short contexts, a small fixed batch, or a single-user local server, paging's gain disappears and only the indirection is left. That is the paper's own caveat. The 20–26% is a 2023 measurement against 2023 kernels. Paged-KV kernels such as FlashInfer's are now used by the major engines, and we haven't measured today's gap.

Reveal

It shrinks. Contiguous reservation still holds 5,120 slots per request but now 4,096 are used, so waste falls to 20%: ⌊487,504 ÷ 5,120⌋ = 95. Paging fits ⌊487,504 ÷ (4,096 + 8)⌋ = 118. The gain drops from 2.5× to about 1.24×: paging helps most when real lengths are far below the reserved maximum.
