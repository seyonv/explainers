Checkpoint 1: filling the batch without stalling it

Ties together why batching works, static batching, dynamic batching, continuous batching, chunked prefill and measuring a server: how a server gets many requests' tokens into each weight read, what each strategy makes users wait for, and how you would see the difference in the numbers.

How to use this page. Close the six cards. Answer each question in writing, in full sentences, before opening its Check. A wrong or shaky answer isn't a failure; it tells you exactly which section to reopen. The questions are mixed on purpose, so you have to work out which idea applies before you can answer.

1 · Mixed retrieval

  1. which concept?A team serves an embedding model (one forward pass per request, 32-token inputs) behind Triton at about 200 req/s. After moving their chat model to continuous batching, they want to do the same for the embedding model. Which idea from this part says they shouldn't, and what should they set instead?
    Check
    • dynamic (time-window) batching is the right tool for one-pass models: every row finishes in the same pass, so there is no decode loop to join mid-flight
    • up to about 295 tokens per pass the step waits on the weight read, so about 9 of these requests ride along for the price of one (209 → 1,873 req/s in our model)
    • a 50 ms window at 200 req/s gives E[b] ≈ 1 + 200 × 0.05 = 11, past that knee, for at most 50 ms of extra wait

    Missed it? Reopen dynamic batching, "Why it is great for one-pass models".

  2. Static batching of 32 at only 2 req/s gave a median time to first token of 8.7 s while the GPU sat mostly idle. Explain where that time goes, and what the 71% "padding waste" in the same run measures.
    Check
    • a request waits for 31 more arrivals (about 15.5 s at 2 req/s, so about half of that on average), then for any running batch to finish
    • a static batch is fixed from first step to last and runs until its longest output is done
    • 71% is the share of decode slot-steps where a row had already finished but still held its seat; it depends only on the spread of output lengths, so it is the same at 2, 20 and 60 req/s

    Missed it? Reopen static batching, "The waste, as an equation" and "Where the numbers come from".

  3. which concept?Users complain that the answer freezes for a moment whenever someone else pastes a long document. The dashboard shows TPOT p99 of 15 ms, far under the 50 ms target. Which two ideas explain both the complaint and the calm dashboard, and what do you change?
    Check
    • a generation stall: with continuous batching, a new prompt's whole prefill joins the running decodes' step (9.9 → 72.8 ms for a 4,096-token prompt with 64 decodes)
    • TPOT is an average per request, so one long gap vanishes: in E3 the worst gap was 185.1 ms while TPOT p99 was 15.5 ms
    • fix: chunked prefill with a token budget sized to the target, and put the SLO on ITL p99 instead of TPOT

    Missed it? Reopen measuring a server, "Why averages lie", and chunked prefill, "The problem".

  4. Compute the step time, total throughput and per-user speed for 64 decodes at 2k context on the running example, and say which term of the step formula is largest.
    Check
    • math 2 × 8.03e9 × 64 ÷ 989e12 = 1.04 ms, under the 4.79 ms weight read, so the max is 4.79 ms
    • KV 64 × 2,048 × 131,072 B ÷ 3.35 TB/s = 5.13 ms, added on top: the largest single term
    • step ≈ 9.9 ms → 6,450 tok/s in total, 101 tok/s per user (205 alone)

    Missed it? Reopen why batching works, "The step-time formula".

  5. which concept?A dynamic batcher for a chat model is set to B = 32 and a 50 ms window. At 2 req/s you'd expect batches of about 1 + 2 × 0.05 = 1.1, but the logs show a mean of 5.92. Which idea explains the gap?
    Check
    • the idle-server formula assumes the model is free when the window closes; for generation it isn't
    • each batch is frozen until its longest output finishes (3.06 s on average here), and requests pile up behind it
    • so the batch is about λ × busy time = 2 × 3.06 ≈ 6.1: the output length sets the batch, not the window

    Missed it? Reopen dynamic batching, "Why it is still wrong for generation".

  6. Your TPOT target is 20 ms and 64 decodes at 2k context are running. Estimate the token budget, and say what a smaller budget costs and why the budget alone can't guarantee the target when traffic grows.
    Check
    • T* ≈ (SLO − KV read) × C ÷ 2P = (20 − 5.13) ms × 61,582 tok/s ≈ 916 (exact search 913)
    • cost: a long prompt needs more steps, so its first token comes later (TTFT p99 375.5 ms at 256 vs 179.4 at 2,048 in E3), plus real per-chunk overhead
    • the budget caps tokens, not time: more running decodes means a longer KV read at the same budget

    Missed it? Reopen chunked prefill, "Picking the budget from a TPOT SLO".

  7. Walk through what continuous batching does between two steps when one request emits its last token and another is waiting. Then explain why it gives about 10× static's saturated throughput but the same tok/s at 2 req/s.
    Check
    • the finished request leaves at once and frees its blocks; next step the running requests go first and the waiting one is admitted if budget, seats and blocks allow
    • under load, freed seats are refilled every step, so no seat idles while work is queued (916 → 9,102 tok/s)
    • at 2 req/s there isn't enough work to fill seats either way (≈ 520 tok/s); what changes is TTFT, 8,698 → 11.1 ms

    Missed it? Reopen continuous batching, "The code" and "What it buys".

3 · Project: a 60-line batching simulator, and a budget that fits the target

What it reinforces: the step-time formula (why batching works), frozen vs re-formed batches (static and continuous batching), the stall and the token budget (chunked prefill) and reading gaps as ITL rather than TPOT (measuring a server).

step(T, ctx) = max(2·P·T / C, W / BW) + ctx · 131,072 B / BW P = 8.03e9 W = 16.06e9 B C = 989e12 BW = 3.35e12
  1. Cost model. Write step(T, ctx) in Python and reproduce three E1 rows: B = 1, 64 and 238 decodes at 2k context (T = B, ctx = B × 2,048).
  2. Slot grids. Six requests are queued with output lengths 5, 2, 7, 3, 4, 6 and there are 4 slots (one token per slot per step, prefill left out). Simulate static batching (batches of 4, in order) and continuous batching (refill a freed slot next step). Count the steps, the idle slot-steps, and the step at which requests 4 and 5 get their first token.
  3. The stall. Price one step with 64 decodes at 2k context alone, and with a 4,096-token prompt joined to it.
  4. The budget. Find the largest token budget whose first step (64 decodes + a slice) stays under 30 ms. Then push the 4,096-token prompt through at that budget, one slice per step, with the decodes' context growing by one token per step and each slice re-reading the prompt's earlier chunks. Record every step time, the worst one and when the prompt's first token comes out. Repeat for budget 1,024 and for no chunking.
  5. Read it as a server. Your targets are ITL ≤ 30 ms for the 64 streams and TTFT ≤ 80 ms for the new prompt (ignore queueing). Which of your three configurations meets each target? Is there a budget that meets both?
Done when: your cost model hits the three E1 step times within 0.1 ms, both slot grids are counted, and you can say in one sentence why no budget meets both targets and what would. Then compare with the check.
Check: the numbers (computed with labs/scheduler.py's CostModel)
  • E1: 4.87 ms (B = 1), 9.92 ms (B = 64), 23.86 ms (B = 238).
  • Static: 13 steps (7 + 6), 52 slot-steps, 25 idle; requests 4 and 5 start at step 8. Continuous: 9 steps, 9 idle (all in the drain); requests 4 and 5 start at steps 3 and 4. Useful work is 27 slot-steps either way.
  • Stall: 9.9 ms alone, 72.8 ms with the prompt: 7.4×.
  • Budget: the formula gives ≈ 1,531, exact search 1,528. The prompt then takes 3 steps (30.0, 30.1, 25.3 ms) and its first token comes out at 85.4 ms. The 30.1 ms step is just over, because later slices re-read the earlier chunks' KV; a budget of 1,500 keeps every step at or under 29.6 ms with the same 85.4 ms first token. Budget 1,024: 5 steps (21.8, 21.8, 21.9, 21.9, 10.5 ms), first token at 97.9 ms. No chunking: one 72.8 ms step, first token at 72.8 ms.
  • ITL ≤ 30 ms: budgets 1,024 and 1,500 pass; no chunking fails. TTFT ≤ 80 ms: only no chunking passes. No budget meets both: a smaller budget smooths the streams by delaying the prompt. Meeting both needs the prefill off the decode GPUs (splitting prefill and decode) or looser targets.
