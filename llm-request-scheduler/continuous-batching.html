Continuous batching: join and leave every step

Also called iteration-level scheduling (the Orca paper, OSDI '22), in-flight batching (NVIDIA TensorRT-LLM), and dynamic or rolling batching (llama.cpp's help text even says "continuous batching (a.k.a dynamic batching)", which is not the time-window dynamic batching of the previous card). Every serious LLM engine does it today. This card uses the same four toy requests as the static card, then the course's simulator: Llama-3.1-8B, BF16, one H100, at 100% of peak.

In one breath

Instead of choosing a batch once and running it until its longest request is done, the scheduler chooses the batch again before every forward step. A request that has just produced its last token leaves right away, and a waiting request takes its seat on the very next step, so the GPU never decodes padding while there is work in the queue.

Static cost depends on the worst row in each batch; continuous cost depends on the average, because a short request hands its seat on instead of holding it. The longer the spread of output lengths, the bigger the gap (the course workload's lognormal outputs with σ 0.8 give the simulator's 71% padding waste below).

The code: two places in labs/scheduler.py

# Scheduler.finish_step(): leave the moment the last token is out if req.num_generated >= req.output_len: req.state = FINISHED req.finish_time = now done.append(req) ... for req in done: self.running.remove(req) # O(R); a linked list would make it O(1) self.bm.free_request(req) # its KV blocks go back to the free list # Scheduler.step(): join while budget, seats and blocks allow while (not preempted and len(self.waiting) and budget > 0 and len(self.running) < self.max_num_seqs): req = self.waiting.peek() ... self.running.append(req)

Nothing else is special: step() runs every iteration, so "leave" and "join" are just a list removal and a list append between two forward passes. The full loop is on step(), line by line.

Why a ragged batch works: selective batching

Orca's second idea makes the mixed batch possible: every operation except attention treats the step's tokens as one flat [total_tokens × D] matrix (for Llama-3.1-8B, D = 4,096), and only attention is run per sequence, each against its own KV cache, so no row needs padding to a common length.

Row counts use the toy trace's prompt lengths (request 4: 30 tokens); D is Llama-3.1-8B's hidden size. Course 5's Orca I draws the split and merge from the paper's figure. Modern engines do the per-sequence part with varlen/paged attention kernels rather than a Python loop, but the shape of the idea is the same.

Why it beats the alternatives

✗ One request at a time

The best per-user speed (205 tok/s at batch 1) and no scheduling at all, but it reads all 16 GB of weights for one token: 49× less throughput than a full 238-sequence batch (E1).

✗ Static batching

Batches of 32 share each weight read, but every batch runs to its longest output: 71% of decode slot-steps are padding, and a new request waits for the whole batch. 916 tok/s at most, TTFT p50 8.7 s even at 2 req/s.

✗ Dynamic (time-window) batching

A 50 ms window stops the wait for a full batch (TTFT p50 1.96 s at 2 req/s), but once running the batch is still frozen: 58–71% padding, same saturated ceiling as static.

✓ Continuous batching

The batch is re-formed every step, so finished rows leave and queued ones join: 0% padding, TTFT p50 11 ms at 2 req/s, ≈ 10× the saturated throughput, and 40 req/s inside the SLO where the others manage none.

The new problems it creates

Re-deciding every step means the scheduler now owns three questions that static batching never had to ask.

  1. A joiner's prefill stalls everyone's decode. The step that admits a new request also runs its whole prompt. In our model, a 4,096-token prefill joined to 64 decodes at 2k makes that step 72.8 ms instead of 9.9 ms (a 7.4× stall), and with long prompts the worst gap between tokens reaches 185.1 ms (E3). The fix is to cap the tokens per step and split long prompts: Chunked prefill and the token budget.
  2. Memory must be checked every step. A request that joins with a short context grows by one token of KV per step (128 KiB for Llama-3.1-8B), and nobody knows its final length. Either reserve for the worst case at admission (TGI, TensorRT-LLM's default) or allocate block by block and evict when the pool runs dry (vLLM). In the toy trace, request 4 is admitted, preempted twice and readmitted: A paged KV block manager and Admission, preemption and thrashing.
  3. Someone has to choose who joins first. With a seat opening every few steps, the queue's order is the latency. Past capacity (55 req/s), FCFS gives a TTFT p50 of 7.5 s; shortest-job-first cuts it to 97 ms but starves long requests (worst E2E 22.4 → 37.3 s, E5): Who goes next: FCFS, SJF, priority, fairness.

All three numbers are our simulation (E3, E8, E5).

Does every engine do this now?

Yes, every mainstream LLM server batches at the iteration level. They differ in when a joiner's prefill runs and in how they make sure it will have memory later:

When it's not the right tool. Models that answer in one forward pass (embeddings, classifiers, image models) have no "next step" to join, so time-window dynamic batching is the right choice there; Baseten's rule is "continuous batching for most LLM deployments and dynamic batching for most other models." A single local user gains nothing from it: batch 1 is the fastest per-user speed (205 vs 42 tok/s per user at 238 sequences, E1), which is why a laptop server with one caller behaves like a plain queue. And on its own it doesn't fix prefill stalls or memory overcommit; those need the next three cards.
