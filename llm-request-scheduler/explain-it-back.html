In one breath

All three answers come from one sentence: every forward step reads all 16.06 GB of weights once, shared by every token in the step, plus each request's own KV cache, which also has to fit in the memory that's left. Bottlenecks are about which of those reads (or the math) is biggest. The KV cache is the per-request part. Throughput levers either put more tokens into the shared read or shrink one of the reads.

1What are the main performance bottlenecks in LLM inference?

THE 60-SECOND ANSWER

It depends on the phase. Decode is memory-bandwidth-bound: to emit one token, a step reads all 16.06 GB of weights, which takes 4.8 ms on an H100, so batch 1 tops out at 4.9 ms per step, about 205 tok/s, while using 0.33% of the GPU's FLOPs. Prefill is compute-bound: a 4,096-token prompt shares that one read and takes 66.7 ms of pure math. Batching fixes decode, but then the KV cache becomes the limit twice over: its size caps the batch at 238 sequences at 2k context, and reading it is 80% of a full-batch step (19.07 of 23.86 ms). Around those sit the CPU that schedules each step (0.85–1.2 ms per step in our Python), long prefills stalling decodes (9.9 → 72.8 ms), and, across machines, the network.

Mental model: decode is one giant read per token; prefill is one read for thousands of tokens. Whichever is longer, the read or the math, sets the step.

To scale, 0–70 ms. Our arithmetic from the course facts: math = 2 × 8.03e9 × tokens ÷ 989 TFLOP/s; read = 16.06 GB ÷ 3.35 TB/s. The ridge between the two regimes is ≈ 295 tokens per step (Bcrit). Red marks the bottleneck; amber is prefill.

✗ The common wrong answer: "just buy more FLOPs."

At B = 1 the step is max(0.016 ms of math, 4.79 ms of weight read) + 0.08 ms of KV. A GPU with twice the FLOPs still takes 4.9 ms, because the max() is taken by the read. What helps decode is moving fewer bytes or doing more work per byte: batching, quantization, speculative decoding, or more bandwidth. FLOPs only help when prefill dominates: long prompts with short answers.

Follow-ups that usually come next

Why is decode memory-bound but prefill compute-bound?

Arithmetic intensity: FLOPs done per byte read. The H100 needs about 295 FLOPs per byte (989 TFLOP/s ÷ 3.35 TB/s) to keep its math busy. A decode step at B = 1 does about 1 (0.98 at 2k); a 4,096-token prefill does 3,964. So decode sits on the bandwidth slope of the roofline at 0.33% MFU, and prefill sits on the compute roof at 99.8% MFU (our model).

Why doesn't a bigger batch fix it forever?

The weight read is shared, but each request reads its own KV cache every step, so the KV term grows with batch × context. At 2k context, decode intensity can never pass 59.8, a fifth of the ridge, however large the batch, and even with unlimited memory throughput levels off at about 12,500 tok/s. In practice memory stops you first, at 238 sequences, and each user slows from 205 to 42 tok/s on the way (our model).

Where does the CPU come in?

In a naive loop the GPU sits idle while Python builds the next batch: 0.85–1.2 ms per step() with 256 running (E9, busy M3, ±50%), against a 23.9 ms GPU step, and 17–25% of the step at B = 1. That's why SGLang and vLLM V1 overlap scheduling for step N+1 with the GPU running step N; SGLang reported 1.1× for it.

2What role does the KV cache play during generation?

THE 60-SECOND ANSWER

Attention compares each new token with every earlier token, using a key and a value vector per earlier token, per layer, per KV head. Those never change once computed, so the KV cache keeps them in GPU memory and each decode step processes one new token instead of re-running the whole prefix: O(n) work instead of O(n²), which is 276× faster at a full batch generating 2,048 tokens in our model. The price is memory: 128 KiB per token for Llama-3.1-8B, so the 63.9 GB left after weights holds 487,504 tokens, which is 238 sequences at 2k context or 59 at 8k. That memory, not compute, caps the batch, which is why the scheduler's real job is managing KV blocks. And it's read every step: at B = 238 the KV read is 80% of the step.

Mental model: each request's notebook of past keys and values. Written once per token, read in full every step, and it's what fills the GPU.

Top bar to scale by bytes; bottom bar to scale by time. Sizes: 2 × 32 layers × 8 KV heads × 128 dims × 2 bytes = 131,072 B per token. Times: our model.

✗ The common wrong answer: "the KV cache stores the model's weights" (or "it caches answers").

The weights are 16.06 GB, fixed and shared by every request. The KV cache is per request and per token: intermediate keys and values computed from this request's tokens, growing by 128 KiB with each one and freed when the request ends. At full batch it's four times the size of the weights (63.9 vs 16.06 GB). Caching whole answers is a different thing again; prefix caching, which keeps KV blocks across requests, is the nearest real relative.

Follow-ups that usually come next

What happens when the KV cache is full?

First the scheduler stops admitting: a waiting request stays queued even if a batch seat is free. If a running request needs a new block and none is free, the scheduler preempts one, in vLLM V1 the newest running request under FCFS, frees its blocks, and later recomputes its prefix (swapping to CPU is the alternative). Too little memory means thrashing: in our simulation at 30 req/s, shrinking the pool from 30,469 to 2,000 blocks caused 270 preemptions and 625,438 recomputed tokens, and throughput fell from 6,736 to 4,063 tok/s.

Why not reserve the maximum length for each request up front?

Because most requests never use it. Reserving 4,096 + 1,024 tokens per request leaves the average request using 18.9% of its row, and only 95 sequences fit where paged 16-token blocks fit 237 (2.5×). vLLM measured 60–80% of KV memory wasted by reservation, and "under 4%" with PagedAttention. Reservation does buy one thing: no preemption, ever, which is why TGI and TensorRT-LLM's default use it.

Is it the same as prompt caching?

No. The KV cache lives inside one request. Prefix caching keeps some of those blocks after the request ends, keyed by the tokens they came from, so the next request with the same opening skips that part of prefill. In our simulation with four shared 2,048-token system prompts it computed 11.9× fewer prefill tokens (1,779,902 → 149,694) and cut TTFT p50 from 3,344 to 16.0 ms.

How do you make it smaller?

Fewer bytes per number (FP8 KV: 64 KiB per token, 476 sequences at 2k), fewer KV heads (GQA, which this model already uses; plain multi-head attention would be 512 KiB and 59 sequences at 2k), or a compressed latent (MLA). Each lever cuts both the memory and the per-step read.

3How do you increase inference throughput?

THE 60-SECOND ANSWER

Throughput is useful tokens per step divided by step time, so you either put more tokens into each step or make the step cheaper. The biggest lever is batching: one weight read shared by 238 requests takes decode from 205 to 9,973 tok/s, 49×. Continuous batching is what keeps the batch full as requests come and go, about 10× over static batching in our simulation (916 → 9,102 tok/s; Anyscale measured 23× on a real system). Then shrink the reads and the work: an FP8 KV cache halves the KV read, which is 80% of a full step (1.67×, to 16,609 tok/s); prefix caching skips repeated prompts (11.9× fewer prefill tokens); chunked prefill keeps long prompts from stalling everyone. Every one of these costs something, usually per-user latency, so the goal is throughput within the latency SLO.

Mental model: tok/s = tokens per step ÷ step time. Raise the top (batch, keep it full), shrink the bottom (fewer bytes, less work, less overhead), or add GPUs.

Output tok/s, log scale. Rows 1, 4, 5: our model at 2k context (E1; FP8 KV from CostModel.raw with 65,536 bytes per token). Rows 2–3: our simulation, E2 saturated. Continuous batching and the full batch aren't separate multipliers: continuous batching is how the batch stays full.

✗ The common wrong answer: "a bigger batch is always better."

Bigger batches raise total tok/s but slow every user (205 → 42 tok/s each at 238), need KV memory that runs out (then preemption and recompute), and stop paying once the KV read dominates. Past the SLO knee, more tok/s is less useful work: at 60 req/s our continuous scheduler hit 9,102 tok/s but only 41% of requests met TTFT ≤ 1 s and TPOT ≤ 50 ms. The number to maximise is goodput, requests per second that met the SLO, not raw tok/s.

Follow-ups that usually come next

How do you trade throughput for latency?

Three knobs. max_num_seqs: under overload, 16 sequences give 2,694 tok/s at 5.8 ms TPOT, 512 give 8,980 tok/s at 37.2 ms (E4). The token budget: at 256 tokens, ITL p99 is 7.2 ms but TTFT p50 is 82.4 ms, against 68.7 and 48.6 ms for whole-prompt prefill (E3). And admission: rejecting or queueing work at the door protects the SLO of what's already running. Pick the largest batch whose TPOT still fits the SLO.

When does speculative decoding hurt?

It spends idle math to get several tokens out of one weight read. At a small batch that math is free; at a big batch it isn't, so the reported gain falls from 1.96× toward 1.21× as the batch grows (ByteByteGo), and DeepSeek's ~1.8× comes with 80–90% acceptance. Our inference, not a sourced number: with a low acceptance rate on a full batch, the rejected guesses cost more than they save and throughput can drop below 1×. Use it for latency at low load; turn it down under heavy load.

Which levers stack, and which don't?

They multiply only when they attack different terms. Batch + FP8 KV stack: the batch shares the weight read and FP8 halves the KV read, 9,973 → 16,609 tok/s. Batch + 8-bit weights mostly don't: 8-bit weights are 2.0× at B = 1 (205 → 404) but only +4% at B = 238 (9,973 → 10,377), because the weight read is only 20% of a full step (our model).

What a good explanation sounds like

✗ The one-word answer

"Memory." True for decode at a full batch, false for prefill, and it hides which kind: bandwidth (the read) or capacity (what fits).

✗ The list of every technique

Naming ten optimisations without saying which term each one shrinks. Your colleague can't tell which matter (49×) and which don't (+4%).

✗ Numbers without a mechanism

"Continuous batching is 23× faster." On what, why, and at what cost? Without the step formula, the number doesn't transfer to another setup.

✓ Mechanism, one number, the trade-off

"Decode reads 16 GB per step, so batch 1 is 205 tok/s; batching shares that read for 49×, until the KV cache runs out or the SLO breaks." Then stop and let them pick the follow-up.

Rapid fire: 10 questions

Answer each in a sentence or two before opening it. They cover batching strategies, the scheduler's data structures and their cost, and the system around it.

BATCHINGAt 2 req/s, static batching of 32 had a TTFT p50 of 8.7 s while the GPU was mostly idle. Why?

A request waits for its batch to form and then for the previous batch to finish, and a static batch runs until its longest output is done. Continuous batching admits a new request at the very next step: TTFT p50 11.1 ms on the same trace (E2).

BATCHINGWhen is dynamic batching (wait up to a time window, then run) the right choice instead of continuous batching?

For one-pass models, such as embedding models, classifiers and rerankers, where a request is one forward pass with no decode loop, so there's nothing to join mid-flight. The knobs are a preferred batch size and a maximum queue delay (Triton's max_queue_delay_microseconds, default 0). For generation it loses: 892 vs 9,102 tok/s saturated in our simulation.

BATCHINGWhat does the token budget (max_num_batched_tokens) trade?

Smoothness against time to first token. A small budget chops long prompts into chunks so decodes never wait long (ITL p99 7.2 ms at 256), but each prompt takes more steps to finish (TTFT p50 82.4 ms). Whole-prompt prefill is the reverse: 68.7 and 48.6 ms (E3). Real engines also pay some per-chunk overhead at small budgets.

DATA STRUCTURESWhat's the cost of admitting one request from an SJF queue? From FCFS?

SJF: O(log W) for W waiting, a heap pop keyed by the predicted length (heapq in WaitQueue). FCFS: O(1), a deque. Fair share across tenants: O(tenants), picking the tenant with the least service so far.

DATA STRUCTURESWhy is vLLM's free-block list a doubly linked list and not a plain deque?

A prefix-cache hit has to pull a specific cached block out of the middle of the free list. Unlinking is O(1); deque.remove is O(N). With 30,469 blocks, that's about 1 µs against 1.4–1.8 ms on the M3 (a rough microbenchmark). The same list doubles as the LRU order for evicting cached blocks.

COMPLEXITYWhat does one step() of the reference scheduler cost?

O(R + A·log W) for R running, A admitted and W waiting (O(R + A) for FCFS), plus O(blocks allocated). It must not scan the whole waiting queue: our measured step time was almost the same with 100 or 10,000 waiting (E9).

SCHEDULINGA running request needs a new KV block and none is free. What does vLLM V1 do?

It preempts: under FCFS the victim is the newest running request (running[-1]); its blocks are freed, its computed-token count goes to 0, and it goes back to the front of the waiting queue to be recomputed. It admits nothing new in a step that preempted. Too little memory turns this into thrashing, like toy request 4, preempted twice.

POLICYSJF cut TTFT p50 from 7,490 to 97.2 ms at 55 req/s. Why not always use it?

It starves long jobs: the worst end-to-end time went from 22.4 to 37.3 s (E5). It also needs a length prediction, though even a very noisy one kept most of the gain. Fixes: aging (priority rises with wait time) or a separate priority class for interactive traffic (interactive TTFT p50 36.1 ms).

SYSTEM DESIGNWhen does splitting prefill and decode onto separate GPUs pay off?

When long prompts keep stalling decodes and you have enough scale to size two pools. DistServe reported 7.4× more requests served within SLO; Splitwise 1.4× throughput at 20% lower cost. The price is moving KV between machines (537 MB for a 4,096-token prompt: 10.7 ms over an illustrative 50 GB/s link) and two pools to balance. At small scale, chunked prefill on one pool is simpler.

SYSTEM DESIGNTraffic grows past one replica's capacity (40 req/s here). What should the system do?

Don't let the replica take everything: at 60 req/s it still produced 9,102 tok/s but only 41% of requests met the SLO. Push back at the door (HTTP 429, like TGI's max_concurrent_requests, default 128), route to other replicas, preferring the one that already holds the prompt's prefix (llm-d measured 2.0× throughput with prefix-aware routing), and add replicas when a serving signal such as queue depth or TTFT climbs (our suggestion: a saturated GPU looks equally busy whether it meets the SLO or not).

Is this the whole story?

No. These answers are for one 8B dense model on one GPU, priced at 100% of peak. Real engines are slower by their kernel efficiency and CPU overhead, so treat every time as a floor and every ratio as a shape. The ranking changes with the setup: for a large mixture-of-experts model spread across nodes, the network and expert load balance can move to the top of question 1, and for a model with a tiny KV cache (MQA or MLA), the KV terms shrink and weight bandwidth dominates for longer.

And sometimes the right answer to question 3 is "don't": a single user on a laptop gains nothing from batching, and a latency-critical service should cap its batch well below the memory limit. Say that too; knowing when a lever doesn't apply is part of explaining it well.
