The build-it problem: interface and constraints

Also called: request scheduler, batch scheduler, engine loop. This card opens the build section of the course. It states the practical engineering problem, the interface (using the names in labs/scheduler.py), the constraints, the questions worth asking first, and a 45-minute plan. The 8-request toy trace is the test input. Every time on this card comes from our simulator (the Llama-3.1-8B / H100 cost model at 100% of peak, so it's a floor).

In one breath

Requests arrive at any time. Each has a prompt and a limit on how many tokens it may write. The GPU runs one forward pass per step over a batch of requests. Your job is the code that decides, before every step, which requests go into that batch and how many tokens each one gets. The goal is to keep the GPU full (throughput) without making anyone wait too long (latency), and never to go over the step's token budget, the sequence cap or the KV memory.

The problem, stated neutrally

THE BUILD-IT EXERCISE

Implement a simplified request scheduler for LLM inference. Requests arrive concurrently, each with a prompt length and a maximum output length. Each step, the GPU runs one forward pass over a batch. Maximise throughput while keeping latency reasonable.

YOU ARE GIVEN

A token budget per step, a cap on sequences per batch, and a KV pool of N blocks of B tokens each. A model call that consumes the batch and returns one new token for every request that has finished its prompt.

YOU WRITE

The request state, the wait queue, step() and the bookkeeping after each step. The model itself is out of scope.

The interface

The stub below uses the names from labs/scheduler.py. Common generic names are in the comments. cancel isn't in the reference, so it's shown as an extension.

@dataclass
class Request:
    rid: int
    arrival: float
    prompt_len: int
    output_len: int           # max output (max_tokens); stop here
    priority: int = 0         # optional: lower = more important
    tenant: str = "a"         # optional: for fairness
    # state the scheduler owns
    state: str = WAITING      # WAITING | RUNNING | FINISHED
    num_computed: int = 0     # tokens whose KV is in the cache
    num_generated: int = 0    # output tokens so far
    blocks: list[int] = field(default_factory=list)

class Scheduler:
    def add(self, req): ...           # submit(req)
    def step(self) -> StepPlan: ...   # plan.scheduled:
                                      #   list[(req, n_tokens)]
    def finish_step(self, plan, now): # on_step_done(outputs)
        ...                           # returns finished reqs
    def cancel(self, rid): ...        # extension, not in ref

The engine loop that drives it is six lines. Each pass is one GPU step:

while True:
    for req in inbox.drain():          # arrivals since last step
        sched.add(req)
    plan = sched.step()                # who runs, how many tokens
    model.forward(plan.scheduled)      # one forward pass
    done = sched.finish_step(plan, now())  # emit tokens, free KV

Green boxes hold work that is using the GPU. The red dashed arrow is preemption: when KV memory runs out, a running request gives back its blocks and goes to the front of the waiting queue.

The constraints, as three inequalities

Every step must satisfy all three. Priorities and tenants don't add an inequality. They change the order in which requests try to fit.

Request 1's 5-token prompt gets a 4-token chunk because the budget runs out. Matches step 0 of the E8 trace (our simulator).

An analogy: a kitchen that can cook 16 plates per round (the budget), with 4 tables (sequences) and 12 chairs (KV blocks). A group that keeps ordering needs more chairs as it stays.

Ask these first

Each answer changes the code. If nobody answers, choose the harder default (in bold) and say so.

QuestionWhat each answer changes
Are output lengths known?default: no, only a maxKnown: reserve all blocks at admission and never preempt, and SJF is exact. Unknown: allocate blocks lazily and add preemption (vLLM), or reserve the max (TGI) and waste memory. SJF needs a predictor, but even a 100%-noise one kept the TTFT median at 109 ms vs FCFS's 7,490 ms (E5).
Is KV memory a constraint?default: yesNo: v1 (budget plus FCFS) is the whole answer. Yes: you need a block manager, an admission check and a policy for running out. On the toy trace, v1 peaks at 17 blocks of a 12-block pool.
Fairness, priorities, tenants?default: priority as an extensionThe waiting deque becomes a heap keyed on (priority, arrival), or one deque per tenant plus a served-token counter (VTC). The victim choice changes too. Add aging if starvation matters.
Streaming?default: yesfinish_step must emit each token as it's made, and the gap between tokens (TPOT/ITL) becomes an SLO. That argues for a smaller token budget with chunked prefill: ITL p99 7.2 ms at 256 vs 68.3 ms at 4,096 (E3). Without streaming, only end-to-end time counts.
Cancellation?default: yes, and tell them you're assuming itYou need cancel(rid) and a map from rid to request. If a step is in flight, mark the request and free its blocks in finish_step, exactly once, and never while another request still shares them.
Who calls add, and from which thread?default: many threadsKeep step() single-threaded, and hand arrivals over through a thread-safe inbox that the loop drains. See Handling concurrent requests.
Optimise throughput or latency?default: throughput under a latency SLOThroughput: large budget, high max_num_seqs. Latency: small budget, low cap. At 60 req/s: cap 16 → 2,694 tok/s and TPOT 5.8 ms; cap 512 → 8,980 tok/s and 37.2 ms (E4). The usual target is goodput: requests per second that meet TTFT ≤ 1 s and TPOT ≤ 50 ms.

Numbers are from our simulator (labs/results.md). Which default to pick when nobody answers is our advice, not a rule from any source.

What a correct scheduler must do on it, as checks you can write before any policy code:

every step:
  assert plan.num_tokens <= 16                  # budget
  assert len(sched.running) <= 4                # max sequences
  assert 0 <= bm.num_free() <= 12               # never over the pool
  assert each request is in exactly one of waiting / running / finished
at the end:
  assert all(r.num_generated == r.output_len for r in trace)
  assert all(len(r.token_times) == r.output_len for r in trace)
  assert bm.num_free() == 12                    # every block back
  assert every request finished                 # no deadlock
sanity bound:
  steps >= ceil(139 / 16) = 9    # 139 = Σ (prompt + output − 1)

The first two end-of-run checks are what labs/test_scheduler.py tests under preemption. The bound works because a request's last output token is never fed back in, so the trace needs 103 prompt + 44 output − 8 = 139 forward tokens. With 12 blocks, our reference takes 21 steps and 3 preemptions. At step 3 there are 0 free blocks, so request 3 waits even though a seat is free. Request 4 is admitted, preempted at steps 6 and 8, and readmitted (E8).

Public practice versions

  • nano-vllm: a scheduler of about 100 lines (engine/scheduler.py, block_manager.py). It's the closest thing to a reference solution: prefill-first, running.pop() preemption, and a hash-chained block cache.
  • continuous-batching-scheduler: set up as an exercise, with submit / step / cancel, shared prefix blocks, a cancellation bug to find and an ABA problem to fix.
  • LLM-Scheduler: a simulator with priority admission, chunked prompts, LRU block eviction, preemption and TTFT/TPOT/SLO metrics.
  • theneuralbase "Continuous batching scheduler": a lesson with step() once per token, max_batch_size and a bounded incoming queue.
  • terminal-bench "llm-inference-batching-scheduler": a static-shape variant (at most 8 batch shapes, with cost, padding and p95 limits). This one really is a packing problem.
  • Jaillet et al., "Online Scheduling for LLM Inference with KV Cache Constraints": the theory version, with a memory budget M, known vs unknown output lengths, and total latency as the objective.

Why build it in three versions

✗ Design it all, then code

Paging, prefix caching and priorities all at once. At minute 45 nothing runs yet. And when the trace breaks, you can't tell whether admission, growth or preemption caused it.

✗ Start from static batching

It's simpler, but it's the thing the exercise wants replaced. In our simulator, 71% of decode slots are padding and it meets the SLO at no rate at all, vs 40 req/s for continuous batching (E2).

✗ Start with threads and locks

Concurrency lives at the edge (the inbox and cancel). The core is one single-threaded step(). Locks added before the invariants hold just hide which part is wrong. This point is our inference.

✓ v1 → v2 → v3, checked on the toy trace

Every 15 minutes you have something that runs, and each version fixes a failure you can see: v1 overflows memory (17 of 12 blocks), v2 is safe but slower (22 steps), v3 finishes sooner (21) and preempts 3 times.

Why is this not an algorithms puzzle?

Because the algorithm is a greedy loop anyone can write: handle the running requests first, then admit from the head of the queue while things fit. There's no clever optimum to find. In the theory version, Jaillet et al. show that "no deterministic online algorithm can achieve a constant competitive ratio" when arrivals are arbitrary. The difficulty is in state and invariants. num_computed must match the blocks a request holds. A request must be in exactly one queue. A preempted request has to reset its progress and go back to the front. A block must be freed exactly once, even when cancel races a step in flight. Most bugs here are bookkeeping bugs, so write the checks above before you tune any policy.

Some parts of it are algorithmic. The static-shape variant is a packing problem. SJF with a length predictor is a real prediction problem. A radix-tree prefix cache is a data-structure exercise. If memory really doesn't bind in your setting, skip v2 and v3 and spend the time on the policy.

Understand and remember

  • Every step must satisfy Σn ≤ budget, |running| ≤ max_seqs and Σ⌈(c_i + n_i) ÷ B⌉ ≤ N blocks → the scheduler is a greedy loop that serves running requests and admits from the queue while all three hold
  • Output lengths are unknown → either reserve the maximum at admission (never preempt, fewer fit) or allocate lazily and preempt when memory runs out → that one answer decides v2 vs v3
  • Build in versions that each run → v1 (budget + FCFS) overflows memory (17 of 12 blocks), v2 (reserve) is safe but slower (22 steps), v3 (lazy + preempt) finishes in 21 steps with 3 preemptions → each failure motivates the next version
  • The hard part is state, not the algorithm → a request in exactly one container, num_computed matching its blocks, every block freed once → write invariant checks before tuning policy
  • detail that matters The last output token is never fed back → a request needs prompt + output − 1 forward tokens → the toy trace needs 139 → at least ⌈139 ÷ 16⌉ = 9 steps, a bound any correct scheduler must respect

6 · Apply use the model, don't restate it

Using the toy config (budget 16, 4 seats, blocks of 4 tokens, 12 blocks): (a) a proposed step schedules a decode for A (num_computed 7, 2 blocks held), a decode for B (num_computed 15, 4 blocks held) and a new request C with a 9-token prompt. Check all three inequalities and say how many blocks are free afterwards. (b) Compute the lower bound on steps for a trace of three requests with (prompt, output) = (10, 5), (20, 3), (6, 8).

Done when: (a) tokens 1 + 1 + 9 = 11 ≤ 16; 3 ≤ 4 running; A needs ⌈8/4⌉ = 2 (no new), B ⌈16/4⌉ = 4 (no new), C ⌈9/4⌉ = 3 new, so 9 of 12 blocks held and 3 free. (b) (10 + 5 − 1) + (20 + 3 − 1) + (6 + 8 − 1) = 49 forward tokens → at least ⌈49 ÷ 16⌉ = 4 steps.

Hint

A block is needed for token positions up to c + n, where c is num_computed before the step.
