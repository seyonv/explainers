Request lifecycle and the data structures

Also called the request state machine, the waiting and running queues, the block table. This card follows one request of the toy trace through labs/scheduler.py, then lists every structure the scheduler keeps with the cost of each operation, with what vLLM V1, SGLang and nano-vllm chose instead. The build-it exercise is judged on exactly this: which container, and what each call costs.

In one breath

A request is a small record with two counters, how many of its tokens have KV in the cache and how many exist. It moves between a waiting queue and a running list until its last token comes out. Every scheduler operation is a push, pop, lookup or removal on one of about six containers, and picking the right container for each is what keeps step() cheap at thousands of queued requests.

The lifecycle: four states, five edges

Grey = waiting, green = doing useful work, red = work thrown away. labs/scheduler.py has the three solid states (WAITING, RUNNING, FINISHED); ABORTED is the usual extension when the exercise asks for cancel(id), sketched further down. vLLM V1 also names a separate PREEMPTED status; ours puts a preempted request straight back to WAITING.

The record: two counters instead of a phase flag

@dataclass class Request: rid: int arrival: float prompt_len: int output_len: int # true length; the scheduler never reads it priority: int = 0 # lower number = more important tenant: str = "a" predicted_len: int | None = None # what SJF is allowed to see state: str = WAITING num_computed: int = 0 # tokens whose KV is in the cache num_generated: int = 0 # output tokens produced so far num_cached: int = 0 # prompt tokens served from the prefix cache blocks: list[int] = field(default_factory=list) # the block table ... # timestamps, preemptions, block_hashes @property def num_tokens(self): # prompt + everything generated so far return self.prompt_len + self.num_generated @property def remaining(self): # tokens that still need a forward pass return self.num_tokens - self.num_computed

Condensed from labs/scheduler.py (names unchanged; the timestamps and hash cache are cut).

The scheduler never asks "is this a prefill or a decode?" It asks only how far num_computed is behind num_tokens, and gives each request as many tokens as the budget allows:

nitokens this step =min( pi+ginum_tokens−ciremaining , bleftbudget left )
piprompt_len30 for toy request 4 ginum_generated: grows by 1 each time c catches up0 → 3 cinum_computed: KV already in the cachereset to 0 on preemption blefttoken budget left in this step16 per step in the toy

A fresh prompt has a large remaining (prefill, possibly in chunks); a decoding request has remaining = 1; a preempted one has remaining = prompt + what it had generated; a prefix-cache hit starts with c already advanced. One rule covers all four. vLLM V1 does the same: its scheduler's comment says there is "no 'decoding phase' nor 'prefill phase'", only num_computed_tokens catching up with num_tokens_with_spec, which is how it also fits speculative decoding in.

Adding cancel(id): a sketch

# not in labs/scheduler.py: needs self.requests = {} filled by add() def cancel(self, rid): req = self.requests.pop(rid, None) # O(1) if req is None or req.state == FINISHED: return # unknown or already done if req.state == RUNNING: self.running.remove(req) # O(R) self.bm.free_request(req) # O(blocks held) req.state = ABORTED # if WAITING: lazy, pop() skips it later

Illustrative code. Two traps a practical version must handle: if the GPU step that includes this request is still running (overlapped scheduling), its blocks must not be freed until that step completes; and blocks must be released exactly once, since finish_step may also try to free a request that finishes in the same step. The public exercise sa-faizal/continuous-batching-scheduler is built around these two bugs.

Why these structures beat the alternatives

✗ One list, scanned every step

Keep all requests in one list with a state field and filter it each step. Simple, but every step pays O(W): with 10,000 queued, the scan dwarfs the 256 running requests that actually get work.

✗ A sorted list for priority

Correct order and an easy head, but each insert shifts the list: 48–56 µs at W = 10,000 in our timing, 11–35× a heap push and pop. A heap is enough, since only the minimum is ever needed.

✗ A plain deque as the free list, with prefix caching

Fine until a cached block is hit while it sits in the free list: deque.remove scans 30,469 entries, 1.4–1.8 ms per block hit, a third of a 4.9 ms decode step for a single block.

✓ deque or heap + list + dict + linked free list

Every per-step operation is O(1) or O(log W) except the walk over running requests, which the step has to do anyway. E9 bears it out: 10,000 waiting cost about the same as 100.

Why keep "running" as a plain list if removal is O(R)?

Because R is small and the step is O(R) anyway. R is capped by max_num_seqs (256 in our runs, 1,024 by default on an H100 in vLLM), and every step already walks every running request to schedule its next token. A removal scan adds one more pass over the same short list: 2.2–5.6 µs at R = 256 against a 0.85–1.2 ms step (E9). The list also gives what the scheduler needs most: iteration in admission order and an O(1) newest-first victim with pop(). vLLM V1 makes the same choice.

When it is the wrong choice. Switch to an OrderedDict keyed by id (or an intrusive linked list) when removal happens outside the walk and often: frequent cancels, or a configuration where R reaches thousands (our judgment, not a measured threshold). Likewise the O(N) deque.remove is harmless with prefix caching off, which is why nano-vllm and our never-used-block deque get away with it. And if you pick policy by key, remember the waiting queue can change containers too: a heap for SJF, an array of deques for a few priority levels, a per-tenant map for fairness.
