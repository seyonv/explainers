The bottlenecks: bandwidth, compute, memory, and the CPU

Also called the roofline view, memory-bound vs compute-bound, or by its two gauges, MBU and MFU. This card answers the question "what are the main performance bottlenecks in LLM inference?" with a ranked list, and proves each one with a number from the running example: Llama-3.1-8B in BF16 on one H100 SXM, priced by our simulator's cost model (100% of peak, so every time is a floor).

Prime · 2 minutes before you read

The problem: "What limits LLM inference?" has no one-word answer: the binding limit changes with the phase, the batch size and the context. Guess wrong and you buy FLOPs for a bandwidth problem, or raise the seat cap on a server that is out of KV memory.

Where it fits: Third card of group 1. The token loop gave you the two phases and the KV cache card gave you the per-request memory. This card puts every limit into one step formula and ranks them, so the batching and scheduler cards can each be read as removing one term.

In one breath

Each forward step has to read all the weights from memory and do two multiply-adds per weight per token. In decode, one token per request isn't enough work to hide the read, so memory bandwidth sets the speed. In prefill, thousands of tokens share one read, so compute does. Around those two sit the limits that decide how big a batch you can actually run: KV cache memory, KV reads that grow with context × batch, the CPU that schedules each step, prefills stalling decodes, and, across machines, the network.

The roofline, with our points on it

A roofline plots what a step can achieve (FLOP/s) against how much work it does per byte it reads. Left of the ridge, the slope is bandwidth: more work per byte means proportionally more FLOP/s. Right of it, the flat roof is peak compute. Every point below is a step priced by our simulator.

Green dots: decode steps at 2k context (B = batch). Amber squares: one prefill of 512 or 4,096 tokens. Every decode point sits on the slope (100% of bandwidth by construction) and far below the roof. Counting weights only, B = 238 would have intensity 238, just short of the ridge (hollow circle). But each request also reads its own 268 MB of KV every step, so real intensity is 2·P·B ÷ (W + B·268 MB) = 47.8, and it can never pass 2·P ÷ 268 MB = 59.8 however large the batch (15.0 at 8k context). Why the CPU row forces overlap

A naive loop runs schedule → run → process results in series, so every millisecond of CPU is a millisecond of idle GPU. SGLang's overlap scheduler, on by default, launches batch N+1 on the GPU and then processes batch N's results on the CPU, so CPU work hides behind GPU work; SGLang reported "1.1x" over its previous version for this "zero-overhead" scheduler. vLLM has the same idea as async scheduling. The catch: batch N+1 is built before batch N's tokens are known, so the engine uses placeholder ("future") tokens and turns overlap off where it would hurt TTFT, for example two consecutive prefills.

How to see it: MFU and MBU

Two gauges tell you which side of the ridge you're on. MFU (model FLOPs utilisation) is the FLOP/s a step achieves ÷ peak. MBU (memory bandwidth utilisation), the metric Databricks introduced for inference, is the bytes per second the step moves (weights plus KV) ÷ peak bandwidth. A decode step with low MFU and high MBU is bandwidth-bound and working as well as it can; low on both means something else (the CPU, a stall, a bad kernel) is in the way.

MFU = 2·P·T / (t_step · C) MBU = (W + KV bytes) / (t_step · BW)

Why "it depends on the phase" beats the one-word answers

✗ "It's compute"

True for prefill only. A decode step at B = 1 uses 0.33% of the H100's FLOPs; doubling them leaves the step at 4.9 ms, because the max() is taken by the weight read.

✗ "It's memory size"

Capacity limits the batch (238 at 2k), but even an unlimited batch at 2k would stay bandwidth-bound: intensity tops out at 59.8, a fifth of the ridge, because KV reads grow with the batch.

✗ "It's the GPU; the software doesn't matter"

The scheduler decides the batch, the stalls and the CPU gap. Continuous batching gives ≈ 10× static's throughput on the same GPU in our model (E2: 9,100 vs 916 tok/s).

✓ Name the phase, then the term

Prefill: compute. Decode: weight bandwidth at small batch, KV bandwidth and capacity at large batch. Then check the CPU gap, the stalls and the network. Measure MFU and MBU for each phase to tell which one you're in.

If decode is memory-bound, why not just buy more FLOPs?

Because the FLOPs aren't what's missing. At B = 1 the step is max(0.016 ms of compute, 4.79 ms of weight read) + 0.08 ms of KV: a GPU with twice the FLOPs gives the same 4.9 ms. What does help is moving fewer bytes or doing more work per byte: batching (the weight read is shared), quantization (INT8 halves the weight read), speculative decoding (verify several tokens per weight read; ByteByteGo cites "roughly 1.8x throughput" for DeepSeek), or a GPU with more bandwidth.

FLOPs are the answer when prefill dominates: long prompts with short answers (retrieval, classification, summarising a document), or re-prefill after preemption. That's also why splitting prefill and decode onto different hardware can pay off; Splitwise argues decode can run on cheaper hardware. And note the ranking changes with the setup: on a big mixture-of-experts model spread across nodes, or with KV shipped between machines, #7 can move to the top.

Understand and remember

  • Every step reads all weights once → decode puts one token per request on that read → intensity ≈ B, far below the 295 ridge → decode is bandwidth-bound; prefill puts thousands of tokens on it → compute-bound
  • Batching shares the weight read but not the KV read → each request reads its own 268 MB of history per step at 2k → intensity is capped at 2·P ÷ 268 MB = 59.8 → decode stays bandwidth-bound even with unlimited memory
  • KV capacity (238 at 2k) stops the batch before the ridge → batch cap, then KV read, then CPU gaps and prefill stalls decide the speed → the fix depends on which term is largest right now
  • A naive loop runs CPU scheduling and GPU work in series → 0.3–1.2 ms of Python per step is idle GPU → overlap scheduling turns the sum into a max
  • detail that matters MBU = bytes moved ÷ (step time × bandwidth) → a decode step at high MBU and low MFU is already optimal for its batch → the only fixes are fewer bytes or more tokens per byte, not faster kernels

5 · Predict commit to an answer before revealing

Keep the batch at 238 but cut every context from 2k to 512 tokens. Before computing: which term becomes the largest, and does intensity cross the 295 ridge?

Reveal

The KV read drops 4× (about 4.8 ms), so it roughly ties the 4.79 ms weight read and the step falls to about 9.6 ms. Intensity rises to about 2·P·238 ÷ (16.06 GB + 238 × 67 MB) ≈ 120, still below 295: decode stays bandwidth-bound, just less dominated by KV. Shorter contexts would also let far more sequences fit, which is where the extra throughput would come from.
