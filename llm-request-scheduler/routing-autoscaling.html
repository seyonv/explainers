Many replicas: routing, admission and autoscaling

Also called the load balancer, the inference gateway, KV-aware or prefix-aware routing, cache-aware load balancing, data parallelism (DP: many copies of the same model), and, for the scaling part, HPA or KEDA on Kubernetes. This card covers the cluster layer that sits above one engine. It compares the routing policies real systems report on, then runs four of them through our simulator (labs/routing_sim.py: four copies of the course's scheduler with a 100%-of-peak cost model for Llama-3.1-8B on one H100 each, so the times are floors, not measurements).

In one breath

One engine tops out at a few dozen requests a second, so production runs N identical replicas behind two layers. A gateway decides whether a request gets in: it authenticates, applies per-tenant token limits, and sheds load with 429. A router decides where it goes. Each replica has its own KV cache, so the router has to trade cache affinity (send the request to the replica that already holds its prefix) against load balance (send it to the least busy replica). An autoscaler watches queue depth and KV use and adds or removes replicas, and every new replica needs seconds to load its weights.

The tension, and how a scored router resolves it

Pure affinity sends every request for prompt P to the one replica that has P cached. If P is popular, that replica melts while the others idle. Pure balance spreads P's requests over all N replicas, so each one prefills and caches P separately, and when the prefixes don't all fit, each replica evicts what the next request needs. A scored router adds both terms into one number and lets the weights set the exchange rate: a cache hit is worth this much queue.

scorek= whit⋅hitkcache affinity − wload⋅loadkmaxjloadjload balance loadk=4⋅waitingk+runningk

The router picks the replica with the highest score. Filled in: a warm replica that is the busiest scores 3·0.94 − 3·1 = −0.18; a cold idle one scores 3·0 − 3·0 = 0, so a replica at maximum load loses its cached request. At half the maximum load, the warm one scores 3·0.94 − 1.5 = 1.32 and keeps it. We added the normalisation; GKE's post gives the weights but not how each scorer is scaled.

The two workloads bracket the real cases. A is the "few big system prompts, huge memory" case, where round robin is fine and a naive hash is the worst choice. B is llm-d's case (their cache demand was "nearly six times larger than any single pod's"), where ignoring the cache turns a comfortable load into an overload: a 46% hit rate means each replica re-prefills about half of 2,048-token prompts at 20 req/s, which E7 shows one replica can't sustain without the cache (3.3 s TTFT p50). The scored router is the only one that is best or tied in both.

Why it beats the alternatives

✗ Round robin

Zero state, perfectly even request counts. But in B it spreads 64 prompts over every replica's cache, hit rate 45.6%, and TTFT p50 is 2.7 s.

✗ Least-loaded (vLLM DP score)

Evens out queues, not work: it can't see that one replica would serve the request from cache. In B it does no better than round robin (47.1%, 2.8 s).

✗ Prefix consistent hashing

Great hit rate, but the load follows the hash. With 4 hot prompts, one replica took 302 requests and another 0, cutting throughput to 10,459 tok/s.

✓ Scored router (hit − load)

Takes the cache hit unless that replica is much busier than the rest. It is best or tied on hit rate, p99 and throughput in both workloads (38.2 ms and 73.2 ms p99).

Admission at the edge: shed before the queues explode

A replica past its capacity doesn't slow down gently. Our E2 workload fits in the SLO up to 40 req/s on one replica (steady state). At 60 req/s only 41% of requests make the SLO (TTFT p50 1,397 ms), and in E5, at 55 req/s with 64 seats, FCFS pushes TTFT p50 to 7.5 s. Once the queue grows, every request in it is late. So the gateway should refuse the excess early, when a rejection is cheap and the client can retry elsewhere or later, rather than admit it into a queue it will time out in.

token bucket per API key (one common design; numbers illustrative) limit = 100,000 tokens / min, refills continuously charge = prompt tokens + max_tokens = 1,000 + 512 = 1,512 (counted at the gateway, so it must tokenize) refund = max_tokens − tokens actually generated, at the end bucket short? → 429, Retry-After: seconds until it refills cluster queue full → 429 or 503, Retry-After from the drain rate
  • Count tokens, not requests. One request can be 50 tokens or 50,000, so a requests-per-minute limit lets one tenant's long prompts starve everyone. The fair-share version of this inside one replica is on Who goes next (E6).
  • Early rejection. Mooncake's scheduler uses "prediction-based early rejection" when overloaded (more on the Mooncake card in Attention and the KV cache). GKE Inference Gateway uses "admission control at the ingress" plus upstream queue management to absorb bursts. TGI's single-replica version is max_concurrent_requests (default 128), which returns an overloaded error.
  • Retry-After matters. Without it, clients retry immediately and the rejected load comes straight back. With it (and client jitter), retries spread out over the time the queue needs to drain.

So scale on the leading signals, keep some headroom, and let admission control absorb the burst while the new replica loads. On Kubernetes, the HPA or KEDA scale on whatever metric you export, and choosing that metric is the actual design decision. Scaling down has the reverse problem: a replica holds running requests and a warm prefix cache, so drain it (stop routing new work, let running requests finish) and expect the hit rate to dip while the survivors re-warm.

Prefill and decode pools scale separately. When prefill and decode run on different replicas (splitting prefill and decode), their load comes from different things: prefill from prompt tokens per second (it shows in TTFT), decode from concurrent sequences and their KV (it shows in TPOT and KV use). NVIDIA Dynamo's Planner "moves GPUs between prefill and decode" based on SLOs like TTFT and ITL, and llm-d lists "variant autoscaling". Which signal drives which pool is our reading of that split, not a rule from either source.

Why not just put an ordinary L7 load balancer in front? Because it balances the wrong thing. An HTTP load balancer sees connections and request counts. It can't see that one request is 50 tokens and the next is 20,000, that replica 3's KV cache is 93% full, or that replica 1 already holds this conversation's 6,000-token history. So it behaves like the round robin or least-loaded rows above: fine in workload A, a 188× worse TTFT p50 in workload B. An inference gateway adds exactly the missing inputs: token counts, queued tokens, KV use and cached prefixes.

When a plain load balancer is enough: when prompts share little (no system prompt, no multi-turn), when every replica can cache every shared prefix (workload A), or with one or two replicas, where affinity barely matters. And the scored router isn't free: it needs a fleet-wide view of each cache (llm-d builds one from vLLM's KV events, SGLang's router keeps "an approximate radix tree" per worker), and weights you have to tune. GKE moved the queue weight from 3 to 5 to steer around hot nodes. Our simulation gives the router a perfect, instant view, so real routers do somewhat worse than our "scored" row.
