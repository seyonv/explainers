Modern concurrency constructs

Also called async/await and event loops, futures and executors, channels (CSP), actors, and lock-free programming with compare-and-swap. The source guide's Modern Concurrency Constructs heading is empty, so this card follows OSTEP, the Python docs and measured runs on an Apple M3.

Prime · 2 minutes before you read

The problem: An OS thread per waiting job costs a kernel object and a stack, and the M3 refused to start thread 6,143. Locks around shared state cost contention and risk deadlock. Modern code needs cheaper ways to hold thousands of waits open, to get results back from workers, and to share state without a lock around it.

Where it fits: Last card. It replaces the tools of the whole course with lighter ones: coroutines instead of threads (threads card), messages instead of locks (locks to monitors), compare-and-swap instead of a mutex, and user-space switching instead of kernel switches (the context-switch cards).

In one breath

Instead of giving every waiting job its own OS thread and guarding shared data with locks, modern code uses lighter pieces: many coroutines on one thread (asyncio), futures as handles to results that a pool computes, messages sent over channels or to actors instead of shared variables, and atomic compare-and-swap for the few counters that must be shared.

Worked example: 10,000 waits of 0.1 s each

Think of 10,000 network calls that each wait 100 ms for a reply. The waiting is the whole job, so the question is how cheaply you can hold 10,000 waits open at once.

0.25 s: series measurement on the M3. The failure at 6,143 is one run on the author's M3: sysctl kern.num_taskthreads caps a macOS process at 6,144 threads (the main thread is one), and peak RSS for the 6,143 idle threads was 152 MB, about 25 KB each actually touched. 16 MiB is the stack a new CPython 3.10 thread got (16,789,504 B) versus the C default of 524,288 B, both read with ctypes. 1.6 KB per task is a tracemalloc reading from one run.

The code: coroutines and futures

import asyncio, time
from concurrent.futures import ThreadPoolExecutor

async def many_waits(n):            # one thread, n coroutines
    await asyncio.gather(*(asyncio.sleep(0.1) for _ in range(n)))

def fetch(i):
    time.sleep(0.1)                 # stands in for a network call
    return i * i

def pool_demo():                    # a future = a handle to a result
    with ThreadPoolExecutor(max_workers=8) as pool:
        futs = [pool.submit(fetch, i) for i in range(16)]
        return sum(f.result() for f in futs)   # blocks until done

# 10,000 asyncio.sleep(0.1): 0.30 s
# 16 x fetch on 8 threads: 0.22 s, sum = 1240

One run of code/modern-concurrency.py under python3 3.10 while the machine was busy (the series best is 0.25 s). 16 jobs on 8 workers is 2 rounds of 0.1 s = 0.2 s at best; the sum is 0² + 1² + … + 15² = 1,240.

Each await is a point where the coroutine hands control back to the event loop, which runs whichever other coroutine is ready. Nothing preempts it in between, so code between two awaits can't be interleaved with other tasks on that loop. A future is a placeholder filled in later: submit returns at once, and result() blocks until the worker has finished.

Lock-free: compare-and-swap with a retry loop

CAS is one atomic instruction: "if the value is still old, set it to new, and tell me whether you did". A lock-free counter reads, computes, then CASes; if another thread got there first, the CAS fails and it simply tries again. Nobody ever waits holding a lock.

old = 55

CAS(5 → 6): ok6

Interleaving is illustrative. Compare the locks card: there the second write silently overwrote the first; here the stale write is refused and redone, so both increments count.

def cas(cell, expected, new):
    with _hw:                       # one indivisible step in hardware
        if cell[0] != expected:
            return False
        cell[0] = new
        return True

def add_one(cell):
    retries = 0
    while True:
        old = cell[0]               # read
        time.sleep(0)               # let another thread get in
        if cas(cell, old, old + 1):  # only if unchanged
            return retries
        retries += 1                # someone beat us: try again

# 4 threads x 10,000 add_one:
# CAS counter: 40,000 of 40,000, 3,385 retries

Python exposes no compare-and-swap, so cas() uses a small lock (_hw) to stand in for the instruction's atomicity. The retry loop is the real technique; the retry count changes every run. In hardware it's LOCK CMPXCHG on x86 and a CAS or load-exclusive/store-exclusive pair on ARM64 such as the M3.

What has a nameThe channel. Goroutines are anonymous; any number can send or receive on a channel.The process. Each one has a process id and one mailbox that only it reads.

Why asyncio beats the alternatives for 10,000 waits

✗ A serial loop

Correct and simple, but the waits add up: 10,000 × 0.1 s = 1,000 s.

✗ A thread per wait

Each thread is a kernel object with its own stack. On this Mac the 6,144-per-process limit stopped it before 10,000.

✗ A process per wait

Worse still: a spawned process costs 72 ms to start and join (measured), so 10,000 of them one after another is 720 s of startup alone.

✓ asyncio tasks

A task is a small heap object, not a kernel thread: about 1.6 KB each, all 10,000 done in 0.25 s on one thread.

So which one do I pick?

  • Many waits (sockets, HTTP): asyncio, if the libraries you call are async. A blocking call inside a coroutine freezes the whole loop.
  • A few dozen blocking calls: a ThreadPoolExecutor. Threads are fine at this scale and need no async rewrite.
  • CPU-bound Python: ProcessPoolExecutor today (3.8× on the M3), or threads on a free-threaded 3.14t build, which then need the same locks C code would.
  • State owned by one worker: a queue in front of it (channel or actor style) instead of a lock around it.

Lock-free isn't automatically faster. Under heavy contention CAS loops burn CPU on retries, and correct lock-free structures beyond a counter are hard (ABA, memory reclamation). A plain Lock costs 58 ns uncontended (measured) and is the right default. None of these constructs removes races by itself: a read, then an await, then a write still races between tasks.

Understand and remember

  • A waiting job needs only its state, not a kernel thread → coroutines are heap objects (≈ 1.6 KB) switched by one event loop at each await → 10,000 waits in 0.25 s (≈ 15 µs overhead per task) → but one blocking call or CPU loop in a coroutine stalls every task
  • Switches happen only at await → code between two awaits can't be interleaved → most races vanish without locks → but read, await, write still races
  • CAS = "set to new only if still old", in one atomic instruction → a stale update fails and retries instead of overwriting → no thread ever waits holding a lock → but under heavy contention retries burn CPU (3,385 retries for 40,000 increments), and structures beyond a counter hit ABA
  • Share by sending instead of by locking → one owner per piece of state behind a queue (channel or mailbox) → no lock around the state → channels name the pipe and can block the sender; actors name the process and send asynchronously
  • detail that matters CPython 3.10 threads got 16 MiB stacks here vs the C default of 512 KiB → 10,000 threads reserve 156 GiB of address space (only ~25 KB each touched) → the real limit hit was macOS's 6,144 threads per process, not memory

Reference only

  • LOCK CMPXCHG on x86, load-exclusive/store-exclusive on ARM64
  • Go's select, Erlang's links and OTP supervisors
  • kern.num_taskthreads = 6,144
  • PEP 703 and PEP 779 (free-threading experimental in 3.13, supported in 3.14)

3 · Retrieve from memory, card closed
  1. concept Explain why an asyncio task is so much cheaper than an OS thread for holding a wait open, and what you give up for that.
    Check
    • a task is a heap object that saves its state at await; switching is a function return inside one thread, no kernel
    • a thread is a kernel object with its own stack and is switched by the kernel
    • you give up preemption: a task that doesn't await (CPU loop, blocking call) freezes the loop
  2. mechanism Walk through the CAS trace: both threads read 5, thread 2's CAS succeeds. What happens to thread 1, step by step, and why does the counter end at 7?
    Check
    • thread 1 calls CAS(5 → 6), but the value is now 6, so the CAS fails and nothing is written
    • thread 1 re-reads 6 and calls CAS(6 → 7), which succeeds
    • both increments count: 5 → 6 → 7; the stale write was refused, not applied
  3. tradeoff 10,000 HTTP calls of 0.1 s each. Compare a serial loop, 10,000 threads, a pool of 8 threads and asyncio, using the card's numbers and one failure mode each.
    Check
    • serial: 1,000 s; correct but slow
    • a thread each: stopped at 6,143 threads on macOS
    • pool of 8: 1,250 rounds × 0.1 s = 125 s
    • asyncio: 0.25 s, if every library call is async
  4. tradeoff When would you choose a queue in front of a worker that owns the state, rather than a lock around shared state?
    Check
    • when many parties update the same state and the updates can be applied one at a time by its owner
    • it removes the lock and its deadlock risk; the queue does the only synchronisation
    • it costs a hop per update and makes the owner a bottleneck if updates are heavy

vs Monitors and condition variables: A hand-written monitor, queue.Queue, and a Go channel all hand items between workers. What does each one hide from you, and which one fits asyncio?

Check
  • the monitor hides nothing: you write the lock, conditions and while loops

  • a Go channel is the same hand-off as a language primitive, with select over several

vs How a context switch works: A kernel context switch vs an asyncio task switch: what is saved, who decides when, and what does each cost according to the course's measurements?

Check
  • kernel: registers into the PCB, maybe a page table; decided by blocking or a timer
  • asyncio: the coroutine's frame stays on the heap; decided only at await
  • the kernel switch is ≤ 4–7 µs each (ceilings) plus cold caches; asyncio's 15 µs covers creating, scheduling and finishing a task, with no trap into the kernel

5 · Predict commit to an answer before revealing

Same 10,000 waits of 0.1 s, but on a ThreadPoolExecutor(max_workers=50), and separately in asyncio with an asyncio.Semaphore(100) around each wait. Predict both wall times. Commit before revealing.

Reveal

Pool of 50: 10,000 / 50 = 200 rounds × 0.1 s = 20 s. asyncio capped at 100: 100 rounds × 0.1 s = 10 s, plus a little overhead. The cap, not the construct, now sets the time; asyncio's advantage is that it can afford a much higher cap. The cap is still worth having, for the server's sake, as the semaphores card argued.
