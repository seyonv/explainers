Modern concurrency constructs

Also called async/await and event loops, futures and executors, channels (CSP), actors, and lock-free programming with compare-and-swap. The source guide's Modern Concurrency Constructs heading is empty, so this card follows OSTEP, the Python docs and measured runs on an Apple M3.

In one breath

Instead of giving every waiting job its own OS thread and guarding shared data with locks, modern code uses lighter pieces: many coroutines on one thread (asyncio), futures as handles to results that a pool computes, messages sent over channels or to actors instead of shared variables, and atomic compare-and-swap for the few counters that must be shared.

Worked example: 10,000 waits of 0.1 s each

Think of 10,000 network calls that each wait 100 ms for a reply. The waiting is the whole job, so the question is how cheaply you can hold 10,000 waits open at once.

The code: coroutines and futures

import asyncio, time
from concurrent.futures import ThreadPoolExecutor

async def many_waits(n):            # one thread, n coroutines
    await asyncio.gather(*(asyncio.sleep(0.1) for _ in range(n)))

def fetch(i):
    time.sleep(0.1)                 # stands in for a network call
    return i * i

def pool_demo():                    # a future = a handle to a result
    with ThreadPoolExecutor(max_workers=8) as pool:
        futs = [pool.submit(fetch, i) for i in range(16)]
        return sum(f.result() for f in futs)   # blocks until done

# 10,000 asyncio.sleep(0.1): 0.30 s
# 16 x fetch on 8 threads: 0.22 s, sum = 1240

One run of code/modern-concurrency.py under python3 3.10 while the machine was busy (the series best is 0.25 s). 16 jobs on 8 workers is 2 rounds of 0.1 s = 0.2 s at best; the sum is 0² + 1² + … + 15² = 1,240.

Each await is a point where the coroutine hands control back to the event loop, which runs whichever other coroutine is ready. Nothing preempts it in between, so code between two awaits can't be interleaved with other tasks on that loop. A future is a placeholder filled in later: submit returns at once, and result() blocks until the worker has finished.

Lock-free: compare-and-swap with a retry loop

CAS is one atomic instruction: "if the value is still old, set it to new, and tell me whether you did". A lock-free counter reads, computes, then CASes; if another thread got there first, the CAS fails and it simply tries again. Nobody ever waits holding a lock.

Interleaving is illustrative. Compare the locks card: there the second write silently overwrote the first; here the stale write is refused and redone, so both increments count.

def cas(cell, expected, new):
    with _hw:                       # one indivisible step in hardware
        if cell[0] != expected:
            return False
        cell[0] = new
        return True

def add_one(cell):
    retries = 0
    while True:
        old = cell[0]               # read
        time.sleep(0)               # let another thread get in
        if cas(cell, old, old + 1):  # only if unchanged
            return retries
        retries += 1                # someone beat us: try again

# 4 threads x 10,000 add_one:
# CAS counter: 40,000 of 40,000, 3,385 retries

Python exposes no compare-and-swap, so cas() uses a small lock (_hw) to stand in for the instruction's atomicity. The retry loop is the real technique; the retry count changes every run. In hardware it's LOCK CMPXCHG on x86 and a CAS or load-exclusive/store-exclusive pair on ARM64 such as the M3.

Why asyncio beats the alternatives for 10,000 waits

✗ A serial loop

Correct and simple, but the waits add up: 10,000 × 0.1 s = 1,000 s.

✗ A thread per wait

Each thread is a kernel object with its own stack. On this Mac the 6,144-per-process limit stopped it before 10,000.

✗ A process per wait

Worse still: a spawned process costs 72 ms to start and join (measured), so 10,000 of them one after another is 720 s of startup alone.

✓ asyncio tasks

A task is a small heap object, not a kernel thread: about 1.6 KB each, all 10,000 done in 0.25 s on one thread.

So which one do I pick?

  • Many waits (sockets, HTTP): asyncio, if the libraries you call are async. A blocking call inside a coroutine freezes the whole loop.
  • A few dozen blocking calls: a ThreadPoolExecutor. Threads are fine at this scale and need no async rewrite.
  • CPU-bound Python: ProcessPoolExecutor today (3.8× on the M3), or threads on a free-threaded 3.14t build, which then need the same locks C code would.
  • State owned by one worker: a queue in front of it (channel or actor style) instead of a lock around it.

Lock-free isn't automatically faster. Under heavy contention CAS loops burn CPU on retries, and correct lock-free structures beyond a counter are hard (ABA, memory reclamation). A plain Lock costs 58 ns uncontended (measured) and is the right default. None of these constructs removes races by itself: a read, then an await, then a write still races between tasks.
