Monitors and condition variables

Also called a condvar, a guarded block, or wait/notify; Python's threading.Condition, POSIX's pthread_cond_t. The source guide's Monitors heading is empty, so this card follows OSTEP chapter 30 and a Python bounded buffer of capacity 2 run on an Apple M3.

Prime · 2 minutes before you read

The problem: Often a thread must wait not for a lock but for the shared state to change: the buffer is no longer full, all workers have arrived. Spinning on the state burns a core and holds the GIL the other thread needs; polling with sleep trades CPU for latency by hand; semaphores fit only when the condition is a count.

Where it fits: Last Synchronization card. It combines the lock (locks, mutexes) with a place to sleep until a predicate holds, the general tool that semaphores approximate with counters. queue.Queue is one, ready-made.

In one breath

A monitor is a lock plus the shared state it guards plus one or more condition variables. A thread holding the lock that finds the state not ready (buffer full, buffer empty) calls wait(), which releases the lock and sleeps in one step. Whoever changes the state calls notify() to wake a waiter, which must take the lock back and check again before going on.

The code

import collections, threading
CAP = 2
lock = threading.Lock()
not_full = threading.Condition(lock)    # two conditions,
not_empty = threading.Condition(lock)   # one shared lock
buf = collections.deque()

def put(x):
    with lock:
        while len(buf) == CAP:          # while, not if (Mesa)
            not_full.wait()             # releases lock, sleeps
        buf.append(x)
        not_empty.notify()              # a hint, not a handoff

def get():
    with lock:
        while not buf:
            not_empty.wait()
        x = buf.popleft()
        not_full.notify()
        return x

Why while, not if: Mesa vs Hoare

✗ if not buf: wait()

WhoDoesbuf

IndexError: buffer empty. C1 trusted a check it made before it slept.

✓ while not buf: wait()

WhoDoesbuf
C1empty: wait()[ ]
main · C2put 1, notify · take 1[ ]
C1wakes, empty: waits again[ ]
C1main puts 2; C1 gets 2[ ]

C1 got 2. The loop re-checks the condition every time it wakes.

if:    ['C2 got 1', 'C1 IndexError: buffer empty']
while: ['C2 got 1', 'C1 woke, empty: waits again', 'C1 got 2']

This is Mesa semantics (Lampson & Redell, 1980), which Python, POSIX and Java all use: notify() only makes a sleeper runnable, and the notifier keeps the lock, so anyone can change the state before the sleeper runs. Under Hoare semantics (Hoare, 1974) the notifier hands the lock straight to the sleeper, the condition is guaranteed on wake-up and if would be enough, but it is harder to build and few real systems use it (OSTEP 30). The loop also covers spurious wake-ups, which POSIX permits. Python's cv.wait_for(pred) is this loop, written for you.

In the demo, "C2" is the main thread taking the item inside the same locked block as the notify, so the steal happens on every run; with real threads it happens only sometimes.

A ready-made monitor ships in the standard library: the demo's last line prints True for q.not_full._lock is q.mutex is q.not_empty._lock, on a queue.Queue(maxsize=2). Most people meet the word through Java, where every object is a monitor: synchronized is the lock and wait/notify act on the object's single condition.

Why it beats the alternatives

✗ Spin on the state

while not buf: pass checked 671,169 times and burned 0.069 s of CPU during a 0.1 s wait, and it holds the GIL the producer needs (one run on the author's M3).

✗ Poll with sleep(0.001)

Only 70 checks in the same 0.1 s, but each wake-up can be up to 1 ms late, and you choose between CPU and latency by hand (same run).

✗ Semaphores only

Two counting semaphores plus a mutex also build a bounded buffer, but take the mutex before waiting for a free slot and it deadlocks (OSTEP 31.4). Conditions that aren't counts don't fit.

✓ Monitor + condition variables

Sleepers use no CPU and wake once per notify. The condition can be any test you can write while holding the lock.

Should you write one by hand?

Usually not in Python. For hand-offs between threads use queue.Queue, which is exactly the monitor above; for one-shot "it's ready" signals use threading.Event; in async code use asyncio.Queue. Reach for Condition when the thing you wait for isn't "an item arrived", like "at least 3 slots free" or "all workers reached this point".

When you do, the rules are: hold the lock around both the check and wait() (Python raises RuntimeError otherwise), loop instead of if, and give each kind of waiter its own condition or use notify_all. With one shared condition and notify(), a consumer can wake another consumer instead of the producer, and every thread ends up asleep (OSTEP 30.2).

Understand and remember

  • A thread must wait for the state, not the lock → it checks under the lock and, if not ready, wait() releases the lock and sleeps atomically → others can get in and change the state → no busy CPU (vs 671,169 spin checks in 0.1 s)
  • Mesa: notify() only makes a sleeper runnable, and the notifier keeps the lock → anyone can change the state before the sleeper runs → the sleeper's earlier check is stale → re-check in a while (the if version raised IndexError)
  • Different waiters wait for different predicates → give each its own condition (not_full, not_empty) or use notify_all → otherwise a consumer can wake another consumer and everyone sleeps
  • Slow consumer (50 ms per item), capacity 2 → the buffer fills → the producer waits once per item beyond capacity → 3 waits for 5 items
  • detail that matters Two Conditions can share one Lock (Condition(lock)) → both predicates are checked under the same mutual exclusion → this is exactly how queue.Queue is built (one mutex, three conditions)

Reference only

  • Hoare 1974 and Lampson & Redell 1980 as the sources of the two semantics
  • cv.wait_for(pred), wait(timeout) returning False
  • Java's synchronized/wait/notify as the origin of the term
  • q.not_full._lock is q.mutex (a CPython internal)

4 · Compare against what you already know

vs Semaphores: Semaphore P vs Condition wait: both put a thread to sleep until something changes. What does each remember when no one is waiting, and how does that change what a missed signal costs?

Check
  • a semaphore remembers: a V with no sleeper raises the count, so a later P goes straight through
  • a condition remembers nothing: a notify with no waiter is lost
  • that's why a waiter must check the predicate before waiting, under the lock, and loop; the state, not the notify, is the source of truth

vs What triggers a context switch: A thread in wait() vs a thread spinning on the state: how does each show up in the voluntary and involuntary switch counters, and why?

Check
  • wait() blocks in the kernel, a voluntary switch per sleep, and uses no CPU while asleep
  • a spinner never blocks, so no voluntary switch; it burns its slice and is preempted: involuntary switches
  • blocking is the cheap way to wait; busy-waiting just converts waiting into preemptions

Why this step?

5 · Predict commit to an answer before revealing

Same log as the card (producer puts 1–5, consumer takes one every 50 ms), but capacity 3 instead of 2. How many times does the producer wait? What about capacity 5? Commit before revealing.

Reveal

Capacity 3: 2 waits. The producer fills the buffer without waiting, then waits once before each remaining item: 5 − 3 = 2. Capacity 5: 0 waits, since all five fit. That matches the card's capacity 2: 5 − 2 = 3 waits. It holds because the consumer is much slower than the producer; with a fast consumer the consumer would do the waiting instead.

6 · Apply use the model, don't restate it

Build a one-shot barrier with a Condition: arrive() increments a count under the lock, and every caller waits until the count reaches N, then all proceed. Run it with N = 4 threads that sleep 0, 0.1, 0.2 and 0.3 s before arriving, and log when each passes. Then break it twice: use if instead of while and wake with notify() instead of notify_all(), and describe what each change breaks or only risks.

Done when: All four pass at about 0.3 s in the correct version. The notify() version leaves at least two threads asleep forever (use wait(timeout=1) to see it). The if version usually still works here; you can say why it is unsafe anyway, and why notify_all is right here: every waiter is waiting for the same predicate.

Hint

The predicate is count >= N. Only the last arriver makes it true, so only it needs to notify, and it must wake everyone. threading.Barrier is the ready-made version; compare yours with it.
