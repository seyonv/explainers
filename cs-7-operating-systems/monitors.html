Monitors and condition variables

Also called a condvar, a guarded block, or wait/notify; Python's threading.Condition, POSIX's pthread_cond_t. The cheat-sheet's Monitors heading is empty, so this card follows OSTEP chapter 30 and a Python bounded buffer of capacity 2 run on an Apple M3.

In one breath

A monitor is a lock plus the shared state it guards plus one or more condition variables. A thread holding the lock that finds the state not ready (buffer full, buffer empty) calls wait(), which releases the lock and sleeps in one step. Whoever changes the state calls notify() to wake a waiter, which must take the lock back and check again before going on.

The picture: one lock, two places to sleep

Snapshot from the run below, just after step 4: P slept in not_full when buf held [1, 2], C took 1 (buf is now [2]) and notified, so P now waits only for the lock. wait() releases the lock as it sleeps, so C could get in.

The code

import collections, threading
CAP = 2
lock = threading.Lock()
not_full = threading.Condition(lock)    # two conditions,
not_empty = threading.Condition(lock)   # one shared lock
buf = collections.deque()

def put(x):
    with lock:
        while len(buf) == CAP:          # while, not if (Mesa)
            not_full.wait()             # releases lock, sleeps
        buf.append(x)
        not_empty.notify()              # a hint, not a handoff

def get():
    with lock:
        while not buf:
            not_empty.wait()
        x = buf.popleft()
        not_full.notify()
        return x

✓ while not buf: wait()

WhoDoesbuf

C1main puts 2; C1 gets 2[ ]

C1 got 2. The loop re-checks the condition every time it wakes.

if:    ['C2 got 1', 'C1 IndexError: buffer empty']
while: ['C2 got 1', 'C1 woke, empty: waits again', 'C1 got 2']

This is Mesa semantics (Lampson & Redell, 1980), which Python, POSIX and Java all use: notify() only makes a sleeper runnable, and the notifier keeps the lock, so anyone can change the state before the sleeper runs. Under Hoare semantics (Hoare, 1974) the notifier hands the lock straight to the sleeper, the condition is guaranteed on wake-up and if would be enough, but it is harder to build and few real systems use it (OSTEP 30). The loop also covers spurious wake-ups, which POSIX permits. Python's cv.wait_for(pred) is this loop, written for you.

In the demo, "C2" is the main thread taking the item inside the same locked block as the notify, so the steal happens on every run; with real threads it happens only sometimes.

A ready-made monitor ships in the standard library: the demo's last line prints True for q.not_full._lock is q.mutex is q.not_empty._lock, on a queue.Queue(maxsize=2). Most people meet the word through Java, where every object is a monitor: synchronized is the lock and wait/notify act on the object's single condition.

Why it beats the alternatives

✗ Spin on the state

while not buf: pass checked 671,169 times and burned 0.069 s of CPU during a 0.1 s wait, and it holds the GIL the producer needs (one run on the author's M3).

✗ Poll with sleep(0.001)

Only 70 checks in the same 0.1 s, but each wake-up can be up to 1 ms late, and you choose between CPU and latency by hand (same run).

✗ Semaphores only

Two counting semaphores plus a mutex also build a bounded buffer, but take the mutex before waiting for a free slot and it deadlocks (OSTEP 31.4). Conditions that aren't counts don't fit.

✓ Monitor + condition variables

Sleepers use no CPU and wake once per notify. The condition can be any test you can write while holding the lock.

Should you write one by hand?

Usually not in Python. For hand-offs between threads use queue.Queue, which is exactly the monitor above; for one-shot "it's ready" signals use threading.Event; in async code use asyncio.Queue. Reach for Condition when the thing you wait for isn't "an item arrived", like "at least 3 slots free" or "all workers reached this point".

When you do, the rules are: hold the lock around both the check and wait() (Python raises RuntimeError otherwise), loop instead of if, and give each kind of waiter its own condition or use notify_all. With one shared condition and notify(), a consumer can wake another consumer instead of the producer, and every thread ends up asleep (OSTEP 30.2).
