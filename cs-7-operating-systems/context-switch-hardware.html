The hardware underneath

Also called privilege modes, protection rings (x86) or exception levels (Arm: EL0 for apps, EL1 for the kernel), plus traps, the vector table, the TLB and its ASIDs. The source guide's Underlying Hardware heading is empty, so this card follows OSTEP chapters 6 and 19, Arm's architecture guides, and one light run on the author's Apple M3.

Prime · 2 minutes before you read

The problem: A context switch is kernel software, but software alone can't stop a user program from rewriting page tables, can't interrupt a loop that never calls the kernel, and can't keep address translations from different processes apart without throwing them away. The hardware has to supply those guarantees, and what it can't hide (cold caches) shows up as cost.

Where it fits: Last Context-switching card. It explains the pieces the two previous cards assumed: the trap in step ①, the timer behind involuntary switches, the page-table register from the process switch, and why the next task starts cold.

In one breath

A context switch is software, but it leans on four pieces of hardware: a mode bit that stops user code from touching the machine, a timer and a trap instruction that force the CPU into the kernel at a fixed address, a register that swaps the page table in one write, and a TLB that tags translations by address space so they needn't be thrown away. What the hardware can't hide is that caches and the TLB start the new process cold.

One switch, process A to process B, on Arm

Two threads of the same process share one page table, so step 3 is skipped and the TLB stays useful. Register names from Arm's exception-model guide; the save/restore order follows OSTEP ch. 6.

One noisy run of code/context-switch-hardware.py on the author's M3 (Python 3.10, machine busy with other jobs). The fault count comes from getrusage and was exact: one per 16 KB page. The 2.7 µs per fault also covers the kernel zero-filling each page, so it's more than the trap alone.

What this does and doesn't show: 64 MB is 4× the 16 MB L2, so even the warm pass streams from DRAM. Most of the gap is the 4,096 traps into the kernel and new page-table and TLB entries, not the cache. A process switched back in after a long absence pays the cache part too: its lines have been evicted by whoever ran meanwhile (our inference; not isolated in this run).

The code

import os, resource, time
import numpy as np

def faults():
    return resource.getrusage(resource.RUSAGE_SELF).ru_minflt

def timed_sum(a):
    f0, t0 = faults(), time.perf_counter()
    a.sum()
    return time.perf_counter() - t0, faults() - f0

a = np.zeros((64 << 20) // 8)   # 64 MB, mapped lazily
print(timed_sum(a))             # cold: every page faults in
print(timed_sum(a))             # warm: pages mapped

def f(): return 1
for _ in range(100_000): f()           # stays in EL0
for _ in range(100_000): os.getppid()  # svc into EL1

Why this design beats the alternatives

✗ Trust processes to yield

Cooperative switching with no timer: a process stuck in an infinite loop never gives the CPU back, and the only fix is a reboot (OSTEP 6.3).

✗ Run everything privileged

No mode bit means any process could rewrite the vector table or its own page table and take over the machine. Isolation would have to be checked in software on every instruction.

✗ Flush the TLB each switch

Correct and simple, but every process restarts with an empty TLB and misses on its first touch of each page, every time it's scheduled (OSTEP 19.5).

✓ Modes + timer + tagged TLB

User code runs directly at full speed, the timer guarantees the kernel gets control back, and ASIDs let A's and B's translations sit in the TLB side by side. OSTEP calls this limited direct execution.

Is every trip into the kernel a context switch?

No. os.getppid() enters EL1 and comes straight back to the same process: that's a mode switch, about 320 ns extra here. A context switch also changes which thread or process runs, so it adds the scheduler, a register save/restore and, between processes, a page-table swap. The measured pipe ping-pong round trip between two processes is 13.6 µs (Event between two threads: 8.2 µs); both include Python overhead, so they are upper bounds. For scale, lmbench in 1996 saw about 4 µs per syscall and 6 µs per switch on a 200 MHz CPU (OSTEP 6).

The direct cost is rarely the whole story: the cold caches and TLB after a switch can cost more than the switch itself. When switches dominate, avoid them: asyncio and green threads switch in user mode with no trap, and a lock held for nanoseconds is better spun on than slept on. On Linux, pinning a busy process to one core (CPU affinity) keeps its caches warm.

Understand and remember

  • A mode bit checked on every privileged instruction → user code (EL0) can't touch page tables, interrupts or the vector table → only the kernel (EL1) can → isolation is enforced by hardware at full speed, not checked in software
  • Timer interrupts and traps jump to fixed offsets in the kernel's vector table → the kernel always regains control, whatever user code does → limited direct execution: user code runs directly, but can't keep the core
  • Each TLB entry is tagged with an address-space ID → only entries matching the current ASID are used → a process switch doesn't need a flush → A's translations survive B's turn (8 or 16 bits: 256 or 65,536 IDs, recycled)
  • First touch of each lazily mapped page traps (page fault) → the kernel maps and zero-fills it → 64 MB ÷ 16 KB = 4,096 faults → cold 15.1 ms vs warm 4.1 ms (≈ 2.7 µs per fault) → a new or long-absent process pays this plus cold caches
  • detail that matters 64 MB is 4× the 16 MB L2 → even the warm pass streams from DRAM (≈ 16.4 GB/s) → so the 3.7× gap here is mostly page faults and TLB set-up, not cache misses → the cache part of a switch's indirect cost was not isolated by this run

Reference only

  • register names: VBAR_EL1, TTBR0_EL1, svc, TLBI ASIDE1IS
  • M3 cache sizes: 128 KB L1d, 16 MB L2 (sysctl)
  • the 422 ns vs 100 ns syscall-vs-call timings
  • lmbench 1996's 4 µs syscall and 6 µs switch

3 · Retrieve from memory, card closed
  1. concept Explain why "limited direct execution" needs both a privilege mode and a timer. What would go wrong with only one of them?
    Check
    • direct execution: user code runs on the CPU at full speed, not interpreted
    • mode bit alone: user code can't seize the machine, but a loop that never traps keeps the core forever
    • timer alone: the kernel regains control, but user code could have rewritten the vector table or its page table first
  2. mechanism Walk through what the hardware does when process A, at EL0, touches a page of a fresh numpy array for the first time.
    Check
    • the address translation misses: no valid page-table entry
    • the CPU raises a synchronous exception, switches to EL1 and jumps to the vector table's entry
    • the kernel allocates a physical page, zero-fills it, installs the mapping and returns
    • the instruction is retried and succeeds; the TLB now caches that translation under A's ASID
  3. tradeoff An OS design choice: flush the whole TLB on every process switch, or tag entries with ASIDs. Give the cost of each and when the ASID approach still has to flush.
    Check
    • flush: simple and correct, but every process restarts with an empty TLB and misses on each page's first touch every time it's scheduled
    • ASIDs: translations survive switches, at the cost of tag bits and ID management
    • with only 256 (8-bit) or 65,536 (16-bit) IDs, the OS must recycle an ID, and flush its old entries, when more processes need them

4 · Compare against what you already know

vs Processes: Copy-on-write in the processes card and the cold-pass page faults here both trap on a memory access. What is the same, and what does the kernel do differently in each?

Check
  • both are page faults: the access hits a page that isn't mapped writable, so the CPU traps to EL1
  • COW: the page exists but is shared read-only; the kernel copies it for the writer
  • cold pass: the page was never mapped; the kernel allocates and zero-fills a new one
  • both are lazy: work is done only for pages actually touched

vs How a context switch works: The how-card says the bill for a switch comes after it. Using this card's parts, list exactly what the next process finds cold, and which of those an ASID keeps warm.

Check
  • caches: filled with the previous task's lines; never saved, simply evicted and refilled
  • TLB: with ASIDs, the returning process's own old entries may still be there; without them, empty
  • so ASIDs save the translation refill, but nothing saves the cache refill; pinning and fewer switches reduce it

Why this step?

5 · Predict commit to an answer before revealing

Repeat the cold/warm run with a 128 MB array on the M3, and imagine the same 64 MB run on a machine with 4 KB pages. How many page faults does each cold pass take, and if each fault cost the same 2.7 µs, how much extra time? Commit before revealing.

Reveal

128 MB ÷ 16 KB = 8,192 faults, about 22 ms extra. 64 MB ÷ 4 KB = 16,384 faults, about 44 ms extra. The 4 KB estimate is shaky in both directions: each small page needs less zero-filling than a 16 KB one, but there are four times as many traps. Bigger pages mean fewer faults and fewer TLB entries, which is one reason the M3 uses 16 KB.

6 · Apply use the model, don't restate it

Extend code/context-switch-hardware.py: run the cold/warm sum for 16, 64 and 128 MB, and record the time and page faults of each pass. Then add a third pass after allocating and touching a different 256 MB array in between (b = np.ones(...)), and see whether the original array's pass slows again. Keep total run time light.

Done when: Cold-pass faults are exactly 1,024, 4,096 and 8,192 (size ÷ 16,384), warm passes show 0 faults, and you can say whether the post-256 MB pass got slower and why that is (or isn't) cache eviction, given that 16 MB of L2 can't hold any of these arrays.

Hint

Fault counts are exact from ru_minflt; times are noisy, so run each pass 3 times and take the best. Since all three sizes are at least as big as the L2, warm passes already stream from DRAM, so don't expect the interfering array to change much.
