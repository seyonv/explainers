Locks and race conditions

Also called a data race, a lost update, or a read-modify-write race; the fix is mutual exclusion around a critical section. The source guide's Locks heading is empty, so this card follows OSTEP chapters 26 and 28 and measured Python runs on an Apple M3.

Prime · 2 minutes before you read

The problem: Threads share the heap, so two of them can read the same counter, both add 1 and both write back: one increment vanishes with no error. The bug depends on timing, so it appears only sometimes and hides from tests. Something has to make the read-to-write stretch run one thread at a time.

Where it fits: First card of the Synchronization part. It takes the shared heap from the threads card and shows its price; mutexes, semaphores and monitors (next) are all refinements of the lock introduced here.

In one breath

A race condition is a bug whose result depends on how threads happen to interleave. The classic one: two threads both read a counter, both add 1 and both write back, so one increment silently disappears. A lock makes the read-to-write stretch run one thread at a time.

Worked example: two threads, one counter, c starts at 0

✗ No lock

Thread 1Thread 2c
v = c # 00
switched outv = c # 00
c = v + 11
c = v + 11

c = 1, but 2 increments ran. Thread 2 wrote a value computed from a stale read, overwriting thread 1's.

✓ With a lock

Thread 1Thread 2c
acquire; v = cacquire: waits0
c = v + 1; releasewaits1
gets lock; v = c # 11
c = v + 1; release2

c = 2. The read and write of each thread can no longer be split by the other thread.

Interleaving is illustrative: the scheduler picks the order, so the bug shows up only sometimes. That's what makes races hard to test for.

The code

import threading, time
N, T = 100_000, 4
lock = threading.Lock()

def unsafe(c):
    for _ in range(N):
        v = c["n"]          # read
        time.sleep(0)       # yield: another thread may run here
        c["n"] = v + 1      # write back, maybe over a newer value

def safe(c):
    for _ in range(N):
        with lock:          # one thread at a time in this block
            v = c["n"]
            time.sleep(0)
            c["n"] = v + 1

def run(body):
    c = {"n": 0}
    ts = [threading.Thread(target=body, args=(c,)) for _ in range(T)]
    for t in ts: t.start()
    for t in ts: t.join()
    return c["n"]

# unsafe 100,009 of 400,000  lost 299,991 (75%)
# safe   400,000 of 400,000  lost 0 (0%)

Output from one run of code/locks.py under python3 3.10 on the author's M3; the unsafe count changes every run.

Why plain += survived with the GIL, and why that's luck

c["n"] += 1 is not one step. It compiles to eight bytecodes, with the read (BINARY_SUBSCR) and the write (STORE_SUBSCR) three steps apart:

LOAD_FAST c · LOAD_CONST 'n' · DUP_TOP_TWO · BINARY_SUBSCR
LOAD_CONST 1 · INPLACE_ADD · ROT_THREE · STORE_SUBSCR

The GIL lets only one thread run bytecode at a time, and CPython 3.10+ hands it to another thread only at certain points, mainly loop back-edges and the start of a Python function call. None of these eight instructions is such a point, so each += ran whole. sleep(0) releases the GIL on purpose, which is why the first row lost 75%. Put a Python function call between the read and the write and losses return even with the GIL: 263,642 of 800,000 kept (one run on the author's M3, switch interval 1 µs). The free-threaded build has no GIL at all, so threads really run at the same time on different cores and lose 72.9%.

The hand-off points are our reading of CPython's eval loop, backed by that run. They're an implementation detail, not a language guarantee.

Why a lock beats the alternatives

✗ Trust the GIL

Plain += lost nothing on 3.10 and 3.14, then lost 72.9% on free-threaded 3.14t. The GIL never protected a read and write split by a call or I/O.

✗ A plain busy flag

while busy: pass then busy = True. The check and the set are two steps, so two threads can both see False and both enter. Same race, moved (OSTEP 28.6).

✗ Turn off interrupts

Early single-CPU kernels did this so nothing could switch threads. It needs kernel privilege and does nothing about a thread running on another core (OSTEP 28.5).

✓ A real lock

Built on an atomic instruction, so acquiring it can't itself race. Waiters sleep instead of spinning. It kept all 400,000 increments.

Should every shared variable get a lock?

No. You need one only when threads share mutable state and at least one of them writes. Often it's simpler to not share: give each thread its own counter and add them at the end, hand work through queue.Queue (it locks internally), use separate processes, or use asyncio, where one thread switches only at await. A read, then an await, then a write still races, though.

Locks aren't free either. Uncontended they cost 58 ns (87 ns with with lock:, measured on the M3). Under contention they make the critical section run one thread at a time, and taking two locks in different orders can deadlock.

Understand and remember

  • Read-modify-write is several steps → a switch between read and write lets another thread write in between → the late writer overwrites with a stale value → lost update (100,096 of 400,000 kept)
  • A lock makes the read-to-write stretch a critical section → only one thread inside at a time → the interleaving can't split it → all 400,000 kept
  • The GIL hands off only at certain bytecode points (loop back-edges, function calls) → the eight bytecodes of += ran whole → no losses on 3.10 → but a call or I/O between read and write, or no GIL at all (3.14t: 72.9% lost), brings the race back
  • A lock must itself be taken atomically → built on a hardware instruction like compare-and-swap → a software flag's check-then-set is two steps and races exactly like the counter
  • detail that matters Uncontended acquire+release is 58 ns → cheap enough to use freely → the real cost is contention, which serialises the critical section (the mutexes card)

4 · Compare against what you already know

vs Modern concurrency constructs: A lock vs a compare-and-swap retry loop for the same counter: what happens to the stale write in each, which design choice causes the difference, and how does each fail under heavy contention?

Check
  • lock: nobody else reads until the holder writes, so no stale value exists
  • CAS: the stale write is attempted, detected (the value changed) and redone
  • lock waiters sleep; CAS losers spin on retries (3,385 retries for 40,000 increments in the demo)
  • locks fail by contention and deadlock; CAS fails by burning CPU and by ABA on pointers

vs Idempotency and retries: A lost update here and a double charge there both come from two actors acting on stale knowledge. What does each course use to make the second attempt harmless?

Check
  • here: mutual exclusion, so the second thread reads only after the first has written
  • there: an idempotency key, so a repeated request is recognised and not applied twice
  • a lock needs shared memory and a cheap atomic; across machines you can't lock cheaply, so you make repeats safe instead

5 · Predict commit to an answer before revealing

In asyncio, one coroutine does v = c["n"], then await asyncio.sleep(0), then c["n"] = v + 1, and 4 tasks run it 10⁵ times each. There is only one thread and no GIL hand-off between tasks. Do updates get lost? Commit before revealing.

Reveal

Yes, and for the same reason as the sleep(0) thread version: the await is a switch point between the read and the write, so another task reads the same value first. The card says so directly: a read, then an await, then a write still races. Remove the await between them and no task can interleave, so nothing is lost without a lock.
