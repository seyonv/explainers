Checkpoint 2: what a switch really costs

Ties together processes, threads and the GIL, how a context switch works, what triggers a context switch and the hardware underneath: how the kernel takes a core from one task and gives it to another, what makes it do so, and what each step costs before and after.

How to use this page. Close the five cards. Answer each question in writing, in full sentences, before opening its Check. A wrong or shaky answer isn't a failure; it tells you exactly which section to reopen. The questions are mixed on purpose, so you have to work out which idea applies before you can answer.

1 · Mixed retrieval

  1. which concept?A single-threaded pure-Python job shows almost no voluntary switches but thousands of involuntary ones, and the count jumps whenever a batch job runs on the same machine. Which idea explains it, and is the GIL's 5 ms switch interval involved?
    Check
    • involuntary switches are preemptions: the timer interrupt or a higher-priority wakeup takes the core, whatever the code does
    • their count is set by competition for cores, not by your code (fib(30): 25 on the series run, 1,543 at load average 81)
    • the GIL interval is not involved: one thread never hands the GIL to anyone, and the kernel doesn't know the GIL exists

    Missed it? Reopen what triggers a context switch, the measured table and "Is CPython's 5 ms switch interval one of these?".

  2. Walk through the difference between switching from thread A to thread A2 of the same process, and from A2 to process B. What does the kernel do in the second case that it skips in the first, and what survives in the TLB each time?
    Check
    • both: trap, save the outgoing registers into its PCB and kernel stack, pick the next task, load its registers, return to its PC
    • A2 → B only: load B's page-table base, so the same virtual addresses map to B's memory
    • A → A2 keeps P1's translations valid; with ASIDs, P1's entries also survive B's turn, so a return to A needn't start from an empty TLB

    Missed it? Reopen how a context switch works, step ④ and the toy CPU, and the hardware, "TLB + ASID".

  3. which concept?Summing a freshly allocated 64 MB numpy array takes 15.1 ms; summing it again takes 4.1 ms. A colleague says "the cache warmed up". What is mostly going on instead, and what number backs it?
    Check
    • 64 MB is 4× the M3's 16 MB L2, so neither pass is served from cache; both stream from DRAM
    • the first pass takes a page fault on each 16 KB page: 64 MB ÷ 16 KB = 4,096 faults, exactly what getrusage counted
    • (15.1 − 4.1) ms ÷ 4,096 ≈ 2.7 µs per fault, which also includes zero-filling the page

    Missed it? Reopen the hardware underneath, "Measured: summing a fresh 64 MB array twice".

  4. A pipe round trip between two processes takes 13.6 µs. Why is 13.6 ÷ 2 = 6.8 µs only a ceiling on one switch, and where does the real extra cost of switching show up?
    Check
    • a round trip includes at least 2 switches, 4 system calls and Python's own work, so half of it overstates one switch
    • the two sides may even run on different cores, where the "switch" is a wake-up elsewhere
    • the real extra cost comes after: cold caches and TLB (Li et al.: 4.1 → 22.4 µs as working sets grow, up to 112 µs)

    Missed it? Reopen how a context switch works, "Measured: what a switch costs, as an upper bound" and the note below it.

  5. which concept?A preforking server loads a 2 GB read-only table of Python objects, then forks 8 workers that only read it. Resident memory climbs toward 18 GB over an hour. Which mechanism was supposed to prevent this, and why didn't it?
    Check
    • copy-on-write: after fork, pages stay shared until someone writes to them
    • reading a Python object updates its reference count, which is a write, so each worker gradually copies the pages it touches
    • the card points to gc.freeze; data that is truly never written (raw buffers) stays shared

    Missed it? Reopen processes, the copy-on-write row of "The words".

  6. Is os.getppid() a context switch? Say what the hardware does for it and what it costs, compared with a Python function call.
    Check
    • no: svc traps from EL0 to EL1 and returns to the same process: a mode switch
    • no scheduler, no register swap to another task, no page-table change
    • 422 ns per call vs 100 ns for a Python call: about 320 ns extra per trap round trip

    Missed it? Reopen the hardware underneath, "Is every trip into the kernel a context switch?".

  7. fib(30) never makes a system call. Explain, piece by piece, how the kernel still takes the core away from it 25 times, and why that must be hardware's job.
    Check
    • a hardware timer interrupts every few ms; the CPU switches to EL1 and jumps to the vector table's IRQ entry, which the kernel set at boot
    • the kernel's handler sees the slice used up (or a more urgent thread ready) and switches
    • it must be hardware: user code runs directly on the CPU, and the mode bit stops it from disabling interrupts or rewriting the vector table

    Missed it? Reopen what triggers a context switch, "Timer interrupt", and the hardware, the parts table.

  8. Starting a process costs 72 ms, but switching to an existing one costs microseconds. Where does the difference come from, and what does it imply for how you use processes?
    Check
    • starting (spawn) builds a new address space, loads a fresh interpreter and re-imports your module
    • switching only saves and loads registers (784 B on AArch64) and a page-table base: memory stays where it is
    • start processes once (a pool) and reuse them; pass work to them, don't create one per task

    Missed it? Reopen processes, "Measured: what a process costs", and how a switch works, "What the registers means".

3 · Project: put a price on every rung

What it reinforces: the start-up cost of a process (processes), thread vs process switches (threads, how a switch works), voluntary vs involuntary counts (what triggers a switch), and mode switches, page faults and cold starts (the hardware).

Build a cost ladder for your own machine, from a Python function call to a process start, then use it to budget a scheduler's time slice. Keep every run light (a few seconds of CPU).

  1. Measure the rungs. Reuse the code/ files: a Python call and os.getppid() (hardware), a thread Event ping-pong and a process pipe ping-pong (how), one multiprocessing.Process start + join, and the cold vs warm 64 MB sum with its fault count.
  2. Count the switches. Around each ping-pong, record ru_nvcsw and ru_nivcsw. Check that the parent blocks about once per round trip.
  3. Derive, don't just measure. Halve each round trip to get per-switch ceilings; divide the cold-minus-warm time by the fault count; compute how long copying the 784 B of AArch64 registers takes at your warm-pass bandwidth.
  4. Budget a time slice. For quanta of 1, 5 and 10 ms, compute the share of CPU lost to switching if each switch costs your process-switch ceiling, and if it costs Li et al.'s 22.4 µs large-working-set total.
Done when: you have one table, sorted by cost, with every rung labelled "measured" or "computed", and a three-row budget table. You can point to the rung where the kernel is first involved and the rung where memory stops staying in place.
Check: the course's numbers (yours will differ; the order shouldn't)
  • Rungs from the cards: register copy ≈ 48 ns (784 B ÷ 16.4 GB/s, computed); Python call 100 ns; getppid() 422 ns; page fault ≈ 2.7 µs; thread switch ≤ 4.1 µs; process switch ≤ 6.8 µs; process start 72 ms.
  • The kernel first appears at getppid() (a mode switch); memory stops staying in place only at the process start, which builds a new address space.
  • Budget at 6.8 µs: 0.68% (1 ms), 0.14% (5 ms), 0.07% (10 ms). At 22.4 µs: 2.24%, 0.45%, 0.22%. OSTEP's 1 ms switch on a 10 ms slice would be 1 ÷ 11 ≈ 9%.
  • The register copy is under 1% of the switch ceiling, and a page fault costs about as much as a thread switch: the direct copy is never the expensive part.
