Processes

Also called a task or a running program. It is the unit the OS isolates: its own memory, its own open files, its own pid. The source guide's Processes heading is empty, so this card follows OSTEP chapters 4, 5 and 13, the Python docs, and measured runs on an Apple M3.

In one breath

A program is a file on disk; a process is that program running. The kernel gives each process a private address space (it seems to own all of memory) and keeps a record of it, the process control block (PCB), so it can stop the process, run others, and resume it exactly where it was.

fork, then exec, then wait: the trace

Unix makes a process in two steps. fork() clones the caller; exec() swaps the clone's program for a new one. The parent then waits to collect the exit code.

import os, sys

def fork_and_wait():
    x = 1
    sys.stdout.flush()      # else the child inherits unprinted text
    pid = os.fork()         # one call, two returns
    if pid == 0:            # child: a copy of the parent
        x += 100            # page copied on this write (COW)
        print(f"child  pid={os.getpid()} parent={os.getppid()}"
              f" x={x}", flush=True)
        os._exit(7)         # exits now: no cleanup, no flush
    _, status = os.waitpid(pid, 0)      # block until it exits
    code = os.waitstatus_to_exitcode(status)
    print(f"parent pid={os.getpid()} child={pid} x={x}"
          f" exit={code}")

def fork_exec_wait():
    sys.stdout.flush()
    pid = os.fork()
    if pid == 0:            # same pid, brand-new program image
        os.execvp("echo", ["echo", "child is now echo"])
    _, status = os.waitpid(pid, 0)
    print(f"parent reaped {pid},"
          f" exit={os.waitstatus_to_exitcode(status)}")

Why processes beat the alternatives for CPU-bound Python

✗ Serial

One core does all the work: 0.121 s while three cores sit idle.

✗ Threads

They share one interpreter and its GIL on 3.10, so pure-Python work takes turns: 0.121 s, no gain at all.

✗ asyncio

One thread that switches only at await. Great for waiting on I/O; a CPU loop never awaits, so it can't overlap anything.

✓ Processes

Each has its own interpreter and GIL, so four really run on four cores: 0.032 s, 3.78×. A crash in one also can't corrupt the others' memory.

fork or spawn? And when not to use processes

multiprocessing can start workers three ways. fork clones the parent (fast, copy-on-write), but copies only the calling thread, so a lock held by some other thread at that moment stays locked forever in the child. spawn starts a fresh interpreter and re-imports your module (slower: the 72 ms above, and your code must sit under if __name__ == "__main__":). Python has defaulted to spawn on macOS since 3.8, because macOS system libraries may start threads; 3.12 warns when you fork a multi-threaded process, and 3.14 made forkserver the Linux default.

Processes are the wrong tool when tasks are tiny (72 ms of start-up, 13.6 µs per message), when workers need lots of shared mutable state (every argument is pickled and copied), or when the work is I/O-bound: there, threads or asyncio are cheaper, and free-threaded Python 3.14t lets threads use all cores too.
