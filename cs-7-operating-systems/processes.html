Processes

Also called a task or a running program. It is the unit the OS isolates: its own memory, its own open files, its own pid. The source guide's Processes heading is empty, so this card follows OSTEP chapters 4, 5 and 13, the Python docs, and measured runs on an Apple M3.

Prime · 2 minutes before you read

The problem: Several programs must share one machine without reading or corrupting each other's memory, and the OS must be able to stop any of them and resume it later exactly where it was. Without a unit that owns its memory and a record of where it stopped, neither isolation nor sharing the CPU is possible.

Where it fits: First card of the course, and the unit everything else is measured against. Threads (next) split a process into several lines of execution; the context-switch cards reuse this card's PCB.

In one breath

A program is a file on disk; a process is that program running. The kernel gives each process a private address space (it seems to own all of memory) and keeps a record of it, the process control block (PCB), so it can stop the process, run others, and resume it exactly where it was.

fork, then exec, then wait: the trace

import os, sys

def fork_and_wait():
    x = 1
    sys.stdout.flush()      # else the child inherits unprinted text
    pid = os.fork()         # one call, two returns
    if pid == 0:            # child: a copy of the parent
        x += 100            # page copied on this write (COW)
        print(f"child  pid={os.getpid()} parent={os.getppid()}"
              f" x={x}", flush=True)
        os._exit(7)         # exits now: no cleanup, no flush
    _, status = os.waitpid(pid, 0)      # block until it exits
    code = os.waitstatus_to_exitcode(status)
    print(f"parent pid={os.getpid()} child={pid} x={x}"
          f" exit={code}")

def fork_exec_wait():
    sys.stdout.flush()
    pid = os.fork()
    if pid == 0:            # same pid, brand-new program image
        os.execvp("echo", ["echo", "child is now echo"])
    _, status = os.waitpid(pid, 0)
    print(f"parent reaped {pid},"
          f" exit={os.waitstatus_to_exitcode(status)}")

# child  pid=97312 parent=97311 x=101
# parent pid=97311 child=97312 x=1 exit=7
# child is now echo
# parent reaped 97314, exit=0

Why processes beat the alternatives for CPU-bound Python

✗ Serial

One core does all the work: 0.121 s while three cores sit idle.

✗ Threads

They share one interpreter and its GIL on 3.10, so pure-Python work takes turns: 0.121 s, no gain at all.

✗ asyncio

One thread that switches only at await. Great for waiting on I/O; a CPU loop never awaits, so it can't overlap anything.

✓ Processes

Each has its own interpreter and GIL, so four really run on four cores: 0.032 s, 3.78×. A crash in one also can't corrupt the others' memory.

fork or spawn? And when not to use processes

multiprocessing can start workers three ways. fork clones the parent (fast, copy-on-write), but copies only the calling thread, so a lock held by some other thread at that moment stays locked forever in the child. spawn starts a fresh interpreter and re-imports your module (slower: the 72 ms above, and your code must sit under if __name__ == "__main__":). Python has defaulted to spawn on macOS since 3.8, because macOS system libraries may start threads; 3.12 warns when you fork a multi-threaded process, and 3.14 made forkserver the Linux default.

Processes are the wrong tool when tasks are tiny (72 ms of start-up, 13.6 µs per message), when workers need lots of shared mutable state (every argument is pickled and copied), or when the work is I/O-bound: there, threads or asyncio are cheaper, and free-threaded Python 3.14t lets threads use all cores too.

Understand and remember

  • Each process gets its own address space + a PCB → the kernel can stop it, run others and resume it exactly → processes are isolated: a crash or stray write can't corrupt another
  • fork clones the caller → pages shared read-only → the first write traps and copies just that page (copy-on-write) → fork is cheap until someone writes → but CPython's refcount updates are writes, so shared objects get copied anyway
  • Each process has its own interpreter and its own GIL → 4 processes really run on 4 cores → 0.121 s → 0.032 s (3.78×) → but a fresh spawn costs 72 ms (60% of the serial job), so pools are created once and reused
  • No shared heap → data crosses by IPC (pipe, shared memory, socket, signal) → every argument is pickled and copied → processes suit big CPU chunks, not chatty shared state (13.6 µs per pipe round trip)
  • detail that matters fork copies only the calling thread → a lock another thread held at that instant stays locked forever in the child → this is why macOS defaults to spawn (since 3.8) and 3.12 warns on forking a threaded process

3 · Retrieve from memory, card closed
  1. concept Explain why a process, and not a thread, is the unit the OS uses to isolate programs from each other.
    Check
    • each process has its own page table, so the same virtual address maps to different physical memory
    • one process can't name another's memory, so a crash or bad write stays inside it
    • threads of one process share the heap, so they get no such protection
  2. mechanism Walk through what happens, from the kernel's side, when the child in the trace runs x += 100 and then os._exit(7), until the parent's waitpid returns.
    Check
    • the write hits a page shared read-only since fork → trap → kernel copies that one page for the child
    • the child's x is 101, the parent's stays 1
    • on exit the child becomes a zombie: its PCB keeps the exit code 7
    • the parent's waitpid collects 7 and the PCB is freed (reaped)
  3. tradeoff A job has 4 CPU-bound chunks of about 0.03 s each and runs once per request. Using the card's numbers, is a fresh multiprocessing pool per request worth it, and what would you do instead?
    Check
    • serial: 0.121 s; a warm pool: 0.032 s
    • a fresh spawn costs 72 ms, so a new pool per request pays more in start-up than it saves in compute
    • create the pool once at start-up and reuse it, or run serially if requests are rare
  4. tradeoff Why is Python's default start method on macOS spawn, even though fork is faster?
    Check
    • fork copies only the calling thread
    • a lock held by another thread (including inside system libraries) stays locked forever in the child
    • spawn starts a clean interpreter: slower (72 ms, re-imports your module) but safe

5 · Predict commit to an answer before revealing

Before forking, the parent builds a 100 MB list of Python ints and never modifies it. The child only reads it (sums it). Does copy-on-write keep memory near 100 MB in total? Commit before revealing.

Reveal

Probably not. Reading a Python object bumps its reference count, which is a write to the page it lives on, so the child's reads trigger page copies across much of the list. The card calls this our reading and points to gc.freeze; COW saves memory for data the child truly never touches, like raw bytes in a numpy array or a bytes buffer, not for Python objects it iterates.
