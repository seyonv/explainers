What triggers a context switch

Also called voluntary vs involuntary switches, blocking vs preemption, or cooperative vs preemptive multitasking. The source guide's heading is empty, so this card follows OSTEP chapters 6 and 7 and a getrusage count on an Apple M3.

Prime · 2 minutes before you read

The problem: While a user thread runs, the kernel isn't running at all. So how does it ever get the core back to run someone else? If it relied on threads to hand the core over, one infinite loop would freeze the machine. There must be both a way for threads to give up the core and a way to take it from them.

Where it fits: Second Context-switching card. The last card showed how a switch works; this one shows what starts it. It links back to the threads card (the GIL's 5 ms interval is a different thing) and forward to scheduling, which decides who runs once the kernel has control.

In one breath

The kernel only gets the CPU back from a running thread in two ways. Either the thread asks for something it has to wait for (a read, a sleep, a lock), and the kernel parks it and runs someone else: a voluntary switch. Or a hardware timer interrupt, or a more urgent thread waking up, hands control to the kernel, which decides the thread has had enough: an involuntary switch, also called preemption.

Worked example: one core, two threads

① A traps into the kernel with a system call and can't continue, so it gives up the core. ② B never asked to stop; the timer interrupt ends its slice. When A's data arrives it becomes ready, but it still waits for the next scheduling decision (OSTEP ch. 6).

Measured: count them with getrusage

The kernel keeps both counters per process: ru_nvcsw (voluntary) and ru_nivcsw (involuntary). Take the difference around a piece of work.

The code

import resource, subprocess, sys, time
# fib() and CHILD (a script that prints 50 bytes, 2 ms apart)
# are in code/context-switch-initiation.py

def switches(work):
    r0 = resource.getrusage(resource.RUSAGE_SELF)
    work()
    r1 = resource.getrusage(resource.RUSAGE_SELF)
    return (r1.ru_nvcsw - r0.ru_nvcsw,     # voluntary
            r1.ru_nivcsw - r0.ru_nivcsw)   # involuntary

def sleeps():                    # block on a timer
    for _ in range(200):
        time.sleep(0.001)

def pipe_reads():                # block on I/O
    p = subprocess.Popen([sys.executable, "-c", CHILD],
                         stdout=subprocess.PIPE)
    for _ in range(50):             # child writes 1 byte
        p.stdout.read(1)             # every 2 ms
    p.wait()

def cpu_bound():                 # never blocks
    fib(30)

One run of code/context-switch-initiation.py (shortened here) under python3 3.10 on the author's M3, while about 80 other processes wanted a core (load average 81).

series run (measure.py): fib(30) 25 involuntary / 0.129 s → one per 5.16 ms this run, load average 81: fib(30) 1,543 involuntary / 0.749 s → one per 0.49 ms 1,543 / 25 = 61.7× as many preemptions; 200 sleeps → 200 voluntary in both

That's the whole story in two columns. Voluntary switches are set by your code: 200 sleeps give 200, however busy the machine is. The 50 reads gave 52, which we read as 50 blocking reads plus two waits for the child process to start and exit (our reading). Involuntary switches are set by the competition: the same fib(30) was preempted 62× as often on a crowded machine. (The series run's load wasn't recorded; we assume it was quieter.)

Why block-or-preempt beats the alternatives

✗ Cooperative only

Switch only when a program makes a system call or yields. One infinite loop and the OS never runs again; OSTEP notes the fix was a reboot (early Mac OS worked this way).

✗ Busy-wait instead of block

Poll a flag in a loop while waiting. No voluntary switch ever happens, so the thread burns its whole slice doing nothing and gets preempted anyway.

✗ A tiny time slice

Preempt constantly for snappier sharing. Each switch has a cost: OSTEP's example, a 10 ms slice with a 1 ms switch, wastes about 10% of the CPU (ch. 7).

✓ Block when waiting, timer for the rest

Waiting threads leave the core at once (200 sleeps, 200 switches), and the timer guarantees the kernel gets control back even from fib(30).

Is CPython's 5 ms switch interval one of these?

No. sys.getswitchinterval() returns 0.005 s, but that's CPython asking the thread holding the GIL to hand it over to another Python thread. The OS knows nothing about it: to the kernel, a thread waiting for the GIL is just blocked on a condition variable. It can't explain the 25 above either, since fib(30) ran in a single thread where the GIL never changes hands. The 5 ms and the 5.16 ms average are a coincidence.

Preemption isn't always welcome. Latency-critical code (trading engines, audio) tries to avoid involuntary switches by giving a thread its own core and keeping other work off it, and asyncio switches tasks in user space at each await, with no kernel switch at all.

Understand and remember

  • A thread asks for something it must wait for (read, sleep, lock) → the kernel marks it blocked and runs someone else → voluntary switch → the count is set by your code (200 sleeps → 200)
  • A hardware timer interrupts every few ms → the kernel's handler checks whether the slice is used up or a higher-priority thread is ready → involuntary switch (preemption) → even a thread that never blocks gets off the core (fib(30): 25)
  • Involuntary switches depend on competition for cores → same fib(30): 25 on the series run vs 1,543 at load average 81 (61.7×) → preemption counts measure the machine, not your code
  • Cooperative only (switch only on syscalls or yields) → one loop that never yields owns the core → the timer is what makes the OS safe from any program; busy-waiting defeats blocking and just turns waits into preemptions
  • detail that matters CPython's 5 ms switchinterval is a user-level GIL hand-off → to the kernel a thread waiting for the GIL is just blocked on a condition variable → GIL hand-offs appear as ordinary voluntary switches, not as a separate kind

Reference only

  • the field names ru_nvcsw and ru_nivcsw
  • the exact counts of the noisy run (12, 52, 25, 1,543)
  • os.sched_yield()
  • OSTEP's 10 ms slice / 1 ms switch example

3 · Retrieve from memory, card closed
  1. concept Explain why a timer interrupt is necessary for an OS that must stay responsive, even though most threads block often.
    Check
    • blocking gives the core back only if the thread chooses to wait
    • a CPU loop never blocks, so without a timer it would keep the core forever
    • the timer forces a trap into the kernel every few ms, so it can preempt any thread
  2. mechanism Walk through what happens on one core when thread A calls read() on an empty pipe while B is ready, until A runs again after its data arrives.
    Check
    • A's read traps into the kernel, which can't finish it, marks A blocked and switches to B (voluntary)
    • B runs until its slice ends on a timer interrupt, or it blocks
    • the data arrives (device interrupt), A becomes ready but doesn't run yet
    • at the next scheduling decision A is chosen and resumes inside read()
  3. tradeoff A latency-critical thread keeps missing deadlines. Its getrusage shows few voluntary and many involuntary switches. What does that tell you, and which remedies does the card mention?
    Check
    • it isn't waiting on I/O; it is being preempted by competing work
    • give it its own core and keep other work off it (isolation, pinning), or reduce competition
    • or restructure waits in user space (asyncio switches at await, no kernel switch)

4 · Compare against what you already know

vs Threads and the GIL: An OS time slice vs CPython's 5 ms GIL switch interval: who enforces each, what does each hand over, and why can both exist at once?

Check
  • the OS slice is enforced by the kernel via a timer interrupt; it hands the core to another thread or process
  • the GIL interval is CPython asking the GIL holder to release it; it hands the right to run bytecode to another Python thread
  • they are independent layers: a thread can hold the GIL and still be preempted by the OS, and a GIL hand-off looks to the kernel like a thread blocking and waking

vs CPU scheduling: This card explains when the kernel gets control; scheduling explains whom it picks. How does the choice of time slice connect the two, and what does a tiny slice cost?

Check
  • the timer's slice is the round-robin quantum: every expiry is a chance to pick again
  • a smaller slice improves response (RR q = 2 → 1: 2.00 → 1.00) but means more switches (7 → 13 slices for the same jobs)
  • each switch costs µs directly plus cold caches; OSTEP's 10 ms slice with a 1 ms switch wastes about 10%

5 · Predict commit to an answer before revealing

Replace time.sleep(0.001) in the 200-iteration loop with a busy-wait: t = perf_counter(); while perf_counter() - t < 0.001: pass. Predict the voluntary and involuntary counts compared with the sleep version. Commit before revealing.

Reveal

Voluntary drops to about 0: the thread never asks to wait. Involuntary becomes whatever the timer and competition impose over about 0.2 s of CPU: on a quiet machine a few dozen at most (the card's fib(30) got 25 in 0.129 s), on a busy one many more. The wall time stays about the same, but the core is now busy the whole time instead of free for other work.
