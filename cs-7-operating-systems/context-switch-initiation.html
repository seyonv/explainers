What triggers a context switch

Also called voluntary vs involuntary switches, blocking vs preemption, or cooperative vs preemptive multitasking. The cheat-sheet's heading is empty, so this card follows OSTEP chapters 6 and 7 and a getrusage count on an Apple M3.

In one breath

The kernel only gets the CPU back from a running thread in two ways. Either the thread asks for something it has to wait for (a read, a sleep, a lock), and the kernel parks it and runs someone else: a voluntary switch. Or a hardware timer interrupt, or a more urgent thread waking up, hands control to the kernel, which decides the thread has had enough: an involuntary switch, also called preemption.

Worked example: one core, two threads

① A traps into the kernel with a system call and can't continue, so it gives up the core. ② B never asked to stop; the timer interrupt ends its slice. When A's data arrives it becomes ready, but it still waits for the next scheduling decision (OSTEP ch. 6).

Measured: count them with getrusage

The kernel keeps both counters per process: ru_nvcsw (voluntary) and ru_nivcsw (involuntary). Take the difference around a piece of work.

The code

import resource, subprocess, sys, time
# fib() and CHILD (a script that prints 50 bytes, 2 ms apart)
# are in code/context-switch-initiation.py

def switches(work):
    r0 = resource.getrusage(resource.RUSAGE_SELF)
    work()
    r1 = resource.getrusage(resource.RUSAGE_SELF)
    return (r1.ru_nvcsw - r0.ru_nvcsw,     # voluntary
            r1.ru_nivcsw - r0.ru_nivcsw)   # involuntary

def sleeps():                    # block on a timer
    for _ in range(200):
        time.sleep(0.001)

def pipe_reads():                # block on I/O
    p = subprocess.Popen([sys.executable, "-c", CHILD],
                         stdout=subprocess.PIPE)
    for _ in range(50):             # child writes 1 byte
        p.stdout.read(1)             # every 2 ms
    p.wait()

def cpu_bound():                 # never blocks
    fib(30)

That's the whole story in two columns. Voluntary switches are set by your code: 200 sleeps give 200, however busy the machine is. The 50 reads gave 52, which we read as 50 blocking reads plus two waits for the child process to start and exit (our reading). Involuntary switches are set by the competition: the same fib(30) was preempted 62× as often on a crowded machine. (The series run's load wasn't recorded; we assume it was quieter.)

Why block-or-preempt beats the alternatives

✗ Cooperative only

Switch only when a program makes a system call or yields. One infinite loop and the OS never runs again; OSTEP notes the fix was a reboot (early Mac OS worked this way).

✗ Busy-wait instead of block

Poll a flag in a loop while waiting. No voluntary switch ever happens, so the thread burns its whole slice doing nothing and gets preempted anyway.

✗ A tiny time slice

Preempt constantly for snappier sharing. Each switch has a cost: OSTEP's example, a 10 ms slice with a 1 ms switch, wastes about 10% of the CPU (ch. 7).

✓ Block when waiting, timer for the rest

Waiting threads leave the core at once (200 sleeps, 200 switches), and the timer guarantees the kernel gets control back even from fib(30).

Is CPython's 5 ms switch interval one of these?

No. sys.getswitchinterval() returns 0.005 s, but that's CPython asking the thread holding the GIL to hand it over to another Python thread. The OS knows nothing about it: to the kernel, a thread waiting for the GIL is just blocked on a condition variable. It can't explain the 25 above either, since fib(30) ran in a single thread where the GIL never changes hands. The 5 ms and the 5.16 ms average are a coincidence.

Preemption isn't always welcome. Latency-critical code (trading engines, audio) tries to avoid involuntary switches by giving a thread its own core and keeping other work off it, and asyncio switches tasks in user space at each await, with no kernel switch at all.
