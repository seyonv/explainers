Deadlock

Also called a deadly embrace or a circular wait. Threads each hold one resource and wait forever for one another's. The source guide's Deadlock heading is empty, so this card follows OSTEP chapter 32 and small Python runs on an Apple M3.

In one breath

Thread 1 holds lock A and wants B. Thread 2 holds B and wants A. Neither will let go of what it has until it gets what it wants, so both wait forever, and nothing crashes or prints an error. The program just stops making progress.

Worked example: two threads, locks taken in opposite orders

The barrier forces the bad interleaving every run; without it, the deadlock appears only when the scheduler happens to split the two acquires. Which thread times out first varies from run to run.

With one instance of each lock, a cycle in the wait-for graph means deadlock and no cycle means none. find_cycle in the code file walks each thread's "waits on" arrow until it repeats: ['T1', 'T2', 'T1'].

The code

import threading, time
A, B = threading.Lock(), threading.Lock()

def worker(name, first, second, gate, log):
    with first:
        if gate:
            gate.wait()                  # everyone holds one lock
        if second.acquire(timeout=1.0):  # False after 1 s
            second.release()
            log.append(f"{name}: got both")
        else:
            log.append(f"{name}: timed out")

def run(orders, force=True):
    gate = threading.Barrier(len(orders)) if force else None
    log = []
    ts = [threading.Thread(target=worker, args=(n, f, s, gate, log))
          for n, (f, s) in orders.items()]
    t0 = time.perf_counter()
    for t in ts: t.start()
    for t in ts: t.join()
    return sorted(log), time.perf_counter() - t0

def ordered(*locks):
    return sorted(locks, key=id)         # one global order for all

run({"T1": (A, B), "T2": (B, A)})
# → ['T1: timed out', 'T2: got both']  1.00 s
run({"T1": ordered(A, B), "T2": ordered(B, A)}, force=False)
# → ['T1: got both', 'T2: got both']  0.0019 s

Output from one run of code/deadlock.py under python3 3.10 on the author's M3. The 1.00 s is the timeout we chose, not a measured cost. Without timeout=, the first call never returns.

The four conditions, and the fix that breaks each

A deadlock needs all four at once (Coffman et al., 1971, as summarised in OSTEP 32). Remove any one and it can't happen.

Mutual exclusionA resource can be held by only one thread at a time. A and B are Locksonly one owner each Lock-free codeatomic compare-and-swap instead of a lock; hard to write in general
Hold and waitA thread keeps what it holds while it waits for more. with first:then asks for second while still inside Take all locks at onceunder one outer lock, so no one holds half a set

Why a global order can't form a cycle

give every lock a rank; always acquire in increasing rank a waiting thread wants a lock ranked above everything it holds so each "waits on" arrow goes to a strictly higher-ranked lock: r1 < r2 < … < rk, and returning to r1 would need rk < r1 ✗

Dining philosophers: the same cycle with 5 threads

Philosopher i needs forks i and i + 1 (mod 5) to eat. If each picks up the left fork first and all five do it at once, every fork is held and every philosopher waits on a neighbour: P0 → P1 → P2 → P3 → P4 → P0.

RuleAte (of 5)Time
Left fork first, forced to collide0, then 1–41.00 s
Lowest-numbered fork first50.0008 s

Nobody ate until the 1 s timeouts fired; then 2, 1, 4, 3, 3, 4 ate in six runs, depending on who backed off first. The fix changes only P4, who now reaches for f0 before f4: the same global-order trick. One run each on the author's M3.

Why a global lock order beats the alternatives

✗ Detect and recover

Time out, or search the wait-for graph for a cycle, then kill or roll back a victim. It cost a full 1.00 s of nothing above, and a thread can't easily undo half its work. Databases do it because transactions can abort.

✗ One big lock

One lock around everything: no second lock, no cycle. But every thread now waits in one line, so threads that touch unrelated data can't run side by side.

✗ Avoidance (banker's algorithm)

Before each grant, check that some order still lets everyone finish. It needs every thread's maximum demand in advance, which OSTEP notes is rarely known outside narrow settings.

✓ One global lock order

Circular wait becomes impossible, at no runtime cost: both threads finished in 0.0019 s and all 5 philosophers ate. The cost is discipline: every code path must follow the order.

Can you always impose an order?

Not always. It breaks down when you can't know the second lock until you hold the first, or when you call into code you don't own (a callback, a library) while holding a lock and it takes locks of its own. Then the usual moves are: don't hold a lock while calling out; use acquire(timeout=…) and back off, accepting that retries can livelock (next card); or, like a database, detect the cycle and abort one side. PostgreSQL checks for a cycle once a lock wait passes deadlock_timeout (1 s by default) and cancels one transaction.

Deadlock isn't only about locks, either: two processes each blocked reading a pipe the other hasn't written, a thread that join()s a thread waiting on it, or one thread re-acquiring a plain Lock it already holds (see the mutexes card). The same four conditions apply to any resource you wait for; that generalisation is ours, following OSTEP.

The source guide's Livelock heading is empty, so this card follows OSTEP's trylock…In one breathIn a deadlock, threads sit blocked forever. In a livelock, they keep running, and each keeps backing off to let the other go, in lockstep, so neither ever finishes. In starvation, the system as a whole makes progress but one unlucky thread keeps losing. The standard cure for livelock is to break the lockstep with a random wait.
