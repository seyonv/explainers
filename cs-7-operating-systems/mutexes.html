Mutexes

Short for mutual-exclusion lock; threading.Lock in Python, pthread_mutex_t in C, std::mutex in C++. The source guide's Mutexes heading is empty, so this card follows OSTEP chapter 28, the Python threading docs and measured runs on an Apple M3.

Prime · 2 minutes before you read

The problem: A plain lock answers "is anyone inside?" but not "who?". Without an owner, a method that calls another locked method waits on itself forever, and a stray release from the wrong thread lets two threads in. And when the lock is taken, the waiter must either burn a core spinning or pay a sleep and a wake-up.

Where it fits: Second Synchronization card. It refines the lock from the last card with ownership, reentrancy and a choice of how to wait; semaphores (next) drop ownership on purpose.

In one breath

A mutex is a lock with an owner: the thread that locked it is the one expected to unlock it, and every other thread waits. That ownership is what separates it from a binary semaphore, and it's what makes a reentrant version (RLock) possible: the owner may lock again without waiting on itself.

Worked example: a method that calls another locked method

transfer() takes the account lock, then calls withdraw(), which takes the same lock. Run both with a plain Lock and with an RLock:

Ownership: who may unlock?

Now the main thread holds the lock and a different thread calls release():

Lock typeAnother thread calls release()So it behaves like
threading.Lockreleased: no errora binary semaphore

Python's docs say Lock.release() may be called from any thread. So Python's plain Lock doesn't enforce ownership; it is only a mutex by convention. RLock and C's error-checking pthread mutexes do enforce it.

The code

import threading

def reenter(lock):
    with lock:                          # outer: transfer()
        got = lock.acquire(timeout=0.1) # inner: withdraw()
        if got:
            lock.release()
        return got

def release_from_other_thread(lock):
    lock.acquire()                      # main thread owns it
    result = []
    def other():
        try:
            lock.release()              # not the owner
            result.append("released")
        except RuntimeError as e:
            result.append(f"RuntimeError: {e}")
    t = threading.Thread(target=other)
    t.start(); t.join()
    if result[0] != "released":
        lock.release()                  # owner cleans up
    return result[0]

# re-enter Lock : False
# re-enter RLock: True
# other thread releases Lock : released
# other thread releases RLock: RuntimeError: cannot release un-acquired lock

What waiting costs: spin or sleep

Taking a free mutex is one atomic instruction (compare-and-swap or similar) and no system call. The difference between designs is what a thread does when the mutex is taken:

TermWhat the waiter doesExample AExample B
SpinlockLoops on the atomic instruction until the lock frees up. Burns a core while waiting. Many cores, short sectionthe holder runs on another core and frees it soon (OSTEP 28.8) Holder descheduledon one CPU, each waiter spins out its whole time slice (OSTEP 28.8)

58 ns, 87 ns and the 8.2 µs threading.Event round trip are measured on the M3 (series runs). Using a round trip between two threads as a stand-in for waking a blocked lock waiter is our inference, not a separate measurement.

Lock convoys. That gap is why contention hurts more than the critical section itself. If a hot lock is released while others sleep on it, each hand-off costs a wakeup (microseconds), and if the lock is re-taken often the waiters line up behind it and the whole group moves at one wakeup per step, even though the work inside the lock takes nanoseconds. The cure is to hold the lock less: shorter sections, fewer shared locks (sharding), or no shared state.

Why a plain mutex beats the alternatives

✗ Binary semaphore

Same one-at-a-time effect, but no owner: a stray release() from the wrong thread silently lets two threads in. Nothing can check the rule for you.

✗ Spinlock in user code

If the holder is descheduled, every waiter spins for its whole time slice. Fine inside a kernel on short sections; wasteful for Python threads.

✗ RLock everywhere

Hides re-entry you may not have meant, and code that re-enters a lock often expects the data to be in a consistent state it isn't in yet. It also does extra owner bookkeeping.

✓ A plain mutex

Cheap when free (58 ns), sleeps instead of spinning when taken, and a self-deadlock shows up at once as a hang rather than as corrupted data.

Is a mutex always the right tool?

No. Use an RLock when a locked method genuinely has to call another locked method on the same object, such as recursive tree code. Many readers and rare writers want a reader-writer lock (Python has none built in). Allowing N at a time is a semaphore's job, and waiting for a condition rather than for a lock is a condition variable's (see the monitors card).

In Python, queue.Queue or one owner thread per piece of state often removes the lock entirely. A mutex also can't stop deadlock between two locks taken in different orders; only a lock ordering can.

Understand and remember

  • A plain Lock records no owner → the same thread re-acquiring it waits on itself → self-deadlock (acquire(timeout=0.1) → False) → RLock records owner + count → the owner re-enters (count 1 → 2 → 1 → 0)
  • Ownership = only the locker may unlock → a stray release from another thread is an error, not a silent second entry → that check is what separates a mutex from a binary semaphore → Python's plain Lock doesn't enforce it; RLock does
  • Free lock → one atomic instruction, no syscall (58 ns) → taken lock → sleep in the kernel and be woken (≈ 4.1 µs hand-off) → contention costs ~71× the lock → hot locks form convoys moving at one wake-up per step → hold them less (shorter sections, sharding)
  • Spin vs sleep depends on who holds the lock → holder running on another core and releasing soon → spinning wins → holder descheduled → spinners waste whole slices → two-phase locks spin briefly, then sleep
  • detail that matters with lock: costs 87 ns vs 58 ns bare → 29 ns of with-statement overhead → irrelevant next to a 4.1 µs contended hand-off, so always use with for safety

5 · Predict commit to an answer before revealing

Eight threads each run for _ in range(10**5): with lock: n += 1. The work inside the lock takes nanoseconds. Will 8 threads finish faster than 1 thread doing all 8 × 10⁵ increments? Commit before revealing.

Reveal

No, and possibly much slower. Every increment needs the same lock, so the critical section runs one thread at a time whatever the thread count, and each time the lock passes to a sleeping waiter it costs a wake-up (≈ 4.1 µs, about 71× the 58 ns free lock). One thread pays only uncontended acquires; eight threads can form a convoy. The fix is to hold the lock less: count locally per thread and add once at the end.
