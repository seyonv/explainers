Livelock and starvation

Livelock is also called "polite threads" or the hallway dance; starvation is also called indefinite postponement. The source guide's Livelock heading is empty, so this card follows OSTEP's trylock example (ch. 32), OSTEP's scheduling chapter for starvation, and Ethernet's backoff rule, tested in a Python simulation.

In one breath

In a deadlock, threads sit blocked forever. In a livelock, they keep running, and each keeps backing off to let the other go, in lockstep, so neither ever finishes. In starvation, the system as a whole makes progress but one unlucky thread keeps losing. The standard cure for livelock is to break the lockstep with a random wait.

Worked example: OSTEP's "polite" trylock, in time slots

T1 takes lock L1 then tries L2; T2 takes L2 then tries L1. On failure, each releases what it holds, waits, and starts over. That avoids deadlock, but both can keep failing:

✗ Both wait exactly 1 slot

Never ends. Both threads use the CPU the whole time; the pattern repeats every 2 slots.

✓ Each waits a random 0 or 1 slot

A discrete-time simulation, not real threads: one slot per attempt, and two attempts collide only when they start in the same slot. Right-hand draws are from random.Random(5), printed by code/livelock.py.

The code

def expo(c, rng):                # Ethernet: 0 .. 2^min(c,10) - 1
    return rng.randrange(2 ** min(c, 10))


def retries(policy, n, rng):
    """Retries until one contender goes alone, and slots spent."""
    slots = 0
    for c in range(1, CAP + 1):  # c = collisions so far
        picks = [policy(c, rng) for _ in range(n)]
        first = min(picks)
        slots += first + 1       # wait, then one slot to try
        if picks.count(first) == 1:
            return c, slots      # earliest one got through
    return None, slots           # still colliding: livelock

# 32 contenders, 10,000 trials, seed 7
#   random 0..7: exact 15.56  sim  15.56 retries  15.78 slots, stuck 0
#   binary exponential:  sim   4.93 retries   6.09 slots, stuck 0

Why random backoff beats the alternatives

✗ Retry immediately

Two identical threads started together stay together: every attempt collides. It also burns the CPU the whole time.

✗ Wait a fixed time

The left trace. Both threads wait the same amount, so they come back in the same slot: "never" in every column of the table.

✗ Just block on the second lock

Plain acquire() instead of trylock. With the A → B / B → A order, that's the deadlock the polite version was trying to avoid.

✓ Random, growing backoff

Random draws break the tie (OSTEP's fix); a window that doubles per collision copes with any number of contenders: 4.93 retries at n = 32, where 0-or-1 needs 1.3 × 108.

Is random backoff always the fix?

No. For the two-lock case, the better fix is to not need retries: take locks in one global order (see deadlock) and use a blocking acquire. OSTEP also notes that trylock-and-restart gets hard when the lock is buried inside a routine or the thread has done other work it must undo. Backoff fits where you can't order things: senders sharing one wire, clients retrying a busy server, optimistic transactions.

Backoff also doesn't prevent starvation, and may cause it. A sender that has collided many times draws from a wide window, while a fresh one draws 0 or 1, so the fresh one tends to win again; our reading of the rule, not simulated here. Ethernet caps the exponent at 10 (at most 1,023 slots of 51.2 µs on 10 Mbit/s Ethernet). For fairness between threads, use a FIFO lock (a ticket lock, OSTEP 28) or a queue, or add aging as MLFQ's boost does.
