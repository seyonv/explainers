Livelock and starvation

Livelock is also called "polite threads" or the hallway dance; starvation is also called indefinite postponement. The source guide's Livelock heading is empty, so this card follows OSTEP's trylock example (ch. 32), OSTEP's scheduling chapter for starvation, and Ethernet's backoff rule, tested in a Python simulation.

Prime · 2 minutes before you read

The problem: The obvious fix for deadlock is to be polite: if you can't get the second lock, release the first, wait and retry. But if every thread waits the same amount, they all come back in the same instant and collide again, forever, while using the CPU the whole time. And a system that does make progress can still pass over one unlucky thread indefinitely.

Where it fits: Second Concurrency-issues card. It picks up the timeout-and-back-off fix from the deadlock card and shows how it fails; starvation also sets up the scheduling card, where MLFQ's priority boost is a cure.

In one breath

In a deadlock, threads sit blocked forever. In a livelock, they keep running, and each keeps backing off to let the other go, in lockstep, so neither ever finishes. In starvation, the system as a whole makes progress but one unlucky thread keeps losing. The standard cure for livelock is to break the lockstep with a random wait.

Worked example: OSTEP's "polite" trylock, in time slots

T1 takes lock L1 then tries L2; T2 takes L2 then tries L1. On failure, each releases what it holds, waits, and starts over. That avoids deadlock, but both can keep failing:

✗ Both wait exactly 1 slot

tT1 (has L1)T2 (has L2)

2try L2 ✗, releasetry L1 ✗, release
3wait 1wait 1
4try L2 ✗, releasetry L1 ✗, release

Never ends. Both threads use the CPU the whole time; the pattern repeats every 2 slots.

✓ Each waits a random 0 or 1 slot

tT1 (has L1)T2 (has L2)

3drew 0: gets L1 + L2drew 1: waits

A discrete-time simulation, not real threads: one slot per attempt, and two attempts collide only when they start in the same slot. Right-hand draws are from random.Random(5), printed by code/livelock.py.

No fixed window wins every column; exponential backoff is never the disaster, because it widens the window until it fits whatever n turns out to be. Fewer retries isn't always less time: at n = 2, the 0-to-7 window spends 3.66 slots on average against 2.51 for 0-or-1 (same run).

Exponential backoff draws from a different window each round, so it has no one-line formula here; for n = 2 the sum 1 + ½ + ⅛ + 1/64 + … = 1.6416 (computed), against 1.65 simulated.

The code

def expo(c, rng):                # Ethernet: 0 .. 2^min(c,10) - 1
    return rng.randrange(2 ** min(c, 10))


def retries(policy, n, rng):
    """Retries until one contender goes alone, and slots spent."""
    slots = 0
    for c in range(1, CAP + 1):  # c = collisions so far
        picks = [policy(c, rng) for _ in range(n)]
        first = min(picks)
        slots += first + 1       # wait, then one slot to try
        if picks.count(first) == 1:
            return c, slots      # earliest one got through
    return None, slots           # still colliding: livelock

# 32 contenders, 10,000 trials, seed 7
#   random 0..7: exact 15.56  sim  15.56 retries  15.78 slots, stuck 0
#   binary exponential:  sim   4.93 retries   6.09 slots, stuck 0

Why random backoff beats the alternatives

✗ Retry immediately

Two identical threads started together stay together: every attempt collides. It also burns the CPU the whole time.

✗ Wait a fixed time

The left trace. Both threads wait the same amount, so they come back in the same slot: "never" in every column of the table.

✗ Just block on the second lock

Plain acquire() instead of trylock. With the A → B / B → A order, that's the deadlock the polite version was trying to avoid.

✓ Random, growing backoff

Random draws break the tie (OSTEP's fix); a window that doubles per collision copes with any number of contenders: 4.93 retries at n = 32, where 0-or-1 needs 1.3 × 108.

Is random backoff always the fix?

No. For the two-lock case, the better fix is to not need retries: take locks in one global order (see deadlock) and use a blocking acquire. OSTEP also notes that trylock-and-restart gets hard when the lock is buried inside a routine or the thread has done other work it must undo. Backoff fits where you can't order things: senders sharing one wire, clients retrying a busy server, optimistic transactions.

Backoff also doesn't prevent starvation, and may cause it. A sender that has collided many times draws from a wide window, while a fresh one draws 0 or 1, so the fresh one tends to win again; our reading of the rule, not simulated here. Ethernet caps the exponent at 10 (at most 1,023 slots of 51.2 µs on 10 Mbit/s Ethernet). For fairness between threads, use a FIFO lock (a ticket lock, OSTEP 28) or a queue, or add aging as MLFQ's boost does.

1 · Core model what to internalise, what to just look up

Keep it if it changes what you can explain, predict, compare, choose, build or debug. Otherwise it's reference.

Understand and remember

  • Identical threads + identical waits → they return in the same slot → collide again → livelock: CPU busy, nobody finishes ("never" in every column for a fixed wait)
  • Random waits break the symmetry → a round succeeds when exactly one contender draws the earliest slot → P = Σk n·(1/W)·((W−1−k)/W)n−1 → expected retries = 1/P (n = 2, W = 2: 2 retries)
  • A fixed window fits only one range of n → too small and collisions dominate (n = 32, W = 2: 1.3 × 10⁸) → binary exponential backoff doubles the window per collision until it fits n → 1.65, 3.03, 4.93 retries at n = 2, 8, 32
  • Progress for the system ≠ progress for each thread → a long-collided sender draws from a wide window while a fresh one draws 0 or 1 → the veteran keeps losing → starvation; fix with FIFO (ticket locks, queues) or aging (MLFQ's boost)
  • detail that matters Fewer retries isn't always less time → each retry also waits its drawn slots → at n = 2 the 0-to-7 window takes 1.14 retries but 3.66 slots vs 2.51 slots for 0-or-1 → tune for slots, not retries

Reference only

  • Ethernet's cap at 210 − 1 = 1,023 slots of 51.2 µs
  • the simulation's seed (7), trial count (10,000) and CAP of 1,000
  • the per-row simulated vs exact values in the table
  • the alternative names: "polite threads", the hallway dance, "indefinite postponement"

3 · Retrieve from memory, card closed
  1. concept Explain why randomness, not waiting longer, is what cures the polite-trylock livelock.
    Check
    • the problem is symmetry: both threads do the same thing at the same time
    • waiting longer but equally keeps them in step (the fixed-wait trace repeats every 2 slots)
    • random waits make it likely that one thread returns alone and takes both locks
  2. mechanism Compute the expected retries for n = 8 contenders with a 0-or-1 window, showing which terms of the sum survive and why.
    Check
    • k = 0: one thread draws 0 and the other 7 draw 1: 8 · ½ · (½)7 = 8/256
    • k = 1: the other 7 would have to draw later than 1, impossible: the term is 0
    • P = 1/32, so E = 32 retries (the simulation gave 32.50)
  3. tradeoff A fleet of clients retries a busy server. Compare a fixed 1 s retry, a random 0–7 s retry and exponential backoff when the number of clients could be 2 or 200.
    Check
    • fixed: all return together, collisions forever at any n
    • fixed random window: fine for small n but overwhelmed when n greatly exceeds the window
    • exponential: adapts to n by widening; costs longer waits for unlucky clients and can starve them, so cap the exponent

4 · Compare against what you already know

vs CPU scheduling: Starvation under backoff vs starvation under MLFQ: who keeps losing in each, which design choice causes it, and how is each cured?

Check
  • backoff: a sender with many collisions draws from a wide window and loses to fresh senders
  • MLFQ: a long job sits in the bottom queue while interactive jobs keep arriving at the top
  • both come from favouring newcomers; cures are FIFO order (ticket lock, queue) or aging (MLFQ's periodic boost)

vs Idempotency and retries: Backoff between threads here vs retries between services there: what extra problem do networked retries have, and what do both use to avoid lockstep?

Check
  • both add randomness (jitter) and growth to the wait so retries don't synchronise
  • networked retries also can't tell whether the first attempt happened, so each retry must be idempotent
  • threads retrying a trylock know for sure they failed; a client after a timeout doesn't

5 · Predict commit to an answer before revealing

Four contenders with a 0-or-1 window: how many retries on average? Then 16 contenders with a 0-to-7 window. Commit to rough numbers before computing.

Reveal

n = 4, W = 2: only k = 0 counts, P = 4 · ½ · (½)³ = 1/4, so 4 retries. n = 16, W = 8: summing the formula gives about 3.35 retries. Four threads with a 2-slot window already do worse than sixteen with an 8-slot window: the window has to grow with the number of contenders, which is the argument for exponential backoff.

Hint
