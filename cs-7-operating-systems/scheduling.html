CPU scheduling

Also called process or thread scheduling; the policies are FCFS (FIFO), SJF (shortest job first), round robin, MLFQ and Linux's CFS. The source guide's Scheduling heading is empty, so this card follows OSTEP chapters 7 to 9 and a small Python simulator.

Prime · 2 minutes before you read

The problem: When more threads are ready than there are cores, someone must decide who runs next and for how long. Choose badly and a 1-unit job waits 12 units behind two long ones, or every job finishes late because the CPU keeps rotating. The OS also doesn't know in advance how long any job will run.

Where it fits: Last-part card. The context-switch cards gave the kernel control (the timer) and a price per switch; this card decides how to spend that control. It also returns to starvation from the livelock card, and to mutexes through priority inversion.

In one breath

When more threads are ready than there are cores, the scheduler decides who runs next and for how long. Every policy trades two goals: finish jobs soon on average (turnaround) and start every job soon (response). No single policy wins both.

Worked example: jobs A = 8, B = 4, C = 1, all arrive at t = 0

arrival = 0 for all, so turnaround = finish time and response = first-run time FCFS turn (8 + 12 + 13) / 3 = 33 / 3 = 11.00 resp (0 + 8 + 12) / 3 = 20 / 3 = 6.67 SJF turn (13 + 5 + 1) / 3 = 19 / 3 = 6.33 resp (5 + 1 + 0) / 3 = 6 / 3 = 2.00 RR q=2 turn (13 + 9 + 5) / 3 = 27 / 3 = 9.00 resp (0 + 2 + 4) / 3 = 6 / 3 = 2.00 RR q=1 turn (13 + 9 + 3) / 3 = 25 / 3 = 8.33 resp (0 + 1 + 2) / 3 = 3 / 3 = 1.00

Green = the 1-unit job C, so you can follow it. Under FCFS it waits 12 units behind A and B for 1 unit of work: the convoy effect. SJF fixes turnaround; round robin fixes response. Times are abstract units, all computed by code/scheduling.py.

The code

from collections import deque
JOBS = {"A": 8, "B": 4, "C": 1}     # name -> CPU burst, arrive at 0

def fcfs(jobs):
    t, out = 0, []
    for name, burst in jobs.items():        # arrival order
        out.append((name, t, t + burst))
        t += burst
    return out

def sjf(jobs):
    order = sorted(jobs, key=jobs.get)      # shortest burst first
    return fcfs({n: jobs[n] for n in order})

def rr(jobs, q):
    left, ready = dict(jobs), deque(jobs)
    t, out = 0, []
    while ready:
        n = ready.popleft()
        run = min(q, left[n])               # one quantum or less
        out.append((n, t, t + run))
        t += run
        left[n] -= run
        if left[n]:
            ready.append(n)                 # back of the queue
    return out

Complexity: the simulator is O(n log n) for SJF (one sort) and O(total burst / q) slices for round robin: a smaller quantum means more slices, and on a real CPU each slice boundary is a context switch.

Why it beats the alternatives

✗ FCFS

Simple and switch-free, but one long job at the front makes every short one wait: C's turnaround is 13 for 1 unit of work, average 11.00.

✗ SJF / STCF

Best average turnaround here (6.33), and optimal when all jobs arrive together. But the OS doesn't know burst lengths in advance, and long jobs can starve behind a stream of short ones.

✗ Plain round robin

Best response (1.00 at q = 1), but it stretches everyone out: turnaround 8.33 to 9.00. With equal-length jobs it is close to the worst possible turnaround.

✓ Feedback schedulers (MLFQ, CFS)

They learn from behaviour instead of needing burst lengths: short and interactive work gets the CPU soon, as under SJF and round robin, while boosting or fairness keeps long jobs from starving.

Is higher priority for short work always right?

No. Priorities break when a low-priority thread holds a lock a high-priority thread needs. On Mars Pathfinder (1997), a low-priority weather task held a mutex that the high-priority bus task wanted; medium-priority communications work kept preempting the weather task, so the lock never came free and a watchdog kept resetting the computer. The fix, uploaded to the spacecraft, turned on priority inheritance for that mutex: the holder temporarily runs at the waiter's priority.

Also: batch and HPC systems care about throughput, not response, and often run FCFS with backfilling; real-time systems need deadlines met, so they use fixed priorities or earliest-deadline-first instead. And a tiny quantum isn't free: every slice ends in a context switch (a pipe round trip between two processes took 13.6 µs, measured on the M3, an upper bound on the switch itself).

Understand and remember

  • FCFS runs jobs in arrival order → one long job at the front makes short ones wait (C: 12 units of waiting for 1 of work) → convoy effect → average turnaround 11.00
  • Run the shortest first → short jobs leave the queue early → turnaround 6.33 (optimal when all arrive together) → but the OS doesn't know burst lengths, and long jobs can starve behind a stream of short ones
  • Round robin gives each ready job a quantum in turn → every job starts soon (response 2.00 at q = 2, 1.00 at q = 1) → but all finish late (turnaround 9.00, 8.33) → and a smaller quantum means more slices (7 → 13), each a context switch
  • Feedback schedulers watch behaviour instead of needing burst lengths → MLFQ drops jobs that use their allotment and boosts all periodically; CFS runs the smallest vruntime → interactive work stays responsive and long jobs don't starve
  • detail that matters CFS keeps tasks in a red-black tree ordered by vruntime → the next task is the leftmost node, found in O(log n) → a task that slept wakes with a small vruntime and runs soon (per the kernel docs CFS is now giving way to EEVDF)

  • CPU schedulers juggle response and turnaround for jobs that can be preempted every few ms

vs Livelock and starvation: Starvation shows up in both cards. What does a periodic priority boost here share with a FIFO or ticket lock there?

Check
  • both guarantee every waiter eventually gets a turn, whatever newcomers do
  • the boost does it by resetting priorities; a FIFO lock by serving in arrival order
  • both give up a little of the favoured case's advantage (short jobs, fresh senders) to buy fairness

Hint

Overhead ≈ switch cost ÷ quantum when the quantum is much longer than the switch: 6.8 µs ÷ 1 ms = 0.68%. OSTEP's example, a 1 ms switch on a 10 ms slice, is 1 / 11 ≈ 9%, the "about 10%" the switch-initiation card quotes.
