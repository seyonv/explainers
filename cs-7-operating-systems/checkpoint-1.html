Checkpoint 1: choosing a synchronization tool

Ties together threads and the GIL, locks and race conditions, mutexes, semaphores and monitors and condition variables: when threads share data, which guard fits, what each one costs, and how each one breaks.

How to use this page. Close the five cards. Answer each question in writing, in full sentences, before opening its Check. A wrong or shaky answer isn't a failure; it tells you exactly which section to reopen. The questions are mixed on purpose, so you have to work out which idea applies before you can answer.

1 · Mixed retrieval

  1. which concept?A crawler's 8 threads each run stats["pages"] += 1 with no lock. On Python 3.10 the total has always been right, in tests and in production. After moving to free-threaded 3.14t, the total comes out far too low. Which idea explains both halves, and what is the cheapest correct fix?
    Check
    • on 3.10 the GIL happens to hand off only at certain points (loop back-edges, calls), and none falls inside the eight bytecodes of +=, so each ran whole
    • 3.14t has no GIL: threads really run at once and lose updates (the card's run kept 1,082,391 of 4,000,000)
    • fix: a Lock around the update (58 ns uncontended), or per-thread counters summed at the end

    Missed it? Reopen locks and race conditions, "Why plain += survived with the GIL, and why that's luck".

  2. Ten downloads of 0.1 s each go through Semaphore(3). What is the counter just after the 0.3 s mark, who is running, and about how long does the whole batch take?
    Check
    • at 0.3 s three downloads end and three V's arrive, but only d9 is still asleep: 0 + 3 − 1 = 2
    • d9 runs alone; the other two permits are free
    • ceil(10 / 3) = 4 waves, so 0.4 s ideal (0.416 s measured)

    Missed it? Reopen semaphores, the download timeline.

  3. which concept?Cache.get() takes self.lock, and on a miss calls self.load(), which also takes self.lock. The first cache miss hangs the thread forever. No other thread is involved and nothing is logged. What is happening, and what are your two options?
    Check
    • a self-deadlock: a plain Lock records no owner, so the same thread waits on a lock it already holds
    • option 1: an RLock, which records owner and count, so the owner re-enters (count 1 → 2 → 1 → 0)
    • option 2 (often cleaner): take the lock once in the public method and call an unlocked helper

    Missed it? Reopen mutexes, the transfer/withdraw trace.

  4. Two consumer threads use if not buf: cv.wait() and then buf.popleft(). Occasionally one crashes with IndexError even though every notify() follows a put. Walk through the interleaving that causes it.
    Check
    • C1 finds the buffer empty and waits (releasing the lock)
    • the producer puts 1 and notifies; C1 becomes runnable but must win the lock again
    • C2 gets the lock first and takes the item
    • C1 wakes, trusts its old check, pops an empty deque. Mesa semantics: notify is a hint, so re-check in a while

    Missed it? Reopen monitors, "Why while, not if: Mesa vs Hoare".

  5. which concept?A worker pool has 50 threads. You need (a) at most 10 of them talking to the database at once, and (b) a coordinator thread that sleeps until at least 3 finished results are waiting to be merged. Which tool fits each, and why not the other one?
    Check
    • (a) Semaphore(10): a pool of 10 permits, taken and returned one at a time, with an atomic check-and-decrement
    • (b) a Condition with while len(results) < 3: cv.wait(): the predicate is about the state, and waking takes nothing
    • a semaphore for (b) would consume permits one by one, not "wait for 3"; a condition for (a) works but rebuilds a semaphore by hand

    Missed it? Reopen semaphores, "Is a semaphore always the right tool?", and monitors, "Should you write one by hand?".

  6. Another thread calls release() on a lock that the main thread holds. What happens with threading.Lock, with threading.RLock and with Semaphore(1), and which of them is a mutex in the strict sense?
    Check
    • Lock: released, no error; Semaphore(1): released, since counters have no owner
    • RLock: RuntimeError: cannot release un-acquired lock
    • only RLock enforces ownership; Python's plain Lock is a mutex by convention

    Missed it? Reopen mutexes, "Ownership: who may unlock?".

  7. Eight threads increment one shared counter under a lock, 10⁵ times each, with nothing else inside the lock. Why can this be slower than one thread doing all 8 × 10⁵ increments, and what should you change?
    Check
    • the critical section runs one thread at a time whatever the thread count, and threads add no parallelism
    • each hand-off to a sleeping waiter costs a wake-up (≈ 4.1 µs, about 71× the 58 ns free lock), so waiters form a convoy
    • hold the lock less: count locally per thread and add once

    Missed it? Reopen mutexes, "What waiting costs" and "Lock convoys".

  8. The bounded buffer's producer is rewritten as with mutex: free.acquire(); buf.append(x), taking the buffer lock before waiting for a free slot. The program hangs once the buffer fills. Why?
    Check
    • the producer sleeps in P(free) while still holding mutex
    • the consumer needs mutex to take an item, and so to V(free)
    • each waits for the other: take P first and the mutex only around the buffer itself

    Missed it? Reopen semaphores, the last paragraph ("Two easy bugs").

3 · Project: build a capped job runner from a monitor

What it reinforces: the lost update and its fix (locks), ownership and re-entry (mutexes), permits and waves (semaphores), wait in a while and one lock shared by conditions (monitors), and why sleeping threads overlap under the GIL (threads).

In about 40 lines of Python 3.10:

  1. Build a semaphore from a monitor. Write MySem(n) with one Condition: acquire() waits in a while until the count is positive, then decrements; release() increments and notifies one.
  2. Cap the downloads. Run 10 fake downloads (sleep(0.1)) on 10 threads through MySem(3). Track how many are in flight and the maximum, under a separate Lock, and count finished jobs in the same locked block.
  3. Hand results back. Each job puts its index into a bounded buffer of capacity 2 built from one lock and two conditions (not_full, not_empty); a collector thread takes all 10.
  4. Break it three ways and record what happens: replace the while in acquire with if and run 30 jobs several times, watching the maximum in flight; drop the lock around the in-flight counter and add a sleep(0) between its read and write; make the finish step call a helper that re-takes the same plain Lock.
Done when: the correct version finishes in about 0.4 s with max in flight 3, 10 jobs counted and 10 results collected; and you can name, for each break, the card and the mechanism that explains it. Then compare with the check.
Check: the numbers
  • Waves: ceil(10 / 3) = 4, so 0.4 s ideal. A run of this project on the author's M3 took 0.431 s with max in flight 3 and done = 10 (the semaphores card's own run: 0.416 s).
  • if instead of while: a woken acquirer can find the permit already taken by a thread that arrived in between, and decrements anyway, so the count goes negative and more than 3 run. It is timing-dependent and may not show on every run (Mesa semantics; monitors).
  • Unlocked counter with sleep(0): lost updates, so the in-flight number drifts and "done" ends below 10 some runs (locks).
  • Re-taking a plain Lock in the helper: the finishing thread hangs on its own lock; use acquire(timeout=0.1) to see it return False (mutexes).
  • All of it overlaps under the 3.10 GIL because sleep releases it; with a CPU loop instead of sleep, the same runner would take about 10× one job's time (threads).
