Semaphores

Also called a counting semaphore, or P/V (Dijkstra's names), wait/signal, down/up, or acquire/release in Python. The cheat-sheet's Semaphores heading is empty, so this card follows OSTEP chapter 31 and the Python docs, with runs on an Apple M3.

In one breath

A semaphore is a counter of permits that never goes below zero. P takes a permit, and if none are left the thread sleeps until one comes back; V returns a permit and wakes one sleeper. Start the counter at 1 and it works as a lock; start it at 3 and it lets at most three threads through at once; start it at 0 and it becomes a signal one thread sends another.

Both P and V are atomic: checking and changing the counter can't be split by another thread, which is exactly what a plain integer can't promise.

Two semaphores make a bounded buffer

A producer and a consumer share a buffer that holds 2 items. free counts empty slots (starts at 2) and full counts items (starts at 0). The producer does P(free), puts, V(full); the consumer does P(full), gets, V(free). A plain lock guards the buffer itself.

In Python

import threading, time
gate = threading.Semaphore(3)         # counter starts at 3

def download(i):
    with gate:                        # P: wait if counter is 0
        time.sleep(0.1)               # the "download"
    # leaving the with-block is V: counter + 1, wakes one waiter

free = threading.Semaphore(2)         # empty slots
full = threading.Semaphore(0)         # filled slots
mutex = threading.Lock()              # guards the deque itself

def producer(items):
    for x in items:
        free.acquire()                # P(free): wait for a slot
        with mutex: buf.append(x)
        full.release()                # V(full): one more item

def consumer(n):
    for _ in range(n):
        full.acquire()                # P(full): wait for an item
        with mutex: x = buf.popleft()
        free.release()                # V(free): one more slot

# 10 downloads, Semaphore(3): 0.416 s
# max in flight: 3
# starts (s): [0.0, 0.0, 0.0, 0.1, 0.1, 0.1, 0.2, 0.2, 0.2, 0.3]
# put a  buffer=['a'] · put b  buffer=['a', 'b'] · get a  buffer=['b'] …
# max buffer size seen: 2 (capacity 2)
# extra release -> ValueError: Semaphore released too many times

Trimmed from code/semaphores.py, which also counts threads in flight under a small lock and prints the full put/get log. Each P and V is O(1); a waiting thread sleeps rather than spins.

OSTEP's version decrements first and lets the value go negative, so −k means k threads waiting. Python's never goes below 0. Same behaviour, different bookkeeping.

Why a semaphore beats the alternatives for "at most 3"

✗ One lock around the download

Correct but serial: one at a time, 10 × 0.1 = 1.0 s, 2.5× the semaphore's 0.4 s.

✗ No limit

All 10 start at once and finish in 0.1 s, until it's 10,000 requests and the server, the rate limit or your file handles give out.

✗ A shared if running < 3

Check-then-act on a plain integer: two threads both see 2 and both go, so 4 run. And waiters have to poll in a loop.

✓ Semaphore(3)

The check and the decrement are one atomic P, waiters sleep, and V wakes exactly one. Max in flight was 3; 10 downloads took 0.416 s.

Is a semaphore always the right tool?

No. For plain mutual exclusion use a lock: its intent is clearer, and with RLock or most OS mutexes only the owner can unlock (see mutexes). For "wait until some condition is true", a condition variable (a monitor) says it directly instead of encoding it in counters. For a bounded buffer in real Python code, queue.Queue(maxsize=2) is this card's two semaphores and lock, already written. To cap work, ThreadPoolExecutor(max_workers=3) also bounds the number of threads; in async code use asyncio.Semaphore.

Two easy bugs. A stray extra V silently raises the limit; BoundedSemaphore turns that into a ValueError (shown in the output). And in the bounded buffer, taking the mutex before P(free) deadlocks: the producer sleeps holding the lock the consumer needs to make room (OSTEP 31.4).
