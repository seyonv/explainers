Semaphores

Also called a counting semaphore, or P/V (Dijkstra's names), wait/signal, down/up, or acquire/release in Python. The source guide's Semaphores heading is empty, so this card follows OSTEP chapter 31 and the Python docs, with runs on an Apple M3.

Prime · 2 minutes before you read

The problem: A lock lets exactly one thread in. Real limits are often "at most 3 downloads", "at most 10 connections" or "wait until an item exists". Counting those with a shared integer is a check-then-act race, and waiters end up polling. You need a counter whose check and decrement happen as one step, and that puts waiters to sleep.

Where it fits: Third Synchronization card. It generalises the lock (a semaphore at 1) and drops the mutex's ownership, which is what lets one thread signal another. Monitors (next) replace counters with arbitrary conditions.

In one breath

A semaphore is a counter of permits that never goes below zero. P takes a permit, and if none are left the thread sleeps until one comes back; V returns a permit and wakes one sleeper. Start the counter at 1 and it works as a lock; start it at 3 and it lets at most three threads through at once; start it at 0 and it becomes a signal one thread sends another.

Both P and V are atomic: checking and changing the counter can't be split by another thread, which is exactly what a plain integer can't promise.

Two semaphores make a bounded buffer

A producer and a consumer share a buffer that holds 2 items. free counts empty slots (starts at 2) and full counts items (starts at 0). The producer does P(free), puts, V(full); the consumer does P(full), gets, V(free). A plain lock guards the buffer itself.

The put/get order is from one run (the consumer sleeps 10 ms per item, so the producer keeps running into a full buffer). The "would block" column is read off the counters, not logged.

In Python

import threading, time
gate = threading.Semaphore(3)         # counter starts at 3

def download(i):
    with gate:                        # P: wait if counter is 0
        time.sleep(0.1)               # the "download"
    # leaving the with-block is V: counter + 1, wakes one waiter

free = threading.Semaphore(2)         # empty slots
full = threading.Semaphore(0)         # filled slots
mutex = threading.Lock()              # guards the deque itself

def producer(items):
    for x in items:
        free.acquire()                # P(free): wait for a slot
        with mutex: buf.append(x)
        full.release()                # V(full): one more item

def consumer(n):
    for _ in range(n):
        full.acquire()                # P(full): wait for an item
        with mutex: x = buf.popleft()
        free.release()                # V(free): one more slot

# 10 downloads, Semaphore(3): 0.416 s
# max in flight: 3
# starts (s): [0.0, 0.0, 0.0, 0.1, 0.1, 0.1, 0.2, 0.2, 0.2, 0.3]
# put a  buffer=['a'] · put b  buffer=['a', 'b'] · get a  buffer=['b'] …
# max buffer size seen: 2 (capacity 2)
# extra release -> ValueError: Semaphore released too many times

Trimmed from code/semaphores.py, which also counts threads in flight under a small lock and prints the full put/get log. Each P and V is O(1); a waiting thread sleeps rather than spins.

OSTEP's version decrements first and lets the value go negative, so −k means k threads waiting. Python's never goes below 0. Same behaviour, different bookkeeping.

Why a semaphore beats the alternatives for "at most 3"

✗ One lock around the download

Correct but serial: one at a time, 10 × 0.1 = 1.0 s, 2.5× the semaphore's 0.4 s.

✗ No limit

All 10 start at once and finish in 0.1 s, until it's 10,000 requests and the server, the rate limit or your file handles give out.

✗ A shared if running < 3

Check-then-act on a plain integer: two threads both see 2 and both go, so 4 run. And waiters have to poll in a loop.

✓ Semaphore(3)

The check and the decrement are one atomic P, waiters sleep, and V wakes exactly one. Max in flight was 3; 10 downloads took 0.416 s.

Is a semaphore always the right tool?

No. For plain mutual exclusion use a lock: its intent is clearer, and with RLock or most OS mutexes only the owner can unlock (see mutexes). For "wait until some condition is true", a condition variable (a monitor) says it directly instead of encoding it in counters. For a bounded buffer in real Python code, queue.Queue(maxsize=2) is this card's two semaphores and lock, already written. To cap work, ThreadPoolExecutor(max_workers=3) also bounds the number of threads; in async code use asyncio.Semaphore.

Two easy bugs. A stray extra V silently raises the limit; BoundedSemaphore turns that into a ValueError (shown in the output). And in the bounded buffer, taking the mutex before P(free) deadlocks: the producer sleeps holding the lock the consumer needs to make room (OSTEP 31.4).

Understand and remember

  • A counter of permits whose P (check + decrement) is atomic → no two threads can both see "one left" → at most s₀ threads between P and V → Semaphore(3) capped 10 downloads at 3 in flight
  • P on 0 sleeps; V wakes one sleeper → waiters use no CPU and each V lets exactly one through → 10 downloads run in ceil(10/3) = 4 waves → 0.4 s ideal, 0.416 s measured
  • No owner: any thread may V → a semaphore can signal between threads (start at 0: one P's, another V's) → two semaphores count empty and full slots → producer and consumer each sleep exactly when they must (bounded buffer)
  • Semaphores encode conditions as counts → correctness depends on the order of P's and locks → taking the mutex before P(free) lets the producer sleep holding what the consumer needs → deadlock
  • detail that matters Python's counter never goes below 0, while OSTEP's goes negative to count waiters → same behaviour, different bookkeeping → when reading OSTEP's traces, −k means k threads asleep

3 · Retrieve from memory, card closed
  1. concept Explain why a semaphore can be used as a signal between two threads but a mutex can't.
    Check
    • a semaphore has no owner: any thread may V, even one that never P'd
    • start at 0: the waiter's P sleeps until the other thread's V
    • a mutex must be released by the thread that locked it, so it can't carry a signal from another thread
  2. mechanism Walk the bounded buffer (capacity 2) through put a, put b, put c with a consumer that hasn't started: give free, full and who is asleep after each step.
    Check
    • put a: free 1, full 1
    • put b: free 0, full 2
    • put c: the producer's P(free) finds 0 and sleeps; free 0, full 2
    • it wakes only when the consumer's get does V(free)
  3. tradeoff You must cap outbound API calls at 3 in flight. Compare one lock, no limit, a shared if running < 3 check and Semaphore(3) for 10 calls of 0.1 s.
    Check
    • one lock: correct but serial, 1.0 s
    • no limit: 0.1 s, until the load is large enough to break the server or rate limit
    • shared check: check-then-act race, 4 can run, and waiters must poll
    • Semaphore(3): about 0.4 s (0.416 measured), never more than 3

4 · Compare against what you already know

vs Monitors and condition variables: The bounded buffer built from two semaphores vs from a lock and two condition variables: what does each encode the "not full" condition as, which design choice makes one easier to get wrong, and when would you pick the semaphore version?

Check
  • semaphores: as counts (free slots, full slots); conditions: as a test while len(buf) == CAP under the lock
  • semaphores rely on the order of P's and the mutex, so a swapped order deadlocks; conditions re-check any predicate under one lock
  • pick semaphores when the condition really is a count (a pool of N, a limit); pick conditions for predicates that aren't counts

vs Backpressure, percentiles, yield and harvest: Semaphore(3) around downloads and backpressure in a service both cap work in flight. What does each protect, and what happens to the excess in each?

Check
  • both keep a downstream resource from being overwhelmed
  • the semaphore makes excess threads sleep in line; backpressure refuses or slows excess requests upstream
  • a waiting queue that grows without bound is the failure both try to avoid

5 · Predict commit to an answer before revealing

Same 10 downloads of 0.1 s, but now Semaphore(4). Then Semaphore(5). Predict the wall time of each and the counter's value at the moment the last download starts. Commit before revealing.

Reveal

Semaphore(4): ceil(10/4) = 3 waves, about 0.3 s. Semaphore(5): 2 waves, about 0.2 s. With 4 permits the last wave has 2 downloads, so when it starts the counter is 4 − 2 = 2 after the other two permits come back; with 5 permits the second wave is full and the counter is 0. Past 5, more permits can't beat 2 waves until you reach 10 (1 wave, 0.1 s).
