Choosing a unit of execution

The overview for course 7 of the core CS canon series. It ties together the 13 cards on the source guide's Operating Systems page (processes, threads, the four synchronization tools, deadlock and livelock, context switches and scheduling): which unit of execution to run your work on, what each one costs on the author's M3, and how to share state between them without losing it.

In one breath

First ask what your work is waiting on. If it is the CPU, you need more cores actually running Python: processes on a GIL build, threads on a free-threaded one. If it is I/O, you need more waits in flight at once: threads for dozens, asyncio for thousands. Then pay as little as you can for the unit itself, because the costs span six orders of magnitude, from a 58 ns lock to a 72 ms process start. Wherever two units touch the same data, guard it with the cheapest tool that fits (a lock, a semaphore, a condition), take locks in one order, and back off at random when you retry.

The map: the cost ladder, and which unit for which bottleneck

Switch costs are measured round trips halved, so they are ceilings that include Python's own work. The 15 µs is 0.25 s of asyncio run time, minus the 0.1 s wait, spread over 10,000 tasks.

The biggest wins come from not paying for units you don't need: reusing a process instead of starting one, holding a lock too briefly for anyone to wait on it, and parking 10,000 waits as tasks instead of threads. Correctness has no bar: without a lock, 4 threads kept 100,096 of 400,000 increments, and on free-threaded 3.14t plain += kept 1,082,391 of 4,000,000.

The words people use

Concurrency vs parallelism

Concurrency: several jobs in progress at once, taking turns if need be. Parallelism: several running at the same instant on different cores. Threads under the GIL give you the first without the second, which is why 4 threads on fib(27) gained 1.00×.

Process, thread, task

A process owns an address space; a thread is one line of execution inside it, sharing the heap; a task (coroutine) is a heap object that one thread's event loop switches between at each await. Each step down is cheaper to start and switch, and shares more.

Race, deadlock, livelock, starvation

A race gives a wrong answer that depends on timing. Deadlock: everyone blocked in a cycle. Livelock: everyone busy retrying in lockstep, nobody finishing. Starvation: the system moves, but one thread keeps losing.

✓ CPU-bound vs I/O-bound

What the work spends its time on: computing, or waiting for a disk, network or timer. It picks the unit: more cores for the first (processes, or threads with no GIL), more waits in flight for the second (threads, asyncio). Get it wrong and you add units without adding speed.

When this advice doesn't apply

Every number here is one Apple M3 under macOS, mostly on Python 3.10 with its GIL, where multiprocessing spawns a fresh interpreter. On Linux, fork and (from 3.14) forkserver start workers faster; on a free-threaded build, threads use every core and the CPU rule flips toward threads; and C extensions such as numpy or hashlib release the GIL while they compute, so threads can already scale for that work. The switch costs are ceilings that include Python's overhead, and the cache cost after a switch can exceed the switch itself.

For small jobs none of it pays: 72 ms of process start dwarfs a few milliseconds of work, and a single thread with no locks can't race, deadlock or livelock. Prefer the ready-made pieces over the primitives: a pool from concurrent.futures, queue.Queue instead of a hand-built monitor, asyncio.Semaphore to cap async work. Reach for the raw lock, condition or CAS loop only when those don't fit.
