Checkpoint 3: making progress, and choosing a unit

Ties together threads and the GIL, deadlock, livelock and starvation, CPU scheduling and modern concurrency constructs: how competing work can stop moving, who decides what runs next, and which lighter constructs avoid the problem in the first place.

How to use this page. Close the five cards. Answer each question in writing, in full sentences, before opening its Check. A wrong or shaky answer isn't a failure; it tells you exactly which section to reopen. The questions are mixed on purpose, so you have to work out which idea applies before you can answer.

1 · Mixed retrieval

  1. which concept?A batch job's worker threads sit at 100% CPU. The logs fill with "could not get both locks, releasing and retrying in 10 ms", and no batch has finished in an hour. Which failure is this, what causes it, and what are the two fixes, best first?
    Check
    • livelock: the threads keep running and backing off, but in lockstep, so they collide again every time
    • the cause is identical, fixed waits: everyone returns in the same slot ("never" in every column of the card's table)
    • best: take locks in one global order and block, so no retry is needed; otherwise random, growing backoff

    Missed it? Reopen livelock and starvation, the trylock traces and "Is random backoff always the fix?".

  2. which concept?A service hangs with CPU at 0%. A stack dump shows thread 1 inside acquire(B) while holding A, and thread 2 inside acquire(A) while holding B. Name the failure, the four conditions it needs, and the fix that costs nothing at run time.
    Check
    • deadlock: a cycle T1 → T2 → T1 in the wait-for graph
    • mutual exclusion, hold and wait, no preemption, circular wait: all four at once
    • one global lock order breaks circular wait: every wait points to a higher-ranked lock, so no cycle can close

    Missed it? Reopen deadlock, the four-conditions table and "Why a global order can't form a cycle".

  3. Eight contenders each draw a random wait of 0 or 1 slot after every collision. How many retries does it take on average until one gets through alone, and what does binary exponential backoff achieve instead?
    Check
    • success needs a unique earliest draw: only k = 0 counts, P = 8 · ½ · (½)7 = 1/32
    • so 32 retries on average (the simulation gave 32.50)
    • exponential backoff widens the window after each collision until it fits n: 3.03 retries at n = 8

    Missed it? Reopen livelock and starvation, the formula and the simulated table.

  4. which concept?An asyncio web service handles 5,000 open connections well, until one endpoint starts parsing a large JSON upload in pure Python for about 200 ms. Now every request's latency jumps by about 200 ms whenever that endpoint is hit. Why, and what is the fix?
    Check
    • all tasks share one thread; the loop switches only at await
    • the parser never awaits, so no other task can run for its 200 ms
    • move the CPU work off the loop: run_in_executor with a process pool (under the GIL a thread won't compute in parallel, though it does free the loop)

    Missed it? Reopen modern concurrency, "So which one do I pick?", and threads for why threads don't speed up CPU work on 3.10.

  5. Jobs A = 8, B = 4, C = 1 arrive together. Give the average turnaround and response under FCFS, SJF and round robin with q = 2, and say which job suffers the convoy effect.
    Check
    • FCFS: 11.00 and 6.67; SJF: 6.33 and 2.00; RR q = 2: 9.00 and 2.00
    • C suffers the convoy under FCFS: it waits 12 units for 1 unit of work
    • no policy wins both measures; SJF needs burst lengths the OS doesn't know

    Missed it? Reopen CPU scheduling, the worked example.

  6. which concept?On Mars Pathfinder, a high-priority task kept waiting while medium-priority work ran, and a watchdog kept resetting the computer. Which two ideas from this course collide here, and what did the fix change?
    Check
    • a mutex: the low-priority task held a lock the high-priority one needed
    • priority scheduling: medium-priority work preempted the low-priority holder, so the lock never came free (priority inversion)
    • priority inheritance: the holder temporarily runs at its waiter's priority, finishes and releases

    Missed it? Reopen CPU scheduling, "Is higher priority for short work always right?".

  7. Exponential backoff cures livelock, yet a sender that has collided many times may keep losing to fresh senders. Why, and how do the course's other cards cure the same kind of starvation?
    Check
    • after many collisions it draws from a wide window, while a fresh sender draws 0 or 1 and tends to go first (the card's reading, not simulated)
    • FIFO order (a ticket lock, a queue) serves waiters in arrival order
    • aging: MLFQ's periodic boost puts every job back at the top so long jobs still run

    Missed it? Reopen livelock and starvation, the last paragraph, and CPU scheduling, the MLFQ row.

  8. Four threads increment a counter 10,000 times each with a compare-and-swap retry loop, and the run reports 3,385 retries. Did any increment get lost? When would a plain lock be the better choice?
    Check
    • no: a stale CAS fails and is redone, so all 40,000 count
    • each retry is wasted work; under heavy contention retries burn CPU, and anything beyond a counter meets ABA and memory-reclamation problems
    • a plain Lock costs 58 ns uncontended and is the right default; one owner behind a queue avoids sharing entirely

    Missed it? Reopen modern concurrency, "Lock-free: compare-and-swap with a retry loop".

3 · Project: an event loop in 60 lines

What it reinforces: round-robin scheduling and its turnaround/response trade (scheduling), coroutines that give up control only at a yield (modern concurrency), cooperative vs preemptive switching (threads), cycles in a wait-for graph (deadlock), and backoff that breaks lockstep (livelock).

asyncio is, at heart, a queue of generators and a loop. Build a tiny one:

  1. Tasks and a loop. Write each job as a generator that yields after every unit of work, yielding how many units are left. A loop pops a task from a deque, runs it one step, and puts it back unless it has finished. Record each task's first-run and finish time.
  2. Schedule the card's jobs. Run A = 8, B = 4, C = 1. Print the one-letter Gantt string, the average turnaround and the average response, and compare them with the scheduling card's RR q = 1 row.
  3. Add locks. Keep a dict held of lock → task. A task that wants a held lock yields ("wait", lock) instead of working. After every step, build the wait-for graph (task → holder of the lock it waits for) and stop if it has a cycle. Run T1 taking A then B, and T2 taking B then A; then run both taking A then B.
  4. Add backoff. Change the opposite-order version so a task that finds its second lock taken releases its first and skips a random 0 or 1 turns (random.Random(5)), then retries. Count retries until both finish, and average over many seeds.
Done when: your Gantt string and averages match the scheduling card's RR q = 1 result; the opposite-order run reports a cycle between T1 and T2 while the same-order run finishes; the backoff version always finishes; and you can say which card each of the four steps came from.
Check: the numbers (from a Python version of steps 1–3)
  • Gantt ABCABABABAAAA; finish A 13, B 9, C 3; first run A 0, B 1, C 2; average turnaround 8.33, average response 1.00: the scheduling card's RR q = 1 row exactly.
  • A classic slip: if the loop only notices a finished task when the generator raises StopIteration on its next turn, C "finishes" at 5 and B at 10, and the turnaround comes out 9.33. Finishing is part of the last unit of work, not of the next turn.
  • Opposite order: the cycle is ['T1', 'T2', 'T1'], found as soon as each holds one lock and waits on the other. Same order: T2 simply waits for A, and both finish.
  • Backoff: no seed can livelock, since a random draw eventually separates the two. Compare your average with the livelock card's slot model (2.00 retries for n = 2 with a 0-or-1 window); a different count per turn can move it a little.
  • Note what this loop can't do: a task that never yields owns it forever, which is exactly the cooperative-only failure of the switch-initiation card, and why the OS uses a timer.
