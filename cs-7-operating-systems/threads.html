Threads and the GIL

Also called threads of execution or lightweight processes; in CPython, the global interpreter lock (GIL). The source guide's Threads heading is empty, so this card follows OSTEP chapter 26, the Python docs, and measured runs on an Apple M3.

Prime · 2 minutes before you read

The problem: A process is expensive to start (72 ms) and shares no memory, so splitting one program into many processes means pickling data back and forth. Programs want several lines of execution that share one heap. In CPython, though, a lock called the GIL decides whether those lines can actually run at the same time.

Where it fits: Second card. It splits the process from the last card into threads that share its address space, and sets up the next part: sharing a heap is exactly what makes the locks cards necessary.

In one breath

A thread is one line of execution inside a process: its own program counter, registers and stack, sharing everything else (code, globals, heap, open files) with the other threads of that process. In standard CPython, the GIL lets only one thread run Python bytecode at a time, so threads speed up waiting (I/O, sleep) but not pure-Python computing.

What threads share, and what each one owns

Switching between two threads of the same process swaps registers and stack pointer but keeps the address space, which is why it is cheaper than a process switch (OSTEP 26). Sharing the heap is also why threads race on shared data: see the locks card.

Why: who holds the GIL, millisecond by millisecond

Green = running Python code, grey = waiting for the GIL. The 5 ms slice is CPython's default switch interval (sys.getswitchinterval() = 0.005, measured); the exact hand-offs are illustrative. Blocking calls like sleep, file and socket reads release the GIL, which is why the 8 sleeps overlapped.

The code

import threading, time
from concurrent.futures import ProcessPoolExecutor

def fib(n):
    return n if n < 2 else fib(n - 1) + fib(n - 2)

def on_threads(fn, args):
    ts = [threading.Thread(target=fn, args=(a,)) for a in args]
    for t in ts: t.start()
    for t in ts: t.join()

def on_processes(fn, args):
    with ProcessPoolExecutor(len(args)) as ex:
        list(ex.map(fn, args))

seen = []                   # one list on the shared heap

def who(_):
    seen.append(threading.get_native_id())   # own kernel thread

Why threads beat the alternatives, for waiting on I/O

✗ Serial

Each wait runs after the last one: 8 × 0.1 s back to back took 0.835 s (measured). The CPU sits idle for almost all of it.

✗ One process per job

Starting one took 72 ms (spawn, measured), most of a 0.1 s wait. Processes also share no heap, so results must be pickled back through a pipe.

✗ asyncio

Cheaper per task, but only works if every blocking call is an async one. A single ordinary blocking call in a task stalls every other task.

✓ Threads

Plain blocking code, a shared heap, and the GIL is released while waiting: 0.105 s, 7.95× faster than serial.

So should Python code use threads?

For waiting (network calls, disk, subprocesses): yes, typically via concurrent.futures.ThreadPoolExecutor. For pure-Python number crunching on a GIL build: no. 4 threads gained 1.00× on 3.10 while 4 processes gained 3.78×. Use multiprocessing or ProcessPoolExecutor, or move the loop into a library that releases the GIL while it computes (the Python glossary names compression and hashing modules as examples).

The free-threaded build (3.13+, python3.14t) removes the GIL, and threads then gained 2.65×. It also removes the accidental protection: plain c["n"] += 1 lost 72.9% of its updates there. Any threaded code that shares mutable state needs a lock either way.

Understand and remember

  • Threads share the address space and keep only their own PC, registers and stack → switching threads skips the page-table change → cheaper than a process switch → but every thread can touch every object, so shared writes race
  • CPython threads must hold the GIL to run bytecode → only one runs Python at a time → 4 × fib(27) on 4 threads: 0.121 s → 0.121 s (1.00×) on 3.10 → threads don't speed up pure-Python CPU work
  • Blocking calls (sleep, file and socket reads) release the GIL → waits overlap → 8 × sleep(0.1): 0.835 s → 0.105 s (7.95×) → threads are the right tool for waiting
  • Free-threaded 3.14t removes the GIL → threads run on several cores (0.045 → 0.017 s, 2.65×) → but plain += on shared data loses updates (1,082,391 of 4,000,000 kept) → shared state needs a lock either way
  • detail that matters The 5 ms switch interval is CPython asking the GIL holder to let go, not an OS time slice → the kernel only sees a thread blocked on a condition variable → this is why GIL hand-offs and OS preemption are counted separately (the switch-initiation card)

  • sys.getswitchinterval() = 0.005 and setswitchinterval

  • PEP 703 and the list of GIL-releasing stdlib modules

3 · Retrieve from memory, card closed
  1. concept Explain why threads in standard CPython speed up a web scraper but not a pure-Python matrix multiply.
    Check
    • the scraper spends its time blocked in socket reads, which release the GIL, so waits overlap
    • the matrix loop is bytecode, and only the GIL holder runs bytecode
    • so the scraper gains roughly one wait's time for all; the loop gains about 1.00×
  2. mechanism Walk through what the GIL does over 15 ms when two threads both run a tight fib loop on 3.10.
    Check
    • T1 holds the GIL and runs; T2 waits for it
    • after the 5 ms switch interval, T2's wait sets a request and T1 drops the GIL at its next check point
    • T2 runs the next slice while T1 waits; they alternate
    • total work is unchanged: the same CPU time, interleaved, no speedup
  3. tradeoff You need to run 4 CPU-heavy pure-Python tasks. Compare threads on 3.10, processes on 3.10 and threads on 3.14t, using the card's numbers, and name the cost of each.
    Check
    • threads 3.10: 1.00×, no gain; cheap and share memory
    • processes 3.10: 3.78×; pay start-up (72 ms fresh) and pickling of arguments
    • threads 3.14t: 2.65×; share memory, but every shared write needs a lock and some libraries may not yet support it

4 · Compare against what you already know

vs Modern concurrency constructs: Threads vs asyncio tasks for I/O: both overlap waits on one core. What is fundamentally different about how each gives up control, and how does each fail at scale?

Check
  • a thread is preempted by the OS or blocks in a system call; a task gives up control only at await
  • threads cost a kernel object and a stack each (the M3 stopped at 6,143); tasks are small heap objects (10,000 in 0.25 s)
  • threads fail by limits and memory; tasks fail when one blocking call or CPU loop inside a coroutine stalls the whole loop

vs Locks and race conditions: The GIL is a lock, and the next card's threading.Lock is a lock. What does each one protect, and why does holding the GIL not make your own code safe?

Check
  • the GIL protects the interpreter's internals (refcounts, object state) and is handed off between bytecodes
  • a user lock protects your critical section, a span of several bytecodes, calls or I/O
  • the GIL can be handed over between your read and your write (a call, a sleep), so your multi-step update still races

Reveal

The sleeps run in two waves of 8 because each thread takes 2 in turn, so about 0.2 s (the card's 8 sleeps on 8 threads took 0.105 s). The fib run stays at about 0.121 s: extra threads can't raise p above 1 under the GIL, and only 4 of the 8 threads get any work anyway.
