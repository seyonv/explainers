FlashAttention-2 II: parallelism and work partitioning

Also called FA2, split-K vs split-Q, or sequence parallelism across thread blocks. Card 2 of 2 on Tri Dao's FlashAttention-2 paper (arXiv 2307.08691). It walks §3.2 (thread blocks), §3.3 (warps), §4 (A100 and H100 benchmarks, end-to-end training) and §5 in order, then recounts the thread blocks for Llama-3.1-8B on an H100.

In one breath

FlashAttention-2 changes who does which piece of attention, at two levels. Across the GPU, it gives each thread block one slice of query rows, not a whole head, so a single long sequence becomes thousands of independent jobs that fill every SM. Inside a block, it gives each warp its own query rows and lets all warps read the same K and V, so warps never have to add up each other's partial results through shared memory.

1. Across thread blocks: parallelize over the sequence too (§3.2)

FlashAttention (FA1) launched one thread block per attention head: batch × heads blocks in total. Each block runs on one SM, and an A100 has 108 SMs. The paper says this "is efficient when this number is large (say ≥ 80)". Long sequences usually come with small batches, and then most SMs sit idle. FA2 therefore also splits the sequence. In the forward pass the outer loop runs over blocks of query rows, and those row blocks are "embarrassingly parallel": each one gets its own thread block, and they never talk to each other. The paper credits Phil Tillet's Triton implementation with first swapping the loop order and parallelizing over sequence length.

Real kernels may fit two blocks on an SM, which halves the wave count but doesn't change the conclusion. The paper's setting keeps batch × N = 16k tokens and d = 128, so 16 heads.

Decode is the case FA2's split doesn't fix. A decode step has one query row per sequence, so ⌈1/128⌉ = 1 row block and FA2 launches the same 32 blocks as FA1. The Flash-Decoding post (Dao, Haziza, Massa, Sizov, Oct 2023) states the problem directly: "With a batch size of 1, FlashAttention will use less than 1% of the GPU!" Their fix splits the keys and values into chunks, runs attention on each chunk in parallel, and writes one extra scalar per row and chunk, the log-sum-exp, used to rescale and combine the chunks at the end. That is the online-softmax ⊕ from card 1 applied across thread blocks. Splitting Llama's 8,192 keys into 16 chunks of 512 (an illustrative choice) gives 32 × 16 = 512 blocks, 3.88 waves. The post reports "up to 8x" faster decoding for very long sequences on CodeLlama-34B, and attention up to 50× faster than FlashAttention at up to 64k tokens (A100, f16).

2. Inside a block: split Q, not K (§3.3)

A thread block typically has 4 or 8 warps (32 threads each). The question is how to divide the block's tile of work between them. FA1 used what the paper calls the "split-K" scheme: every warp sees all of Q, and K and V are cut into slices across the warps. FA2 flips it.

Figure 3 of the paper (forward pass), redrawn. In split-K each warp gets a slice of QKᵀ and multiplies it by its slice of V, which yields a partial sum for every output row. In split-Q each warp's slice of QKᵀ times all of V is already the finished output for its rows.

The paper's words: split-K "is inefficient since all warps need to write their intermediate results out to shared memory, synchronize, then add up the intermediate results". With split-Q, "there is no need for communication between warps" in the forward pass. In the backward pass FA2 also avoids split-K, but it "still requires some synchronization" because of the dependencies between Q, K, V, O, dO, dQ, dK and dV.

How much traffic is that? (our model, not from the paper.) Count only what warps must exchange per inner-loop iteration, that is, per Kj, Vj tile of Bc columns. Both schemes load the same K, V tile, so it cancels.

split-K, per iteration: write W·B_r·d·4 B (partial O, fp32) + W·B_r·2·4 B (row max, sum) read the same back, plus ≥ 2 __syncthreads split-Q: 0 B, 0 syncs W=4, B_r=64, B_c=64, d=64: 67,584 + 67,584 = 135,168 B = 8.2× the 16,384 B K,V tile W=4, B_r=128, B_c=64, d=128: 266,240 + 266,240 = 532,480 B = 16.2× the 32,768 B K,V tile × 128 iterations (N = 8,192) = 65.0 MiB per row block, 256 syncs

From labs/fa2-occupancy.py. At the larger tile the four fp32 partials alone are 256 KiB, more than the 227 KB an H100 block may use (163 KB on an A100). So a real split-K kernel at that size would need smaller tiles or a reduction in rounds; that's our inference, not the paper's. Split-Q with 4 warps and Br = 128 gives each warp 32 rows (16 rows with 8 warps).

Tuning block sizes (§3.3). Bigger blocks cut shared-memory loads and stores but need more registers and more shared memory. Past some size, register spilling "causes significant slowdown", or the kernel needs more shared memory than the GPU has and can't run at all. FA2 uses blocks of {64, 128} × {64, 128}, chosen by hand for each head dimension and device. With "essentially only 4 choices", the paper leaves auto-tuning to future work.

The words, with two examples each

Think of grading a stack of exams. Thread blocks are separate rooms, warps are graders in one room. FA1 gave each room one whole subject. FA2 splits each subject's exams across many rooms, and inside a room it gives each grader whole exams, not one page of every exam.

3. Benchmarks: about 2× FlashAttention (§4.1)

The paper's summary claims: 1.7–3.0× faster than FlashAttention, 1.3–2.5× faster than FlashAttention in Triton, 3–10× faster than standard PyTorch attention, and up to 230 TFLOPs/s, 73% of the A100's theoretical peak (the forward pass alone reaches 227 at d = 128 in Fig 5b). Against Triton FA2 is about 1.3–1.5× faster forward and about 2× backward. The paper gives no ablation that separates the three changes (fewer non-matmul FLOPs, sequence parallelism, split-Q), so the ~2× can't be attributed to any one of them.

H100, same code. Run unchanged on an H100 80GB SXM5, "using no special instructions to make use of new features such as TMA and 4th-gen Tensor Cores", FA2 reaches "up to 335 TFLOPs/s" (the plotted 16k point reads 338). The paper expects "another 1.5x-2x speedup" from the new instructions and leaves it to future work. That became FlashAttention-3.

Quirks: the paper headlines "2.8×" vs no FlashAttention, but the 1.3B 8k row works out to 3.06×; and §4.2's text says "1.3× speedup compared to FlashAttention-2" where it means FlashAttention.

The gain grows with context: at 2k, attention is a small share of the model's work and FA2 adds only 4–8% over FA1; at 8k, 29%. §5 turns this into its headline: being 2× faster than FlashAttention "means that we can train models with 16k longer context for the same price as previously training a 8k context model". Our reading of why: attention FLOPs per token grow linearly with N (4·N²·d·heads over N tokens), so doubling the context roughly doubles attention's cost per token, and a 2× faster kernel pays for it. The rest of the model's cost per token doesn't change with N. The paper then lists next steps: H100 features (TMA, 4th-gen Tensor Cores, FP8), AMD GPUs, and combining with local, dilated and block-sparse attention.

Four ways to divide the work

✗ FA1 grid: one block per (batch, head)

Fine at batch × heads ≥ 80 on an A100. One 8k-token Llama-3.1-8B prompt makes only 32 blocks, so 100 of the H100's 132 SMs sit idle (24.2% busy).

✓ FA2 grid: + one block per row block

The same prompt becomes 2,048 independent blocks, 15.52 waves, 97% average SM use. Forward row blocks never communicate; backward pays only atomic adds on dQ.

✗ Split-K warps (FA1)

Every warp makes a partial output for all rows, so each K,V tile ends in a shared-memory write, a sync and an add: in our model 8–16× the bytes of the tile itself, every iteration.

✓ Split-Q warps (FA2)

Each warp owns 32 (or 16) query rows and reads the shared K and V. Its output rows are final, so the forward pass needs no warp-to-warp exchange at all.

Two winners, one per level: the top row is how blocks divide the grid, the bottom row how warps divide a block.

When does sequence parallelism not help?

When batch × heads already fills the GPU. The paper's own threshold is "say ≥ 80" blocks on a 108-SM A100. In training (batch 32 × 16 heads = 512 blocks in its N = 512 setting) and in batched serving (Llama-3.1-8B at batch 8 = 256 blocks), FA1's grid already fills every SM, and cutting rows into more blocks mainly smooths the last wave (97.0% → 99.3% in our model). The gain is in long prompts at small batch, like a single 8k or 16k prefill.

  • It doesn't help decode. One query token per sequence is one row block. The KV length is the long axis, so the fix is Flash-Decoding's split over keys and values, combined by log-sum-exp, which is split-K again, this time between thread blocks.
  • It isn't free in the backward pass. Column blocks all write into dQ with atomic adds, and inside a block the backward still needs some synchronization.
  • Split-Q isn't a law. It wins in FA2's forward pass because each warp's rows are independent. When there are few rows, as in decode, splitting over K is the only parallelism left.
