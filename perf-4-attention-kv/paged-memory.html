Before this: Memory: parameters vs the KV cache (perf-2)

PagedAttention I: KV memory as pages

Also called vLLM's KV blocks, the block table, or virtual memory for the KV cache. This card walks the PagedAttention paper (Kwon et al., SOSP '23) from the abstract through §4.3: why existing servers use only 20.4%–38.2% of their KV memory for tokens, and how cutting the cache into fixed-size blocks fixes it. The paper's numbers are OPT-13B and a 13B model on a 40 GB A100; Llama-3.1-8B on an H100 is our recomputation.

In one breath

Older servers gave each request one contiguous slab of KV memory sized for the longest answer it might write, and most of that slab was never used. PagedAttention splits each request's KV cache into small fixed-size blocks, places them anywhere in GPU memory, and keeps a per-request table from "block 0, 1, 2 of this sequence" to "physical block 7, 1, 3". A request then wastes less than one block, so many more requests fit in the same memory.

The problem (abstract and §1)

Serving throughput comes from batching many requests. Batching needs memory for each request's KV cache, and that cache is large, grows by one token per step, and has a length nobody knows in advance. The paper's Fig 1 shows a 13B-parameter model on a 40 GB A100:

Fig 1 (left), redrawn from its labels. The text says "approximately 65%" for weights and "close to 30%" for the KV cache, and the figure labels it ">30%". The weights never change, so how the KV slice is managed decides the batch size.

Existing systems (FasterTransformer, and Orca, which the authors reimplemented because it wasn't public) store each request's KV cache as one contiguous tensor, because deep learning frameworks want tensors contiguous. The paper profiled how that memory is actually used during its §6.2 experiment (Fig 2):

Orca (Max) reserves 2,048 tokens, Orca (Pow2) up to 2× the true output length, and Orca (Oracle) knows the exact output length, which no real system does.

The paper's fix is borrowed from operating systems: "one can think of blocks as pages, tokens as bytes, and requests as processes".

Why KV memory is hard (§3)

  • It's large. OPT-13B (hidden size 5,120, 40 layers, FP16) needs 800 KB per token, and a 2,048-token request up to 1.6 GB. Even all of a GPU's memory holds only a few tens of such requests. The paper adds that FLOPS grew more than 2× from A100 to H100, while memory stayed at 80 GB.
  • Decoding can be complex. Parallel sampling and beam search create several sequences that could share KV (the next card).
  • Lengths are unknown. Output grows each step, and the system must decide what to evict or swap when memory runs out.
OPT-13B KV per token = 2 (K, V) × 5,120 (hidden) × 40 (layers) × 2 B (FP16) = 819,200 B = 800 KiB (paper: "800 KB") one 2,048-token request = 2,048 × 819,200 B = 1.68 GB = 1.56 GiB (paper: "1.6 GB")

PagedAttention: attention over blocks (§4.1)

Cut the keys and values of a sequence into blocks of B tokens: key block Kj = (k(j−1)B+1, …, kjB), value block Vj likewise. Attention for query token i becomes a loop over blocks, each of which can live anywhere in memory:

The math is unchanged; only where the kernel reads K and V from changes. A footnote adds a layout choice: a token's K and V span every layer and head, and vLLM gives each layer and head its own blocks and block tables (the paper reports no performance difference between the two designs). For Llama-3.1-8B, one block of 16 tokens is 16 × 128 KiB = 2 MiB summed over all 32 layers and 8 KV heads, or 16 × 128 × 2 B × 2 (K and V) = 8 KiB per layer per KV head (our arithmetic).

Walk-through: decoding with block tables (§4.3, Fig 6)

Fig 6 redrawn as three steps, B = 4. Physical block numbers are whatever the free list hands out; the paper's are 7, 1 and 3. In the prefill step the KV of the prompt (and the first output token) is computed with ordinary attention; decode steps use PagedAttention. labs/paged-allocator.py prints this exact trace.

Across a batch, each iteration the scheduler picks which sequences run, allocates any blocks they newly need, and runs all their new tokens as one input. Bigger blocks let the kernel work on more positions in parallel but waste more per request (the block-size ablation is on card III). When a request finishes, its blocks go back to the free list for anyone.

Why it beats the alternatives

✗ Reserve the max length

Orca (Max): one contiguous chunk of 2,048 (or 8,192) slots per request. Only 20.4% of KV memory holds tokens in the paper; 6.3% in our Llama run, so just 59 requests fit.

✗ Reserve pow2 or the exact length

Pow2 or an oracle output length shrinks the internal waste, but the chunk is still locked from the first token to the last, and chunk sizes vary, so the allocator leaves gaps. Best case 38.2% (Oracle), which needs lengths nobody knows.

✗ Contiguous plus compaction

Move chunks together to close the gaps. The paper calls it impractical: copying gigabytes of KV cache stalls a latency-sensitive server, and fixed chunks still can't be shared between sequences.

✓ Paged KV blocks

Equal-size blocks allocated on demand: no reservation, no external gaps, under one block of waste per request. 96.3% of KV memory holds tokens in the paper and 97.7% in our run, so 14.5× more requests fit than with reserve-max.

Doesn't the indirection slow attention down?

Yes. Looking up the block table, extra branches and variable lengths make vLLM's attention kernel 20–26% slower than FasterTransformer's highly optimised one (§7.1). The paper's argument is that only the attention operator pays this, not the linear layers, and fitting far more requests per step more than makes up for it: 2–4× higher throughput at the same latency end to end. Details and the block-size trade-off are on PagedAttention III.

It isn't always the right tool. §8 says paging pays off because LLM serving allocates memory dynamically and is limited by memory capacity. In DNN training, tensor shapes are static and allocation can be planned ahead; when serving non-LLM models that are compute-bound, better memory use buys nothing, and the indirection can make things slower. Even for LLMs, the gain over Orca (Oracle) and (Pow2) shrinks on OPT-175B with short Alpaca requests, where plenty of requests fit anyway and the run becomes compute-bound (§6.2). And a full KV pool has a cost of its own: in decode every step reads all of it, 63.94 GB ÷ 3.35 TB/s ≈ 19 ms on an H100 (our arithmetic), so engines also cap the batch for latency, not just memory. That trade-off is on inference engine design.
