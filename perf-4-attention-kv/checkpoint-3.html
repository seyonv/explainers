Checkpoint 3: reuse, move and stretch the KV cache

Ties together RadixAttention I, RadixAttention II, Mooncake I, Mooncake II and long context: keeping KV after a request ends, deciding which request runs where so the cache actually hits, and what to do when one sequence's KV is too long to keep.

How to use this page. Close the five cards. Answer each question in writing, in full sentences, before opening its Check. A wrong or shaky answer isn't a failure; it tells you exactly which section to reopen. The questions are mixed on purpose, so you have to work out which idea applies before you can answer.

1 · Mixed retrieval

  1. which concept?Prefix caching is on, yet a few-shot service recomputes its 1,500-token templates over and over. Traffic mixes 8 templates, arrivals are first-come, first-served, and the cache holds about 3 templates. Which idea explains it, and what is the cheapest fix?
    Check
    • cache thrashing: FCFS interleaves templates, so LRU evicts each one just before its next request
    • fix the order, not the cache: longest-shared-prefix-first runs each template's requests back to back
    • on the card's 64-request batch: 30.2% → 84.7% hit rate, the optimum, with no extra memory

    Missed it? Reopen RadixAttention II, "The problem" and the worked example.

  2. A new chat arrives that shares only the system prompt with a cached chat, whose system prompt and first turn sit on one edge of the radix tree. Walk through what the tree does, and why the system prompt later survives when memory runs short.
    Check
    • the match walks the edge and diverges after the system prompt, so the edge is split: a system-prompt node with two children
    • only the new chat's own tokens are prefilled
    • eviction takes least-recently-used leaves with reference count 0; the system prompt is an ancestor of every chat, so it goes only after everything below it

    Missed it? Reopen RadixAttention I, steps 3–5 of the replay and the four rules.

  3. which concept?A cluster could load a cached 2,000-token Llama-3.1-8B prefix from another machine over a 25 Gbps link (about 3.1 GB/s), or recompute it on the H100. Which idea decides it, and which wins?
    Check
    • store vs recompute: load wins only above Bmin = 2sG / (gqa · (a p + b d)), about 8.6 GB/s here
    • 0.262 GB at 3.1 GB/s ≈ 84 ms vs ≈ 30 ms to recompute (Eq 1 at 100% of 989 TF): recompute wins
    • at 100 Gbps (12.5 GB/s) loading takes ≈ 21 ms and wins, though only narrowly (our arithmetic)

    Missed it? Reopen Mooncake I, "More storage for less computation" and "When is storing KV a bad deal?".

  4. Why is longest-shared-prefix-first provably optimal for a fixed batch, and what is the smallest cache the proof needs?
    Check
    • every edge of the batch's request tree must be computed at least once, so Σ|e| is a lower bound
    • a depth-first order finishes an edge's whole subtree while it is cached, so each edge is computed exactly once
    • LSPF picks the deepest branch-off point, which is DFS; the cache only has to hold the longest single request

    Missed it? Reopen RadixAttention II, "Theorem 3.1".

  5. In Mooncake II's example, instance A holds 4,000 of a 6,000-token prompt but has 150 ms of queued work; idle B holds nothing. If A's queue drops to 20 ms, where does Algorithm 1 send the request, and why did B win before?
    Check
    • estimated TTFT = transfer + queue + prefill of the uncached part
    • before: A 150 + 32.5 = 182.5 ms; B pulls 4,000 tokens (21.0 ms) + 40 + 32.5 = 93.4 ms, so B
    • with A's queue at 20 ms: 20 + 32.5 = 52.5 ms, so A wins; with a short queue the cache holder is best

    Missed it? Reopen Mooncake II, "Worked example: one 6,000-token request".

  6. which concept?A lab is pretraining a new model for 128k-token contexts. It wants decode to read far fewer bytes per step, but any old token must stay reachable directly. Sliding window, ring attention or NSA: which fits, and what does it still cost?
    Check
    • NSA: compressed, selected and window branches read s/16 + 1,536 tokens: 9,728 at 128k, 13.5× fewer bytes, and the selection branch can pick any old block
    • a sliding window cuts storage too but reaches far tokens only indirectly; ring attention keeps attention exact but doesn't cut bytes read, it splits them across devices
    • NSA still stores the full cache (3 sequences of 128k per H100) and must be trained in

    Missed it? Reopen long context, section 3 and "All three on the running example".

  7. Mooncake's first version of early rejection used the decode pool's current load and made the prefill and decode pools oscillate. Why, and what fixed it?
    Check
    • a request admitted now reaches decode only after its prefill, so current decode load is the wrong signal: it lags by one prefill
    • the pools took turns being busy while the other sat idle (anti-phase)
    • predict decode load at the time prefill will finish, and admit on that: rejections fell 3,771 → 3,589 (baseline 4,183)

    Missed it? Reopen Mooncake II, "Overload: reject early, and predict".

  8. Ring attention splits a 1M-token prefill over 8 hosts. Why is the result exact even though every host sees the KV blocks in a different order, and when does the communication stop hiding behind compute?
    Check
    • each host keeps running (m, ℓ, O) for its query block and merges each arriving KV block with online softmax, which is exact in any order
    • it hides only if a block's compute outlasts its transfer: c ≥ F/B tokens, with about 6c tokens per host
    • A100 NVLink: c ≈ 1K; A100 InfiniBand: ≈ 25K, so about 150K tokens per host

    Missed it? Reopen long context, section 2.

3 · Project: trace a few-shot service, then give it a store

What it reinforces: prefix reuse and LRU eviction (RadixAttention I), request order and the Σ|e| bound (RadixAttention II), store vs recompute (Mooncake I), per-request placement cost (Mooncake II), and what long contexts do to the plan (long context).

Setting: Llama-3.1-8B on one H100. Three few-shot templates T0, T1, T2 of 1,000 tokens, each followed by three different 50-token questions: 9 requests, arriving round-robin T0, T1, T2, T0, T1, T2, T0, T1, T2. The GPU's prefix cache holds two templates with their questions (2,100 token slots), LRU on leaves. Use the course's prefill floor, 2 × 8.03e9 × tokens ÷ 989e12, and 128 KiB of KV per token.

  1. FCFS. Simulate the cache in about 40 lines (a dict of templates and question leaves with last-use times is enough). Count computed prompt tokens, the hit rate and the prefill floor.
  2. LSPF. Re-sort the same 9 requests longest-cached-prefix-first and rerun. Compare the computed tokens with the lower bound Σ|e|.
  3. Add a store. Back to FCFS order, but now every template computed once is also kept in a remote DRAM store reachable at 12.5 GB/s. On a local miss, load it if that's faster than recomputing. How much prefill time does FCFS need now? At what link speed would loading stop being worth it for a 1,000-token template?
  4. Stretch the context. Suppose each conversation instead grows to 128k tokens. How many full-attention sequences fit on the H100, how many with a 4,096-token window, and how many tokens would an NSA-style model read per decode step?
Done when: you have computed tokens, hit rate and prefill floor for FCFS, LSPF and FCFS + store, the break-even link speed, and the three step-4 numbers, and you can say in one sentence why the store helps FCFS but LSPF doesn't need it here.
Check: the numbers (computed with a Python version of this exact project)
  • FCFS: every template is evicted just before its next use, so all 9 × 1,050 = 9,450 prompt tokens are computed: 0% hit rate, 153.5 ms of prefill floor.
  • LSPF: Σ|e| = 3 × 1,000 + 9 × 50 = 3,450 tokens, 63.5% hit rate (the optimum), 56.0 ms.
  • FCFS + store: the 3 first-time templates and all 9 questions are computed (3,450 tokens, 56.0 ms) and the 6 repeat templates are loaded: 0.131 GB each at 12.5 GB/s = 10.5 ms, so 62.9 ms of transfer, about 118.9 ms in all if nothing overlaps. Loading beats recomputing a 1,000-token template (16.2 ms) above 0.131 GB ÷ 16.2 ms ≈ 8.1 GB/s by this floor; Mooncake's Eq 2 gives about 8.9 GB/s at p = 1,000. LSPF already meets the bound locally, so it has nothing to load.
  • 128k: full attention 17.18 GB per sequence, 3 fit; a 4,096 window keeps 0.54 GB per sequence at any length, 119 fit; NSA-style reads 131,072 / 16 + 1,536 = 9,728 tokens per step but still stores all 17.18 GB.
