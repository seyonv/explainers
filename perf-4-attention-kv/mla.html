Before this: Grouped-query attention

Multi-head latent attention (DeepSeek)

Also called MLA, low-rank KV compression, latent KV, weight absorption and decoupled RoPE. This card walks DeepSeek-V2 §2.1 in order, then Table 1, the App. C and D appendices and the V3 configuration. Llama-3.1-8B numbers are our recomputation.

In one breath

Instead of caching a key and a value for every head, MLA caches one short latent vector per token per layer: 512 numbers, plus a 64-number key that carries position. At inference the up-projections that would rebuild per-head K and V are folded into the query and output matrices, so the full keys and values are never built. DeepSeek-V3 stores 68.6 KiB per token, where plain MHA with the same heads would need 3.81 MiB (both at BF16, our recomputation).

1 · The starting point: standard MHA

Each token's input ht ∈ ℝd is projected by WQ, WK, WV ∈ ℝdhnh×d and sliced into nh heads. "During inference, all keys and values need to be cached", so every token costs:

KVMHA= 2K and V⋅ nhheads⋅ dhhead dim⋅ llayers  elements per token

DeepSeek-V3's shape as MHA (hypothetical): 2 · 128 · 128 · 61 = 1,998,848 elements = 3,997,696 B = 3.81 MiB per token at BF16. "This heavy KV cache is a large bottleneck that limits the maximum batch size and sequence length."

2 · Low-rank key-value joint compression

MLA squeezes each token's input through one narrow matrix and caches only the result. Keys and values for all heads are then expanded from that one latent vector.

3 · Weight absorption: never build K and V at all

Caching only c would be pointless if every decode step had to rebuild all past keys from it. It doesn't, because matrix multiplication is associative. Take head i, whose slice of the up-projection is WiUK (128 × 512):

qiTkj,i = qiTWiUKcj = (WiUKTqi)Tonce per token · 512-dim cjstraight from the cache u=∑i WiO∑jpijWiUVcj =∑i (WiOWiUV)merged, d × 512 ∑jpijcjattend over c, not V
same thing in plain text: score(i, j) = (W_UK_i^T · q_i) · c_j W^UK folded into the query side output u = Σ_i (W_O_i · W_UV_i) · Σ_j p_ij c_j W^UV folded into W^O lab (float32, n_h=8, d_h=16, d_c=32, 10 tokens): scores explicit vs absorbed max |diff| = 3.9e-07 (scores up to ~3.4) scores explicit vs merged W_UK^T·W_UQ max |diff| = 3.9e-07 output explicit vs absorbed (W_O·W_UV) max |diff| = 2.4e-07 (float64: ~1e-16)

A naming quirk to know: the main text (§2.1.2) says WUK is absorbed "into WQ", while App. C, which writes out the full formulas with query compression, says "into WUQ". Same idea: WUQ is the matrix that produces the content query in the full version. App. C: "we do not need to compute keys and values out for each query."

4 · Decoupled RoPE: why position needs its own small key

RoPE rotates each key by a matrix R(j) that depends on the key's position j. Put it on the compressed keys and the score becomes qiT R(j) WiUK cj. A different R(j) now sits between the query side and WUK for every past token, and "matrix multiplication does not obey a commutative law", so no single merged matrix works. The paper: "we must recompute the keys for all the prefix tokens during inference".

The fix keeps RoPE on a separate, small channel: per-head queries qt,iR ∈ ℝ64 and one key shared by all heads, ktR ∈ ℝ64, which is cached too.

qt,i=[qt,iC;qt,iRper head · 64] kt,i=[kt,iC;ktRshared · 64 · cached] ot,i=∑j=1t Softmaxj(qt,iTkj,idh+dhR) vj,iC cache: (dc+dhR)l

The score is a content part (absorbable, no position) plus a RoPE part (tiny, 64-dim). The scale is 1/√(128 + 64) = 1/√192. Lab: with RoPE on kC, one merged matrix is exact at a single key position (|diff| 9.5e-07) but off by up to 9.03 at the others. V2 also applied its YaRN long-context extension (4K → 128K) to kR alone, "as it is responsible for carrying RoPE".

5 · Query compression: a training-memory trick, not a KV trick

Queries get the same low-rank treatment: ctQ = WDQht with dc′ = 1536, then qC = WUQcQ and qR = RoPE(WQRcQ). The paper's reason is "to reduce the activation memory during training, … even if it cannot reduce the KV cache". Queries are never cached, so this changes nothing at serving time. DeepSeek-V2-Lite skips it.

The decode trade: fewer bytes, more math per byte

In decode, one new query meets every cached token. With absorption each of the 128 heads does a 576-dim dot product against [c; kR] and a 512-dim accumulation of c, all from the same 1,152 cached bytes. Why it beats the alternatives

✗ MHA

Best quality of the classic three in DeepSeek's 7B ablation (MMLU 45.2), but V3's shape would cache 3.81 MiB per token, so batch size and context collapse first.

✗ GQA

Divides the cache by the group ratio (Llama: 4×) but gives up quality: MMLU 41.2 at 8 groups in the same ablation. Decode attention is still at ≈ G FLOPs/byte.

✗ MQA

The smallest cache (V3 shape: 30.5 KiB), but the weakest model: MMLU 37.9, rated "Weak" in Table 1.

✓ MLA

Per DeepSeek's ablation: 4–14% of MHA's KV with better scores than MHA, the cache of GQA with 2.25 groups, and absorption so K and V are never built.

If K and V are rebuilt from c, where does the saving come from?

From what sits in memory and what gets read every step. MHA stores 32,768 numbers per token per layer (V3 shape), MLA stores 576. The up-projections WUK and WUV are weights, shared by every token and every sequence, and absorption means per-head K and V are never built at inference at all. You pay in FLOPs instead: every head works in the 512-dim latent space. Decode attention has FLOPs to spare (1–4 FLOPs/byte against a 295 ridge), so that trade is cheap.

When it is not the right choice:

  • You serve an existing model. MLA is decided in pretraining. A serving team can't switch Llama-3.1-8B to it; the levers you have are KV quantization and paging.
  • Prefill and training. With many queries per step, rebuilding K and V once per token can be cheaper than absorbing per query. Absorption is a decode optimization; the paper describes it only "during inference". (Our inference; the paper doesn't discuss prefill.)
  • Small models and short contexts. When weights dominate the bytes read, KV size matters little. For the smallest possible cache, MQA is still smaller, at a quality cost.
  • Tensor parallelism. The single latent is shared by all heads, so splitting heads across GPUs does not split the cache the way it does for MHA/GQA (our inference; see sharding the KV cache).
