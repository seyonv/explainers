PagedAttention II: sharing, copy-on-write and preemption

Also called parallel sampling and beam search on shared blocks, shared prefix, reference counts, swap vs recompute, sequence groups. This card walks the PagedAttention paper (Kwon et al., SOSP '23) §4.4–4.6 in order: how several sequences share KV blocks, how vLLM picks and restores victims when blocks run out, and how one block table serves many GPUs. The paper's memory numbers are OPT-13B on an A100; Llama-3.1-8B on an H100 is our recomputation.

In one breath

A block table is just a list of pointers, so two sequences can point at the same physical KV block. vLLM gives every block a reference count, lets samples and beams share their common history, and copies a block only when a sequence has to write into one that someone else is still reading (copy-on-write). When memory runs out it evicts whole sequences, never parts of them, and brings them back by copying from CPU memory or by recomputing the KV cache.

Why sharing is worth building (§3, §6.3)

§3 names complex decoding as the second memory challenge: in the paper's parallel sampling experiment the prompt is 12% of total KV memory and can be shared, and beam search shares far more ("up to 55% memory saving"). §6.3 measures the saving as blocks saved by sharing ÷ blocks without sharing, serving OPT-13B:

Parallel sampling: Fig 8 step by step

One request asks for several samples of the same prompt (the paper's use case is program assistants that show several completions). The prompt's KV is computed and stored once; both samples' logical blocks 0 and 1 map to physical blocks 7 and 1, whose reference counts are both 2.

Beam search: Fig 9 and the process tree

Beam search keeps the k most probable sequences at each step, chosen from k · |V| candidates. Unlike parallel sampling, beams share not just the prompt but also parts of their generated text, and the sharing pattern changes every step, "similar to the process tree in the OS created by compound forks". Fig 9 (k = 4): before the step, all candidates share block 0, candidates 0–2 also share blocks 1 and 3, and candidate 3 went its own way after block 0. Then the new top 4 all come from candidates 1 and 2:

Fig 9 rebuilt from the §4.4 text; the exact before-tables are our reading of it (candidate 0's fourth block = 2, candidate 3's = 4, 5, 8), and they reproduce every block number the text gives. Candidates 0 and 3 drop out, their refs fall, blocks 2, 4, 5, 8 reach 0 and are freed, and blocks 9–12 are allocated. Now all share 0, 1, 3; new candidates 0 and 1 share 6; 2 and 3 share 7. labs/paged-cow.py prints this trace.

In an older system each beam owns one contiguous buffer, so after this step candidate 3 "would need to copy a large portion of candidate 2's KV cache". In vLLM a new beam only forks a block table, and copy-on-write copies at most one block, the partly filled last one. To see what that means over a whole generation we ran a beam of width k on the running example (1,000-token prompt, 300 steps, B = 16) with a synthetic, seeded survival pattern: at each step each beam drops out with probability 0.02 and is replaced by a fork of the beam ranked 1st–4th with probability 0.4 / 0.3 / 0.2 / 0.1. That pattern is made up, not a real model's.

At k = 4 that's 25,614 tokens × 128 KiB = 3.36 GB moved over the run, against 23 blocks × 2 MiB = 48 MB of copy-on-write in vLLM. At k = 4 the four final beams still share their first 76 of 82 blocks (the prompt and the first 216 generated tokens), which is why beam search saves more than parallel sampling (56.7% at the same n). Set the drop-out probability to 0 in the lab and beams share only the prompt, which gives exactly the parallel-sampling numbers.

Shared prefix and mixed decoding (§4.4)

Many requests start with the same long task description, a system prompt with instructions and examples (Fig 10 uses a few-shot machine-translation prompt). The provider can keep the KV cache of predefined prefixes in reserved physical blocks, "as how OS handles shared library across processes". A request maps its first logical blocks to those cached blocks (the last one marked copy-on-write), and the prompt phase runs only on the user's own input.

5-shot prefix, 341 tokens (paper §6.4), B = 16 341 = 21 × 16 + 5 → 21 shared blocks + a 5-token copy-on-write last block 100 requests: 2,100 prefix blocks → 21 saved 2,079 × 2 MiB = 4.36 GB

Our recomputation with the Llama-3.1-8B block size. In the paper this is an explicit, provider-chosen list of prefixes. Finding shared prefixes across arbitrary requests automatically (with LRU eviction) is RadixAttention's job.

Mixed decoding. One batch can contain a greedy request, a 4-sample request and a beam search at once, which the paper says existing systems can't do efficiently. The mapping layer hides all sharing: the model and the kernel just see a list of physical block IDs per sequence, whoever else happens to be pointing at them.

Scheduling and preemption (§4.5)

When traffic exceeds capacity, vLLM serves requests first-come-first-served, so the earliest requests run first and the latest are preempted first, and nothing starves. Outputs grow with no known end, so at some step there may be no free block for the next token. The paper then answers two questions.

  • Which blocks to evict? All of one sequence's blocks or none of them (see the box below). And sequences of one request, such as the beams of a beam search, form a sequence group that is gang-scheduled: preempted and resumed together, because they may share blocks.
  • How to bring them back? Either swap or recompute:

Both Example B numbers are ideal floors (our arithmetic). 64 GB/s is our assumption of half of the 128 GB/s NVIDIA lists for the H100 SXM's PCIe Gen5 link, i.e. one direction. At peak bandwidth swapping looks 4× cheaper, but the paper measured that small blocks mean many small CPU–GPU transfers, which fall far short of peak PCIe bandwidth. In §7.3 recomputation is faster at small block sizes, swapping at large ones, and "for medium block sizes from 16 to 64, the two methods exhibit comparable end-to-end performance". The measurements are on PagedAttention III.

Distributed execution (§4.6)

Models too big for one GPU run with Megatron-LM tensor parallelism: linear layers are split across GPUs, attention is split by head, and the GPUs all-reduce intermediate results. Every shard processes the same tokens, so it needs KV for the same positions. So vLLM keeps one KV cache manager in the central scheduler and gives every GPU the same block IDs; each GPU stores only its own heads' slice of each block.

Drawn for Llama-3.1-8B on 2 GPUs (TP = 2), our example: the model fits on one H100, so this is only to show the layout. 8 KV heads split 4 + 4, so each GPU holds 1 MiB of each 2 MiB block (512 KiB at TP = 4, 256 KiB at TP = 8). Each step the scheduler broadcasts token IDs and block tables, and the workers send sampled tokens back. The workers "do not need to synchronize on memory management". How the KV is split when KV heads run out is on sharding the KV cache.

Why it beats the alternatives

✗ Copy the whole KV per sample or beam

Older systems give each sequence its own contiguous buffer. Four samples store the prompt four times (328 vs 142 blocks here), and beam search keeps copying caches between beams: 3.36 GB moved in our k = 4 run.

✓ Share blocks, copy on write

Forking copies a block table, not KV. Only the partly filled last block is ever copied: 3 blocks for 4 samples, 23 blocks (48 MB) over a whole k = 4 beam search. 56.7% (samples) and 72.0% (synthetic beam) less KV memory here.

✗ Preempt by swapping to CPU

Keeps the work already done, but the KV crosses PCIe twice, small blocks waste that bandwidth, CPU RAM up to the GPU's KV size is set aside, and no new requests are admitted until swapped sequences finish.

✗ Preempt by recomputation

Needs no CPU memory and one prefill pass rebuilds everything, but it burns GPU compute (≥ 21.1 ms for 1,300 tokens here). Which of the two wins depends on block size (§7.3 on card III).

The bottom row isn't a loss to sharing: they're the two options for recovering KV that no longer fits, and vLLM supports both.

Why all-or-nothing eviction?

An OS evicts single pages, choosing the one it expects to be used furthest in the future. The paper points out that this heuristic buys nothing here: every decode step of a sequence reads every one of its KV blocks, so "all blocks of a sequence are accessed together". Evict half of a sequence and it can't take its next step until the other half is back, while the half still on the GPU uses memory for nothing. So vLLM evicts all of a sequence's blocks or none, and whole sequence groups at once, since beams may share blocks. §8 lists this as one of the LLM-specific twists on paging, along with recomputation, which an OS can't do.

This isn't the only possible policy. Later engines keep evicted prompt blocks around as a cache instead of throwing them away (RadixAttention's LRU over a radix tree), or move KV to slower tiers on purpose (Mooncake). And sharing only helps when sequences really share history: for one greedy sample per request, reference counts are always 1, and this whole section does nothing.
