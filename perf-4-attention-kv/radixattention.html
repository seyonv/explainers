RadixAttention I: the radix tree of KV caches

Also called SGLang's automatic prefix caching, prefix reuse, or an LRU KV cache. This is SGLang (Zheng et al., NeurIPS 2024) §3, the RadixAttention core, plus Appendix A.1. Card 1 of 2: the data structure and eviction are here, and the scheduling that raises the hit rate is card 2. The trace numbers come from our lab, not from the paper.

Prime · 2 minutes before you read

The problem: PagedAttention frees a request's KV the moment it finishes. But the next turn of the same chat, the next few-shot question or the next sample of the same question starts with the same tokens, and pays their prefill again: 32.5 ms and 262 MB for a 2,000-token system prompt on Llama-3.1-8B, every time.

Where it fits: First card on reusing KV across requests. It builds on paging (block size 1 here) and on paged II's copy-on-write sharing, and replaces "provider lists the shared prefixes" with a tree that finds them automatically.

In one breath

When a request finishes, don't throw its KV cache away. Keep it in a tree keyed by token sequences. Any later request that starts with the same tokens (a system prompt, few-shot examples, the earlier turns of a chat) skips prefill for that part. When memory runs short, drop the least recently used branch tips first.

Why the KV can be reused at all

A token's keys and values depend only on the tokens before it. So two requests with the same first n tokens have the same KV for those n tokens, bit for bit, and the second one can reuse the first one's. (Appendix A.1: the KV "only depends on all previous tokens, so different sequences with the same prefix can reuse the KV cache of the prefix tokens".) The Scaling Book course introduced the idea in designing an inference engine. This card is the data structure behind it. The paper's Fig 9 lists four places where prefixes get shared:

The radix tree: edges carry runs of tokens

Illustrative tokens and slot numbers. The tree maps each token sequence to its KV tensors. Those tensors sit in "a non-contiguous, paged layout, where the size of each page is equivalent to one token" (§3), which is PagedAttention with block size 1. The tree itself lives on the CPU. The KV it points to lives on the GPU.

Four rules turn the tree into a cache (§3). Each one has an example from the trace below and one from the running example:

The server finds the first turn in the tree, reuses its KV, and appends the new turn as a new node.

A new chat with the same system prompt. The node splits so both chats share the system prompt.

(5) Chat 2 continues

Memory is short. Chat 1's turn 2 is the LRU leaf, so it is evicted (the paper's node c). The new turn hangs under chat 2.

cached 40 of 46 · evicted 51 · pool 90/140

(6) A few-shot query

It shares no prefix with anything cached, so the root gets a second branch (node e).

cached 0 of 28 · pool 122/140

(7) A batch of few-shot queries

They share the same examples, so node e splits and the examples are stored once.

cached 48 of 56 · pool 138/140

(8) Chat 1 returns

Chat 2's two nodes are least recently used and are evicted (g and h). Chat 1's turn 2 was evicted back in step 5, so it is prefilled again together with turn 3.

The running example: one 2,000-token system prompt

A chatbot on Llama-3.1-8B (BF16, one H100) where every chat starts with the same 2,000-token system prompt. Our recomputation, using the course's shared numbers:

KV of the prefix = 2,000 × 131,072 B (128 KiB/token) = 262.1 MB prefill skipped/hit = 2 × 8.03e9 × 2,000 / 989e12 = 32.5 ms (2 × the 16.2 ms per-1,000-token floor) 10% of free HBM = 0.1 × 63.9 GB = 6.39 GB prefixes that fit = 6.39 GB / 262.1 MB = 24 prefixes (24.4) all free HBM = 63.9 GB / 262.1 MB = 244 prefixes 100 chats, 1 prompt = 26.2 GB as private copies vs 0.262 GB shared

The prefix sits at the top of the tree, so every chat's own turns are evicted before it is. That is LRU on leaves doing the right thing without any pinning. How many prefixes fit depends on the model's KV size and the GPU. Here is the paper's own test setup next to ours:

On the paper's hardware one long system prompt already costs a tenth of the free memory, which is why the cache has to yield to the batch.

Why it beats the alternatives

✗ No caching

KV is thrown away when a request finishes, and every request prefills its whole prompt. Trace: 0/390 cached. Running example: every chat pays 32.5 ms of prefill and 262 MB for its own copy of the same prompt.

✗ Exact-match prompt cache

The key is the whole prompt, so it only hits when an identical prompt comes back. A chat's next turn is a new prompt and misses. Trace: only the self-consistency samples hit, 84/390 = 21.5%.

✗ Block-hash prefix cache (vLLM style)

vLLM's design doc hashes each block from its parent's hash plus the block's tokens (and extras such as LoRA IDs), "only cache[s] full blocks", and evicts LRU with reference counts. It shares any prefix, but at block granularity. Trace, 16-token blocks: 224/390 = 57.4%. Our tiny segments exaggerate the loss. With long prompts it is small.

✓ Radix tree (RadixAttention)

Shares any prefix to the exact token, at many levels (examples → question → samples). It evicts leaves first and never touches running requests. Trace: 303/390 = 77.7% with no limit, 64.6% in 140 slots. Overhead in the paper: 0.2 s of 74.3 s (< 0.3%) with no reuse at all.

All four hit rates come from the same trace in labs/radix-tree.py, with no memory limit unless stated. The block-hash cell is our summary of the vLLM design doc. The SGLang paper (§7) only says vLLM, at the time, covered "simple reuse cases (e.g., system prompt sharing)". With 1-token blocks the hash chain finds the same prefixes as the tree (lab, try-this 3).

What happens when memory runs out?

  • Leaves go first, oldest first. A shared prefix stays because it is an ancestor, and it only becomes evictable once everything below it is gone (step 8 → step 9 in the trace).
  • Running requests are protected. Any node on a running request's path has a reference count above 0 and can't be evicted. If every leaf is in use, there is nothing left to evict. The lab raises "out of KV memory" at that point. The paper's §3 doesn't say what happens next. Admission control is card 2's Algorithm 1, and preemption is PagedAttention II.
  • The cache yields to the batch. There is no reserved cache region: "When enough waiting requests run, the system will evict all cached tokens in favor of a larger batch size."

When it doesn't help: prompts that share nothing (one-off documents, random traffic) give a 0% hit rate, and you pay only the small bookkeeping cost. Hit rate also depends on the order requests run in: with a first-come-first-served queue, LRU can evict a prefix just before the next request that needs it (our illustration). That is card 2's topic. When the reusable KV outgrows one GPU's HBM, systems move it to CPU DRAM and SSD pools (Mooncake).

Understand and remember

  • A token's K and V depend only on the tokens before it → requests sharing the first n tokens share that KV exactly → keep finished requests' KV keyed by their token sequence → a later match skips prefill for the matched part
  • Store sequences in a radix tree (edges = runs of tokens) → matching a new prompt is a walk from the root, splitting an edge where it diverges → any shared prefix is found automatically, at token granularity, at many levels (system prompt → examples → question → samples)
  • Cache and running batch share one pool → when short, evict least-recently-used leaves with reference count 0 → shared prefixes are ancestors, so they're evicted only after everything below them → system prompts survive; running requests are never touched
  • detail that matters Block-hash caching only caches full blocks and matches block by block → hits end at the last full shared block → 57.4% vs the tree's 77.7% on the lab trace with 16-token blocks (the gap is small with long prompts)

5 · Predict commit to an answer before revealing

The trace runs FCFS. Suppose 100 users each send one question after the same 1,500-token few-shot template, but their requests arrive interleaved with 100 users of 7 other templates, and the cache holds only 3 templates. Will LRU keep your template cached between its requests? Commit first.

Reveal

Often not. With 8 templates cycling through a cache that holds 3, LRU evicts each template just before its next request arrives, and it is recomputed again and again: cache thrashing. The tree and LRU are fine; the order is the problem. That's the next card: sort waiting requests by longest cached prefix.
