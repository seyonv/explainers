Mooncake II: KV-centric scheduling

Also called the Conductor, cache-aware prefill selection, chunked pipeline parallelism (CPP), early rejection or SLO-aware admission. This card covers Mooncake FAST'25 §3.3–5 and the arXiv v4 report's §5.2 and §7. They are two different papers with different numbers, and each number below says which one it comes from. Card 2 of 2. The KV store and the store-vs-recompute argument are in card 1.

In one breath

Once KV caches live in a shared pool, deciding where a request runs becomes a question about where its KV is. For each new request Mooncake's scheduler, the Conductor, checks every prefill machine. It works out how much of the prompt that machine already has cached, how long its queue is, and how long the rest would take to compute. It sends the request to the machine that gives the earliest first token. If no machine can meet the latency target, it rejects the request straight away, before any GPU time is spent on it.

Where this sits

Mooncake serves Kimi (Moonshot AI). It runs prefill and decode on separate GPU pools and keeps KV blocks in a pooled CPU-DRAM/SSD store (card 1). A request goes through four steps (FAST §3.1): (1) load the reusable prefix KV, (2) incremental prefill of the uncached part, which is chunked and pipelined when that part is over a threshold "typically larger than 1000 tokens", (3) stream the new KV layer by layer to the chosen decode node's CPU memory, (4) join that node's continuous batch. Splitting prefill from decode is itself the topic of perf-6 (not built yet). The short version is in perf-2: designing an inference engine. This card is about the scheduling layer on top.

The prefill pool: why chunked pipeline parallelism FAST §3.3 · arXiv §5.1

Long prompts (Kimi serves up to 128k tokens, and inputs are "10 to 100 times larger" than outputs) make TTFT the hard target. One 8-GPU node is too slow for them, so one prefill has to be spread over several nodes. The paper rules out two standard ways of doing that:

  • Tensor parallelism across nodes needs "two expensive RDMA-based all-reduce operations per layer". For the paper's LLaMA3-70B (80 layers) that means 160 cross-node all-reduces per forward pass (our arithmetic), which drags down MFU.
  • Sequence parallelism (split the tokens across nodes, for example ring attention) still needs cross-node communication "at least once per layer" (arXiv). For short inputs it gives lower MFU than single-node TP. It also "competes with network resources for transferring KVCache", the same network Mooncake Store relies on. Elastic SP would fix the MFU but complicates the Conductor.

Chunked pipeline parallelism groups every X prefill nodes into a pipeline. The prompt is cut into chunks no longer than prefill_chunk, and "different chunks of the same request can be processed simultaneously by different nodes". It relies on the autoregressive property: chunk 2 at a given layer only needs the KV that chunk 1 already left at that same layer, on that same node.

Illustrative: X = 3 and four equal chunks. The paper does not say how layers are split. "Pipeline stage" as in training pipeline parallelism is our reading. The hand-off is small: 1,000 tokens × 8,192 hidden × 2 B = 16.4 MB for LLaMA3-70B, and 8.2 MB for Llama-3.1-8B (our arithmetic). Compare two all-reduces in every layer for cross-node TP.

The paper names two benefits: communication "only at the boundaries of each pipeline stage", which "can be easily overlapped with computation", and a design that "naturally fits both short and long contexts". A short prompt is simply one chunk, and there is no need to keep re-partitioning nodes. The paper calls it, "to our knowledge, … the first application in the inference stage" of pipeline-style acceleration from training.

Layer-wise prefill arXiv §5.2

VRAM is the other scarce resource. The arXiv report defines a request's occupation cost as S × T, its KV size times how long that KV sits in VRAM. (Chunked prefill mixed into decode batches makes T longer.) Prefill runs layer by layer and is compute-bound, so the KV loads and stores are overlapped with compute:

for each layer ℓ: wait load(KV prefix, layer ℓ) # launched during layer ℓ−1 launch load(KV prefix, layer ℓ+1) attention + MLP for layer ℓ launch store(new KV, layer ℓ) # streams to the decode node / store wait for all stores prefill time ≈ max(KV loading time, compute time), whichever dominates depends on the cached fraction

The payoff, in the report's words, is that it "enables us to disregard the available VRAM size in prefill scheduling, as long as it can contain a single request". Prefill scheduling then only has to consider where the KV is and how much DRAM is free. That is what the Conductor does next.

The Conductor: pick the earliest first token FAST §4.1 · Algorithm 1

Older schedulers balance on request count. The Conductor also counts cache hits: a busy node with a long cached prefix can still be the fastest place to run. Algorithm 1, shortened (both papers print the same algorithm):

Cache load balancing: hot blocks replicate themselves FAST §4.2

Some blocks are hot: a system prompt is read "by almost every request", while one user's long document is read once. Predicting future block popularity is "impossible" for a fast-growing service, so Mooncake uses a heuristic hot-spot migration instead:

  • When the instance with the longest prefix is too busy, the Conductor "forwards the cache's location and the request to an alternative instance if the estimated additional prefill time is shorter than the transfer time". That instance pulls the KV from the holder and keeps it. In the example above, B ends up with a copy of A's 4,000 tokens.
  • It prefers to recompute when the best remote prefix is no longer than the local prefix times kvcache_balancing_threshold. A small gain isn't worth network traffic.
  • Result (FAST §5.3, Fig 11): in the conversation and tool&agent traces, the hot keys (for example the top 100) end up "with replicas on almost every instance in the prefill pool". The synthetic trace, with less sharing, gets fewer replicas that fluctuate "even for the top 10 blocks".

Pooling the cache this way also raises the hit rate. FAST §5.3 compares a global cache with per-node local caches, 3M tokens per node in both: up to 136% higher hit rate and up to 48% less prefill compute time.

Overload: reject early, and predict arXiv §7 only

Most serving papers assume every request gets served. Kimi's traffic grew faster than its GPU fleet, so the arXiv report treats overload as the normal case. Three ideas, in order:

  1. Load = SLO headroom. Coupled systems measure load as running requests / max capacity. With prefill and decode separated, Mooncake compares each instance's predicted max TTFT and TBT against the SLO limits lttft and ltbt.
  2. Early rejection. If a request is refused by a full decode pool after its prefill is done, that prefill was wasted. So the Conductor checks "the greater load between the prefill and decoding pools" when the request arrives.
  3. Prediction. Early rejection alone caused "significant anti-phase fluctuations" between the pools (Fig 9: 20 machines over 20 minutes). The decision is based on the current decode load, but the decode load that matters arrives one prefill later.

Schematic redrawn from the four stages described for arXiv Fig 10a (the paper colours them green and yellow). The shapes are illustrative, not measured. Each pool is busy while the other sits idle, which the report calls "poor resource utilization".

The fix is early rejection based on prediction (Fig 10b). Predicting each request's output length is "challenging due to high costs or low accuracy", so Mooncake predicts at the system level. It assumes every decode takes the same time td. Requests whose prefill will finish by time t are added to the decode pool, requests older than td are removed, and the predicted load is the average TBT / ltbt at t. Admission uses that predicted load. The result, on 8P + 8D with 23,000 real requests replayed at 2× speed (arXiv Table 3):

Why it beats the alternatives

✗ Random placement

It ignores both cache and queue, so hot prefixes are recomputed everywhere and queues pile up by chance. Worst in both papers: 19.65 s (FAST) and 92.07 s (arXiv) average TTFT. Our example: 148.3 ms expected.

✗ Load-only balancing

It sends work to the shortest queue, as older schedulers did, and throws away cache hits the cluster already paid for. 5.27 s (FAST) and 60.41 s (arXiv). Our example: B recomputes all 6,000 tokens, 137.4 ms.

✗ Local cache-aware

It weighs each node's own hits against its queue but never moves KV between nodes, so a hot prefix stays stuck on a busy node. 3.58 s (FAST) and 14.36 s (arXiv). Our example: C at 125.0 ms.

✓ Global KV-centric (Algorithm 1)

It considers transfer + queue + prefill across the whole pool, pulls a prefix to an idle node when that is faster, and so replicates hot blocks. Best in both papers: 3.07 s (FAST, −14% vs local) and 6.26 s (arXiv). Our example: B with a pulled prefix, 93.4 ms.

Why reject requests early instead of queueing them?

Because in a disaggregated system, work done before the rejection is lost. The arXiv report argues that if a request's prefill finishes and the decode pool then turns it away, "the computational resources expended during the prefill stage are wasted". That prefill GPU time could have gone to a request that would have finished. A queue doesn't help at sustained overload: arrivals outpace capacity, so the queue keeps growing, every waiting request's TTFT rises past 30 s, and those requests fail their SLO anyway. HTTP 429 at admission is cheap. It costs a hash lookup, not a prefill.

  • Not when capacity is only briefly short. A short spike is better absorbed by a queue (the report mentions deferring "for later retry"). Rejecting throws away demand you could have served a second later.
  • Not naively. Rejecting on the current decode load caused the anti-phase oscillation above. The decision needs the predicted load, and even the simple uniform-td predictor cut rejections from 3,771 to 3,589.
  • Not for a single-box engine. In a coupled engine (vLLM on one node) prefill and decode share GPUs, so load is simply running/max requests, and chunked prefill or priority scheduling is the usual tool (our note). The report leaves request-level output-length prediction to future work and names priority classes as a further need.
