Online softmax

Also called the online normalizer calculation, running-max softmax, or one-pass softmax. This card walks Milakov & Gimelshein (NVIDIA), Online normalizer calculation for softmax (arXiv 1805.02867, 2018), section by section: Eq 1–2, Algorithms 1–4, Theorem 1, the parallel ⊕ of §3.1, and the V100 benchmarks of §5–6. Their numbers are on a Tesla V100 PCIe in fp32. The Llama-3.1-8B and H100 figures are our recomputation.

In one breath

A safe softmax needs the maximum of the vector before it can sum the exponentials, so it reads the input three times. Online softmax keeps a running maximum m and a running sum d, and whenever the maximum grows it rescales the sum it already has by emold − mnew. Max and sum then come out of one pass, 4 memory accesses per element drop to 3, and the answer is exactly the same. Because two partial (m, d) pairs can be merged, the vector can also be split across threads, which is the trick FlashAttention applies to every tile.

§1 Why softmax is worth speeding up

The paper's motivation is the language-model output layer: a projection turns the hidden state into one logit per vocabulary word, and softmax turns logits into probabilities. It lists the known shortcuts (differentiated and SVD-softmax, hierarchical softmax, importance sampling, NCE, BlackOut, self-normalized softmax) and notes that almost all of them still run the original softmax on a full or reduced vector. So a faster exact softmax helps nearly all of them. It is also orthogonal to them (§6).

Two places this shows up in the running example (our connection; the 2018 paper doesn't mention attention):

  • Sampling. Llama-3.1-8B produces V = 128,256 logits per token, and every decode step runs a softmax over them (often followed by top-k).
  • Attention. Every query row takes a softmax over its N scores against the keys. For N = 8,192 that's 8,192 scores per row, per head, per layer. This is where the trick matters most, and it sets up FlashAttention I.

§2 Original softmax: naive (Eq 1) and safe (Eq 2)

yi=exi∑j=1VexjEq 1, naive: e^x overflows yi=exi−mV∑j=1Vexj−mV,mV=maxk=1VxkEq 2, safe: every exponent ≤ 0

Subtracting the max multiplies top and bottom by the same e−m, so Eq 2 equals Eq 1 exactly. What changes is the range: every exponent is ≤ 0, so every e… lies in (0, 1] and the sum lies between 1 and V.

fp32 exp overflows above x = 88.72 (fp64: 709.78) x = [1000, 999, 998] naive: e^x = [inf, inf, inf] → y = inf/inf = [nan, nan, nan] safe: e^(x−1000) = [1, 0.367879, 0.135335], sum 1.503215 y = [0.665241, 0.244728, 0.090031]

Algorithm 1: naive

d ← 0 for j: d ← d + e^x[j] load for i: y[i] ← e^x[i] / d load, store

Loops run j, i = 1 … V. 2 passes. 2 loads + 1 store = 3 accesses per element. Can overflow (line 3).

Algorithm 2: safe

m ← −∞ for k: m ← max(m, x[k]) load d ← 0 for j: d ← d + e^(x[j]−m) load for i: y[i] ← e^(x[i]−m) / d load, store

3 passes. 3 loads + 1 store = 4 accesses. The paper says this is what TensorFlow, PyTorch, MXNet, CNTK and Chainer used.

§3 The online normalizer (Algorithm 3)

Merge the first two loops. Walk the vector once, keeping the maximum so far and a sum whose exponents are relative to that running maximum. When a new element raises the maximum, everything already in the sum was scaled by the old max, so multiply the sum by emold − mnew (a number ≤ 1) to re-base it, then add the new term.

mj=max(mj−1,xj) dj= dj−1·emj−1−mjre-base the old sum + exj−mjadd the new term m0=−∞,d0=0 then yi=exi−mVdV
x_jthe j-th logit or attention scorej = 1 … V m_jrunning maximum of x_1 … x_jnever overflows: it is one of the x's d_jrunning normalizer Σ e^(x_k − m_j) over k ≤ j1 ≤ d_j ≤ j e^(m_old − m_new)rescale factor: 1 if the max didn't move, < 1 if it rosee^(3−5) = 0.135

Cost: "negligible additional cost of two operations per vector element" (our reading: the rescale multiply and its exp). Accesses: 1 load for the normalizer pass, then 1 load + 1 store for y = 3 per element, 4/3 = 1.33× fewer than safe. The authors credit Welford's 1962 online variance algorithm as the inspiration.

Theorem 1 (why it's exact). Lines 1–6 compute mV = max xk and dV = Σ exj − mV. Proof by induction. The base case V = 1 gives d1 = e0 = 1. For the step, assume dS−1 = Σj<S exj − mS−1. Multiplying by emS−1 − mS turns every term into exj − mS: the old max cancels, and the sum is re-based onto the new one. Adding exS − mS completes Σj≤S. So Algorithm 3 computes Eq 2, not an approximation of it.

It's also safe. mj is always one of the inputs, so it can't overflow. dj is bounded, 1 ≤ dj ≤ j: the term at the current max contributes exactly 1, and each of the j terms is ≤ 1. The paper says fp32 storage for d is enough for up to 1.7 × 1037 elements. Beyond that, use fp64. Algorithm 2 has the same bound.

§3.1 The parallel version: the ⊕ merge

Lines 1–6 are sequential, but a GPU needs thousands of threads. The paper generalises the recurrence into a binary operator on (m, d) pairs. Each element starts as the pair (xi, 1), and the whole vector reduces with ⊕:

[midi] ⊕ [mjdj] = [M=max(mi,mj)di·emi−M+dj·emj−M] [mVdV]=[x11]⊕⋯⊕[xV1]Eq 3: any grouping, any order

⊕ is associative, so the pairs can be grouped any way you like: a tree reduction across threads, warps or blocks. It is also commutative, so the order doesn't matter either. The paper omits both proofs. Applied left to right, ⊕ is exactly Algorithm 3. The same example, split into two halves that could run on two threads:

Thread A's partial sum was measured against its own max, 3. The merge shrinks it by e3−5 to put it on the common max, 5, which is the same rescale as row j = 3 of the trace. This per-block (m, d) merge is exactly what FlashAttention does across key tiles (next card), where d is called ℓ.

§4 Softmax + top-k fusion (Algorithm 4)

Beam search and top-k sampling need only the K largest probabilities, not all V of them. Top-k must load every element at least once. Running them one after the other costs 5 accesses per element with safe softmax, or 4 with online softmax. Algorithm 4 folds top-k into the online pass: alongside m and d, keep a sorted buffer u of the K best logits (K + 1 slots) and their indices p. Each new element goes into slot K + 1 and bubbles up with a single insertion loop. At the end, only K outputs are written: vi = eui − mV / dV. That's 1 access per element. It works because the logits and the probabilities have the same order.

§5–6 Benchmarks (Tesla V100 PCIe 16 GB, fp32, CUDA 9.1, CUB 1.8)

The paper's reasoning: softmax does few FLOPs per byte, so it is memory-bandwidth-bound, and fewer accesses should mean proportionally less time. One thread block per vector. Batch 4,000 fills the GPU (training, batch inference). Batch 10 is just 10 blocks (online inference), and there "various latencies are exposed".

§6–7 Results and discussion. Online softmax is 1.15× faster for V ≥ 1,000 and up to 1.3× for large batches with V ≥ 4,000. If you use naive softmax, switching to online softmax improves accuracy at no or negligible cost. The fused top-k is 1.5–5× faster. They didn't test CPUs but expect similar gains if the code stays vectorised. The last open idea is to fuse softmax with the preceding layer to avoid the memory round trip, which they call "more challenging". For attention, that is exactly what FlashAttention did four years later (our connection, not the paper's).

2. An attention row. Each query row needs a softmax over its N scores. At N = 8,192, one fp32 row is 8,192 × 4 B = 32 KiB, which fits on-chip (the H100 has 256 KB of L1/SMEM per SM). The full score matrix doesn't: 8,192² × 4 B = 268.4 MB per head per layer, or 8.59 GB per layer across 32 heads. Safe softmax over a stored matrix means writing S, reading it 3 times and writing P: 5 × 268.4 MB = 1,342 MB per head, about 401 µs at 3.35 TB/s. With online softmax and ⊕, a kernel can stream the keys in blocks, keep (m, ℓ) per row in registers, and never write S at all. The one extra step is to rescale the running output row along with ℓ. That's FlashAttention I. Our recomputation, labs/online-softmax.py section 7.

Why it beats the alternatives

✗ Naive softmax (Alg 1)

3 accesses, but ex overflows above x = 88.72 in fp32. Logits of 1,000 give inf/inf = NaN. No framework ships it.

✗ Safe softmax (Alg 2)

Correct and stable, but it needs the global max before the sum, so it takes 3 passes and 4 accesses. It was the 2018 default in every major framework, and it forces the whole row to exist before normalising.

✓ Online softmax (Alg 3 + ⊕)

As safe as Alg 2 with Alg 1's 3 accesses: 1.33× fewer, ≈1.3× faster on V100. Its (m, d) pairs merge in any order, so it parallelises and can process a row one tile at a time.

✗ Fused online + top-k (Alg 4)

1 access instead of 5, up to 5× on V100, but only when you need just the top K and K is small. At K = 30 the gain falls to 1.4×, and it can't give full-vocabulary probabilities (e.g. for top-p).

The fused version wins big but in a narrower job, so it gets a ✗ here only as a general-purpose softmax. The tiled cousin (FlashAttention) is the next card.

Is online softmax an approximation?

No. Theorem 1 shows it computes Eq 2 exactly in exact arithmetic. The rescale only moves each term onto a new reference point, and the terms themselves are unchanged. In floating point, the results differ from safe softmax only at rounding level. In the lab on 128,256 synthetic logits: fp64 max |yonline − ysafe| = 1.8 × 10−16. In fp32 end to end, with ⊕ over 132 chunks: 1.49 × 10−8, on probabilities as large as 0.114 and below fp32's epsilon of 1.19 × 10−7. Alg 4's top-5 indices match np.argsort exactly.

When it's not worth it:

  • Short vectors (V ≤ ~1,000). The paper measured no difference: the vector stays in cache, so the extra passes cost nothing.
  • Small batches. The kernel is latency-bound (1.15× instead of 1.3×). A single sampling softmax on an H100 is ~0.5 µs of bandwidth, so launch overhead dominates it.
  • The cost is extra exps. The rescale adds work per element. That's harmless on a memory-bound op, but in FlashAttention-3/4 exp throughput becomes the bottleneck, and FA4 rescales only when the max jumps by more than log2256 = 8 (see FA3, FA4, FlashInfer).
