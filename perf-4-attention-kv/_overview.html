KV memory is the currency of serving

Overview of perf-4, the attention and KV cache course. It is also called KV cache management, or attention systems. It ties together the section-by-section walks of online softmax, FlashAttention 1 and 2, GQA, MLA, PagedAttention, SGLang's RadixAttention and Mooncake. Paper numbers name their GPU and model; the Llama-3.1-8B on H100 numbers are our recomputation from the course labs.

In one breath

Once the weights are loaded, what's left of GPU memory is a pool of KV cache. How many users fit is that pool divided by the bytes each user holds, and in decode every one of those bytes is read every step. So nearly everything in this course either shrinks the bytes per token (GQA, MLA, quantization, sliding windows), stops wasting the pool (paging), avoids storing the same bytes twice (copy-on-write, radix-tree prefix caching, a cluster-wide KV store), or computes attention without ever writing the N×N score matrix (online softmax → FlashAttention). The first three decide how many users fit and how fast decode runs. The last decides how fast prefill runs and how long a context can get.

Filled in for Llama-3.1-8B on one H100 at 8k context with every byte used: 63.9 GB ÷ (128 KiB × 8,192) = 59 sequences. The decode step then reads 59 × 1.07 GB of KV plus 16.06 GB of weights, which is 23.7 ms per step, or 2,489 tokens/s. The KV is 80% of the bytes. Halve the bytes per token and roughly twice as many users fit, each step reading the same total, so throughput nearly doubles. That holds until the step turns compute-bound (perf-2's Bcrit).

The same thing in plain text:

users that fit = (GPU memory − weights) × share used ÷ (KV bytes per token × tokens per user) KV bytes per token = 2 × layers × KV heads × head dim × bytes decode step ≈ users × KV bytes per user ÷ bandwidth + weights ÷ bandwidth

The mental model: every technique attacks one term

FlashAttention sits apart because it is about the attention computation: it never writes S or P (8.59 GB per layer at 8k for 32 heads in BF16) to HBM, which makes prefill faster and long context possible. Decode attention still has to read the whole KV cache every step, so the other three columns are what move decode.

The rows don't simply multiply. Each "fewer bytes" row only pays until the step becomes compute-bound: MQA's 32× smaller KV buys 28.9× throughput for Llama, and KIVI-2 at 297 sequences sits right at that edge. Paging and prefix caching change what fits, not the bytes per token, so they stack with the first group. FlashAttention barely changes decode, which is dominated by reading the cache; it changes prefill and what context lengths are possible.

The words people use

Online softmax, logsumexp

Keep a running max m and running sum ℓ, and rescale ℓ when the max rises. Two partial (m, ℓ) pairs merge exactly, so a row can be processed in tiles. FA2 stores only L = m + log ℓ for the backward pass.

IO-awareness, SRAM vs HBM

Count bytes moved, not FLOPs. FlashAttention moves Θ(N²d²/M) elements of HBM traffic instead of Θ(Nd + N²). It does more FLOPs (75.2 vs 66.6 GFLOPs on GPT-2) and is still 5.7× faster.

GQA, MQA, MLA

GQA shares one K/V head across a group of query heads; MQA shares one across all of them. MLA caches a compressed latent (512 dims plus a 64-dim RoPE key per layer) and folds the up-projections into the query and output weights at inference.

KV block, block table

The KV cache in fixed pages (vLLM's default is 16 tokens, 2 MiB for Llama-3.1-8B). A per-request table maps logical to physical blocks, so waste is under one block. Reference counts and copy-on-write let requests share blocks.

Prefix cache, radix tree, hit rate

Keep finished requests' KV keyed by their token prefix and reuse it for later requests with the same prefix. Hit rate is cached prompt tokens ÷ prompt tokens. Longest-shared-prefix-first order is optimal in the batch setting.

KV tiers, disaggregated KV store

HBM → CPU DRAM → SSD → other machines' DRAM over RDMA. Loading beats recomputing when bandwidth exceeds Mooncake's threshold (6 GB/s for LLaMA3-70B on 8×A800). One node's DRAM holds about 3M tokens of 70B KV.

The takeaway

Treat HBM as a budget of KV bytes and spend it on tokens only once. Pick an architecture with a small KV per token (GQA or MLA), then quantize the cache if quality allows. Page it so nothing is reserved or fragmented, and share every prefix you can, within a GPU (radix tree) and across the cluster (KV store). Use a FlashAttention-family kernel for prefill so long prompts are affordable and never materialise N×N.

Where this doesn't apply as-is: at small batch and short context, the weights, not the KV, dominate each step, so these levers barely move latency. Quantization and speculation (perf-5) matter more there. Once the batch is past Bcrit, fitting more users stops raising throughput. Prefix caching only helps if prefixes actually repeat: in Mooncake's trace over half the cached blocks were never reused. Many of these numbers are paper-specific (OPT-13B on A100, T5 on TPUs, synthetic lab traces), so measure your own workload. The H100 vLLM script in paged-results is the place to start.
