Mooncake I: trading storage for computation

Also called a KVCache-centric architecture, a disaggregated KV cache, Mooncake Store, or KV tiers (HBM → CPU DRAM → SSD → remote DRAM). This is the FAST'25 Mooncake paper (Qin et al., Moonshot AI and Tsinghua) §1–3 and §5.3–5.4. Card 1 of 2: the store and the arithmetic behind it are here. The scheduler that uses them is card 2. Mooncake also has an arXiv tech report (2407.00079) that is a different paper with different numbers. Each number below says which one it comes from.

In one breath

A prefix's KV cache is expensive to compute and cheap to keep, so keep all of it. Pool the spare CPU DRAM and SSD of every machine in the GPU cluster into one shared KV store, and connect it with fast RDMA networking. When a request arrives, load its prefix's KV from the pool instead of running prefill on it again. Loading wins whenever moving the bytes takes less time than the FLOPs it replaces, and that bandwidth bar turns out to be low: a few GB/s.

The setting: Kimi, long contexts, and two pools FAST'25 §1, Fig 2

Mooncake serves Kimi, Moonshot AI's chatbot. The paper says it runs "across thousands of nodes, processing over 100 billion tokens daily", and that long-context inputs are where it helps most. It splits the cluster three ways. A prefill pool processes prompts, and a decoding pool generates tokens (prefill/decode disaggregation, introduced in perf-2). The third part is new: the CPU, DRAM, SSD and RDMA NICs of all those GPU servers, which usually sit underused, pooled into Mooncake Store. The paper calls it a "petabyte-level disaggregated cache" on an RDMA network of "up to 8×400 Gbps". A global scheduler, Conductor, routes each request (card 2). More storage for less computation FAST'25 §2.2, the core argument

A token's K and V depend only on the tokens before it, so any request that repeats a prefix could reuse that prefix's KV (the same fact RadixAttention uses inside one GPU). Other systems keep that cache in local HBM or DRAM, assuming that moving KV between machines needs too much bandwidth. The paper checks that assumption. Prefill on n tokens costs (Eq 1):

8×A800: G = 8 × 312 TF = 2.496e15 FLOP/s B_min = 2·2·2.496e15 / (8·(4·8192 + 22·8192)) = 9.984e15 / 1,703,936 = 5.86 GB/s paper: "6 GB/s" 8×H800: G = 8 × 989 TF = 7.912e15 (our assumption, not in the paper) B_min = 3.165e16 / 1,703,936 = 18.57 GB/s paper: "19 GB/s" check (A800): prefix KV = 8192 × 80 × (2·8192/8) × 2 B = 2.68 GB 2.68 GB / 5.86 GB/s = 458 ms to load 80·(4·8192²·8192 + 22·8192·8192²) = 1.143 PFLOP 1.143 PFLOP / 2.496e15 = 458 ms to recompute (break-even)

The paper's point is that 6 GB/s is small. A 100 Gbps NIC carries 12.5 GB/s. The paper adds that the real requirement is higher, because the transfer stages can't be perfectly overlapped with compute, and that "a fully utilized 100 Gbps NIC" per A800 machine meets it (§5.4.2). The bar is lower for bigger models: B_min shrinks as b·d and gqa grow, because a bigger model spends more FLOPs per byte of KV it stores.

Worked example: Llama-3.1-8B on one H100 our recomputation

Same inequality for the running example: l = 32, d = 4096, gqa = 32/8 = 4 query heads per KV head, s = 2, G = 989 TF. We keep the paper's a = 4. For b we use the same convention: 2 FLOPs per weight, divided by d². A layer has 2d² for Q and O, 2·d·(d/4) for K and V, and 3·d·14,336 for the MLP, which totals 13d², so b = 26. (Applied to LLaMA3-70B the same count gives 25.5, not the paper's 22. The paper doesn't derive its 22.) The KV check also works: 32 × (2·4096/4) × 2 B = 131,072 B, the course's 128 KiB/token.

Grey track = 64 GB/s. For this model, B_min is 9.29 GB/s at most, reached as p → 0 where only the b·d term is left, and it falls as the prefix grows. A 400 Gbps NIC has 5.6× headroom over the 1k-prefix bar and a 100 Gbps NIC has 1.4×. At prefix 8k, loading 1.07 GB takes 21.5 ms over the NIC instead of 151 ms of prefill. The 8B model needs 7.18e-6 bytes of bandwidth per FLOP at 8k, about 3× the 70B's 2.35e-6. That is the paper's "larger d" point, seen from the other side.

Read together: one machine's DRAM holds too few tokens to catch most repeats, so the pool has to span machines, and a modest network is enough to feed it. The same 1 TB holds 2.5× more tokens of Llama-3.1-8B (7.63M), because the 8B's KV is 128 KiB per token against 320 KiB. Which capacity is enough depends on the traffic. The paper's 50M-token figure is for its own traces.

Why it beats the alternatives

✗ Recompute every prefix

No cache: every request prefills its whole prompt. For the 8B, that is 151 ms of H100 time for each repeated 8k prefix (Eq 1, at a 100% MFU floor). Long, repetitive chat traffic pays this over and over.

✗ Local HBM prefix cache

RadixAttention-style reuse at 3.35 TB/s, but it shares HBM with the running batch: at most 488k tokens of the 8B per H100. In §5.2 vLLM's HBM prefix cache still used 1.43× Mooncake's prefill GPU time on the conversation trace.

✗ Local DRAM cache

About 1 TB, or about 3M tokens of LLaMA3-70B, per node. That is under 50% of the theoretical hit rate on most of the paper's workloads (Fig 9), and a node only hits prefixes that happened to be routed to it.

✓ Global pooled KV store

Every node's DRAM and SSD form one cache that any prefill node can read over RDMA. That beats the local cache by up to +136% hit rate and −48% prefill time (§5.3.2), and it needs only ≈ 6–19 GB/s for LLaMA3-70B (≈ 9 GB/s for our 8B) per the inequality, with 100 Gbps recommended.

The winner is for the paper's traces (Kimi's conversation and tool&agent traffic plus a synthetic mix). Others: LMCache describes itself as "a KV cache management layer for LLM inference". It moves KV out of GPU memory into "a tiered storage hierarchy spanning CPU memory, local storage, and remote backends", and its README lists Mooncake itself among the backends. The same tiering idea, as a layer for engines such as vLLM.

When is storing KV a bad deal?

  • Low bandwidth flips the inequality. For the 8B on an H100, anything below about 9.3 GB/s can lose to recompute on short prefixes. A 25 Gbps link (3.1 GB/s, illustrative) is below it even at 32k (4.16 GB/s needed). The paper's own curve shows TTFT jumping below 100 Gbps.
  • Short prefixes lose on overheads the equation leaves out. Eq 2 is pure throughput. Prefix length barely changes B_min (9.29 → 8.94 GB/s from 0 to 1k tokens), but a 1k prefix saves only about 15 ms, and a hash lookup, a remote round trip and imperfect overlap can eat that. The paper says the real requirement is "even higher" than Eq 2. We infer that short prefixes are where this bites. The paper doesn't measure it.
  • Low reuse means you pay for storage that never hits. The arXiv report (not FAST'25) finds "over 50% of cache blocks remaining unused" in its trace. It also says that up to only 50% of KV can theoretically be reused in its workloads, even with infinite capacity. Random, one-off traffic gets little from any cache.
  • Slow GPUs make storing easier, fast GPUs make it harder. B_min scales with G. An 8×H800 needs about 3× the bandwidth of an 8×A800 (19 vs 6 GB/s), and faster future GPUs will raise the bar again (our inference from the formula).

What people use instead: a local HBM prefix cache when prompts repeat within one server, and smaller KV per token (KV quantization, GQA, MLA), which lowers the bytes side of the inequality and raises how many tokens every tier holds.
