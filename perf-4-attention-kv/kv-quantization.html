Quantizing the KV cache

Also called FP8 KV cache, KV-cache quantization, KIVI or 2-bit KV, and the per-channel vs per-token quantization question. This card covers the FP8 option serving engines ship today, then walks the KIVI paper (Liu et al., ICML 2024) through §3–4: its measurements are on Llama-2, Falcon and Mistral, with the speed test on Llama-2-7B and one A100 80GB. The capacity numbers are our recomputation for the running example, Llama-3.1-8B on one H100.

Prime · 2 minutes before you read

The problem: GQA and MLA are fixed when the model is trained. A serving team with an existing model still pays 128 KiB per token for Llama-3.1-8B, and decode reads all of it each step. Storing each number in fewer bits is the lever they control, but at 2 bits naive rounding wrecks the model.

Where it fits: Third card on bytes per token, and the first a serving team can apply to any model. It reuses the capacity formula (GQA card) and perf-3's FP8 formats, then walks KIVI's study of which axis to quantize along.

  2. Why does one outlier channel in a per-token group make all the normal numbers in that group round to the same level?
  3. Values have no outlier channels. So why does quantizing them per-channel blow up the output error almost 15×?
  4. Per-token groups stream naturally as tokens arrive. What does per-channel quantization of keys need that a stream doesn't give, and how does KIVI's residual window supply it?
  5. At what batch does a smaller KV cache stop buying throughput on the running example, and why?

In one breath

Store each cached key and value in fewer bits: 8 instead of 16 (FP8), or 2 plus a small scale per group (KIVI). Every byte you drop per token means more sequences fit in HBM, and fewer bytes to read on every decode step. At 8 bits a single scale is enough. At 2 bits it only works if you respect the data's shape. Keys have a few huge, fixed channels, so you quantize them channel by channel. Values have no such channels but get mixed by attention, so you quantize them token by token. The newest 128 tokens stay in full precision.

1. Why bits per token are a direct lever

Decode is memory-bound (attention intensity ≈ 4 FLOPs/byte with GQA-4, vs the H100's 295). So a step costs the bytes it reads, and a full H100 always reads about the same 80 GB. Shrinking the KV cache does two things: at the same batch, each step reads fewer bytes, and at a full HBM, more sequences share each step.

2. FP8 KV in practice

FP8 is the default first step because it needs no new data layout. Every K and V number becomes one E4M3 byte (the format, its max of 448 and why scales matter are on tensor cores and low precision). One scale per tensor maps the largest value onto 448: s = amax / 448, stored = E4M3(x / s).

3. KIVI, section by section

FP8 is 2×. Going to 2 bits needs a way to keep the error under control, and KIVI's contribution is the study that finds one. Everyday analogy: rounding a spreadsheet to a coarse grid. Round each column on its own scale if one column holds millions and the rest hold units. Round each row on its own scale if you will later add up just a few rows.

Illustrative: 12 tokens × 16 channels with groups of 4 (KIVI uses groups of 32). Every group gets its own zero-point z = min and step s = (max − min) / (2b − 1), so a 2-bit group has just 4 levels.

§3.1 Preliminary study: what breaks at 2 bits

KV arrives one token at a time, so heavy methods like GPTQ are out and round-to-nearest is the tool. Prior work quantized both caches per token because a new token's row can simply be appended. The authors padded to test every combination with "fake" quantization (quantize, then dequantize), groups of 32, on Llama-2-13B:

The paper's Table 1. Its three observations: 4-bit per-token is fine, 2-bit per-token drops a lot; per-channel values fail whatever you do with keys; at 2 bits the winner is keys per-channel, values per-token.

§3.2 Why keys and values want different axes

Keys: "some fixed channels exhibit very large magnitudes" (Fig 2), the same outlier columns seen in activations before (LLM.int8, AWQ). A per-token group that contains one of those channels stretches its range, and the normal numbers in it all round to the same level. A per-channel group confines the outlier "to each individual channel without impacting the other normal channels".

Values: no outlier pattern. Measured on V itself, per-channel is even slightly better (error 3.73 vs 4.57). But the output is [A·XV]i = Σj Aij [XV]j, and attention is sparse, so "the output is just the combination of value caches of a few important tokens". Per-token quantization keeps each token's error inside that token, so rounding the unimportant tokens can't damage the few that matter.

§3.3 The algorithm: grouped part plus a residual window

Per-token quantization streams easily: quantize the new row and append it. Per-channel can't, because a channel group spans 32 tokens that haven't all arrived yet. KIVI splits each cache in two:

Our redraw of the idea in the paper's Fig 3 (Algorithm 1 in its appendix). Green = quantized, dashed = full precision.

  • Keys: new keys collect in a full-precision residual. When it reaches R tokens it is quantized per channel in groups of G, appended, and emptied. Values: a queue of the last R tokens; the oldest pops out and is quantized per token. So the full-precision window averages R/2 tokens for keys and R for values.
  • Attention logits are computed in two tiles and concatenated: A = [q·Q(Kg)ᵀ, q·Krᵀ]. Dequantization is fused into the matmul ("Q_MatMul", CUDA), and the quantize kernel is written in Triton. During prefill the exact K and V feed the next layer, and only the stored copy is quantized.
  • Settings for every experiment: G = 32, R = 128 (R ≤ 128 and divisible by G). No fine-tuning and no calibration: "tuning-free", "plug-and-play".

From the paper's accuracy table and its ablation table. It attributes the jump from 12.21 to 20.77 to the full-precision window, finds "no consistent pattern" between R = 32, 96 and 128, and says "a reasonably large residual length is important". Group size 128 (R = 128) drops to 17.29. Mistral-7B: 38.36 at 16 bit, 26.46 fake 2-bit, 36.01 KIVI-2.

Speed (Llama-2-7B, one A100 80GB, ShareGPT-like requests averaging 161 prompt + 338 output tokens, batch raised until out of memory, R = 32 and 128): "2.6× less peak memory (including model weight)", "up to 4× larger batch size", "2.35× ∼ 3.47× throughput". That is below our 5.00× for two reasons, both our reading. First, at 499 tokens the window is a quarter of each sequence: with R = 128 the cache shrinks only 2.53×, with R = 32 it shrinks 4.17× (labs/kv-quant.py). Second, the quantize step isn't fused yet: the paper says the speed-up "can be greatly increased" once it is.

Why it beats the alternatives · at 2–3 bits per number

✗ BF16 KV

Exact, but 128 KiB per token: 59 sequences of 8k on an H100, 2,489 tok/s, and each step spends 80% of its bytes on KV.

✗ FP8, one scale per tensor

Simple, one flag in vLLM, no layout change: 2× capacity (119 sequences, 4,986 tok/s). But it stops at 2×. Quality is usually close, yet vLLM still recommends calibrated scales and skipping sensitive layers.

✗ 2 bit per-token, K and V

Streams naturally, but the keys' outlier channels sit in every token group and wipe out the normal channels: CoQA 66.37 → 52.93 and GSM8K 22.67 → 4.55 on Llama-2-13B. Synthetic softmax error 2.817 vs 0.458.

✓ KIVI-2

Keys per channel, values per token, the newest 128 tokens kept in BF16. About 3 bits per number with scales, 5× smaller KV on the running example (297 sequences, 12,437 tok/s upper bound), GSM8K 20.77 vs 22.67, no fine-tuning.

Doesn't quantizing K and V hurt quality?

Sometimes, and you only find out by measuring. FP8 KV is usually a small change, but it depends on the model: vLLM's docs call sliding-window layers "more sensitive", and uncalibrated scales default to 1.0. At 2 bits the naive scheme fails outright, and even KIVI loses about 2 points of GSM8K on Llama-2-13B (22.67 → 20.77). In the paper, maths (GSM8K) suffers most. It also skips MMLU-style tasks on purpose, because they "only involve one decoding step", which is "not suitable for studying the impact of compressed KV cache".

  • When it's not the right choice: short contexts at small batch, where weights dominate the bytes and a smaller KV barely moves the step; models near the compute edge (on the running example, 297 sequences already put the matmuls level with the weight reads); and workloads so short that the full-precision window is most of each sequence (at 499 tokens with R = 128 KIVI shrinks the cache only 2.53×).
  • What people use instead or on top: fewer KV heads at training time (GQA, MLA), then paging so that the smaller cache isn't wasted. DeepSeek-V2 stacks MLA with ~6-bit KV.

Always evaluate on your own task: a long-context and a reasoning benchmark, not just perplexity. Course 7's reliability and quality card covers evaluating a speed change.

Understand and remember

  • Decode is memory-bound → a full H100 reads ~80 GB per step whatever the format → fewer bits per KV number → more sequences share each step (59 → 119 → 297 for BF16 → FP8 → KIVI-2) → throughput scales with the cut → until matmuls (4.82 ms at 297 sequences) match the weight read
  • Keys have a few fixed huge channels → a per-token group spans those channels, so its step is set by the outlier and normal values collapse → per-channel groups confine each outlier to its own channel → key and attention-score error ~3–5× lower
  • Attention is sparse, so each output is a mix of a few tokens' values → per-channel groups let 31 neighbours set an important token's step → per-token groups keep each token's error inside that token → values go per-token (output error 3.55 vs 49.89)
  • Per-channel groups need 32 tokens before they can be quantized → keep the newest R = 128 tokens in full precision, then quantize in groups → streaming works and recent tokens (which attention often weights) stay exact → GSM8K 12.21 → 20.77
  • detail that matters Scales and zero-points are part of the bill: 2 bits + two 16-bit values per 32-number group = 3 bits per number → 24 KiB/token, not 16 → quote bits "including scales"
