RadixAttention II: cache-aware scheduling

Also called longest-shared-prefix-first (LSPF) scheduling, DFS order, the fix for cache thrashing, and, across replicas, prefix-aware routing. This is SGLang (Zheng et al., NeurIPS 2024) §3 "Cache-aware scheduling" with Theorem 3.1, Appendix A.2–A.4 and the §6 evaluation. Card 2 of 2: the tree and its LRU eviction are in card 1. The 64-request batch below is our recomputation, from labs/radix-schedule.py.

In one breath

The radix tree can only reuse KV that is still in memory. So when many requests are waiting, run the ones whose prompt shares the longest prefix with what is cached. Then each shared prefix serves all of its requests back to back, instead of being evicted and recomputed between them. For a fixed batch this order is provably optimal: it is a depth-first walk of the requests' radix tree.

Theorem 3.1: depth-first order is optimal

"For a batch of requests, we can achieve an optimal cache hit rate by visiting the radix tree of the requests in the depth-first search order, with a cache size ≥ the maximum request length. The longest-shared-prefix-first order is equivalent to a depth-first search order." The request radix tree for our batch, drawn in the order LSPF visits it:

Green: each template edge is computed once under LSPF and then hit by its 7 other questions. Right column: how many times FCFS (seed 0) prefilled that template. Visit numbers are the position in the LSPF run. Ties (all matches 0) go to the earliest arrival, which is why T3 comes first.

The proof in Appendix A.3 has two halves:

C≥ ∑e∈edges(T) |e| =8×1,500+64×50=15,200
Tthe radix tree built from all requests in the batch1 root, 8 + 64 edges |e|tokens (KV slots) on edge e1,500 or 50 Ctotal prompt tokens computed, under any orderLSPF: 15,200
  • Lower bound. Every edge's KV has to be computed at least once, so no order can compute less than the sum of edge lengths.
  • DFS meets it. The first time DFS computes an edge, it finishes that edge's whole subtree before leaving. During the subtree the edge is hit every time, and afterwards it is never needed again. If the cache holds at least the longest request (the longest root-to-leaf path), the path being worked on always fits, so the edge is never evicted mid-subtree. Each edge is computed exactly once: C = Σ|e|, and the hit rate is at its maximum.
  • LSPF is a DFS (by induction). At the start nothing is cached, so any request runs and its root path gets cached. After visiting node y, the cached path runs from the root to y, and every unvisited node branches off somewhere on that path. The unvisited request with the longest shared prefix branches off deepest, which is exactly where DFS would go next.

The lab checks it: LSPF computes exactly 15,200 tokens, the bound. The theorem needs only one request's worth of cache, and with BUDGET = 1,550 LSPF still computes 15,200 while FCFS drops to 18.1% (lab, try-this 1). The paper's footnote adds a caveat: "In practice, the computation is not the same as what is described in the proof of Theorem 3.1 because the unpredictable number of output tokens can cause the recomputation of the KV cache." Our lab ignores outputs (one-token answers, like the paper's MMLU runs), so it meets the bound exactly.

Online: DFS gets disrupted, and greedy can starve

A real server doesn't get one fixed batch. New requests keep joining the tree. Appendix A.3 argues the schedule "still approximates the DFS behavior on the augmented part" of the tree. It runs the unfinished subtree under the deepest still-cached node, and evictions shrink the cached set (C → C⁽¹⁾ → … ) until it is back in a valid DFS state. There's no optimality claim for this case. The paper then states the cost plainly: "While greedy cache-aware scheduling can achieve high throughput, it can lead to starvation. We leave its integration with other fair scheduling methods [42] as future work." Our lab shows it with a burst of traffic: one hot template gets 70% of the requests and the other seven share 30%.

In a real engine a hit also shortens prefill, so LSPF should cut the mean wait too (our inference, consistent with the paper's Fig 8(a)(b): lower latency at higher hit rate).

Across replicas: the router's meta-tree (Appendix A.4)

With data parallelism, each worker keeps its own radix tree and a router keeps a meta-tree: a trie of all the workers' sub-trees, recording which device holds what. New requests are prefix-matched on the meta-tree and dispatched by affinity, "measured by the length of the shared prefix with specific workers and other requests in the same group". Router and workers update their trees independently. When a worker evicts, it queues the eviction and the router applies it "during periods of low activity", so the router's view is only weakly consistent. On MMLU with four workers the paper reports "linear scaling and an optimal cache hit rate with minimal overhead". It notes a trade-off between data locality and parallel efficiency and leaves better policies to future work (Preble is concurrent work on this).

The Table 2 ratios are our arithmetic (1.15 / 0.18, 0.10 / 0.02). The paper sums it up as "up to 6×". The 6.4× and 3.7× headlines combine KV reuse, parallelism inside a program and faster constrained decoding. They are not the scheduler alone. Multi-turn chat with long outputs shows "almost no speedup" because decoding dominates. Production hits came from "common system messages, frequently reused example images, and multi-turn chat histories".

Ablation (Fig 8(c), Llama-7B on one A10G, on LLM judge, tree-of-thought, MMLU and short multi-turn chat): no cache, no tree structure (a table-based cache), FCFS schedule, random schedule, no frontend parallelism and no frontend hint are each compared with full optimization. The paper's conclusion: "each of these components is required to achieve the best performance". So scheduling is a measured contributor, not an afterthought. The paper gives the bars only as a figure, so we don't quote their heights. Fig 8(a)(b), on tree-of-thought, shows that a higher hit rate gives a larger batch, higher throughput and lower latency.

The paper's other runtime trick, in one paragraph. For outputs constrained by a regex (such as a JSON schema), SGLang compresses chains of forced single-token transitions in the finite state machine, so a constant run like {"summary": " decodes in one forward pass instead of several (§4; Appendix B calls it jump-forward decoding). On the JSON benchmark that gives 1.6× throughput. Not reusing the preprocessed FSM across a batch makes throughput 2.4× lower. Constrained decoding in engines is covered in perf-5 (inference engines).

Why it beats the alternatives

✗ First-come, first-served

Fair and simple, but it interleaves unrelated prefixes, so LRU evicts a template just before its next request. Our batch: 30.2% hit rate, 36 template recomputations, 1,123.7 ms of prefill. Round-robin arrivals: 0%.

✗ Random order

Statistically the same as FCFS on shuffled arrivals: 28.8% on average, anywhere from 16.6% to 40.8% depending on luck. It is a separate bar in the paper's ablation, and it loses to cache-aware scheduling there too.

✗ LSPF online, with a starvation guard

Needed in practice, but a guard gives up hit rate and any optimality claim. Our age cap (ours, not the paper's) keeps the worst wait at 85 slots instead of 354, but drops the hit rate from 93.2% to 80.4%. The paper leaves fairness to future work [42].

✓ LSPF = DFS order

Each shared prefix is computed once and reused by its whole subtree. That is provably optimal for a batch once the cache holds the longest request. Ours: 84.7%, exactly the 15,200-token lower bound, 4.55× less prefill than FCFS. The paper: ≈ 96% of the optimal hit rate on its benchmarks.

Doesn't reordering hurt fairness and latency?

Yes, it can, and the paper says so. Greedy longest-prefix-first "can lead to starvation". A request that shares nothing with the cache keeps getting sorted behind requests that do. In our burst, cold requests waited 354 slots in the worst case against 85 under FCFS. The paper's own hedge is "In more latency-sensitive settings we may still be able to tolerate limited batch re-ordering". It points to fair-scheduling work (its ref. [42], Sheng et al., "Fairness in serving large language models") and lists "fixing starvation in cache-aware scheduling" as a future direction.

  • Common fixes (our suggestions, not from this paper): cap how long a request may wait (our lab's age cap), bound how far a request can be reordered, or schedule fairly per client and only sort by prefix within that.
  • Mean latency usually improves anyway (our inference). Hits shorten prefill and allow bigger batches, so most requests finish sooner. The cost lands on the tail and on requests that share nothing.

When it doesn't help: if prompts share nothing, every match is 0 and LSPF is just FCFS plus the matching cost. If the cache holds the whole request tree, every order reaches the optimum (lab, try-this 2: all three reach 84.7% at 15,200 slots). And with strict per-request deadlines, a fair or deadline-aware queue matters more than the last few points of hit rate.
