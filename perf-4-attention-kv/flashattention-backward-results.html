FlashAttention III: backward pass and results

Also called recomputation in the backward pass, selective gradient checkpointing, or (for §4) the FlashAttention benchmarks. This card covers the FlashAttention paper's Appendix B (the memory-efficient backward pass, Algorithm 4, Theorem 5, the comparison with Rabe & Staats), its experiments in §4 and Appendix E, and its limitations in §5. All numbers are the paper's, measured on A100s, unless marked "our recomputation".

In one breath

Training needs the attention matrix P a second time, in the backward pass. Standard attention keeps all N×N entries of it in HBM. FlashAttention keeps only two numbers per query row from the forward pass, the running max m and the softmax sum ℓ, and rebuilds each tile of P on chip when the backward pass needs it. That costs about 13% more FLOPs but moves about 9× fewer bytes, so the backward pass gets faster as well as smaller. The paper then shows what this buys: 15% faster BERT, up to 3.5× faster GPT-2, memory that grows linearly in N, and the first Transformers to beat chance on Path-X (16K tokens) and Path-256 (64K).

Algorithm 4: the backward loop

The forward pass (card I) walks K,V blocks in the outer loop and Q blocks in the inner loop. The backward pass does the same, and the choice decides which gradients stay on chip. dKj and dVj depend only on column j, so they build up in SRAM for the whole column and go to HBM once. dQi collects contributions from every column, so it's read, updated and written back to HBM at every step.

Algorithm 4, line numbers in brackets. Block sizes as in the forward pass: Bc = ⌈M/4d⌉, Br = min(⌈M/4d⌉, d). Only one Br×Bc tile of P, dP and dS exists at a time, and it lives in SRAM. The paper: "Conceptually it is just a block version of the derivation in Section B.2."

Theorem 5 gives the IO cost: standard backward Θ(Nd + N²) HBM accesses, FlashAttention backward Θ(N²d²M−1), the same form as the forward pass's Theorem 2 (card II). Both still do O(N²) FLOPs and need only O(N) extra memory beyond the inputs, output and gradients. The paper's Fig 2 measures the whole trade on GPT-2 medium (N = 1,024, d = 64, 16 heads, batch 64, A100, forward + backward):

GFLOPs HBM R/W runtime standard 66.6 40.3 GB 41.7 ms FlashAttention 75.2 4.4 GB 7.3 ms ratio 1.13× 9.2× less 5.7× faster (our recomputation)

How it differs from Rabe & Staats (App B.5)

Rabe and Staats ("Self-attention does not need O(n²) memory") had already shown that attention can run in linear memory. Both methods tile the matrix and recompute it in the backward pass. The paper lists three differences:

FMHA was the starting point for FlashAttention's code. It only supported head dimension 64, sequence length ≤ 512 and A100s. The paper's version added tiling and recomputation to reach 64K, head dims 16–128, and "all Turing and Ampere GPUs at the time of writing". That was true in 2022. Today the repo's README says FlashAttention-2 supports Ampere, Ada and Hopper GPUs, and points Turing (T4, RTX 2080) users to a separate flash-attention-turing repo that "supports a core subset of FlashAttention features". FlashAttention-3 needs an H100/H800, and FlashAttention-4 targets Hopper and Blackwell. The README doesn't say that FlashAttention 1.x is the route for Turing.

Training cares about backward, inference only runs forward

This framing is ours, not the paper's. Everything in §4.1–4.2 is training, and training memory is dominated by activations kept for the backward pass. Keeping P is the quadratic one, and it's the one this card removes. Inference never runs a backward pass:

  • Prefill is one forward pass over the prompt, so it still has an N×N score matrix per head. For an 8,192-token prompt on Llama-3.1-8B that's the same 4.29 GB per layer computed above, just transient. FlashAttention's forward kernel keeps it on chip, so prefill gets the forward half of the win.
  • Decode handles one new query row per step against the KV cache. There's no N×N matrix to avoid, and the step is bound by reading the cache (≈ 4 FLOPs/byte with GQA-4, see attention intensity). The levers there are KV size and layout: GQA, MLA, paging and quantization, later in this course and in perf-5 (inference engines).

What the paper says it can't do (§5)

  • One CUDA kernel per attention variant. Each new variant needs a new hand-written kernel, in a much lower-level language than PyTorch, "and requires significant engineering effort". Kernels may also not carry over between GPU generations. The paper asks for a compiler from high-level code, like Halide for image processing. Triton and FlexAttention-style tools went that way later (our note).
  • Other layers. Attention is the most memory-intensive layer, but every layer touches HBM, so the IO-aware approach could apply more widely (App D).
  • Multi-GPU. The algorithm is "optimal within constants" on one GPU only. Across GPUs, the IO analysis has to count transfers between them too. Ring attention is one answer (long context), and perf-6 (scaling out) covers the rest.

Why it beats the alternatives

✗ Store P for backward

Standard attention (Alg 0 + 3). P, dP and dS are N×N per head: 4.29 GB per layer for Llama-3.1-8B at 8K, 137 GB over 32 layers. It also moves Θ(Nd + N²) bytes. In Table 11, PyTorch runs out of 40 GB after 4K.

✗ Checkpoint the whole layer

Keep only the layer's input and rerun its whole forward pass during backward. Memory drops, but every FLOP runs twice and the N×N matrix is still built in HBM during the rerun. The paper: all such implementations "trade speed for memory". Rabe & Staats end up at roughly standard speed.

✗ Approximate attention

Linformer, Performer, Reformer and others change the model to get linear cost. They're slower than exact FlashAttention below the 512–1K crossover, lose accuracy on LRA (Linformer 54.9 vs 59.8), and none solved Path-X.

✓ Recompute P from (m, ℓ)

Keep 2 numbers per row (2 MiB per layer at 8K) and rebuild each tile of P in SRAM. It's exact, takes 13% more FLOPs but moves 9× fewer bytes, and ran 5.7× faster on GPT-2 medium. The backward pass gets faster, not slower.

Why did FlashAttention enable longer context, not just speed?

Because the limit on long context was memory before it was time. Standard attention's memory is quadratic: 17,024 MB at 4K in Table 21, and out of memory on a 40 GB A100 at 8K. FlashAttention's is linear: 836 MB at 4K, and 13,376 MB even at 64K. Once it fits, speed decides whether training is affordable. At 4K it's 3.3× faster than PyTorch, which is how GPT-2 at 4K context trained faster than Megatron's at 1K. Together they gave the first Transformers above chance on Path-X (16K) and Path-256 (64K). Earlier ones ran out of memory or guessed.

Linear memory doesn't mean linear time. FLOPs are still O(N²), and FlashAttention's time roughly quadruples per doubling of N: 9,341 ms at 64K. Only the block-sparse version (64 ms at 64K) changes that, and it's an approximation.

When it's not the right tool: very short sequences (FlashAttention takes 0.43 ms at 128 and 0.41 ms at 256, so time isn't tracking N and fixed overhead probably dominates, our reading; Apex FMHA was 4% faster there); decode, where the KV cache read is the bottleneck, not an N×N matrix; attention variants nobody has written a kernel for yet (§5), where people fall back to PyTorch/SDPA or a Triton or FlexAttention-style kernel; and older GPUs like the T4, where the speedup is smaller and today's FlashAttention-2 doesn't officially run.
