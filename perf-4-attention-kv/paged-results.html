Before this: PagedAttention II: sharing, copy-on-write and preemption

PagedAttention III: implementation and results

Also called the vLLM engine, KV block size, recompute vs swap, or KV slots. This card walks §5–8 of the PagedAttention paper (Kwon et al., SOSP '23) in order: how vLLM is built, the three custom kernels, the evaluation against FasterTransformer and three versions of Orca, the ablations, and where paging doesn't help. The paper's numbers are OPT and LLaMA models on A100s; Llama-3.1-8B on an H100 is our recomputation.

In one breath

vLLM is a small serving engine (8.5K lines of Python, 2K of C++/CUDA) whose kernels read and write KV blocks through the block table. On traces built from real chat lengths it sustains 1.7×–2.7× the request rate of an Orca that magically knows every output length, and up to 22× that of FasterTransformer, because it fits far more requests in the same memory. The price is a 20–26% slower attention kernel, and the gain disappears where memory isn't the limit.

How vLLM is built (§5)

A FastAPI frontend that extends the OpenAI API (so each request can set its own sampling parameters, such as maximum length and beam width), and a GPU inference engine. The scheduler and block manager are Python; the PagedAttention kernels are custom CUDA. Models (GPT, OPT, LLaMA) are written in PyTorch and Transformers, and NCCL moves tensors between GPUs.

Three custom kernels (§5.1)

PagedAttention reads memory in a pattern existing kernels don't handle well, so vLLM adds three. Each one fuses several small steps into one launch, the same idea as kernel fusion and CUDA graphs.

Three calls cover every decoding algorithm (§5.2)

vLLM implements parallel sampling, beam search and shared prefixes with three methods on sequences. Parallel sampling, for example, forks n outputs from one prompt, appends a token to each every iteration, and frees each one when it stops.

The metric is normalized latency, taken from Orca: each request's end-to-end latency divided by its output length, averaged over all requests. A good server keeps it flat as the request rate rises; when the rate passes capacity, the queue grows without limit and the curve shoots up. "Sustains 2× the request rate" means the knee of that curve is twice as far right.

The abstract's headline, "2-4× with the same level of latency compared to … FasterTransformer and Orca", is a summary of this spread, not one measurement.

Why: more requests in the batch (Fig 13a)

Average number of requests batched together, OPT-13B, ShareGPT at 2 requests/s (Fig 13a labels; bars matched to systems via the text's "2.2× … 4.3×": 30.42 ÷ 13.62 = 2.23, 30.42 ÷ 7.00 = 4.35). Orca (Max)'s 7 is exactly 15,729 slots ÷ 2,048. The whole speedup comes from batch size: the per-step kernels are no faster (§7.1).

The exception (Fig 12f). On OPT-175B with Alpaca, vLLM's lead over Orca (Oracle) and (Pow2) is small. Table 1 gives that setup 264 GB of KV, and Alpaca requests are short, so even wasteful allocators batch a lot of requests and the run becomes compute-bound, not memory-bound. Roughly: 60,075 slots ÷ (19.31 + 58.45) tokens ≈ 773 average-length requests fit even with exact reservation (our arithmetic, ignoring allocator gaps).

Sharing (§6.3–6.4). The more KV the sequences of one request share, the bigger the win: over Orca (Oracle) on OPT-13B and Alpaca, 1.3× with basic sampling rises to 2.3× with beam width 6. Sharing saved 6.1%–9.8% of blocks for parallel sampling and 37.6%–55.2% for beam search on Alpaca; on ShareGPT, 16.2%–30.5% and 44.3%–66.3%. With a shared translation prefix (LLaMA-13B, WMT16 English→German), one example of 80 tokens gives 1.67× and five examples of 341 tokens give 3.58×.

Chatbot (§6.5). Prompts are the chat history cut to the last 1,024 tokens, with up to 1,024 generated. vLLM sustains 2× the request rate of all three Orcas, which behave alike here: with most prompts at 1,024 tokens, the buddy allocator reserves 1,024 output slots whatever length they predict. vLLM doesn't keep KV between chat rounds in this experiment; keeping it is what RadixAttention does.

Where paging fits, and where it doesn't (§8)

  • It fits LLM serving because allocation is dynamic (output length is unknown) and throughput is limited by GPU memory capacity.
  • Not training: tensor shapes are usually static, so memory can be planned ahead of time.
  • Not compute-bound serving (for example non-LLM DNNs): saving memory buys nothing, and the indirection and scattered blocks can make it slower.
  • It bends the OS idea to LLM semantics: swap-out is all-or-nothing, because a request needs every one of its blocks on the GPU to run, and recomputing evicted blocks is something an operating system can't do. Fusing memory access into the attention kernel hides much of the indirection cost.

From the paper to today's vLLM

The 2–4× headline is a 2023 comparison against 2023 baselines (FasterTransformer and the authors' own Orca). Paged KV memory has since spread well beyond vLLM (FlashInfer's paged-KV kernels, for example, are used by SGLang, vLLM, TensorRT-LLM and TGI, per its README), so the paper's baselines are gone and its numbers don't describe current vLLM. What the sources we opened do say:

  • vLLM's V1 engine (alpha announced January 2025) rebuilt the core: a scheduler that treats prompt and output tokens the same way (so chunked prefill falls out naturally), a separate API-server process, and up to 1.7× the throughput of V0, which the blog attributes to lower CPU overhead rather than new kernels.
  • Prefix caching, which the paper handles as reserved shared-prefix blocks (§4.4), is on by default in V1 because it costs almost nothing even at a 0% hit rate; current vLLM source still defaults enable_prefix_caching to true.
  • --gpu-memory-utilization now defaults to 0.92 of GPU memory for the whole instance (weights, activations and KV); the engine fills whatever is left with KV blocks.

We don't quote current vLLM throughput against other engines: it changes release to release and needs a benchmark we haven't run. The H100 script below is the way to get a real number.

The script's second test sends requests that share one 2,000-token prefix plus a 100-token suffix. With prefix caching on, only the suffix needs prefill after the first request. The compute floors at 100% MFU are 2 × 8.03e9 × 2,100 ÷ 989e12 = 34.1 ms for the full prompt against 1.6 ms for 100 tokens (our arithmetic). Measured TTFT will be higher in both cases (queueing, scheduling, the HTTP path), and we make no prediction for the ratio.

Run it yourself

H100 script: labs/h100-vllm-kv.sh [H]. Not yet run by the author. Bash for any rented single-H100 box: it installs vLLM, starts vllm serve for Llama-3.1-8B-Instruct at --gpu-memory-utilization 0.9 and 0.5, greps the start-up log for the KV-cache lines and prints them next to the prediction above, then runs vllm bench serve with a shared 2,000-token prefix, prefix caching on and then off (--enable-prefix-caching / --no-enable-prefix-caching), and prints the mean TTFT for both. About 20–30 minutes including the model download, about $1–2 at $2–3.50 per GPU-hour. Llama-3.1-8B is gated: set HF_TOKEN after accepting its licence, or run it with MODEL=Qwen/Qwen3-8B, which is ungated (the prediction then uses that model's config and weight size).

Why it beats the alternatives

✗ FasterTransformer (static reservation)

Very fast kernels, but no fine-grained scheduling and memory reserved like Orca (Max), so the batch stays small. vLLM sustains up to 22× its request rate on ShareGPT despite a 20–26% slower attention kernel.

✗ Orca (Max)

Iteration-level scheduling, but every request reserves 2,048 slots: 15,729 slots hold 7 requests on OPT-13B. vLLM batches 4.3× more and sustains 2.7×–8× the request rate.

✗ Orca (Oracle), impossible in practice

Reserves exactly the true output length, which no real server knows. Still contiguous chunks with buddy-allocator gaps and no sharing: vLLM batches 2.2× more and sustains 1.7×–2.7× the rate.

✓ vLLM (PagedAttention)

Blocks allocated on demand, shared across samples, beams and prefixes, with fused kernels to hide the indirection. It wins wherever memory limits the batch, and the lead grows with sharing: 2.3× at beam width 6, 3.58× with a 341-token shared prefix.

Why is paging not used for training?

Because training doesn't have the problem paging solves. §8: in DNN training tensor shapes are typically static, so the framework can plan every allocation ahead of time, with no unknown output lengths, no reservation and no fragmentation to recover. Training is also mostly compute-bound (our addition: §8 makes the compute-bound argument about non-LLM serving, not training), and when memory isn't the bottleneck, better memory use buys nothing while the block-table indirection and scattered blocks add overhead (the paper's 20–26% slower attention kernel).

The same logic limits paging in serving. The paper's own OPT-175B on Alpaca run, with lots of KV memory and short requests, turned compute-bound, and vLLM's lead over Orca (Oracle) and (Pow2) shrank (§6.2). Serving non-LLM models that are compute-bound, the paper expects no gain and possibly a slowdown. Where memory does limit the batch, the next wins come from sharing more across requests (RadixAttention) and shrinking each token's KV (GQA, KV quantization), not from paging itself.
