Checkpoint 2: smaller KV, fuller pool

Ties together grouped-query attention, multi-head latent attention, quantizing the KV cache and the three PagedAttention cards (I, II, III): two independent ways to fit more users on one GPU, fewer bytes per token and less wasted pool, and where each one stops paying.

How to use this page. Close the six cards. Answer each question in writing, in full sentences, before opening its Check. A wrong or shaky answer isn't a failure; it tells you exactly which section to reopen. The questions are mixed on purpose, so you have to work out which idea applies before you can answer.

1 · Mixed retrieval

  1. which concept?A team serves Llama-3.1-8B on H100s with paging already on. They need twice as many concurrent 8k-token users next week and can't retrain. Their options: convert to GQA-4, switch to MLA, or turn on FP8 KV. Which idea decides it, and what capacity do they get?
    Check
    • GQA and MLA are fixed at training time; converting needs uptraining (GQA) or retraining (MLA)
    • FP8 KV is a serving switch that halves bytes per token: 128 → 64 KiB
    • 59 → 119 sequences of 8k, 2,489 → 4,986 tokens/s; calibrate scales and check sensitive layers first

    Missed it? Reopen quantizing the KV cache, sections 1–2, and GQA, "Can you convert an existing MHA model to GQA for free?".

  2. Four samples of one 1,000-token prompt, 300 new tokens each, blocks of 16 tokens. Walk through what vLLM stores: how many blocks with and without sharing, and how many block copies happen at the first decode step?
    Check
    • the prompt is 62 full blocks + 1 block with 8 tokens; each finished sample needs ⌈1,300 / 16⌉ = 82 blocks
    • without sharing 4 × 82 = 328 blocks (687.9 MB); with sharing 62 + 4 × 20 = 142 (297.8 MB), −56.7%
    • the partly filled prompt block has ref 4: three writers copy it, the fourth writes in place, so 3 copies

    Missed it? Reopen PagedAttention II, "Worked example: four samples".

  3. which concept?Quantizing both K and V to 2 bits per token drops Llama-2-13B's CoQA from 66.37 to 52.93, while 4-bit per-token was fine. Which idea explains the collapse, and what does KIVI change?
    Check
    • keys have a few fixed, huge channels; in a per-token group the outlier sets the step, and at 4 levels the normal numbers all round to the same value
    • KIVI quantizes keys per channel (outliers stay in their own groups) and values per token (sparse attention keeps each important token's error its own)
    • plus a 128-token full-precision window, which per-channel grouping needs and which recovers accuracy (GSM8K 12.21 → 20.77)

    Missed it? Reopen quantizing the KV cache, §3.1–3.3.

  4. MLA caches 576 numbers per token per layer, yet all 128 of DeepSeek-V3's heads attend with full keys and values. Why doesn't every decode step have to rebuild those keys and values for every past token?
    Check
    • scores are qiᵀWiUKcj, and matrix products are associative
    • so WUK is folded into the query side and WUV into the output projection: attention runs over the cached latents directly
    • RoPE would break this, so position lives in a separate 64-dim key shared by all heads

    Missed it? Reopen MLA, sections 3 and 4.

  5. On one H100 with 63.94 GB free, a reserve-8,192 allocator fits 59 Llama-3.1-8B requests, while the paged simulation fits about 851. Name the three kinds of waste the first one has, and the one waste paging still has.
    Check
    • reserved: slots for tokens not generated yet, locked for the request's life
    • internal fragmentation: slots past the request's real end (88% of KV in the simulation)
    • external fragmentation: allocator gaps between slabs
    • paging keeps only the empty tail of each request's last block: under one block, 1.3% here

    Missed it? Reopen PagedAttention I, "Three kinds of waste" and the worked example.

  6. which concept?In the paper, vLLM's lead over Orca (Oracle) nearly vanished on OPT-175B with short Alpaca requests. Which idea explains it, and would FP8 KV have helped there?
    Check
    • paging only pays when KV memory limits the batch
    • 264 GB of KV and short requests let even wasteful allocators batch hundreds of requests, so the run was compute-bound
    • FP8 KV wouldn't help either: more room for requests buys nothing once the step is compute-bound

    Missed it? Reopen PagedAttention III, "The exception (Fig 12f)" and "Why is paging not used for training?".

  7. Llama-3.1-8B's shape with a single KV head (MQA) would cache 32× fewer bytes than MHA, but the card's H100 table shows only 28.9× more throughput at 8k. What stops the gain, and at 32k would you expect more or less than 32×?
    Check
    • MQA fits 476 sequences; the step's matmuls (2·B·P / C = 7.73 ms) then exceed the weight read (4.79 ms)
    • so the step is no longer only KV + weights read: the compute edge
    • at 32k far fewer sequences fit (MHA 3, MQA 119), every row stays weight-bound, and the gain is the full 33.5×

    Missed it? Reopen GQA, the worked example and its try-this.

3 · Project: a capacity planner for one H100

What it reinforces: bytes per token from KV heads (GQA) and from a latent (MLA), bits per number (KV quantization), blocks and block tables (Paged I), shared blocks (Paged II), and the compute edge where extra users stop paying (Paged III).

Write a short Python script for Llama-3.1-8B on one H100 SXM: 63.94 GB free after 16.06 GB of BF16 weights, 3.35 TB/s, 989 TFLOP/s, 8.03B parameters. Step time = B · KVseq / BW + max(2 · B · P / C, W / BW).

  1. Architecture × format. For 8,192-token sequences, print KV per token, sequences that fit, step time and tokens/s for: MHA (32 KV heads, hypothetical), GQA-8 (the real model), MLA-shaped (hypothetical: (512 + 64) × 32 layers), each in BF16, and GQA-8 in FP8.
  2. Which is compute-bound? For each row, print which term of the max wins. Then add KIVI-2 (3 bits per number with scales, the newest 128 tokens in BF16) and check it against the card's 297 sequences.
  3. A sampling workload. Each request is a 1,000-token prompt with 4 samples of 300 tokens, blocks of 16 tokens. At the end of generation, how many such requests fit with and without block sharing, in BF16 and in FP8 KV?
  4. Explain the stack. In three sentences: which of your rows changed bytes per token, which changed how much of the pool is wasted, and which changed how many copies of the same tokens are stored.
Done when: your table reproduces the cards' 14 / 59 / 119 / 297 sequences and 616 / 2,489 / 4,986 tokens/s, you have the MLA row and the four workload counts, and your three sentences put each lever on the right term.
Check: the numbers (computed with a Python version of this exact planner)
  • MHA 512 KiB: 14 sequences, 22.74 ms, 616 tok/s. GQA-8 128 KiB: 59, 23.70 ms, 2,489. MLA-shaped 36 KiB: 211, 23.81 ms, about 8,860 tok/s (our arithmetic; the card gives 211). GQA-8 FP8 64 KiB: 119, 23.86 ms, 4,986. All weight-bound (4.79 ms beats the FLOP term).
  • KIVI-2: 24 KiB per token plus the BF16 window, 0.215 GB per sequence, 297 sequences, 23.88 ms, 12,437 tok/s. Here the FLOP term (4.82 ms) just passes the weight read: the compute edge.
  • Sampling workload, BF16: 142 blocks × 2 MiB = 297.8 MB shared → 214 requests; 328 blocks = 687.9 MB unshared → 92. FP8 (1 MiB blocks): 148.9 MB → 429; 343.9 MB → 185.
  • Bytes per token: GQA, MLA, FP8, KIVI. Pool waste: paging (these counts already assume it). Copies: copy-on-write sharing. They multiply: FP8 + sharing fits 429 vs 92 for neither.
