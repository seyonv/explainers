How many runs do you need?

Also called power analysis, sample-size planning or the minimum detectable effect. Miller (2024) derives a sample-size formula for paired LLM evals, and Wolfe walks through it; here it is turned into a task count for the false-claim rate, before any money is spent.

Prime · 2 minutes before you read

The problem: You run an experiment, the false-claim rate moves by a few points, and the interval straddles zero. Was there no effect, or were there too few tasks to see one? Without a plan made beforehand those two look identical, and the money is already spent.

Where it fits: The measuring-an-agent card taught you to read an interval after the runs, and that repeats of one task aren't independent. This card turns the same arithmetic around to pick the number of tasks before the runs, and sets the size of the capstone experiment.

You already know: measuring an agent (repeats, a 95% interval, why trials of one task aren't independent). That card reads an interval after the runs. This one picks the number of runs before.

In one breath. Decide the smallest change you care about, how often you can tolerate a false alarm, and how often you can tolerate missing a real change. The formula then says how many tasks you need. Repeats of one task are correlated, so they count for less than new tasks. If the answer is more tasks than you can afford, you learn that before the experiment, not after.

Predict first. You want to know whether compaction raises the false-claim rate from 20% to 30%. With 30 tasks, does going from 3 to 30 repeats per task get you there?

The formula, for a rate measured on the same tasks twice

Setup (the Tuesday run, illustrative): a false claim is a run that ends "all tests pass" while the checker's pytest still exits 1. Every task runs under both conditions, say no compaction and one compaction, m = 3 repeats each. Assume the baseline false-claim rate is 0.20.

ntasks= (zα/2+zβ)2·[p0(1−p0)+p1(1−p1)]Δ2runs per condition, if every run were independent × 1+(m−1)ρmdesign effect ÷ repeats
znormal cut-offs for α/2 and for power1.960 + 0.842 = 2.802 p0, p1false-claim rate without and with the change0.20 and 0.20 + Δ Δminimum detectable effect, p1 − p00.10 to 0.20 mrepeats per task per condition3 ρcorrelation between repeats of one task0.2 or 0.5
Δ = 0.10, ρ = 0.2: runs = 2.802² × (0.20×0.80 + 0.30×0.70) ÷ 0.10² = 7.849 × 0.37 ÷ 0.01 = 290.4 tasks = 290.4 × (1 + 2×0.2) ÷ 3 = 290.4 × 1.4 ÷ 3 = 135.5 → 136 tasks, 816 runs

The left factor is the textbook two-proportion formula. The right factor is the survey-sampling design effect (Kish), which isn't in Wolfe's post. It is Miller's formula in other clothes: his between-question variance ω² and within-question σ²/K become ρ·p(1−p) and (1−ρ)·p(1−p)/m. That rewrite is this card's, and it assumes the two conditions are uncorrelated within a task, which is the cautious case.

Runs = tasks × 3 repeats × 2 conditions. The simulation draws each task's true rate from a beta distribution with the chosen ρ, runs 20,000 fake experiments at that task count, and counts how often a paired test on per-task differences says "significant". It lands on 0.80 every time, so the formula holds under its own assumptions. Halving Δ costs about 4× the tasks, as Wolfe notes (here 3.7×, because the variance also moves with p1).

def tasks_needed(p0, delta, m, rho, alpha=0.05, power=0.8): p1 = p0 + delta z = Z(1 - alpha / 2) + Z(power) deff = 1 + (m - 1) * rho # design effect runs = z**2 * (p0 * (1 - p0) + p1 * (1 - p1)) / delta**2 return runs * deff / m # runs per arm -> tasks $ python3 code/power-analysis.py rho = 0.2: design effect 1.4 delta 0.10: 136 tasks ( 816 runs) sim power 0.799

Repeats only average away the noise within a task. The task-to-task part, ρ × 290.4 = 145.2, never shrinks, so no number of repeats gets below about 145 tasks. Miller's advice, via Wolfe, is the same: raise K until the within-question term is small next to the between-question one, then add questions. That answers the prediction: no. Even with endless repeats, Δ 0.10 needs at least 58 tasks at ρ 0.2 (0.2 × 290.4) and 145 at ρ 0.5, so 30 tasks can't reach it.

What 30 tasks × 3 repeats can see

The capstone's planned size is too small for a 10-point effect. With 30 tasks and 3 repeats per dose, comparing two doses:

smallest change detectable at 80% power: ρ 0.2 → Δ 0.222 (20% → 42%) ρ 0.5 → Δ 0.267 (20% → 47%) chance of catching a true Δ: 0.10 0.15 0.20 ρ 0.2: 27.4% 49.8% 71.5% ρ 0.5: 20.9% 37.5% 56.5%

So the honest claim is: 30 × 3 detects a large compaction effect (false claims roughly doubling) and will usually miss a 10-point one. Pooling the 2 prompts × 2 models gives 12 runs per task per dose and lowers the detectable change to 0.165 (ρ 0.2) or 0.240 (ρ 0.5), but only if the effect and ρ are the same in every cell, which is the thing being tested. The cheaper fix is more tasks, and the pilot audit's job is to measure the baseline and ρ these numbers depend on.

Why it beats the alternatives

✗ Pick n from the budget

You find out afterwards that 30 tasks had a 21–27% chance of seeing a 10-point effect. "Not significant" then means nothing: no effect and too few tasks look the same.

✗ Count runs, not tasks

Treat every run as an independent coin and 290 runs per condition, or 97 tasks × 3, looks enough for Δ 0.10. At ρ 0.2 you need 136 tasks; at ρ 0.5, 194.

✗ Run until it looks significant

Checking after every batch and stopping at the first p < 0.05 gives many chances to hit a false alarm, so the real α is well above 0.05. (General statistics, not from the post.)

✓ Power analysis first

Fix α, power and the smallest change that matters, estimate the baseline and ρ from a pilot, and get a task count, or learn the eval isn't worth running, before spending anything.

Is the answer exact?

No. It is only as good as its guesses: the baseline rate and ρ come from a pilot, and a wrong ρ moves the answer a lot (136 vs 194 tasks above). The formula leans on the normal approximation, and Bowyer et al. (via Wolfe) show CLT-based intervals are too narrow below about 100 questions, which is where 30 tasks sits; report those results with the more robust intervals they suggest.

It is also cautious in one way. The numbers above assume the two conditions don't share task difficulty. Miller notes that scores on the same questions are usually positively correlated, which makes paired comparisons cheaper, so the real requirement can be lower once the pilot measures that correlation. Power analysis is the wrong tool when you aren't testing a change at all: for a one-off rate estimate, size the run by the interval width you want instead.

Understand and remember

  • Smaller Δ → the signal shrinks against the same noise → tasks needed grow as 1/Δ² → a 10-point effect at baseline 0.20 costs 136 tasks where a 20-point one costs 37 (ρ 0.2)
  • Repeats of one task share its difficulty (ρ > 0) → each extra repeat adds less new information → variance per task is p(1−p)(1 + (m−1)ρ)/m, not p(1−p)/m → count tasks, and multiply by the design effect
  • Repeats only average the within-task noise → the between-task part ρ·p(1−p) never shrinks → past a few repeats you must add tasks (≥ 145 tasks at Δ 0.10, ρ 0.5, however many repeats)
  • Fixed budget → solve the formula for Δ instead of n → the minimum detectable effect → 30 × 3 sees only Δ ≈ 0.22–0.27, so a null result there is not evidence of no effect
  • detail that matters The formula and the check both use a normal approximation → at 30 tasks the CLT intervals run too narrow (Bowyer et al.) → plan with the formula but report small-n results with more robust intervals

Reference only

  • z cut-offs 1.960 (α 0.05, two-sided) and 0.842 (power 0.8)
  • the beta-distribution trick for simulating a given ρ (a + b = 1/ρ − 1)
  • Miller's form with ω², σ²_A/K_A and σ²_B/K_B

4 · Compare against what you already know

vs Measuring an agent: That card builds a by-task interval after the runs; this card sizes the run before it. What is the same piece of arithmetic in both, and how does each one fail if you treat runs as independent?

Check
  • both treat the task, not the run, as the unit, because repeats of a task are correlated
  • the interval card divides by √tasks; this card multiplies by the design effect and divides by m
  • after the fact: an interval that is too narrow and a false win; before the fact: too few tasks and an experiment that can't see the effect

vs The group is the baseline.: GRPO compares samples against others for the same prompt; a paired eval compares conditions on the same task. What variance does each remove, and what does each leave behind?

Check
  • both subtract what is shared within a prompt or task, its difficulty
  • GRPO: the group mean is the baseline, so easy and hard prompts don't swamp the advantage
  • paired eval: the per-task difference cancels shared difficulty when the two conditions are positively correlated
  • neither removes the sampling noise within a prompt or task; only more samples or repeats shrink that
