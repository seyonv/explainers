pass@k vs pass^k

Also written Pass@K / Pass^K; pass^k is read "pass hat k". pass@k asks whether an agent solves a task at least once in k tries; pass^k asks whether it solves it every time. τ-bench introduced pass^k for agents that serve users, and Wolfe's agent-evals guide argues it fits agents better than the pass@k most benchmarks still report.

Prime · 2 minutes before you read

The problem: A benchmark says your agent solves 97% of tasks, yet users hit failures constantly. Both can be true: one number counts a task as solved if any of k tries worked, while a user only ever gets one try, every time.

Where it fits: You met pass@3 and pass^3 as counts on a tasks × trials grid in the agent-evals card, and pN for chained steps in compounding errors. This card turns those into formulas, honest estimators from n trials, and a rule for which one to report.

You already know: what pass@3 and pass^3 count on a tasks × trials grid · why chained steps multiply, pN. This card adds the formulas, the honest way to estimate them from n trials, and why averaging over tasks matters.

In one breath. If one trial of a task passes with chance p, then k independent trials contain at least one pass with chance 1 − (1 − p)k, which climbs toward 100%, and are all passes with chance pk, which falls toward 0. A user meets the agent on every run, not on the best of k, so for an agent that does things for people, the falling number is the one they live with.

Estimating them from n trials

You never know p. You run each task n times and count c passes. The unbiased estimators count how many groups of k, chosen from your n trials, would have passed:

pass@kChen et al., 2021 =meantasks [1− (n−ck)(nk) ] passkYao et al., 2024 (τ-bench) =meantasks (ck)(nk)
ntrials you ran on one task (needs n ≥ k)8 below chow many of them passed5 below (n k)"n choose k": number of ways to pick k of the n trials(8 3) = 56
from math import comb def pass_at_k(n, c, k): # 1 - all-k-fail subsets / all subsets return 1 - comb(n - c, k) / comb(n, k) def pass_hat_k(n, c, k): # all-k-pass subsets / all subsets return comb(c, k) / comb(n, k) # the Tuesday task, run 8 times, 5 passed (illustrative) k=1: pass@k 0.625 pass^k 0.625 plug-in (c/n)^k 0.625 k=3: pass@k 0.982 pass^k 0.179 plug-in (c/n)^k 0.244 k=8: pass@k 1.000 pass^k 0.000 plug-in (c/n)^k 0.023

The Tuesday run (illustrative): fix test_parse_due_date, graded by re-running pytest. Suppose 5 of 8 trials pass. pass^3 = (5 choose 3) ÷ (8 choose 3) = 10 ÷ 56 = 0.179; pass@3 = 1 − 1 ÷ 56 = 0.982. pass^8 is exactly 0: no group of 8 was all passes.

Why not just plug in c/n?

true p = 0.70, n = 8, k = 3 true pass^3 = 0.7³ = 0.343 average of (c/8)³ over all outcomes = 0.397 ← plug-in, too high average of C(c,3)/C(8,3) = 0.343 ← exact

Computed exactly over the binomial distribution of c (code/pass-k.py). Raising a noisy estimate to the k-th power inflates it on average, so the plug-in flatters reliability. The counting estimators have no such bias. Chen et al. made the same point for pass@k.

Average per task, then over tasks

two agents, 4 tasks, both pass 70% of all trials (illustrative) even: every task 0.7 pass^8 = 0.7⁸ = 0.058 split: tasks 1.0, 1.0, 0.4, 0.4 pass^8 = (1+1+0.4⁸+0.4⁸) ÷ 4 = 0.500

Same average, almost nine times the pass^8 (0.5003 ÷ 0.0576 = 8.7). τ-bench defines pass^k per task and averages across tasks for this reason: failures cluster on hard tasks. The compounding-errors card shows the real case: gpt-4o's measured pass^8 on τ-bench retail sat far above 0.6128.

How it differs from related ideas

✗ pass@k

Rewards one lucky try. Right when a checker picks the winner from k samples; wrong for a user who gets one run. 5 of 8 reads as 98% at k = 3.

✗ avg@k (mean success)

A fair estimate of p, but blind to whether failures cluster. The even and split agents above both score 70%.

✗ Plug-in (c/n)k

Right idea, biased estimate: 0.397 vs the true 0.343 above. It overstates reliability, most at small n.

✓ pass^k, counted per task

C(c,k) ÷ C(n,k) per task, averaged over tasks. Unbiased, matches what repeat users see, and keeps the clustering that a single p hides.

Is pass^k always the number to report?

No. When something picks the best of k for you (a verifier that keeps the first passing attempt, best-of-n selection, exploration during RL), pass@k is the honest measure of what you get. Report both, with k stated; one alone hides half the picture.

pass^k has its own limits. It assumes trials are independent draws from the same setup; rerunning the identical prompt with a cached environment may agree with itself more than different users would. τ-bench gets its variation from a simulated user who phrases the task differently each time, which is closer to real use. It needs n ≥ k trials per task, so large k is expensive. And it is only as good as the grader: a task that is ambiguous or wrongly specified drags pass^k down without saying anything about the agent. Wolfe cites τ²-bench-verified, which found such task errors in the τ-bench domains.

1 · Core model what to internalise, what to just look up

Keep it if it changes what you can explain, predict, compare, choose, build or debug. Otherwise it's reference.

Understand and remember

  • k independent trials with per-trial chance p → all pass with pk, at least one with 1 − (1 − p)k → as k grows one heads to 0 and the other to 1 → a 70% agent reads 97% at pass@3 and 34% at pass^3
  • A user gets one run each time, with no picker choosing the best of k → their experience over k visits is all-k-succeed → pass^k, not pass@k, measures reliability for agents that act for people
  • Raising a noisy c/n to the k-th power inflates it on average → the plug-in (c/n)k overstates reliability (0.397 vs a true 0.343 at p=0.7, n=8, k=3) → count all-pass k-subsets instead: C(c,k) ÷ C(n,k) is exactly unbiased
  • Failures cluster on hard tasks → per-task rates vary at the same overall average → pk of the average badly underestimates mean per-task pass^k (0.058 vs 0.500) → estimate per task, then average across tasks
  • detail that matters The estimators need n ≥ k trials per task, and pass^k is exactly 0 whenever c < k → large k costs many trials per task, and small c can't distinguish 'rarely all pass' from 'never'

Reference only

  • Chen et al. (2021) introduced the unbiased pass@k estimator 1 − C(n−c,k) ÷ C(n,k)
  • τ-bench (Yao et al., 2024) introduced pass^k, read "pass hat k"
  • Python's math.comb(n, k) computes n choose k
  • Wolfe's example: o4-mini at 26% pass^4 on τ²-bench Telecom
  • avg@k: mean success over k trials, an estimate of p

3 · Retrieve from memory, card closed
  1. concept A colleague says "pass@8 is 99.99%, so the agent is basically perfect." Explain what that number does and doesn't tell you, using p = 0.7.
    Check
    • at p = 0.7, pass@8 = 1 − 0.38 ≈ 99.99%: almost any task gets solved once in 8 tries
    • the same agent has pass^8 = 0.78 = 5.8%: 8 runs in a row nearly never all succeed
    • a user who gets one run each visit lives with pass^k
  2. mechanism Walk through estimating pass^3 and pass@3 for the Tuesday task with n = 8 trials and c = 5 passes.
    Check
    • C(8,3) = 56 possible groups of 3 trials
    • all-pass groups: C(5,3) = 10 → pass^3 = 10 ÷ 56 = 0.179
    • all-fail groups: C(3,3) = 1 → pass@3 = 1 − 1 ÷ 56 = 0.982
    • the plug-in (5/8)3 = 0.244 would overstate pass^3
  3. tradeoff You have budget for 400 runs. Do you run 50 tasks × 8 trials to report pass^8, or 100 tasks × 4 trials to report pass^4? What does each choice cost you?
    Check
    • pass^k needs n ≥ k per task, so pass^8 forces at least 8 trials per task
    • more tasks shrink the task-to-task uncertainty, which usually dominates
    • pass^4 on 100 tasks is better measured; pass^8 tells you about longer streaks but on fewer tasks
    • state k either way; the numbers aren't comparable across k
  4. mechanism Two agents both pass 70% of all trials. Why can one have pass^8 of 0.058 and the other 0.500, and which estimator design captures that?
    Check
    • one fails evenly (every task 0.7), the other clusters failures on hard tasks (1.0, 1.0, 0.4, 0.4)
    • mean of per-task p8 differs even though the mean p is the same
    • τ-bench computes pass^k per task and averages, which keeps the clustering

4 · Compare against what you already know

vs Measuring an agent: The agent-evals card reported pass^3 as a count on a 10 × 3 grid (4 of 10 tasks). How does C(c,k) ÷ C(n,k) generalise that count, and when do the two give the same answer?

Check
  • with n = k = 3, C(c,3) ÷ C(3,3) is 1 if c = 3 else 0: exactly the 'all 3 passed' count
  • with n > k it averages over every group of k trials, using all n runs
  • both are per task, then averaged across tasks
  • neither comes with an interval; that is the error-bars card's job

vs Compounding errors in agent loops: Compounding errors multiplies per-step success over N steps; pass^k multiplies per-trial success over k runs. What is the same, what differs, and how does each fail as a prediction?

Check
  • same arithmetic: everything must go right, so chances multiply (0.9510 ≈ 60%)
  • pN chains steps inside one task; pass^k repeats the whole task
  • both assume independence; clustered failures make measured pass^k sit far above pk (τ-bench retail: below 25% measured vs 2% predicted)
  • checking each step changes pN; nothing inside one run changes how many users hit a bad run

Why this step?

5 · Predict commit to an answer before revealing

A model upgrade lifts every task's per-trial success from 0.70 to 0.80. Before computing: does pass^8 go up by about 14%, about 2×, or about 3×? And pass@8?

Reveal

pass^8 goes from 0.78 = 0.058 to 0.88 = 0.168, about 2.9×. pass@8 barely moves: 99.993% to 99.9997%. Small gains in p are amplified by the k-th power in pass^k and invisible in pass@k, which is why reliability work shows up in pass^k and not in pass@k.
