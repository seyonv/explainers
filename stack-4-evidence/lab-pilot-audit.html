Lab: audit 21,000 public runs

Claim under test: when a public coding agent says "fixed, tests pass" while its own last test run failed, that self-contradiction is common enough to study directly. You re-run the pilot's analysis on 21,438 SWE-bench Verified runs (offline, free), watch 426 automatic flags shrink to 14 genuine ones, and leave with the paper's Figure 1 and the ρ its power analysis needs.

Prime · 2 minutes before you read

The problem: A paper about false success claims needs to know how common they are before it designs an experiment. Guess the base rate and the clustering, and you either build a study that can't detect anything or measure a detector's mistakes instead of agents' behaviour.

Where it fits: The hands-on end of course 4. Error bars that don't lie taught the task-cluster bootstrap and How many runs do you need? left ρ and the baseline as placeholders from a pilot; this lab re-runs that pilot on 21,438 public runs and fills both in.

The claim to test

HypothesisAmong public runs that end in a success claim, a sizeable share (several percent) contradict the agent's own last executed test run, on tests that matter for the task.
ControlThe same claims, split by what the agent's last executed test showed: passed (and the hidden tests then failed: an honest miss), failed, or never ran. Every rate has a 95% interval from resampling tasks (B = 2,000), and the automatic positives were read by hand.
What would change your mindIf the hand audit leaves well under 1% of claims as genuine self-contradiction, natural runs can't power a study of it, and the paper must manufacture the failing state instead.

56 of the 105 fail only on a FAIL_TO_PASS test that the reference test patch rewrites: the agent ran the old test, which encodes the old behaviour, so its failure is what a correct fix produces (a random 20 of them were audited: 19 expected, 1 environment). Of the other 49, 27 were environment or configuration failures (the wrong Python interpreter, network tests, a custom Django runner, or tests the harness passes on the final patch), 6 were old tests again, 2 unclear, and 14 were genuine: the change broke the code or left it broken. The pilot also tried an automatic filter encoding these rules; in-sample it flagged 24 runs of which only 8 were genuine. No automatic rule replaced the reading.

5 · Turn ρ into a task count2 min

Plug the pilot's ρ for task-relevant self-contradiction into the power formula from How many runs do you need?, for a doubling of the rate, at two baselines: the population rate, and a 5% baseline in a setting where the failing state is forced.

python3 - <<'EOF'
z = 1.959964 + 0.841621          # alpha 0.05 two-sided, power 0.80
rho, m = 0.055, 3                # pilot rho (task-relevant SC), 3 repeats
for p0 in (0.0017, 0.05):        # population rate vs a forced-failing baseline
    p1 = 2 * p0                  # detect a doubling
    runs = z**2 * (p0*(1-p0) + p1*(1-p1)) / (p1 - p0)**2
    tasks = runs * (1 + (m - 1) * rho) / m
    print(f"p0 {p0:.4f} -> {p1:.4f}: {runs:8.0f} runs/arm if independent,"
          f" {tasks:7.0f} tasks at rho {rho}, m {m}")
EOF
You should see
p0 0.0017 -> 0.0034:    13812 runs/arm if independent,    5110 tasks at rho 0.055, m 3
p0 0.0500 -> 0.1000:      432 runs/arm if independent,     160 tasks at rho 0.055, m 3

The hypothesis fails. Honest misses outnumber genuine self-contradictions by about 90 to 1, and untested claims are 2–73% of claims depending on the scaffold. That is why the paper was reframed (the series spec's "REFRAME after pilot v2"). It now makes two linked contributions:

  1. An observational decomposition of the claim–pass gap on these ~21,000 runs: untested claims, honest misses, contradictions on unrelated or pre-existing tests, and genuine self-contradiction, per claim and per tested claim, by scaffold and model. Prior work reports the gap; it doesn't split it by cause against the agent's own test evidence at this scale.
  2. A controlled causal test: does compaction while tests are failing turn a rare behaviour into a common one? Its baseline is the dose-0 rate in the same forced-failing setting, not the 0.17% population rate. Step 5 shows why: a doubling from 0.17% needs about 5,110 tasks, from 5% about 160.

ρ is small for self-contradiction (0.055 for task-relevant, 0.082 strict) and large for honest misses (0.32): honest misses are about the task, self-contradictions mostly about the agent. Small ρ means repeats of a task are cheap to add, which is what the branching design does.

Honest caveat. The 14 rest on one reader's judgement, without re-running the tests in the official SWE-bench images, and with no second annotator; the pilot calls 0.17% a lower bound with a rough ceiling near 0.4%. "Claim" means the final prose message only, so scaffolds that end with a bare submit (mini v2, the GPT-5 family) barely claim at all. And step 5 borrows ρ from a different setting: here the repeats of a task are different agents, not reruns of one agent, and the hand-verified ρ (0.003 from 14 events) is not estimable, so the 160 is a starting point for the trigger spike, not a final n.

1 · Core model what to internalise, what to just look up

Keep it if it changes what you can explain, predict, compare, choose, build or debug. Otherwise it's reference.

Understand and remember

  • A detector flags any claim after a failing last test → many failures are pre-existing, environmental or old tests the reference patch rewrites → 105 automatic "task-relevant" cases became 14 genuine ones on reading → a detector-defined metric must be hand-audited before it is trusted
  • Genuine self-contradiction is 0.17% of claims while honest misses are 15.6% → natural runs can't power a study of self-contradiction (a doubling needs about 5,110 tasks) → the paper splits into an observational decomposition plus a controlled test whose baseline is the dose-0 rate in a forced failing state
  • ρ measures how alike outcomes on one task are → honest misses depend on how hard the task is (ρ 0.32), self-contradiction mostly on the agent (ρ 0.055) → low ρ makes extra runs per task nearly as informative as new tasks for the paper's outcome
  • Scaffolds differ most in whether and how agents claim and test (the same model claims success in 29% of runs on one scaffold and 99% on another; untested claims run from 2% to 73%) → a per-claim rate partly compares testing habits → report rates per tested claim too
  • detail that matters Every interval resamples tasks, keeping all runs of a sampled task → runs of one task by different agents aren't treated as independent → the intervals stay honest even with 45 submissions per task

Reference only

  • the label names sc, sc_rel, sc_rel_robust, sc_f2p_mod_only, honest, untested, sc_verified
  • B = 2,000 bootstrap resamples; 45 submissions, 500 Verified tasks
  • the pipeline order: fetch.py → parse.py → detect.py → analyze.py → fig.py
  • disk: 7.06 GB of trajectories, 57 MB detected.jsonl
  • hand-audit counts: 27 environment, 6 old test, 2 unclear, 14 genuine

3 · Retrieve from memory, card closed
  1. concept Explain what an honest miss is, and why it is not a false success claim in the sense of the claim checker.
    Check
    • the agent's last executed test passed and it claimed success, but SWE-bench's hidden tests failed
    • the claim agrees with the evidence the agent had; the evidence was incomplete
    • the claim checker's false claim contradicts the world it can see (its own re-run); this is a gap in the tests, not a contradiction
  2. mechanism Walk a run through the pipeline from a failing last test to a hand verdict of "env_or_config".
    Check
    • the final message matches the claim regex
    • the last test run that executed tests failed: strict sc
    • a failing test is in PASS_TO_PASS and wasn't seen failing before the edit: sc_rel
    • it isn't only a rewritten old test, so it enters the audited bucket
    • reading the output shows, e.g., the base Python interpreter instead of the testbed env: env_or_config
  3. tradeoff You could publish the automatic 1.2% or the hand-verified 0.17%. What does each cost and risk?
    Check
    • 1.2% is reproducible by code but mostly measures environment and old-test artefacts
    • 0.17% measures the phenomenon but rests on one reader, unrepeated tests and no second annotator
    • publish both, with the audit, and re-execute the cases in official images before submission
  4. mechanism Use the pilot's ρ to compute the design effect for m = 3 repeats per task, and say what it does to the task count.
    Check
    • design effect = 1 + (3 − 1) × 0.055 = 1.11
    • tasks = runs per arm × 1.11 ÷ 3
    • so three repeats are worth almost three new tasks; at the card's illustrative ρ 0.5 they'd be worth far less

Why this step?

5 · Predict commit to an answer before revealing

The controlled experiment forces a failing state and finds a dose-0 false-claim rate of 2%, not 5%. Using step 5's formula with ρ 0.055 and m 3, predict roughly how many tasks a doubling now needs, before computing it.

Reveal

Runs per arm scale roughly with 1/p0 for small rates, so going from 5% to 2% multiplies the 432 runs by about 2.5 or a bit more: the formula gives 1,138 runs per arm and 421 tasks at ρ 0.055 and m 3. So either the forced failing state must produce a higher baseline, or the paper must target a larger effect, or it needs many more tasks.
