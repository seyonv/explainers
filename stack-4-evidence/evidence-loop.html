Trace, audit, eval, feedback

Also called observability, the audit trail, evaluation and the production feedback loop; Govindarajan calls the four together "the evidence loop". He builds it in The Agent Stack Part 8, extends it to data agents in Data Agent Stack Part 7, and first sketches it as offline and online loops in OpenClaw Part 6.

Prime · 2 minutes before you read

The problem: A team adds tracing and thinks it has evals, or collects thumbs-downs and thinks the agent is learning. Then the same failure ships again after the next model or prompt change, because nothing that saw it could stop a release.

Where it fits: First card of the evidence course. The claim chain showed that 'done' needs evidence per link; this card asks who keeps that evidence, who judges it, and how a judged failure changes what ships next.

  1. Why should a trace and an audit record share a run ID but live in different stores?
  2. The Tuesday run's trace records exit 1 perfectly. Why does that not make it an eval?
  3. In the loop diagram, why is the dashboard drawn off the loop while the release gate is on it?
  4. Why does changing a grader count as shipping something, even though the agent didn't change?
  5. How can the overall pass rate go up while a release should still be blocked?

In one breath. These are four different jobs, not four names for logging. A trace says what happened in a run. An audit record says under whose authority a side effect happened. An eval judges whether the behaviour was acceptable. Feedback (a thumbs-down, a bad trace, a failed eval) only becomes learning when someone owns it, turns it into a test, and a release gate uses that test to change what ships.

You already know: measuring an agent (tasks, hidden tests, repeats) · 'done' is a chain of states (the Tuesday run's false success claim).

The loop, and the one box that matters

Redrawn from Part 8's loop. The dashboard sits off the loop on purpose: in his words a dashboard informs someone, while a gate changes what ships. The audit box is dashed because it is only needed once a run has a side effect.

OpenClaw Part 6 adds a use: a clean trace separates system faults (one message became two runs) from model faults.

One average is not a gate

He wants pass thresholds set per slice (domain, policy path, failure class), with policy failures as hard blockers that no judge can average away. The reason is just the weighted mean:

poverall= ∑s nsNslice's share of cases × psslice pass rate
sa slice of the eval set, such as a domaincommon, finance ns / Nthat slice's share of all cases160/200 and 40/200 pspass rate within the sliceset per slice by its owner

A small slice has a small weight, so it can collapse while the average rises. Part 7's failure mode: a model upgrade improves common questions and breaks a smaller Finance slice.

from fractions import Fraction as F # exact rates, no float rounding # slice -> (passed, cases); illustrative BASELINE = {"common": (128, 160), "finance": (36, 40)} CANDIDATE = {"common": (152, 160), "finance": (20, 40)} FLOOR = {"common": F("0.80"), "finance": F("0.85")} MAX_DROP = F("0.05") # per slice, vs baseline # plus: every known regression must pass; any policy failure blocks
baseline overall 164/200 = 82% (common 128/160 = 80%, finance 36/40 = 90%) candidate overall 172/200 = 86% (common 152/160 = 95%, finance 20/40 = 50%) average-only gate: SHIP slice gate: BLOCK - finance: 50% < floor 85% - finance: down 40 points

Real output of python3 code/evidence-loop.py; the slice counts and floors are illustrative. Rates are exact fractions: in floating point, 0.90 − 0.85 comes out as 0.050000000000000044, which would wrongly count a drop of exactly 5 points as more than 5. Check: 0.8 × 95% + 0.2 × 50% = 76% + 10% = 86%. On real evals each rate also carries noise, so a floor needs error bars and enough cases (power analysis).

Traces are sensitive data

An agent trace can hold prompts, responses, retrieved documents, tool outputs, user IDs and app state. Part 8 asks for retention, access control, redaction and sampling rules; Part 7 says to keep IDs, versions and hashes and point to sensitive documents in their governed home rather than copy them, and to give the run record itself an access policy and tamper-evident storage.

The emerging standard agrees. In OpenTelemetry's GenAI semantic conventions (status: Development, now kept in their own semantic-conventions-genai repo), the Tuesday run would be an invoke_agent span with a chat span per model call and an execute_tool span for step 6's pytest. Token counts are recommended attributes; the message contents (gen_ai.input.messages, gen_ai.output.messages) are opt-in, flagged as likely to contain personal data. Compaction is not among the well-known operation names, so step 7 would need a custom one. Govindarajan's own caution: the schema is still moving, so don't bet on one vendor's object model.

Same lesson from product churn: Part 7 notes OpenAI's Evals API, used in OpenAI's own data-agent write-up, goes read-only on 31 Oct 2026 and shuts down on 30 Nov 2026 (confirmed on OpenAI's evals guide; that's 30 and 60 days after this card's date, 1 Oct 2026). What lasts is the dataset, comparators, graders, gates and canaries.

Why it beats the alternatives

✗ Trace everything, call it quality

The Tuesday run's trace records exit 1 perfectly and still ends in a false claim. A trace is evidence, not a verdict.

✗ One bucket of logs

Debug and accountability merged: too sensitive to share with every engineer, too weak to say who authorized a refund.

✗ Dashboards and thumbs-down

Signals with no owner and no gate. The same class of failure comes back after the next model, index or schema change.

✓ The evidence loop

Trace and audit share IDs, evals assert the path and final state, every confirmed failure gets an owner and a regression case, and per-slice gates decide what ships.

Does every agent need the whole loop?

No. Part 8 says a trace may be enough for an agent that only drafts a reply; audit records matter once it sends, refunds, writes files or deploys, and his checklist asks for gates on high-risk releases. A weekend hackathon agent needs traces and a handful of regression cases, not a canary pipeline.

Know what the sources are. This is a design argument from careful reading, not a measurement: Govindarajan reports no data on how much gates cut repeat failures. The GitHub, Spotify, Grab and Pinterest practices in Part 7 are what those companies describe doing, cited by him, not things he ran. And a gate is only as good as its evals: a judge that shares the agent's blind spot passes the same wrong answer every release.

1 · Core model what to internalise, what to just look up

Keep it if it changes what you can explain, predict, compare, choose, build or debug. Otherwise it's reference.

Understand and remember

  • A trace records what happened, not whether it was acceptable → a perfect trace can document a bad run → judgment needs a separate eval that asserts the path and the final state (the checker's exit 1, approval-before-refund)
  • A side effect needs accountability, not just debugging → trace and audit share IDs but not storage → merging them makes the debug stream too sensitive to share and the audit record too weak to answer 'who authorized this'
  • A signal (thumbs-down, bad trace, failed eval) changes nothing by itself → an owner labels the root cause and writes a regression case → a release gate runs it and blocks the release if the failure returns → only then has the system 'learned'
  • Anything that can change an answer (model, prompt, tool description, context, index, metric, policy, grader) → is a deployable → needs a version, an owner and a test, and a grader change needs a frozen human-labelled set so a 'change in the ruler' isn't read as an agent improvement
  • detail that matters Overall pass rate is a case-weighted mean of slice rates → a 20% slice can fall from 90% to 50% while the overall rises 82% → 86% → gates need per-slice floors and hard blockers (policy failures, known regressions)
  • detail that matters Message contents are opt-in in the OpenTelemetry GenAI conventions and flagged as likely PII → traces are a sensitive data store → they need retention, access control, redaction and sampling, and the run record should point to sensitive data rather than copy it

Reference only

  • OTel GenAI operation names: invoke_agent, chat, execute_tool, retrieval (status: Development; repo semantic-conventions-genai)
  • content attributes gen_ai.input.messages / gen_ai.output.messages are opt-in; gen_ai.usage.input_tokens / output_tokens are recommended
  • OpenAI Evals API: read-only 31 Oct 2026, shutdown 30 Nov 2026
  • Part 7's release path: change manifest → component evals → end-to-end suite → repeated trials → slice comparison → review → shadow or canary → rollout → monitoring → promote or roll back
  • replay levels in Part 7: exact, behavioural, diagnostic reconstruction

vs 'Done' is a chain of states: The claim chain checks one run link by link; the evidence loop runs across many runs and releases. What does each one decide, which one could have stopped the Tuesday run's false claim, and which stops it from happening again next month?

Check
  • the claim chain decides whether this run's 'done' is true (effect verified fails)
  • an eval on that run catches it; the claim chain is in effect the eval's checklist
  • only the loop, through a regression case and a release gate, stops the same failure from re-shipping

vs Measuring an agent: Measuring an agent compares two harness versions on a fixed task set. What does the evidence loop add on top, and how does each fail when used alone?

Check
  • the loop adds where cases come from (production failures), who owns them, and a gate that blocks releases
  • evals alone: a fixed set ages as production moves and misses the cases you didn't know to write
  • the loop alone without honest eval statistics: a gate reacting to noise, or one average hiding a broken slice

vs The forensics method: The forensics method checks an agent's claims against the evidence its runs leave behind, with negative controls. How is that the same job as a trace plus an eval, and what does the loop do with a finding that a one-off experiment doesn't?

Check
  • both set a claim against recorded evidence: what happened vs what was said
  • forensics is a deliberate experiment pinned to one release; the loop runs on every production run and release
  • the loop turns a confirmed failure into an owned regression case and a gate, so the finding keeps protecting later releases

Why this step?

5 · Predict commit to an answer before revealing

A team's eval set is built entirely from past production incidents, and every release must pass all of them. After a year the gate never fails, yet users keep reporting new problems. Before reading on: what has gone wrong, and which control from the card would have shown it?

Reveal

The offline set only protects known failures; production keeps creating cases nobody wrote down, and the question distribution drifts. Part 7 says offline gates aren't enough: you also need sampled production review, canaries, shadow runs and online monitoring split by signal (satisfaction, reliability, correctness, governance, drift), feeding new cases back in. A gate that never fails is protecting yesterday's workload.

Hint

The script compares exact fractions. Print 0.9 - 0.85 in Python to see what a float gate would have done at 34/40: the drop comes out a hair above 0.05 and blocks. 'At the limit' needs a deliberate rule, and someone who owns it.
