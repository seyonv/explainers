Backprop through log, normalise and exp

Also called: the softmax backward pass, atom by atom; the first half of Exercise 1. Lecture 5 · exercise 1: backproping the atomic compute graph · 0:13:01

Prime · 2 minutes before you read

The problem: loss.backward() hands you every gradient, but if one is wrong you can't say which step broke it. You can only check and debug a backward pass you can write yourself, line by line.

Where it fits: It follows the chunked forward pass and cmp, and it is the micrograd chain rule (gradient from above × local derivative) applied to whole tensors. It covers the first seven gradients of Exercise 1, from the loss back to norm_logits.

Needs first: The forward pass in small steps, and a gradient checker · Backprop by hand with the chain rule

Builds on: The += bug: reused nodes add their gradients · exp and log: turning products into sums · Broadcasting: the two rules · Logits → counts → probabilities: the softmax

You'll meet: gradient from above × local derivative, per tensor the derivatives of log, x⁻¹ and exp a broadcast forward → a sum backward a tensor used twice → += the collapse to (p − 1)/n

By the end: Write dlogprobs through dnorm_logits from memory, explain each local rule and each sum or +=, and read a cmp False as a missing path or a missing sum.

Read with these questions (answer them in your head as you go; don't take notes line by line):

  1. Why are 832 of the 864 entries of dlogprobs exactly zero, and why is each of the other 32 equal to −1/n and not −1?
  2. counts_sum_inv has shape (32, 1) but multiplies a (32, 27) tensor. What does that force its gradient to do?
  3. counts reaches the loss by two routes. Which route does each backward line cover, and what does cmp print if you cover only one?
  4. Why does multiplying by 1/probs make a low-probability correct character pull hardest, and why is that a numerical worry?
  5. After substituting all seven lines, why does the target entry come out as (p − 1)/n and every other entry as p/n?

In one breath: the loss is the last link of a chain that turned logits into probabilities in small steps (exp, sum, invert, multiply, log, pick). You walk that chain backwards one line at a time. Each line multiplies the gradient arriving from above by the local derivative of its one operation, and wherever the forward pass reused or broadcast a tensor, the backward pass has to add up the contributions.

Predict first: counts feeds two places: it is multiplied into probs, and it is summed into counts_sum. If you write only dcounts = counts_sum_inv * dprobs and run cmp, what does it say, and how big is the error?

exact: False | approximate: False | maxdiff: 0.00613. You have only the first path. The missing path adds the same small amount, 1/(n·counts_sum), to every entry of a row. It is largest in the row with the smallest counts_sum (5.0985 here), so maxdiff = 1/(32 × 5.0985) = 0.006129. One += for the second path turns the line True.

The chain you are undoing

A few words first. norm_logits are the network's 27 scores per example, minus each row's maximum. counts = exp(norm_logits) makes them positive. counts_sum is each row's total, shape (32, 1), and counts_sum_inv is 1 over it. probs is each row divided by its total, so it sums to 1. logprobs is its log, and the loss is minus the mean of the 32 log-probabilities of the correct next characters Yb. d<name> means dloss/d<name>, always the same shape as <name>.

Worked example: row 0, one line at a time

Row 0 of the batch has target character Yb[0] = 8. Its numbers (from the lab, torch 2.14): counts[0,8] = 0.19669, counts_sum[0] = 11.0700, so probs[0,8] = 0.19669 / 11.0700 = 0.017768. Each step is the chain rule from micrograd: gradient from above × local derivative.

Three ways to get this chain wrong

✗ = instead of += for counts

Keeps only path 1. cmp says False, maxdiff 0.00613: exactly the 1/(n·S) that path 2 should have added.

✗ Dropping keepdim=True

The sum gives shape (32,) instead of (32, 1), which then broadcasts against (32, 1) into a (32, 32) mess without any error. cmp: False, maxdiff 0.348 (my own check).

✗ Forgetting the sum in step 3

counts * dprobs alone is (32, 27): one gradient per use, not per value. cmp: False, maxdiff 0.507 (my own check).

✓ One line per atom, cmp after each

Every gradient keeps its tensor's shape, broadcasts become sums, reused tensors get +=, and a False points at the exact line that is wrong.

Would you ever write softmax backward like this?

Not in real code. Step 2 divides by probs, which blows up when a probability is tiny (here the smallest target probability is 0.0129, giving a dprobs of −2.42; a confident wrong model can get far smaller probabilities). The seven lines also collapse to (p − one-hot)/n, so frameworks compute that directly, which is what the cross-entropy card does. The atom-by-atom version is for learning each local rule and for finding a bug by bisection.

One odd detail: Karpathy writes counts_sum**-1, not 1.0/counts_sum. On torch 2.14 the lab confirms why: with 1.0/, the same manual gradient is only approximate (maxdiff 9.31e-10, exact False), because autograd takes a slightly different floating-point route.

Keep it if it changes what you can explain, predict, compare, choose, build or debug. Otherwise it's reference.

Understand and remember

  • loss = −mean of 32 picked log-probs → only those 32 entries affect the loss, each with weight 1/n → dlogprobs is −1/32 there and 0 in the other 832
  • counts_sum_inv (32, 1) is broadcast across 27 columns → one value is used 27 times → its gradient is the sum of those 27 contributions, .sum(1, keepdim=True), and keeps the (32, 1) shape
  • counts feeds both probs and counts_sum → two paths to the loss → the gradients add → dcounts needs +=, and with = cmp is off by exactly the missing 1/(n·S) (0.00613)
  • every step is gradient × local derivative (1/x for log, −x⁻² for the inverse, eˣ = counts for exp) → substituting the chain cancels cy → dnorm_logits = (p − one-hot)/n, the short form of the cross-entropy card
  • detail that matters dprobs = dlogprobs / probs → a tiny probability gives a huge intermediate gradient (−2.42 here at p = 0.0129) → that is why real code computes the fused (p − one-hot)/n instead of this chain
  • detail that matters counts_sum**-1 vs 1.0/counts_sum → autograd takes a different floating-point route → the manual gradient is exact with **-1 but only approximate (maxdiff 9.31e-10) with 1.0/

Reference only

  • torch.zeros_like and fancy indexing [range(n), Yb]
  • torch.ones_like(counts) * dcounts_sum as the explicit broadcast
  • the cmp output format (exact / approximate / maxdiff)
  • row 0's numbers: Yb[0] = 8, counts 0.19669, counts_sum 11.0700

5 · Predict commit to an answer before revealing

Row 0 of dnorm_logits sums to −1.86e-9 (essentially zero). The previous forward step was norm_logits = logits - logit_maxes, with logit_maxes of shape (32, 1). Before the next card, predict dlogit_maxes: its size and why.

Reveal

About zero. logit_maxes was broadcast across the row with a minus sign, so its gradient is minus the row sum of dnorm_logits, which is (sum of p − 1)/n = 0 up to float noise. That makes sense: shifting all logits in a row by the same amount leaves the softmax, and so the loss, unchanged. The lab measures values like 1.86e-09, and at most 1.02e-08.
