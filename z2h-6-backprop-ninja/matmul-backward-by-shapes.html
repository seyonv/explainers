Matmul backward is a matmul

Also called: the linear layer's backward pass; backprop through @; deriving gradients from shapes. Lecture 5 · exercise 1: backproping the atomic compute graph · 0:41:39

Prime · 2 minutes before you read

The problem: The output layer logits = h @ W2 + b2 mixes whole matrices, so the scalar chain rule from micrograd doesn't say directly which matrix to multiply by which, or where the transpose goes. Get the order wrong and the code either crashes or, worse, runs and gives wrong gradients.

Where it fits: You've just backpropagated through the softmax chain down to dlogits, and seen that a broadcast forward becomes a sum backward. This card crosses the first linear layer and hands dh on to tanh and BatchNorm. Linear layer 1 on the embedding card reuses exactly the same three lines.

In one breath: the output layer computes logits = h @ W2 + b2. Given the gradient arriving at logits, the gradients for h and W2 are each one more matrix multiply, with a transpose, and the gradient for b2 is a sum over the batch. Derive this once on a 2×2 example. After that, the shapes tell you which arrangement is right.

Some notation first. @ is matrix multiply: an (m, k) matrix times a (k, n) matrix gives (m, n), and the shared inner dimension k is summed away. .T is the transpose, which swaps rows and columns. dX means the gradient of the loss with respect to X. It always has the same shape as X. The gradient arriving from above is called the upstream gradient. Here that's dlogits, the gradient that the cross-entropy cards compute.

Predict first: in D = A @ B + c with 2×2 matrices, the entry a11 (row 1, column 1 of A) affects some entries of D. Which entries of B end up in dL/da11?

b11 and b12, the first row of B. a11 appears in D11 = a11·b11 + a12·b21 + c1 and in D12 = a11·b12 + a12·b22 + c2. Its gradient is dD11·b11 + dD12·b12. That's row 1 of dD dotted with row 1 of B. "Dot with a row of B" is what multiplying by Bᵀ does, which is where the transpose comes from.

In the net: let the shapes choose

Karpathy doesn't memorise these formulas (0:49:49). He rebuilds them from shapes. dh must be (32, 64) like h. The only things available are dlogits (32, 27) and W2 (64, 27). The one way to multiply them into (32, 64) is to line up the 27s, which means transposing W2. The same reasoning gives dW2. Here n = 32 examples in the batch, 64 hidden units and 27 characters.

Why it beats the alternatives

✗ Memorise the formulas

It's easy to flip the order or put the transpose on the wrong matrix. W2.T @ dlogits and dlogits @ W2 look just as plausible as the right answer.

✗ Loop over every entry

Correct, but dW2 alone is 64 × 27 entries, each a sum over 32 examples: 55,296 multiply-adds in Python loops instead of one fast matmul.

✗ Build the full Jacobian

The derivative of every logit with respect to every entry of h is a (32·27) × (32·64) table, 1,769,472 numbers, almost all zero. You only ever need it multiplied by dlogits.

✓ Derive once on 2×2, then match shapes

The small example shows why a transpose appears. After that the shapes pick the one arrangement that fits, and each gradient costs one matmul, the same 55,296 multiply-adds as the forward pass.

When the shapes can't tell you

Shape matching works here because 32, 64 and 27 are all different, so only one arrangement fits. If two dimensions are equal, a wrong answer can have the right shape. For example, with a square 64×64 weight, dD @ W and dD @ W.T are both (32, 64), and the wrong one runs silently. In that case, go back to the 2×2 derivation or trust cmp. The 2×2 example itself is the extreme case: every candidate is 2×2, so there you have to derive.

The trick also only covers matmuls and sums. Elementwise ops like tanh or BatchNorm's normalising step need their own local derivative (next card). It doesn't count as "the gradient is correct" until cmp says so.

1 · Core model what to internalise, what to just look up

Keep it if it changes what you can explain, predict, compare, choose, build or debug. Otherwise it's reference.

Understand and remember

  • aij multiplies row j of B in every entry of row i of D → the chain rule sums dDik·Bjk over k → that is row i of dD dotted with row j of B → dA = dD @ B.T (and by symmetry dB = A.T @ dD)
  • Every dX has the shape of X → only one way to combine dlogits (32,27) with W2 (64,27) into (32,64) → the 27s must meet, so W2 is transposed → dh = dlogits @ W2.T falls out without calculus
  • W2 and b2 are reused by all 32 rows of the batch → a forward reuse becomes a backward sum → dW2 contracts over the 32 examples (h.T @ dlogits) and db2 = dlogits.sum(0)
  • Shape matching only picks the arrangement when the dimensions differ → equal dimensions (a square weight, or the 2×2 example) let a wrong formula have the right shape → it runs silently, so derive or cmp
  • detail that matters Each backward matmul does the same work as the forward one (32·64·27 = 55,296 multiply-adds) → a linear layer's backward pass costs about twice its forward pass, and no Jacobian (1,769,472 numbers for dlogits/dh) is ever built

3 · Retrieve from memory, card closed
  1. concept Explain, without quoting the formula, why the gradient of the left matrix in a matmul ends up multiplied by the transpose of the right one.
    Check
    • aij contributes to every entry Dik in row i, each time multiplied by Bjk
    • the chain rule adds those uses: Σk dDik·Bjk
    • that pairs row i of dD with row j of B, which is what dD @ B.T computes
  2. mechanism Walk through deriving dW2 from shapes alone: what must its shape be, which two tensors can you use, and how do you arrange them?
    Check
    • dW2 must be (64,27), the shape of W2
    • available: h (32,64) and dlogits (32,27)
    • the shared 32 must be the inner dimension, so transpose h: (64,32) @ (32,27) = h.T @ dlogits
    • summing over the 32 is adding up every example's contribution to the shared weight
  3. mechanism With the 2×2 example A=[[1,2],[3,4]], B=[[5,6],[7,8]], dD=[[1,0],[2,−1]], compute dA[2,1] and dc by hand.
    Check
    • dA[2,1] = dD21·b11 + dD22·b12 = 2·5 + (−1)·6 = 4
    • dc = dD.sum(0) = [1+2, 0−1] = [3, −1]
  4. tradeoff You're backpropagating through a layer whose weight is 64×64 with a batch of 64. Can you still rely on shape matching? What would you do instead, and what does it cost?
    Check
    • no: dD @ W and dD @ W.T both have the right shape, and so do several other arrangements
    • derive it (the 2×2 argument generalises) or check each candidate with cmp against autograd
    • the cost is a derivation or one extra autograd run, which is cheap next to a silently wrong gradient

4 · Compare against what you already know

vs Sum and broadcast are each other's backward: db2 = dlogits.sum(0) and dW2 = h.T @ dlogits both add up over the batch. How is the bias case an instance of the sum/broadcast duality, and how does the matmul hide the same sum inside its inner dimension?

Check
  • b2 is broadcast (copied) to 32 rows forward, so its gradient sums the 32 rows backward
  • W2 is also reused by all 32 rows; the matmul h.T @ dlogits performs that sum as its inner-dimension contraction
  • both come from the same rule: a value used many times collects the sum of its gradients
  • failure mode for both: forget the sum (or the transpose) and you get a shape error or a per-example gradient

vs Matrix multiply by shapes: The toolkit card used shapes to check a forward matmul; this card uses them to choose a backward formula. What extra rule makes the backward use possible, and where does it stop working?

Check
  • the extra rule: every gradient has the same shape as the tensor it belongs to
  • forward: shapes confirm an expression is valid; backward: they also pin down the only valid arrangement
  • stops working when dimensions coincide, because then several arrangements fit

vs tanh and BatchNorm, atom by atom: Crossing the linear layer takes three lines found from shapes; crossing tanh needs (1 - h**2) * dh. Why can't shapes derive the tanh line, and what kind of knowledge does it need instead?

Check
  • tanh is elementwise: input, output and gradient all have the same shape, so shapes don't constrain anything
  • you need the local derivative of tanh (1 − tanh²), which is calculus, not bookkeeping
  • matmul backward is determined by structure; elementwise backward is determined by the function

5 · Predict commit to an answer before revealing

Suppose n_hidden were 27 instead of 64, so W2 is a square 27×27 matrix. You mistakenly write dh = dlogits @ W2 (no transpose). What happens when it runs, and what catches the mistake?

Reveal

It runs without any error: (32,27) @ (27,27) gives (32,27), which is exactly h.shape. The values are wrong unless W2 happens to be symmetric. Shape matching can't see it, so only the derivation or cmp (exact: False, approximate: False) catches it. That's why Karpathy keeps the dimensions distinct and checks every line.
