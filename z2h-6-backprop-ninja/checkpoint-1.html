Checkpoint 1: four local rules and a checker you can trust

Ties together why write backprop by hand, the chunked forward pass and cmp, log, normalise and exp, the sum ↔ broadcast duality and matmul backward by shapes, with micrograd's += bug and derivative as a nudge, the toolkit's broadcasting rules and matmul by shapes, and saturated tanh. Lecture 5 · chapters 1–3, up to the hidden layer · 0:00:00 to 0:53:17

Prime · why this checkpoint, why now

You've now walked the gradient from the loss back to the hidden layer h: 11 of the 26 gradients in Exercise 1. At 0:53:17 the lecture goes into tanh and BatchNorm, the longest stretch, and nothing new is added: every line there is one of the rules below, applied again. If a rule is loose now, those twelve lines will feel like guesswork.

  • Leaky abstraction → the backward pass multiplies local slopes, so one slope of 0 (a clamp, a saturated tanh, a dead ReLU) silently zeroes everything behind it.
  • Chunked forward + cmp → about 20 named tensors, retain_grad() on the 19 intermediates, and a verdict per tensor: exact, approximate (allclose), maxdiff.
  • Softmax chain → each line is gradient from above × local derivative (1/x, −x⁻², eˣ); a tensor used twice needs +=, as in micrograd.
  • Sum ↔ broadcast → a broadcast forward is a sum backward, a sum forward is a copy backward; the gradient always has its tensor's shape.
  • Matmul by shapes → the backward pass of @ is two more @s with a transpose, and the bias gradient is a sum over the batch.

How to use this page. Close the cards. Answer each question in writing, in full sentences, before opening its Check. The questions are mixed on purpose and don't say which card they come from: working out which idea applies is half the exercise. A miss tells you exactly which section to reopen.

1 · Mixed retrieval

  1. Row 0 of the batch has target character 8 with counts[0,8] = 0.19669 and counts_sum[0] = 11.0700. Without running anything, get dprobs[0,8] and dnorm_logits[0,8], and say what the whole seven-line chain collapses to for this entry.
    Check
    • p = 0.19669 / 11.0700 = 0.017768; dlogprobs there is −1/32 = −0.03125
    • log's local derivative is 1/p: dprobs = −0.03125 / 0.017768 = −1.7588
    • path 1 into counts: (1/11.0700) × −1.7588 = −0.15888; path 2 adds 0.0028229; total −0.15606
    • exp's local derivative is counts itself: 0.19669 × −0.15606 = −0.030695
    • which is (p − 1)/n = (0.017768 − 1)/32 = −0.030695; every other entry j gets pj/n

    Missed it? Reopen log, normalise and exp, "Worked example: row 0, one line at a time", and the toolkit's softmax and cross-entropy, "Cross-entropy: −log of the right answer's probability".

  2. which idea?A later layer is square: h2 = h1 @ W with W of shape (64, 64) and a batch of 32. You write dh1 = dh2 @ W. It runs and every shape looks right. Which idea tells you this line can be wrong anyway, and what is the right one?
    Check
    • shape matching only works when the dimensions differ; with 64 = 64, dh2 @ W and dh2 @ W.T are both (32, 64)
    • go back to the 2×2 derivation: for D = A @ B, dA = dD @ Bᵀ, so here dh1 = dh2 @ W.T
    • the transpose comes from "dot with a row of B": a11 meets b11 and b12, the first row of B
    • and trust cmp, not the shapes: the wrong version runs silently

    Missed it? Reopen matmul backward by shapes, "When the shapes can't tell you" and "The 2×2 derivation, with numbers", and the toolkit's matmul by shapes, "The shape rule".

  3. You add a constant to every entry of a correct dlogprobs and call cmp. For +1e-9 it prints approximate: True with maxdiff 1.86e-9; for +2e-8 it prints approximate: False. Explain both numbers from the allclose rule.
    Check
    • allclose passes an entry when |dt − t.grad| ≤ 1e-8 + 1e-5·|t.grad|
    • 832 of the 864 true entries are exactly 0, so there the only slack is atol = 1e-8: 1e-9 fits, 2e-8 doesn't
    • 1.86e-9 instead of 1e-9: float32 can't store −0.03125 + 1e-9 and rounds to the nearest neighbour, 2⁻²⁹ = 1.86e-9 away
    • so exact: False with approximate: True is rounding; approximate: False with a maxdiff far above 1e-8 is a bug

    Missed it? Reopen the chunked forward pass and cmp, "The checker: three answers per tensor", and "Does "exact: False" mean I made a mistake?".

  4. which idea?cmp('counts', …) prints exact: False, approximate: False, maxdiff 0.00613. Inside each row the error is the same number in every column, and it is largest in the row with the smallest counts_sum (5.0985). Which idea is missing, and where did you first meet it?
    Check
    • counts reaches the loss by two routes: multiplied into probs and summed into counts_sum
    • you wrote only path 1; path 2 adds 1/(n·S) to every entry of a row, which is why the error is constant along the row
    • largest where S is smallest: 1/(32 × 5.0985) = 0.006129
    • fix: dcounts += torch.ones_like(counts) * dcounts_sum; it's micrograd's rule that a node used twice adds its gradients (b = a + a gives a.grad = 2)

    Missed it? Reopen log, normalise and exp, "Three ways to get this chain wrong", and micrograd's += bug, "The smallest case: b = a + a".

  5. debugYou rebuild the starter code but give BatchNorm its textbook init: bngain = 1, bnbias = 0. The forward loss at step 0 is 3.3396 instead of the lab's 3.3444, and every gradient you write passes cmp first time, including dbnraw = dhpreact. What's wrong?
    Check
    • the loss isn't the problem: 3.3396 is just a different init, and near uniform guessing's 3.2958, as a healthy step-0 loss should be
    • the real bug is dbnraw = dhpreact, which forgot the factor bngain; with bngain = 1 that factor is invisible, so cmp says exact: True, maxdiff 0.0
    • a bias of exactly 0 hides a missing term the same way
    • fix: give biases and BatchNorm parameters small random values, as Karpathy's starter code does; then the same line prints approximate: False, maxdiff 0.0017

    Missed it? Reopen the chunked forward pass and cmp, "Why the starter code uses odd initial values", and the loss you should see at step 0, "What "knowing nothing" should cost".

  6. counts_sum_inv has shape (32, 1) and multiplies the (32, 27) counts. Write its backward line, say why it has a sum in it, and predict what happens if you leave out keepdim=True.
    Check
    • dcounts_sum_inv = (counts * dprobs).sum(1, keepdim=True)
    • each of its 32 values was broadcast across 27 columns, so its gradient is the sum of those 27 uses: a broadcast forward is a sum backward
    • the mirror case is counts_sum = counts.sum(1): a sum forward, so its gradient is copied back across the row
    • without keepdim the sum is (32,); lined up from the right against (32, 1) it broadcasts to (32, 32) with no error; cmp fails with maxdiff 0.348

    Missed it? Reopen sum ↔ broadcast, "Where the net uses it: four lines of exercise 1", and the toolkit's broadcasting rules, "Six shape pairs, lined up on the right".

  7. which idea?A regression model clamps its error to [−1, 1] inside the loss and then squares it. On a dataset where every prediction starts far off (errors −3.0, −1.5, 2.0, 4.0, 2.5) the loss sits at exactly 1.0 forever and nothing errors. Separately, a tanh unit whose input is 3 barely learns. Which one idea explains both, and what is the fix for the loss?
    Check
    • the backward pass multiplies local slopes; a slope of 0 (or nearly 0) cuts off everything behind it
    • clamp's slope is 0 outside ±1, so all five gradients are 0.0 and the clipped δ² is 1 for each: loss 1.0, no movement
    • tanh's local slope 1 − tanh(x)² is 0.00987 at x = 3: about 1% gets through
    • autograd computed both correctly; the leak is in the function. Fix the loss with Huber (gradient capped at a constant, ±0.4 in the card's example) or clip the gradient after backward()

    Missed it? Reopen why write backprop by hand, "The clip-the-loss bug, worked out" and "Two more leaks you've already met", and saturated tanh, "On the way back, tanh is a gate".

  8. dlogit_maxes comes out with entries around 1e-8, never exactly 0, and dlogits passes allclose even if you skip the F.one_hot branch. Why is the true gradient 0, why isn't the printed one, and why write the branch at all?
    Check
    • subtracting the same c from a whole row cancels in softmax (e−c is in the top and the bottom), so the loss doesn't depend on logit_maxes: true gradient 0
    • printed: minus each row's sum of dnorm_logits, which is 0 only up to float32 rounding (largest 1.02e-8 on the M3)
    • skipping the branch leaves dlogits off by that 1.02e-8: approximate: True, exact: False; with it, exact: True
    • it's bookkeeping practice, and the same one-hot pattern routes the gradient of any max (or max-pool) to the winner only

    Missed it? Reopen sum ↔ broadcast, "Why dlogit_maxes is almost exactly 0" and "Is the max branch worth writing?", and the toolkit's softmax and cross-entropy, "Scale stretches it, shift does nothing".
