The embedding gradient: undoing view and indexing

Also called: backprop through an embedding lookup; the dC loop; scatter-add. Lecture 5 · exercise 1: backproping the atomic compute graph · 1:18:32

Prime · 2 minutes before you read

The problem: Without this step the manual backward pass stops at hprebn: you'd have gradients for W2, BatchNorm and tanh, but nothing for W1, b1 or the embedding table C, so the character vectors could never learn.

Where it fits: It is the last stretch of Exercise 1. It reuses the matmul-by-shapes rule from layer 2 and the idea that a value used many times collects the sum of its gradients, now applied to a table lookup.

In one breath: the first three lines of the forward pass look up character vectors (emb = C[Xb]), flatten them (embcat = emb.view(32, -1)) and multiply by the first weight matrix (hprebn = embcat @ W1 + b1). Backward, you undo them in reverse. The matmul gives the same three lines as layer 2. The view is undone by viewing back. The lookup sends each gradient row home to the row of C it was copied from, and adds it there when a character was looked up more than once.

The names, all Karpathy's: C (27, 10) is the embedding table, one row of 10 learned numbers per character (26 letters plus '.'). Xb (32, 3) is the minibatch: 32 examples, each the indices of the 3 previous characters. C[Xb] copies one row of C for each of those 96 indices, giving emb (32, 3, 10). dhprebn (32, 64) is the gradient that arrives from BatchNorm, built on the previous card. As always, dX has the same shape as X.

Predict first: instead of Karpathy's double loop, you write the one-liner dC[Xb] += demb. It runs, and the shapes line up. What does cmp('C', dC, C) print?

False. exact: False | approximate: False | maxdiff: 0.0367 (run in my scratch check against this lab's batch). With fancy indexing, += reads all the old rows first, adds, then writes each row back, so for a repeated index one write overwrites the others instead of adding up. Exactly the 12 characters that appear more than once in this batch come out wrong. The 9 used once are correct, which is why the bug is easy to miss.

Linear 1 is the matmul-by-shapes pattern again: the only arrangements that give (32, 30), (30, 64) and (64,).

The view costs nothing. view doesn't move or change any numbers. It only reads the same 960 numbers as (32, 30) instead of (32, 3, 10), so columns 10–19 of an embcat row are character slot 1 of that example. Its gradient is the same relabelling in reverse. In the lab's batch, embcat.grad[0, 10:13] and emb.grad[0, 1, 0:3] are both [-0.0023, 0.0013, 0.0021], the same three numbers under two names.

The lookup: route each row home, and add

In the forward pass a row of C can be copied into emb many times. Each copy is a separate use of that row, and (as with every tensor used twice in this lecture) the uses' gradients add. So row c of dC is the sum of every demb row whose index was c:

dC[c]= ∑(k,j):Xb[k,j]=c demb[k,j]one 10-number row per lookup

The character 'k' is looked up twice: slot 0 of example 2 (context 'k', 'e', 'i') and slot 1 of example 25 (context '.', 'k', 'o'). Its gradient row is those two rows added, shown here for the first 3 of its 10 numbers, in units of 10⁻⁴:

dembcat = dhprebn @ W1.T         # (32,64) @ (64,30) -> (32,30)
dW1 = embcat.T @ dhprebn         # (30,32) @ (32,64) -> (30,64)
db1 = dhprebn.sum(0)             # (64,)
demb = dembcat.view(emb.shape)   # (32,30) -> (32,3,10)
dC = torch.zeros_like(C)
for k in range(Xb.shape[0]):
    for j in range(Xb.shape[1]):
        ix = Xb[k, j]
        dC[ix] += demb[k, j]     # repeats add up
# the same thing in one call: add row i of the source into row index[i]
dC2 = torch.zeros_like(C).index_add_(0, Xb.view(-1), demb.view(-1, 10))

Then cmp each of embcat, W1, b1, emb, C and dC2 against C. Xb.view(-1) lists the 96 indices in order, and demb.view(-1, 10) lists the matching 96 gradient rows. Unlike dC[Xb] +=, index_add_ adds repeated indices.

Why it beats the alternatives

✗ dC[Xb] += demb

Looks like the loop and runs without error, but repeated indices overwrite each other instead of adding. The 12 repeated characters come out wrong (maxdiff 0.0367); cmp says False.

✗ Reshape demb into C's shape

demb has 960 numbers and C has 270. There's no one-to-one match: 96 lookups land in 27 rows, so some rows need a sum and some get nothing.

✗ One-hot matmul

F.one_hot(Xb.view(-1), 27).float().T @ demb.view(-1, 10) is exact too (maxdiff 0.0). But it builds a 96 × 27 matrix (2,592 entries, 96 of them ones) and does 25,920 multiply-adds to perform 960 additions. That grows with the vocabulary.

✓ Scatter-add: the loop, or index_add_

Each of the 96 lookups adds its row into its character's row once. That's 960 additions, correct for repeats, and bit-exact against autograd. The loop is easiest to read; index_add_ does the same in one call.

Things that look like bugs but aren't

Zero rows are fine. The 6 characters nobody looked up this batch get a gradient of exactly 0, so their rows of C don't move this step. That's correct: they didn't affect this loss. Other batches will update them.

db1 is tiny. Its largest entry here is about 2.3e-9 (computed from autograd's b1.grad in my scratch check). BatchNorm subtracts the batch mean right after linear 1, which removes any constant added to every example, so b1 can't change the loss. Karpathy keeps it "just for fun" (notebook comment) to practise its gradient.

When not to do this by hand: in real code, C[Xb] or nn.Embedding and autograd do this scatter-add for you. And "view back" only undoes a view or reshape. If the forward pass had reordered axes (a permute or a transpose), you'd have to reorder them back, not just view.

Keep it if it changes what you can explain, predict, compare, choose, build or debug. Otherwise it's reference.

Understand and remember

  • emb = C[Xb] copies one row of C per lookup → a character looked up m times is used m times → by the multi-use rule its gradient is the sum of m demb rows → dC[ix] += demb[k, j], a scatter-add
  • view only relabels the same 960 numbers in the same order → its local derivative is the identity → the backward is just dembcat.view(emb.shape), with no arithmetic
  • fancy-index dC[Xb] += demb reads, adds, then writes each index → for a repeated index the writes overwrite each other instead of adding → only repeated characters go wrong (12 rows here, maxdiff 0.0367), so the bug hides behind the correct single-use rows
  • hprebn = embcat @ W1 + b1 is a matmul plus a broadcast bias → same pattern as layer 2 → dhprebn @ W1.T, embcat.T @ dhprebn, dhprebn.sum(0), chosen by matching (32,30), (30,64), (64,)
  • detail that matters BatchNorm subtracts the batch mean right after linear 1 → a constant added to every example (b1) cancels → db1 is about 2.3e-9, and b1 never learns anything useful
  • detail that matters Rows of C that no example looked up get exactly 0 → those characters don't move this step → rare characters learn only on the batches that contain them

Reference only

  • torch.zeros_like(C).index_add_(0, Xb.view(-1), demb.view(-1, 10)), the vectorized scatter-add
  • index_put_(..., accumulate=True) as another correct one-liner
  • the lab batch's counts: 96 lookups, 21 distinct characters, '.' ×29, 6 unused rows
  • the double-loop indices k (example) and j (context slot)

5 · Predict commit to an answer before revealing

Delete the BatchNorm layer so hprebn goes straight into tanh. Would db1 still be about 1e-9? Commit, then reason about which forward step made it vanish.

Reveal

No. The near-zero db1 comes from BatchNorm subtracting the batch mean, which cancels any constant added to every example. Without BatchNorm, b1 shifts each preactivation before tanh, so it changes the loss, and db1 = dhprebn.sum(0) becomes a real, non-zero gradient. The formula for db1 doesn't change; the incoming dhprebn does, since it no longer sums to zero across the batch.
