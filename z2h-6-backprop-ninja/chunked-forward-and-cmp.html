The forward pass in small steps, and a gradient checker

Also called: the "chunkated" forward pass, gradient checking, cmp(). Lecture 5 · starter code · 0:07:26

Prime · 2 minutes before you read

The problem: Writing a backward pass by hand for a whole network gives you 26 gradients and one loss. If any one is wrong, training quietly gets worse, and nothing tells you which line broke.

Where it fits: This is the setup for all of Exercise 1. It reuses Lecture 4's MLP with BatchNorm and the micrograd idea that every intermediate has a gradient; now each intermediate becomes a named tensor you can check against PyTorch.

In one breath: before writing any backward pass by hand, Karpathy rewrites the network's forward pass as about twenty tiny steps, each one a tensor with its own name. He asks PyTorch to keep the gradient of every one of them, so autograd becomes an answer key. A short function, cmp, then checks each gradient you write against that key, one tensor at a time.

Predict first: you write dbnraw = dhpreact and forget to multiply by bngain. If bngain starts as all ones (the usual BatchNorm init), what does cmp say?

exact: True, maxdiff 0.0. Multiplying by 1 changes nothing, so the bug is invisible. With Karpathy's init, where bngain is randomised to between 0.79 and 1.21, the same line prints exact: False, approximate: False, maxdiff 0.0017. That's why the starter code gives every bias and BatchNorm parameter small random values (see the table below).

Twenty small steps

The network is Lecture 4's: a 2-layer MLP (multi-layer perceptron) with BatchNorm, reading 3 characters and scoring each of the 27 possible next characters. A minibatch of n = 32 examples goes through it at once. Normally the last stage is one call, F.cross_entropy(logits, Yb). Here every stage is spelled out so that each intermediate is a separate tensor you can backprop through by hand.

parameters: C 27×10 + W1 30×64 + b1 64 + W2 64×27 + b2 27 + bngain 64 + bnbias 64 = 270 + 1920 + 64 + 1728 + 27 + 64 + 64 = 4,137 gradients to check: 19 intermediates + 7 parameters = 26

PyTorch normally throws away the .grad of intermediate tensors to save memory; it only keeps it for leaf tensors (ones you created, like W1). Calling t.retain_grad() on each of the 19 intermediates before loss.backward() tells it to keep them. The gradient dt of any tensor t always has the same shape as t: emb is (32, 3, 10), hprebn is (32, 64), logits is (32, 27), counts_sum is (32, 1).

The checker: three answers per tensor

cmp(s, dt, t) compares your gradient dt with PyTorch's t.grad in three ways. exact asks whether every entry is bit-for-bit equal. approximate uses torch.allclose, which forgives tiny floating-point differences using this rule for each entry:

|dt−t.grad| ≤ atol10⁻⁸ + rtol10⁻⁵ ·|t.grad|
atolabsolute tolerance: the slack every entry gets, even where the true gradient is 0default 1e-8 rtolrelative tolerance: extra slack in proportion to the entry's sizedefault 1e-5 maxdiffthe largest absolute difference over all entries0.0 when exact

The first gradient is the easiest one. The loss is minus the mean of 32 log-probabilities, so dlogprobs is −1/32 = −0.03125 at the 32 correct characters and 0 at the other 832 of its 864 entries. Here is cmp on the right answer, a nearly right one and a wrong one:

What you pass as dtexactapproximatemaxdiffWhy
dlogprobsTrueTrue0.0the same arithmetic as autograd, bit for bit
dlogprobs + 1e-9FalseTrue1.86e-9far inside 1e-8. It's 1.86e-9, not 1e-9, because float32 can't store −0.03125 + 1e-9 and rounds it to the nearest neighbour, 2−29 = 1.86e-9 away
-dlogprobsFalseFalse0.0625a sign error: |0.03125 − (−0.03125)| = 2/32 = 0.0625

Why the starter code uses odd initial values

Usually you'd start biases at 0, and bngain at 1 and bnbias at 0. Karpathy instead gives b1, b2, bngain and bnbias small random values, noting in the notebook that zeros can hide a broken backward pass. Multiplying by 1 or adding 0 leaves a number unchanged, so a gradient that forgot that factor still matches. The same buggy line, under both inits:

def cmp(s, dt, t):
    ex = torch.all(dt == t.grad).item()
    app = torch.allclose(dt, t.grad)
    maxdiff = (dt - t.grad).abs().max().item()
    print(f'{s:15s} | exact: {str(ex):5s} | '
          f'approximate: {str(app):5s} | maxdiff: {maxdiff}')
# after the forward pass: keep .grad on all 19 intermediates
for t in [logprobs, probs, counts, counts_sum, counts_sum_inv,
          norm_logits, logit_maxes, logits, h, hpreact, bnraw,
          bnvar_inv, bnvar, bndiff2, bndiff, hprebn, bnmeani,
          embcat, emb]:
    t.retain_grad()
loss.backward()
dlogprobs = torch.zeros_like(logprobs)
dlogprobs[range(n), Yb] = -1.0/n
cmp('logprobs', dlogprobs, logprobs)

Why it beats the alternatives

✗ One fused forward pass

With F.cross_entropy and BatchNorm as single calls, you only see gradients at the parameters. A wrong sign in step 3 shows up as a wrong dW1 twenty lines later, with no hint where it started.

✗ Checking only the 7 parameters

Even with the steps split out, comparing only dC … dbnbias tells you that something is wrong, not which of the 26 gradients broke first.

✗ Numerical nudging

Nudge each parameter up and down and re-run the forward pass: 2 × 4,137 = 8,274 passes, and the result is only approximate, so it can never tell you "exact". It's the classic check for a hand-written backward pass when no autograd exists.

✓ Small steps + retain_grad + cmp

One loss.backward() gives autograd's answer for all 26 tensors. You check each gradient the moment you write it, so a mistake is pinned to one line.

Does "exact: False" mean I made a mistake?

Not always. If you compute the same math in a different order, float32 rounding differs by around 1e-9, and approximate: True is the verdict that matters. Writing 1.0/counts_sum instead of counts_sum**-1 already gives exact: False, maxdiff 9.3e-10 (measured on the softmax card). The short analytic formulas in Exercises 2–3 aren't bit-exact either (maxdiff about 1e-8 and 9e-10 on your M3). Only approximate: False, with a maxdiff far above 1e-8, is a real bug.

The chunked pass is a learning and debugging tool, not how you'd train. It keeps all 19 intermediates and their gradients in memory, and it's more code to maintain. Real training code uses fused calls like F.cross_entropy, and Exercises 2–3 derive the equivalent short backward formulas.

Understand and remember

  • Forward pass split into ~20 named tensors → each has its own .grad from autograd → you can check each hand-written d<name> the moment you write it → a mistake is pinned to one line instead of surfacing twenty lines later in dW1
  • PyTorch frees intermediate gradients to save memory → t.grad is None for non-leaf tensors → retain_grad() on all 19 intermediates before loss.backward() → autograd becomes an answer key for every step
  • Same math in a different order → float32 rounds differently (~1e-9) → exact can be False for a correct formula → trust allclose (1e-8 + 1e-5·|x|) and a tiny maxdiff; only approximate: False is a bug
  • Init of exactly 1 or 0 → multiplying by 1 or adding 0 changes nothing → a gradient that forgot that factor still matches (dbnraw = dhpreact is exact: True) → small random inits make the bug show (maxdiff 0.0017)
  • detail that matters counts_sum**-1 rather than 1.0/counts_sum → autograd's backward for the power op matches the hand formula bit for bit → exact: True instead of maxdiff 9.3e-10

Reference only

  • the cmp print format ({s:15s} | exact: … | approximate: … | maxdiff: …)
  • torch.allclose defaults: rtol=1e-05, atol=1e-08
  • the exact retain_grad list and its order
  • parameter shapes: C (27, 10), W1 (30, 64), W2 (64, 27); 4,137 in total
  • the loss 3.3377 in the video vs 3.3444 in the lab (unseeded bngain/bnbias draw)

4 · Compare against what you already know

vs More operations, and PyTorch agrees: In micrograd you checked your Value gradients against PyTorch too. What is fundamentally different about checking at tensor level, and what new way of failing appears?

Check
  • micrograd compared a handful of scalars; here each check covers a whole tensor (up to 32×64 entries)
  • at tensor level you need a verdict over many entries: exact vs allclose vs maxdiff
  • new failure: shapes and broadcasting, so a gradient can have the right values in the wrong shape, or pass only because of a special init

vs Cross-entropy backward in three lines: softmax − one-hot: The atomic backward through cross-entropy checks exact: True; the three-line analytic dlogits only gets approximate: True. Which design choice causes the difference, and when would you pick each?

Check
  • atomic: same operations in the same order as autograd, so bit-identical
  • analytic: a simplified formula, so rounding differs (maxdiff about 1e-8)
  • pick atomic to learn and debug one step at a time; analytic to train fast with less memory
  • atomic fails by being long and easy to break; analytic fails silently if the derivation has an error and you don't check it

Why this step?

5 · Predict commit to an answer before revealing

You add one more intermediate to the forward pass but forget to put it in the retain_grad list. What does cmp do when you check its gradient?

Reveal

It crashes rather than printing False. The tensor's .grad is None (PyTorch warns that you're reading .grad of a non-leaf tensor), so dt == t.grad is a plain Python False, and torch.all(False) raises a TypeError. An error you can't miss is better than a silent pass.
