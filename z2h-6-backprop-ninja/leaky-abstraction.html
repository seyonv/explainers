Why write backprop by hand?

Also called: backprop is a leaky abstraction; becoming a backprop ninja. Lecture 5 · intro: why you should care & fun history · 0:00:00

Prime · 2 minutes before you read

The problem: loss.backward() always returns some gradient. If a flat operation, a dead unit or a badly placed clip zeroes it, training quietly slows or stops and nothing raises an error.

Where it fits: You built autograd yourself in micrograd and saw saturated tanh and dead neurons in the BatchNorm lecture. This card explains why the whole next lecture throws loss.backward() away and does every tensor's backward pass by hand.

In one breath: loss.backward() computes every gradient for you, but it can't tell you when those gradients are useless. If you don't know what each operation passes backwards, a flat function, a dead unit or a misplaced clip can quietly stop learning, and nothing crashes. So for one lecture you throw autograd away and write the backward pass yourself.

Three words first. The gradient of the loss with respect to a number (written pred.grad or dpred) says how much the loss moves if that number nudges up. The backward pass (backprop) computes all of them, from the loss back to the inputs, using the chain rule. Each operation multiplies the incoming gradient by its own local gradient, the slope of that one operation. If any slope on the way is 0, everything behind it gets 0.

Predict first: a model predicts 2.5 where the target is 0. The loss clips the error to [−1, 1], then squares it. What gradient does that prediction get?

Exactly 0. After clipping, the error is 1.0 whether the prediction is 1.5, 2.5 or 100, so nudging it changes nothing. The worst prediction in the batch is the one the model ignores. Autograd computes that 0 correctly; the loss itself is wrong.

The clip-the-loss bug, worked out

Karpathy's example from the wild (at about 0:02:18) is code that meant to limit how hard big errors push, and clipped the error inside the loss instead. Here it is on five predictions, all with target 0, so the error delta equals the prediction (toy numbers, chosen for this card).

The two outliers, the examples the model is most wrong about, get no gradient at all. What was intended is the Huber loss: it equals δ² inside ±1 (here scaled ×2 to match) but keeps a constant slope outside, so the gradient is capped at ±0.4 instead of zeroed.

Two more leaks you've already met

Saturated tanh. tanh's local gradient is 1 − tanh(x)². Once a unit's input is a few units from 0, almost nothing passes back through it:

input xlocal gradient 1 − tanh(x)², linear scalevalue x = 0
1.00e+00 x = 1
4.20e-01 x = 2
7.07e-02 x = 3
9.87e-03 x = 5
1.82e-04

At x = 3 only about 1% of the gradient gets through; at x = 5, about 0.02%.

Dead ReLU. ReLU passes x if x > 0, else 0, so its slope is 0 for negative inputs. Give a unit weights [−1, −2] and 100 positive inputs: every input lands on the flat side, and its weight gradient comes out [0.0, 0.0]. It never gets a push to recover. Karpathy's list also includes gradients that explode or vanish as they're multiplied through many steps of a recurrent net (no numbers on this card).

▶ Build itruns on your M3 · about 2 s

When: pause at 0:02:18, while Karpathy shows the clipping bug (chapter 1 starts at 0:00:00). Before running it, predict which of the five gradients come out 0.

import torch
import torch.nn.functional as F
r = lambda t: [round(v, 3) for v in t.tolist()]
pred = torch.tensor([-3.0, -0.5, 0.2, 0.8, 2.5], requires_grad=True)
delta = pred - 0.0                        # all five targets are 0
loss_bug = (torch.clamp(delta, -1, 1)**2).mean()   # clip, then square
loss_bug.backward()
grad_bug = pred.grad.clone(); pred.grad = None
loss_ok = 2*F.huber_loss(pred, torch.zeros(5), delta=1.0)
loss_ok.backward()
print('grad, clipped delta    :', r(grad_bug))
print('grad, Huber (intended) :', r(pred.grad))

You should see (measured on your M3):

grad, clipped delta    : [0.0, -0.2, 0.08, 0.32, 0.0]
grad, Huber (intended) : [-0.4, -0.2, 0.08, 0.32, 0.4]

About ten years before the lecture, writing the backward pass yourself was simply how it was done.

Why it beats the alternatives

✗ Trust autograd as a black box

It computes the gradient of the loss you wrote, bugs included. The clipped loss runs without errors while two of five examples get no gradient.

✗ Only watch the loss curve

Saturated or dead units still let the loss go down, just slower. The curve tells you something is off, not which operation is swallowing the gradient.

✗ Hand-write every backward pass forever

The 2006–2014 way: slow to write, easy to get subtly wrong, and every model needs a gradient checker. Autograd won for good reasons.

✓ Write it by hand once, then use autograd

After you've derived each op's local gradient yourself, you can read a model and predict where the gradient will stop, then debug it.

Does this mean you should stop calling loss.backward()?

No. Every other lecture in the series trains with autograd, and so will you. This lecture is an exercise, like doing long division once so a calculator's answers make sense. The aim is to understand the flow, not to ship hand-written gradients.

And clipping itself is fine when it's aimed at the gradient. If big errors should push less, use a Huber-style loss, or clip the gradient after backward() (the GPT-2 lecture uses clip_grad_norm_ for this). Clipping inside the loss throws away exactly the examples you most need.

1 · Core model what to internalise, what to just look up

Keep it if it changes what you can explain, predict, compare, choose, build or debug. Otherwise it's reference.

Understand and remember

  • Backward pass multiplies local gradients along the path → one local gradient of 0 zeroes everything behind it → a flat op silently cuts off learning for its inputs
  • Clamping the error inside the loss → clamp has slope 0 outside ±1 → the outliers (the examples the model is most wrong about) get gradient 0 → the fix is to cap the gradient (Huber loss, or clip after backward()), not the loss
  • tanh flattens for large |x| → 1 − tanh(x)² falls from 1.0 at x = 0 to 0.00987 at x = 3 → saturated units barely learn; ReLU with every input negative → slope 0 → a dead unit never gets the push to recover
  • Autograd differentiates whatever you wrote, exactly → it can't warn you that the gradient is useless → you need to know each op's local gradient to spot and debug these leaks
  • detail that matters Huber loss is δ² (×½ in PyTorch) inside ±1 and linear outside → its gradient is capped at a constant instead of dropping to 0 → outliers still push, just not wildly

Reference only

  • F.huber_loss(pred, target, delta=1.0) is ½δ² inside ±delta (the card multiplies it by 2 to match δ²)
  • torch.clamp(x, -1, 1) syntax
  • the history: Hinton & Salakhutdinov 2006, Karpathy's 2010 MATLAB RBM code, his 2014 numpy code with a gradient checker
  • clip_grad_norm_, the gradient clipping used in the GPT-2 lecture

    Check
    • loss → 1
    • mean and square: 2·clamp(δ)/5 = 2·1.0/5 = 0.4

  3. tradeoff Your model has a few examples with huge errors. Compare clamping δ inside the loss, Huber loss and plain squared error. Which one do you pick and what does each cost?
    Check
    • clamp inside the loss: outliers get 0 gradient, so they're ignored
    • Huber: outliers push with a capped, constant gradient; you pick the threshold
    • squared error: outliers push with a gradient proportional to δ, which can dominate the batch
  4. mechanism tanh units show 1 − tanh(x)² values of 0.07, 0.0099 and 0.00018 at x = 2, 3, 5. What does that tell you about those units, and what earlier fixes address it?
    Check

    • the weights feeding them barely change
