Sum and broadcast are each other's backward

Also called: the sum ↔ broadcast duality; backprop through the max-subtraction trick. Lecture 5 · exercise 1: backproping the atomic compute graph · 0:22:29

Prime · 2 minutes before you read

The problem: PyTorch broadcasts silently: a (32, 1) column used against a (32, 27) grid is copied 27 times without any line of code saying so. If you backprop through that line as if nothing was copied, your gradient has the wrong shape or the wrong size, and nothing warns you.

Where it fits: You just walked dlogprobs back to dnorm_logits atom by atom, and micrograd taught you that a value used twice gets its gradients added with +=. This card turns that rule into the tensor version: a broadcast is a value used many times at once.

  2. Which axis do you sum over in the backward pass: the one that was stretched, or the one that was already full size?
  3. Why does subtracting each row's maximum leave the loss unchanged, and what must that mean for dlogit_maxes?

In one breath: when the forward pass quietly copies one number into many places (a broadcast), the backward pass must add up the gradients from every copy. When the forward pass adds many numbers into one (a sum), the backward pass hands the same gradient back to each of them. Every d<name> must end up with the same shape as <name>, and this pair of rules is how you get there.

Two words first. Broadcasting is PyTorch stretching a tensor with a size-1 dimension to match a bigger one: in logits - logit_maxes, the (32, 1) column of row maxima is used against all 27 columns of the (32, 27) logits (the raw scores for the 27 characters, one row per example in the minibatch of n = 32). The gradient dlogit_maxes means dloss/dlogit_maxes: how much the loss moves if each entry nudges up.

Predict first: a is (2, 3) and b is (2, 1). You compute (a + b).sum() and call .backward(). What is b.grad?

[3.0, 3.0], not 1. Broadcasting used each entry of b in three columns, and each of those three uses adds 1 to the loss when b nudges up. The three contributions sum. The values in a and b don't matter.

The two rules on a toy

Both are just the chain rule, applied to every place a number is used. Write y for the stretched copy of b:

yij=bi ⇒ ∂L∂bi= ∑j∂L∂yijbroadcast forward → sum backward si=∑jxij ⇒ ∂L∂xij= ∂L∂sisum forward → broadcast backward
i, jrow and column indexi = 0, 1 · j = 0, 1, 2 Lthe number you call .backward() onthe loss ∂L/∂yijgradient arriving at one copy of bi1 each in the toy ∂L/∂sigradient arriving at the row sum10 and 20 in the toy
left : b.grad[i] = 1 + 1 + 1 = 3 → [3.0, 3.0] right: ds = [[10], [20]] → copy along the row → [[10, 10, 10], [20, 20, 20]]

Every copy of b has a local derivative of 1, and every x enters its sum with a coefficient of 1, so all the work is in the bookkeeping.

Where the net uses it: four lines of exercise 1

The softmax part of the forward pass (the previous card) is full of (32, 1) columns meeting (32, 27) grids. Each such line flips direction on the way back:

Forward lineWhat the shapes didBackward line
probs = counts * counts_sum_inv0:22:29(32, 1) broadcast over 27 columns(counts * dprobs).sum(1, keepdim=True)→ dcounts_sum_inv, a sum
counts_sum = counts.sum(1, keepdims=True)0:29:07(32, 27) summed to (32, 1)torch.ones_like(counts) * dcounts_sum→ added into dcounts, a copy
norm_logits = logits - logit_maxes0:33:26(32, 1) broadcast over 27 columns(-dnorm_logits).sum(1, keepdim=True)→ dlogit_maxes, a sum (the minus is the local derivative of -)
logit_maxes = logits.max(1, keepdim=True).values0:38:27(32, 27) reduced to (32, 1), one entry per row winsF.one_hot(ix, 27) * dlogit_maxes→ added into dlogits, a copy to the winner only

keepdim=True keeps the summed axis as size 1, so the result is (32, 1) and lines up with the variable. Without it you get (32,), which broadcasts against the last axis: one_hot(...) * dlogit_maxes then fails with "size of tensor a (27) must match the size of tensor b (32)" (checked on torch 2.14).

Why dlogit_maxes is almost exactly 0

The forward pass subtracts each row's maximum before exp purely for safety: in float32, exp(88) is 1.65e38 but exp(89) is already inf. Shifting a whole row by the same c changes nothing downstream, because the shift cancels in the softmax:

e^(z_k − c) / Σ_j e^(z_j − c) = e^(−c)·e^(z_k) / (e^(−c)·Σ_j e^(z_j)) = e^(z_k) / Σ_j e^(z_j) (e^(−c) cancels)

So the loss doesn't depend on logit_maxes at all, and its true gradient is 0. Numerically, each row of dnorm_logits sums to about zero, and dlogit_maxes is minus that sum. On your M3 the largest entry is 1.02e-8, pure float rounding. (The video says "about 1e-9"; torch 2.14 with this seed gives up to 1e-8.)

Then the second branch: max picks one entry per row, so its local derivative is 1 at the winning position and 0 everywhere else. F.one_hot(ix, num_classes=27) builds exactly that (32, 27) mask of 0s with a single 1 per row, and multiplying by the (32, 1) dlogit_maxes broadcasts each row's gradient onto its winner. Because that gradient is ~1e-8, skipping the branch still passes allclose (maxdiff 1.02e-8); adding it makes dlogits bit-exact.

Why it beats the alternatives

✗ Keep the forward shape

Writing dlogit_maxes = -dnorm_logits gives a (32, 27) gradient for a (32, 1) variable. cmp reports exact False, approximate False, maxdiff 0.031 (checked).

✗ Drop the max branch

Passes allclose here only because this gradient is ~1e-8. The same slip on counts, the previous card's two-branch variable, gives maxdiff 0.0061 and fails.

✗ Loop over every element

Correct, and it makes the "one copy, one contribution" logic explicit, but it runs Python per entry and you still have to remember which axis was stretched.

✓ Flip sum ↔ broadcast

Sum along the axis that was stretched (with keepdim=True), copy along the axis that was summed. Every d<name> gets its variable's shape and cmp goes exact.

Is the max branch worth writing?

For correctness of training, no: its contribution is float noise, and Karpathy says as much at 0:37:15. The exercise asks for it because it is exact bookkeeping practice, and because the same one-hot pattern is how gradient flows through any max or max-pooling: only the winner gets it. In practice you don't backprop through the shift at all; the fused cross-entropy formula (the cross-entropy-analytic card) never mentions logit_maxes.

The duality itself is not optional. Any time a (32, 1) or (1, 64) tensor meets a bigger one, a broadcast has happened whether you wrote it or not, and its backward is a sum. Karpathy states the pair as a rule at about 1:09:45, when it shows up again in BatchNorm's variance.

1 · Core model what to internalise, what to just look up

Keep it if it changes what you can explain, predict, compare, choose, build or debug. Otherwise it's reference.

Understand and remember

  • Broadcast copies one entry into k places → each copy is a separate use with its own gradient → the chain rule adds uses (micrograd's +=) → backward is a sum over the stretched axis, keeping it as size 1
  • A sum gives every input a coefficient of 1 in the output → each input's local derivative is 1 → each gets the output's gradient unchanged → backward is a copy (broadcast) of the output gradient back to the input's shape
  • Softmax is unchanged by shifting a whole row by c → the loss doesn't depend on logit_maxes → its true gradient is 0 → the measured dlogit_maxes (up to 1.02e-8) is float rounding, so skipping its branch still passes allclose
  • max passes one entry per row through and ignores the rest → local derivative is 1 at the winner, 0 elsewhere → one_hot(indices) * dlogit_maxes routes the gradient only to the winner → the same pattern explains max-pooling's backward
  • detail that matters keepdim=True on the backward sum → result is (32, 1), not (32,) → it broadcasts along the right axis next time; a (32,) tensor aligns with the last axis and fails (27 vs 32) or, worse, silently mis-broadcasts when the sizes happen to match

Reference only

  • F.one_hot(ix, num_classes=logits.shape[1]) returns an integer (32, 27) tensor
  • logits.max(1) returns .values and .indices
  • keepdim=True vs keepdims=True (both spellings work on sum)
  • float32 exp overflows to inf just above 88.7

5 · Predict commit to an answer before revealing

Suppose the forward pass subtracted each row's mean instead of its max: m = logits.mean(1, keepdim=True). Would dm still be ≈ 0? What would the second branch into dlogits look like, and how is it different from the one-hot branch?

Reveal

Still ≈ 0: any per-row shift cancels in the softmax, so the loss doesn't depend on m. But the mean uses every entry with coefficient 1/27, so its backward is a copy of dm/27 to all 27 positions, a dense broadcast, instead of the one-hot's single winner. Both contributions are float noise here.
