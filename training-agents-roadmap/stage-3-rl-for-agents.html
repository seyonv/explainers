  1. From RLVR to agent RL

    ~1.5 h

You need this because your environment hands the model a multi-turn game, and this is what changes when the policy acts over many turns.

In RLVR on a maths problem, one episode is one completion: a few hundred tokens, graded once. For an agent, one episode is a multi-turn rollout: the model calls a tool, the environment answers, the model calls another, for minutes or hours, and the reward (tests pass?) arrives only at the end. Three things get harder: rollouts are long and uneven, credit for the final reward has to spread over many actions, and each rollout needs its own sandbox so agents can't break each other or the grader.

That's why the workshop keeps saying environment. An environment packages tasks + a runtime the agent acts in + a grader. The same package serves evaluation (run it, report the score), RL (run it, update on the score), distillation and synthetic data. Build the environment first and the rest reuses it.

  1. The ultimate guide to RL environments

    ~1.5 h

You need this because you're about to write the environment, and this guide is the checklist for it.

The Hugging Face survey (Kolavi, Tunstall, von Werra, Gallouédec, Burtenshaw, Paniego and others) builds the same toy environment in six frameworks (OpenEnv, ORS, NeMo Gym, Verifiers, SkyRL Gym, GEM) and compares them on ten dimensions. Its big claim: the bottleneck has moved from the algorithm to the environment. They all do the same job in different clothes, and the choice is about fit, not capability.

Read it for three ideas. (1) The five-stage spine: tasks → harness → reward → rollout collector → trainer. (2) The first fork is HTTP vs in-process: sandboxed code, shell or browser work wants an environment server; pure-Python games and maths can live inside the trainer. (3) Scale: GRPO needs num_generations × prompts live environments at once (64 × 8 = 512), and the free Spaces tier handles about 128 concurrent sessions, a laptop with Docker about 2,048.

Its companion is FineEnvs (formerly HuggingEnvs): a GitHub repo and Hub org with runnable environment Spaces, task datasets and a Wordle environment written in all six frameworks. You'll use it in stages 7 and 8.

  1. What makes a game a good RL environment

    ~1.5 h

You need this because you're about to decide what feedback the safe may give, and one wrong hint makes a trivial policy optimal.

Adithya Kolavi's GeoGuessr article is the playbook for this stage. It's the story of turning a game into an OpenEnv environment and training Qwen3.5-4B on it, with the dead ends left in. Its criteria for an environment idea: a continuous, verifiable reward; multi-turn play; not saturated (strong models don't already ace it); and cheap to simulate on a CPU. Then: never leak the answer through feedback. Its pin tool never says how close a guess is, or the best policy would just be binary search.

Its war stories are exactly what you'll hit. The first reward scored 77 of 200 episodes at exactly zero, which means zero GRPO advantage, so they added a second, slower decay. The trained model learned to stop exploring: turns fell from 6.7 to 1.1 and it committed from the first frame. That came from the reward's flat region, not a bug. Before training they ran a concurrency test, a no-gradient rollout simulation (which found three bugs) and an overfit-4-tasks run, and watched frac_reward_zero_std. Result: 0.4825 → 0.6445 on 200 held-out tasks, 2nd of 11 models. It cost about $100 on 4×A100s, and it also runs on one.

FineEnvs's six-step recipe, in short: in-process or HTTP? single- or multi-turn? where does the reward come from? stateful tools? build the smallest version first; validate with a rollout, not a training run.

Checkpoint

Closed book. Write your answer before you open each one. If you miss one, reread the block it names, not the whole stage.

  1. Name three things that get harder when RL moves from a single maths answer to a coding agent.

    Answer

    Rollouts become multi-turn and minutes long (and uneven); credit for one end reward must spread over many actions; each rollout needs an isolated sandbox with a grader the agent can't touch. Also: generation cost dominates.

    Reread: From RLVR to agent RL

  2. What does Will Brown mean by “evals and environments are the same thing”?

    Answer

    Both are tasks + a harness the model acts in + metrics. Run it and read the score, and it's an eval; run it and update the model on the score, and it's an RL environment.

    Reread: Watch

  3. Why does synchronous RL leave the trainer idle, and what does async RL pay to fix it?

    Answer

    The trainer can't update until every rollout in the batch is finished, and agent rollouts have a long tail. Async keeps generating while training, so each batch was written by weights one or more updates old (off-policy staleness), which the trainer must correct for.

    Reread: From RLVR to agent RL
