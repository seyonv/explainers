Primer

Read these in order. Each block is short on purpose: the diagram and the “best first” link carry the idea; “Go deeper” is only for when a block doesn't land.

  1. SFT is next-token prediction, masked

    ~2 h

You need this because the next rung imitates a probing script's winning games, which is SFT on traces.

Supervised fine-tuning is the same cross-entropy loss as pretraining, on example conversations. A chat template turns a messages list into the exact token string the model was trained on, with special role markers (<|im_start|>assistant and friends). Get it wrong and the model silently underperforms.

Loss masking means training only on tokens the model should learn to produce. In an agent trace that's the assistant turns: its reasoning and tool calls. System prompt, user task and tool output are masked. Class 1's script turns each assistant turn into a prompt/completion pair (everything before it is the prompt), which is why 627 sessions become 15,251 examples, 6,727 after dropping those longer than 4,096 tokens.

SFT has an emulation ceiling: the model copies the traces, so it can't beat them. Aim it at a narrow job, and pair a task eval (held-out loss on traces) with general ones (HumanEval, MBPP) to catch what it forgot.

  1. LoRA and GPU memory

    ~1.5 h

You need this because you'll fine-tune Qwen3-1.7B on a single cheap GPU, which only fits with LoRA.

LoRA freezes the base weights and learns a thin low-rank correction next to each chosen matrix: h = Wx + (α/r)·BAx. At rank 16 on a 4096×4096 matrix that's 131,072 trainable numbers instead of 16.8 million. Because the frozen weights need no gradients or optimizer state, memory drops from ~16 bytes per parameter to ~2. QLoRA also stores the frozen weights in 4-bit, as Class 1 does (--load-in-4bit).

LoRA usually wants a learning rate about 10× a full fine-tune's: Class 1 uses 2e-4. Gradient accumulation runs small micro-batches before one optimizer step: Class 1's batch 1 × accumulation 16 is an effective batch of 16 on one GPU. Gradient checkpointing recomputes activations instead of storing them.

Lab A · A free SFT run you can watch

Time ~1.5 hCost $0Where Colab T4

Two official TRL notebooks that run on Colab's free T4. The tool-calling one is closest to agent traces.

  1. Run TRL's “Teaching tool calling with SFT” notebookOpen in Colab↗. Before training, print one formatted example and find the tool-call tokens.You should see the model emitting a well-formed tool call it couldn't produce before training.
  2. Or: SFT with LoRA/QLoRA on a free ColabOpen in Colab↗. Change the LoRA rank from 16 to 8 and compare the trainable-parameter count it prints.You should see roughly half the trainable parameters at r = 8.
  3. Count the trained tokens yourself on a real agent trace (Mac, no GPU)
    uv run --python 3.12 --with transformers --with jinja2 --with datasets python - <<'EOF'
import json, os, sys
from datasets import load_dataset
from transformers import AutoTokenizer
tok = AutoTokenizer.from_pretrained("Qwen/Qwen3-0.6B")
row = next(iter(load_dataset("SWE-bench/SWE-smith-trajectories", split="tool", streaming=True)))
raw = json.loads(row["messages"]) if isinstance(row["messages"], str) else row["messages"]
text = lambda c: c if isinstance(c, str) else " ".join(p.get("text", "") for p in c or [])
msgs = [{"role": m["role"], "content": text(m.get("content"))} for m in raw[:6]]
print(tok.apply_chat_template(msgs, tokenize=False)[:1200])
# Class 1's trick: each assistant turn = full prefix minus the prompt before it
n = lambda m, gen=False: len(tok.apply_chat_template(m, tokenize=True, add_generation_prompt=gen, return_dict=True)["input_ids"])
trained = sum(n(msgs[:i + 1]) - n(msgs[:i], True) for i, m in enumerate(msgs) if m["role"] == "assistant")
print("tokens:", n(msgs), "| trained on (assistant turns):", trained)
sys.stdout.flush(); os._exit(0)   # streaming datasets can hang on exit
EOF
    You should see the rendered template with its role markers (tool turns included), then something like tokens: 1061 | trained on (assistant turns): 89. Under 10% of this trace is the model's own writing; the rest is prompt and tool output.
    If it breaks

    Why not return_assistant_tokens_mask=True? Qwen3's chat template has no {% generation %} markers, so that mask comes back all zeros. That's exactly why Class 1 builds prompt/completion pairs and uses completion-only loss instead of assistant_only_loss.

  1. Prepare the data only, on your Mac

    hf jobs uv run --flavor l40sx1 --timeout 30m --secrets HF_TOKEN \
  tutorials/01-sft-on-traces/train_sft.py \

  --gradient-accumulation-steps 1 --logging-steps 1 --eval-steps 1 --save-steps 1 \
  --trackio-project my-sft --trackio-space-id <you>/my-sft-trackio --run-name smoke
    You should see one training step, then “205” LoRA targets verified. This costs cents and catches auth, data-shape and out-of-memory bugs before the hour-long run.
  3. The real run (one variant, not the sweep)
    hf jobs uv run --flavor l40sx1 --timeout 3h -d --secrets HF_TOKEN \
  tutorials/01-sft-on-traces/train_sft.py \
  --output-dir outputs/sft-lr2e4-r16 --hub-model-id <you>/gemma-4-E2B-it-pi-mono-lora \
  --push-to-hub --max-length 4096 --max-steps 200 --learning-rate 2e-4 \
  --lora-r 16 --lora-alpha 32 --gradient-accumulation-steps 16 \
  --trackio-project my-sft --trackio-space-id <you>/my-sft-trackio --run-name lr2e4-r16
hf jobs ps
hf jobs logs --tail 200 <job-id>
    You should see about 65 minutes. In Class 1 this variant ended at train loss 0.65, eval loss 0.55 and eval token accuracy 0.86.

Checkpoint

Closed book. Write your answer before you open each one. If you miss one, reread the block it names, not the whole stage.

  1. Why does Class 1 get 15,251 examples from 627 sessions?

    Answer

    Each assistant turn becomes its own prompt/completion example: the conversation up to that turn is the prompt, the turn is the completion. Many turns per session.

    Reread: SFT is next-token prediction, masked

  2. LoRA r = 16 on a 4096×4096 matrix: how many trainable parameters, and what fraction?

    Answer

    2 × 4096 × 16 = 131,072, which is 0.78% of 16,777,216.

    Reread: LoRA and GPU memory

  3. Roughly how much memory does a full AdamW fine-tune of Qwen3-0.6B need before activations, and why?

    Answer

    ≈ 9.6 GB: 16 bytes per parameter (2 bf16 weights + 2 grads + 4 fp32 master + 8 for Adam's two moments) × 0.6B.

    Reread: LoRA and GPU memory

  4. The class reports HumanEval 0.744 for the adapter. What's missing before you can call it an improvement?

    Answer

    The base model's score on the same eval (with its error bar). Also a task-specific held-out eval, since HumanEval is saturated and measures general coding, not Pi-harness skill.

    Reread: Lab B
