Primer

  1. reset(), step() and OpenEnv

    ~2 h

You need this because your safe becomes an OpenEnv environment with reset() and step(), served from a Space.

Gymnasium's contract is two calls: reset() returns the first observation; step(action) returns the next observation, a reward, and whether the episode ended. OpenEnv keeps that contract for LLM agents and puts it behind a server: a FastAPI app in a Docker container (or a Hugging Face Space), reached from the trainer over a WebSocket. openenv init my_env scaffolds the models, the client, the server and a Dockerfile; openenv push publishes it as a Space. The Hub has thousands of them.

In TRL you don't call step() yourself. You write a small class with reset() and tool methods with typed docstrings, and pass the class as environment_factory. The trainer makes one instance per rollout, exposes the public methods as function-calling tools, runs the multi-turn loop, and reads the reward from the instance at the end. Class 4's MBPP environment has one tool, run_python, and a get_reward that runs the hidden tests.

Two gotchas from the class. Each rollout holds a live session on the environment Space, so the generation batch must not exceed the Space's concurrent sessions (OpenEnv defaults to 1). And tool outputs are written by the environment, so they're masked from the loss, exactly like stage 4.

  1. White box, black box, async

    ~1.5 h

You need this because training against a Space means rollouts over the network, and this explains what that changes.

White box: the trainer owns the loop. It generates, parses the tool call, calls the environment, and continues. Good for your own tools and tasks. Black box: the agent owns the loop. OpenCode runs untouched in its own HF Sandbox, one per rollout; an in-sandbox proxy forwards its model calls to vLLM and captures the exact token IDs and log-probs; a held-out verifier scores the workspace; TRL rebuilds the training rows and never calls step(). That's how you train in the harness you deploy (Will Brown's advice from stage 3).

Agent rollouts are long and uneven, so the black-box demo uses async GRPO: generation never waits for training, and the trainer corrects for batches written by slightly older weights. Harbor, a task format with many harnesses (Claude Code, Codex, OpenCode, Pi), plugs into the same path.

Time ~2.5 hCost $0Where Mac

The most important build in the roadmap: stage 8 reuses it for your game.

OpenEnv quick start↗ · TRL grpo_echo example↗

  1. Scaffold an environment and run its server
    uv tool install openenv
openenv init guess_env
cd guess_env && uv pip install -e .
uv run server --host 0.0.0.0 --port 8000
    You should see a FastAPI server on :8000, and a web UI where you can call reset and step by hand.
  2. Replace the template logic with a tiny game: guess a number 1–100 in 7 triesIn server/*_environment.py: reset() picks a secret and returns “guess 1–100”; step(guess) returns “higher/lower”, reward 1 on a hit and done after 7 guesses. Update models.py for the action and observation types.You should see you can win and lose it from the web UI. You've just written an RL environment.
  3. Optional shortcut: let an agent scaffold it with the FineEnvs skillsnpx skills add adithya-s-k/FineEnvs installs skills for Claude Code and other agents, including rl-env-from-description (“make me an env where the agent plays connect-four”) and OpenEnv/Verifiers generators. Scaffold it, then read every file it wrote: understanding it is the point.You should see a working environment you could explain line by line. If you can't, write it by hand instead.
  4. Play it from Python with a scripted policy (binary search)You should see binary search always wins in ≤ 7 guesses. That's your “oracle” score; a random policy's win rate is your floor.
  5. Push it to the Hub as a Space
    openenv push --repo-id <you>/guess-env
    You should see a running Space at https://<you>-guess-env.hf.space that the echo-style client can call from anywhere.

Checkpoint

Closed book. Write your answer before you open each one. If you miss one, reread the block it names, not the whole stage.

  1. What does GRPOTrainer(environment_factory=MyEnv) do with MyEnv's methods?

    Answer

    It creates one instance per rollout, calls reset() at the start, exposes the public methods (with typed docstrings) as tools, runs the multi-turn tool-calling loop, and reads the reward from the instance at the end.

    Reread: reset(), step() and OpenEnv

  2. Class 4's training reward looked flat, yet the model improved. How?

    Answer

    Each step scores a few random problems whose difficulty varies far more than the model improves in one run (noise 0.21 vs effect ~0.06). A fixed held-out set removes the problem-sampling noise, and its curve rose clearly (t ≈ 5).

    Reread: Watch

  3. Three different held-out numbers were quoted for the same demo. Suspicious?

    Answer

    No: different eval sets (257 problems, 64 fixed problems) and different runs. Reruns moved the size of the gain by about a third. Report the eval set and the spread, not one number.

    Reread: Lab B

  4. White box vs black box: who calls the model, and why use black box at all?

    Answer

    White box: the trainer generates and calls tools. Black box: the agent harness (OpenCode) runs its own loop and a proxy captures tokens for the trainer. Black box lets you train in the exact harness you'll deploy.

    Reread: White box, black box, async
