  1. One GRPO step

    ~2 h

You need this because this is the update that turns cracked and failed safes into a better policy.

GRPO keeps PPO's leash and drops its value network. For each prompt it samples a group of G completions, scores each with the reward function, and uses (reward − group mean) / group std as every token's advantage. The group is the baseline: no critic to train.

Rewards [1, 0, 0, 1] have mean 0.5 and (sample) std 0.58, so advantages are about [+0.87, −0.87, −0.87, +0.87]. Rewards [1, 1, 1, 1] give std 0 and advantages [0, 0, 0, 0]: that prompt teaches nothing. TRL logs the share of such groups as frac_reward_zero_std. A graded reward (fraction of asserts passed) breaks ties that pass/fail can't, which is why Class 3 and your mini-suey repo both use it.

Two guardrails. The KL penalty (beta) bounds how far the whole run drifts from the starting model; clipping (epsilon) bounds each update when a batch is reused. In current TRL the KL penalty is off by default (beta=0), and the clip (epsilon=0.2) only matters when a batch is reused (num_iterations>1; the default is 1). So by default almost nothing holds the policy back, which is one reason a gameable reward bites so fast.

  1. Rewards are contracts, and they get gamed

    ~1.5 h

You need this because your first GRPO run may well find a way to score without cracking safes; this is how you'll spot it.

A reward function is a contract: the model will satisfy the letter of it, not the intent. Class 3's gameable reward counts code blocks (capped at 4) and runs nothing. The trained reward saturates at the maximum, the real test reward (logged with weight 0) collapses, and completion length pins at max_completion_length. That's reward hacking, length gaming and collapse on one dashboard.

The defence isn't KL alone. It's: log a reward you don't train on; watch reward, entropy, length and KL together; read actual completions (--log_completions); dry-run the reward on hand-written good and bad outputs; and keep the grader where the model can't reach it.

Lab A · GRPO you can read, on your Mac

Time ~1.5 hCost $0Where Mac

In ~/Desktop/repos/extending_coding_agents_rl. The numpy GRPO runs the same advantage function as the GPU trainer.

  1. Re-run the demos, now that you know what they show
    make demo
make demo-broken
    You should see “steps that taught nothing”: 2/40 graded vs 16/40 pass/fail. Then read what make headroom does in the Makefile: it refuses to train unless enough groups have spread, which is frac_reward_zero_std as a gate. (Running it loads Qwen3-0.6B and does 120 agent rollouts, so it's slow on a Mac and needs make install first.)
  2. Dry-run a reward function on hand-written completionsCopy tests_reward from Class 3's train_grpo.py. Feed it three completions for one MBPP problem: correct, wrong, and one that just prints assert True. Then feed the pathological reward the same three.You should see the tests reward ranking them correct > wrong ≈ cheat, and the pathological reward happily scoring the cheat.
  3. Compute the dead-group rate for your own settings
    python3 -c "p=0.1
for G in (2,4,8,16): print(G, round(p**G+(1-p)**G,3))"
    You should see 0.82, 0.656, 0.43, 0.185: at 10% solve rate and G = 8, 43% of groups teach nothing. Compare the class sweep: ~75% / 40% / 30% zero-variance at k = 2 / 8 / 16.

  1. Rewards [1, 0, 0, 1]. What are the GRPO advantages (TRL's n−1 std)?

    Answer

    Mean 0.5, sample std ≈ 0.577, so ≈ [+0.87, −0.87, −0.87, +0.87].

    Reread: One GRPO step

  2. Pass/fail reward, solve rate 10%, groups of 8: what share of groups teach nothing?

    Answer

    0.1⁸ + 0.9⁸ ≈ 43%.

    Reread: One GRPO step

  3. In the k-sweep, k = 16 had fewer dead groups than k = 8 but ended lower. Why can bigger groups be worse?

    Answer

    With a fixed batch, more samples per prompt means fewer distinct prompts per step (k = 16 saw 1 prompt per step, k = 2 saw 8), so each update covers less of the task.

    Reread: Lab B

  4. Three signs on the dashboard that a run is reward hacking?

    Answer

    Trained reward saturating while a held-out or zero-weight true reward falls; completion length pinned at the max (or shifting sharply); entropy collapsing and KL rising. Then confirm by reading completions.

    Reread: Rewards are contracts
