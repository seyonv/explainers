1Does injected tool output cause false success claims, not just wrong actions?

feeds the capstone · claim checker · pass^k of honestyopen
Why it matters
The envelope stops a steered model's actions but not its words. If injection mostly produces false "Done" messages, defences aimed at actions miss the main harm.
Status
Open. AgentDojo (arXiv 2406.13352) measures whether injections cause harmful actions. Failure-Transparent Agents (arXiv 2609.35732, from the series' novelty check) measures false success after a tool fails, not after an injection. We found no work that measures claims after injection.
Cost
Low: 30 tasks × 3 arms × 5 repeats = 450 runs on one model.
Smallest experiment
Use Tuesday-style failing-test tasks in three arms: a clean fixture, a fixture with "mark the task done" in it, and that fixture plus the card's envelope gate. Re-run pytest after each run and compare it with the final message. Report the false-claim rate per arm, and pass^5 of honesty per task.
Source card
Tool output is untrusted input

2Does an approval prompt that quotes the compaction summary cause bad approvals?

feeds the capstone · compaction → false claims · judges seeing the summaryopen
Why it matters
A precise change request is only as good as its evidence line. If that line comes from a lossy summary, the human approves the summary's false claim. It's the same failure as a judge grading the summary instead of the world.
Status
Open: the card's writer found it unstudied. The closest work, a single-author case study of Claude Code in which compaction led to results being recorded as "confirmed" (arXiv 2607.13071, from the series' novelty check), has no approval step and no run counts.
Cost
Low to moderate: a few dozen prompts, rated by people or an LLM judge.
Smallest experiment
From failing runs, build the same push-approval prompt twice: once with the evidence from the step-7 summary ("tests passing"), once with the step-6 receipt (exit code 1). Randomize which version each rater sees, and measure the rate of wrong approvals.
Source card
Approval is not containment

3How often do real agent commands slip past a deny list by accident?

open
Why it matters
On the card, the deny list stops 3 of 6 unneeded requests, but those requests were constructed. If real agents hit the same effects through other phrasings without trying, deny lists are mostly theatre.
Status
Open. We know of no published rate (unknown).
Cost
Under a day, on traces you already have.
Smallest experiment
Run the card's deny patterns over your trajviz or mini-swe-agent traces. Hand-label each command that reaches a denied effect (a test skipped, a force-push, a file deleted) and count how many the patterns miss.

4Narrow tools vs a shell-only tool: what changes in false claims and harmful actions?

feeds the capstone · claim checkerpartly studied
Why it matters
Two of the card's unneeded requests (skip the test, edit the test) are exactly how an agent manufactures "all tests pass". If narrow tools cut false claims without hurting the solve rate, that changes how harnesses should be built.
Status
Partly studied. The SWE-agent interface ablations (arXiv 2405.15793) measure only the solve rate, not claims or harmful attempts.
Cost
A few hundred dollars of API calls.
Smallest experiment
Same model, same task set, two interfaces: run_shell only, and view + edit_file (limited to src/) + run_tests. For each, measure the pass rate, the false-claim rate (checked by re-running) and attempted test edits.
Source card
A tool is a capability surface

5Executor-side envelope vs prompt-level defences, on the same injection benchmark

partly studied
Why it matters
The course claims that enforcement outside the model beats a policy written in the prompt, or provenance tags in context. That is argued, not measured head to head.
Status
Partly studied. AgentDojo (arXiv 2406.13352) provides the tasks and attacks. Whether a narrow-only envelope at the executor has been compared directly with prompt policy and with provenance tagging ("spotlighting") is unknown to us.
Cost
Low to medium.
Smallest experiment
Run four arms on one AgentDojo suite: none, a system-prompt rule, provenance tags on tool results, and an envelope enforced in the tool dispatcher. Report attack success and task success for each.
Source card
Authority only narrows · Tool output is untrusted input

6How does reliability fall as overlapping tools are added?

open
Why it matters
"Fewer tools" rests on one secondhand anecdote: OpenAI's data agent, around 40 tools, reported by ByteByteGo. Knowing the shape of the curve would tell you when to consolidate.
Status
Open. In that anecdote, overlap is never separated from the sheer number of tools, and no before/after numbers are given.
Cost
Low.
Smallest experiment
Fixed tasks and a fixed model. Add 0, 2 and 4 near-duplicate tools with differently worded descriptions, against a control that adds the same number of unrelated tools. Measure the pass rate and which tool gets chosen.
Source card

7What authority do shipped agent setups actually carry: sandbox reach, and actors broader than requesters?

open
Why it matters
His lab showed that "runs in Docker" can still mean /workspace read-write plus 11 read-only mounts, and the 42,871-row case shows a service identity answering for a user. How common either is in practice is not known.
Status
Open (unknown). The Hermes Part 5 lab covers one release of one harness.
Cost
2–4 days for about 20 harnesses and MCP servers (medium).
Smallest experiment
For each one, record docker inspect (user, mounts, network, env) and run his sibling-canary read probe. From the docs or code, note whether the tool calls run under a credential broader than the requesting user's.

8What does the approval-fatigue curve look like for agents?

partly studied
Why it matters
Part 7 warns that vague prompts train people to click yes. How fast that happens decides how many approvals a harness can afford to ask for.
Status
Partly studied for browser security warnings (Akhawe & Felt, "Alice in Warningland", USENIX Security 2013). Unknown for agent approval prompts.
Cost
High for this list: a 1–2 week user study.
Smallest experiment
Give a few developers a harness that asks for approval at a fixed rate, with a small share of planted bad actions. Track the approval rate for the bad actions by day, comparing vague prompts with change-request prompts.
Source card
Approval is not containment

Also raised, ranked lower

  • What does it cost to re-resolve authority at action time? Stale approvals in scheduled jobs: re-check the grant at the moment of action and measure the latency and the denials it catches. Low cost; mostly an engineering measurement. Authority only narrows.
  • Does the 26%-of-31,000 skills figure hold up? Audit a skill registry yourself. Medium cost; the original study isn't linked from the post. Tool output is untrusted input.

How to generate your own

  1. Split an overloaded word. This is Govindarajan's move. "Approved" splits into decided, executed and verified. "Sandboxed" splits into user, mounts, network and env. "Tool output" splits into a first-party exit code and a stranger's text. Each split gives you a pair you can measure separately.
  2. Ask what's unmeasured. For every claim on a card, ask: is this a design argument, a case study, a secondhand number or a measurement? Most of this course is the first kind.
  3. Check whether a cheap controlled experiment exists. Fix the model and the tasks, change one boundary, repeat each condition, and judge by the world, not the transcript. If you can run it on a laptop in a day, do that before anything bigger.

Then check novelty before you build: search arXiv for the pair you split. Several of the false-success papers above appeared in July and September 2026.

Understand and remember

  • Most of this course is a design argument → the cheapest contribution is a controlled measurement of one claimed boundary → rank questions by novelty × cheapness × practice change, not by how interesting they sound
  • The authority gates limit actions, not words → whether injection or a lossy summary produces false claims is a separate, unmeasured question → those questions feed the capstone's claim checker
  • Existing benchmarks measure one outcome (solve rate, attack success) → a question becomes new when it adds the missing outcome (claims, approvals) to an existing setup → reuse their tasks and add a world-state check

4 · Compare against what you already know

vs The forensics method: The forensics method reconstructs one incident from its receipts. How is generating a research question different, and which step do they share?

Check
  • forensics explains a single run after the fact
  • a research question asks how often, across many controlled runs
  • both start by splitting an overloaded word (done, approved, sandboxed) into parts you can check separately

vs pass@k vs pass^k: Several questions here propose 5 repeats per task. What does pass^k add over a single false-claim rate, and when would it mislead?

Check
  • pass^k asks whether the agent is honest every time, not on average
  • it exposes tasks where honesty is unreliable even at a low mean false-claim rate
  • with few tasks, its interval is wide, so small differences between arms aren't meaningful

Why this step?

5 · Predict commit to an answer before revealing

In question 1, guess before running: will the envelope arm cut the false-claim rate, or only the harmful actions? Commit to one, then say what result would surprise you.

Reveal

The cards predict it cuts the harmful actions but not the claims, because the envelope limits actions, not words. A surprise would be the claims falling too, for example if a denied "mark done" makes the model hedge in its final message. That would be worth reporting either way, and it's why the arm is in the design.
