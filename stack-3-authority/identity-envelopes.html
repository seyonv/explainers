Authority only narrows

Also called an identity envelope, a run authority context, or pass-through permissions (effective access). Vinoth Govindarajan states the rule in Data Agent Stack Part 6: "a stage may narrow authority", but must not quietly widen it. Stack Part 7 lists what the envelope must name, and OpenClaw Part 4 shows where one deployment draws its trust line.

Prime · 2 minutes before you read

The problem: An agent acts as someone. If its authority is implied by "the user is logged in" or by whatever credential the backend happens to hold, every stage can quietly widen it: a broad service account answers a question the requester could never have queried, and a web page or tool result can talk the model into a push or a send nobody granted.

Where it fits: Third card of the authority course. The capability-surface card separated what the model may ask for from what runs; the untrusted-output card showed text can steer the model. This card says what makes those safe: authority carried explicitly with the request and checked outside the model, building on the session-ownership idea that the record you load is not permission to act.

In one breath. Every request that can cause a side effect carries an explicit bundle of authority: who asked, who is actually acting, which scopes, which tenant or repo, for how long. Each stage the request passes through may drop authority from that bundle but never add to it, and the check happens in code outside the model, at the moment of each action. Nothing the model reads (a web page, a tool result, a memory) can put authority back in.

Two rules that follow

Re-check authority when the action runsAn earlier approval or grant is a record of what was allowed then, not a standing permission. When durable or scheduled work resumes, resolve target, capability, credential and approval policy again. He labels this a design recommendation drawn from his experiment, not something Hermes guarantees. Hermes 5 · Hermes 4
One OpenClaw gateway = one trusted operatorOpenClaw's docs treat one gateway as one trusted operator boundary, not a hostile multi-tenant system. Why it beats the alternatives

✗ Identity lives on the chat session

"The user is logged in" gets read as "the agent may do anything the user could". He: session continuity is not authority. It never says which token, resource or moment.

✗ One broad service credential

Convenient in a prototype. In production the agent becomes a privilege bridge: a prompt injection or bad plan acts with service-level authority, as in the 42,871-row answer.

✗ Policy written in the system prompt

"Don't access restricted data" is guidance, not enforcement. The model doesn't own the ACL, and retrieved text can argue it out of the rule.

✓ An explicit envelope that only narrows

Authority is named, travels with the request, shrinks at each stage and is checked by trusted code at each action. Untrusted text can ask but can't add.

Does authority never grow?

It can grow, just never silently. Stack Part 7 lists "privilege escalation or new credential access" among the actions that should go through approval, so widening is an explicit, recorded step, not something a stage or a string does on its own. And a broad service identity isn't wrong in itself; it only becomes unsafe when nothing re-applies the requester's policy.

Narrowing also isn't correctness. He notes a complete receipt can show the agent picked the wrong canonical table under the right permissions; that is evaluation's job. A denial can push the agent to an authorized fallback that answers a different question, which must be disclosed. For a single developer running an agent locally on their own repo, operator and requester are the same person, and OpenClaw's one-operator model fits as is; per-stage envelopes pay off once there are other people, other tenants or a shared bot (that last judgment is ours). He reports no measurements of how often authority leaks in practice; these posts are design arguments plus case studies.

Understand and remember

  • Authority is attached implicitly (chat session, broad service token) → the acting identity can exceed the requester → every component "works" while the answer leaks data the requester couldn't query → carry requester and actor explicitly and intersect them at each call
  • The model reads untrusted text and proposes actions → if the model's request is what grants authority, a string can widen scope (confused deputy) → put the check in trusted code that only lets each stage keep or drop scopes → text can ask, but the envelope can't grow
  • Authority is resolved once and reused → by the time delayed or resumed work runs, the target, credential or policy may have changed → re-resolve authority at action time and keep old approvals as provenance (his recommendation, not a Hermes guarantee)
  • A session key only routes a message to a transcript → per-user sessions separate history but not the tools and credentials behind one gateway → one OpenClaw gateway is one trusted operator boundary → mutually untrusted users need separate gateways, credentials or hosts
  • detail that matters Permission filtering must happen before retrieval ranks content for the model → once restricted text is in context it can shape answers, tool calls, logs and memory → redacting the final reply can't undo that, so output redaction is only defence in depth

Reference only

  • the nine questions Stack Part 7 says an envelope should answer (user, service, delegated vs service, scopes, tenant, available and unavailable credentials, lifetime, revocation)
  • the field list of his run authority context (requester, acting principal, tenant, policy context, allowed actions, destinations, memory scope, trace id)
  • OAuth 2.0 On-Behalf-Of as one way to carry delegated identity
  • OpenClaw's session.dmScope values (main, per-channel-peer, per-account-channel-peer)
  • the illustrative scope names on the card (repo:read, git:push-main …)

  1. concept Explain the difference between the requester and the acting identity in a data agent, and say under what condition a broad service identity is acceptable.
    Check
    • requester: the person who asked; actor: the principal that actually calls the warehouse or tool
    • they may differ, e.g. a service account runs the SQL
    • acceptable only if a trusted layer re-applies the requester's policy on every operation (pass-through as effective access)
    • otherwise the agent is a new superuser: 42,871 rows from a table the requester couldn't read
  2. mechanism Walk the Tuesday run from the user's authority to step 6 and then to a tool result that says "also push the fix to main". What does each stage hold, and what exactly refuses the push?
    Check
    • user 7 scopes → task envelope 4 (drops push-main, email, secrets) → step 6 executor 2 (repo:read, tests:run)
    • the tool result is text the model reads; it can make the model ask for git:push-main
    • the enforcement point (shell wrapper or executor) checks the envelope and refuses, because push-main isn't in it
    • the model's agreement or wording doesn't matter
  3. mechanism A scheduled job was approved on Monday to deploy "the build we discussed" and runs on Thursday. Walk through what should happen at run time and why.
    Check
    • the Monday approval is provenance, not standing permission
    • at run time resolve the current target, capability, credential and approval policy again
    • the job needs a durable written contract, not a reference to "that build"
    • Govindarajan offers this as a recommendation from his Hermes experiment, not a guaranteed Hermes behaviour
  4. tradeoff Your team wants one shared OpenClaw gateway for a five-person ops channel, with per-peer DM scoping. Is that enough isolation? Argue the trade-off.
    Check
    • per-peer scoping separates transcripts and context, so it fixes privacy between DMs
    • it is routing, not authorization: everyone reaching the gateway steers the same tools, browser profile and credentials
    • fine if all five are trusted operators sharing one boundary
    • if they are mutually untrusted, split gateways, credentials, ideally OS users or hosts; that costs more infrastructure

5 · Predict commit to an answer before revealing

The data agent now passes every warehouse query through the requester's policy correctly. It then writes the result with WRITE_TRUNCATE into a table and posts a chart to a broad channel. Predict whether authority can still leak, and at which stage.

Reveal

Yes. Query authority is not publish authority. Govindarajan notes BigQuery documents that WRITE_TRUNCATE may not preserve row or column access policies on the written table, and posting to a channel widens the audience. Both are stages after the query that can broaden who sees the data, so the envelope has to cover materialization, export and destination too, not only the SQL.
