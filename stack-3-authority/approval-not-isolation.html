Approval is not containment

Also called human-in-the-loop approval vs sandboxing, or "checkpoint vs boundary". Govindarajan's Agent Stack Part 7 says to put approval right next to the side effect, worded as a small change request. His Hermes Part 5 lab shows that a separate profile, or the word "Docker", contains nothing by itself: the effective user, mounts, network and environment do.

Prime · 2 minutes before you read

The problem: Teams add an approval prompt, see it block one command, and conclude the agent is safe. Or they run it "in Docker" and stop asking what it can reach. Each control then gets credit for a job it never does, and the gap shows up as a sibling file read or an approved-but-wrong payment.

Where it fits: Builds on the boundary pairs in Same label, different authority (approval ≠ isolation, profile ≠ sandbox) and on the approval-is-not-commit lesson from the memory card. This card is the authority course's look at the last step before a side effect lands.

In one breath. Approval answers "should this one action happen now?" Containment answers "whatever runs, approved or not, what can it reach?" An approval prompt guards only the code paths that call it. A sandbox limits every path that runs inside it, but it decides nothing. You need each for a different failure, and neither can stand in for the other.

You already know: anatomy of a tool call (the model only asks; the harness runs the tool). This card is about what stands between that request and the world.

The checkpoint sits on one lane. The box sits around all of them. "An approval prompt is a checkpoint, not a containment boundary" (Hermes Part 5), and "a sandbox ... does not decide whether the command should execute" (Agent Stack Part 7).

Put the approval next to the side effect

Approval is worth most at the moment preparation becomes commitment: drafting vs sending, filling a form vs submitting it, generating SQL vs running it. Part 7's contrast:

✗ At the start of the task

"Can I help you pay this invoice?"

Ten steps later the agent submits a payment. The yes never saw the amount, the recipient or the account, so it approved nothing in particular.

✓ At the submit step, as a tiny change request
What
pay $4,812.43
As whom
your user token, payments scope (illustrative)
Where
from account ending 0042 (illustrative)
To
a recipient new to this account (illustrative)
Undo?
can it be reversed, and how

The amount is Part 7's; the account, scope and recipient are illustrative. Part 7 lists seven questions a good approval answers (what, as whom, where, what data, what is sent or changed, can it be undone, what evidence) and says: if the system can't answer them, it probably isn't ready to execute.

Too broadOne yes up front covers every later step. Meaningless, because nothing specific was shown.
At the side effectPart 7's list: external sends, submits, payments and posts; destructive or hard-to-reverse operations; sensitive data; new recipients or accounts; physical actions; crossing tenants or repos; privilege escalation. That is 8 kinds.
Too oftenPart 7 warns against a vague modal that trains people to click yes. Asking on every read has the same effect (our inference).

The Tuesday run (illustrative). Suppose the harness asked before pushing the fix in invoice-tools. If the change request's evidence line came from the step-7 compaction summary ("tests passing"), the human would approve a push of a still-failing test. If it came from the step-6 receipt (exit code 1), they wouldn't. A precise prompt is only as good as the evidence it shows; that link is our inference, not Part 7's.

Hermes Part 5: the profile picked the state, the backend picked the reach

One canary file inside the workspace, one in a sibling folder, the same read probe, three execution setups (Hermes v0.21.0, 4 September 2026, disposable profile, Docker on Linux):

SetupSibling file ../outside/outside.txtWhat changed
Local backend, cwd=workspacereadthe process inherited the host user's reach
Docker, sibling not mountedFileNotFoundErroronly paths exposed into the container exist
Docker, sibling mounted read-onlyreadone mount; "a read-only mount still grants read authority"

Local vs Docker changes the OS identity, the filesystem namespace and the backend at once, so he treats the two Docker runs, which differ by one mount, as the clean comparison. The container ran as a non-root user with networking off, capabilities dropped and no privilege escalation. It still exposed /workspace read-write plus eleven read-only mounts (skills, attachments, images, cache). Zero environment variables were passed through, which he notes is not the same as an empty environment. "Runs in Docker" is not the contract; the effective user, mounts, network, environment and lifetime are.

A control is only as wide as its path

A toy harness (not Hermes' code) with two tools that reach the same sibling folder. Approval is unattended and set to deny, as in his lab.

def write_file(path, text): # calls the checkpoint if not approve(f"write {path.name}"): return "blocked" path.write_text(text) def shell(cmd, cwd): # never calls it return subprocess.run(cmd, shell=True, cwd=cwd, ...) # output, python3 code/approval-not-isolation.py write_file ../outside/a.txt: blocked a.txt exists: False shell echo > ../outside/b.txt: exit 0 b.txt exists: True shell cat ../outside/outside.txt: exit 0 CANARY-OUTSIDE

The deny worked, and it covered nothing outside its own path. Hermes shows the real version: its write-root setting HERMES_WRITE_SAFE_ROOT blocked an out-of-root write_file, and its security guide says shell reach belongs to the execution boundary instead. Hermes does send some shell commands through its approval classifier (the python -c case), but the post stresses that this doesn't show every side effect goes through it.

How the four controls differ

Approval prompt

Decides: may this one proposal proceed now.

Doesn't: limit anything that skips it, or prove the action ran where intended. In Hermes Part 3 an approved skill still failed on replay: its 152-character description broke the 60-character limit.

Allowlist or tool filter

Decides: which caller may dispatch, which tools the model can see. Hermes' MCP filter showed one of two tools.

Doesn't: shrink the authority inside a tool that stays visible, or the files and credentials behind it.

Container

Decides: reach, through user, mounts, network, environment and lifetime.

Doesn't: decide anything, and it is only as narrow as its real mount table. Part 7: a sandbox with mounted secrets and open egress "is not much of a boundary".

MicroVM

Decides: the same reach, behind its own guest kernel instead of the host's.

Doesn't: make decisions either; a wide mount or a live credential passed in leaks the same way. Not in these posts: general practice, added for contrast with Part 7's "kernel" containment item.

So is containment the stronger control?

No. They fail differently, so most consequential agents need both. A sandbox can't stop a wrong but in-scope action: a $4,812.43 payment sent through an API with a valid token happens entirely inside the allowed reach, and only an approval that shows the amount and recipient can catch it. An approval can't stop a command that never asks. Hermes' security policy says that against adversarial model output the operating system is the load-bearing containment boundary; approval, redaction and tool filtering are guardrails on top.

When not to reach for each: approval on low-risk reads only trains people to say yes; a container adds little to a pure API call, where the scope of the credential is the real limit. And approval is not the end of the story: approval, execution and verification are three separate receipts. Old approvals should be kept as provenance, with authority resolved again when work resumes. He flags that as his recommendation, not a Hermes guarantee. His Hermes results are narrow on purpose: one release, synthetic canaries, and no adversarial test of credential theft or network egress.

Understand and remember

  • Approval is a check inside one code path → it only fires on paths that call it → a shell or other tool that never calls it runs unchecked → a blocked command proves nothing about the machine; reach must be limited by the OS or execution backend
  • Containment limits what a process can reach but decides nothing → an in-scope but wrong action (a payment through an API with a valid token) passes straight through → only an approval that shows the amount, recipient and account can catch it → consequential agents need both controls
  • A prompt at the start of a task shows no specifics → the human approves nothing in particular, and later steps inherit the yes → move approval to the step where preparation becomes commitment and word it as a change request (what, as whom, where, data, change, undo, evidence)
  • A profile selects state and cwd only sets where relative paths start → the process still runs as the host user → under the local backend ../outside/outside.txt was readable → reach is set by user, mounts, network, environment and lifetime, and one read-only mount restored it
  • detail that matters The approval prompt's evidence line is only as good as its source → if it quotes a compacted summary ("tests passing") instead of the tool receipt (exit 1), a precise prompt still gets a wrong yes (the Tuesday run, our inference)
  • detail that matters Approval, execution and verification are three receipts → an approved Hermes skill still failed on replay (152-character description vs a 60-character limit) → never report "approved" as "done"

3 · Retrieve from memory, card closed
  1. concept Explain the difference between approval and authorization using the card's file-deletion example, and say why collapsing them leaks authority.
    Check
    • authorization: this principal is allowed to delete the file at all
    • approval: should this specific deletion happen now, given what is visible
    • if being logged in or authorized is read as approved, the agent can take any action the user could, with no one deciding on the specific one
  2. mechanism Walk the Hermes canary probe through the three setups: what it tried to read, what each setup returned, and what caused each result.
    Check
    • local backend, cwd=workspace: sibling readable, because the process had the host user's reach
    • Docker, sibling not mounted: FileNotFoundError, because only mounted paths exist in the container's filesystem
    • Docker with the sibling mounted read-only: readable again; a read-only mount still grants read
  3. mechanism Walk the toy harness: unattended approval is set to deny. What happens to write_file and to the shell command aimed at the same folder, and what does that say about where to enforce limits?
    Check
    • write_file calls approve, gets deny, returns blocked; the file doesn't exist
    • the shell never calls approve: exit 0, the file exists, and it can also read the canary
    • path-specific guards cover only their path, so limits on reach belong in the OS or execution backend
  4. tradeoff Your agent can send email and run shell commands on your laptop. You can afford one more control this week: an approval prompt on every send to a new recipient, or moving the shell into a container with no network and only the repo mounted. Which risk does each remove, and which would you pick first?
    Check
    • approval on new recipients catches wrong or injected sends, which a container can't, because sending is in scope
    • the container cuts the shell's reach to your files, credentials and network, which approval on email doesn't touch
    • pick by blast radius: whichever side effect is harder to undo or wider in reach; the honest answer is that both are needed eventually

5 · Predict commit to an answer before revealing

Take Hermes' tight Docker posture (non-root, network off) and add the sibling folder back as a read-only mount. The task: "summarize outside.txt and post it to a webhook". Commit first: does network-off stop the contents leaving the machine?

Reveal

Not necessarily. The read succeeds, because a read-only mount grants read. The container itself can't reach the network, but the probe's output returns to the model, and the post notes the provider call stays in the host process. Any host-side tool with network access (a web or MCP tool) could then send it, and only an approval on that send, or that tool's own limits, would stop it. As the post puts it, network isolation does not erase filesystem exposure.
