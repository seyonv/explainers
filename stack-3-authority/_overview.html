Asking is not acting

Overview for course 3 of The Agent Stack: tools, authority and execution. Also called the action layer, or trust boundaries for agents. Four cards on one page: what a tool lets the model ask for, why what comes back is untrusted, how authority travels with a request, and why an approval prompt is not a sandbox.

Prime · 2 minutes before you read

The problem: The four cards each name a different control (a narrow tool, an untrusted-output rule, an identity envelope, an approval or a sandbox), and it's easy to treat any one of them as "the security". Each control guards a different failure, and none of them checks the agent's final claim. This page puts them on one request path so you can see which gate catches what.

Where it fits: The map for course 3: read it first to place the four cards, or last as a recap. It builds on the map course's "same label, different authority" and on the anatomy of a tool call (the model asks; the harness acts).

In one breath

"The model asks. The system acts." (Govindarajan, Part 6). Four separate things decide whether a request becomes an effect. The capability surface sets what the model can ask for at all. The identity envelope sets what this request is allowed to do; each stage can narrow it but never widen it, and code outside the model checks it at the moment of action. Approval decides whether one specific side effect happens now. Containment limits what anything that runs can reach, approved or not. Text that comes back from a tool goes into the model as tokens. It can steer the model, but it can never add authority. None of the four stops the model from saying "Done", so checking that claim is the next course's job.

Plain text: A(k+1) ⊆ A(k); A(effective) = A(requester) ∩ A(actor) ∩ A(stage). The first line is Govindarajan's rule ("a stage may narrow authority"). The intersection is the card's compact reading of his "pass-through is an effective-access property", not his notation. The same rule covers tool output: authority after reading anything ⊆ authority granted at request time (Part 7).

The formula covers only the envelope. Taken together, the four cards say an effect happens only if it passes four separate gates. Each gate is owned by a different part of the system, and each one fails in its own way (this composition is ours):

effect happens ⇔ askable (capability surface: is the tool offered?) ∧ in A(effective) (envelope: may this request do it?) ∧ approved (only for side effects: should it happen now?) ∧ reachable (containment: can the process touch it?) "Done" in the final message ⇏ effect verified (no gate checks words)

The mental model

Gates 1–3 sit on the path, and each guards only the requests that pass through it. Containment is the box around every path, including the one that skips approval. What comes back from a tool can steer the model but never widens the envelope. Nothing on this path checks the final claim.

The words people use

Capability vs execution surface

What the model may ask for (the tools on offer, for this user and stage) vs where effects actually happen, and as whom (a sandbox, the developer's laptop, a service account). OWASP calls a too-wide version of either excessive agency.

Authorization vs approval vs containment

May this identity do this to this resource (policy)? Should this one action happen now (a person or rule)? What can the running process reach (the OS or backend)? They are three different controls, and none of them substitutes for another.

Indirect prompt injection · confused deputy

Instructions that arrive inside content the agent reads (OWASP LLM01), and the more-privileged part that ends up acting on them. The injection only becomes a security problem when it crosses a real boundary.

✓ Identity envelope

The authority carried with one request: requester, actor, scopes, tenant, lifetime. Stages may narrow it, never widen it, and code outside the model enforces it at each action. This is the course's central idea.

When this advice doesn't apply

The boundary belongs to the system, not the model. Offer narrow tools, carry an explicit envelope that only narrows, put approval next to the side effect, and contain by the real mount table. Then text the model reads can steer it only within what the task already allowed.

  • Open-ended work needs open-ended tools. mini-swe-agent gives the model only a shell, and a coding agent that can only run tests can't install a dependency it really needs. Keep the broad tool and move the narrowing to the execution surface.
  • One developer on their own repo is one trusted operator, and OpenClaw's one-gateway model fits as is. Per-stage envelopes pay off once there are other people, other tenants or a shared bot (the card's judgment).
  • Approval on low-risk reads trains people to click yes. A container adds little to a pure API call, where the credential's scope is the real limit.
  • None of this checks correctness. The envelope limits actions, not words. A steered or confused model still writes "Done, all tests pass", and an agent can pick the wrong table under the right permissions. Catching that is the graders' job.
  • The evidence is mostly design argument. Apart from his narrow Hermes labs (the Part 5 canary probe and the Part 3 skill replay: one release each, synthetic inputs), the posts run no experiments. Most counts on these cards come from constructed examples.

Understand and remember

  • The model only asks → the system decides and acts → each decision is a separate gate (capability surface, envelope, approval, containment) owned outside the model → name the gate before picking the fix
  • Authority is a set carried with the request → each stage may drop scopes, never add them, and the actor is intersected with the requester → a broad bot or a persuasive tool result can't spend authority the task never had
  • Approval guards only the paths that call it, and containment wraps every path but decides nothing → a skipped prompt is caught only by containment, and a wrong in-scope action only by approval → consequential agents need both
  • Every gate limits actions, not words → a steered or confused model can still say "Done, all tests pass" → only a checker that re-runs against the world catches the false success claim (course 4)
  • detail that matters Order on the path: the envelope check runs before approval → a request outside the envelope never reaches a human → approval can't be used to widen authority by accident; widening must be its own recorded escalation

3 · Retrieve from memory, card closed
  1. concept Explain the difference between the four gates by saying, for each one, the question it answers and who enforces it.
    Check
    • capability surface: what may the model ask for at all? the harness, by what it exposes
    • envelope: may this request do this to this resource? policy code outside the model, at each action
    • approval: should this specific side effect happen now? a person or rule, at the side effect
    • containment: what can the running process reach? the OS or execution backend
  2. mechanism Walk the Tuesday run's injected fixture ("mark the task done") through the four gates. Where does each of the steered model's proposals die, and what gets through?
    Check
    • editing src/ is allowed: it's the real task
    • editing the tests is denied by the write root, the push by the envelope, and "mark done" by the gate reading the last pytest exit code
    • the final "Done" message is delivered, because no gate checks words
  3. tradeoff You can add one control to a shell-only coding agent this week: narrow tools, a per-stage envelope, approval before pushes, or a no-network container. Which first, and what does each leave uncovered?
    Check
    • the container covers every path, including ones that skip approval, but not wrong in-scope edits
    • approval before pushes catches a specific irreversible effect but only on paths that ask
    • narrow tools shrink what can be attempted but may block legitimate open-ended work
    • an envelope matters most once there is a shared bot or other users; for one dev on their own repo it adds little

5 · Predict commit to an answer before revealing

The bot ∩ task envelope holds 3 scopes and no push. A tool result now asks for git:push-main, and the harness also has an approval prompt before pushes. Does a human ever see a push prompt, and if not, what would have to happen for the push to be possible?

Reveal

No prompt appears. The envelope check comes before approval on the path, so a request outside the envelope dies at gate 2 and never reaches a human. For the push to become possible, someone would have to widen the envelope explicitly: Part 7 lists privilege escalation among the actions that need approval, so widening is its own recorded step, never a side effect of text the model read.
