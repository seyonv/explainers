Before this: The transformer forward pass

Attention: Q, K, V, heads, and GQA

Also called scaled dot-product attention or self-attention; the head layouts are MHA, MQA and GQA. Every layer of Llama-3.1-8B runs it with 32 query heads sharing 8 key/value heads, and those 8 heads are exactly what the KV cache stores.

Prime · 2 minutes before you read

The problem: A token's meaning depends on the words before it, but the MLP sees each token alone. Something has to let tokens read each other, and whatever it keeps from earlier tokens becomes memory that every request carries for its whole life.

Where it fits: Opens the attention box of the forward-pass card (41.94M parameters per layer). It explains where the KV cache comes from and why its size depends on the KV-head count; the roofline and serving cards later turn that cache into bytes read per step.

In one breath

Each token asks a question (its query). Every earlier token offers a label (its key) and some content (its value). Attention scores how well each label matches the question, turns the scores into weights that sum to 1, and returns the weighted mix of the contents. Heads run this many times in parallel on smaller slices of the vector. GQA lets several query heads share one key/value head, so there is less to cache.

The formula

Attention(Q,K,V)= softmax(QK⊤dk)weights: how well each key matches each query Vcontents to mix
Qqueries: one row per token, "what am I looking for?"T × dk Kkeys: one row per token, "what do I contain?" (the label)T × dk Vvalues: one row per token, the content that gets passed alongT × dv QK⊤every query dotted with every key: a T × T grid of match scores9 here · 67M at T = 8,192 √dkscale down by the square root of the head size, so scores don't grow with dk and saturate the softmax√4 = 2 here · √128 ≈ 11.3 in Llama softmaxper row: exponentiate, then divide by the row sum, so each row's weights are positive and sum to 1row by row
same thing in plain text: out = softmax( (Q @ K.T) / sqrt(d_k) + causal_mask ) @ V causal_mask = 0 where key position ≤ query position, −∞ where the key is in the future

Heads, and why the KV head count sets memory

During decode, every new token needs the keys and values of all earlier tokens in every layer. Recomputing them each step would be wasteful, so the engine stores them: that store is the KV cache (green). Its size per token depends only on how many KV heads there are, not on the query heads:

Grey boxes are query heads, green boxes are key/value heads, which get cached. Under GQA, query heads 0–3 all read K,V head 0, heads 4–7 read head 1, and so on. The GQA paper calls this GQA-g, with g groups: GQA-1 is MQA, and GQA-32 (one group per query head) is MHA.

Why GQA beats the alternatives

✗ MHA: one KV head per query head

The most expressive, but the KV cache is 4× bigger than GQA-8 (512 vs 128 KiB per token). On one H100, that's 14 users at 8k context instead of 59, and 4× more KV bytes to read per decode step.

✗ MQA: one KV head for all

Smallest cache (16 KiB per token), but the GQA paper reports that MQA "can lead to quality degradation". All 32 query heads must share one set of keys and values.

✗ No cache: recompute K and V

Nothing is stored, but every decode step must recompute K and V for every earlier token. Generating T tokens then costs work that grows as T² instead of T.

✓ GQA: a few shared KV heads

The GQA paper reports that uptrained GQA reaches "quality close to multi-head attention with comparable speed to MQA". Its GQA-8 came close to MHA-XXL on T5. Llama-3.1-8B uses 8 KV heads.

The next step past GQA is MLA (multi-head latent attention, used by DeepSeek-V2 and V3). Instead of whole K/V heads, it caches a smaller compressed vector per token and expands it when needed. It is covered in the attention & KV cache course.

What GQA does not do

It shrinks memory and decode bandwidth, not prefill compute. All 32 query heads still compute their own scores, so the Q·K⊤ and weights·V FLOPs (about 4·T²·N·H per layer, halved by the causal mask) stay the same. Only the K and V projections shrink: attention parameters per layer drop from 67.1M to 41.9M. During decode the savings are real, because each step reads the whole cache. At 8k context, one MHA sequence's cache (4.29 GB) is 27% of the 16.06 GB of weights read every step, while GQA-8's (1.07 GB) is 6.7%.

You can't switch it on for an existing model. The KV-head count is part of the architecture. An MHA checkpoint has to be trained or uptrained into GQA. The paper mean-pools the K/V projections within each group, then continues pre-training for a small fraction of the original steps (5% in its main recipe).

When it's not the right choice: it doesn't help when nothing is cached, for example an encoder-only model or a one-shot scoring pass with no decode. If memory is still the limit at long context, look at MLA, sliding-window attention or KV-cache quantization. GQA is also not the same as attention being "cheap": at very long context, the T² score grid still dominates prefill.

Understand and remember

  • Query dotted with every earlier key → scores ÷ √d_k → causal mask sets the future to −∞ → softmax per row gives weights that sum to 1 → the output is a weighted mix of values: the only step where tokens exchange information
  • Each new token's query needs every earlier token's K and V in every layer → recomputing them would make a generation cost grow as T² → store them: the KV cache → bytes per token = 2·L·K·H·2, whatever the number of query heads
  • GQA lets 4 query heads share one KV head → KV per token 512 → 128 KiB → 4× more 8k sequences fit (14 → 59 on an H100) and 4× fewer KV bytes per decode step → but the query-side score and mix FLOPs stay the same
  • The score grid is T × T per head → it grows as T² (67M cells per head per layer at 8,192) → at long context attention's work and cache reads, not the weights, start to dominate
  • detail that matters The KV-head count is part of the architecture → switching needs uptraining (mean-pool each group's K/V projections, then about 5% more pretraining in the paper's main recipe) → an engine can't turn GQA on for an MHA model
  • detail that matters Dot products of d_k-dim vectors grow with d_k → unscaled logits saturate the softmax → dividing by √128 ≈ 11.3 keeps Llama's scores in a usable range

4 · Compare against what you already know

vs Multi-head latent attention (DeepSeek): GQA vs MLA: both shrink the KV cache. What does each one cache, which design choice makes the cache smaller, when would you pick each, and what does each cost?

Check
  • GQA caches fewer whole K/V heads, shared by groups of query heads
  • MLA caches one short latent vector per token per layer and folds the expansion into other matrices
  • GQA is simple and supported everywhere; MLA gets a much smaller cache (DeepSeek-V3: 68.6 KiB per token vs 3.81 MiB for MHA with the same heads)
  • both must be trained into the model; MLA adds complexity (decoupled RoPE, weight absorption)

vs FLOPs per token: 2N to serve, 6N to train: This card says the score grid grows as T²; the FLOPs card says attention adds 4·S·D FLOPs per token per layer. How are these the same fact, and why doesn't the 2N rule see it?

Check
  • one new token at context S computes S scores and mixes S values per head: 2·S·H + 2·S·H, × N heads = 4·S·D
  • summed over all T tokens of a sequence that becomes the T² grid
  • these multiply activations (cached K, V), not parameters, so a per-parameter rule misses them: +27% at 8k, 4.3× at 128k

5 · Predict commit to an answer before revealing

A variant keeps 32 query heads but uses 4 KV heads (groups of 8). Before computing: KV per token, how many 8k sequences fit in 63.9 GB, and whether you'd expect quality to move toward MHA or toward MQA.

Reveal

KV per token = 2 × 32 × 4 × 128 × 2 = 65,536 B = 64 KiB, half of GQA-8. An 8k sequence is 0.537 GB, so about 119 fit (computed). Quality moves toward MQA: more query heads share each set of keys and values, so each group has less to work with.
