Checkpoint 2: from bytes to step time

Ties together the GPU as a machine, the roofline, prefill vs decode on your Mac and serving metrics, with FLOPs per token underneath: how a chip's two numbers decide what a step costs, and what a user and a provider see as a result.

How to use this page. Close the four cards. Answer each question in writing, in full sentences, before opening its Check. A wrong or shaky answer isn't a failure; it tells you exactly which section to reopen. The questions are mixed on purpose, so you have to work out which idea applies before you can answer.

1 · Mixed retrieval

  1. which concept?Your team's H100 service decodes Llama-3.1-8B at batch 4 and feels slow. Someone proposes a month of work rewriting the matmul kernels to reach 95% of tensor-core peak. Which idea predicts whether that helps, and what would you try instead?
    Check
    • the roofline: at batch 4 a weight matmul's intensity is about 4 FLOPs per byte, far below the ridge of 295
    • the step is memory-bound; the math term is already tiny, so faster math doesn't move the max
    • instead: fewer bytes (FP8 weights: 4.79 → 2.40 ms at batch 1), more tokens per weight read (a bigger batch), or more bandwidth (an H200)

    Missed it? Reopen the roofline, "Batching moves you along the roof" and "Why it beats the alternatives".

  2. An H100 decodes Llama-3.1-8B at batch 1. For what fraction of the step are the tensor cores busy, and which fact about the memory hierarchy is the root cause?
    Check
    • 16.2 µs of math in a 4.8 ms step: about 0.3% busy, 99.7% idle
    • the 16.06 GB of weights is about 321× the 50 MB L2, so nothing can stay on chip between steps
    • every step streams all of it from HBM at 3.35 TB/s

    Missed it? Reopen the GPU as a machine, "The memory hierarchy, level by level" and "Where the FLOPs come from".

  3. which concept?Users say the first word takes about 4 seconds when they paste a long document, but once text starts it streams smoothly. Which phase and which metric is this, what resource bounds it, and what else could be adding to it?
    Check
    • TTFT, set by prefill; streaming smoothly means TPOT is fine
    • prefill is compute-bound, and its time grows with prompt length (a 10× longer prompt is about 10× longer prefill)
    • queueing adds straight onto TTFT, and so does the network; check the queue before blaming the model

    Missed it? Reopen serving metrics, worked example 1 and the E2E formula, and prefill vs decode, "How it differs from related ideas".

  4. Your M3 decodes qwen3.5:4b at 15.25 tok/s from a 3.4 GB model file. What memory bandwidth is it achieving, what fraction of peak is that, and why is the estimate only approximate?
    Check
    • 15.25 × 3.4 GB ≈ 51.9 GB/s
    • about half of the M3's ~100 GB/s
    • the file includes a vision encoder that text decoding never reads; with the ~2.85 GB text-weights estimate it's about 43 GB/s

    Missed it? Reopen prefill vs decode, "Why decode is stuck at ~15 tok/s".

  5. On an H200 (989 TF/s, 4.8 TB/s), where is the ridge, and what is Llama-3.1-8B's batch-1 decode ceiling? Does a 1,000-token prefill get faster than on an H100?
    Check
    • ridge = 989e12 ÷ 4.8e12 ≈ 206
    • decode: 16.06 GB ÷ 4.8 TB/s ≈ 3.35 ms per step, about 299 tok/s (1.43× the H100)
    • prefill doesn't change: it's compute-bound, and C is the same 989 TF/s (16.2 ms floor)

    Missed it? Reopen the roofline, "It depends on the chip", and the GPU card, "Does more FLOPs mean faster?"

  6. which concept?A provider running ~1,100-token contexts on one H100 raises its decode batch from 120 to 240 and announces a 32% throughput gain. Your dashboard shows every request now misses the 10 ms TPOT target. Which number should they have reported, and what does it read now?
    Check
    • goodput: throughput from requests that meet the SLO
    • at B = 240 each step takes about 15.1 ms (every sequence's KV read is added), so total tok/s rises from 12,050 to about 15,870 (computed with the card's step formula)
    • but no request meets 10 ms, so goodput falls from 12,050 to 0

    Missed it? Reopen serving metrics, worked example 2 and "Why goodput beats the alternatives".

  7. X[B, 4096] · W[4096, 14336] takes 35.07 µs at B = 1 and 37.87 µs at B = 256 on an H100, but 60.80 µs at B = 512. Explain all three numbers with one mechanism.
    Check
    • the 117 MB of weights are read once however many rows share them, so below the ridge the time is set by that read
    • intensity grows about linearly with B; up to 256 the step stays memory-bound and barely moves (the activations add a little)
    • at 512 the intensity (441) passes the ridge, so the time becomes FLOPs ÷ C and grows with B

    Missed it? Reopen the roofline, the batch-sweep table.

3 · Project: a step-time model you check against your own Mac

What it reinforces: the chip's C and W (GPU card), the max() and the ridge (roofline), 2N (FLOPs per token), the two phases (prefill vs decode), and TTFT, TPOT, SLOs and goodput (serving metrics). You build the model on the H100 and then test it against a machine you can actually measure.

H100: C = 989e12 FLOP/s W = 3.35e12 B/s HBM = 80e9 B model: N = 8.03e9 weights = 16.06e9 B KV = 131,072 B per token M3: W ≈ 100e9 B/s qwen3.5:4b file ≈ 3.4e9 B

In about 50 lines of Python:

  1. Step time. Write step(B, S) = B·S·KV ÷ W + max(2·B·N ÷ C, weights ÷ W). Reproduce the serving card's rows for B = 1, 64, 120 and 443 at S = 1,100.
  2. Limits. Write max_batch(slo, S) (the largest B with step ≤ slo) and mem_batch(S) (sequences that fit beside the weights). Tabulate both for S = 1,100 and 8,192, with SLOs of 10 and 25 ms, and mark which limit binds first.
  3. One request. Add ttft(P) = max(2·N·P ÷ C, weights ÷ W) and e2e(P, n) = ttft(P) + (n − 1)·step(1, P + n/2) (the context averages P + n/2 over the output). Compute both for a 1,000-token prompt and 200 output tokens.
  4. Port it to your Mac. Set W = 100e9 and weights = 3.4e9. What decode ceiling does the model predict, and what fraction of it does the measured 15.25 tok/s reach? Calibrate an effective W from that measurement.
  5. Test it. Run labs/measure_ollama.py with a prompt of about 1,000 tokens. Predict decode tok/s with your calibrated W before you look, then compare, and explain any gap with a term your model leaves out.
Done when: steps 1–4 print the numbers in the check; you have written your step-5 prediction down before running the measurement; and you can say in one sentence which term explains any gap between your prediction and the measurement.
Check: the numbers (computed with a Python version of this exact model)
  • Step: 4.84, 7.55, 9.96 and 26.26 ms at B = 1, 64, 120 and 443.
  • Limits at S = 1,100: 10 ms → B = 120, 25 ms → B = 421, memory → 443; the SLO binds first in both cases. At S = 8,192: 10 ms → 16, 25 ms → 63, memory → 59; at 25 ms memory binds first.
  • One request: TTFT 16.2 ms (the math beats the 4.79 ms weight read), E2E ≈ 979 ms.
  • M3: predicted ceiling 100 ÷ 3.4 ≈ 29.4 tok/s; measured 15.25 is about 52% of it, so the effective W ≈ 51.9 GB/s. With that W the model predicts about 15 tok/s at any prompt length.
  • Step 5 is yours to measure. If decode comes out below your prediction, the model's missing term is the one the Mac card points to: each step also reads a KV cache that grows with the prompt (and the file-size estimate of bytes per step is approximate).
