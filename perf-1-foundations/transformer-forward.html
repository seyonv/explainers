The transformer forward pass

Also called the decoder-only transformer, "a forward pass", or "one step of the model". Every prefill is one of these over the whole prompt, and every decode step is one of these over a single new token.

Prime · 2 minutes before you read

The problem: Every serving number later in the series (16 GB of weights, 128 KiB of KV per token, 16 GFLOP per token) starts from one question: what does one forward pass compute, and where do the weights sit? Without that inventory those numbers have no origin, and you can't tell which part of the model a trick is shrinking.

Where it fits: First content card of the course; it assumes nothing. The attention card opens the attention box, the FLOPs card turns this parameter count into work, and the machine cards ask how long it takes to read these weights.

In one breath

Each token becomes a vector of numbers. That vector passes through L identical blocks: in each block, attention mixes in information from earlier tokens, and the MLP transforms each token on its own. At the end, the last token's vector is turned into a probability for every word in the vocabulary, and one is picked.

The parts, each with two examples

Analogy: the residual stream is a shared notebook per token. Each block has two editors. Attention copies in notes from earlier tokens' notebooks; the MLP rewrites this token's notes on its own. Neither erases; both add.

The stream stays [T, D] from start to finish; only inside attention (heads) and the MLP (width F) does it change shape. The k and v rows are exactly what the KV cache stores.

How it differs from related ideas

✗ Encoder-only (BERT)

Same blocks, but attention looks both left and right, and there is no generation loop: one pass gives a vector per token for search, classification or embeddings. Nothing to decode, so no growing KV cache.

✗ Encoder-decoder (T5, Whisper)

The original "Attention Is All You Need" layout: an encoder reads the input once, and a decoder generates while also cross-attending to it. Two stacks and two kinds of attention; common for translation and speech-to-text.

✗ MoE transformer (DeepSeek-V3)

The MLP becomes 256 routed experts plus 1 shared, and each token uses 8 routed ones: 671B parameters stored, 37B active per token. Memory follows the 671B, compute per token follows the 37B.

✗ State-space and hybrids (Mamba)

Replace most or all attention with a recurrence that carries a fixed-size state, so per-request memory does not grow with context length. Hybrids keep a few attention layers.

✓ Dense decoder-only (Llama, Qwen, Mistral)

The model this series optimises. Every weight is used for every token, and every prefill and every decode step is exactly the pass above. Once you can count its parameters and its KV cache, the serving math in the next courses follows.

Most parameters live in the MLP. Is that where the cost is?

For weights, yes: 70.2% of Llama-3.1-8B is MLP. But most per-request memory lives in attention's KV cache. Attention's weights are 1.34B params (2.68 GB in BF16), shared by every request. On top of that, each request stores k and v for every token in every layer: 128 KiB per token, so 1.07 GB per 8,192-token sequence. Fill the 63.9 GB left on an H100 after weights and you hold about 59 such sequences: about 4× the memory of the whole model, all of it attention's.

Where the parameter view misleads:

  • MoE. DeepSeek-V3 stores 671B but uses 37B per token. Count total parameters for memory and active parameters for FLOPs and per-token bandwidth.
  • Long context. Weight matmuls cost about 2 FLOPs per parameter per token no matter the length, but attention's score and mix steps grow with the number of earlier tokens. The Scaling Book's rule of thumb (it assumes F = 4D and plain multi-head attention) says dot-product attention FLOPs overtake the matmuls once T > 8D. For D = 4096 that would be about 32k tokens. This is my extrapolation: Llama's F = 3.5D and GQA shift the exact crossover.
  • Tied embeddings. Small models often share one matrix for embedding and LM head, so the "13.1%" slice halves. Llama 3.1 8B doesn't share.

1 · Core model what to internalise, what to just look up

Keep it if it changes what you can explain, predict, compare, choose, build or debug. Otherwise it's reference.

Understand and remember

  • The residual stream stays [T, D] → each sublayer reads norm(x) and adds its result back → the 32 blocks are identical and stackable → params = L × (attention + MLP + norms) + embedding + LM head = 8.03B
  • A dense model uses every weight for every token → one forward pass touches all 8.03B → each decode step must read all 16.06 GB of BF16 weights → reading, not math, will set decode speed (the machine cards)
  • Attention is the only step where tokens talk → each token's k and v must stay available to later tokens → they're cached per token per layer (128 KiB) → per-request memory belongs to attention even though the MLP holds 70% of the weights
  • Decode feeds each sampled token back in → one full pass per generated token; prefill runs the same pass over all T prompt tokens at once → same weights, very different amount of work per weight read
  • detail that matters Llama 3.1 doesn't tie embedding and LM head → 2 × 525.34M = 13.1% of the model → in a small model with tied embeddings that slice halves
  • detail that matters MoE (DeepSeek-V3) stores 671B but uses 37B per token → count total parameters for memory, active parameters for FLOPs and bytes per token

5 · Predict commit to an answer before revealing

A hypothetical Llama-3.1-8B variant keeps every shape but doubles the vocabulary to 256,512. Before computing: how many parameters does it add, which share grows, and does the KV cache per token change?

Reveal

The 2·V·D term doubles from 1.05B to 2.10B, so the model grows by 1.05B to 9.08B, and embedding + head go from 13.1% to about 23%. The KV cache per token is unchanged: it depends only on L, K and H. Each decode step now reads about 18.16 GB instead of 16.06, so the H100 floor rises from 4.79 to about 5.42 ms (computed).
