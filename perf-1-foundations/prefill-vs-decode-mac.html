Before this: Compute-bound or memory-bound?

Prefill vs decode, measured on your Mac

Also called prompt processing vs generation, or in Ollama's words "prompt eval rate" vs "eval rate": the two phases of inference. Measured here with qwen3.5:4b on your M3, then projected to Llama-3.1-8B on an H100.

Prime · 2 minutes before you read

The problem: Everything so far was arithmetic from spec sheets. Until you measure on hardware you own, "prefill is compute-bound, decode is memory-bound" is a slogan, and you can't tell a slow machine from a slow setup.

Where it fits: Applies the roofline right after you learn it: the same model does 188 tok/s in prefill and 14 in decode on your M3. The serving-metrics card next turns these two phases into TTFT and TPOT.

In one breath

Reading the prompt (prefill) pushes all its tokens through the model in one parallel pass, so each weight fetched from memory gets used for many tokens and the limit is compute. Writing the answer (decode) makes one token per full pass over the weights, so the limit is how fast memory can deliver them. On your M3 that's about 190 vs 15 tokens/s.

To scale, for the 244-token row: 1.30 s + 9.07 s = 10.37 s, of which prefill is 12.5%. Token n+1 can't start until token n exists, so decode can't be parallelised within one request.

Why decode is stuck at ~15 tok/s: the bandwidth arithmetic

Every decode step has to stream (roughly) all the weights from memory to the chip, and it does very little math per byte. So the speed is capped by bandwidth:

vdecode≤ Bmemory bandwidth Wbytesbytes read per step so Beffective≈ vmeasured×Wbytes
vdecode speed, tokens per second (one request, batch 1)≈ 15 on your M3 Bmemory bandwidth of the chip~100 GB/s M3 · 3.35 TB/s H100 Wweight bytes read per decode step (plus a little KV cache)~3.4 GB · 16.06 GB
your M3: 15 tok/s × ~3.4 GB ≈ 51 GB/s (≈ half of ~100 GB/s peak) per row: 15.25 → 51.9 · 15.14 → 51.5 · 14.12 → 48.0 GB/s H100, running example (Llama-3.1-8B, BF16, batch 1): 3.35 TB/s ÷ 16.06 GB ≈ 209 tok/s ≈ 4.8 ms/step ← a ceiling, not a measurement

The 3.4 GB is the model file, and it's an approximation: the file also contains a vision encoder that text decoding never reads. Using the ~2.85 GB text-weights estimate from the memory-bandwidth card instead gives 15 × 2.85 ≈ 43 GB/s. Either way, well below peak. The H100 figure is arithmetic from the spec sheet; real engines reach a fraction of it.

The two phases, on two machines

Like a cashier scanning a whole trolley at once (prefill) versus a pen writing a letter one word at a time, where each word depends on the last (decode).

PhaseWhat actually happensExample A: your M3, measuredExample B: H100, running example (ceiling)
PrefillAll prompt tokens go through every layer together as one big matrix multiply; the keys and values are saved in the KV cache and the first output token comes out. 244 tokens in 1.30 s188 tok/s, still rising with prompt length 1,000 tokens in ≥ 16.2 ms2 × 8.03B × 1,000 ÷ 989 TFLOPS, at 100% MFU ≈ 61,600 tok/s
DecodeOne new token goes through every layer, reading all the weights and the KV cache so far, then is appended and the loop repeats. 14.12–15.25 tok/s65.6–70.8 ms per token; ~51 GB/s implied ≤ 209 tok/s3.35 TB/s ÷ 16.06 GB, ≈ 4.8 ms per step
H100, batch 1, BF16 (2 FLOPs and 2 bytes per parameter per token): prefill ceiling = 989e12 ÷ 2N decode ceiling = 3.35e12 ÷ 2N ratio = 989 ÷ 3.35 ≈ 295 (N cancels: the gap is the chip's ops:byte)

The 295 is derived on this card from the spec numbers, not measured. On the H100 the gap between the phases is about 295× at batch 1; on your M3 it's 13× measured, because Ollama's prefill at 244 tokens is still far from saturating the chip (our inference from the rising prefill numbers, not a measured utilisation).

How it differs from related ideas

✗ TTFT

Time to first token is what the user feels before anything appears: ≈ queue + network + prefill. On your Mac, with no queue or network, it's mostly the 0.29–1.30 s of prefill. See serving metrics.

✗ Throughput with batching

A server decodes many users at once: one read of the weights serves the whole batch, so cost per token falls even though each user's speed doesn't rise. See step time.

✗ Prompt caching

Reuses the KV cache from an earlier request with the same prefix, so prefill is skipped for those tokens. It shortens TTFT but does nothing for decode speed. See prompt caching.

✓ Separating the two phases

The first thing every serving system does: prefill is tuned for FLOPs (TTFT), decode for bandwidth and batch size (tok/s). Chunked prefill and disaggregated serving both start from this split.

Why did decode slow down with a longer prompt? And is it always like this?

The dip from 15.25 to 14.12 tok/s (7%) at 244 prompt tokens most likely comes from the KV cache: each decode step reads the weights plus the keys and values of every earlier token, and that second read grows with the prompt. This is our inference; the lab didn't measure the KV reads directly. At 244 tokens the cache is small next to 3.4 GB of weights, so the effect is small; at long contexts it becomes a big part of each step.

Not always memory-bound. Your Mac serves one request at a time (batch 1), the worst case for decode. A datacenter GPU batches many users into each step. Once the batch passes the critical batch size (≈ 295 for an H100 in BF16), decode's matrix multiplies become compute-bound too. See critical batch size. And prefill isn't always compute-bound: very short prompts (like the 27-token row, at half the speed of the 244-token row) don't give the chip enough tokens to work on at once.

Understand and remember

  • Prefill pushes every prompt token through each weight in one pass → many FLOPs per byte fetched → limited by compute and by how well the prompt fills the chip → tok/s rises with prompt length (92 → 188)
  • Decode makes one token per full pass → each weight byte serves one token → I ≈ 1 → speed ≤ bandwidth ÷ bytes per step → about 15 tok/s on the M3, a 209 tok/s ceiling on an H100
  • Measured tok/s × bytes per step = effective bandwidth → 15 × 3.4 GB ≈ 51 GB/s, about half the M3's ~100 GB/s → the gap to peak is efficiency, not the model
  • Token n+1 needs token n → decode is serial inside a request → only batching across requests shares each weight read → one user on a laptop is the worst case for decode
  • detail that matters Each decode step also reads the KV cache → it grows with context → likely the 7% dip at 244 tokens (inferred, not measured) → at long context it becomes a big part of each step

  1. concept Explain why an H100's prefill-to-decode ceiling ratio equals the chip's ops:byte, whatever model it runs.
    Check
    • prefill ceiling = C ÷ 2N tokens/s (2 FLOPs per parameter per token)
    • decode ceiling = W ÷ 2N tokens/s (2 bytes per parameter in BF16, one read per token)
    • the ratio is C ÷ W = 295; N cancels
  2. mechanism Using the 244-token row, compute the per-token cost of prefill and of decode, the total time for 128 output tokens, and prefill's share of it.
    Check

    • prefill is 12.5% of it
  3. mechanism Why is the 27-token prompt's prefill only about half as fast per token as the 244-token one?
    Check
    • with few tokens, each weight fetched does little work, so the chip isn't saturated
    • the pass still has to fetch the weights and pay fixed costs
    • the card flags this as an inference from the rising numbers, not a measured utilisation
  4. tradeoff Your M3 decode implies about 51 GB/s. Name two changes that would raise single-user tok/s and one that wouldn't, and say why.
    Check
    • fewer bytes per step: a smaller or more aggressively quantized model
