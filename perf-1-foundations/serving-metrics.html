Before this: Compute-bound or memory-bound?

Serving metrics: TTFT, TPOT, throughput, goodput

Also called time to first token; time per output token, inter-token latency (ITL) or time between tokens (TBT); end-to-end (E2E) latency; tokens/s per user vs total tokens/s; SLO; P50/P99. These are the numbers an inference provider is judged and priced on. Here they're worked out for the running example: Llama-3.1-8B BF16 on one H100.

Prime · 2 minutes before you read

The problem: A model that's fast for one user can still be too expensive to serve, and a server with huge throughput can still feel slow to every user. Without TTFT, TPOT, percentiles and goodput you can't tell which one you have, or price a GPU-hour in good requests.

Where it fits: Last card of the course. It prices the two phases you just measured: prefill becomes TTFT and decode becomes TPOT. It then uses the roofline's max() to show how batching trades per-user speed for total throughput, which perf-2's step-time formula makes rigorous.

In one breath

A provider is judged on how fast the first token arrives (TTFT), how fast the rest stream in (TPOT), and how many tokens per second per GPU it can sell while still hitting those targets for most requests. Goodput is throughput that meets the SLO. It's the number that sets the cost per request.

Worked example 2: the provider's view, batch 1 → 443

Batching lets one read of the weights serve B users at once. Each user's step gets a little slower as B grows, because every sequence's KV cache is read too, while the total goes up a lot. The Scaling Book's general step-time formula (step-time) adds the KV reads to whichever is slower: the weight math or the weight reads. With ~1,100 tokens of KV per sequence (144.2 MB), it gives:

Up to B ≈ 295 (B_crit), reading the weights costs more than the math on them. Past that, the math term takes over: at B = 443 it's 7.19 ms against 4.79 ms. Going from B = 120 to 443 raises raw throughput by 40% (12,050 → 16,870 tok/s), but every user drops to 38 tok/s and misses the SLO. Goodput falls from 12,050 to 0. Prefill work and attention FLOPs are left out, so the columns are decode-only ceilings.

An odd fact about one H100: even the step with HBM completely full (B = 443) takes only 26.3 ms. So Etalon's "medium" 50 ms TPOT target can never bind here, and its "strict" 25 ms target only binds at B ≈ 421, just below the 443 memory limit. Memory capacity stops the batch first. Tight SLOs like 10 ms, long contexts, or big models that need several chips are where the SLO sets the batch.

Goodput: what the papers actually define

"…maximize per-GPU goodput, defined as the maximum request rate that can be served adhering to the SLO attainment goal (say, 90%) for each GPU provisioned – higher per-GPU goodput directly translates into lower cost per query."DistServe (Zhong et al., OSDI 2024), §1. Its SLOs are set on both TTFT and TPOT.

Etalon (Agrawal et al. 2024) doesn't use the word "goodput" except in its reference to DistServe. Its §2.2 defines the standard metrics: TTFT "includes the scheduling delay … and the prompt processing time", TPOT is "the total decode time of a request normalized by the number of decode tokens", and capacity is "the maximum request load (queries-per-second) a system can sustain while meeting certain latency targets (SLOs)", which is the same idea as goodput. §3.1 argues that TPOT averages away stalls. For example, a vLLM request stalled for about 10 s behind a long prefill barely moves its TPOT. §4.1 proposes a deadline-based replacement:

token i is due at D_i = D_p + i × D_d D_p = prefill target, a function of prompt length · D_d = per-token (TBT) target fluidity-index = fraction of token deadlines met (after a miss, deadlines reset) fluid token rate = 1 ÷ smallest D_d with 99% of requests at fluidity-index ≥ 0.9 D_d targets: 25 ms (strict, chat) · 50 ms (medium) · 100 ms (relaxed)

In Etalon's public-API test, Groq showed about 600 tokens/s by TPOT, while tail TBT implied roughly 4× less. The "tok/s total that meets the SLO" in the table above is my token form of DistServe's request-rate definition. The idea is the same, but the unit is mine.

Synthetic and illustrative: 1,000 seeded requests in the lab. The queue averages 30 ms, and 3% of requests get stuck behind a burst for 0.3–1.5 s. TPOT is about 7.5 ms with jitter. Under an SLO of TTFT ≤ 250 ms and TPOT ≤ 10 ms, 889 of 1,000 requests pass: 88.9% SLO attainment, just short of a 90% goal. The mean TTFT (79 ms) is twice the median and still hides a P99 of about 1 s.

Your own measurement shows the same right skew. 20 identical requests on the M3 gave p50 4.66 s, p95 6.54 s, max 7.14 s, so p95 is 1.40× the median with nothing else running.

Why goodput beats the alternatives

✗ Mean latency

Hides the tail. In the synthetic run the mean TTFT is 79 ms, which looks fine, while 1 in 100 users waits about a second.

✗ Raw throughput

You can buy it by making everyone wait. Going from batch 120 to 443 gives +40% tok/s, but every user gets 38 tok/s and misses the SLO.

✗ TTFT alone

Ignores streaming speed. A 16 ms first token followed by 100 ms gaps still feels slow, and TTFT also grows with prompt length (Etalon §3.1).

✓ Goodput under SLOs

Counts only the work that met the TTFT and TPOT targets for the agreed share of requests, so it can't be gamed from either side. Divide by GPU cost and you get the cost per good request.

Which number matters depends on the product

Goodput is not always the right target:

  • Chat and streaming: TTFT, plus a TPOT fast enough to beat reading speed. DistServe notes that TPOT "only remains important until it is faster than human reading speed (i.e., 250 words/min)".
  • Agents and tool calls: the tokens aren't useful one at a time, so Kiely measures "total response time" (E2E), and one user action triggers many calls.
  • Offline batch (evals, data generation, document processing): the Scaling Book says it "only cares about bulk cost of inference and is blind to the latency of individual samples". Here raw throughput per dollar is the right metric, and goodput with a loose SLO reduces to it.
  • Edge / your laptop: one user at a time, lowest latency, so batching and goodput don't apply.

Also note that GPU-only numbers (like the floors above) leave out network and queue time. Kiely separates "inference time" from end-to-end time: if inference is fast but E2E is slow, fix the infrastructure, not the model.

Understand and remember

  • E2E = queue + prefill (TTFT) + (n_out − 1) × TPOT → prefill is compute-bound (16.2 ms for 1,000 tokens), each decode step memory-bound (4.84 ms) → for long outputs decode dominates (962.6 of 979 ms)
  • One weight read serves every sequence in the batch → total tok/s rises with B (207 → 12,050 at B = 120) → but every sequence's KV cache is also read each step → TPOT grows (4.84 → 9.96 ms) → per-user speed falls
  • An SLO caps TPOT → B ≤ (SLO × W − weight bytes) ÷ KV bytes per sequence (120 at 10 ms) → past it throughput still rises (+40% at B = 443) but no request meets the SLO → goodput = 0 → goodput is what sets cost per good request
  • Latency distributions are right-skewed (queues, bursts) → the mean sits above the median yet far below the tail (79 ms mean, ≈ 1 s P99 TTFT) → SLOs are set on percentiles, not on means
  • detail that matters Past B_crit ≈ 295 the weight math (2BN/C) outgrows the weight read → the step switches from the memory term to the math term (B = 443: 7.19 vs 4.79 ms)
  • detail that matters TPOT averages away stalls (a ~10 s stall barely moves it) → Etalon proposes per-token deadlines (fluidity-index) instead

Reveal

Each sequence now reads 1.07 GB per step. The SLO allows B ≤ (0.010 × 3.35e12 − 16.06e9) ÷ 1.07e9 ≈ 16, at 9.92 ms and about 1,613 tok/s, well below the memory cap of 59. At 25 ms the SLO would allow about 63, so memory binds first at 59 (23.7 ms, ≈ 2,489 tok/s). All computed with the card's step formula. Long context makes the SLO bite far sooner.
