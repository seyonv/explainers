The GPU as a machine

Also: streaming multiprocessor (SM), tensor core, HBM, shared memory / SRAM, warp. Every number here is for one H100 SXM, the chip in this course's running example (Llama-3.1-8B in BF16).

Prime · 2 minutes before you read

The problem: "Decode is memory-bound" means nothing until you know what the memory is, how far it sits from the math units, and how much math those units can do. Without a picture of the chip, every later optimisation (tiling, batching, fusing, quantizing) looks like an unrelated trick.

In one breath

A GPU is 132 small, independent processors (SMs) that each keep up to 2,048 threads in flight, run in lockstep groups of 32 called warps. They are fed by a memory hierarchy that gets smaller and closer to the math at each step: 80 GB of HBM, then a 50 MB L2 cache, then 256 KB of SMEM per SM, then registers. Tensor cores do matrix multiply-accumulate and provide nearly all the FLOPs.

Worked example: inside one H100

One SM highlighted (green). Each SM has 4 sub-partitions; the H100 has 132 × 4 = 528 tensor cores and 132 × 4 × 32 = 16,896 CUDA cores. Layout after Scaling Book Part 12's H100 SM figure; not to scale.

Each part, with two real examples

Think of a factory: 132 workshops (SMs), each with 4 benches (sub-partitions). Each bench has one big press for matrices (tensor core), a crew of 32 that must do the same move together (a warp on the CUDA cores), and a tiny tray of parts at hand (registers). The workshop shares a shelf (SMEM), the factory shares a warehouse (L2), and the trucks bring everything from a depot (HBM).

How it differs from related ideas

✗ CPU

A few big cores (your M3 has 8) built for complex sequential work. Great at branchy logic; far too few lanes and too little bandwidth to stream 16 GB of weights per token quickly.

✗ TPU

One or two big TensorCores with systolic-array MXUs and a large programmer-managed VMEM (about 128 MB on v5p vs ≈33 MB of SMEM on an H100). Simpler and cheaper, but a single thread of control that leans on the compiler.

✗ Apple unified memory

CPU and GPU share one 24 GB pool, so a model that fits is simple to run. But at ~100 GB/s it has about 1/33 of H100 bandwidth, which caps Llama-3.1-8B BF16 near 6 tokens/s.

✓ GPU: massive parallelism + HBM

132 independent SMs, up to 270,336 resident threads, 528 tensor cores, and 3.35 TB/s to 80 GB of HBM. It hides memory waits by switching warps and turns matmuls into 990 TFLOP/s.

Does more FLOPs mean faster?

Not for LLM decode. At batch 1, each token needs 16.2 µs of tensor-core math but 4.8 ms of weight reads, so the math units wait about 99.7% of the time. Kiely's advice: for more tokens per second, pick the GPU with more memory bandwidth (an H200 over an H100), not more FLOPs. FLOPs win for prefill, large batches, and image or video generation.

Tensor cores also only help with part of the work:

  • They do matmul-shaped work. Softmax, activations, norms and reductions run on CUDA cores and special function units, at 66 TFLOP/s or less.
  • Their headline numbers are for specific precisions: BF16 at 990 TFLOP/s, FP8 at twice that. A precision or shape the kernel can't map onto them runs far slower.
  • They need enough rows to reuse each weight byte: below about 295 FLOPs per byte (the H100's ops:byte) you're memory-bound. That's the roofline.

For one user on a laptop, a GPU is not the only option: your M3 runs 4B models fine because a Q4 model is small and bandwidth, not FLOPs, sets the speed.

Understand and remember

  • Each memory level is smaller and closer to the math (80 GB HBM → 50 MB L2 → 256 KB SMEM per SM → registers) → 16.06 GB of weights is 321× the L2 → the weights can't stay on chip → every decode step streams them from HBM: ≈ 4.8 ms at 3.35 TB/s
  • Tensor cores do matrix multiply-accumulate → 990 vs 66 TF/s on the CUDA cores (15×) → matmul-shaped work in a supported precision runs fast → softmax, norms and activations don't get that speed
  • Batch-1 decode needs 16.2 µs of math but 4.8 ms of reads → the tensor cores sit idle ≈ 99.7% of the step → for decode speed buy bandwidth (an H200 over an H100), not FLOPs
  • An SM keeps up to 64 warps resident → when one waits on memory, another runs → latency is hidden by switching, not by caching everything → but only if each thread uses few enough registers to leave room for many warps
  • detail that matters A warp's 32 threads run one instruction together (SIMT) → an if/else split runs both branches in turn with the idle lanes masked → divergent code wastes lanes
  • detail that matters Registers are 64 KB per sub-partition → at 256 registers per thread only 8 warps fit per SM instead of 64 → fewer warps to switch between, less latency hiding

Reference only

  • 132 SMs, 528 tensor cores, 16,896 CUDA cores
  • L2 ≈ 5.5 TB/s (measured, not published)
  • NVLink 450 GB/s per H100, 900 on B200
  • V100/A100 SMEM sizes and tensor-core FLOPs per cycle
  • TPU VMEM of about 128 MB on v5p

3 · Retrieve from memory, card closed
  1. concept Explain why a GPU keeps thousands of threads resident instead of running a few very fast ones like a CPU.
    Check
    • a read from HBM takes a long time
    • with many resident warps the SM switches to one that is ready and hides the wait
    • a CPU's few big cores (8 on the M3) suit branchy sequential work but have too few lanes and too little bandwidth to stream 16 GB per token
  2. mechanism Follow one weight from HBM to a tensor core during a matmul: which levels does it pass through, and who manages each one?
    Check
    • HBM: you allocate it (global memory, cudaMalloc)
    • L2: hardware only; you can only shape access patterns
    • SMEM: you as shared memory (tiles for the tensor cores), or hardware as L1
    • registers: the compiler, then the tensor core's multiply-accumulate
  3. mechanism Using the card's register numbers, how many warps can one SM keep resident if every thread uses 256 registers, and why should a kernel writer care?
    Check
    • 4 sub-partitions × 16,384 registers = 65,536 per SM
    • 256 × 32 threads = 8,192 registers per warp → 8 warps, instead of the maximum 64
    • fewer resident warps means fewer to switch to while one waits on memory
  4. tradeoff Pick a chip to maximise single-user tokens/s on Llama-3.1-8B in BF16: an H100, an H200, or a hypothetical chip with 2× the H100's FLOPs and the same bandwidth. Rank them and justify it.
    Check
    • H200 first: 4.8 TB/s → about 3.35 ms per step, ≈ 299 tok/s ceiling (computed)
    • the H100 and the 2×-FLOPs chip tie at 3.35 TB/s → ≈ 209 tok/s
    • extra FLOPs don't help batch-1 decode; they would help prefill
