The GPU as a machine

Also: streaming multiprocessor (SM), tensor core, HBM, shared memory / SRAM, warp. Every number here is for one H100 SXM, the chip in this course's running example (Llama-3.1-8B in BF16).

In one breath

A GPU is 132 small, independent processors (SMs) that each keep up to 2,048 threads in flight, run in lockstep groups of 32 called warps. They are fed by a memory hierarchy that gets smaller and closer to the math at each step: 80 GB of HBM, then a 50 MB L2 cache, then 256 KB of SMEM per SM, then registers. Tensor cores do matrix multiply-accumulate and provide nearly all the FLOPs.

Worked example: inside one H100

One SM highlighted (green). Each SM has 4 sub-partitions; the H100 has 132 × 4 = 528 tensor cores and 132 × 4 × 32 = 16,896 CUDA cores. Layout after Scaling Book Part 12's H100 SM figure; not to scale.

Each part, with two real examples

Think of a factory: 132 workshops (SMs), each with 4 benches (sub-partitions). Each bench has one big press for matrices (tensor core), a crew of 32 that must do the same move together (a warp on the CUDA cores), and a tiny tray of parts at hand (registers). The workshop shares a shelf (SMEM), the factory shares a warehouse (L2), and the trucks bring everything from a depot (HBM).

How it differs from related ideas

✗ CPU

A few big cores (your M3 has 8) built for complex sequential work. Great at branchy logic; far too few lanes and too little bandwidth to stream 16 GB of weights per token quickly.

✗ TPU

One or two big TensorCores with systolic-array MXUs and a large programmer-managed VMEM (about 128 MB on v5p vs ≈33 MB of SMEM on an H100). Simpler and cheaper, but a single thread of control that leans on the compiler.

✗ Apple unified memory

CPU and GPU share one 24 GB pool, so a model that fits is simple to run. But at ~100 GB/s it has about 1/33 of H100 bandwidth, which caps Llama-3.1-8B BF16 near 6 tokens/s.

✓ GPU: massive parallelism + HBM

132 independent SMs, up to 270,336 resident threads, 528 tensor cores, and 3.35 TB/s to 80 GB of HBM. It hides memory waits by switching warps and turns matmuls into 990 TFLOP/s.

Does more FLOPs mean faster?

Not for LLM decode. At batch 1, each token needs 16.2 µs of tensor-core math but 4.8 ms of weight reads, so the math units wait about 99.7% of the time. Kiely's advice: for more tokens per second, pick the GPU with more memory bandwidth (an H200 over an H100), not more FLOPs. FLOPs win for prefill, large batches, and image or video generation.

Tensor cores also only help with part of the work:

  • They do matmul-shaped work. Softmax, activations, norms and reductions run on CUDA cores and special function units, at 66 TFLOP/s or less.
  • Their headline numbers are for specific precisions: BF16 at 990 TFLOP/s, FP8 at twice that. A precision or shape the kernel can't map onto them runs far slower.
  • They need enough rows to reuse each weight byte: below about 295 FLOPs per byte (the H100's ops:byte) you're memory-bound. That's the roofline.

For one user on a laptop, a GPU is not the only option: your M3 runs 4B models fine because a Q4 model is small and bandwidth, not FLOPs, sets the speed.
