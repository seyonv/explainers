Before this: The transformer forward pass

FLOPs per token: 2N to serve, 6N to train

Also called the 2N / 6N rule, 6ND, or just FLOP counting. It's the first number anyone computes about a model: how much arithmetic one token costs to serve, and how much a whole training run costs. Worked here for Llama-3.1-8B.

Prime · 2 minutes before you read

The problem: Before you can say how long a model step takes, you need to know how much work it is. Without a quick count you can't budget a training run, compare a dense model with an MoE, or notice that a chip with more FLOPs won't help decode.

Where it fits: Turns the forward-pass card's parameter count into work, and adds the attention card's context-dependent term. The machine half of the course then asks how long that work takes, and whether math is even the bottleneck.

In one breath

Multiplying an (m×k) matrix by a (k×n) matrix takes 2mkn FLOPs: every one of the mkn multiplies is paired with one add. A forward pass sends each token through every weight matrix once, so it costs about 2 FLOPs per parameter per token. Training also runs a backward pass, which costs about twice the forward, so the total is 6 per parameter per token.

Cinfer≈ 2Nper token Ctrain≈ 6NDwhole run = 2NDforward + 4NDbackward
Ccompute: a count of floating-point operations (FLOPs), not a speed16 GFLOP · 7.2e23 Nparameters actually used per token (for MoE, the active ones)8.03B · 37B of 671B Dtokens in the training run (not the model width here)~15T for Llama 3.1 2, 6FLOPs per parameter per token: 2 forward, +4 backward8 with full remat

Both ignore the attention dot-products, whose cost grows with context length (step 3). This card writes D for tokens in 6ND; in the Scaling Book, D is the model width and tokens are B·T.

Worked example: Llama-3.1-8B, one token

1 · One matrix · the 2mkn rule

A single token is one row (m = 1). Push it through the MLP's gate matrix Wgate, which is 4096 × 14336:

2 · m · k · n = 2 · 1 · 4,096 · 14,336 = 117,440,512 FLOPs ≈ 117.44 MFLOP params in W_gate = 4,096 · 14,336 = 58,720,256 → exactly 2 FLOPs per param

That's the whole trick: with one row, a matmul costs 2 × (the matrix's parameter count). Batch more rows (tokens) and it scales linearly: m tokens cost 2·m·params.

The 6.5% gap is the 525M-parameter embedding table: looking up a row costs no FLOPs, but it still counts in N. Norms, softmax and the SwiGLU multiply are O(D) per token and are left out, as the Scaling Book does.

3 · What 2N leaves out · attention grows with context

Attention also multiplies the token's query against every cached key, then the scores against every cached value. Those are matmuls against activations, not parameters, so 2N never sees them. For one token at context S, each layer does 2·S·H per query head for q·KT and again for scores·V: 4·S·N·H = 4·S·D FLOPs. GQA shares K and V across 4 query heads, which saves memory, not these FLOPs.

Scaling Book shortcut: attention FLOPs / matmul FLOPs ≈ T / (8D) Llama-3.1-8B, D = 4096: 8,192 / 32,768 = 0.25 131,072 / 32,768 = 4.0 break-even: T = 8D = 32,768 tokens

The shortcut assumes F = 4D, D = N·H, K = N (plain MHA, where the book gets 24·D·N·H of projection FLOPs), full non-causal T×T attention, and it leaves out the LM head. Llama has F = 3.5D and GQA, so the exact count above runs a little higher (26.7% vs 25%). In prefill with a causal mask, token t only attends to t earlier tokens, so a T-token prompt averages T/2 of context and pays half of the "S = T" row.

4 · Training · 6ND, then hours

C_train = 6 · N · D = 6 × 8.03e9 × 15e12 = 7.23e23 FLOPs one H100 at 40% MFU (assumed) = 0.40 × 989e12 = 395.6 TFLOP/s H100-hours = 7.227e23 / 3.956e14 / 3600 ≈ 0.51 M Meta's model card, Llama 3.1 8B = 1.46 M GPU-hours (H100-80GB) MFU implied if all 1.46M hours were this 6ND run = 13.9% attention on 8k-token sequences, causal: 3 × 32 × 4 × 4,096 × 4,096 = 6.44 GFLOP/token → +13.4% on 6N sanity check, 405B: 6 × 405e9 × 15.6e12 = 3.79e25 (Llama 3 paper: 3.8e25)

The 40% MFU is an assumption, chosen because the Llama 3 paper reports 38–43% BF16 MFU for its 405B pretraining; it doesn't report MFU for the 8B. The gap to Meta's 1.46M hours is unexplained here. My guess, not verified: the card's figure covers more than one clean pretraining pass (long-context and annealing stages, restarts, maybe post-training), and a small model reaches lower MFU. The 405B check shows 6ND itself is right: 3.79e25 against 3.8e25.

The terms, each with two examples

Think of a FLOP count like a recipe's number of chopping motions: it tells you how much work there is, not how long it takes. That depends on how fast the cook is and whether the ingredients have arrived.

Same FLOPs, different hardware

One decode token of Llama-3.1-8B needs 16.06 GFLOP and, at batch 1, a read of all 16.06 GB of BF16 weights. Compare how long each takes at 100% of peak:

ChipPeak BF1616.06 GFLOP takesBandwidth16.06 GB takesRatio
H100 SXM989 TF/s16.2 µs3.35 TB/s4.79 ms295×

TPU v5e197 TF/s81.5 µs0.82 TB/swon't fit: 16 GB HBM240×
memory time / compute time = (2N bytes ÷ bandwidth) / (2N FLOPs ÷ FLOP/s) = FLOP/s ÷ bandwidth = the chip's ops:byte (295 for H100)

At batch 1 the FLOPs finish ~300× sooner than the weights arrive, so the FLOP count says almost nothing about decode speed. You'd need a batch of about that many tokens to make them match: the critical batch size, covered in perf-2. For TPU v5e, the ratio is the chip's own (1.97e14 / 8.2e11), since 16.06 GB doesn't fit in its 16 GB.

How it differs from related ideas

✗ FLOPs vs FLOP/s

FLOPs is a count of work (16.06 G per token); FLOP/s is a chip's speed (989 T for an H100). Divide one by the other to get a floor on time, never a prediction.

✗ FLOPs vs bytes moved

Decode at small batch reads 16 GB to do 16 GFLOP, so it waits on memory, not math. See step time for when each one wins.

✗ Total vs active params

For MoE, N is what each token touches: DeepSeek-V3 serves at 2 × 37B = 74 GFLOP/token, not 2 × 671B. Memory still has to hold all 671B.

✓ 2N / 6N as the first napkin estimate

One multiplication gives a model's cost per token and a training run's total within ~10% at contexts of a few thousand tokens, before you know anything about the hardware.

Does 2N tell me how fast a model runs?

No. FLOPs are a cost, not a time. The rule fails or needs adjusting when:

  • Decode at small batch: time is set by bytes (≈ 4.8 ms per step on an H100 for weights alone), not by the 16 µs of math. See roofline intuition.
  • Long context: attention adds 4·S·D·L FLOPs per token, 27% at 8k and 4.3× at 128k for Llama-3.1-8B.
  • MoE: use active parameters for FLOPs and total parameters for memory.
  • Training with recomputation: saving only each layer's input makes the backward pass redo the forward, so 6N becomes roughly 8N (Scaling Book, "Gradient checkpointing").

Where it shines: prefill and large-batch serving, where the chip really is doing math (1,000 tokens of prefill ≥ 16.2 ms on an H100 at 100% MFU), and budgeting training runs.

Understand and remember

  • Every multiply is paired with an add → an (m×k)·(k×n) matmul costs 2mkn → one token (m = 1) through a matrix costs 2 × its parameters → a forward pass ≈ 2N FLOPs per token (16.06 GFLOP for Llama-3.1-8B)
  • Backward needs gradients for activations and for weights → about 2× the forward → training ≈ 6N per token and 6ND per run (7.23e23 for 8B on ~15T tokens) → recomputing activations adds one more forward → ≈ 8N
  • Attention multiplies activations (cached K, V), not parameters → its 4·S·D per layer per token is invisible to 2N → it grows with context: +27% at 8k, 4.3× at 128k, break-even near 8D = 32,768 tokens
  • FLOPs are a count, not a time → FLOPs ÷ FLOP/s is only the math floor → at batch 1 reading 16.06 GB takes 295× longer than 16.06 GFLOP of math → the FLOP count says almost nothing about decode speed
  • detail that matters For MoE, N means active parameters → DeepSeek-V3 serves at 2 × 37B = 74 GFLOP per token, not 1,342 → but memory must still hold all 671B
  • detail that matters The embedding lookup is a table read → its 525M parameters count in N but cost no FLOPs → why the exact count is 93.5% of 2N
