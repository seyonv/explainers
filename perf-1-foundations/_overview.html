In one breath

A model step does about 2 FLOPs per parameter per token and must read every weight once, plus the KV cache. Whichever takes longer, the math or the reading, sets the time. Prefill (many tokens per weight read) is limited by math. Decode (one token per sequence) is limited by memory, so its main lever is batching: more tokens share each weight read.

The words people use

Prefill vs decode

The two phases of every request. Prefill reads the prompt in one parallel pass and sets TTFT. Decode writes one token per step and sets TPOT. Also called prompt processing and generation.

Compute-bound vs memory-bound

Whether the math units or the memory reads finish last. Prefill and big batches are compute-bound. Batch-1 decode is memory-bound, with its tensor cores idle about 99.7% of the time on an H100.

TTFT, TPOT, goodput

Time to first token, time per output token, and throughput that still meets the latency targets (SLOs). Goodput is what a provider can actually sell.

Arithmetic intensity

FLOPs per byte moved. Compare it with the chip's ops:byte (295 on an H100) and you know which resource to fix. This one number carries through the rest of the series.

The takeaway

Before optimising anything, ask which side of the max() you're on. If memory sets the step (decode at small batch), then more FLOPs, faster kernels for the math, or a bigger compute chip change nothing. What helps is batching, fewer bytes (quantization, GQA) or more bandwidth. If math sets it (prefill, large batch), those memory tricks buy little and you need tensor-core efficiency.

Where this simple picture breaks: at very long context, attention FLOPs and KV reads grow with every token. MoE models read only their active experts, so N means active parameters. Tiny operations are dominated by launch overhead, not by either roof. Real systems also reach only part of the peak (about 80–85% of spec FLOPs on H100s). Understand and remember

  • Each token needs ≈ 2N FLOPs and each step reads all N·b weight bytes plus the KV cache → step time ≈ max(math, memory) → which side wins depends on tokens per weight read vs the chip's ops:byte (295 on an H100)
  • Prefill: 1,000 tokens share one weight read → math 16.2 ms beats memory 4.8 ms → compute-bound, sets TTFT; decode: 1 token per read → 16.2 µs of math vs 4.79 ms of reading → memory-bound, sets TPOT
  • Decode is memory-bound → the levers that help cut bytes (FP8 2×, GQA 4× on KV), share each read (batching: 207 → 16,870 tok/s total) or add bandwidth (M3 → H100, 33.5×) → more FLOPs change nothing until the batch passes ≈ 295
  • KV bytes grow with context × batch → HBM fills (≈ 59 sequences of 8k) before the math side wins; attention FLOPs also grow with context (+27% at 8k) → the simple 2N picture needs its context terms
  • detail that matters MoE: N means active parameters in the math and per-token bytes, but total parameters for memory capacity
  • detail that matters Real systems reach only part of peak (about 80–85% of spec FLOPs on H100s) → every number on this card is a floor, not a prediction

5 · Predict commit to an answer before revealing

A team moves from Llama-3.1-8B to an MoE with 37B active of 671B total parameters (ignore that it needs several GPUs). Before reading on: which symbols in the formula change, and is batch-1 decode still memory-bound?

Reveal

N in the math term becomes 37B active (74 GFLOP per token), and at batch 1 the bytes read per token also follow the active experts, while memory capacity must hold all 671B. Both sides grow about 4.6× from the dense 8B, so batch-1 decode is still memory-bound. The formula still works once you use active parameters for work and bytes per token, and total parameters for capacity.
