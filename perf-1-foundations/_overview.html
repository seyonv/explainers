Foundations on one card

Overview of perf-1: what a transformer computes, what a GPU is, and why one step of inference takes as long as it does. Everything later in the series (the Scaling Book chapter, kernels, serving engines) builds on this one formula.

In one breath

A model step does about 2 FLOPs per parameter per token and must read every weight once, plus the KV cache. Whichever takes longer, the math or the reading, sets the time. Prefill (many tokens per weight read) is limited by math. Decode (one token per sequence) is limited by memory, so its main lever is batching: more tokens share each weight read.

The mental model: one request through the machine

Measured on your M3 (4B model): prefill ≈ 188 tok/s vs decode ≈ 14 tok/s, about 13× apart. That's the same split, at about 1/30 of an H100's bandwidth (prefill-vs-decode-mac).

The words people use

Prefill vs decode

The two phases of every request. Prefill reads the prompt in one parallel pass and sets TTFT. Decode writes one token per step and sets TPOT. Also called prompt processing and generation.

Compute-bound vs memory-bound

Whether the math units or the memory reads finish last. Prefill and big batches are compute-bound. Batch-1 decode is memory-bound, with its tensor cores idle about 99.7% of the time on an H100.

TTFT, TPOT, goodput

Time to first token, time per output token, and throughput that still meets the latency targets (SLOs). Goodput is what a provider can actually sell.

Arithmetic intensity

FLOPs per byte moved. Compare it with the chip's ops:byte (295 on an H100) and you know which resource to fix. This one number carries through the rest of the series.

The takeaway

Before optimising anything, ask which side of the max() you're on. If memory sets the step (decode at small batch), then more FLOPs, faster kernels for the math, or a bigger compute chip change nothing. What helps is batching, fewer bytes (quantization, GQA) or more bandwidth. If math sets it (prefill, large batch), those memory tricks buy little and you need tensor-core efficiency.

Where this simple picture breaks: at very long context, attention FLOPs and KV reads grow with every token. MoE models read only their active experts, so N means active parameters. Tiny operations are dominated by launch overhead, not by either roof. Real systems also reach only part of the peak (about 80–85% of spec FLOPs on H100s).
