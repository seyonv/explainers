One token at a time

Autoregressive generation, the decoding loop, the KV cache, chat templates · Language Models are Few-Shot Learners (GPT-3), Brown et al., OpenAI, 2020

Prime · 2 minutes before you read

The problem: One forward pass gives a probability for one next token. An answer is many tokens, so something has to run the model again and again, decide when to stop, and avoid redoing the same work every time.

Where it fits: This is the last stop on the route. The previous card chose one token from the model's probabilities; this card puts that choice in a loop, and shows what the loop costs and how the text around the question changes the very first step.

Each trip through the model ends with a probability for every possible next token, and one of them is picked. That's one token, but an answer needs many. So the model runs again on the question plus the token it just picked, and again, until it picks the end-of-text token. Our 9-token answer took 9 full trips through all 24 layers.

Try this first

Guess first: the model writes The capital of India is New Delhi. when it always takes its top token. Out of everything it could have written, how likely was it to write exactly this sentence: about 90%, 50% or 10%?

Show the answer

About 11%. Most words were near-certain (0.964, 0.994), but the probability of a whole answer is the product of its steps, and the first word, The, had only 0.277. Counting the decision to stop afterwards, it's about 7.6%.

Three words first

Autoregressive

Each output is fed back in as input for the next step. The model predicts token n from tokens 1 to n−1, and nothing else.

End-of-text token

A special token the model can pick like any other. In Qwen it's written <|endoftext|>. Picking it means "the text is over", and the loop stops.

KV cache

The keys and values (the K and V vectors each attention layer computes for a token) of every earlier token, kept in memory so that no step has to compute them again.

The answer is built by running the model nine times

← scroll the sketch →

Every row is one forward pass: the question plus the tokens picked so far go into the model, and its top token comes out in green. That token is appended, and the next row starts. On row 9 the model picks <|endoftext|>, so the loop ends. A length limit (here, 20 new tokens) would have stopped it anyway. All numbers are measured by the lab below.

The probability of an answer is the product of its steps

At step n the model gives P(tn | t1 … tn−1): the probability of the next token, given everything before it. Probability's chain rule says the chance of a whole sequence is these steps multiplied together:

P(answer | question) = P(t1 | q) × P(t2 | q, t1) × … × P(t9 | q, t1 … t8)

= 0.277 × 0.964 × 0.919 × 0.994 × 0.969 × 0.698 × 0.994 × 0.680 = 0.111

× 0.682 for <|endoftext|> = 0.076

Products of many numbers below 1 shrink fast. So code adds log-probabilities instead of multiplying probabilities. Our nine steps sum to −2.58, and e−2.58 = 0.076, the same answer. A 1,100-token answer whose steps are each 0.5 has a probability of 0.51100, which is smaller than the tiniest number a 64-bit float can hold, so it comes out as exactly 0.0 (underflow). Its log is a perfectly ordinary −762.5.

Because the product shrinks with every token, long answers always look less likely than short ones. When GPT-3 scored multiple-choice answers by the model's likelihood, it mostly compared the per-token likelihood "to normalize for length" (§2.4).

The loop is what makes generation slow, and the KV cache is what keeps it bearable

← scroll the sketch →

At step 4, without a cache the model recomputes everything for all 10 tokens. With a cache, the 9 earlier tokens' keys and values are already stored, and only the newest token goes through the 24 layers. Both give the same next token.

Why can the keys and values be kept? In a model like this, a token's attention only looks at itself and earlier tokens (the causal mask). So a token's K and V at every layer never change once computed, however much text comes after it. Recomputing them is pure waste.

Other jobs were running at the same time, so treat the times as rough; an earlier run gave 63 ms per cached step and 2.2 s vs 8.9 s in total. Both runs show the cache about 4× faster here. The gap widens as the text grows, because without a cache step n re-reads all n tokens.

The cache costs memory. For this model it's 12 KB per token in bf16 (16-bit numbers): 24 layers × 2 KV heads × 64 numbers × 2 (K and V) × 2 bytes. Our float32 run stores twice that, 24 KB. A 4,096-token conversation needs 48 MB of cache in bf16, per conversation.

The first pass and each later step behave differently: the first reads the whole question in one go, and each later step does a small amount of work for one token but still has to read all 494 million weights. Why that makes later steps slow, measured on a Mac, is in Prefill vs decode, measured on your Mac. What it means for a chat app's speed is in How to think about LLM speed.

A wrapper around the question changes what the model thinks comes next

← scroll the sketch →

The same question in three wrappers, all measured on the base model. The wrapper is ordinary input text. With the Q/A wrapper the first token is already the answer, New, at 0.797. With the chat wrapper the base model starts with ratulations (the end of "Congratulations"), at only 0.127.

Plain What is the capital of India? is ambiguous text. On the internet, a line like that is followed by an answer, by another question, or by a list of options, and the model spreads its bets: The got only 0.277. The model doesn't know an answer is expected.

GPT-3's paper makes this the whole method. It treats the model as a next-token predictor and specifies tasks "purely via text interaction with the model" (abstract): a description and K worked examples written into the input, with no weight updates (§2). It typically fit 10 to 100 examples into the 2,048-token context window. When it needed the model to answer, it put the string Answer: or A: before the slot (§2.4). Our Q/A wrapper does the same, and the first token goes from 0.277 on The to 0.797 on New.

A chat template is the same idea, made fixed. The text is cut into turns with special tokens (<|im_start|>, <|im_end|>), and the template ends with the start of the assistant's turn. An instruction-tuned model has been trained on many conversations in exactly this format, so it has learned that an answer follows, and that it should close the turn when done. The base model we use never was, and you can see it: the template only partly works. Its first token is junk, though the greedy text then recovers to "The capital of India is New Delhi." We didn't run the chat-tuned Qwen model here.

Principle

Generation is a loop around a next-token predictor

The model only ever answers one question: what comes next, given this text? Everything else is the loop around it. The wrapper decides what "next" means, the decoding rule picks one token, and the KV cache keeps the work per step small.

Buys you: one trained model that can answer, translate or chat, depending on the text you put in front of it.

Brown et al. 2020, §2 and §2.4; timings and probabilities from the lab

The failure you will hit: a base model treated like a chat model

Failure · wrong input format
Symptom
You wrap a question in a chat template and the model answers with junk (ratulations!), keeps writing new questions, or never stops.
Cause
The model is a base model, or the template isn't the one it was trained on. It has never learned what follows <|im_start|>assistant.
Isolate
Print the top 4 first tokens under each wrapper, as the lab does. A trained format puts most of the probability on a sensible first token.
Fix
Use the instruction-tuned model with its own tokenizer's chat template (apply_chat_template). With a base model, write the input like text it has seen: a Q/A pattern, or a few worked examples.

The model can't see what you meant, only which text usually comes next.

Where "one token at a time" needs care

  1. It doesn't mean the model thinks only one word ahead. Picking New with 0.698 only makes sense if Delhi is coming next, so what the model computes at one step is already about more than the next word. (How far ahead models plan is still being researched.) Output is still emitted one token per step, though, and each token is fixed once picked.
  2. Several tokens per step is possible. Speculative decoding lets a small model guess a few tokens, and the big model checks them all in one pass. It produces the same distribution of answers as the plain loop, just with fewer slow steps.
  3. Taking the top token is only one choice. Greedy picking gave us this answer; sampling, temperature and top-p are the previous stop, Choosing the next token is a choice.
  4. The cache isn't free. At 12 KB per token it's small for one short chat, but it grows with every token of every conversation a server holds at once.

Understand and remember

  • The model only predicts P(next token | all earlier tokens) → pick one → append it → run the whole model again on the longer text → repeat until the end-of-text token or a length limit → an n-token answer costs n forward passes
  • Each step is a conditional probability → chain rule: P(answer) = product of the step probabilities → one uncertain step (The at 0.277) drags the whole answer to 0.111 → products underflow for long texts → code sums log-probabilities instead (−2.58 here)
  • Causal mask: a token attends only to itself and earlier tokens → its keys and values never change when text is appended → store them (KV cache) → each later step pushes 1 token through the layers instead of all of them → same output, about 4× faster for 32 tokens here, and the gap grows with length → at the price of 12 KB per token in bf16
  • The model continues whatever text it is given → plain question = ambiguous, first token only 0.277 → GPT-3-style A: makes an answer the likely continuation (New 0.797) → a chat template only works on a model trained on it → the base model answers ratulations 0.127
  • detail that matters Later steps process one token but still read all 494 million weights each time → per-step time is set mostly by memory traffic, not by the one token's arithmetic → that's why decode is slow per token (the prefill-vs-decode card)

Reference only

  • <|endoftext|> is token 151643 in Qwen2.5
  • KV cache size: 24 layers × 2 KV heads × 64 × 2 (K and V) × 2 bytes = 12,288 B per token in bf16; 24,576 B in float32
  • Measured timings (M3 CPU, float32, median of 5, busy machine): first pass 167 ms, cached step 38 ms, 32 tokens 1,374 ms with cache vs 5,900 ms without
  • Qwen's chat template: <|im_start|>role, newline, text, <|im_end|>; built by tokenizer.apply_chat_template
  • GPT-3: 175 billion parameters, 2,048-token context, 10 to 100 few-shot examples (§2), Answer: /A: prefix and per-token likelihood for multiple choice (§2.4)

vs Choosing the next token is a choice: The decoding card picks one token from a distribution; this card loops that choice. How does the decoding rule affect the loop's output and its probability, and where does each go wrong?

Check
  • decoding decides which token at each step; the loop feeds that choice back as input
  • greedy gives the highest-probability token per step, not necessarily the most likely whole answer (beam search searches for that)
  • a bad early pick is never revised, because every later step conditions on it
  • decoding fails by being dull or incoherent; the loop fails by not stopping or by growing slow and memory-hungry

vs Prefill vs decode, measured on your Mac: This card measured a 167 ms first pass and 38 ms later steps. What does the prefill-vs-decode card add about why later steps are limited the way they are?

Check
  • prefill processes many tokens per pass, so the weights read from memory are reused across tokens
  • decode processes one token per pass but still reads every weight, so it is limited by memory bandwidth
  • the KV cache is what makes decode one token per pass in the first place

vs Speculative decoding: Speculative decoding produces several tokens per big-model pass. How does that fit with "one token at a time", and when does it fail to help?

Check
  • a small model guesses a few tokens; the big model checks them in one pass and keeps the accepted prefix
  • the result has the same distribution as the plain loop, so it's still one token per position
  • it helps because checking k tokens costs about as much as generating one when decode is memory-bound
  • if the small model's guesses are often rejected, you pay for the extra work and gain little

Why this step?

5 · Predict commit to an answer before revealing

Without a cache, the loop pushed 7 + 8 + … + 38 = 720 token positions through the model for 32 new tokens; with a cache, 7 + 31 = 38. That's 19× fewer, yet the measured time was only about 4× faster. Commit to a reason before revealing. And for 64 new tokens, is the token-position ratio bigger or smaller than 19×?

Reveal

Each forward pass has a large fixed cost: it reads all 494 million weights whatever the number of tokens, so a 38-token pass (200 ms) isn't 38× a 1-token pass (38 ms). The extra tokens are partly 'free' while the weights are being read. For 64 new tokens the counts are 7 + … + 70 = 2,464 versus 70, about 35×, so the gap keeps widening as the text grows and the per-token work starts to dominate.
