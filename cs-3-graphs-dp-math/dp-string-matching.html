DP on two strings

Also called 2-D string DP, or the prefix-by-prefix table behind edit distance and LCS. The cheat-sheet's Recursion page uses it twice, both in C++: Regular Expression Matching (two rolling rows of booleans) and Distinct Subsequences (one row of counts, filled backwards).

In one breath

Ask the question about prefixes: cell (i, j) holds the answer for the first i characters of one string and the first j of the other. Each cell only looks at its neighbours up and to the left, which are already filled, so one pass fills m × n cells and the bottom-right cell is the answer.

In Python

def is_match(s, p):              # regex with . and *, two rows
    n = len(p)
    prev = [True] + [False] * n     # row i-1; starts as row 0
    for j in range(2, n + 1):        # "x*" can match nothing
        prev[j] = p[j - 1] == "*" and prev[j - 2]
    for ch in s:
        cur = [False] * (n + 1)     # cur[0]: s nonempty, p empty
        for j in range(1, n + 1):
            c = p[j - 1]
            if c == "*":
                cur[j] = cur[j - 2] or (   # zero times, or
                    p[j - 2] in (ch, ".") and prev[j])  # one more
            else:
                cur[j] = c in (ch, ".") and prev[j - 1]
        prev = cur
    return prev[n]

def num_distinct(s, t):          # one row, j backwards
    dp = [1] + [0] * len(t)
    for ch in s:
        for j in range(len(t), 0, -1):
            if ch == t[j - 1]:
                dp[j] += dp[j - 1]  # dp[j-1] is still last row's
    return dp[-1]

print(is_match("aab", "c*a*b"), num_distinct("rabbbit", "rabbit"))

The source's C++ is correct: a line-by-line Python port also agrees with re.fullmatch on all 20,000 cases. Its third || term, is_match[1][j + 1], is redundant (after the row copy it equals is_match[0][j + 1], the term before it); our reading, harmless.

Time O(m·n) · Space O(n). Each of the (m + 1)(n + 1) cells is filled once in O(1) from up to three neighbours; since a row needs only the row above, one or two rows of length n + 1 suffice.

Why it beats the alternatives

✗ Plain recursion

Try "x* matches zero" then "x* eats one" at every star. On s = 15 a's, p = "a*a*a*a*a*b" (no match), it makes 35,852 calls; the same subproblems (i, j) come back again and again.

✗ Greedy star

Let each x* eat as much as it can. "a*a" on "aa": a* takes both a's, the final a has nothing left, and greedy says no. The right split (a* takes one) needs the table's "zero or more" choice.

✗ List every subsequence

For distinct subsequences, try every set of positions of s. 7 here, but C(40, 20) = 137,846,528,820 for a 40-char s and a 20-char t.

✓ Prefix table

Every (i, j) pair solved once: (15 + 1)(11 + 1) = 192 cells for the case that took 35,852 calls, and 24 cells for "aab". With rolling rows it needs O(n) memory.

Is it always the right tool?

For "match or count between two sequences" it's the default: edit distance, longest common subsequence, interleaving strings and wildcard matching all fill the same kind of table with a different cell rule. Memoised recursion over (i, j) is the same algorithm top-down and can skip cells that never matter, at the cost of Python's recursion limit (1000 by default). These are standard practice, not from the source.

It's not the right tool when you need the alignment itself and memory is tight: rolling rows throw the path away, so keep the full table or use Hirschberg's divide-and-conquer. And in production just call re.fullmatch; beware that Python's re backtracks and can go exponential on patterns like (a*)*b, which is why engines such as RE2 simulate an automaton instead, in linear time.
