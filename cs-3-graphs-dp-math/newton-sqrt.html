Newton's method for square roots

Also called the Babylonian method or Heron's method; the integer form is the integer square root, isqrt. The source guide solves LeetCode's Sqrt(x) with it in C++: start at 8000, stop once |y² − x| ≤ 1, truncate.

Prime · 2 minutes before you read

The problem: Integer square root without math.sqrt: binary search gains one bit per step (31 steps for a 31-bit x), and the source's float Newton with a tolerance of 1 returns a wrong answer on 3 of the 2³¹ inputs. You want quadratic convergence and an answer that is exact for every int.

Where it fits: Second maths card. Like the bit-arithmetic card it cuts the step count, but faster: each Newton step roughly doubles the correct digits. Its integer stopping rule replaces the fragile float tolerance.

In one breath

Guess y. If y is too big, x / y is too small, so their average is a better guess. Repeat. Once the guess is close, each step roughly doubles the number of correct digits, so even a 31-bit input needs only a handful of steps.

Where the source's version breaks

I ran the source's loop, in IEEE doubles as C++ uses them, on every input 0 … 2³¹ − 1: 2,147,483,648 values, at most 13 steps each. Three come back one too high, all right next to the 8000 start:

Each time y lands exactly on an integer k with k² = x + 1, so |y² − x| = 1 is not > ε and the loop exits at k, one above ⌊√x⌋. Everywhere else Newton stays just above √x and truncation happens to round the right way.

The source's float loop with ε = 1 is off by one on these 3 inputs; corrected here with integer-only Newton, which stops on z ≥ y instead of a tolerance.

In Python

def my_sqrt(x):
    """floor(sqrt(x)) with integers only: Newton on y*y = x."""
    if x < 2:
        return x
    y = 1 << ((x.bit_length() + 1) // 2)  # a power of 2 >= sqrt(x)
    while True:
        z = (y + x // y) // 2          # Newton step, rounded down
        if z >= y:                     # stopped shrinking: done
            return y
        y = z

def source_sqrt(x, y=8000.0, eps=1.0):
    """The source guide's C++ (double SQRT0 = 8000, EPSILON = 1)."""
    while abs(y * y - x) > eps:
        y = (y + x / y) / 2
    return int(y)                      # truncates, like static_cast

print(my_sqrt(2_147_395_599), source_sqrt(2_147_395_599))
print(my_sqrt(63_999_999), source_sqrt(63_999_999))
# → 46339 46339
# → 7999 8000

Time O(log log x) steps once within 2× of √x · Space O(1). The start 2^⌈bits / 2⌉ is within 2× of √x, and then each step doubles the correct bits, so a 31-bit input needs at most 6 loop passes in our checks (all x < 10⁵, every k² − 1 and k² below 2³¹, and every 9,973rd x). For big ints each step is a long division, so the cost is dominated by division, not the step count.

Why it beats the alternatives

✗ Binary search on y

Correct and simple: keep the largest y with y² ≤ x. But it gains 1 bit a step: 31 steps for x = 2,147,395,599, versus 5 for integer Newton.

✗ int(math.sqrt(x))

Fine for 32-bit x, and fast. Above 2⁵³ the float can't hold x: int(math.sqrt(94906266**2 - 1)) gives 94906266, one too high. The problem also forbids exponent helpers.

✗ Float Newton, stop at ε = 1

The source's version. Right on 2,147,483,645 of 2³¹ inputs, wrong on 3, and the answer depends on how the last float happens to round.

✓ Integer Newton

Quadratic convergence with no fractions: floor division, stop when the guess stops falling. Exact for every int, any size; matches math.isqrt on all checks.

Is Newton always the tool?

In real Python code, no: call math.isqrt(x) (exact floor square root of any non-negative int, since 3.8), or math.sqrt for floats. Write Newton yourself when an interview forbids built-ins, or when you need a root the library lacks (a cube root of a big int, say, with y ← (2y + x // y²) // 3).

For square roots Newton converges from any positive start. For other functions it needs a start near the root and a derivative that isn't close to zero, or it can overshoot or cycle; binary search is slower but can't diverge, so it's the safer choice when you only know a bracket.

Understand and remember

  • y and x/y bracket √x → their average is closer → the new error is e²/(2y) → error squared each step → digits roughly double: 5 → 11 → 24 → 48 for √2
  • Far from the root x/y is negligible → y just halves, gaining 1 bit per step → a start 2⌈bits/2⌉ (within 2× of √x) skips that slow phase → at most 6 passes for 31-bit input
  • Integer Newton from above: floor divisions keep y ≥ ⌊√x⌋ → it decreases until the next guess z stops falling → stop at z ≥ y → exact for every int, never a fraction to truncate
  • Float Newton with |y² − x| ≤ 1 → can land exactly on an integer k with k² = x + 1 → exits at k, one above ⌊√x⌋ → 3 wrong inputs out of 2³¹
  • detail that matters For big ints each step is a long division → the cost is dominated by division, not the number of steps

5 · Predict commit to an answer before revealing

Predict the integer Newton trace for x = 99 from the start 2⌈7/2⌉ = 16, and the final answer.

Reveal

16 → 11 → 10 → 9, then z = (9 + 99 // 9) // 2 = (9 + 11) // 2 = 10 ≥ 9, so it stops at 9. That's right: 9² = 81 ≤ 99 < 100 = 10². Every guess stays at or above ⌊√99⌋, which is why the first guess that fails to fall is the answer.

GCD and number theoryAlso called Euclid's algorithm, the Euclidean algorithm, or gcd/lcm tricks. The source guide's Mathematics page uses it three times: Reaching Points (a gcd run backwards), Max Points on a Line…In one breathAnything that divides both a and b also divides a − b, and so a − q·b for any q. So you can replace the bigger number by its remainder without changing the common divisors, and repeat until the remainder is 0. The same "subtract many times at once with %" move turns problems that look like long walks into a handful of steps.
