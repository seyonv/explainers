GCD and number theory

Also called Euclid's algorithm, the Euclidean algorithm, or gcd/lcm tricks. The source guide's Mathematics page uses it three times: Reaching Points (a gcd run backwards), Max Points on a Line (gcd-reduced slopes) and Nth Magical Number (lcm plus inclusion–exclusion).

Prime · 2 minutes before you read

The problem: Walking (1, 1) back to (10⁹, 3) one subtraction at a time takes 333,333,335 steps; float slopes for Max Points divide by zero and collide at 0.9999999894638303; counting magical numbers one by one takes 2 × 10¹³ checks. One idea, replacing many subtractions by a remainder, fixes all three.

Where it fits: Third maths card. It is the purest case of the overview's "take a remainder instead of subtracting", and it sets up modular inverses (extended Euclid) for the next card.

In one breath

Anything that divides both a and b also divides a − b, and so a − q·b for any q. So you can replace the bigger number by its remainder without changing the common divisors, and repeat until the remainder is 0. The same "subtract many times at once with %" move turns problems that look like long walks into a handful of steps.

Three problems from the source, traced

Reaching Points · (x, y) may become (x, x + y) or (x + y, y). Can (1, 1) reach (3, 5)?

Forwards, every point has two children. Backwards there is only one parent: coordinates stay positive, so the bigger one must be the sum. Replacing "subtract the smaller" by "mod the smaller" is exactly Euclid.

Point (tx, ty)Bigger one was the sumBackward step
(3, 5)5 > 35 % 3 = 2 → (3, 2)
(3, 2)3 > 23 % 2 = 1 → (1, 2)
(1, 2)tx = sx = 1, loop stopssy ≤ ty and (2 − 1) % 1 = 0 → True

The last check covers the leftover (1, 1) → (1, 2) moves, which all add sx = 1 to y. For (1, 1) → (10⁹, 3) the loop runs once (10⁹ % 3 = 1) where one-at-a-time subtraction takes 333,333,335 steps. Both moves keep the gcd, so from (1, 1) you reach exactly the coprime pairs: (2, 2) is False (inferred from the algorithm; the source doesn't say it).

Every anchor gets its own counter; only later points are compared, so each pair is looked at once. Duplicates of the anchor are added to every line.

Nth Magical Number · the 4th number divisible by 2 or 3

x1234567
count(x) = x//2 + x//3 − x//60123344

count(x) never decreases, so binary search for the smallest x with count(x) ≥ 4: 6 (3 halvings on 1..8). For n = 10⁹, a = 40,000, b = 39,999 it takes 45 halvings, where counting up would test 2 × 10¹³ integers. Answer mod 10⁹ + 7: 999,860,007.

In Python

import math

def gcd(a, b):
    while b:                     # gcd(a, b) = gcd(b, a mod b)
        a, b = b, a % b
    return a

def reaching_points(sx, sy, tx, ty):
    while sx < tx and sy < ty:     # walk back: bigger one was the sum
        if tx > ty: tx %= ty
        else: ty %= tx
    if sx == tx: return sy <= ty and (ty - sy) % sx == 0
    if sy == ty: return sx <= tx and (tx - sx) % sy == 0
    return False

def direction(dx, dy):           # exact key for Max Points
    g = math.gcd(dx, dy)          # always >= 0 in Python
    dx, dy = dx // g, dy // g
    if dx < 0 or (dx == 0 and dy < 0):
        dx, dy = -dx, -dy
    return dx, dy

def nth_magical(n, a, b):
    lcm = a * b // math.gcd(a, b)
    count = lambda x: x // a + x // b - x // lcm
    lo, hi = 1, n * min(a, b)
    while lo < hi:                # smallest x with count(x) >= n
        mid = (lo + hi) // 2
        if count(mid) >= n: hi = mid
        else: lo = mid + 1
    return lo % (10**9 + 7)

print(gcd(1071, 462), reaching_points(1, 1, 3, 5),
      direction(-2, 2), nth_magical(4, 2, 3))
# → 21 True (1, -1) 6

The source's three solutions all pass a brute-force check (code/ file). Its Nth Magical Number skips the binary search: it counts whole lcm blocks (lcm/a + lcm/b − 1 = 4 magical numbers per block of 6 here), then estimates inside the last block with floats. It matched the binary search on 100,000 random inputs; the integer-only version above is easier to trust.

Euclid and Reaching Points: time O(log min) · space O(1). Every two steps at least halve the smaller number; the worst case is neighbouring Fibonacci numbers (gcd(89, 55) takes 9 steps). Max Points: time O(n²) · space O(n), one counter per anchor. Nth Magical: O(log(n · min(a, b))), one halving per loop.

Why it beats the alternatives

✗ Walk back one subtraction at a time

Correct, since each point has one parent, but (1, 1) → (10⁹, 3) takes 333,333,335 steps. Searching forwards is worse: two children per point.

✗ Float slope dy / dx as the key

Divides by zero on vertical lines, and different lines collide: 94911150/94911151 and 94911151/94911152 are both 0.9999999894638303 in float64.

✗ Count magical numbers one by one

O(answer): 2 × 10¹³ checks for n = 10⁹, a = 40,000, b = 39,999.

✓ gcd, mod and lcm

Exact integers throughout. 1 loop round for (10⁹, 3), a gcd-reduced key per direction, 45 halvings for the huge magical query.

Is it always the tool?

In Python, call math.gcd and math.lcm (3.9+) rather than your own loop; they're in C and take any number of arguments. Write Euclid yourself only to explain it, or to get the quotients (extended Euclid gives x, y with ax + by = gcd, which is how modular inverses are found when the modulus isn't prime).

The backward trick in Reaching Points needs every state to have one parent; with moves like (x, y − x) as well, it's a general graph and you need BFS. Reduced-direction keys need integer coordinates; for floating-point points, compare with a cross product and a tolerance. Inclusion–exclusion with k divisors has 2ᵏ − 1 terms, fine for 2 or 3 but not 20.

Self Crossing, Perfect Rectangle, Largest Palindrome Product and Number of Digit One are empty headings in the source.

Understand and remember

  • A common divisor of a and b divides a − q·b for any q → replace a by a mod b without changing the common divisors → repeat until 0 → at least halves the smaller number every two steps → O(log min(a, b))
  • Reaching Points: coordinates stay positive → the bigger one must have been the sum → exactly one parent → walk backwards, and many identical subtractions collapse into one % → 1 loop round instead of 333,333,335
  • Integer directions divided by their gcd with a fixed sign → exact, hashable keys → no division by zero on vertical lines, no float collisions
  • Multiples of a or b below x: x//a + x//b − x//lcm (inclusion–exclusion) → count(x) never decreases → binary search the smallest x with count ≥ n → 45 halvings instead of 2 × 10¹³ checks
  • detail that matters Consecutive Fibonacci numbers are Euclid's worst case (Lamé) → gcd(89, 55) takes 9 steps → the log bound is tight

Check
  • forwards each point has two children, so the tree doubles per level
  • backwards each point has one parent, so it's a single path, compressed by %
  • adding moves like (x, y − x) gives several parents: a general graph, so BFS

5 · Predict commit to an answer before revealing

Predict how many remainder steps Euclid takes for gcd(240, 46) and what the gcd is, before computing.

Reveal

5 steps, gcd 2: 240 = 5·46 + 10, 46 = 4·10 + 6, 10 = 1·6 + 4, 6 = 1·4 + 2, 4 = 2·2 + 0. Both numbers are even and 240 / 2 = 120 and 46 / 2 = 23 share no factor, so 2 is right.
