Arithmetic with bits

Also called shift-and-subtract division, or binary long division. The source guide's Mathematics page opens with Divide Two Integers: divide without *, / or %, truncate toward zero, and clamp to the 32-bit range [−2³¹, 2³¹ − 1].

Prime · 2 minutes before you read

The problem: Divide without *, / or %: subtracting the divisor until you can't is correct but needs 2,147,483,648 steps for −2³¹ / −1, and that same input overflows a 32-bit int. You need division in about log² n steps and a careful sign and range story.

Where it fits: First maths card. It opens the "fewer steps" family from the overview: instead of caching states, skip ahead by powers of two. The same doubling idea returns in square-and-multiply on the modular-arithmetic card.

Builds on: Fenwick tree (binary indexed tree)

You'll meet: shift-and-subtract (binary long division) << and >> two's complement the lopsided 32-bit range x & −x

By the end: Divide by doubling the divisor, explain why the quotient's bits are the chunks taken, and handle truncation, sign and the −2³¹ / −1 overflow.

  4. Why take absolute values first, and why is that itself dangerous in a 32-bit language?
  5. How does x & −x isolate the lowest set bit?

In one breath

Keep doubling the divisor with << 1 until one more doubling would overshoot what's left of the dividend, subtract that chunk, and add the matching power of two to the quotient. Repeat with the remainder. It's school long division, done in base 2, where each "digit" is just 0 or 1.

The idea: write the dividend as divisor-sized powers of two

a= ∑k∈Sb⋅2kchunks subtracted + rleft over, r < b ⇒ q=∑k∈S2kquotient: one bit per chunk
a, b|dividend|, |divisor|; the sign is fixed at the end43, 8 b⋅2kb << k: a shift, not a multiply32 = 8 << 2 Swhich powers were used = the set bits of q{2, 0} rwhat's left when even b itself doesn't fit3
43 = 8·2² + 8·2⁰ + 3 = 32 + 8 + 3 q = 2² + 2⁰ = 4 + 1 = 5 = 101₂

In binary: 101011₂ ÷ 1000₂ = 101₂ remainder 11₂. The quotient's bits are exactly the chunks the loop took.

−2³¹ / −1 = 2,147,483,648 = 2³¹ but INT_MAX = 2³¹ − 1 = 2,147,483,647 a 32-bit register wraps 2³¹ to −2,147,483,648 the problem says: clamp → 2,147,483,647

The 32-bit range is lopsided: one more negative number than positive, so −2³¹ has no positive twin and it's the only quotient that can overflow (dividing by anything else shrinks |a|). Python ints never overflow, so the clamp is applied by hand; the wrap value comes from ctypes.c_int32.

In Python

INT_MIN = -1 << 31              # -2,147,483,648
INT_MAX = -INT_MIN - 1          #  2,147,483,647

def divide(dividend, divisor):
    negative = (dividend < 0) != (divisor < 0)
    a, b = abs(dividend), abs(divisor)
    q = 0
    while a >= b:
        d, m = b, 1             # d = b * m, m a power of two
        while d << 1 <= a:      # double until the next would overshoot
            d <<= 1
            m <<= 1
        a -= d                  # take the biggest chunk out
        q += m                  # ...and record how many b's it held
    q = -q if negative else q
    return max(INT_MIN, min(q, INT_MAX))   # the 32-bit clamp

# divide(43, 8)            → 5
# divide(-7, 2)            → -3     (truncates; -7 // 2 is -4)
# divide(-2147483648, -1)  → 2147483647   (clamped from 2^31)
# 100,000 random 32-bit pairs vs truncating //: 0 wrong

The source negates with quotient *= -1, a multiplication the problem forbids, and clamps with statistics.median([int_min, q, int_max]); corrected here to unary minus and min/max. Its logic is otherwise right.

Time O(log² n) · Space O(1), n = |a / b|. Each round restarts doubling from b and takes one set bit of q, so up to 31 rounds of up to 31 shifts: 2³¹ − 1 / 1 costs 31 + 30 + … + 1 = 496 shift-compares, against 2,147,483,647 subtractions. Keeping the chunk list and walking it back down once makes it O(log n).

Why it beats the alternatives

✗ Subtract b until you can't

Correct and allowed, but O(a / b). −2³¹ / −1 needs 2,147,483,648 subtractions; 10⁹ / 7 needs 142,857,142 (vs 174 shift-compares).

✗ int(a / b)

Uses the banned operator, and goes through a float: int((2⁵³ + 1) / 1) is 9,007,199,254,740,992, off by one. Fine for 32-bit inputs, wrong past 2⁵³.

✗ a // b or >>

Also banned, and both floor toward −∞: -7 // 2 = −4, but truncation wants −3. Taking abs first and fixing the sign last avoids the mismatch.

✓ Shift and subtract

Only <<, -, + and compares. At most 496 steps on 32-bit input, exact, and the sign and clamp are handled once at the end.

Would you ever write this for real?

Rarely. It's an interview puzzle: every CPU has a divide instruction, and in Python // on big ints is already exact. The pieces are what carry over: x & -x drives Fenwick trees, shifts turn power-of-two division and multiplication into one cheap step, and building an answer one power of two at a time is also how square-and-multiply computes pow(a, n, m) (our comparison, not the source's).

If you port it to a 32-bit language, don't take abs first: abs(−2³¹) itself overflows back to −2³¹. Either widen to 64 bits or run the whole loop on negative numbers, where the range is one larger. That's standard practice for this problem, not something the source discusses.

5 · Predict commit to an answer before revealing

Predict how many rounds and shift-compares divide(2**30, 1) takes, compared with divide(2**31 − 1, 1)'s 496.

Reveal

One round and 31 shift-compares: the doubling climbs 1, 2, 4, … to 2³⁰ (30 that fit, one that overshoots), subtracts everything and stops. The number of rounds equals the number of set bits in the quotient: 2³⁰ has one, 2³¹ − 1 has 31.
