Eulerian paths

Also called an Euler trail, or an Euler circuit when it ends where it started; found with Hierholzer's algorithm. A walk that uses every edge exactly once. The source guide files it under Stacks, as Reconstruct Itinerary: use every airline ticket once, starting from JFK.

Prime · 2 minutes before you read

The problem: "Use every ticket exactly once" sounds like a search over orderings, and greedy walking can strand tickets at a dead end. Backtracking fixes that but can take exponential time. There is a linear answer, and a degree test that tells you in advance whether any answer exists.

Where it fits: Eighth and last graph-basics card. It reuses DFS's explicit stack from the flood-fill card, but writes nodes down when they get stuck (post-order) instead of when they are reached.

Builds on: Depth-first search and flood fill · Monotonic stack

  2. When the walk gets stuck, why must the stuck node be the end of the finished path?

  4. Why is "every edge once" linear while "every node once" is NP-complete?

In one breath

An Eulerian path exists when every node's in-edges and out-edges balance, except that the start may have one extra out and the end one extra in. To find it, walk along unused edges until you're stuck, write down where you're stuck, back up one step and keep walking. The list you wrote, reversed, is the path.

Worked example: 5 tickets → JFK, ATL, JFK, SFO, ATL, SFO

Tickets [JFK→SFO], [JFK→ATL], [SFO→ATL], [ATL→JFK], [ATL→SFO]. Green numbers = the order the answer uses them. Where there's a choice, the problem wants the alphabetically smallest itinerary, so JFK flies to ATL before SFO.

Plus every edge must sit in one connected piece. Undirected version: 0 or 2 nodes of odd degree. Königsberg's four land masses had 5, 3, 3 and 3 bridges, all odd, so no walk crosses each bridge once (Euler, 1736).

In Python

from collections import defaultdict

def find_itinerary(tickets):
    adj = defaultdict(list)
    for a, b in sorted(tickets, reverse=True):
        adj[a].append(b)             # smallest destination at the end
    stack, route = ["JFK"], []
    while stack:
        top = stack[-1]
        if adj[top]:                 # unused ticket out of top: take it
            stack.append(adj[top].pop())
        else:                        # stuck: top is final from here on
            route.append(stack.pop())
    return route[::-1]               # finished last-to-first

t = [["JFK", "SFO"], ["JFK", "ATL"], ["SFO", "ATL"],
     ["ATL", "JFK"], ["ATL", "SFO"]]
print(find_itinerary(t))
# → ['JFK', 'ATL', 'JFK', 'SFO', 'ATL', 'SFO']
print(find_itinerary([["JFK", "KUL"], ["JFK", "NRT"], ["NRT", "JFK"]]))
# → ['JFK', 'NRT', 'JFK', 'KUL']

Same algorithm as the source, which is correct; its inner while is split into one step per loop here so each line of the trace is one iteration. The code file checks both against brute-force backtracking on 2,000 random ticket sets.

Time O(E log E) · Space O(E) for E tickets. The sort dominates; the walk itself is O(E), because each ticket is popped from adj once and each stack entry is pushed and popped once (E + 1 entries).

Why it beats the alternatives

✗ Greedy, smallest first

Always take the alphabetically smallest ticket and never back up. On the dead-end case it flies JFK→KUL and strands 2 of 3 tickets.

✗ Backtracking DFS

Try tickets in sorted order, undo on a dead end. Correct, and the first full route is the smallest, but repeated undoing can take exponential time in the worst case.

✗ Fleury's algorithm

Never cross a bridge (an edge whose removal disconnects the rest) unless forced. Correct, but the bridge test is O(E) per step, so O(E²): 10⁸ steps for E = 10⁴.

✓ Hierholzer with a stack

Walk until stuck, record in post-order, reverse. Dead ends are written last instead of undone. O(E) after sorting, and never backs out a ticket.

Is this always the tool?

Only when the job is "use every edge once". LeetCode promises a valid itinerary exists; in general, run the degree check first (and check that all edges connect), or the walk silently returns a route that misses tickets. Start at the +1 node when there is one. For undirected graphs, each edge sits in two adjacency lists, so give edges ids and mark them used from both ends.

It's the wrong tool when the question is really about nodes (visit every city once: Hamiltonian, so DP over subsets for small n) or about cost (cheapest route that covers every street: the Chinese postman problem, which adds duplicate edges until the degrees balance, then runs Euler). A recursive version is shorter, but Python's default recursion limit of 1,000 breaks it on long paths; the explicit stack doesn't care. The splice argument above is our reading of why the reversal works, not the source's.

Understand and remember

  • Every visit to a middle node uses one edge in and one out → balanced degrees everywhere except start (+1 out) and end (+1 in) → the degree test decides existence in O(V + E), plus one connected piece
  • Walk unused edges until stuck → with balanced degrees the only place you can get stuck first is the end node (or the start, for a circuit) → write it down as last → back up and keep walking → detours found later splice in before it
  • Hierholzer never undoes an edge → each ticket popped once, each stack entry pushed and popped once → O(E) after the O(E log E) sort for lexical order, vs exponential worst case for backtracking
  • detail that matters Sorting destinations in reverse and popping from the end of each list → the smallest destination is always taken first in O(1) → lexical order at no extra per-step cost

Reference only

  • Königsberg's degrees 5, 3, 3, 3
  • Fleury's algorithm and its O(E²) bridge test
  • de Bruijn sequences (Cracking the Safe)
  • the Chinese postman problem

vs Depth-first search and flood fill: Both use an explicit stack and pop when stuck. What does each write down, and when?

Check
  • flood fill marks a cell when it is pushed (pre-order)
  • Hierholzer writes a node when it has no unused edge left (post-order)
  • post-order + reverse is what orders the path correctly, like finishing order in topological sort
