Permutations and combinations

Also called the factorial number system (factoradic) or Lehmer code for the first half, and the binomial coefficient, n-choose-k or C(n, k) for the second. The source guide's Combinatorics section has Permutation Sequence (the k-th permutation of 1…n) and the n-choose-k formula with math.comb.

Prime · 2 minutes before you read

The problem: The k-th permutation of 1…9 by listing costs up to 362,880 permutations, and by "next permutation" up to 362,879 steps. For combinations, 52!/(5!·47!) passes through a 68-digit 52! even though the answer, 2,598,960, fits in 22 bits, which overflows fixed-width integers from n = 21.

Where it fits: Last maths card. It counts in blocks like the Fibonacci bit walk (skip whole groups without building them) and gives the exact, small-intermediate C(n, k) that the modular card's tables replace when a modulus is involved.

In one breath

The permutations of 1…n in sorted order come in n equal blocks of (n − 1)! each, one block per leading digit. So you never list them: divide k − 1 by (n − 1)! to learn which unused digit comes first, keep the remainder, and repeat with (n − 2)!. Choosing is ordering with the orders thrown away: C(n, k) = n! / (k! (n − k)!), best computed one factor at a time so the numbers stay small.

In Python

import math

def kth_permutation(n, k):
    k -= 1                          # 0-based rank
    pool = list(range(1, n + 1))    # unused digits, sorted
    out = []
    for m in range(n - 1, -1, -1):  # block sizes (n-1)!, ..., 0!
        d, k = divmod(k, math.factorial(m))
        out.append(str(pool.pop(d)))  # d-th smallest unused
    return "".join(out)

def comb(n, k):
    if not 0 <= k <= n:
        return 0
    k = min(k, n - k)               # C(n, k) = C(n, n - k)
    r = 1
    for i in range(1, k + 1):
        r = r * (n - k + i) // i    # r is C(n-k+i, i): exact
    return r

print(kth_permutation(4, 9), comb(52, 5), math.comb(52, 5))
# → 2314 2598960 2598960

The source imports the third-party sortedcontainers.SortedList for the pool; a plain list does the same job here (n ≤ 9 in the original problem). Its LaTeX for the binomial is also malformed; typeset correctly above.

Time O(n²) · Space O(n) for the k-th permutation: n divmods, but each pop(d) shifts up to n items. Time O(min(k, n − k)) multiplications for comb. The full file checks all 873 permutations for n ≤ 6 against itertools, and comb against math.comb for every n < 80.

Why multiply one factor at a time

After step i the running value is itself a binomial, C(n − k + i, i), so the division by i is always exact and nothing grows past the answer times n. Python ints never overflow, but in Java or C++ the width is the whole story:

comb(52, 5): 48 → 1,176 → 19,600 → 249,900 → 2,598,960 largest intermediate 249,900 × 52 = 12,994,800 52! / (5! 47!): 52! has 68 digits; a 64-bit long holds 20! but not 21! central C(n, n/2) in a signed 64-bit long, multiplicative: intermediate overflows first at n = 62, result at n = 67

All printed by code/factorial-number-system.py. So the factorial formula fails for any n ≥ 21 in 64 bits, while the multiplicative loop works almost until the answer itself stops fitting.

Why it beats the alternatives

✗ List them all, take the k-th

itertools.permutations is already in order, but you generate up to n! strings. For n = 9 that's 362,880 permutations to read one.

✗ Next permutation, k − 1 times

O(n) per step with no big list, but still k − 1 steps: up to 362,879 for n = 9. Fine for small k, hopeless if k is near n!.

✗ Backtrack and count leaves

Depth-first over digit choices, stop at the k-th leaf. It visits every leaf before the answer, so it's the "list them all" cost with more code.

✓ Factorial digits

One divmod per position: 4 steps for n = 4, 9 for n = 9, however big k is. Whole blocks of (n − 1)!, (n − 2)!, … are skipped without being built.

Is it always the tool?

No. If you need every permutation or subset, just iterate itertools.permutations or itertools.combinations: the output is n! or C(n, k) long anyway. For large n (say ranking a permutation of 10⁵ items) the list pop makes it O(n²); swap the pool for a Fenwick tree that finds the d-th unused digit in O(log n), for O(n log n) total. That's standard practice, not from the source.

For combinations, math.comb is exact and should be your default in Python. When the answer is wanted mod a prime p (the usual 10⁹ + 7), precompute factorials and inverse factorials instead; when the modulus isn't prime, or you need many small C(n, k), fill Pascal's triangle, which only adds and never exceeds the answer.

Understand and remember

  • Sorted permutations group by first digit into n blocks of (n − 1)! → divmod(k − 1, (n − 1)!) picks the block and the rank inside it → repeat with (n − 2)! on the remaining digits → n steps instead of up to n! − 1
  • The quotients are the factorial digits of k − 1 (digit i runs 0…i) → each indexes the still-unused digits → rank 9 of n = 4 is 8 = 1·3! + 1·2! → "2314"
  • After step i the running value is C(n − k + i, i) → the next division by i is exact → intermediates stay near the answer × n (12,994,800 for C(52, 5)) instead of passing through n!
  • Choosing = ordering with the k! orders thrown away → C(n, k) = n!/(k!(n − k)!) = product of (n − k + i)/i
  • detail that matters pool.pop(d) shifts up to n items → O(n²) for the k-th permutation → a Fenwick tree finds the d-th unused digit in O(log n) for large n

vs Fibonacci counting: Both cards count past whole groups without listing them. What is the block size in each, and what is the digit that selects the block?

Check
  • permutations: blocks of (n − 1)!, selected by the factorial digit

Check
  • DFS must visit every leaf before the k-th
  • the factorial method knows each subtree's size in advance ((n − i)!)
  • knowing subtree sizes lets you skip whole subtrees: a counting descent
