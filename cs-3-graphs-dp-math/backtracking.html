Backtracking

Also called depth-first search over choices, or "choose, explore, un-choose". The source guide's one worked backtracking problem is Expression Add Operators on its Recursion page, solved with an explicit stack and a running multiplier instead of recursion.

Prime · 2 minutes before you read

The problem: "List every expression that evaluates to the target" can't be cached into a DP: the answers themselves can be exponentially many (19,683 for ten zeros). Generating every string and calling eval re-parses 262,144 strings for 10 digits and still chokes on operands like "05".

Where it fits: Last DP-part card, and the counterpoint to it: here the state includes everything chosen so far, so nothing repeats and caching is useless. It reuses the explicit stack from the flood-fill and Euler cards.

In one breath

Build the answer one decision at a time, walk depth-first down each choice, and step back to the last decision as soon as a branch is finished or can't work. Here the decisions are which operator (or none) goes between two digits, and each partial expression carries just enough state to be evaluated in O(1) per step.

Worked example: num = "123", target = 6 → ['1*2*3', '1+2+3']

All 21 states the search visits: 3 first operands, then + − × and a next operand, until every digit is used. 16 complete expressions, 2 hits. The small labels are the state each node carries: its value so far and its last operand.

The multiplier trick: undo the last operand

A running total alone can't handle precedence: after 1 + 2 the total is 3, but × 3 must multiply only the 2. So each state also keeps last, the signed term that was added most recently. Multiplying takes that term back out and puts it back in, times the new operand.

v′= v−ℓundo the last term + ℓ×dredo it, times d ℓ′=ℓ×d
vvalue of the expression so far3 for "1+2" ℓlast: the signed term added most recently2 for "1+2", −2 for "1−2" dthe operand being appended3
+ d: v' = v + d last' = d − d: v' = v − d last' = −d × d: v' = v − last + last × d, last' = last × d 1+2 (v 3, last 2) × 3: 3 − 2 + 2 × 3 = 7 (1 + 6) 1−2 (v −1, last −2) × 3: −1 − (−2) + (−2) × 3 = −5 (1 − 6) 1×2 (v 2, last 2) × 3: 2 − 2 + 2 × 3 = 6 (a hit)

Chains work too: last is already the whole product, so 1+2×3×4 gives 7 − 6 + 6 × 4 = 25. The source writes the same update as eval + multiplier × (d − 1), which is equal.

The four moving parts, two examples each

Like trying keys on a ring: pick one, try the lock, and if it fails put it back and pick the next. Nothing about a wrong key is kept.

In Python

def add_operators(num, target):
    n = len(num)
    stack = []                      # (i, expr, value, last)
    for j in range(1, n + 1):       # first operand is num[:j]
        if j > 1 and num[0] == "0":
            break                   # no leading zeros: "05"
        d = int(num[:j])
        stack.append((j, num[:j], d, d))
    found = []
    while stack:
        i, expr, value, last = stack.pop()
        if i == n:                  # leaf: every digit used
            if value == target:
                found.append(expr)
            continue
        for j in range(i + 1, n + 1):
            if j > i + 1 and num[i] == "0":
                break               # prune "05", "007", ...
            s = num[i:j]
            d = int(s)
            stack.append((j, expr + "+" + s, value + d, d))
            stack.append((j, expr + "-" + s, value - d, -d))
            stack.append((j, expr + "*" + s,  # undo last, redo x d
                          value - last + last * d, last * d))
    return found

print(add_operators("123", 6))   # → ['1*2*3', '1+2+3']
print(add_operators("105", 5))   # → ['10-5', '1*0+5']
print(add_operators("00", 0))    # → ['0*0', '0-0', '0+0']

The source's version names its loop variable operator, the same name as the global '+-*' it zips over. That makes operator local to the whole function, so any input longer than one digit raises UnboundLocalError under Python 3.10; corrected here with separate names. With the rename, the source returns the same lists as this code.

Each state is an immutable tuple, so there is nothing to un-choose: popping the next tuple is the step back. code/backtracking.py also has the recursive form with an explicit path.append / path.pop(); both agree with a brute force on 500 random inputs.

How big the search is

leaves = 4^(n−1) (+, −, × or nothing at each of n − 1 gaps) states = 1 + 4 + … + 4^(n−1) = (4^n − 1) / 3 n = 3, "123": 4^2 = 16 leaves, (64 − 1) / 3 = 21 states n = 10, "3456237490": 4^9 = 262,144 leaves, (4^10 − 1) / 3 = 349,525 states

Counts from code/backtracking.py, which counts the states it pops. Leading zeros only ever shrink this ("105": 13 leaves, not 16).

Time O(n · 4n) · Space O(n2). There are up to 4n−1 leaves and each builds an O(n) string. Because the stack pops the newest state first, it never holds more than 3(n − 1) states (27 for n = 10), each carrying an O(n) string; the output list is extra.

Why it beats the alternatives

✗ Generate every string, eval() it

Correct in outline, but it re-parses all 262,144 strings for n = 10, and eval("1*05") is a SyntaxError, so you still have to filter operands by hand.

✗ Keep only a running total

Evaluates left to right and ignores precedence: 1 + 2, then × 3, becomes (1 + 2) × 3 = 9 instead of 7. The missing piece is last.

✗ Memoize it like DP

The question asks for every expression, and there can be exponentially many: "0000000000" with target 0 has 39 = 19,683 answers. A cache can't make listing them cheaper.

✓ Backtracking with (value, last)

O(1) arithmetic per step, no parsing, bad operands cut before they grow. "123" is done in 21 states with both answers found.

Is backtracking always the tool?

It fits when you must list every solution, or when constraints cut most branches early: permutations and subsets, N-queens, sudoku, word search. Its cost is the number of states visited, so the pruning rule is where the speed comes from.

It's the wrong tool when you only need a count or a best answer and the same sub-question keeps coming back. Target Sum (only + and −) asks how many sign choices hit the target; a DP over reachable sums answers that in O(n · range of sums) instead of 2n branches. That's the move on the recursion-to-DP card. Understand and remember

  • Build the answer one decision at a time → go deep on each choice → step back when a branch is complete or dead → cost = number of states visited → pruning is where the speed comes from
  • Multiplication binds tighter than + and − → keep last = the most recent signed term → × d replaces it: v′ = v − last + last·d, last′ = last·d → O(1) evaluation per step, no parsing
  • Four choices per gap (+, −, ×, join) → 4n−1 leaves and (4n − 1)/3 states → 349,525 for n = 10 → exponential, but so is the output in the worst case
  • The state includes the expression so far → no two branches share a subproblem → a cache can't help; if only a count is needed (Target Sum), the state shrinks to (i, sum) → DP
  • detail that matters The stack pops the newest state first → it never holds more than 3(n − 1) states (27 for n = 10) → each carries an O(n) string, so memory is O(n²) even though the tree has 349,525 states
