State-machine DP

Also called buy/sell state DP, or the "hold / sold" states trick. The source guide uses it for Best Time to Buy and Sell Stock with at most two transactions (C++, four numbers) and at most k transactions (Python, a k-row table).

Prime · 2 minutes before you read

The problem: "At most two trades" looks like a search over every buy/sell pair: O(n⁴) for two trades, O(n2k) for k. Even a DP table with an inner loop over buy days is O(k·n²), about 2 × 10¹⁰ steps at n = 10⁵.

Where it fits: Fifth DP card. The state stops being a position and becomes a mode (holding share 1, sold share 1, …). The "rest" option makes it the same max-or-carry shape as every earlier recurrence.

In one breath

Name the few situations you can be in at the end of a day ("holding my first share", "sold my first share", …) and keep one number per situation: the best result that ends there. Each new day, every situation either stays put or is reached by one action from its neighbour, so updating all of them takes one line each and the past can be thrown away.

The machine for at most two trades

Values after the last day of prices = [3, 3, 5, 0, 0, 3, 1, 4]. c = the cheapest effective price paid for the share you hold; p = the best profit once you've sold. The answer is the green state.

Each trade needs its own rising stretch, and 8 prices have at most 7 steps, so at most 4 separate rises: no k ≥ 4 can bind. The source's IV makes the same test (k < n >> 1). Here even k = 3 already reaches 8, since there are only 3 rises.

In Python

import itertools

def max_profit_2(prices):
    c1 = c2 = float("inf")   # cheapest effective cost of buy 1 / 2
    p1 = p2 = 0              # best profit after sell 1 / 2
    for x in prices:
        c1 = min(c1, x)          # buy 1: pay x
        p1 = max(p1, x - c1)     # sell 1: collect x - c1
        c2 = min(c2, x - p1)     # buy 2: pay x, already up p1
        p2 = max(p2, x - c2)     # sell 2
    return p2

def max_profit_k(k, prices):
    if k >= len(prices) // 2:    # k can't bind: take every rise
        return sum(max(b - a, 0)
                   for a, b in itertools.pairwise(prices))
    cost = [float("inf")] * (k + 1)
    profit = [0] * (k + 1)       # profit[0] = 0: no trades yet
    for x in prices:
        for j in range(1, k + 1):
            cost[j] = min(cost[j], x - profit[j - 1])
            profit[j] = max(profit[j], x - cost[j])
    return profit[k]

p = [3, 3, 5, 0, 0, 3, 1, 4]
print(max_profit_2(p))                         # → 6
print([max_profit_k(k, p) for k in range(6)])  # → [0, 4, 6, 8, 8, 8]

The source's code is correct: its Python IV matches a brute force on 2,000 random cases. Its C++ III uses vector without #include <vector>, which only compiles if another header pulls it in.

Time O(nk) · Space O(k). Each day updates 2k numbers once, and nothing older than yesterday is needed. The source's IV loops over j outside and days inside, so it keeps two rows of n profits (O(n) space); putting days outside, as here, needs just the 2k numbers.

Why it beats the alternatives

✗ Try every set of trades

For 8 days: 28 single trades and 126 ordered pairs with sell 1 ≤ buy 2. That's O(n⁴) for k = 2, and O(n2k) in general.

✗ Keep the k biggest rises

On [1, 5, 4, 8, 2, 6] with k = 2 the rises are 4, 4, 4, so greedy says 8. The best is 1→8 then 2→6 = 7 + 4 = 11: merging two rises across a small dip beats keeping both.

✗ Table with a buy-day loop

dp[j][i] = best of dp[j][i−1] and, for every earlier buy day b, dp[j−1][b] + xi − xb. Correct, but O(kn²): about 2·10¹⁰ steps for n = 10⁵, k = 2.

✓ State machine

That inner "best earlier buy" is exactly cj, kept as a running min. O(nk) time: 4 updates × 8 days = 32 here, 4·10⁵ for n = 10⁵, k = 2.

Is it always the tool?

It fits whenever the rules allow only a few "modes" and each day moves you at most one step: cooldowns, fees and alternating choices all add a state or an edge. For unlimited trades it's overkill: the sum of rises is O(n) and needs no states. For exactly k = 2 there's also a two-pass trick (best single trade ending by day i plus best starting after it), also O(n), but it doesn't extend to k.

It's the wrong frame when the state isn't small, e.g. holding up to m shares at once turns 2k states into far more. And it assumes you know every future price: it's a hindsight puzzle, not a trading strategy.

Understand and remember

  • Name the modes you can end a day in → keep the best value per mode → each day every mode either rests (keeps its value) or is reached by one action from its neighbour → 2k updates per day, O(n·k) time, O(k) space
  • cj = min(cj, x − pj−1) is a running minimum of "price paid minus profit already banked" → it is exactly the best earlier buy day for trade j → the O(n) inner loop disappears
  • Each trade needs its own rising stretch → n prices have at most n // 2 separate rises → k ≥ n // 2 can't bind → just sum every rise in O(n)
  • Greedy on individual rises can't see that merging two rises across a small dip is better → [1, 5, 4, 8, 2, 6], k = 2: greedy 8, true 11
  • detail that matters Update order within a day (c1, p1, c2, p2) lets a buy and sell happen the same day → harmless: it adds 0 profit → the values stay correct
