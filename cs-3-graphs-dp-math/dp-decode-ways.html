Decode Ways II

Also called Decode Ways with wildcards (LeetCode 639); a counting DP on a string, cousin of Fibonacci. The source guide solves it twice, in numpy and in C++, with the same three-number state; here it is in plain Python.

Prime · 2 minutes before you read

The problem: Each * is any of nine digits, so ten stars already mean 3,486,784,401 plain strings to decode, and the count itself grows about 10× per star: past 64-bit integers by 20 stars. Plain recursion also recomputes suffixes like naive Fibonacci.

Where it fits: Sixth DP card. It is the Fibonacci recurrence from the recursion-to-DP card with weights per character, kept in three running counts like the state-machine card, and it uses the mod 10⁹ + 7 that the modular-arithmetic card explains.

In one breath

Letters map to 1–26, and a * stands for any digit 1–9. Read the string left to right and keep just a few counts: how many ways decode everything so far, and how many of those end on a 1 or a 2 that could still pair with the next digit. Each new character updates those counts with small weights, so the whole count takes one pass, taken mod 10⁹ + 7.

Filled in for 1*: f(1) = 1 (just "A"), f(2) = 9·f(1) + 9·f(0) = 9 + 9 = 18: the 9 strings 11…19 each split as two letters or read as one.

* never means 0, so after a 1 it is 11–19 (9, not 10) and after a 2 it is 21–26 (6). A lone 0 is a dead end unless a 1 or 2 sits in front of it.

The three running counts, two examples each

In Python

MOD = 10**9 + 7

def weights(c):
    """(alone, after a 1, after a 2) for the char c."""
    if c == "*":
        return 9, 9, 6          # 1-9 / 11-19 / 21-26
    return c != "0", 1, c <= "6"   # 1-9 / 10-19 / 20-26

def num_decodings(s):
    e, one, two = 1, 0, 0       # empty prefix: one way
    for c in s:
        a, b, d = weights(c)
        e, one, two = (
            (e * a + one * b + two * d) % MOD,
            e if c in "1*" else 0,   # c opens "1?"
            e if c in "2*" else 0,   # c opens "2?"
        )
    return e

for s in ["*", "1*", "2*", "**", "11106"]:
    print(f"{s!r:8} -> {num_decodings(s)}")
# '*'      -> 9
# '1*'     -> 18
# '2*'     -> 15
# '**'     -> 96
# '11106'  -> 2

The source's numpy and C++ versions are correct: both match a brute force (expand every *, try every split) on 2,000 random strings. The rewrite only drops numpy, which buys nothing for three numbers.

Time O(n) · Space O(1). One constant-time update per character, and only three numbers are kept, because f(i) looks back at most two characters.

Why the modulo

'*' × 10 → 13,483,456,911 ways (11 digits: past a 32-bit int, 2,147,483,647) '*' × 20 → 206,837,489,828,967,090,336 (21 digits: past a 64-bit int, 9.2 × 10¹⁸) '*' × 10⁵ → a 101,859-digit number; mod 10⁹ + 7 = 81,890,275 largest sum before the % : (9 + 9 + 6) · (M − 1) < 24 · M = 24,000,000,168 < 2⁶³

Each * multiplies the count by about 10.4. Reducing every step keeps each count below M, so the C++ version's long never overflows. In Python, skipping the % still gives the right answer (big ints) but took 3.7 s instead of 0.020 s on '*' × 10⁵ (one run on the author's M3), because the numbers grow to 100,000 digits.

Why it beats the alternatives

✗ Expand every star

Replace each * by 1–9 and solve each plain string. That's 9k strings: 3,486,784,401 for ten stars, before any decoding.

✗ Recurse without a memo

"Take one digit or two" branches like Fibonacci and recomputes the same suffixes. On thirty 1s it makes 3,524,577 calls to count 1,346,269 decodings.

✗ Count with big ints, mod at the end

Correct in Python, but the counts grow about 10× per star, so each addition gets slower: 3.7 s vs 0.020 s on 10⁵ stars (one run). In C++ or Java it silently overflows.

✓ Three counts, mod every step

Weights per character absorb all nine meanings of a * at once. One pass, three numbers, every intermediate below 2.4 × 10¹⁰.

Is this always the tool?

For counting, yes: any "how many ways to split a string into valid pieces" problem with short pieces works the same way, with one pending count per unfinished piece. Decode Ways I (no stars) is this code unchanged, with weights only 0 or 1. The common slips are treating * as 0–9 (then 1* comes out 19, not 18, and 2* 16, not 15) and forgetting that *0 has two readings, 10 and 20.

It's the wrong tool when you need the decodings themselves rather than how many: '*' × 10⁵ has a 101,859-digit count of them, so you'd list a few with backtracking instead. And if valid pieces can be long or come from a dictionary (Word Break), the state is "which positions are reachable", so use a dp array over start positions or a trie.

Understand and remember

  • A letter is 1 or 2 digits long → the last piece is either the last char alone or the last two together → f(i) = A(si)·f(i−1) + P(si−1si)·f(i−2) → Fibonacci-shaped, O(n) time, O(1) space
  • A * stands for 1–9 → count all nine readings at once with weights (alone 9, after 1: 9, after 2: 6) → no expansion into 9k strings
  • Pending counts one/two = ways that end on a 1 or 2 that could still start a two-digit code → the next char multiplies them by its after-1 / after-2 weight → the pair rule is applied without storing the string
  • The count grows about 10.4× per star → reduce mod 10⁹ + 7 every step → every intermediate stays below 24·M < 2⁶³ → no overflow in C++, and in Python 0.020 s instead of 3.7 s on 10⁵ stars
  • detail that matters A 0 has weight 0 alone → it wipes out every decoding that would read it alone → only readings where it closes a 10 or 20 survive ("11106" drops from 3 to 2)

5 · Predict commit to an answer before revealing

Reveal

18. The 0 must close a two-digit code with the * before it (10 or 20: 2 ways), so the 1 stands alone, and the final * stands alone (9 ways): 1 × 2 × 9 = 18. "1*" as a teen would leave the 0 alone, which is invalid.
