From recursion to dynamic programming

Also called memoization (top-down DP) and tabulation (bottom-up DP). The source guide's Recursion page opens straight on hard DP problems (Regular Expression Matching, Dungeon Game, Coin Path…), so this card supplies the step before them, with Fibonacci and the source's own Coin Path.

Prime · 2 minutes before you read

The problem: The natural recursion for fib(30) makes 2,692,537 calls to compute 31 different values, and each extra n multiplies the work by about 1.618. The same blow-up hides inside every hard problem on the source's Recursion page.

Where it fits: First card of the DP part. It turns the "handle each state once" idea from the graph cards into a cache or a table, and it gives the four-question checklist the next seven cards all answer.

Builds on: Divide and conquer and the master theorem · Topological sort and cycle detection

You'll meet: overlapping subproblems memoization (top-down) with @lru_cache tabulation (bottom-up) state = the numbers that pin a subproblem down the recursion limit

By the end: Turn a recursion into a memoized or tabulated DP, count its states, and decide from four questions whether DP applies at all.

Read with these questions (answer them in your head as you go; don't take notes line by line):

  1. Why does naive fib(n) make 2Fn+1 − 1 calls when only n + 1 distinct values exist?
  2. What exactly does a cache hit save: one call, or a whole subtree of calls?
  3. Why does a bottom-up table need a fill order, and what guarantees each cell's inputs are ready?
  4. In Coin Path, why is the state just the index i and not the path taken to reach it?
  5. Why does @lru_cache hit the recursion limit at n = 498 while a plain dict reaches 998?

In one breath

Write the answer as a recursion over smaller versions of the same question. If those smaller questions keep coming back, store each answer the first time you compute it: a cache on the recursion (top-down) or a table filled from the smallest case up (bottom-up). Exponential work becomes one unit of work per distinct subproblem.

Three ways to write it, in Python

from functools import lru_cache

def fib_naive(n):                # the recursion, as written
    return n if n < 2 else fib_naive(n - 1) + fib_naive(n - 2)

@lru_cache(maxsize=None)         # top-down: same code + a cache
def fib_memo(n):
    return n if n < 2 else fib_memo(n - 1) + fib_memo(n - 2)

def fib_table(n):                # bottom-up: small to large
    dp = [0, 1] + [0] * (n - 1)
    for i in range(2, n + 1):
        dp[i] = dp[i - 1] + dp[i - 2]
    return dp[n]

def fib_two(n):                  # keep only the last two cells
    a, b = 0, 1
    for _ in range(n):
        a, b = b, a + b
    return a

print(fib_naive(30), fib_memo(30), fib_table(30), fib_two(30))
print(fib_memo.cache_info())
# → 832040 832040 832040 832040
# → CacheInfo(hits=28, misses=31, maxsize=None, currsize=31)

Naive: time O(φn) ≈ O(1.618n) · space O(n). Each call spawns two more, and the stack holds one path from root to leaf. Memo and table: time O(n) · space O(n). n + 1 states, O(1) work each. fib_two: O(n) time · O(1) space, because each cell reads only the two before it.

Grey = the base cases you seed. Every other cell is the two to its left added: dp[10] = dp[9] + dp[8] = 34 + 21 = 55. The order is the whole trick: by the time you reach a cell, everything it needs is already filled in.

The recursion limit: why bottom-up is safer in Python

sys.getrecursionlimit() → 1000 cold fib_memo(n) with @lru_cache, largest n → 498 cold memo with a plain dict, largest n → 998 fib_memo(1000) → RecursionError fib_two(10**5), no recursion → fine: a 69,424-bit integer

From code/recursion-to-dp.py under Python 3.10. A cold top-down call recurses n deep before anything is cached. That lru_cache halves the reach looks like its C wrapper counting against the limit as well: our reading, backed by the 498 vs 998 run. Warming the cache in order (for i in range(n): fib_memo(i)) also avoids it.

Why it beats the alternatives

✗ Plain recursion

Correct but exponential: 2,692,537 calls for fib(30), 0.129 s on the M3, and each extra n multiplies the work by about 1.618.

✗ Greedy

Take the cheapest next cell: on Coin Path that's 1 → 2 → 3 → 5, costing 1 + 2 + 4 + 2 = 9, not 7. A cheap step now can force an expensive one later.

✗ A closed form

Binet's formula gives fib(n) in O(1), but only for Fibonacci, and in float64 round(φn/√5) is first wrong at n = 71. Most DPs have no formula at all.

✓ DP: memo or table

Solve each state once and reuse it: 31 values for fib(30), 5 for Coin Path. Exact, general, and linear in the number of states times the work per state.

Is DP always the answer to a recursion?

No. It pays only when subproblems overlap. Merge sort and quicksort split into disjoint halves that never repeat, so a cache would just cost memory; that's plain divide and conquer. And it needs a small state: when the state is "everything chosen so far", as in the source's Expression Add Operators (whose state includes the expression string), there's nothing to reuse, so you search with backtracking and prune instead.

Top-down or bottom-up? Top-down is quicker to write and visits only the states it needs. Bottom-up avoids the recursion limit and the call overhead, and it lets you drop rows you're done with (fib_two; the source's two-row Regex and Dungeon tables). Interview habit, not from the source: write the recursion first, add @lru_cache, then convert to a table if n can be large.

Understand and remember

  • The recursion revisits the same subproblems through different call paths → store each answer the first time → every repeat becomes an O(1) lookup that also prunes its whole subtree → cost = states × work per state (31 states, 59 calls for fib(30))
  • Bottom-up fills cells in an order where every dependency is already filled → no recursion, so no 1,000-frame limit → and rows you're done with can be dropped (fib_two: O(1) space)
  • State = the few numbers that decide the rest of the problem, nothing about how you got there → Coin Path's state is the index i, not the path → a small state is what makes subproblems repeat
  • DP needs overlap + optimal substructure → disjoint halves (merge sort) never repeat, so a cache just costs memory; "everything chosen so far" states never repeat either → backtracking instead
  • detail that matters A cold top-down call recurses n deep before anything is cached → deep inputs raise RecursionError even with a cache → warm the cache in increasing order, or tabulate

4 · Compare against what you already know

vs Backtracking: Both explore a tree of choices recursively. Which property of the subproblems decides whether you cache (DP) or prune (backtracking), and which problems need listing rather than counting?

Check
  • DP: the same small state recurs, so caching merges many paths
  • backtracking: the state includes everything chosen so far, so nothing recurs
  • listing every solution (Expression Add Operators) can't be cached away; counting or optimising usually can

vs Divide and conquer and the master theorem: Merge sort also recurses on smaller inputs. Why does adding a cache to it do nothing useful, while it transforms fib?

Check
  • merge sort's subproblems are disjoint halves, each solved once anyway
  • fib's subproblems overlap: fib(n − 1) and fib(n − 2) share almost everything
  • overlap, not recursion, is what DP exploits
