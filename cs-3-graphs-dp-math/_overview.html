Modelling problems as states

The overview for course 3 of the core CS canon series. It ties together the 27 cards on the source guide's Graphs, Recursion and Mathematics pages: traversals, shortest paths and spanning trees, the DP patterns behind its hard problems, and the number tricks. It covers which method to reach for, what each one costs, and how much work it saves on real inputs.

In one breath

Turn the problem into states (a node, a cell, a prefix, "holding share 2 on day 5") and moves between them, then make sure each state is handled once. A graph search visits each node once, so it costs O(V + E). A DP stores each subproblem's answer, so it costs states × moves per state. Shortest paths do the same thing with a relax step, dist[v] = min(dist[v], dist[u] + w), applied in an order that makes it safe. The maths cards shrink the step count itself: take a remainder instead of subtracting, do one step per bit, or skip whole blocks at once.

The words people use

Top-down vs bottom-up

Top-down is the recursion plus a cache (memoization); bottom-up fills a table from the smallest case (tabulation). Same states, same answers. Bottom-up avoids Python's 1,000-frame recursion limit and lets you keep only the last row.

Relaxation

Trying one edge: if dist[u] + w beats dist[v], lower it. Dijkstra relaxes each edge once in distance order, Bellman–Ford relaxes all of them each round, Floyd–Warshall relaxes through one middle node at a time.

DAG, dependency order

A directed graph with no cycle. Every DP is one: each subproblem points at the smaller ones it needs, and a table fill is a topological order. With a cycle (four-way grid moves) there is no fill order, so you search instead.

✓ State

The few numbers that pin a subproblem down and say nothing about how you got there: a node, an index i, a pair (i, j), (day, trades used). Get it right and the cost is states × moves. Leave something out (stops used, current health) and the answer comes out wrong.

When this advice doesn't apply

Some state spaces are just too big. Visiting every node once (a Hamiltonian path) or deciding whether 3 colours are enough are NP-complete: the natural state is "which nodes are used so far", a subset, so DP over subsets is 2ⁿ. And when the question asks for every solution, the output alone can be exponential ('*' × 10⁵ decodes more than 10¹⁰⁰⁰⁰⁰ ways), so no cache helps. Backtracking with good pruning, or a solver, is what's left.

In Python, reach for the built-in first: math.gcd, math.isqrt, math.comb, pow(a, e, m), graphlib.TopologicalSorter, random.choices. For a small, dense or one-off input the simple O(V²) or O(n²) version is often fine, and the recursive form hits the 1,000-frame limit long before it gets slow. Write the algorithm when you need a guarantee the built-in doesn't give, or when the interview asks for it.
