Tensors: shapes, dims and indexing

Also called: n-dimensional arrays, ndarrays (NumPy); a dim is also an axis, and the number of dims the rank or ndim. Lecture 3 · implementing the embedding lookup table · 0:12:19

Prime · 2 minutes before you read

The problem: Every lecture from the bigram model on works on whole tensors at once. If you can't say which dim a sum collapses, what shape C[X] returns or whether a reshape copied memory, you get shape errors you can't read, or worse, code that runs and computes the wrong thing.

Where it fits: It follows the matmul card, which gave you the (n, k) @ (k, m) rule for 2-d shapes. This card covers everything else you do to a tensor's shape: collapse a dim, keep it, relabel it with .view, or grow it by indexing with another tensor. The broadcasting card comes next.

In one breath: a tensor is a block of numbers plus a shape, a tuple saying how many entries lie along each dim (direction). Most tensor bugs in the course come down to which dim an operation walks along, collapses or looks up, so read the shape before you read the numbers.

Predict first: M = [[1, 2, 3], [4, 5, 6]] has shape (2, 3). How many numbers does M.sum(dim=0) return, and what are they?

Three numbers: [5, 7, 9], shape (3,). dim=0 names the dim that disappears. The sum runs down the 2 rows and leaves one total per column. The common guess, one total per row [6, 15], is dim=1 (lab).

An index picks along dims from the left, and every dim you fix disappears from the shape: M[1] = [4, 5, 6] with shape (3,) is row 1; M[:, 1] = [2, 5] with shape (2,) is column 1 (: means "all of this dim"); M[1, 2] = tensor(6.) is 0-d, and .item() gives 6.0 (computed).

keepdim keeps the collapsed dim as size 1, and that matters as soon as you divide by the total. M / M.sum(1, keepdim=True) is (2, 3) ÷ (2, 1), so each row is divided by its own total: [[0.1667, 0.3333, 0.5], [0.2667, 0.3333, 0.4]], and every row sums to 1 (computed). Drop keepdim and it's (2, 3) ÷ (2,): here PyTorch raises "The size of tensor a (3) must match the size of tensor b (2) at non-singleton dimension 1" (computed). On a square (27, 27) table the same slip runs without error and divides the wrong way; the broadcasting card shows why.

view: a new shape over the same numbers

A tensor is really a flat storage (one block of memory) plus small metadata: the shape, a stride per dim and an offset. .view(...) writes new metadata over the same storage, so reshaping copies nothing. -1 means "work this dim out": 18 ÷ 6 = 3.

A view only works if one stride per dim can describe the walk. M.t() (the transpose, shape (3, 2)) has strides (1, 3): its rows are not consecutive in storage, so M.t().view(6) raises "view size is not compatible with input tensor's size and stride" (lab). .reshape(6) copies into new memory instead and gives [1, 4, 2, 5, 3, 6] (computed). And because a view shares storage, writing through it writes the original: after a.view(3, 6)[0, 0] = 100, a[0] is 100 (computed).

Why it beats the alternatives

Getting from integer contexts X (32, 3) to the (32, 6) input of the hidden layer:

✗ A Python loop

Fetch C[ix] for each of the 32 × 3 = 96 positions and glue lists together. Correct, but every lookup is a Python step, and batches grow into the thousands.

✗ One-hot, then matmul

Gives identical numbers (one_hot(5).float() @ C equals C[5], computed), but builds a (32, 3, 27) tensor and does 32·3·27·2 = 5,184 multiply-adds to copy out 192 numbers, plus a .float() cast.

✗ torch.cat the slices

cat([emb[:,0,:], emb[:,1,:], emb[:,2,:]], 1) gives the right (32, 6), but allocates new memory and hard-codes block_size = 3.

✓ C[X].view(-1, 6)

One lookup gives (32, 3, 2); the view relabels it (32, 6) with no copy, and -1 adapts to any batch size.

When view and indexing bite

Not every result is a view. Slicing (M[:, 1]) and .view share storage; indexing with a tensor or list (C[X], M[[0, 1]]) makes a new copy (both checked with untyped_storage().data_ptr(), computed). So editing a view edits the original, while editing C[X] leaves C alone.

view isn't always possible. After a transpose or a permute the tensor is not contiguous (its rows aren't laid out one after another in storage), and .view fails. Use .reshape, which views when it can and copies when it must, or .contiguous().view(...). Reach for .view when you want the no-copy guarantee; a silent copy would hide a bug. The PyTorch docs: torch.Tensor · Tensor.view · ezyang, PyTorch internals (linked in the Lecture 3 description).

Understand and remember

  • A reduction's dim names the axis it walks along → that axis is summed away → (2, 3).sum(0) keeps the 3 columns → [5, 7, 9] with shape (3,)
  • keepdim=True leaves the reduced axis as size 1 → (2, 3) ÷ (2, 1) lines up row by row → each row is divided by its own total; without it the (2,) or (27,) total lines up with the columns → an error, or on a square table a silent wrong answer
  • A tensor is flat storage + shape + stride → .view only writes new shape and stride → no numbers move, so it is free and shares memory → edits through a view change the original, and a non-contiguous tensor (a transpose) can't be viewed, so .reshape copies
  • Indexing a table with an integer tensor looks up one row per index → result shape = X.shape + C.shape[1:] → (32, 3) + (2,) = (32, 3, 2) → .view(-1, 6) puts each example's 3 embeddings side by side for the hidden layer
  • detail that matters Advanced indexing (C[X], M[[0, 1]]) returns a copy while slicing (M[:, 1]) returns a view → writing into C[X] never changes C → the gradient has to be added back into C's rows (the embedding-backward card)
  • detail that matters torch.Tensor always makes float32 while torch.tensor infers int64 from integers → float indices raise an IndexError and int64 @ float32 raises a dtype error → build indices with lowercase torch.tensor and cast one-hot vectors with .float()

Reference only

  • t.shape, t.dim(), t.stride(), t.is_contiguous(), t.data_ptr()
  • dim=-1 means the last dim
  • torch.arange(18).view(3, 3, 2) has strides (6, 2, 1)
  • the exact error texts: "view size is not compatible with input tensor's size and stride", "tensors used as indices must be long, int, byte or bool tensors"
  • .contiguous() as the fix before .view; / promotes ints to float, // floors

4 · Compare against what you already know

vs Matrix multiply by shapes: Matmul and sum(dim=…) both make an axis disappear. Which axis does each remove, what decides it, and how does each one fail when you pick the wrong layout?

Check
  • matmul always sums away the shared inner axis k: the left's last dim against the right's first
  • a reduction removes whichever axis you name with dim
  • a matmul with mismatched inner sizes raises an error
  • a reduction over the wrong dim often runs fine and returns the wrong numbers, so check the output shape

vs Broadcasting: the two rules: This card makes a (27, 1) total with keepdim; the broadcasting card explains how PyTorch stretches it. What design choice in broadcasting turns a missing keepdim into a silent bug instead of an error?

Check
  • broadcasting aligns shapes from the right
  • a (27,) total is treated as (1, 27), a row, and stretched down the rows
  • a square (27, 27) table always matches, so there's no error
  • the result divides each column by a row total: wrong, with no warning

vs An embedding is just indexing: Here C[X] is a shape trick; in the MLP course C is a learned layer. What is the same computation behind C[5] and one_hot(5) @ C, and why does the course always use the lookup?

Check
  • both return row 5 of C
  • the one-hot matmul multiplies by 26 zeros and a single 1
  • the lookup skips the (…, 27) one-hot tensor and all its multiply-adds
  • the one-hot view is how you explain an embedding as a linear layer; the lookup is how you run it

5 · Predict commit to an answer before revealing

The WaveNet lecture has e of shape (4, 8, 10): 4 examples, 8 characters, 10 embedding numbers each. What shape is e.view(4, 4, 20), and which two characters' numbers end up in the first row of e.view(4, 4, 20)[0]? Is it a copy?

Reveal

Shape (4, 4, 20): 4·8·10 = 320 = 4·4·20, so the view is legal. Storage runs through the last dim fastest, so each new row of 20 is two consecutive characters' 10 numbers: row 0 holds characters 0 and 1. That is exactly how FlattenConsecutive groups pairs. No copy: e is contiguous, so only the shape and strides change.
