Broadcasting: the two rules

Also called: broadcasting semantics, implicit expansion, "stretching" size-1 dimensions. Lecture 2 · efficiency! vectorized normalization of the rows, tensor broadcasting · 0:36:17

Prime · 2 minutes before you read

The problem: Real code constantly combines tensors of different shapes: a table divided by its row sums, a bias added to a whole batch. Without a rule for mismatched shapes you'd write a loop for each, and with the rule misunderstood you get wrong numbers and no error.

Where it fits: The tensors card taught shapes, dim and keepdim. This card says what happens when two different shapes meet in + - * /. Every lecture from makemore onwards leans on it, starting with normalising the bigram table.

In one breath: when you add, subtract, multiply or divide two tensors of different shapes, PyTorch lines their shapes up from the right and stretches any dimension of size 1 (or any missing dimension) to match the other tensor. If a pair of sizes can't be matched that way you get an error. If it can be matched in a way you didn't mean, you get no error at all, just wrong numbers.

Predict first: N is the 3×3 count table below, and its row sums are [4, 4, 10]. You want every row to sum to 1, so you write N / N.sum(1) and forget keepdim=True. Does PyTorch raise an error? If not, what does row 0 of the result sum to?

No error, and row 0 sums to 0.7 (the rows sum to 0.7, 0.85 and 2.2, lab output). N.sum(1) has shape (3,), and rule 1 pads it on the left to (1, 3), a row. That row is copied down, so column j gets divided by the sum of row j. The shapes fit perfectly, which is exactly why nothing warns you.

The two rules

A tensor's shape lists its size along each dimension, e.g. (27, 27) is 27 rows by 27 columns and (27,) is a flat list of 27 numbers. For an elementwise operation like A / B, PyTorch's broadcasting semantics page boils down to two rules:

  1. Line the shapes up on the right. Compare the last dimensions first, then move left. If one shape runs out of dimensions, treat each missing one as size 1 (it is padded on the left, never the right).
  2. Each lined-up pair must be equal, or one of them must be 1. A size-1 dimension is stretched (copied) to the other size, and the result takes the larger size. Any other pair, like 4 against 3, is an error.

Worked: the keepdim bug on a 3×3 count table

N.sum(1) adds across each row (dim 1 = the column index), giving [4, 4, 10]. With keepdim=True the summed-away dimension stays as a 1, so the shape is (3, 1), a column. Without it the dimension is dropped and the shape is (3,), which rule 1 reads as a row (1, 3). Dashed cells are the stretched copies; no real memory is used for them.

Why it beats the alternatives

✗ Loop over the rows

for i in range(27): P[i] /= P[i].sum() is correct and obvious, but it's 27 separate Python-level steps instead of one call, and it gets slower as the table grows.

✗ Build the full-size copy

.repeat(1, 27) turns the (27, 1) sums into a real 27×27 tensor before dividing. It gives the same answer but allocates 729 numbers to hold 27 distinct values.

✗ Demand identical shapes

A stricter library would reject (27, 27) / (27, 1) and make you reshape by hand every time. That is safer against the keepdim bug, but every bias add and normalisation gets noisier.

✓ Broadcasting

One line, no loop, and no copy: the stretched dimension is a view with stride 0, so the same 27 numbers are reused along it (expand(27, 27).stride() is (1, 0), computed).

Where broadcasting bites

It fails silently when the shapes fit by accident. A square table is the worst case: a (27,) of row sums lines up with the 27 columns just as happily as a (27, 1) lines up with the rows. Karpathy's advice in this chapter (from 0:36:17) is to treat broadcasting "with respect". In practice: keep keepdim=True on any sum you will divide by, print .shape before you trust a result, and spot-check one row (P[0].sum() should be 1).

In-place ops only stretch the right-hand side. N /= N.sum(1) still runs (the result keeps N's shape), but b += M with b (3,) and M (3, 3) fails: "output with shape [3] doesn't match the broadcast shape [3, 3]" (computed). And stretching has a price in the backward pass: a value copied along a dimension gets its gradient summed back along that dimension, which is the sum–broadcast duality in z2h-6.

Understand and remember

  • Shapes are compared from the right → a shorter shape is padded with 1s on the left → a (3,) of row sums becomes a row (1, 3) → it is copied down the rows, so column j is divided by row-sum j
  • keepdim=True keeps the summed dimension as size 1 → (3, 1) is a column → it stretches across each row → each row is divided by its own sum and sums to 1
  • Broadcasting only checks that sizes are equal or 1 → a square table fits both the right and the wrong reading → no error, just wrong numbers (row 0 sums to 7.02 on the bigram counts) → check .shape and one row sum yourself
  • A stretched dimension is a view with stride 0 → the same numbers are reused, nothing is copied → one line replaces a loop at no memory cost → but in backprop the gradient of a stretched value must be summed back along that dimension
  • detail that matters In-place ops (/=, +=) keep the left tensor's shape → only the right side may stretch → b += M with b (3,) and M (3, 3) errors, while N /= N.sum(1) silently runs

Reference only

  • the error text "The size of tensor a (4) must match the size of tensor b (3) at non-singleton dimension 1"
  • keepdim and keepdims are both accepted by torch.sum (the notebook uses keepdims)
  • each tensor needs at least one dimension to broadcast (the docs' fine print)
  • .expand (view, no copy) vs .repeat (real copy) when you want the stretch explicitly
