BatchNorm at test time: running statistics

Also called: running mean and std, running stats, BN buffers, train mode vs eval mode, calibrating BatchNorm. Lecture 4 · batch normalization: summary · 1:03:07

Prime · 2 minutes before you read

The problem: In training, BatchNorm standardises with the current minibatch's mean and std. At test time that makes one input's prediction depend on its batchmates, and a batch of one gives nan. A deployed model needs one fixed answer per input.

Where it fits: The last card built the BatchNorm forward pass with batch statistics. This card adds the second half of the layer: fixed statistics for inference, kept as buffers beside the learned bngain/bnbias.

In one breath: during training, BatchNorm standardises each hidden unit with the mean and standard deviation of the current minibatch, so every example's output depends on which other examples happen to share its batch. At test time you want one fixed answer per input, even for a single input, so you swap the batch statistics for fixed ones: either measured once over the whole training set after training, or kept as a slow running average during training.

Predict first: after training, you feed one example (a batch of 1) through the net, still computing the mean and std from the batch. What does the net output?

nan (not a number) in every logit. hpreact.std(0) of a single row divides by n − 1 = 0, so the std is nan, and nan spreads through everything after it. The lab prints logits contain nan? True. With the running statistics instead, the same example gets a normal prediction: probability 0.0129 on the correct next character.

The problem: an example's output depends on its batchmates

The lab takes training example 0 (the context ..., predicting a name's first letter), puts it in five batches with 31 different random batchmates each, and reads the probability the trained net gives to the correct next character. The input never changes; only the batchmates do.

batchp(correct next char) for example 0value 10.0121 20.0134 30.0268 40.0158 50.0130 running stats0.0129

Bars to scale (full width = 0.03). Batch 3 gives 0.0268 / 0.0121 = 2.2× the probability of batch 1 for the same input. The green row uses the fixed running statistics, so it is the same every time.

In training this jitter is tolerated, and even helps: each example gets slightly different treatment every time it's seen, which acts like extra data and makes overfitting harder. That regularising effect is a side effect, not the reason BN was invented. But a deployed model can't give different answers depending on who else is in the queue, and it has to handle a batch of 1.

Two modes, two sources of statistics

Option 1: calibrate after training

When training ends, push the whole training set (182,625 examples) through embcat @ W1 once, under torch.no_grad(), and take one mean and one std per hidden unit over all of it. That is notebook cell 9. It is exact, but it's an extra pass over the data and a separate step you can forget.

Option 2: keep a running estimate during training

The route the lecture keeps, and what PyTorch does: after computing each batch's statistics, nudge a stored copy a tiny bit toward them. This is an exponential moving average (EMA): a weighted average in which each older batch counts a little less than the one after it.

μrun← 0.999·μrunkeep 99.9% of the old estimate + 0.001·μbatch0.1% of this batch
μ_runthe running mean, bnmean_running (1 × 200, one per hidden unit); starts at zerosstd: bnstd_running, starts at ones μ_batchthis minibatch's mean, bnmeani, over its 32 rowssame update for the std 0.001momentum: how far the estimate moves each stepPyTorch default: 0.1
a batch 1,000 steps old still weighs 0.001 × 0.999^1000 = 0.00037 (37% of the newest) half-life of a batch's influence: ln 0.5 / ln 0.999 ≈ 693 steps the zeros it started from, after 200k: 0.999^200000 ≈ 1.3e-87 → gone

So the running mean is an average over roughly the last thousand batches of a net that is still changing, which is close to, but not exactly, what the finished net produces.

Why momentum 0.001, not PyTorch's 0.1

With momentum 0.1 the running estimate is mostly the last few batches (half-life ln 0.5 / ln 0.9 ≈ 6.6 steps), and a batch of 32 has a noisy mean. The lab runs both EMAs over the same 10,000 batch-32 means of the trained net and compares each to the calibrated mean:

momentumhalf-lifemean |running − calibrated|
0.1 (PyTorch default)≈ 6.6 steps0.0570
0.001 (the lecture)≈ 693 steps0.0076

0.0570 / 0.0076 = 7.5× farther from the truth with 0.1. A large batch has a steadier mean, so the default is fine there; at batch 32 Karpathy lowers it.

When: pause the video at 1:03:07, where the BatchNorm summary starts. Add the buffers to your BN MLP from the last card, train, then calibrate and compare.

bnmean_running = torch.zeros((1, n_hidden))  # before the loop
bnstd_running = torch.ones((1, n_hidden))
# in the loop, right after bnmeani and bnstdi:
with torch.no_grad():
  bnmean_running = 0.999 * bnmean_running + 0.001 * bnmeani
  bnstd_running = 0.999 * bnstd_running + 0.001 * bnstdi
# after training: calibrate over the whole training set
with torch.no_grad():
  hpreact = C[Xtr].view(Xtr.shape[0], -1) @ W1
  bnmean = hpreact.mean(0, keepdim=True)
  bnstd = hpreact.std(0, keepdim=True)
print((bnmean - bnmean_running).abs().max().item())
print((bnstd - bnstd_running).abs().max().item())

Then, in split_loss, normalise with (hpreact - bnmean_running) / bnstd_running instead of the batch statistics.

Why it beats the alternatives

✗ Batch statistics at test time

The prediction for an input depends on the rest of the batch (2.2× swing above), and a single input gives nan.

✗ Calibrate only after training

Works and matches to the third decimal, but it costs an extra full pass over the training set and is one more step to forget before you ship.

✗ Running stats with momentum 0.1 at batch 32

The estimate follows the last few noisy batches: 7.5× farther from the calibrated mean than momentum 0.001 in the lab.

✓ EMA buffers with a small momentum

Fixed statistics come for free as a by-product of training, match calibration, and let the net predict one example at a time.

The bug everyone hits

Running statistics only help if the net actually uses them. In PyTorch that's the difference between model.train() and model.eval(): forget eval() and a BatchNorm1d layer keeps using batch statistics and keeps updating its buffers while you evaluate. Karpathy sums up BN as a layer that has caused him bugs many times, and the coupling of examples is why.

BN is not the right tool when batches are tiny or examples must stay independent (for example, generating text one token at a time). LayerNorm normalises each example over its own features instead, so it has no batch statistics and no running buffers; the GPT course uses it. PyTorch's version also stores a variance rather than a std and adds ε = 1e-5 before dividing; the resnet-and-torch-nn card compares the two.

Understand and remember

  • BN normalises with batch statistics → each example's output is a function of its batchmates → the same input's prediction jitters (2.2× in the lab) → at test time you must replace the batch statistics with fixed ones
  • Batch of one → std divides by n − 1 = 0 → nan std → nan logits → only stored statistics make single-example inference possible
  • EMA with momentum m → each step keeps 1 − m of the old estimate → it effectively averages the last ~1/m batches → small m (0.001) smooths out noisy batch-32 means and lands on the calibrated values; large m (0.1) tracks the last few noisy batches (7.5× farther off)
  • Running stats are updated by assignment inside no_grad, not by gradients → they are buffers, not parameters → the optimiser must skip them, and the model must be switched to eval mode to use them
  • detail that matters The EMA averages over a net that is still changing (half-life ≈ 693 steps) → it can lag the final weights slightly → which is why it differs from calibration by up to 0.0266 in the mean, though the losses agree to 0.0001 on val

Reference only

  • the lecture's names bnmean_running, bnstd_running, bnmeani, bnstdi
  • PyTorch's names running_mean, running_var, num_batches_tracked, and its default momentum=0.1, eps=1e-5
  • model.train() / model.eval() and the @torch.no_grad() decorator
  • notebook cells: 7 (EMA in the loop), 9 (calibration), 10 (split_loss)

Check
