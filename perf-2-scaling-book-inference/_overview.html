In one breath

Every decode step reads every sequence's KV cache (always memory-bound), then either reads all the weights once or does 2 FLOPs per parameter per token, whichever is slower. Batching amortises the weight read until the step turns compute-bound at Bcrit ≈ 240–295 tokens. In practice you usually run out of KV memory first. So most of the chapter is about fitting more sequences: shrink the KV cache, shard it, and schedule prefill and decode so they don't block each other.

The KV term is 80% of the step. The book's Pop Quiz (30B, int8, v5e 4×4) gives 2.5 ms at B = 4 and 21 ms at B = 256.

The same thing in plain text:

step ≈ B × KV bytes per seq ÷ bandwidth ← attention: always memory-bound + max( 2 × B × params ÷ FLOP/s, weight bytes ÷ bandwidth ) ← MLP: compute-bound only past B_crit throughput = B ÷ step

The mental model: what each section of the chapter attacks

Prefill is the other half of the chapter: a big batch of prompt tokens, compute-bound, set by 2·N·T ÷ C (0.91 s for 8k tokens of 70B on 16 v5e at 40% MFU). That's why engines schedule it separately.

The multipliers don't simply multiply. Fitting more sequences only helps until the step turns compute-bound (Bcrit). Speculation competes with batching for the same idle FLOPs. Tensor parallelism buys latency with more chips. In the 70B example, the cost per query moves 6.7× from bf16 on the minimum slice to int4 on a doubled slice.

The words people use

Critical batch size, B_crit

The number of tokens per step at which a linear layer stops waiting on memory: C ÷ W, which is 240 on v5e and 295 on H100. With int8 weights and bf16 math it halves. For MoE it multiplies by E/k (3,840 for DeepSeek).

Model vs data parallelism in decode

Split the weights and move activations (tensor/model parallel), or run copies (replicas). FSDP in decode re-reads weights over slow links, which would be 31 ms per step instead of 4.8 ms on 8×H100.

Continuous batching, disaggregation

Slot requests in and out of a running decode batch, and at scale put prefill and decode on separate servers so one prompt doesn't stall everyone. The book's 70B pipeline wants about 3 prefill servers per generate server.

KV bytes per token

2·L·K·H·bytes: 128 KiB for Llama-3.1-8B, 800 KiB for LLaMA-2-13B. It sets how many users fit and how long each decode step takes. Most of the chapter's tricks exist to shrink it.

The takeaway

Serving cost is tokens per second per chip, and in decode that's set by memory. First fill the chip with as many sequences as fit, up to about Bcrit. Then make each sequence cheaper to hold (GQA, FP8 KV, paging). Then pick the topology and precision that maximise QPS per chip rather than the smallest one that fits. Keep prefill from stalling decode, with continuous batching, and with disaggregation at scale.

Where this doesn't apply as-is: these are rooflines, and the book says real systems reach about half. At long context with many users the KV term dominates and batching stops helping. At batch 1 and low latency (edge, a single user) you're weight-read-bound, so quantization and speculation beat batching. For MoE, Bcrit rises by E/k, so a far bigger batch is needed before the math matters. The TPU numbers transfer to GPUs through two constants, C/W and the interconnect bandwidth.

Understand and remember

  • Every decode step reads all weights once (shared by the batch) → batching spreads that fixed read over more tokens → throughput rises almost for free until the MLP math (2·B·N/C) overtakes the weight read at Bcrit = C/W
  • Each sequence brings its own KV cache → the KV term grows with B × context and is always memory-bound → HBM fills before B reaches Bcrit at long context (59 sequences at 8k on one H100) → most of the chapter is about fitting more sequences: shrink, shard or page the KV
  • Levers act on different terms → shrinking KV bytes raises how many sequences fit and cuts the KV read; quantizing weights cuts the weight read; tensor parallelism divides the weight read across chips → each lever only helps while its term dominates, so their gains don't multiply
  • Prefill is one big compute-bound batch (2·N·T/C) and decode is many small memory-bound steps → running them in lockstep makes one stall the other → engines schedule them apart (continuous batching, disaggregation)
  • detail that matters Speculative sampling spends the idle FLOPs of a memory-bound step on verifying guesses → it competes with batching for the same idle math → a 2.2× win at batch 1 turns into a slowdown at batch 256

Why this step?

3 · Retrieve from memory, card closed
  1. concept Explain why one extra decoding user costs almost nothing at batch 1 but costs a full KV read at batch 59 on the same H100.
    Check
    • at batch 1 the 4.79 ms weight read dominates; one more sequence adds only its KV read (0.32 ms at 8k) and shares the weights
    • at batch 59 the KV term is already 80% of the step (18.9 of 23.7 ms); each new sequence adds its own 1.07 GB read and HBM is full, so it can't even be added
    • the weight read is amortised; the KV read never is
  2. mechanism Walk the overview's filled-in example: Llama-3.1-8B, one H100, 8k context, B = 59. Which three numbers go into the step, and which term would you attack first?
    Check
    • KV read 59 × 1.07 GB ÷ 3.35 TB/s = 18.9 ms
    • max(math 0.96 ms, weight read 4.79 ms) = 4.79 ms
    • step 23.7 ms → 2,489 tokens/s; the KV term is 80%, so shrink KV (FP8 KV doubles to 4,986) before touching the weights
  3. tradeoff A team wants the lowest per-user latency for one edge user, another wants the lowest cost per token for an offline eval. Which levers from the table does each pick, and which lever helps one and hurts the other?
    Check
    • edge / batch 1: weight-read-bound, so quantize weights and use speculative sampling; batching is irrelevant
    • offline: fill HBM with sequences up to Bcrit, shrink KV so more fit
    • speculation helps the first and hurts the second: at batch 256 it is a 0.70× slowdown because verify tokens push past Bcrit

5 · Predict commit to an answer before revealing

Same model and GPU, but context drops from 8k to 4k tokens. Commit first: how many sequences fit, what is the step time, and does the KV share of the step go up, down or stay about the same?

Reveal

KV per sequence halves to 0.537 GB, so B = ⌊63.94 / 0.537⌋ = 119. KV read 19.07 ms, weight read 4.79 ms (math 1.93 ms is still below it), step 23.86 ms, 4,986 tokens/s. The KV share stays about 80%: when HBM is full, the step always reads roughly the whole 80 GB, so halving context doubles the batch instead of shortening the step.
