Attention's arithmetic intensity

Also called "why attention stays memory-bound in decode", ST/(S+T), or GQA intensity. This is Scaling Book Part 7, "What about attention?", plus the GQA version from Part 4, Question 4. The book's numbers are TPU v5e; H100 and Llama-3.1-8B are alongside as our recomputation.

In one breath

Unlike linear layers, attention in decode reads a different KV cache for every sequence, so batching doesn't raise its intensity. It stays at ≈ 1 FLOP/byte, or ≈ G with GQA, so it is always memory-bound in generation. Prefill attention, by contrast, becomes compute-bound past a few hundred tokens.

What one Flash Attention fusion moves

The book looks at one head of plain multi-head attention, fused into a single Flash Attention kernel, in bf16 (2 bytes per number). Softmax and mask FLOPs are ignored; the book notes they should overlap with the rest, but "this can be non-trivial to do on certain TPU generations".

  • Read Q, bf16[B, T, D]: 2BTD bytes.
  • Read the KV cache, a pair of bf16[B, S, D]: 4BSD bytes.
  • QK matmul: 2BSTD FLOPs. The bf16[B, S, T] score matrix is never written to HBM, which is the point of Flash Attention.
  • AV matmul: another 2BSTD FLOPs.
  • Write the output, bf16[B, T, D]: 2BTD bytes.

What gets read, prefill vs decode

Per sequence, per head. Green = KV cache. In prefill the K/V tiles are reused by every query, like weights reused by a batch. In decode the whole cache is read to serve one query row, and a second sequence brings its own cache, so B adds bytes as fast as FLOPs.

Running example: which bytes dominate a decode step?

Llama-3.1-8B, bf16, H100. Each step reads all the weights once (16.06 GB, shared by the batch) plus every sequence's KV cache (1.07 GB each at 8,192 tokens). At batch 64: weights 16.06 GB vs KV 64 × 1.07 = 68.7 GB, so 81% of the bytes are KV.

The book's rule of thumb for when this happens: throughput gains from batching fade once KV bytes reach parameter bytes, and the ratio for one sequence is "roughly 2DF / SHK". Since HK ≈ D, that is roughly F vs S. For Llama-3.1-8B at S = 8192: 2·4096·14336 / (8192·128·8) = 14.0, close to the exact 16.06 GB / 1.074 GB = 14.96 (our recomputation).

How it differs from related ideas

✗ Linear layers (intensity ≈ B)

Weights are shared across the batch, so each extra sequence adds FLOPs but no weight bytes, and intensity climbs to Bcrit = 240 / 295. Attention's "weights" are the KV cache, and every sequence has its own.

✗ Flash Attention

Already assumed in ST/(S+T): it keeps the [B, S, T] score matrix out of HBM, which is what lets prefill reach T/2. Decode must still read the whole KV cache for one query, so it doesn't move the ≈ 1 bound (our reading of the book's algebra).

✗ GQA / MQA (and MLA)

Share each K/V row across G query heads, so decode intensity rises from ≈ 1 to ≈ G and the cache shrinks by G. Llama-3.1-8B gets 4, MQA ≈ 32: better, still far below the ridge. MLA compresses KV further; it isn't in the book.

✓ The ST/(S+T) view

One ratio explains all of them: B and D cancel, so only the reuse of each K/V row matters. That's T in prefill, G with GQA, and 1 in plain decode. To speed up decode attention, read fewer KV bytes.

So FLOP optimizations don't help decode attention?

Mostly, no. This is why long-context, large-batch decode is dominated by KV reads, and why KV-shrinking tricks matter more than FLOP optimizations for decode: GQA, local attention layers, KV quantization and ragged/paged reads that skip padding. A faster matmul does nothing when the arithmetic units are idle 99% of the time. The book puts attention in its own term of the step-time formula: batch × KV size ÷ bandwidth, "never compute-bound".

Where this is not the main problem:

  • Short context, small batch. At batch 1 and 8k, KV is only 6.3% of the bytes; the weights dominate, and batching (critical batch size) or weight quantization is the lever.
  • Prefill. Past ≈ 480 tokens (v5e) or ≈ 590 (H100) attention is compute-bound, so FLOP efficiency does matter there. The book's Part 4 answer says "compute-bound at S = 240" for prefill "depending on how you interpret the question"; Part 7's T/2 derivation gives 480, which is what this card uses.
  • Very aggressive architectures. The book says we'll almost always be memory-bound "unless the architecture is adjusted aggressively". Large G pushes toward the ridge, but no mainstream G gets near 240.
