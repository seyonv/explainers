Tricks that shrink the KV cache

Also called GQA / MQA, sliding-window (local) attention, cross-layer KV sharing, KV quantization, ragged reads and PagedAttention. This is Scaling Book Part 7, "Tricks for Improving Generation Throughput and Latency", all of it. The worked numbers are our recomputation on Llama-3.1-8B and one H100, not in the book.

In one breath

KV-cache memory caps how many sequences fit in a batch, and reading the KV cache dominates long-context decode. So most serving wins come from storing fewer KV bytes per token, or from wasting fewer of the bytes you store. The book's big picture: together these tricks "can reduce KV cache sizes by over an order of magnitude compared to a standard MHA Transformer", which "can lead to an order-of-magnitude improvement in the overall cost".

Why KV bytes per token set the throughput

The step-time formula for a memory-bound decode step reads the weights once and every sequence's KV cache once. If you fill the free HBM with sequences, the step reads nearly the whole 80 GB, so the step time barely moves. Throughput is then just "how many sequences fit", which is inversely proportional to KV bytes per token.

What each trick does, in the book's words

Everyday analogy: the KV cache is a filing cabinet each conversation drags into every step. The tricks either shrink each file (fewer heads, fewer bits, shorter window, shared drawers) or stop reserving empty drawers (ragged reads, paging).

Our redraw of the book's "gmqa" figure, with 8 query heads (grey) and their KV heads (green). Llama-3.1-8B is the middle case at 32 : 8. The book: GQA "reduces the KV cache by a factor of the Q:KV ratio over pure MHA" and "effectively increases the arithmetic intensity" of attention (see attention intensity).

Quantization and Bcrit: with 8-bit weights and bf16 compute, each weight byte feeds 2 FLOPs per sequence, so Bcrit halves. The book gives 240 → 120 on v5e; the H100 analogue is 295 → 148 (our recomputation, labs/kv-tricks.py).

Why it beats the alternatives

✗ Buy more HBM

Batch that fits grows only linearly with memory, and so does the bill. Every sequence still costs 1.07 GB at 8k, and each step still reads all of it.

✗ Cap the context

Halving the context halves KV per sequence, but it removes the thing users came for: long documents, long chats, agents. It's a product cut, not an efficiency gain.

✗ Don't cache: recompute K, V

That's the naive sampler from the KV cache card: re-processing the whole prefix every step, Θ(n²) work for n tokens. Memory is traded for far more compute.

✓ Shrink and pack the KV

Fewer bytes per token and no padding multiply the batch without touching weight traffic. In our ladder: 27.7× less KV, up to 28× the throughput on the same H100.

Can a serving team just turn all of these on?

No. The book lists these tricks "ignoring effects on quality", and they split by who can apply them:

  • Training-time architecture choices: GQA/MQA, local layers and cross-layer sharing (and MLA). The book: the model "can learn to share" KVs. A server can't turn an existing model into GQA or give it a sliding window; you serve whatever the lab trained. Llama-3.1-8B already has GQA, so the first row of the ladder is not a lever for you.
  • Post-hoc serving choices: quantization ("can often be applied post training") and ragged / paged reads ("a runtime optimization… indifferent to architecture"). These are what an inference team controls day to day. Quantization can still cost quality, so it gets evaluated per model.
  • When they don't help: short contexts at small batch, where weights dominate the bytes (see attention intensity); local layers at contexts shorter than the window; and cross-layer sharing when the kernel re-reads the shared cache, which "does not necessarily improve the step time". Once the batch is large enough to be compute-bound (the MQA "try this" gets there), shrinking KV further stops raising throughput.

Run it: labs/kv-tricks.py It prints the ladder (KV per token, sequences that fit, memory and compute step times, throughput), the padding example and Bcrit with 8-bit weights. Try this: at 128k context MHA can't fit a single sequence (68.7 GB), the real model fits 3, and the local-layer row jumps to 43.8× smaller KV because a 4k window keeps only 3% of each local layer. With MQA instead of GQA the 8k ladder turns compute-bound at the local-layer row, and throughput stops following the KV shrink.
