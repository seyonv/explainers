Modelling LLaMA 2-13B on 8 TPU v5e

Also called the batch–throughput table, or "why GQA matters for serving". This is Scaling Book Part 7, "Modeling throughput and latency for LLaMA 2-13B": two tables that feed a real model's shapes into the step-time formula on 8 TPU v5e chips, first with full multi-head attention, then with a 5× smaller KV cache. The book's numbers are TPU v5e. The H100 and Llama-3.1-8B figures are our recomputation.

In one breath

Put real shapes into the step-time formula. With full multi-head attention the KV cache runs out of memory at batch ~16 (~790 tokens/s). A 5× smaller KV cache fits batch 64 and ~3,750 tokens/s. That is about 4.8× more throughput from the same chips, and every batch size gets lower latency too.

What the tables teach

1. Throughput has diminishing returns in batch. Throughput = B·W / (B·KV + P) approaches W / KV. It is already halfway there when the batch's KV bytes equal the weight bytes, at B = P / KV = 26 / 6.7 = 3.9 sequences for MHA. From 1 → 8 MHA gains 3.3×, 8 → 16 only 1.2×, and 16 → 240 (15× the batch) just 1.22×. The book: "increasing the batch size does give us better throughput, but we suffer rapidly diminishing returns … we've hit a wall on the per chip throughput." Our aside: the per-chip wall is 0.82e12 / 6.7e9 = 122 tok/s whatever the number of chips.

2. Shrinking the KV cache moves both the wall and the memory limit. With KV ÷ 5, the halfway point moves to 26 / 1.34 = 19.4 sequences, the ceiling rises 5× to 4,896, and the batch that fits rises from 16 to 64 or more. "The theoretical throughput per chip continues to scale up to batch size 240." At the largest batch that fits, 3,756.62 / 787.99 = 4.77× the throughput from the same 8 chips (98.5 → 469.6 tok/s per chip).

3. Latency improves too, at every batch. The per-step time is each user's time per token. At batch 1 GQA is only 1.19× faster (4.98 → 4.17 ms, since the weights dominate), but at batch 16 it is 2.81× faster (20.30 → 7.23 ms). Even at 4× the batch, GQA's batch-64 step (17.04 ms, 58.7 tok/s per user) beats MHA's batch-16 step (20.30 ms, 49.3 tok/s per user). In the book's words: "The latency, maximum throughput, and maximum batch size all improve dramatically!" Later LLaMA generations did exactly this: LLaMA-3 8B has 32 query heads and 8 KV heads.

"In addition to params, the size of KV cache has a lot of bearing over the ultimate inference performance of the model. We want to keep it under control with a combination of architectural decisions and runtime optimizations."

Why it beats the alternatives

✗ Bigger batch, same KV

Out of memory. MHA batch 32 needs 240.4 GB and batch 240 needs 1,634, 12.8× the 128 available. The book: "need an order of magnitude more memory to go near 240". Even if it fit, 240 would give only 1.22× batch 16's throughput.

✗ Just add chips

More HBM fits more sequences, but "a bigger topology can improve the latency, but we've hit a wall on the per chip throughput." Our recomputation: 8 → 64 chips moves MHA from 97 to only 119 tok/s per chip (wall 122). So cost per token barely falls.

✗ Shorter contexts

Halving T to 4k halves KV per sequence (3.35 GB) and roughly doubles the batch. But that limits the product: users who need 8k or 32k can't have it. At 32k, MHA fits only 3 sequences on 8 chips (our lab).

✓ Shrink the KV cache

1:5 GQA with the same params: batch 64 fits, 3,757 tok/s (4.77×), and lower latency at every batch. It raises the per-chip wall 5×, which neither alternative can do. See tricks that shrink the KV cache.

Are these the throughputs you'd actually get?

No, they are ceilings. They are roofline bounds that assume perfect overlap of loads and compute, and no prefill, sampling or communication time. The book lists why reality falls short. XLA doesn't overlap HBM reads perfectly with FLOPs. Sharded models often "start taking a latency hit on linears over BS=32" from ICI communication. So use the tables for ratios and limits, not as promised numbers. See sharding the KV cache and serving LLaMA 3-70B for the fuller picture.

Per-chip throughput is what sets cost per token. You rent chips by the hour, so $/token ∝ chips ÷ total tokens/s = 1 ÷ tokens/s per chip. That is why the 98.5 → 469.6 tok/s per chip jump matters more than the latency gain (what we optimize).

When shrinking KV is not the lever:

  • Short contexts. At 1k tokens MHA's KV is only 0.84 GB per sequence and ~121 sequences fit (our arithmetic), so the weights, not KV, set the limit (params vs KV cache).
  • Batch-1, latency-first serving. KV is a small share of the bytes, so GQA only buys 1.19×. Our view: quantized weights or speculative decoding help more there (speculative sampling).
  • Quality. Sharing KV heads can cost some model quality. The book's list of tricks is explicitly "ignoring effects on quality", so check evals before assuming the gain is free (our caveat).
