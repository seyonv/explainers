Linear layers and the critical batch size

Also called Bcrit, the batch-240 rule (TPU v5e), "~300 on H100", or the point where decode turns compute-bound. This is Scaling Book Part 7, "Linear operations: what bottlenecks us?". The book's numbers are TPU v5e; H100 and Llama-3.1-8B figures are our recomputation.

In one breath

A weight matrix is read from memory once per step, however many tokens use it. So the number of tokens in the step, B, is the arithmetic intensity of a linear layer. Above Bcrit (≈ 240 on v5e, ≈ 295 on H100) the layer stops waiting on memory and starts waiting on math.

The derivation

Every linear op in a Transformer has the same shape: the MLP's Win/Wout and attention's WQ, WK, WV, WO. Each one is a bf16[B, D] × bf16[D, F] matmul. Load both arrays from HBM, multiply, and write the [B, F] result back.

What "batch" means: total tokens in the step, per replica

A matmul doesn't care which sequence a row came from. B is the number of rows in X, which is all tokens pushed through the same copy of the weights in one step.

Precision changes Bcrit (β)

With B ≪ D, F, the bytes are about DF × bytes-per-weight and the FLOPs are 2BDF, run at whatever precision the math uses. So Bcrit ≈ (Cat that precision ÷ Whbm) × bytes-per-weight ÷ 2. Narrower weights halve it. Faster, narrower math doubles the ridge. Doing both cancels out. The book writes this as β · αhbm, with α taken at bf16.

The book's takeaways

"Transformer matmuls are compute-bound iff the per-replica token batch size is greater than Bcrit … For bf16 activations on TPU v5e, this is 240 tokens. For an H100, it is about 280 tokens."
"During prefill, all matrix multiplications are basically always compute-bound." · "During generation, the total token batch size must be greater than Bcrit … this requires us to batch multiple requests together, which is hard!"

Two H100 numbers: Part 7's takeaway says "about 280"; Part 12 computes 990e12 / 3.35e12 = 295 (and says "around 280" as the GPU-family figure alongside B200's 281). This course uses 295 for H100.

Why it beats the alternatives

✗ "Just use a bigger GPU"

H100 → B200 raises FLOPs and bandwidth together: 295 → 281. Batch-1 decode stays memory-bound at well under 1% of peak on either chip. It runs faster, but it is no better used.

✗ "Batch 1 is fine"

Lowest latency per token, but the H100 does 0.12 µs of math in a 35 µs step on this matrix: 0.3%, about 1/295 of peak. You pay for a whole GPU and use a sliver of it.

✗ "Use fp8 math for more FLOPs"

Faster math on the same bytes doubles the ridge (295 → 591 on H100). It only pays off if the weights shrink too (fp8 × fp8 → back to 295). Weight-only int8/fp8 is what actually lowers Bcrit, to ≈ 148.

✓ Batch tokens up to Bcrit

Each weight byte read is reused by B tokens. From B = 1 to 325 the step only goes from 35.1 to 38.6 µs for 325× the tokens. Stop near the knee: past it, latency grows with no gain in throughput.

If Bcrit is only ~300, why is decode so hard?

Every decoding sequence needs its own KV cache. The book: "a generate batch size of 240 means 240 concurrent requests … and 240 separate KV caches". On one H100 running Llama-3.1-8B, 63.9 GB of HBM is free after weights, which is 487,823 tokens of KV at 128 KiB/token. Spread over 295 sequences, that is only ~1,652 tokens of context each. At 8k context only 59 sequences fit, so the linear layers stay memory-bound (our recomputation; see params vs KV cache and modelling LLaMA 2-13B for the book's version). Prefill has no such problem: one 1,000-token prompt already exceeds 295.

MoE raises the bar by E/k. E experts' worth of weights are read, but each token only does k experts' worth of FLOPs, so the book's Q5 (E = 16, k = 2) needs 240 × 8 = 1,920 tokens on v5e (worked problems).

When Bcrit is not the right target:

  • Latency-first serving (one interactive user, speculative decoding) deliberately runs below it and accepts idle FLOPs.
  • Attention doesn't follow this rule. Its "weights" are each sequence's own KV cache, so batching doesn't reuse them, and decode attention stays memory-bound at any B (attention's intensity).
  • Small matrices (D = F = 1024) cross much later than 295: exact ≈ 697 on H100, per the lab.
  • Real kernels reach 80–85% of peak on GPUs (book, Part 1), so the real knee is softer than the plot's corner.
