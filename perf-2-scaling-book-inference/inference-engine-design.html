Before this: The step-time formula

Designing an inference engine

Also called continuous batching (TensorRT-LLM: in-flight batching), disaggregated serving (prefill/decode disaggregation) and prefix caching. This is Scaling Book Part 7, "Designing an Effective Inference Engine", plus two sizing answers from Part 8. The book is qualitative here; the timings for Llama-3.1-8B on an H100 are our recomputation.

In one breath

Prefill and generation want different things: prefill is big and compute-bound, generation is small and batch-hungry. So good engines stop running them in lockstep. They slot requests in and out of a running decode batch (continuous batching), reuse shared prompt prefixes (prefix caching), and at scale put prefill and decode on different servers (disaggregation).

Three ways to feed prefill and generate

All three timelines share one illustrative time scale: a decode step is drawn at about 10 ms and a 1k-token prefill at about 16 ms, the ratio from the table above. Request lengths are made up.

prefill (compute-bound)decode step (memory-bound)waiting or idlestall or wasted slotfirst token

1. Batched prefill, then generate ✗

Illustrative. The book lists four problems: latency coupling (TTFT waits for the whole prefill batch, and small batches starve generate throughput); short sequences block on long ones (B and D finish and their slots idle); padded prefills waste compute on the shorter prompts; and one sharding for both phases, although "generate wants a lot more model sharding". The book recommends it only for edge serving of a single user and for the first version of a codebase.

2. Interleaved: prefill at batch 1, generation batched ✗ for chat

Illustrative. TTFT is good and no padding is needed. The orchestrator "can be configured to prioritise prefill the moment any generation slots open up", so throughput stays high, which is why the book calls it "very powerful for bulk generation applications like evaluations". But while the GPU prefills user B, user A's decoding stops: "the token generation will be jittery and slow on average".

3. Disaggregated: separate prefill and generate servers ✓ at scale

Illustrative. Prefill servers build each KV cache (and the first token) and send it over the network. Generate servers slot it into their batch. The book's advantages: low latency at scale, since a request never blocks on another user's; independent scaling of prefill and generate server counts; and specialised sharding per phase. The prefill server also holds only the one KV cache it is building, which frees HBM for prefix caching. The cost: shipping the KV cache, "another motivation for reducing KV cache size".

"For latency-sensitive, high-throughput serving, we typically have to separate prefill and generation into separate servers, with prefill operating at batch 1 and generation batching many concurrent requests together." (Part 7 takeaway)

Continuous batching: refill a slot the step after it frees

Illustrative. Four decode slots. When a sequence ends, the next queued request's prefill result goes into that slot, and the batch never waits for its longest member. This fixes problem 2 above.

The book's recipe compiles two functions and wraps them in an orchestrator:

  • prefill: handles variable context lengths and inserts its result into a KV buffer that has a maximum batch size and context length (or number of pages).
  • generate: takes the KV cache and runs one generation step for every active request.
  • orchestrator: queues incoming requests, calls prefill and generate based on the free slots, handles history (prefix) caching, and streams tokens out.

JetStream, Google's open-source version, has a prefill thread, a generate thread and a transfer thread that copies KV caches from prefill slices to generate slices. Any model plugs in by implementing the Engine interface:

prefill(tokens) -> KV cache (+ first token) insert(kv, decode_state) -> puts that KV cache into a slot of the running batch generate(decode_state) -> one token per slot; appends one token's KV to each

Prefix caching: don't prefill what you already have

request 1
Ilikedogsall 3 prefilled, KV cached
request 2
Ilikecatsfirst 2 reused: 1/3 of the compute

Because the model is autoregressive, a token's KV depends only on the tokens before it. The book lists the wins: chatbots, where each turn strictly appends and so only the newest tokens need prefill, and few-shot prompts and system instructions, which are reused "for free". The caches live in a trie, with LRU eviction:

Why it beats the alternatives

✗ Batched prefill + generate

Simple, but TTFT waits for the whole batch, finished slots sit idle, and short prompts are padded. In the lab at 8 req/s it can't keep up: 7.3 s mean TTFT and 1,603 tok/s.

✗ Interleaved on one server

Great TTFT and throughput, but every prefill freezes the batch: a 1k prompt costs 1.6 decode steps and an 8k prompt 13.4. That gives a P99 gap of 63.8 ms and a worst of 257 ms. Jittery streaming.

✗ Prefix cache per replica, no routing

Each replica only has the history it happened to serve, so random routing reuses 55.9% of prompt tokens in the lab's chats, against 80.4% with affinity routing.

✓ Continuous batching + prefix caching (+ disaggregation at scale)

Slots refill every step, repeated prefixes skip prefill, and at scale prefill moves to its own right-sized fleet (P ≈ 3G in the book's example) so decode never stalls.

Is disaggregation always the answer?

No: it needs scale and prefill-heavy traffic. Kiely's Inference Engineering (p. 149) says to reach for it only when (1) you serve "one hundred million to one billion tokens per day depending on model size", (2) the model has "at least a hundred billion parameters", and (3) traffic is "prefill-heavy with long input sequences". Otherwise "you're likely wasting money on extra hardware", or you're better off adding replicas. The lab shows the small-scale cost: same tokens, half the per-GPU throughput. Kiely also describes conditional disaggregation, where short or already-cached prompts are prefilled locally on the decode engine.

The other common fix for the interleaving stall is chunked prefill (Sarathi-Serve). It splits a long prompt into chunks that ride along with decode steps, so no single step freezes for 133 ms. It is covered in perf-5 (inference engines), not yet written.

Batched prefill still has uses: the book keeps it for edge devices serving one user, and for the first version of a codebase. And interleaving is the right choice for offline bulk generation, where nobody watches the stream.

What the book doesn't give: any latency or throughput numbers for these designs. Every timing on this card is our ideal-floor recomputation or a synthetic simulation. Real engines add kernel overheads, scheduling and attention cost.
