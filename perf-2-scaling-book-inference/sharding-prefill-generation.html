Sharding prefill vs generation

Also called tensor parallelism for inference, model parallelism, or "why not FSDP at inference". This is Scaling Book Part 7, "Distributing Inference Over Multiple Accelerators": the Prefill and Generation subsections. The book's numbers are TPU v5e; the 8×H100 and Llama-3.1-8B figures are our recomputation.

In one breath

Prefill is big matmuls, so it shards like training. Generation runs small batches that are bound by loading weights, so you split the weights across chips (model parallelism) and move only small activations. You can shard further than training would allow, because each chip now loads fewer weight bytes.

The four ways to split a model, in plain words

Think of a kitchen with four cooks. You can split the recipe (each cook does part of every dish), split the orders (each cook makes whole dishes), keep one shared cookbook that gets passed around, or split one very long order into courses. Those are, in order, the four strategies below.

ICI is the TPU's chip-to-chip link. On an H100 node the equivalent is NVLink: 450 GB/s per GPU in theory, "difficult in practice to exceed 370 GB/s" (book Part 12).

How model parallelism splits an MLP

Megatron's trick: cut the first matrix by columns and the second by rows, using the same slice of hidden units on each chip. Each chip then computes a full-size but partial output, and one sum across chips (an all-reduce) finishes the layer. The weights never move.

The activation between the matrices (h = act(X·Win)) is elementwise, so each chip can apply it to its own columns without talking. For Llama's SwiGLU, Wgate and Wup are both split by the same columns. Checked in labs/sharding-prefill-generation.py part (a): 4 simulated devices, sum of partials vs unsharded, max difference 2.22e-15. Skip the sum and device 0 alone is off by 1.84. Attention is split the same way: WQ by heads (columns) and WO by heads (rows), so a Megatron layer costs two all-reduces, one after attention and one after the MLP. (Megatron-LM §3.)

Prefill: shard it like training

"From a roofline standpoint, prefill is almost identical to training and almost all the same techniques and tradeoffs apply — model (Megatron) parallelism, sequence sharding (for sufficiently long context), pipelining, even FSDP are all viable! You just have to keep the KVs kicking around so you can do generation later."

The book's rule, for prefill of a single sequence (no batch dimension):

  1. Model sharding first, up to the point where chip-to-chip communication takes longer than the math. For one axis of TPU links that is about Y < F / 2200, "usually around 4-8 way". For the book's F = 16,384 that gives 7.4, and for Llama-3.1-8B's F = 14,336 it gives 6.5.
  2. Then sequence parallelism. Split the prompt's tokens across more chips. It adds some communication in attention, "typically fairly small at longer contexts", and it is overlapped with compute: collective matmuls for the Megatron part, ring attention for the attention part.

Why ~2200: to stay compute-bound, the math per chip (∝ BDF/Y ÷ FLOPs/s) must beat the activation traffic (∝ BD ÷ link bandwidth). B and D cancel, leaving Y < F · Wlink / C. The book states this in Part 5 (TPU) and Part 12 (GPU). Our check for v5e: 1.97e14 / (2 × 4.5e10 bidirectional) = 2,189. H100: 990e12 / 450e9 = 2,200 (book Part 12, "Within a node, this gives us about F / 2200").

Generation: three strategies are out

"Generation is a more complicated beast than prefill. For one thing, it is harder to get a large batch size because we need to batch many requests together. Latency targets are lower. Together, these mean we are typically more memory-bound and more sensitive to communication overhead."
  • FSDP is impossible. Decode is bound by reading weights and KV caches from HBM, and chip links are "orders of magnitudes slower than HBM". "We want to move activations rather than weights." The book adds: "Accidentally leaving it on after training is an easy and common way to have order of magnitude regressions."
  • Data parallelism is pointless. "It replicates our parameters and doesn't help us load parameters faster. You're better off spinning up multiple copies of the model instead."
  • Sequence sharding is impossible. "No sequence = no sequence sharding. Good luck sequence sharding."

That leaves model sharding. And because decode is limited by loading weights, not by math, the prefill limit of 4–8 way no longer applies: "we can actually go beyond this limit to improve latency!"

How far can generation shard?

With Y-way model sharding, each chip reads 1/Y of a D × F weight matrix. The chips must also exchange the B × D activations. Sharding more keeps helping until the exchange takes longer than the read.

D cancels, so the ratio TICI / THBM = Y · B · β / F. For the book's example: Y = 8 → 0.125, 16 → 0.25, 32 → 0.5, 64 → 1.0, 128 → 2.0 (lab part b1). The book's caveat: "This assumes we can fully shard our KV caches 64-ways which is difficult" (see sharding the KV cache). The book says β is "usually around 8" for v5e/v6e. Our check: 8.2e11 / 9e10 (4.5e10 each way) = 9.1.

Why training's limit stops applying

Training (and prefill) asks "does communication take longer than the math?". Decode asks "does it take longer than reading the weights?". At small B the math is tiny and weight reading is huge, so the second question allows far more chips. As B grows toward the critical batch size, decode becomes compute-bound too, and the prefill limit F/2200 (≈ F/α) comes back. The book's takeaway:

"Our only options during generation are variants of model parallelism. We aim to move activations instead of KV caches or parameters, which are larger. When our batch size is large, we do model parallelism up to the FLOPs-ICI bound (F / α). When our batch size is smaller, we can improve latency by model sharding more (at a modest throughput cost). When we want to model shard more ways than we have KV heads, we can shard our KVs along the batch dimension as well."

H100: the book's GPU chapter (Part 12) says TP within a node is comms-bound past "about F / 2200". For Llama-3's F ≈ 28,000 "this is about 11-way TP (or rounding down, about 8-way, which is how large a node is)". Its takeaway line quotes F / 2475 (the beyond-node figure, 990e12 / 400e9), and one worked answer uses F / 1995. They're all the same ballpark. Leaving the node drops per-GPU bandwidth several-fold, so TP almost always stays inside it. The 68.8 is 16384 / (32 · 7.44).

Attention weights: shard Q and O, maybe copy K and V

The book: "we also model shard attention WQ and WO over heads Megatron style. The KV weights are quite small, and replicating them is often cheaper than sharding beyond K-way sharding." You can't split K = 8 KV heads 16 ways without splitting a head. For Llama-3.1-8B (GQA, K = 8), WK + WV are 16.8 MB per layer against 67.1 MB for WQ + WO, which is a quarter. At 8-way TP each GPU gets exactly one KV head, so nothing needs copying (our recomputation).

Why it beats the alternatives (for generation)

✗ FSDP

Gathers weights over slow links every step. For Llama-3.1-8B on 8 H100s that is 16.06 GB × 7/8 over 450 GB/s = 31.2 ms per token, vs 4.8 ms to read it all from one GPU's own HBM.

✗ Data parallelism

Each copy still reads all 16.06 GB per step, so each user still waits 4.8 ms per token. It adds throughput, not speed, and separate replicas do that more simply.

✗ Sequence sharding

Decode has one new token per sequence, so there is no sequence dimension to cut. It's the right move for long prefill, not for decode.

✓ Model parallelism, moving activations

Each chip reads 1/Y of the weights, so the step drops from 4,794 to 599 µs at 8-way. Only a bf16[B, 4096] activation moves, twice per layer: 65 µs total at B = 32.

So should you always tensor-parallelise decode?

No. TP adds communication to every layer (64 all-reduces per step for Llama-3.1-8B), and at small batches each one pays a fixed start-up cost that our bandwidth table doesn't show. An 8B model fits comfortably on one H100 (16.06 GB of 80 GB), so the usual answer for small models is one GPU per replica and data-parallel replicas for throughput. Reach for TP when you need lower per-token latency than one GPU's bandwidth allows (4.8 ms/step floor for 8B), or when the model doesn't fit. That is the 70B+ case: ~140 GB of bf16 weights needs at least two H100s (see serving LLaMA 3-70B).

Also not always right: at large batch (near Bcrit) extra TP ways cost throughput per chip, so throughput-first serving stops at F / α. Past the node, bandwidth drops and TP turns comms-bound fast. MoE models add expert parallelism, which the book's GPU chapter generally prefers to TP.

And "FSDP at inference" is a real bug, not a straw man. The book calls leaving training's sharding on "an easy and common way to have order of magnitude regressions".
