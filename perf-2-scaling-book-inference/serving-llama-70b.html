Serving LLaMA 3-70B end to end

Also called the applied inference chapter, sizing a deployment, or "QPS per chip". This is Scaling Book Part 8, "Serving LLaMA 3-70B on TPUs", worked in full on TPU v5e. The H100 panel near the end is our recomputation, not in the book.

Worked example: the sizing sheet

The book's questions in order, each with its arithmetic. Every number is reproduced by the lab. Where the lab's exact value differs from the book's rounding, both are shown.

How big is the KV cache per token? (int8)

2 · K · H · L = 2 · 8 · 128 · 80 = 163,840 B ≈ 160 kB per token 32k-token sequence: 160e3 · 32,768 = 5.3 GB (exact bytes: 5.37 GB) batch 240 of those: 5.3e9 · 240 = 1.3 TB chips just to hold it: (70e9 + 1.3e12) / 16e9 = 85.6 → ≈ 86 TPU v5e

The book: "Note just how big this is!" 1.3 TB of KV against 70 GB of weights.

Batch 32, 8,192 context, all int8: how much memory, and what's the smallest slice?

KV = 160e3 · 8192 · 32 = 41.9e9 B params = 70e9 · 1 byte = 70e9 B total = 112 GB → 112e9 / 16e9 = 7 chips → 4x2 (tight) → 4x4 realistically

A 4x2 has no room left for overhead, so the book's answer is "a 4x4 at minimum (or … drop the batch size)".

On that 4x2 with bf16 FLOPs: step time and throughput?

B_crit with int8 weights, bf16 FLOPs ≈ 120 ≫ B = 32 → memory-bound T_step ≈ (KV + params) / (8 · W_hbm) = 112e9 / (8 · 8.2e11) = 17 ms lab, full formula: 6.39 KV + max(10.67 params, 2.84 FLOPs) = 17.06 ms throughput = 32 / 0.017 = 1,882 tok/s → 1,882 / 8 = 235 tok/s/chip ICI check (2 model axes): comms-bound only if Y > 2 · F / 2200 = 2 · 28672 / 2200 = 26 4x4: same bytes over 16 chips → 17 / 2 = 8.5 ms, per-chip throughput unchanged

Doubling the chips halves latency but leaves cost per token the same, as long as you stay memory-bound and under the ICI limit.

The minimum slice at 8k context

With a tiny batch, the only limit is fitting the parameters: ceil(70e9 · bytes per weight / 16e9), rounded up to a real topology. Whatever HBM is left holds KV caches, and the number of caches that fit is your batch size.

This is the book's table. Two quirks: 35 / 16 = 2.19, not the printed 2.81 (the 2x2 answer doesn't change), and the exact KV bytes are 327.7 / 163.8 / 81.9 kB, which still gives 43 caches. The book: "you could fit LLaMA 70B on a TPU v5e 2x2 … Except … the number of KV caches is very small. That's our batch size!" With a batch of 43 against a Bcrit of 120–240, most of the FLOPs sit idle.

Latency and cost at that batch

HBM full → every step reads a whole chip's worth of bytes: T_step = 16e9 / 8.2e11 = 19.5 ms ≈ 19 ms (the same for every slice) 512-token answer: 0.019 · 512 = 9.7 s ≈ "about 9 s" (exact 19.5 ms → 10.0 s) int4, params only (small batch): 35e9 / (4 · 8.2e11) = 10.7 ms ≈ "about 10 ms" QPS/chip = B / (T_step · 512 · N) = 43 / (0.019 · 512 · N) = 4.42 / N

The book's takeaway: decode latency is lower-bounded by the time to load all the parameters from HBM, and that bound is usually within 1.5× of reality. At big batches, KV loading dominates instead.

Now double each slice. Step time stays about 19 ms because HBM is still full, but the extra HBM goes to KV caches, so B rises from 43 to 140. The bars below use a log scale from 0.1 to 2 QPS/chip.

Sharding: how far can model parallelism go?

During generation the only real option is model (tensor) parallelism. You become ICI-bound roughly when Y > F · MY / 2200, where MY is the number of mesh axes you shard over (see sharding prefill vs generation).

bf16 on a 4x8, 2 model axes: Y = 28672 · 2 / 2200 = 26 → 16 chips fine, 32 not small batch loosens it: Y = F / (8 · B) = 28672 / (8 · 64) = 56 at B = 64 sanity check, one matmul on 32 chips at B = 64: T_ici = 2BD / W_ici = 2 · 64 · 8192 / 9e10 = 11.7 µs (book 11) T_hbm = 2DF / (Y · W_hbm) = 2 · 8192 · 28672 / (32 · 8.2e11) = 17.9 µs (book 18) T_math = 2BDF / (Y · C) = 2 · 64 · 8192 · 28672 / (32 · 1.97e14) = 4.8 µs (book 4) HBM is the largest → still bandwidth-bound → 4x8 lowers latency, not cost

Book tip: "the maximum amount of useful model parallelism depends on dff and the number of axes … usually ranges between 8 and 32". int8 and int4 fit on smaller slices with pure model parallelism. So quantization has a benefit beyond faster FLOPs: it lets you run a larger batch before communication becomes the bound.

Prefill and the end-to-end pipeline

prefill 8192 tokens, 16 v5e, 40% MFU: 2 · 70e9 · 8192 / (16 · 1.97e14 · 0.4) = 0.91 s evictions (P = 8192 prompt, G = 4096 decode, B = 32): 32 / 4096 sequences finish per step B · (P + G) / G = 32 · 12288 / 4096 = 96 tokens freed per step prefill : generate servers, P = 8192, G = 512 decode steps, 19 ms/step, B ≈ 32: P / 0.91 = 32 · G / (0.019 · 512) → P = 2.99 G ≈ 3 prefill servers per generate server

At 8k tokens prefill is "solidly compute bound", and at 0.91 s it is "actually quite a lot" next to a 19 ms decode step. That's why the book sizes disaggregated serving at about 3:1 prefill to generate (see designing an inference engine).

The book's printed code (the part that makes the curves), and the one fix the lab applies
batch_sizes = np.arange(1, 1024, 4) # in get_max_batch_size required_chips = min_topology(kv_cache_size(S * batch_sizes) + param_size) max_idx = np.where(required_chips <= num_chips)[0][-1] # an index into a step-4 array batch_sizes = np.arange(1, 512, 1)[:max_idx] # ...reused as a count kv_comms_time = kv_sizes / (num_chips * hbm_bandwidth) param_comms_time = param_size / (num_chips * hbm_bandwidth) flops_time = 2 * param_size * batch_sizes / (num_chips * flops) mlp_time = np.maximum(flops_time, param_comms_time) latency = 1000 * (mlp_time + kv_comms_time) # ms throughput = batch_sizes / (latency * num_chips) # tokens / ms / chip

Run verbatim, the code stops the 8k curve at B = 34 rather than the 137 that fit, because max_idx (34) indexes the step-4 array whose value there is 137. The lab prints both. Why it beats the alternatives

✗ Smallest slice that fits

Minimises chips, but HBM is then mostly weights and the batch is stuck at 43. Doubling the slice raises QPS/chip 1.63× (0.27 → 0.45 in bf16). "The smallest topology is not the most performant".

✗ Maximum sharding

More chips cut latency, but past Y ≈ 2F/2200 = 26 (2 axes) each step waits on ICI. You buy latency with throughput, and the useful maximum is 8–32 chips.

✗ bf16 everything

No quantization risk, but you need 4× the chips of int4 for the same 43-sequence batch. In the book's model that's 0.27 vs 1.11 QPS/chip, 4× the cost per query.

✓ Size by QPS per chip

Fit the params, then grow the slice and quantize until KV room pushes B toward Bcrit without breaking the ICI limit or the latency target. In the book's tables that's int4 on a 2x4: 1.80 QPS/chip, 6.7× bf16's minimum.

Are these the numbers you'd see in production?

No, about half. The book says so: the QPS tables ignore the forward pass's working memory ("not ridiculous with Flash Attention, but … not realistic"), so "the real numbers are likely around 1/2 of this". Perfect overlap of comms and compute is also assumed, so the ICI limit is "overly optimistic". Every number here is a roofline, a floor on latency and a ceiling on throughput.

The constants are TPU-specific, but the method transfers exactly. On GPUs, swap in 80 GB and 3.35 TB/s, use NVLink instead of ICI, and use FP8 instead of int8 (see the panel above). The steps don't change: bytes → slice → bound → sharding → QPS per chip.

When "maximise QPS per chip" is the wrong goal:

  • A hard latency target (the book's Q3: 15 ms/token for 405B) caps the batch and forces more sharding, even though cost per token goes up.
  • Quantization has a quality cost that the roofline doesn't show. int4 KV and weights need evaluating on your task, and many deployments stop at int8/FP8.
  • Long prompts move cost to prefill. At 0.91 s per 8k prefill you need about 3 prefill servers per generate server, and the generate side's QPS/chip is only half the bill.

Reveal
