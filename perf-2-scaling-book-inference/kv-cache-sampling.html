Sampling and the KV cache

Also called autoregressive decoding, KV caching, or prefill and generation. This is the opening of Scaling Book Part 7, "The Basics of Transformer Inference": how one token is sampled, why nobody runs the naive loop, and how the KV cache turns inference into two different jobs.

Prime · 2 minutes before you read

The problem: A language model emits one token at a time. Run literally, every new token re-processes the whole prefix, so generating n tokens costs O(n²) MLP work and O(n³) attention work. Without a fix, long answers get quadratically slower.

Where it fits: The first card of the chapter. It builds on perf-1's attention card (Q, K, V and GQA) and introduces the object the rest of the course keeps measuring: the KV cache, and the split of inference into prefill and generation.

In one breath

A model predicts one token at a time. If you re-run the whole prefix every step, generating is Θ(n²) in the MLPs and worse in attention. So you compute each token's keys and values once and keep them in a KV cache. That splits inference into prefill, which processes the prompt and fills the cache, and generation, which produces one token per step and reads the cache.

The loop, done naively

The book: "We put a sequence in and our favorite Transformer will spit out log p(next token | previous tokens)… We can sample from this distribution and obtain a new token. Append this token and repeat." Done literally, every step feeds the whole sequence back in:

Redrawn from the book's figure "naive-inference". The words are illustrative. Step k re-processes all the earlier tokens (red) just to add one (green). The book's caption calls this Θ(n²) overall, and its text says it's "O(n²) on the FFW and O(n³) on the attention mechanism to generate n tokens".

The loop, with a KV cache

Attention is causal: a token only ever looks back. So earlier tokens' keys and values never change once computed. The book: "we can simply write each token's key and value projections into a new data structure called a KV cache… future tokens can simply compute their qi·kj products without performing any new FLOPs on the earlier tokens."

Redrawn from the book's figure "cached-inference". Prefill runs the whole prompt in one pass and writes every prompt token's K and V. Each generation step feeds in only the newest token, attends to the cache and appends one new KV (solid green). The book calls this "an O(n) algorithm in the MLP block", and O(n²) in attention.

Two tasks in disguise

An analogy: prefill is reading the whole question at once. Generation is writing the answer one word at a time while glancing back at your notes (the cache). The book: "prefill and generation are very different beasts — Transformer inference is two tasks in disguise!"

per token: 2 · 32 · 8 · 128 · 2 = 131,072 B = 128 KiB this run: 131,072 B × 1,200 tokens = 157,286,400 B ≈ 157 MB (150 MiB) long chat: 131,072 B × 8,192 tokens ≈ 1.07 GB

The cache holds 1,199 entries when token 200 is sampled and 1,200 once it's fed back (the book's loop writes every sampled token's KV). That's small next to the 16.06 GB of weights, but it grows linearly with every token of every sequence in the batch.

What the cache saves in FLOPs

Our recomputation, not in the book (a floor that ignores attention FLOPs and overheads). FLOPs fell 183×, but time only 3.6×. Each generation step still has to stream all the weights from memory to do only 16 GFLOP of work, so it's memory-bound. That's the "different beasts" the rest of the chapter is about. *Llama-3.1-8B's 16.06 GB doesn't fit one v5e's 16 GB; the row is "as if it did", only to show the ratio holds.

Why it beats the alternatives

✗ Naive recompute

Needs no extra memory, but the work is quadratic: 219,900 token-passes instead of 1,199 here, and at 10,000 generated tokens it's 5,455× the FLOPs.

✗ Cache each layer's hidden state

Also skips re-running earlier layers, but costs D = 4,096 values per token per layer against K+V's 2·8·128 = 2,048 (2× the memory with GQA). Every step would also redo the K and V projections on all past tokens, which is O(n) work per step again.

✗ A fixed-size recurrent state (RNN / SSM)

Constant memory per sequence, but it's a different architecture you'd have to train. It compresses history, so it can't replay exact attention over the past. You can't apply it to an already-trained Transformer.

✓ KV cache

It stores exactly what future tokens need: K and V are the only per-token things attention reads later. Outputs don't change, and MLP work drops from O(n²) to O(n). Cost: 128 KiB per token for Llama-3.1-8B.

Is it free, and always used?

It trades compute for memory. 157 MB for one 1,200-token sequence sounds small, but a server holds a cache for every sequence in the batch. On an 80 GB H100, the 63.9 GB left after weights fits about 488k tokens, only ~59 sequences of 8k tokens. From here on, memory, not FLOPs, is the constraint the chapter keeps running into (see parameters vs KV cache and tricks that shrink it).

Sometimes there's nothing to cache. One-shot scoring (the book's example is multiple-choice benchmarks that score the options' log-probs) runs one forward pass with no generation loop. That's why, as the book notes, research code often skips a proper KV cache and inference paths have "a lot of low hanging fruit".

Related ideas that build on it rather than replace it: prefix (prompt) caching reuses a shared prefix's KV across requests, and sliding-window attention caps the cache at the last W tokens at some cost in long-range recall. Both still use a KV cache.

Understand and remember

  • Attention is causal → a token's K and V depend only on earlier tokens → they never change once computed → store them once (the KV cache) → each step feeds only the newest token, cutting MLP work from O(n²) to O(n) and attention from O(n³) to O(n²)
  • The cache splits inference in two → prefill processes the whole prompt in one parallel pass and fills the cache (compute-heavy) → generation adds one token per step and reads the cache (memory-heavy) → two different jobs with different bottlenecks, the chapter's theme
  • Each generation step still streams all 16.06 GB of weights to do only ~16 GFLOP of work → the step is memory-bound → cutting FLOPs 183× cuts time only 3.6× on an H100
  • KV bytes per token = 2·L·K·H·bytes (128 KiB for Llama-3.1-8B) → it grows with every token of every sequence → memory, not FLOPs, becomes the constraint (≈ 59 sequences of 8k fit in 63.9 GB)
  • detail that matters Caching hidden states instead would store D = 4,096 values per token per layer vs 2·K·H = 2,048 for GQA's K and V, and would force recomputing K, V projections on all past tokens every step → back to O(n) work per step

3 · Retrieve from memory, card closed
  1. concept Explain why caching K and V gives exactly the same tokens as the naive loop, while a fixed-size recurrent state would not.
    Check
    • future tokens only need past tokens' K and V for their q·k and p·v products, and those values never change
    • the cache stores them exactly, so attention computes the same numbers (the lab's max logit difference is 2.7e-15)
    • a recurrent or SSM state compresses history into a fixed size, so it cannot replay exact attention and needs a different trained model
  2. mechanism Trace one generation step with a KV cache: what goes into the model, what is read, what is written, and what comes out?
    Check
    • input: only the newest sampled token
    • each layer computes that token's Q, K, V; Q attends over all cached K, V plus its own
    • its K and V are appended to the cache (one new entry per layer)
    • out: logits for the next token, from which one token is sampled and fed back
  3. tradeoff The cache trades compute for memory. For a 1,200-token run it costs 157 MB; why does the card still call memory, not FLOPs, the chapter's recurring constraint?
    Check
    • a server holds one cache per sequence in the batch, and each grows with every token
    • at 8k tokens one sequence is 1.07 GB, so the 63.9 GB left after weights fits only about 59
    • the FLOPs saved are huge, but the bytes stored cap how many users share each weight read

4 · Compare against what you already know

vs Memory: parameters vs the KV cache: This card computes one sequence's cache; the memory card sets it against the weights. What is fundamentally different about the two kinds of bytes, and which one decides how many users fit?

Check
  • weights: one shared copy, fixed size, read once per step for the whole batch
  • KV: one cache per sequence, grows with context, read by that sequence only
  • weights decide whether the model fits; KV decides how many sequences fit
  • for LLaMA 2-13B, four 8k caches (26.8 GB) already outweigh the 26 GB model

vs Prefill vs decode, measured on your Mac: Your M3 measured prefill about 13× faster per token than decode. Using this card, which design choice causes that gap, and would it close or widen on an H100?

Check
  • prefill processes all prompt tokens in one pass, so each weight read feeds many tokens
  • decode processes one token per step, so each weight read feeds one token
  • the gap follows the chip's FLOPs per byte: on an H100 prefill of 1,000 tokens takes ≥ 16.2 ms (16 µs/token) vs ≥ 4.8 ms per decode token, a far wider gap
