The chapter's worked problems

Also called Scaling Book Part 7 Q1–Q7, or the practice problems. These are the seven questions at the end of Part 7, all on one invented model on TPU v5e. The book's answers are quoted and re-checked with the lab. The book gives no answer for Q4 or Q6, so ours are labelled. The Llama-3.1-8B-on-H100 versions are our recomputation.

In one breath

Seven problems that use every formula in the chapter on one invented model. Do each one yourself before you read the answer: this is the back-of-envelope fluency that interviews test.

The invented model

The book: "I'm going to invent a new model based on LLaMA-2 13B for this section." Input and output embeddings are shared. Unless a question says otherwise, everything runs on a TPU v5e 4x4 slice: 16 chips, 16 GB HBM and 8.2e11 B/s each, 3.94e14 int8 OPs/s, and ICI at 4.5e10 B/s one way.

Q1Parameters and KV cache per token

Problem

How many parameters does the model have? How large is its KV cache per token in int8? Assume the input and output projection matrices are shared.

Hint

Count by block: 3 MLP matrices of D×F, and Q, K, V, O projections with N or K heads of size H. KV per token is one K and one V vector per layer per KV head. See params vs KV cache.

Answer
P= L·D·( 3FMLP + 2H(N+K)attention )+ DVshared embedding KVtoken=2LKHbytes in int8
MLP 64 · 4096 · 3·16384 = 12,884,901,888 attn 64 · 4096 · 2·256·(32+8) = 5,368,709,120 emb 4096 · 32128 = 131,596,288 total = 18,385,207,296 ≈ 18.4e9 params KV/token = 2 · 64 · 8 · 256 = 262,144 B ≈ 262 kB (int8, 1 B per value)

The book's answer: 18.4 billion parameters, 262 kB per token. The MLP is 70% of the weights.

Q2How many 128k-token users fit?

Problem

Serve the model on a TPU v5e 4x4, with the KV cache fully sharded over the slice. What's the largest batch that fits if everything is int8 and each sequence is 128k tokens long? What if you drop to one KV head (K = 1)?

Hint

Total HBM minus weights, divided by KV bytes per sequence. See params vs KV cache.

Answer
KV per sequence = 262e3 · 128e3 = 33.5 GB (book) 262,144 · 128e3 = 33.6 GB (exact, lab) HBM = 16 chips · 16e9 = 256 GB free = 256 − 18.4 = 237.6 GB batch = 237.6 / 33.6 = 7.08 → 7 sequences K = 1: KV/token = 2·64·1·256 = 32,768 B, 4.19 GB per sequence batch = 237.6 / 4.19 = 56.6 → 56 ("8 times this")

The book's answer: 7, and about 56 with K = 1. Seven users fill a 16-chip slice, far below Bcrit = 240. Long context is a memory problem before it is a compute problem.

Q3The weight-loading floor on step time

Problem

How long does it take to load all the parameters from HBM into the MXU, assuming they are fully sharded over a v5e 4x4 in int8? The book: "This is a good lower bound on the per-step latency."

Hint

Bytes ÷ (chips × HBM bandwidth). This is the parameter term of the step-time formula; see the step-time formula.

Answer
18.4e9 bytes / (8.2e11 B/s · 16 chips) = 18.4e9 / 1.312e13 = 1.40 ms

The book's answer: about 1.4 ms (it writes 18e9 in the numerator). No decode step can be faster than this at any batch size. Q4 shows the KV reads usually cost much more.

Q4Sharding for prefill and for decode

Problem

Serve the model on a v5e 4x4 with int8 FLOPs, parameters and activations. How would you shard it for prefill, and for decode? The book's hints: what does ICI look like on a 4x4? What's the roofline bound on tensor parallelism? How can you shard the KV cache? What is the rough per-step latency for generation?

Hint

Prefill follows training rules: model-parallel up to the ICI bound, then shard the sequence. Decode is memory-bound, so it can model-shard past that bound, as long as Y < F / (B·β). See sharding prefill vs generation and sharding the KV cache.

Answer
Our solution, not the book's (the book gives no answer)

Assumptions: we treat the 4x4 as a 2D grid of 16 chips, 4 per axis, and don't count on wraparound links. We use the book's thresholds: the ICI bound for model parallelism of about F / 2200 per axis, β = Whbm / Wici ≈ 8 (this is a different β from the precision factor on the Bcrit card), and latency-bound collectives when Y > BD / 45,000.

Prefill: weights/chip = 18.4 GB / 4 = 4.60 GB (11.4 GB left per chip for activations + KV) Decode: weights/chip = 18.4 GB / 16 = 1.15 GB Decode step ≈ (weights + all KV read) / (16 · 8.2e11 = 13.12 TB/s) B = 7 at 128k (Q2's full load): (18.4 + 234.9) GB / 13.12 TB/s = 19.3 ms B = 32 at 8k context: (18.4 + 68.7) GB / 13.12 TB/s = 6.6 ms T_math (B = 7) = 2 · 18.4e9 · 7 / (16 · 3.94e14) = 40.8 µs (tiny) comms: B·D / 45,000 = 7·4096 / 45,000 = 0.64 < 16 → latency-bound 64 layers · 6 collectives · 4 hops · 1 µs ≈ 1.5 ms (illustrative counts)

Takeaway: with a full HBM, a decode step reads almost all 16 GB on every chip, so it can't beat 16e9 / 8.2e11 = 19.5 ms. At 128k context, KV reads, not weights, set the latency. Comms are small but not free, since each hop costs about 1 µs whatever the data size (Appendix C).

Q5The same model as an MoE (E = 16, k = 2)

Problem

Make each FFW block into E = 16 copies. Each token passes through k = 2 of them, and their outputs are averaged. How many total and activated parameters does the model have? What batch size makes it FLOPs-bound on v5e? How large is the KV cache per token? How many FLOPs does a forward pass over T tokens take?

Hint

Only the MLP term scales, by E for total and k for active. Bytes scale with E and FLOPs with k, so Bcrit scales by E/k. See the critical batch size.

Answer
total = 64·4096·(3·16·16384 + 2·256·40) + 4096·32128 = 211.7e9 ≈ 212e9 (11.5× dense, "about 12x") active = 64·4096·(3·2·16384 + 2·256·40) + 4096·32128 = 31.27e9 ≈ 31.2e9 (1.7× dense) B_crit = 240 · E/k = 240 · 16/2 = 1,920 tokens KV/token = 262 kB, unchanged (attention untouched) FLOPs = 2 · active · T = 2 · 31.2e9 · T ≈ 62.5e9 · T

The book's answers: 212e9 total, 31.2e9 active, 1,920 tokens, KV unchanged, 2 · 31.2e9 · T. (Our 31.27e9 rounds to 31.3; the book truncates.) Part 4 Q8 asks the same for DeepSeek's 256 routed experts with k = 8, using int8 weights (Bcrit 120): 120 · 256/8 = 3,840.

Q6Expert sharding on an 8x16

Problem

With MoEs you can shard the experts over one mesh axis. The first FFW weight has shape [E, D, F], sharded as [EZ, DX, FY]. X is only the FSDP axis during training, so it is unused here. On a v5e 8x16 slice with Y = 8 and Z = 16, what is the HBM weight-loading time, and how much HBM is free per chip? What is the smallest slice the model fits on?

Hint

Chips = Y·Z = 128. Divide the Q5 total (int8 bytes) by the chips each tensor is split over, then by 8.2e11 B/s. See sharding prefill vs generation and MoE.

Answer
Our solution, not the book's (the book gives no answer)

Assumptions: int8 weights (1 byte each). Expert weights split 16 ways over E and 8 over F, so each chip holds one expert's 1/8. For attention and embeddings, which the question doesn't specify, we show two cases.

split: experts 206.2e9 · attention 5.37e9 · embedding 0.13e9 (a) everything 128-way: 211.7e9 / 128 = 1.65 GB/chip load = 1.65e9 / 8.2e11 = 2.02 ms free = 16 − 1.65 = 14.35 GB/chip (7.0M tokens of KV in total) (b) experts 128-way, attn+emb only Y = 8-way: 206.2e9/128 + 5.50e9/8 = 2.30 GB/chip load = 2.80 ms free = 13.70 GB/chip smallest slice: 211.7 GB / 16 GB = 13.2 chips → 16 chips (a 4x4) 13.2 GB of weights per chip; 44 GB left in total = 169k tokens of KV

The load time barely depends on batch. Even when few experts are hit, the step waits for the busiest chip, and that chip reads its whole 1/128 slice (our reasoning). A 4x4 does hold the model, but its 169k KV tokens can't come close to the 1,920 concurrent tokens that Bcrit asks for. It fits, but it stays memory-bound.

Q72D weight-stationary sharding

Problem

The ESTI paper's 2D weight-stationary scheme shards the weights over both D (axis X) and F (axes YZ), so each chunk is roughly square: AllGatherYZ the input, matmul, AllReduceX, matmul, ReduceScatterYZ. Work out Tmath and Tcomms. When does it beat ordinary 1D model sharding?

Hint

Each collective costs bytes ÷ (axis size · Wici), and an AllReduce costs twice as much. Minimise over X with XYZ = N fixed. Covered briefly in Appendix B; see sharding the KV cache.

Answer
T2D comms= 2BDX·Wicigather + scatter over YZ + 4BFYZ·WiciAllReduce over X T2D commsF = 4D, X = √(N/8), YZ = √(8N) = 128BDN·Wici ≈11.3BDN·Wici 4BD3Wici1D model parallel > 128BDNWici ⇔ N>128(34)2= 72chips

T_math = 4BDF / (N·C), fully sharded, unchanged. Minimise 2/X + 16X/N over X: X² = N/8. Then both terms equal 2·√(8/N); total = √(128/N) · BD/W. The book's answer: 2D wins when N > 72, and the general condition is N > 32·(F/D)·(3/4)². The book's point is that total comms keep falling as √N grows, so more chips and bigger batches keep lowering latency, even past the ~20-way tensor-parallel limit that 1D hits. The book's own 3-term sum writes each gather/scatter as 2BD/(2X·W); we follow its simplified total.

The four formulas you need most

Parameter count

L·D·(3F + 2H(N+K)) + D·V

Sets the weight bytes, and so the Q3 floor on every step. For MoE, put E in front of F for the total and k for the active count.

Bcrit for MoE

B_crit · E/k

MoE reads E experts' bytes for k experts' FLOPs, so you need 8× the batch for E/k = 8: 1,920 tokens on v5e, 2,360 on H100.

2D comms

2BD/(X·W) + 4BF/(YZ·W)

Falls as 1/√N, so it beats 1D's 4BD/(3W) above 72 chips. It matters only for very large slices.

✓ KV per token

2·L·K·H · bytes

This decides how many users fit (Q2: 7 vs 56 with K = 1) and what a decode step costs at long context (Q4: 235 GB of KV vs 18 GB of weights).

Which of these come up in practice?

Our view, not the book's: Q2 ("how many users of this context length fit on this box?") and Q5 ("how much batch does this MoE need before it stops wasting FLOPs?") are everyday questions at an inference company. Q3 and Q4's step-time estimates come up whenever someone sets a latency target. Q1 is the arithmetic under all of them.

Where these answers mislead:

  • They are bounds, not measurements. Q3's 1.4 ms assumes 100% of HBM bandwidth. Real kernels get less, and Q2's "7" leaves no room for activations or fragmentation.
  • Q7 rarely matters at serving scale. Below 72 chips, including the 4x4 and any 8-GPU H100 node, plain 1D model sharding has less comms. In our view most serving deployments stay in that range.
  • GPUs don't shard this way. On an H100 node, NVLink is all-to-all, not a 2D grid, so Q4's "one axis vs both axes" question becomes "TP = 2, 4 or 8" (see serving LLaMA 3-70B).
  • Our Q4 and Q6 are one reasonable answer each. Other shardings are defensible, for example 16-way model parallelism for prefill (right at the 2-axis bound of 14.9), or replicating attention in Q6.
