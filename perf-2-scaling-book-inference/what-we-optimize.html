Before this: Serving metrics (perf-1)

What we optimize: TTFT, per-token latency, throughput

Also called latency vs throughput, the Pareto frontier of serving, or offline vs online inference. Scaling Book Part 7, "What do we actually want to optimize?" and "A more granular view of the Transformer": the three regimes, the three metrics, and the three kinds of operation the rest of the chapter analyses.

Prime · 2 minutes before you read

The problem: Training has one goal: tokens per second per chip. Serving has three that pull against each other (throughput, time to first token, per-token latency), and optimising the wrong one wastes chips or loses users. Without a clear objective, every later trick is a solution looking for a problem.

Where it fits: Second card. It builds on perf-1's serving metrics and the prefill/generation split from the KV cache card, then names the three regimes and the three kinds of operation the rest of the chapter analyses one at a time.

In one breath

Training only cares about throughput (tokens processed per second per chip). Inference adds latency: how long until the first token appears (TTFT) and how long each following token takes. Which of the three matters most depends on the regime: offline batch jobs only care about cost, chat has to be cheap and fast enough to read, and edge inference serves one user as fast as the hardware allows.

The trade-off between latency and throughput

Qualitative shape only, not to scale. A bigger batch moves you right and up: more total tokens per second, slower for each user. The curve flattens once the chip is compute-bound. The book doesn't draw this figure; it's our sketch of the trade-off it describes. The real curve, computed, is in the step-time formula.

The book's summary: maximising hardware utilisation "is still critical and helps with cost and TTFT, but unlike training, it does not necessarily translate to better experience for individual users". Many optimisations "make tradeoffs between latency, throughput, context length and even model quality".

Where the batch-1 point sits depends on the hardware (Llama-3.1-8B BF16, bandwidth ÷ weight bytes):

A more granular view: three kinds of operation

For inference, "a stack of feedforward blocks" isn't detailed enough. The book splits every forward pass into three kinds of operation, then asks for each one whether prefill and generation are compute-bound or memory-bound. Here's one decode step (batch 1) through one Llama-3.1-8B layer, at a short and a long context S:

Linear ops dominate at batch 1, but attention's share grows with context, and its bytes (the KV cache) aren't shared across a batch. That's why the next cards treat them separately: linear ops, then attention.

How it differs from related ideas

✗ Training metrics (throughput, MFU)

These are all training needs. In inference, maximising MFU with huge batches lowers cost but can make every user wait longer per token.

✗ One latency number (TTFT or TPOT)

TTFT is set by prefill, per-token latency by decode, and they trade off differently. Chat needs both, and an agent's tool call cares about total response time instead.

✗ Cost per token alone

This is right for offline batch, but it pushes the batch size up until chat users see tokens slower than they can read.

✓ The regime decides the objective

First decide offline, chat or edge. Then optimise cost subject to that regime's latency limits (none, readable speed with low TTFT, or the lowest possible).

Is lower latency always better?

No. For offline batch inference (evals, data generation, corpus preparation), latency per sample is irrelevant and cost dominates. Running at a small batch to shave latency just wastes chips. Kiely makes the same point: offline jobs are "better served by high-throughput model deployments where each individual request would be too slow for a good user experience".

Interactive products pay for latency with a lower batch size, which means fewer users per chip and a higher cost per token. Beyond reading speed, faster streaming buys little for a human reader (our inference; the book only sets "exceed human reading speed" as the bar). It does still matter when the tokens feed a machine, such as an agent's next call. Kiely even recommends two deployments of the same model, one tuned for latency and one for throughput, when both workloads have volume.

Understand and remember

  • Throughput sets cost per token; TTFT is set by queueing plus prefill; per-token latency is one decode step → a bigger batch raises throughput but slows every user's step → the regime decides which constraint binds
  • Offline jobs are blind to per-sample latency → pack the batch until memory runs out; chat must beat reading speed (≈ 5.2 tokens/s ≈ 194 ms/token) with low TTFT → batch as far as that budget allows; edge serves one user → batch 1, fit the model, quantize
  • Linear ops' FLOPs and weight bytes don't depend on context, while attention's FLOPs and KV bytes grow with S → at batch 1 linear ops are 96.2% of a layer's FLOPs at S = 1,024 but only 76.3% at 8,192 → and KV bytes aren't shared across a batch → so the chapter treats linear ops and attention separately
  • detail that matters The batch-1 ceiling is bandwidth ÷ weight bytes (209 tok/s for Llama-3.1-8B on H100) → it is about 40× reading speed → that headroom is what a chat service spends on batching other users

Why this step?

5 · Predict commit to an answer before revealing

Push the per-layer FLOP split to a 32,768-token context at batch 1 (Llama-3.1-8B). Commit: is attention now under or over half of a layer's FLOPs?

Reveal

Over half. Attention matmuls are 4 × 32 × 128 × 32,768 = 536.9 MFLOP plus about 5.2 MFLOP of softmax, 542.1 MFLOP against a fixed 436.2 MFLOP of linear ops: about 55%. Linear ops don't change with context; attention grows linearly with it. And the bytes tell the same story harder: that layer reads 134 MB of KV against 436 MB of weights, a share that grows with every sequence in the batch.
