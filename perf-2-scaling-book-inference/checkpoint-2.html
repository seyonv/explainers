Checkpoint 2: memory decides the batch

Ties together parameters vs the KV cache, modelling LLaMA 2-13B and tricks that shrink the KV cache, with attention's intensity and the step-time formula behind them: why KV bytes per sequence, not FLOPs, set how many users fit and how many tokens per second a chip can sell.

1 · Mixed retrieval

  1. which concept?A product serving Llama-3.1-8B on one H100 at 8k context fits 59 users. Product wants 128k context for the same GPU. What happens to the user count, and which bytes now dominate a decode step?
    Check
    • one 128k sequence holds 17.2 GB of KV, more than the 16.06 GB of weights
    • only 3 sequences fit in the 63.9 GB left
    • KV bytes dominate every step: KV per sequence, not the weights or the math, now caps both users and speed

    Missed it? Reopen parameters vs the KV cache, "Is KV always the bigger problem?" and its try-this.

  2. Rebuild the book's 6.7 GB: LLaMA 2-13B (L = 40, K = 40, H = 128), one 8,192-token sequence in bf16. How many such caches outweigh its 26 GB of weights?
    Check
    • 2 × 2 bytes × 128 × 40 × 40 × 8,192 = 6,710,886,400 B ≈ 6.71 GB (800 KiB per token)
    • 26.03 / 6.71 = 3.88, so four caches (26.8 GB) outweigh the model

    Missed it? Reopen parameters vs the KV cache, step 3.

  3. In the book's MHA table, batch 16 → 240 (15× the sequences) buys only 1.22× the throughput. What sets the ceiling, what is its value, and what is the only lever that raises it?
    Check
    • throughput = B·W / (B·KV + P) → W / KVseq as B grows
    • 6.56e12 / 6.7e9 ≈ 979 tok/s on the 8 chips; batch 16 already gives 788
    • only fewer KV bytes per sequence raise it: 5× smaller KV → ceiling 4,896

    Missed it? Reopen modelling LLaMA 2-13B, "What the tables teach", point 1.

  4. which concept?In the H100 ladder, a model that shares each KV cache between adjacent layers stores half as many bytes, yet one variant gets 28.0× the MHA throughput and another only 15.6×. Which idea separates them, and which one would you ask the kernel team to build?
    Check
    • storage vs reads: both variants store 18.5 KiB per token, so both fit 412 sequences
    • if every layer re-reads the shared cache, bytes read per step don't halve: 144 GB per step, 43.0 ms, 9,589 tok/s
    • build the kernel that reads each shared cache once: ≈ 23.9 ms and 17,253 tok/s

    Missed it? Reopen tricks that shrink the KV cache, the ladder's re-read row and "Cross-layer sharing".

  5. With HBM full, why does the H100 step stay near 23.9 ms whether the KV is 128 KiB or 18.5 KiB per token, and what does that make throughput proportional to?
    Check
    • the batch grows until weights plus KV fill ≈ 80 GB, so each step reads ≈ 80 GB
    • 80 GB ÷ 3.35 TB/s ≈ 23.9 ms, whatever the trick
    • throughput = sequences that fit ÷ 23.9 ms, which is ∝ 1 / KV bytes per token (while decode stays memory-bound)

    Missed it? Reopen tricks that shrink the KV cache, "Why KV bytes per token set the throughput".

  6. which concept?A finance lead proposes serving LLaMA 2-13B (MHA) on 64 chips instead of 8 to cut cost per token. Which idea predicts the result, and what number backs it?
    Check
    • cost per token ∝ 1 / tokens per second per chip
    • more chips add HBM and cut latency, but per-chip throughput hits a wall of 0.82e12 / 6.7e9 ≈ 122 tok/s
    • the card's check: 8 → 64 chips moves MHA from 97 to only 119 tok/s per chip, so cost barely falls

    Missed it? Reopen modelling LLaMA 2-13B, "Just add chips" and the per-chip paragraph.

  7. Training LLaMA 2-13B needs roughly 100 GB for parameters plus optimizer state and several TB of checkpointed activations. Serving it needs 26 GB plus KV. Name each thing that disappears, and the one thing that appears.
    Check
    • gone: fp32 optimizer state (Adam moments), gradients, and activations kept for a backward pass (≈ 80 MB remain for an 8k prefill)
    • appears: the KV cache, one per sequence, growing with every token

    Missed it? Reopen parameters vs the KV cache, step 2.

  8. A 4k sliding window saves little on Llama-shaped layers at 8k context but a lot at 128k. Why, and who would have to make that change?
    Check
    • a local layer keeps only the last W tokens; at 8k it keeps half, at 128k about 3%
    • the local-layer rung is 13.8× smaller KV than MHA at 8k but 43.8× at 128k
    • it's an architecture choice made at training time; a server can't add it to an existing model

    Missed it? Reopen tricks that shrink the KV cache, the ladder and "Can a serving team just turn all of these on?".

3 · Project: an HBM budget for a mixed workload

What it reinforces: the fit count (parameters vs KV), the throughput ceiling and why the step stays fixed when HBM is full (modelling 13B, KV tricks), the per-sequence KV read (attention's intensity) and the step formula (step time).

Llama-3.1-8B in bf16 on one H100 (80 GB, 3.35 TB/s, 63.94 GB free after weights, 131,072 B of KV per token). Requests come in a repeating mix of four lengths: 1,200, 3,000, 6,500 and 8,192 tokens of context (the illustrative mix from the KV tricks card). Write a short script that, for each configuration below, prints KV per request, the number of requests that fit, the step time (weights + KV actually read) and tokens/s:

  1. Padded 8k slots, bf16 KV. Every request reserves and reads 8,192 tokens.
  2. Padded slots with ragged reads. Same reservation, but each step reads only real tokens.
  3. Paged, bf16 KV. Each request stores only its real tokens (use the mix's average length).
  4. Paged, fp8 KV. As 3, with half the bytes per token.
  5. Check the bound. For the largest batch, compare 2·B·N/C with the weight read. Is decode still memory-bound?
  6. Decide. Which of these can a serving team switch on today for this model, and which gain came from changing reads rather than fits?
Done when: you have four rows (requests, step, tokens/s), a memory-bound check for the largest batch, and one sentence each on what ragged reads fix that paging doesn't, and vice versa. Then compare with the check.
Check: the numbers (computed with the cards' formulas)
  • Average request: (1,200 + 3,000 + 6,500 + 8,192) / 4 = 4,723 tokens.
  • Padded, bf16: 1.07 GB per slot → 59 requests, step 23.7 ms, ≈ 2,489 tok/s.
  • Padded + ragged reads: still 59 requests (the memory stays reserved), but each step reads only 59 × 0.62 GB + 16.06 GB → 15.7 ms, ≈ 3,759 tok/s. Reads fell; fits didn't.
  • Paged, bf16: 0.62 GB per request → 103 requests, step 23.8 ms, ≈ 4,323 tok/s. Fits rose.
  • Paged, fp8: 0.31 GB per request → 206 requests, step 23.8 ms, ≈ 8,645 tok/s. Math at B = 206 is 3.35 ms, under the 4.79 ms weight read: still memory-bound.
  • All four are serving-side choices; GQA is already built into this model, and local layers or sharing would need retraining.
