Before this: Compute-bound or memory-bound? (perf-1)

The roofline, properly

Also called roofline analysis, arithmetic intensity (ops:byte), or "communication vs computation bound". This is Scaling Book Part 1, which Part 7 (inference) relies on for every "is it memory-bound?" answer. The book's numbers are TPU v5e; H100 is shown alongside.

In one breath

Every operation takes at least max(Tmath, Tcomms) and at most their sum. Which one wins depends on the op's FLOPs per byte compared with the hardware's FLOPs per byte.

Three times, two bounds

T_mathFLOPs ÷ peak FLOP/sv5e 1.97e14 · H100 9.89e14 T_commsbytes ÷ bandwidth: HBM↔cores inside a chip, or chip↔chip (ICI, DCN, PCIe)v5e 8.2e11 · H100 3.35e12 B/s T_lowerif compute and data movement overlap perfectlywhat the book optimizes T_upperif nothing overlapsat most 2× the lower bound

The book optimizes against the max "as the algebra is simpler and we can usually come close to this bound by overlapping". Overlap regions and overheads are then modelled from profiles.

When Tmath > Tcomms the op is compute-bound and the chip is fully used. When Tcomms > Tmath it is communication-bound; the book uses comms-, memory- and bandwidth-bound interchangeably. Some FLOP/s are then wasted waiting. Dividing both sides by bytes turns this into one comparison:

On NVIDIA spec sheets the headline tensor FLOPs assume structured sparsity. The dense value is half that (Q5), so 1.979e15 "bf16" becomes 9.89e14.

Worked example 1: the dot product never gets there

x · y: bf16[N], bf16[N] → bf16[1]. Load both vectors (2N bytes each), do N multiplies and N−1 adds, write 2 bytes.

Intensity(dot)= N+N−12N+2N+2 = 2N−14N+2 →12
N = 1 (2·1−1)/(4·1+2) = 0.1667 FLOPs/byte N = 10 19/42 = 0.4524 N = 1,000 1999/4002 = 0.4995 N = 10^6 = 0.5000 ≪ 240 → bandwidth-bound, at any N

The book adds that a dot product really runs on the TPU's VPU (vector unit), not the MXU. The v5p VPU's critical intensity is about 3, so the op is "still somewhat comms-bound". Intensity that is low and constant is hard to make compute-bound on any hardware.

Worked example 2: matmul, where intensity grows with batch

X bf16[B, D] · Y bf16[D, F] → Z bf16[B, F]. Load 2BD + 2DF bytes, do 2BDF FLOPs, write 2BF bytes. Strictly it is BF(2D−1) FLOPs; the output is fp32 inside the chip and cast to bf16 before it is written.

Intensity(matmul)= 2BDF2BD+2DF+2BF = BDFBD+DF+BF ≈B ≪ D, F BDFDF=B B>1.97e148.20e11=240 (TPU v5e) B>9.89e143.35e12=295 (H100)

The weights (the DF term) are loaded once, however many rows B you push through them, so each extra token adds FLOPs almost for free. B here means tokens per replica, not sequences. It is tokens in the step, from any mix of sequences, per independent copy of the weights. Sharding one matmul over more chips scales FLOP/s and bandwidth together, so it doesn't move the threshold. The book's example: 512 sequences × 4,096 tokens on 2,048 GPUs is a 2M-token global batch but a 1k-token local batch.

From labs/roofline.py. At B = 1 the time is almost entirely spent reading the 33.5 MB weight matrix. That is decode's problem in one row. B = 240 is still memory-bound here because D = F = 4096 isn't much bigger than B: the exact crossover is B ≈ 272 on v5e and ≈ 345 on H100 (our recomputation, exact bytes). "B > 240" is the B ≪ D, F approximation, and it gets tighter as D and F grow. For Llama-3.1-8B's MLP (D = 4096, F = 14336) the exact values are ≈ 260 and ≈ 325.

Here the same regions are filled in with our recomputed H100/H200 numbers (from labs/roofline.py). Red: bandwidth-bound at both bandwidths. Yellow: bandwidth-bound only at the lower one (BW1). Green: compute-bound at both, where more bandwidth or intensity no longer helps. The matmul at B = 240 sits in the yellow strip: 720 TFLOP/s on H100, full peak on H200. There are two ways to go faster: raise intensity (move right) or raise bandwidth (BW1 → BW2).

Across chips the threshold moves to D

Split X[B, D]·Y[D, F] along D over 2 TPUs. Each chip does half the matmul, then they swap bf16 partial sums of shape [B, F] over ICI at 4.5e10 B/s each way.

T_math = 2BDF / (2 · 1.97e14) = BDF / 1.97e14 T_comms = 2BF / 4.5e10 intensity = BDF / 2BF = D/2 > 1.97e14 / 4.5e10 = 4,378 → D > 8,755

B cancels, so the threshold is on D, not B. Both the FLOPs and the bytes sent grow with B. The book calls most of the rooflines that matter in the rest of the book network rooflines like this one. Llama-3.1-8B's D = 4096 is below 8,755, so this split would be comms-bound on v5e ICI (our reading).

Why it beats the alternatives

✗ FLOP-only estimate

Time = FLOPs ÷ peak. It says a batch-1 matmul on H100 takes 0.03 µs; the bytes say 10 µs, about 300× longer. It is wrong for all of decode.

✗ Bytes-only estimate

Time = bytes ÷ bandwidth. It is right at batch 1, but at B = 1024 it gives 61 µs on v5e when the math needs 174 µs. It misses the point where batching stops being free.

✗ Profile only

Tells you what happened on one config, not why, or what changes if you double the batch, quantize, or shard. You have to rerun it for every what-if.

✓ Roofline bounds

Two divisions and a max give the right answer in both regimes, with a guaranteed 2× bracket. One comparison (intensity vs 240 or 295) says which knob to turn.

Is the roofline the whole story?

No. It is a bracket, not a prediction. Real kernels overlap compute and data movement imperfectly, and the peak itself isn't reachable. The book says H100s and B200s "can usually only achieve around 80–85% of the claimed peak FLOPs, while TPUs can get closer to 95%". It adds that tiling (breaking a big matmul into VMEM/SMEM tiles) reloads chunks, so the real intensity is closer to bm·bn/(bm+bn) for tile sizes bm, bn.

It stops being the right tool when:

  • ops are tiny. Microsecond ops are dominated by fixed latency and kernel-launch overhead, which neither FLOPs nor bytes capture. This is our inference; the book doesn't discuss launch overhead here.
  • collectives are small. Inter-chip transfers of a few KB are latency-bound, not bandwidth-bound; see the book's Appendix C on sharding the KV cache.
  • the op isn't on the matrix unit. Elementwise work runs on the VPU or CUDA cores, which have a different peak, so the ridge isn't 240 or 295.
  • it's capacity, not speed. The third roofline constraint is total memory. Whether weights plus KV cache fit is a separate question (params vs KV).
