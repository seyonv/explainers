Batched matmul and FlattenConsecutive

Also called: batch dimensions in @, grouping consecutive embeddings, a hierarchical flatten. Lecture 6 · implementing WaveNet · 0:21:36

Prime · 2 minutes before you read

The problem: The flat model reads all 8 characters as one row of 80 numbers and squashes them in a single layer. To fuse context slowly, two neighbours at a time, you need a layer that works on pairs, with the same weights for every pair, without writing a loop.

Where it fits: The tree-idea card drew the picture; this card turns it into code. It builds on Flatten and Sequential from the containers card and on view from the MLP lecture.

In one breath: matrix multiply (@) only multiplies along the last dimension of its left input; every dimension in front of that just comes along as extra batch. So instead of flattening all 8 character embeddings into one long row, you view them as 4 pairs and let one Linear layer process all 4 pairs at once. Do that three times and you have WaveNet's tree.

Predict first: a Linear layer's weight is (80, 200): it expects rows of 80 numbers. You hand it a tensor of shape (4, 5, 80) instead of (4, 80). Error, or some shape?

(4, 5, 200), no error. @ treats (4, 5) as a batch of 4 × 5 = 20 rows, multiplies each row of 80 by the same (80, 200) weight, and puts the 20 results back in a (4, 5) arrangement. This is the check Karpathy runs before building anything.

Only the last dimension gets multiplied

Notation: B is the batch size (4 here, so the shapes are easy to read), T is the number of positions (characters of context), and C is the number of channels, the length of the vector at each position (10 for a character embedding). A view reinterprets the same numbers under a new shape without copying them.

The last row is the one the tree needs: 4 examples × 4 pairs, each pair a row of 20 numbers, all pushed through one (20, 200) weight.

Grouping pairs is a free view

After the embedding, each example is 8 vectors of 10 numbers, stored one after another: 80 numbers in a row. The old Flatten read them as one row of 80. Read the same 80 numbers as 4 rows of 20 instead and each row is two neighbouring characters side by side:

memory of one example: c0 c1 c2 c3 c4 c5 c6 c7 (each cN = 10 numbers) view(4, 80) -> 1 row : [c0 c1 c2 c3 c4 c5 c6 c7] Flatten view(4, 4, 20) -> 4 rows: [c0 c1] [c2 c3] [c4 c5] [c6 c7] FlattenConsecutive(2)

The lab checks that this view equals gluing the even and odd positions together explicitly, torch.cat([e[:, ::2, :], e[:, 1::2, :]], dim=2): True. The view just doesn't copy anything. Repeat the trick on the hidden layer, (4, 4, 200) → (4, 2, 400), and again, (4, 2, 200) → (4, 1, 400), and you get the tree below. When only one group is left, FlattenConsecutive squeezes that middle dimension away so the last layers see a plain (4, 400).

class FlattenConsecutive:
    def __init__(self, n):
        self.n = n                  # how many neighbours to fuse
    def __call__(self, x):
        B, T, C = x.shape
        x = x.view(B, T//self.n, C*self.n)
        if x.shape[1] == 1:        # one group left: drop the dim
            x = x.squeeze(1)
        self.out = x
        return self.out
    def parameters(self):
        return []
model = Sequential([Embedding(vocab_size, n_embd),
  FlattenConsecutive(2), Linear(n_embd*2, n_hidden, bias=False),
  BatchNorm1d(n_hidden), Tanh(),
  FlattenConsecutive(2), Linear(n_hidden*2, n_hidden, bias=False),
  BatchNorm1d(n_hidden), Tanh(),
  FlattenConsecutive(2), Linear(n_hidden*2, n_hidden, bias=False),
  BatchNorm1d(n_hidden), Tanh(),
  Linear(n_hidden, vocab_size)])
model(Xb)                           # Xb: 4 contexts of 8
for layer in model.layers:
    print(layer.__class__.__name__, ':', tuple(layer.out.shape))

A fair fight needs equal parameters

With n_hidden 200 the tree has 170,897 parameters, almost 8× the flat block_size-8 model's 22,097, so any win would just be size. Karpathy shrinks n_hidden to 68 to match:

n_hidden 68: 270 (Embedding 27×10) + 1,360 (20×68) + 136 (BN γ, β) level 1 + 9,248 (136×68) + 136 level 2 + 9,248 (136×68) + 136 level 3 + 1,863 (68×27 + 27) output = 22,397 vs flat 22,097

At equal size the first training run lands at val 2.029 against the flat model's 2.027 (notebook log): no better yet. The next card finds out why.

How it differs from related ideas

✗ Flatten all 8 at once

Flatten → (4, 80) → one Linear(80, 200). It works (val 2.027 in the notebook), but all 8 characters are squashed together in a single layer.

✗ A separate Linear per pair

Four different (20, 200) weights: 4 × 4,000 = 16,000 parameters instead of 4,000, and a pattern like "ch" learned at one position doesn't transfer to the others.

✗ A Python loop, or torch.cat

Looping over the 4 pairs, or building them with cat(e[:, ::2], e[:, 1::2]), gives the same numbers. But the loop runs 4 small matmuls, and cat copies memory.

✓ view + batched @

No copy, one matmul, and one shared weight per level. The pairs become just another batch dimension.

When the view trick doesn't fit

A view can only group characters that are next to each other in memory. Pairing position 0 with 2 (a skipping, "dilated" pattern) would need a permute first, and T must divide by n: FlattenConsecutive(3) on 8 positions fails with shape '[4, 2, 30]' is invalid for input of size 320. That error is useful: explicit shapes fail loudly instead of guessing, which is why Karpathy writes out B, T, C rather than -1.

Two things this layer does not do. It doesn't make training faster; the real speed-up is the dilated convolution (the convolutions card). And the layers after it now get 3-D input: Linear copes, but the hand-written BatchNorm1d silently computes the wrong statistics (the next card).

Understand and remember

  • @ sums only over the last dimension of its left input → every leading dimension is carried along as batch → Linear(20, 200) applied to (4, 4, 20) runs the same weight on all 16 pairs → (4, 4, 200) with no loop
  • Embeddings for one example sit in memory as c0 c1 … c7 → view(B, T/2, 2C) reads them as [c0 c1] [c2 c3] [c4 c5] [c6 c7] → pairs of neighbours for free (no copy) → repeating it after each hidden layer builds the 2 → 4 → 8 character tree
  • Shared weights per level → a pattern learned for one pair works at every position → level 1 costs 20×200 = 4,000 weights instead of 4 × 4,000 for separate ones
  • The tree at n_hidden 200 has 170,897 parameters vs the flat model's 22,097 → a win would only prove size → shrink to n_hidden 68 (22,397) so the comparison isolates the architecture
  • detail that matters The view groups only contiguous positions and needs T divisible by n → a dilated (skipping) pairing needs a permute first, and FlattenConsecutive(3) on 8 positions errors out
  • detail that matters 3-D activations now flow into BatchNorm1d → x.mean(0) keeps separate statistics per position → no error, just wrong normalisation (the next card)

5 · Predict commit to an answer before revealing

The level-1 output is now (32, 4, 68) during training. The hand-written BatchNorm1d still computes x.mean(0, keepdim=True). What shape is that mean, and from how many numbers is each entry estimated?

Reveal

(1, 4, 68): a separate mean for each of the 4 pair positions, each from only 32 numbers. Nothing errors, because it broadcasts fine. The intended statistics are one per channel, (1, 1, 68), from 32 × 4 = 128 numbers, which needs x.mean((0, 1)). That is the next card's bug.
