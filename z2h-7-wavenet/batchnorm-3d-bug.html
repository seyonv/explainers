The silent BatchNorm bug: reduce over (0, 1)

Also called: BatchNorm on 3-D input, per-channel statistics, NLC vs NCL. Lecture 6 · fixing batchnorm1d bug · 0:38:50

Prime · 2 minutes before you read

The problem: The tree-shaped net scored val 2.029, no better than the flat net's 2.027 at the same size. Part of the reason was a layer that ran without errors but computed the wrong statistics, because its code was written for 2-D input and was now fed 3-D.

Where it fits: You built BatchNorm1d for (batch, channels) input in the BatchNorm lecture, and FlattenConsecutive just added a position axis. This card makes the two agree before the network is scaled up.

  3. How many numbers feed each mean before and after the fix, and why does that change the noise?

In one breath: in the tree-shaped net, BatchNorm1d suddenly receives a 3-D tensor (batch, position, channel), but its code still averages over dimension 0 only. Nothing crashes, because broadcasting makes every shape fit. It just keeps a separate mean and variance for each position, each estimated from only 32 numbers. The fix averages over dimensions 0 and 1, so each of the 68 channels gets one statistic from 32 × 4 = 128 numbers.

Predict first: running_mean is created as torch.zeros(68). After one training step on an input of shape (32, 4, 68) with xmean = x.mean(0, keepdim=True), what shape is it, and does anything raise an error?

Shape (1, 4, 68), and no error. The update 0.9 * running_mean + 0.1 * xmean adds a (68,) tensor to a (1, 4, 68) one. Broadcasting stretches the first to match, so the buffer silently grows a position axis. At eval time (x - running_mean) broadcasts too, so the bug never announces itself.

What BatchNorm sees inside the tree

A quick recap of the words. BatchNorm makes each channel (one neuron's output; the C axis) have mean 0 and variance 1 across the batch, then rescales it with learned gamma and beta. During training it also keeps running_mean and running_var, slow averages used at eval time. Karpathy's version expects channels in the last axis, a layout called NLC (batch N, length L, channels C).

In the flat net, BatchNorm saw (32, 200): 32 examples by 200 channels. In the tree net (n_hidden 68), FlattenConsecutive(2) and Linear leave a position axis in place: the first BatchNorm gets (32, 4, 68), meaning 32 examples, 4 character pairs, 68 channels. The same Linear weights made all 4 positions, so channel 17 at position 0 and channel 17 at position 3 are the same feature, measured on different pairs. They should share one mean.

why no error: zeros(68) → 0.9·(68,) + 0.1·(1, 4, 68) → (1, 4, 68) broadcast, silently noise in a mean of unit-variance numbers ≈ 1/√n: 1/√32 = 0.177 1/√128 = 0.088 (half)

Both lines computed. The second is a rule of thumb for independent samples; the 4 positions of one name are related, so the real gain is smaller.

How it differs from related ideas

✗ Reduce over 0 only

The bug. Runs without complaint, but keeps 272 statistics in the first BatchNorm, each from 32 numbers, and treats one feature as 4 different features.

✗ nn.BatchNorm1d(68) as is

PyTorch expects channels in the middle, (N, C, L), and reduces over (0, 2). Fed (32, 4, 68) it at least fails loudly: running_mean should contain 4 elements not 68. Transpose to (32, 68, 4) first.

✗ Normalizing each example instead

Averaging over the channels of one example is a different layer (LayerNorm, coming in the GPT lecture). It needs no batch and no running stats, but it answers a different question.

✓ Reduce over (0, 1)

One mean and variance per channel from all 128 numbers, because the same weights made every position. Same parameters (22,397), steadier statistics, val 2.0265 → 2.0202.

Is a 0.006 gain even real?

Karpathy notes he can't tell whether 2.029 → 2.022 is statistically significant, and neither run here was repeated with other seeds. The reason to make the fix isn't the number. The buggy layer computes something other than BatchNorm, and the correct version is the one whose shapes you can predict.

Per-position statistics would be the right call only if the positions held genuinely different features, for example if each position had its own weights. Here they share one Linear, so sharing statistics matches the model. The wider lesson: as Karpathy puts it, everything broadcasts and yet BatchNorm isn't doing what we need. Broadcasting turns shape mistakes into silent wrong answers, so it pays to print the shapes of your buffers, not just your outputs.

Understand and remember

  • FlattenConsecutive keeps a position axis → BatchNorm gets (32, 4, 68) → x.mean(0) averages only over examples → a separate mean and variance for each of the 4 positions, each from 32 numbers
  • The same Linear weights produce every position → channel c means the same feature at each position → it should have one mean and variance → reduce over (0,1): 68 statistics from 128 numbers each
  • running_mean starts as (68,) → the update broadcasts it against (1, 4, 68) → the buffer silently grows a position axis, and eval-time x - running_mean broadcasts too → no error anywhere, only a slightly worse loss (val 2.0265 vs 2.0202)
  • detail that matters Karpathy's layer expects channels last (NLC); nn.BatchNorm1d expects them in the middle (NCL) and reduces over (0, 2) → feeding it (32, 4, 68) raises running_mean should contain 4 elements not 68 → you transpose to (32, 68, 4) first, and the statistics then match the fixed version exactly

5 · Predict commit to an answer before revealing

Suppose you grow the net to block_size 16 with four levels of FlattenConsecutive(2) and keep the buggy layer. What shape does each BatchNorm's running_mean get, and from how many numbers is the first layer's fixed statistic computed?

Reveal

The inputs are (32, 8, 68), (32, 4, 68), (32, 2, 68) and then 2-D (32, 68), so the buggy buffers are (1, 8, 68), (1, 4, 68), (1, 2, 68) and (1, 68). The fixed first layer averages 32 × 8 = 256 numbers per channel. A deeper tree makes the bug worse at the bottom, where positions are most numerous.
