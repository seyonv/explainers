In one breath: give the character model 8 characters of context, but don't squash them into one hidden layer at once. Fuse neighbours in pairs, then pairs of pairs, then the last pair, with one shared layer per level, so each level sees twice as much: 2, 4, 8 characters. Along the way every piece of the network becomes a torch.nn-style module, one silent BatchNorm shape bug gets fixed, and widening the tree takes validation loss from 2.1065 to 1.9937.

“too quickly” · Karpathy, 0:00:00, on crushing all the context into a single hidden layer. And on the paper's dilated causal convolutions: “just an implementation detail to make everything fast” · 0:17:11

1 · Core model what to internalise, what to just look up

Keep it if it changes what you can explain, predict, compare, choose, build or debug. Otherwise it's reference.

Understand and remember

  • A flat MLP glues all 8 embeddings into 80 numbers → one Linear mixes every character at once and grows with the window (6,000 → 16,000 weights at block_size 3 → 8) → fuse neighbour pairs over 3 levels instead → each level doubles the receptive field (2, 4, 8) and the depth grows with log₂ of the context
  • @ multiplies only the last dimension → a view of (B, 8, C) as (B, 4, 2C) makes the pairs a batch dimension → one shared weight per level, no copy and no loop → but every activation after it is 3-D, which the 2-D BatchNorm was not written for
  • BatchNorm averaging over dim 0 only on (32, 4, 68) → broadcasting silently grows running_mean to (1, 4, 68) → per-position stats from 32 numbers although the same weights made every position → reduce over (0, 1): 68 stats from 128 numbers, val 2.0265 → 2.0202
  • At equal size the tree only tied the flat net (22,397 vs 22,097 params, notebook val 2.029 vs 2.027) → widening the fixed tree to 76,579 params reached val 1.9937 → but one run per row and no widened flat control → the log can't separate structure from size without a harness
  • detail that matters Modules with state behave differently in training → BatchNorm on a batch of 1 divides by n − 1 = 0 → nan logits and a poisoned running_var → set training = False before every evaluation and sample, and before comparing a loop with a batched call

Reference only

  • the chapter timestamps and each card's exact numbers (12,097, 22,097, 22,397, 76,579)
  • the performance-log values to 4 decimals and the notebook's 3-decimal versions
  • module method names: __call__, parameters(), squeeze(1)
  • PyTorch spellings: nn.Sequential, model.eval(), nn.BatchNorm1d's (N, C, L) layout

3 · Retrieve from memory, card closed
  1. concept Explain to a programmer who knows the flat MLP why the formula h⁽ˡ⁾ₜ = tanh(BN([h⁽ˡ⁻¹⁾₂ₜ ; h⁽ˡ⁻¹⁾₂ₜ₊₁] W⁽ˡ⁾)) is still an MLP, and what the one change buys.
    Check
    • each level is the familiar Linear → BatchNorm → tanh hidden layer
    • the only change is its input: two neighbouring vectors instead of all 8 embeddings
    • so context is fused gradually and a node's receptive field doubles per level (2, 4, 8)
    • and the per-level weight is shared, so doubling the context adds one level rather than a wider first layer
  2. mechanism Walk one batch of 32 contexts through the final model and say at each step the shape, which card built that step, and which statistic BatchNorm computes.
    Check
    • (32, 8) indices → Embedding (32, 8, 24) (torch-nn-containers)
    • FlattenConsecutive(2) views (32, 4, 48); Linear (32, 4, 128) with one weight for all 4 pairs (flatten-consecutive)
    • BatchNorm takes mean and variance per channel over (0, 1): 32 × 4 = 128 numbers each (batchnorm-3d-bug)
    • levels 2 and 3: (32, 2, 256) → (32, 2, 128) → (32, 256) → (32, 128); output Linear (32, 27) logits → loss (scale-up)
  3. tradeoff Across the log, which comparisons are fair and which aren't? For each row-to-row step, say whether parameters, wiring or a bug changed, and which step is most likely noise.
    Check
    • 3 → 8 characters: more parameters (12,097 → 22,097) and more context at once, so not a pure test of context
    • flat → tree: fair on size (22,097 vs 22,397), and it tied (2.027 vs 2.029 in the notebook)
    • bug fix: same parameters, 0.006–0.007 gain from one run each, the likeliest to be noise
    • scale-up: 3.4× the parameters with no widened flat control, so structure and size are confounded
  4. mechanism You add a fourth level to take block_size 16. Which lines of code change, which parameter counts grow, and what stays the same about BatchNorm?
    Check
    • block_size = 16 and one more FlattenConsecutive(2) → Linear(2h, h) → BatchNorm1d → Tanh block
    • the new level adds 2h·h weights plus 2h for BatchNorm: 256 × 128 + 256 = 33,024 at n_hidden 128 (computed)
    • the embedding and the output layer don't change size
    • BatchNorm still reduces over (0, 1); level 1 now sees (B, 8, 2e), so each statistic uses 8 × 32 = 256 numbers

4 · Compare against what you already know

vs The six big ideas of becoming a backprop ninja: The backprop-ninja lecture's big idea says sum and broadcast are each other's backward. This course's worst bug came from a broadcast nobody asked for. Which forward broadcasts does BatchNorm over (0, 1) perform, what does its backward therefore sum over, and why did the dim-0 version still run?

Check
  • forward: the (1, 1, 68) mean and variance broadcast back over the batch and the positions
  • backward: the gradients of those statistics sum over dims 0 and 1, with n = N·T (128 at level 1) in place of N
  • the dim-0 version broadcast (68,) against (1, 4, 68) in the running-stat update, which is legal, so no error
  • same lesson both lectures: track which dims a reduction covers, because broadcasting will make the wrong choice fit

vs The six big ideas of activations, gradients and BatchNorm: The BatchNorm lecture says BatchNorm couples the batch, so test time needs fixed statistics. Where does that idea bite twice in this course, and how is each case different?

Check
  • sampling one context in training mode: batch statistics of a batch of 1 give nan variance and poison running_var
  • the tree: the batch is now examples × positions, so the statistics must pool over (0, 1)
  • the first is about when to use batch statistics (train vs eval), the second about which numbers form the batch
  • both are silent: the model runs; only printed shapes or broken samples reveal it

5 · Predict commit to an answer before revealing

The next lecture trains on chunks of block_size 8 and asks for a prediction at every position of a chunk in one call. How many training examples does one chunk of 9 characters give, how does that relate to this course's convolution argument, and what replaces the fixed pair tree for mixing positions?

Reveal

8 examples: the context grows from 1 to 8 characters, one target each, and a 4 × 8 batch holds 32. That is the setting where this course's convolution pays off: many outputs from one sequence, so shared work is computed once. Instead of a fixed tree that always fuses positions 1+2, 3+4, …, self-attention mixes all earlier positions with weights computed from the data, and a mask keeps it causal.
