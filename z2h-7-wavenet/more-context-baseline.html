Just widen the window: block_size 8

Also called: a longer context, a bigger context length. Lecture 6 · dataset: bump the context size to 8 · 0:19:33 · re-running baseline code on block_size 8 · 0:19:55

Prime · 2 minutes before you read

The problem: With 3 characters of context the model almost never sees a whole name, so it guesses where a name ends from its last few letters. Before building a new architecture you need to know how far just showing it more characters gets you, or you can't tell whether the fancy version actually helped.

Where it fits: It reuses the flat MLP you packaged with Embedding, Flatten and Sequential, and the rolling-window dataset from the MLP lecture. It sets the number (val 2.0342 at 22,097 parameters) that the WaveNet-style tree on the next cards has to beat.

In one breath: before building anything clever, change one number. Let the same flat MLP see the last 8 characters instead of the last 3 (block_size, the context length). It costs 10,000 extra weights, all in the first layer, and the validation loss drops from 2.1065 to 2.0342. The catch is that one layer now has to squash all 8 characters together in a single step.

Predict first: with block_size = 3 the training set had 182,625 rows. How many rows does it have with block_size = 8?

Still 182,625. build_dataset makes one row per character to predict: each name gives its letters plus the final '.'. The context length only changes how wide each row is, (182625, 3) → (182625, 8), not how many rows there are. More context means more information per example, not more examples.

What the rows look like now

Xtr holds the inputs, one row of 8 character indices per example, and Ytr holds the character that comes next. Every name starts from eight '.' pads (index 0), then slides one character to the left at each step. These are the first 15 rows, the names "yuheng" and "diondre":

........ --> y ........ --> d .......y --> u .......d --> i ......yu --> h ......di --> o .....yuh --> e .....dio --> n ....yuhe --> n ....dion --> d ...yuhen --> g ...diond --> r ..yuheng --> . ..diondr --> e .diondre --> .

From labs/more-context-baseline.py; identical to the notebook's printout. The last row of "diondre" sees the whole name at once.

That last detail is the point. The 25,626 training names average 6.1 letters. At block_size = 3, only 2.0% of them are 3 letters or shorter, so the model almost never sees a whole name when it decides where the name ends. At block_size = 8, 94.7% fit completely inside the window (computed from the 80% training split).

The same model, one layer wider

An embedding is a learned row of 10 numbers per character (n_embd = 10). Flatten lays the 8 rows side by side into 80 numbers. The first Linear layer multiplies those 80 numbers by a weight matrix to make 200 hidden values (n_hidden = 200). Only that matrix depends on block_size:

Extra weights: 10 × (8 − 3) × 200 = 10,000. The first layer is now 16,000 / 22,097 = 72% of the model (it was 50%). The lab prints the same totals.

The result

The loss here is the average negative log likelihood (cross-entropy) of the correct next character: lower is better, and a uniform guess over 27 characters scores ln 27 = 3.2958. Train is measured on the 80% of names the model learned from, val on 10% it never saw.

Measured on your M3 (torch 2.14). Val improves by 2.1065 − 2.0342 = 0.072. As a rough feel, e2.1065 ≈ 8.2 and e2.0342 ≈ 7.6: like narrowing a blind guess from about 8.2 equally likely characters to 7.6.

The notebook logs train 1.918 / val 2.027 (from 2.058 / 2.105); torch 2.14's random numbers differ, so your run gives 1.9163 / 2.0342.

Note the last column. The gap between train and val more than doubled, from 0.048 to 0.118. The wider layer fits the training names better than it generalises to new ones. That is one hint that mixing all 80 numbers at once isn't the best use of the extra context.

Why it beats the alternatives

✗ Stay at 3 characters

Only 2.0% of training names fit in the window, so the model rarely sees the whole name when it decides where it ends. Val stays at 2.1065.

✗ Count 8-character contexts

The bigram trick, scaled up: a table with 278 ≈ 2.8 × 1011 possible contexts, filled from 182,625 rows. Almost every context is never seen, so its counts are all zero.

✗ Widen to 16

The first layer grows to 160 × 200 = 32,000 weights (38,097 in total), but 80% of the context slots would hold '.' padding (60% at 8), because the longest name has only 15 letters. Not measured here.

✓ block_size 8, same flat MLP

One changed number and 10,000 more weights. 94.7% of names now fit, and val drops from 2.1065 to 2.0342.

Is widening the window the whole answer?

No. This is a baseline to beat, not the destination. One Linear layer takes all 80 numbers and mixes them in a single matrix multiply, so everything about the 8 characters is squashed together at once. Karpathy's goal for the lecture, set out in the intro, is to stop crushing the context into one layer so early and to fuse it gradually instead: pairs of characters, then pairs of pairs (the next card). Stretching the window further only makes that one layer bigger.

Be careful comparing the tree against this baseline. At the same ~22K parameters, the notebook's first hierarchical net scored val 2.029, no better than this flat model's 2.027. Only after a BatchNorm fix and scaling up to 76,579 parameters does it reach 1.993. A wider window is cheap and worth trying first, but it isn't where the big gains come from.

Understand and remember

  • build_dataset emits one row per character to predict → block_size only sets each row's width → 182,625 rows either way, now of shape (182625, 8) → more information per example, not more examples
  • Embedding is per character and output is per prediction → only the first Linear sees n_embd·block_size inputs → its weights go 30×200 → 80×200 → all +10,000 params land there (12,097 → 22,097)
  • Wider window → 94.7% of training names fit whole (vs 2.0%) → the model sees more of the name before predicting → val 2.1065 → 2.0342
  • One Linear mixes all 80 numbers in a single matmul → every character pair must be combined at once → context is squashed early, and the train–val gap grows 0.048 → 0.118 → motivates fusing characters gradually in a tree
  • detail that matters Most rows are mostly padding (96.8% of block_size-8 rows contain at least one '.' pad) → the first layer spends weights on positions that are usually '.' → widening further (e.g. 16) buys mostly padding

Suppose names.txt had names up to 30 letters long, but the average stayed about 6. Would widening from 8 to 32 help the flat model much? Commit to a guess and a reason.

Reveal

Probably only a little, and it could hurt. The first Linear would grow to 320×200 = 64,000 weights, but for most rows the extra 24 positions are just '.' padding. The few long names would gain context; everything else pays the parameter cost and the extra room to overfit. This is illustrative reasoning, not a measured result: the fix the lecture takes is to change how the context is combined (a tree), not only how much of it there is.
