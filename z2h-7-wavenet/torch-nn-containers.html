In one breath: every step of the forward pass becomes a small object (a module) that you call like a function and that can list its own parameters. Wrap the modules in a Sequential container and the whole network becomes one call, logits = model(Xb). The catch: some modules, like BatchNorm, carry a training switch, and forgetting to flip it breaks sampling.

Predict first: the model is trained, but you forget to set training = False before sampling. Sampling feeds one context at a time, a batch of 1. What variance does BatchNorm compute for that batch?

nan, for every one of the 200 channels. The variance of a single number divides by n − 1 = 0, so it's 0/0. The lab prints x.var(0)[:3] = [nan, nan, nan], and the nan flows through to every logit.

One call, six layers

A module here is any object with two methods: __call__(x), which Python runs when you write layer(x) and which does the forward step, and parameters(), which returns the tensors that training should update. Linear, BatchNorm1d and Tanh came from the previous lecture; this chapter adds three more.

The container does two jobs: it runs the layers in order, and it collects every layer's parameters into one list for the training loop.

The fun bug: sampling with BatchNorm still in training mode

In training mode, BatchNorm normalises with the mean and variance of the current batch. Sampling feeds one context at a time, so the batch has n = 1 example, and the unbiased variance (the torch default) divides by n − 1:

σ2= 1n−1n = 1 → 1/0 ∑i=1n (xi−x¯)2x₁ is its own mean → 0 =00=nan
σ²the batch variance BatchNorm divides by (per channel)nan for all 200 nexamples in the batch32 in training · 1 when sampling x̄the batch mean of that channelequals x₁ when n = 1
x̂ = (x − x̄) / √(nan + 1e-5) = nan → logits = nan → softmax = nan running_var = 0.9 × running_var + 0.1 × nan = nan (the buffer is poisoned)

One forgotten flag breaks two things: this sample, and the running statistics that eval mode would have used afterwards.

In the video the output is just garbage names (~0:16:01). On torch 2.14, torch.multinomial refuses nan probabilities and raises an error instead.

class Embedding:
    def __init__(self, num_embeddings, embedding_dim):
        self.weight = torch.randn((num_embeddings, embedding_dim))
    def __call__(self, IX):
        self.out = self.weight[IX]
        return self.out
    def parameters(self):
        return [self.weight]

class Flatten:
    def __call__(self, x):
        self.out = x.view(x.shape[0], -1)
        return self.out
    def parameters(self): return []
class Sequential:
    def __init__(self, layers):
        self.layers = layers
    def __call__(self, x):
        for layer in self.layers:
            x = layer(x)
        self.out = x
        return self.out
    def parameters(self):
        return [p for layer in self.layers for p in layer.parameters()]

model = Sequential([Embedding(vocab_size, 10), Flatten(),
    Linear(30, 200, bias=False), BatchNorm1d(200), Tanh(),
    Linear(200, vocab_size)])

Train it with your usual loop (now just logits = model(Xb)), set every layer.training = False and sample. Then set them back to True and sample again.

How it differs from related ideas

✗ Loose tensors and a hand-typed forward

What the last lecture did: C, W1, bngain… and a forward pass written line by line. Every new layer means editing the forward pass and the parameter list by hand, and the two drift apart.

✗ A plain list of layers

Runs the forward pass, but the training loop still has to collect parameters and flip training itself, and a list can't be nested inside another model as a single layer.

✗ Parameters as a separate global list

Nothing ties a tensor to the layer that owns it, so a forgotten tensor never gets gradients or updates, and nothing reports the mistake.

✓ Modules plus a container

Each module owns its parameters and its forward step; Sequential is itself a module, so containers nest. Changing the architecture means changing one list. This is exactly torch.nn's design.

Is this how torch.nn works?

Yes: this is the same design, and from here on Karpathy uses torch.nn directly (0:51:34). nn.Sequential(nn.Embedding(27, 10), nn.Flatten(), nn.Linear(30, 200, bias=False), nn.BatchNorm1d(200), nn.Tanh(), nn.Linear(200, 27)) also has 12,097 parameters (checked on torch 2.14). Three differences matter. nn.Linear stores its weight transposed, as (200, 30). model.eval() flips training on every sub-module for you, which is the fix for the bug above. And the real nn.BatchNorm1d refuses a training-mode batch of 1 outright: ValueError: Expected more than 1 value per channel when training.

Our modules are plain Python classes, so they don't get nn.Module's extras: automatic parameter registration, state_dict() for saving, and .to(device). That is why you move to the real library once you understand it.

Understand and remember

  • Each module owns its tensors and its forward step → Sequential just loops x = layer(x) and concatenates parameters() → the forward pass and the parameter list can't drift apart → changing the architecture is editing one list
  • Sequential has the same interface as a layer → containers nest → big models are trees of small modules (this is torch.nn's design)
  • BatchNorm in training mode uses the current batch's statistics → sampling feeds a batch of 1 → unbiased variance divides by n − 1 = 0 → 0/0 = nan → every logit is nan and torch.multinomial fails
  • Training mode also updates the running buffers → running_var = 0.9 × old + 0.1 × nan = nan → the forgotten flag poisons eval mode too, so the model must be re-trained or the buffers reset
  • detail that matters Flatten is a view, not a copy → (4, 3, 10) becomes (4, 30) for free, with each example's 3 embeddings side by side → the next card generalises it to FlattenConsecutive to group only pairs

Reference only

  • the exact class code of Embedding, Flatten and Sequential

  • nn.Linear stores its weight as (out, in), e.g. (200, 30)
  • model.eval() / model.train() in real torch.nn
  • the torch 2.14 error text probability tensor contains either inf, nan or element < 0

4 · Compare against what you already know

vs BatchNorm at test time: running statistics: That card computed running statistics so a trained net could handle one example at a time. Here the flag that selects them was forgotten. What exactly differs between the two modes, and how does each one fail?

Check
  • training mode: normalise with the batch's own mean and variance and update the running buffers
  • eval mode: normalise with the stored running mean and variance, no updates
  • training mode fails on a batch of 1 (nan) and also poisons the buffers
  • eval mode fails only if the buffers were never estimated well (or were poisoned by the bug)

vs Batched matmul and FlattenConsecutive: Flatten vs FlattenConsecutive(n): what does each glue together, and why does the tree-shaped model need the second one?

Check
  • Flatten: (B, T, C) → (B, T·C), all characters fused at once
  • FlattenConsecutive(2): (B, T, C) → (B, T/2, 2C), only neighbouring pairs fused
  • the tree fuses context slowly, two at a time, so each level needs pairs, not everything
  • FlattenConsecutive(8) on 8 characters behaves like Flatten (it squeezes the middle dim)

5 · Predict commit to an answer before revealing

Suppose BatchNorm used the biased variance (divide by n, not n − 1). You still forget training = False and sample one context at a time. Does sampling crash, and are the samples any good?

Reveal

No crash, and that's worse. With n = 1 every value equals its own mean, so x − x̄ = 0 and the variance is 0/1 = 0. Then x̂ = 0 / √(0 + 1e-5) = 0, so every hidden unit outputs just β, whatever the context was. The logits are the same for every context, so the model samples every character from one fixed distribution: names come out, but they ignore the context completely. A nan that crashes is easier to catch than a silently wrong answer.
