Automatic backward: closures and topological order

Also called: reverse-mode autodiff, loss.backward(), the autograd engine. Lecture 1 · implementing the backward function for each operation · 1:09:02, then for a whole expression graph · 1:17:32

Prime · 2 minutes before you read

The problem: Filling in grads by hand works for 10 nodes and falls apart at 41 parameters, let alone millions. You'd also have to work out the right order yourself every time the expression changes.

Where it fits: The neuron card did backprop by hand, one local derivative at a time. This card hands that job to the graph the Value object already records: each node learns to do its own step, and one call runs them all in the right order.

In one breath: each operation, at the moment it creates its output, also leaves behind a tiny function, _backward, that knows how to pass the output's gradient to its own inputs. Put every node in topological order (each node after everything it was made from), walk that list backwards from the output, and call each node's _backward once. That's the whole of o.backward().

Predict first: you forget reversed() and call every _backward inputs-first (leaves first, o last), after setting o.grad = 1.0. Which of the neuron's 10 Values end up with a non-zero grad?

Only two: o (1.0) and n (0.5). Every other node ran its _backward while its own grad was still 0, so it passed on 0. n got its 0.5 last, from o, when nobody was left to hand it to. (Computed with the card's code; the order is the whole trick.)

One rule, stored three times

Every _backward is the chain rule for one node: take the gradient that arrived at the output, multiply by the op's own local derivative, and add it to each input's grad. Here grad always means do/d(this Value), how much the final output moves per unit nudge of this node.

Filled in for x1 in the neuron: x1.grad += w1.data × (x1*w1).grad = −3 × 0.5 = −1.5.

Why a closure? A closure is a function defined inside another function that keeps using the outer function's variables after it returns. _backward is defined inside __mul__, so it still sees self, other and out later, when backprop calls it. Each node carries its own recipe; no central code needs to know what ops exist.

The walk: Karpathy's neuron, node by node

build_topo does a depth-first walk from o and appends a node only after all its children (the Values in its _prev). So the list runs inputs → output, and reversed(topo) runs output → inputs: by the time a node's _backward runs, everything that uses it has already added its share. When: pause the video at 1:09:02 and add the closures, then at 1:17:32 add backward(). In your Value from the earlier cards, add self._backward = lambda: None to __init__, then give each op its closure. __add__ is the same as __mul__ with 1.0 in place of other.data and self.data.

    def __mul__(self, other):
        out = Value(self.data * other.data, (self, other), '*')
        def _backward():
            self.grad += other.data * out.grad
            other.grad += self.data * out.grad
        out._backward = _backward     # store it, don't call it
        return out
    def tanh(self):
        t = (math.exp(2*self.data) - 1)/(math.exp(2*self.data) + 1)
        out = Value(t, (self,), 'tanh')
        def _backward():
            self.grad += (1 - t**2) * out.grad
        out._backward = _backward
        return out
    def backward(self):
        topo, visited = [], set()
        def build_topo(v):
            if v not in visited:
                visited.add(v)
                for child in v._prev:
                    build_topo(child)
                topo.append(v)        # only after all its children
        build_topo(self)
        self.grad = 1.0               # base case: do/do = 1
        for node in reversed(topo):
            node._backward()
x1 = Value(2.0, label='x1'); x2 = Value(0.0, label='x2')
w1 = Value(-3.0, label='w1'); w2 = Value(1.0, label='w2')
b = Value(6.8813735870195432, label='b')
n = x1*w1 + x2*w2 + b; n.label = 'n'
o = n.tanh(); o.label = 'o'
o.backward()
print(', '.join(f"{v.label} {v.grad:.4f}"
                for v in (b, w1, x1, w2, x2, n, o)))

Why it beats the alternatives

✗ Call each _backward by hand

What Karpathy does first: o._backward(), n._backward(), … It works for 10 nodes, but you must pick the order yourself, and the MLP at the end of this lecture has 41 parameters.

✗ One central backward with an if per op

Every new op means editing that function, and it must dig the inputs back out. The closure is written right next to the forward code, while self, other and out are in hand.

✗ Recurse from o, passing grads down as you go

Fine on a tree like this neuron. But when one Value feeds two ops, it can pass its gradient on before the second share has arrived. The topological order rules that out.

✓ Closures + reversed topological order

Each op brings its own local rule. The sort guarantees every node's grad is complete before it's passed on. One call, each node visited once.

Is this backward finished?

Not quite, and not for every graph. The closures use += so that a Value used twice collects both shares, which is exactly the bug the next card, the += bug, is about. backward() also never resets grads, so calling it again piles new gradients on top of old ones (hence zero_grad in the training loop).

And build_topo is recursive. Python's default recursion limit is 1000, so in micrograd's own engine.py, a chain of 500 additions backprops fine while a chain of 1000 raises RecursionError (checked with a script). For deep graphs you'd use an iterative sort; real frameworks do the walk in C++ over tensor ops instead of Python over scalars.

1 · Core model what to internalise, what to just look up

Keep it if it changes what you can explain, predict, compare, choose, build or debug. Otherwise it's reference.

Understand and remember

  • Each op creates out inside its own method → it defines _backward right there as a closure over self, other, out → later it can apply its local derivative × out.grad to its inputs → backprop needs no central table of ops
  • A node's grad is complete only after every node that uses it has passed its share down → so its _backward must run after theirs → build_topo appends a node after its children, and reversed(topo) runs output-first → each _backward runs once, with its full grad
  • Every closure multiplies by the grad above it → the chain has to start from something non-zero → o.grad = 1.0 (do/do) is the base case → skip it and every grad stays 0.0
  • Order comes from dependencies, not from _prev → _prev is a set, so the topological list differs between runs → any order with each node after its children gives the same grads (b 0.5, w1 1.0, x1 −1.5, w2 0, x2 0.5)
  • detail that matters out._backward = _backward stores the function; _backward() would call it now and store None → the error only shows up later, at backward time, as 'NoneType' object is not callable
  • detail that matters build_topo is recursive → recursion depth equals the graph's depth → in micrograd's engine.py a chain of 1000 additions hits Python's default limit of 1000 and raises RecursionError

Reference only

  • leaves default to self._backward = lambda: None
  • the visited set in build_topo
  • Karpathy's engine.py L24–L33 (__mul__) and L54–L70 (backward)
  • the 1.0 * in __add__'s closure is only for readability

5 · Predict commit to an answer before revealing

Build the neuron, then call o.backward() twice in a row without resetting anything. What is x1.grad after the second call: still −1.5, doubled to −3.0, or something else?

Reveal

Something else: −7.5 (computed with the card's code). backward() resets only o.grad to 1.0. On the second pass n.grad becomes 0.5 + 0.5 = 1.0, and each node then passes its accumulated grad down, so the error compounds on the way to the leaves: the sum node reaches 1.5, x1*w1 reaches 2.0, and x1.grad = −1.5 + (−3 × 2.0) = −7.5. A third call gives −22.5. This is why the training loop must zero the grads before each backward.
