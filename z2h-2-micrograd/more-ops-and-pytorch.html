More operations, and PyTorch agrees

Also called: composite operations, operator overloading, checking your autograd against a reference. Lecture 1 · breaking up a tanh, exercising with more operations · 1:27:05 · doing the same thing but in PyTorch · 1:39:31

Prime · 2 minutes before you read

The problem: Your Value only knows +, * and tanh. Real models need division, subtraction, exp and powers, and 2 * a or a + 1 crash outright. And so far nothing independent has confirmed that your gradients are right.

In one breath: any new operation needs only two things: how to compute its output (the forward) and its local derivative (the backward). Give Value an exp and a power, and division, subtraction and even tanh can be built from pieces it already has. The gradients come out the same, and PyTorch, a completely separate engine, gets the same numbers too.

Predict first: you replace the single tanh op with e = (2*n).exp(); o = (e - 1)/(e + 1). The graph grows from 10 nodes to 18. What happens to x1.grad, which was −1.5?

Nothing: it is still −1.5, and w1 1.0, x2 0.5, w2 0.0 too. The chain rule doesn't care how finely you split a function. Multiplying the local derivatives along the longer path gives the same product, 1 − o² = 0.5 at n. Only the amount of bookkeeping changes.

Each new op: a forward and a local derivative

Karpathy adds two genuinely new operations and builds everything else out of them. Here "local derivative" means how much this one node's output moves per unit nudge of its input, which the chain rule then multiplies by out.grad. Examples use a = Value(2.0), b = Value(4.0).

Rebuilding tanh out of exp

The lecture's tanh has its own local derivative, 1 − o². But tanh is only an exp in disguise:

de/dn = 2·e = 2 × 5.8284 = 11.6569 do/de = 2/(e+1)² = 0.0429 (= 0.14645 − 0.10355) do/dn = 0.0429 × 11.6569 = 0.5000 (= 1 − 0.7071²) x1.grad = 0.5 × w1 = 0.5 × −3 = −1.5 (unchanged)

Node e feeds both e − 1 and e + 1, so its gradient is the sum of two paths. That is the += from the previous card doing its job. With =, the second path would overwrite the first.

PyTorch gets the same numbers

PyTorch is a production autograd library. A tensor is its n-dimensional array of numbers; here each one holds a single number, so it plays the role of a Value. Karpathy's cell builds the same neuron:

import torch
x1 = torch.Tensor([2.0]).double();  x1.requires_grad = True
x2 = torch.Tensor([0.0]).double();  x2.requires_grad = True
w1 = torch.Tensor([-3.0]).double(); w1.requires_grad = True
w2 = torch.Tensor([1.0]).double();  w2.requires_grad = True
b = torch.Tensor([6.8813735870195432]).double(); b.requires_grad = True
n = x1*w1 + x2*w2 + b
o = torch.tanh(n)
print(o.data.item())
o.backward()
print('x2', x2.grad.item()); print('w2', w2.grad.item())
print('x1', x1.grad.item()); print('w1', w1.grad.item())

.double() switches to 64-bit floats (float64), the same precision as a Python float; tensors default to 32-bit (float32). requires_grad = True asks PyTorch to track gradients for a leaf tensor, which it doesn't do by default. .item() pulls the plain number out.

    def exp(self):
        out = Value(math.exp(self.data), (self,), 'exp')
        def _backward():
            self.grad += out.data * out.grad  # (e^x)' = e^x
        out._backward = _backward
        return out
    def __pow__(self, other):  # other: a plain int/float
        out = Value(self.data**other, (self,), f'**{other}')
        def _backward():
            self.grad += other * self.data**(other - 1) * out.grad
        out._backward = _backward
        return out
    # first line of __add__ and __mul__:
    # other = other if isinstance(other, Value) else Value(other)
    def __rmul__(self, other): return self * other
    def __radd__(self, other): return self + other
    def __neg__(self): return self * -1
    def __sub__(self, other): return self + (-other)
    def __truediv__(self, other): return self * other**-1

a = Value(2.0); b = Value(4.0)
print(a + 1, 2 * a, a / b, a - b, a.exp())

Why check against PyTorch

✗ Trust it because it runs

Backprop bugs don't crash; they give plausible wrong numbers. The lecture's own exp was typed with = instead of += in the video (the notebook notes the fix).

✗ Only nudge-and-measure

A numerical slope is approximate and fragile: on the first card, shrinking h to 10−15 turned the true slope 14 into 10.658. It also costs one extra forward pass per input.

✗ Derive every grad by hand

Fine for a neuron with 5 inputs; hopeless for the 41-parameter net on the next card, and you can make the same mistake in your head as in your code.

✓ Compare with an independent engine

Same inputs into PyTorch; exact gradients from code you didn't write. Agreement to 6+ decimals is strong evidence. micrograd's test_engine.py does exactly this.

So should tanh be one op or many?

Either is correct; how finely you split is your choice. The trade-off: small primitives mean fewer derivatives to write (and get wrong), but more nodes to store and walk (18 vs 10 here). A single op with a hand-written local derivative is shorter and faster, which is why PyTorch ships one tanh whose backward is a formula like a * (1 - b*b), b being the tanh output (shown at 2:21:10).

A common misreading of the table above: the red digits are not PyTorch being "less accurate at autograd". They are a data-entry effect: torch.Tensor made float32 numbers first. Also note __pow__ only takes a plain number as the exponent; a**b with b a Value needs a different derivative (with respect to the exponent) that micrograd doesn't implement.

Understand and remember

  • Backprop only ever needs each node's local derivative → an op is fully defined by its forward plus that derivative → so /, - and even tanh can be composed from *, +, ** and exp with no new backward code
  • Chain rule multiplies local derivatives along a path and sums over paths → splitting a function into smaller ops just factors the same product differently → identical grads (x1 −1.5, w1 1.0, x2 0.5, w2 0.0) with 18 nodes instead of 10
  • A node used twice (e feeds e−1 and e+1) → its grad is a sum of paths (0.14645 + (−0.10355) = 0.0429) → composite ops silently depend on += accumulation being right
  • torch.Tensor([...]) stores float32 first → b loses digits (6.881373405…) before .double() → PyTorch's grads differ in the 7th decimal → build in float64 from the start and it matches micrograd
  • detail that matters Granularity is a cost choice: more primitive ops → fewer hand-written derivatives but more nodes to store and walk; one fused op (PyTorch's tanh, backward a*(1-b*b)) → shorter graph and faster backward

Reference only

  • the dunder names: __rmul__, __radd__, __neg__, __sub__, __truediv__, __rtruediv__
  • other = other if isinstance(other, Value) else Value(other)
  • .item(), .data, .grad on a tensor; requires_grad defaults to False
  • micrograd's __pow__ asserts an int/float exponent

3 · Retrieve from memory, card closed
  1. concept Explain why micrograd needs a new _backward for exp but not for a / b.
    Check
    • exp is a new function with its own local derivative (ex = out.data)
    • a / b is rewritten as a * b**-1, and * and ** already know their derivatives
    • backprop only needs local derivatives at each node, so composition inherits them
  2. mechanism Walk through what happens, in Python and in the graph, when you evaluate 2 * n and then e - 1.
    Check
    • int.__mul__ fails, so Python calls n.__rmul__(2), which does n * 2
    • __mul__ wraps 2 in a constant Value and makes a * node
    • e - 1 becomes e + (-1): another hidden constant Value and a + node
    • those hidden constants are why the graph has 18 nodes, not 15
  3. mechanism Backward through (e - 1)/(e + 1): which two contributions reach e, and what do they add up to?
    Check
    • through e−1: 0.14645 (= 1/(e+1))
    • through e+1: −0.10355 (= −(e−1)/(e+1)²)
    • sum 0.0429, times de/dn = 11.6569 gives n.grad = 0.5 = 1 − o²
  4. tradeoff You're adding GELU to your engine. Would you compose it from existing ops or write it as one op with its own derivative? What does each choice cost?
    Check
    • composing: no new derivative to get wrong, but more nodes, more memory and a slower backward
    • one op: shorter graph and faster, but you must derive and code the local derivative correctly
    • either way, check the gradients against PyTorch
