The += bug: reused nodes add their gradients

Also called: gradient accumulation, the multivariate chain rule. Lecture 1 · fixing a backprop bug when one node is used multiple times · 1:22:28

Prime · 2 minutes before you read

The problem: Your automatic backward() gives correct gradients for the neuron, but the moment one Value is used twice (a + a, or a weight shared by several examples) it silently returns the wrong number, and nothing crashes.

Where it fits: This fixes the engine from the automatic-backward card. It relies on the chain rule you did by hand: each operation passes back local derivative × out.grad. Now you'll see what happens when two of those messages land on the same node.

In one breath: when one Value feeds into two places, it gets a gradient from each place, and its true gradient is the sum. Our _backward closures wrote self.grad = …, so the second contribution erased the first. Writing self.grad += … instead (with every grad starting at 0) adds them up and fixes it.

Predict first: a = Value(3.0), then b = a + a and b.backward(). What should a.grad be, and what does the engine from the last card print?

It should be 2.0; the old engine prints 1.0. b = 2a, so nudging a by h moves b by 2h. The + closure hands 1·b.grad to self and then to other, but here both are the same object a, so the second assignment just overwrites the first.

The general case: two branches meet again

Karpathy's second example uses a=−2, b=3, d=a·b, e=a+b, f=d·e, so f = (−6)·1 = −6. Now a and b each reach f by two different routes. Backprop sends one share of the gradient down each route (the local rules from the chain-rule card: * passes back the other input times out.grad, + passes out.grad straight through).

This is the multivariate chain rule: if a variable reaches the output along several paths, its derivative is the sum over paths of (the chain-rule product along that path). Here ∂f/∂d means "how much f moves per nudge of d, holding e fixed" (a partial derivative).

∂f∂a= ∂f∂d·∂d∂avia d: e · b = 1 · 3 = 3 + ∂f∂e·∂e∂avia e: d · 1 = −6 =−3
∂f/∂d = ef = d·e, so nudging d scales by e1 ∂d/∂a = bd = a·b3 ∂f/∂e = dthe other input of the last ×−6 ∂e/∂a = 1e = a+b, plus passes gradients through1
∂f/∂b = e·a + d·1 = 1·(−2) + (−6)·1 = −2 − 6 = −8 numerical check (h = 1e-6): df/da = −3.0 df/db = −8.0

With =, whichever of the d and e closures runs last wins, and the order comes from the topological sort over _prev, which is a set. So the buggy answer is not even stable:

Both buggy rows are real runs: your M3's lab printed 3.0 / −2.0 (30 runs out of 30 in one session); the course's measurement run printed −6.0 / −6.0. Forcing each order by hand gives exactly these two rows. The += row never changes, because addition doesn't care about order.

When: pause the video at 1:22:28. First run b = a + a on your current engine and watch it print 1.0, then make this change in every _backward.

def __add__(self, other):
    out = Value(self.data + other.data, (self, other), '+')
    def _backward():
        self.grad += 1.0 * out.grad     # was: self.grad = ...
        other.grad += 1.0 * out.grad
    out._backward = _backward
    return out
# the same = to += change in __mul__ and tanh:
#   self.grad  += other.data * out.grad
#   other.grad += self.data * out.grad
#   self.grad  += (1 - t**2) * out.grad
a = Value(3.0, label='a')
b = a + a; b.backward()
print(a.grad)
a = Value(-2.0, label='a'); b = Value(3.0, label='b')
d = a * b; e = a + b; f = d * e
f.backward()
print(f.data, a.grad, b.grad)

Why it beats the alternatives

✗ Assign with =

Fine while every Value is used once, which is why the neuron example never caught it. With reuse, the last branch to run silently erases the others, and the forward values still look right.

✗ Never reuse a Value

Impossible in practice. In the MLP at the end of this lecture, every weight is used once per training example, and the loss adds all four examples together.

✗ Collect shares in a list, sum later

Correct, but each node now stores a list and needs a separate pass to add it up. += is the same sum, done as each share arrives.

✓ += onto a grad that starts at 0

Each branch adds its share when its closure runs, in any order, because addition is order-free. One character changes, and the engine now implements the multivariate chain rule.

Does += ever cause trouble?

Yes: grads now only ever grow, so nothing clears them for you. Call f.backward() a second time on the same graph and a.grad becomes −9.0 and b.grad −24.0, not −3 and −8 (run in a scratch script; the intermediate grads d and e pile up too, so it isn't a clean doubling). That's why a training loop must reset every p.grad = 0.0 before each backward pass, the forgot-zero_grad bug on the training-loop card. PyTorch's .grad accumulates the same way.

Understand and remember

  • A Value used in two places → it receives one gradient share from each place → its true gradient (multivariate chain rule) is the sum of the shares → = keeps only the last share, += keeps all of them
  • b = a + a → self and other are the same object → the second line of the closure overwrites the first → a.grad = 1 instead of 2
  • Buggy = → the surviving share is whichever closure runs last → that order comes from a topological sort over the set _prev → the wrong answer can change between runs (3/−2 or −6/−6 for f = (a·b)·(a+b))
  • += → gradients only grow and are never cleared automatically → a second backward (or the next training step) adds on top → you must reset every grad to 0 first (zero_grad)
  • detail that matters Grads start at 0.0 in __init__ → the first += equals a plain assignment → the fix changes nothing for Values used only once, which is why the neuron example stayed correct

Reference only

  • the exact lines changed: self.grad += … in __add__, __mul__, tanh (and later exp, __pow__)
  • Karpathy's test values: a = 3 for a + a; a = −2, b = 3 for f = (a·b)·(a+b) = −6
  • engine.py L13–L33

    Check

  2. mechanism Walk through b.backward() for b = a + a with the buggy engine: which closure runs, which lines execute, and what is a.grad after each line?
    Check

  3. tradeoff += fixes reuse but makes grads pile up across calls. Would you rather have backward() reset every grad to 0 at its start, or leave resetting to the training loop? What does each choice cost?
    Check

    • the order comes from the topological sort, which walks the set _prev

5 · Predict commit to an answer before revealing

With the fixed += engine, you build f = (a·b)·(a+b) at a=−2, b=3 and call f.backward() twice without resetting anything. Does a.grad become 2 × (−3) = −6? Commit to a number.

Reveal

No, it becomes −9.0 (and b.grad −24.0). The second call resets only f.grad to 1; the intermediate grads d and e also accumulate (d.grad 2, e.grad −12), so the leaves receive the doubled shares on top of the −3 they already had: −3 + 2·(−3) = −9. Accumulation compounds through the graph, which is why stale grads are so damaging.
