Checkpoint 2: the engine, checked and trained

Ties together automatic backward, the += bug, more operations, and PyTorch agrees and from neuron to MLP to a training loop, looping back to backprop by hand and to the toolkit's Python you need, chain rule and softmax and cross-entropy. Lecture 1, 1:09:02 to 2:14:03.

What this ties together, and why now

The second half of the lecture turns your hand backprop into an engine and then puts the engine to work. Each op stores its own _backward, and a topological order runs them. += makes a reused Value collect every share of its gradient. New ops need only a forward and a local derivative, and PyTorch gives the same numbers. The training loop repeats forward, zero_grad, backward, update.

Two of those pieces meet in a way that is easy to miss. The += that fixes reused nodes is the same += that makes a forgotten zero_grad pile gradients up across steps. The next lecture swaps scalars for tensors and keeps all of this, since Karpathy says of tensors that “none of the math changes” (0:00:25). Tie it together here, while the engine is still small enough to read.

How to use this page. Close the cards. Answer each question in writing before you open its Check. The questions are mixed, and none of them names its card. Missed ones point to the exact section to reopen.

1 · Mixed retrieval

  1. For f = (a·b)·(a + b) with a = −2 and b = 3, your engine prints a.grad = 3.0 and b.grad = −2.0. A colleague runs the same code and gets −6.0 and −6.0. What is the bug, why do the two runs disagree, and what are the right answers?
    Check
    • the closures assign with =. a and b each reach f along two paths (through d = a·b and e = a + b), so the second share overwrites the first
    • which share survives depends on which closure runs last, and that order comes from _prev, which is a set. The via-d share gives 3, −2; the via-e share gives −6, −6
    • with +=: a.grad = e·b + d·1 = 3 − 6 = −3, and b.grad = e·a + d·1 = −2 − 6 = −8, in any order. This is the multivariate chain rule: the paths add

    Missed it? Reopen the += bug, “The general case: two branches meet again”, and the chain rule, “When x is used twice, the paths add”.

  2. which idea applies?You want a new activation in your engine. You can write it as one op with a hand-derived local derivative, or build it from exp, +, − and / that you already have. Which idea says both give identical gradients, and what does each choice cost?
    Check
    • the chain rule doesn't care how finely a function is split: the product of local derivatives along the longer path equals the single op's derivative. For tanh, both give x1 −1.5, w1 1.0, x2 0.5, w2 0.0
    • one op: fewer nodes (10 for the neuron), but one more derivative to write, and to get wrong
    • from primitives: no new derivative to write, but more nodes to store and walk (18), and it relies on += because the exp node feeds both e − 1 and e + 1

    Missed it? Reopen more operations, “Rebuilding tanh out of exp” and “So should tanh be one op or many?”.

  3. MLP(3, [4, 4, 1]) has how many parameters? In one computation of the loss on the 4-example dataset, how many times is a single first-layer weight used, and what does that mean for how its gradient is built?
    Check
    • (3·4 + 4) + (4·4 + 4) + (4·1 + 1) = 16 + 20 + 5 = 41
    • 4 times, once for each example's forward pass, because the loss adds all four squared misses
    • so its .grad is the sum of 4 shares, and the network only trains correctly because the closures use += (“never reuse a Value” is impossible here)

    Missed it? Reopen from neuron to MLP, “Neuron → Layer → MLP”, and the += bug, “Why it beats the alternatives”.

  4. debuggingSame seed (1337), same 20-step loop at lr 0.1. Your loss prints 6.0054 at step 0, which is right. At step 5 it prints 0.0016, which looks great, but at step 7 it jumps to 0.174 and at step 11 to 3.78. What's wrong, and why did step 5 look better than a correct loop?
    Check
    • the loop is missing p.grad = 0.0 before loss.backward(), so each step's grad is the sum of every gradient so far
    • that acts like a growing step size. On this easy problem it races ahead (0.0016 against 0.7001 at step 5), then overshoots near the minimum, where the fresh gradient is tiny but the stale sum still pushes hard
    • a correct loop reaches 0.0178 at step 19. The buggy one ends at 0.000000 with every tanh saturated, so the gradient is exactly 0 and the net can't learn anything more. Bugs hide

    Missed it? Reopen from neuron to MLP, “Forgetting zero_grad”, and the += bug, “Does += ever cause trouble?”.

  5. which idea applies?Your engine gives the neuron x1.grad = −1.5, while PyTorch's cell prints −1.5000003851533106. Is one of the engines wrong? Which idea settles it, and how do you make the two agree?
    Check
    • comparing against an independent engine: agreement to 6+ decimals is strong evidence that both are right
    • the gap is data entry, not autograd. torch.Tensor([...]) stores float32 first, so b becomes 6.881373405456543 before .double()
    • build the tensors as float64 from the start and PyTorch gives −1.4999999999999998

    Missed it? Reopen more operations, “PyTorch gets the same numbers”.

  6. After o.backward() on the neuron, run A shows every grad as 0.0. Run B shows only o = 1.0 and n = 0.5, with everything else 0. Run C crashes with 'NoneType' object is not callable. Name the one-line mistake behind each.
    Check
    • A: the base case self.grad = 1.0 is missing, so every closure multiplies by a 0 from above
    • B: you forgot reversed(). Nodes run inputs-first, before their gradient has arrived, and n receives its 0.5 last, when nothing is left to pass it on to
    • C: out._backward = _backward() calls the function and stores its return value, None, instead of the function itself

    Missed it? Reopen automatic backward, “Three ways to break it, measured”, and the Python you need, “Closures”.

  7. The update is p.data += -0.1 * p.grad. Why the minus sign? And the inputs xs get a .grad too, so why doesn't the loop update them? Use the weight layer 0, neuron 0, w[0] (data 0.2355, grad −0.4537) as your example.
    Check
    • a gradient points toward more loss, and training wants less. Stepping against it gives 0.2355 − 0.1 × (−0.4537) = 0.2809, so the weight rises because raising it lowers the loss
    • it is the one-step card with the sign flipped: along the gradient, L went −8 → −7.2865; against it, −8 → −8.7263
    • xs are fixed facts about the world, so only the 41 parameters are stepped. Input grads matter only when the “input” is another neuron's output

    Missed it? Reopen one step along the gradient, “Is this a training step yet?”, and from neuron to MLP, “The loop, and the loss falling”.

  8. Why does build_topo append a node only after all its children? And what goes wrong if backward instead recurses from o and passes each gradient down as soon as it has one?
    Check
    • appending after the children makes the list run inputs → output. Reversed, every node's _backward runs only after all the nodes that use it have added their share
    • when passing down eagerly, a Value that feeds two ops can pass its gradient on before the second share has arrived, so everything below it gets an incomplete grad. On a tree like the neuron you'd never notice
    • the visited set stops a shared node from being added twice. Because it's a set, the order of siblings varies between runs, but the grads never do

    Missed it? Reopen automatic backward, “Why it beats the alternatives”, and the Python you need, “A set and recursion”.

3 · Integrated build: Karpathy's softmax exercise on your engine, checked and trained

▶ Build itruns on your M3 · under 1 s

What it reinforces: a new op is a forward plus a local derivative (more ops), sum() needs __radd__ (Python you need), a node feeding several ops collects its shares with += (the += bug), one backward() call fills everything (automatic backward), checking against nudges and PyTorch, and the four-line loop (training loop). The loss is the one from softmax and cross-entropy.

Where: your Value class from the cards (with exp, __pow__, / and __radd__) in the course venv. This is section 2 of the lecture's exercise Colab.

  1. Add a log op. Its local derivative is 1/x.
  2. Build the loss. Start from logits [0, 3, −2, 1] as Values, apply softmax, and take the loss as the NLL of class 3: 
    def log(self):
    out = Value(math.log(self.data), (self,), 'log')
    def _backward():
        self.grad += (1 / self.data) * out.grad
    out._backward = _backward
    return out
Value.log = log

def softmax(logits):
    counts = [l.exp() for l in logits]
    denom = sum(counts)        # needs __radd__
    return [c / denom for c in counts]
loss = -softmax(logits)[3].log()
  3. Backward and check. Call loss.backward(), then compare each logit's grad with a central difference (h = 10⁻⁶) and with torch.softmax plus torch.log on a float64 tensor.
  4. Train it. Treat the 4 logits as parameters and run 20 steps at lr 0.1: forward, zero the grads, backward, p.data += -0.1 * p.grad. Print the loss at steps 0, 1, 5, 10 and 19.
  5. Break it. Delete the zero_grad line and run again.

Done when: your grads read [0.04177, 0.83902, 0.00565, −0.88645] (the Colab's expected values); they match the numerical check to better than 10⁻⁹ and PyTorch to about 10⁻¹⁶; the correct loop takes the loss from 2.1755 to 0.5625; and you can explain why the buggy loop's lower final loss is not a good sign.

  • the grads are the probs minus a one-hot for class 3: 0.11355 − 1 = −0.88645, and the other three are just their probs. So the gradient pushes the correct logit up and every other logit down
  • the loss checks against the toolkit's shortcut, log of the total minus the correct logit: log(1 + e³ + e⁻² + e) − 1 = log 23.94 − 1 = 2.1755
  • denom feeds all four divisions, so its grad is four shares added together. With = in the closures it would keep only one of them
  • the forgot-zero_grad run ends lower, just as on the MLP. The stale grads act as a growing step size (after 20 steps, the logit for class 3 has climbed to 9.502, against 2.317 in the correct run), and that only works because the problem is easy
