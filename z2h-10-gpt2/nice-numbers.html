Nice numbers: 50,257 → 50,304

Also called: vocab padding, padding to a multiple of 64 / 128, nice vs ugly numbers. Lecture 9 · nice/ugly numbers. vocab size 50257 → 50304, 93ms · 2:06:54

Prime · 2 minutes before you read

The problem: GPU kernels are built to chew through matrices in fixed power-of-two blocks. When one dimension doesn't divide evenly, the leftover block takes a slower special-case path, and you pay for it every step without seeing why.

Where it fits: This is the last rung of the A100 speed ladder, after precision, torch.compile and flash attention took a step from ~1000 ms to 96.5 ms. It reuses the output layer lm_head from the module card and the shared matrix from weight tying.

In one breath: GPU matmul kernels chop their work into fixed-size blocks whose sides are powers of two. A size that doesn't divide evenly, like GPT-2's vocabulary of 50,257 tokens, leaves a ragged leftover block that is handled less efficiently. Karpathy pads the vocabulary to 50,304 with 47 tokens that never occur. That is slightly more arithmetic, yet the training step on an A100 got faster: 96.5 → 93 ms.

Predict first: padding adds 47 fake tokens, so the output layer does about 0.09% more multiply-adds. On the A100, does a training step get slower, stay the same, or get faster?

Faster: 96.5 → 93 ms per step, about 3.6%. The extra work is real (47 / 50,257 = 0.094% more in the output matmul), but every block of the matmul is now full, so the kernel never runs its slower edge-case path. Karpathy adds that on an earlier PyTorch version the same change gave something like 30% (2:14:28).

The one ugly size in the model

A number is "nice" when it has many factors of 2, so it splits evenly into the power-of-two blocks the hardware likes. Factor every size the matmuls in GPT-2 124M see (computed):

50,257 is odd, so it has no factor of 2 at all: 50,000 BPE merges + 256 byte tokens + 1 <|endoftext|>. 50,304 is the next multiple of 64, and also of 128 (393 × 128).

Where the last tile goes

The output layer lm_head multiplies the final vectors, shape (B·T, 768), by its weight, shape (V, 768), to get one score (logit) per token: shape (B·T, V). A GPU kernel computes that output in tiles, fixed blocks of columns. Take a tile width of 128 (illustrative; each kernel picks its own tile shapes):

tiles 1–392
392 × 128 = 50,176 columns
tile 393:
81 real
47 missing: edge path
V = 50,304nice
tiles 1–392
392 × 128 = 50,176 columns
tile 393:
81 real
47 fake tokens

Not to scale: the last tile is drawn large. Both sizes need 393 tiles. The ugly one ends in a partial tile the kernel must treat as a special case; the nice one fills it with 47 columns of scores nobody uses.

⌈V128⌉tiles needed 2·B·T·C·VFLOPs of the lm_head forward
Vvocabulary size: columns of the output50,257 or 50,304 B, Tbatch size and context length; B·T rows of vectors16 × 1024 on the A100 Cchannels, the model width n_embd768 ⌈ ⌉round up to a whole number of tiles
tiles 50,257 / 128 = 392.63 → 393 (last tile 50,257 − 392×128 = 81 wide) 50,304 / 128 = 393.00 → 393 (every tile full) FLOPs 2 × 16 × 1024 × 768 × 50,257 = 1.2648e12 2 × 16 × 1024 × 768 × 50,304 = 1.2659e12 (+0.094%) params 47 × 768 = 36,096 extra, so 124,439,808 → 124,475,904 step 96.5 ms → 93 ms = 3.6% faster (A100, B=16, T=1024)

Counting a multiply-add as 2 FLOPs (floating-point operations). The padding only touches the tables whose size is V: wte and lm_head, which are one shared matrix after weight tying.

What about the fake tokens? They never appear in the data, so they are never the right answer. The cross-entropy loss keeps pushing their scores down, and the model learns to give them almost zero probability, the same way it learns that some real tokens are rare.

▶ Build itruns on your M3 · about 14 s

When: pause the video at 2:06:54. The model change is one argument; then time the matmul it affects on MPS (Apple's GPU backend in PyTorch).

model = GPT(GPTConfig(vocab_size=50304))   # was 50257
import time, statistics, torch
dev = "mps"; BT = 2048                  # B*T rows of vectors
def lm_head_ms(V):
    torch.manual_seed(1337)
    x = torch.randn(BT, 768, device=dev, requires_grad=True)
    W = torch.randn(V, 768, device=dev, requires_grad=True)
    ts = []
    for _ in range(11):                   # first run = warm-up
        t0 = time.time()
        (x @ W.t()).backward(torch.ones(BT, V, device=dev))
        torch.mps.synchronize()             # wait for the GPU
        ts.append(time.time() - t0)
    return statistics.median(ts[1:]) * 1000
print(lm_head_ms(50257), lm_head_ms(50304))

Why it beats the alternatives

✗ Keep 50,257

Correct, but the output matmul ends in a ragged 81-wide tile that runs the kernel's slower edge path: 96.5 ms per step on the A100.

✗ Trim to 50,176 (392 × 128)

Nicer and smaller, but 81 real tokens would lose their ids, so the GPT-2 tokenizer could no longer encode all text.

✗ Retrain the tokenizer to 50,304

All tokens would be real, but you lose compatibility with GPT-2's tokenizer and weights, and must re-tokenize every shard of data.

✓ Pad with 47 unused tokens

One argument changes. The tokenizer and data stay the same, the model learns to ignore the extra ids, and every tile is full: 93 ms.

Is padding always a win?

No. The gain depends on the kernels your framework picks. Karpathy measured about 4% on PyTorch at the time of the video and says an earlier version gave something like 30%; on your M3 the effect is lost in the noise. It is a cheap change worth measuring, not a law. The same thinking applies to other sizes you choose, such as the batch size B: prefer 16, 32 or 64 over 17.

Two things stay at 50,257. OpenAI's checkpoint has 50,257 rows, so from_pretrained builds the model with the original size. And the tokenizer only knows ids 0–50256: tiktoken's decode([50300]) raises KeyError: 'Invalid token for decoding: 50300' (checked for this card). The trained model gives the fake ids almost no probability, so in practice sampling never picks them.

Understand and remember

  • GPU matmul kernels split the output into power-of-two tiles → a size like 50,257 (odd, 29 × 1733) leaves a partial last tile → the kernel runs a slower boundary path for it → padding to 50,304 (27 × 3 × 131) fills every tile and removes that path
  • Padding adds 47 columns → 0.094% more lm_head FLOPs, but no ragged tile → wall time is set by how well the hardware is used, not by the FLOP count → 96.5 → 93 ms on the A100 (the same lesson as flash attention)
  • The 47 extra ids never appear in the data → they are never the correct next token → cross-entropy keeps pushing their logits down → the model learns to give them almost no probability, so the tokenizer and data need no change
  • The gain comes from the kernel library, not from maths → it changes with PyTorch version and device (~30% earlier, ~4% in the video, noise on an M3 via MPS) → measure it on your hardware instead of assuming it
  • detail that matters V only sizes the tied wte/lm_head matrix and the logits → the padding costs 47 × 768 = 36,096 parameters (124,439,808 → 124,475,904) and nothing else in the blocks changes

Reference only

  • the one-line change: GPT(GPTConfig(vocab_size=50304)) in train_gpt2.py L339, commit 7230096
  • 50,257 = 50,000 BPE merges + 256 byte tokens + 1 <|endoftext|>
  • from_pretrained keeps vocab 50,257 so OpenAI's checkpoint loads
  • tiktoken's decode raises KeyError for ids ≥ 50,257
  • timing on MPS needs torch.mps.synchronize() before reading the clock

    Check
    • nice = many factors of 2, so it splits evenly into power-of-two tiles
    • 50,257 is odd (29 × 1733): not even divisible by 2

  2. mechanism Walk through what the kernel computing logits = x @ W.t() does with the last columns when V = 50,257, and what changes at V = 50,304.
    Check
    • output is (B·T, V), computed tile by tile
    • with 128-wide tiles, 392 full tiles cover 50,176 columns and 81 are left over
    • the leftover tile needs special boundary handling, which is slower
    • at 50,304 the 393rd tile is full (81 real + 47 fake columns) and runs the same fast path as the rest
  3. tradeoff Your team wants to pad every model's vocab to a multiple of 128 by default. What does it cost, what could it buy, and what would you check first?
    Check
    • cost: a few extra rows (47 × 768 = 36,096 params here), tiny extra FLOPs, and ids the tokenizer can't decode
    • buy: a few percent to tens of percent, depending on kernels and framework version
    • check: time a real training step before and after on the target hardware, synchronizing the device
    • keep the original size when loading pretrained checkpoints
  4. concept Why doesn't the model need any special code to stop it predicting the 47 fake tokens?
    Check
    • they never occur as a target in the data
    • cross-entropy lowers the probability of every wrong token, so their logits are pushed down every step
    • the same mechanism that makes rare real tokens unlikely

4 · Compare against what you already know

vs Kernel fusion: torch.compile and flash attention: Flash attention and vocab padding both add or keep arithmetic yet make the step faster. What is the shared principle, what different bottleneck does each remove, and how would each fail to help?

Check
  • shared: time depends on how the hardware is used, not on FLOP count
  • flash: avoids writing the T×T attention matrix to slow memory (memory traffic)
  • padding: avoids the ragged last tile in the lm_head matmul (kernel efficiency)
  • flash helps little at short T; padding helps little when the kernel handles odd sizes well (newer PyTorch, MPS)

vs Where the time goes: fp32 → TF32 → bf16: TF32 promised 8× but gave 3×; padding promised nothing on paper and gave 3.6%. What does each say about reading hardware numbers?

Check
  • TF32: peak FLOPS only helps if the step is compute-bound, and GPT-2 was largely memory-bound
  • padding: the FLOP count went up, yet time went down because the kernel got a friendlier shape
  • both: measure wall time per step, with a synchronize, rather than predicting from FLOPs

vs Weight tying: one matrix, two jobs: Padding and tying both change the size of the wte/lm_head matrix. How does each change it, and why?

Check
  • tying removes one of two 50,257 × 768 matrices: −38,597,376 params, for better learning and memory
  • padding grows the shared matrix by 47 rows: +36,096 params, purely for speed
  • with both, the shared matrix is 50,304 × 768 = 38,633,472

5 · Predict commit to an answer before revealing

The first-loss card expects an initial loss of −ln(1/50257) = 10.82. With the vocab padded to 50,304, does that sanity-check value change, and by how much?

Reveal

Barely. A fresh model spreads probability almost evenly over all 50,304 outputs, including the fake ones, so the expected loss is −ln(1/50304) = 10.8258 instead of 10.8249: up by 0.0009. At init the 47 fake tokens hold 47 / 50,304 = 0.093% of the probability, which the loss then drains away.
