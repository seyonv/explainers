Half-million-token batches: gradient accumulation and DDP

Also called: micro-batching, gradient accumulation steps, data parallelism, DistributedDataParallel (DDP), all-reduce. Lecture 9 · gradient accumulation · 2:34:09 and distributed data parallel (DDP) · 2:46:52

Prime · 2 minutes before you read

The problem: The GPT-3 recipe you borrowed assumes one weight update per 524,288 tokens, but one forward pass only holds 16,384 tokens on an A100 and about 4,096 on your M3 (B=4, T=1024). Shrink the batch and the borrowed learning rate no longer fits; try to fit it all at once and you run out of memory.

Where it fits: You have a full training step with AdamW, clipping and the learning-rate schedule (the optimizer-recipe card). This card changes how many tokens one step averages over, and then spreads that work across 8 GPUs. It reuses micrograd's lesson that gradients accumulate with +=.

In one breath: GPT-3's recipe updates the weights once per 524,288 tokens, far more than fits in memory at once. Gradient accumulation runs many small forward/backward passes (micro-steps) and lets their gradients add up before a single optimizer step; dividing each micro-loss by the number of micro-steps turns that sum into the mean the big batch would have given. DDP then splits those micro-steps across 8 GPUs, one process each, and averages their gradients before every update.

Predict first: a tiny net's loss is the mean over a batch of 4 examples. You instead call backward() once per example, 4 times, without dividing anything. How do the accumulated gradients compare with the batch-of-4 gradients?

Exactly 4× too large. In the lab, the first weight's gradient is −0.0765 for the batch of 4 and −0.306 = 4 × −0.0765 for the four separate calls. backward() adds into .grad, but the batch loss averages, so the 1/4 is lost. Divide each micro-loss by 4 and the numbers match to every printed digit.

Why 219 tokens, and why it needs accumulation

The batch size is how many tokens the loss is averaged over before each optimizer step. Karpathy copies GPT-3 Small's 0.5M tokens and rounds it to a power of two: 219 = 524,288. A forward pass on the A100 holds a micro-batch of B = 16 sequences × T = 1024 tokens = 16,384 tokens, so one real step is 32 micro-steps:

The bug: backward() adds, but the loss averages

Cross-entropy (and the lab's toy squared error) returns the mean loss over the batch. Split that batch into pieces and the mean becomes a sum of pieces, each weighted by 1/N:

▶ Build itruns on your M3 · about 15 s

When: pause the video at 2:34:09 and turn your training step into an accumulating one before watching on. Keep total_batch_size tiny (4096 = 4 micro-steps of B=4, T=256) so a step takes seconds.

total_batch_size = 4096      # 524288 (2**19) in the real run
B, T = 4, 256
grad_accum_steps = total_batch_size // (B * T)   # 4
for step in range(3):
    optimizer.zero_grad()
    loss_accum = 0.0
    for micro_step in range(grad_accum_steps):
        x, y = train_loader.next_batch()
        x, y = x.to(device), y.to(device)
        logits, loss = model(x, y)
        loss = loss / grad_accum_steps   # sum of grads -> mean
        loss_accum += loss.detach()      # for printing only
        loss.backward()
    norm = torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
    optimizer.step()

DDP: eight copies of the model, one averaged gradient

torchrun --standalone --nproc_per_node=8 train_gpt2.py starts the same script 8 times. Each copy (a process) reads three environment variables: RANK (which copy it is, 0–7), LOCAL_RANK (which GPU on this machine to use) and WORLD_SIZE (8). Every process builds the same model with the same seed, so all 8 start with identical weights. Wrapping it in DDP(model) adds one thing: during backward(), the gradients are all-reduced, meaning averaged across the 8 GPUs and handed back to every one of them. Same weights plus same gradient means the same update, so the copies never drift apart.

  • Different data per rank. The loader starts rank r at chunk r and jumps 8 chunks at a time (L238, L246), so no two GPUs see the same tokens.
  • Sync once per step. With accumulation, averaging after every micro-step would send the gradients over the wire 4 times for no benefit. Karpathy sets model.require_backward_grad_sync to true only on the last micro-step (L490–L491).
  • One process talks. Rank 0 is the master_process that prints and saves. Its loss_accum would describe only its own 1/8 of the tokens, so it's all-reduced too before printing (L501–L502).
# the DDP setup, trimmed from train_gpt2.py L290-L300 (CUDA only)
ddp = int(os.environ.get('RANK', -1)) != -1   # launched by torchrun?
if ddp:
    init_process_group(backend='nccl')
    ddp_rank = int(os.environ['RANK'])
    ddp_local_rank = int(os.environ['LOCAL_RANK'])
    ddp_world_size = int(os.environ['WORLD_SIZE'])
    device = f'cuda:{ddp_local_rank}'
    master_process = ddp_rank == 0
# ... after building the model:
model = DDP(model, device_ids=[ddp_local_rank])

Needs a rented GPU box: the script asserts CUDA, and NCCL is NVIDIA's communication library. On the M3, labs/big-batch.py prints [skipped] DDP ... needs an NVIDIA GPU (CUDA).

Why it beats the alternatives

✗ Just train with B=16

An update every 16,384 tokens averages 32× fewer tokens than GPT-3's, so its gradient is noisier, and the borrowed learning rate and schedule were tuned for 0.5M-token batches. You'd have to re-tune the recipe.

✗ Raise B until 2¹⁹ tokens fit

That is B=512 at T=1024 in one forward pass. The final script runs B=64 on an 80 GB A100; on the M3, B=8 at T=1024 already stalled in swap.

✗ Accumulate without the division

The gradient is N× the mean, yet nothing looks broken: clipping to 1.0 and AdamW's per-parameter scaling hide it. Without the division at 16 micro-steps, the lab printed loss 174.958 and norm 460.7, 16× the true values, and still took the same steps. The logs lie, and with plain SGD it's an N× larger learning rate.

✓ Accumulate with the division, spread over DDP

Divide each micro-loss by grad_accum_steps and you get the exact 219-token mean gradient on any hardware. Accumulation trades time for memory; DDP buys back the time with more GPUs.

Does accumulation make training faster?

No. It makes the big batch possible, not quicker: 32 micro-steps take 32 times as long as one. The speed comes only from DDP, which needs several NVIDIA GPUs. On your M3, accumulation gives the correct half-million-token gradient at about 450 s per step, which is why the full run is a rented-GPU job and the laptop runs use a 2,048-token batch instead (the results card).

A bigger batch also isn't free quality. GPT-3 ramped its batch size up during training, and Karpathy skipped that. Early on, the gradients from different examples mostly agree, so a small batch already points the right way and a huge one wastes compute. If you shrink the batch for a laptop run, treat the borrowed 6e-4 learning rate as a starting point to re-check, not a given.

Understand and remember

  • The loss is a mean over the batch → splitting it into N micro-batches turns it into a sum of N terms each weighted 1/N → backward() only adds into .grad → divide each micro-loss by N or the gradient comes out N× too large (4× in the lab: −0.306 vs −0.0765)
  • total_batch_size is fixed by the recipe (219) → memory caps the micro-batch B·T → grad_accum_steps = 219 / (B·T·GPUs) absorbs the gap → the same mean gradient on any hardware, with only the wall-clock time changing
  • DDP runs one process per GPU with identical weights → each rank reads different chunks → all-reduce averages the gradients → every rank takes the same optimizer step → the copies never drift and 8 GPUs do 8× the tokens per step
  • Accumulation trades time for memory (32 micro-steps take 32× as long) → only more GPUs (DDP) buy the time back → on the M3 a 219 step costs ~450 s, ~99 days for the run, so full training is a rented-GPU job
  • detail that matters require_backward_grad_sync is true only on the last micro-step → averaging is linear, so syncing once gives the same gradient as syncing every time → one all-reduce per step instead of grad_accum_steps of them
  • detail that matters loss_accum collects loss.detach() → the printout doesn't keep every micro-step's graph alive in memory, and it must itself be all-reduced or rank 0 prints only its own 1/8 of the loss

Reference only

  • torchrun --standalone --nproc_per_node=8 train_gpt2.py
  • the env vars RANK, LOCAL_RANK, WORLD_SIZE and master_process = ddp_rank == 0
  • init_process_group(backend='nccl'), DDP(model, device_ids=[ddp_local_rank]), raw_model = model.module
  • the assert that total_batch_size divides evenly by B·T·world_size
  • the loader's start offset B*T*process_rank and stride B*T*num_processes

3 · Retrieve from memory, card closed
  1. concept Explain why the accumulated gradient is wrong without the division, using the batch-of-4 example: what does the batch loss compute, and what does four calls to backward() compute?
    Check
    • the batch loss is (1/4)·Σℓi, so its gradient is (1/4)·Σ∇ℓi
    • four backward calls add ∇ℓ1 + … + ∇ℓ4 into .grad
    • so the result is 4× too big; dividing each ℓi by 4 restores the mean
  2. mechanism Walk through one optimizer step on 8 GPUs at B=16, T=1024: how many micro-steps does each rank run, which tokens does rank 1 see, and when do the GPUs talk to each other?
    Check
    • grad_accum_steps = 524,288 / (16·1024·8) = 4 per rank
    • rank 1 reads chunks 1, 9, 17, 25 (start at its rank, stride 8)
    • gradients add locally for 3 micro-steps; on the 4th backward DDP all-reduces (averages) them
    • every rank then clips and steps with the same gradient
  3. tradeoff You have one A100. Would you rather run B=16 with 32 micro-steps or B=64 with 8, and what limits how far you can push B?
    Check
    • both give the same mean gradient over 219 tokens
    • a bigger B uses the GPU better per token, so it's usually faster
    • B is capped by memory for activations; past it you get out-of-memory (or swap on the M3)
  4. tradeoff A run without the / grad_accum_steps prints a loss 16× too high but, after dividing by 16, trains exactly like the correct run. Why is the bug hidden here, and when would it stop being harmless?
    Check
    • every step's gradient norm is above 1.0, so clipping rescales it to norm 1 either way
    • AdamW divides each update by the running size of that parameter's gradient, so a constant factor mostly cancels
    • it bites with plain SGD (an N× larger learning rate), once norms fall below the clip threshold, and whenever you read the logged loss or norm
  5. tradeoff Your M3 runs the recipe correctly with 128 micro-steps of B=4, T=1024. What have you gained over training with a small batch, and what haven't you gained?
    Check
    • gained: the exact 219-token gradient the borrowed hyperparameters expect
    • not gained: speed; at ~1,100–1,700 tok/s a step takes minutes and the run takes months
    • DDP isn't available on the Mac (it asserts CUDA and uses NCCL)

4 · Compare against what you already know

vs The += bug: reused nodes add their gradients: In micrograd, += in _backward fixed a bug; here the same adding behaviour of .grad is used on purpose. What is fundamentally the same, and why does accumulation across micro-steps need an extra division that micrograd's did not?

Check
  • same: gradients from several contributions must be summed, never overwritten
  • micrograd sums paths through one expression, which is exactly the chain rule
  • micro-steps sum gradients of N separate means, but the target is one mean, so each term needs 1/N
  • failure modes: = instead of += drops paths; no /N inflates the gradient N×

vs Minibatches: noisy but fast: The makemore MLP trained on minibatches of 32 examples and took many noisy steps. Here the batch is 524,288 tokens. What does each choice trade, and when would you pick each?

Check
  • small minibatch: cheap, noisy steps, many updates per second; fine for small models and quick experiments
  • huge batch: each step is costly but the gradient is much less noisy, matching the recipe's tuned learning rate
  • accumulation lets you pick the big batch without the memory for it
  • a too-small batch is noisy; a too-big one wastes compute when examples' gradients already agree (why GPT-3 ramped it)

vs Where the time goes: fp32 → TF32 → bf16: bf16 autocast and DDP both make training faster. What different bottleneck does each attack, and why can't bf16 replace DDP for the 10B-token run?

Check
  • bf16: fewer bits per number, so less memory traffic and faster matmuls on one GPU (1000 → 300 ms ladder)
  • DDP: more GPUs working on different data at once
  • bf16 gives at most a few × on one chip; DDP scales with the number of GPUs
  • bf16 fails through rounding; DDP fails through bad data splits or wrong syncing

You rent 4 A100s instead of 8 and keep B=64, T=1024. What is grad_accum_steps now, and does the loss curve plotted against step number change?

Reveal

524,288 / (64·1024·4) = 2. Each step still averages the gradient over 219 tokens, so the loss per step follows essentially the same curve (up to data order and float rounding), and the learning-rate schedule needs no change. Only the wall clock changes: each step takes about twice as long.
