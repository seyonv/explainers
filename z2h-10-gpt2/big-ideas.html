The six big ideas of reproducing GPT-2

Big idea 1: Write GPT-2 with OpenAI's names and shapes, and its real weights become your test

A lookup at the bottom, 12 pre-norm Blocks adding onto a residual stream, and a scoring layer at the top that shares the lookup's matrix. Name every piece like the checkpoint, transpose the four Conv1D weights, and your logits match Hugging Face's.

mirror the Hugging Face names so every OpenAI tensor loads one to one · Karpathy, paraphrased, 0:28:08

Why it matters: Once your module reproduces OpenAI's logits, every later change (flash attention, a padded vocabulary, a new init) is a change to code you own and have already checked. It is the z2h-8 GPT, arranged the way GPT-2 is.

Big idea 2: Predict the numbers before training: 10.82 at step 0, then crush one batch

A model that knows nothing spreads its bets over 50,257 tokens, so its first loss is ln 50257 = 10.82. Then train on one batch: if 50 steps can't memorise 128 answers, something is wired wrong.

“seeing something around 11” · Karpathy, 0:55:49

Why it matters: Every run in this lecture starts with these two checks. A wrong number at step 0, or a loss that won't fall on one batch, costs a minute to see instead of an overnight run. It is the same habit as ln 27 in makemore and overfitting the MLP's batch.

Big idea 3: Every Block adds to the residual stream twice, so the layers that write to it start 1/√24 smaller

Variances add, so 24 unscaled adds grow the stream like √24. GPT-2 draws every weight at std 0.02 (near 1/√768 = 0.036) and gives the two c_proj layers per Block 0.02/√24 = 0.00408.

“roughly in the vicinity” · Karpathy, 1:16:34

Why it matters: It is the 1/√fan_in reasoning of Kaiming init, applied to depth. The model starts with signals of a sensible size, and its loss at init sits near the 10.82 of idea 2.

Big idea 4: The step waits on memory, not maths: move fewer bytes and it runs 11× faster

TF32 promised 8× faster matmuls and delivered 3×, because most of the step is data travelling between the GPU's big memory (HBM) and its tiny fast chip. What pays is moving fewer bytes: fewer bits, fused kernels, no T × T matrix in HBM, full tiles.

“because a lot of these workloads are memory bound” · Karpathy, 1:38:35

Why it matters: Speed is what makes the reproduction affordable: without it the same run would take about 11× as long. On your M3 the ratios differ (TF32 does nothing there) but the principle holds: SDPA is 7.88× faster than manual attention at T = 1024.

Big idea 5: Borrow GPT-3's recipe, and build its half-million-token batch from micro-batches divided by N

GPT-2's paper is vague, GPT-3's lists every setting for a model of the same shape. Its batch is 2¹⁹ = 524,288 tokens, so you add up micro-batch gradients (each loss divided by their count), clip to norm 1, and set the lr from warmup plus cosine.

“cosine decay for learning rate down to 10% of its value over 260 billion tokens” · Karpathy, 2:21:27

Why it matters: Hyperparameters that OpenAI tuned on a same-shaped model are a free, solid starting point. The / N is micrograd's += accumulation again: backward() adds, the loss averages, so you divide yourself. DDP then spreads the micro-batches over 8 GPUs.

Big idea 6: Judge the run on text it never trained on, against GPT-2's own scores

Every 250 steps the loop scores held-out shard 0 and 10,042 HellaSwag questions. After 10B tokens the from-scratch model passes GPT-2 124M on both, with about 10× fewer tokens; 40B reaches 33.24% against GPT-3's 33.7%.

“only training on 10 billion tokens while gpt2 was trained on 100 billion” · Karpathy, 3:44:50

Why it matters: A falling training loss proves little on its own. A held-out loss and an outside task, read against fixed baselines and with their noise in mind (±0.47 points on 10,042 examples), are what turn a training run into a claim. It is the MLP's train/dev split, grown up.

Understand and remember

  • Module names and shapes match OpenAI's checkpoint → the 149 tensors copy by name (four Conv1D kinds transposed) → logits agree with Hugging Face to 4.58e-05 → the architecture is proven before any training, and later edits are changes to checked code
  • An untrained model spreads its bets over 50,257 tokens → step-0 loss ≈ ln 50257 = 10.82 (lab 10.96) checks the init → a big model must memorise one small batch (10.96 → 0.36 in 50 steps) → that checks backward, zero_grad and the optimizer before any long run
  • Each Block adds to the residual stream twice → 24 independent adds and variances add → std grows like √24 → scale the two c_proj layers to 0.02/√24 = 0.00408 → the stream ends at 0.30 instead of 1.54 at block 12
  • The step is memory-bound (8× faster maths gave 3×) → the wins come from moving fewer bytes: bf16, fused kernels, flash attention never writing T × T, full tiles at 50,304 → 1000 → 93 ms on one A100 with the same loss → which is what makes a 10B-token run a ~2-hour job on 8 GPUs
  • detail that matters backward() adds into .grad while the loss is a mean → accumulating N micro-batches without / N gives an N× gradient → clipping and AdamW's per-parameter scaling hide it, so only the printed loss and norm (N× too big) give it away
  • detail that matters Val loss is measured on shard 0 of our own training distribution → it favours our model over GPT-2's WebText-trained checkpoint → the outside task (HellaSwag, completion-scored, ±0.47 points on 10,042 examples) is the fairer head-to-head

Reference only

  • config: 12 layers, 12 heads, 768 wide, context 1024, vocab 50257 padded to 50304 (124,475,904 params)
  • recipe constants: AdamW betas (0.9, 0.95), eps 1e-8, weight decay 0.1 on 2-D tensors, clip 1.0, max lr 6e-4, min lr 6e-5, warmup 715, max_steps 19,073
  • the A100 ladder: ~1000 → 333 → 300 → 130 → 96 → 93 → 90 ms
  • torchrun --standalone --nproc_per_node=8 train_gpt2.py
  • baselines: val 3.2924, HellaSwag 0.294463 (GPT-2), 0.337 (GPT-3)

    Check

4 · Compare against what you already know

vs The six big ideas of Let's build GPT: The z2h-8 GPT and GPT-2 use the same block: communicate, then compute, added onto a residual stream. What does this lecture add that the character-level GPT didn't need, and which of those additions are about correctness and which about scale?

Check
  • correctness: matching OpenAI's names and loading its weights, the residual-scaled init, tied wte/lm_head
  • scale: a 50,257-token BPE vocabulary instead of 65 characters, context 1024
  • speed: bf16, compile, flash attention, padded vocab, fused AdamW, DDP
  • recipe: GPT-3's hyperparameters and a 219-token accumulated batch, judged on held-out data and HellaSwag

vs The six big ideas of activations, gradients and BatchNorm: Makemore kept activations healthy with gain/√fan_in init and BatchNorm. GPT-2 uses a fixed std 0.02, a 1/√(2·n_layer) residual scale and LayerNorm. What is fundamentally different about the problem each is solving?

Check
  • makemore: activations shrink or saturate through a stack of tanh layers → scale by fan_in, normalise per batch
  • GPT-2: a residual stream that is only ever added to → its std grows with the number of adds → scale the writers by depth
  • LayerNorm normalises each token alone, so no batch coupling and nothing special at test time
  • both check the result the same way: a step-0 loss near ln V (ln 27 = 3.30 there, ln 50257 = 10.82 here)

vs From neuron to MLP to a training loop: micrograd's loop was forward, zero_grad, backward, update. Which of GPT-2's additions live inside that same loop, and which one is micrograd's += bug turned into a feature?

Check
  • the four steps are unchanged; GPT-2 wraps forward in autocast, and adds clip and set-lr before the update
  • gradient accumulation deliberately skips zero_grad between micro-batches so the grads add
  • because they add, each micro-loss must be divided by N to get the mean
  • the same accumulation is why tied wte/lm_head gets the sum of both uses' gradients

Reveal

The step-0 loss is still ≈ ln 50304 = 10.826, because it depends only on the vocabulary, not the depth. grad_accum_steps = 524,288 / (B·T·GPUs) doesn't depend on the model either, so it stays the same unless the bigger model forces a smaller B to fit in memory, which raises the number of micro-steps.
