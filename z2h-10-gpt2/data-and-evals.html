Data and scorecards: FineWeb-Edu, val loss, HellaSwag

Also called: the pretraining corpus and data shards; held-out (validation) loss; a completion-style multiple-choice eval. Lecture 9 · datasets used in GPT-2, GPT-3, FineWeb (EDU) · 3:10:21 · validation data split, validation loss · 3:23:10 · evaluation: HellaSwag · 3:28:23

Prime · 2 minutes before you read

The problem: Tiny shakespeare is 338,025 tokens; a real run needs 10 billion, far too many to tokenize on the fly every step. And once training runs for hours, the training loss alone can't tell you whether the model is learning language or just fitting its data, or whether it's any good at anything.

Where it fits: The overfit-then-load card streamed tiny shakespeare through DataLoaderLite and watched the training loss. This card swaps in FineWeb-Edu, pre-tokenized into shards, and adds the two measurements the final run is judged by: val loss (the train/dev split idea from the MLP course) and HellaSwag.

In one breath: to train for real you need billions of tokens of good text and two honest scorecards. The text is FineWeb-Edu, tokenized once into files of 100M uint16 tokens (shards), with shard 0 kept aside. The scorecards are the loss on that held-out shard, and HellaSwag: 10,042 sentence starts, each with 4 possible endings, where the model "answers" by picking the ending it finds least surprising.

Predict first: a random guess gets 25% on HellaSwag's 4-way questions. What does OpenAI's finished GPT-2 124M score with Karpathy's script?

29.55%, only 4.5 points above chance. Measured on your M3 over all 10,042 examples: 2967 right, and 2967 / 10042 = 0.2955, matching the number in hellaswag.py. The questions were built to fool models, so a small model barely beats a coin. That's what makes it a good scorecard: there is room to climb, and the climb from 25% shows up early in training.

An epoch is one pass over the data; 219 = 524,288 tokens is one optimizer step's batch (the big-batch card). Every document starts with <|endoftext|> (id 50256), so the model sees where one page ends and the next begins. The lab's first train tokens: [50256, 43460, 560, 4992, …] = "<|endoftext|>Literary Research Paper…".

Scorecard 1: loss on text the model never trains on

The training loss is measured on the batch the model is about to learn from. The validation loss ("val loss") is the same cross-entropy, measured on shard 0, which the training loop never reads. Every 250 steps, train_gpt2.py switches to model.eval(), resets the val loader to the start of shard 0, runs 20 batches under torch.no_grad() (no gradients, no update) and averages their losses. Starting from the same place each time means every check scores the same tokens, so two checks are directly comparable.

tokens per val check = 20 batches × B × T = 20 × 64 × 1024 = 1,310,720 (per GPU)

The target line for the results card: OpenAI's GPT-2 124M checkpoint scores 3.2924 on this same shard (loss_baseline in play.ipynb). The comparison is only fair because both models use the same tokenizer on the same tokens.

Scorecard 2: HellaSwag, the completion way

Each HellaSwag example is a context plus 4 endings, one of them right. A big chat model could be asked "A, B, C or D?", but a 124M model has never learned that question format. So Karpathy scores it the way it was trained: glue each ending onto the context, run all 4 rows through the model as a batch of shape (4, N), and see how likely the model finds each ending's tokens. Here is the first validation example, scored by OpenAI's GPT-2:

Computed on CPU in a scratch run.

scorei= 1|Ei|∑t∈Ei−lnp(xt∣x<t)average loss over the ending only pred_norm=argminiscoreilowest average wins
iwhich ending (row) of the 40, 1, 2, 3 Eithe positions of ending i's tokens; |Ei| is how many there are8 for the rubik's cube xtthe token at position t; x<t is everything before it, context included" cube" after "…rub ik 's" −ln pthe per-token cross-entropy you already use for training10.82 = a uniform guess

Plain text: loss per position with reduction='none', multiply by a mask that is 1 on ending tokens and 0 on the context and padding, sum each row, divide by the row's count of 1s. acc_norm picks by this average; acc picks by the plain sum, which penalises long endings just for being long. Predictions are shifted by one (position t predicts token t+1), so the mask is shifted too: the first scored guess is made at the last context token, "he".

When: pause at 3:10:21 and write the tokenizer for shards, then at 3:28:23 write the scorer. fineweb.py would download all 28.5 GB, so stream a couple of million tokens instead (pip install datasets).

enc = tiktoken.get_encoding("gpt2")
eot = enc._special_tokens['<|endoftext|>']      # 50256
def tokenize(doc):
    tokens = [eot]              # every doc starts with eot
    tokens.extend(enc.encode_ordinary(doc["text"]))
    tokens_np = np.array(tokens)
    assert (tokens_np < 2**16).all()      # fits in uint16
    return tokens_np.astype(np.uint16)
fw = load_dataset("HuggingFaceFW/fineweb-edu", name="sample-10BT",
                  split="train", streaming=True)
# fill 1M-token buffers; np.save shard 0 as val, shard 1 as train
logits = model(tokens).logits             # tokens: (4, N)
shift_logits = (logits[..., :-1, :]).contiguous()
shift_tokens = (tokens[..., 1:]).contiguous()
shift_losses = F.cross_entropy(
    shift_logits.view(-1, shift_logits.size(-1)),
    shift_tokens.view(-1), reduction='none').view(4, -1)
shift_mask = (mask[..., 1:]).contiguous()  # 1 on ending tokens
sum_loss = (shift_losses * shift_mask).sum(dim=1)
avg_loss = sum_loss / shift_mask.sum(dim=1)
pred_norm = avg_loss.argmin().item()      # lowest average wins

How the scorecards differ

✗ Training loss

Measured on each step's own batch, so it jumps around. Once the model starts repeating data, it can fall by memorising text instead of learning.

✗ Ask for the letter

"Answer A, B, C or D" needs a model that has learned the quiz format. At 124M it hasn't. The Eleuther harness scores in this multiple-choice style and gives GPT-2 28.92% / 31.14% (acc / acc_norm).

✗ Pick by total loss (acc)

Every extra token adds loss, so a long right ending can lose to a short wrong one. On the full set: 28.58% by sum, 29.55% by average.

✓ Val loss + acc_norm

Val loss is the exact training objective on unseen text. acc_norm needs no quiz skills, starts at chance on day one, and rises as the model learns language. Together they show both fit and ability.

Can you trust these numbers?

Only within limits. Val loss compares models that share a tokenizer and the same val tokens. A different tokenizer changes what a "token" is, so the numbers stop lining up. Shard 0 also comes from FineWeb-Edu itself, so it can't show how the model handles other kinds of text: English-only web pages have little code, maths or other languages. HellaSwag is public web text, so some of it may have leaked into the training data, which would inflate the score. Karpathy flags both caveats.

Completion-style HellaSwag is not the tool for chat models: they can answer the letter directly, so the multiple-choice style suits them. Use it, as here, to watch a small base model climb away from 25%. The same script shows plenty of headroom above GPT-2 124M: gpt2-xl (1558M) scores 48.93%.

Understand and remember

  • Tokenize once and save uint16 shards → training only loads numbers from disk → the GPU never waits on the tokenizer, and 10B tokens cost 20 GB (2 bytes each) instead of 40 GB as int32
  • Shard 0 is never passed to the training loader → its loss measures prediction on unseen text → a gap between train and val loss exposes memorising, and the fixed 20-batch slice makes every check comparable
  • A small model can't do quiz lettering → score each ending by the model's own objective (average per-token loss over the ending, via a shifted mask) → the lowest-loss ending is the answer → the test works from step 0 at 25% and rises with language skill
  • Few examples → a huge noise band (±19 points at 20, ±0.9 at 10,042) → only the full 10,042 set separates GPT-2's 29.55% from chance
  • detail that matters Every document starts with <|endoftext|> (50256) → documents are packed back-to-back in a shard → the model learns that anything after that token is a fresh start, instead of reading one page as a continuation of the last
  • detail that matters acc_norm divides by the ending's token count → long endings aren't penalised for length → on the full set it's 29.55% vs 28.58% by sum

Reference only

  • load_dataset("HuggingFaceFW/fineweb-edu", name="sample-10BT"); 14 parquet files, 28.5 GB
  • file names edufineweb_{val,train}_{index:06d}.npy; 100 shards × 1e8 tokens
  • max_steps = 19073; val every 250 steps with val_loss_steps = 20
  • the HF mirror Rowan/hellaswag (validation split, label as a string) because the GitHub source is DMCA-blocked
  • reference scores: hellaswag.py 0.2859 / 0.2955; Eleuther harness 28.92% / 31.14%; play.ipynb baselines 0.294463 (GPT-2) and 0.337 (GPT-3 124M)
  • uint16 → int32 → long when loading (README errata)

5 · Predict commit to an answer before revealing

Score a randomly initialised GPT-2 with this exact HellaSwag scorer. What accuracy do you expect over all 10,042 examples, and would the result on only the first 20 examples tell you anything?

Reveal

About 25%, chance: a random model gives every token a loss near ln 50257 = 10.82, so the four averages differ only by noise and the argmin is effectively a coin flip. On 20 examples the noise band is ±19 points, so almost any result is possible; the results card's quick run measured 3/20 = 0.15 at step 0 on your M3. You can't read ability off 20 examples.
