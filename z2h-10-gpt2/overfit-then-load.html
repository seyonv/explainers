Overfit one batch, then a real data loader

Also called: the single-batch overfit test, a training sanity check; a data loader, batch iterator. Lecture 9 · optimization loop: overfit a single batch · 0:56:42 · data loader lite · 1:02:00

Prime · 2 minutes before you read

The problem: A 124M-parameter model can train for hours with a silent bug (gradients never cleared, targets not shifted, a step that updates nothing) and the loss will still wobble downwards a little. You need a fast yes-or-no test that the whole training step works, and then a way to feed the model new text every step.

Where it fits: The first-loss card gave you a batch x, y and a loss of 10.96 at init. This card adds the optimizer loop that makes that number fall, the same overfit-one-batch check you did in the MLP course, and the loader that the rest of the lecture grows into sharded, multi-GPU loading.

In one breath: before you train on real data, train on one small batch over and over. A working model, loss and optimizer will memorise it and drive the loss towards 0, which proves the whole pipeline is wired up. Then swap in a data loader that hands out a fresh slice of text each step. The loss now stops around 6.8, because 50 steps is only long enough to learn which tokens are common.

Predict first: same model, same 50 steps, same learning rate. Run A sees one batch 50 times; run B sees 50 different batches. Both start at 10.96. Where does each end?

A ends at 0.36, B at 6.80. A only has to remember 128 fixed answers, so it can nearly memorise them: a loss of 0.36 means it gives the right token about 70% probability. B has never seen its next batch, so all it can learn in 50 steps is how often each token appears. Guessing from token frequencies alone scores 6.32 on this text (computed below), and B is closing in on that.

The loop: four lines per step

Every training step does the same four things. AdamW is the optimizer: the rule that turns gradients into parameter updates. For each parameter it keeps a running average of the gradient (like momentum) and of its size (like RMSprop), so each number gets its own step size. lr = 3e-4 (0.0003) is the learning rate, which scales every step. Karpathy calls it a pretty good default for early debugging (1:01:08).

start e^−10.96 = 0.0000174 ≈ 1/50257, a uniform guess A, step 49 e^−0.3619 = 0.696 the batch is nearly memorised B, step 49 e^−6.7992 = 0.00112 = 56 × the uniform guess

Why B stalls near 6.3: token frequencies

The fastest thing to learn from new text is which tokens are common. Tiny shakespeare uses only 11,706 of the 50,257 tokens; the other 38,551 never appear, and '\n' alone is 11.8% of all tokens. A model that ignores context entirely and always predicts these frequencies scores the entropy of the token distribution:

H=−∑vpvlnpvfrequency-only loss =6.32 ln50257uniform guess =10.82
vone token of the vocabulary11,706 appear in the text pvits share of all tokens in tiny shakespeare'\n': 39,996 / 338,025 = 0.118 Hthe average loss of "always predict the frequencies"6.3161 nats

Computed from the lab's own token row (tiktoken gpt2 on tiny shakespeare). Getting from 10.82 to 6.32 needs no understanding of context: mostly pushing the 38,551 never-seen tokens' scores down. Getting below 6.32 is where the model starts to use the words before.

DataLoaderLite: walk the text in order

1 batch = B × T = 4 × 32 = 128 tokens 1 epoch = 338,025 // 128 = 2640 batches (105 tokens left over) 50 steps = 50 × 128 = 6,400 tokens = 1.9% of one epoch

An epoch is one full pass over the data. Run B saw under 2% of tiny shakespeare, so every batch it saw was new to it.

▶ Build itruns on your M3 · about 30–40 s

When: pause at 0:56:42 and write the loop, run it, then pause again at 1:02:00 and write the loader. Start from your GPT and the (4, 32) batch x, y from the first-loss card.

model = GPT(GPTConfig())
model.to(device)
optimizer = torch.optim.AdamW(model.parameters(), lr=3e-4)
for i in range(50):
    optimizer.zero_grad()           # clear last step's grads
    logits, loss = model(x, y)      # forward + cross-entropy
    loss.backward()                 # fill every p.grad
    optimizer.step()                # update every parameter
    print(f"step {i}, loss: {loss.item()}")
class DataLoaderLite:
    def __init__(self, B, T):
        self.B, self.T = B, T
        text = open('input.txt').read()
        self.tokens = torch.tensor(enc.encode(text))  # tiktoken gpt2
        self.current_position = 0
    def next_batch(self):
        B, T, p = self.B, self.T, self.current_position
        buf = self.tokens[p : p + B*T + 1]
        x, y = buf[:-1].view(B, T), buf[1:].view(B, T)
        self.current_position += B * T
        if self.current_position + B*T + 1 > len(self.tokens):
            self.current_position = 0          # next epoch
        return x, y
train_loader = DataLoaderLite(B=4, T=32)
# inside the loop, first thing each step:
x, y = train_loader.next_batch()
x, y = x.to(device), y.to(device)

Why it beats the alternatives

✗ Start the full run straight away

Real-data loss is noisy (run B jumped from 6.95 to 7.53) and falls slowly, so a wiring bug can hide in it for hours. The one-batch test gives a clear yes or no in under a minute.

✗ Only check the loss at init

Seeing 10.96 next to the expected 10.82 proves the forward pass and the loss. It says nothing about backward, zero_grad or the optimizer; only a falling loss tests those.

✗ Random offsets per batch

The GPT lecture's get_batch draws positions with torch.randint. Fine for small data, but some tokens get drawn twice and others never, and there is no clean epoch or order to split across GPUs later.

✓ Overfit one batch, then stream in order

The overfit proves every part of the step works. The loader then covers each token once per epoch with one integer of state, and later grows into sharded, multi-GPU loading.

Is a loss near 0 the goal?

No. Run A's 0.36 means the model memorised 128 answers, and it would do badly on any other text. That is the point of the test: a big model should be able to memorise a tiny batch, so failing to is a bug signal (a missing zero_grad, targets not shifted, a learning rate far too low). Real progress is measured on text the model hasn't trained on, which is the validation loss in the data-and-evals card.

The test is also weak in one direction: passing it doesn't prove the data is right. A loader that hands out the wrong slices or unshifted targets can still be memorised. And this loader never shuffles; build-nanogpt keeps the documents in order all the way through, which the results card lists as one of its caveats.

Understand and remember

  • One fixed batch = only 128 answers to fit → 124M parameters can memorise them → loss falls towards 0 (0.36 at step 49) → if it doesn't, something in the forward, backward or optimizer step is broken
  • A new batch each step → the model can't memorise what it hasn't seen → the quickest thing to learn is how common each token is → the loss heads for the frequency-only entropy (6.32 here) before context starts to help
  • backward adds into .grad → without zero_grad each step would also carry every earlier step's gradients → the update is wrong even though the loss is computed correctly
  • Walk the token row in B·T chunks, take B·T + 1 tokens → x = buf[:-1], y = buf[1:] are shifted by one → every position gets its next-token target for free → one integer of state covers each token once per epoch
  • detail that matters The printed loss in run B is measured on that step's own batch → it wobbles (6.95 at step 29, 7.53 at step 39) → never read one step's loss as a trend; the validation loss later averages over many batches

Check
  • random offsets: overlapping windows, no epochs, some tokens seen twice and others never in a given number of steps
  • in order: disjoint windows, exact epochs, deterministic
  • the cause is the state: a random draw per batch vs one advancing position
  • random fails to give clean epoch accounting; in-order fails to shuffle, so ordered data can bias training
