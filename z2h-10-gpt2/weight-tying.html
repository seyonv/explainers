Weight tying: one matrix, two jobs

Also called: weight sharing, parameter sharing, tied input and output embeddings. Lecture 9 · parameter sharing wte and lm_head · 1:06:14

Prime · 2 minutes before you read

The problem: GPT-2 needs a table to turn token ids into vectors at the bottom and a layer to turn its final vector into 50,257 scores at the top. Built separately, those are two 50,257 × 768 matrices: almost a third of the model spent twice on the same tokens.

Where it fits: You have the full GPT module and a loss that falls. This card revisits the embedding lookup from the MLP course and the output layer you wrote in the module card, and notices they are the same shape.

In one breath: GPT-2 has one table with a row of 768 numbers for each of its 50,257 tokens, and it uses that table at both ends. At the bottom, wte (the token embedding) looks up a token's row to feed it in. At the top, lm_head (the output layer) scores the model's final vector against every row to decide which token comes next. One line of code makes the two the same tensor, which removes 38.6 million parameters.

Predict first: tying removes one whole matrix from GPT-2 124M. About what share of the model's parameters does that save: 1%, 10% or 30%?

About 31%. The matrix is 50,257 × 768 = 38,597,376 numbers, which is 31.0% of the tied model's 124,439,808. Without tying, the model would have 163,037,184 parameters. A single lookup table is almost a third of the network because the vocabulary is so large.

The same rows, read two ways

xt=W[it]wte: look up one row logitst,j=ht·W[j]lm_head: dot product with every row j
Wthe shared matrix, one row per tokenshape (50257, 768) itthe token id at position t of the input0 … 50256 xtthat token's embedding, the vector the blocks start from768 numbers htthe final vector at position t, after 12 blocks and ln_f768 numbers ja candidate next token; one score (logit) for each50,257 scores

In PyTorch, nn.Linear(768, 50257) stores its weight as (out, in) = (50257, 768), exactly the shape of the embedding table. That is why the two can be one tensor with no transpose.

Why share? If two tokens mean similar things, you want their rows close together at the input, and you want them to get similar scores at the output. With one matrix, both happen together: a row that moves toward ' queen' moves the input vector and the output score at once. The idea comes from Attention Is All You Need and the work it cites (Press & Wolf, 2016). The trained checkpoint shows the rows of related tokens really do end up close:

TokenIts 5 nearest rows in OpenAI's wte (cosine similarity, measured)
' king'' kings' · ' King' · ' queen' · 'King' · ' prince'
' Monday'' Tuesday' · ' Thursday' · ' Wednesday' · ' Friday' · ' Sunday'
' dog'' dogs' · ' Dog' · 'Dog' · ' canine' · 'dog'

The nearest-row check is the lab's extra, not in the video. Cosine similarity compares two rows' directions: 1 means they point the same way.

What it saves

one matrix = 50,257 tokens × 768 numbers = 38,597,376 untied model = 124,439,808 + 38,597,376 = 163,037,184 share saved = 38,597,376 / 124,439,808 = 31.0% of the tied model = 38,597,376 / 163,037,184 = 23.7% of the untied one

Karpathy rounds this to "40 million … 30%" (1:12:48); the exact figures are 38.6M and 31.0%. Training later pads the vocabulary to 50,304 (the nice-numbers card), where the tied model has 124,475,904 parameters.

from transformers import GPT2LMHeadModel
sd_hf = GPT2LMHeadModel.from_pretrained("gpt2").state_dict()
a = sd_hf["lm_head.weight"]
b = sd_hf["transformer.wte.weight"]
print(a.shape, b.shape, (a == b).all().item())
print(a.data_ptr() == b.data_ptr())   # same memory, not a copy?
# in GPT.__init__, after creating wte and lm_head:
self.transformer.wte.weight = self.lm_head.weight   # one tensor

# count parameters; .parameters() lists a shared tensor once
print(sum(p.numel() for p in model.parameters()))

How it differs from related ideas

✗ Two separate matrices

163,037,184 parameters. An embedding row only gets a gradient when its token is in the batch: in one 4×32 batch, 67 of 50,257 wte rows got one (computed). Rare tokens' input rows barely train.

✗ Copying the values once

wte.weight.data = lm_head.weight.data.clone() makes them equal at the start, but they are still two tensors. After the first optimizer step they drift apart, and memory is still doubled.

✗ Tying wpe too

The position table (1024 × 768) has no output twin: the model never predicts a position, so there is nothing to share it with. It stays a separate 786,432-parameter table.

✓ One shared tensor

Assigning the Parameter object makes both names point at the same memory. Its gradient is the sum of both uses, and the output side reaches every row each step: in the same batch, all 50,257 rows got a gradient (computed).

Is tying always a good idea?

For GPT-2 124M it is a clear win: the table is almost a third of the model, and OpenAI's checkpoint ties it. The saving shrinks as models get wider, though. For GPT-2's largest size (1,542M parameters, width 1,600 in the GPT-2 paper), the same table is 50,257 × 1,600 = 80,411,200, about 5% of the model. Whether a given larger model ties is a design choice this lecture doesn't cover.

One trap when you count: summing over state_dict() lists the shared tensor under both names and gives 163,037,184, while model.parameters() counts it once. (The 67 and 50,257 gradient rows in the grid come from a small check run for this card, B=4, T=32 of tiny shakespeare, seed 1337, CPU; they are not a lab row.)

Understand and remember

  • nn.Linear stores its weight as (out, in) = (50257, 768) → the same shape as the embedding table → row i is token i in both → one tensor can serve as input lookup and output scorer
  • Similar tokens should have close rows at the input and get similar scores at the output → sharing one matrix makes both true together → each update to a row improves how the token is read and how it is predicted
  • Assigning the Parameter (not copying values) → both modules point at one memory block → the gradient is the sum of both uses → every row trains every step through the softmax, not only the rows of tokens in the batch
  • The table is 50,257 × 768 = 38.6M numbers → 31% of the 124M model → tying cuts the count from 163.0M to 124.4M → the saving shrinks as the width grows relative to the vocabulary
  • detail that matters state_dict() still lists both names (149 entries, 148 parameters) → summing it double-counts to 163,037,184 → count with model.parameters(), which lists a shared tensor once

Reference only

  • the tie line: self.transformer.wte.weight = self.lm_head.weight (train_gpt2.py L93–L94, commit ec39245)
  • tensor.data_ptr() returns the memory address; equal addresses mean the same storage
  • HF key names: lm_head.weight and transformer.wte.weight
  • _init_weights reaches the shared tensor twice (as Linear and as Embedding), both with std 0.02

3 · Retrieve from memory, card closed
  1. concept Explain in plain words why the input embedding and the output layer can reasonably be the same matrix, rather than two that happen to have the same shape.
    Check
    • each row stands for one token in both places
    • a good row puts similar tokens close together
    • that closeness helps both reading a token in and scoring it as the next token
    • sharing forces the two roles to agree
  2. mechanism Walk through one training step with tying on: which forward operations touch W, and what happens to W's gradient before the optimizer step?
    Check
    • forward: wte gathers the rows of the input tokens
    • forward: lm_head takes a dot product with every row
    • backward: the lookup sends gradient to the rows used; the output layer sends gradient to all rows
    • both contributions are added into the one W.grad; the optimizer updates W once
  3. tradeoff You copy the values with wte.weight.data = lm_head.weight.data.clone() instead of assigning the Parameter. What do you gain, what do you lose, and how would you catch the mistake?
    Check
    • they are equal only at the start and drift apart after the first step
    • no parameter saving: still 163,037,184
    • memory is still doubled
    • catch it: data_ptr() differs, or the parameter count doesn't drop
  4. tradeoff Why does tying save 31% of GPT-2 124M but only about 5% of GPT-2's largest 1,542M model?
    Check
    • the table is vocab × width: 50,257 × 768 vs 50,257 × 1,600
    • the blocks grow much faster with width and depth than the table does
    • so the table's share of the model falls as models grow

4 · Compare against what you already know

vs An embedding is just indexing: The MLP course's C[X] table and GPT-2's tied wte both turn ids into vectors. What is fundamentally different about how their rows are trained, and which design choice causes it?

Check
  • C is only read at the input, so a row learns only when its character appears in the batch
  • the tied wte is also the output layer, so every row gets gradient every step
  • cause: sharing the matrix with the softmax output
  • with 27 characters the difference barely matters; with 50,257 tokens many are rare, so it matters

vs The += bug: reused nodes add their gradients: In micrograd, a used twice needs += in backward. How is a tied W the same situation, and what would go wrong if PyTorch overwrote instead of adding?

Check
  • W is one leaf used by two operations, just like a in a + a
  • its gradient must be the sum of both paths
  • overwriting would keep only one use's gradient, so W would learn as only an embedding or only an output layer

vs Nice numbers: 50,257 → 50,304: Padding the vocabulary to 50,304 adds 47 tokens that never appear in the data. How does tying interact with that padding: what does it cost and how are those rows trained?

Check
  • the tied table grows by 47 × 768 = 36,096 parameters, counted once
  • the fake tokens never appear as inputs, so only the output side touches their rows
  • the softmax gives them a little probability, so each step pushes their scores down

Why this step?

5 · Predict commit to an answer before revealing

After padding to vocab 50,304, the 47 fake tokens never appear in the input or as targets. With tying on, will their rows of W ever get a nonzero gradient? And how many parameters does tying save now?

Reveal

Yes, every step. The output layer scores every row, and the softmax gives each fake token a small probability, so the loss pushes those scores down through their rows. Tying now saves 50,304 × 768 = 38,633,472 parameters (computed: untied 163,109,376 vs tied 124,475,904).
