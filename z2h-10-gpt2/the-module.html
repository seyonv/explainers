Writing GPT-2 as an nn.Module

Also called: the GPT class, the model skeleton, a decoder-only Transformer. Lecture 9 · SECTION 1: implementing the GPT-2 nn.Module · 0:13:47

Prime · 2 minutes before you read

The problem: You can't load OpenAI's GPT-2 weights, or train your own copy, until you have a PyTorch model with exactly the right pieces, the right shapes and the right names. One misnamed or misshapen module and the 149 checkpoint tensors have nowhere to go.

Where it fits: z2h-8 built a small GPT for Shakespeare. This card rewrites that same architecture at GPT-2's size and in GPT-2's arrangement (pre-norm, final ln_f, tanh-GELU), with names that match the checkpoint you toured on the target card.

  2. Which sublayer lets token 5 use information from token 2, and which one never mixes positions?
  3. Why does c_attn output 2304 numbers per token rather than 768?
  4. How does the Python attribute path self.transformer['h'][0].attn turn into the key transformer.h.0.attn.c_attn.weight?

In one breath: GPT-2 is a lookup at the bottom (each token and each position gets a row of 768 numbers), a stack of 12 identical Blocks in the middle, and a scoring layer at the top that turns 768 numbers into one score per vocabulary token. You write it as four small PyTorch classes and name every piece exactly the way OpenAI's checkpoint does, so that the real weights can later drop straight in.

Predict first: inside one Block, which part holds more parameters: attention (where tokens exchange information) or the MLP (which works on each token alone)?

The MLP, by almost exactly 2×. Attention has 1,771,776 + 590,592 = 2,362,368 parameters; the MLP has 2,362,368 + 2,360,064 = 4,722,432 (ratio 2.0, computed from the lab's counts). The MLP widens each token's 768 numbers to 3,072 and back, while attention only mixes 768-wide vectors. So about two-thirds of every Block is the per-token "thinking" part.

The shape of the model

Three terms carry this chapter. The residual stream is the tensor x of shape (B, T, 768): B sequences in the batch, T tokens each, and C = 768 numbers (channels) per token. It runs from the embeddings to the top, and each Block adds to it rather than replacing it. LayerNorm rescales each token's 768 numbers to mean 0 and spread 1 (then applies a learned scale and shift). Pre-norm means GPT-2 applies LayerNorm before each branch, on the way in, rather than after the add as the 2017 Transformer paper did, and adds one last LayerNorm, ln_f, before the output (~0:14:38).

x←x+attn(ln1(x))tokens communicate x←x+mlp(ln2(x))each token computes
xthe residual stream: one 768-vector per token(B, T, 768) ln_1, ln_2the Block's two LayerNorms, one per branch768 scales + 768 shifts each attncausal self-attention: each token takes a weighted average over itself and earlier tokens (z2h-8)12 heads × 64 dims mlpLinear 768→3072, GELU, Linear 3072→768, applied to every token separately4× wider inside

Karpathy's framing: attention is where tokens pool information across positions (a "reduce"), and the MLP processes each token independently (a "map"). Because each branch adds into x, the plain path x → x runs untouched from bottom to top, and gradients can flow down it straight to the embeddings.

Counts measured by labs/the-module.py; the arithmetic and shares are computed. c_attn is 3 × 768 = 2304 wide because it makes the query, key and value for all 12 heads in one matmul (12 heads × 64 = 768 each). "+ 2304" is the bias. lm_head has no bias and reuses wte (the weight-tying card); training later pads the vocabulary to 50,304, giving the course's 124,475,904.

Why the names matter. PyTorch builds every parameter's name from the attribute path: the attribute self.transformer, the dict key h, list index 0, then attn.c_attn.weight. Choose the same attributes as OpenAI's code and your state_dict() keys come out identical to the 149 tensors in the checkpoint (the-target card), so loading is a loop over matching keys. (This module's own state_dict() also has 149 keys, checked for this card.)

▶ Build itruns on your M3 · about 5 s

When: pause the video at 0:13:47 and write the classes as he explains them. Copy CausalSelfAttention (c_attn, then c_proj) from train_gpt2.py L12–L40; it is the multi-head attention you built in z2h-8, batched.

class MLP(nn.Module):
    def __init__(self, config):
        super().__init__()
        self.c_fc = nn.Linear(config.n_embd, 4 * config.n_embd)
        self.gelu = nn.GELU(approximate='tanh')
        self.c_proj = nn.Linear(4 * config.n_embd, config.n_embd)
    def forward(self, x):
        return self.c_proj(self.gelu(self.c_fc(x)))

class Block(nn.Module):  # __init__ makes ln_1, attn, ln_2, mlp
    def forward(self, x):
        x = x + self.attn(self.ln_1(x))
        x = x + self.mlp(self.ln_2(x))
        return x
class GPT(nn.Module):
    def __init__(self, config):
        super().__init__()
        self.config = config
        self.transformer = nn.ModuleDict(dict(
            wte = nn.Embedding(config.vocab_size, config.n_embd),
            wpe = nn.Embedding(config.block_size, config.n_embd),
            h = nn.ModuleList([Block(config)
                               for _ in range(config.n_layer)]),
            ln_f = nn.LayerNorm(config.n_embd),
        ))
        self.lm_head = nn.Linear(config.n_embd, config.vocab_size,
                                 bias=False)
        self.transformer.wte.weight = self.lm_head.weight  # tying
@dataclass
class GPTConfig:
    block_size: int = 1024   # longest context, in tokens
    vocab_size: int = 50257  # number of distinct tokens
    n_layer: int = 12        # Blocks
    n_head: int = 12         # attention heads per Block
    n_embd: int = 768        # channels per token

model = GPT(GPTConfig())
print(sum(p.numel() for p in model.parameters()))

How it differs from related ideas

✗ The 2017 encoder–decoder

Built for translation: an encoder reads the source sentence and the decoder attends to it through cross-attention. GPT-2 only continues its own text, so the encoder and cross-attention are gone.

✗ Post-norm Blocks

x = ln(x + attn(x)) puts a LayerNorm on the main path, so every signal and gradient must pass through 24 of them in series. Pre-norm keeps the path from embeddings to ln_f a plain chain of additions.

✗ Your own names

z2h-8 called things token_embedding_table and blocks. That runs fine, but OpenAI's 149 tensors would then need a hand-written key map, and one typo means a weight silently never loads.

✓ Pre-norm, decoder-only, HF names

Same math as z2h-8's GPT, arranged the way GPT-2 is: LayerNorm before each branch, a final ln_f, tanh-GELU, and a module tree whose keys equal the checkpoint's.

Why the tanh GELU, and is this module the whole story?

GELU is a smooth, ReLU-like activation whose exact form uses the Gaussian error function. GPT-2 used a tanh approximation of it, a choice Karpathy puts down to history (~0:21:38). The two differ by at most 0.000473 on [−5, 5] (measured). You pick approximate='tanh' to reproduce OpenAI's model exactly; for a model trained from scratch, a difference this small is unlikely to matter (our inference, not tested here).

This class holds shapes, not knowledge: with random weights it prints word salad (the sampling card). It also leaves out things that come later: forward() (next card), the initialisation (init card), and z2h-8's dropout, which build-nanogpt drops. And it is fixed at the 124M size only through GPTConfig: the same code builds the 350M, 774M and 1558M models by changing n_layer, n_head and n_embd.

Understand and remember

  • Each Block computes x + f(ln(x)) → the Block adds a correction instead of replacing x → an untouched identity path runs from the embeddings to ln_f → signals and gradients reach the bottom of a 12-Block stack without passing through 24 LayerNorms in series (the post-norm problem)
  • Attention mixes information across positions (reduce) while the MLP transforms each token alone (map) → alternating them 12 times lets tokens gather context, then process it → the MLP's 4× widening (768 → 3072 → 768) makes it hold about 2/3 of every Block's parameters
  • PyTorch names parameters by attribute path → using OpenAI's names (transformer.wte, h, attn.c_attn, ln_f, lm_head) makes our state_dict keys equal the checkpoint's → loading becomes a loop over matching keys, and a naming slip shows up as a missing key instead of a silently wrong model
  • Parameters per Block ≈ 12·C² (c_attn 3C², attn c_proj C², c_fc 4C², mlp c_proj 4C²) → 12 Blocks × 7.09M = 85.1M, 68% of the model → the one 50257 × 768 token table is most of the rest (31%), which is why tying it matters
  • detail that matters nn.GELU(approximate='tanh') instead of the exact GELU → the two differ by at most 0.000473 on [−5, 5] → irrelevant for a fresh model, but needed to reproduce OpenAI's weights exactly
  • detail that matters nn.ModuleList (not a plain Python list) for h → PyTorch registers each Block's parameters → they appear in parameters() and state_dict() as h.0 … h.11; a plain list would hide them from the optimizer and from loading

Reference only

  • the exact GPTConfig fields and defaults (block_size 1024, vocab_size 50257, n_layer 12, n_head 12, n_embd 768)
  • per-module counts: c_attn 1,771,776 · attn c_proj 590,592 · c_fc 2,362,368 · mlp c_proj 2,360,064 · 2 LayerNorms 3,072
  • lm_head is nn.Linear(768, 50257, bias=False)
  • the larger GPT-2 configs: 24/16/1024, 36/20/1280, 48/25/1600 (layers/heads/channels)
  • nn.ModuleDict(dict(wte=…, wpe=…, h=…, ln_f=…)) syntax

  1. concept Explain what the residual stream is in GPT-2 and why every Block adds to it rather than overwriting it.
    Check
    • a (B, T, 768) tensor carried from the embeddings to ln_f
    • each branch computes a correction from a normalised copy and adds it back
    • the plain identity path lets gradients reach early Blocks and the embeddings directly
  2. mechanism Walk one token's 768-vector through a single Block: which modules touch it, in what order, and what shape comes out of each?
    Check
    • ln_1 → 768; c_attn → 2304 (q, k, v, each 12 heads × 64); attention mixes with earlier tokens → 768; c_proj → 768; added to x
    • ln_2 → 768; c_fc → 3072; tanh-GELU → 3072; c_proj → 768; added to x
    • output is (B, T, 768), the same shape as the input, so Blocks stack
  3. tradeoff You want a bigger model for the same memory. Adding Blocks and widening n_embd both add parameters: how does each scale, and what do you give up if you choose depth?
    Check
    • each Block costs about 12·C² (7,087,872 at C = 768), so depth adds linearly
    • width grows the Block cost as C² and the token table as 50257·C
    • more Blocks means more sequential steps per forward pass, and deeper stacks lean harder on the residual path and on init (the init card)
  4. mechanism Your state_dict has a key transformer.blocks.0.attn.c_attn.weight while the checkpoint has transformer.h.0.attn.c_attn.weight. What went wrong in your class, and what does the loader see?
    Check
    • the ModuleList was assigned to blocks instead of h
    • keys are built from attribute names, so all 12 Blocks' keys differ
    • a key-matching loader finds them missing, or a non-strict load leaves those weights random
