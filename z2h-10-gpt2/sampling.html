Sampling: top-k 50 and the token loop

Also called: autoregressive generation, decoding, top-k sampling. Lecture 9 · sampling init, prefix tokens, tokenization · 0:33:31

Prime · 2 minutes before you read

The problem: A trained GPT-2 only returns one probability per vocabulary token for the next position. That is not text. Without a loop that picks a token and feeds it back, you can't see what the model has learned, and without a rule for which token to pick you get either the same sentence every time or nonsense from the long tail.

Where it fits: The previous card loaded OpenAI's weights and got logits of shape (B, T, 50257). This card turns those logits into text, the same multinomial draw you used for bigram names, now with a top-k cut and a model that looks at the whole prefix.

In one breath: GPT-2 only ever answers one question: "given these tokens, how likely is each of the 50,257 tokens to come next?" To write text you ask it again and again. Keep the scores at the last position, turn them into probabilities, throw away everything except the 50 most likely tokens, draw one of those at random, append it to the input, and repeat.

Predict first: top-k 50 keeps 50 of GPT-2's 50,257 tokens, about 0.1% of them. After the prompt "Hello, I'm a language model,", roughly what share of the model's probability do those 50 tokens hold: 5%, 30% or 80%?

About 80% (0.8064, computed). The trained model is very lopsided: the top 5 tokens alone hold 57%. Only 19.4% is spread over the other 50,207 tokens. Top-k throws that thin tail away and redraws among the 50 tokens that carry most of the belief. Across all 22 steps of the lab's run the 50 kept tokens held 79% on average, but at one step only 16% (measured on MPS).

One turn of the loop

The prompt is 8 tokens, [15496, 11, 314, 1101, 257, 3303, 2746, 11], which is 'Hello' ',' ' I' "'m" ' a' ' language' ' model' ','. The lab copies it into 5 rows (B = 5, the batch size), so one forward pass writes 5 samples at once. T is the current length of each row.

device = "cpu"
if torch.cuda.is_available():
    device = "cuda"
elif torch.backends.mps.is_available():
    device = "mps"          # the GPU in your M3
model = GPT.from_pretrained("gpt2").eval().to(device)
torch.manual_seed(42)
tokens = enc.encode("Hello, I'm a language model,")  # 8 ids
x = torch.tensor(tokens).unsqueeze(0).repeat(5, 1).to(device)
while x.size(1) < 30:
    with torch.no_grad():
        logits, _ = model(x)                    # (5, T, 50257)
    probs = F.softmax(logits[:, -1, :], dim=-1)  # (5, 50257)
    topk_probs, topk_indices = torch.topk(probs, 50, dim=-1)
    ix = torch.multinomial(topk_probs, 1)       # (5, 1) slot
    xcol = torch.gather(topk_indices, -1, ix)   # (5, 1) token id
    x = torch.cat((x, xcol), dim=1)
for row in x.tolist():
    print(">", enc.decode(row))

How it differs from related ideas

✗ Greedy: always take the top token

No randomness, so all 5 rows are the same text. Run on your M3 with k = 1 it gets stuck: "…model, not a programming language. I'm a language model. I'm a language model. I'm a language model" (measured).

✗ Sample from all 50,257

At the first step 19.4% of the probability sits on 50,207 tail tokens that are each unlikely. That is roughly one draw in five from the tail at this step, and one odd token can steer everything after it.

✗ Top-p (nucleus)

Keeps the smallest set of tokens whose probability adds up to p. It adapts to how sure the model is: for p = 0.9 it keeps 291 tokens at this step. It's a different knob, not the one this lecture (or the Hugging Face pipeline's default, top-k 50) uses.

✓ Top-k 50, then draw

A fixed cut: the tail can never be picked, yet each row still draws at random, so 5 rows give 5 different texts. Here it keeps 80.6% of the mass and costs one topk and one multinomial per step.

Is this how real models generate?

The idea is the same, but this loop is deliberately simple. Karpathy calls it "correct but inefficient" (0:38:01): each step runs the model over the whole row again, although only the new last token has changed. Growing from 8 to 30 tokens processes 8 + 9 + … + 29 = 407 positions per row. A KV cache (keys and values stored from earlier steps) would process 8 + 21 = 29 (computed).

Top-k 50 is also not always the right choice. A fixed k ignores how sure the model is: at one step in the lab's run the top 50 held only 16% of the probability, and the cut threw away most of the plausible options. When you need one repeatable answer, use greedy (k = 1) or no sampling at all: the HellaSwag eval later scores answers by their loss and never samples.

Understand and remember

  • GPT-2 predicts only the next token → text needs a loop: forward, pick one token, append, forward again → each new token is conditioned on everything written so far (autoregressive) → one bad pick changes every later step
  • A trained model puts most probability on a few tokens (top 50 hold 80.6% after the prompt) → the other 50,207 share the remaining 19.4% → sampling from everything draws a tail token about one step in five here → cutting to the top 50 and redrawing keeps variety but removes the tail
  • topk returns sorted values plus their positions → multinomial picks a slot (0–49) in the value tensor → gather maps that slot back through topk_indices to a real token id → skipping gather appends slot numbers, i.e. token ids 0–49, which decode to single characters (punctuation, digits, A–R)
  • Random weights → nearly flat probabilities (top 50 hold 0.54%, entropy 10.67 vs the uniform 10.83 nats) → the top-k cut removes almost nothing meaningful → the same loop writes word salad, which proves the text comes from the weights, not the loop
  • detail that matters No KV cache: each step re-runs the model over the whole row → 8 + 9 + … + 29 = 407 positions per row instead of 29 → fine for 22 tokens, quadratic-ish waste for long generations
  • detail that matters A seed fixes the random stream on one device only → the video's CUDA samples and your MPS samples differ with the same manual_seed(42), yet each repeats exactly on its own machine

Reference only

  • the prompt ids [15496, 11, 314, 1101, 257, 3303, 2746, 11], 5 rows, max_length = 30
  • device order: torch.cuda.is_available() → torch.backends.mps.is_available() → "cpu"
  • torch.multinomial accepts unnormalised weights, so no explicit division is needed
  • top-k 50 is the Hugging Face pipeline's default; later build-nanogpt code uses its own torch.Generator seeded 42 + ddp_rank
  • wrap the forward in torch.no_grad() so no graph is stored during sampling

Why this step?

5 · Predict commit to an answer before revealing

Over the lab's 22 steps × 5 rows, the top-50 mass averaged 0.79 but dropped to 0.1613 at one step. At that step, what does top-k do to the other 84% of the probability, and would top-p 0.9 keep more or fewer than 50 tokens there?

Reveal

Top-k sets that 84% to zero and scales the kept 16% up to 100%, so each kept token's chance grows about 6× (1 / 0.1613 = 6.2). The model was very unsure there, so many plausible tokens were dropped. Top-p 0.9 would keep far more than 50 tokens, since 50 tokens cover only 16%: that step is exactly where a fixed k and an adaptive p disagree most.
