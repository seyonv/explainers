The GPT-3 recipe: AdamW, clipping, warmup and cosine decay

Also called: the training hyperparameters, the optimizer setup, a warmup + cosine learning-rate schedule, gradient-norm clipping, decoupled weight decay. The problem: Your GPT-2 trains, but only with a fixed lr of 3e-4 and every AdamW default. For a 19,073-step run you have to choose the betas, the lr at every step, how to survive a bad batch, and what to decay. Searching for all of that yourself would cost many full runs.

Where it fits: The model is written and fast. This card turns the plain AdamW loop from the overfit-one-batch card into the real training setup, reusing the Adam mechanics (the two running averages and the W in AdamW) from the GPT lecture.

In one breath: OpenAI released GPT-2's weights but said little about how it was trained, while the GPT-3 paper lists its training settings in full. The two models are nearly the same shape, so Karpathy borrows GPT-3's recipe. Each step, he clips the gradient to length 1. He sets the learning rate from a schedule that ramps up for 715 steps and then glides down a cosine curve from 6e-4 to 6e-5. And he applies weight decay only to the matrices.

Predict first: weight decay is skipped for 98 of the model's 148 parameter tensors. What share of the 124,475,904 parameters escapes decay: about 66%, about 10%, or under 1%?

Under 1%: 121,344 parameters, or 0.097%. The 98 skipped tensors are all 1-D vectors (biases and LayerNorm gains and biases), each 768 to 3,072 numbers long. The 50 decayed tensors are the 2-D matrices, and they hold 124,354,560 parameters (99.90%). So "decay only 2-D tensors" still decays almost everything.

Six settings, borrowed from GPT-3 Small

One step is one optimizer update. In the real run each step sees 219 = 524,288 tokens (the big-batch card shows how). So a token budget from the paper becomes a step count once you divide by 524,288.

Where each setting acts in one step

Clipping: one length for the whole gradient

Treat all 124M gradients as one long vector g. Its global norm is its length, ‖g‖ = √(sum of every gradient squared). If ‖g‖ is above 1.0, clip_grad_norm_ multiplies every gradient by 1.0 / ‖g‖. That shrinks the step but keeps its direction, and one bad batch can't shove the model far. Karpathy calls it a bit of a hack and prints the norm every step, because a norm that keeps climbing is a warning sign.

step 0 (the lab, B=4 T=32, fresh model): ‖g‖ = 48.8147 (returned by clip_grad_norm_, before clipping) scale = 1.0 / 48.8147 = 0.0205 (every gradient × 0.0205) ‖g‖ after = 48.8147 × 0.0205 = 1.0000

Steps 0–4 had norms 48.81, 33.64, 40.73, 35.32, 35.76, so every one was clipped (measured). A fresh model has large gradients; in the laptop training run (results card) the norm falls from 6.99 at step 1 to 1.86 at step 49.

The learning-rate curve

The learning rate (lr) scales every update. get_lr(it) gives it for step it in three pieces: a straight ramp up to max_lr, half a cosine wave down to min_lr, then flat.

warmup it = 0: lr = 6e-4 × (0+1) / 715 = 8.39e-7 it = 714: lr = 6e-4 × 715 / 715 = 6.00e-4 decay it = 5000: r = (5000 − 715) / 18358 = 0.2334 coeff = 0.5 × (1 + cos(π × 0.2334)) = 0.5 × 1.7430 = 0.8715 lr = 6e-5 + 0.8715 × 5.4e-4 = 5.31e-4

Warmup uses it + 1, so step 0 already moves a little. Karpathy calls 715 warmup steps very mild and guesses 100 would do (3:19:35). GPT-3 decays over 260B tokens; here the decay ends at 10B, which he admits isn't exactly faithful.

Weight decay only on the matrices

Weight decay is a regularizer: every step, AdamW shrinks each weight by a fraction lr × 0.1 on top of the normal update, so no single weight grows large unless the gradient keeps pushing it there. configure_optimizers splits the parameters by dimension into two groups, each with its own weight_decay:

GroupWhich tensors (vocab 50304)TensorsParameters
dim ≥ 2 · decay 0.1per block: c_attn, attn.c_proj, c_fc, mlp.c_proj weights (12 × 4 = 48), plus wte and wpe50124,354,560
dim < 2 · decay 0per block: 4 biases + 2 LayerNorms × (weight, bias) = 8 (12 × 8 = 96), plus ln_f's 298121,344
98 small tensors: 12 × (2304 + 768 + 3072 + 768 + 4 × 768) + 2 × 768 = 121,344 per-step shrink at max lr: 6e-4 × 0.1 = 6e-5 of each weight whole run: Π (1 − lr_t × 0.1) over 19,073 steps = 0.534 (computed)

lm_head shares wte's tensor (weight tying), so it's counted once. A weight that never got a gradient would shrink to 53% of its size over the run; real weights are pushed back by their gradients. The usual reason to spare biases and LayerNorm: they are few, and pulling a LayerNorm gain (which starts at 1) toward 0 would just shrink the signal it passes on.

Fused AdamW. fused=True runs the whole update for all tensors in one GPU kernel instead of many small ones. The math is the same, and the step went from 93 to 90 ms on the A100 (2:33:20). The code turns it on only for CUDA, so on your M3 it prints using fused AdamW: False.

When: pause the video at 2:14:55, add the clip line to your training loop, then write get_lr and the two parameter groups as the next two chapters reach them.

max_lr, min_lr = 6e-4, 6e-4 * 0.1
warmup_steps, max_steps = 715, 19073
def get_lr(it):
    if it < warmup_steps:                  # 1) linear warmup
        return max_lr * (it + 1) / warmup_steps
    if it > max_steps:                     # 3) floor
        return min_lr
    r = (it - warmup_steps) / (max_steps - warmup_steps)
    coeff = 0.5 * (1.0 + math.cos(math.pi * r))  # 1 -> 0
    return min_lr + coeff * (max_lr - min_lr)
for it in (0, 714, 9894, 19072):
    print(f"get_lr({it:5d}) = {get_lr(it):.4e}")
params = [p for p in model.parameters() if p.requires_grad]
decay = [p for p in params if p.dim() >= 2]
nodecay = [p for p in params if p.dim() < 2]
optimizer = torch.optim.AdamW(
    [{'params': decay, 'weight_decay': 0.1},
     {'params': nodecay, 'weight_decay': 0.0}],
    lr=6e-4, betas=(0.9, 0.95), eps=1e-8)
# in the loop, after loss.backward():
norm = torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
for group in optimizer.param_groups:
    group['lr'] = get_lr(step)
optimizer.step()

Why it beats the alternatives

✗ Full lr from step 0

A fresh model's gradient norm is around 49 (measured), and Adam's running averages have seen only one or two gradients. Full-size steps on those noisy estimates can knock training off course, which is the usual reason for warming up.

✗ One sudden drop

makemore trained at 0.1, then switched to 0.01 at step 100,000. That works for a small MLP, but you must choose where to drop. Cosine lowers the lr smoothly and needs only the final step.

✗ Decay on every tensor

AdamW(model.parameters(), weight_decay=0.1) would also pull the 98 bias and LayerNorm vectors toward 0. That buys almost no regularization, since they hold 0.1% of the parameters.

✓ The GPT-3 recipe

Warm up, then glide down a cosine curve. Cap the gradient's length at 1, use β2 = 0.95, and decay only the matrices. All of it was already tuned by OpenAI on a model of the same shape, so you run it instead of searching for it.

Are these the right numbers for your run?

They are GPT-3 Small's settings for 300B tokens, reused for a 10B-token run. So they're a solid starting point, not an optimum. The paper itself lowers max lr as models grow (6e-4 at 125M down to 0.6e-4 at 175B), and warmup and max_steps are token counts divided by the batch size. Change the model, the batch or the token budget and you have to redo that arithmetic.

Clipping can also hide a bug: if every step is clipped long after the start, the norm is telling you something is wrong. And on the M3, fused AdamW is off. That changes the speed, never the result.

Understand and remember

  • All gradients treated as one vector → its length ‖g‖ is measured once → if ‖g‖ > 1 every gradient is scaled by 1/‖g‖ → the update keeps its direction but can't exceed a fixed size → one unlucky batch (or a fresh model with ‖g‖ ≈ 49) can't shove the weights far
  • Fresh model: large noisy gradients and Adam's running averages built from one or two samples → full-size steps are risky → linear warmup over 715 steps lets them settle → then cosine decay lowers the lr smoothly to 10% → small late steps settle into a lower loss without picking a drop point by hand
  • Paper budgets are in tokens → divide by the tokens per step (219) → 375M → 715 warmup steps, 10B → 19,073 max_steps → change the batch or the token budget and the schedule must be re-derived, or warmup and decay land in the wrong place
  • AdamW shrinks each weight by lr × 0.1 per step, separately from the gradient → a weight only stays large if its gradient keeps pushing → applied to matrices only (dim ≥ 2) → biases and LayerNorm gains, 0.1% of the parameters, aren't pulled toward 0
  • detail that matters β2 = 0.95 instead of 0.999 → the squared-gradient average forgets in about 1/(1 − β2) = 20 steps instead of 1,000 → the step size adapts quickly when gradient scale shifts
  • detail that matters fused=True does the whole AdamW update in one CUDA kernel → identical math, 93 → 90 ms per step on the A100 → only a speed setting, and off on MPS

Reference only

  • the exact values: max_lr 6e-4, min_lr = 0.1 × max_lr, warmup_steps 715, max_steps 19073, weight_decay 0.1, eps 1e-8
  • torch.nn.utils.clip_grad_norm_(params, 1.0) returns the norm before clipping
  • setting the lr by writing param_group['lr'] for every group each step
  • the inspect.signature(torch.optim.AdamW) check for fused
  • the counts 50 / 98 tensors and 124,354,560 / 121,344 parameters (vocab 50304)
  • GPT-3's batch-size ramp (32K tokens to full over 4–12B tokens), skipped here

  1. concept Explain what problem global-norm clipping solves and why it scales all gradients by the same factor rather than clipping each one to ±1.
    Check
    • it limits how far one step can move the weights when a batch gives an unusually large gradient
    • one shared factor keeps the update's direction, so it's still a descent direction, just shorter
    • clipping each value separately would change the direction and distort the relative sizes
  2. mechanism Walk through get_lr(5000) with warmup 715 and max_steps 19,073: which branch runs, what is the decay ratio, the coefficient, and the lr?
    Check
    • 5000 ≥ 715 and ≤ 19,073, so the cosine branch runs
    • r = (5000 − 715) / 18,358 = 0.2334
    • coeff = 0.5 × (1 + cos(0.2334π)) = 0.8715
    • lr = 6e-5 + 0.8715 × 5.4e-4 = 5.31e-4
  3. tradeoff You double the batch to 220 tokens per step but keep the 10B-token budget. Which schedule numbers must change, to what, and what goes wrong if you forget?
    Check
    • max_steps halves: 10e9 / 220 ≈ 9,537
    • warmup halves: 375e6 / 220 ≈ 358
    • if you keep 19,073, the 10B tokens run out around step 9,536, where the lr is still 3.47e-4 (computed): the low-lr finish never happens. Run all 19,073 steps instead and you see 20B tokens, two passes over the data
  4. tradeoff Weight decay is skipped on 98 of 148 tensors, yet 99.9% of parameters are still decayed. What would you lose, and what would you gain, by decaying all 148?
    Check
    • gain: nothing meaningful for regularization, the extra 121,344 parameters are 0.1%
    • loss: biases and LayerNorm gains get pulled toward 0, and a LayerNorm gain that starts at 1 sets the scale of what its layer passes on
    • so the split is about protecting those few parameters, not about saving compute

5 · Predict commit to an answer before revealing

Your run crashes at step 10,000. You reload the weights and restart the loop, but the step counter starts again from 0. What lr does the model see over the next 715 steps, and why is that a problem for a model that is half trained?

Reveal

The lr should be 3.2510e-04 at step 10,000 and falling. Instead get_lr(0) gives 8.3916e-07, and the lr climbs back to the full 6.0000e-04 by step 714, almost twice what the model should get. Then the cosine starts over, so the run needs another 19,073 steps to finish. A trained model has lost the large, noisy gradients warmup was protecting against, so the fresh peak lr is more likely to bump the loss up than to help. If the optimizer state wasn't saved either, Adam's running averages start empty again. So a checkpoint needs the step and optimizer.state_dict() as well as the weights.
