Prime · why this checkpoint, why now

You're at the end of the lecture's first section. Everything so far answers one question: before you spend GPU hours, how do you know the model is right? The first half checks against someone else's numbers: OpenAI's weights go into your module, and its logits must match Hugging Face's. The second half checks against arithmetic: a fresh model must start near ln 50,257 = 10.82, crush one batch, and have two design choices (tying, the residual scale) that you can verify by counting. Section 2 is about speed, and it changes the code in ways that should never change these numbers. Check now that you could redo each check from memory.

  • Loading OpenAI's weights → copy 149 tensors by name, transpose the four Conv1D kinds, then compare logits with Hugging Face.
  • Sampling → last position, softmax, keep the top 50, draw, append; the pretrained model's top 50 hold 80.6% of the mass.
  • Batches and the 10.82 check → x and y are one buffer shifted by one; B·T predictions, one mean loss, ln V at init.
  • Overfit, then load → one batch falls to 0.36; fresh batches stall near the 6.32 frequency-only floor.
  • Weight tying → wte and lm_head are one tensor: 38,597,376 parameters saved, and every row trains every step.
  • Init → std 0.02, and 0.02/√24 = 0.00408 on the two c_proj layers that write into the residual stream.

1 · Mixed retrieval

  1. In one 4 × 32 batch of tiny shakespeare, how many of the 50,257 rows of wte.weight.grad are nonzero if wte and lm_head are two separate matrices, and how many once they are tied? Which rule from micrograd decides what the tied gradient is?
    Check
    • untied: 67 rows, one per distinct token in the batch; an embedding row gets a gradient only when its token is looked up
    • tied: all 50,257, because the output layer scores every row at every position, so the loss reaches every row
    • the tied W is one leaf used twice (lookup at the bottom, dot products at the top), like a in a + a: its gradient is the sum of both paths, which is why .grad accumulates with +=
    • bonus: counting over state_dict() lists the shared tensor twice (163,037,184); model.parameters() counts it once (124,439,808)

    Missed it? Reopen weight tying, "How it differs from related ideas", the micrograd lecture's += rule, "The smallest case: b = a + a", and the MLP lecture's embedding lookup, "If it's only indexing, how does C learn?".

  2. debugYour freshly built GPT-2 prints loss 24.01 at step 0 on the 4 × 32 batch. You fix that. A teammate's version prints 9.94 at step 0, then overfits its one batch happily. What is wrong in each, and which check catches the second?
    Check
    • expected at init: −ln(1/50,257) = ln 50,257 = 10.8249; with std-0.02 init the lab measures 10.9600
    • 24.01 is far above ln V: the logits are too large, i.e. confidently wrong (24.01 is what every logit × 10 gives). Suspect the init: scores should start small and nearly equal
    • 9.94 looks healthy, and that's the trap: it's the no-shift bug, y = x. At init nothing knows the task, so the loss sits near ln V either way; and the overfit test memorises wrong targets as easily as right ones
    • what catches it: score your batch with the pretrained weights. OpenAI's GPT-2 gives 5.11 on the real targets and 8.97 on y = x; a trained model is only unsurprised by correct targets

    Missed it? Reopen batches and the 10.82 check, "Why 10.82" and "What the 10.82 check does not prove", overfit, then load, "Is a loss near 0 the goal?", and the BatchNorm lecture's step-0 loss, "What "knowing nothing" should cost".

  3. After the prompt "Hello, I'm a language model,", the pretrained model gives ' not' p = 0.1643 and its top 50 tokens hold 0.8064 of the probability. With top-k 50, what chance does ' not' actually get? The random-init model's top 50 hold only 0.0054: what does top-k do for it? And why did the bigram name sampler never need top-k?
    Check
    • renormalised over the kept 50: 0.1643 / 0.8064 = 0.2038 (multinomial does that division itself)
    • random model: almost flat (entropy 10.671 nats vs 10.825 for uniform), so the "top 50" are barely better than the rest; top-k cuts nothing meaningful and the text is word salad
    • bigram: one row of 27 characters, each a plausible option, so there is no long tail of 50,207 unlikely tokens to cut

    Missed it? Reopen sampling, "What top-k does at the first step" and "Same loop, random weights", and the bigram lecture's name sampler, "One row becomes a distribution".

  4. which idea?A teammate scales c_proj by 1/√n_layer instead of 1/√(2·n_layer). The residual stream's std at block 12 comes out 0.430 instead of 0.300. Which idea explains the factor, and how is this square root different from Kaiming's 1/√fan_in?
    Check
    • variances of independent adds add, so N adds of std σ give √N·σ; each block adds twice (attn, then mlp), so 12 blocks = 24 adds, not 12
    • scaling by 1/√12 leaves each add √2 too big: 0.300 × √2 ≈ 0.42 (measured 0.430)
    • Kaiming's √fan_in counts terms summed inside one layer (0.02 ≈ 1/√768 = 0.036 plays that role here); the residual scale counts adds stacked across depth
    • the demo behind both: 100 adds of std 1 → 10.0898; scaled by 1/√100 → 1.0046

    Missed it? Reopen init, "Why the residual stream needs its own scale" and "Why it beats the alternatives", and the BatchNorm lecture's Kaiming init, "Why the spread grows by √fan_in".

  5. which idea?You port the weights and forget the .t() on attn.c_proj.weight only. Every shape assert passes and the script prints "didn't crash yay!", yet the top next token is now ' the' at 2.6%. Which idea explains why the asserts were silent, and which one line of checking would have caught it?
    Check
    • OpenAI's Conv1D stores weights as (in, out), nn.Linear as (out, in); three of the four sideways kinds aren't square, so a missing .t() fails the assert, but c_proj is 768 × 768 and fits either way round
    • so a shape check cannot tell a transposed square matrix from the right one: 12 of the 48 transposed tensors are unprotected
    • the check that catches it: compare logits with Hugging Face's on the same input: 4.58e-05 when right (MPS), 161.7 with this bug (CPU)
    • the damage in numbers: top guess 16.4% ' not' → 2.6% ' the'; loss on 256 tokens of tiny shakespeare 4.34 → 7.37

    Missed it? Reopen loading OpenAI's weights, "Why four weights arrive sideways" and "Why it beats the alternatives".

  6. With B = 4 and T = 32, how many tokens does the buffer need, how many predictions does one forward pass get graded on, and what makes it fair to grade position 5 against y[:, 5] when the model was given all 32 inputs?
    Check
    • B·T + 1 = 129 tokens: x = buf[:-1], y = buf[1:], each viewed as (4, 32)
    • B·T = 128 predictions; logits (4, 32, 50257) are flattened to (128, 50257) for one cross-entropy call, which averages them
    • attention is causal: position t sees only positions 0 … t, so its output is an honest guess at token t + 1. One row of T tokens gives T examples, just as block_size 8 gave 8 in the GPT lecture
    • grading only the last position would keep 4 of the 128 signals

    Missed it? Reopen batches and the 10.82 check, "One buffer, two views" and "From (B, T) to one number", and the GPT lecture's chunks and batches, "One chunk, eight examples".

  7. which idea?Same seeded model, 50 AdamW steps at lr 3e-4. Run A reuses one batch and ends at 0.36; run B gets a new batch each step and ends at 6.80. A colleague calls B "stuck". Which idea explains 6.80, and what would B's loss have to do for you to agree something is broken?
    Check
    • A memorises 128 fixed answers: e−0.36 ≈ 0.70 average probability on the right token. It proves forward, backward, zero_grad and step all work, and nothing about generalisation
    • B has seen 6,400 tokens, 1.9% of one epoch; what it can learn that fast is token frequencies. "Always predict the frequencies" scores the entropy of tiny shakespeare's tokens: 6.32 nats, versus 10.82 for a uniform guess
    • worry if B stays pinned at 6.32 for hundreds of steps: getting below it needs the context, so suspect attention, positions or the x/y shift (run for 300 steps and most batches from about step 190 on score 4.5–6.0)
    • the MLP lecture's overfit stopped at 0.2561, not 0, for the same kind of reason a single batch may not reach 0: identical inputs that need different targets

    Missed it? Reopen overfit, then load, "Two runs, one model" and "Why B stalls near 6.3: token frequencies", and the MLP lecture's first overfit, "Why it stops at 0.2561, not 0".

3 · Build: the whole trust ladder in one script

runs on your M3 · about 30 s (CPU)

What it reinforces: the port and its HF check, the top-50 mass, the x/y shift and ln V, a pretrained model as a data checker, tying (one tensor, one count) and the init stds, then the one-batch overfit. New here: all of it runs in order on the same 4 × 32 batch, so each rung has to pass before the next one means anything.

  1. Ladder rung 0. Print ln 50,257, the target for step 0.
  2. Port. GPT.from_pretrained('gpt2') from labs/common.py; compare its logits on the "Hello, I'm a language model," prompt with Hugging Face's, and print the top token and the top-50 mass.
  3. Score the data. With the pretrained weights, compute the loss on the first 4 × 32 batch of tiny shakespeare from DataLoaderLite.
  4. Fresh model. torch.manual_seed(1337), GPT(GPTConfig()): print the parameter count, whether lm_head and wte share data_ptr(), and the std of c_attn and c_proj. Also print the loss of a default-init model (init=False) and the count of an untied one (tie=False).
  5. Overfit. 50 AdamW steps at lr 3e-4 on that one batch.
torch.manual_seed(1337)
f = GPT(GPTConfig())
b = f.transformer.h[0]
wte, head = f.transformer.wte.weight, f.lm_head.weight
print(num_params(f), head.data_ptr() == wte.data_ptr())
print(b.attn.c_attn.weight.std(), b.attn.c_proj.weight.std())
opt = torch.optim.AdamW(f.parameters(), lr=3e-4)
for i in range(50):
    opt.zero_grad()
    _, loss = f(x, y)          # the same (4, 32) batch every step
    loss.backward()
    opt.step()
    if i % 10 == 9 or i == 0: print(i, round(loss.item(), 4))
Done when: ln V prints 10.8249; the port matches Hugging Face (max difference 0.00e+00 on CPU; the lab's MPS run gives 4.58e-05) with ' not' at p = 0.1643 and a top-50 mass of 0.8064; the pretrained model scores the batch at 5.1067; the fresh model has 124,439,808 parameters, shared memory True, c_attn std 0.02000 and c_proj std 0.00408; the default-init model starts at 10.8889 and the untied one has 163,037,184 parameters; and the overfit goes 10.9600 → 5.7886 (step 9) → 3.6664 → 2.2104 → 1.1224 → 0.3649 (step 49). All measured in this checkpoint's scratch run on the M3's CPU (27 s, 355 ms per step, other jobs running). The lab's MPS run prints the same losses to within 0.0001 through step 29 and ends at 0.3619.
