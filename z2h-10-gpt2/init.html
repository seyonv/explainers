Init: std 0.02 and the 1/√(2·n_layer) residual scale

Also called: weight initialization, GPT-2 init, scaled residual init, NANOGPT_SCALE_INIT. Lecture 9 · model initialization: std 0.02, residual init · 1:13:47

Prime · 2 minutes before you read

The problem: A fresh network is nothing but random numbers. If they start too big, every residual add piles onto the last and the signal inflates block after block; if the scale is careless, the model begins training from a lopsided place (positions drowning tokens, a stream five times too large).

Where it fits: You have the full GPT module, a loss near 10.82 and weight tying. This card revisits the Kaiming rule from the BatchNorm course (std = gain/√fan_in) and the residual connection from the GPT course, and asks what happens when 24 residual adds stack up.

In one breath: before training, every weight is a random number, and the size of those random numbers decides whether signals start out tiny, sensible or huge. GPT-2 draws every weight from a normal (bell-curve) distribution with mean 0 and standard deviation (std, the typical size of a value) 0.02, and sets biases to 0. The one exception is the two c_proj layers in each block, whose output is added onto the residual stream: they start 0.02/√24 = 0.00408, so 24 additions don't pile up.

Predict first: you add 100 random vectors, each with std 1, into a vector that starts at zero. What is the std of the result: about 1, about 10, or about 100?

About 10 (the lab measured 10.0898). The variance (std squared) of independent random numbers adds up: 100 × 1² = 100, and √100 = 10. So the std grows with the square root of the number of adds, not the number itself. Shrink each vector by 1/√100 = 0.1 first, and the sum stays at about 1 (measured 1.0046).

Where 0.02 comes from

A layer's output is a sum over its inputs, one weight each. The count of inputs is its fan_in. The Xavier rule picks std = 1/√fan_in so that the sum keeps roughly the size of its inputs (the Kaiming card derives this). For GPT-2, fan_in is usually the model width n_embd. OpenAI's GPT-2 code just uses a fixed 0.02, and Karpathy keeps it because it is "roughly in the vicinity" (1:16:34) of 1/√width for every GPT-2 size:

Why the residual stream needs its own scale

Each block reads a normalized copy of the running vector x (the residual stream) and adds its result back: x = x + attn(ln_1(x)), then x = x + mlp(ln_2(x)). Nothing ever shrinks x between blocks, so every add makes it bigger. With 12 blocks that is 2 × 12 = 24 adds, and variances add:

std(x1+⋯+xN)=N⋅σgrows as √N std(x1N+⋯+xNN)=σscale each add by 1/√N: stays at σ
xione add: a random vector of 768 numbers, independent of the others1 of N σthe std of one add1 in the demo Nhow many adds pile up100 in the demo · 24 in GPT-2

The demo: √100 × 1 = 10 (measured 10.0898); with each add × 0.1, measured 1.0046.

In the code, only the two c_proj layers (the last linear layer of attention and of the MLP) are the ones whose output lands on the stream, so only they get the scale. The GPT-2 paper scales "residual layers" by 1/√N; counting two per block, as the lecture does, gives N = 2·n_layer:

stream at start = wte + wpe, both std 0.02 → √(0.02² + 0.02²) = 0.0283 scale = (2 · n_layer)^-0.5 = 24^-0.5 = 0.2041 c_proj std = 0.02 × 0.2041 = 0.00408 expected effect = √24 = 4.90× smaller adds

x = torch.zeros(768)
n = 100  # e.g. 100 layers

    x += torch.randn(768)             # unscaled
print(x.std())
x = torch.zeros(768)
for i in range(n):
    x += n**-0.5 * torch.randn(768)   # scaled by 1/sqrt(n)
print(x.std())
# in CausalSelfAttention and MLP, right after creating c_proj:
self.c_proj.NANOGPT_SCALE_INIT = 1
# at the end of GPT.__init__:  self.apply(self._init_weights)
def _init_weights(self, module):
    if isinstance(module, nn.Linear):
        std = 0.02
        if hasattr(module, 'NANOGPT_SCALE_INIT'):
            std *= (2 * self.config.n_layer) ** -0.5
        torch.nn.init.normal_(module.weight, mean=0.0, std=std)
        if module.bias is not None:
            torch.nn.init.zeros_(module.bias)
    elif isinstance(module, nn.Embedding):
        torch.nn.init.normal_(module.weight, mean=0.0, std=0.02)

Why it beats the alternatives

✗ PyTorch's defaults

nn.Linear draws uniformly in ±1/√fan_in (std 0.0208 for 768 inputs), but nn.Embedding draws std 1. In our tied model wpe starts 48× larger than wte, so the stream starts at std 1.00, mostly position (computed).

✗ 0.02 everywhere, no scale

All 24 adds land at full size. The stream reaches std 1.54 by block 12, 5.1× the scaled model's 0.30 (lab), and it keeps growing as √(adds) in deeper models.

✗ Scale by 1/√n_layer only

Forgets that each block adds twice. c_proj gets 0.00577, and the stream ends at 0.430 instead of 0.300, √2 too big (computed with the lab's code and seed).

✓ 0.02, and 0.02/√(2·n_layer) on c_proj

Matches OpenAI's GPT-2. The final stream size stops depending on depth: a 24-layer model with its own scale (0.00289) ends at 0.298, the 12-layer at 0.300 (computed).

Does init settle how the model trains?

No. Init only sets the starting point: after the first optimizer steps the weights move wherever the gradients push them. What a good init buys is a healthy start. Signals and gradients have sensible sizes at step 0, and the loss at init sits near the uniform-guess 10.82 (the lab's model starts at 10.96, see the first-loss card). The scale doesn't stop the stream growing either: it still goes from 0.028 to 0.30 over 12 blocks. The LayerNorms (ln_1, ln_2, and ln_f before the output) re-normalize what each block reads, so a moderate growth is harmless.

0.02 is a GPT-2 convention, not a law. It is fixed rather than tied to width. That works for widths 768–1,600, but past width 2,500 the Xavier value 1/√width falls below 0.02 (computed), so a much wider model would start with relatively larger weights. The lecture keeps the GPT-2 values so the reproduction stays faithful. (The PyTorch-defaults, 1/√n_layer and 24-layer numbers above come from a check run for this card: CPU, seed 1337, the lab's stream_std; they are not lab rows.)

Understand and remember

  • Independent random adds → their variances add → N adds of std σ give std √N·σ → shrink each add by 1/√N and the sum stays at σ (100 adds: 10.09 vs 1.00)
  • Pre-norm blocks do x = x + attn(ln_1(x)) then x = x + mlp(ln_2(x)) → 2 adds per block → 24 adds in 12 blocks → the two c_proj layers that produce those adds start at 0.02/√24 = 0.00408
  • Without the scale all 24 adds land at full size → the stream reaches std 1.54 by block 12 instead of 0.30 (5.1×, close to √24 = 4.9) → with the scale the final size stops depending on depth (24 layers with their own scale: 0.298)
  • Xavier picks std = 1/√fan_in so a layer's output keeps its input's size → for GPT-2 widths that is 0.036 to 0.025 → a fixed 0.02 is close enough for every GPT-2 size → the reproduction keeps OpenAI's value rather than a formula
  • detail that matters nn.Embedding's default is std 1, not 1/√fan_in → with PyTorch defaults wpe starts 48× larger than the tied wte → the stream starts at std 1.00 and is mostly position → so _init_weights must also cover the Embedding branch

  2. mechanism Walk through what happens to the stream std, from the embeddings to block 12, in the scaled 124M model. Where does each piece of growth come from?
    Check

    • each block reads a LayerNorm'd copy, so its output size doesn't depend on the stream's size

    • the adds pile up as √N: 0.14 at block 3, 0.30 at block 12
  3. tradeoff Your model has 24 layers instead of 12. Which is cheaper to get wrong: keeping 0.02 everywhere, or keeping the 12-layer scale 0.00408? What does each cost at the end of the stream?
    Check

    Check
    • c_attn and c_fc feed the block's inside, after a LayerNorm
    • c_proj is the last layer of each branch; its output is what gets added to x
    • scaling it sets the size of each add directly

Why this step?

4 · Compare against what you already know

vs Kaiming init: gain / √fan_in: Kaiming init and GPT-2's residual scale both divide by a square root. What is each one counting, and which failure does each prevent?

Check
  • Kaiming: √fan_in, the number of terms summed inside one layer; keeps one layer's output the size of its input
  • residual scale: √(2·n_layer), the number of adds stacked on the stream across the depth
  • Kaiming prevents blow-up or collapse inside a deep stack of layers; the residual scale prevents the stream growing with depth
  • GPT-2 needs both: 0.02 ≈ 1/√width per layer, and 1/√24 on c_proj

vs Feed-forward and residual connections: The char-level GPT added residual connections with no special init. Why was that fine there, and what changes at GPT-2's depth?

Check
  • the residual path keeps gradients flowing because x + f(x) passes the gradient straight through
  • with few blocks there are only a handful of adds, so √N growth stays small
  • at 12 blocks (24 adds) and more, the growth reaches 5× unless the adds are scaled

vs Batches, targets and the 10.82 sanity check: The first-loss card checks the loss at init against 10.82. Would that check catch a missing residual scale? What would?

Check
  • no: the loss at init stays near 10.8–11 either way, because ln_f normalizes the stream before lm_head
  • the missing scale shows up in the stream's std (1.54 vs 0.30) or in the c_proj weight std (0.02 vs 0.00408)
  • so print weight stds, not just the loss
