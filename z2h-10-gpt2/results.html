The results: beating GPT-2 on 10B tokens

Also called: the morning-after results, the eval curves, reading the log. Lecture 9 · SECTION 4: results in the morning! GPT-2, GPT-3 repro · 3:43:05

Prime · 2 minutes before you read

The problem: A training run ends with a log full of numbers. Without a fair baseline and a sense of how noisy each score is, you can't tell a real win from a home-field advantage, a leaked test or plain luck.

Where it fits: This is the payoff of the whole lecture. The data card built the scorecards (val loss on a held-out shard, HellaSwag); this card reads them after the 10B-token run and asks how far to trust them.

In one breath: after one pass over 10 billion FineWeb-Edu tokens, Karpathy's from-scratch 124M model scores a lower validation loss than OpenAI's GPT-2 checkpoint on the same held-out text, and a higher HellaSwag accuracy, even though GPT-2 saw about 10× more tokens. Four passes (40B tokens) bring HellaSwag to 33.24%, close to GPT-3 124M's 33.7%. To read those numbers correctly you also need their caveats: whose data the test favours, how noisy each score is, and whether the answers leaked into the training data.

Predict first: GPT-2 124M trained on about 100B tokens. This run trains the same-sized model on 10B. On HellaSwag (random guessing = 25%, GPT-2 = 29.4%), does the 10B-token model end up above or below GPT-2?

Above. Karpathy points out that he trained on "only 10 billion tokens" while GPT-2 had about 100 billion (3:44:50), and it still crosses the 29.4% line. Token count isn't everything: FineWeb-Edu is filtered for educational text, which suits a common-sense test like HellaSwag. Part of the win may also be unfair, since HellaSwag's text could have leaked into the web crawl. The caveats below cover this.

Is 33.24% vs 33.7% a real gap?

Every accuracy measured on n examples has sampling noise. Its standard error (SE, the typical size of that noise) is:

SE= p(1−p)n 0.337×0.66310042=0.0047full HellaSwag: ±0.47 points 0.25×0.7520=0.097your laptop's 20 rows: ±9.7 points
pthe accuracy being measured0.337 · 0.25 nhow many examples it was measured on10,042 · 20 SEstandard error: how far a rerun on fresh examples typically landscomputed

The gap to GPT-3 is 33.7 − 33.24 = 0.46 points, about one SE, so "almost GPT-3" is fair. The gap over GPT-2 at 40B is 33.24 − 29.45 = 3.8 points, about 8 SE, so that one is real. Your laptop's 3/20 → 4/20 is well inside the ±9.7-point noise.

Where the numbers come from

The script doesn't decide whether it won. It appends one line per measurement to log/log.txt, in the form step, stream, value. The last cell of play.ipynb groups those lines into three streams (train, val, hella) and plots each one against the dashed baselines. That's why the run can go overnight: you judge it in the morning from the file.

Why it beats the alternatives: which number to trust

✗ Train loss

It's measured on the batches the model is learning from, so it can't tell learning apart from memorising. In this run it also swings periodically, which Karpathy suspects comes from the unshuffled data (3:46:35).

✗ Val loss vs GPT-2's 3.2924

A home game. Our model trained on FineWeb-Edu and GPT-2 on WebText, so part of the lower loss only means our model knows this kind of text better, not that it is a better model.

✗ HellaSwag on 20 rows

Your laptop's 3/20 and 4/20 carry ±9.7 points of noise. They prove the eval code runs, and nothing about quality.

✓ Full HellaSwag beside val loss

A task neither model trained for, measured on 10,042 rows (±0.47 points), read next to the held-out loss. That's what makes "beats GPT-2" and "almost GPT-3" believable.

So did it really beat GPT-2?

On these two scorecards, yes, with caveats Karpathy states himself. FineWeb-Edu is English, educational web text with little code, math or other languages. GPT-2's WebText was broader, so it may be stronger at things neither test measures. HellaSwag's text may also have leaked into the web crawl. And the data was never shuffled, which shows up as a periodic wobble in the loss. His suggested next steps: shuffle documents and shards every epoch, try a max learning rate about 3× higher, and use T=2048 with B=32 to match GPT-3 (3:51:11).

This is also only a base model: it continues internet text and can't chat. For the same run in raw C/CUDA, see llm.c (124M in 90 minutes for $20). For the chat finetuning that build-nanogpt skips, see nanochat. The start-here course (z2h-0) has the full "where next" card.

Understand and remember

  • GPT-2 trained on WebText, ours on FineWeb-Edu → the val shard is our distribution → lower val loss is partly home advantage → a task neither model trained on (HellaSwag) is the fairer head-to-head
  • Accuracy on n examples has noise SE = √(p(1−p)/n) → n = 10,042 gives ±0.47 points, n = 20 gives ±9.7 → 33.24 vs 33.7 is about one SE ("almost GPT-3"), while 29.4 → 33.24 is about 8 SE (a real win)
  • Better-curated data (educational text) → more signal per token → 10B tokens beat GPT-2's ~100B on HellaSwag → but a test that leaked into the web crawl would inflate the same score, so the win carries a caveat
  • 10B tokens ÷ tokens per second = wall time → ~1.5M tok/s on 8×A100 gives ~1.9 h, ~1,300 tok/s on the M3 gives ~89 days (≈1,150× slower) → you do the full run on a rented GPU and use the laptop to check the plumbing
  • detail that matters The loop only appends step stream value lines to log.txt and a separate notebook plots them → the run needs no supervision, and you can judge an overnight run (or re-plot one) from the text file alone
  • detail that matters The data is read in a fixed shard order with no shuffling → the same documents come round at the same point every epoch → a periodic wobble in the loss that looks like a training problem but is really a data-order artefact

Reference only

  • baselines hard-coded in play.ipynb: 3.2924, 0.294463, 0.337
  • eval cadence: every 250 steps, 20 val batches; checkpoint every 5000 steps
  • torchrun --standalone --nproc_per_node=8 train_gpt2.py
  • llm.c ~223k vs PyTorch ~185k tok/s on one GPU
  • README cost: ~1 h, ~$10

4 · Compare against what you already know

vs Data and scorecards: FineWeb-Edu, val loss, HellaSwag: That card builds the scorecards (val shard, HellaSwag completion scoring) and this card reads them. Which design choices made there decide how much you can trust the numbers here?

Check
  • holding out shard 0 as val → val loss measures generalisation within FineWeb-Edu, not across datasets
  • completion-style acc_norm → a small model can be scored at all, with length-normalised loss
  • the size of the val set → the noise level of every comparison
  • the dataset choice (FineWeb-Edu) → both the 10× token efficiency and the home-field caveat

vs Overfit one batch, then a real data loader: Crushing one batch to loss 0.36 and beating GPT-2's val loss both show a loss going down. What does each prove, and how would each mislead you if you read it as the other?

Check
  • overfitting one batch proves the plumbing (gradients flow, the optimizer works) and says nothing about generalisation
  • a held-out val loss below a baseline is evidence of real learning
  • read an overfit loss as quality and you fool yourself; read a val loss as a plumbing check and you waste a 2-hour run finding bugs

vs Train/dev/test and under- vs overfitting: The makemore MLP used a train/dev/test split of one dataset. How is comparing against an outside checkpoint (GPT-2) on our val shard different, and what new failure does that bring?

Check
  • splits of one dataset compare models on the same distribution
  • GPT-2 trained on different data, so our val shard is off-distribution for it
  • new failure: a distribution-shift win that looks like a quality win
  • fix: add an external task (HellaSwag) that neither model trained on

5 · Predict commit to an answer before revealing

Karpathy suggests shuffling documents and shards every epoch for the 40B run. What would you expect to change in the train-loss curve and in the final HellaSwag, and which of the two changes would you be more confident about?

Reveal

The periodic wobble in the train loss should flatten, because the same documents no longer arrive at the same point in every epoch. That's the confident prediction, since it follows directly from the cause. Any HellaSwag change is less certain: a shuffle mostly affects later epochs, the effect could easily be under one SE (±0.47 points), and you'd need to rerun the whole thing to see it.
