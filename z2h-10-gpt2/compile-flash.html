Kernel fusion: torch.compile and flash attention

Also called: operator fusion, compiling the model, fused attention, SDPA (F.scaled_dot_product_attention), FlashAttention, online softmax. Lecture 9 · torch.compile, Python overhead, kernel fusion, 130ms · 1:48:15 and flash attention, 96ms · 2:00:18

Prime · 2 minutes before you read

The problem: After TF32 and bf16, GPT-2's step on an A100 is still 300 ms, and faster arithmetic no longer helps: the GPU spends its time moving tensors between main memory and the compute cores, one small operation at a time, and attention writes a huge T × T matrix it immediately reads back.

Where it fits: This is the third rung of the speed ladder, after the precision card. It builds on the four-line masked attention from the GPT course and on the idea that the step is memory-bound, which is why TF32 gave 3× instead of 8×.

In one breath: after bf16, GPT-2's training step is slow mostly because data keeps travelling between the GPU's big main memory and its tiny fast compute cores, one small operation at a time. torch.compile merges chains of small operations into one GPU program ("kernel fusion"), and flash attention rewrites attention so the huge T × T score matrix is never written to main memory at all. On Karpathy's A100 that takes one step from 300 ms to 130 ms to 96 ms, and the loss doesn't change.

Predict first: flash attention does more arithmetic than the 4-line manual attention (it rescales partial results as it goes). Swapping it in, does Karpathy's step get slower, stay the same, or get faster? And does the loss change?

Faster, and the loss is identical. The step goes from 130 ms to about 96 ms, 26% less time (computed: (130 − 96) / 130), and the step-49 loss matches up to float noise (2:05:38). The extra arithmetic is cheap; the memory traffic it saves is not. On your M3 the whole model's forward + backward goes 738 → 600 ms with the loss 10.961859 both times.

Where the time goes: trips to memory

A GPU has two kinds of memory. HBM (high-bandwidth memory) is the big one, 80 GB on an A100, where every tensor lives between operations. SRAM is on-chip memory right next to the compute cores (megabytes, not gigabytes): very fast, but far too small to hold a whole tensor. A kernel is one program launched on the GPU. In normal ("eager") PyTorch, every tensor operation you write is its own kernel: Python launches it, it reads its inputs from HBM, computes, and writes its output back to HBM, then Python launches the next one.

For cheap element-by-element maths, the reading and writing costs far more than the arithmetic. Take the tanh-GELU in the MLP. Written out op by op, its formula is 8 separate operations on the MLP's hidden tensor, which at B = 16, T = 1024 holds 16 × 1024 × 3072 fp32 numbers = 201.3 MB:

0.5 * x * (1 + tanh(0.7979 * (x + 0.044715 * x**3))) op-by-op : x**3, *0.044715, +x, *0.7979, tanh, 1+, x*, 0.5* 18 reads/writes of a 201.3 MB tensor = 3,624 MB of HBM traffic fused : read x once, write the result once 2 × 201.3 MB = 403 MB (9× less)

Computed for this card, fp32, one forward pass of one layer's GELU. Ops that take two tensors (+x, x*) read two and write one, hence 18. PyTorch's built-in nn.GELU is already one kernel; the point is what happens to any chain of small ops you write yourself.

torch.compile: one line, 300 → 130 ms

model = torch.compile(model) looks at your whole forward before running it, turns it into a graph of tensor operations, and generates new kernels that fuse neighbouring operations. Two costs disappear: the Python interpreter no longer launches ops one by one, and fused chains skip the HBM round trips in between. It's a compiler for the model, the way GCC is for C code. You pay once: the first call compiles (1.7 s in your lab run), and every call after that uses the fused kernels.

Flash attention: never write the T × T matrix

Attention in GPT-2 is four lines: scores q @ kᵀ (scaled by 1/√64), a causal mask that sets future positions to −∞, a softmax along each row, and @ v. Here q, k, v are the query, key and value tensors of shape (B, nh, T, hs): batch, 12 heads, T positions, head size 64. The scores tensor att is (B, nh, T, T), and every one of the four lines writes it to HBM or reads it back.

one layer, forward, B=4, nh=12, T=1024, fp32 (the lab's big case) att (T × T) : 4 × 12 × 1024 × 1024 × 4 bytes = 201.3 MB q, k, v, y : 4 × 12 × 1024 × 64 × 4 bytes = 12.6 MB each manual : write att, then r/w for scale, mask, softmax, read for @v 8 × 201.3 + 4 × 12.6 = 1,661 MB flash : read q, k, v, write y 4 × 12.6 = 50 MB (33×)

Computed for this card; counts memory traffic only. The measured speedup of the attention op on your M3 is smaller, 7.88× at T = 1024 and 2.50× at T = 256, because the two matmuls still cost real arithmetic. Going from T = 256 to 1024 makes the matrix 16× bigger (12.6 → 201.3 MB), which is why the win grows with context length.

torch.compile can't find this on its own (2:00:18). Fusing the four lines needs a different algorithm, because softmax seems to need a whole row of scores before it can divide by the row's sum. Flash attention gets around that with the online softmax.

The online softmax: normalise as you go

Flash attention reads the keys and values one tile (block of positions) at a time. For each query it keeps three running numbers: the largest score so far m, the softmax denominator so far l, and the unnormalised output so far y. When a new tile brings a bigger maximum, the old sums are simply rescaled (2:02:10):

m′=max(m,sj)new running max l′=l·em−m′+esj−m′rescale old sum, add new term y′=y·em−m′+esj−m′vjsame rescale for the output
sjthe score of key j for this query (one entry of q @ kᵀ, already scaled)2, 1, 3 below vjthe value vector at position j (a single number here)10, 20, 30 below mthe largest score seen so far; subtracting it keeps every e… ≤ 1starts at −∞ lrunning softmax denominator, measured relative to mstarts at 0 yrunning weighted sum of values; the answer is y / l at the endstarts at 0
scores s = [2, 1, 3], values v = [10, 20, 30] (illustrative inputs) tile 1 = keys 0,1 : m = 2 l = e^0 + e^-1 = 1.3679 y = 10·e^0 + 20·e^-1 = 17.358 tile 2 = key 2 : m' = 3 rescale by e^(2-3) = 0.3679 l = 1.3679·0.3679 + 1 = 1.5032 y = 17.358·0.3679 + 30 = 36.386 answer : y / l = 36.386 / 1.5032 = 24.205 full softmax : [0.2447, 0.0900, 0.6652] · v = 24.205 ✓

Computed for this card. The tile-by-tile answer equals the one from the full row, so a kernel can stream tiles through SRAM and never hold the whole row, let alone the whole T × T matrix. The backward pass recomputes the scores from q and k instead of storing them: more arithmetic, far less memory traffic.

▶ Build itruns on your M3 · about 25 s

When: pause the video at 1:48:15 for torch.compile and at 2:00:18 for flash attention. First check that the one-line SDPA call gives the same answer as your four lines:

import math, torch
import torch.nn.functional as F
def manual(q, k, v):                  # Karpathy's 4 lines
    T = q.size(-2)
    att = (q @ k.transpose(-2, -1)) * (1.0 / math.sqrt(k.size(-1)))
    keep = torch.ones(T, T, dtype=torch.bool, device=q.device).tril()
    att = att.masked_fill(~keep, float('-inf'))
    att = F.softmax(att, dim=-1)
    return att @ v
B, nh, T, hs = 4, 12, 1024, 64
q, k, v = (torch.randn(B, nh, T, hs, device='mps') for _ in range(3))
y1 = manual(q, k, v)
y2 = F.scaled_dot_product_attention(q, k, v, is_causal=True)
print((y1 - y2).abs().max().item())

Then time both with torch.mps.synchronize() before reading the clock (the CPU only queues GPU work). In your GPT, replace the four lines in CausalSelfAttention.forward with the SDPA call, and after building the model add:

model = torch.compile(model)   # compiles on the first call

You should see (measured on your M3 by labs/compile-flash.py):

Why it beats the alternatives

✗ More raw FLOPS

TF32 promised 8× faster matmuls and delivered about 3× (1000 → 333 ms), because the step is waiting on memory, not arithmetic (1:38:35). Faster maths doesn't fix slow trips to HBM.

✗ Hand-written CUDA kernels

You can fuse everything by hand, as llm.c does, and go faster still. But every change to the model means rewriting and re-checking kernels, and you leave Python behind.

✗ torch.compile on its own

It fuses the small elementwise chains (300 → 130 ms) but keeps the four attention lines as separate kernels, so the T × T matrix still goes through HBM.

✓ compile + flash attention

Two lines of code, the same maths and the same loss. Compile removes Python overhead and fuses the small ops; SDPA runs attention in one kernel with the online softmax. 300 → 96 ms, 3.1× in all.

When they don't help

torch.compile costs a compile on the first call (1.7 s here, 12.5 s on the lab's first-ever run). At build-nanogpt's final commit it's switched off (use_compile = False) because it interfered with the HellaSwag eval and text generation. On the M3 its gain is unreliable, and for a short script it can cost more than it saves.

Flash attention's gain grows with T: at T = 256 the matrix is 16× smaller and the attention op speeds up 2.50× rather than 7.88×. The FlashAttention kernels themselves are CUDA code; on your Mac, PyTorch serves the same SDPA call with its own backend, so the M3 shows the principle, not the A100's ratio. To go deeper: kernel fusion, launch overhead and CUDA graphs and FlashAttention I: tiling and recomputation.

Understand and remember

  • Eager PyTorch runs one kernel per op → each op reads its inputs from HBM and writes its output back → for elementwise maths the memory traffic dwarfs the arithmetic → fusing a chain into one kernel (read once, write once) cuts traffic, e.g. 18 → 2 passes for an op-by-op GELU
  • torch.compile sees the whole forward as a graph before running → it can drop the Python launch loop and generate fused kernels → 300 → 130 ms on the A100, paid for with a compile on the first call
  • Manual attention writes the (B, nh, T, T) score matrix to HBM and re-reads it for scale, mask, softmax and @v → traffic grows with T² → flash attention streams k, v tiles through SRAM and writes only y → about 33× less traffic in the lab's case, 7.88× faster measured, 130 → 96 ms on the A100
  • Softmax needs the row's max and sum before it can normalise → a tile-by-tile kernel would seem impossible → the online softmax keeps a running max m, sum l and output y and rescales them by e^(m − m′) when the max grows → the result equals the full-row softmax, so the loss doesn't change
  • detail that matters Flash attention's backward recomputes the scores from q and k instead of storing the T × T matrix → more FLOPs but far less memory → it's faster because the step is memory-bound, not compute-bound
