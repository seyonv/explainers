What compilers and interpreters do for you

Also called compiler optimization: inline expansion, constant folding, strength reduction, common-subexpression elimination, tail-call elimination, JIT compilation. The source guide names these under Compilers, and its string-concatenation loop (Java there, Python here) is the worked example.

In one breath

An optimizing compiler rewrites your code into something faster that gives the same answer: it pastes small functions in, computes constants ahead of time, swaps costly operations for cheap ones and turns tail recursion into a loop. CPython does almost none of this, because almost any name or type can change while the program runs. Neither can turn an O(n²) loop into an O(n) one; that part is up to you.

Worked example: the source's string loop, in Python

s = ""
for i in range(10**5):
    s = s + str(i) + " "     # builds a new s: copies all of the old one

s = " ".join(str(i) for i in range(10**5))  # sizes once, copies once

The middle row is CPython helping out. When it sees s = s + t or s += t and nothing else holds a reference to s, it grows the string in place instead of copying it. The source's form, s + str(i) + " ", adds str(i) first, while s is still referenced, so every pass copies. PEP 8 calls this optimization fragile and tells you not to rely on it; join is the O(n) answer everywhere.

The source says Java's + uses StringBuffer. javac emitted StringBuilder chains and, since Java 9, an invokedynamic call (JEP 280); the point, a fresh builder every pass, still holds.

What CPython 3.10 compiles, seen with dis

import dis
def folded():       return 2 * 3
def square(x):      return x * x
def use_square():   return square(5)
def times8(x):      return x * 8
def cse(x, y):      return (x + y) * (x + y)
def sum_to(n, acc=0):
    return acc if n == 0 else sum_to(n - 1, acc + n)

for f in (folded, use_square, times8, cse):
    ops = [(i.opname + " " + i.argrepr).strip()
           for i in dis.get_instructions(f)]
    print(f.__name__ + ":", " · ".join(ops))
# folded: LOAD_CONST 6 · RETURN_VALUE
# use_square: LOAD_GLOBAL square · LOAD_CONST 5 · CALL_FUNCTION
#   · RETURN_VALUE
# times8: LOAD_FAST x · LOAD_CONST 8 · BINARY_MULTIPLY · RETURN_VALUE
# cse: LOAD_FAST x · LOAD_FAST y · BINARY_ADD · LOAD_FAST x
#   · LOAD_FAST y · BINARY_ADD · BINARY_MULTIPLY · RETURN_VALUE
print(sum_to(900))        # → 405450

Why a better algorithm beats the alternatives

✗ Hope the interpreter fixes it

CPython's in-place trick saved the += form but not the source's form. That's about a 40× gap (0.468 / 0.012) from moving one +, and PyPy and other runtimes may not do the trick at all.

✗ Inline by hand, or use C macros

An optimizing compiler already inlines, and more safely than a macro, as the source notes. CPython won't inline, but a function call there is not what makes code O(n²).

✗ Wait for better compilers

Proebsting: hardware gains about 60% a year and compilers about 4%. That doubles speed every 1.47 years versus every 17.7 years (ln 2 / ln 1.04), or "every 18 years" in his words.

✓ Change the algorithm

join copies each of the 588,890 characters about once instead of copying the growing string 105 times. 64× faster, on every Python and with no compiler help.

So should you ever lean on the compiler?

Yes, in C, C++, Rust or on the JVM: write the clear version (a helper function, x * 8, a named temporary) and let -O2 or the JIT inline, fold and reduce it. Hand-tuning those things usually buys nothing there. In CPython, assume nothing is rewritten except constant folding. Write loops, not deep recursion, and raise sys.setrecursionlimit only for recursion you know is bounded.

When CPython's overhead per operation is the problem, and not the algorithm, change the engine: numpy for array work, PyPy for a pure-Python hot loop, or Numba. The next card measures those. Tuning won't rescue an O(n²) design, and it also isn't worth it on code that runs once.
