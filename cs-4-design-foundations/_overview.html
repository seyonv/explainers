Framing and sizing a design

The overview for course 4 of the core CS canon series. It ties together the 16 cards on the source guide's System Design framing pages: scoping requirements and weighing trade-offs, object-oriented design in Python, and the estimation and performance habits that tell you whether a design will fit before you build it.

In one breath

Before drawing any boxes, write two lists: what the system does, and how well it must do it, in numbers. The first list becomes classes: nouns turn into objects, each rule lives on the class that owns its data, and anything you might swap is passed in. The second list becomes arithmetic: load times time per request says how much is in flight, and availabilities multiply along the request path. If an estimate within 10× says a design can't fit, faster hardware, a better compiler or loop tuning won't save it; a better algorithm might.

The words people use

Functional vs non-functional

Functional: what the system does (shorten a link, follow it). Non-functional: how well (3,858 reads/s, never lose a row, 99.9%). The first sets what you build; the second picks which design survives.

Is-a, has-a, can-do

Is-a is inheritance (Circle is an Ellipse). Has-a is composition (a Level has Spots). Can-do is an interface (anything with update_status). Reach for has-a and can-do first; keep is-a shallow and stable.

SLO, SLA, error budget

The SLO is the target you engineer for, the SLA the looser promise with a penalty, and the error budget is 1 − SLO spent as time: 43.2 minutes a month at 99.9%.

✓ Back of the envelope

Rounded inputs, units kept, an answer within 10×, then a safety factor. It rules designs out before they're built: 2M Python nodes need 168 MB of a 128 MB budget, and 20 parts at 99.99% miss 99.9%.

When this advice doesn't apply

Both formulas are about averages in a steady state, with parts that fail independently. Little's law gives the mean number in flight, and the p99 can be many times the mean; three copies stop helping the moment one config push reaches all of them. An estimate is a filter that catches designs off by 10×, not a measurement. Once a design passes, measure it.

The object-oriented habits are for code that is shared, tested or changed often. A three-line script needs no Protocol, a Card with no behaviour is a frozen dataclass or a tuple, and a deck is a list plus random.shuffle. Know which round you're in, too: an OOD round wants classes and methods, a system-design round wants APIs, storage and scale, and a class diagram there is the wrong altitude. And below the crossover, constants win: under 471,146 items the fast machine with insertion sort beats the slow one with merge sort.
