Back-of-the-envelope estimation

Also called Fermi estimation, napkin maths or capacity estimation. The source guide's Resource Estimation page: Bob Martin's Mississippi question, a 2M-node memory check, an n³ run time, Little's law and Roebling's safety factor. Here each one is recomputed, then the memory check is asked of Python itself.

Prime · 2 minutes before you read

The problem: Gut feel says "2M small records is nothing"; in C it's 75% of a 128 MB budget and in Python it doesn't fit at all. Without five minutes of arithmetic you find out after building, like a system that would need more than 120 seconds of work each minute.

Where it fits: First card of the estimation part. The requirements card gave TinyURL's numbers; here they become a feasibility check, with overheads and Little's law. SLO arithmetic and the performance cards build on the same habit of multiplying rounded numbers with units.

By the end: Estimate memory, rate or time within 10× in a few lines, including the overhead the machine adds, and use Little's law to size what's in flight.

In one breath

Before building, multiply a few rounded numbers you already know, keeping the units, to get an answer within a factor of ten. That is enough to kill a design that needs "more than 120 seconds in each minute" (the source's Olympic example) or to show that 2M records will nearly fill 128 MB of RAM.

The first three are the source's. The TinyURL row uses the course's illustrative 3,858 reads/s and an illustrative 50 ms per request: about 193 requests are being served at any instant, which sizes a connection pool.

The same 2M-node question, asked of Python

The source's node is an int and a pointer: 8 bytes of payload. In CPython every value is a heap object with a header, and the list holding the nodes stores one more 8-byte pointer each. sys.getsizeof gives the parts; the dashed red line is the 128 MB budget.

Parts from sys.getsizeof in CPython 3.10, 64-bit: object 48 (with __slots__) or tuple 56, int 1000 → 28, list slot 8, a plain object's __dict__ 104. tracemalloc on 2M real __slots__ nodes gives 84.6 B each (one run on the author's M3). Both C rows fit; every Python layout breaks the budget, even the leanest.

In Python

import sys

def littles_law(rate=None, time=None, count=None):
    """L = lambda * W. Pass any two; returns the third."""
    if count is None:
        return rate * time
    if rate is None:
        return count / time
    return count / rate

class Node:                      # the source's node: int + pointer
    __slots__ = ("val", "next")
    def __init__(self, val, nxt=None):
        self.val, self.next = val, nxt

obj = sys.getsizeof(Node(1000))   # header + 2 slots
num = sys.getsizeof(1000)         # the int it points to
per = obj + num + 8               # + the list's pointer to it
print(f"one node = {obj} obj + {num} int + 8 ref = {per} B")
print(f"2M nodes = {2_000_000 * per / 10**6:.0f} MB > 128 MB")
print("wine: W =", littles_law(rate=25, count=150), "years")
reads = 100_000_000 / (30 * 86_400) * 100   # TinyURL
print(f"in flight: {littles_law(rate=reads, time=0.05):.0f}")
# → one node = 48 obj + 28 int + 8 ref = 84 B
#   2M nodes = 168 MB > 128 MB
#   wine: W = 6.0 years
#   in flight: 193

Output under python3 3.10. getsizeof counts the object's own bytes only, never what it points to; that is why the int and the list slot are added by hand. The full file also recomputes every row of the first table and the TinyURL sizing below.

The course's running example: TinyURL

writes/s = 100,000,000 new links / (30 × 86,400 s = 2,592,000 s) = 38.6 reads/s = 38.58 × 100 (read:write) = 3,858 records = 100,000,000 × 12 months × 5 years = 6,000,000,000 storage = 6,000,000,000 × 500 B = 3 × 10¹² B = 3 TB

Inputs are illustrative (the source gives TinyURL's features, not its scale); the same numbers appear on the requirements card. 3 TB of payload is small for disk. The overhead lesson says what not to do: 6×10⁹ Python objects would cost at least 6×10⁹ × 84 B ≈ 504 GB before the 500-byte payload, so the mapping belongs in a database, not a dict.

Why it beats the alternatives

✗ Guess from experience

"2M small records, that's nothing." In C it came to 75% of RAM; in Python it doesn't fit at all. Nothing checks the gut feeling.

✗ Build it, then measure

The most accurate, and the most expensive way to learn the design was wrong. The source's n³ job takes 200 s per try; the Olympic system would have needed 120 s a minute.

✗ Model it exactly

A full simulation or queueing model before any design exists. Its inputs are guesses anyway, so the extra digits are noise.

✓ Estimate, then derate

Five minutes with rounded inputs and units, within 10×, then a safety factor for what you missed. It rules designs out before you build them.

Is an estimate ever enough on its own?

No. It is a filter, not a measurement. It tells you whether a design is off by 10×, not whether it is 20% too slow; once a design passes, measure it. Averages hide the tail too: Little's law gives the mean number in flight, and the p99 latency can be many times the mean (general practice, not from the source; see the averages card). A safety factor like Roebling's 6× is a response to that ignorance, not a substitute for measuring.

Watch the silent multipliers: allocator and object overhead (6× in the source's C, 10.5× for a Python __slots__ node), replication, indexes and peaks. Each one is easy to leave out and alone can flip a "fits" into a "doesn't".

Understand and remember

  • Round inputs to one or two digits but keep units → multiply → an answer within 10× in minutes → enough to kill a design off by 10× before it is built
  • Payload is not the cost → allocator padding (8 → 48 B) or Python object headers, int objects and list pointers (8 → 84 B for a __slots__ node) → 2M nodes go from 16 MB to 96 MB (C) or 168 MB (Python) → the "silent multiplier" flips fits to doesn't-fit
  • In steady state, average count in system L = arrival rate λ × average time inside W → any two give the third → TinyURL: 3,858 reads/s × 0.05 s ≈ 193 requests in flight → size pools and memory by L
  • An estimate is uncertain and averages hide the tail → provision a safety factor (derate, 6× for Roebling) → then measure once the design passes
  • detail that matters sys.getsizeof counts only the object's own bytes, never what it points to → the int (28 B) and the list slot (8 B) must be added by hand → forgetting them undercounts a node by 36 of 84 bytes

Why this step?

5 · Predict commit to an answer before revealing

TinyURL's per-request time grows from 50 ms to 200 ms (a slow database), and the read rate stays 3,858/s. Before computing: what happens to the number of requests in flight, and what breaks first if the connection pool was sized for the old number?

Reveal

In flight goes from about 193 to 3,858 × 0.2 ≈ 772, four times as many, because L scales with W. A pool sized for ~200 runs out, new requests queue, W grows further, and the queue feeds on itself. Slowing down W is as dangerous as more traffic.

6 · Apply use the model, don't restate it

Estimate whether one month of TinyURL links (100M) fits in a Python dict on a 16 GB machine. Use the card's 84 B per object as the lower bound for overhead and ignore the payload first. Then add the 500-byte payload and decide. Finally compute Little's law for 3,858 reads/s at 50 ms and apply Roebling's 6× derating to the rate.

Done when: Your estimate says at least 100,000,000 × 84 B ≈ 8.4 GB of overhead alone, and with 500 B of payload each (another 50 GB) it can't fit in 16 GB; in flight ≈ 193, and the derated capacity to provision is 23,148 reads/s.
