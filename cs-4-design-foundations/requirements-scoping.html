Functional vs non-functional requirements

Also called scoping, features vs quality attributes, or "the -ilities". The source guide's Feature Sets page: ask clarifying questions, split the requirements into what the system does and how well it does it, and keep raw data. Its examples are TinyURL and a financial dashboard.

In one breath

Before drawing any boxes, write two lists. Functional requirements are the features a user touches: shorten a link, follow it. Non-functional requirements are how well the system must do them: how much load, how little data loss, which rules it must obey. The first list tells you what to build; the second tells you which design will survive.

Worked example: the TinyURL requirements sheet

Functional: what it doesthe source's four TinyURL features

  1. Derive a short alias from a long URLshorten(code, url): one write
  2. Look up the original and redirectredirect(code): the hot read path
  3. Track click ratesone event per redirect
  4. Let users sign up to manage their linksaccounts, ownership of links

Non-functional: how wellthe source's -ilities, applied to TinyURL

  • Scalability: 38.6 writes/s, 3,858 reads/s, 3 TB in 5 yearsfrom the illustrative inputs below
  • Reliability: never lose a mappinga lost row is a link broken for good
  • Maintainability: bug fixes need no manual intervention
  • Security: encrypted access; only owners edit links
  • Compliance: click logs hold user dataprivacy regulations apply (source: "financial or privacy")
writes/s = 100,000,000 new links / (30 × 86,400 s = 2,592,000 s) = 38.6 reads/s = 38.58 × 100 (read:write) = 3,858 records = 100,000,000 × 12 months × 5 years = 6,000,000,000 storage = 6,000,000,000 × 500 B = 3 × 10¹² B = 3 TB

Inputs are illustrative (100M new links a month, 100:1 reads to writes, 500-byte records, 5 years, 30-day months): the source lists TinyURL's features but gives no scale. The non-functional bullets are the source's -ility definitions applied to TinyURL by us.

Keep raw data: a feature nobody asked for yet

The source's rule: store raw events, not only summaries, because you can't predict tomorrow's analytics. Here redirect writes both. A month later, product asks for clicks by country.

import sqlite3
db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE links(code TEXT PRIMARY KEY, url TEXT)")
db.execute("CREATE TABLE clicks(code TEXT, ts INT, country TEXT)")
counter = {}                     # the summary-only alternative

def redirect(code, ts, country):  # functional 2 and 3
    (url,) = db.execute(
        "SELECT url FROM links WHERE code = ?", (code,)).fetchone()
    db.execute("INSERT INTO clicks VALUES (?, ?, ?)",
               (code, ts, country))          # raw event, kept
    counter[code] = counter.get(code, 0) + 1  # summary only
    return url

def clicks_by_country(code):     # a later feature, from raw rows
    return db.execute(
        "SELECT country, COUNT(*) FROM clicks WHERE code = ? "
        "GROUP BY country ORDER BY country", (code,)).fetchall()

# 5 illustrative clicks: US, CA, US, IN, US
# counter     {'a1b2': 5}
# by country  [('CA', 1), ('IN', 1), ('US', 3)]
# duplicate → UNIQUE constraint failed: links.code

Output from code/requirements-scoping.py under python3 3.10. The counter says 5 and can never say more; the raw rows answer a question asked after the fact. The primary key turns "short codes are unique" into a rule the database enforces. sqlite3 ships with Python and speaks standard SQL, the source's recommended interface.

Why scope both lists first

✗ Jump to boxes

Draw load balancers and caches before asking anything. You may design a paid, tiered, multi-level system for a free one-floor lot, or miss that data is pushed in bursts.

✗ Features only

Four TinyURL features fit on one laptop with a dict. Without "3,858 reads/s, 3 TB, never lose a row", nothing tells you that design fails.

✗ Store only summaries

Cheaper on day one: one counter per link instead of 100 click rows. Then "clicks by country" needs an ingestion change and past clicks are gone.

✓ Two lists, then the check

Functional sets what to build; the -ilities, as numbers, pick the design. Each new feature goes through the three questions before it joins the scope.

Is the split always clean, and is raw data always right?

No to both. Some requirements sit on the line: for a trading system, "respond in under a millisecond" is arguably the feature itself, and "links expire after a year" is a feature that exists to meet a storage limit. The labels matter less than having both lists and numbers on the second one.

Raw data has a price. At the illustrative scale, raw clicks are 100 × 100,000,000 = 10,000,000,000 rows a month, 100 for every new link. And the source's own Compliance line can cut the other way: privacy rules may limit how long you keep per-user events. A common answer (our inference, not the source's) is to keep raw events in cheap storage for a fixed retention period and serve reads from summaries built from them.
