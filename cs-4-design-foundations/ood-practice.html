Object-oriented design practice

Also called OOD, low-level design, or the "design a parking lot" interview. The cheat-sheet lists the parking lot's objects (ParkingLot, Level, ParkingSpot, Vehicle), draws a Card/Deck class diagram, asks "how does a Deck shuffle?", and ends with ten practice prompts. This card answers the first two in Python and sketches the rest.

In one breath

Turn the nouns in the problem into classes and the verbs into methods, then put each rule in the class that owns the data it reads. A spot knows its own size, so spot.fits(vehicle) lives on the spot. Anything you might want to swap later, such as which free spot to pick or which random source to shuffle with, gets passed in rather than baked in.

Worked example 1: the parking lot

Diamond = "has" (the lot owns its levels, a level owns its spots). Hollow triangle = "is a". Vehicle types and the accessible spot come from the source's footnotes; the size rule and both policies are our sketch.

class Size(Enum):
    SMALL = 1; COMPACT = 2; LARGE = 3

class Car(Vehicle): size = Size.COMPACT     # also Motorcycle, Bus

@dataclass
class Spot:
    name: str
    size: Size
    accessible: bool = False
    vehicle: Vehicle | None = None

    def fits(self, v):                      # the spot owns the rule
        return (self.vehicle is None
                and v.size.value <= self.size.value
                and (v.permit or not self.accessible))

def first_fit(spots): return spots[0]      # whatever comes first
def best_fit(spots):                       # smallest spot that fits
    return min(spots, key=lambda s: (s.size.value, s.accessible))

@dataclass
class ParkingLot:
    levels: list[Level]
    choose: callable = best_fit             # policy is swappable

    def park(self, v):
        spots = [s for lv in self.levels for s in lv.free(v)]
        if not spots:
            return None
        spot = self.choose(spots)
        spot.vehicle = v
        return spot

Same lot, same six arrivals, two policies. Level 1 has spots L1 large, C1 compact, S1 small; level 2 has L2 large, C2 compact, H1 compact and accessible. The lot and the arrivals are illustrative.

Time O(S) per arrival · Space O(S) for S spots: park scans every spot once. A min-heap of free spots per size would make it O(log S), which matters for thousands of spots and not for six.

Worked example 2: how does a Deck shuffle?

Fisher–Yates: walk from the last position to the second. At each position i, pick j uniformly from 0…i and swap. After the swap, position i is final and is never touched again.

class Deck:
    def shuffle(self, rng=random):
        a = self.cards                     # Fisher-Yates, in place
        for i in range(len(a) - 1, 0, -1):
            j = rng.randrange(i + 1)       # 0 <= j <= i, uniform
            a[i], a[j] = a[j], a[i]        # a[i] is now final

    def deal(self):
        return self.cards.pop()

Why it beats the alternatives

✗ One class, if/elif on type

if kind == "bus": … inside park(). Every new vehicle or spot type edits the same method, and a typo in a string fails silently.

✗ Rules on the vehicle

Car.can_park(spot) with isinstance checks: 3 vehicles × 4 spot kinds = 12 cases spread over 3 classes, and a new spot kind edits all of them.

✗ Policy baked into park()

First-fit hard-coded put car a in L1 and turned bus y away (5 of 6). Trying another rule means editing and retesting the lot.

✓ Rule with the data, policy passed in

fits() is one expression on Spot, because sizes compare. Passing best_fit parked 6 of 6 without changing any other class.

Are more classes always better?

No. Use a class when data and the rules about it travel together; otherwise a function over plain data is simpler. A Card has no behaviour, so a frozen dataclass is enough, and outside an interview a deck is a list plus random.shuffle. Don't give Car, Bus and Motorcycle subclasses methods they don't need: here they differ only by one value.

Know which round you're in. An OOD round wants classes, relations and one or two methods written out. A system-design round for "a parking service" or "a chat server" wants APIs, storage and scale instead, and a class diagram there is the wrong altitude. Either way, ask the clarifying questions first (levels? vehicle types? paid or free?), because they decide the classes.
