Object-oriented design practice

Also called OOD, low-level design, or the "design a parking lot" interview. The source guide lists the parking lot's objects (ParkingLot, Level, ParkingSpot, Vehicle), draws a Card/Deck class diagram, asks "how does a Deck shuffle?", and ends with ten practice prompts. This card answers the first two in Python and sketches the rest.

Prime · 2 minutes before you read

The problem: "Design a parking lot" goes wrong when rules land on the wrong class (a vehicle checking every spot type, 12 cases over 3 classes) or the policy is baked into one method, so trying best-fit instead of first-fit means rewriting the lot.

Where it fits: Last OOD card: it uses everything before it. Classes and frozen values, inheritance (Car is a Vehicle), interfaces (a policy is anything callable), and the requirements card's clarifying questions, which decide the classes.

In one breath

Turn the nouns in the problem into classes and the verbs into methods, then put each rule in the class that owns the data it reads. A spot knows its own size, so spot.fits(vehicle) lives on the spot. Anything you might want to swap later, such as which free spot to pick or which random source to shuffle with, gets passed in rather than baked in.

Worked example 1: the parking lot

Diamond = "has" (the lot owns its levels, a level owns its spots). Hollow triangle = "is a". Vehicle types and the accessible spot come from the source's footnotes; the size rule and both policies are our sketch.

class Size(Enum):
    SMALL = 1; COMPACT = 2; LARGE = 3

class Car(Vehicle): size = Size.COMPACT     # also Motorcycle, Bus

@dataclass
class Spot:
    name: str
    size: Size
    accessible: bool = False
    vehicle: Vehicle | None = None

    def fits(self, v):                      # the spot owns the rule
        return (self.vehicle is None
                and v.size.value <= self.size.value
                and (v.permit or not self.accessible))

def first_fit(spots): return spots[0]      # whatever comes first
def best_fit(spots):                       # smallest spot that fits
    return min(spots, key=lambda s: (s.size.value, s.accessible))

@dataclass
class ParkingLot:
    levels: list[Level]
    choose: callable = best_fit             # policy is swappable

    def park(self, v):
        spots = [s for lv in self.levels for s in lv.free(v)]
        if not spots:
            return None
        spot = self.choose(spots)
        spot.vehicle = v
        return spot

Same lot, same six arrivals, two policies. Level 1 has spots L1 large, C1 compact, S1 small; level 2 has L2 large, C2 compact, H1 compact and accessible. The lot and the arrivals are illustrative.

Time O(S) per arrival · Space O(S) for S spots: park scans every spot once. A min-heap of free spots per size would make it O(log S), which matters for thousands of spots and not for six.

Worked example 2: how does a Deck shuffle?

Fisher–Yates: walk from the last position to the second. At each position i, pick j uniformly from 0…i and swap. After the swap, position i is final and is never touched again.

class Deck:
    def shuffle(self, rng=random):
        a = self.cards                     # Fisher-Yates, in place
        for i in range(len(a) - 1, 0, -1):
            j = rng.randrange(i + 1)       # 0 <= j <= i, uniform
            a[i], a[j] = a[j], a[i]        # a[i] is now final

    def deal(self):
        return self.cards.pop()

n = 5: 1/5 · 1/4 · 1/3 · 1/2 = 1/120 = 1/5! n = 52: 52! = 8.0658… × 10^67 (a 68-digit number) ≈ 2^225.6 naive "swap a[i] with a[randrange(n)]", n = 3: 3^3 = 27 equally likely paths onto 3! = 6 orders; 27 / 6 = 4.5 is not whole, so it can't be fair: counts 4, 5, 5, 5, 4, 4 out of 27 (Fisher–Yates: 1 each out of 6)

All computed by the script (the naive counts by enumerating all 27 paths). A generator seeded from 32 bits can reach at most 232 ≈ 4.29 × 109 of the 8.07 × 1067 orders, so for a real card game the seed, not the loop, is the weak point. Time O(n) · Space O(1) extra: one swap per position.

Why it beats the alternatives

✗ One class, if/elif on type

if kind == "bus": … inside park(). Every new vehicle or spot type edits the same method, and a typo in a string fails silently.

✗ Rules on the vehicle

Car.can_park(spot) with isinstance checks: 3 vehicles × 4 spot kinds = 12 cases spread over 3 classes, and a new spot kind edits all of them.

✗ Policy baked into park()

First-fit hard-coded put car a in L1 and turned bus y away (5 of 6). Trying another rule means editing and retesting the lot.

✓ Rule with the data, policy passed in

fits() is one expression on Spot, because sizes compare. Passing best_fit parked 6 of 6 without changing any other class.

Are more classes always better?

No. Use a class when data and the rules about it travel together; otherwise a function over plain data is simpler. A Card has no behaviour, so a frozen dataclass is enough, and outside an interview a deck is a list plus random.shuffle. Don't give Car, Bus and Motorcycle subclasses methods they don't need: here they differ only by one value.

Know which round you're in. An OOD round wants classes, relations and one or two methods written out. A system-design round for "a parking service" or "a chat server" wants APIs, storage and scale instead, and a class diagram there is the wrong altitude. Either way, ask the clarifying questions first (levels? vehicle types? paid or free?), because they decide the classes.

Understand and remember

  • Put each rule in the class that owns the data it reads → a spot knows its size, so spot.fits(v) is one comparison of sizes → a new vehicle or spot kind changes one place, not 3 × 4 cases
  • Pass swappable behaviour in (strategy/policy) → ParkingLot(choose=best_fit) → changing first-fit to best-fit changes the outcome (5 of 6 → 6 of 6) without editing any class
  • Fisher–Yates: at step i pick j uniformly in 0…i and swap → position i is final → n · (n−1) ⋯ 1 equally likely paths map one-to-one onto n! orders → uniform; the naive loop's nⁿ paths can't split evenly over n! orders
  • Clarifying questions → decide the classes (levels? vehicle types? permits?) → and the round decides the altitude: classes and methods for OOD, APIs, storage and scale for system design
  • detail that matters A seeded RNG passed into shuffle(rng) → the same shuffle every test run; and a 32-bit seed reaches at most ≈ 4.29 × 10⁹ of 52! ≈ 8.07 × 10⁶⁷ orders → for a real card game the seed, not the loop, is the weak point

4 · Compare against what you already know

vs Simple is not easy: Passing choose into ParkingLot and passing state into shorten are both "pass it in, don't hardwire it". What does each one make swappable or testable, and what would the hardwired version cost?

Check
  • the policy can be swapped (first-fit vs best-fit) without editing the lot
  • the state can be any literal, so one call tests any case
  • hardwired: edit and retest the lot for each policy; replay history for each test

vs Random pick with a blacklist: Fisher–Yates and the blacklist random-pick card both need every outcome equally likely. What mechanism guarantees uniformity in each, and what bug breaks it?

Check
  • Fisher–Yates: each step picks uniformly among the positions still unfixed, giving n! equally likely paths
  • blacklist pick: draw uniformly from [0, m) and remap each hole to a distinct allowed value
  • bugs: picking from the whole range each step, or a remap that sends two draws to the same value

Why this step?

5 · Predict commit to an answer before revealing

Before computing: with the naive "swap with randrange(n)" shuffle on 4 cards, is the bias worse or better than on 3? Guess the fewest and the most paths any single order gets out of 4⁴ = 256.

Reveal

Worse. 256 paths onto 24 orders is 10.67 each on average, and the real counts range from 8 to 15 paths per order (enumerated by a short script). The most likely order is almost twice as likely as the least likely one. On 3 cards the range was only 4 to 5.
