Availability and SLO arithmetic

Also called "counting nines", uptime budgeting, or the error budget. The source guide's image-resize service asks for 99.9% overall and 99.99% at the API tier, and calls "replicate until PN < R" hogwash, but never turns a percentage into minutes. This card does.

Prime · 2 minutes before you read

The problem: "99.9%" sounds like a quality, not a budget, so teams give every part the same target, add copies without asking what they share, and discover in the first incident that a 60-minute manual failover spends the whole month's 43.2 minutes at once.

Where it fits: Third estimation card. Back-of-envelope turned rates into what's in flight; this card turns an availability target into minutes, and shows how parts in series and copies in parallel combine. cs-5 picks up where the independence assumption breaks.

In one breath

An availability target is a downtime allowance in disguise: 99.9% means you may be down 0.1% of the time, which is 43.2 minutes in a 30-day month. Parts you need all of multiply their availabilities (the total gets worse); copies you need only one of multiply their failure chances (the total gets better), but only if they fail independently.

In Python

from math import comb
MONTH_MIN = 30 * 24 * 60         # 43,200

def downtime(a, minutes=MONTH_MIN):
    return (1 - a) * minutes     # the error budget

def serial(*parts):              # all parts must be up
    out = 1.0
    for a in parts:
        out *= a
    return out

def parallel(p, k):              # any 1 of k is enough
    return 1 - (1 - p) ** k

def k_of_n(p, k, n):             # at least k of n up
    return sum(comb(n, i) * p**i * (1 - p) ** (n - i)
               for i in range(k, n + 1))

# downtime(0.999)                 → 43.20 min
# serial(*[0.9999] * 20)          → 0.998002   86.32 min
# parallel(0.99, 3)               → 0.999999    0.04 min
# k_of_n(0.99, 2, 3)              → 0.999702   12.87 min
# serial(0.9995, parallel(.99,3)) → 0.999499   21.64 min

Time O(n) · Space O(1): one multiply per part, or one binomial term per allowed number of survivors. Output from code/slo-arithmetic.py under python3 3.10.

Why budgeting beats the alternatives

✗ Give every part the target

Twenty parts at 99.9% each give 0.999²⁰ = 98.0%. Parts on the path need more nines than the whole, which is why the source sets the API tier at 99.99%.

✗ Replicate until PN < R

Assumes copies fail independently. A bad config or shared power supply takes all of them at once; above, three copies still lose 21.6 min to a 99.95% shared layer.

✗ Measure uptime only

A second at 3 a.m. and a second at peak count the same. The source prefers yield, the share of requests served, which weighs outages by traffic.

✓ Budget the downtime

Turn the SLO into minutes (or requests), split them along the request path, and check recovery against them: a 60-minute manual failover spends 43.2 minutes at once.

Should you always add another nine?

No. Each nine cuts the budget tenfold and costs more redundancy, automation and slower launches. Past a point users can't tell: someone on a 99%-reliable phone can't tell 99.99% from 99.999% (the SRE book's example). An internal batch job may be fine at 99%. Unspent budget is also a signal that you could ship faster.

The formulas assume steady state and independent parts. Real availability is MTTF / (MTTF + MTTR): at 99.9% with a 60-minute repair you need 41.6 days between failures, with a 2-minute automatic failover 1.39 days (illustrative repair times). That's why the source insists on automated leader election: cutting repair time is often cheaper than preventing failures.

Understand and remember

  • Availability target → allowed downtime = (1 − A) × T → 99.9% of a 30-day month = 43.2 min → a single 60-minute failover spends the budget at once → recovery time must be checked against the budget
  • A request needs every part on its path → availabilities multiply → 20 parts at 99.99% = 0.998 = 86.3 min a month → parts need more nines than the whole (the source's 99.99% API tier under a 99.9% service)
  • Copies where any one is enough → failure chances multiply (1 − 0.01³) → huge gains, but only if copies fail independently → a shared layer in series sets the floor (21.6 min at 99.95%), which is why "replicate until pᴺ < R" is hogwash
  • A = MTTF / (MTTF + MTTR) → the same target can be met by failing less or recovering faster → at 99.9%, a 2-minute automatic failover needs a failure-free stretch of only 1.39 days vs 41.6 days for a 60-minute manual one
  • detail that matters Time availability counts a second at 3 a.m. the same as a second at peak → yield (share of requests served) weights outages by traffic → at 10K RPS the 99.9% budget is 25,920,000 failed requests a month

5 · Predict commit to an answer before revealing

Your read path has 3 parts at 99.95% each, then a database pair where either copy is enough, each at 99.9%. Before computing: does the path meet 99.9%, and which piece dominates the downtime?

Reveal

It misses. The pair gives 1 − 0.001² = 0.999999, so it's nearly free. The three serial parts give 0.9995³ ≈ 0.9985, about 64.8 min a month against a 43.2-minute budget. The serial chain dominates, so another database copy wouldn't help; fewer or better serial parts would.

Budget TinyURL's read path: the course's 99.9% target over a 30-day month. The path has a load balancer, an app server and a cache, each at 99.99%, and a database at 99.95%. (1) Compute the path's availability and monthly downtime. (2) Say how many minutes are left for incidents. (3) At 99.95% with 10-minute repairs, compute how long the database must run between failures.

Done when: You get 0.9999³ × 0.9995 ≈ 0.99920 (about 34.5 min of expected downtime a month, leaving about 8.7 min), and MTTF = 10 × 0.9995 / 0.0005 ≈ 19,990 min ≈ 13.9 days.

Hint

From A = MTTF / (MTTF + MTTR), MTTF = MTTR × A / (1 − A).
