Checkpoint 1: framing a design before drawing boxes

Ties together functional vs non-functional requirements, everything is a trade-off, simple is not easy, robustness and APIs as layers of abstraction: what to decide, and how to decide it, before any architecture exists.

How to use this page. Close the five cards. Answer each question in writing, in full sentences, before opening its Check. A wrong or shaky answer isn't a failure; it tells you exactly which section to reopen. The questions are mixed on purpose, so you have to work out which idea applies before you can answer.

1 · Mixed retrieval

  1. which concept?A link shortener kept one click counter per link. Product now wants "most-clicked links this week". Which idea from this part explains why that's hard, and what should have been stored?
    Check
    • raw data vs summaries: a running total can't be split by time after the fact
    • the fix is one raw row per click, e.g. (code, ts, country); any later report is a query over those rows
    • the source's third feature-check question ("raw data to support it?") catches this; the price is storage (100 click rows per new link at the illustrative scale) and privacy limits on retention

    Missed it? Reopen requirements, "Keep raw data" and "Is the split always clean".

  2. You must remember which of 10⁶ IPv4 addresses you've seen. A Python set or a 2³²-bit bitmap: which is smaller, by how much, and at what count would the answer flip?
    Check
    • set ≈ 64.6 B per address → about 61.6 MiB; bitmap is fixed at 2³² / 8 B = 512 MiB
    • the set is roughly 8× smaller here
    • break-even ≈ 536,870,912 / 64.6 ≈ 8.3 million addresses; above that the bitmap wins

    Missed it? Reopen trade-offs, worked example 1.

  3. which concept?A phone client times out on POST /v1/links, retries, and the user ends up with two identical short links. Which concept fixes this, and what exactly does the server do on the second request?
    Check
    • idempotency: the client sends a key with the request
    • on the retry the server finds the key, returns the stored id and created: False, and inserts nothing
    • it makes a timeout safe to retry, because the client can't tell a lost request from a lost reply

    Missed it? Reopen API layers, the code and the Idempotency row.

  4. On a 5 × 5 board, a player moves at (2, 2). How many counters does the robust winner check update, and how many cells would a full rescan read?
    Check
    • (2, 2) lies on its row, its column, the diagonal (r = c) and the anti-diagonal (r + c = N − 1 = 4): 4 updates
    • a rescan reads (2N + 2) × N = 12 × 5 = 60 cells
    • the counters stay O(1) per move for any N because a move can only complete lines through it

    Missed it? Reopen robustness, the worked example and its hand trace.

  5. which concept?To test Scheduler.next_slot() for one tricky case, a teammate has to call book() 40 times first. Which idea diagnoses the problem, and what's the refactor?
    Check
    • simplicity: hidden state braided into the object makes every output depend on history
    • pull the slot calculation out as a pure function and pass the state in (and a new state out)
    • the test becomes one call with a literal state; the essential state still lives somewhere, but in one visible place

    Missed it? Reopen simple is not easy, "Count what each one couples".

  6. Your v1 API returns url. A new team wants it renamed to target. Can that ship as v1? What can ship as v1 instead?
    Check
    • no: renaming breaks every v1 client that reads url, so it needs /v2
    • additive changes stay in v1: add target as an optional new field next to url; old parsers ignore it
    • the contract is what clients depend on; the layers below can change freely as long as it holds

    Missed it? Reopen API layers, the Versioning row.

  7. A recursive DFS works in tests and crashes in production on a 5,000-node chain. Which trade-off did the author make without pricing it, and what's the other side?
    Check
    • recursion vs iteration: short, clear code in exchange for the call stack
    • CPython stops at depth 1,000 by default, so a 5,000-deep chain raises RecursionError
    • an explicit stack has no depth limit, at the cost of more bookkeeping; the input's shape decides

    Missed it? Reopen trade-offs, the "Recursion vs iteration" row.

3 · Project: the link-creation path, framed end to end

What it reinforces: numbers on the non-functional list (requirements), pricing a choice by its break-even (trade-offs), pure logic with state at the edge (simplicity), a parameter instead of a constant plus loud rejection (robustness), and an idempotent, versioned contract (API layers).

illustrative inputs (the course's): 100M new links a month, 30-day months, 5 years writes/s = 100,000,000 / 2,592,000 s = 38.6 records = 100,000,000 × 12 × 5 = 6,000,000,000 codes = 62^length 5 chars: 916,132,832 6 chars: 56,800,235,584

In about 60 lines of Python:

  1. Requirements. Write the two lists for link creation only (3 lines each). Put a number on every non-functional line.
  2. Price the code length. Make the code length a parameter. Compute how long 5-character codes last at 38.6 writes/s, and how much headroom 6 characters give over 5 years.
  3. Pure core. Write base62(n) and shorten(state, url, length) with no hidden state; one test per case, each a single call.
  4. Reject. shorten raises on a URL without a scheme and on a code that would exceed length; nothing is written in either case.
  5. Contract. Wrap it as v1_create(url, idem_key) over sqlite3 with the key stored, so a retry returns the same id with created: False.
Done when: base62(125) == "21" in one call; a retry with the same key creates no second row; an invalid URL raises before any insert; and your sizing says 5 characters run out in about 275 days while 6 characters cover 5 years about 9.5× over. Then compare with the check.
Check: the numbers (computed with a short Python script)
  • 5 characters: 916,132,832 codes / 38.58 writes/s ≈ 23,746,000 s ≈ 274.8 days. Fine for a demo, not for the 6,000,000,000 records the 5-year requirement implies.
  • 6 characters: 56,800,235,584 / 6,000,000,000 ≈ 9.47× headroom. Changing one parameter, not the design, is what makes this robust.
  • The trade-off: shorter codes are nicer to share; longer ones last. The break-even is the requirement (records over the retention period), not taste.
  • The state that can't go away (the counter and the links) lives in one place: the database row, written once per call at the edge.
