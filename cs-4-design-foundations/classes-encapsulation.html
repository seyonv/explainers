Classes, objects and encapsulation

A class is also called a type or a blueprint; an object is an instance; encapsulation is also called information hiding. The source guide shows all three with one Java class, Point, where new Point(5, 10).relativeTo(-5, 5) prints (0, 15). Here it is in Python.

Prime · 2 minutes before you read

The problem: A bare tuple can't say which field is x, a dict silently accepts a typo'd key, and a mutable object changes under every other name that points at it (b = a; b.x = 0 changes a). Without a class that guards its state, nothing protects the rules of your data.

Where it fits: First card of the OOD part. The framing part talked about where state should live (simplicity) and what callers may depend on (APIs); here the same ideas shrink to one class: what it holds, what callers may touch, and how Python (unlike Java) enforces it.

In one breath

A class says what state (attributes) and actions (methods) its objects have. Each object holds its own copy of that state. Encapsulation means callers use the actions and don't reach into the state, so the class can protect its rules. Java enforces that with private. Python has no private: it relies on a naming convention, and a frozen dataclass when the object shouldn't change at all.

Worked example: Point(5, 10).relative_to(−5, 5) → (0, 15)

In Python

from dataclasses import dataclass

@dataclass(frozen=True)           # writes raise FrozenInstanceError
class Point:
    x: int                        # fields: __init__, __repr__,
    y: int                        # __eq__, __hash__ are generated

    def relative_to(self, dx, dy):
        return Point(self.x + dx, self.y + dy)     # new object

    def __str__(self):
        return f"({self.x}, {self.y})"             # Java toString()

p1 = Point(5, 10)
p2 = p1.relative_to(-5, 5)
print(p2)                         # → (0, 15)
print(repr(p2))                   # → Point(x=0, y=15)
print(p1, p1 is p2)               # → (5, 10) False
print(p2 == Point(0, 15))         # → True (compares fields)

The source's Java uses private int x, y, two getters and a copy constructor Point(Point other). Python needs none of them: fields are read directly, and a frozen object can be shared instead of copied (dataclasses.replace(p1, y=0) gives (5, 0) when you want a changed copy). The source's class diagram also lists setX, setY and distanceTo, which its code doesn't have; this card follows the code.

Why it beats the alternatives

✗ A bare tuple (5, 10)

Is p[0] x or y? There's nowhere to put relative_to, and nothing stops someone passing (5,) as a point.

✗ A dict {"x": 5, "y": 10}

A typo like p["X"] = 0 silently adds a third key. Anyone can change it, and hash fails with "unhashable type: 'dict'", so it can't go in a set.

✗ A mutable class with set_x

Every name for the object sees a change: b = a; b.x = 0 printed MutablePoint(0, 10) for a. Java-style getters add code Python doesn't need.

✓ Frozen dataclass

Two field lines; __init__, __repr__, __eq__ and __hash__ are generated. Writes raise, so sharing it is safe, and it works as a dict key.

Should every class be a frozen dataclass?

No. Freeze small values: points, money amounts, config, dict keys. Objects whose job is to change, like a bank account, a game board or an open connection, stay mutable. There encapsulation means the methods guard the rules: withdraw refuses to go below zero, so outside code shouldn't write balance directly. And for millions of points in a hot loop, one object per point is slow; use a numpy array of shape (n, 2) instead.

Frozen isn't a security boundary either. The docs say truly immutable Python objects can't be made, and object.__setattr__ gets around it, as the table shows. In Python, encapsulation stops accidents, not someone determined to get in.

Understand and remember

  • Callers use methods instead of writing state → the class can protect its rules (withdraw refuses to go below zero) → changing the internals doesn't break callers
  • Python has no private → _x is a convention, __x only renames to avoid subclass clashes, @property blocks writes to one name → encapsulation in Python stops accidents, not someone determined
  • Frozen value object → ordinary writes raise → it can be shared instead of copied and hashed as a dict key → a mutable object shared by two names changes for both (the aliasing bug)
  • Freeze small values (points, money, config); keep objects whose job is to change (accounts, boards, connections) mutable with guarding methods → and for millions of points, one object each is too slow: use an array
  • detail that matters @dataclass generates __init__, __repr__, __eq__ (and __hash__ when frozen) → two field lines replace Java's getters and copy constructor → equality compares fields, not identity (p2 == Point(0, 15) is True, p1 is p2 is False)

5 · Predict commit to an answer before revealing

You make Point frozen, then store a list in it: Path(points=[p1, p2]) with frozen=True. Can outside code still change the path? Commit, then reveal.

Reveal

Yes. Frozen blocks rebinding the field (path.points = [] raises), but the list object itself is still mutable, so path.points.append(p3) works. Hashing it also fails, because a list is unhashable. For a truly immutable value, store a tuple: frozen is shallow.
