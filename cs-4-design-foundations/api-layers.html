APIs as layers of abstraction

Also called abstraction layers, the API contract, or "representing each layer in terms of the next-lower one". The source guide's API Discussions page describes four layers (app objects, general data models, bytes, hardware) and the concerns an API must hide; this card follows one TinyURL link down through all of them.

In one breath

Every layer stores the same thing in a different form: your code holds an object, the database holds a document or row, the storage engine holds bytes in pages, and the hardware holds charge or magnetism. An API is the promise at the top: callers get the same answers in the same shape no matter how the layers underneath change.

def v1_create(url, idem_key):
    """POST /v1/links. A retry with the same key gets the same id."""
    row = db.execute("SELECT id FROM links WHERE idem = ?",
                     (idem_key,)).fetchone()
    if row:
        return {"id": row[0], "created": False}
    cur = db.execute("INSERT INTO links(url, idem) VALUES (?, ?)",
                     (url, idem_key))
    return {"id": cur.lastrowid, "created": True}

def v1_list(after=0, limit=2):
    """GET /v1/links?after=..&limit=.. (keyset, not OFFSET)."""
    rows = db.execute("SELECT id, url FROM links WHERE id > ?"
                      " ORDER BY id LIMIT ?", (after, limit)).fetchall()
    nxt = rows[-1][0] if len(rows) == limit else None
    return {"items": rows, "next": nxt}

What the API has to hide, two examples each

The source lists what a good API owes its callers when the layers below misbehave or grow. A restaurant menu is the everyday version: the dishes stay the same while the kitchen changes cooks, suppliers and stoves.

Why a stable API layer beats the alternatives

✗ Clients read the table

Every client now depends on the schema. Renaming a column, adding a cache or sharding the table breaks all of them at once.

✗ Ship the object (pickle)

Ties callers to Python and to your class layout, and the Python docs warn that unpickling untrusted data can run arbitrary code.

✗ One call per field

get_url(code), get_created(code): showing 50 links costs 100 round trips instead of 1. The source warns that early granularity choices decide how you scale.

✓ A small versioned contract

/v1/links in JSON. The layers below can go from SQLite to a sharded store without a client noticing, as long as the contract holds.

Are more layers always better?

No. Each layer translates, and each translation costs: the same link is 243 B as an object, 75 B as bytes and a 12,288-byte file on disk. Layers also leak. Callers still feel the page size in latency, and the network in timeouts and 429s, even when the API hides how they happen (our reading; the source doesn't discuss leaks).

Inside one program, a function signature is the whole API; wrapping it in HTTP adds a network hop for nothing. Hot paths sometimes skip a layer on purpose, for example a bulk export reading the database's files directly. Add a layer where two teams or two release schedules meet, not by default.
