Checkpoint 2: choosing between is-a, has-a and can-do

Ties together classes, objects and encapsulation, inheritance and polymorphism, interfaces vs abstract classes and object-oriented design practice: where state lives, how behaviour is shared or varied, and which Python tool says so.

How to use this page. Close the four cards. Answer each question in writing, in full sentences, before opening its Check. A wrong or shaky answer isn't a failure; it tells you exactly which section to reopen. The questions are mixed on purpose, so you have to work out which idea applies before you can answer.

1 · Mixed retrieval

  1. which concept?A game stores each unit's position as a mutable Pos object. After b = a.pos; b.x = 0, a different unit jumps across the map, and a dict keyed by position stops finding it. Which idea explains both bugs, and what's the one-line fix?
    Check
    • aliasing: two names share one mutable object, so a change through one is seen through the other
    • a mutable object used as a key can change after it was hashed
    • fix: @dataclass(frozen=True); writes raise, the value can be shared safely and hashed, and "changes" build a new object

    Missed it? Reopen classes, "Why it beats the alternatives" (the mutable class) and the frozen row of the hiding table.

  2. Which class's code runs for Circle((1, 1), 2).bounds(), how does Python find it, and what comes back?
    Check
    • Python walks Circle.__mro__: Circle → Ellipse → Shape → ABC → object
    • Circle doesn't define bounds, so Ellipse's runs, with a = b = 2
    • it returns Rectangle((1, 1), w = 4, h = 4)

    Missed it? Reopen inheritance, the hand trace of paint_shapes.

  3. which concept?Your report tool should accept any third-party object with a render(ctx) method, and the plugins must not import your package. ABC, Protocol, or a concrete base class?
    Check
    • a typing.Protocol: it matches by shape, so a class fits without naming or subclassing it
    • an ABC or a concrete base would force every plugin to inherit from your code
    • remember that @runtime_checkable checks only names; signatures are checked by a static type checker

    Missed it? Reopen interfaces vs abstract classes, the table's Relationship row and "Do you always need both?".

  4. With first-fit, the card's parking lot parks 5 of 6 arrivals; best-fit parks all 6. Which single early decision makes the difference, and what design choice lets you swap policies without editing the lot?
    Check
    • first-fit puts the first compact car (car a) in L1, a large spot, so bus y later finds nothing
    • best-fit gives car a the smallest spot that fits (C1), keeping large spots for buses
    • the policy is a function passed into ParkingLot(choose=…), so no class changes

    Missed it? Reopen OOD practice, worked example 1 and its trace table.

  5. which concept?You add class Square(Rectangle), then someone adds Rectangle.set_w(). Code that doubles a rectangle's width now computes wrong areas for squares. Which principle is violated, and what does the card recommend instead?
    Check
    • Liskov substitution: a subclass must work everywhere the base is expected, for every base operation
    • a Square either breaks w = h or silently changes h too; it's the circle–ellipse problem again
    • keep inheritance for shallow, stable is-a relations with no conflicting mutators; otherwise prefer composition

    Missed it? Reopen inheritance, "Should every is-a become a subclass?".

  6. A subclass of XMLReaderBase forgets from_reader. When does it fail, and when would it fail if the base had used raise NotImplementedError instead?
    Check
    • with @abstractmethod: at construction, a TypeError naming from_reader
    • with NotImplementedError: the object builds fine and fails at the first call, possibly in production
    • the written method (from_string) is inherited either way; only the check's timing changes

    Missed it? Reopen interfaces vs abstract classes, "What happens when you try to build one".

  7. Why can't "swap a[i] with a[randrange(n)]" shuffle 3 cards fairly, while Fisher–Yates can?
    Check
    • the naive loop has 3³ = 27 equally likely paths onto 3! = 6 orders; 27/6 = 4.5 isn't whole, so the counts are uneven (4, 5, 5, 5, 4, 4)
    • Fisher–Yates picks j in 0…i, giving 3 · 2 · 1 = 6 paths, one per order
    • so each order has probability exactly 1/n!

    Missed it? Reopen OOD practice, worked example 2.

  8. What does each of these stop from outside code: self._x, self.__x, @property with no setter?
    Check
    • _x: nothing enforced; it's a convention meaning "internal"
    • __x: renamed to _ClassName__x to avoid clashes with subclasses; still reachable under the new name
    • property without setter: blocks writes to that name; the value behind it (_x) is still writable. Python encapsulation stops accidents, not someone determined

    Missed it? Reopen classes, "Python has no private".

3 · Project: a small file system, using every relation

What it reinforces: a frozen value (classes), an abstract base with one call site for every kind (inheritance), a Protocol that outside classes fit by shape (interfaces), and has-a plus a policy passed in (OOD practice, the file-system prompt).

/ (Directory) ├── a.txt 120 B ├── docs/ (Directory) │ ├── b.md 300 B │ └── c.md 80 B └── img/ (Directory) └── d.png 2,048 B

In about 60 lines of Python:

  1. Value. A frozen Meta(name, owner) dataclass. Show that assigning to meta.name raises.
  2. Is-a. An ABC Entry with an abstract size(). File returns its bytes; Directory sums its children. Show that Entry(...) raises TypeError.
  3. Has-a. A Directory holds a list of Entries and never checks which kind each one is (composite).
  4. Can-do. A Sized Protocol with size(), and a function du(items) typed against it. Pass it a third-party Link class that has size() but doesn't subclass Entry.
  5. Policy. Directory.listing(order=by_name), with by_size as the alternative, and no if/elif inside Directory.
Done when: root.size() prints 2,548; the listing of / by size is img (2,048), docs (380), a.txt (120) and by name is a.txt, docs, img; du accepts your Link without inheritance; and nothing but the policy argument changes between the two listings. Then compare with the check.
Check: what should have happened
  • Sizes: docs = 300 + 80 = 380, img = 2,048, root = 120 + 380 + 2,048 = 2,548.
  • size() on the root is one polymorphic call; Directory's version calls size() on each child, whatever it is: the same shape as paint_shapes.
  • Entry(...) fails at construction, naming size; a Directory that forgot size would fail the same way.
  • The Protocol is what lets Link in: it matches by shape. An ABC would have forced Link to subclass Entry.
  • If you wrote if order == "size" inside listing, you baked the policy in; passing the key function is the fix.
