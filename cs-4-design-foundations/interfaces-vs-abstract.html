Interfaces vs abstract classes

Also called a contract vs a base class; in Python, typing.Protocol vs abc.ABC; in C++, a class of pure virtual functions. The source guide's Interfaces page: a 5-row comparison table, a StatusCallback in C++ and Java, and an XMLReader interface with an abstract XMLReaderImpl. All of it is rewritten in Python here.

In one breath

An interface is a list of methods a class promises to have: a can-do contract that unrelated classes can each sign. An abstract class is a half-built class: some methods are written, some are left blank for subclasses, so it's the shared is-a base of one family. Neither can be instantiated; the difference is whether you're sharing a promise or sharing code.

Worked example: the source's two patterns

Dashed box = interface (a promise, no code). Solid line = inheritance. Green = can be built; red = missing its abstract method, so it can't. Each subclass of XMLReaderBase writes 1 of the 2 contract methods and inherits the other.

from abc import ABC, abstractmethod
from typing import Protocol, runtime_checkable
import io, xml.etree.ElementTree as ET

@runtime_checkable
class StatusCallback(Protocol):       # interface: can-do
    @abstractmethod
    def update_status(self, old: int, new: int) -> None: ...

class ProgressBar(Widget):            # never names StatusCallback
    def update_status(self, old, new):
        if new > old:
            print(f"  {self.name}: {old} -> {new}")

class XMLReaderBase(ABC):             # XMLReaderImpl in the source
    def from_string(self, s):         # written once, for everyone
        return self.from_reader(io.StringIO(s))

    @abstractmethod
    def from_reader(self, f): ...     # the core each subclass writes

class EtreeReader(XMLReaderBase):
    def from_reader(self, f):
        return ET.parse(f).getroot()

notify(ProgressBar("upload"), 3, 7)
isinstance(ProgressBar("p"), StatusCallback)
root = EtreeReader().from_string("<feed><item/><item/></feed>")
# →   upload: 3 -> 7
#     True                      (matched by shape, not ancestry)
#     from_string -> <feed> with 2 children

The source's first block is labelled java but is C++ (virtual … = 0, public:), and its footnote [^11] (public abstract void run();) is never referenced. Both are rewritten above as Python.

Why it beats the alternatives

✗ raise NotImplementedError

A plain base whose blank methods raise. Broken() builds fine and fails later, at the first call, maybe in production. An ABC fails at construction.

✗ Bare duck typing

No declaration at all: just call cb.update_status. It works, but the contract lives only in your head, and a type checker has nothing to check against.

✗ One concrete base for all

Make every callback subclass Callback. A class that already is-a Widget is forced into a hierarchy it doesn't belong to, and inherits state it doesn't need.

✓ Protocol for the promise, ABC for the code

The contract stays open to any class, by shape. The shared code is written once, and a missing method is caught when the object is built. It's the source's XMLReader pattern.

Do you always need both?

No. For a one-method callback like StatusCallback, Python usually just takes a function: on_status: Callable[[int, int], None]. Use an ABC only when there is code to share, like from_string; use a Protocol when outside classes should fit without inheriting. The source's rule of thumb holds: share code among close relatives → abstract class; define a behaviour any class can have → interface.

Protocols are checked mostly by static type checkers such as mypy. At runtime, @runtime_checkable looks at method names only: a class with def update_status(self) and the wrong arguments still passes isinstance (True, printed by code/). And an ABC's check is only "is every abstract method defined?", not "is it correct?".
