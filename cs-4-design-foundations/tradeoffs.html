Everything is a trade-off

Also called the time–space trade-off, or "there is no free lunch". The cheat-sheet's Trade-offs page lists it as commandment 8 of ten ("make trade-offs when you have to") and runs from hash tables to hiring. This card puts numbers on four of its examples.

In one breath

Almost every choice buys one thing (speed, memory, simplicity, hiring quality) by paying with another, so the question is never "which is best?" but "best for which n, which workload, and at what price?". Put numbers on both sides and the answer usually falls out, often as a break-even point.

Worked example 1: storing a set of IPv4 addresses

Three ways to answer "have we seen this address?". A bitmap spends one bit on every possible address (2³² of them), whether or not you store it.

Worked example 2: dynamic programming buys time with memory

Rod cutting (the source's footnote): a rod of length j sells for pj; cut it to earn the most. Plain recursion tries every first piece and re-solves the rest each time, which is 2n calls. Keep a table r[0..n] of solved lengths instead: n + 1 cells of memory buy O(n²) time.

r[j] = max over 1 ≤ i ≤ j of ( p[i] + r[j − i] ), r[0] = 0 n = 10: plain recursion 2¹⁰ = 1,024 calls · table: 1 + 2 + … + 10 = 55 steps, 11 cells

Worked example 3: interview less or hire better (the 37% rule)

The source's hiring puzzle is the secretary problem: n candidates in random order, you must say yes or no on the spot, and you only see how each ranks against those before. Skip the first k, then hire the first one better than all of them.

Exact sums, checked by simulation: 10⁵ shuffles of n = 100 with k = 37 hire the best 0.3706 of the time (seed 0). The price: with probability k/n = 37% the best was among those you skipped, and you end up with the last candidate.

In Python

class Bitmap:
    def __init__(self, nbits):
        self.bits = bytearray((nbits + 7) // 8)
    def add(self, x):
        self.bits[x >> 3] |= 1 << (x & 7)
    def __contains__(self, x):
        return self.bits[x >> 3] >> (x & 7) & 1 == 1

def rod_cut(p, n):
    r = [0] * (n + 1)            # r[j] = best revenue for length j
    first = [0] * (n + 1)        # first piece in that best plan
    for j in range(1, n + 1):
        for i in range(1, j + 1):          # first piece has length i
            if p[i - 1] + r[j - i] > r[j]:
                r[j], first[j] = p[i - 1] + r[j - i], i
    return r, first

def p_best(n, k):             # skip k, then take the first better
    if k == 0:
        return 1 / n
    return k / n * sum(1 / (i - 1) for i in range(k + 1, n + 1))

bm = Bitmap(2**32)               # really allocates 512 MiB
bm.add(192 << 24 | 168 << 16 | 1 << 8 | 1)   # 192.168.1.1
# len(bm.bits) = 536,870,912
# 192.168.1.1 in bm: True | 7 in bm: False
rod_cut([1, 5, 8, 9, 10, 17, 17, 20, 24, 30], 10)
# r = [0, 1, 5, 8, 10, 13, 17, 18, 22, 25, 30]
# first = [0, 1, 2, 3, 2, 2, 6, 1, 2, 3, 10]
max(range(100), key=lambda k: p_best(100, k))   # → 37
p_best(100, 37)                                    # → 0.3710…

Time O(n²) · Space O(n) for rod_cut: j runs to n and tries j first pieces, 55 steps for n = 10, against 2n calls without the table. The bitmap is O(1) per operation and O(U) space for a universe of U keys, however few you store.

Why it beats the alternatives

✗ Always pick the fastest

The bitmap is O(1) for everything, and it costs 512 MiB to hold 1,000 addresses that fit in 4 kB as a sorted array.

✗ Always pick the smallest

The packed array is 16× smaller than the set, but inserting keeps it sorted by shifting up to n items, and above 134 million addresses the bitmap is smaller anyway.

✗ Go by the worst case alone

Insertion sort's O(n²) worst case looks worse than quicksort's average, yet on nearly sorted input it made 2,009 comparisons to quicksort's 1,987,616.

✓ Price both sides for your n

Ask how many items, how often each operation runs and what limit binds. The answer is usually a break-even point: 8.3 M and 134 M addresses here, k = n/e for hiring.

Is there always a trade-off?

Not always. Sometimes one option wins on both axes, like the source's bitmap that fits in RAM and so beats a bigger structure that spills to disk; then there is nothing to weigh. And at small n the costs are too small to matter: with 1,000 addresses any of the three is fine, so choose the simplest and move on (the simplicity card).

The numbers are only as good as their assumptions. The 37% rule assumes no second chances, random order, only relative ranks, and that only the single best counts; if you can call a candidate back, or would settle for a good hire, it is the wrong rule. The source's system-level trade-offs (a monolith vs many processes, cleverness vs maintainability) rarely reduce to one number; there, writing down the assumptions is the work, since two good engineers can reach different designs from different starting points.
