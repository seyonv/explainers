Checkpoint 3: will it fit, and which lever fixes it?

Ties together back-of-the-envelope estimation, averages and expected value, availability and SLO arithmetic, an algorithm beats a faster computer, what compilers do for you and why Python loops are slow: sizing a design with a few numbers, and choosing the fix that actually scales.

How to use this page. Close the six cards. Answer each question in writing, in full sentences, before opening its Check. A wrong or shaky answer isn't a failure; it tells you exactly which section to reopen. The questions are mixed on purpose, so you have to work out which idea applies before you can answer.

1 · Mixed retrieval

  1. which concept?A team plans to buy servers 4× faster for a nightly job whose run time grows as n², because next year's data will be 10× bigger. Will the job finish sooner or later next year, and by how much? Which card's model answers it?
    Check
    • T = c·f(n)/s: 10× the data is 10² = 100× the steps; 4× the speed divides by 4
    • net: 100 / 4 = 25× slower than today
    • hardware changes s, a constant; only an algorithm with a lower f(n) keeps up as n grows

    Missed it? Reopen algorithm vs hardware, "The three knobs".

  2. 2 million linked-list nodes, each an int and a pointer, in CPython with __slots__. Do they fit in 128 MB? Show the per-node parts.
    Check
    • object with two slots 48 B + the int object 28 B + the list's pointer 8 B = 84 B
    • 2,000,000 × 84 B = 168 MB: over budget (the packed C layout is 16 MB)
    • sys.getsizeof counts only the object's own bytes; the parts it points to are added by hand

    Missed it? Reopen back of the envelope, "The same 2M-node question, asked of Python".

  3. which concept?A Python ETL step does two things: it adds a constant to 10⁷ floats in a for loop, and it builds a report with s = s + line + "\n". Each is slow. Which fix goes with which, and why are they different kinds of fix?
    Check
    • the add loop is already O(n); its cost is per-item interpreter bookkeeping → vectorize with NumPy (58.2 → 0.286 ns per item on the M3)
    • the string loop is O(n²) because each pass copies the whole string → change the algorithm: "".join (0.468 s → 0.0073 s at 10⁵ pieces)
    • one cuts the constant c, the other changes f(n); CPython itself only folds constants

    Missed it? Reopen Python loops, the trace, and compilers, the worked example.

  4. A request passes through 5 parts, each at 99.99%. What is the path's availability and its downtime in a 30-day month? Does it still meet 99.9%, and what about 20 parts?
    Check
    • 0.9999⁵ ≈ 0.99950 → (1 − 0.99950) × 43,200 ≈ 21.6 min a month: meets 99.9% (43.2 min)
    • 20 parts: 0.9999²⁰ ≈ 0.998 → 86.3 min: misses
    • serial parts multiply, so parts need more nines than the whole

    Missed it? Reopen SLO arithmetic, worked example 2.

  5. which concept?Dashboards show the mean latency is fine, yet users complain that about 1 request in 20 hangs for a second. Which number should the dashboard show, and which card's warning is this?
    Check
    • latency is skewed: the mean is pulled by the slow requests and describes nobody
    • show the median for the typical request and a tail percentile (p95, p99) for what users feel
    • the mean is still right for totals, such as Little's law and capacity

    Missed it? Reopen averages, "The words" (median, p50 vs p99), and back of the envelope, "Is an estimate ever enough".

  6. A worker pool has 50 threads, and each job holds a thread for 0.2 s on average. What is the highest steady arrival rate it can sustain, and which law gives it?
    Check
    • Little's law, L = λ × W, solved for λ: 50 / 0.2 s = 250 jobs/s
    • that is the average ceiling at 100% busy; derate it, because a fully busy pool queues without limit
    • if W rises (a slow dependency), the ceiling falls in proportion

    Missed it? Reopen back of the envelope, Little's law and derating.

  7. 50 people at 1% prevalence: pools of 50 or pools of 10? Give the expected number of tests for each.
    Check
    • pools of 50: 1 × 0.605 + 51 × 0.395 ≈ 20.75 tests
    • pools of 10: 5 pools × (1 × 0.904 + 11 × 0.096) ≈ 9.78 tests
    • use pools of 10; the expected value is the right guide because the clinic repeats the choice many times

    Missed it? Reopen averages and EV, the pooled-testing table and the pool-size sweep.

  8. Why can't CPython 3.10 turn x * 8 into a shift or reuse (x + y) in (x + y) * (x + y), when clang does both?
    Check
    • x could be a float, a list or any object; a shift is only correct for machine ints
    • __add__ might have side effects, so computing it once could change the program's meaning
    • clang knows the C types at compile time; CPython can't prove them, so it only folds all-constant expressions

    Missed it? Reopen compilers, "Six optimizations, two examples each".

3 · Project: size and speed up a latency report

What it reinforces: memory per item and Little's law (back of the envelope), which average to report (averages), an SLO counted in requests (SLO arithmetic), and choosing between an algorithm fix, a compiler-proof string build and vectorization (algorithm vs hardware, compilers, Python loops).

illustrative log: 1,000,000 requests at 500 requests/s 980,000 took 20 ms, 20,000 took 1,000 ms target: 99.9% of requests under 500 ms
  1. Estimate first. Before loading anything, write the memory for the latencies as a Python list of floats and as a float64 NumPy array.
  2. Averages. Compute the mean, the median and the p99. Say which one goes on the dashboard and which one goes into Little's law.
  3. Little's law. At 500 requests/s, how many requests are in flight on average?
  4. SLO. What fraction of requests met the target, and how many failures does 99.9% allow in this log? Does it pass?
  5. Speed. Compute the p99 twice, with sorted() on the list and with np.percentile on the array, and time both once. Build a 1,000-line text report with join, not s = s + ….
Done when: your estimate says about 32 MB as a list (8 B pointer + 24 B float each) vs 8 MB as an array; you get mean 39.6 ms, median 20 ms, p99 1,000 ms; about 19.8 requests in flight; 98% under 500 ms, so 20,000 failures against 1,000 allowed: it fails the SLO by 20×; and you can say which of your two p99 timings was faster and why. Then compare with the check.
Check: the numbers (computed with a short Python script)
  • Memory: 10⁶ × (8 + 24) B = 32 MB vs 10⁶ × 8 B = 8 MB. The difference is boxing, the same reason the loop card's ints cost 36 B.
  • Mean = (980,000 × 20 + 20,000 × 1,000) / 10⁶ = 39.6 ms. Median = 20 ms. p99: the 990,000th sorted value is 1,000 ms, because 2% of requests are slow.
  • Little's law uses the mean: 500/s × 0.0396 s ≈ 19.8 in flight. The dashboard shows the median and p99: the mean is nearly twice what a typical request sees, and far below what the slowest 2% see.
  • Yield = 980,000 / 10⁶ = 98%. At 99.9% the log may contain 10⁶ × 0.001 = 1,000 failures; it has 20,000.
  • Both p99 methods sort or select in C, so neither is a Python loop per item; NumPy's advantage comes from unboxed data. Either way it's O(n log n) or better, so the algorithm isn't the problem here.
