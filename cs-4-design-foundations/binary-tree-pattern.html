The binary tree as a design pattern

Also called recursive decomposition or binary partitioning. Ask one yes/no question, and the answer picks which half to deal with next. The source guide's System Design notes show it four ways: a DNS hierarchy, a search-tree index, a credit decision tree and a Huffman code, and they call balance the design risk all four share.

In one breath

If a problem splits into two smaller problems of the same kind, you can model it as a tree: each internal node is a decision and each leaf is a final outcome. The cost of an answer is the length of the path to its leaf. So the design work is choosing which leaves sit near the root and keeping every path short.

In Python

import heapq
from collections import Counter

def huffman_tree(freq, log=None):
    heap = [(f, i, s) for i, (s, f) in enumerate(freq.items())]
    heapq.heapify(heap)
    tick = len(heap)                 # tie-breaker: never compare
    while len(heap) > 1:             # two subtrees directly
        f1, _, a = heapq.heappop(heap)   # lightest
        f2, _, b = heapq.heappop(heap)   # next lightest
        if log is not None:              # for the hand trace
            log.append((f1, a, f2, b))
        heapq.heappush(heap, (f1 + f2, tick, (a, b)))
        tick += 1
    return heap[0][2]                # leaf = symbol, node = (l, r)

def code_lengths(tree):             # iterative: no recursion limit
    out, stack = {}, [(tree, 0)]
    while stack:
        node, d = stack.pop()
        if isinstance(node, tuple):
            stack += [(node[0], d + 1), (node[1], d + 1)]
        else:
            out[node] = d
    return out

def canonical(lengths):           # codes from lengths, as DEFLATE
    code, prev, out = 0, 0, {}
    for s in sorted(lengths, key=lambda s: (lengths[s], s)):
        code <<= lengths[s] - prev       # step down a level
        out[s] = format(code, f"0{lengths[s]}b")
        prev, code = lengths[s], code + 1
    return out

freq = Counter("ABACABADA")
print(canonical(code_lengths(huffman_tree(freq))))
# → {'A': '0', 'B': '10', 'C': '110', 'D': '111'}

Time O(k log k) · Space O(k) for k distinct symbols: k − 1 merges, each two pops and a push on a heap of at most k items. Encoding the message is then one table lookup per symbol.

The applicants are illustrative inputs to the source's credit tree (score > 650, income > $50k, debt < 40% of income). DNS is really a many-way tree (the root has com, org, gov…), so it's "binary" only in the source's broad sense of one choice per level.

The shared risk: balance

levels to reach any of n = 10⁶ keys naive BST, keys inserted sorted: 1,000,000 (each node has one child: a list) perfectly balanced: ⌈log₂(10⁶ + 1)⌉ = ⌈19.93⌉ = 20 red-black tree guarantee: ≤ 2·log₂(10⁶ + 1) = 39.9, so ≤ 39 B-tree, fanout 100 (illustrative): ⌈log₁₀₀ 10⁶⌉ = 3 block reads

For n = 1,000 the script builds real trees: sorted inserts give height 1,000, one random order (seed 1) gives 20, and perfect balance is 10. Self-balancing trees (AVL, red-black) turn the "usually fine" random case into a guarantee. On disk, B-trees trade depth for fanout because each level is a block read.

Deep trees also break naive recursion: Python's default limit is 1,000 frames, so a recursive depth count on a 5,000-node chain raises RecursionError: maximum recursion depth exceeded, while a plain while loop down the same chain returns 5000. That's the source's "favor iterative solutions" advice, run.

Why a balanced tree beats the alternatives (as an index)

✗ Unsorted list

Append is O(1), but every lookup is a linear scan: up to 10⁶ comparisons for 10⁶ keys, and range queries scan everything too.

✗ Sorted array + bisect

Lookups take 20 comparisons, but each insert shifts every later element: up to 10⁶ moves. Fine only if data rarely changes.

✗ Hash table

O(1) average lookup, but no order: "all keys between 100 and 200" or "the next key after x" means scanning every entry.

✓ Balanced search tree

Lookup, insert and delete in O(log n), about 20 levels for 10⁶ keys, and an in-order walk gives ranges in sorted order.

Is a binary tree always the right shape?

No. Data bigger than RAM wants a B-tree: many keys per node, so 3 levels instead of 20. One shared tree is also a single point of contention; the source lists coarse locks (simple, slow), fine-grained locks (fast, deadlock-prone) and lock-free trees (fastest, expert-only), and advises using an existing concurrent library. In Python there's no balanced tree in the standard library, so the usual choice is a dict for point lookups and bisect on a sorted list for ranges.

Huffman is two passes (count, then encode), so pure streaming needs an adaptive variant, and for 9 symbols the frequency table costs more than the 3 bits saved (our estimate). On serialization: the source says a preorder walk rebuilds the tree exactly. That holds only if you also write a marker for each empty child (or the tree is a BST, whose order fills in the gaps); a plain preorder list can come from more than one tree shape.
