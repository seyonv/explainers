Why Python loops are slow

Also called the interpreter overhead problem; the fix is usually vectorization (array programming, NumPy-style). The source guide's "for Loop Problems" adds 17 to every item of 108 integers, once with a CPython loop and once with NumPy, then covers the limits and the alternatives: PyPy, Numba and compiled extensions.

Prime · 2 minutes before you read

The problem: An O(n) Python loop over numbers can still be hundreds of times slower than it needs to be: adding 17 to 10⁷ ints took 0.582 s as a loop and 0.00286 s with NumPy on the M3. The algorithm is fine; the cost is per-item bookkeeping.

In one breath

A Python list holds pointers to full Python objects, so a loop spends almost all its time on bookkeeping for each item: dispatching bytecodes, checking types and allocating a new integer object. The actual add is a tiny part of it. A NumPy array holds raw machine integers, so a += 17 is one C loop that does the add and little else.

Grey = bookkeeping, green = the useful add. ⟨…⟩ is a pointer to a heap int object. Steps 1–5 are the source's list, mapped onto CPython 3.10's long_add (our reading of Objects/longobject.c). NumPy's inner loop per item is load 8 bytes, add, store 8 bytes; with SIMD a single instruction adds several items.

The code, and the catch

import numpy as np

def add_loop(l):
    for i in range(len(l)):
        l[i] += 17              # 11 bytecodes per item

def add_numpy(a):
    a += 17                     # one C loop over raw int64s

def mean_abs(a):
    return np.abs(a).mean()     # np.abs makes a full temp array

def mean_abs_chunked(a, chunk=100_000):
    total = 0.0
    for s in range(0, len(a), chunk):
        total += np.abs(a[s:s + chunk]).sum()
    return total / len(a)

# on 10**7 float64s (80 MB), tracemalloc peak:
# mean_abs         peak  80,001,950 B
# mean_abs_chunked peak     801,020 B
# same answer: True

Output of code/for-loop-vectorization.py under python3 3.10. The source's point: vectorizing mean(|x|) hides a second array as big as the input, 107 × 8 B = 80 MB here. Chunks of 105 cap it at 800 KB, which is the batching numexpr and Dask do for you.

The source says NumPy is "implemented in Rust"; it's C (numpy.org: "the core of NumPy is well-optimized C code", and the source's own last section says "mostly written in C"). It also calls PyPy an implementation of CPython; it's an alternative implementation of Python. Corrected here.

Time O(n) both ways · Space O(1) extra for a += 17, O(n) for np.abs(a).mean(). Vectorizing doesn't change the complexity. It cuts the constant, from 58.2 ns to 0.286 ns per item on the M3.

"Vectorization" means three things

MeaningWhat it isExample AExample B
An API over bulk dataOne call names the whole array; no Python-level loop in your code. arr += 1NumPy: every item df["x"] * 2pandas builds on NumPy
A fast compiled loopThe loop behind that call runs in C over raw machine values. The source's main focus. 0.286 ns / itema += 17 on the M3 58.2 ns / itemthe same add as a CPython loop
SIMD instructionsOne CPU instruction operates on a whole register of values at once. 512 / 64 = 8 int64sper AVX-512 register (16 if 32-bit, the source's "16 operands") 128 / 64 = 2 int64sper Arm Neon register, as on the M3

Why it beats the alternatives

✗ A plain CPython loop

Easy to write, but 11 bytecodes and a fresh int object per item: 0.582 s for 107 on the M3, 203× slower than NumPy.

✗ PyPy

Its JIT turns the same loop into machine code: 25.9 s → 0.484 s in the source. But it doesn't interface with NumPy well: a loop over a NumPy array is slower than in CPython.

✗ Write a C, Cython or Rust extension

Most flexible, but it adds a compile step to your build, and users need a compiler installed.

✓ Vectorize with NumPy

No build step, and your code still reads as one line. The loop runs in C over packed 8-byte values: 0.286 ns per item.

Is vectorizing always the answer?

No, and the source ends on exactly that. It fits when you do the same operation to many items of the same type. It fails in three ways: memory, since each step allocates a temporary (80 MB above); missing operations, when your per-item logic has branches or each item depends on the one before (a running recurrence like x[i] = f(x[i-1]) has no array form); and tiny inputs, where each NumPy call's fixed setup cost can outweigh a short loop (our inference; not measured here).

For those cases the source suggests Numba: @numba.njit compiles your own loop, works with NumPy arrays and needs no temporaries (4.85 s → 0.0642 s in the source, after the first compile). And before any of this, check the algorithm: a better one can win by far more than 203×.

Keep it if it changes what you can explain, predict, compare, choose, build or debug. Otherwise it's reference.

Understand and remember

  • A list holds pointers to full int objects → each l[i] += 17 dispatches ~11 bytecodes, checks types, calls a C function and allocates a new 28-byte int → the add itself is a tiny fraction of 58.2 ns per item
  • A NumPy array holds raw 8-byte ints → a += 17 is one C loop of load, add, store (plus SIMD) → 0.286 ns per item, 203× faster, with the same O(n)
  • Each vectorized step materialises a full-size temporary → np.abs(a).mean() allocates another 80 MB at 10⁷ items → chunking (10⁵ at a time) caps the peak at ~800 KB
  • Vectorization needs the same operation on many items of one type → branches or recurrences like x[i] = f(x[i-1]) have no array form → compile the loop instead (Numba, PyPy for pure Python), and check the algorithm first
  • detail that matters The same data costs 36 B per item as a list of ints (8 B pointer + 28 B object) vs 8 B in an int64 array → 360 MB vs 80 MB at 10⁷ → memory traffic, not only instructions, is part of the 203×

5 · Predict commit to an answer before revealing

Your data starts as a Python list of 10⁷ ints. You write np.array(l) + 17 once and convert back with .tolist(). Before trying: do you get anything like the 203× speed-up over the plain loop? Commit, then reveal.

Reveal

No, not for a single operation. np.array(l) has to visit all 10⁷ Python int objects to unbox them, and .tolist() allocates 10⁷ new ones: the same kind of per-item work the loop did. The 203× applies to work done while data stays in the array. Convert once, do many operations, convert back once (or never).
