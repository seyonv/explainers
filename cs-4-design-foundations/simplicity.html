Simple is not easy

Also called simple vs easy, or essential vs accidental complexity. The source guide's Simplicity page draws on Rich Hickey's "Simple Made Easy" talk (our attribution; the page quotes his definitions without naming him) and Moseley and Marks' "Out of the Tar Pit". It ends with a What/Who/How/When/Why checklist and a table of simple constructs.

In one breath

Simple means one twist: a piece does one job and isn't braided into others. You can check that by looking at the code. Easy means near or familiar, so it depends on who's asking. The habit you already know, often a class that holds state, is easy, and it often braids several jobs together. The way out is to pull the pure logic away from the state.

Worked example: one TinyURL feature, written two ways

The feature: give each new long URL the next id and turn that id into a short base-62 code. It's the course's running example.

✗ A · easy: a stateful class

class Shortener:
    def __init__(self):
        self.next_id = 0
        self.links = {}
        self.log = []

    def shorten(self, url):
        self.next_id += 1              # id allocation
        n, code = self.next_id, ""
        while n:                       # encoding, inline
            n, r = divmod(n, 62)
            code = ALPHABET[r] + code
        self.links[code] = url         # storage
        self.log.append(code)          # auditing
        return code

✓ B · simple: a pure function, with the state passed in and out

def base62(n):                      # logic only: no state at all
    code = ""
    while n:
        n, r = divmod(n, 62)
        code = ALPHABET[r] + code
    return code or "0"

def shorten(state, url):             # state is an argument
    n = state["next_id"] + 1
    code = base62(n)
    links = {**state["links"], code: url}
    return {"next_id": n, "links": links}, code

B leaves the audit log out of shorten. A caller can put each code on a queue for the log, following the checklist's When/Where rule below. ALPHABET is 0–9, a–z, A–Z.

Why disentangling beats the alternatives

✗ Do the easy thing

Write the familiar class. It ships fastest, but shorten reads and writes all three fields, so testing one code means replaying 125 calls.

✗ Put a façade on it

The source says a façade puts a pretty face on the mess and sweeps it under the rug. That helps callers, but the braid is still inside.

✗ Lean on tests and refactoring

The source calls these a safety net: good but secondary. They catch breakage and don't make anything simpler. A's tests stay tied to its history.

✓ Separate logic from state

Pure base62, with the essential state passed in explicitly. Each piece has one job, tests need one call, and the pieces can be swapped (Moseley and Marks; Kowalski's "Algorithm = Logic + Control").

Is the stateless version always better?

No. Essential state doesn't go away: TinyURL has to remember its links somewhere. B only moves that state to one visible place. Purity also costs something in plain Python: {**links, code: url} copies the whole dict on every call, so 105 shortens copy 105·(105−1)/2 = 4,999,950,000 entries. That's O(n) per call, where A's in-place insert is O(1). In practice, keep base62 pure and do the single mutation at the edge (a dict or a database row), or use a persistent map library.

The source also warns against over-abstracting: wrapping data in classes the problem doesn't need adds complexity, because how you group the data is subjective. A three-line script doesn't need this split. The split pays off when code is shared, tested or changed often.
