Inheritance and polymorphism

Also called subclassing ("is-a"), method overriding, and dynamic dispatch or subtype polymorphism. The source guide builds an abstract Shape with Rectangle and Ellipse under it and one paintShapes loop that draws them all; here it is in Python, with the Circle the source mentions added.

Prime · 2 minutes before you read

The problem: Code that handles many kinds of thing with an isinstance chain must be edited in every function each time a new kind appears, and a forgotten branch fails silently. Copying shared parts into each class drifts apart the first time one copy is fixed.

Where it fits: Second OOD card. The classes card gave you one class with guarded state; this one relates classes: a subclass reuses a base and overrides what differs, and one call site dispatches to the right method at run time. The interfaces card next compares this with a pure contract.

In one breath

Inheritance lets a class start as a copy of another and change only what differs: a Circle is an Ellipse with a = b. Polymorphism is the payoff: code written against the base class, like "for each shape, draw it", calls the right draw for whatever object it holds, chosen at run time from the object's own class.

The hierarchy

Worked example: Ellipse(center (0, 0), a = 3, b = 2).bounds()

Ellipse.bounds() = Rectangle(center, 2 * a, 2 * b) = Rectangle((0, 0), w = 2 * 3 = 6, h = 2 * 2 = 4) area: ellipse π·a·b = π·3·2 = 18.85 box w·h = 6·4 = 24 → 18.85 / 24 = 0.785 = π/4

The caller gets back a Rectangle, whatever shape it asked. A Rectangle's bounds is itself; an Ellipse's is the box it fits in, which it fills to π/4 ≈ 78.5% (computed).

Hand trace: paint_shapes over three shapes

In Python

from abc import ABC, abstractmethod

class Shape(ABC):
    def __init__(self, center):
        self.center = center          # shared by every subclass
    @abstractmethod
    def bounds(self): ...             # every subclass must supply
    @abstractmethod
    def draw(self, canvas): ...

class Rectangle(Shape):
    def __init__(self, center, w, h):
        super().__init__(center)
        self.w, self.h = w, h
    def bounds(self):
        return self                   # a rectangle is its own box
    def draw(self, canvas):
        canvas.append(f"rect {self.w}x{self.h} at {self.center}")

class Ellipse(Shape):
    def __init__(self, center, a, b):
        super().__init__(center)
        self.a, self.b = a, b         # semi-axes
    def bounds(self):
        return Rectangle(self.center, 2 * self.a, 2 * self.b)
    def draw(self, canvas):
        canvas.append(f"ellipse a={self.a} b={self.b} at {self.center}")

class Circle(Ellipse):
    def __init__(self, center, r):
        super().__init__(center, r, r)    # an ellipse with a = b
    def draw(self, canvas):               # override; bounds inherited
        canvas.append(f"circle r={self.a} at {self.center}")

def paint_shapes(canvas, shapes):
    for s in shapes:
        s.draw(canvas)    # which draw? looked up on type(s) at run time

# Ellipse((0, 0), 3, 2).bounds() -> Rectangle((0, 0), w=6, h=4)
# Circle.__mro__: Circle -> Ellipse -> Shape -> ABC -> object
# Shape((0, 0)) -> TypeError: Can't instantiate abstract class
#     Shape with abstract methods bounds, draw
# Triangle((0, 0)) -> TypeError: Can't instantiate abstract class
#     Triangle with abstract method draw

Why it beats the alternatives

✗ One function with an isinstance chain

if isinstance(s, Rectangle): … elif …. Every new shape means editing every such function (draw, bounds, and the rest), and a forgotten branch fails silently or at run time.

✗ Copy the shared parts into each class

No base class: each shape keeps its own center and getter. It works until one copy is fixed and the others aren't, and isinstance(s, Shape) can't be asked.

✗ Duck typing, no base at all

Python will happily call s.draw on anything that has one. But a Triangle missing draw fails only when the painter reaches it, with an AttributeError far from the bug.

✓ Abstract base + overrides

paint_shapes never changes: a new shape is one new class. Shared code lives once in Shape, and a missing method fails at construction with a TypeError naming it.

Should every "is-a" become a subclass?

No. The source's own Circle is the classic trap: if Ellipse had set_a(), a Circle would either stop being a circle or refuse a call every Ellipse accepts, and code written for Ellipses breaks (the circle–ellipse problem, a Liskov substitution violation). Here it's safe only because nothing mutates a or b. Deep trees also couple every subclass to its parent's internals, so a change to Shape can break all of them.

The usual advice is composition over inheritance: give an object a part rather than a parent, such as a Shape that has a Style instead of RedShape, DashedShape and RedDashedShape subclasses. Keep inheritance for a shallow, stable "is-a" with one shared interface, as here. In Python, a typing.Protocol gives polymorphism with no shared parent, and functools.singledispatch picks a function by argument type when you'd rather add operations than classes. This guidance is standard practice, not from the source.

Understand and remember

  • Code written against the base class → Python looks up the method on type(s) along its MRO at run time → each object runs its own class's version → a new shape is one new class and paint_shapes never changes
  • A subclass inherits everything and overrides only what differs → shared code lives once in the base → a fix in Shape reaches every subclass (Circle reuses Ellipse's bounds with a = b)
  • Mark required methods @abstractmethod on an ABC → a class that leaves one unfilled can't be built → the bug surfaces at construction with a TypeError naming the method, not later as an AttributeError far away
  • Is-a must hold for every operation of the base (Liskov) → a mutating base method like set_a breaks Circle → keep inheritance shallow and stable; prefer composition (has-a) when variants multiply
  • detail that matters The MRO is one linear order per class (C3), even with several bases → lookups are deterministic and each class appears once → this is what makes Python's multiple inheritance (the next card's "implements many") work

5 · Predict commit to an answer before revealing

Add class Square(Rectangle) and then give Rectangle a set_w(w) method. Before running: what goes wrong for code that takes any Rectangle, and is this the same trap as Circle and Ellipse?

Reveal

Yes, the same trap. Code written for Rectangles expects set_w to change only the width. A Square either breaks its own rule (w ≠ h) or silently changes h too, so the caller's area calculation is wrong. Either way a Square can't stand in for every Rectangle once rectangles are mutable: a Liskov violation. It's safe only while nothing mutates the sides.
