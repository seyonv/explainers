An algorithm beats a faster computer

Also called "asymptotics beat constants" or "algorithms as a technology". The source guide's Algorithm vs. Hardware diagram (CLRS §1.2's example): sort 10 million numbers on a 1000× faster computer running insertion sort, or on a slow one running merge sort.

In one breath

Run time is steps divided by speed. A faster computer divides every run by the same fixed number, but a better algorithm changes how the step count grows with n. Once n is big enough, growth wins, however large the speed gap.

The three knobs, A and B side by side

Think of two couriers: one drives a sports car (speed) but visits every house once per parcel (growth); the other rides a bike but plans one route for all parcels.

A ÷ B = 2n²·10⁷ / (50 n lg n·10¹⁰) = n / (25,000 lg n): it grows almost linearly in n. The crossover solves n = 25,000 lg n by binary search. Below it, the fast machine's 1000× head start still wins.

Proebsting's law: why "wait for faster hardware" rarely rescues a bad algorithm

hardware +60%/yr: 2× in ln 2 / ln 1.60 = 1.5 yr 1000× in ln 1000 / ln 1.60 = 14.7 yr compiler +4%/yr: 2× in ln 2 / ln 1.04 = 17.7 yr 1000× in ln 1000 / ln 1.04 = 176.1 yr

Computer A's 1000× lead is about 15 years of hardware progress, or 176 years of compiler progress, and one algorithm change beats it at n = 10⁷. The 17.7-year doubling matches the law's own headline, "compiler advances double computing power every 18 years".

In Python

import math
A_SPEED, B_SPEED = 10**10, 10**7   # instructions per second

def time_a(n):                    # insertion sort on A
    return 2 * n * n / A_SPEED

def time_b(n):                    # merge sort on B
    return 50 * n * math.log2(n) / B_SPEED

def crossover():
    """Smallest n >= 2 where slow B with merge sort beats fast A."""
    lo, hi = 2, 10**7              # A wins at 2, B wins at 1e7
    while lo < hi:
        mid = (lo + hi) // 2
        if time_b(mid) < time_a(mid):
            hi = mid
        else:
            lo = mid + 1
    return lo

print(time_a(10**7), round(time_b(10**7), 1), crossover())
# → 20000.0 1162.7 471146

The source writes "n log n" with the base unstated. The 1,163 s needs log₂; with the natural log, B would take 806 s.

Insertion sort: time O(n²) · space O(1). Merge sort: time O(n log n) · space O(n). Insertion sort shifts each new item past about half the sorted prefix, so it does about n²/4 comparisons. Merge sort halves lg n times and does at most n comparisons per level.

Why it beats the alternatives

✗ Buy faster hardware

Divides T by a constant. A's 1000× (about 15 years of +60%/yr) still loses 17.2× at n = 10⁷, and 1,338× at n = 10⁹.

✗ Wait for a better compiler

Proebsting: about 4%/yr, so a 2× gain takes about 18 years. Compilers shrink c; they don't turn n² into n log n.

✗ Micro-tune the loop

A's c = 2 is already the best on the card, 25× leaner than B's 50, and A still loses. Tuning buys a constant factor, like hardware does.

✓ Change the algorithm

Changes f(n), so the gain grows with n: A ÷ B = n / (25,000 lg n). "Code tuning may solve a problem, but a better algorithm can redefine it."

Is the better big-O always better?

Not below the crossover. For n under 471,146 in this example, the fast machine with the worse algorithm wins, by 250× at n = 1,000. The same holds on one machine: insertion sort has a tiny c, so it beats merge sort on small inputs. That's why CPython's Timsort sorts short runs (up to 64 items) with binary insertion sort, then merges the runs.

Constants and hardware matter once the algorithm is already optimal. Sorting by comparisons can't beat Θ(n log n), so from there the wins come from c and s: cache-friendly layout, C instead of Python loops (numpy's np.sort: 0.031 s vs sorted() 0.130 s for 10⁶ floats on the M3), and parallel hardware. The source's claim that the advantage "grows even more" is true only above the crossover; the card's growth table shows both sides.
