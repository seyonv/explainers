The inference stack in one picture

Also called the serving stack, or "from API request to tensor core". This card is the map for the series: each layer below is covered by one course, perf-1 to perf-7. Kiely's Inference Engineering ch. 0 splits the same picture into runtime and infrastructure.

Prime · 2 minutes before you read

The problem: "Make inference faster" is not actionable until you know where a request spends its time and who owns each piece. Without a picture of the layers, a kernel win, a scheduler change and a routing rule all look like the same kind of work.

Where it fits: Second view of the series map. The overview gave one formula for $/token; this card lays the same field out as six layers a request passes through, from the API down to HBM, and ties each layer to the course that teaches it.

In one breath

A request passes down through layers: the API and router, a pool of autoscaled replicas, an inference engine (scheduler, KV cache manager, model runner), the kernels (attention, matmul), and finally the GPU's tensor cores and HBM. A company that serves inference cheaply wins by squeezing every layer. This series walks up the stack one course at a time.

The picture

Green arrows: the path of one request down the stack; the generated tokens stream back up the same path. perf-7 also covers the economics ($/token), which cut across every layer. Kiely's third layer, tooling (the developer experience on top of runtime and infrastructure), isn't drawn. Where his "runtime" ends is our reading: he puts parallelism inside one instance in runtime, and autoscaling and multi-region capacity in infrastructure.

Kiely's words for the two halves (book p. 17): the runtime is "optimizing the performance of a single model on a single GPU-backed instance", and the infrastructure is "scaling across clusters, regions, and clouds without creating silos while maintaining excellent uptime". He lists six runtime techniques (p. 19), and each one lives at a specific layer of the picture:

Follow one request

The running example: Llama-3.1-8B in BF16 on one H100 SXM, a 1,000-token prompt and 200 output tokens. The shapes and floors come from perf-1's shared facts.

  1. Client & API. The prompt arrives and is tokenized into 1,000 tokens. Network and queue time aren't in the floors below: they depend on distance and load (see the consumer view in llm-latency: TTFT).
  2. Router. It picks a replica. If a replica already holds this prompt's prefix in its KV cache, those tokens skip prefill. Here: a cold request, no hit.
  3. Replica. One H100 is enough: the 16.06 GB of weights leave 80 − 16.06 = 63.9 GB for KV cache. A 70B model (about 140 GB in BF16) wouldn't fit on one GPU, so this layer would split it with tensor parallelism (perf-6).
  4. Engine. The scheduler adds the request to the running batch (continuous batching). The KV manager reserves pages for up to 1,200 tokens × 128 KiB = 157 MB. 63.9 GB ÷ 157 MB ≈ 406 requests like this one fit at once.
  5. Kernels + hardware, prefill. All 1,000 prompt tokens go through in one forward pass. That's 2 × 8.03e9 × 1,000 ≈ 1.61e13 FLOP, which reuses each weight byte 1,000 times. 1,000 is above the H100's 295 FLOPs per byte, so prefill is compute-bound: the floor is 16.2 ms of GEMMs and attention, and it produces the first token (TTFT).
  6. Kernels + hardware, decode. The other 199 tokens take one step each. Every step streams all 16.06 GB of weights from HBM to make 1 token: about 1 FLOP per byte, so decode is memory-bound. That's 4.79 ms/step. KV reads add under 1%: at most 157 MB against 16 GB of weights.
  7. Sampler → API. Each step's logits become a token, which streams back up through the API as it's made.
prefill 2 × 8.03e9 × 1,000 ÷ 989e12 FLOP/s = 16.2 ms (TTFT floor) decode 16.06 GB ÷ 3.35 TB/s = 4.79 ms × 199 steps = 954 ms (TPOT floor 4.79 ms) total 16.2 + 954 ≈ 970 ms (GPU-only, batch 1)

These are floors: 100% of peak FLOP/s and bandwidth, with no network, queue or engine overhead. A real engine is slower at every layer. A provider also doesn't run batch 1, because the same weight read can serve many users at once. Our computation, taking each request at its end-of-generation size of 1,200 tokens of KV:

batch 1 16.06 GB ÷ 3.35 TB/s = 4.79 ms/step → 209 tok/s batch 64 (16.06 + 64 × 0.157 GB KV) ÷ 3.35 TB/s = 7.80 ms/step → 8,206 tok/s same GPU-hour, 39× the tokens; each user: 209 → 128 tok/s

At batch 64 the matmuls need only 2 × 8.03e9 × 64 ÷ 989e12 = 1.04 ms, so the step is still memory-bound. That trade, cheaper tokens against a slower TPOT, is what layer 4 tunes all day (perf-2 step-time, perf-5).

How it differs from related ideas

✗ The training stack

It optimizes one thing, throughput (MFU). There's no KV cache, no TTFT, and no router. It pays 6N FLOPs per token instead of 2N and shards weights, gradients and optimizer state with FSDP. The kernels and hardware are shared; the layers above them aren't (perf-7).

✗ A single-user local stack

llama.cpp or Ollama on your M3: one process, batch 1, no router and no autoscaler. Decode is memory-bound at about 15 tok/s (qwen3.5:4b, measured). Batching, the provider's main cost lever, never comes into play.

✗ A closed API, seen from outside

The llm-latency view. You see TTFT, tok/s and a price, but every layer below the API is hidden. Your only levers are the prompt, the model choice and caching.

✓ The provider's inference stack

You own all six layers and tune each one for $/token at a latency target, packing many users onto each GPU. It's the view this series teaches, and the one a job at an inference company needs.

Where does a provider actually win, and what will you touch?

Our view, not a sourced claim:

  • Kernels and engine scheduling decide $/token. The batch-64 line above shows the size of the lever: 39× more tokens from the same GPU-hour. Faster kernels then lower every one of those steps.
  • Routing and capacity decide reliability and the tail. Kiely says multi-cloud capacity "improves reliability, protecting against downtime in any individual region or cloud provider" (p. 20).

Day to day, most engineers work in the upper layers. Kiely: "Most inference engineering today happens at the higher levels of abstraction, configuring and deploying inference engines and orchestrating inference across multiple GPUs" (p. 96), and "most inference engineers will never need to write their own kernels. However, kernel selection ... is an important part of inference optimization" (p. 98). A kernel-focused company is the exception. There, layer 5 is the product, which is why perf-3 exists.

Not every deployment has all six layers. For Dynamo, Kiely writes: "Unless you're operating with enough volume for disaggregation and KV-aware routing to matter, Dynamo will be unnecessary work and excess overhead" (p. 112). A small deployment is one replica running an engine directly, so layers 2–3 shrink to almost nothing. The six boxes are also a simplification: "Routing occurs throughout the stack with load balancers injected at key points" (p. 191).

Understand and remember

  • Prefill processes 1,000 tokens per weight read → about 1,000 FLOPs per weight byte → above the H100's 295 ops:byte → compute-bound → TTFT floor 16.2 ms, set by the tensor cores
  • Decode makes 1 token per full weight read → about 1 FLOP per byte → far below 295 → memory-bound → 4.79 ms per step set by HBM bandwidth → a faster chip for decode means more TB/s, which is why the H200 (4.8 TB/s) cuts decode but not prefill
  • Each layer owns one decision (which replica, how many GPUs, who shares a step, how close to the ceilings) → each moves a different metric (TTFT, uptime, TPOT/throughput, every latency) → the provider must tune all six for $/token at a latency target
  • Layer 4 packs requests into one step → the 16 GB weight read is shared → batch 64 gives 39× the tokens from the same GPU-hour → but per-user speed falls 209 → 128 tok/s → the scheduler trades TPOT for cost all day
  • detail that matters KV per token is 128 KiB for Llama-3.1-8B → a 1,200-token request reserves 157 MB → 63.9 GB of free HBM holds ≈ 406 of them → so HBM left after the weights, not FLOPs, caps how many users an engine can batch

Reference only

  • the software list: CUDA → cuBLAS/cuDNN/CUTLASS/FlashInfer/DeepGEMM → PyTorch → vLLM/SGLang/TensorRT-LLM → Dynamo
  • router products: llm-d, Gateway API Inference Extension, Dynamo KV-aware router
  • H100 SXM: 132 SMs, 989 TFLOPS BF16, 80 GB, 3.35 TB/s
  • Kiely's page numbers (pp. 17, 19, 95–99, 112, 191)
  • the example knobs (min replicas 0 vs 2, max batch 8 vs 256)

5 · Predict commit to an answer before revealing

Change the request to a 2,000-token prompt and a 100-token answer, still batch 1 on one H100. Before computing: does the total floor go up or down from 970 ms, and which phase now takes a bigger share?

Reveal

Down, to about 507 ms. Prefill doubles to 2 × 8.03e9 × 2,000 ÷ 989e12 ≈ 32.5 ms (still compute-bound, 2,000 > 295), but decode shrinks to 99 × 4.79 ≈ 475 ms. Prefill's share grows from about 2% to about 6%, yet decode still dominates: output length matters far more than prompt length for the floor.
