Glossary: the words of fast LLM inference

Also called the jargon decoder for inference serving and GPU performance. It has 80 terms from this series' cards and from Kiely's Inference Engineering Appendix A (pp. 211–229). Each term comes with one number from the running example, Llama-3.1-8B in BF16 on one H100 SXM, and the card that teaches it.

In one breath

Nearly every word here names one of three things: a part of the model (weights, attention, the KV cache), a part of the machine (tensor cores, HBM, links), or a way of arranging work so the machine stays busy (batching, caching, sharding, quantizing). The metrics (TTFT, TPOT, throughput) tell you whether the arranging worked. When a word is new, ask which of the three it belongs to and whether it saves FLOPs or bytes.

THE MODEL · what one forward pass computes

Token, vocabularytokenizer
A token is the integer unit a model reads and writes, and the vocabulary is the full set of them. Llama-3.1-8B: V = 128,256 tokens. Kiely: English runs about 4:3 tokens to words (p. 227). transformer-forward →
Parametersweights
The learned numbers in the weight matrices, stored in memory and read on every step. 8.03B = 16.06 GB in BF16: MLP 70.2%, attention 16.7%, embeddings and LM head 13.1%. transformer-forward →
Forward passa step · decoder-only transformer
One run of every layer over some tokens. Prefill is one forward pass over the whole prompt, and each decode step is one forward pass over one new token. L = 32 layers of 218.11M parameters each. transformer-forward →
MLPFFN, feed-forward, SwiGLU
The per-token block of big matrix multiplies in each layer. It holds most of the parameters and most of the FLOPs. 3 matrices of 4096 × 14336: 176.16M parameters per layer. flops-per-token →
AttentionQ, K, V · heads · self-attention
Each token scores its query against every earlier token's key, then takes a weighted mix of their values. 32 query heads of H = 128. Its FLOPs grow with context, and 2N doesn't count them. attention →
MHA, GQA, MQAmulti-head · grouped-query · multi-query
How many key/value heads the query heads share: one each (MHA), one per group (GQA), or one for all (MQA). KV per token: 512 KiB MHA · 128 KiB GQA-8 (the real model) · 16 KiB MQA. 8k-token sequences that fit: 14 · 59 · 476. attention →
KV cachekey–value cache
The saved keys and values of every past token in every layer, so they're never recomputed. It turns decode from re-running the prefix into one new token per step. 2·L·K·H·2 bytes = 128 KiB per token, 1.07 GB for an 8,192-token sequence. kv-cache-sampling →
Logits, samplinggreedy · temperature · top-k · top-p
Logits are one score per vocabulary token. Sampling turns them into probabilities and picks the next token. 128,256 logits per step. Kiely lists greedy, temperature, top-k and top-p (p. 225). kv-cache-sampling →
Prefillprompt processing · "prompt eval"
The phase that reads the whole prompt in one parallel pass, writes its KV cache and produces the first token. 1,000 tokens ≥ 16.2 ms on an H100. Your M3: 188 tok/s at 244 tokens. prefill-vs-decode-mac →
Decodegeneration · autoregressive decoding
The phase that writes one token per step, each depending on all the tokens before it. ≥ 4.8 ms per step, so at most ≈ 209 tok/s at batch 1. Your M3: 14.1 tok/s, 13× slower per token than its prefill. prefill-vs-decode-mac →
Context lengthcontext window · sequence length S
How many tokens a request holds (prompt plus output so far). The window is the model's maximum. Attention FLOPs over 2N: +27% at 8k, +428% at 128k. Break-even at 32,768 tokens. flops-per-token →
Sliding-window attentionlocal attention
Layers that only attend to the last W tokens, so their KV cache stops growing past the window. Hypothetical Llama with 1 global layer in 6 and a 4k window: 64 → 37 KiB per token at 8k (with FP8 KV). kv-tricks →
MLAmulti-head latent attention
DeepSeek's attention caches one compressed latent vector per token instead of per-head K and V. DeepSeek-V2 paper: −93.3% KV cache vs DeepSeek 67B. mla →
Mixture of expertsMoE · router · experts
Kiely: "A model architecture where linear layers of weights are separated into sparse experts. A router activates a subset of experts for each forward pass." (p. 222) DeepSeek-V3: 256 routed experts + 1 shared, 8 routed active per token. moe-basics →
Active vs total parameters
An MoE stores every expert but only uses the active ones per token. FLOPs follow active, memory follows total. DeepSeek-V3: 37B of 671B, so 2 × 37e9 = 74 GFLOP/token, not 1,342. flops-per-token →

THE HARDWARE · where the FLOPs and bytes live

SMstreaming multiprocessor
One of the GPU's many independent processors. A thread block runs entirely on one SM. 132 SMs on an H100, 148 on a B200. gpu-machine →
Thread, warpSIMT
A thread is the smallest unit of GPU work. A warp is 32 threads that run one instruction together. Up to 2,048 threads resident per SM. An if/else inside a warp runs both branches in turn. gpu-machine →
Tensor core vs CUDA core
Tensor cores do matrix multiply-accumulate and provide nearly all the FLOPs. CUDA cores do scalar and vector math. H100: 990 vs 66 TFLOP/s (15×), from 528 tensor cores. gpu-machine →
HBMVRAM · device or global memory
The GPU's main memory, stacked beside the chip. It holds the weights and the KV cache, and its bandwidth sets decode speed. H100: 80 GB at 3.35 TB/s. After the weights, 63.9 GB is left for KV. gpu-machine →
SMEM, L2, registersshared memory / L1 · on-chip memory
The small, fast memory on the chip. Kernels stage tiles here so they can reuse them instead of re-reading HBM. 256 KB SMEM per SM, 50 MB L2. The weights are 321× the L2, so they never fit on chip. gpu-machine →
Memory bandwidthW, Whbm
Bytes per second that memory can deliver to the chip. For batch-1 decode it's the speed limit. H100 3.35 TB/s vs M3 ~0.1 TB/s = 33.5×, and so are the 8B decode ceilings: 209 vs 6.2 tok/s. gpu-machine →
NVLink, nodeNVSwitch · scale-up
The fast GPU-to-GPU links inside a node, which is usually 8 GPUs. 450 GB/s per H100 each way (18 × 25 GB/s), about 370 achievable. Kiely says 900 for Hopper (p. 223): see the note on overloaded words below. gpu-machine →
InfiniBandscale-out · multi-node
Kiely: "Inter‑node interconnect for scaling inference and training across multiple nodes", with bandwidth "substantially lower than NVLink" (p. 219). Kiely: tensor parallelism is too chatty for it, so multi-node serving uses PP or EP between nodes (p. 222). pipeline-data-parallel →
TPU, ICITPU v5e · inter-chip interconnect
Google's accelerator and its chip-to-chip links. The Scaling Book's numbers are all for this chip. v5e: 197 TFLOP/s, 16 GB at 0.82 TB/s, ICI 4.5e10 B/s one way. Llama-3.1-8B BF16 doesn't fit on one chip. roofline →
H100, H200, B200Hopper · Blackwell · SXM
NVIDIA's datacenter GPUs. A newer part mostly adds bandwidth and capacity, which is what decode needs. H100 989 TF, 80 GB, 3.35 TB/s · H200 141 GB, 4.8 TB/s · B200 2,250 TF, 192 GB, 8 TB/s. gpu-machine →

PERFORMANCE VOCABULARY · FLOPs, bytes, and which one runs out first

FLOP vs FLOP/sFLOPs · FLOPS · TFLOPS
A FLOP is one multiply or one add, and FLOP/s is how many a chip can do per second. The same four letters get used for both. 16.06 GFLOP per token, against an H100's 989 TFLOP/s dense BF16 (1,979 FP8). flops-per-token →
2N and 6N rules6ND · FLOP counting
A forward pass costs about 2 FLOPs per parameter per token. Training adds a backward pass at about twice that, for 6 in total. 2N = 16.06 GFLOP/token. 6ND for Llama 3.1 8B on ~15T tokens = 7.23e23 FLOPs. flops-per-token →
GEMM, matmulthe 2mkn rule
A matrix multiply, the operation that inference spends nearly all its FLOPs on. (m×k)·(k×n) costs 2mkn FLOPs. One token through Wgate: 2·1·4,096·14,336 = 117.44 MFLOP. flops-per-token →
Arithmetic intensityops per byte of an algorithm
How many FLOPs an operation does for each byte it moves. More reuse of each byte means higher intensity. A matmul over B tokens has intensity ≈ B, so batch-1 decode is ≈ 1. roofline-intuition →
Ops:bytehardware intensity αhbm · ridge point
The chip's peak FLOP/s divided by its memory bandwidth, which is the intensity an operation needs to keep the math busy. H100 989e12 ÷ 3.35e12 ≈ 295 · v5e 240 · B200 281. roofline →
Rooflineroofline model
A plot of achievable FLOP/s against intensity: a slanted bandwidth roof, a flat compute roof, and the ridge where they meet. Left of 295 on an H100 you're paying for bytes. Right of it you're paying for math. roofline →
Memory-boundbandwidth-bound
The reads finish last, so the math units wait. Batch-1 decode: 16.2 µs of math against 4.79 ms of weight reads, so the tensor cores sit idle ≈ 99.7% of the time. roofline-intuition →
Compute-boundmath-bound · FLOPs-bound
The math finishes last, so faster memory would not help. A 1,000-token prefill: 16.2 ms of math against 4.8 ms of weight reads. roofline-intuition →
Critical batch sizeBcrit · "the batch-240 rule"
The number of tokens per step at which a linear layer turns from memory-bound to compute-bound. It equals β·αhbm. v5e 240 · H100 ≈ 295 · int8 weights with bf16 math halve it (120). For MoE it's × E/k: 3,840 for DeepSeek (book, int8). critical-batch-size →
Attention intensityST/(S+T)
Attention reads each sequence's own KV cache, so batching can't share it. In decode its intensity stays near 1 at any batch size. Prefill ≈ T/2, decode ≈ 1. GQA raises it toward the group size, 4 for Llama-3.1-8B. attention-intensity →
Step time"the one equation of LLM serving"
How long one decode step takes: the time to read every KV cache, plus the larger of the weight math and the weight read. 59 sequences at 8k: 18.9 + max(0.96, 4.79) = 23.7 ms → 2,489 tok/s. The book's Pop Quiz: 2.5 ms and 21 ms. step-time →
MFUmodel FLOPs utilization
The share of the chip's peak FLOP/s that the model's own FLOPs actually use. Llama 3 paper: 38–43% for 405B pretraining. The book's 70B prefill assumes 40%: 0.91 s for 8k tokens on 16 v5e. flops-per-token →

METRICS & REGIMES · what a provider is judged on

TTFTtime to first token
From request arrival to the first output token: queueing plus prefill. H100 floor for 1,000 tokens: 16.2 ms. Your M3: 1.30 s for 244 tokens. serving-metrics →
TPOTITL · inter-token latency · TBT
The time per output token after the first one, which is one decode step for that request. H100 batch 1: 4.84 ms. Kiely: a 2 ms ITL equals 500 TPS (p. 220). serving-metrics →
E2E latencyend-to-end · request latency
From arrival to the last token, which is TTFT + (nout − 1) × TPOT. 1,000 in, 200 out: 16.2 + 199 × 4.84 = 979 ms. serving-metrics →
Tokens/s per user vs totalperceived TPS · throughput
Per-user speed is 1 ÷ TPOT, what one reader feels. Total throughput is what the whole server produces, and it's what the provider sells. Batch 1: 207 and 207. Batch 120: 100 per user, 12,050 total. serving-metrics →
Goodput
Throughput that counts only requests meeting their latency targets. DistServe defines it per GPU, in requests per second. Under a 10 ms TPOT SLO (illustrative): 12,050 tok/s at batch 120 and 0 at batch 443, although raw throughput is higher there. serving-metrics →
SLO, SLAservice level objective · agreement
The SLA is the promise made to customers. Kiely: the SLO is "An internal target designed to meet or beat the SLA" (p. 226). A 10 ms TPOT SLO (illustrative) caps the H100 batch at 120. serving-metrics →
PercentilesP50 · P95 · P99 · tail latency
The latency that a given share of requests beats. P99 is the slowest 1 in 100, where users actually notice. Your M3, 20 identical requests: P50 4.66 s, P95 6.54 s. serving-metrics →
ISL, OSLinput / output sequence length
The prompt and answer lengths in tokens. A benchmark has to state them, because they decide which phase dominates. Kiely pp. 219, 223. The worked example here is ISL 1,000 and OSL 200. benchmarking →
Offline, chat, edgebatch vs online inference · the three regimes
The book's three regimes. Offline cares only about cost, chat must also stay fast enough to read, and edge serves one user as fast as possible. Reading speed ≈ 5.2 tok/s, so the 209 tok/s batch-1 ceiling is ≈ 40× headroom to share. what-we-optimize →

SERVING & ENGINES · arranging requests so the GPU stays busy

Batch, batch sizeB · tokens per step
Processing many sequences' tokens in one step, so one read of the weights serves all of them. 2k context: B = 1 → 238 takes 205 → 9,973 tok/s total, while per-user speed falls to 41.9. step-time →
Latency–throughput frontierPareto frontier
The curve you move along by changing batch size: more total tokens per second, but each user's tokens arrive more slowly. Batch 443 (HBM full): 16,870 tok/s total but 38 per user. what-we-optimize →
Continuous batchingin-flight batching · iteration-level scheduling
Requests join and leave a running decode batch at every step, instead of the whole batch finishing together. The problem it's paired with: an 8k-token prefill freezes 32 decoding users for 13.4 steps. inference-engine-design →
Static, dynamic batching
Kiely: dynamic batching "starts a batch when the batch is full or a short timer elapses, whichever comes first", and it's "superseded by continuous batching for LLMs" (p. 216). The book's "batched prefill, then generate" pads to the longest prompt and leaves finished slots empty. inference-engine-design →
Chunked prefill
Kiely: "Splits long inputs into chunks and overlaps prefill with decode or other work, preventing single long sequences from monopolizing resources." (p. 214) It's the fix for the 13.4-step stall above (Sarathi-Serve). sarathi-chunked-prefill →
Prefix cachingRadixAttention · prompt caching
Reuse the KV cache of a shared prompt prefix and skip its prefill. The book's example: "I like dogs" and "I like cats" share 2 of 3 tokens, so the second needs only ⅓ of the prefill. inference-engine-design →
PagedAttentionpaged KV cache · vLLM
Store the KV cache in fixed-size pages, like OS virtual memory, so padding is never stored. 16-token pages: 20 tokens wasted of 18,912 (illustrative lengths). vLLM reports 2–4× throughput. kv-tricks →
Disaggregationprefill/decode disaggregation · disaggregated serving
Run prefill and decode on separate servers and ship each KV cache between them, so one prompt never stalls other users. The book's 70B pipeline wants about 3 prefill servers per generate server. inference-engine-design →
Speculative decodingspeculative sampling · draft-and-verify
A cheap draft proposes K tokens, and the big model checks them all in one memory-bound pass. The output distribution doesn't change. α = 0.8, K = 4, 1B draft: 209 → 468 tok/s at batch 1, but a 0.70× slowdown at batch 256. speculative-sampling →
Acceptance rateα (speculation)
The chance that the big model accepts a drafted token. Expected tokens per verify pass = (1 − αK+1) ÷ (1 − α). α = 0.8, K = 4: (1 − 0.85) ÷ 0.2 = 3.36 tokens per pass. speculative-sampling →
EAGLE, Medusa, n-gram, MTPkinds of draft
Kiely: EAGLE is "A small, purpose‑built draft model trained to consume hidden states" (p. 217). Medusa "Adds extra decoder heads via fine‑tuning" (p. 221). N-gram drafts are "Extremely effective for code completion" (p. 223). DeepSeek-V3 trains with MTP (multi-token prediction). eagle →
Inference enginevLLM · SGLang · TensorRT-LLM
Kiely: "A high‑performance runtime (vLLM, SGLang, TensorRT‑LLM) with support for optimization techniques like batching, caching, quantization, and speculation." (p. 219) Its parts include an API server, a scheduler with a KV budget, a model runner and a sampler. engine-anatomy →
LoRA, structured outputmulti-LoRA serving · constrained decoding
Kiely: services "often need to swap between thousands of LoRAs for a single foundation model" (p. 221). Structured output is "Created by constraining generation to a supplied schema via logit biasing rather than via prompting" (p. 227). multi-lora →
Cache-aware routing, cold startKV-aware routing · autoscaling
Kiely: routing means "Steering requests to replicas that already hold matching prefixes or required LoRAs" (p. 213). A cold start is "The time from scaling a replica from zero to its first successful response" (p. 214). autoscaling-cold-starts →

KERNELS · the code that runs on the GPU

CUDA kernelkernel
Kiely: "A user-defined function that executes parallelized code on the GPU." (p. 215) One launch runs a grid of thread blocks, each on one SM. execution-model →
Kernel fusion
Kiely: "Taking two or more kernels and re-implementing them into a single kernel that handles both operations, avoiding unnecessary round-trips through memory." (p. 220) fusion-cuda-graphs →
CUDA graphlaunch overhead
Kiely: "A directed acyclic graph (DAG) of kernels and other GPU operations for optimizing repeated workflows." (p. 215) Engines capture a decode step once and replay it, so they skip the per-kernel launch cost. fusion-cuda-graphs →
cuBLAS, CUTLASS, Tritonkernel libraries and languages
cuBLAS is NVIDIA's library of ready-made GEMMs. CUTLASS is "A CUDA C++ template library that provides building blocks for … GEMM and related kernels" (Kiely p. 215). Triton, the language, writes kernels in Python over blocks rather than threads. triton-programming-model →
FlashAttentionFA2 · FA3 · FA4
Kiely: "A series of optimized attention kernels that minimize memory traffic. FlashAttention 3 is written for Hopper, FlashAttention 4 targets Blackwell." (p. 217) It never writes the T×T score matrix to HBM. flashattention-tiling →

SCALING OUT · more than one chip

Data parallelismreplicas · DP
Run full copies of the model and give each copy different requests. It adds throughput, but no single request gets faster. Every replica holds all 16.06 GB of weights. sharding-prefill-generation →
Tensor parallelismTP · model parallelism (the book's name) · Megatron
Split each weight matrix across chips so each reads only its share, then combine the results with collectives every layer. 8×H100: weight read per step 4,794 → 599 µs. Lower latency, not lower cost. sharding-prefill-generation →
FSDPfully sharded data parallel · ZeRO-3
Shard the weights across chips and gather them just in time for each layer. It suits training but is a poor fit for decode. Decode on 8×H100 would take 31 ms per step instead of 4.8 ms. sharding-prefill-generation →
CollectivesAllReduce · AllGather · ReduceScatter · AllToAll
Standard patterns for moving data among a group of chips, such as summing partial results or swapping shards. AllReduce = 2× AllGather. Batch-sharded KV costs 2 AllToAlls per layer. sharding-kv-cache →
Pipeline parallelismPP · pipeline bubble
Kiely: it "Splits layers into stages across GPUs" and "introduces bubbles in the pipeline where some GPUs are idle while waiting for other steps to finish" (p. 224). pipeline-data-parallel →
Expert parallelismEP · dispatch/combine
Kiely: "Shards experts of an MoE across GPUs; each GPU contains multiple full experts." (p. 217) DeepSeek-V3 has 256 routed experts to place. expert-parallel →
Context parallelismCP · ring attention · sequence parallelism
Kiely: CP "Replicates weights across GPUs and partitions the attention context" (p. 214). In ring attention, "GPUs pass partial attention results in a ring" (p. 225). long-context →

NUMBER FORMATS · fewer bits, fewer bytes to read

BF16, FP16bfloat16 · half precision
Two 16-bit float formats. Kiely: BF16 has a "larger exponent than FP16", so it handles outliers better (p. 213). 2 bytes per parameter: 8.03B → 16.06 GB. params-vs-kv →
FP8E4M3 · E5M2
8-bit floats, which halve the bytes and, on Hopper, double the tensor-core rate. H100 1,979 TFLOP/s FP8. FP8 weights: decode floor 4.79 → 2.40 ms. FP8 KV: 2,489 → 4,986 tok/s. kv-tricks →
INT8, INT4integer formats
Integer formats with less dynamic range than floats of the same width, used mostly for stored weights. Book, LLaMA 3-70B QPS per chip: bf16 0.276 → int4 1.105 (4.0×). serving-llama-70b →
Quantizationpost-training · weights-only · W8A8 · GPTQ · AWQ
Kiely: "Lowering precision of weights, activations, and potentially KV cache to reduce compute and memory bandwidth demands." (p. 224) Weights-only keeps "the best quality preservation but the lowest performance improvements" (p. 229). quantization-serving →
MicroscalingMXFP8 · MXFP4 · NVFP4
Kiely: low-bit floats with "blockwise quantization with small-block scale factors (e.g., every 32 elements)" (p. 221). NVFP4 uses "a block size of 16" (p. 222). tensor-cores-low-precision →

TRAINING & ECONOMICS · where weights come from, and what a token costs

Training stepforward · backward · optimizer · remat
A forward pass, a backward pass costing about 2× the forward, and an update of the weights. Rematerialization (activation checkpointing) recomputes activations to save memory. 6N = 48.18 GFLOP per training token for Llama-3.1-8B, or 8N with full remat. flops-per-token →
Pretraining, fine-tuning, distillation
Kiely: pretraining is "Large‑scale (usually self‑supervised) training on broad corpora to create a base model" (p. 224). Distillation is "Training a smaller student to emulate a larger teacher model based on probability distributions, not just outputs" (p. 216). post-training →
Cost per million tokens$/M tokens · QPS per chip
GPU cost per hour divided by millions of tokens produced per hour. The book says throughput per chip "is exactly correlated with cost / token". H100 at $10.8/hr (Google Cloud list, Feb 2025, Scaling Book Part 8) ÷ (2,489 tok/s × 3,600 = 8.96M tok/hr) ≈ $1.21 per M tokens; at batch 1 it's $14.35. See the map. cost-per-token →

The most-confused pairs

TTFT vs TPOT

TTFT is paid once per request (queue plus prefill). TPOT is paid on every token after the first (one decode step). Prefill work moves TTFT, and decode work moves TPOT.

16.2 ms once vs 4.84 ms × 199: for a 200-token answer, TPOT is 98% of the wait.

Total vs active parameters

Total sets the memory you need to hold the model. Active sets the FLOPs and the bytes each token actually reads. For a dense model they're equal.

DeepSeek-V3: 671B to store, 37B to use per token.

Tensor vs data parallel

Tensor parallel splits one copy of the model, so each request gets faster but the chips talk every layer. Data parallel runs whole copies, so there's more throughput and no talking, but no request gets faster.

8×H100 TP: 4,794 → 599 µs weight read. 8 replicas: 8× the tokens at the same 4.8 ms.

✓ Memory-bound vs compute-bound

This is the pair that matters most. Before tuning anything, find which one finishes last: the reads or the math. Memory-bound work gets faster from fewer bytes or more batching. Compute-bound work gets faster from better tensor-core use.

The line between them is ops:byte, ≈ 295 tokens per step on an H100.

The field reuses its words: which meaning is meant?

  • "Batch" in the Scaling Book means tokens per step. In decode that equals the number of sequences, but in prefill one 1,000-token prompt is a batch of 1,000. Engines, Kiely and most papers mean requests. The perf-2 cards write B as "tokens in this step, per replica (not sequences)".
  • β means two things in the same chapter. In Bcrit = β·α it's a precision ratio, bits per parameter ÷ bits per activation (½ for int8 weights with bf16 math). In the sharding section it's Whbm ÷ Wici, how much faster memory is than the links ("around 8" on v5e, 7.4 on H100).
  • α is the chip's ops:byte (αhbm = 240 or 295) in the roofline sections, and the draft acceptance rate in speculative decoding.
  • K is the number of KV heads, the key tensor (the book apologises: "I apologize for using K for both the key tensor and the KV head dimension"), and the number of drafted tokens in speculation. D is model width in the Scaling Book but training tokens in "6ND".
  • "Model parallelism" is the Scaling Book's name for tensor parallelism. In Kiely it's the umbrella term for tensor, expert and pipeline parallelism together (p. 222).
  • "TPS" in Kiely is a per-user latency metric (perceived TPS, p. 228). In most dashboards it means the server's total throughput. Check which one a number is before comparing.
  • NVLink bandwidth is 450 GB/s in the Scaling Book (per GPU, each direction) and 900 GB/s in Kiely. Our reading, not stated by either source: 900 counts both directions (18 links × 50 GB/s).
  • "Triton" is two different things: the Python kernel language (perf-3) and NVIDIA's Triton Inference Server, a serving framework (Kiely p. 228). "FLOPS" can mean a count or a rate, and GB vs GiB differ by 7%. The book's 13B tables mix them.

When this glossary isn't enough: it gives one sentence per term, which is enough to follow a conversation but not to use the idea. Words like Bcrit or step time only make sense with their formula, so read the linked card. For a grey-tagged term, Kiely's full chapter is the best source until its course exists.
