In one breath

An inference company sells tokens. Its cost per token is what a GPU-hour costs divided by how many tokens that GPU produces in an hour. Nearly everything in this field, from kernels and the KV cache to batching, quantization, parallelism and routing, is a way to raise tokens per GPU-second without breaking the latency users will accept.

$106 tokens= GPU price per hourhardware & capacity 3600·BTsteptokens/s per GPU ×106 subject to Tstep≤latency SLO
GPU $/hrwhat the chip costs to rent or ownH100 $10.8/hr (GCP list, Feb 2025) Btokens decoded per step: users sharing one pass over the weights1 … memory limit Tsteptime per decode step: KV reads + max(math, weight reads)4.79 ms at B = 1 (Llama-3.1-8B) SLOthe per-token latency the product promisese.g. 25–100 ms (Etalon's targets)

Filled in for Llama-3.1-8B on one H100 at $10.8/hr (theoretical floors): at batch 1, 209 tokens/s → $14.35 per million tokens. At batch 64 with 1,200-token contexts, 8,206 tokens/s → $0.37. That's the same chip and the same model, 39× cheaper, while each user still gets 128 tokens/s. List prices vary a lot between clouds, so compare the ratios, not the dollars.

The same thing in plain text:

$ per million tokens = GPU $/hour ÷ (3600 × tokens/s per GPU) × 1,000,000 tokens/s per GPU = batch ÷ step time (perf-1, perf-2) step time ≤ what the latency SLO allows

The words people use

Runtime vs infrastructure

Kiely's split. Runtime is one model on one instance (kernels, engine, batching). Infrastructure is autoscaling, capacity and routing across many instances.

Shared vs dedicated inference

Paying per token on someone else's API, or renting whole GPUs per hour and running the model yourself. At scale, dedicated is where $/token engineering pays off.

TTFT, TPOT, goodput

The latency a user feels (first token, then each token after it) and the throughput that still meets those targets, which is what a provider can sell.

Tokens per GPU-second

The quantity every lever in this series ultimately moves. Divide a GPU-hour's price by it and you have the business.

The takeaway

Learn the formula first, then the machinery. Courses 1 and 2 give you the arithmetic that everyone at an inference company uses daily: FLOPs, bytes, Bcrit, KV per token, step time. The later courses are the machinery that gets real systems close to those numbers. Read each course's cards, run its labs, then read the primary-source sections named in the reading plan. That's about 93 hours by our estimate.

When the plan doesn't fit: if your company runs AMD, TPU or Trainium, promote those SKIP items. If it serves image, audio or video models, add Kiely ch. 6. And $/token isn't the only goal. Latency-first products deliberately run at small batch and pay more per token.

1 · Core model what to internalise, what to just look up

Keep it if it changes what you can explain, predict, compare, choose, build or debug. Otherwise it's reference.

Understand and remember

  • Decode reads all 16.06 GB of weights per step whatever the batch → the weight read is shared by every user in the batch → tokens per step rises with B while Tstep rises only by the extra KV reads → tokens/s per GPU climbs → $/token falls (batch 1 → 64: $14.35 → $0.37)
  • Bigger batch → more KV reads per step → longer Tstep → slower tokens for each user (209 → 128 tok/s) → the latency SLO caps B → so every byte saved per token (GQA, FP8 KV, quantized weights) buys a bigger batch under the same SLO
  • Decode is memory-bound → the tensor cores sit mostly idle → spare math can verify guessed tokens (speculative decoding) → more tokens per weight read at small batch → but at large batch the math is no longer spare, so speculation costs more than it saves
  • The course formulas give theoretical floors → real kernels and engines reach only about half of them → kernel and engine work (perf-3, perf-5) is a multiplier on every lever, not a separate lever
  • detail that matters Hardware choice for decode is really bandwidth per dollar → the same request drops from 970 ms on an H100 to 407 ms on a B200 because HBM goes 3.35 → 8.0 TB/s → compare chips on $/hr ÷ TB/s, not on FLOP/s

Reference only

  • the H100 list price $10.8/hr (GCP, Feb 2025) and that cloud prices vary
  • Etalon's 25–100 ms SLO examples
  • the lab tags [L] local Mac, [C] Colab T4, [H] rented H100

  1. concept Explain to a new colleague why an inference company's margin is set by tokens per GPU-second, and what single constraint stops them from simply maximising it.
    Check
    • the GPU-hour is a fixed cost, so $/token = price ÷ tokens produced
    • every technique in the series raises tokens per GPU-second
    • the per-user latency SLO limits how large the batch (and so the step time) can get
  2. mechanism Walk through what happens to one decode step's time and to throughput when the batch goes from 1 to 64 users with 1,200-token contexts on Llama-3.1-8B/H100.
    Check
    • weights read once either way: 16.06 GB ÷ 3.35 TB/s = 4.79 ms
    • KV reads add 64 × 0.157 GB, so the step becomes 7.80 ms
    • math is only ~1 ms at batch 64, so the step stays memory-bound
    • tokens/s: 209 → 8,206 (39×); per user: 209 → 128 tok/s
  3. tradeoff A product team wants the lowest possible per-token latency for a single premium user. Which levers from the ranking still help, which stop mattering, and what does the company pay?
    Check
    • run at small batch, so the batching lever is given up deliberately
    • speculative decoding helps most here (209 → 468 tok/s at batch 1)
    • bandwidth per dollar and fewer weight bytes still shorten each step
    • the cost: many times more $ per token (batch 1 is $14.35/M vs $0.37 at batch 64)
  4. concept Place each of the eight courses on the $/token formula: which term does it change, and which course would you open first if a deployment's step time is fine but its batch stays small?
    Check
    • perf-1/2: the arithmetic for every term
    • perf-3/4: shorter Tstep and fewer bytes per token
    • perf-5: keeps B high (scheduling, batching) and uses idle math (speculation)

Why this step?

5 · Predict commit to an answer before revealing

Keep Llama-3.1-8B on one H100 at $10.8/hr and 1,200-token contexts, but run batch 16 instead of 64. Before computing: will the cost per million tokens land closer to $0.37 or to $14.35, and what will each user's speed be?

Reveal

Much closer to $0.37: step = (16.06 + 16 × 0.157) GB ÷ 3.35 TB/s ≈ 5.54 ms, so 16 ÷ 5.54 ms ≈ 2,885 tok/s and ≈ $1.04 per million tokens, with each user at ≈ 180 tok/s. Most of the batching win arrives early, because the shared weight read dominates the step until KV reads grow.

Hint
