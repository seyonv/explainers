Heapsort

Also called heap sort; introsort falls back to it. The cheat-sheet gives it last under Sorting, as an in-place C++ loop that first sifts the array into a max-heap and then repeatedly swaps the maximum to the end.

In one breath

Read the array as a binary tree (the children of index i are 2i + 1 and 2i + 2) and rearrange it so every parent is at least as big as its children. Now the largest value sits at a[0]. Swap it to the last slot, treat the heap as one shorter, let the new root sink back into place, and repeat. The sorted tail grows from the right while the heap shrinks.

Worked example: a = [38, 27, 43, 3, 9, 82, 10]

Only indices 2, 1 and 0 have children, so the build phase sifts those three, last one first. Small numbers are the array indices.

Why building the heap is O(n), not O(n log n)

A node sinks at most its height (the levels below it), and most nodes are near the bottom: half are leaves and never move, a quarter can drop one level, an eighth two. Adding that up bounds the whole build:

In Python

def sift_down(a, root, end):
    while (child := 2 * root + 1) < end:
        if child + 1 < end and a[child] < a[child + 1]:
            child += 1                    # pick the bigger child
        if a[root] >= a[child]:
            break                         # heap property holds
        a[root], a[child] = a[child], a[root]
        root = child                      # follow it down

def heapsort(a):
    n = len(a)
    for start in range(n // 2 - 1, -1, -1):   # build: O(n)
        sift_down(a, start, n)
    for end in range(n - 1, 0, -1):           # extract: O(n log n)
        a[0], a[end] = a[end], a[0]           # max goes to its place
        sift_down(a, 0, end)
    return a

print(heapsort([38, 27, 43, 3, 9, 82, 10]))
# → [3, 9, 10, 27, 38, 43, 82]

The source runs both phases in one while loop (start counts down first, then end); it is correct and matches this version swap for swap on a. Two loops here make the phases visible.

Time O(n log n) · Space O(1). Building is O(n) (above), then n − 1 sift-downs from the root each walk at most ⌊log₂ n⌋ levels. That bound holds for every input, sorted or not, and the only extra memory is a few indices.

Why it beats the alternatives (when memory and the worst case matter)

✗ Quicksort

Fastest here (0.031 s), in place, but a bad pivot sequence gives n(n − 1)/2 comparisons: sorted input with a last-element pivot. No guarantee.

✗ Merge sort

Guaranteed O(n log n) and stable, but the merge needs an extra n-element buffer: 8 MB for 10⁶ floats.

✗ Selection sort

Same idea, "move the max to the end", but finds the max by scanning: 21 comparisons on a, 49,995,000 for n = 10⁴ against heapsort's 235,415.

✓ Heapsort

O(n log n) on every input and O(1) extra space; neither alternative has both. That's why introsort switches to heapsort when quicksort's recursion gets too deep.

So when do you use it?

Mostly as a safety net. Introsort (Musser, 1997) runs quicksort and switches to heapsort once the recursion depth passes about 2 log₂ n, so it keeps quicksort's speed and heapsort's worst case. Use heapsort alone when memory is fixed and a worst case of n² is not acceptable.

It's the wrong pick when you need stability (use merge sort or Timsort) or raw speed on large arrays. Our reading of the 3.1× gap: a sift-down jumps from index i to 2i + 1, so at n = 10⁶ it touches about 20 levels and, beyond the first few, each step lands on a different cache line, while quicksort's partition scans memory in order. In Python, call sorted(); for the k largest, heapq.nlargest keeps a heap of k, O(n log k).
