Knuth–Morris–Pratt

Also called KMP; its table is the prefix function (π), the failure function, or lps ("longest proper prefix that is also a suffix"). The source guide uses it twice under Searching: to find every match of a pattern, and inside Shortest Palindrome.

In one breath

When a naive search hits a mismatch, it slides the pattern one step and re-reads text it has already seen. KMP first works out, for every prefix of the pattern, how much of what just matched could also be the start of a new match. On a mismatch it keeps that much and carries on, so the pointer into the text never moves backwards.

The one idea: a border

A border of a string is a proper prefix that is also a suffix. lps[j] is the length of the longest border of p[0..j]. For the whole pattern ABABCABAB it's ABAB, length 4:

Worked example: build lps for ABABCABAB

t is the length of the border found so far. Compare the new character p[j] with p[t], the character just after that border. Equal: the border grows by one. Not equal: shrink to the next shorter border, t = lps[t − 1], and try again.

The source's other use: Shortest Palindrome, s = aacecaaa

You may only add characters in front of s. The part you don't have to add is the longest palindromic prefix of s. Glue s + "#" + reverse(s): its longest border is a prefix of s that equals a suffix of reverse(s), which is exactly a palindromic prefix.

s # rev(s)
aacecaaa#aaacecaa
lps
01000122012234567
k = lps[-1] = 7 → aacecaa is the longest palindromic prefix add reverse(s)[:8 − 7] = "a" in front → "a" + "aacecaaa" = aaacecaaa

Why the #: without it a border can run across the join. For s = aaa, "aaaaaa" has border 5 > len(s) = 3, and the answer breaks; with "aaa#aaa" it's 3, correct. The separator must be a character that never appears in s.

In Python

def build_lps(p):
    lps, t = [0] * len(p), 0   # t = length of current border
    for j in range(1, len(p)):
        while t and p[j] != p[t]:
            t = lps[t - 1]        # next shorter border
        if p[j] == p[t]:
            t += 1
        lps[j] = t
    return lps

def kmp_search(p, s):
    lps, j, out = build_lps(p), 0, []
    for k, c in enumerate(s):      # k never goes back
        while j and c != p[j]:
            j = lps[j - 1]
        if c == p[j]:
            j += 1
        if j == len(p):
            out.append(k - j + 1)
            j = lps[j - 1]        # allow overlaps
    return out

def shortest_palindrome(s):
    r = s[::-1]
    k = build_lps(s + "#" + r)[-1]  # longest palindromic prefix
    return r[:len(s) - k] + s

print(build_lps("ABABCABAB"))
print(kmp_search("ABABCABAB", "ABABDABACDABABCABAB"))
print(shortest_palindrome("aacecaaa"))
# → [0, 0, 1, 2, 0, 1, 2, 3, 4]
# → [10]
# → aaacecaaa

The source's C++ is correct. Its KMP stores the table shifted by one (lps[j + 1], falling back with t = lps[t]) while Shortest Palindrome uses the 0-based form above; the values are the same. It joins with a space rather than #, which is fine because the problem's s has only lowercase letters.

Time O(n + m) · Space O(m). t (or j) rises by at most 1 per character and every fall-back lowers it by at least 1, so the fall-backs over the whole run can't outnumber the rises: at most m − 1 of them building the table and n while searching, so ≤ 2n comparisons in the search.

Why it beats the alternatives

✗ Naive: try every start

Simple and fine on random text, but it re-reads characters after every mismatch: 990,100 comparisons for a×99 + b in a×10,000, where KMP needs 19,901.

✗ Rabin–Karp (rolling hash)

Compares hashes of windows in O(1) each. Expected O(n + m), but every hash hit still needs a character check, and input built against a fixed, known hash can make many windows collide.

✗ Boyer–Moore(–Horspool)

Matches right to left and skips ahead on a bad character, so on long patterns over a big alphabet it can read far fewer than n characters. The simple Horspool variant is O(nm) in the worst case, and it needs m characters of text in view at once.

✓ KMP

Guaranteed O(n + m) with no hashing and no luck, reads the text once left to right, and its lps table answers other border questions: palindromic prefixes, or a string's smallest period m − lps[m − 1] (9 − 4 = 5 for ABABCABAB).

Should you write KMP in real code?

Usually not in Python: p in s and s.find(p) run in C, and since 3.10 CPython switches to the Crochemore–Perrin two-way algorithm for long needles to avoid quadratic behaviour. Write KMP when an interview asks for a linear worst case, when the text arrives as a stream you can't rewind, or when you need the lps table itself (Shortest Palindrome, repeated-substring checks).

It's the wrong tool for many patterns at once (use Aho–Corasick, KMP's multi-pattern cousin), for many different queries against one fixed text (build a suffix automaton or suffix array once), or for "is there any repeated substring of length L" (rolling hash plus binary search).
