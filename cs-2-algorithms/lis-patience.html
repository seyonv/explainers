Longest increasing subsequence

Also called LIS, patience sorting, or the tails-array trick. Keep the smallest possible ending value for every length, and binary-search where each new number goes. The source guide uses it under Binary Search to solve Russian Doll Envelopes.

Prime · 2 minutes before you read

The problem: The obvious longest-increasing-subsequence DP compares every pair: 5 × 10⁹ steps at n = 10⁵. Most of that information is useless: for each length you only need to know the smallest value a run of that length can end with.

Where it fits: Third binary-search card. Binary search on the answer searched a predicate; here you binary search an array you maintain yourself (tails), kept sorted by an invariant. The O(n²) DP it replaces returns in cs-3's recursion-to-DP card.

In one breath

Walk the list once and keep tails, where tails[k] is the smallest number that can end an increasing subsequence of length k + 1. Each new number either extends the longest one (append) or gives some length a smaller ending (overwrite). tails stays sorted, so finding the slot is a binary search, and its final length is the answer.

Worked example: nums = [10, 9, 2, 5, 3, 7, 101, 18] → 4

Patience sorting, dealt left to right from the list. Grey cards were covered; green cards are the current pile tops. The tops always increase left to right, which is what makes the binary search legal.

In Python

import bisect

def lis_length(nums):
    tails = []  # tails[k]: smallest tail of any run of length k+1
    for x in nums:
        i = bisect.bisect_left(tails, x)  # first tail >= x
        if i == len(tails):
            tails.append(x)       # x extends the longest run
        else:
            tails[i] = x          # x is a smaller tail for length i+1
    return len(tails)

def max_envelopes(envelopes):
    # width up; height DOWN inside a width, so equal widths can't chain
    order = sorted(envelopes, key=lambda e: (e[0], -e[1]))
    return lis_length([h for _, h in order])

print(lis_length([10, 9, 2, 5, 3, 7, 101, 18]))        # → 4
print(max_envelopes([[5, 4], [6, 4], [6, 7], [2, 3]]))  # → 3

Time O(n log n) · Space O(n). Each of the n numbers does one binary search over at most n tails, about log₂ n comparisons, and one O(1) write. tails grows to the answer's length, at most n.

Russian doll envelopes: envelopes = [[5, 4], [6, 4], [6, 7], [2, 3]] → 3

An envelope fits inside another only if it is strictly smaller in both width and height. Sort by width, then the question is just "longest strictly increasing run of heights". The catch is equal widths: [6, 7] can't hold [6, 4], yet if 4 came before 7 a plain height-LIS would count them as a chain. Sorting heights descending within a width makes any two same-width envelopes a decreasing pair, so they can never both be in an increasing run.

Why it beats the alternatives

✗ Try every subset

Check each of the 2ⁿ subsequences for being increasing. 256 for this card's n = 8; hopeless by n = 40 (about 1.1 × 10¹²).

✗ O(n²) dynamic programming

best[j] = 1 + max(best[i]) over earlier i with a smaller value. Correct and easy to extend, but n(n − 1)/2 comparisons: 28 here, 4,999,950,000 for n = 10⁵.

✗ LCS with the sorted copy

The LIS is the longest common subsequence of the list and sorted(set(list)). True, but the LCS table is n × n, so it's O(n²) time and, done naively, O(n²) memory.

✓ Tails array + binary search

O(n log n) with a 6-line loop. At most n · ⌈log₂(n + 1)⌉ = 1,700,000 comparisons for n = 10⁵, about 2,900× fewer than the DP.

Is it always the tool?

It gives the length. To print an actual subsequence, store for each number the index of the tail it sat on (a parent pointer) and walk back from the last pile; code/lis-patience.py does this and returns [2, 3, 7, 18]. Reading tails directly is the classic bug, as [3, 4, 1] → [1, 4] shows.

Use something else when the question changes shape. Counting how many LIS there are, or a weighted LIS (maximise the sum, not the count), breaks the "smaller tail is always better" argument: use the O(n²) DP, or index values and keep a Fenwick tree of best-so-far per value for O(n log n). For LIS inside a sliding window or with updates, a segment tree is the usual answer. These alternatives are standard practice, not from the source.

Understand and remember

  • For each length keep only the smallest possible ending value → a smaller end can be extended by anything the bigger end could → overwriting never loses an answer → tails[k] is the best tail for length k + 1
  • tails is strictly increasing (a length-(k + 2) run contains a length-(k + 1) run with a smaller end) → the slot for x is the first tail ≥ x → one binary search per element → O(n log n), about 2,900× fewer compares than the O(n²) DP at n = 10⁵
  • 2-D nesting needs strict increase in both → sort by width → then LIS on heights → but equal widths must never chain → sort their heights descending, so they form a decreasing run and can't both be picked
  • detail that matters bisect_left overwrites an equal tail (repeats can't chain: strictly increasing); bisect_right lands after it (repeats chain: non-decreasing) → one call decides which problem you solve

5 · Predict commit to an answer before revealing

Run the tails loop on [0, 8, 4, 12, 2, 10, 6, 14, 1, 9]. Predict the final tails array and whether it is itself an increasing subsequence of the input.

Reveal

tails ends as [0, 1, 6, 9], so the LIS length is 4. But it is not a subsequence: 1 appears at index 8, after 6 at index 6. The last overwrite (1 over 2) improved length 2's tail without touching the longer runs. A real LIS is [0, 2, 6, 9] (or [0, 4, 6, 9], among others).
