Counting during a merge

Also called inversion counting by merge sort, or the "sort and count" trick. The source guide puts two problems under Merge Sort that use it: Count of Smaller Numbers after Self and Reverse Pairs, each as a bottom-up C++ merge plus a Python SortedList version.

Prime · 2 minutes before you read

The problem: "For each element, how many smaller ones come after it?" asks about all n² pairs. Checking them is 5 × 10⁹ tests for n = 10⁵, and inserting into a sorted list shifts almost as much. You need a way to count whole blocks of pairs at once.

Where it fits: Right after merge sort, and it reuses its merge unchanged. It also finishes insertion sort's story: the inversions insertion sort removes one swap at a time are counted here in O(n log n).

In one breath

While merge sort merges a left block with a right block, every right element that goes out before a left element x is smaller than x and sat to its right in the original array. So when x is placed, the number of right elements already placed is exactly how many smaller numbers after x this merge has found. Every pair of positions meets in exactly one merge, so adding those numbers up counts each pair once, in O(n log n).

Second problem: Reverse Pairs, nums = [1, 3, 2, 3, 1] → 2

A reverse pair is i < j with nums[i] > 2·nums[j]. That test is not the merge's own comparison, so run a separate count pass first: both halves are already sorted, so as the left element grows, the right pointer only moves forward.

In Python

import heapq

def count_smaller(nums):
    n = len(nums)
    idx = list(range(n))           # indices, sorted by value per block
    counts = [0] * n
    width = 1
    while width < n:
        for lo in range(0, n, 2 * width):
            mid, hi = min(lo + width, n), min(lo + 2 * width, n)
            left, right = idx[lo:mid], idx[mid:hi]
            out, j = [], 0
            for i in left:
                while j < len(right) and nums[right[j]] < nums[i]:
                    out.append(right[j])   # smaller one jumps ahead
                    j += 1
                counts[i] += j             # j smaller ones from right
                out.append(i)
            idx[lo:hi] = out + right[j:]
        width *= 2
    return counts

def reverse_pairs(nums):
    a, n, total = list(nums), len(nums), 0
    width = 1
    while width < n:
        for lo in range(0, n, 2 * width):
            mid, hi = min(lo + width, n), min(lo + 2 * width, n)
            j = mid
            for i in range(lo, mid):       # count pass: both sorted
                while j < hi and a[i] > 2 * a[j]:
                    j += 1
                total += j - mid
            a[lo:hi] = heapq.merge(a[lo:mid], a[mid:hi])
        width *= 2
    return total

print(count_smaller([5, 2, 6, 1]))       # → [2, 1, 1, 0]
print(reverse_pairs([1, 3, 2, 3, 1]))    # → 2

The source's Python versions use sortedcontainers.SortedList, a third-party package (pip install sortedcontainers), not the standard library. Its C++ merges are correct; this rewrite keeps their bottom-up widths and uses strict < so equal values are not counted as smaller.

Time O(n log n) · Space O(n). There are ⌈log₂ n⌉ widths and each moves every element once; the count pass adds one more forward sweep per merge, because j never moves back. The extra space is the merge buffer plus the counts.

Why it beats the alternatives

✗ Check every pair

n(n − 1)/2 tests: 6 for nums, 4,999,950,000 for n = 10⁵. Always O(n²), even on sorted input.

✗ bisect.insort from the right

Standard library and short. The binary search is O(log n), but each insert shifts the list: about n(n − 1)/4 = 2,499,975,000 element moves on average for n = 10⁵ (O(n²)).

✗ SortedList (the source's Python)

O(log n)-ish inserts, so it scales, but it's a third-party package: not in the standard library, and not always allowed in an interview or on a judge.

✓ Count during the merge

O(n log n), standard library only, and it gives per-element counts, totals and variants like 2× from one pass: 17 widths × 10⁵ ≈ 1,700,000 element moves for n = 10⁵.

Is the merge always the way?

It fits any "count pairs i < j with a condition that is monotone in the values" problem: inversions, Count Smaller, Reverse Pairs, and count-of-range-sums on prefix sums (these uses beyond the two source problems are standard practice, not from the source). A condition like nums[i] > 2·nums[j] needs its own count pass before the merge; a plain inversion can be counted inside the merge.

A Fenwick tree over value ranks is just as fast, O(n log n), and is the better choice when elements arrive one at a time or when you also need updates; scan from the right, query "how many ranks below mine", then add yourself. It needs the values compressed to ranks first (code/ has both, checked against each other). For small n, or when sortedcontainers is allowed, the one-loop SortedList version is the quickest to write.

Understand and remember

  • Left and right halves each sorted, left items earlier in the array → right items output before left item x are smaller and after it → j − mid at x's placement = its smaller-after count from this merge
  • Two positions are separated by exactly one merge (the level where they first join) → each pair is counted once → summing over ⌈log₂ n⌉ levels gives all inversions in O(n log n) (4 for [5, 2, 6, 1]; 11 for a)
  • A condition that isn't the sort order (x > 2y) → can't piggyback on the merge compare → but both halves are sorted, so the right pointer only moves forward as x grows → one extra linear count pass per merge, still O(n log n)
  • detail that matters Counts belong to original positions → merge a list of indices keyed by value → otherwise you know how many but not whose
  • detail that matters Strict < when pulling right items → equal values aren't counted as smaller

  1. concept Explain why the merge can count inversions in O(n log n) when any method that checks pairs one at a time is O(n²).
    Check
    • at placement, one number j − mid covers a whole block of pairs at once
    • sortedness of both halves guarantees every one of those j pairs is an inversion
    • each merge is linear and there are log n levels
  2. mechanism Walk through the width-2 merge of [2, 5] + [1, 6] in Count Smaller for [5, 2, 6, 1]: in what order do items come out, what does each left item gain, and what are the final counts?
    Check
    • 1 (right) goes first; then 2 is placed with j = 1 → +1; then 5 with j = 1 → +1; then 6 copied
    • counts go from [1, 0, 1, 0] to [2, 1, 1, 0]
    • the 6 on the right is bigger than everything left, so it adds nothing
  3. tradeoff Elements arrive one at a time and you need "how many earlier values are larger than this one" after each arrival. Merge-count, Fenwick tree, or bisect.insort? Cost of each?
    Check
    • merge-count needs the whole array up front: offline only
    • Fenwick tree over value ranks: O(log n) per arrival, but values must be compressed to ranks first
    • bisect.insort: O(log n) search but O(n) shift per insert, so O(n²) total

4 · Compare against what you already know

vs Fenwick tree (binary indexed tree): Both count smaller-after-self in O(n log n). What does each structure store, which design choice makes one offline and the other online, and how does each fail?

Check
  • the merge stores nothing extra beyond the buffer; it counts during a divide-and-conquer pass over the whole array
  • the Fenwick tree stores prefix counts over value ranks and answers one query per element as you scan
  • merge fails when data streams in or changes; Fenwick fails without rank compression on wide value ranges

vs Prefix sums with an ordered set: Count-of-range-sums can be done by merge-counting prefix sums, while the rectangle problem keeps prefix sums in a sorted set. What question does each answer, and why does one need order-statistics per step?

Check
  • merge-count answers "how many pairs": a total, computed offline over all prefix sums
  • the sorted set answers "which earlier prefix is the best partner for this one": an argmin per step
  • the best-partner query needs a searchable set at each step; a count can be batched inside merges

Reveal

3. A reverse pair needs nums[i] > 2·nums[j] with i < j. Only the final 1 is small enough to be the right side: 4, 3 and 5 are all > 2·1 = 2, while 2 > 2 fails. No other pair works (4 > 2·3? no).
