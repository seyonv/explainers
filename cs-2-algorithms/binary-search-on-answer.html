Binary search on the answer

Also called parametric search, bisecting the answer space, or "binary search on a monotone predicate". The source guide's Binary Search section uses it for Find kth Smallest Pair Distance (search the distance itself) and Find Minimum in Rotated Sorted Array (search an index with duplicates), both in C++.

Prime · 2 minutes before you read

The problem: "The k-th smallest pair distance" ranges over 5 × 10⁷ pairs at n = 10⁴, far too many to list or sort. But checking a single candidate answer d ("are at least k pairs within d?") is one cheap linear scan. If those checks go no, no, …, yes, yes, you can binary search the answer itself.

Where it fits: First binary-search card, and the template the next three reuse (median cut, LIS tails, prefix-set search). Its predicate is the two-pointer pair count from the previous card; later, rolling hash binary searches a substring length the same way.

In one breath

You don't need a sorted array to binary search; you need a yes/no question whose answers go no, no, …, no, yes, …, yes as x grows. Keep a range [lo, hi] that always holds the first yes, ask the question at the middle, and throw away the half that can't hold it. For k-th pair distance the question is "are there at least k pairs within distance d?", and the first d that says yes is the answer.

The predicate: nums = [1, 6, 1], k = 3

The one template, and its invariant

def first_true(lo, hi, ok):
    # invariant: ok(hi) is True, ok(x) is False for every x < lo
    while lo < hi:
        mid = (lo + hi) // 2      # floor: mid < hi, so hi = mid shrinks
        if ok(mid):
            hi = mid              # mid works: answer is mid or left
        else:
            lo = mid + 1          # mid fails: answer is right of mid
    return lo                     # lo == hi: the first True

Why the answer is a real distance: count(d) only changes at actual pair gaps, so the first d where it reaches k is one of them.

In Python

def pairs_within(a, d):
    """Pairs i < j of sorted a with a[j] - a[i] <= d. Two pointers."""
    count = j = 0
    for i in range(len(a)):
        while j < len(a) and a[j] <= a[i] + d:
            j += 1
        count += j - i - 1        # partners of i: i+1 .. j-1
    return count

def smallest_distance_pair(nums, k):
    a = sorted(nums)
    return first_true(0, a[-1] - a[0],
                      lambda d: pairs_within(a, d) >= k)

print(smallest_distance_pair([1, 3, 1], 1))   # → 0
print(smallest_distance_pair([1, 6, 1], 3))   # → 5

The source starts its count at −n and adds j − i, which counts i as its own partner once per i; j − i − 1 is the same total. bisect.bisect_left(range(lo, hi + 1), True, key=ok) (Python 3.10+) is this template built in.

Time O(n log n + n log W) · Space O(n). W = max − min. Sorting is n log n; each of the log W probes is one two-pointer pass, and j only moves forward, so a pass is at most 2n steps. The sorted copy is the O(n).

Rotated minimum, and why duplicates cost O(n)

Here the predicate is "is index x at or past the drop?", and the test is to compare nums[mid] with nums[hi]: bigger means the drop is to the right of mid, smaller means mid..hi climbs so the minimum is mid or left. Equal tells you nothing, so the source shrinks hi by one.

Why it beats the alternatives (k-th pair distance)

✗ List every pair, sort

O(n² log n) time and O(n²) memory: n = 10⁴ makes 49,995,000 distances before you read one.

✗ Heap of pairs

Pop the smallest gap k times from a heap seeded with neighbours: O((n + k) log n). Fine for small k, but k can be ≈ 5·10⁷ at n = 10⁴.

✗ Try d = 0, 1, 2, …

Same count, but linear in the answer: up to 10⁶ + 1 passes of 2·10⁴ steps ≈ 2·10¹⁰ when values reach 10⁶.

✓ Bisect d

20 passes instead of 10⁶ + 1, each O(n), with O(1) extra memory past the sort: ≈ 4·10⁵ pointer moves for the same input.

When does it apply?

Look for "minimise the maximum", "maximise the minimum", "smallest x such that…", or a k-th smallest over something too big to list (pair distances, a sorted matrix, a multiplication table). If you can write a fast check for "is the answer ≤ x?" and that check is monotone, bisect x. Capacity to ship in D days and Koko eating bananas are the same shape (standard practice, not in the source).

It's the wrong tool when the check isn't monotone (count == k above, or a rotated array with duplicates, where it degrades to O(n)), when the check itself is as slow as solving directly, or when the answer is a real number: lo never meets hi, so run a fixed number of rounds for the precision you need, or use Newton's method when the function is smooth.

Understand and remember

  • Monotone yes/no test over candidate answers → the no/yes boundary is unique → keep [lo, hi] containing the first yes, test the middle, discard the half that can't hold it → ⌈log₂(range)⌉ tests instead of one per candidate
  • Answer space can be values, not indices → k-th pair distance searches d ∈ [0, max − min] → each test is one O(n) two-pointer count → O(n log W) after the sort (20 passes vs 10⁶ + 1 for W = 10⁶)
  • The half you discard must provably lack the answer → with duplicates in a rotated array, nums[mid] == nums[hi] says nothing about the side → only hi −= 1 is safe → worst case O(n) (999 steps for 1,000 equal values vs 10 when distinct)
  • detail that matters Floor mid pairs with hi = mid (mid < hi, so the range shrinks) and lo = mid + 1 → the other pairing (lo = mid with floor) can stall forever → always match the rounding to the side that keeps mid

Reference only

  • bisect.bisect_left(range(...), True, key=ok) on Python 3.10+
  • the source's −n + Σ(j − i) count
  • the heap-of-pairs O((n + k) log n) alternative
  • Koko bananas / ship-in-D-days as the same shape

  1. concept Explain why you can binary search for the k-th smallest pair distance without ever sorting the pair distances.
    Check
    • count(d) = pairs within d never decreases as d grows, so count(d) ≥ k flips from no to yes once
    • the first yes is exactly the k-th smallest distance
    • each test is a two-pointer count over the sorted values, not over pairs
  2. mechanism Walk through the search on nums = [1, 6, 1], k = 3: each (lo, hi, mid), the count, and the final answer. Why is 5 never tested directly?
    Check
    • sorted [1, 1, 6], range [0, 5]
    • mid 2: count 1 < 3 → lo = 3; mid 4: count 1 → lo = 5
    • lo == hi = 5 → answer 5
    • ok(hi) holds from the start because every pair fits within max − min, so the loop can end on it untested
  3. tradeoff An interviewer asks for the k-th smallest pair distance where k is always 1 or 2. Is binary search on the answer still the best choice? Compare with a heap of neighbouring gaps.
    Check
    • for tiny k, sort then pop k gaps from a heap seeded with neighbours: O(n log n + k log n)
    • binary search costs O(n log n + n log W) regardless of k
    • for small k the heap (or just scanning adjacent gaps for k = 1) is simpler; binary search wins when k can be ≈ n²/2

5 · Predict commit to an answer before revealing

For nums = [1, 6, 1] and k = 2, predict what binary search on the answer returns, and what would happen if you had used the predicate count(d) == k instead.

Reveal

5. The distances are 0, 5, 5; count(d) is 1 for d < 5 and 3 at d = 5, so the first d with count ≥ 2 is 5: the 2nd smallest distance. With count(d) == 2 the predicate is never true (the count jumps from 1 to 3), so there's no boundary to find; the search would return garbage.
