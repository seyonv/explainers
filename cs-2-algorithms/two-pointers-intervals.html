Two pointers and intervals

Also called the two-index technique, a sliding window or caterpillar (same direction), and a sweep line (intervals). The source guide has no heading for it, but its solutions lean on it: the counting loop in kth smallest pair distance, Minimum Window Substring, and the event sweep in The Skyline Problem.

Prime · 2 minutes before you read

The problem: Pair and window questions look like n² work: every pair, every window. On sorted data most of those candidates can be ruled out by a single comparison, but only if you move your indices in a way that never needs to go back.

Where it fits: Opens the Searching part because the next card's predicate uses its same-direction count. It builds on sorting (the whole technique needs order) and comes back in greedy wildcard matching and the source's skyline sweep.

Builds on: Sliding window with counts · Merge sort

You'll meet: opposite-end pointers (two-sum) same-direction pointers (window, pair counts) sort by start, then sweep +1/−1 events and tie order at most 2n pointer moves

By the end: Pick the right pointer shape for a problem, state the invariant that makes each move safe, and sweep intervals correctly at ties.

In one breath

On sorted data, one comparison can rule out a whole row of candidates at once. So instead of trying all n² pairs, keep two indices and only ever move them forward (or inward). Each index crosses the array once, so the whole scan is O(n). Intervals are the same idea: sort by start, then sweep left to right.

2 · Same direction: count pairs with a[j] − a[i] ≤ 10 in the same a

In Python

def two_sum_sorted(a, target):
    lo, hi = 0, len(a) - 1
    while lo < hi:
        s = a[lo] + a[hi]
        if s == target: return lo, hi
        if s < target: lo += 1   # a[lo] is too small for anyone
        else: hi -= 1             # a[hi] is too big for anyone

def pairs_within(a, d):         # a sorted
    count, j = 0, 0
    for i in range(len(a)):
        while j < len(a) and a[j] - a[i] <= d:
            j += 1                # j never moves back
        count += j - i - 1
    return count

def merge(intervals):
    out = []
    for s, e in sorted(intervals):
        if out and s <= out[-1][1]:
            out[-1][1] = max(out[-1][1], e)
        else:
            out.append([s, e])
    return out

def min_rooms(meetings):
    ev = sorted([(s, 1) for s, _ in meetings] +
                [(e, -1) for _, e in meetings])  # ends first
    rooms = best = 0
    for _, delta in ev:
        rooms += delta
        best = max(best, rooms)
    return best

Time O(n) · Space O(1) for the two scans on sorted input: each pointer only moves one way, so there are at most 2n moves. O(n log n) for merge and meeting rooms, all of it the sort; the sweep after it is O(n). Merge treats touching intervals ([1,3], [3,5]) as overlapping; meeting rooms treats a meeting as ending just before its end time.

Why it beats the alternatives (two-sum on sorted input)

✗ Every pair

Two nested loops: n(n − 1)/2 sums, 21 for a, about 5 × 10¹¹ for n = 10⁶. Ignores that the array is sorted.

✗ Binary search per value

For each a[i], bisect for target − a[i]. Correct, but O(n log n): it re-searches ground an earlier step already ruled out.

✗ Hash set of seen values

O(n) time, but O(n) extra memory, and it only answers "equals". It can't count pairs within a distance d, a range question.

✓ Two pointers

O(n) time and O(1) memory: 5 sums for a instead of 21. The same one-way scan also answers range questions, like the 4 pairs within 10.

Is it always the right tool?

No. It needs order: sorted values, or a window condition that stays true as the window shrinks. On unsorted input with the original indices wanted (classic two-sum), sorting costs O(n log n) and loses the indices, so a hash map in one pass wins. A same-direction window breaks when values can be negative: for "shortest subarray with sum ≥ k", growing the window can lower the sum, so use prefix sums with a monotonic deque instead.

For intervals, the event sweep gives the peak count only. To say which room each meeting gets, keep a min-heap of end times (the source's skyline does the same with a heap of heights). And when intervals arrive one at a time with queries in between, use an ordered structure or an interval tree rather than re-sorting.

Understand and remember

  • Sorted input → if a[lo] + a[hi] > target, a[hi] is too big even with the smallest live partner → drop it; symmetric for too small → each step discards one candidate forever → ≤ n − 1 steps instead of n(n − 1)/2 pairs (5 vs 21 on a)
  • Same-direction scan: as a[i] grows, the first a[j] > a[i] + d can only move right → j never restarts → both pointers cross the array once → O(n) total moves (14, not 49, on a)
  • Sort intervals by start → any interval that overlaps the current block must start before its end → one sweep with a running end merges them; +1/−1 events with ends before starts at ties give the peak room count
  • detail that matters Window validity must be monotone (shrinking a valid window keeps it valid) → true for non-negative values → with negatives, growing can lower the sum → use prefix sums with a monotonic deque or an ordered set instead

  1. concept Explain why two pointers find a sorted two-sum in O(n) without ever missing the answer.
    Check
    • invariant: if a valid pair exists, both indices are in [lo, hi]
    • a sum too big means a[hi] can't pair with anything ≥ a[lo], so dropping it is safe (and symmetric for too small)
    • each step shrinks the range by one, so at most n − 1 steps
  2. mechanism Walk through counting pairs with a[j] − a[i] ≤ 10 in a = [3, 9, 10, 27, 38, 43, 82] at i = 3 and i = 4: where does j stop, and what is added?
    Check
    • i = 3 (27): j stops at 4 because 38 > 37; partners j − i − 1 = 0
    • i = 4 (38): j moves to 6 because 82 > 48; partner 43 → +1
    • running total goes from 3 to 4
  3. tradeoff Classic two-sum: unsorted input, and you must return the original indices. Two pointers or a hash map? Cost of each, and what would flip your choice?
    Check
    • two pointers need a sort: O(n log n) and you lose the original indices unless you carry them
    • hash map: one pass, O(n) time, O(n) memory
    • flip to two pointers when the data is already sorted, memory is tight, or the question is a range (pairs within d), which a hash map can't answer
