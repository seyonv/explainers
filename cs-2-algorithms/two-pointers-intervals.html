Two pointers and intervals

Also called the two-index technique, a sliding window or caterpillar (same direction), and a sweep line (intervals). The cheat-sheet has no heading for it, but its solutions lean on it: the counting loop in kth smallest pair distance, Minimum Window Substring, and the event sweep in The Skyline Problem.

In one breath

On sorted data, one comparison can rule out a whole row of candidates at once. So instead of trying all n² pairs, keep two indices and only ever move them forward (or inward). Each index crosses the array once, so the whole scan is O(n). Intervals are the same idea: sort by start, then sweep left to right.

2 · Same direction: count pairs with a[j] − a[i] ≤ 10 in the same a

In Python

def two_sum_sorted(a, target):
    lo, hi = 0, len(a) - 1
    while lo < hi:
        s = a[lo] + a[hi]
        if s == target: return lo, hi
        if s < target: lo += 1   # a[lo] is too small for anyone
        else: hi -= 1             # a[hi] is too big for anyone

def pairs_within(a, d):         # a sorted
    count, j = 0, 0
    for i in range(len(a)):
        while j < len(a) and a[j] - a[i] <= d:
            j += 1                # j never moves back
        count += j - i - 1
    return count

def merge(intervals):
    out = []
    for s, e in sorted(intervals):
        if out and s <= out[-1][1]:
            out[-1][1] = max(out[-1][1], e)
        else:
            out.append([s, e])
    return out

def min_rooms(meetings):
    ev = sorted([(s, 1) for s, _ in meetings] +
                [(e, -1) for _, e in meetings])  # ends first
    rooms = best = 0
    for _, delta in ev:
        rooms += delta
        best = max(best, rooms)
    return best

Time O(n) · Space O(1) for the two scans on sorted input: each pointer only moves one way, so there are at most 2n moves. O(n log n) for merge and meeting rooms, all of it the sort; the sweep after it is O(n). Merge treats touching intervals ([1,3], [3,5]) as overlapping; meeting rooms treats a meeting as ending just before its end time.

Why it beats the alternatives (two-sum on sorted input)

✗ Every pair

Two nested loops: n(n − 1)/2 sums, 21 for a, about 5 × 10¹¹ for n = 10⁶. Ignores that the array is sorted.

✗ Binary search per value

For each a[i], bisect for target − a[i]. Correct, but O(n log n): it re-searches ground an earlier step already ruled out.

✗ Hash set of seen values

O(n) time, but O(n) extra memory, and it only answers "equals". It can't count pairs within a distance d, a range question.

✓ Two pointers

O(n) time and O(1) memory: 5 sums for a instead of 21. The same one-way scan also answers range questions, like the 4 pairs within 10.

Is it always the right tool?

No. It needs order: sorted values, or a window condition that stays true as the window shrinks. On unsorted input with the original indices wanted (classic two-sum), sorting costs O(n log n) and loses the indices, so a hash map in one pass wins. A same-direction window breaks when values can be negative: for "shortest subarray with sum ≥ k", growing the window can lower the sum, so use prefix sums with a monotonic deque instead.

For intervals, the event sweep gives the peak count only. To say which room each meeting gets, keep a min-heap of end times (the source's skyline does the same with a heap of heights). And when intervals arrive one at a time with queries in between, use an ordered structure or an interval tree rather than re-sorting.
