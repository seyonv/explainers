Insertion sort

Also called the card-player's sort; in Timsort it runs as binary insertion sort. The source guide gives it first under Sorting, as a three-line C++ loop that swaps each new element left until it fits.

Prime · 2 minutes before you read

The problem: Every sort has to decide how much work nearly sorted input deserves. A sort that ignores existing order does n² or n log n work on data that is only a few swaps from done, and on tiny arrays the clever sorts' bookkeeping costs more than the sorting.

Where it fits: First sort of the course. It builds on cs-1's big-O, and its swap count (inversions) comes back in counting during a merge and in the n log n card's compare table.

Builds on: Big-O and amortized O(1)

In one breath

Keep the left part of the array sorted. Take the next element (the key) and swap it leftwards past every bigger neighbour; when the neighbour is not bigger, it has landed. Each swap fixes exactly one out-of-order pair, so the work is the number of such pairs: none for sorted input, all of them for reversed input.

Why the count is the inversion count

An inversion is a pair of positions i < j with a[i] > a[j]. Swapping two adjacent out-of-order neighbours fixes exactly that one pair and leaves every other pair's order alone, so each swap removes one inversion, and the loop stops only at zero. For a random order each of the n(n − 1)/2 pairs is inverted with probability ½:

compares= inv(a)one per swap + (n−1)−fone stop per key E[inv]= n(n−1)4
inv(a)number of out-of-order pairs11 for a · 0 sorted · 21 reversed fkeys that slid all the way to index 0 (no stopping compare)2 for a (27 and 3) E[inv]average over random orders6,248,750 for n = 5,000

n = 5,000: 5,000 × 4,999 / 4 = 6,248,750 swaps on average; reversed input needs 12,497,500.

In Python

def insertion_sort(a):
    a = list(a)
    swaps = 0
    for i in range(1, len(a)):
        j = i
        while j > 0 and a[j - 1] > a[j]:   # left neighbour too big
            a[j - 1], a[j] = a[j], a[j - 1]
            j -= 1                         # decrement after the swap
            swaps += 1
    return a, swaps

print(insertion_sort([38, 27, 43, 3, 9, 82, 10]))
# → ([3, 9, 10, 27, 38, 43, 82], 11)

The source writes swap(a[j], a[--j]), which relies on C++ evaluating the left argument before --j. That order is unspecified (clang warns -Wunsequenced); if --j runs first, a[j − 1] is swapped with itself. It sorts correctly under clang; the version here decrements after the swap.

Time O(n + inv) · Space O(1). Best O(n) on sorted input, average and worst O(n²), because the work is one swap per inversion plus one stop per key. It sorts in place, and it is stable: > (not >=) means a key never jumps over an equal one.

Why it beats the alternatives (on small or nearly sorted input)

✗ Selection sort

Always scans the whole unsorted part: 21 compares on a, and still 21 on sorted input. Only 5 swaps, so it wins only when writes are costly.

✗ Bubble sort

Also one adjacent swap per inversion (11 on a), but it rescans the array each pass: 20 compares with the early-exit check, against 15.

✗ Merge sort or quicksort

O(n log n), but on a handful of elements the recursion, index bookkeeping and extra buffer cost more than the few moves insertion sort makes.

✓ Insertion sort

15 compares on a, 6 on sorted input. In place, stable and online (it can take elements as they arrive). That's why CPython's Timsort uses it for every run shorter than minrun (32–64).

So when do you use it?

Inside other sorts, mostly. CPython's Timsort extends each short run to minrun (between 32 and 64 elements) with binary insertion sort, and a list under 64 elements is sorted that way outright. Binary search cuts the compares to about log₂ i per key, but the shifts stay O(n²), which is fine at that size. listsort.txt adds that comparisons are expensive in Python, which is why saving them matters more than saving moves.

Don't use it on large arrays in arbitrary order: a random list of 5,000 took 0.828 s against 0.00026 s for sorted(). In Python just call sorted() or list.sort(); they already adapt to nearly sorted input and use insertion sort where it pays. To count inversions on large input, use the merge-sort trick in O(n log n) instead of counting swaps.

Understand and remember

  • Adjacent swap of an out-of-order pair → fixes exactly that pair, leaves all others' order unchanged → swaps = inversions → 0 on sorted input, n(n − 1)/2 on reversed, n(n − 1)/4 on average
  • Each key stops at the first neighbour that isn't bigger → one extra compare per key except those that slide to index 0 → compares = inv + (n − 1) − f (11 + 6 − 2 = 15 on a) → nearly sorted input costs about n
  • Work tracks disorder, not size → tiny or nearly sorted runs cost almost nothing, while n log n sorts pay recursion and buffer overhead → Timsort extends short runs to minrun (32–64) with binary insertion sort
  • detail that matters Strict a[j - 1] > a[j] → a key never jumps over an equal one → stable; >= breaks stability and adds swaps on duplicates

5 · Predict commit to an answer before revealing

Change the inner test to a[j - 1] >= a[j] and sort [2, 1, 2, 2]. Predict the swap count for each version and whether the relative order of the three 2s survives.

Reveal

Strict >: only the pair (2, 1) is an inversion, so 1 swap, and the 2s keep their order (stable). With >=, each later 2 also swaps past every equal 2 before it: 1 swap for the 1, then the third 2 jumps one 2 and the fourth jumps two, 4 swaps in total, and the 2s end up reversed. Equal keys are treated as inversions, so the sort is no longer stable and does extra work.
