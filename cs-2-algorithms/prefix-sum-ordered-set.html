Prefix sums with an ordered set

Also called "max subarray sum no larger than k", or prefix sums + lower_bound. The source guide uses it for Max Sum of Rectangle No Larger than k, under Binary Search: a C++ std::set of prefix sums, searched with lower_bound, once per pair of columns.

Prime · 2 minutes before you read

The problem: "The largest subarray sum that is at most k" breaks both standard tools: Kadane finds the unbounded maximum and can't honour a cap, and a sliding window fails once values can be negative. You need to find, at each step, the best earlier partner under a constraint.

Where it fits: Last Searching card. It combines prefix sums (a subarray is a difference of two) with the sorted-structure search from LIS, and it's the case where the two-pointer window from the start of this part stops working.

In one breath

A subarray sum is the difference of two prefix sums, cur − prev. To keep it at most k and as large as possible, you want the smallest earlier prefix that is still ≥ cur − k. Keep the earlier prefixes in sorted order and that is one binary search. For a matrix, fix a pair of columns, squash them into one column of row sums, and run the same 1D search.

Worked example 2: matrix [[1, 0, 1], [0, −2, 3]], k = 2 → 2

Every rectangle spans some columns j1..j2 and some rows. Fix the columns, add each row across them, and the rectangle's sum is a contiguous run of those row sums: the 1D problem again, once per column pair.

In Python

import bisect

def best_at_most(xs, k):
    seen = [0]                  # sorted prefix sums so far
    cur, best = 0, None
    for x in xs:
        cur += x
        i = bisect.bisect_left(seen, cur - k)  # smallest >= cur-k
        if i < len(seen) and (best is None or cur - seen[i] > best):
            best = cur - seen[i]
        bisect.insort(seen, cur)    # O(log n) search, O(n) shift
    return best

def max_sum_submatrix(matrix, k):
    m, n = len(matrix), len(matrix[0])
    best = None
    for j1 in range(n):
        rows = [0] * m          # row sums of columns j1..j2
        for j2 in range(j1, n):
            for i in range(m):
                rows[i] += matrix[i][j2]
            got = best_at_most(rows, k)
            if got is not None and (best is None or got > best):
                best = got
    return best

print(best_at_most([2, 2, -1], 3))                     # → 3
print(max_sum_submatrix([[1, 0, 1], [0, -2, 3]], 2))   # → 2

The source's C++ is correct. Python's standard library has no ordered set, so this uses a sorted list: bisect_left is the same search as lower_bound, but insort shifts the list, O(m) per insert. Fine in an interview; say so. sortedcontainers.SortedList (third-party) gives fast inserts.

Time O(n² · m log m) · Space O(m) with a balanced-tree set like C++'s, for an m × n matrix: n(n + 1)/2 column pairs, each a pass over m rows with one O(log m) search and insert. The sorted-list version keeps the O(log m) search but its inserts make the worst case O(n² · m²), though the shift is a fast memory move.

Why it beats the alternatives

✗ Every rectangle

With a 2D prefix-sum table each rectangle is O(1), but there are (n(n+1)/2)² of them: 25,502,500 for a 100 × 100 matrix.

✗ Kadane per column pair

O(m) and perfect for the unbounded maximum, but it can't honour the cap: on [2, 2, −1] it finds 4, and a sum over k tells you nothing about the best sum under it.

✗ Sliding window

Grow right, shrink left while the sum is over k. Only works when all values are ≥ 0, so the prefix sums only rise. Negatives like the −1 and −2 here break it.

✓ Ordered set of prefixes

Handles negatives and the cap. For 100 × 100: 5,050 column pairs × 100 rows × log₂ 100 ≈ 3.4 million steps, about 7.6× fewer than checking all 25.5 million rectangles.

Is it always the tool?

No. With no cap, Kadane is O(m) per column pair and simpler. With all values ≥ 0, a sliding window (two pointers) does the 1D part in O(m) with no set. And if you only need to count runs with sum in a range, merge sort on the prefix sums or a Fenwick tree over their ranks does it in O(m log m). These are standard practice, not from the source.

Put the smaller dimension in the outer pairs loop. The source always pairs columns. For a tall 10,000 × 10 matrix that's 55 pairs × 10,000 × log₂ 10,000 ≈ 7.3 million steps; pairing the 10,000 rows instead would be 50,005,000 pairs ≈ 1.7 billion. You can also stop early once a sum equals k, since nothing can beat it. Both tweaks are standard practice too, not in the source.

Understand and remember

  • Subarray sum = P_j − P_i → the constraint ≤ k becomes P_i ≥ P_j − k → the best partner is the smallest such P_i → keep earlier prefixes sorted and lower_bound it → O(log n) per step
  • Negative values make prefix sums non-monotone → a window can't shrink from one side safely and Kadane can't respect a cap → the sorted set of all earlier prefixes handles any sign
  • Fix columns j1..j2 → each row contributes one number (its sum across those columns) → a rectangle is a contiguous run of that column → the 1-D search runs once per column pair: O(n² · m log m)
  • detail that matters Python has no ordered set → bisect.insort keeps the search O(log m) but each insert shifts the list, O(m) → worst case O(n² · m²) → fine for interviews if you say so; a balanced tree or SortedList restores O(log m)

Reference only

  • C++ std::set::lower_bound
  • sortedcontainers.SortedList is third-party
  • the 100 × 100 step counts (3.4 M vs 25.5 M)
  • early exit when a sum equals k

Check
  • LIS: tails per length; the bisect finds which length x extends or improves; overwrite in place, O(1)
  • here: every earlier prefix; the bisect finds the best partner under the cap; insort shifts, O(n)
  • LIS's list never grows by insertion in the middle; this one does, which is why a balanced tree matters here

5 · Predict commit to an answer before revealing

Run the 1-D search on [3, −4, 2, 5, −1] with k = 4. Predict the answer and which step first reaches it.

Reveal

4, first reached at the last step. There cur = 5 and the bound is 5 − 4 = 1; the smallest prefix ≥ 1 in {−1, 0, 1, 3, 6} is 1 (the prefix after 3, −4, 2), so the run is the last two values, 5 + (−1) = 4. Until then the best was 3, the first element on its own.
