Checkpoint 1: choosing a sort

Ties together insertion sort, quicksort, merge sort, heapsort, radix sort and why n log n: what each sort pays per input shape, what it guarantees, and how to pick one.

How to use this page. Close the six cards. Answer each question in writing, in full sentences, before opening its Check. A wrong or shaky answer isn't a failure; it tells you exactly which section to reopen. The questions are mixed on purpose, so you have to work out which idea applies before you can answer.

1 · Mixed retrieval

  1. which concept?A nightly job sorts yesterday's orders with a hand-written quicksort that pivots on the last element. It used to take seconds; since the upstream service started sending the orders already sorted by time, it takes hours. Which idea explains it, and what are two fixes?
    Check
    • split quality sets the depth: on sorted input a last-element pivot is always the range's maximum, so each partition peels off one element
    • n levels of about n compares: n(n − 1)/2, which is 499,999,500,000 compares for 10⁶ items instead of about 24.8 million
    • fixes: a random or median-of-3 pivot, or introsort (fall back to heapsort past about 2 log₂ n depth); or just call sorted(), which finds the existing run in n − 1 compares

    Missed it? Reopen quicksort, "Worst case: sorted input with a last-element pivot".

  2. Insertion sort on a = [38, 27, 43, 3, 9, 82, 10] makes 11 swaps. Without re-running it, say how many it makes on a reversed, and why the count is exactly the number you name.
    Check
    • each adjacent swap fixes exactly one out-of-order pair, so swaps = inversions
    • a reversed 7-element array (distinct values) has every pair inverted: 7 × 6 / 2 = 21 swaps
    • on sorted input it's 0 swaps and 6 compares: the work tracks disorder, not size

    Missed it? Reopen insertion sort, "Why the count is the inversion count".

  3. which concept?A vendor claims their general-purpose sort handles any 10⁶ keys that support only <, using at most 10⁷ comparisons in the worst case. Do you believe them? What would have to be true of the keys for a sort to get under that?
    Check
    • no: any comparison sort must distinguish 10⁶! orders, so some input needs at least log₂(10⁶!) = 18,488,885 compares
    • 10⁷ is below that floor, whatever the algorithm
    • to go lower, stop comparing: fixed-width integer keys let LSD radix (w = 256, 4 passes) sort with about 4,001,024 bucket moves and no compares

    Missed it? Reopen why n log n, "The bound for any n", and radix sort, "When it beats a comparison sort".

  4. Why is building a max-heap from an unordered array O(n), even though a single sift-down can cost log₂ n swaps? Give the number the heapsort card computes for n = 10⁶.
    Check
    • a node sinks at most its height, and most nodes are near the bottom: half are leaves, a quarter have height 1, …
    • the heights sum to n − popcount(n): 999,993 for 10⁶, below n, against n log₂ n ≈ 19.9 million
    • pushing items one at a time with sift-up costs depth instead of height, and most nodes are deep: O(n log n)

    Missed it? Reopen heapsort, "Why building the heap is O(n)".

  5. which concept?You sort a team roster by name, then sort the result by team with the course's heapsort. Within the ops team the names come out Cy, Ed, Ana. What went wrong, and give two fixes.
    Check
    • heapsort isn't stable: its long-distance swaps reorder equal keys, so the name order from the first pass is lost within a team
    • fix 1: do the second pass with a stable sort (sorted(), merge sort): Bo Di | Ana Cy Ed
    • fix 2: one pass with a tuple key, key=lambda p: (p[1], p[0]), which works with any sort

    Missed it? Reopen why n log n, "Stability: sort by the second key, then the first".

  6. Merge sort needs 20 passes for 10⁶ items whatever their order. Walk through why the pass count can't depend on the input, and what one change to the merge would make it unstable.
    Check
    • bottom-up, the run width doubles every pass (1, 2, 4 …) until it covers n: ⌈log₂ 10⁶⌉ = 20, set by n alone
    • each pass copies all n elements: 20,000,000 copies
    • taking the right item on ties (<= instead of <) lets later equal keys overtake earlier ones: unstable

    Missed it? Reopen merge sort, "Why it's n log n every time" and "Stable: ties take the left run".

  7. An LSD radix sort's bucket pass is replaced by an in-place swap partition, which is faster but not stable. The keys are [2, 24, 45, 66, 75] going into the hundreds pass (all have hundreds digit 0). What can go wrong, and why does no later pass fix it?
    Check
    • the earlier passes already ordered these five by their lower digits; in the hundreds pass they all tie
    • an unstable pass may emit 24 before 2, and the hundreds pass is the last one, so nothing re-sorts them
    • stability isn't a nicety in LSD radix: it is the correctness argument

    Missed it? Reopen radix sort, the worked example and "Stable pass".

3 · Project: race the sorts on four input shapes

What it reinforces: inversions and adaptivity (insertion sort), pivot luck (quicksort), input-independent passes and stability (merge sort), the heap's compare cost (heapsort), passes × (n + w) (radix sort) and the floor they're all measured against (why n log n).

In about 60 lines of Python (the n log n card's code/ file already has most of it):

  1. Count. Write a Counted wrapper whose __lt__ adds 1 to a class counter. Implement insertion sort, bottom-up merge sort, Lomuto quicksort (last-element pivot, explicit stack) and heapsort so they only use <.
  2. Race. Run all four plus sorted() on four shapes of 7 items: a = [38, 27, 43, 3, 9, 82, 10], a sorted, a reversed, and [5] × 7. Put the compares in a 5 × 4 table next to the floor ⌈log₂ 7!⌉ = 13.
  3. Explain. For every cell below 13, say why it doesn't break the lower bound. For every cell of 21, say which mechanism forces n(n − 1)/2.
  4. Stability. Sort [(Ana, ops), (Bo, dev), (Cy, ops), (Di, dev), (Ed, ops)] by team only with each sort and record the name order within each team.
  5. Radix. Add a base-10 LSD radix sort. How many passes does a need, and how many bucket operations is that by d × (n + w)?
Done when: your table has 20 counts that you can each explain in one line, your stability run shows which sorts keep Ana, Cy, Ed in order, and you can say which sort you'd pick for each of the four shapes. Then compare with the check.
Check: the numbers (computed with the n log n card's counting harness)
  • a: insertion 15, merge 14, quicksort 11, heapsort 19, sorted() 13 (the same as the card's table).
  • Sorted: insertion 6, merge 11, quicksort 21, heapsort 21, sorted() 6. Reversed: insertion 21, merge 9, quicksort 21, heapsort 18, sorted() 6. All equal: insertion 6, merge 11, quicksort 21, heapsort 15, sorted() 6.
  • Below 13 is fine: the floor bounds the worst of all 5,040 orders, not every input. Insertion and Timsort exploit existing order; merge sort copies a run without compares once the other side is exhausted.
  • Quicksort's 21 on sorted, reversed and all-equal input is 7 × 6 / 2: the last element is always the max (or ties go right), so each partition peels off one item. Insertion's 21 on reversed input is 21 inversions.
  • Stability by team: insertion, merge and sorted() give Bo Di | Ana Cy Ed; heapsort gives Bo Di | Cy Ed Ana; quicksort gives Di Bo | Ed Cy Ana.
  • Radix: the largest value 82 has 2 digits, so 2 passes × (7 + 10) = 34 bucket operations, and no compares.
