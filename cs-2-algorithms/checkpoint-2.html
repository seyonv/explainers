Checkpoint 2: searching with an invariant

Ties together two pointers and intervals, binary search on the answer, median of two sorted arrays, longest increasing subsequence and prefix sums with an ordered set: five ways to throw work away safely, and the invariant each one relies on.

How to use this page. Close the five cards. Answer each question in writing, in full sentences, before opening its Check. A wrong or shaky answer isn't a failure; it tells you exactly which section to reopen. The questions are mixed on purpose, so you have to work out which idea applies before you can answer.

1 · Mixed retrieval

  1. which concept?Packages with weights [7, 2, 5, 10, 8] must ship in order within 2 days. Find the smallest daily capacity that works. Which technique fits, what is the yes/no test, and why is that test monotone?
    Check
    • binary search on the answer: search capacity c in [max = 10, sum = 32]
    • test: "can a greedy left-to-right fill use ≤ 2 days with capacity c?"; a bigger capacity never needs more days, so no … no, yes … yes
    • answer 18 (days [7, 2, 5] and [10, 8]), found in 4 probes instead of trying 23 capacities

    Missed it? Reopen binary search on the answer, "The one template, and its invariant", and "When does it apply?".

  2. In the pair-count scan (pairs with a[j] − a[i] ≤ d on sorted a), j never moves back when i advances. Why is that safe, and what does it do to the cost?
    Check
    • a[i] only grows, so the first a[j] > a[i] + d can only be further right
    • each pointer crosses the array once: at most 2n moves (14, not 49, on the 7-item example)
    • that O(n) pass is what makes it cheap enough to be a binary-search predicate

    Missed it? Reopen two pointers, "Same direction".

  3. which concept?Daily net sign-ups are [7, −2, 5, 10, −8]. You want the best stretch of consecutive days whose total is at most 12. A teammate's sliding window returns 10. Which idea explains the bug, and what do you use instead?
    Check
    • negatives make prefix sums non-monotone, so shrinking the window from the left can discard the best partner
    • prefix sums + a sorted set: for each cur, bisect the smallest earlier prefix ≥ cur − 12
    • it finds 12 (the whole five days: 7 − 2 + 5 + 10 − 8)

    Missed it? Reopen prefix sums with an ordered set, "Why it beats the alternatives" (sliding window).

  4. The median-of-two-arrays loop tests only A[i] ≥ B[j−1], yet a valid cut needs two conditions. Why is the second one guaranteed at the first i that passes?
    Check
    • the test is false for small i and true from some point on, so the loop finds the smallest passing i
    • at i − 1 (where j is one larger) the test read A[i−1] ≥ B[j] and failed, so A[i−1] < B[j]
    • so A[i−1] ≤ B[j] holds for free: one comparison per probe

    Missed it? Reopen median of two sorted arrays, the note under the hand trace.

  5. which concept?Boxes (w, h) nest only if strictly smaller in both. A candidate sorts by width, then heights ascending, and runs a longest-increasing-subsequence on heights. On [[1, 1], [1, 2], [1, 3]] it answers 3. What's wrong, and what's the one-character fix in the sort key?
    Check
    • equal widths can't nest, but ascending heights let them form an increasing run
    • sort by (w, −h): equal widths become a decreasing run, so at most one of them is chosen
    • heights 3, 2, 1 → LIS 1, the correct answer

    Missed it? Reopen LIS, "Russian doll envelopes".

  6. After running the tails loop on [0, 8, 4, 12, 2, 10, 6, 14, 1, 9], tails is [0, 1, 6, 9]. Is that a longest increasing subsequence? Explain what tails does and doesn't mean.
    Check
    • its length (4) is the LIS length, but it isn't a subsequence: 1 comes after 6 in the input
    • tails[k] is only the smallest end of some run of length k + 1; different entries can come from different runs
    • to print a real LIS, keep parent pointers and walk back (e.g. [0, 2, 6, 9])

    Missed it? Reopen LIS, "The three moving parts" and "Is it always the tool?".

  7. which concept?Meetings [1, 5], [2, 6], [5, 8], [6, 9]. Your sweep reports 3 rooms, but a colleague says 2. Which detail of which technique decides it, and who is right?
    Check
    • the interval sweep's tie rule: at the same time, an end (−1) must sort before a start (+1)
    • with ends first the peak is 2: the rooms freed at 5 and 6 are reused immediately
    • starts first counts the arriving meeting before the leaving one and wrongly peaks at 3

    Missed it? Reopen two pointers and intervals, the meeting-rooms table.

  8. Rotated sorted array with duplicates, [1, 1, 1, 0, 1]: why can't binary search always discard half, and what is the worst case?
    Check
    • when nums[mid] == nums[hi], the drop could be on either side ([1, 1, 1, 0, 1] and [1, 0, 1, 1, 1] look the same at the first probe)
    • the only safe move is hi −= 1, since hi's value also sits at mid
    • worst case O(n): 999 steps for 1,000 equal values, against 10 when all are distinct

    Missed it? Reopen binary search on the answer, "Rotated minimum, and why duplicates cost O(n)".

3 · Project: split an array, three ways

What it reinforces: a monotone check plus the first_true template (binary search on the answer), a forward-only greedy scan and a sliding window (two pointers), and prefix sums with a sorted set for when values go negative (prefix sums with an ordered set).

Split Array Largest Sum: split nums into m contiguous parts so that the largest part-sum is as small as possible. In about 50 lines of Python:

  1. The check. Write parts_needed(nums, cap): scan left to right, start a new part whenever adding the next number would exceed cap. Explain in one sentence why a bigger cap can never need more parts.
  2. The search. Use the card's first_true over cap ∈ [max(nums), sum(nums)] with the test parts_needed(nums, cap) ≤ m. For nums = [7, 2, 5, 10, 8] and m = 2, print every probe (lo, hi, mid, parts, ok).
  3. Check it. Brute-force every way to place m − 1 cuts and compare for m = 1 … 5.
  4. One chunk under a cap. Now find the single best contiguous chunk with sum ≤ 17: first with a shrink-while-over sliding window, then with prefix sums + bisect. They should agree. Say why.
  5. Break the window. Repeat step 4 on [7, −2, 5, 10, −8] with cap 12. Which method is still right, and what exactly did the window throw away?
Done when: your search prints 4 probes and returns 18, brute force agrees for every m, and you can explain in one sentence each why the window works on the first array and fails on the second. Then compare with the check.
Check: the numbers (computed with a Python version of exactly these steps)
  • Probes for m = 2: [10, 32] → mid 21, 2 parts, yes → [10, 21] → mid 15, 3 parts, no → [16, 21] → mid 18, 2 parts, yes → [16, 18] → mid 17, 3 parts, no → [18, 18]. Answer 18: [7, 2, 5] = 14 and [10, 8] = 18.
  • Brute force agrees: m = 1 → 32, 2 → 18, 3 → 14, 4 → 10, 5 → 10.
  • Best chunk ≤ 17 on [7, 2, 5, 10, 8]: both methods give 17 (2 + 5 + 10). All values are ≥ 0, so prefix sums only rise and shrinking from the left always lowers the sum.
  • On [7, −2, 5, 10, −8] with cap 12: prefix sums + bisect give 12 (all five values; prefixes 7, 5, 10, 20, 12). The window gives 10: when 10 pushes the sum to 20 it drops from the left until the sum fits, and the −8 that would have brought the whole stretch back to 12 comes too late.
