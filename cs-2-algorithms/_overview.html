In one breath

Count the passes you make over the data and the work in each pass, then cut one of them. There are three ways to do that: halve what's left each pass (binary search, merge sort, divide and conquer), make one pass whose pointers never move back (two pointers, KMP, Manacher), or stop comparing and look inside the keys (radix sort, hashing). Each shortcut is only allowed once you can say why it's safe: an invariant, a monotone test, or an exchange argument.

The words people use

Worst case vs expected

Worst case bounds every input; expected averages over the algorithm's own random choices. Quicksort, quickselect and rolling hash are fast in expectation only; heapsort, KMP and Manacher promise the worst case.

Comparison sort

A sort that learns about keys only by asking "x < y?". It can't beat log₂ n! compares. Radix sort reads digits instead, so the bound doesn't apply to it.

Stable, in place

Stable: equal keys keep their input order (merge, Timsort, insertion, LSD radix). In place: O(1) or O(log n) extra memory (heapsort, quicksort). Between sorts that tie on speed, these two decide.

✓ Invariant

A fact that stays true at every step: "the answer is in [lo, hi]", "tails is sorted", "[1, miss) is covered". It's what lets an algorithm throw work away safely, and it's the first thing an interviewer asks you to state.

When this advice doesn't apply

Big-O counts steps, not time. np.sort and sorted() are both n log n, yet 0.031 s against 0.130 s on 10⁶ floats. Small inputs flip the ranking too: Timsort sorts runs under 64 items with insertion sort, and CPython only switches to Karatsuba multiplication above 70 internal digits (about 632 decimal digits).

In Python, a built-in usually beats the algorithm you'd write: sorted() over any hand-written sort, s.find(p) over KMP or Rabin–Karp, np.partition over quickselect. Write the algorithm when you need a guarantee the built-in doesn't give (a linear worst case, a stream you can't rewind) or when the interview asks for it. And greedy is only right with a proof: coins {1, 3, 4} for 6 fool it, and that problem needs DP (course 3).

Understand and remember

  • Cost = passes × work per pass → halving what's left makes passes log₂ n (binary search, merge sort, D&C) → a one-way sweep makes it one pass of ≤ 2n pointer moves (two pointers, KMP, Manacher) → reading keys instead of comparing escapes the compare count altogether (radix, hashing)
  • Compare-only sorting must tell n! orders apart → each yes/no halves them at best → at least log₂ n! ≈ n log₂ n compares (18,488,885 for 10⁶) → only an algorithm that looks inside the keys can go under it
  • A shortcut throws work away → it is only correct if something proves the thrown-away part can't hold the answer → invariant (lo/hi, tails), monotone predicate, or exchange argument → no proof, no shortcut (greedy coins {1, 3, 4} for 6 fails)
  • Big-O counts steps, not seconds → constants and language decide real time (np.sort 0.031 s vs sorted() 0.130 s, both n log n) → in Python the built-in in C usually wins → write the algorithm for a guarantee or an interview
  • detail that matters Worst case vs expected: quicksort, quickselect and rolling hash are fast only in expectation over their own random choices → an adversary who knows a fixed pivot or a fixed (B, p) can force the bad case → heapsort, KMP and Manacher promise the worst case

Why this step?

5 · Predict commit to an answer before revealing

The "wrong → right" table shows a 50,000× gain from bisecting d in k-th pair distance. Predict what happens to that ratio if values only go up to 10³ instead of 10⁶ (n still 10⁴). Bigger, smaller, or the same?

Reveal

Smaller. Trying d = 0, 1, 2 … needs up to W + 1 passes and bisecting needs ⌈log₂(W + 1)⌉ passes. At W = 10⁶ that's 10⁶ + 1 vs 20 (≈ 50,000×). At W = 10³ it's 1,001 vs ⌈log₂ 1,001⌉ = 10, only about 100×. Halving pays most when the answer space is huge.

Insertion sortAlso called the card-player's sort; in Timsort it runs as binary insertion sort. The source guide gives it first under Sorting, as a three-line C++ loop that swaps each new element left until it fits.In one breathKeep the left part of the array sorted. Take the next element (the key) and swap it leftwards past every bigger neighbour; when the neighbour is not bigger, it has landed. Each swap fixes exactly one out-of-order pair, so the work is the number of such pairs: none for sorted input, all of them for reversed input.
