Merge sort

Also called two-way merge sort; this is the bottom-up (iterative) form, which merges runs of width 1, 2, 4 … instead of recursing. The source guide gives it under Sorting as a C++ loop over width with one scratch buffer.

Prime · 2 minutes before you read

The problem: Quicksort's speed depends on pivot luck and it scrambles equal keys. Sometimes you need a sort whose cost is the same on every input and which keeps ties in order: sorting records by several keys, sorting a linked list, or sorting a file bigger than memory.

Where it fits: Fourth sort. Quicksort put its work before the recursion; merge sort puts it after, in the merge. The merge is reused on the next card to count inversions, and divide and conquer later derives its n log n from the recurrence.

Builds on: Quicksort · Insertion sort

In one breath

Two sorted lists can be merged into one sorted list in a single pass: look at the two front items and take the smaller. So start with runs of one element (already sorted), merge neighbours into sorted runs of 2, then 4, then 8, until one run covers everything. Each pass touches every element once, and there are only log₂ n passes.

Why it's n log n every time

Each pass copies all n elements once, and each pass doubles the run width, so ⌈log₂ n⌉ passes finish the job. The top-down (recursive) version gives the same count as a recurrence: sort two halves, then merge them in n steps.

T(n)= 2T(n/2)sort both halves + nmerge them ⇒ T(n)= nper level × log2nlevels (passes)
nelements; also the work of one full level of merges7 for a log₂ nlevels, rounded up: width doubles each pass3 for a · 20 for 10⁶ T(n)element copies (compares are at most this)21 for a · 2 × 10⁷ for 10⁶

n = 10⁶: ⌈log₂ 10⁶⌉ = 20 passes, 10⁶ × 20 = 20,000,000 copies and at most that many compares. The input's order doesn't change the pass count, so best, average and worst case are all Θ(n log n).

Stable: ties take the left run

Sort four cards by their number only: [A 2, B 1, C 2, D 1]. The merge rule "take the right item only if it is strictly smaller" keeps equal keys in input order, because the left run always holds the earlier ones.

Merge ruleAfter width 1After width 2Equal keys
if right < leftB1 A2 | D1 C2B1 D1 A2 C2B before D, A before C: stable
if right <= leftB1 A2 | D1 C2D1 B1 C2 A2both ties flipped

The two rules differ only in the width-2 merge: on B1 vs D1 and on A2 vs C2 they pick different sides. Stability is what lets you sort by a second key, then a first, and keep the second order within ties.

In Python

def merge_sort(a, key=lambda x: x):
    a, n, width = list(a), len(a), 1
    while width < n:
        b = []                              # this pass's output
        for lo in range(0, n, 2 * width):
            mid, hi = min(lo + width, n), min(lo + 2 * width, n)
            i, j = lo, mid
            while i < mid and j < hi:
                if key(a[j]) < key(a[i]):  # strict: ties take left
                    b.append(a[j]); j += 1
                else:
                    b.append(a[i]); i += 1
            b += a[i:mid] + a[j:hi]         # one side ran out
        a, width = b, width * 2
    return a

print(merge_sort([38, 27, 43, 3, 9, 82, 10]))
print(merge_sort([("A", 2), ("B", 1), ("C", 2), ("D", 1)],
                 key=lambda t: t[1]))
# → [3, 9, 10, 27, 38, 43, 82]
# → [('B', 1), ('D', 1), ('A', 2), ('C', 2)]

The source's C++ is correct (it takes the right item only on a[left] > a[right], so it is stable too). It copies the buffer back into a after each pass; the Python here just swaps in the new list.

Time O(n log n) · Space O(n). ⌈log₂ n⌉ passes, each copying all n elements, whatever the input order. The merge needs a second buffer of size n; it is not in place.

Why it beats the alternatives (when you need a guarantee)

✗ Quicksort

Faster in memory (0.031 s vs 0.072 s above), but not stable, and a bad pivot on sorted input degrades it to O(n²).

✗ Heapsort

O(n log n) worst case and in place, but not stable, and its jumps between parent and child indices miss the cache.

✗ Insertion sort

Stable and in place, but one swap per inversion: 11 on a, and up to n(n − 1)/2 ≈ 5 × 10¹¹ for n = 10⁶.

✓ Merge sort

Stable and Θ(n log n) on every input: 3 passes and 14 compares on a. It reads and writes in straight lines, so it also sorts linked lists and files too big for memory.

Is it always the right sort?

No. It needs a second buffer of n elements, and for plain numbers in memory an in-place quicksort variant is faster: 0.031 s against 0.072 s for 10⁶ floats. When you don't need stability or a worst-case bound, np.sort's default introsort is the better call.

Where it wins: linked lists (merging just relinks nodes, so no buffer is needed), external sorting (sort chunks that fit in memory, then merge the sorted files in sequential reads), and anything that must be stable. In Python you rarely write it: sorted() is Timsort, a merge sort that first finds runs already in the input, so sorted input costs O(n). The same merge also counts inversions in O(n log n), which is the next card.

Understand and remember

  • Two sorted runs → the smaller front item is the smallest remaining overall → take it, advance → one linear pass merges them (at most sum − 1 compares)
  • Width doubles each pass → ⌈log₂ n⌉ passes, each touching all n elements → Θ(n log n) on every input (20 passes, 2 × 10⁷ copies for 10⁶) → no worst-case surprise, unlike quicksort
  • Take from the right only when strictly smaller → equal keys always leave from the left run, which holds the earlier ones → stable → you can sort by a secondary key, then a primary key, and keep the secondary order within ties
  • detail that matters Merging reads and writes in straight lines → works on linked lists (relink, no buffer) and external files (sequential reads) → but on arrays it needs an n-element buffer, so in-memory introsort is faster (0.031 s vs 0.072 s)

3 · Retrieve from memory, card closed
  1. concept Explain why merge sort's best, average and worst cases are all Θ(n log n), when quicksort's range from n log n to n².
    Check
    • merge sort always splits at the midpoint (or doubles width), so depth is always ⌈log₂ n⌉
    • every level moves all n elements regardless of values
    • quicksort's split point depends on the pivot's value, so its depth can reach n
  2. mechanism Walk through the width-2 pass on [27, 38 | 3, 43 | 9, 82 | 10]: which runs merge, in what order do items come out, and how many compares does each merge take?
    Check
    • [27, 38] + [3, 43] → 3, 27, 38, 43: 3 compares (3v27, 27v43, 38v43), then 43 copied
    • [9, 82] + [10] → 9, 10, 82: 2 compares (9v10, 82v10), then 82 copied
    • 5 compares in the pass
  3. tradeoff You're sorting a 50 GB log file on a machine with 8 GB of RAM. Why is merge sort's structure the right starting point, and what does it cost you?
    Check
    • sort memory-sized chunks, write them out as sorted runs, then merge the runs with sequential reads
    • the merge only needs the front of each run in memory
    • cost: extra disk passes and an output buffer; random-access sorts like quicksort or heapsort would thrash the disk

5 · Predict commit to an answer before revealing

Merge sort on already-sorted [3, 9, 10, 27, 38, 43, 82]: more compares than on a's 14, fewer, or the same? And what about the number of passes?

Reveal

Fewer compares: 11 (counted by the n log n card's compare harness). Sorted runs make every merge exhaust the left run first, so the right run is copied without compares. But the passes stay at 3: bottom-up merge sort can't skip a pass, which is exactly what Timsort fixes by detecting runs already in the input (n − 1 = 6 compares on sorted input).
