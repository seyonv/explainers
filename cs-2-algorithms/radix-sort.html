Radix sort

Also called LSD (least-significant-digit) radix sort, or bucket sort by digits. The source guide gives a short Python version under Sorting that buckets by base-w digits and then splits off the negatives. That version doesn't run as written; the fixed version is below.

Prime · 2 minutes before you read

The problem: Every sort so far learns only by asking "x < y?", and that caps it at about n log₂ n compares. For integers there's another source of information: the digits themselves. Reading them lets you place items without comparing them at all.

Where it fits: The last sort, and the counterexample to the next card's lower bound. It depends on the stability idea from merge sort: every pass must keep the previous pass's order.

In one breath

Don't compare keys at all. Deal every number into 10 buckets by its last digit, gather the buckets in order, then do it again for the tens digit, then the hundreds. Each pass is stable (it keeps the order the last pass left), so after the last pass the array is sorted by every digit at once. The cost is passes × (n + buckets), not n log n.

3 passes because the largest |x| is 802 (3 digits). In pass 2, five numbers share hundreds digit 0: they come out as 2, 24, 45, 66, 75 only because the bucket keeps the order pass 1 left. That's the stability the whole method rests on.

Why −90 reads as 910: Python's // floors and % takes the divisor's sign ones: −90 // 1 % 10 = −90 % 10 = 0 tens: −90 // 10 % 10 = −9 % 10 = 1 hundreds: −90 // 100 % 10 = −1 % 10 = 9 digits 9 1 0 = 1000 − 90 = 910

Every negative x is sorted as 10d + x (here d = 3, so 1000 + x). That keeps the negatives in the right order among themselves but puts them after all the positives, so one final stable split moves them to the front.

In Python

def radix_sort(a, w=10):
    a = list(a)
    if not a:
        return a
    m = max(abs(x) for x in a)
    d = 1
    while w ** d <= m:          # passes = digits of the largest |x|
        d += 1
    for i in range(d):          # least significant digit first
        buckets = [[] for _ in range(w)]
        for x in a:             # -90 // 10 % 10 == 1: Python floors,
            buckets[x // w**i % w].append(x)  # so -90 reads as 910
        a = [x for b in buckets for x in b]   # keep bucket order
    neg = [x for x in a if x < 0]   # already in order among themselves
    return neg + [x for x in a if x >= 0]

print(radix_sort([170, 45, 75, -90, 802, 24, 2, 66]))
# → [-90, 2, 24, 45, 66, 75, 170, 802]
print(radix_sort([-5, 0, 5]), radix_sort([0, 0]))
# → [-5, 0, 5] [0, 0]

The source's version has four problems, corrected here: it reads max(map(abs, arr)) but the parameter is array (NameError); its split [element > 0] files 0 with the negatives, ahead of them, so [−5, 0, 5] → [0, −5, 5]; math.log(0) crashes on an all-zero list; and round(log) + 1 gives 802 four passes where 3 suffice. Its negative digits are fine: the floor trick above is exactly what it relies on.

Time O(d(n + w)) · Space O(n + w). Each of the d passes touches all n numbers once and all w buckets once. With w fixed and keys of bounded width, d is a constant, so it's linear in n. It's stable, and it isn't in place: the buckets hold a full copy.

Why it beats the alternatives (on fixed-width integer keys)

✗ Comparison sort

Quicksort, merge sort, heapsort, Timsort: each needs at least log2(n!) compares, 1.85 × 107 for n = 106, however clever.

✗ Counting sort on the whole key

One pass, but one counter per possible value: 232 = 4,294,967,296 counters for an int32. Great for a small range, hopeless for a wide one.

✗ MSD radix

Starts at the top digit and recurses, so it needs a separate sweep per bucket and lots of tiny buckets near the bottom. Better suited to variable-length strings.

✓ LSD radix

Counting sort one digit at a time: 4 passes of 256 buckets for int32, about 4.0 × 106 moves, and never a compare. Stable for free.

Should you reach for it?

Rarely by hand in Python. A pure-Python radix sort runs in bytecode, so expect it to lose to sorted(), which is written in C (our expectation, not timed here). Radix pays off when the keys are small, fixed-width integers (or anything you can map to them: dates, IP addresses, fixed-length strings) and it runs in a compiled language, as NumPy does for int16 above. In interviews it's the standard answer to "sort n integers in a known range faster than n log n" and to problems like Maximum Gap.

It's the wrong choice for floats without a bit-trick key transform, for arbitrary objects with a custom comparison, for keys much wider than log n bits (d grows with the width), or when memory is tight: it needs n extra slots, and wide w adds cache misses. On int64 NumPy switches to timsort, and there introsort was faster still.

Understand and remember

  • Each pass stably buckets by one digit → items with equal digits keep the order the previous pass left → after the last pass the array is sorted by the whole key (most significant digit decides, lower digits break ties) → stability is the correctness argument, not a nicety
  • No compares → the log₂ n! floor doesn't apply → work is d passes × (n items + w buckets) → with fixed-width keys d is a constant → linear in n (4 × (10⁶ + 256) = 4,001,024 moves for 32-bit keys, w = 256)
  • Bigger base → fewer passes (d = ⌈b / log₂ w⌉) but more buckets per pass and scattered writes → w = 256 or 65,536 for machine integers → wider keys or big w erase the win
  • detail that matters Python's // floors and % takes the divisor's sign → a negative x reads as 10ᵈ + x → negatives come out correctly ordered among themselves but after the positives → one stable split moves them to the front
