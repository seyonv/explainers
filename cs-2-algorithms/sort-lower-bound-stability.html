Why n log n, and which sort to use

Also called the comparison-sort lower bound, the decision-tree argument or the information-theoretic bound; plus stability, the property that decides between sorts that tie on speed. The source guide's Sorting page gives five sorts but no complexities or trade-offs, so this card is supplemented.

In one breath

A sort that learns about its input only by asking "is x < y?" must tell apart all n! possible orders of the input. Each yes/no answer at best cuts the remaining orders in half, so some input needs at least log₂(n!) ≈ n log₂ n questions. No cleverness gets under that; only sorts that look inside the keys (like radix sort) can.

Worked example: the decision tree for n = 3

Insertion sort on three items x, y, z, drawn as the questions it asks. Every run follows one root-to-leaf path; each green leaf is one of the 3! = 6 possible sorted orders. Inputs already in order (x y z) or with only the first pair swapped (y x z) finish in 2 compares; the other four take 3.

a tree of depth d has at most 2^d leaves; it needs n! leaves 2^d ≥ n! → d ≥ log₂ n! n = 3: log₂ 6 = 2.58 → at least 3 compares n = 7: log₂ 5040 = 12.30 → at least 13 compares (the course array a)

In Python

import math

class Counted:
    """Wraps a value and counts every < comparison made on it."""
    compares = 0

    def __init__(self, v):
        self.v = v

    def __lt__(self, other):
        Counted.compares += 1
        return self.v < other.v

def lower_bound(n):
    """log2(n!) via lgamma, so it works for n = 10**6 too."""
    return math.lgamma(n + 1) / math.log(2)

def compares(sort, a):
    Counted.compares = 0
    sort([Counted(x) for x in a])
    return Counted.compares

a = [38, 27, 43, 3, 9, 82, 10]
print(f"{lower_bound(7):.2f}", compares(sorted, a))
# → 12.30 13

people = [("Di", "dev"), ("Ana", "ops"), ("Ed", "ops"),
          ("Bo", "dev"), ("Cy", "ops")]
by_name = sorted(people, key=lambda p: p[0])   # secondary key first
by_team = sorted(by_name, key=lambda p: p[1])  # then primary: stable
print(by_team)
# → [('Bo', 'dev'), ('Di', 'dev'), ('Ana', 'ops'), ('Cy', 'ops'),
#    ('Ed', 'ops')]

Time Ω(n log n) for any comparison sort · Space: whatever the sort needs. Counting costs O(1) per compare on top of the sort itself. The code file adds the other four sorts, all 5,040 orders of a, and the n = 10⁵ count.

Why sorted() is the right default

✗ Hand-written quicksort

Fast on average, but a fixed pivot hits n² on sorted input (n(n − 1)/2 = 21 compares for n = 7), it isn't stable, and in pure Python it loses to C anyway.

✗ Heapsort

n log n guaranteed and in place, but 22 compares worst for n = 7 against merge sort's 14, not stable, and its parent-child jumps miss the cache.

✗ Radix sort

Beats n log n, but only for integer or fixed-width keys, needs O(n + b) extra memory, and can't sort by an arbitrary key= function.

✓ Timsort

Stable, n log n worst case, 0.8% above the floor on random input, and n − 1 compares on sorted input because it merges the runs already there.

Can anything beat n log n?

Yes, by breaking an assumption. Radix and counting sort don't compare, so for 32-bit integers they run in a few linear passes. Nearly sorted input has far fewer than n! likely orders, which is why Timsort does n − 1 compares on sorted data. And if you don't need the full order, don't sort: heapq.nsmallest(k, xs) is O(n log k), and quickselect finds the median in O(n) on average.

The bound also says nothing about constants. np.sort and sorted() are both n log n, yet 0.031 s vs 0.130 s on 10⁶ floats. For numbers in an array, when you don't need stability, numpy's introsort is the faster call; for Python objects, records and multi-key sorts, use sorted().
