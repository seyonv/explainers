Quicksort

Also called partition-exchange sort; the version with a heapsort fallback is introsort. The source guide gives it in C++ as an iterative loop over an explicit stack of (lo, hi) ranges, with Lomuto partitioning around the last element.

Prime · 2 minutes before you read

The problem: Insertion sort's one-swap-per-inversion is O(n²) on random data. To get n log n in place, you need a single sweep that settles one element for good and splits the rest into independent halves. How evenly it splits decides everything.

Where it fits: Second sort. Insertion sort showed the cost of fixing order locally; quicksort fixes it globally with a partition. Quickselect reuses the partition next, and heapsort appears here as introsort's fallback.

In one breath

Pick a pivot, then sweep the range once so everything smaller ends up on its left and everything else on its right. The pivot now sits exactly where it belongs in the sorted output, and the two sides are separate, smaller problems. Push them on a stack and repeat until every range has fewer than two elements.

Worst case: sorted input with a last-element pivot

In Python

def partition(a, lo, hi):          # Lomuto, pivot = a[hi]
    p, i = a[hi], lo - 1           # a[lo..i] holds values < p
    for j in range(lo, hi):
        if a[j] < p:
            i += 1
            a[i], a[j] = a[j], a[i]
    a[i + 1], a[hi] = a[hi], a[i + 1]   # pivot lands between
    return i + 1

def quicksort(a):
    stack = [(0, len(a) - 1)]
    while stack:
        lo, hi = stack.pop()
        if lo >= hi:
            continue
        m = partition(a, lo, hi)
        left, right = (lo, m - 1), (m + 1, hi)
        if m - lo < hi - m:        # push the larger side first,
            stack += [right, left]  # so the smaller is done first
        else:
            stack += [left, right]

a = [38, 27, 43, 3, 9, 82, 10]
quicksort(a); print(a)
# → [3, 9, 10, 27, 38, 43, 82]

The source always pushes left then right. It sorts correctly, but on reversed input of 2,000 elements 1,001 ranges wait on its stack at once, which is O(n) memory. Pushing the larger side first (so the smaller one is finished first) caps it at 2 there and O(log n) in general; changed here.

Time O(n log n) average, O(n²) worst · Space O(log n). Each partition level costs about n compares; random-looking splits give about log n levels, while a pivot that is always the extreme gives n levels. The array is sorted in place, and the only extra memory is the stack of pending ranges. Not stable: the long-distance swaps reorder equal keys.

Why it beats the alternatives

✗ Plain quicksort, fixed pivot

28 compares on sorted n = 8 and 5 × 10¹¹ on sorted n = 10⁶. Sorted, reversed and all-equal inputs are common, and an attacker can build a bad one on purpose.

✗ Merge sort

O(n log n) always and stable, but it needs an n-element buffer and copies every element at each of the log₂ n levels. kind="stable" took 0.072 s against 0.031 s.

✗ Heapsort

O(n log n) worst case in place, but it jumps between a node and its children at 2i + 1, far apart in memory, so it misses cache on big arrays. Kept as a fallback only.

✓ Introsort

Quicksort's sequential sweeps and in-place splits for the common case, heapsort only when depth passes about 2 log₂ n, so the worst case is O(n log n). 0.031 s for 10⁶ floats.

Should you write quicksort?

Almost never in production: call sorted() or np.sort. Python's own sort is Timsort, not quicksort, because it must be stable and it gains a lot on the partly sorted data people actually have. Write it in interviews, and reuse its partition step for quickselect (the k-th smallest in O(n) on average).

Don't use it when you need stability (sorting records by a second key), on linked lists (merge sort needs no random access), or on inputs with many equal keys under a plain Lomuto partition: all-equal n = 8 costs the full 28 compares, because < sends every equal key right. A 3-way partition (less / equal / greater) fixes that, and a random or median-of-3 pivot fixes sorted input.

Understand and remember

  • One sweep puts everything < pivot left and the rest right → the pivot sits at its sorted index → the two sides are independent subproblems → about n compares per level
  • Split quality sets the depth → balanced splits give ≈ log n levels (≈ 2n ln n ≈ 1.39 n log₂ n compares, 24,785,482 for 10⁶) → an extreme pivot every time gives n levels → n(n − 1)/2 (28 for sorted n = 8; 499,999,500,000 for 10⁶)
  • Sorted, reversed and all-equal inputs are common and an attacker can craft them → fixed pivots are unsafe → random or median-of-3 pivot, a 3-way partition for duplicates, and introsort's heapsort fallback past ≈ 2 log₂ n depth give an O(n log n) guarantee
  • detail that matters Process the smaller range first (push the larger one first) → every waiting range is at most half its parent → the stack holds O(log n) ranges instead of O(n) (2 vs 1,001 on reversed n = 2,000)
  • detail that matters Partition scans memory sequentially and sorts in place → cache-friendly → why introsort (0.031 s) beats numpy's stable sort (0.072 s) on 10⁶ floats

4 · Compare against what you already know

vs Merge sort: Quicksort splits then does nothing to combine; merge sort splits trivially then merges. Where does each put its work, which design choice makes merge sort's cost input-independent, and how does each fail?

Check
  • quicksort's work is the partition before recursing; merge sort's is the merge after
  • merge sort always splits in the middle, so depth is always log₂ n
  • quicksort fails on bad pivots (n²) and isn't stable; merge sort needs an n-element buffer and is slower in memory

vs Heapsort: Introsort runs quicksort and falls back to heapsort. What does each contribute, and why not run heapsort from the start?

Check
  • quicksort: fast sequential sweeps, in place, fastest on average
  • heapsort: O(n log n) on every input, in place
  • heapsort alone is slower (0.096 s vs 0.031 s for 10⁶ floats) because its parent–child jumps miss the cache
  • so heapsort is only the safety net when depth passes ≈ 2 log₂ n
