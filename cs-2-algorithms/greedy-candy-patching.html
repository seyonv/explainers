Greedy II: candy and patching an array

Two greedy problems from the source guide's Greediness section: Candy (LeetCode 135) and Patching Array (LeetCode 330), both given there as short C++. Here: candy as two passes, patching as a growing reach, and the proof that neither greedy can be beaten.

Prime · 2 minutes before you read

The problem: A greedy algorithm commits and never looks back, so it's fast. It's also often wrong: coins {1, 3, 4} for 6 fool it. Candy and Patching Array are greedy problems where the local choice is provably optimal, and the proofs are the reusable part.

Where it fits: Last card of the course. Greedy I showed a safe greedy; this card names the two standard proofs, a lower bound (candy) and an exchange argument (patching), and marks where greedy stops and cs-3's DP starts.

  2. Why do equal neighbours impose nothing, and what happens to child 3 in the 87, 87, 87 plateau?
  3. What does the invariant "[1, miss) is covered" guarantee, and why does using x ≤ miss extend it to [1, miss + x)?
  4. When no number ≤ miss is left, why is patching miss itself the best possible patch?
  5. Why can there be at most about log₂ n patches?

In one breath

A greedy algorithm commits to one local choice at each step and never revisits it. That is only safe when you can prove no other choice does better. In Candy, each child's count is forced from below by its rising neighbours, so giving exactly that lower bound is optimal. In Patching Array, when a sum is missing, the largest useful patch is the missing sum itself, and taking it can only grow what you can reach.

The source counts the same thing in O(1) space. It starts with 1 per child, then for each rise-then-fall adds 1 + 2 + … + up and 1 + 2 + … + down. The peak was counted in both runs but only needs the larger, so it subtracts min(up, down):

source: total = n + Σ [ (1+…+up) + (1+…+down) − min(up, down) ] [1, 2, 87, 87, 87, 2, 1]: 7 + [(1+2) + 0 − 0] + [0 + (1+2) − 0] = 13 [1, 2, 3, 2, 1]: 5 + [(1+2) + (1+2) − min(2, 2)] = 9 = 1 + 2 + 3 + 2 + 1, peak gets 1 + max(2, 2) = 3

The plateau of 87s splits the first example into two runs that share no peak, so nothing is subtracted.

In Python

def candy(ratings):
    n = len(ratings)
    left = [1] * n
    for i in range(1, n):                    # beat the left neighbour
        if ratings[i] > ratings[i - 1]:
            left[i] = left[i - 1] + 1
    right = [1] * n
    for i in range(n - 2, -1, -1):           # beat the right neighbour
        if ratings[i] > ratings[i + 1]:
            right[i] = right[i + 1] + 1
    return sum(max(a, b) for a, b in zip(left, right))

def min_patches(nums, n):
    miss, i, patches = 1, 0, 0               # [1, miss) is formable
    while miss <= n:
        if i < len(nums) and nums[i] <= miss:
            miss += nums[i]                  # use it: reach grows
            i += 1
        else:
            miss += miss                     # patch miss: reach doubles
            patches += 1
    return patches

print(candy([1, 0, 2]), candy([1, 2, 87, 87, 87, 2, 1]))
print(min_patches([1, 5, 10], 20), min_patches([], 2**31 - 1))
# → 5 13
#   2 31

The source's C++ is correct. Its Patching Array counts every loop step and returns patches − i (steps minus numbers used); the Python counts patches directly. It keeps miss in a long, presumably because miss can pass 231 − 1 while n is an int. Python ints can't overflow.

Candy: time O(n) · space O(n) for two passes and two arrays; the source's run counting does it in O(1) extra space. Patching: time O(len(nums) + log n) · space O(1). Each number is used once and each patch at least doubles miss, so there are at most about log₂ n patches: with nums = [] and n = 231 − 1, exactly 31 (1, 2, 4, …, 230).

Why it beats the alternatives

✗ Candy in one left pass

Only looks at the left neighbour. [1, 0, 2] gets [1, 1, 2]: child 0 is rated above child 1 but gets no more. Falling runs need the right pass.

✗ Sweep and fix until stable

Correct, but a falling run lifts only one level per sweep. Ratings n, n−1, …, 1 need n sweeps: 1,000 sweeps for n = 1,000, so O(n²).

✗ Search patch sets

Try all multisets of k patches from 1 … n, smallest k first. For n = 20 that is 1 + 20 + 210 = 231 sets before finding the answer, each needing a subset-sum check, and it grows exponentially in k.

✓ Greedy with a proof

Two O(n) passes give 13 candies; the reach loop finds 2 patches in 5 steps. The lower bound (candy) and the exchange argument (patching) prove nothing smaller exists.

Is greedy always safe?

No. Greedy works here only because of the two proofs above. Without one, it's a guess. Coin change with coins {1, 3, 4} and amount 6: greedy takes 4 + 1 + 1 = 3 coins, but 3 + 3 = 2 coins. That needs dynamic programming. The usual test: can you prove the local choice is either forced (a lower bound) or swappable into any optimal answer (an exchange)? This framing is standard practice, not from the source.

Both solutions also lean on their exact rules. Patching assumes nums is sorted ascending, as the problem states; sort it first otherwise. Candy treats equal neighbours as unconstrained, so [87, 87, 87] gets 1 each; reading "equal ratings get equal candies" into it is the common mistake, and that variant would need its own proof.

Understand and remember

  • Candy: a rising run of length L before child i forces c[i] ≥ L in any valid answer → left[i] and right[i] are lower bounds → max(left, right) is necessary, and it satisfies both neighbours' rules, so it's valid → the minimum total (13 for [1, 2, 87, 87, 87, 2, 1])
  • Patching: [1, miss) makeable and x ≤ miss → every t in [miss, miss + x) is x + (t − x) with t − x makeable → reach grows to miss + x; if the next number is > miss, miss is unreachable, so some patch ≤ miss is needed → patching miss itself covers the most ([1, 2·miss))
  • Exchange argument: take any optimal solution, swap its patch p ≤ miss for miss → coverage only grows, count unchanged → some optimal answer makes the greedy choice → by induction greedy is optimal; each patch doubles miss, so ≤ log₂ n patches (31 for n = 2³¹ − 1)
  • detail that matters The source's O(1)-space candy counts rising and falling runs and subtracts min(up, down) for the shared peak → same total as two passes, no arrays

vs Minimum spanning trees: Kruskal's MST is the classic greedy with an exchange proof. What is exchanged there and here, and what would break each proof?

Check
  • Kruskal: a cheapest edge crossing a cut can replace any heavier crossing edge in an optimal tree
  • patching: miss can replace any smaller useful patch
  • Kruskal breaks without the cut property (e.g. degree limits); patching breaks if nums weren't sorted or sums weren't subset sums
