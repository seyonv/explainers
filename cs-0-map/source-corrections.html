What the source got wrong

Every real error the 181 cards found in the source guide, in one place: what the source said or did, what is correct, and how we checked. Each card also shows the fix where it happens, in a muted line under the code or the answer.

Prime · 2 minutes before you read

The problem: Interview notes are copied, trusted and memorised. If a line of code crashes, mutates its input or answers the wrong question, you learn the bug along with the idea and repeat it in the interview.

Where it fits: The second card of the map. It builds on the overview's source-to-course table: the errors are grouped by the same courses, and the cards written from references have no rows because there was nothing to check.

Builds on: The core CS canon, mapped · LFU cache in O(1) · Monotonic stack · Bellman–Ford and Floyd–Warshall · Newton's method for square roots · Uniform distributions · Deductibles and policy limits

You'll meet: four kinds of error (crash, wrong answer, silent, stated backwards) "ran it", "compiled" and "brute force" as checking methods wrong but silent: mutation, leaks, reading memory it shouldn't unclear vs wrong where errors cluster in hand-kept notes

Read with these questions (answer them in your head as you go; don't take notes line by line):

In one breath

We found 30 real errors on 27 of the 181 cards. Most are code that crashes or won't compile as printed, usually a name used outside its scope. Eight are wrong answers: four probability results, a shortest-path problem solved with a spanning-tree algorithm, and three that fail only on rare inputs or repeated calls. Five are silent: no crash, but the code mutates its input, leaks memory or reads memory it shouldn't. That leaves six places where a paper or a textbook fact is stated backwards. The notes are otherwise sound: at least 30 cards say outright that they checked the source's code or answer and found it right, most of them against a brute force.

Unclear or mislabelled, but not wrong

These don't change an answer. The cards fix or explain them, and they are listed here so you don't count them as errors.

  • C++ that works by luck. Insertion sort (swap(a[j], a[--j])) and palindrome cuts (reads and increments j in one expression) rely on an evaluation order C++ doesn't promise; both are right under clang. State-machine DP uses vector without including it.
  • Code that isn't there. Five graph cards call a code/graph.py that is missing from the repo (representations, flood fill, BFS, bipartite, Dijkstra); two import the third-party sortedcontainers; bit arithmetic negates with a multiplication the problem forbids.
  • Typos and labels. τ called "e" and 1\cwnd for 1/cwnd (delay); WARS expanded wrongly (quorums); "Savich" and u ∈ I (query complexity); a dropped term in a delta rule (semi-naïve); "zero one" outputs and pseudocode tagged cpp (MapReduce); C++ tagged java (interfaces); a Weibull filed under Gamma (Weibull); a density printed with the wrong sign (deductibles); 68.26/95.44/99.74% for 68.27/95.45/99.73% (kσ, normal); footnotes that point to the wrong note or to none.
  • Loose wording. p99 as "the worst 1%" (backpressure); "consumers can't exceed partitions" when the extras just sit idle (load balancing); ZooKeeper in memory "to avoid" GC (service discovery, our reading); a proof direction mislabelled (I-confluence); a self-contradicting sentence on block size (anti-caching); the adjoint method described by its forward half only (autodiff tape); a figure and its text describing two different share policies (GPU fair share); StringBuffer where modern javac emits StringBuilder or invokedynamic (compilers); the log base left unstated (algorithm vs hardware); Type I and II errors under the opposite convention (averages); "20% headroom" with two readings (sizing).
  • Right answer, assumption unstated. Whether a negative binomial counts failures or trials (negative binomial); a nonsmoker death rate the table implies but never gives (Bayes); "doors lock behind him", which hints at a variant with a different answer (first-step analysis). The chuck-a-luck formula on averages looks off but is right: −17/216, checked over all 216 rolls.

How much of the source is right

27 of 181 cards (15%) correct a real error; 154 don't. About 30 more flag something from the list above, and at least 30 say outright that the source's code or answer was checked and is right, often against a brute force on thousands of random cases. A few also make correct code leaner without calling it wrong: the quicksort stack depth, the suffix automaton's memory, bidirectional BFS growing the smaller side.

The errors cluster where you'd expect in hand-kept notes: code that was probably never run (most of cs-3's rows are name errors), and one-line summaries of long papers (cs-5 and cs-6). The worked answers in probability are mostly right; four aren't. 25 of the 154 (all of cs-7 and cs-10) had no source content to check, because the heading was empty and the card was written from references.

1 · Core model what to internalise, what to just look up

Keep it if it changes what you can explain, predict, compare, choose, build or debug. Otherwise it's reference.

Understand and remember

  • Code that was never run → names used outside their scope, missing colons, undefined helpers → it crashes on first use → cheap to catch (just run it) → which is why crashes are the biggest group (11) and most of cs-3's rows
  • A function that changes its argument (heights.append(0), board.pop()) or forgets to clean up (the LFU count map) → the returned answer is still right → example-based tests pass → the bug only shows on repeated calls or in memory → you need an invariant or a check of the input after the call
  • A one-line summary of a long paper → a qualifier gets flipped ("no" → "most" queues, truncation "guarantees" catch-up) → the claim reads fine and nothing crashes → only the paper itself can catch it → treat one-line paper summaries as leads to verify, not facts
  • Compare with a slow, obviously correct version on many random inputs → any disagreement is a bug, whatever kind it is → but a bug that fires on only a few inputs (3 of 2³¹ for Newton) needs exhaustive or targeted edge tests, not random ones
  • detail that matters Code that relies on unspecified C++ evaluation order (swap(a[j], a[--j])) happens to work under clang → it can break under another compiler or flag → listed as unclear, not wrong, because no run produced a wrong answer

3 · Retrieve from memory, card closed
  1. concept Explain why the card counts "a right answer with an unstated assumption" and "C++ that works by luck" separately from the 30 real errors.
    Check
    • an error must change an answer or fail a run
    • unstated assumptions give the right answer under the intended reading
    • evaluation-order code is correct under clang; it's a portability risk, not a wrong result
    • counting them would inflate the error rate and blur what to actually fix
  2. mechanism Walk through what happens when the source's monotonic-stack function is called three times on the same list [2, 1, 5].
    Check
    • each call appends the sentinel 0 to the caller's list
    • the answer is right each time, since one extra 0 at the end changes no area
    • after three calls the list is [2, 1, 5, 0, 0, 0]
    • fix: work on heights + [0], so the input is left alone
  3. tradeoff You have time for one checking method on a new set of notes: run every snippet, or compare each against a brute force. Which do you pick, and what does each one miss?
    Check
    • running catches the largest group (crashes) cheaply but misses wrong answers and silent bugs
    • brute force catches wrong answers and some silent ones, but costs a second implementation per problem
    • neither catches a paper stated backwards; that needs the source paper
    • neither reliably catches a bug on 3 of 2³¹ inputs; that needs exhaustive or edge-targeted tests
  4. mechanism Explain why the Cheapest Flights solution returns a plausible-looking number instead of crashing, and why that makes it harder to catch.
    Check
    • Prim builds a minimum spanning tree over the whole graph and returns its weight
    • it never reads src, dst or k, so it answers a different question
    • a number comes back, so nothing looks broken
    • only comparing against a correct shortest path with at most k stops (Bellman–Ford, k + 1 rounds: 700) exposes it

Why this step?

5 · Predict commit to an answer before revealing

The source says Y ~ U(0, 5) and asks for P(4x² + 4xY + Y + 2 = 0 has real roots). Before working it out: is the source's 2/5 too high or too low, and roughly what should a million-draw simulation print?

Reveal

Too low. Real roots need the discriminant 16Y² − 16(Y + 2) ≥ 0, i.e. (Y − 2)(Y + 1) ≥ 0, so Y ≥ 2 on (0, 5): probability 3/5. The source kept (0, 2), where the roots are complex. A 10⁶-draw simulation prints about 0.600 (one seeded run gave 0.6006).
