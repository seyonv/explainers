Problem curation by CI tracing

Also: sys.setprofile tracing, mining problems from continuous integration · How the paper manufactured about 40,000 unit-tested training problems without any human labelling, for the Codex-S stage (Sections 4.2 and 4.3).

In one breath

Run an open-source project's own integration tests with a Python profiler hook attached, record the arguments and return value of every function that gets called, and each observation becomes a unit test for that function. The project's existing test suite does the labelling for you.

Worked example: one traced call becomes one problem

1. read the project's travis / tox config -> build and test commands 2. set up the virtualenv, install dependencies, run integration tests 3. sys.setprofile(hook) records every call: slugify("Hello World!") -> "hello-world" slugify(" A B ") -> "a-b" 4. emit a training problem def slugify(text): """...""" <- docstring lifted from the source ... <- body is the reference solution assert slugify("Hello World!") == "hello-world" assert slugify(" A B ") == "a-b"

The slugify trace is illustrative — the paper gives no example. Every count is the paper's. The paper does not report how many of the ~50,000 problems survived filtering.

Why it beats the alternatives

✗ Hand-write the training problems

What HumanEval's 164 problems cost. It does not scale to the tens of thousands Codex-S needs.

✗ Scrape docstring-and-body pairs from GitHub

Barone & Sennrich's approach. Plentiful, but with no tests there is no way to check the body is correct or the docstring sufficient.

✗ Competitive-programming problems only

Excellent statements and coverage, but puzzle-shaped: they reward algorithms over following instructions. The paper says tracing “complements the puzzle nature” of these.

✓ Tracing CI runs with sys.setprofile

Real inputs and outputs from real code, verified by the project's own tests, at zero labelling cost. Yields everyday utility functions rather than puzzles — the paper notes these test instruction-following, not advanced data structures.

What does this method quietly select for?

A biased slice of code. Only functions with picklable inputs and outputs survive, which is why 40,000 came out of millions; the paper observes the survivors “tended to be the building blocks of command-line utilities”. Even builtin and library calls invoked by a project became problems.

Two caveats the paper raises. Traced projects are untrusted code that had to run inside the gVisor sandbox. And the 100-sample filter removes exactly the problems Codex-12B cannot already solve, so the curriculum is shaped by the model's current ability — the paper's stated reason is quality control (underspecified prompts, stateful problems), not difficulty targeting.
