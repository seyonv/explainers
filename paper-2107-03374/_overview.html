The problem in one breath

Nobody knew how good a large language model could get at actually writing working code, partly because the usual way of scoring generated code — comparing its text to a reference answer — says nothing about whether the code runs correctly. This paper fine-tunes GPT on GitHub Python, builds a hand-written benchmark that runs the code against unit tests, and reports what the model can and cannot do.

What they did

Stage names are the paper's own. The paper does not state the exact count of curated supervised problems; it reports 10,000 from competitive programming plus about 40,000 from continuous-integration tracing, before filtering.

pass@1 is the chance a single generated function passes all of the problem's unit tests; pass@100 is the chance at least one of 100 samples does. The abstract leads with 28.8% for Codex and 70.2% solved with 100 samples per problem. All Figure 1 samples are drawn at temperature 0.8.

Why it matters / what to be careful about

✓ Why it matters

Functional correctness, scored by running unit tests, replaces BLEU-style text matching as the benchmark for code generation. HumanEval is released publicly.

Drawing many samples is a surprisingly strong strategy: 100 samples lift Codex-S-12B from 37.7% to 77.5%.

Even without an oracle, ranking 100 samples by mean token log-probability solves 44.5% — a usable deployment recipe.

✗ What to be careful about (the paper's own limitations)

Not sample efficient: it trains on hundreds of millions of lines, far more code than any developer sees, and a strong intro-CS student would still beat Codex-12B.

Performance falls roughly 2–3× per extra chained instruction in a docstring, and it mis-binds operations to variables.

Misalignment: given subtly buggy context, it writes worse code than it is capable of, and the gap grows with model size. It can also emit insecure or biased code.

Understand and remember

  • Text-overlap metrics can't tell a working program from a near-copy with one flipped operator → grade by running unit tests (functional correctness) → needs hand-written, uncontaminated problems (HumanEval) and a sandbox to run untrusted code → pass@k becomes the headline number
  • Code is judged by tests, not taste → many independent samples + a filter beats one careful sample → pass@k rises with k and the best temperature rises with it → but only an oracle (tests) can pick the winner, so without tests you fall back to ranking by mean log-probability
  • GitHub Python is mostly not 'docstring → function' → a second fine-tune on ~50k task-shaped problems (Codex-S) → better pass@k at every size, but a narrower distribution that needs a higher temperature for diversity
  • The model continues its prompt rather than following intent → long chained docstrings decay roughly 2–3× per step and buggy context yields buggier code → these limits are about specification and alignment, not raw scale
  • detail that matters pass@k is estimated from n = 200 samples with an unbiased formula, evaluated in a numerically stable product form → numbers are comparable across papers that sampled different amounts, and the estimator never overflows

  2. mechanism Walk one HumanEval problem through the whole pipeline: from the prompt the model sees to the number that lands in pass@100.
    Check
    • the model gets the signature and docstring
    • 200 bodies are sampled at the chosen temperature inside a 0.95 nucleus
    • each runs in a gVisor sandbox against the problem's unit tests; c of them pass

5 · Predict commit to an answer before revealing

Suppose the authors had kept BLEU as the headline metric and still trained Codex-S. Would Codex-S's gain over Codex have been visible, hidden, or possibly reversed? Commit, then reveal.

Reveal

Possibly hidden or even reversed. Codex-S learns to write bodies that work for docstring-shaped tasks, not bodies that textually match a reference. Correct programs with a different algorithm score near 0 BLEU, and near-copies with one flipped operator score high, so a metric that can't separate the two can't reliably see a gain in correctness either.
