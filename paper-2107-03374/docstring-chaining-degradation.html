Docstring chaining degradation

Also: the synthetic building blocks, chained components, operation-to-variable binding · The paper's sharpest measured limitation: chain more instructions into one docstring and Codex-12B's pass rate falls by roughly a factor of 2–3 per component (Section 6, Figure 11, Appendix C).

In one breath

The authors built 13 one-line string operations, each with a plain-English description and a one-line Python implementation, then concatenated them into longer docstrings with matching longer bodies. Difficulty per step is constant by construction — so any drop measures the model's ability to follow a list, nothing else.

The related failure: binding operations to variables

prompt given to Codex-12B (Section 6) def do_work(x, y, z, w): # Add 3 to y, then subtract 4 from both x and w. # Return the product of the four numbers. what it produced what the docstring asked for t = y + 3 y + 3 done u = x - 4 x - 4 done v = z * w w - 4 never decremented return v x*y*z*w returned z*w instead

Quoted from Section 6, reformatted. The paper links this to the same difficulty text-conditional image models have binding attributes to objects (Ramesh et al., 2021), and says it worsens as the number of operations and variables in the docstring grows.

How it differs from related ideas

✗ “The problem was just harder”

Ruled out by construction. Every block is one line of trivial string manipulation; only the count changes.

✗ Human-like difficulty scaling

The paper's point of contrast: a programmer who can chain two blocks can chain any number. Exponential decay is “uncharacteristic of a human programmer”.

✗ Sample inefficiency (the other limitation)

Also in Section 6, but about training cost, not inference. A strong intro-CS student beats Codex-12B despite seeing a tiny fraction of the code.

✓ Exponential decay in chain length

Consistent with per-step independence: if each step succeeds with probability q, a chain of n succeeds with qn. A factor of 2–3 per component implies a per-step success rate of roughly 0.33–0.5.

Does sampling 100 times fix this?

Not at any useful chain length. If pass@1 decays exponentially, pass@k does too — it just starts from a higher number. The measurement is single-sample pass rate on synthetic tasks, so treat the exact percentages as a shape, not as a prediction for real docstrings.

The paper is careful about scope elsewhere: this is a synthetic probe of one axis (chain length) on one operation type (string manipulation) for one model (Codex-12B). It does not show whether the decay rate improves with model size. What it does establish is qualitative and load-bearing for the rest of the paper: Codex “struggles to parse through increasingly long and higher-level or system-level specifications”, which is why Section 7 treats it as unsuited to synthesising complex systems.
