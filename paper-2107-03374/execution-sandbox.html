Execution sandbox

Also: gVisor container runtime, eBPF firewall rules · The paper runs every model-generated program, and every traced GitHub project, inside gVisor containers behind eBPF firewall rules (Section 2.3; reused for CI tracing in Section 4.2).

Prime · 2 minutes before you read

The problem: Grading by execution means running thousands of programs nobody has read, some from a model and some scraped from GitHub, where environment-altering code is known to exist. Run them on a plain host and one bad program can alter the host or leak data.

Where it fits: The infrastructure under functional correctness. HumanEval's tests only mean something if the samples can be run safely, and the same sandbox later hosts CI tracing of untrusted GitHub projects.

In one breath

Grading code by running it means executing programs nobody has read — some generated by a model, some scraped from GitHub, where malicious code is known to live. The sandbox is the layer that lets the benchmark run those programs without letting them touch the host or the network.

What the sandbox is holding back

Layout is a redrawing of the paper's prose; the paper gives no architecture diagram and no numbers here. It does note the choice was constrained by staying “idiomatic” with Kubernetes and cloud services, since that is what OpenAI's training infrastructure runs on.

Why it beats the alternatives

✗ Just run it on the machine

Generated programs are often incorrect and scraped ones have unknown intent. GitHub is known to contain programs that alter their environment (Rokon et al., 2020).

✗ A plain Docker container

The paper's stated objection: container runtimes like Docker share host resources with containers, so a malicious container could compromise the host.

✗ Static analysis instead of execution

Avoids running anything, but then you are back to judging code without executing it — which is the thing functional correctness exists to replace.

✓ gVisor plus eBPF firewalling

gVisor emulates host resources, putting a security boundary between host and container; eBPF rules cover the network side that container isolation does not.

Is a sandbox the same as being safe?

No. The sandbox protects the evaluation infrastructure, not the eventual user. Nothing here stops Codex from suggesting insecure code to a developer — that is a separate finding in Appendix G.3, where models of every size frequently generate clearly insecure cryptographic configurations.

The paper also does not report any escape testing, residual-risk assessment or performance cost for this sandbox. It describes the design and its goals; treat it as an engineering note, not a verified security claim. The released human-eval package ships execution disabled by default for the same reason.

Understand and remember

  • Functional correctness = run untrusted code → generated code is often wrong and scraped code has unknown intent → isolation is a precondition of the benchmark, not an add-on
  • Docker containers share the host kernel → a malicious program can reach it through syscalls → gVisor emulates host resources so syscalls never hit the real kernel → a security boundary between container and host
  • Container isolation doesn't cover the network → eBPF rules deny all inbound and outbound except experiment control → no exfiltration and no attacks on neighbouring services
  • The sandbox protects the evaluation infrastructure → nothing in it stops Codex from suggesting insecure code to a developer → user-side safety is a separate problem (Appendix G.3)
  • detail that matters Kubernetes/cloud-idiomatic design was a constraint → gVisor fits as a container runtime → the security choice was shaped by existing infrastructure, not chosen in isolation

5 · Predict commit to an answer before revealing

A sample passes all its unit tests but, as a side effect, tries to download a file from the internet during the test run. In this sandbox, does it still count as correct? Commit, then reveal.

Reveal

If the download isn't needed for the tests, yes: the network call is blocked by the eBPF rules, but pass/fail depends only on the test assertions. The sandbox contains side effects; it doesn't grade them. If the code needs the download to produce its output, it fails.
