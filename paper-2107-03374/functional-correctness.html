Functional correctness

Also: execution-based evaluation, unit-test correctness · This paper's definition of a correct sample: it must pass the problem's unit tests, not match a reference solution (Section 2.1, evidence in Figure 8).

Prime · 2 minutes before you read

The problem: Two correct programs can share almost no text, and a wrong one can differ from the answer key by one character. Any grade based on resemblance to a reference will reward the wrong one.

Where it fits: The definition everything else in the deck rests on: pass@k counts samples that are correct in this sense, HumanEval supplies the tests, and the sandbox makes running them safe.

In one breath

Instead of asking “how similar is this code to the answer key?”, functional correctness asks “does this code do the job?” — scored by running it against tests. The paper argues this is the only honest way to grade code, because two correct programs can look nothing alike.

Worked example: three samples for the same docstring

reference def has_dup(xs): return len(set(xs)) != len(xs) sample A def has_dup(xs): return len(set(xs)) != len(xs) sample B def has_dup(xs): for i, x in enumerate(xs): if x in xs[i+1:]: return True return False sample C def has_dup(xs): return len(set(xs)) == len(xs) # inverted

Samples and the overlap column are illustrative, written to make the ordering visible; the 7.7 figure is HumanEval's reported average number of tests per problem. A text-similarity score ranks these A > C > B. Functional correctness ranks them A = B > C. The paper's Figure 8 shows the real version of this: for 4 random HumanEval tasks, the BLEU distributions of correct and wrong Codex-12B samples are not cleanly separable.

Why it beats the alternatives

✗ Exact match against a reference

Any correct program that is not the reference scores zero. Sample B above is thrown away.

✗ BLEU

Built for translation. Ren et al. (2020) found it misses code-specific semantics; the paper shows functionally inequivalent samples often out-score equivalent ones.

✗ Human judging of code samples

What natural-language generation does. Slow and unrepeatable — the paper only resorts to it for Codex-D docstrings, and then just 10 samples per problem.

✓ Functional correctness via unit tests

Automatic, repeatable, and the criterion human developers actually use. Also what makes sampling 100 times and picking a passing program a meaningful strategy.

Is functional correctness always enough?

No, and the paper is explicit about the catch. Correctness is only as good as the test suite: Qi et al. (2015) found that repair systems “passed” weak suites by deleting the failing functionality. The paper notes human-written suites have limited, targeted coverage, which “does not always work well against an algorithm”.

It also says nothing about efficiency, readability or security. On APPS the paper has to report separately how many solutions pass every test but time out at 3 seconds, and Appendix G.3 shows Codex writing code that passes while using insecure cryptography.

Understand and remember

  • Many programs compute the same function → a reference is just one of them → similarity to it rewards copying, not correctness → run the code on tests instead
  • A one-character change (!= → ==) can invert behaviour while keeping near-total overlap → text metrics rank a wrong sample above a correct different algorithm → only execution sees the flip
  • Correctness = passing these tests → weak or narrow suites let wrong programs pass (Qi et al.: repairs that delete functionality) → the metric is only as strong as its tests
  • Tests check input/output behaviour only → efficiency, readability and security stay invisible → APPS needs a separate timeout column, and insecure crypto can still pass
  • detail that matters Grading by execution means running untrusted code → it requires a sandbox and trusted tests → cost and safety move from the grader's judgement to infrastructure

Reference only

  • Ren et al. (2020) on BLEU missing code semantics
  • HumanEval's 7.7 tests per problem on average
  • Qi et al. (2015) on weak program-repair suites

5 · Predict commit to an answer before revealing

A sample for has_dup returns True for every input. HumanEval-style tests for this problem happen to include only lists that contain duplicates. Does the sample count as correct, and what does that do to pass@k? Commit, then reveal.

Reveal

It counts as correct: it passes every test it's given. pass@k goes up for a program that's plainly wrong, which is exactly the Qi et al. failure. Functional correctness moves the question from 'does it look right' to 'are the tests good enough', which is the gap EvalPlus later fills.
