Numerically stable pass@k

Also: the term-by-term product form, the Figure 3 pass_at_k script · The paper notes that evaluating its pass@k estimator (Eq. 1) directly "results in very large numbers and numerical instability", so Figure 3 gives an algebraically simplified numpy version. Used for every pass@k number in the paper (n = 200, k ≤ 100).

Prime · 2 minutes before you read

The problem: The unbiased pass@k estimator is a ratio of binomial coefficients. At n = 200 those coefficients are enormous, and computing them through factorials in floating point overflows to inf, giving nan instead of a probability.

Where it fits: The implementation of pass@k, used for every number in the paper. It revisits the estimator from the pass@k card and changes only how it's evaluated.

In one breath

The pass@k estimator is a ratio of two binomial coefficients, and at the paper's scale those coefficients are astronomically large even though their ratio is an ordinary probability. Cancelling the factorials first turns the whole thing into a product of small factors between 0 and 1, which floating point handles exactly as well as any other arithmetic.

The algebra: the same number, a different route

Eq. 1 pass@k = 1 - C(n-c, k) / C(n, k) <- ratio of huge integers C(n-c, k) (n-c)! (n-k)! n k --------- = --------------- = PROD ( 1 - - ) C(n, k) n! (n-c-k)! i=n-c+1 i Figure 3 pass@k = 1 - prod(1.0 - k / arange(n-c+1, n+1)) guard: if n - c < k: return 1.0 # C(n-c,k) = 0

The identity is exact, not an approximation: every factorial cancels. Each factor 1 - k/i lies in [0, 1], so no intermediate value is ever larger than 1.

Worked example: one HumanEval problem at the paper's settings, n = 200, c = 8, k = 100

Why the direct route breaks: magnitude of the intermediates, n = 200

Log scale, bar length proportional to the exponent. Whether the direct route overflows or merely loses precision depends on how the binomials are computed — factorials blow past float64 immediately, while an exact-integer math.comb survives at n = 200 and fails at larger n. The paper states the problem qualitatively and does not give an error analysis; the overflow thresholds here are added context.

Why it beats the alternatives

× Factorials, then divide

Compute n!, (n-c)!, (n-k)!, (n-c-k)! in floating point and combine. At n = 200 the first factorial is already 1e375: it becomes inf, and inf/inf is nan.

× Exact big-integer binomials

Correct, and fine at n = 200, but it builds 59-digit integers to return a number near 1, is slow inside a loop over 164 problems × many k values, and still overflows once converted to float at larger n.

× Approximate with 1 - (1 - p̂)k

Cheap and stable, using p̂ = c/n as the pass@1 estimate. But the paper shows in Appendix A that this is biased, so it does not estimate the same quantity.

✓ Term-by-term product (Figure 3)

Exactly equal to Eq. 1, evaluated as c multiplications of factors in [0, 1]. No overflow, no big integers, one vectorised numpy line, plus a guard returning 1.0 when n - c < k.

Worth knowing

This is a numerics fix, not a statistics fix. It does not change the estimator, its unbiasedness, or its variance — it only changes how the same expression is evaluated, so it can never explain a difference between two papers' pass@k numbers.

The product can underflow to 0.0 when c is large, which returns pass@k = 1.0. That is harmless here, because the true value is then within float precision of 1 anyway. The failure the paper is guarding against is the opposite one: large intermediates. Note also that Eq. 1 is a per-problem quantity; the reported pass@k is its mean over the 164 HumanEval problems.

Understand and remember

  • C(n−c,k)/C(n,k) written out → the factorials cancel → the ratio becomes Π_{i=n−c+1..n} (1 − k/i) → the same exact value with no intermediate above 1
  • Factorials at n = 200 reach about 10³⁷⁵ → float64 tops out near 1.8×10³⁰⁸ → inf/inf = nan → the naive route fails at exactly the paper's settings
  • One factor per correct sample → c multiplications of numbers in [0,1] → fast, vectorisable, no big integers
  • Same formula, different evaluation → estimator bias and variance unchanged → a numerics fix can never explain two papers' different pass@k
  • detail that matters When n − c < k every draw contains a correct sample → return 1.0 immediately → also avoids a factor 1 − k/i ≤ 0 that would otherwise appear

5 · Predict commit to an answer before revealing

With n = 200 and k = 100, what does the product form return when c = 150? Does the code even reach the product? Commit, then reveal.

Reveal

It doesn't reach the product: n − c = 50 < k = 100, so the guard returns 1.0. Any 100 draws from 200 must include at least 50 correct samples. Without the guard, the product would include factors 1 − 100/i for i ≤ 100, which are ≤ 0.
