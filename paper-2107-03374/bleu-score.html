BLEU score

Also: bilingual evaluation understudy, match-based / fuzzy-match metric, n-gram overlap; code variant CodeBLEU · This paper's role for it: the foil. Prime · 2 minutes before you read

The problem: BLEU was the standard way to score generated text against a reference. For code it can reward a program that's wrong by one character and punish a correct program written differently.

Where it fits: The foil for the whole paper. Functional correctness and pass@k exist because this metric fails; this card shows exactly how, with the same has_dup samples.

In one breath

BLEU grades a generated string by how many of its n-grams (runs of 1 to 4 tokens) also appear in a reference string, times a penalty for being too short. It was built for machine translation, where many phrasings are near-equivalent — but in code, a one-character change can flip behaviour while barely moving the overlap.

Worked example: three samples, one docstring

reference def has_dup(xs): return len(set(xs)) != len(xs) 14 tokens A return len(set(xs)) != len(xs) identical B for i, x in enumerate(xs): correct, different algorithm if x in xs[i+1:]: return True return False C return len(set(xs)) == len(xs) wrong: one operator flipped
BLEU = BP · exp( ¼ ∑n=1..4 log pn ) pn = clipped n-gram matches / n-grams in sample

Illustrative example and tokenisation (whitespace plus punctuation split); the BLEU numbers are actually computed from the counts shown. C: exp(¼[ln .929 + ln .846 + ln .750 + ln .636]) = 0.783. B scores 0 because no 4-gram matches and no smoothing is applied. BLEU ranks these A > C > B; running the tests ranks them A = B > C. The wrong sample outscores the correct one by 78 points.

What figure 8 shows

Schematic redraw, not the paper's data: Figure 8 plots BLEU densities for correct and wrong Codex-12B samples on 4 random HumanEval tasks. The paper's point is only that the two distributions are “not cleanly separable” — it does not report a separation statistic, an AUC, or by how much the means differ. Every wrong sample is guaranteed functionally inequivalent to the reference, yet many of them sit in the high-BLEU region.

How it differs from related ideas

✗ Exact match

Scores 1 only for a character-identical program. Sample B is discarded; the metric cannot see the space of functionally equivalent programs at all.

✗ BLEU

Fuzzy overlap, so B still scores 0 and C scores 78. Ren et al. (2020) found it fails to capture code-specific semantics.

✗ CodeBLEU

Ren et al.'s repair: add weighted keyword, AST and data-flow matching. Still structural, not behavioural. This paper mentions it via CodeXGLUE but never computes it.

✓ Functional correctness (pass@k)

Run the sample against unit tests. A and B both pass, C fails — the ordering developers actually care about, and what the paper benchmarks on.

So is BLEU useless?

No — and the paper's claim is narrower than “BLEU is broken”. It says improvements in BLEU may not indicate improved functional correctness, on the evidence of one figure covering 4 HumanEval tasks and one model. It does not claim BLEU is uncorrelated with correctness, and it reports no BLEU numbers for its own models.

BLEU still earns its keep where it was designed to work: natural-language translation and summarisation, and any setting where you have references but no executable tests — code search, docstring generation, or languages and codebases you cannot safely run. It is also cheap and needs no sandbox, whereas functional correctness needs test suites you trust and an execution sandbox, and stays blind to efficiency, readability and security.

Understand and remember

  • BLEU = brevity penalty × geometric mean of 1- to 4-gram precisions → it counts shared token runs with a reference → a one-token change breaks only the few n-grams that include it → sample C keeps 78.3
  • Geometric mean with no smoothing → any p_n = 0 makes BLEU 0 → a correct program with a different algorithm and no shared 4-grams scores 0
  • Correct and wrong Codex samples overlap in BLEU (Figure 8) → BLEU gains may not mean correctness gains → the paper grades by tests instead
  • BLEU needs only references, no execution → cheap, no sandbox → still useful for docstrings, translation, or code you can't safely run
  • detail that matters CodeBLEU adds keyword, AST and data-flow matching → closer to structure but still not behaviour → it would still miss a flipped == that keeps the AST shape

5 · Predict commit to an answer before revealing

Apply 'add-one' smoothing to sample B's precisions (so 0/22 becomes 1/23). Would B's BLEU rise above C's 78.3? Commit, then reveal.

Reveal

No. Smoothing only rescues B from exactly 0; its precisions (5/25, 2/24, 1/23 and a smoothed ~1/23) are all tiny, so its geometric mean stays in the single digits. The ranking C over B is caused by low overlap, not by the zero, so smoothing can't fix what the paper objects to.
