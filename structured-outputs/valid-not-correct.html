Valid is not correct

Also called schema compliance vs semantic accuracy, or "right shape, wrong answer". The paper keeps the two apart: its compliance rate (Table 4) only asks whether the output passes the schema, and it measures task accuracy separately (Table 8). The cookbook's version is the McFlurry case on its handle-exceptions page.

Prime · 2 minutes before you read

The problem: Your constrained pipeline reports 100% valid output, and still ships wrong orders. A grammar can only ask "is this allowed here?", never "is this true?", so a dashboard that counts valid outputs will hide exactly the errors that matter to the business.

Where it fits: Last card of part 1, and the distinction the whole course keeps returning to. The schema card defined what "valid" means; this card separates it from "correct" before you learn how grammars work, so you never mistake one for the other.

In one breath. A grammar can guarantee that the output parses and fits the schema. It can't check that the values are true. "total_usd": 60 passes {"type": "number"} just as easily as the right answer, 54. So "30 out of 30 valid" tells you nothing about how many answers were right.

Filled in: 3 × 12 + 1 × 18 = 54. The model does the reading (which items, how many), where the grammar helps. Your code does the maths, where the grammar can't.

When the right answer is "no order at all"

The cookbook's warning: force a resume schema on "I want a McFlurry" and "you'll still get a JSON, but what would be ideal here is an Exception." The same thing happens with our order schema. There were 3 runs of each, seeds 3000–3002, measured on M3, qwen3.5:4b:

Without the escape hatch, minItems: 1 forces at least one real SKU, so the model makes up an order (and gets 2 of its 3 sums wrong). The escape-hatch branch is a common practice, not something the paper or cookbook prescribes. This test changed the prompt and the schema together, with 3 runs each, so it shows the idea works here, not how often.

Why it beats the alternatives

✗ Trust the grammar

It gave 30/30 valid and shipped 8 wrong totals, plus a made-up order for a McFlurry. It checks total_usd is a number, and 60 is a number.

✗ Add more schema constraints

"minimum": 0 or a maximum still lets 60 through. JSON Schema has no keyword for "equals the sum of qty × price", and "const": 54 only works if you already know the answer.

✗ Ask the model to double-check

The same model does the same arithmetic again and costs a second pass of tokens. It can repeat the mistake, or "fix" a right answer. (Not tested on this card.)

✓ Validate values in code, compute derived fields

Ask the model only for what it has to read (SKUs, quantities). Compute total_usd from your price list and check values against business rules. Here that fixes all 8 wrong runs: 22 + 8 = 30/30.

So did the grammar make the answers more correct?

Maybe, but 30 runs can't show it. 22/30 vs 15/30 looks like a big gap. A two-sided Fisher exact test on those counts gives p ≈ 0.11, and the 95% ranges overlap (Wilson: 56–86% vs 33–67%). Treat it as a hint, not a result, and don't read it as "grammars make models smarter". This card didn't test why the numbers differ. The paper's own quality test (Llama-3.1-8B, GSM8K) found constrained engines at 81.6–83.8% against 80.1% prompt-only. Even the best one got about 1 in 6 wrong, in valid JSON.

The grammar guarantees syntax, never truth. Computing the value in code only works when there's a rule to compute it from (sums, dates, IDs you can look up). For judgement fields, like which product the customer meant or a sentiment label, you need other checks: a labelled eval set, a second model, or a person. An escape hatch also adds a branch that every consumer of the JSON has to handle. Check your provider supports anyOf first: the paper found OpenAI's and Gemini's structured outputs support only a subset of JSON Schema features (low declared coverage, near-100% compliance on what they do support).

Understand and remember

  • A grammar checks each token against the schema → 60 is a number just like 54 → wrong values are schema-valid → "30/30 valid" says nothing about how many are right
  • The model reads items and quantities well but adds badly → move the sum to code from your price list → 22/30 correct becomes 30/30, because every wrong answer had the right items
  • A strict schema has no way to say "not an order" → minItems: 1 forces at least one SKU → the model invents an order → add an out-of-scope branch so refusing is a valid output
  • n = 30 per arm → 22 vs 15 gives p ≈ 0.11 with overlapping ranges → the difference is a hint, not evidence that grammars make models smarter

4 · Compare against what you already know

vs The prompt-and-repair loop: Computing the total in code and running a repair loop with a value check both target wrong values. What is fundamentally different, and when does each one win?

Check
  • computing replaces the model's value; the repair loop asks the model to try again
  • computing fixed 30/30 in one call; the repair loop reached 26/30 at 1.67 calls per request, with 4 stuck on 60 or 78
  • compute when a rule exists; repair when the check is possible but the value can't be computed (e.g. a lookup the model must choose)

vs Over- and under-constrained: A wrong total of 60 and an engine that lets an empty items array through are both "bad output". Which one is a grammar failure, and which one no grammar could fix?

Check
  • the empty array is an under-constrained engine: it breaks the schema, so a correct grammar would block it
  • 60 is schema-valid, so even a perfect grammar allows it
  • one is fixed by a better engine or a validator; the other only by a value check

5 · Predict commit to an answer before revealing

You rerun the 30 constrained calls at temperature 0 with no other change. Predict: does the correct count go to 30/30, stay near 22/30, or can't you tell?

Reveal

You can't tell from the setup alone, but it will be either 0/30 or 30/30, because greedy decoding gives all 30 runs the same answer. The sampling card ran 3 greedy calls and got the right total every time, so for this prompt the greedy path happens to be correct. Temperature changes how often the model's wrong beliefs surface; it can't fix a model whose top guess is wrong.
