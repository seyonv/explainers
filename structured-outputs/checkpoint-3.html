Checkpoint 3: trusting it in production

Ties together valid is not correct, coverage and compliance, over- and under-constrained, the repair loop and where constrained decoding runs, with JSON Schema underneath: what a "guaranteed" structured output actually guarantees, and what you still have to check.

How to use this page. Close the cards. Answer each question in writing before opening its Check. Several questions describe a production symptom; the first job is naming which idea it is, the second is the fix.

1 · Mixed retrieval

  1. which concept?Your dashboard shows 100% schema-valid orders for a week, yet finance finds wrong totals. Which idea applies, and what two design changes close most of the gap?
    Check
    • valid is not correct: 60 passes {"type": "number"} as easily as 54 (30/30 valid, 22/30 right on the M3)
    • compute derived fields in code from your own data (22/30 → 30/30), and check values against business rules
    • count value errors separately from schema errors on the dashboard

    Missed it? Reopen valid is not correct, "The fix: don't let the model do the arithmetic".

  2. Turn Llamacpp's GitHub-Hard row (declared 0.61, empirical 0.39) into counts per 100 schemas, compute its compliance, and say what kind of engine behaviour the gap represents.
    Check
    • 39 rejected up front, 61 accepted, 39 valid, so 22 accepted then failed
    • compliance = 0.39 ÷ 0.61 ≈ 0.64 (the paper prints 0.63; its columns are rounded)
    • the gap is outputs from accepted schemas that still didn't validate: timeouts or a constraint that didn't match the schema

    Missed it? Reopen coverage and compliance, "The formula".

  3. which concept?Engine X lets through "items": [] even though the schema says minItems: 1. Engine Y never lets the model write total_usd before items. Name each failure, and say which one breaks the guarantee you were paying for.
    Check
    • X is under-constrained: it allows an invalid output. That breaks the validity guarantee
    • Y is over-constrained: it blocks a valid output (key order doesn't matter in JSON Schema). Validity holds; options and possibly quality are lost
    • either way, keep a real validator on every output

    Missed it? Reopen over- and under-constrained, "The two failures as sets".

  4. A repair loop's checker passes a call with p = 15/30. What are the expected calls per request and the chance of three independent failures? Why did the real run have more stuck requests than that independence suggests?
    Check
    • E[calls] = 1/p = 2.00; (1 − p)³ = 0.125
    • the observed 4/30 stuck matched the number, but not the mechanism
    • repairs in one chat see the earlier wrong answer and repeat it (60 or 78 again), so they aren't independent; fresh chats at temperature above 0 re-roll

    Missed it? Reopen the repair loop, "What the loop does with wrong-but-valid values".

  5. which concept?You send the order schema, with qty minimum: 1, to a hosted API whose SDK silently drops minimum. Which idea applies, and what does your pipeline need?
    Check
    • declared vs enforced: the provider accepts the schema but enforces only its subset
    • the guarantee now covers the shape, not qty ≥ 1
    • re-validate every reply against your full schema with jsonschema, and send a repair or reject on failure

    Missed it? Reopen where it runs, "Hosted APIs", and coverage, "True".

  6. Under minimum: 5, the model wrote qty 30 for "three bottles". Is that engine over-constrained, under-constrained, or neither? What is actually going on?
    Check
    • neither: the engine enforced the schema exactly, and 30 is a valid value
    • the schema and the input disagree, so the mask pushed the model onto a valid but wrong number
    • enforcement protects validity, not truth; the fix is the schema (or a check on the value), not the engine

    Missed it? Reopen JSON Schema, the "Number range" row, and valid is not correct.

  7. OpenAI's strict mode scored 1.00 compliance on GitHub-Hard. Explain why a team could still be right to reject it.
    Check
    • 1.00 compliance means it refuses what it can't do: 91 of 100 GitHub-Hard schemas were rejected up front
    • if your schema is among the rejected, you get an error, not an output, and need another route (prompt + repair, or self-hosting)
    • compliance only speaks for the schemas it accepted; coverage decides whether yours is one of them

    Missed it? Reopen coverage and compliance, "Is 100% compliance the one to pick?".

3 · Project: an acceptance harness and a pipeline for the store order

What it reinforces: keyword enforcement (JSON Schema), coverage and compliance (coverage), too strict vs too loose (over/under), value checks (valid is not correct), the loop and its price (repair loop), and what your stack enforces (where it runs).

  1. Probe set. Write 8 probes for the engine you use. Three valid instances it must be able to write: the correct order; the same with total_usd first; the same pretty-printed. Three invalid ones it must block: "items": []; an unknown SKU; "qty": 0. Two keywords it may accept but ignore: maximum: 50 on total_usd, and multipleOf: 7 on an integer.
  2. Run. For each probe, prompt the model toward that output 3 times with the grammar on, and validate every reply with jsonschema (format checks on). Label each probe: correct acceptance, correct rejection, over-constrained, or under-constrained.
  3. Value layer. Write check(order, prices): known SKU, qty ≥ 1, total equal to Σ qty × price. Add the out-of-scope branch (anyOf with {"out_of_scope": string}) and test it on "I want a McFlurry".
  4. Pipeline. Draw it: grammar or strict mode → re-validate against the full schema → compute the total in code → one repair only for failures code can't fix → fresh chat if a repair repeats itself.
  5. Price it. Using the course's M3 numbers, compare three designs per request: prompt-only with a value-check repair loop; grammar alone; grammar with the total computed in code. Give calls per request, correct out of 30, and median time.
Done when: you have an 8-row probe table with a label per probe, a check function that flags wrong totals, a pipeline diagram, and a 3-row price table. For Ollama, your labels agree with what the cards measured (below), or you can explain every disagreement.
Check: what the cards measured (M3, qwen3.5:4b, Ollama 0.34.2)
  • Probes on Ollama: empty items blocked (the model invented an item instead); unknown SKU blocked (swapped to BW-CITRUS: valid, wrong); total_usd first never written (over-constrained on key order, harmless here); indentation allowed; qty: 0 should be blocked, since integer minimum was enforced; maximum on a number and multipleOf accepted but not enforced (under-constrained: 54 passed maximum: 50, and {"n": 10} came back under multipleOf: 7).
  • McFlurry: without the escape hatch, 3 of 3 runs invented an order; with it, 3 of 3 returned out_of_scope.
  • Price table: prompt-only + value-check repair: 1.67 calls per request, 26/30 correct, about 1.67 × 5.53 ≈ 9.2 s (not timed directly). Grammar alone: 1 call, 22/30 correct, 2.72 s median. Grammar + total in code: 1 call, 30/30 correct, 2.72 s median.
