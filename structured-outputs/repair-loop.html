The prompt-and-repair loop

Also called the unconstrained method, parse-and-repair, retry with feedback, or "reask" (Instructor, Pydantic AI and BAML style). The cookbook's version (unconstrained-method page) wraps the model in a control loop: a careful prompt, then clean, parse and validate the text, feed any error back, and give up after 3 repairs × 3 fresh starts. The paper calls this setup "LM-only" and notes under-constrained engines "often necessitat[e] additional post-processing or retry logic".

In one breath. Don't touch the decoder. Ask nicely for JSON, then check the answer in code, and if it fails, show the model its own mistake and ask again. Each extra try is a whole new model call, so it works well when the first try usually passes, and it only catches the mistakes your checker knows to look for.

The pipeline, as the cookbook writes it

Grey = extra work you pay for. In the cookbook's code each of the 3 inner tries is one llm.chat call, so "3 repair attempts" means 1 first answer + 2 repairs per chat, and the loop stops at 9 calls. The cookbook's own example is an internal expense bot with a person checking the output, not the store chatbot.

What the loop does with wrong-but-valid values

With a schema-only checker, 29/30 answers pass on the first call and 14 of 30 ship with a wrong total (60, 66 or 78 instead of 54). Only the one invalid answer triggers a retry; for the other 14, nothing failed. So I added a value check (total must equal qty × price from the list, without telling the model the answer) and re-ran the cookbook's inner loop, up to 3 calls in one chat, on the 15 seeds that were wrong or invalid. The totals match, but the mechanism doesn't: the 4 stuck chats kept writing 60 or 78 in each repair, so a repair is not a fresh coin flip. Only fresh retries (step 6, not run here) would re-roll them. Every first call reproduced the recorded total for its seed. Seed 1007 (the bare array) needed 3 calls: its first repair still had extra unit_price keys, which my strict jsonschema check rejected; the cookbook's allow-list would have dropped them silently. Rough time cost, not timed: 1.67 × 5.53 s median per call ≈ 9.2 s per request, vs 2.72 s median with the grammar on and no value check. If your code can compute the total, just compute it (see valid-not-correct) instead of asking again.

Why it beats the alternatives, when you can't use a grammar

✗ Single-shot parse

Call once, json.loads, hope. Locally that passed 7 of 30 times, because the model wraps answers in fences. One failure is one failed request.

✗ Constrained decoding

30/30 valid here, and usually the better pick. But it needs logits or a provider feature, and closed APIs support only part of JSON Schema (paper: OpenAI declares 0.30 coverage on GitHub Easy, Llama-3.2-1B setup).

✗ A person fixes every failure

Catches wrong values a schema can't, but costs minutes per request instead of seconds. The cookbook keeps a human for review in its expense bot, not as the repair step.

✓ Prompt, check, repair, retry

Works with any model and any checker you can write in code, including value checks a grammar can't express. Here it took 15 → 26 correct of 30 for 1.67 calls per request.

When should you use it?

Good fit. Closed models or endpoints with no schema support; output a person reads and only needs to "loosely adhere to schema" (cookbook); schemas built on the fly, where the cookbook says constrained decoding's first-use cost (milliseconds to seconds) isn't amortised; and checks that no grammar can hold, like "the total matches the price list".

Poor fit. Machine consumers at high volume. The cookbook recommends constrained decoding there, because failed answers "need regeneration, which increases latency linearly with the error rate". Locally, a grammar gave 30/30 valid in one call at 2.72 s median, while this loop averaged 1.67 calls. The loop also only catches what the validator checks: with a schema-only checker, all 14 wrong totals would have shipped. Best of both is common: a grammar for the shape, plus a value check and one repair for the meaning.
