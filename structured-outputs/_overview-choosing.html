Choosing a method and a tool

Overview card, decision guide. Also called picking a structured-outputs stack: method, grammar backend, inference engine or hosted API. The whole-picture card is structured outputs: the whole picture. Every number here comes from the course's cards, and each row says whose number it is.

Prime · 2 minutes before you read

The problem: There are a dozen ways to get structured output: prompt and repair, JSON mode, provider strict modes, Ollama, vLLM with three backends, and more. Choosing by popularity or by one benchmark number picks a tool whose failure mode you didn't plan for: a schema the API rejects, a compile on every request, or a keyword quietly ignored.

In one breath

Four questions settle almost every choice. Who reads the output, a machine or a person? Can you reach the model's logits, meaning self-hosted or a closed API? Is the schema fixed or new on every request? And does your schema use hard features, such as recursion, oneOf, counts or patterns? There is no single formula here. The answer is a path through those questions.

Green boxes are where you land. The grey one is the only route with no guarantee. Question 4 sits under every self-hosted route: whichever engine you pick, check it accepts and enforces your schema's keywords.

Words people use

Static schema vs dynamic schema

Static means one schema used for many requests, so compile cost is paid once. Dynamic means built per request (for example from a CSV header), so compile cost is paid every time. This single question separates XGrammar from llguidance.

Tool / function calling vs structured outputs

These use the same mechanism with a different wrapper. Tool calling constrains the arguments of a named function; structured outputs constrains the whole reply. Strict tool use on the hosted APIs applies the same schema subset.

Backend vs library

A backend (Outlines-core, llguidance) builds masks. A library (Outlines, Guidance, Instructor, BAML) wraps prompting, caching and parsing into typed objects. Instructor and BAML are prompt-and-retry libraries, not mask engines.

✓ Declared vs enforced

An engine "supporting" a keyword can mean it silently ignores it. Locally, Ollama accepted maximum, format:email and multipleOf without enforcing them. Ask what is enforced, not what is accepted.

The takeaway

Choose by constraint, then test on your own schemas. Machine consumers get constrained decoding. How often the schema changes decides the backend: XGrammar for fixed schemas, llguidance for dynamic ones. Needing a closed model decides that you use its strict mode and stay inside its subset. Then run your real schemas through it with a validator, because what an engine declares and what it enforces can differ.

When this guide is wrong: if your schema is trivial and your model is strong, prompt-only may already be at 29/30 or better, and simplicity wins. If you're throughput-bound on one fixed model, the cookbook reports that TensorRT-LLM or LMDeploy can beat vLLM/SGLang, which we did not test. And every engine row can change within months.

Understand and remember

  • A machine consumer can't tolerate a parse failure → constrain decoding (7/30 → 30/30 raw) → a person reading loosely can live with prompt + light cleaning (29/30 schema-valid after cleaning)
  • Only whoever runs the model can mask → a closed model means its strict mode and its schema subset (compliance 0.92–1.00 when accepted, declared coverage falling to 0.06) → self-hosting gives you the backend choice
  • Schema fixed and reused → compile once, amortise (XGrammar precomputes; 0.11–0.30 s alongside prefill) → schema new per request → pick near-zero compile (llguidance 0.00–0.02 s vs Outlines 3.06–12.77 s)
  • Hard features (recursion, oneOf, counts, patterns) → engines differ in what they accept and enforce → test your real schemas with a validator before committing, because declared ≠ enforced
  • detail that matters No route fixes values → the constrained route is 30/30 valid but 22/30 correct until the total is computed in code → every path in the tree ends with a value check

5 · Predict commit to an answer before revealing

A schema is static, used a million times, self-hosted, and recursive (a comment tree). The tree's question 3 says "XGrammar". Is anything about the recursion a problem for that choice, and which engine from the course would be ruled out? Commit before revealing.

Reveal

XGrammar is fine: it compiles a CFG to a pushdown automaton and handles recursion, precomputing the stack-independent tokens. What recursion rules out is Outlines-core, which has no PDA. The real risk is the model nesting without end, so set max_tokens or bound the depth in the schema, as the grammars card showed. Then run question 4's test: check that the recursive $ref is accepted and enforced.
