Regex and finite state machines

Also called FSM, DFA (deterministic finite automaton), regex-guided generation, or Outlines-core. The cookbook uses the toy regex \{"name":("John"|"Paul"),"age":(20|30)\}; in the paper, Outlines 0.1.8 turns each JSON Schema into a regex like this before generating.

Prime · 2 minutes before you read

The problem: Constrained decoding must decide which tokens are legal at every step. Checking all 248,320 tokens against the schema each time is hopeless, so the engine needs a compact way to hold "where am I in the schema?" and look up the answer. A finite state machine is the simplest such memory, and its limits decide which schemas it can serve.

Where it fits: Second card of part 2. Token masking gave you the loop and assumed some oracle supplies the mask. This card is the first real oracle: compile the schema to a regex, the regex to a state machine, and the state machine to a token lookup table.

In one breath. A regex describes every string you'll accept. A finite state machine is the same rule drawn as a map: circles are "how far along am I", arrows are "which character may come next". Before generation, the engine converts that character map into a map over the model's tokens and stores it. Then each step is a table lookup: "in state 9, only John or Paul are allowed; mask the rest."

Worked example 1: the regex as a character machine

forced: only one legal character a real choice Double ring = accept, where only end-of-sequence is allowed.

states: 10 ({"name":" = 9 chars, plus start) + 3 (J o h) + 3 (P a u) + 1 (after n / l) + 8 (" , " a g e " :) + 3 (after 2|3, after 0, after }) = 28 arrows: 9 + 4 + 4 + 1 + 7 + 2 + 2 = 29 choices: state 9 (J or P) and state 24 (2 or 3) = 2 outputs: 2 names × 2 ages = 4 strings

Counted with a script and cross-checked: the Python regex-to-FSM library interegular 0.3.3 reduces this regex to the same 28 states. The "John" and "Paul" branches merge at state 16 because everything after them is identical. The cookbook's own figure numbers states the same way: its token {"name": jumps from state 0 to state 8.

The naive counts are arithmetic, not measured: real indexers prune and share work, so they check fewer.

Why it breaks on recursion

The cookbook's example is the Wikipedia first-link game: {"title":…,"link":{"title":…,"link":{…}}}, nested as deep as the chain goes. At the end the machine must write exactly as many } as it opened, and an FSM has no counter, so it needs a separate branch for every depth.

Max nesting depth D12351020unbounded
States (minimal DFA)14355698203413infinite
states = 21 × D − 7 (e.g. D = 20: 21 × 20 − 7 = 413)

Counted with interegular on a simplified schema (titles [a-z]+, no spaces), one regex per depth limit. It grows linearly here because each level adds one fixed object. Real schemas with several recursive fields multiply, which is the cookbook's "memory explosion". A pushdown automaton adds a stack and handles any depth with one small machine: see grammars and pushdown automata.

Why it beats the alternatives (for small, flat, reused schemas)

✗ Check every token each step

Test all 248,320 of qwen3.5:4b's tokens against the rule at every step: 2,483,200 checks for a 10-token answer, and again for the next answer. The FSM does that work once.

✗ Post-hoc regex match

Generate freely, then run re.fullmatch. You find out only after paying for the whole answer. On the M3 (qwen3.5:4b), 23 of 30 unconstrained answers came wrapped in ```json fences, which a strict match rejects.

✗ CFG / pushdown automaton

Handles recursion, but carries a stack and must check some tokens against it at run time (XGrammar: under 1% of tokens). A flat schema never needs that stack.

✓ Precomputed regex FSM

One O(1) table lookup per step, forced runs skipped, and the build cost spread over every call that reuses the schema.

So should you use an FSM backend?

Good fit: a small, flat, fixed schema that you call many times, like a classifier label, a date, an ID pattern or a short fixed record. The build cost gets spread thin, and the cookbook suggests Outlines for "low-to-medium throughput needs and simple schemas", prototypes and internal tools.

Poor fit: recursive schemas (social graphs, code ASTs, SQL subqueries, matching HTML tags), which need infinite states. Also per-request or dynamic schemas: precompute "becomes a problem in dynamic schemas as you incur TTFT costs with every new schema" (cookbook). Even for flat schemas, big enums and array lengths were the slow cases in the paper. The cookbook's own advice is that llguidance and XGrammar "generally work better in high-performance production systems, both for recursive and non-recursive schema". Those backends use grammars and compute masks on the fly (llguidance) or mostly precomputed with a stack check (XGrammar); see computing masks fast.

One inference, labelled as mine: Ollama and llama.cpp (the reader's setup) don't build an FSM index at all. They compile a GBNF grammar lazily, which is why the local grammar setup measured only +0.04 s. This card's costs apply to Outlines-style engines.

Understand and remember

  • Constraint (regex) → FSM state (how far along the pattern) → allowed transitions → allowed tokens (precomputed per state) → logits mask → sampling: the state is the only thing the engine needs to know to mask
  • Finite states → no stack or counter → can't track unbounded nesting → a recursive schema needs a separate branch per depth (21·D − 7 states here, infinite without a limit) → recursion needs a CFG/PDA engine
  • Walk every token from every state once, before generation → each step becomes one table lookup regardless of vocabulary size → but that build is paid up front (Outlines GCT 3.48–12.77 s) → it only pays off when a schema is reused many times
  • Many token paths spell the same forced text (7 spellings of name, 1,344 paths for 4 outputs) → collapse each forced run to one spelling → the model is asked only at real choices (2 calls instead of 10)
  • detail that matters The token index maps (state, token) → next state → masking is a lookup, not a vocabulary scan → this is why an FSM backend's per-step cost doesn't grow with 248,320 tokens, while its build cost does
  • detail that matters Counting keywords (minItems, maxItems, big enums) must be unrolled into states → the index balloons → the paper's 40 s–10 min Outlines timeouts

Reference only

  • the toy regex's exact state numbering (0–27) and the 33-row table
  • the interegular 0.3.3 library used to count states
  • Outlines' internal index format and API
  • the break-even arithmetic (≈ 75 reuses on GlaiveAI)

  1. concept Explain why an FSM engine can serve a flat schema with a lookup per step but can't serve a recursive one at all, in terms of what a state can remember.
    Check
    • a state is one position in a fixed pattern; there are finitely many
    • a flat schema has finitely many positions, so every prefix maps to a state
    • a recursive schema must remember how many objects are open; each depth needs its own states, so unbounded depth needs infinitely many
  2. mechanism Walk through what the engine does between the model producing logits and sampling the next token at state 9 of the toy regex.
    Check
    • look up state 9's row in the precomputed index: John → 16, Paul → 16
    • mask every other token (24 of the 26 illustrative tokens)
    • renormalise the model's probabilities over John and Paul, sample one
    • move to state 16 for the next step
  3. tradeoff Your service uses one fixed 10-field schema for millions of calls; another team builds a new schema from each user's CSV header. Which one should use an FSM backend, and what number decides it?
    Check
    • the fixed schema: the build is paid once and spread over every call
    • the per-request schema pays GCT every time (seconds on Outlines) for no reuse
    • the deciding number is reuses k vs the build cost: on GlaiveAI the card's arithmetic breaks even near 75 reuses, and never on GitHub-Hard, where Outlines' TPOT is also worse
  4. mechanism The toy regex has 28 character states but the token table only uses 21 of them. Why, and does the model ever lose a valid output because of it?
    Check
    • whole-word tokens like John and age jump over the middle states (10–15, 25)
    • those states are still reachable by single-character tokens in a real vocabulary, but not in this illustrative one
    • no output is lost: all 4 strings still reach the accept state

4 · Compare against what you already know

vs Grammars and pushdown automata: FSM vs PDA: what is fundamentally different about the state each one keeps, which design choice gives the FSM its speed and the PDA its reach, when do you pick each, and how does each fail?

Check
  • FSM: one position in a fixed pattern. PDA: a position plus a stack of what's still open
  • no stack means everything can be precomputed into a table (fast lookups); the stack lets one small machine handle any depth
  • pick the FSM for small, flat, reused schemas; the PDA for recursive or deeply nested ones
  • the FSM fails by state explosion or compile timeouts, and can't express recursion. The PDA fails by per-token stack work that can't all be precomputed, and by letting the model nest without end

vs Why constraining can be faster: This card's "2 LLM calls instead of 10" and Guidance's fast-forward both skip forced text. What is the same, and what does an FSM make easier about it?

Check
  • both notice that only one continuation is legal and append it without asking the model
  • in a precomputed FSM a forced run is visible at compile time: a chain of states with one way out
  • an on-the-fly engine must discover it at run time, step by step

5 · Predict commit to an answer before revealing

Four schemas go to an FSM backend: (a) an array of 1 to 1,000 SKUs, (b) an object with 200 optional fields in any order, (c) a comment with replies: [comment], (d) a string matching an email-like regex. Which one first exposes a pure FSM's limit (not just its cost)? Commit before revealing.

Reveal

(c). It is recursive, so exact support needs unbounded depth, which no finite machine can track: that is a limit of expressiveness. (a) and (b) are finite, so an FSM can represent them, but counting to 1,000 and 200 optional fields in any order both blow up the number of states: that is the cost limit behind the paper's Outlines timeouts. (d) is exactly what regexes are for.
