Regex and finite state machines

Also called FSM, DFA (deterministic finite automaton), regex-guided generation, or Outlines-core. The cookbook uses the toy regex \{"name":("John"|"Paul"),"age":(20|30)\}; in the paper, Outlines 0.1.8 turns each JSON Schema into a regex like this before generating.

In one breath. A regex describes every string you'll accept. A finite state machine is the same rule drawn as a map: circles are "how far along am I", arrows are "which character may come next". Before generation, the engine converts that character map into a map over the model's tokens and stores it. Then each step is a table lookup: "in state 9, only John or Paul are allowed; mask the rest."

Worked example 1: the regex as a character machine

forced: only one legal character a real choice Double ring = accept, where only end-of-sequence is allowed.

states: 10 ({"name":" = 9 chars, plus start) + 3 (J o h) + 3 (P a u) + 1 (after n / l) + 8 (" , " a g e " :) + 3 (after 2|3, after 0, after }) = 28 arrows: 9 + 4 + 4 + 1 + 7 + 2 + 2 = 29 choices: state 9 (J or P) and state 24 (2 or 3) = 2 outputs: 2 names × 2 ages = 4 strings

Counted with a script and cross-checked: the Python regex-to-FSM library interegular 0.3.3 reduces this regex to the same 28 states. The "John" and "Paul" branches merge at state 16 because everything after them is identical. The cookbook's own figure numbers states the same way: its token {"name": jumps from state 0 to state 8.

The naive counts are arithmetic, not measured: real indexers prune and share work, so they check fewer.

Why it breaks on recursion

The cookbook's example is the Wikipedia first-link game: {"title":…,"link":{"title":…,"link":{…}}}, nested as deep as the chain goes. At the end the machine must write exactly as many } as it opened, and an FSM has no counter, so it needs a separate branch for every depth.

Max nesting depth D12351020unbounded
States (minimal DFA)14355698203413infinite
states = 21 × D − 7 (e.g. D = 20: 21 × 20 − 7 = 413)

Counted with interegular on a simplified schema (titles [a-z]+, no spaces), one regex per depth limit. It grows linearly here because each level adds one fixed object. Real schemas with several recursive fields multiply, which is the cookbook's "memory explosion". A pushdown automaton adds a stack and handles any depth with one small machine: see grammars and pushdown automata.

Why it beats the alternatives (for small, flat, reused schemas)

✗ Check every token each step

Test all 248,320 of qwen3.5:4b's tokens against the rule at every step: 2,483,200 checks for a 10-token answer, and again for the next answer. The FSM does that work once.

✗ Post-hoc regex match

Generate freely, then run re.fullmatch. You find out only after paying for the whole answer. On the M3 (qwen3.5:4b), 23 of 30 unconstrained answers came wrapped in ```json fences, which a strict match rejects.

✗ CFG / pushdown automaton

Handles recursion, but carries a stack and must check some tokens against it at run time (XGrammar: under 1% of tokens). A flat schema never needs that stack.

✓ Precomputed regex FSM

One O(1) table lookup per step, forced runs skipped, and the build cost spread over every call that reuses the schema.

So should you use an FSM backend?

Good fit: a small, flat, fixed schema that you call many times, like a classifier label, a date, an ID pattern or a short fixed record. The build cost gets spread thin, and the cookbook suggests Outlines for "low-to-medium throughput needs and simple schemas", prototypes and internal tools.

Poor fit: recursive schemas (social graphs, code ASTs, SQL subqueries, matching HTML tags), which need infinite states. Also per-request or dynamic schemas: precompute "becomes a problem in dynamic schemas as you incur TTFT costs with every new schema" (cookbook). Even for flat schemas, big enums and array lengths were the slow cases in the paper. The cookbook's own advice is that llguidance and XGrammar "generally work better in high-performance production systems, both for recursive and non-recursive schema". Those backends use grammars and compute masks on the fly (llguidance) or mostly precomputed with a stack check (XGrammar); see computing masks fast.

One inference, labelled as mine: Ollama and llama.cpp (the reader's setup) don't build an FSM index at all. They compile a GBNF grammar lazily, which is why the local grammar setup measured only +0.04 s. This card's costs apply to Outlines-style engines.
