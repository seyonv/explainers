Checkpoint 1: from mask to machine

Ties together token masking, regex and finite state machines, grammars and pushdown automata, computing masks fast and token boundaries: how an engine knows, at every token, what is still allowed, and what that knowledge costs.

How to use this page. Close the five cards. Answer each question in writing, in full sentences, before opening its Check. A wrong or shaky answer isn't a failure; it tells you exactly which section to reopen. The questions are mixed on purpose, so you have to work out which idea applies before you can answer.

1 · Mixed retrieval

  1. which concept?Your schema has an integer price field, and the prompt shows prices written like 1,299. Every output is valid JSON, but now and then a price comes out ten times too big. Which idea from this part explains it, and what is the cheapest fix?
    Check
    • token vs grammar boundaries: the model wants , after the first digits, and the integer grammar masks it
    • it continues with digits from a spot it rarely saw, so the number keeps growing (89,000 → 890000 in the paper's toy)
    • cheapest fix: make the prompt ask for exactly what the schema enforces (digits only, no separators), and check the forced-vs-leading gap

    Missed it? Reopen token boundaries, worked example 1 and "How big the pull is".

  2. The model's first-step probabilities are Sure 45%, Here 25%, { 5%, {" 4%, plus others, and for our order schema only { and {" are valid. What does the sampler actually draw from, and does the order of the two survivors change?
    Check
    • every other token gets m = 0; 9% of the mass survives
    • p′({) = 5/9 ≈ 55.6%, p′({") = 4/9 ≈ 44.4%
    • the order is unchanged: masking removes and rescales, it never reorders

    Missed it? Reopen token masking, "What the mask does to the probabilities".

  3. which concept?A team's schema is a comment whose replies is an array of comments, nested to any depth. Their engine compiles JSON Schema to a regex, then to an FSM. Which concept predicts what happens, and what exactly goes wrong?
    Check
    • an FSM has finitely many states and no stack, so it can't count open brackets
    • unbounded depth would need a separate branch per level, so infinitely many states: the schema can't be represented exactly (or only up to a fixed depth)
    • fix: a CFG/PDA engine (llguidance, XGrammar, llama.cpp GBNF), plus max_tokens so the model can't nest forever

    Missed it? Reopen regex and FSMs, "Why it breaks on recursion", and grammars, "Why a regex can't do this".

  4. A PDA's state includes a stack that can grow without limit. So how can XGrammar precompute almost all of its mask ahead of time?
    Check
    • most tokens' legality depends only on the grammar position, not on what's on the stack (a digit after (, an operator after a number)
    • those are precomputed into a lookup table: over 99% of tokens, per the cookbook
    • only context-dependent tokens (a closing bracket, end-of-text) are checked against the stack at run time: under 1%

    Missed it? Reopen computing masks fast, the "Context-independent / Context-dependent" rows.

  5. An engine's mask takes 20 μs for most schemas but 100 ms on one edge-case schema. The model step on an A100 is 15.40 ms. Which case costs you time, and how much slower does each token get?
    Check
    • the mask runs in parallel with the forward pass: t_token ≈ max(t_GPU, t_mask)
    • 20 μs is 0.13% of the step: completely hidden
    • 100 ms is 6.5× the step: every token now takes about 100 ms instead of 15.40 ms, and the GPU sits idle

    Missed it? Reopen computing masks fast, "Is it fast enough?".

  6. which concept?A product builds a new flat schema from each user's CSV header and needs about 40 tokens back. Choose between a precomputed FSM backend, an on-the-fly Earley backend, and a PDA with a precomputed table, and say which cost decides it.
    Check
    • the schema is new every request, so any precompute is paid on every call and never amortised
    • a precomputed FSM costs seconds per new schema (Outlines 3.06–12.77 s GCT in the paper) for a 40-token answer: the worst fit
    • on-the-fly (llguidance, GCT 0.00–0.02 s) fits best; a flat schema doesn't need a stack, but that doesn't rescue the FSM's compile

    Missed it? Reopen regex and FSMs, "What the precompute costs", and computing masks fast, "Four ways to do it".

  7. Walk through what a precomputed FSM backend does between the model producing logits and sampling the next token, at a state with two legal tokens. What was paid before generation so that this step is a single lookup?
    Check
    • look up the current state's row in the token index: the two legal tokens and the state each leads to
    • mask every other token, rescale the survivors, sample one, move to its next state
    • paid up front: walking every vocabulary token from every state once (the grammar compilation time), per schema

    Missed it? Reopen regex and FSMs, worked example 2.

3 · Project: build a tiny mask engine for nested lists

What it reinforces: the mask and the EOS rule (token masking), a state made of phase plus stack (grammars and PDAs), the FSM's limit (regex and FSMs), stack-dependent tokens (computing masks fast), and multi-character tokens that cross grammar boundaries (token boundaries).

list ::= "[" "]" | "[" item ("," item)* "]" item ::= "1" | "2" | list vocabulary: [ ] , 1 2 [1 1] ], ,[ ]] + EOS

Valid outputs include [], [1], [1,[2]] and [[1],[]]. In about 40 lines of Python:

  1. State and step. Represent the state as (phase, depth) with phases START, OPEN (just after [), COMMA (just after ,), AFTER (just after an item) and DONE. Write step(state, char) that returns the next state or None.
  2. Mask. Write allowed(state): a token is legal if feeding its characters one by one never returns None. EOS is legal only in DONE.
  3. Trace. Write [1,[2]] as four tokens: [1 · ,[ · 2 · ]]. Before each token, print the phase, the stack and the legal and masked tokens. Then write it again as seven one-character tokens.
  4. Split. For every token, test whether its legality in a given phase changes with the depth. Those are the tokens an XGrammar-style engine must check against the stack at run time.
  5. Break the FSM. Cap the depth at D, build the states (phase, d) for d ≤ D, minimise, and count them for D = 1, 2, 3, 10. What happens at depth D + 1?
  6. Break the vocabulary. Delete the single-character ] token. Which of [], [1], [2], [[1]], [1,2], [1,[2]] can still be written?
Done when: your program prints both traces, your split lists exactly the stack-dependent tokens, you have a formula for the FSM's states in D, and you can explain the deletion result in one sentence. Then compare with the check.
Check: the numbers (computed with a Python version of this exact grammar)
  • Trace with 4 tokens: START, empty stack → legal [ [1 (2 of 11). After [1: AFTER, stack [ → ] , ,[ (3). After ,[: OPEN, stack [[ → 8 legal, only , ,[ and EOS masked. After 2: AFTER, stack [[ → ] , ], ,[ ]] (5). After ]]: DONE, empty → only EOS.
  • With one-character tokens, ] is legal at depth 1 and at depth 2, but in the first case it ends the whole output (DONE) and in the second it only closes the inner list.
  • Stack-dependent: ], and ]] (both need at least 2 open, because after closing one list there must still be one open). All other tokens are decided by the phase alone, and EOS only in DONE. That's 2 of 10 tokens here; JSON's real vocabulary is under 1%.
  • Minimal FSM: 3D + 2 states (5, 8, 11 … 32 at D = 10): three phases per level, plus start and done. A depth-(D + 1) input is rejected.
  • Without ]: [1], [[1]] and [1,[2]] are still writable (through 1] and ]]); [], [2] and [1,2] are not, because no remaining token can close a list right after [ or 2 at depth 1. The grammar allows them, the vocabulary can't spell them: token boundaries decide what is writable, not just the grammar.
