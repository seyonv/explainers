Token masking

Also called constrained decoding, logit masking, a logit processor, or guided decoding. It's the core loop of every grammar engine in the paper (Algorithm 1), what the cookbook's "constrained method" page simulates token by token, and what Ollama runs when you pass format.

Prime · 2 minutes before you read

The problem: Prompt-only JSON fails because nothing stops the sampler from picking Sure or ```. To guarantee the format, some component has to veto invalid tokens before the pick, at every single step, across the whole vocabulary.

Where it fits: First card of part 2. Part 1 showed the failure (sampling ignores the parser) and the contract (the schema). This card is the mechanism every grammar engine shares; the next cards are about how the engine knows which tokens to veto, and how fast.

In one breath. Before each token is picked, a checker looks at every token in the vocabulary and asks "would this break the schema?". Every token that would break it gets probability 0, and the model samples from what's left. So it can't write Sure! Here is…, because Sure is never on the table.

The loop, one token at a time

The paper's Algorithm 1, lines 4–14. C is the constraint (the compiled schema), f the model, x the prompt, o the output so far. The paper notes the mask "can run in parallel with the LM's forward pass". As printed, line 8 reads m ⊙ v′ and line 9 decode(α′); both are typos for v.

Why it beats the alternatives

✗ Prompt engineering

Ask for JSON, show the schema, hope. On your M3 the prompt-only answer passed json.loads as-is only 7 / 30 times; 23 / 30 came wrapped in ```json fences.

✗ Post-hoc validation

Clean and check after the model finishes. It finds problems but can't fix them: after cleaning, 29 / 30 were schema-valid, and the 30th (a bare array with extra keys) was only caught once the call was done.

✗ Retry until valid

Send the failure back for another go. Every retry is a whole new call (5.53 s median on your M3) with no guarantee it passes, so you need a cap: the cookbook uses 3 repairs × 3 fresh retries.

✓ Token masking

Invalid tokens are never picked, so the first pass parses: 30 / 30 raw parse and schema-valid, median 2.72 s. It's faster mostly because the answers were shorter (38 vs 80 tokens).

Does the mask make the answer right?

No. The mask only removes options; the model still chooses the values. The cookbook puts it plainly: it "enforces the schema, while the LLM is still responsible for filling in the values". On your M3 the constrained run was valid 30 / 30 times but fully correct only 22 / 30. The wrong totals (60 ×5, 58, 62, 66 instead of 54) are schema-valid numbers, so no mask can catch them. See valid is not correct.

If the prompt fights the schema, masking pushes the model onto tokens it rated unlikely. In the cookbook's step 1 it had to choose inside 15% of its own probability. The cookbook warns that masking the most likely tokens derails the model onto "unnatural paths" and lowers quality (token boundaries, quality shift). So keep the prompt and schema in agreement. It's the wrong tool when you can't reach the logits (a hosted API only gives you the provider's own version, with limited schema support), for free-form reasoning text you don't want shaped, and as a correctness check, which needs a validator on the values.

Understand and remember

  • Grammar state after the tokens so far → which next tokens keep the output valid → a 0/1 mask over the whole vocabulary → masked tokens get probability 0 → the sampler can't pick an invalid token, so the first pass always parses
  • Masking removes probability mass and renormalises the rest → survivors keep their relative order but grow ({ 5% → 33.3%) → if the removed tokens were chatter nothing is lost, but if the prompt fights the schema the model is pushed onto tokens it rated unlikely
  • The mask only removes options → the model still chooses among valid values → schema-valid but wrong values (60 for 54) pass → correctness needs a separate check
  • The mask covers every vocabulary token every step (248,320 on the M3) → computed on the CPU while the GPU runs the model → cheap only if the engine avoids checking tokens one by one
  • detail that matters Mask and forward pass run in parallel → the mask is free until it is slower than the model step → then the GPU waits every token (the fast-masks card)

Check

5 · Predict commit to an answer before revealing

The mask only needs to say which tokens are allowed. For our flat order schema, how many distinct masks does the whole answer need? One per output token (38), or fewer? Commit, then reveal.

Reveal

Fewer. Many steps share the same situation ("inside a SKU string", "after a comma between items"), so a precomputed engine can store one mask per grammar state and look it up. That's the idea behind the next card: compile the schema into a finite set of states once, so each step is a lookup instead of a scan of 248,320 tokens.

6 · Apply use the model, don't restate it

Build the smallest mask by hand. The allowed outputs are exactly ab and ac. The vocabulary is a, b, c, ab, ac, aa, plus EOS. Write down the legal tokens (m = 1): (1) at the start, (2) after the token a, (3) after the single token ab. (4) State the rule for when EOS becomes legal. Then break it: a buggy checker validates only the first character of the text. Name one token it wrongly admits at the start, and say what goes wrong next. If you missed anything, repair with a harder variant: allowed outputs xy and xyz, and vocabulary x, y, z, xy, yz, xx, plus EOS. Answer the same questions (1)–(4). Here one output is a prefix of the other, so watch EOS.

Done when: You have written all five answers, each with a one-line reason, before opening the check. Every answer matches it, or you did the xy/xyz variant and its answers match.

Hint

Check, only after trying: (1) start: a, ab, ac are legal; b and c (wrong first letter), aa (no allowed output continues with a second a) and EOS are masked. (2) After a: only b and c. (3) After ab: only EOS. (4) EOS is legal only once the text is a complete allowed output (ab or ac), never after a bare a. Buggy checker: it admits aa (or an invented ax): right first letter, impossible output. From aa no allowed output is reachable, but the buggy checker keeps saying yes, so invalid text ships: an under-constrained mask.

Variant check (open only after you have tried the xy/xyz variant)Variant (xy/xyz): start {x, xy}; after x {y, yz}; after xy {z, EOS}. Both are legal, because xy is already complete but xyz can still continue, so EOS is a real choice left to the model.
