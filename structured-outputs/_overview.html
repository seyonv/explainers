Structured outputs: the whole picture

Overview card. Also called structured generation, constrained or guided decoding, JSON mode, or response_format. It ties together the 17 cards in this course, built from Geng et al. 2025 (JSONSchemaBench) and the Nanonets cookbook, with numbers measured on your M3. To pick a tool, see choosing a method and a tool.

Prime · 2 minutes before you read

The problem: A model writes one likely token at a time and has no idea a parser will read the result. So "reply in JSON" sometimes fails, and even when it parses, the values can be wrong. Without a map you end up tuning the wrong thing: a faster engine when the real cost was retries, or a stricter grammar when the real error was arithmetic.

Where it fits: This is the map for the whole course. It assumes only what the latency course taught you: time ≈ prefill + output tokens × time per token. Everything here adds two new terms to that law: a one-off compile cost and a pass rate.

Builds on: Output length · Time to first token (TTFT)

In one breath

A model writes one token at a time and has no idea your parser exists, so "reply in JSON" is only a request. You get a structured answer in one of two ways. You can check it afterwards and retry. Or you can constrain decoding: before each token is picked, zero out every token that would break the schema. Either way, what you pay is the time per attempt divided by the chance that an attempt passes your check.

The same thing in plain text:

expected time to a usable object ≈ (compile ÷ reuses + prefill + tokens × time per token) ÷ probability an attempt passes your check

Filled in with the running example: 30 runs per setup of "three bottles of the citrus body wash and one lavender candle" on qwen3.5:4b, where the correct total is 3 × $12 + $18 = $54. Per-attempt times are measured medians. The 1/p step assumes attempts are independent and equally long.

The mental model: where each card lives

The grey mask box is the only difference between the two methods: prompt-only skips it and relies on the red retry loop instead. Coverage (coverage and compliance) is the question of whether the engine can build that box for your schema at all. Being over- or under-constrained means building the wrong box.

Where to look it up

  • JSONSchemaBench: the paper's 9,558 schemas and harness. Run it on your own engine.
  • Geng et al. 2025: the paper behind this course (efficiency, coverage, quality).
  • Ollama structured outputs: format takes "json" or a JSON schema. This is what your M3 runs.
  • vLLM and SGLang structured outputs: pick the XGrammar, llguidance or Outlines backend.
  • Hosted APIs: OpenAI, Gemini, Anthropic. Check each one's list of supported keywords before you rely on it.
  • Nanonets cookbook: how the backends work inside, and a prompting and repair playbook.
  • Measure it yourself: validate every output with Python jsonschema, even when decoding is constrained, and count value errors separately. LM Format Enforcer's output_scores shows where the schema fights the model.

Words people use

JSON mode vs structured outputs

JSON mode promises valid JSON of any shape. With no schema in the prompt, 0 of 10 local runs matched our schema. Structured outputs (a schema in format or response_format, strict) promises the shape.

Grammar engine vs inference engine

The grammar engine (backend) builds masks: XGrammar, llguidance, Outlines-core, llama.cpp GBNF. The inference engine runs the model and calls it: vLLM, SGLang, Ollama. The paper also calls the first a "constrained decoding framework".

Coverage vs compliance

Coverage is how many of your schemas the engine accepts and gets right. Compliance = empirical ÷ declared coverage: once it accepts a schema, how often the output is valid. OpenAI on GitHub-Hard is 0.09 coverage with 1.00 compliance.

✓ Valid vs correct

This is the distinction the course keeps coming back to. A grammar guarantees the shape, never the facts: 30/30 valid but 22/30 right on the M3. Check the values, compute what you can in code, and give the model a way to say "this doesn't fit".

The takeaway

If a machine reads the output, constrain decoding and still validate the values. With a grammar, broken syntax goes from "usually" to "never". It often makes answers shorter and faster too, and on the paper's benchmarks it did not cost accuracy. Pick the engine by your schema's features and whether the schema changes per request. Then spend the remaining effort on checking values, because that is where the errors that remain actually are.

When this doesn't apply: output a human reads loosely, a closed model whose API rejects your schema, or schemas generated fresh per request on an engine with a slow compile step. There, prompt-only with a repair loop is reasonable (repair loop). The same goes for reasoning-heavy tasks where a format measurably hurts on your data. The usual cause is an answer-first schema, which scored 0/10 on the local Last Letter test against 8/10 with reasoning first.

Understand and remember

  • Model samples the likely next token → the parser isn't in that choice → prompt-only output fails some of the time → you either retry (pay 1 ÷ p attempts) or mask invalid tokens before sampling (p for syntax → 1)
  • Each attempt costs compile ÷ reuses + prefill + tokens × time per token → divide by the chance an attempt passes → so raising p, shrinking n, cutting TPOT and amortising GCT are four separate levers
  • A grammar fixes the shape, not the facts → schema-valid numbers like a wrong total still pass → the errors that remain after constraining are value errors → check or compute values in code
  • Coverage decides whether the engine can build the mask for your schema at all → over- or under-constrained means it builds the wrong mask → so engine choice moves p, TPOT and GCT at once
  • detail that matters Constrained answers were shorter (38 vs 80 tokens: no fences, compact JSON) → most of the M3's 2× speedup came from a smaller n, not a faster TPOT

3 · Retrieve from memory, card closed
  1. concept Explain why the formula divides by p instead of adding a retry cost, and what assumption that makes about the attempts.
    Check
    • with pass probability p the expected number of attempts is 1 ÷ p (geometric)
    • each attempt costs the whole numerator again
    • it assumes attempts are independent and about equally long
  2. mechanism Walk one constrained request through the map: what happens before the first token, at every token, and after the answer?
    Check
    • before: the schema is compiled into a grammar (GCT, cacheable)
    • every token: the model scores all tokens, the mask zeroes the invalid ones, one is sampled, the grammar state advances
    • after: validate the output and check the values; a failure means a new attempt
  3. tradeoff Your constrained extraction is valid 30/30 but only right 22/30. Which lever from the ranking table do you pull, what does it change in the formula, and what does it cost?
    Check
    • compute the derived field (the total) in code
    • it raises p for "values right" from 22/30 to 30/30, taking expected time from 3.71 s to 2.72 s
    • it costs a small lookup in your code, and only works where a rule exists to compute the value
  4. tradeoff Rank the four levers for a team whose schema changes on every request and whose answers are long. Which term dominates, and which lever do you pull first?
    Check
    • k = 1, so GCT is paid on every call: pick an engine with near-zero compile
    • long answers make n × TPOT large: compact output and a low-TPOT engine matter next
    • then raise p for values with checks in code

Why this step?

5 · Predict commit to an answer before revealing

Suppose the prompt-only setup kept its 5.53 s per try, but you switched its checker from "values right" (15/30) to "raw json.loads works" (7/30). Before computing: does expected time go up or down, and by roughly how much?

Reveal

Up. Expected time = 5.53 ÷ p. With p = 15/30 it is 11.06 s; with p = 7/30 it is 23.7 s, a bit over 2× worse. A stricter-looking check isn't always the costly one: the raw-parse check fails every fenced answer, which the value check never saw because cleaning ran first.
