Over- and under-constrained

Also called too strict / too loose, or false rejections / false acceptances. The paper (§5.3) defines both terms and measures them with the official JSON Schema Test Suite: 45 categories, one per keyword or keyword group, where an engine passes a test only if it can generate every valid instance and blocks every invalid one (Tables 5 and 6).

In one breath. A grammar engine turns your schema into a rule for which tokens may come next. If that rule is stricter than the schema, some valid answers can never be written: the engine is over-constrained. If the rule is looser, some invalid answers get through: the engine is under-constrained. Only a rule that matches the schema exactly lets you skip checking.

The two failures as sets

L(S)∖L(G)≠∅over-constrained: valid but blocked L(G)∖L(S)≠∅under-constrained: invalid but allowed
L(S)every JSON text the schema accepts (what jsonschema.validate passes)the truth L(G)every text the engine's grammar lets the model writewhat the mask allows ∖"in the first set but not the second"set difference goalboth differences empty, i.e. L(G) = L(S)Guidance: 13 of 45 categories

The paper states the definitions in words ("rejects JSON instances that are valid" / "allows JSON instances that are invalid"); the set notation is this card's restatement. An engine can be both at once, on different keywords.

Over-constraining costs you options: here, only format choices, so the answer is still reachable. It gets worse when the blocked valid instance is the only right one (for example a keyword the engine can't express). The cookbook's LM Format Enforcer page argues that forcing an order or whitespace "that contradicts its training data" pushes the model onto low-probability tokens and "degrades the semantic quality of subsequent tokens". Under-constraining costs you the guarantee: you're back to checking every output.

A false acceptance. The model may still write valid JSON, but nothing guarantees it. XGrammar's main failure (38 categories).

A false rejection. A right answer may become unwritable, and the model is pushed onto tokens it didn't want. Llamacpp: 18 categories.

If I use constrained decoding, can I skip validation?

No: keep a real validator. Under-constrained engines exist, so "the grammar allowed it" isn't proof it's valid. Run jsonschema (or Pydantic) on every output anyway; it's cheap next to a model call, and a failure can go to a repair loop. The paper doesn't call permissiveness a bug: under-constraining "effectively delegates responsibility to the LM, which may produce valid output despite a lack of strict constraints", and "can be a legitimate strategy, [but] it requires careful implementation and transparency". A loose engine plus a validator is a fine design; a loose engine you think is strict is not.

Test-suite scores don't map 1:1 onto your schemas. The paper says so itself: "there is no straightforward correspondence between test suite performance and empirical coverage", because real schemas use a few keywords a lot and most rarely. XGrammar's 38 under-constrained categories may never touch a schema like ours, and a strict engine that fixes key order costs you nothing if you never needed another order. The suite also skips format and remote $ref. Test the engine on your schemas, with some deliberately invalid outputs, before trusting it. When compile errors are the risk (dynamic or exotic schemas), a permissive engine or the prompt-only route with validation can be the better pick.
