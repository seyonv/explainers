JSON Schema, the contract

Also called the schema, the response_format or format you send an API, or the output type; a Pydantic model becomes one when the library calls model_json_schema(). The paper (§1–2) calls JSON Schema "a key specification language for constrained decoding" and "an industry-wide standard", and builds its whole 10K-schema benchmark out of it.

In one breath. A JSON Schema is a JSON document that describes which other JSON documents are allowed: what type each value is, which keys must be there, which strings are allowed, how long a list can be. It was built to check finished data. Constrained decoding borrows it as the contract that the model's output must satisfy, and each engine has to translate it into rules about the next token.

Our contract: the store order

{
  "type": "object",
  "properties": {
    "items": {
      "type": "array",
      "minItems": 1,                                     at least one line item
      "items": {                                         every entry must match this
        "type": "object",
        "properties": {
          "sku": {
            "type": "string",
            "enum": ["BW-CITRUS", "BW-EUCALYPT",         one of the 10 SKUs
                     "CANDLE-LAVENDER", "CANDLE-SANDAL",
                     "LOTION-SHEA", "SOAP-OATMEAL",
                     "DIFF-BERGAMOT", "SCRUB-SUGAR",
                     "BALM-PEPPER", "MIST-ROSE"]
          },
          "qty": { "type": "integer", "minimum": 1 }     a whole number, 1 or more
        },
        "required": ["sku", "qty"],
        "additionalProperties": false                    no extra keys like unit_price
      }
    },
    "total_usd": { "type": "number" }                    any number: 54, 60 and 540 all pass
  },
  "required": ["items", "total_usd"],
  "additionalProperties": false
}

Bold = JSON Schema keywords; grey notes are not part of the schema. Correct answer: {"items":[{"sku":"BW-CITRUS","qty":3},{"sku":"CANDLE-LAVENDER","qty":1}],"total_usd":54}. Pretty-printed, the schema is 911 characters and 286 tokens (measured on M3, qwen3.5:4b tokenizer), which you pay again if you also paste it into the prompt. Writing the same thing as a Pydantic model (Field(ge=1), Field(min_length=1), Literal[...], extra="forbid") gives the same keywords, plus 6 titles, with the item moved into $defs and pointed to by "$ref": "#/$defs/Item" (checked locally, Pydantic 2.13.5).

What "valid" means

valid(x,S)= ⋀k∈S k(xk)each keyword says yes about its part
xthe finished JSON document the model wroteour order object Sthe schema: a set of keyword uses16 in ours kone keyword use, e.g. minimum: 1 on qtytype ×6, required ×2 … xkthe part of x that keyword looks ateach qty value ⋀"and": every one must passone fail = invalid
our schema: type 6 + properties 2 + required 2 + additionalProperties 2 + items 1 + minItems 1 + enum 1 + minimum 1 = 16 keyword uses a validator reads the whole x, then asks all 16. A grammar engine never sees x whole: it must turn each k into a rule about the next token, before x exists.

That gap is the whole card. Keywords about shape turn into token rules easily; keywords about the whole value (a number's size, a string's format, a list with no repeats) do not.

The paper calls the APIs' approach "a more conservative strategy, implementing only a subset of JSON Schema features that they can reliably support". Your own setup is a third case: Ollama accepted every keyword we sent without complaint, and silently ignored format and a number maximum (measured above).

How it differs from related ideas

✗ Regex

Describes one string, character by character. Great for a date or a SKU, but it can't count nesting, so a link chain of any depth needs infinite states (cookbook). Outlines compiles schemas to regex, and has by far the longest compile times in the paper.

✗ CFG / GBNF grammar

Rules that expand into rules, so recursion is free and it can describe SQL or code, not only JSON. But you write it by hand in each engine's own dialect (GBNF for llama.cpp), and most engines build one from your schema anyway.

✗ Pydantic, BAML type defs

Nicer to write and read in code. Pydantic compiles to JSON Schema (same 16 keyword uses here, plus titles and a $ref); BAML turns types into a prompt that uses "60% less tokens than JSON schemas" (cookbook). Neither is what the engine enforces.

✓ JSON Schema

The one format every layer accepts: OpenAI, Gemini and Anthropic APIs, Ollama, vLLM, SGLang, and your validator. Write it once (or generate it from Pydantic) and the same file both constrains the model and checks the result.

Does the schema guarantee the output is right?

No, for two reasons. First, JSON Schema is a validation language: it was written to check a finished document, not to steer one being written. Shape keywords translate cleanly into token rules. Keywords about a whole value don't: format (email, date-time), number ranges, uniqueItems (the engine would have to remember every earlier item; our inference, not tested here), and remote $ref, which no engine fetches. The paper's Test Suite run left out format and remote $ref, testing 43 of the 45 categories (45 − 2). Even the checker can miss things: the paper had to turn format checks on in jsonschema, and says it "doesn't guarantee the validation of all the schema constraints".

Second, a schema only says what's allowed, not what's true. "total_usd": 60 passes as easily as 54, and a keyword the engine does enforce can push the model into a wrong but valid answer (qty 3 became 30). So always validate the output again after decoding. And JSON Schema isn't always the right contract: for recursive or non-JSON output (SQL, code), write a grammar directly; for a tiny answer on a slow model, a compact pipe format is 18 tokens vs 35 for minified JSON (measured on M3; see compact formats).
