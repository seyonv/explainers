Where constrained decoding runs

Also called the inference engine or serving stack, the constrained-decoding backend, a structured outputs API, response_format, strict tool (function) calling, or JSON mode. The cookbook's "full stack" and "inference engines" pages lay it out. Every claim here is dated 2026-09-21, and these tools change every few months.

Prime · 2 minutes before you read

The problem: "Which structured-output tool should I use?" has no answer until you know where the mask would run. The grammar is a small backend library inside an inference engine's sampling loop, and on a hosted API it runs on someone else's servers with their subset of JSON Schema. Pick the wrong layer and you get a guarantee that doesn't cover your schema, or no guarantee at all.

Where it fits: Second card of part 6. Token masking gave the loop; the backend cards showed how masks are computed; coverage showed which engines enforce what. This card places each backend inside a real stack, from Ollama on a laptop to vLLM, SGLang and the hosted APIs.

In one breath. The grammar isn't a separate product. It is a small backend library (XGrammar, llguidance, Outlines-core, llama.cpp's GBNF) that plugs into the inference engine's sampling loop and hands it a token mask at every step. So "which structured output tool?" really means "which engine runs my model, which backend does it plug in, and can I reach the logits at all?"

Hosted APIs: the provider runs the whole stack

You can't mask a closed model's logits yourself: the cookbook says constrained decoding "needs access to the model's logits", and OpenAI, Google and Anthropic don't expose them. Instead they run the mask on their servers and accept a subset of JSON Schema. The last column checks the running example's order schema (enum, minItems:1, minimum:1, additionalProperties:false, everything required) against each doc.

JSON mode is not schema-constrained

JSON mode (OpenAI json_object, Ollama format:"json") only guarantees that the reply parses as JSON. The keys, types and SKUs can be anything. Schema-constrained (json_schema + strict, Ollama format = a schema) also forces the shape. OpenAI's doc puts it plainly: both output valid JSON, but "only Structured Outputs ensure schema adherence".

How it differs from related ideas

✗ JSON mode

The engine forces some JSON, not your JSON. Missing keys, extra keys and wrong enum values still get through, so you still need a validator.

✗ Prompt, then parse and retry

Instructor, BAML and Pydantic AI work with any API, even one with no structured mode. But nothing stops a bad token, so you pay for retries (repair loop).

✗ A bare backend library

XGrammar or Outlines-core on its own gives you masks, not a server. You still need batching, caching, a tokenizer match and an engine adapter; the cookbook's libraries page lists that chore list.

✓ An engine or API with the backend built in

The mask sits inside the sampling loop, next to the logits, for every request. You send a schema and get back JSON that fits it. You still have to check the values yourself.

So which one should you use?

Pick by your constraints, not by what's popular. Need the best closed model? Then you can't reach the logits: use its strict mode, and keep your schema inside its subset (or prompt, validate and repair). Does the data have to stay on your machines? Self-host. Do you generate a new schema per request? Pick a backend with near-zero compile time (llguidance, llama.cpp), since each new schema pays compile again (compile vs per-token). Serving many users? Use vLLM or SGLang, because Ollama "will choke on concurrent users". One model on one laptop? Ollama is the cookbook's "easiest entry point".

When it's the wrong tool: if your schema uses keywords the API drops (like minimum on Claude) or rejects, "structured outputs" no longer guarantees your whole contract, and you're back to validating. And every row above is a snapshot. Backends get swapped, defaults change and limits grow within months, so check the engine's current docs and the date on any benchmark (the paper's engines are from late 2024).

Understand and remember

  • Masking needs the logits → only whoever runs the model can mask → self-hosted engines plug in a backend (XGrammar, llguidance, Outlines-core, GBNF); hosted APIs run their own and expose a strict mode
  • Hosted APIs support a subset of JSON Schema → unsupported keywords are rejected or silently dropped (Claude's SDKs drop minimum) → the guarantee covers only what was kept → check the dropped constraints in code
  • JSON mode constrains to some JSON, not your schema → syntax is guaranteed, the shape only if the prompt spells it out (10/10 vs 0/10, 7 different key sets) → use schema-constrained mode for machine consumers
  • The mask is per request and runs on the CPU beside the GPU → a batching server keeps one grammar state per request → engines differ in which backend they plug in and how well they scale (Ollama "will choke on concurrent users"; vLLM/SGLang batch)
  • detail that matters Schema compile happens on first use and is cached (Anthropic: 24 hours) → the first request with a new schema is slower → per-request schemas pay it every time, on hosted APIs too

5 · Predict commit to an answer before revealing

You send the order schema to a provider that silently drops minItems (the way Claude's SDKs drop minimum) and the message is "I want a McFlurry". Predict the output, and whether your pipeline notices. Commit before revealing.

Reveal

Likely a schema-valid object with an empty items list and some total. Without minItems the grammar no longer forces an invented SKU, so the model can leave the list empty (the prompt-only runs in the over/under card chose "items": [] for a non-order). Your pipeline notices only if you re-validate the reply against your full schema, where minItems: 1 still applies, or handle the empty list explicitly. That is arguably better than the invented order the full grammar produced, but it's a silent change in behaviour, which is exactly why dropped keywords must be checked after the reply.
