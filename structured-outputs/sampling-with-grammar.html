Sampling settings under a grammar

Also called decoding settings or generation parameters: temperature, top-p (nucleus), top-k, min-p, repetition / presence penalty, beam search, best-of-N. The cookbook's "sampling methods" page says: temperature 0 for extraction, turn the repetition penalty off, avoid top-k/top-p with strict schemas, prefer min-p. The course's M3 runs used temperature 0.7 on top of qwen3.5:4b's shipped defaults.

In one breath. The grammar decides which tokens are allowed; the sampling settings decide which allowed token gets picked. They're separate knobs, and the order they run in matters: a filter like top-p that runs before the mask can throw away the one token the grammar would allow.

How it differs from related ideas

✗ Beam search

Looks ahead so an early likely token doesn't lead into an unlikely dead end. It suits SQL and code, but the cookbook warns VRAM and latency grow linearly with the width, and it still can't check the arithmetic.

✗ Typical sampling

Picks tokens with "typical" information content. The cookbook suggests it for long structured output that gets stuck looping on whitespace or keys. It's a fix for long documents, not short extractions.

✗ Best-of-N with a validator

Fixes wrong values after the fact by generating several and checking each. It's the only row here that can catch 60 ≠ 54, but it needs a checker you can write, and it costs N calls.

✓ Greedy under the mask, penalties off

The grammar handles validity and temperature 0 takes the model's best guess among valid tokens. On your M3 that was 3 / 3 correct and identical. Add a validator only where a wrong value is costly.

Is temperature 0 always the right setting?

No. It's the right default for extraction, classification and tool calls, and the cookbook says to benchmark at temperature 0 first. It's the wrong choice when you want variety (prose fields, synthetic data), when you do best-of-N (N greedy runs give N identical answers), and when the model's top guess is systematically wrong: then greedy is wrong every time, where sampling at least sometimes lands right. The cookbook also warns that sampling above 0 can walk into "grammar traps", valid tokens that lead to dead ends and repetitive output later.

The order of operations is engine-specific. The cookbook says only that "certain older backends" stall when top-p cuts the only valid token. Of the engines we read, llama.cpp checks its pick and retries with the mask first, and Ollama's MLX runner masks before truncating, so neither strands }. That's from code at one version, not a test, so for any other engine, turn top-p/top-k off with strict schemas rather than trusting the order.
