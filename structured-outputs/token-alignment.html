Token boundaries vs grammar boundaries

Also called token healing, tokenization ambiguity, token misalignment, the whitespace trap or the grammar trap. The paper (§6) names "ambiguity of tokenization" as the reason masking can still hurt quality and credits Guidance's lead to token healing ("we believe"). The cookbook warns about it on its libraries and LM Format Enforcer pages.

In one breath. A grammar thinks in characters (", ,, a digit), but the model writes in tokens, and one token can span several characters, like " (space + quote) or ://. When the grammar blocks the token the model was about to write, the model has to take one it rated unlikely. Every token after that is written from a spot the model rarely saw in training, and that is where answers drift.

Worked example 1: the paper's toy, 89,000

The paper calls this "a hypothetical toy example": blocking , keeps the output valid "but potentially may cause the LM to go out of distribution and generate '890000' instead". The one-digit-per-token split is how Qwen tokenizes numbers (seen in the logprobs below); other tokenizers group digits differently.

Worked example 3: whitespace is tokens too

The running example answer, measured with the Qwen tokenizer: pretty-printed (indent 2) is 72 tokens / 152 characters; minified is 35 / 88. Both are the same JSON, but the grammar's whitespace rule decides which token sequence is legal.

72 − 35 = 37 tokens that are only newlines and spaces 72 / 35 = 2.06× 152 − 88 = 64 characters of whitespace

The cookbook: if the grammar "doesn't explicitly account for an optional newline or space between JSON keys, the LLM might try to predict a newline or space token, get masked out, and degrade into nonsense output". On Ollama this didn't bite: in example 2 the model's own { \n were picked unchanged, so its grammar let that whitespace through (observed, not read from Ollama's source).

Token healing: the fix at the prompt end

From Guidance's notebook, with StableLM-3B: ending a prompt with : rules out the 34 tokens that start with a colon, and "about 70% of the 10k most common tokens… are prefixes of longer possible tokens". Token healing "backs up the generation process by one token before the end of the prompt, then constrains the first token generated to have a prefix that matches the last token in the prompt". It's on by default for Transformers models.

Why it beats the alternatives

✗ Force exact whitespace

One legal layout, e.g. minified. If the model wants \n it gets masked, and the cookbook warns it can "degrade into nonsense". LM Format Enforcer's page says forcing a layout "degrades the semantic quality of subsequent tokens".

✗ Character-level masking only

Check each character and ignore how tokens group them. Tokens that span a rule change ( ", ",) get thrown out, pushing the model onto odd single-character tokens. (My inference from the boundary examples; the sources don't test this directly.)

✗ Ignore it

Usually fine, but in example 2 the model was overruled 3–4 times per answer, and once the sum lost its second term (64500). You only find out when a value is wrong.

✓ Loose grammar, healing and a prompt that agrees

Allow any whitespace (and field order where you can), heal the prompt boundary, and ask for the same format the schema enforces ("integer, no separators"). Then the forced and leading tokens match, and the gap stays near 0.

Is this a big effect?

Usually not. Across the paper's Table 8, the constrained engines score 0 to 3.7 points above LM only, and it only guesses that token healing explains Guidance's 3.3–3.7 point lead. In the running order example on your M3, constrained runs were valid 30 / 30 and the wrong totals were arithmetic errors, not boundary drift. It shows up most with rigid whitespace or field order, with numbers (separators, decimals, exponents), and when the prompt asks for one format and the schema enforces another.

Don't reach for a special engine just for this. With hosted APIs (OpenAI, Gemini, Anthropic) you can't see the logits or change how they mask, so the lever you have is the prompt: describe the exact format the schema expects. Locally, check a few forced vs leading tokens first; if the gap is near 0, the grammar isn't fighting the model.
