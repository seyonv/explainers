Compact formats

Also called token-efficient output, minified JSON, custom delimited formats, BAML type definitions or ID remapping. The cookbook's "compact prompts" page uses incident.io's dashboard agent, which went from 11 s to 2.3 s mostly by writing fewer output tokens.

In one breath. The model writes its answer one token per forward pass, so every brace, space and repeated key name in the answer costs one step of waiting. Saying the same thing in fewer tokens (minified JSON, a pipe-separated line, short IDs) cuts the writing time almost in proportion. Shrinking the prompt helps far less, because the prompt is read in one parallel pass.

The mechanism

Tanswer≈ tprefill(nin)read prompt, in parallel + noutvoutwrite answer, one token per pass

same thing in plain text: time ≈ prefill(prompt tokens) + answer tokens ÷ tokens per second

Filled in for our order at 15.4 tokens/s: pretty JSON 72 ÷ 15.4 = 4.68 s of writing; pipe format 18 ÷ 15.4 = 1.17 s. The same law is in output length from the latency course.

The tricks, each with two examples

Think of a telegram charged by the word: you drop "please" and "stop" where the reader can guess them. Every trick below removes tokens the reader (your parser) can already infer.

Why it beats the alternatives

✗ Pretty-printed JSON

Readable for people, but half of our 72 tokens are indentation and newlines. That's 37 extra forward passes, 2.4 s per answer on the M3, for nothing the parser needs.

✗ Only dropping fields

It's the biggest single step at incident.io (−4 s), but it removes information, not just padding. The cookbook's advice: reasoning fields "improve output quality", so drop them only "if your outputs are good enough".

✗ YAML

No braces or quotes, but indentation comes back. Our order in YAML is 42 tokens (measured, same method): shorter than pretty JSON, longer than minified (35). And Ollama's format option and the paper's engines all take JSON Schema, so the grammar guarantee is gone.

✓ Compact formats

Keep every field, drop only what the parser can infer. Minified JSON halves our answer with zero risk; a delimited line quarters it; small int IDs replace 35-token UUIDs. Writing time falls in proportion.

Is a custom format always better?

No. The cookbook warns: "LLMs are very familiar with JSON format", and a different format "can hurt performance in subtle ways" on complex tasks. For nested or optional fields, minified JSON is the safer default: it keeps most of the saving (72 → 35) and your JSON Schema, validators and grammar engines still work. A pipe format is only guaranteed if you write your own grammar or regex for it; with a prompt alone, you're back to parsing and repair.

You may already have the saving. Constrained decoding usually emits no whitespace: our constrained run's median answer was 38 tokens, against 80 unconstrained (pretty JSON plus fences). Most of its 2× end-to-end speedup was this shorter answer, not faster tokens. Also don't remap values that carry meaning. The cookbook's example: turning London, Paris, Los Angeles into 1, 2, 3 "will impair your LLMs knowledge and reasoning". And on a fast host (Cerebras row above), the saving is minutes per 10,000 answers, so readability may matter more.
