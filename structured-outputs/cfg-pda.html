Grammars and pushdown automata

Also called a CFG (context-free grammar), a PDA (pushdown automaton), and grammar files written in GBNF (llama.cpp and Ollama), EBNF or Lark. The cookbook's example is a calculator grammar that makes a model write (3 + (5 * 2)). It's what lets an engine handle nested, recursive output that a regex can't describe.

Prime · 2 minutes before you read

The problem: A finite state machine can't count open brackets. Recursive or deeply nested output (trees, link chains, expression ASTs) is either out of reach or needs one regex per depth, and that regex doubles in size at every level. Constrained decoding needs a machine that remembers what is still open and can still produce a mask at every token.

Where it fits: Third card of part 2. The FSM card's state was only "how far along the pattern am I". This card adds a stack to that state, the smallest change that buys unbounded nesting. The next card, computing masks fast, is about paying for that stack cheaply.

In one breath

A grammar is a small set of rules that say how bigger pieces are built from smaller ones, and a rule can refer to itself, so it can nest to any depth. The engine runs it as a pushdown automaton: a state machine plus a stack. It pushes when a bracket opens and pops when one closes. The stack is how it knows, at every token, which closing brackets are still owed.

The four parts, in plain words

Think of a recipe book. Terminals are the ingredients you can actually put on the plate. Non-terminals are dish names like "sauce" that point to another recipe. Rules are the recipes. The root is the dish you were asked to make. A recipe can call for itself ("a sauce made from a sauce"), and that is where nesting comes from.

Why a regex can't do this: one pattern per depth

A regex (and the FSM it compiles into) has no stack. To accept brackets nested d deep, the cookbook chains a separate pattern for each depth, and each depth pastes the previous pattern in twice. We built those patterns in Python the cookbook's way and counted their characters:

Ld= 2⁢Ld−1previous depth, pasted twice + 27brackets, op, number options ⇒ Ld=44⋅2d−1−27

How it differs from related ideas

✗ Regex / FSM

A fixed set of states with no memory. Fast, fully precomputable lookups, but it can't count open brackets, so recursive shapes need infinite states.

✗ JSON Schema

Describes the data you want, not how to write it out character by character. Engines translate it into a grammar (GBNF in Ollama) or a regex (Outlines). It isn't a machine itself.

✗ Earley parser

Not an alternative to a grammar but a way of running one. It keeps every possible parse alive at once (it simulates a non-deterministic PDA), which llguidance uses to handle ambiguous anyOf.

✓ CFG + PDA

A few recursive rules plus a stack. It handles any nesting depth, so the mask at each token depends on what is still open.

Does JSON always need a grammar?

JSON in general, yes. Your schema, often not. JSON itself is recursive (objects hold arrays that hold objects, to any depth), so "any valid JSON" needs a CFG. A specific schema with no recursion, like our order schema, only nests a fixed number of levels. It can be flattened into one long regex, and that is what Outlines does (the paper calls it "JSON Schema to Regex Conversion"). A flat regex is the better choice when the schema is fixed and reused: it's precomputed once and each step is a lookup. Its cost is compile time: 3.48 s per new schema versus 0.05 s for llama.cpp in the paper's table.

Recursion has a catch. A grammar allows unlimited depth, and it doesn't make the model stop. In one run on your M3 (qwen3.5:4b, temperature 0, capped at 120 tokens), we gave Ollama a recursive expression-tree schema for the apples problem. The model opened "left": { about 20 times and never closed a bracket before the cap. That is one run, not a rate, but the lesson holds: set num_predict or max_tokens, and if you can, write a schema with a fixed depth.

Understand and remember

  • A rule that uses its own name (expr ::= … expr …) → output can nest to any depth → the machine must remember how many brackets are open → a stack: push on open, pop on close → one small PDA handles every depth
  • Grammar position + stack contents → allowed next tokens → mask → the same position can have different masks at different depths () is legal only while something is open) → part of the mask can't be precomputed from the position alone
  • No stack → a regex/FSM must spell out each depth separately → each level pastes the previous pattern in twice → L_d = 44·2^(d−1) − 27 characters (22,501 at depth 10) → and depth d + 1 is still rejected
  • A grammar allows unbounded depth but never makes the model stop → a model can keep opening objects → output runs to the token cap → set max_tokens/num_predict, or bound the depth in the schema
  • detail that matters JSON in general is recursive, but a non-recursive schema only nests a fixed number of levels → it can be flattened to one regex (Outlines' JSON-Schema-to-regex step) → "needs a PDA" is a property of your schema, not of JSON
  • detail that matters Only tokens whose legality depends on the stack need a runtime check (closing brackets, end-of-text) → an engine can precompute the rest per position (XGrammar: over 99%) → the stack's per-token cost stays small, which the next card measures

5 · Predict commit to an answer before revealing

OpenAI's strict mode caps schemas at 10 levels of nesting (see where it runs). With that cap, recursive JSON becomes a finite language. Can a pure FSM now serve it, and is that a good idea? Commit before revealing.

Reveal

It can: with bounded depth there are finitely many situations, so a finite machine exists. The cap removes the expressiveness limit. It's usually not a good idea, though, because the limit turns into a cost limit: each extra level adds states (21·D − 7 for the link chain in the FSM card), and the calculator's regex doubles per level (22,501 characters at depth 10). A PDA serves every depth with the same small machine. The same reasoning explains why a depth cap is a practical fix for runaway nesting: it makes the language finite and forces the model to close.
