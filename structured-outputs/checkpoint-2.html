Checkpoint 2: what constraining costs and changes

Ties together compile time vs per-token time, why constraining can be faster, does constraining hurt quality? and sampling settings under a grammar, with computing masks fast and token boundaries underneath: where the time goes, and what the grammar does to the answer.

How to use this page. Close the cards. Answer each question in writing before opening its Check, and do the arithmetic yourself; every number you need is in the question or in the paper's GitHub-Medium row (A100, Llama-3.1-8B, llama.cpp backend): GCT / TTFT / TPOT = LM-only none / 0.20 s / 16.68 ms, Guidance 0.01 / 0.54 / 7.57, Llamacpp 0.06 / 0.30 / 29.08, Outlines 8.05 / 8.38 / 46.57.

1 · Mixed retrieval

  1. which concept?A team switched a math-word-problem service to structured output and accuracy dropped sharply. Their schema is {"answer": integer, "explanation": string}, and they also rewrote the prompt when they switched. Which ideas apply, and what do you change first?
    Check
    • field order: the answer is committed before any working is written, and the explanation after it can't change it (0/10 vs 8/10 on the local Last Letter test)
    • put a free, unconstrained reasoning field first
    • the prompt changed along with the format, so the comparison measures the prompt too (the Tam vs dottxt disagreement); rerun with one prompt for both arms

    Missed it? Reopen quality, "Three things that decide the answer" and "Why the studies disagree".

  2. For an 80-token answer on GitHub-Medium with the schema already cached, compute the time per call for Guidance and for Outlines. Which term makes the difference, and why couldn't caching remove it?
    Check
    • Guidance: 0.53 + 79 × 7.57 ms ≈ 1.13 s; Outlines: 0.33 + 79 × 46.57 ms ≈ 4.01 s
    • the difference is TPOT: 46.57 vs 7.57 ms on every token
    • caching removes GCT only; per-token work is paid on every token of every answer

    Missed it? Reopen compile vs per-token, "Compared per engine".

  3. which concept?An extraction service runs at temperature 0.7, top-p 0.9 and presence penalty 1.5, on an engine that applies filters before the mask. Symptoms: totals are sometimes wrong but valid, and occasionally generation stalls just before the final }. Match each setting to its symptom and fix it.
    Check
    • temperature 0.7 samples valid-but-wrong totals: use 0 for extraction (and compute the total in code)
    • top-p before the mask can cut the only valid token (} at 2%): turn top-p off, use min-p, or use an engine that masks first
    • the presence penalty fights keys and layout that must repeat: turn it off (at 1.5 vs 0 the same answer was 38 vs 61 tokens)

    Missed it? Reopen sampling, "Worked example: the only valid token is }" and "Repetition penalty".

  4. Explain how constrained decoding can be faster per token than no grammar at all, and why the M3's 2× speedup was not that effect.
    Check
    • most of a JSON answer is forced (74 of 88 characters of our order); an engine that fast-forwards appends forced spans in one pass
    • fewer model passes: Guidance 6.37 ms vs LM-only 15.40 ms per token on GlaiveAI
    • the M3 used Ollama, which showed no sign of skipping; its 2× came from shorter answers (38 vs 80 tokens: no fences, compact JSON)

    Missed it? Reopen fast-forward, "Your 2× on the M3 is a different effect".

  5. which concept?A report generator writes about 500 tokens per call from a schema that never changes. The team is arguing about Outlines' 8-second compile. What should they be looking at instead?
    Check
    • with a fixed schema, the compile is paid once and cached, so GCT is irrelevant
    • at 500 tokens, TPOT dominates: the cached ratio heads toward the TPOT ratio, 46.57 / 7.57 ≈ 6.2×
    • so pick the engine with the lowest per-token cost, ideally one that fast-forwards, and shorten the output

    Missed it? Reopen compile vs per-token, "So is Outlines' 8 seconds a real cost?".

  6. Guidance beat the other engines on all three of the paper's quality tasks, by 3.3–3.7 points over prompt-only. What does the paper guess the reason is, what would test the guess, and what else could explain it?
    Check
    • the paper's guess ("we believe"): token healing, which avoids forced awkward splits at the prompt boundary
    • test: the same engine with healing on and off, same prompts and tasks
    • alternatives: differences in whitespace and field-order handling, and run noise (no error bars; no engine won every instance)

    Missed it? Reopen token boundaries, "Token healing", and quality, the Table 8 worked example.

  7. Two schemas run on an engine that fast-forwards: a 12-field config object with enum values, and a single free-text notes field. Which one gets the bigger drop in TPOT, and does end-to-end time drop by the same factor?
    Check
    • the config object: keys, quotes and most of each enum value are forced; the notes field is almost all chosen text
    • no: TPOT divides by all output tokens, including skipped ones that cost almost nothing, so it drops faster than the real time
    • compare end-to-end time for the real schema

    Missed it? Reopen fast-forward, "The mechanism as a formula" and "Will my structured calls get 2× faster?".

3 · Project: size a serving setup for two workloads

What it reinforces: the three-term time model (compile vs per-token), skipping (fast-forward), field order (quality) and decoding settings (sampling), all in one design.

The workloads. A: the fixed store-order schema, 10,000 requests a day, 80-token answers. B: a new flat schema per request, built from a CSV header, 40-token answers. Use the GitHub-Medium numbers in the box at the top (paper, A100, Llama-3.1-8B), with per call = GCT/k + (TTFT − GCT) + (n − 1) × TPOT.

  1. Time. For each of the four rows, compute the time per call for A (k = 10,000) and B (k = 1), and the machine-hours per day for A.
  2. Pass rate. Time per call isn't time per valid object. Empirical coverage on GitHub-Medium was LM-only 0.38, Guidance 0.69, Llamacpp 0.57, Outlines 0.29 (paper, Llama-3.2-1B). Divide each A time by its coverage, as in the overview's formula, and see whether the ranking changes.
  3. Skipping. Using the fast-forward formula and our order (35 tokens, about 26 forced, 7 spans), estimate the TPOT ratio an engine that skips should reach, and check it against Guidance's measured ratio on GlaiveAI.
  4. Decoding and schema. Write the sampling settings and the field order for A (pure extraction) and for a variant of A that adds a free-text gift_note.
  5. Decide. Pick an engine for each workload and name the one measurement you'd take on your own hardware before committing.
Done when: you have a 4 × 3 table (A per call, A hours per day, B per call), a time per valid object for each row, a skipping estimate next to the paper's ratio, a settings block per variant, and one engine per workload with a reason and a measurement. Then compare with the check.
Check: the numbers (paper medians; our arithmetic)
  • A per call / hours per day: LM-only 1.52 s / 4.2 h, Guidance 1.13 s / 3.1 h, Llamacpp 2.54 s / 7.0 h, Outlines 4.01 s / 11.1 h (compile amortised to nothing).
  • B per call: LM-only 0.85 s, Guidance 0.84 s, Llamacpp 1.43 s, Outlines 10.20 s: the 8.05 s compile is paid every time.
  • Per valid object: LM-only 1.52 ÷ 0.38 ≈ 4.0 s, Guidance 1.13 ÷ 0.69 ≈ 1.6 s, Llamacpp 2.54 ÷ 0.57 ≈ 4.5 s, Outlines 4.01 ÷ 0.29 ≈ 13.8 s. Guidance stays first; LM-only moves ahead of Llamacpp. Treat this as a rough guide: it mixes the 1B coverage run with the 8B timing run, and uses a per-schema share as if it were a per-attempt pass rate.
  • Skipping estimate: (35 − 26 + 7) / 35 ≈ 0.46; Guidance measured 6.37 / 15.40 ≈ 0.41 on GlaiveAI. Same range, by different routes.
  • Settings: A at temperature 0, penalties off, top-p/top-k off (or min-p), total computed in code. The gift-note variant: keep extraction fields first, the note unconstrained, and either a second call for the note at 0.2–0.7 or accept one compromise temperature.
  • Choice: Guidance/llguidance for both on these numbers (lowest TPOT, near-zero compile); for A, an XGrammar engine is also reasonable, since compile is amortised. Measure: time per call for a fresh and a cached schema on your own engine and model; the paper's numbers are one A100 at batch size 1.
