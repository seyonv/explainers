Why asking for JSON isn't enough

Also called prompt-only JSON, unconstrained generation, or LM-only (the paper's baseline). Often confused with "JSON mode". The cookbook's store chatbot "breaks for 20%" of production messages this way; the paper's LM-only baseline covers 0.90 of easy schemas but only 0.13 of hard ones.

In one breath. A language model writes one token at a time, picking what is likely to come next. Chat training made "Sure! Here is…" and ```json fences likely. Nothing in that choice knows your code will call json.loads on the result, so a polite instruction lowers the failure rate but never removes it.

"JSON mode" guarantees syntax, not your schema. OpenAI: "While both ensure valid JSON is produced, only Structured Outputs ensure schema adherence." Our 10/10 schema-valid is this easy schema, not a guarantee. JSON mode still got 5/10 values right.

Why it beats the alternatives

✗ Just ask nicely in the prompt

Our prompt already said "Output only the valid JSON." and 23 of 30 replies still came in fences. Instructions shift the probabilities; they cannot set any of them to zero.

✗ Use a bigger model

Bigger and JSON-tuned models help on easy schemas, and cost more time and money per call. We have no number for how far size alone closes the gap: the paper's coverage study uses only a 1B model for LM-only.

✗ Regex the answer out afterwards

Honestly, it worked well here: cleaning took us from 7/30 to 30/30 parsed and 29/30 valid. But it only strips wrappers. It could not turn run 8's bare array into an order, and it can't add a missing total_usd.

✓ Constrained decoding

Mask every token that would break the schema, so the parser's rules are part of sampling. Same model and prompt: 30/30 parsed raw, 30/30 schema-valid, no cleaning code, and shorter replies (38 vs 80 tokens).

So is prompt-only JSON always broken?

No. Modern instruct models are often fine on easy schemas: ours got the shape right 29 times in 30 once the fences were stripped, and the paper's LM-only covers 0.90 of GlaiveAI's function-call schemas. The failure rate grows with schema difficulty: nesting, enums, minItems, many required fields (0.13 on GitHub-Hard). Prompt-only is still the right call when you use a hosted API without schema support, when you need a keyword the engine doesn't support, or when a library like Instructor or BAML already wraps it in a parse-and-retry loop (see the repair loop).

The trap is the cleaning code. It makes the success rate look high by quietly fixing wrappers, so your logs never show that 77% of raw replies failed. It also hides the wrong-shape cases until a missing field crashes something further down. Cleaning hides problems; only a grammar rules them out, and even a grammar only guarantees the shape: 22/30 constrained answers had the right values, not 30.

Inferred, not stated by a source: that the fences come from chat training data. The cookbook says this about the "Sure!" preamble; we assume the same cause for fences.
