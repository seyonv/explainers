Compile time vs per-token time

Also called grammar compilation time (GCT), time to first token (TTFT), time per output token (TPOT), or mask overhead. The paper's efficiency section (§4, Tables 2, 3 and 13) measures all three on one A100 with Llama-3.1-8B-Instruct (Q8, 128K vocabulary), batch size 1, medians.

In one breath. A grammar engine can spend its time in two places. It can do the work up front, turning your schema into a ready-made lookup table before the first token (compile time). Or it can do the work at every token, working out the allowed next tokens as it goes (per-token time). Up-front work is paid once per schema. Per-token work is paid on every token of every answer.

The three costs, in plain words

Think of a translator given a style guide. Compile is reading the whole guide before starting. Prefill is reading your letter. Per token is checking the guide before writing each word. A translator who memorises the guide is slow to start and quick after that. One who looks things up as they go starts at once, but every lookup adds to each word.

The paper's Outlines TTFT is always GCT plus a few tenths of a second (8.38 = 8.05 + 0.33), so we read its TTFT as already including compile and don't add GCT twice. That's our inference; the paper doesn't say it directly. Figures computed with a short Python script.

Amortisation: the same schema, k calls

average per call = GCT / k + t_prefill + 79 × TPOT (Outlines, GitHub-Medium) k = 1: 8.05 / 1 + 0.33 + 3.68 = 12.06 s k = 10: 8.05 / 10 + 0.33 + 3.68 = 4.81 s k = 100: 8.05 / 100 + 0.33 + 3.68 = 4.09 s Guidance, any k: 1.13–1.14 s

The cookbook: constrained decoding can add "milliseconds to seconds" to TTFT, a "one-time cost" per schema that is "amortized when you use the same schema across many generations", and it only matters "when you generate dynamic schemas on-the-fly". The paper couldn't show this, because every one of its schemas was unique.

Why it beats the alternatives

✗ Precompile everything

Outlines builds the whole FSM first, so each step is a lookup. But it pays 8.05 s (GitHub-Medium) to 12.77 s (GitHub-Hard) for every new schema, and its TPOT was still 46.57–81.22 ms.

✗ Compute everything per token, naively

Llamacpp compiles in 0.05–0.06 s but works out each mask as it goes: 29.08 ms per token vs 16.68 ms with no grammar, +74% on every token of every answer.

✗ No constraint, then retry

No compile and no mask cost, but LM only was schema-compliant on just 38% of GitHub-Medium (paper, Llama-3.2-1B). Every retry repeats the whole 1.52 s call.

✓ Hybrid work plus a grammar cache

Precompute only what doesn't depend on context (XGrammar: over 99% of tokens, overlapped with prefill) or compute lazily with a trie and a lexer (llguidance). Then compile once per schema and reuse it. Guidance on GitHub-Medium: 1.14 s for 80 tokens, faster than no grammar at all (1.52 s).

So is Outlines' 8 seconds a real cost?

Only when schemas change. The paper says grammar caching "does not offer any benefits" in its benchmark, because every schema in the dataset is unique. In production with one fixed schema, like the order schema, you pay GCT once, on the first call, and the cache serves the rest. What caching can't fix is TPOT: cached Outlines still takes 4.01 s for 80 tokens vs 1.14 s for Guidance. For long answers, per-token time decides the bill.

Compile time does matter when a schema is built per request: a schema made from a user's CSV headers, a per-tenant form, or tool definitions that change each turn. There the cookbook recommends an engine with no precompute (llguidance), or prompting with no constraint. These are January 2025 versions at batch size 1 with a 128K vocabulary. Speeds depend on the model, the vocabulary size and the backend, so time your own setup.
