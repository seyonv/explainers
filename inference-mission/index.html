The mission · LLM inference

The chat benchmark picks the wrong vLLM config for coding agents

Show that a chat benchmark picks the wrong vLLM config for coding-agent traffic, and measure how much goodput stock flags recover on one GPU. This page is the finished result, written as the post you'll make at the end. Every day of the path fills in one rung.

Why this is worth posting

The benchmark everyone runs is the wrong workload

vllm bench serve replays the first turn of ShareGPT conversations, and 0.9% of those prompt blocks ever repeat. Real coding-agent sessions resend most of their context every turn: the providers served 95.7% of TraceLab's prompt tokens from cache. A config tuned on one can lose on the other.

A rank flip is a finding people can act on

If the config that wins on ShareGPT ranks low on agent traffic, every team choosing flags from the standard benchmark is choosing wrong. The slope chart shows it in one picture.

No custom scheduler, just flags

Systems built for agent traffic change the engine itself: Continuum keeps a session's KV cache alive through tool calls, and KVFlow replaces LRU eviction with a workflow-aware policy. This asks how much you get from flags vLLM already ships, on one GPU, today.

Every number is reproducible

The trace is public (CC BY 4.0), the slice is seeded, the SLO (TTFT ≤ 2 s, TPOT ≤ 50 ms) is fixed before any run, and every config is one command line.

What makes the comparison fair

  • Same GPU, model (Qwen3-8B), vLLM version, trace slice, seed and arrival schedule for every config.
  • The SLO is fixed before any run: time to first token ≤ 2000 ms and time per output token ≤ 50 ms. Goodput counts only requests that meet both.
  • TraceLab prompts are longer than the 40,960-token context vLLM gives Qwen3-8B by default (max_position_embeddings in its config.json; the model card quotes 32,768 native) (only 10.7% fit), so every token count is divided by 8, each session's prefix reuse is kept, and anything still too long is dropped (92.8% of requests fit at ÷8). Time inside each session also runs 10× faster (every gap × 0.1) so tool calls and user pauses fit in 30 minutes; shorter pauses mean less time for the KV cache to be evicted between turns, which flatters every config. The post states both.
  • TraceLab has no prompt text, so the replay's prompts are synthetic token blocks with the trace's sharing pattern; ShareGPT prompts are real text. Report each config's preemptions and prefix-cache hit rate on the agent run next to its goodput: --rank reads them from the logs/ the GPU scripts save.

Measure the gap yourself: download the trace (54 MB) and the chat benchmark file (673 MB), then compare their prompt reuse. No GPU, no account.

What could go wrong, and the fallback

  • Eviction is rare at ÷8, so every config looks the same. Raise the load (--sessions) or lower the divisor (--scale 4) until stock vLLM misses the SLO on some requests. A workload with no pressure can't separate configs.
  • Every config meets the SLO on ShareGPT. At a light load the chat benchmark can't separate configs, and a near-tie decides its winner. --rank warns when configs land within 2% of the winner; rerun ShareGPT with a higher --commands --rate until stock misses the SLO on some requests. The agent side is capped by its offered 2.20 requests per second the same way.
  • No rank flip. Then the post says the standard benchmark picks well here, with the τ between the two rankings. The goodput-per-dollar table still ranks the flags.
  • The synthetic prompts behave differently from real text. Speculation (n-gram) depends on real repetition in text, so treat Day 7's n-gram result on the agent slice as a lower bound and say so.

What would make this wrong
  • An SLO chosen after seeing the results. Fix it first; the lab prints it in every command.
  • Configs run at different times on different machines. Same GPU type, same vLLM version, same slice and seed.
  • Synthetic prompts read as real ones. The agent slice keeps the trace's sharing pattern but not its text; say so, especially for n-gram speculation.
  • The ÷8 length scaling left out. It changes the workload; state it, and show one config at ÷4 if you can afford it.
